### 2026-04-17 — Stage 3 triage outcome

Agent traced the 1541 CPU firmware's wait-loop to `0x1000_09A4..=0x1000_09B0` and dumped its working registers. Key finding: **the 1541 fixture's CPU firmware reads CS from GPIO0**, not GPIO13. Register state at case entry: `R4=SIO_GPIO_IN, R8=R9=0x00000001` → wait loop only exits when bit 0 of `LDRH R0,[R4]` is high.

Our harness drives CS via `GPIO_CS1=13` (set high for gap, low for stim). GPIO0 is only incidentally high in the stim pattern when `addr_bits & 0x80 != 0` (because `ADDR_PINS[7] = 0`). Empirically:

```
bit7=1 (GPIO0 high during stim): pass=140, fail=884
bit7=0 (GPIO0 low during stim):  pass=0,   fail=1021
```

Zero passes when GPIO0 is low, confirming the firmware uses GPIO0 as its select.

Root cause is firmware-specific pin configuration baked into the 1541 CPU-mode metadata. The fix belongs in `CpuServingOracle` (parameterise over a `PinProfile` read from fixture metadata), which is out of scope — would risk regressing the 15-case CPU oracle the wave is explicitly not allowed to destabilise.

**Resolution**: land the stress CPU binary as-is with an explicit `Known limitation` header comment pointing at the library constraint, log tech_debt entry, and document as a latent regression target that will flip to 2048/2048 once the pin-profile parameterisation lands. Proceed to Stage 4.

### 2026-04-17 — Stage 4 devil's-advocate

Independent reviewer raised three substantive concerns:

1. **PIO latency "distribution" is misleading.** Only 5 unique cycle values across 2048 cases — `p95=p99=240 ns` isn't a tail, it's "the higher of two steady-state buckets". Reader could misquote "226±14 ns" as calibrated timing. **Applied:** added `unique_cycles` field to `Histogram`, surfaced in report as `unique cycle values: N`, with a warning note when N ≤ 3. New TDD test covers the three shape cases (all-same, step, continuous). Post-fix PIO run shows `unique cycle values: 5` — still narrow but honestly reported.

2. **CPU 140 passes are a double-coincidence, not real coverage.** Every "pass" requires both (a) stim pattern setting GPIO0 high AND (b) expected shadow byte = 0x00. No case currently verifies actual serve-path byte delivery. **Applied:** expanded both the CPU binary's header comment and the tech_debt entry to call this out explicitly — pass count should be read as "0 of 2048 cases are real serve-path verifications" until the pin-profile fix lands.

3. **Is the CPU diagnosis complete?** Reviewer questioned whether tripwire/envelope/timeout might also contribute. After their own instrumentation, rejected — pin-map mismatch is the single factor.
