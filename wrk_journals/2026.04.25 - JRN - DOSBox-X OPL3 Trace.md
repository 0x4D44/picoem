### Code review (separate agent)

Verdict: **APPROVE-WITH-NITS**. Highlights:
- ODR clean (one definition, one extern decl). No symbol collisions across the tree.
- Recursion safe: `Module::PortRead` is a flat switch; Adlib installs handlers
  with `IO_MB` only, so 16-bit guest accesses fall through `IO_ReadSlowPath`
  upstream — they never reach `OPL_Read`. The kept `iolen == 2` ternary is
  defensive dead code, mirrors the GUS hook style.
- CSV format byte-compatible: `# picogus-tap v1` header, `ns,port,value,kind`
  rows with port `0x%03x`, kinds in `{read8,read16,write8,write16}`. Parser at
  `picogus_diff_rp2040.rs:148-155` already accepts all four.
- Read-value enrichment (OPL logs actual byte; GUS logs `0`) is harmless —
  the parser only reads the value field for write events.
- Two pre-existing nits in the patch (NOT introduced by Phase D, but visible
  in the refreshed diff): five `[DIAG]` `fprintf(stderr, ...)` blocks left
  over from prior PicoGUS-callout debugging, and a `#if 0 → #if 1` flip +
  uncommenting of `IO_ReadHandleObject ReadHandler[12]`. The diag prints
  pollute stderr but don't break anything (trace goes to its own file). Out
  of scope for this phase; flagged for future cleanup.

Patch is good. Real blocker is the build environment.

### Capture result

- M1 distribution turned out to be SCUMM v4 with no SETUP utility — sound
  card is picked at the command line via `MONKEY a` (= Adlib). No config-file
  reverse-engineering needed.
- DOSBox-X 2026.03.29 + the patched OPL3 tap booted M1 cleanly with
  `cycles=fixed 8000`, GUS disabled, OPL3 enabled.
- Capture file: `crates\mdpicoem-harness\fixtures\monkey_island_adlib.trace`,
  874,700 bytes, **29,172 write8 events** spanning ns 1,540,665,000 →
  49,407,*** (~47.87 s of title-screen music). Port histogram is exactly
  14,586 × 0x388 and 14,586 × 0x389 — the perfect register-select/data 1:1
  balance you'd expect from a clean OPL2 driver. Zero rows on GUS ports
  (0x24x), zero on the OPL3 upper bank (0x38a/0x38b) — M1's driver is
  OPL2-only, but slot 5 (SB-DBOPL3) is OPL3 which is backward-compatible
  with OPL2 register layout.
- First 10 rows match the canonical OPL init dance: `0x01 ← 0x00`
  (waveform-select unlock for OPL2; OPL3 ignores), `0xbd ← 0x00` (rhythm-off),
  `0x08 ← 0x00` (CSW + NoteSel = 0), `0x01 ← 0x20` (real waveform-select
  unlock). Then the first carrier setup at `0xa0`.
- One pre-existing zombie `dosbox-x.exe` from 22:28 was on the host before
  the agent started; none of the agent's own launches left zombies. Out of
  scope.

## Session 6 — Replay through picogus_diff_rp2040

Now we have the trace, the slot-5 firmware path is the same as the Phase
B/C synthetic pipeline. Dispatching replay agent to:
1. Build `picogus_diff_rp2040` (release).
2. Run with `--firmware-mode 5 --trace <m1_adlib.trace> --output <wav path>`
   and a long-enough `--seconds` to cover the full 47.87 s of trace.
3. FFT-analyse the resulting WAV.
4. Cake gate: peak ≥ −20 dBFS, FFT shows multiple distinct peaks (not flat
   noise / not silence), output duration matches trace duration.
5. Listen-test request: leave the WAV at a fixed path so Arthur can play it.

### Replay result (and the long wait)

The replay ran for 57 minutes wall-clock (started 22:52:46, finished 23:49:00).
That's 70× slowdown vs. real-time — much more than the 5–10 min the agent
predicted. RP2040 emulator running OPL3 in serial mode just isn't fast.
I burned several /loop wakeups checking on a healthy-but-slow process. Note
for next time: when picogus_diff_rp2040 is asked to render >10 s of OPL3,
budget an hour and don't poll.
