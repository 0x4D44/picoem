# 2026.04.25 — JRN — FM Pivot

After two days of GUS investigation hitting a per-voice-machinery
wall (see `2026.04.24 - JRN - Single-voice dump and FM trace.md`
session 19), pivoting to FM (OPL3) as the path to producing
recognisable PicoGUS audio out of mdrp2040.

## Plan

| # | Phase | Goal | Owner |
|---|-------|------|-------|
| A | Build OPL3-capable PicoGUS firmware | `PROJECT_TYPE=SB` + `USE_YMFM_OPL=1`. Output: `pg-sb-opl3.bin` | agent |
| B | Hand-craft a minimal FM trace (~1 s tone) | Rust binary `fm_trace_gen` under `mdpicoem-harness` | agent |
| C | Replay hand-crafted trace, listen | If tone audible → FM pipeline alive; iterate to a known melody | agent |
| D | (Later) Extend DOSBox-X patch to `adlib.cpp` | For real game capture; only if A–C succeed | deferred |
| E | (Later) Pick DOS test program + capture | After D | deferred |

Cake gate revised: peak ≥ −20 dBFS (samples > 3,277), recognisable
tone or melody on playback. Anything below that is "made noise but
not music" and we treat as failure (lesson from session 18).

## Why this ordering

OPL3 protocol is documented and small (register select 0x388, data
0x389; ~30 lines to set up an operator + key-on). Hand-crafting a
trace bypasses DOSBox-X plumbing entirely for first validation,
which is half a day of yak-shaving we don't need until we know the
firmware pipeline works.

DOSBox-X source isn't checked out locally; the existing patch at
`third_party/dosbox-x-picogus-tap.patch` only hooks `gus.cpp`, so
even if we cloned + applied it, OPL ports wouldn't be captured.
Patch extension is real work — defer until A/B/C prove FM is alive.

## Open scoping notes

- Firmware: PicoGUS source under `third_party/picogus/upstream/sw/`.
  CMakeLists.txt selects backend via `USE_YMFM_OPL` (OPL3) /
  `USE_YMF3812` (OPL2) / `USE_DBOPL_OPL`. Default for `PROJECT_TYPE=SB`
  is emu8950 (OPL2). We want OPL3 (more common in DOS games).
- Replay harness `picogus_diff_rp2040` is port-agnostic — drives
  whatever port appears in the trace through PIO0 SM0.
- Firmware ISA analyser already filters 0x388–0x38B per agent
  research, so the wiring is plausible.
- Risk: if firmware ISA decode doesn't actually route OPL ports
  to the synth backend, B/C will silently fail. Need to confirm
  in firmware source before assuming pipeline works.

### Session 15 — Root cause: RESETS gate drops our write

Crystal-clear instrumentation result:

```
[diag scratch3] post-reset:       0x00000000
[diag scratch3] post-poke:        0x00000000  ← our write dropped
[diag scratch3] post-boot-setup:  0x00000000  (RESETS=0x01ffffff)
[diag scratch3] post-warmup:      0x00000000  (RESETS=0x00000000)
[diag scratch3] post-pre-roll:    0x00000000
```

After `Emulator::reset()`, `bus.resets.reset()` re-asserts
`RESET_MASK = 0x01FF_FFFF`, which holds every peripheral
(including watchdog at bit 24) in reset. `Bus::peripheral_write32`
calls `is_held_in_reset(WATCHDOG_BASE)` and **silently drops the
write** at `crates/mdrp2040/src/bus/mod.rs:753-755`. By the time
pico-sdk's `runtime_init` releases the RESETS bits (post-warmup),
our write is long gone.

The 12/12 watchdog unit tests passed because they call
`WatchdogTickRegs::write32` directly — bypassing the bus-level
reset gate.

**Fix**: write directly to the field
`emu.bus.watchdog_tick.scratch[3] = slot;`. Field is already
`pub`. One-line change. No need to simulate RESETS gating for a
debug test fixture.

Spawning agent to: apply the fix, keep the diagnostic
instrumentation in place to confirm scratch[3] now persists,
re-run mode 5, report.

### Session 18 — Octave bug is in WAV sample-rate stamping

Agent walked through the entire chain:

1. **`fm_trace_gen` output**: A0=0x44, B0=0x32 — exactly what
   OPL3 spec dictates for 440 Hz at BLOCK=4. Decode: F-num=580,
   BLOCK=4, predicted f = 580 × 49716 / 2^16 = **440.00 Hz**.
2. **DBOPL3 formula** (`third_party/picogus/upstream/sw/opl/dbopl/
   dbopl.cpp:350-356`): standard OPL3, `(freq << block) ×
   freqMul / 2^WAVE_SH`. With our values + freqMul[MULT=1]=4096 +
   WAVE_SH=22 + sample rate 49716 → **440.0 Hz**. Correct.
3. **WAV header sample rate**: stamped via
   `inferred_sample_rate_hz()` in
   `crates/mdpicoem-devices/src/i2s_capture.rs:323-333`. That
   formula assumes 2 LRCLK edges per stereo frame. If firmware
   emits 1 frame per edge, WAV is stamped at **half** the true
   rate — and any FFT applied with that header rate reports
   frequencies at **2× the true value**.

Smoking gun: 872.88 Hz / 440 Hz = 1.984. Two bin widths shy of
exactly 880 Hz, which is FFT resolution noise. The audio is
**actually 440 Hz** — we're just stamping the WAV with the wrong
rate.

Implications if true:
- `fm_trace_gen` is correct; don't touch it.
- DBOPL3 is correct; don't touch it.
- The audio pipeline really works.
- This same bug affected the GUS Apr 24 final iteration — the
  "rumbling" left-channel signal might have been correct audio
  played back at half-speed.

Spawning a verification agent to confirm the hypothesis by
inspecting the I2S LRCLK toggle pattern directly.

### Session 19 — Sample-rate hypothesis refuted

WAV-rate inference checks out: 43,755 Hz inferred vs 44,100 Hz
configured in `audio_i2s_minimal_setup(&config, 44100)` —
0.84 % discrepancy explained by the clkdiv quantisation
(370 MHz / 131 / 64 = 44,124 Hz). LRCLK edges = 2× frame count
exactly (220,064 / 110,031 = 2.0004), so no edge-doubling.

### Session 21 — DBOPL3 internals: 440 Hz expected per its own code

Deep dive landed: DBOPL3 itself computes **440.0 Hz exactly** for
our inputs.

Key constants found:
- `Setup(rate)` ignores its argument; "force 49716 Hz rendering,
  just like real OPL3 would" (`dbopl.cpp:1275`).
- `WAVE_SH = 22`, `scale = 1`, `freqScale = 2^11 = 2048`,
  `freqMul[MULT=1] = 2048 × FreqCreateTable[1] = 2048 × 2 = 4096`.
- `waveAdd = (580 << 4) × 4096 = 38,010,880`.
- `samples_per_period = 2^32 / 38,010,880 ≈ 113.0`.
- Output = 49716 / 113.0 = **440.0 Hz**.

So DBOPL3 *should* produce 440 Hz. Our measurement is 880 Hz.

The 2× error is downstream of DBOPL3's frequency math.
Candidates from the deep dive:
- MULT effectively becoming 2 due to operator-slot routing
  (4-op mode active? OPL3 array1 confusion?)
- Resampler pumping twice per output sample
- WriteB0's chanData bit packing differing from spec
- Sample loop reading DBOPL output at 2× rate

### Session 22 — Empirical: consistent 2× shift across frequencies

220 Hz request → 436.01 Hz output (FFT bin spacing 2 Hz, so this
is essentially 440 Hz). Combined with the earlier 440 → 880,
this is a uniform 2× shift independent of frequency.

WriteB0 bit-packing audit confirmed dbopl3 correctly reads FNUM
from chanData[9:0] and BLOCK from chanData[12:10]. So the
problem isn't in dbopl3's register decode — it's in the formula
that converts FNUM/BLOCK into output frequency.

Empirical formula (working backwards from observation):
- FNUM=580, BLOCK=4 → 880 Hz
- 880 / 580 = 1.517
- 1.517 = 49716 / 2^15 → 2^(19-BLOCK) when BLOCK=4

So DBOPL3 effectively uses **`f = FNUM × 49716 / 2^(19-BLOCK)`**
not the textbook `2^(20-BLOCK)`. There's a missing factor of 2
somewhere — most likely in `scale` or `WAVE_SH` that the
session-21 deep dive misread.
