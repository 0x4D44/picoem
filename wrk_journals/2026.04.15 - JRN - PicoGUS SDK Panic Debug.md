## Goal

Identify and fix the root cause of the `hard_assertion_failure("Hard
assert", 1)` taken by real PicoGUS v4.0.0 firmware at cycle ~1.35 M
when booted via `picogus_diff_rp2040 --flash <real-fw>` with the
vendored B2 bootrom + `direct_boot_from_flash` shortcut. Acceptance:
firmware progresses past cycle 1.35 M, and ideally produces I2S audio
in the captured WAV.

## Phase 0 — Research

**Status: complete.** Research agent `ae927b963727dd0e9` dispatched
with "map every `hw_claim_or_assert` call site that can fire before
`main()`, identify suspect peripheral registers, rank likelihood".

### Finding (supervisor summary)

The peripheral-register hypothesis was **wrong**. The panic is not
about a stub returning the wrong value for a claim-bit. It is about
an uninitialised `SCB.VTOR`.

**Root cause:** `Emulator::direct_boot_from_flash`
(`crates/mdrp2040/src/lib.rs:184-195`) sets SP/PC on both cores but
never writes `VTOR`. On real silicon, the boot2 stage 2 routine
`exit_from_boot2` writes `VTOR = 0x10000100` immediately before
branching into the SDK's `_reset_handler` (source: pico-sdk 2.1.1
`src/rp2040/boot_stage2/asminclude/boot2_helpers/exit_from_boot2.S`).

The downstream effect: pico-sdk 2.1.1's
`runtime_init_install_ram_vector_table` (in
`pico_runtime_init/runtime_init.c:199–217`) does
`memcpy(ram_vector_table, (uint32_t *) scb_hw->vtor, 192)`. With
`vtor=0` (reset value from `Ppb::new()`), the memcpy copies from
bootrom base `0x00000000` — the raw B2 bootrom binary — instead of
the flash-resident vector table. Vtable slot 17 (=
`VTABLE_FIRST_IRQ + 1` = `IRQ[1]`) then contains bootrom Thumb
bytes, not `__unhandled_user_irq`.

Shortly after, the firmware calls `irq_add_shared_handler(1, ...)`.
In `hardware_irq/irq.c:362-394`, that function takes
`PICO_SPINLOCK_ID_IRQ`, loads `get_vtable()[VTABLE_FIRST_IRQ + num]`
(which decodes as `LDR R3, [array + (r0+0x10)<<2]` — exactly what
Arthur's journal captured from the panic disassembly), then does
`hard_assert(vtable_handler == __unhandled_user_irq)`. Vtable slot
holds bootrom garbage → assert fails → `hard_assertion_failure()` →
`panic("Hard assert")`.

The `r0=1` in the journal's panic format args is **not** `alarm 1`
— it is the `num` parameter to `irq_add_shared_handler`, i.e. the
IRQ number being registered (most likely `TIMER_IRQ_1`, which the
SDK wires for its alarm-pool when `hardware_alarm_claim_unused` is
called). That explains why the journal's working hypothesis
("alarm 1 claim-bit") kept not matching any of our emulator stubs.

### Supporting evidence (agent-verified)

- `direct_boot_from_flash` confirmed at `lib.rs:184-195` — only SP,
  PC, halt core 1.
- `Ppb::new()` at `bus/ppb.rs:59` sets `vtor: 0`. VTOR RW handler
  present at `ppb.rs:126`/`160`.
- `Bus.ppb: [Ppb; 2]` at `bus/mod.rs:122` — **per-core PPB**. Fix
  must set `bus.ppb[0].vtor` AND `bus.ppb[1].vtor` so that either
  core observes the correct value when it runs `runtime_init`.
- Real PicoGUS firmware boots past cycle 1.35 M on real silicon
  (obviously — it's shipped firmware). Our `i2s_chime` smoke works
  because it never calls into pico-sdk runtime init, so it never
  reaches `irq_add_shared_handler` or reads VTOR.

### Confidence

Agent reports ≈95 %. Supervisor concurs — the call-chain pattern
the agent pulled from pico-sdk source
(`(r0+0x10)<<2` LDR inside a spinlock, compared to a magic
constant) is a **1:1 match** for the journal's captured disassembly.
Three independent pieces line up: pico-sdk source, our missing VTOR
write, our bootrom base containing non-`__unhandled_user_irq` bytes
at slot 17.

### Decision

Skip originally-planned "Phase 1 empirical confirmation" — fix blind
in Phase 1 (was Phase 2). Two-line change + smoke test is cheaper
than instrumenting a stack-walker, and the confidence is high enough
that a failed fix would still teach us something actionable.

### 2026-04-15 afternoon — empirical smoke after mdrp2350 build cleared

mdrp2350 build break cleared; harness rebuilt clean (0 warnings).
Chime smoke test still passes. Ran the real-firmware smoke:

```
direct-boot skipped: flash+0x100 has SP=0x20042000 PC=0x100001f7 (not an SDK vector table) — booting via bootrom reset vector
```

**First discovery**: the direct-boot heuristic I committed earlier
(commit f429122) uses an EXCLUSIVE-top range `0x2000_0000..0x2004_2000`
that rejects the canonical top-of-SRAM SP = `0x2004_2000`. Fixed in
`picogus_diff_rp2040.rs:841` to use `..=0x2004_2000` (inclusive
top); the fix belongs to the VTOR-debug commit cluster, not its own
commit yet (staged in working tree).

With direct-boot firing, re-ran:
```
direct-boot: SP=0x20042000 PC=0x100001f6 (flash+0x100)
warning: emulator stalled at cycle 42569 — subsequent events fire at the stall cycle
```

**Second discovery**: firmware stalls at cycle 42569 (= step 21501
instructions). The OLD-baseline cycle count of ~1.35 M was probably
post-panic loop cycles; the actual pre-panic instruction count
matches today (21,500). So the VTOR fix did **not** bypass the
panic.

Probe with ring-buffer BL tracing shows the full call chain:
```
step=20989  0x200007f0 -> 0x20000364  (caller -> checker)
step=21009  0x2000038e -> 0x20000db8  (checker -> hard_assertion_failure)
step=21012  0x20000dbc -> 0x20000274  (hard_assertion_failure -> panic)
... formatting ...
step=21500  0x20000298 -> 0x200035ac  (panic -> BKPT)
```

Disassembly of the checker at SRAM 0x20000364 matches pico-sdk's
`irq_set_exclusive_handler` exactly:
```
push {r4, r5, r6, lr}
r5 = r1                  // handler being registered
cpsid i; spin_lock(SIO+0x124)
r3 = *(0xe000ed00 + 8)   // r3 = *(SCB.VTOR) = current vector table base
r4 = (r0 + 0x10) * 4     // vtable offset for IRQ num
r3 = vtable[r4]          // existing handler slot
r2 = 0x100001cd          // __unhandled_user_irq magic
if r3 == r2: OK (slot free)
if r5 == r3: OK (same handler already installed)
else: bl hard_assertion_failure    // PANIC
```

The "magic constant" is `0x100001cd` — which IS what the real flash
vector table has at every IRQ slot (verified by dumping flash bytes
at offset 0x140..0x1c0). So if `scb_hw->vtor` reads a valid value
pointing at the flash vector table, the check passes.

**Third discovery** (and the actual root cause): the ring-buffer
trace reports `vtor=0x00000000` at EVERY logged step. My VTOR fix
*did* write `bus.ppb[0].vtor = 0x10000100`, but the memory-mapped
read of `0xe000_ed08` still returns 0.

Why: `crates/mdrp2040/src/bus/ppb.rs` has a broken mask + pattern
pair:

```rust
pub fn read32(&self, addr: u32) -> u32 {
    match addr & 0x0FFF_FFFF {
        0x000E_D000 => 0x410C_C601, // CPUID
        0x000E_D004 => self.icsr,
        0x000E_D008 => self.vtor,    // ← never matches
        ...
```

For `addr = 0xE000_ED08`, `addr & 0x0FFF_FFFF = 0x0000_ED08`, but
the match pattern is `0x000E_D008 = 0x000ED008`, off by one hex
digit. None of the PPB SCB registers match their patterns; every
read falls through to `_ => 0` and every write is a no-op.

mdrp2350's equivalent (`crates/mdrp2350/src/bus/ppb.rs:173,208`)
uses `match addr & 0xFFFF { 0xED08 => self.vtor, ... }` — the
correct idiom. Its unit tests even round-trip VTOR through the
memory-mapped path (`test_vtor_roundtrip`).

**Why the existing mdrp2040 smoke tests didn't catch this**: every
VTOR test in `crates/mdrp2040/src/tests.rs` (line 1394 and
exception tests) sets `bus.ppb[0].vtor` directly, bypassing
`read32` / `write32`. The field-assignment path is bug-free;
only the memory-mapped path is broken. And no existing test
exercises `bus.read32(0xE000_ED08)`.

### Conclusion: Phase 1 VTOR write is necessary but NOT sufficient

The VTOR fix writes the correct value into the field, but the
memory-mapped read by the SDK's `get_vtable()` can't see it due to
the ppb.rs mask-pattern bug. Phase 2 (next) fixes ppb.rs.

## Phase 3 — Diagnose new stall at cycle 43929

**Status: complete.** Research agent
(`ab2836f69d69411a2`) ran `picogus_probe_pc`, captured
exception-entry PC + SRAM dump + ring-buffer BL trace + capstone
disassembly of the faulting SRAM code.

### Finding

Firmware now reaches **gcc's `_vfprintf` format-char switch-jump
table**. Execution is running cleanly through:
```
reset_handler -> runtime_init -> picogus_bootloader_main ->
  stdio_printf("copying settings from %u with size %u", ...) ->
    vprintf -> _vfprintf_r -> format-dispatch jump table @ 0x20002a1e
```

The fault is at SRAM 0x20002a2e: `mov pc, r3` with `r3 = 0x20002a66`
— an EVEN label address from a literal pool at 0x20003ddc+0x34.
Our `mdrp2040::core::execute.rs` raises `Fault::InvalidEpsr` whenever
`ADD PC` or `MOV PC` lands on an even destination. Per ARMv6-M ARM
DDI 0419E §A5.1.2 this is wrong:

- `ALUWritePC(addr)` — used by `MOV Rd, Rm` and `ADD Rdn, Rm` when
  `Rd == 15` — is defined as `BranchWritePC(addr)` →
  `BranchTo(addr<31:1>:'0')`. **LSB is masked, never checked.**
  No fault path.
- `BXWritePC(addr)` — used by `BX` / `BLX` — checks the Thumb bit
  and raises a fault. CORRECT for those two.
- `LoadWritePC(addr)` — used by `POP {PC}` / `LDR PC, …` — is
  defined as `BXWritePC(addr)`. CORRECT for those too.

mdrp2350's reference implementation at
`crates/mdrp2350/src/core/execute.rs:383-389` already does
`self.regs.set_pc(val & !1); return 3` without a fault check.
mdrp2040 needs to match.

**gcc generates `mov pc, rN` for switch jump tables** (with rN
holding an even-aligned label address from a literal pool). Real
silicon handles this fine; our overstrict check rejects it. No
wonder every non-trivial C function that uses `switch` on a small
dense key set trips this.

Decision: fix is obvious and narrow — delete the LSB check from the
two ALUWritePC call sites, invert the `mov_pc_with_t0_raises_fault`
unit test, add positive tests for MOV/ADD PC with even targets.

## Phase 5 — Diagnose silent I2S output

**Status: diagnosis complete (no fix dispatched).**

Research agent (`a1549bba09abce2eb`) instrumented `picogus_probe_pc`
to prime ISA pins idle, run 10 M instructions, and dump PIO0/PIO1/
DMA/CLOCKS/GPIO/core state at end.

### Findings

**PC parked at 0x2000d628** from step ~500k onward (stable for 19
consecutive samples). Disassembly:
```
d624  LSLS  R0, R0, #3
d626  LDR   R3, [R2, #0x28]   ; R2 = 0x40054000 (TIMER_BASE)
d628  SUBS  R3, R3, R1        ; R3 = now - start
d62a  CMP   R0, R3            ; elapsed >= delay?
d62c  BHI   0x2000d626        ; loop until elapsed
```

This is pico-sdk's `busy_wait_us_32` polling **TIMERAWL** (TIMER +
0x28). `R2 = 0x40054000` = TIMER_BASE. `R0 = 0xfa = 250` — a 250 μs
wait inside a higher-level "copy settings from flash 0x10200000"
helper. The stack contains a pending UART format string `"copying
settings from 270528512 with size 152"`.

**Root cause**: mdrp2040 has no TIMER peripheral model. Reads at
0x40054000+offset fall through to the generic `peripheral_regs`
HashMap stub in `bus/mod.rs:473` which returns 0 for any unknown
offset. `busy_wait_us_32` reads `now = 0`, `now - start = 0`, loop
never exits.

**PIO state at end of run**: PIO0 and PIO1 both completely blank.
CTRL=0 (all 4 SMs disabled on both blocks), FSTAT=0x0F000F00 (TX
empty, RX empty — reset value), INSTR_MEM all zeros. **No PIO
program loaded → no BCLK/LRCLK/DOUT activity possible.** Firmware
never reaches the I2S bring-up path.

**DMA state**: all zeros across CH0/CH1. Note: **DMA is not
modelled in `mdrp2040` at all.** Writes land in the generic HashMap
stub; no transfers execute. Future blocker beyond Phase 6.

**CLOCKS state**: `sys_clk_hz=125_000_000`. PLL_SYS FBDIV=125,
POSTDIV1=6, POSTDIV2=2 → (12×125)/(6×2) = 125 MHz. Clock tree is
correctly configured. Not a blocker.

**Core 1**: never woken (PC still at 0x100001f6, halted). PicoGUS
runs the ISA service loop on core 1 — that's a separate blocker
beyond Phase 6.

### Ranked follow-up gates for end-to-end audio

1. **TIMER peripheral model** — smallest change, unblocks current
   stall. Minimum: cycle-driven 64-bit microsecond counter at
   TIMER_BASE+0x24 (TIMERAWH) / 0x28 (TIMERAWL) returning
   `bus.cycles / (sys_clk_hz / 1_000_000)`. Probably needs the full
   ALARM/IRQ path later.
2. **Core 1 launch handshake** — tracked in existing tech_debt
   ("RP2040 core 1 SDK handshake not parsed"). Core 1 must wake for
   PicoGUS's ISA service loop.
3. **DMA block model** — new blocker. I2S output relies on DMA
   feeding PIO TX FIFO. No DMA = no samples ever reach FIFO even
   after PIO loads an I2S program.
4. **Real DOSBox-X trace capture** — pre-existing external
   dependency (Stage 3/6 PicoGUS Integration journal). Current
   `fixtures/sample_gus.trace` is a synthetic 19-event fixture, not
   a real GUS MIDI capture.

All three emulator gates (1-3) are sequential — none of them alone
produces audio. Plus gate 4.

### Secondary discovery — ISA-pin default state

The Phase 4 smoke "no stall" result depends on picogus_diff_rp2040's
replay sink priming ISA pins idle (`IOW# = IOR# = HIGH`) between
events. `picogus_probe_pc` without that priming observes a different
bus fault at PC=0x20002a2e much earlier. Not a regression —
`picogus_diff_rp2040` has always primed pins idle via its
`CapturingSink` wrapper — but it means the oracle has a hidden
dependency on pin defaults being consistent with real ISA.

### Decision

**Stop here for the debug workstream.** We've cleared the SDK panic
(Phases 1-4) and firmware now runs cleanly through init. The
remaining work to produce audio is three separate peripheral-model
projects (TIMER, core 1 handshake, DMA), each substantial in its
own right, plus a DOSBox-X trace capture. Each deserves its own
HLD + sprint, not continued chasing.

Phase 6+ is tracked as future work. See `tech_debt.md` for the
detailed follow-up list.
