## A/B reference table — RP2350 @ step-quantum 4096, 5 reps, unpaced

Measured on `main` at commit tip of 2026-04-24, Windows x86_64, core 2
pinned at `HIGH_PRIORITY_CLASS` / `THREAD_PRIORITY_TIME_CRITICAL`. All
throughputs in MHz (per-core peak, from executed cycles).

**Methodology note (N=5):** reps=5 is the smallest IQR-stable count —
p25/p75 are computed as nearest-rank indices (rank 1 and 3 of 5) and
the bench discards 1 warm-up per model. This keeps the A/B run under
~60s total on a warm host. The trade-off: a single OS preemption can
shift one sample materially, and the IQR may not flag it (5 points
give only 3 interior). For regression capture or contested results,
bump to `--reps 10` or higher. Verdict thresholds (`max(3·IQR/median,
5%)`) absorb this fragility in the bulk case but not in edge cases
like `stress` where Serial's median sits close to Threaded's floor.

## Interpretation

- **Threaded wins CPU-compute-dominated workloads.** `basic` (tight ALU
  loop, single core) is +7.1%; `contention` (both cores running ALU,
  sequential-interleave vs parallel execution) is +98.0% — effectively
  the dual-core parallelism speed-up. `onerom-shape` (single CPU core
  + 3 PIO SMs across 2 blocks) lands +22.9%.
- **Serial wins peripheral-MMIO-dominated workloads.** `peripheral`
  (single core driving SIO XOR writes at every loop + PIO0 SM0 wrap)
  is Serial +58.3%. The threaded path's per-quantum barrier
  rendezvous between core 0 and the PIO worker serialises every MMIO
  write visibly, while Serial's single-thread interleave has no
  cross-worker handshake. `stress` (`peripheral` + live core 1 ALU) is
  Serial +28.1% — the added core 1 doesn't recover enough to flip the
  verdict because the PIO worker is still the bottleneck.
- **HLD §1 hypothesis validated.** Both models win different workloads
  on RP2350. The runtime selector is load-bearing, not speculative —
  no single model dominates the spread measured here. This matches
  the anchor evidence from `wrk_journals/2026.04.20 - JRN - Threaded
  Perf Investigation.md` (basic @ sq=1024: Threaded 275 vs Serial 164;
  peripheral at default sq: Threaded ≪ Serial).

## OneROM CPU-mode anchor

The bench `onerom-shape` workload above is the *block/SM shape mirror*
of OneROM (PIO1×1 SM + PIO2×2 SMs + CPU peripheral loop), not OneROM's
real serving pipeline. The true OneROM CPU-mode benchmark lives at
`crates/mdpicoem-harness/src/bin/onerom_cpu_speed_grade_rp2350.rs`
(Threaded) and `onerom_cpu_speed_grade_serial_rp2350.rs` (Serial).
Arthur's observation from the OneROM runs: Serial grades faster than
Threaded on that workload — consistent with the peripheral/stress
column above where PIO-heavy, MMIO-busy loads favour Serial. The
`threaded_probe` crossover (Threaded warm 311.4 MHz vs Serial 229.6
MHz on basic at sq=4096) reproduces in this bench as
`basic` +7.1% Threaded — different magnitude (the probe uses a
plain ALU loop with no pacer or setup), same direction. Together the
three data points (probe `basic` Threaded-favoured, paced-bench
`peripheral`/`stress` Serial-favoured, OneROM CPU-mode Serial-
favoured) confirm the crossover is workload-driven, not a tooling
artefact.

## Surprises

- `onerom-shape` going +22.9% **Threaded** in this bench appears to
  contradict Arthur's OneROM CPU-mode observation — but the workloads
  are different (see footnote below the A/B table). The difference is
  the workload shape: the bench's `onerom-shape` mode runs PIO blocks
  with plain wrap-loops and
  core 1 halted — no DMA, no FIFO handshakes, no cross-worker data
  dependencies. Real OneROM CPU-mode has the CPU and PIO workers
  tightly coupled through FIFO + IRQ path, which is exactly the
  Serial-favoured cost shape. The bench shape is not a faithful
  crossover proxy; the Serial-vs-Threaded direction on *real* OneROM
  needs the dedicated speed-grade oracles.
- `peripheral` Threaded median 75.0 MHz is pinned by the 150 MHz
  target clock / 2 — Threaded's coord fetch-adds `master_cycle` by
  `step_q` per quantum regardless of whether the CPU worker produced
  work, so a PIO-blocked CPU worker still "pays" cycles on the
  master counter. The executed-cycles metric from `core_cycles()`
  corrects for this but the MHz figure here uses
  `executed / wall_secs`, not the coord-tick total. Low variance
  (IQR 74.9–75.0) implies the PIO worker is saturated, not that the
  measurement is noisy.

  **Barrier-latency floor — why 75 MHz is real throughput, not a
  counting artefact.** The 75.0 MHz figure is the barrier-latency
  floor, not a cycle-counting artefact. The CPU worker in Threaded
  mode rendezvous at a `SpinBarrier` every quantum; on MMIO-bound
  workloads the worker spends most of each quantum waiting for the
  peripheral tick to complete, reducing executed-cycle throughput to
  ~sys_clk / 2 (150 MHz / 2). This IS real executed throughput — the
  MHz column is `executed_cycles / wall_seconds`, computed from
  `core_cycles()` which tracks instructions genuinely executed by the
  CPU worker, not coord ticks. The cause is barrier-sync cost, not
  the threaded scheduler model being fundamentally slower. Serial's
  179.7 MHz reflects its ability to advance the peripheral tick
  between instructions without thread-sync handoff — single-threaded
  interleave collapses the CPU↔PIO ordering constraint into
  instruction-level interleaving, paying no barrier cost.
