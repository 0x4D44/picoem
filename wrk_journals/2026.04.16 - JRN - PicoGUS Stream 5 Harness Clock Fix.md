# PicoGUS Stream 5 — Harness Time-Base Clock Fix

Date: 2026-04-16
Author: implementer agent
Scope: fix the harness-side static 125 MHz assumption that made post-PLL-reprogram
audio report at 0.34× the true rate.

## Context

Diagnostic agent (`wrk_scratch/picogus-pll-diagnosis.md`) established that:

- The emulator correctly tracks PicoGUS's 125 MHz → 370 MHz PLL reprogram at
  master-cycle ~32.78 M (`ClockTree::sys_clk_hz` updates to 370_000_000).
- The harness binary `crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs`
  hardcoded `DEFAULT_SYS_CLK_HZ = 125_000_000` and used it for every
  ns↔cycle conversion, so after the switch every conversion was off by
  the 370/125 = 2.96× ratio. The WAV came out at 13_655.5 Hz; true rate
  should be ~44 kHz.

## Option chosen: hybrid (b) + (c)

Both options from the brief are needed because the two use-sites have
different semantics:

- **Replay loop** (option (b)): the fast-forward must honour the *live*
  sysclk when pacing trace events, because the mapping from trace-ns
  (captured wall-clock) to sim-cycles changes mid-run.
- **I2S capture** (option (c)): edge timestamps are already stored in
  cycle-domain (`I2sCapture::first_lrclk_cycle`, `last_lrclk_cycle`);
  only `inferred_sample_rate_hz()` uses `sys_clk_hz`. Since the PicoGUS
  I2S output only begins *after* the PLL reprogram (~33 M cycles in,
  boot phase), snapshotting the post-reprogram clock before reporting
  is correct without per-edge clock tagging.

Full option (a) (snapshot post-init) was rejected because the 9% residual
error from the boot-phase pre-reprogram interval is unnecessary — the
loop fix is cheap (a new trait method + accumulator variable), and the
I2S fix doesn't need per-edge tagging for this firmware.

## Tests

`cargo test -p mdpicoem-harness --bin picogus_diff_rp2040` — 47 tests
pass, including the three new tests. Full `cargo test -p mdpicoem-harness`
also green.

The crown-jewel regression guard:
`replay_adjusts_ns_to_cycles_across_pll_reprogram` uses a
`VariableClockSink` that flips from 125 MHz → 370 MHz at a scripted
cycle boundary. It asserts the final cycle count is ~1.74 M (matches
the 8 ms pre-flip @ 125 MHz + 2 ms post-flip @ 370 MHz math) AND that
a no-flip run of the same trace comes in lower at ~1.25 M (10 ms ×
125 MHz) — proving the loop is sensitive to mid-run clock changes.

## Surprises

1. **`reset()` clobbers the clock tree**. `mdrp2040::Emulator::reset()`
   writes `self.bus.clock_tree = Default::default()`, which zeros back
   to ROSC 6.5 MHz regardless of `Config::sys_clk_hz`. The `build()`
   path calls `seed_sys_clk_hz(config.sys_clk_hz)` once, but a subsequent
   `reset()` undoes it. Two unit tests were implicitly relying on the
   old static 125 MHz harness math masking this; they now explicitly
   re-seed after reset. The main harness binary isn't affected because
   firmware's boot path reprograms PLL early on.

2. **Post-roll cycles are now ~3× larger at 370 MHz**. The reporting
   line now says `185 M cycles (0.502 s @ 370 MHz)` instead of the
   pre-fix `62 M cycles (0.5 s @ 125 MHz)`. The *sim wall time* is the
   same 0.5 s — but firmware now actually executes 3× more work during
   post-roll, which is why the frame count tripled. The 42.6 kHz
   inferred rate is stable between the two post-roll cycle regimes
   because the inference uses `sys_clk_hz * (edges-1) / (2 * (last -
   first))` and `last - first` scales with `sys_clk_hz`, so the ratio
   cancels — modulo that more edges = more statistics = tighter rate
   estimate.

## No open issues / residual risks

- The advance_to_sim_ns loop caps chunk size at 64 cycles, so any
  mid-chunk PLL reprogram is observed within 64 cycles (~170 ns at
  370 MHz). For a trace measured in ms this is negligible.
- The loop's initial-clock cold-start is `sink.sys_clk_hz()` before
  the first chunk; at POR the RP2040 tree is at 6.5 MHz ROSC, so the
  very first chunks may run at the ROSC rate until firmware reaches
  its first CLOCKS/PLL write. This matches real silicon behaviour and
  is correct — the pre-PLL boot phase on real silicon also runs at
  ROSC.
- The existing `VariableClockSink` is unit-test-only; it has no
  `drive_write_cycle` overhead because `drive_pins` is a no-op. Future
  tests wanting a full-featured variable-clock sink can derive one.
