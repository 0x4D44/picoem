# JRN: Contention Modelling Declined for RP2350

**Date:** 2026-04-15
**Related HLD:** `wrk_docs/2026.04.15 - HLD - Paced Bench Workload Spread.md`
**Related memory:** `feedback_threading_perf.md`

## Question

Paced-bench Stage 1–4 left RP2350 `contention`/`stress` as dual-core-
compute-only measurements: `mdrp2350::Emulator::step` runs cores
sequentially (core 0 drains its quantum, then core 1), with no per-
instruction interleave and no `contention_check_active` plumbing on
the bus. The Stage 4 HLD tracked "Per-instruction interleave +
contention hooks on mdrp2350" as **out of scope / future**, implying
the RP2040 model was the reference and RP2350 would catch up.

Arthur pushed back: are we sure we should be emulating contention at
all, given the perf gap?

## Decision

**Do not model bank contention on RP2350. Do not extend or defend
the RP2040 contention model; treat it as deprecated-in-place.**

## Rationale

1. **The perf error swamps the contention error by an order of
   magnitude.** RP2040 `basic` paced at 125 MHz is REAL-TIME MARGINAL
   (~96%) — already 4% of timing debt on the simplest possible
   single-core workload with all peripherals quiescent. Unpaced
   realistic workloads (`peripheral` 42 MHz, `stress` 37 MHz) run at
   ~30% of silicon. Bank contention adds +1 cycle on same-port
   accesses and fires maybe half the time on pathological layouts —
   ~10-15% cycle-count shift on dual-core memory-heavy code, zero
   effect on anything that avoids same-bank hot paths (which is what
   competent firmware *does*, precisely because contention is
   pessimal). The error we refuse to fix (perf) is 5-30× bigger than
   the error we'd be chasing (contention).

2. **Contention cycles are virtual.** A contention cycle is a counter
   increment on the emulator's cycle count; host compute for that
   cycle is near-zero (both cores still execute their next
   instruction on the following step). So modelling contention makes
   the emulator slower at computing numbers that don't correspond to
   anything measurable unless you're asserting exact cycle counts.
   When we need that level of precision, `probe_diff_rp2350` /
   `silicon_cycle_oracle_rp2350` already give it to us from real
   silicon.

3. **Threading obsoletes the serial-interleave path.** Arthur's
   roadmap has threaded cores on it. Per-instruction interleave is
   exactly the direction we don't want to reinforce: it forces
   serialisation and widens the perf gap. Investing in contention
   hooks now would (a) slow the serial interleaver, (b) add
   complexity that evaporates when threading lands, and (c) delay
   the real perf fix. Once cores run in their own threads, bank
   contention can fall out naturally from a shared bus arbiter
   without per-instruction bookkeeping — if we decide we want it
   then.

## Impact

- **RP2350 paced-bench workloads** (`contention`, `stress`) remain
  named as they are for CLI symmetry with RP2040. They continue to
  measure dual-core-compute-only, serve as dual-core-compute
  baselines, and will keep reporting ~0.5× `basic` MHz. The HLD's
  "Chip asymmetry" paragraphs stay accurate; only the "future work"
  framing changes to "declined".
- **RP2040 contention model** (`note_sram_access`,
  `contention_check_active`, the `Bus::core0_port`/`core0_bank_touched`
  flags) stays in place. It works, it's tested, ripping it out is
  more churn than it's worth. But we will not invest further: no
  parity work on RP2350, no perf tuning of the contention path, no
  new tests defending its behaviour. If it shows up in a perf
  profile, the presumption flips to "remove" rather than "preserve".
- **`bank_conflict_test_rp2350`** harness remains valid — it
  characterises real silicon timing, which is useful reference data
  regardless of whether we model it. We just won't use its output
  as a target for emulator convergence.

## Next

Nothing. The follow-up that would have existed (mdrp2350 contention
hooks) is now declined. The real next step for timing honesty is the
perf gap itself, which is its own multi-stage story (decode cache,
threaded cores, etc.) already in flight.
