## Key Discoveries

1. **RCP handler was the critical blocker.** The bootrom's Core 1 path uses
   `rcp_canary_status pc` (MRC2 encoding 0xFE30) and `rcp_salt_coreN` (MCRR2
   encoding 0xFC4x). The existing handler only matched 0xEE prefix (MCR T1).
   Required: split into MCR/MCR2 (0xEE/0xFE) and MCRR/MCRR2 (0xEC/0xFC)
   families, with Rt=15 writing APSR flags and (opc1, CRm) from hw1
   discriminating salt_core0 vs salt_core1 vs rcp_iequal.

2. **State-dependent canary_status flags.** Core 1's `wait_for_rcp_salt` loop
   (0x1c4–0x1d6) uses `bpl.n 1c4` (branch if N==0) to loop. Core 0's sites
   at 0x38b8 and 0x3990 use `bvc`, `bvs`, `bmi`. Solution: N = rcp_salt_valid[core],
   V=0 always. Before salt init: N=0 (loop/proceed). After: N=1 (exit).

3. **Core 1 steady state in Phase 4.** Core 1 exits `wait_for_rcp_salt` after
   Core 0's SEV at 0x39a0, enters the handshake loop, sends one value (r6=0)
   via FIFO_WR, then enters `receive_and_check_zero` WFE at 0x19c waiting
   for Core 0's reply. In Phase 4, Core 0 never replies → Core 1 sleeps
   permanently at PC=0x19e.

4. **FIFO echo protocol.** The bootrom echoes ALL values (including zeros).
   Core 0 must drain each echo to prevent FIFO backpressure. Without this,
   Core 1 remains stuck in `receive_and_check_zero`.

5. **Bus contention is asymmetric.** Core 0's progress is unaffected by
   Core 1's concurrent bootrom execution — contention stalls only Core 1.
   Phase 4 cycle count is essentially unchanged.
