# Devil's Advocate Review R2: Threaded Dual-Core Emulation HLD v2.0.0

**Reviewer:** Claude (devil's advocate, second pass)
**Date:** 2026-04-14
**HLD under review:** `d:\language\mdrp2354\wrk_docs\2026.04.14 - HLD - Threaded Dual-Core Emulation.md` v2.0.0
**Prior review:** `d:\language\mdrp2354\wrk_journals\2026.04.14 - Review - Devils Advocate.md` (R1 against v1.0.0)

## Executive summary

V2 did real work. The honest 120–130 MHz target, the Phase 0a decision gate,
the PPB move, the atomicization inventory, the SPSC hand-roll, and folding the
coordinator into worker 0 are all improvements. R1's main complaints are
answered.

That's also the problem. V2 has absorbed enough R1 feedback that it now reads
like a reasonable design, and a reasonable design invites implementation
momentum. My job in R2 is to resist that. The new issues cluster in four
buckets:

1. **Phase 0a is load-bearing but under-specified.** The gate decides whether
   weeks of risky refactoring happen. The HLD doesn't describe what the
   instrumentation is, how long it takes, who writes the firmware, or what
   "representative OneROM workload" means when OneROM doesn't exist yet.
   (Issues 1, 5, 6, 11)
2. **The "coordinator in worker 0" fold is elegant but not symmetric.** It
   introduces a per-quantum source of nondeterminism in cross-core event
   delivery that neither R1 nor V2 address. (Issues 4, 8)
3. **The architectural lock-in is real.** V2 commits to
   two-Arm-Cortex-M33-cores-specifically. Adding Hazard3, asymmetric
   configurations, or even instrumented single-thread modes becomes a
   refactor. (Issue 2)
4. **The speedup is still an assumption.** V2's headline number (120–130 MHz)
   depends on an unmeasured "perfect parallelism minus overhead" coefficient
   that could be anywhere between 1.2x and 1.9x. We'd only know after
   building most of Phase 0b and Phase 1. (Issue 14)

V2's biggest remaining gap is not technical — it's temporal. The decision
gate sits at Phase 0a, but the *evidence* needed to pass the gate requires
Phase 0b work (PPB move, atomicize) to exist in a form that supports
instrumentation. The HLD treats these as sequential; I think they're
entangled, and the entanglement can sink the schedule.

## ISSUE 1: Phase 0a's instrumentation is itself a project
**Severity:** IMPORTANT
**Type:** HIDDEN SCOPE

V2 says "Run the existing bootrom + representative OneROM firmware under
single-threaded `paced_bench`. Instrument to count: cycles spent in core 0
decode/execute, cycles in core 1 decode/execute, cycles in core 1 WFI,
cycles in bus contention stalls, peripheral register access frequency."

None of this exists today. `paced_bench.rs` runs a two-core MOVS/ADDS/B loop
and reports wall time + MIPS. It has no per-core classification. It has no
WFI-vs-active breakdown. It does not distinguish SRAM from peripheral
accesses. The Bus already tracks some contention state, but that's for
cycle-accurate arbitration, not a histogram.

To deliver the Phase 0a data, we need, at minimum:
- Per-core step classifier (ran, halted, WFI, WFE, stalled-on-contention).
- Per-access region tagging (SRAM / ROM / XIP / SIO / PPB / APB / AHB).
- Counters plumbed through `Bus::read*/write*` and `CortexM33::step`.
- A reporting harness that runs to completion and emits a CSV or JSON.
- A way to run OneROM firmware through it (see Issue 5).

Rough estimate: 3–5 days for a trustworthy workload profiler. That's not
free — it's comparable in cost to Phase 2 (ThreadedSio). The HLD lists
Phase 0a as if it were a measurement in an afternoon.

If Phase 0a says "don't do it," that engineering was spent on telemetry
we didn't need to deeply optimize. That's fine — tooling has value — but
it should be acknowledged, not hidden under a "decision gate" that makes
it sound cheap.

**Ask:** Add a "Phase 0a scope" subsection enumerating the instrumentation
to be added, the cost estimate, and what we keep in tree if the gate says
"no." Be explicit that Phase 0a is ~1 week, not an afternoon.

## ISSUE 2: Threaded design locks out Hazard3 and mixed-ISA
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION / ARCHITECTURAL LOCK-IN

RP2350 / RP2354 silicon has two Cortex-M33 cores *and* two Hazard3 RISC-V
cores. Only one pair runs at a time (architecture switch in the bootrom).
The v1 HLD (`2026.04.12 - RP2350 Emulator HLD.md:50`) explicitly scopes
Hazard3 as out of scope for v1 — but does not say out of scope forever.

V2 commits in several places to a Cortex-M33-specific design:
- `CortexM33 { ppb, exclusive_address, ... }` as the per-core owner.
- PPB (`SCB`, `NVIC`, `SAU`) moving into `CortexM33`. PPB is Armv8-M
  terminology; Hazard3 has CLINT/PLIC instead.
- LDREX/STREX/CLREX exclusive monitor with an address register. Hazard3
  RISC-V uses `lr.w/sc.w` with reservation sets that have different
  semantics (e.g., platform-defined eviction on any store to the
  reservation set).
- Memory-fence translation: `DMB` → `fence(AcqRel)`. Hazard3 `fence` has
  RISC-V predecessor/successor semantics that don't map 1:1.
- The workers are typed as running `CortexM33::step`.

None of this is wrong for the current scope. But the `ThreadedEmulator`
shape — two workers, each owning one `CortexM33` — hard-codes the ISA
into the runtime skeleton. When Hazard3 arrives (if it arrives), either:
(a) we generalize `ThreadedEmulator` over a `Core` trait, which is a big
ask once state has accreted, or
(b) we ship `ThreadedEmulatorM33` and `ThreadedEmulatorHazard3` side by
side, duplicating the worker/barrier/shared-memory plumbing.

V2 doesn't pick a lane. A cheap alternative exists: parameterize the
worker on a `Core` trait (which is small — `step(&mut self, bus: ..)` plus
a handful of halt/wake accessors) and keep Phase 1 single-implementation.
That costs ~0 today and leaves a door open.

More subtle: the RP2350 spec also allows *mixed-ISA asymmetric* boots
(one Arm + one RISC-V) via reboot paths. V2 doesn't need to support it,
but it should state that it doesn't, so nobody assumes we're preserving
the option.

**Ask:** Add a "Core architecture abstraction" note. Either commit to
"this design is M33-only and RISC-V will require a parallel implementation"
or state that the worker will be generic over a `Core` trait from day one.
Don't leave it implicit.

## ISSUE 3: CortexM33 field ownership — per-core vs shared — is not enumerated
**Severity:** IMPORTANT
**Type:** MISSING SCOPE

V2 moves PPB and exclusive-monitor state into `CortexM33`. Good. But
`CortexM33` also contains things that are Arm-architecture shared state
regardless of core:
- `rcp_salt` / `rcp_salt_valid` — V2 Phase 0b item 4 says "audit against
  datasheet." That's a research task, not a design decision. The HLD
  shouldn't accept an atomicize-or-not decision as a phase-0 audit
  outcome; it should *state* the outcome and cite the datasheet section.
- `dcp_data` — DCP is per-core (used for sign-extension etc.). Fine, but
  the HLD doesn't mention it.
- FPU state (`s[32]`, `fpscr`) — per-core, fine.
- `wfe_waiting`, `halted`, `event_flag` — V2 correctly atomicizes.
- Exception-return state (`secure`, mode, stack selection) — per-core,
  but exception entry currently reads from `Bus::ppb` and will now need
  to read from `CortexM33::ppb`. That's a touch of every exception
  handler in `exceptions.rs`.

The claim in the HLD is "shared things wrapped in `Arc`, core-local
things owned directly." But *which* things are which is left to
implementation. A field-by-field table is what this needs, and it's the
kind of table that catches design errors before they ship.

Concretely: `CortexM33` as designed today will have *fields that are
logically per-core (PPB) living alongside a pointer to shared state
(exclusive monitor addresses are in `SharedMemory`, not `CortexM33`)*.
That split has correctness consequences — e.g., reset. If someone calls
`CortexM33::reset()` expecting to reset "everything core-local," does it
clear the exclusive monitor entry for that core held in `SharedMemory`?
It has to, and that's a cross-struct invariant that's easy to forget.

**Ask:** Produce a full field inventory — one row per `CortexM33` field,
one row per `SharedMemory` field, one row per `ThreadedSio` field — with
columns "thread ownership," "mutation model," "lifecycle events." Land
this before Phase 0b starts. Without it, Phase 0b will be a rolling
series of "oh, we also need to atomicize this" discoveries.

## ISSUE 4: Coordinator in worker 0 introduces quantum-boundary nondeterminism
**Severity:** IMPORTANT
**Type:** CORRECTNESS SUBTLETY

The fold looks like this:

```
Worker 0:  step core 0 for Q cycles -> barrier -> pacer.wait + event handling -> barrier -> repeat
Worker 1:  step core 1 for Q cycles -> barrier ->                                barrier -> repeat
```

Worker 0 does "handle_cross_core_events()" between the two barriers.
During that window, worker 1 is parked at barrier 2. Now consider:

Core 0 issued a SEV at cycle 140 of a 150-cycle quantum. In the single-
threaded model, `event_flag[1]` is set at cycle 140 of the ordered
execution, and core 1 will observe it at cycle 141. In the V2 threaded
model:
- If `SEV` is written directly to `event_flag[1]` (AtomicBool), core 1
  sees it *during its own quantum* — possibly at cycle 10 of core 1's
  same-window quantum. Cycle 10 < cycle 140, so core 1 wakes "too early"
  relative to lockstep.
- If `SEV` is instead queued for worker-0 post-quantum handling, core 1
  sees it after the next quantum starts — at cycle 150+X of lockstep.
  That's later than lockstep.

Neither is right. V2 doesn't specify which. And the answer changes the
semantic of `paced_bench --threaded` vs `paced_bench` for any firmware
that uses WFE for sync.

Worse: because worker 0 does the event handling non-atomically with core
0's own execution, a SEV issued by *core 1* at cycle 140 of worker 1's
quantum also has this ambiguity — except now worker 0 has to process
events from "the other core's current quantum" while its own core might
have already executed into the next quantum.

V2 says "quantum-synchronized, not cycle-accurate per cycle (still
real-time accurate at quantum boundaries)." But cross-core events
crossing quantum boundaries is the subtle case. The HLD's two-line
diagram doesn't address ordering.

**Ask:** Write the event-delivery protocol explicitly. Specifically:
- When is `event_flag[other]` set — in the producing core's `SEV`
  opcode, or queued for coordinator processing?
- If queued, is there any guarantee that a SEV in the *nth* quantum is
  observed no later than the (n+1)th quantum?
- What about `WFE` in the same quantum as its waking `SEV` — is that
  deadlocky (core goes to sleep after SEV has already been delivered)?

Propose: atomic flag, Release on SEV, Acquire on WFE poll, document the
1-quantum-max latency and accept it. Then test.

## ISSUE 5: "Representative OneROM workload" presupposes OneROM exists
**Severity:** IMPORTANT
**Type:** CIRCULAR DEPENDENCY / UNSTATED ASSUMPTION

V2 Phase 0a says "Run the existing bootrom + representative OneROM
firmware." The bootrom is in-tree (we've been debugging it for weeks).
OneROM firmware is the downstream deliverable that depends on this
emulator. As of today, it does not exist in any form that can be loaded
into the emulator as a realistic workload.

What's actually available for Phase 0a measurement:
- The in-tree bootrom (well understood, already profiled, known to be
  ~single-core dominant early, with limited core 1 work during secure
  transition).
- The two-busy-loop `paced_bench` (synthetic).
- SIO ping-pong test firmware (synthetic, symmetric but contrived).
- Probe-rs diff test firmware (short snippets, not sustained workload).

The actual OneROM firmware — whatever it ends up doing — is the whole
reason we're emulating RP2354. It's also the reason we need *this* HLD,
because dual-core OneROM is presumably where the performance target
comes from. If it doesn't exist yet, Phase 0a cannot actually answer the
question it's asked to answer. It can only answer "do the synthetic
workloads we have today benefit from threading" — a question with a
likely answer but different meaning.

This is a real tension: the HLD's gate is "measure the workload that
matters, decide go/no-go." But that workload is the downstream
consumer's work product, which we can't wait on (they need the emulator
to write it, roughly).

**Ask:** Be honest about what Phase 0a actually measures. Two options:
(a) Measure the bootrom only, acknowledge it's asymmetric and will
probably say "don't do threading," and use *that* as the gate.
(b) Build a proxy workload (e.g., concurrent DMA-heavy PIO emulation,
or an internal dual-core cooperative test program that reflects
OneROM's expected shape). Document the proxy choice and its biases.

Don't leave Phase 0a reading as if we have OneROM firmware to run.

## ISSUE 6: The decision gate has a chicken-and-egg problem
**Severity:** IMPORTANT
**Type:** CIRCULAR DEPENDENCY

Related to Issue 5, stated as a program-management problem:

- OneROM can't be written efficiently without threaded emulation
  (because its developers want faster iteration cycles).
- Threaded emulation can't be justified without OneROM data.

This is the classic "we can't afford a saw until we chop firewood, but
we can't chop firewood without a saw" dynamic. The HLD's decision gate
pretends this isn't a structural issue: just go measure. But the
measurement question is ill-posed if the workload doesn't exist yet.

Three realistic resolutions:
1. **Decide on vibes.** We believe OneROM will run both cores hot because
   of its expected signal-processing / security workload. Ship threaded
   emulation without the gate. (Honest, but risky — we gave up the one
   design-discipline lever the HLD introduced.)
2. **Gate on a proxy.** Use the bootrom + synthetic "dual-core SIO ping"
   as the gate workload. Accept the bias. Ship if either shows >20%
   core-1 activity.
3. **Time-box.** "If OneROM isn't runnable in 4 weeks, we re-evaluate."

V2 doesn't say which of these it's doing. The default read is "we'll
measure OneROM when it's ready," which could be never.

**Ask:** Acknowledge the circular dependency explicitly in the HLD. Pick
one resolution and commit. My recommendation: option 2, with option 3 as
escape hatch if the proxy is inconclusive.

## ISSUE 7: Phase 0b is ~2 weeks of risky refactoring that Phase 0a can invalidate
**Severity:** IMPORTANT
**Type:** SEQUENCING / RISK

V2 Phase 0b lists four refactors:
1. Move PPB from `Bus::ppb[2]` to `CortexM33`.
2. Implement proper LDREX/STREX with exclusive monitor.
3. Atomicize `halted`, `wfe_waiting`, `event_flag`.
4. Audit & maybe atomicize `rcp_salt` / `rcp_salt_valid`.

Each is a significant change to live code:
- **PPB move:** `active_core()` is called in exception entry/exit,
  interrupt handling, SysTick, MPU checks. Every exception path has to
  move from `bus.ppb[bus.active_core()]` to `self.ppb`. Dozens of call
  sites. Regression risk: high.
- **LDREX/STREX proper impl:** Today they're LDR/STR stubs. A real
  exclusive monitor changes cycle counts (CLREX timing, STREX-fail
  spurious success/failure) and the bootrom spinlock path. Differential
  fuzz testing has to re-pass. This is a ~week by itself.
- **Atomicize booleans:** mostly mechanical, but reset paths and
  initialization need to be audited.
- **RCP salt audit:** undefined scope (see Issue 3).

The HLD estimates "1–2 weeks, each refactor its own commit." That's
optimistic. In practice this is 3 weeks of work if LDREX/STREX are done
well, and Phase 0a comes *after*. So: we may do 3 weeks of refactors,
then Phase 0a says "don't thread," and we're left with:
- PPB in `CortexM33`: arguably correct-by-design even single-threaded,
  keep it.
- LDREX/STREX: correct-by-design, keep it.
- Atomic booleans: single-threaded regression — atomic loads are *not*
  free, and these booleans are hot. We take a throughput hit on
  single-threaded for threading we won't ship.
- RCP salt audit: documentation value, keep.

Two of four refactors have standalone value. One (atomic booleans) is
actually counterproductive if we don't thread. The HLD sells Phase 0b as
"single-threaded-correct improvements," which is true only for 2.5 of
the 4.

**Ask:** Reorder. Do Phase 0a with *minimal* instrumentation first (1
week). If it fails, stop. If it passes, do Phase 0b (which now knows
it's not wasted work). Alternatively, cleave Phase 0b into "standalone
wins" (PPB move, LDREX/STREX) vs "threaded-only" (atomize booleans,
atomize RCP salt), and do only the former until Phase 0a decides.

## ISSUE 8: Asymmetric worker assignment is fine for throughput, subtly bad for determinism
**Severity:** NICE-TO-HAVE
**Type:** EDGE CASE

The "coordinator folded into worker 0" design means worker 0 always
does the pacer spin-wait + cross-core event handling. Worker 1 always
waits at barrier 2.

For throughput this is fine: both host cores are used; the pacer work
fits into the idle tail of the quantum.

For determinism and debuggability it has two subtle effects:
- **Nondeterministic timing in cross-core event delivery.** If core 0
  hits `SEV` at quantum-end cycle 148, worker 0 finishes its loop, hits
  barrier 1, processes the SEV, hits barrier 2, both cores resume. If
  core 0 hits `SEV` at cycle 2, worker 0 keeps running for 148 more
  cycles (during which core 1 may observe a race on the event flag —
  see Issue 4).
- **Asymmetric thermal and scheduling behavior on host.** Worker 0's
  host core runs hotter than worker 1's, over long runs. On a laptop
  with per-core DVFS, worker 0's core may throttle down first. This is
  benign for correctness, but for benchmarking, `paced_bench --threaded`
  numbers will have an odd temperature-sensitive asymmetry that's
  annoying to explain. Pin with fixed affinity, yes, but the *work*
  distribution still asymmetric.
- **Priority inversion under load.** If worker 0 is preempted by a
  Windows kernel interrupt while doing pacer spin-wait, worker 1 sits
  at barrier 2 wasting cycles. If it's preempted mid-step, same thing.
  Worker 1's preemption only stalls worker 0 at barrier 1, which is
  shorter.

None of these are showstoppers. The clean alternative (three threads:
two symmetric workers + one coordinator) was explicitly rejected for
cost, and I agree with that. But the asymmetry should be documented.

**Ask:** Note in the HLD under "Thread topology" that worker 0 carries
coordinator load and this creates mild asymmetric CPU/thermal/scheduling
characteristics. Document it so future perf investigations know to look
there.

## ISSUE 9: CAS loops on byte writes are "fine uncontended" — what about real contention?
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION

V2 says "u16/u8 writes use CAS loops (~10-20 cycles on contention, ~5
cycles uncontended)." This is the quiet assumption that worries me most.

Consider: Cortex-M code doing byte-level framebuffer writes, or two
cores both writing into a byte-granular circular log, or the common
`volatile u8*` peripheral-register pattern where both cores poll+clear.

Each byte write is a full CAS-loop read-modify-write on the backing u32.
If both cores write adjacent bytes in the same word:
- Core 0 loads word.
- Core 1 loads word.
- Core 0 computes new value, `compare_exchange_weak` succeeds.
- Core 1 computes new value from stale word, CAS fails, loops.
- Core 1 re-reads, recomputes, CAS succeeds.
- Total: 3 atomic ops plus one false-share cache line bounce.

Under heavy contention (pathological case: both cores in a tight byte-
write loop to adjacent bytes), this can be 100s of cycles per write, not
20. x86 MESI traffic on false-shared lines is the usual culprit.

More practically: firmware rarely does sustained byte-level contention
on SRAM (it's a false-sharing anti-pattern real developers avoid). But
the RP2350 SIO FIFO data is u32, the bootrom hash state is u32, and the
interesting cross-core writes are mostly word-granular. The u8/u16 path
is likely cold in real code — but the HLD doesn't assert this and doesn't
have data.

There is also a subtler performance gotcha. On x86, aligned u32
atomic stores are free (MOV). Aligned u16 atomic stores are *also* free
on x86 (MOV). Our emulation converts the u16 store into a CAS loop on
u32 — which is strictly slower than the host's own u16 atomic store
would be. We're paying host overhead to faithfully model guest-ISA
ordering that the guest ISA already guarantees on aligned u16. Is that
right?

Armv8-M guarantees single-copy atomicity of aligned u32 and u16. So
`AtomicU16` on the host, over a u16 slice, would give the same guarantee
without CAS loops. The HLD chose `[AtomicU32]` as the backing because
it's "one uniform type" — clean, but strictly slower for u16 writes than
`[AtomicU32; N/4]` overlaid with `[AtomicU16; N/2]` via a union or
transmute. That's scary in Rust; probably not worth it; but the tradeoff
deserves a sentence.

**Ask:**
1. Measure the u8/u16 write frequency in Phase 0a's instrumentation. If
   it's <1% of writes, the CAS overhead is irrelevant.
2. Document that pathological byte-level false sharing between cores is
   a known performance cliff — if firmware hits it, add cache-line
   padding or a fast-path for word-aligned sequences.
3. Acknowledge that we're emulating *more strictly* than the host ISA
   requires for u16. This is conservative but costs cycles we don't
   have to spend if we use `AtomicU16` overlays. Either accept the cost
   or plan a Phase 1.5.

## ISSUE 10: SIO FIFO sticky ROE/WOF semantics don't map cleanly to SPSC ring
**Severity:** IMPORTANT
**Type:** CORRECTNESS SUBTLETY

The existing single-threaded SIO (`sio/mod.rs:80-90`) has:
- `fifo_wof: [bool; 2]` — sticky write-overflow, per core.
- `fifo_roe: [bool; 2]` — sticky read-on-empty, per core.
- W1C semantics on FIFO_ST: writing 1 to bits 2/3 clears WOF/ROE.

A minimal SPSC ring (the "100 LOC" the HLD mentions) has just
`{buf, head, tail}` and a push/pop pair. The sticky status flags are
*not* naturally part of a ring. They're per-core side-channel state
that's set on push-when-full and pop-when-empty.

Where do they live in V2's `ThreadedSio`?
- If `fifo_wof`/`fifo_roe` are `[AtomicBool; 2]`, fine for atomicity —
  but the clearing is W1C from a *different* register access, and the
  setting is from within the SPSC ring's push/pop path. The ring has to
  know about the "sticky flag" concept, or the caller has to check the
  push/pop return and update the flag.
- W1C writes are cross-core: core 1 can write to clear its own WOF/ROE,
  which is set by core 1's own pop path. Each core only clears its own
  flags — that's fine for locality.
- The real subtlety: when core 0 pushes and the FIFO is full, core 0's
  WOF becomes set. Is the "set WOF" step a Release or Relaxed store?
  When core 0 later reads FIFO_ST, is it reading its own WOF store
  (same-core, no ordering needed) or worker 1's last WOF clear (also
  same-core, none)? WOF and ROE are per-core — they might actually be
  per-thread locals, not atomics at all.

The HLD's "~80 lines including sticky WOF/ROE flag semantics" is doing
a lot of work. Sticky flag integration is the finicky part of SIO FIFO
emulation today (see `fifo_st_read`, `fifo_st_write` at
`sio/mod.rs:233-257` — it's not one-line-per-flag). Preserving exact
register-level behavior in a new data structure is where bugs live.

**Ask:**
- State in the HLD that WOF/ROE are per-core-local (not shared), stored
  on the owning worker's local state, not in the SPSC ring.
- Or if they're in the ring, show the atomic-ordering argument.
- Add a unit-test line item to the plan: "FIFO_ST sticky flag behavior
  matches single-threaded golden reference under all push/pop/read
  orderings."

## ISSUE 11: `run(duration)` + dual-WFI = deadlock
**Severity:** IMPORTANT
**Type:** EDGE CASE

V2's API: `ThreadedEmulator::run(pacer, duration, stop)`.

Consider: both cores execute `WFE` after handshaking SIO. No ISR is
pending. No external event. Real hardware: both cores wait forever in
low-power state — the system is stuck and a watchdog resets it.

Our emulator doesn't have a watchdog (or if it does, it's emulated and
depends on guest ticks). So:
- Worker 0: core 0 is `wfe_waiting` — its `step()` returns early.
- Worker 1: core 1 is `wfe_waiting` — same.
- Both workers complete their quanta in zero cycles.
- Worker 0's post-quantum event handling finds no pending events.
- Pacer spins waiting for wall-clock to advance.
- Loop repeats until `duration` elapses or `stop` is signaled.

The user's intent was probably "run the firmware until it finishes."
If firmware "finishes" by entering a dual-WFE sleep, we don't detect
that — we just burn wall time until `duration` ends or the user hits
Ctrl-C.

This is not a correctness bug (the emulator is doing what was asked),
but it's a usability bug: the natural "run for 5 seconds" invocation
becomes "run for 5 seconds and discover at second 4.9 that nothing has
been happening since second 0.1."

More concerning: worker 0's pacer-spin burns real host CPU (100%
utilization) while waiting for a wall-clock tick that doesn't do
anything. The HLD says "target crossing cost: <100 ns. Burns one host
cycle per iteration while waiting — fine." It's fine for one quantum.
It's not fine for 5 seconds of quanta where every quantum has zero
useful work.

Fixes:
1. Detect "both cores WFE/halted with no pending events and no external
   wake source" and either return early or enter a blocking-sleep state
   until an external signal (timer, stop) fires.
2. Add a heartbeat: if we've processed N consecutive no-op quanta, log
   a warning or return early.
3. Document the behavior: "run(duration) will spin for the full duration
   even if the emulated system is idle." Users can handle this with
   timeouts.

**Ask:** Pick one of the three. Don't let the default be "burn 100% CPU
for 5 seconds doing nothing."

## ISSUE 12: Loom covers primitives, not the pipeline
**Severity:** IMPORTANT
**Type:** VALIDATION GAP

V2 says "Loom tests for SIO ring + barrier. Catches ordering bugs under
weak memory models."

This is true and useful. It's also limited. Loom's state space explodes
with model size. The practical limit is 2–3 threads, 4–8 atomic
operations per thread, tiny state. That fits:
- SPSC ring: 2 threads, push/pop sequences of length 3–5. Fits.
- SpinBarrier: 2 threads, wait/wait. Fits.

It does *not* fit:
- The full event-delivery pipeline (SEV on core 0, observed by core 1
  through `event_flag[1]`, wake from WFE, bus.write32 happening
  concurrently).
- Cross-core exclusive monitor invalidation (atomic load + compare +
  clear on up to 3 state locations).
- SIO FIFO push + WOF set + FIFO_ST read sequence.
- Memory-fence semantics across the full SharedMemory surface.

Loom gives us confidence in the primitives. It gives us approximately
zero confidence in the integration. The HLD doesn't distinguish.

What actually catches integration races:
- **Stress tests.** 10K+ iterations of dual-run differential with random
  quantum sizes, random start delays, hot scheduler pressure. Slow, but
  effective.
- **Thread Sanitizer (TSan).** Unstable on Rust, unsupported on Windows.
  Linux WSL2 might work — it's a real ask to set up.
- **Formal review.** The "manual audit" line in the HLD is doing a lot
  of work. Needs structure.

**Ask:** Narrow the Loom claim. Rephrase "Loom tests for SIO ring +
barrier" to "Loom tests for SIO ring and SpinBarrier primitives in
isolation." Add a separate line: "Integration race coverage via stress
tests (≥10K iterations dual-run differential) + manual field-ownership
audit per Issue 3." Set expectations.

## ISSUE 13: "Armv8-M is weakly ordered" needs a citation check for RP2350 Cortex-M33
**Severity:** IMPORTANT
**Type:** SPEC ACCURACY

V2 says "Relaxed ordering + explicit fences matches the guest
architecture: Armv8-M is a weakly-ordered memory model."

Mostly true at the architecture level. But RP2350 specifics:
1. The Cortex-M33 in RP2350 is a single-issue in-order core. Its
   *own* reordering is minimal compared to generic Armv8-M.
2. The inter-processor memory-access path on RP2350 goes through a
   shared bus fabric with defined arbitration order — not a generic
   weakly-ordered system.
3. Armv8-M's "weak ordering" is about the guarantees the *architecture*
   makes, not about what implementations do. A conforming implementation
   can be TSO-like. RP2350's documentation should specify actual
   inter-processor ordering promises.

I don't have the RP2350 datasheet memorized. The HLD's claim "Armv8-M
is weakly ordered, firmware without DMB/DSB has ordering bugs on real
silicon too" is architecturally-defensible but hardware-specifically
unverified.

If RP2350 guarantees stronger ordering between its two Cortex-M33 cores
than generic Armv8-M, then firmware developers may have written code
that relies on this stronger ordering (without DMB/DSB, because on real
hardware they didn't need to). Our threaded emulator, doing pure Relaxed
loads/stores, would then *have bugs* that only show on our emulator —
even though the firmware "has a bug" in an architectural sense.

That's a bad place to be: emulator reports race, firmware developer
insists their code works on hardware, we argue about specs. Usually
wins are had by being conservative on emulator side (Acquire/Release
everywhere) and documenting that this costs cycles.

**Ask:** Read RP2350 datasheet section on bus fabric and inter-processor
memory ordering. Cite it in the HLD. If RP2350 specifies stronger-than-
Armv8-M ordering between cores, state whether we match it exactly, or
accept the divergence and document it.

Fallback: use Acquire/Release on all shared memory access (not Relaxed).
x86 cost is near-zero; ARM host cost we don't care about; correctness
surface shrinks dramatically. The "Relaxed + explicit fences" model is
strictly harder to reason about than "Acquire/Release everywhere."

## ISSUE 14: Target achievability is asserted, not derived
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION

V2's target is 120–130 MHz per core. The derivation: current single-
core is 143 MHz = 21 host cycles/emulated cycle; threading adds atomic-
load overhead, barrier overhead, cache coherence traffic, fence cost;
"realistic per-core throughput with those overheads is ~120–130 MHz."

That's hand-waving dressed as arithmetic. What's the actual overhead?

- **Atomic-load overhead:** on x86, `load(Relaxed)` of aligned u32 is a
  plain MOV. Cost: ~1 cycle. If we do 2 loads per emulated cycle (fetch
  + data), that's 2 extra cycles = ~10% slowdown. That drops 143 → 130.
- **Barrier overhead:** 100 ns per barrier cross, 2 crosses per quantum,
  Q=150 cycles = 1 µs quantum. 200 ns / 1 µs = 20% overhead. That drops
  130 → 104.
- **Cache coherence:** depends entirely on workload. If both cores write
  adjacent cache lines, this dominates. If they work in separate
  regions, near-zero.
- **Fence cost on x86:** `fence(AcqRel)` is approximately free on x86
  (~2-3 cycles). If DMB is 1% of instruction mix, overhead is 1%.

Per the back-of-envelope: barrier is the big item. 20% overhead means
we're looking at ~115 MHz per core, not 130. If barrier overhead is
worse (measured 3–10 µs for std::sync::Barrier, and spin-barrier is
optimistically 100 ns — but hasn't been measured in our context), we
could land much lower.

If the target is 120–130 MHz but the realistic outcome is 100–115 MHz,
we're 20% under target. Phase 5's success criterion is "≥120 MHz per
core to declare success." If we get 115 MHz, is that failure?

And if we ship threaded with 115 MHz per core, aggregate is 230 MHz —
versus single-threaded 143 MHz — a 1.6x speedup. Real, but not 2x. Is
1.6x enough to justify the engineering effort + cycle-accuracy loss?

V2 doesn't ask. It treats "120–130 MHz per core" as achievable and
"≥120 MHz" as the bar. Neither is derived from measurement.

This is Phase 5 territory — by then the work is mostly done. If the
answer is "1.3x, not 2x," we can't easily revert.

**Ask:** Two options:
1. Build a minimal-viable throughput proxy in Phase 0a (pin two threads,
   each running a trivial step loop, with a barrier every Q cycles, no
   bus). Measure the raw overhead of the synchronization envelope
   *without* emulation cost. Use that to predict achievable per-core
   rate more honestly.
2. Reframe Phase 5's "≥120 MHz per core" as "any measurable improvement
   over single-threaded 73 MHz paced dual-core." That's a lower, honest
   bar.

Either way: the number 120–130 is a wish, not a model. Mark it as such
or derive it.
