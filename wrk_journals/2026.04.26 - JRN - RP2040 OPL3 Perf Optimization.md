### Iteration 3 — Fast-path gate broadening (REJECTED, no payoff possible)

Investigation outcome: gate broadening is **dead end** for PicoGUS.

- `picogus_diff_rp2040` hard-codes `step_quantum=1` (`picogus_diff_rp2040.rs:1669`) for ISA-waveform precision. At quantum=1, fast path = slow path (both do `step_n(1)`). No bulk-amortisation to win.
- Diagnostic counter at gate site for 50 M post-boot iterations: **`peri_idle` 0%, `dma_idle` 0%, `pio_idle` 0%**. PWM/UART/DMA are reporting busy 100% post-boot. So gate would never fire even if PIO were satisfied.
- `tick_pio(consumed)` in fast path doesn't route PIO IRQs into `bus.irq_pending` — only `tick_pio_and_route_irqs_single` does. Naïve broadening would silently drop PicoGUS's PIO0_IRQ_0 ISA event flow.

Expected speedup from gate broadening if pursued: **<1.05×**. Not worth the implementation cost.

### Iteration 4 — PIO `step_n` stalled-SM bulk-skip (in progress)

Real bottleneck: `PioBlock::step_n` (`crates/mdpicoem-common/src/pio/mod.rs:347-354`) is a **naive `for _ in 0..n { step() }` loop**. The doc-comment literally says: *"A bulk-advance optimisation is future work if PIO appears hot in a flamegraph."* PIO is hot.

PicoGUS workload runs `step_n(1)` 1.02 B times for 1811 PC advances on PIO0 SM0 — SMs are stalled **99.9998%** of cycles. Each stalled cycle still does `clock_tick()` → `execute_cycle()` → re-checks the stall predicate → returns to caller. Pure waste.

**Stall types** (`crates/mdpicoem-common/src/pio/sm.rs:106-114`):
- `Pull` (tx_fifo empty), `Push` (rx_fifo full), `WaitGpio`, `WaitPin` — these stall predicates are **invariant within a `step_n` call** (FIFO writes happen between calls; gpio_in is captured once at entry).
- `WaitIrq`, `IrqWait` — irq_flags can change because OTHER SMs in the same block can set/clear them. Cannot trivially bulk-skip unless ALL other SMs are also stalled-without-IRQ-effect.

**Strategy**: in `step_n`, fast-path when ALL enabled SMs are stalled with stall types in `{Pull, Push, WaitGpio, WaitPin}` AND `clkdiv_int=1, clkdiv_frac=0` AND `delay_count=0`. In that case the next N cycles produce no observable state change; bulk-update diagnostic counters, return.

**Expected gain**: ~30-60% of total wall (the PIO bucket from iter 1, with the assumption that the noise-floor measurement under-attributed PIO). Risk: incorrect bulk-skip could lose a stall→unstall transition or a side-set edge. Tests: existing PIO unit tests in `pio_tests.rs` + `pio/mod.rs` (~30 stall scenarios), `tests/dual_model.rs` Serial/Threaded parity, picogus audio cake-gate.

Implementation agent dispatched.

**Iter 4 result (escalated, not committed):**

### Iteration 5 — Generalise PIO bulk-skip to non-trivial CLKDIV (in progress)

Yesterday's main-tree diagnostic of mode-5 PIO state:
- PIO0 SM0: enabled, **CLKDIV=2.006 (int=2, frac=2 of 256)**, stalled at PC 0x0b
- PIO0 SM1: enabled, CLKDIV=1.000
- PIO0 SM2: enabled, **CLKDIV=2.006**, stalled at PC 0x15
- PIO0 SM3: enabled, CLKDIV=1.000

Stall ratio (full main-tree replay): 262 551 PC advances / 19 108 876 435 PIO ticks = **~73 000:1 stall**. So if bulk-skip eligibility is satisfied, it fires effectively-always.

Strategy: keep iter4's stall-invariance check (still correct — gpio_in / FIFO unchanged within step_n), generalise the clkdiv check:
1. For each enabled SM with stable stall, compute exact `(tick_count, end_acc)` over N cycles using the divider logic.
2. Advance `sm.clkdiv_acc` by the residual.
3. Bump per-SM `stall_cycles` diagnostic by `tick_count`.
4. Bump `cycles_stalled_at_pc_0x19` if applicable.
5. SM stall state unchanged (was stalled, stayed stalled — predicate still holds).

Risk: clkdiv math has to be bit-identical to the per-cycle path, especially for fractional dividers. Add unit tests for clkdiv=2, clkdiv=2.006, clkdiv=4, edge cases.

Acceptance: ≥10% wall improvement on mode-5 bench, audio cake-gate passes, cycles bit-identical, all PIO unit tests pass.

**~2% regression** (slight slowdown from larger function body inhibiting inlining of step_n's hot path, plus wider-divide cost during warmup). Cake-gate still passes. Reverted per spec rule.

**The architectural blocker:** `picogus_diff_rp2040.rs:1669` (and 4 other call sites) hard-code `step_quantum=1` for ISA-waveform precision. `step_quantum=64` is only used during the 200k-iteration WARMUP (`picogus_diff_rp2040.rs:1804`), not during replay. So `step_n` is ALWAYS called with `n=1` on the 1 B-iteration hot path, where the `if n > 1` guard early-outs and the bulk-skip is unreachable.

The bulk-skip strategy is **dead** until `step_n` is called with `n > 1` on the hot path. Two ways to fix that:

1. **Change harness to use dynamic quantum** (= cycles-to-next-event, or some cap). Requires confirming ISA-waveform precision is preserved. Big harness refactor.
2. **Refactor the slow path itself** to chunk multiple cycles per inner loop iteration (broadening the fast-path gate), with bulk methods on each peripheral. Even bigger refactor.

Neither is iter4/iter5's <100-line scope.

### Iteration 7 — `is_pure` fast-path skip in `step()`

Iter 6r pre-classified `FLAG_PURE` at populate time but never read it. Iter 7 wires it into the inline fast path on `CortexM0Plus::step` (`crates/mdrp2040/src/core/mod.rs:266`):

- Peeks the cache slot for the fetched PC before falling through to the normal `decode_execute` slow path.
- On a tag-match + `FLAG_PURE` hit: dispatches the cached `hw0` (`/+hw1`) directly into `execute_thumb16` / `execute_thumb32`, **skipping** `bus.set_active_pc(pc)` (the MMIO-trace tag is unobserved by handlers that never touch the bus) **and** the post-step `bus.bus_fault()` check (pure handlers cannot reach the bus).
- The `pending_fault.take()` drain is still run because the conservative classifier marks `MSR`/`MRS` pure even for reserved SYSm patterns that escalate to UNDEFINED. Skipping the drain there would silently lose the fault.

Mirrors the `is_pure` fast path on mdrp2350 (commit `0c31479`) but smaller surface — RP2040 has no `extra_wait_states` accumulator, so the M33's wait-state reset/replay drop doesn't apply. The structural saving is one bus store + one bus load + a couple of branches per pure cache hit.

Tests added (8 new):

- `classifier_marks_adds_imm_pure` / `classifier_marks_b_uncond_pure` / `classifier_marks_bl_pure` — populate-time flag set on representative pure encodings.
- `classifier_marks_str_impure` / `classifier_marks_ldr_impure` — confirms loads/stores still classify impure.
- `fast_path_skips_set_active_pc` — sentinels `bus.active_pc[0]` to `0xDEAD_BEEF` after a populate run; second step on the cached pure entry must leave the sentinel intact.
- `fast_and_slow_paths_produce_identical_state` — same instruction run cold then hot must produce identical register/PC/cycle state.
- `impure_instruction_skips_fast_path` — STR cache hit must still go through the slow path (sentinel gets clobbered, asserting fast path correctly bypassed for impure).

Why the M0+ and M33 paths diverge here. ## High-level summary (sprint close-out, Arthur Q&A)

### Real-time gap
- **paced_bench basic --unpaced**: ~166 MHz throughput on x86 host → **1.33× faster than RP2040's 125 MHz silicon** on synthetic ALU loops.
- **PicoGUS OPL3 firmware mode 5**: **~36–55× slower than real-time** (89–137 s wall per 2.5 s sim audio, host noise dependent). Yesterday's M1 Adlib trace: 51.6 s of audio in 3420 s wall = **~70× slowdown** on the longer track.
- A 100× spread across workloads, driven entirely by per-cycle slow-path overhead, not core dispatch.

### Why OPL3 specifically is slow
Bottleneck is **`step_quantum=1` plus PIO**, not the ISA dispatcher.

`crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs:1669` hard-codes `step_quantum=1` for ISA-waveform precision. Every emulated master cycle runs the full slow path: `tick_peripherals + systick + tick_pio(×2 SMs) + update_gpio + drain_pending_irqs_to_cores` ≈ 200 ns of host work × ~1.02 B cycles for 2.5 s of audio = ~200 s wall.

The single ugliest line item: PIO. `PioBlock::step_n` is a naive `for _ in 0..n { step() }`. PicoGUS calls it **1.02 B times** to produce **1811 PC advances** — i.e. 99.9998% of PIO ticks are pure stall-checking waste. Iter 4 attempted to bulk-skip stalled SMs but `clkdiv=2` on the OPL3 PIO programs killed the predicate.

### Single-thread vs multi-thread (RP2040 paced_bench, quantum=256, 5 reps)
| Workload    | Serial   | Threaded | Δ        |
|-------------|---------:|---------:|---------:|
| basic       | 222 MHz  | 292 MHz  | +31%     |
| contention  | 122 MHz  | 271 MHz  | +122%    |
| peripheral  | 14 MHz   | 63 MHz   | +349%    |
| stress      | 10 MHz   | 63 MHz   | +511%    |

Threaded wins everywhere on RP2040. **But** `picogus_diff_rp2040` hard-codes `Serial`, so threading is not currently helping OPL3. Wiring `--model threaded` is a lever we haven't pulled — but at `step_quantum=1` the barrier amortises across nothing, so the 30–500% A/B gains above will not transfer until quantum is also raised.

### How useful is this emulator
Not a real-time emulator for full-system audio firmware — it's a **correctness oracle and firmware playground**:
- ARMv6-M and ARMv8-M ISAs differentially validated against QEMU + real silicon (probe-rs) + Spike.
- Silicon oracles for peripherals, cycle counts, ISRs, dual-core contention.
- PicoGUS firmware boots end-to-end: OPL3 register writes → I2S DMA → audio that passes the cake-gate (peak −16 dBFS, 10/10 musical-band peaks). Slow but functionally correct.
- Strong value for firmware development without burning a board cycle, and for chasing emulator-vs-silicon divergences.

The 1.3× real-time on basic ALU shows the dispatch core is in good shape. The 36–55× on OPL3 is overwhelmingly a peripheral-tick problem. Tractable if you decide to spend on it, but a different sprint with different scope.

## Next-steps assessment (three candidate moves)

Arthur proposed three follow-ons. Honest ranking:

### 1. Enable threading in picogus_diff_rp2040 (low effort, low expected ROI in isolation)
Mechanical: add `--model {serial|threaded}` like paced_bench, lift the hard-coded `Serial`. **But** at `step_quantum=1` the barrier syncs at every cycle — barrier cost (~50–100 ns) lands on top of the 200 ns/cycle slow-path overhead. The +31% to +511% A/B gains are at quantum=256 because the barrier amortises across 256 cycles. At quantum=1 the barrier overhead dominates and threading is likely flat-or-worse than serial. Threading is a *second* move that depends on a quantum lift first. Worth doing as a measurement once quantum is sorted, not before.

### 2. Skip-stepping unused peripherals / unused PIO SMs (low ROI for "unused" framing, real lever for PIO bulk advance)
This conflates two things that need separating:

**(a) Outer "is this peripheral idle?" skip**: tried in iter 2. Result: **3% within noise**. The reason: each peripheral's `.tick()` already has a cheap internal early-out (`!enabled || tx_empty` for UART/SPI; masked-zero for I2C; `cycles == 0` for PWM). Adding `if !is_idle()` outside replaces one cheap branch with another of the same shape — branch predictor handles both. Diminishing returns.

**(b) PIO bulk-advance for stalled SMs**: this IS a real lever (1.02 B step_n calls for 1811 advances). Iter 4 implemented it for `clkdiv=1` (didn't fire on OPL3 which uses clkdiv=2). Iter 5 generalised it (correctly) but it was unreachable on the hot path because `step_n` gets called with `n=1` from the slow path. **Bulk-skip only fires if `step_n` gets `n>1`, which means we need `step_quantum>1` first.**

So both halves of option 2 are gated on option 3. The "unused peripheral" framing alone is a known dead-end (iter 2's evidence).

### 3. Lift step_quantum (highest leverage, but more nuanced than "just bump the number")
The harness chunker already aligns to `clamp(1, 64)` cycles per call (per the journal's iter 0 notes), so lifting from 1 to 64 doesn't violate any precision contract that doesn't already exist. RP2350 runs quantum=1024 by default for the same workload class.

**The catch**: at `step_quantum=N` in the current code:
- **Fast path** (gate fires): does bulk `step_n(N)` and bulk peripheral advance → real Nx amortisation. But the gate at `lib.rs:652` requires `pio_idle && peri_idle && dma_idle && systick_idle && !any_irq`, and iter 3 found PWM/UART/DMA report busy 100% post-boot. The gate doesn't fire on PicoGUS today.
- **Slow path** (gate doesn't fire — current PicoGUS reality): the inner loop still does `tick_peripherals + tick_pio(1) + update_gpio + ...` per cycle. Lifting quantum just amortises the *outer* `step()` function call overhead, which is small.

**So quantum lift alone is probably 5–15% on OPL3, not the ~Nx the simple model suggests.** The big win from quantum requires *also* doing a slow-path chunked refactor — i.e. `tick_peripherals(N)` instead of `tick_peripherals` × N — so the per-cycle overhead amortises across the whole quantum. That's the "slow-path chunked refactor" architectural move from Final state §2 above.

### Recommended sequencing
The three options aren't independent; they have dependencies:

1. **Quantum lift + slow-path chunked refactor as a paired move** (the real architectural change). Requires per-peripheral `advance_n_cycles(n)` methods, careful handling of mid-quantum assertion edges (DMA fires on cycle 7, PIO IRQ clears on cycle 12, etc.). Expected win: large — directly attacks the 200 ns/cycle overhead on the actual hot path. This is the substantive sprint.
2. **Threading wired into picogus_diff** as a follow-up once quantum > 1 is real. Expected additional win: per the paced_bench A/B, +31% on basic-like / +120% on contention-like patterns. Cheap to wire once the quantum question is resolved.
3. **PIO bulk-skip from iters 4/5 resurrected** once `step_n` actually gets called with `n>1`. Expected win: significant on the PIO portion specifically (PIO was ~32% of slow-path bucket per iter 1's instrumentation, with the Instant-overhead caveat).

The honest framing: option 3 (Arthur's quantum question) is the load-bearing one. Options 1 and 2 stand on top of it. Trying any of them in isolation will hit the same noise-floor walls iters 1–7 hit.

**Open question for Arthur**: why was `step_quantum=1` originally chosen for `picogus_diff_rp2040`? If the answer is "ISA-bus waveform sampling needs cycle-accurate edges" then we need to confirm what "cycle-accurate" actually buys at the audio output — the chunker is already 64-cycle bucketed, so we may already be tolerating 64-cycle imprecision at the ISA boundary. If it's "we never measured what looser quantum costs in fidelity", the answer is to *measure*: bench at quantum=4, 16, 64 and diff the WAV against quantum=1.

### Interpretation

- **q=4**: top-5 peak frequencies match q=1 exactly; peak/RMS within 0.1 dB; bytes differ by <1 KB out of 336 KB. **Spectrally indistinguishable from q=1** — the small cycle shift (−855 K cycles, −0.08%) is firmware path-length variation from ISA-pin sample alignment, not audible content change.
- **q=16**: cake-gate still passes (peak −16.15 dBFS, 10/10 musical peaks) **but the fundamental shifts** — top peak moves from 324 Hz to 288 Hz, with three of the top-5 peaks at frequencies absent from q=1. This is detuning, not silence — the OPL3 voices sound musical but slightly off-pitch. Audible if compared back-to-back; might pass casual listening.
- **q=64**: complete silence (−∞ dBFS). Cycles count is closest to q=1 (only 24 K different) — firmware execution didn't break, but the ISA-pin sampling missed enough edges that the I2S DMA chain produced no output. This is the regime the original 1-cycle-overshoot doc-comment was warning about.

### Findings

1. **Quantum lift alone delivers more than the pre-bench estimate.** I'd predicted 5–15% on OPL3 because the fast-path gate doesn't fire (peri/dma busy 100% post-boot). Actual: 13% at q=4, 14% at q=16, 28% at q=64. So the slow-path inner loop is paying enough per-call overhead (function frame, register save/restore around the inner loop body) above the per-cycle peripheral work itself that quantum amortisation alone moves the needle without any chunked-advance refactor.
2. **q=4 is a free win.** Spectrally identical to q=1, 13% wall reduction, no further engineering work needed. Worth landing as the default — the ISA-overshoot bound becomes 4 cycles instead of 1, well below the 37-cycle ISA write window the original doc-comment was protecting.
3. **q=16 trades fidelity for an additional 1.4% perf.** Marginal value — going from q=4 to q=16 saturates the same dispatch overhead while ISA precision starts to slip into audible detuning. Not worth it.
4. **q=64 is broken.** The 28% perf headline is real but unusable. Useful as the upper-bound calibration: confirms ISA edges DO matter once overshoot approaches the ISA-write window length.
5. **Architectural ceiling visible.** q=4 → q=16 is +1.4%; q=16 → q=64 is +13.6% (with broken audio). The big gain at q=64 comes from somewhere quantum amortisation alone can't reach within audio-correct bounds. Suggests 15–20% remains on the table from the slow-path chunked refactor — keep per-cycle ISA precision, bulk-advance the peripherals/PIO/SysTick at the slow-path boundary.

### Recommendation

Three escalating moves now visible:

1. **Default `--step-quantum 4`** in `picogus_diff_rp2040`. Cheap, free 13%, no audible regression. Keep the flag so the historical 1-cycle behaviour is reachable for ISA-edge debugging.
2. **Slow-path chunked peripheral advance.** Keep `step_quantum=4` (or 1 for paranoid debug); add `tick_peripherals_n(N)`, `tick_pio_n(N)`, etc., so the per-cycle inner loop becomes one call per quantum instead of N. Expected: another 15–25% on top of (1).
3. **Wire `--model threaded` into picogus_diff** once (1) and (2) are landed. At q=4 the barrier amortises across 4 cycles; at the post-(2) effective quantum, more.

The quantum question Arthur asked was the right one. The original "quantum=1 for ISA waveform precision" guard was over-conservative — q=4 is safe, q=16 starts to bite, q=64 breaks. Defaulting to 4 captures the safe gain immediately.
