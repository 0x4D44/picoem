**Why it didn't help (analysis)**:

### Iteration 3 — Fast-path gate broadening (REJECTED, no payoff possible)

Investigation outcome: gate broadening is **dead end** for PicoGUS.

- `picogus_diff_rp2040` hard-codes `step_quantum=1` (`picogus_diff_rp2040.rs:1669`) for ISA-waveform precision. At quantum=1, fast path = slow path (both do `step_n(1)`). No bulk-amortisation to win.
- Diagnostic counter at gate site for 50 M post-boot iterations: **`peri_idle` 0%, `dma_idle` 0%, `pio_idle` 0%**. PWM/UART/DMA are reporting busy 100% post-boot. So gate would never fire even if PIO were satisfied.
- `tick_pio(consumed)` in fast path doesn't route PIO IRQs into `bus.irq_pending` — only `tick_pio_and_route_irqs_single` does. Naïve broadening would silently drop PicoGUS's PIO0_IRQ_0 ISA event flow.

Expected speedup from gate broadening if pursued: **<1.05×**. Not worth the implementation cost.

### Iteration 4 — PIO `step_n` stalled-SM bulk-skip (in progress)

Real bottleneck: `PioBlock::step_n` (`crates/mdpicoem-common/src/pio/mod.rs:347-354`) is a **naive `for _ in 0..n { step() }` loop**. The doc-comment literally says: *"A bulk-advance optimisation is future work if PIO appears hot in a flamegraph."* PIO is hot.

PicoGUS workload runs `step_n(1)` 1.02 B times for 1811 PC advances on PIO0 SM0 — SMs are stalled **99.9998%** of cycles. Each stalled cycle still does `clock_tick()` → `execute_cycle()` → re-checks the stall predicate → returns to caller. Pure waste.

**Stall types** (`crates/mdpicoem-common/src/pio/sm.rs:106-114`):
- `Pull` (tx_fifo empty), `Push` (rx_fifo full), `WaitGpio`, `WaitPin` — these stall predicates are **invariant within a `step_n` call** (FIFO writes happen between calls; gpio_in is captured once at entry).
- `WaitIrq`, `IrqWait` — irq_flags can change because OTHER SMs in the same block can set/clear them. Cannot trivially bulk-skip unless ALL other SMs are also stalled-without-IRQ-effect.

**Strategy**: in `step_n`, fast-path when ALL enabled SMs are stalled with stall types in `{Pull, Push, WaitGpio, WaitPin}` AND `clkdiv_int=1, clkdiv_frac=0` AND `delay_count=0`. In that case the next N cycles produce no observable state change; bulk-update diagnostic counters, return.

**Expected gain**: ~30-60% of total wall (the PIO bucket from iter 1, with the assumption that the noise-floor measurement under-attributed PIO). Risk: incorrect bulk-skip could lose a stall→unstall transition or a side-set edge. Tests: existing PIO unit tests in `pio_tests.rs` + `pio/mod.rs` (~30 stall scenarios), `tests/dual_model.rs` Serial/Threaded parity, picogus audio cake-gate.

Implementation agent dispatched.

**Iter 4 result (escalated, not committed):**

- State: bit-identical (cycles, events, stall counts) — proves bulk-skip is correctness-preserving on the workload that ran.

### Iteration 5 — Generalise PIO bulk-skip to non-trivial CLKDIV (in progress)

Yesterday's main-tree diagnostic of mode-5 PIO state:
- PIO0 SM0: enabled, **CLKDIV=2.006 (int=2, frac=2 of 256)**, stalled at PC 0x0b
- PIO0 SM1: enabled, CLKDIV=1.000
- PIO0 SM2: enabled, **CLKDIV=2.006**, stalled at PC 0x15
- PIO0 SM3: enabled, CLKDIV=1.000

Stall ratio (full main-tree replay): 262 551 PC advances / 19 108 876 435 PIO ticks = **~73 000:1 stall**. So if bulk-skip eligibility is satisfied, it fires effectively-always.

Strategy: keep iter4's stall-invariance check (still correct — gpio_in / FIFO unchanged within step_n), generalise the clkdiv check:
1. For each enabled SM with stable stall, compute exact `(tick_count, end_acc)` over N cycles using the divider logic.
2. Advance `sm.clkdiv_acc` by the residual.
3. Bump per-SM `stall_cycles` diagnostic by `tick_count`.
4. Bump `cycles_stalled_at_pc_0x19` if applicable.
5. SM stall state unchanged (was stalled, stayed stalled — predicate still holds).

Risk: clkdiv math has to be bit-identical to the per-cycle path, especially for fractional dividers. Add unit tests for clkdiv=2, clkdiv=2.006, clkdiv=4, edge cases.

Acceptance: ≥10% wall improvement on mode-5 bench, audio cake-gate passes, cycles bit-identical, all PIO unit tests pass.

Implementation was clean: exact divider math (`total_acc / threshold`), 3 new tests for clkdiv=2 / 2.006 / mixed, 240 mdpicoem-common tests + 945 mdrp2040 tests + 2810 mdrp2350 tests all pass. Cycles bit-identical (1 056 157 608) across baseline + 3 different optimised builds.

**~2% regression** (slight slowdown from larger function body inhibiting inlining of step_n's hot path, plus wider-divide cost during warmup). Cake-gate still passes. Reverted per spec rule.

**The architectural blocker:** `picogus_diff_rp2040.rs:1669` (and 4 other call sites) hard-code `step_quantum=1` for ISA-waveform precision. `step_quantum=64` is only used during the 200k-iteration WARMUP (`picogus_diff_rp2040.rs:1804`), not during replay. So `step_n` is ALWAYS called with `n=1` on the 1 B-iteration hot path, where the `if n > 1` guard early-outs and the bulk-skip is unreachable.

The bulk-skip strategy is **dead** until `step_n` is called with `n > 1` on the hot path. Two ways to fix that:

1. **Change harness to use dynamic quantum** (= cycles-to-next-event, or some cap). Requires confirming ISA-waveform precision is preserved. Big harness refactor.
2. **Refactor the slow path itself** to chunk multiple cycles per inner loop iteration (broadening the fast-path gate), with bulk methods on each peripheral. Even bigger refactor.

Neither is iter4/iter5's <100-line scope.
