# V3 HLD — Architecture Review (R3)

Date: 2026-04-14
Reviewer: Claude (architecture pass)
Subject: `d:\language\mdrp2354\wrk_docs\2026.04.14 - HLD - Threaded Dual-Core Emulation.md` v3.0.0

## Verdict

**Not yet ready to ship.** V3 is a large improvement over V2 — the
one-way conversion, the field ownership table, the rtrb decision, and the
phased schedule with clear gates all land correctly. But four issues at
the API / contract layer need resolution before implementation starts;
two more need at least a stated policy in the doc. None are architectural
rewrites — most are a paragraph of doc, one is a re-slicing of Phase 0b.

The serious ones in order:

1. `Pacer` cfg-gating breaks non-x86_64 builds silently.
2. `into_threaded()` signature omits peripheral injection, which is the
   entire point of `EmulatorBuilder`.
3. Phase 0b.1 / 0b.2 / 0b.3 are not independent commits as claimed.
4. `ExitReason` is incomplete in a way that matters for the debugger.

The rest are doc-policy gaps (benchmark rollback, lock-order inversion,
module layout forecast).

---

## CRITICAL #1 — Pacer cfg-gating

The HLD says on line 135:

```
pub fn run(
    &mut self,
    pacer: &mut Pacer,
    duration: Duration,
    stop: Arc<StopSignal>,
) -> ExitReason;
```

But `Pacer` is `#[cfg(target_arch = "x86_64")]`-only
(`d:\language\mdrp2354\crates\mdrp2354\src\pacer.rs:253`). `PacerStats`
and `PacerSnapshot` are cross-platform (no cfg on their definitions),
only `Pacer` itself is gated. This means on aarch64/riscv64 host builds,
`ThreadedEmulator::run` as written does not type-check — `Pacer`
doesn't exist.

The HLD is silent on this. Options:

- (a) Make `ThreadedEmulator` itself x86_64-only. Simple, honest —
  threaded mode depends on TSC pacing anyway. Recommended.
- (b) Take a trait (`trait PacingSource`) and let non-x86_64 use
  `Instant::now()`. More engineering, lower value.
- (c) Time-source abstraction parameter on `run()` (generic `P:
  Pacing`). Complicates the signature; bikeshed-prone.

This has to be decided before Phase 3 or we will hit a cfg wall
mid-implementation. **Require V4 to state the policy.**

Note the downstream impact: any crate that names `ThreadedEmulator` in
a function signature inherits the cfg. Test harness binaries need it;
`mdrp2354-app` may not care (GUI). Either `ThreadedEmulator` is gated
everywhere or nowhere.

## CRITICAL #2 — into_threaded() and peripheral injection

The API says `pub fn into_threaded(self) -> ThreadedEmulator`. But
today's `Emulator` does NOT own peripherals — they are injected via
`EmulatorBuilder`, and the comment in `lib.rs:57` is explicit:
"Peripherals and PIO are injected via builder."

So the flow in V3 reads:

```rust
let emu = EmulatorBuilder::new(cfg)
    .with_peripheral(...)  // today's pattern
    .build();
let threaded = emu.into_threaded();  // where do the peripherals go?
```

V3 shows `Peripherals { apb, ahb, clocks, qmi, resets }` with sharded
mutexes (line 372), but never says:

- Does `into_threaded()` wrap the existing single-threaded peripherals
  in `Mutex<_>` and move them into a `Peripherals` struct?
- If peripherals have internal state that's `!Send` (today nothing
  enforces `Send` on the `Peripheral` trait), does the conversion
  require a trait bound change on `Peripheral`?
- Is there a parallel `ThreadedEmulatorBuilder` with a parallel
  injection pattern, and `into_threaded()` is just for cases without
  peripherals?

**The silent assumption is that peripherals are already inside
`Emulator` by Phase 3.** That is not today's layout, and reorganizing
peripheral ownership into `Emulator` is a refactor with its own call
sites — not listed in the files-changed table for any phase.

Also on the cost question asked: yes, `Vec<u8>` → `Box<[AtomicU32]>`
is ~520KB. That's fine on its own — one-time conversion at startup,
sub-millisecond — **but only once we've verified the emulator isn't
mid-run at conversion time** (it's moved by value, so the type system
guarantees it). The real cost is bytewise widening, not the copy.
Mention this in the doc as a known, bounded cost.

**Action:** V4 must spell out the peripheral-ownership story across
the conversion boundary. If today's injection pattern is retained,
`into_threaded()` needs parameters.

## CRITICAL #3 — Phase 0b subdivision is optimistic

The schedule claims `Phase 0b.1` (PPB move, 62 call sites), `0b.2`
(LDREX/STREX), and `0b.3` (atomize fields) are three independent
commits. Look at what each touches:

- 0b.1 modifies `CortexM33` to own `Ppb`, and changes every bus method
  that needed `active_core()` to take `CoreId`. That's `src/core/mod.rs`
  and most bus call sites in `src/core/execute.rs`, `execute_thumb32.rs`,
  `exceptions.rs`.
- 0b.2 adds `exclusive_address` to `CortexM33`, modifies LDREX/STREX in
  `execute_thumb32.rs`, adds invalidation hook on writes in
  `src/bus/mod.rs` (all write paths).
- 0b.3 changes `halted`, `wfe_waiting`, `event_flag` from `bool` to
  `AtomicBool` on `CortexM33`. Every read/write site in `src/core/*.rs`
  and `src/lib.rs:128-144` must change.

All three edit `src/core/mod.rs` (the `CortexM33` struct definition)
and at least two edit `execute_thumb32.rs`. 0b.1 is a mechanical
refactor, 0b.3 is a type change touching the same struct. If 0b.1
lands first and adds `ppb: Ppb`, then 0b.3 adds `halted: AtomicBool`,
0b.3 rebases cleanly on 0b.1. Likely fine.

The bigger risk: **these are all premise-shifting refactors on the
hottest path.** `active_core()` is a crosscut; atomizing fields
changes read/write ergonomics; exclusive monitor changes write path.
Doing them in three separate commits is correct for reviewability.
But "~62 call sites" for 0b.1 is a lot — call it 1.5 weeks rather
than 1, and explicitly budget a merge week between 0b.1 and 0b.2 (or
land them on one branch and cherry-pick).

**Action:** Acknowledge in V4 that these sub-phases are sequenced,
not parallel. Add a sentence: "0b.1 must land and stabilize before
0b.2 starts; 0b.3 must wait on 0b.1 but can overlap 0b.2."

## CRITICAL #4 — ExitReason is incomplete

`enum ExitReason { Duration, Stopped, BothWfi, Panic(String) }`

Missing cases that the debugger and test harness both need:

- **Breakpoint hit.** The doc mentions breakpoints at line 164
  ("Breakpoint or fault escalation") but folds them under `Stopped`.
  A caller that issued `stop.stop()` needs to distinguish its own
  stop from a BKPT-induced stop — otherwise `mdrp2354-debug` can't
  tell why `run` returned.
- **Emulator error** (unhandled instruction, fault escalation to
  lockup). Currently implicit under `Stopped` or a panic. A real
  HardFault that the emulator models is not a panic; it's an
  emulator condition the caller may want to inspect state for.
- **Duration elapsed with progress vs. without.** The "both cores
  WFI indefinitely" check at line 331 exits as `BothWfi`. But what
  if one core is WFI and the other is spinning on a memory location
  that will never change (livelock)? Duration fires — caller can't
  distinguish "made progress, time's up" from "stuck but not WFI".
  Probably OK to not split this one; just document.

Suggested enum:

```rust
pub enum ExitReason {
    Duration,                      // quantum budget elapsed
    Stopped,                       // external stop signal
    BothWfi,                       // WFI deadlock detected
    Breakpoint { core: CoreId, addr: u32 },
    Error(EmulatorError),          // fault / unmapped / unhandled instr
    Panic(String),                 // worker thread panic
}
```

Breakpoint is the one the debugger will scream about if absent.

**Action:** V4 must add at least `Breakpoint` and `Error` variants.

## CRITICAL #5 — Benchmark rollback policy is missing

Line 436: "Below 110 MHz: investigate before declaring success." This
is vague enough to be unactionable. If the bench lands at 102 MHz:

- Do we ship ThreadedEmulator but document it as "35% speedup, not
  the full 2×"?
- Do we ship it behind a feature flag?
- Do we NOT ship it and keep single-threaded only, then pivot to
  decode cache?
- Do we keep `src/threaded/*` in-tree but not `pub`, to salvage the
  work?

All four are defensible. The HLD has to pick one.

The non-goal "No feature flags" (line 36) implies the answer is
binary: either it meets the bar or it doesn't ship. Then line 436
should say: "**If < 110 MHz and cannot be fixed in Phase 5: revert
Phase 3–5 commits, leave Phase 0–2 landed (they have standalone
value), and open a decode-cache HLD.**"

Phase 0–2 landing standalone is the safety net. Make it explicit.

**Action:** V4 needs a one-paragraph "rollback plan" section.

## NON-CRITICAL — worth noting, not blocking

### API surface is right, but needs `CoreId` exposed

The caller-visible surface — `Emulator`, `ThreadedEmulator`, `Pacer`,
`StopSignal`, `ExitReason` — is coherent. The conversion API is clean.
One addition needed: if `ExitReason::Breakpoint` is added, `CoreId`
becomes part of the public surface too. Today `CoreId` is internal.
Export it.

### Worker 1 idle during coordinator work

Q4 asked. Answer: on a 2-host-core machine (the realistic deployment —
no one targets this emulator at 1-core hosts), worker 1 spin-waiting
on the barrier while worker 0 does coordinator work **uses the second
core's cycles for nothing**. That's not wasteful in the sense of
blocking other work (you own both cores); it's wasteful in the sense
of host power and thermals. For the target workload (minutes-to-hours
interactive use), that's acceptable. For CI or server batch use, not
ideal — but also not this HLD's concern.

The real question is: can worker 1 do useful work during the
coordinator phase? Yes — PIO stepping, peripheral ticks. But now
you've split coordinator work between workers, barriers get more
complex, and you've reintroduced the contention you tried to
eliminate. Keep it simple; don't optimize this.

**Minor doc suggestion:** add one line acknowledging "worker 1 spins
~100ns per quantum ~= 10% of quantum length". It's budgeted in the
115–125 MHz model but not stated.

### Module layout forecast

Phase 2 creates `src/threaded/`, Phases 3–5 add files. Final layout:

```
src/threaded/
    mod.rs              (re-exports)
    barrier.rs          (SpinBarrier)
    sio.rs              (ThreadedSio)
    memory.rs           (SharedMemory — Phase 1, MISSING FROM TABLE)
    emulator.rs         (ThreadedEmulator)
    worker.rs           (worker loop, spawn)
    stop.rs             (StopSignal)
    exit.rs             (ExitReason — optional, could live in emulator.rs)
    peripherals.rs      (Mutex-wrapped Peripherals — MISSING)
```

The files-changed table on line 478 says Phase 1 changes
`src/memory/mod.rs` (replace). That conflates "shared memory for
threading" with "single-threaded Memory". The plan presumably is
`SharedMemory` lives alongside `Memory`, not replacing it. If that's
wrong and `Memory` becomes atomic-backed even in single-threaded
mode, that's a much bigger change (all the `&self` readers become
`&mut` or need `&AtomicU32` accessors).

**Action:** V4 should either put `SharedMemory` in `src/threaded/`
explicitly, or state "`memory/mod.rs` gains a `SharedMemory` type
alongside `Memory`". As written it reads ambiguous.

### Lock order and the inversion question

Q9 asked whether `clocks < qmi < resets < apb < ahb` handles "reset
controller needs to stop a clock" (which would want `resets < clocks`).
Looking at the actual RP2350 model: the RESETS controller doesn't
*stop* clocks — it asserts reset on peripheral blocks, which have
independent reset signals from the clocks. CLOCKS writes go into
CLOCKS registers; RESETS writes go into RESETS registers. They don't
cross-lock in firmware-typical code.

The firmware pattern is: configure CLOCKS → deassert RESETS → program
peripheral. All three in sequence, each with its own lock, released
before the next. No held-concurrent pattern.

So the stated order is probably fine. The doc should **justify** it
rather than just assert it:

> Lock order justification: RP2350 firmware initializes clocks before
> deasserting resets before programming peripherals (AHB then APB by
> frequency class). The lock order matches this causal chain, which
> means any held-concurrent pattern we've seen in bootrom or target
> firmware traverses the order monotonically.

That also invites "what if a non-firmware-typical pattern emerges" —
at which point `debug_assert` catches it and we reorder. Fine.

**Action:** one sentence of justification in V4.
