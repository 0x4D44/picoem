Date: 2026-04-16
Supervisor: Claude (Opus 4.6) — team lead
Journal owner: Arthur

## Goal

Find and fix whatever stops PicoGUS firmware from processing ISA bus
events fired by the harness. End state: `picogus_diff_rp2040` with
`monkey_island_theme.trace` produces a WAV with non-zero audio.

## Starting state (after PIO INTn routing fix `4944d3d`)

Diagnostic dump after a 5s capped run with 514,667 ISA writes fired:

```
Core 0 PC:        0x20001c42  (active, NOT in sleep_ms)
Core 1 PC:        0x200073d8  (synth function)
PIO0 SM enabled:  0x7         (SMs 0/1/2)
PIO0 INT0_INTE:   0x004       (firmware enables IRQ flag 2 only)
PIO0 INT0_INTS:   0x000
PIO0 INTR:        0xf00       (TXNFULL=0xF, RXNEMPTY=0)
NVIC[0].pending:  0x00000001  (TIMER only)
PSRAM non-zero:   0 bytes
WAV non-zero:     0 frames
```

The ISA events fire but never reach PSRAM. The PIO0 RX FIFO is
always empty (RXNEMPTY=0), suggesting either:
- DMA drains it instantly (where does the data go?)
- The PIO program isn't autopushing (why not?)
- The PIO program doesn't recognize our synthetic IOW waveform

## Plan

1. **Stage 1 (research):** Understand the PicoGUS PIO0 ISA program

4. **Stage 4 (GREEN):** Implement the fix; verify PSRAM populated

## Stage log

### Stage 1 — Research PicoGUS ISA ingestion

**Status:** complete.

Got the PIO0 IOW program source from polpo/picogus v4.0.0:

```
restart:
.wrap_target
    wait 1 gpio IOW_PIN     ; slot 10 — wait IOW high (idle)
    wait 0 gpio IOW_PIN     ; slot 11 — wait IOW falling edge
    jmp pin restart         ; slot 12 — restart if DACK_PIN high (DMA)
read_addr:
    in pins, 10 [3]  side 0b10  ; slot 13 — read 10-bit addr, ADS=1
    nop [3]          side 0b10  ; slot 14
    in pins, 8       side 0b10  ; slot 15 — read 8-bit data
    out X, 32        side 0b00  ; slot 16 — pull condition from FW
    jmp !X restart   side 0b00  ; slot 17
    ...
```

Confirmed: ADS is a PIO-driven output (sideset bit 1, pin 27). Our
harness correctly does NOT touch GPIO 27. Firmware uses
RXNEMPTY-driven IRQ handler on core 1 (or polling) to consume RX FIFO,
splits 18-bit word into 10-addr + 8-data, decodes, pushes "condition"
back via TX FIFO. GUS DRAM writes queue to PIO1 (PSRAM driver).

### Stage 2 — Diagnose where the pipeline breaks

**Status:** complete. **Bug found.**

Added PIO0 SM0 deep-dive diagnostics to `picogus_diff_rp2040.rs`:
CLKDIV, PC, EXECCTRL, INSTR_MEM dump, DACK pin state, FSTAT.

Run results:

```
SM0 CLKDIV raw:   0x00020600  (~2.0 sysclk/PIO-tick)
SM0 PC:           0x0b        (= slot 11 = WAIT 0 GPIO 4)
INSTR_MEM[10]:    0x2084  WAIT 1 GPIO 4
INSTR_MEM[11]:    0x2004  WAIT 0 GPIO 4   ← PIO is stuck here
INSTR_MEM[12]:    0x00ca  JMP PIN, 0x0a
INSTR_MEM[13]:    0x5b0a  IN PINS, 10 [3] side 0b10
DACK (GPIO19):    low  (gpio_in=0x0e420034)
FSTAT:            0x0f000f00  SM0 RX empty, TX empty
```

Hypotheses **rejected** by the data:
- H1 clkdiv too high — clkdiv=2, plenty of time per phase
- H2 DACK high — DACK=0, JMP PIN won't restart-loop
- H3 program not loaded — opcodes loaded correctly at slots 10-15

**The actual mystery:** PIO0 SM0 is stuck at slot 11 (WAIT 0 GPIO 4)
despite the harness driving IOW=0 for 37 cycles per event, 514,667
times. The PIO never sees IOW=0.

Next diagnostic: add a counter that increments every time PIO0 SM0
ticks with `gpio_in bit 4 = 0`. If the counter is 0, the PIO's view
of `gpio_in` never has IOW=0 — meaning gpio_in is being clobbered
between drive_pins and the PIO step.

**Tick counter result:** PIO ticks total 504,317,695, with IOW low
39,463,966 (7.83%). The override merge IS working — PIO sees IOW
low millions of times. Bug is elsewhere.

**SM0 progress counters:** max PC = 0x11 (slot 17), 3.73M PC
advances, but **autopush_count = 0**. SM0 is cycling through the
program but never autopushing.

**SHIFTCTRL diagnostic:** SM0 SHIFTCTRL = `0x80000000` (AUTOPUSH=0,
PUSH_THRESH=32). PicoGUS expects AUTOPUSH=1, PUSH_THRESH=18.

**Write log of SHIFTCTRL:** firmware writes the CORRECT value
`0x012b0000` (AUTOPUSH=1, PUSH_THRESH=18, AUTOPULL=1, PULL_THRESH=9).
Then writes `0x80000000` with **alias=1 (XOR)** twice — intended as
a no-op pair to flip/unflip bit 31 (FJOIN_TX) for FIFO flushing.

**Root cause:** `PioBlock::write32` in
`crates/mdpicoem-common/src/pio/mod.rs` dispatches per-SM register
writes (offsets 0xC8-0x127) to `write_sm_reg(offset, val)` WITHOUT
FORWARDING THE ALIAS. The signature of `write_sm_reg` has no alias
parameter (line 564) — every per-SM write is unconditionally
treated as a plain write, regardless of whether the firmware used
the XOR/SET/CLR alias.

Net effect: the firmware's XOR-alias writes clobber SHIFTCTRL to
`0x80000000`, losing AUTOPUSH and PUSH_THRESH. PIO never autopushes,
RX FIFO stays empty, ISA handler never runs, PSRAM stays empty,
audio is silent.

Affects ALL per-SM registers (CLKDIV, EXECCTRL, SHIFTCTRL, INSTR,
PINCTRL). Per RP2040 datasheet §2.1.2, the entire APB block
including the per-SM register window supports the four alias windows
uniformly.

Also noted: post-reset default of SHIFTCTRL in our model is
`0x000C_0000` (line 112 of sm.rs) instead of silicon's `0xC000_0000`
(FJOIN_RX/TX both set). Not load-bearing for this bug since the
firmware overwrites SHIFTCTRL explicitly. Fix later.
