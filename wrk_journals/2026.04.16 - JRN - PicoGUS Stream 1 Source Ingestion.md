# 2026.04.16 — JRN — PicoGUS Stream 1: Source Ingestion + Symbol Map

## Summary

Stream 1 of the two-stream PicoGUS audio-path investigation. Ingested upstream
v4.0.0 source into `third_party/picogus/upstream/`, mapped every emulator-
observed PC to a function/role, and identified a concrete emulator bug that
fully explains the observed symptom (PSRAM DMA armed, PIO1 SM3 I2S never fed).

Deep notes and the full PC → symbol table live in
[`wrk_scratch/picogus-stream1-symbols.md`](../wrk_scratch/picogus-stream1-symbols.md).

## Actions

1. **Verified upstream identity.** Release ZIP SHA-256 matches the value
   already pinned in `third_party/picogus/VERSION` (`27f34281…`). Shallow
   cloned `polpo/picogus` tag `v4.0.0` with submodules into
   `third_party/picogus/upstream/`. Submodule `rp2040-psram @ 7786c93e`
   matches the VERSION informational line.
2. **Did NOT build firmware.** No ARM toolchain on this host; upstream
   release publishes no `.elf`/`.map`. Per brief instructions, fell back to
   source-reading + byte-pattern matching over `picogus-v4.0.0.bin`.
3. **Confirmed personality layout.** `multifw/generate_ld.cmake` puts first
   personality at FW_ORIGIN `0x8000`. `multifw/fw_memmap_c2ram.ld` places
   `.text` in RAM with `AT > FLASH` — entire personality is flash→SRAM
   copied at boot. Copy table walked; matches prior session's
   `0x100082B4 → 0x200000C0` observation.
4. **Identified audio pipeline end-to-end.** Core 1 runs `play_gus`
   (`gusplay.cpp:110`), sets up PWM slice 4 as a sample-rate timer firing
   `PWM_IRQ_WRAP` → `audio_sample_handler` (`gusplay.cpp:81`). The ISR
   writes samples **directly from CPU** to `pio1_hw->txf[3]` — **no DMA on
   the I2S TX side**. The PIO1 TXF3 MMIO constant (`0x5030001C`) is never
   loaded as a literal in the GUS personality (18 copies of PIO1 base
   `0x50300000` though) — the compiler folds the `+0x1C` into a scaled
   immediate of an `STR`. The "DMA armed for PSRAM but nothing arms TXF3"
   observation is thus **expected upstream behaviour**, not a bug.
5. **Mapped all 11 emulator-observed PCs.**
   - Core 0 five-PC sweep `0x2000_1C58..0x2000_1DDE` lives in
     `handle_iow`/`write_gus` hot decode loop (`picogus.cpp:747`; GUS state
     RMW around `gus_crit` spinlock at `SIO+0x2A00`).
   - Core 0's isolated `0x2000_D628` is a busy-wait loop inside a PSRAM
     PIO-status poll (most likely `pio_spi_write_read_blocking` —
     `psram_spi.h:127`).
   - Core 1's `0x2000_73AE`/`73EA` is `send_midi_bytes` entry +
     DSB-guarded UART0 FR read.
   - Core 1's `0x2000_75E2`/`760C` is pico-sdk `uart_write_blocking` (spin
     on `UART_FR & TXFF == 0`, then `STR` to UART0.DR).
   - Core 1's `0x2000_A088`/`A0D0` is an MPU401 helper prologue + state
     decode (likely `MPU401_Write_Data` or `send_midi_byte`).
6. **Found the emulator gap** —
   `crates/mdrp2040/src/peripherals/pwm.rs:310-316`:

   PWM tick requires BOTH per-slice `CSR.EN` AND a global `EN[slice]` bit.
   On real RP2040 silicon, `PWM_EN` is an alias of the eight per-slice
   `CSR.EN` bits — they are the **same storage**. Pico-sdk's
   `pwm_set_enabled(slice, true)` writes `CSR.EN` only and does not touch
   `PWM_EN`. In our emulator, `PwmRegs::en` stays `0`, so:
   - `is_idle()` returns true (only checks `self.en`) → fast path in
     `Emulator::step` skips `tick_peripherals` → PWM counter is never
     advanced.
   - Even if slow path is active via some other peripheral, the tick's
     per-slice gate `globally_enabled && locally_enabled` blocks the
     counter advance.
   - `INTR[4]` never latches → NVIC[4] never pends → `PWM_IRQ_WRAP`
     never fires on core 1 → `audio_sample_handler` never runs → PIO1 SM3
     TXF3 never gets written → **I2S stays dead**.

## Findings

- **Upstream confirmed**: repo `polpo/picogus`, tag `v4.0.0`, commit
  `4860c2685d5f985f23665ff3ffb05e6bfd569be1`. Our bin is derivable from
  their `picogus.uf2` (same 906 752 B payload after UF2→raw extraction).
- **Bin hash match**: only the ZIP has a published SHA-256 (matches). The
  `.bin` is derived so only bitwise-equivalence is provable, not a
  reproducible independent hash. That's fine — VERSION pins the ZIP.
- **PC coverage**: 11/11 mapped with high confidence (source anchors
  validated by nearby MMIO literal addresses: UART0 base `0x40034000`,
  PADS_BANK0 `0x4002001A`, SIO spinlock literal `0xD0002A01`, PIO0 base
  `0x50200000`).
- **Audio path is CPU-driven, not DMA-driven** — critical correction to
  the round-2 devils-advocate assumption that "something must DMA to
  TXF3". The stall is upstream of the PIO, in the PWM_IRQ delivery to
  core 1.
- **Most-likely emulator gap**: `pwm.rs:310-316` +
  `pwm.rs:168` (`is_idle`). Single fix unblocks the whole chain.

## Assumptions to revisit

- `0x2000_D628` as PSRAM spin is inference from surrounding literals, not
  a hard match. If Stream 2's oracle builds the firmware with symbols we
  should confirm.
- `0x2000_A088`/`A0D0` was pattern-matched to MPU401/MIDI from call-chain
  reasoning (reached from `send_midi_bytes`), but without symbols we
  can't name the function exactly. Either way it's on the MIDI/UART
  path — **not the audio path** — which is what matters for this bug.
- **Did not verify**: that `audio_pio->txf[3] = sample` on RP2040 silicon
  generates exactly one 32-bit write at `0x5030001C`, rather than the
  compiler folding it differently. High confidence from ARMv6-M scaled
  immediate rules (`LDR/STR Rd, [Rn, #imm5<<2]`), but worth a sanity
  check if the PWM fix doesn't resolve the symptom.
