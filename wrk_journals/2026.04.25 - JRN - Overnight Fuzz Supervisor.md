#### Recommendations for next session

- **Reduce M33 batch size to `--fuzz 10000`** in `fuzz-runs/run-m33.sh`.
  `--fuzz 30000` generates ~1.19 M tests per batch ⇒ ~75 min per batch
  on this machine. In an 8h window that's only ~6 batch-end checkpoints.
  At `--fuzz 10000` it'd be ~25 min per batch, ~19 checkpoints — much
  better failure-detection cadence and less work-in-flight to lose if
  a kill event hits mid-batch.
- **Investigate the 04:03 mass kill.** If it's Windows Automatic
  Maintenance, either move the maintenance window or set the drivers
  to "wake the computer" so the kill doesn't trigger. The rc=137 itself
  is recoverable, but the kill is suspicious enough to identify.
- **Consider a dedicated kill-survival wrapper.** The current scripts
  re-launch on rc≠0 within seconds, but if the bash *itself* dies
  (which is what I incorrectly assumed at heartbeat 2) we lose the
  whole window. A simple `while pgrep -x bash | grep run-m33; do
  sleep 60; done; bash fuzz-runs/run-m33.sh &` outer loop would survive
  bash death.
- **Don't restart probes mid-night unless they're confirmed dead.** The
  USB-bus exclusivity makes duplicate launches extra-painful.
