## Progress

### Step 1 — Investigation

**Finding that changes the framing:** The `isr_tail_chain_pendsv_systick`
oracle scenario does NOT actually exercise tail-chain transitions. The
shared `HANDLER_BASELINE` (10 halfwords at HANDLER_OFFSET=0x044) ends in
`bkpt #0` at halfword [4], which halts the core for mailbox readback.
No EXC_RETURN is ever issued. With both PendSV + SysTick pending at the
same priority, arbitration picks the lower exception number (PendSV) —
its handler runs, writes the mailbox CYCCNT, BKPTs. SysTick never
services.

So the previous session's diagnosis ("EMU's path is faster than silicon
because it skips the tail-chain state-machine overhead in
exit_exception → re-entry") can't apply here: `exit_exception` is
never called. The HW=19 / EMU=15 delta on this scenario must be caused
by something else — most likely pre-armed SysTick's ICSR.PENDSTSET
affecting HW arbitration timing that EMU doesn't model.

**Implication for this task:**

1. The approximate tail-chain IS a real gap in the emulator (exit_exception
   does full unstack then the top-of-loop check re-enters; a proper ARMv8-M
   tail-chain on EXC_RETURN with a pending higher-priority exception skips
   both unstack and re-stack at ~6 cycles instead of ~24). Fix still
   valuable on its own merits.
2. The fix will NOT close the `isr_tail_chain_pendsv_systick` HW/EMU
   delta — I'll log that as a separate tech_debt item with the honest
   diagnosis (likely pre-armed SysTick arbitration timing).
3. TDD: write a unit test that exercises EXC_RETURN with a pending
   exception directly, not an ISR oracle scenario.

### Step 4 — Implementation (`crates/mdrp2350/src/core/exceptions.rs`)

Three additions, no changes to public API:

1. **Tail-chain speculation block** in `exit_exception` right after
   sync_sp_to_banked. Peeks stacked xPSR at sp+28 to determine the
   post-pop IPSR (handles nested return correctly), temporarily swaps
   self.regs.xpsr's IPSR field, clears active tracking (ppb
   clear_active for external IRQs; IPSR swap covers system exceptions
   since execution_priority consults IPSR, not nvic_iabr), then calls
   `pick_tail_chain_target`. If a tail-chain candidate exists, jumps
   to `activate_tail_chain` and returns 6 cycles. Otherwise restores
   IPSR and falls through to the existing unstack. The existing
   `clear_active` at end-of-function is removed (moved up into the
   speculation block).

2. **`pick_tail_chain_target`** — shares arbitration logic with
   `try_take_any_pending_exception` (NMI unconditional; priority +
   exc-num tie-break over PendSV / SysTick / highest pending external
   IRQ); adds the `can_preempt` gate to ensure the candidate actually
   preempts post-pop priority.

3. **`activate_tail_chain`** — dispatch cleanup (clear pending for
   system exc via ICSR; clear NVIC_ISPR + set NVIC_IABR for external
   IRQ), update IPSR, set self.regs.r[14] = exc_return (preserve
   EXC_RETURN so the new handler's eventual return unstacks to the
   original pre-emption state), fetch vector, set PC. Returns 6.

### Step 7 — Investigation: real cause of `isr_tail_chain_pendsv_systick` delta

Added a scratch test `test_investigate_cold_vs_tail_chain_emu_cyccnt` in
`crates/mdpicoem-harness/src/isr_scenarios.rs` (tests module) that
replicates the EMU-side scenario pipeline for both scenarios and
prints the mailbox CYCCNT values.

Current output (with tail-chain fast path landed):
```
isr_pendsv_cold                  mailbox_cyccnt = 22
isr_tail_chain_pendsv_systick    mailbox_cyccnt = 15
delta (cold - tail)              = 7
HW reference (previous session)  = 19 for both
```

Cold is now +3 vs HW=19 (previous session reported +6, so tail-chain
fast path may have trimmed 3 cycles from cold too — uncontrolled
variable, can't confirm). Tail-chain is still -4.

**Root cause identified — SysTick CVR=0 off-by-4 bug.**

`Ppb::systick_advance` at `crates/mdrp2350/src/bus/ppb.rs:743`:

```rust
loop {
    if rem <= self.syst_cvr { self.syst_cvr -= rem; break; }
    rem -= self.syst_cvr + 1;      // "consume cvr cycles to hit 0 + 1 reload cycle"
    self.syst_cvr = self.syst_rvr & SYST_24BIT_MASK;
    self.syst_csr |= SYST_CSR_COUNTFLAG;
    if TICKINT: pend_systick();
    if (self.syst_rvr & SYST_24BIT_MASK) == 0 { break; }
}
```

ARMv8-M §B11.2.1 counter operation:
- When CVR transitions to 0, COUNTFLAG set + pend_systick (if TICKINT).
- On the **next** tick after CVR=0, CVR reloads from RVR (no pend).
- Subsequently CVR decrements each tick until it hits 0 again.

For `cvr > 0` at start: silicon takes `cvr` ticks to fire (countdown
to 0), plus 1 more tick to reload. EMU's `cvr + 1` formula matches —
EMU folds the fire and reload into one consumption block. OK.

For `cvr == 0` at start (just enabled, or just written): silicon
takes 1 tick to reload (no fire), then `rvr` more ticks to count
down and fire. Total: `rvr + 1` ticks to first fire. EMU's `cvr +
1 = 1` tick is WRONG by `rvr` cycles.

In the tail-chain scenario:
- Preamble writes SYST_CVR=0 (clears CVR), then SYST_CSR=ENABLE.
- First main instruction executes → `systick_advance(1)` → EMU
  treats `cvr=0, rem=1` as an immediate underflow → PENDSTSET=1
  set after main[0], 4 cycles earlier than silicon.
- At next instruction boundary, SysTick dispatches (preempts thread).
- Main never reaches [2] (the CYCCNT=0 reset) on EMU. Handler reads
  "cycles since scenario start" (12 entry + 3 handler prologue = 15).
- On silicon, SysTick fires 4 cycles later — by then main has either
  run further (reaching [2] and resetting CYCCNT, or [5] and pending
  PendSV first). HW=19 is consistent with CYCCNT reset at [2] +
  further main instructions + exception entry.

**Fix scope:** `Ppb::systick_advance` — add a "reload-without-fire"
step when CVR=0 at the start of an advance. Small (~5 lines),
localized, testable via the existing systick unit tests.

### Step 8 — Fix the CVR=0 bug

Added "reload-without-fire" block at top of `systick_advance` at
`crates/mdrp2350/src/bus/ppb.rs`:

```rust
if rem > 0 && self.syst_cvr == 0 {
    self.syst_cvr = self.syst_rvr & SYST_24BIT_MASK;
    rem -= 1;
    if self.syst_cvr == 0 { return; }  // RVR=0 edge: counter stopped
}
```

Two regression tests added:
- `test_systick_cvr_zero_reloads_without_fire_on_first_tick` — with
  CVR=0, RVR=4, delta=1: CVR must reload to RVR, no fire.
- `test_systick_cvr_zero_rvr_zero_counter_stops` — CVR=0, RVR=0:
  counter never fires (ARMv8-M §B11.2.1).

Result after bug 1 fix: tail-chain mailbox CYCCNT = 22 (was 15).
Cold scenario unchanged at 22. Both now at +3 vs HW=19, unified
residual matching the cold-ISR gap.

### Step 9 — Second systick bug discovered, and deferred

While writing the new regression test, found a second silicon-
semantic gap in `systick_advance`: the `rem <= cvr` branch does
`cvr -= rem` and doesn't fire when the result is exactly 0.
Silicon fires on the cvr→0 transition regardless of whether
reached by decrement or by a multi-cycle subtraction.

Attempted bug 2 fix: add the fire in the `rem <= cvr` branch.
Silicon-accurate in isolation, but interaction with the cold-ISR
cycle-model residual (HLD §9, main instruction cycle costs over-
count by ~3 cycles) caused tail-chain's mailbox to drop from 22
(+3 vs HW) to 16 (-3 vs HW). Split the unified ISR oracle residual
into +3 (cold) / −3 (tail-chain) — worse oracle signal.

Reverted bug 2 fix; logged in tech_debt with the note "re-apply
once cold-ISR residual is closed". Kept the regression test
adjusted to assert the current (non-silicon-accurate) behaviour so
future re-application of the fix produces a loud test-diff signal.
