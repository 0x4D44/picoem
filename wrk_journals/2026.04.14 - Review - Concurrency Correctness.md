# Concurrency & Correctness Review — Threaded Dual-Core Emulation HLD

Reviewer: design-review (concurrency/correctness focus)
Document reviewed: `d:\language\mdrp2354\wrk_docs\2026.04.14 - HLD - Threaded Dual-Core Emulation.md` (v1.0.0)
Date: 2026-04-14

## Summary

The HLD proposes a workable threading model but glosses over several load-bearing
concurrency details. The biggest problems are: (a) word-level atomicity is broken
under a byte-atomic backing store, which violates Armv8-M's single-copy-atomicity
guarantee and will break common firmware idioms (flag polling, SIO spinlock
handshake, Ring 3 "double-buffered atomic write"); (b) LDREX/STREX and exclusive
monitors are absent from the design entirely and today are stubs — threaded mode
makes that absence catastrophic rather than merely wrong; (c) the PPB, NVIC and
exception state are shared via `Bus` today and indexed by `active_core()`, which
the design does not address; (d) the barrier + mutex topology admits at least
two deadlock paths on panic. Details below.

## ISSUE 1: AtomicU8 backing violates Armv8-M single-copy-atomicity for aligned u16/u32

**Severity:** CRITICAL
**Section:** §3 Memory model
**Problem:**
Armv8-M Architecture Reference Manual (DDI 0553) §B7.2 guarantees single-copy
atomicity for naturally-aligned byte, halfword and word accesses. Firmware relies
on this — every Cortex-M RTOS in existence (FreeRTOS, Zephyr, ThreadX) plus
hand-rolled code uses volatile `uint32_t` and `uint16_t` reads as atomic
snapshots of shared state without any explicit guard. The pico-sdk
`multicore_fifo_*` helpers, spinlock helpers, and the bootrom itself depend
on this.

The proposed `read16` / `read32` do two/four independent `Relaxed` loads on
`AtomicU8` and concatenate. On x86 this may happen to be a single `mov` in
release builds if LLVM recognizes the pattern, but it is not guaranteed —
and on any host where the bytes end up in different cache lines (crossing
64B), or the compiler elects to load them separately, you will observe torn
values that **no real Cortex-M33 program would see**.

Concrete breakage scenario (common in firmware):
```
Core 1 writes *state = 0xDEAD_BEEF   (one aligned STR)
Core 0 polls:   if (*state == 0xDEAD_BEEF) { ... }
```
Real hardware: either Core 0 sees 0 or 0xDEAD_BEEF. Proposed design: Core 0
may see 0x0000_BEEF, 0xDEAD_0000, 0xDE00_BEEF, etc. The firmware proceeds
into the "ready" path with partial data. You will chase this bug for days
because it will only reproduce occasionally in threaded mode and never in
single-threaded mode — and it is not a bug in the firmware.

The HLD's claim that "this matches a relaxed memory model" is **wrong**. A
relaxed memory model still provides single-copy-atomicity at the load/store
granularity the architecture defines. DMB/DSB order operations; they do not
fuse multi-byte operations into atomic ones. There is no DMB/DSB pattern that
rescues a word-sized load that tore mid-flight.

**Proposed solution:**
Back memory with `[AtomicU32]` (and a parallel `[AtomicU16]` view, or compute
halfword/byte atomically from the word). Require 4-byte alignment for the
underlying storage. For aligned u32 reads/writes: single atomic op. For aligned
u16 reads/writes: atomic-CAS loop that reads the containing word, replaces one
half, and writes back (on x86 the raw u16 load/store is still atomic — but the
write needs to preserve the other half without tearing the RMW). For u8:
same CAS-on-word approach. Unaligned accesses can fall back to the current
byte-at-a-time scheme **only if** we also track that Armv8-M permits the core
to take a UsageFault on unaligned u16/u32 access (CCR.UNALIGN_TRP) and real
Cortex-M33 firmware essentially never does unaligned shared-memory accesses.

Alternative: use `core::sync::atomic::AtomicU32` storage and expose `read8` /
`read16` / `read32` that all ultimately go through a word load, with masking.
This is what QEMU MTTCG does for its target memory backing. It is not free
but `mov` + shift + mask on x86 is still ~1-2 cycles.

## ISSUE 2: LDREX/STREX are stubs — threaded mode turns this from "wrong" into "deadlocking"

**Severity:** CRITICAL
**Section:** §3 / not addressed anywhere
**Problem:**
Inspection of `crates/mdrp2354/src/core/execute_thumb32.rs:709-738` shows
LDREX is treated as plain LDR and STREX always returns success (Rd=0). This
is documented as "Phase 1 stub". In single-threaded mode it *happens* to work
for a lot of firmware because there's no other core racing — the load and the
store are adjacent in the instruction stream with nothing in between.

In threaded mode this is now **actively broken** in two ways:

1. `__atomic_compare_exchange` idioms and pico-sdk's `spin_lock_unsafe_blocking`
   fallback path (the one used when SIO hardware spinlocks are exhausted)
   implement spinlocks using LDREX/STREX. Our STREX always succeeds, so
   two cores can both "acquire" the same software spinlock simultaneously.

2. The bootrom's `multicore_launch_core1` uses LDREX/STREX around the
   handshake state machine in non-SIO paths. Same double-acquire problem.

3. The Rust core library's `AtomicU32::compare_exchange` on Cortex-M33
   compiles to LDREX/STREX loops. Any firmware written against Rust's
   `core::sync::atomic` loses all atomicity guarantees.

The HLD does not mention exclusive monitors at all. This is the
**single biggest gap** in the document.

**Proposed solution:**
Implement a global exclusive monitor in shared state:
```rust
struct ExclusiveMonitor {
    // Per-core: address of the latest LDREX-tagged region, or None.
    // Address is word-aligned and represents the "exclusive reservation
    // granule" (ERG) — Armv8-M requires at least 8 bytes, we pick 8.
    tags: [AtomicU64; 2],   // hi bit = valid, low 32 = addr
}
```
- LDREX: store `(addr & !7) | VALID` into `tags[core]`.
- STREX: CAS on the shared word — if the monitor for *this* core is still
  valid and the write succeeds via atomic CAS on `[AtomicU32]` memory, return
  success (0) and clear `tags[core]`. Otherwise clear and return failure (1).
- Any store by *any* core that falls within another core's tagged granule
  invalidates that core's monitor. Practical implementation: before every
  STR/STM/STREX write to shared memory regions, do
  `tags[other_core].compare_exchange(tag_of(addr), 0)` — if it matched,
  invalidate.
- CLREX clears `tags[core]`.
- Context switch / exception entry clears the monitor (Armv8-M §B7.3).

Cost: ~2 atomic ops per shared-memory store in the hot path. Acceptable on
x86. This must be implemented regardless of threaded vs single-threaded, but
threaded mode is where not having it becomes a correctness hole rather than
a "stub we get away with".

## ISSUE 3: DMB/DSB → `fence(AcqRel)` is almost right but not sufficient; ISB is wrong

**Severity:** IMPORTANT
**Section:** §3 memory model, accuracy note
**Problem:**
Two sub-issues.

(a) DMB/DSB translation. The HLD says "DMB/DSB translate to host fence(AcqRel)".
This is **necessary but not sufficient**. On x86, `fence(AcqRel)` compiles to
a compiler fence only — no instruction is emitted, because x86 is already TSO.
That is correct for ordering `mov`-backed loads/stores, **but** our memory
backing uses `Relaxed` atomics per ISSUE 1. `Relaxed` atomics in LLVM's memory
model explicitly tell the optimizer "you may reorder this freely up to the
next fence." An `AcqRel` fence between a `Relaxed` store and a `Relaxed` load
in the same thread does order them — but a **cross-thread** observation of
ordering requires the *other* thread to also issue a fence, which Cortex-M33
firmware only does if it explicitly uses DMB. So today an M33 firmware doing:
```
Core 1: store data; DMB; store flag
Core 0: load flag (no DMB); load data
```
...works on real M33 under the weakly-ordered memory rules + transitive
"release→acquire by observation" reasoning. Under the proposed model, Core 0
never issues a fence, so our translation of Core 1's DMB does nothing
observable for Core 0. You can only fix this by either (a) using `SeqCst`
on all shared memory ops (expensive), or (b) using `Acquire` on all loads
and `Release` on all stores (the C++11/Rust model that corresponds most
closely to Armv8-M semantics with DMB on every store).

We should use `Acquire`/`Release` uniformly on shared-memory atomic ops, and
treat DMB/DSB as `SeqCst` fences (belt-and-braces, since real DSB has
stronger semantics than DMB). This costs basically nothing on x86 — acquire
loads and release stores are plain `mov` on TSO.

(b) ISB. The HLD does not address ISB. ISB flushes the pipeline and
guarantees that subsequent instructions see the effect of CPSR/CONTROL/MSR
writes, MPU/SAU reconfigurations, and VTOR changes. In an interpreter these
all take effect immediately on the next instruction, so ISB as a no-op is
correct for most cases — **except** for shared state. If Core 0 changes
something Core 1 needs to observe instruction-fetch-side (e.g., writes new
vector-table pointer, then sends SEV to wake Core 1, Core 1 does ISB before
branching into the new handler), Core 1's ISB has nothing to serialize
against because we have no i-cache model. The HLD's "no cross-thread cache
simulation" (§"What this does NOT do") correctly covers this, but the
interaction with VTOR, CONTROL, and MPU writes to shared PPB (see ISSUE 6)
must be re-examined.

**Proposed solution:**
- Use `Acquire` on all shared-memory loads and `Release` on all shared-memory
  stores in the threaded path.
- Translate DMB → `fence(SeqCst)`, DSB → `fence(SeqCst)`, ISB → `fence(SeqCst)`
  (the last one is belt-and-braces but cheap).
- Document explicitly that writes to a core's own PPB are not visible to
  the other core without an SIO/memory-mediated synchronization — which
  matches real hardware (PPB is per-core).

## ISSUE 4: PPB is per-core and indexed by `bus.active_core()` — threaded mode breaks this utterly

**Severity:** CRITICAL
**Section:** §2 shared state layout (not addressed)
**Problem:**
`crates/mdrp2354/src/bus/mod.rs:330` defines `active_core()` as
`if self.contention_check_active { 1 } else { 0 }`. This is a single-threaded
hack: it flips a flag on `Bus` between core 0's step and core 1's step. The
PPB register file (`bus.ppb[0]`, `bus.ppb[1]`) is per-core as the real
hardware requires, but the *selection* of which one to access is done via
a shared mutable field on `Bus`.

In threaded mode:
- `Bus` is behind a mutex (per HLD §5).
- Two threads each call `bus.read32(0xE000ED08)` simultaneously to read
  their own VTOR.
- Both threads will go through `self.ppb[self.active_core()]` — but
  `active_core()` returns whatever `contention_check_active` happened to be.
  This is wrong by construction.

This affects:
- VTOR reads/writes (every exception entry/exit)
- NVIC stubs
- SCB/CFSR/HFSR/SHCSR (`crates/mdrp2354/src/core/mod.rs:82-90`, exception
  delivery paths in `crates/mdrp2354/src/core/exceptions.rs:87,142,161,171,179,188,213`)
- SAU/MPU lookups (`crates/mdrp2354/src/core/exceptions.rs:213` — every TT
  and every memory access with SAU enabled)
- CPACR (FPU enable check, hit on every FP instruction)

Additionally the coprocessor module reads `bus.ppb[bus.active_core()].cpacr`
on every FPU instruction (`crates/mdrp2354/src/core/coprocessor.rs:10`).
In threaded mode, two cores executing FP instructions will both query via
`active_core()` and get whichever one the other thread last set.

**Proposed solution:**
PPB access must be by explicit core ID, not by a shared mutable state flag.
Refactor before threading lands:

1. `Bus::read32(addr, core_id)` and `Bus::write32(addr, val, core_id)` take
   the core ID explicitly. Remove `contention_check_active` and `active_core()`.
2. Alternatively, split `Bus` into `SharedBus` (memory, peripherals, SIO —
   actually shared) and per-core `CoreBus` views that own `&mut Ppb` and
   hold a reference to `SharedBus`. Each worker thread owns its own
   `CoreBus`. Memory accesses go through `SharedBus` (which is `Arc`-shared
   and uses atomics or internal mutex per region). PPB accesses are local.
3. `Arc<[Mutex<Ppb>; 2]>` if we must share PPB for coordinator visibility
   (the coordinator might need to inspect PPB to decide who to wake on
   timer interrupt) — but inside the worker's step, only that worker's
   PPB mutex is ever held, so no contention.

This refactor is load-bearing and should be a prerequisite phase for the
threading work, not deferred.

## ISSUE 5: Interrupt dispatch is undefined — who decides which core takes an IRQ?

**Severity:** CRITICAL
**Section:** §6 quantum barrier protocol, coordinator responsibilities (not addressed)
**Problem:**
On a real RP2350:
- External peripherals (UART, I2C, SPI, PIO, timers) drive a set of 64 IRQ
  lines. Each core has its own NVIC that independently observes those lines
  (the RP2350 hardware fans out the peripheral IRQ lines to both NVICs; each
  NVIC has its own ENABLE mask). Either core can have the IRQ enabled,
  disabled, or masked by PRIMASK / BASEPRI.
- When a peripheral raises an IRQ, **both NVICs see it**. Typically only one
  is enabled via NVIC_ISER, so only that core takes the handler. If both are
  enabled, both take it (real hardware does fan-out).
- SIO-generated events (FIFO/DOORBELL/MTIME_MATCH) are per-core and only
  the target core's NVIC observes them.

The HLD says "the coordinator handles WFI/WFE wake + timer tick" (§1) but
does not address:

1. Who runs the "are there pending interrupts I should take?" check on
   each core? In single-threaded mode today, this check would happen each
   step via PPB queries. In threaded mode, the worker thread must do it
   inside its quantum loop, but the interrupt-pending state lives in a
   shared data structure that a peripheral mutation (from the other core
   or the coordinator) just wrote.

2. The `event_flag[0..1]` for WFE wake is a `[bool; 2]` field on `Bus`
   (`crates/mdrp2354/src/bus/mod.rs:87`). `signal_sev` writes both
   (`crates/mdrp2354/src/bus/mod.rs:355-358`). In threaded mode, Core 0
   doing SEV while Core 1 is simultaneously checking `event_flag[1]` inside
   its `wfe()` (`crates/mdrp2354/src/core/mod.rs:174-183`) is a data race
   on plain `bool`. The wake check in `Emulator::step` at `lib.rs:142-147`
   is in the single-threaded path — there is no equivalent in the HLD for
   threaded mode.

3. MTIME compare match (`crates/mdrp2354/src/sio/mod.rs:397-411`) runs in
   `tick_mtime()`, called from `Emulator::step`. Under the HLD, this runs
   on the coordinator thread. The coordinator sets `mtime_match_asserted[core]`
   which the worker thread then needs to observe and turn into an exception.
   No memory ordering specified.

**Proposed solution:**
- All interrupt-pending state must be `AtomicBool` / `AtomicU64`.
- Each worker thread, at a well-defined point in its quantum loop (e.g.,
  between instructions, or at least at barrier arrival), calls
  `check_pending_interrupts(core_id)` which reads the shared IRQ-pending
  bitfield with `Acquire`, ANDs against its local NVIC enable mask (held
  in its own PPB), and dispatches via `enter_exception` if any match.
- SEV: `signal_sev()` becomes an atomic RMW that sets both event bits with
  `Release`. The WFE check in the worker is `Acquire`.
- MTIME: compare match writes to an `AtomicBool` per core with `Release`.
  Worker reads with `Acquire` in its pending-interrupt check.
- Document explicitly: interrupts are delivered at most one-per-quantum of
  latency. Real hardware is ~1 cycle; we drift by up to `Q` cycles. This
  matches the HLD's accuracy trade-off but needs to be called out.

## ISSUE 6: Barrier deadlock on worker panic; no poison/timeout path

**Severity:** IMPORTANT
**Section:** §6 quantum barrier protocol
**Problem:**
`std::sync::Barrier::new(3)` blocks until all three threads arrive. If one
worker panics (hit a UsageFault we don't model correctly, stack overflow,
arithmetic issue in the interpreter, LLVM bug, anything), that worker never
reaches the barrier. The other worker and the coordinator wait forever.
`Barrier` is not poison-aware.

Consequences:
- `paced_bench --threaded` hangs silently instead of erroring.
- `cargo test --package mdrp2354 threaded_` hangs CI.
- Downstream users running in threaded mode see their app hang on any
  unexpected emulator bug, with no recovery.

The HLD acknowledges this in §"What this does NOT do": "panic in a worker
panics the process. Matches existing single-threaded behavior." This is
wrong — in single-threaded behavior, a panic in `step()` unwinds back to
`run()` back to the caller. In threaded mode, only the *worker thread*
unwinds; the coordinator sits in the barrier. `thread::spawn` does not
propagate panics to siblings.

**Proposed solution:**
Replace `std::sync::Barrier` with a custom barrier that supports poisoning:
```rust
struct QuantumBarrier {
    state: Mutex<BarrierState>,
    cv: Condvar,
}
struct BarrierState {
    waiting: u8,
    generation: u64,
    poisoned: bool,
}
```
Or use `crossbeam_utils::sync::WaitGroup` with an explicit poison flag
checked on wait. Workers register a panic hook that sets `poisoned = true`
and notifies all. Coordinator checks poison on wake and unwinds cleanly.

Alternatively: use `std::thread::JoinHandle` with a top-level `catch_unwind`
wrapper in each worker:
```rust
let result = std::panic::catch_unwind(AssertUnwindSafe(|| worker_loop(...)));
if result.is_err() { barrier.poison(); }
```
And have the coordinator periodically check (or use a timeout on the barrier
wait with `Condvar::wait_timeout`).

Either way, the HLD should specify one of these. Current design ships a hang.

## ISSUE 7: SIO FIFO semantics — ArrayQueue is correct shape but firmware expects specific overflow/underflow behavior

**Severity:** IMPORTANT
**Section:** §4 SIO redesign
**Problem:**
The current `Fifo` (`crates/mdrp2354/src/sio/mod.rs:14-65`) is 8-deep and
models:
- Full → push drops, sets WOF sticky flag (bit 2 of FIFO_ST).
- Empty → pop returns 0, sets ROE sticky flag (bit 3 of FIFO_ST).
- VLD/RDY bits reflect instantaneous state.

Replacing with `crossbeam_queue::ArrayQueue<u32>` gets the bounded capacity
right but loses the sticky flag semantics as a natural byproduct. The HLD
does not address:

1. How are WOF/ROE sticky flags implemented? They are per-core, not per-FIFO,
   and must be observable from the writing core (WOF) or reading core (ROE).
   Two `AtomicBool` arrays of length 2, updated via `Release` when push fails
   or pop fails. Fine — just needs to be stated.

2. FIFO_ST.VLD and RDY are computed from FIFO state. `ArrayQueue::is_empty`
   and `is_full` are snapshot queries and race with concurrent `push`/`pop`.
   This is actually fine semantically — real hardware also has these flags
   race because the other core could be pushing/popping at the exact moment
   you read FIFO_ST. Firmware uses VLD/RDY to *gate* a push/pop attempt and
   then handles failure via the actual push/pop result. OK. But the HLD
   should call this out.

3. The `pending_fifo_event` mechanism at `sio/mod.rs:88-89,259-273`:
   successful push sets a sticky field, and `Bus::write32` on SIO region
   drains it and sets `event_flag[receiver]`. In threaded mode this whole
   handshake is racy: worker A pushes to FIFO, drains pending_fifo_event,
   sets `event_flag[B]`; between those two steps worker B could have
   checked event_flag and gone to sleep. Needs a single atomic operation:
   push succeeds → fetch_or `event_flag[other]` with release, done.

4. Doorbells (`sio/mod.rs:217`): `doorbell_pending[1 - core] |= ...` is a
   RMW on a shared u8. In threaded mode this is a data race. Must become
   `AtomicU8::fetch_or`.

5. Interp registers (`sio/mod.rs:103-104`): per-core, so no cross-thread
   sharing on the data — but if the HLD wraps the entire `Sio` behind a
   single mutex (§5 implies peripheral mutex may cover SIO?) the lock is
   contended on every SIO access, which is *every cycle* of any firmware
   that uses `sio_hw->gpio_out`. That is the hot path and cannot be a
   global mutex.

**Proposed solution:**
- `ThreadedSio` is **not** wrapped in a mutex. It uses lock-free primitives
  internally:
  - FIFOs: `ArrayQueue<u32>` (crossbeam).
  - WOF/ROE flags: `[AtomicBool; 2]`.
  - Spinlocks: `[AtomicU32; 1]` (single word, bit per spinlock) with CAS
    for acquire. Current implementation already uses a single `u32` bitmask
    (`sio/mod.rs:85,298`); just wrap in `AtomicU32`.
  - Doorbells: `[AtomicU8; 2]`.
  - GPIO out/oe: `AtomicU32`.
  - Dividers: per-core, only ever touched by that core's worker — can
    remain plain data owned by each worker. Move out of `Sio` into a
    per-core struct.
  - Interpolators: same — per-core, worker-owned.
  - MTIME: `AtomicU64` for counter, `[AtomicBool; 2]` for match-asserted.
  - `pending_fifo_event` mechanism: eliminate. Fold the event signal into
    `fifo_wr()` directly: on successful push, atomic-OR into
    `event_flag[other_core]` with release. Drop the intermediate field.
- CPUID register (offset 0): in threaded mode, worker 0 returns 0, worker 1
  returns 1. The current `read32(offset, core)` signature already does this
  correctly — just ensure the threaded bus passes the right `core` id.

## ISSUE 8: Peripheral mutex + interrupts — head-of-line blocking

**Severity:** IMPORTANT
**Section:** §5 peripheral access via Mutex
**Problem:**
The HLD proposes a single global `Mutex<Peripherals>` wrapping "UART, SPI,
I2C, PWM, ADC, etc." Scenario:
- Core 0 does a UART register write, holds the mutex.
- Between acquiring and releasing, Core 0's host thread is pre-empted by
  the OS scheduler (possible under load — we can't guarantee otherwise).
- Meanwhile, Core 1 hits a timer interrupt deadline for MTIMER. Core 1's
  worker thread calls `enter_exception` which reads VTOR (PPB — OK, per-core)
  but then fetches the vector from memory, which involves reading flash
  through the peripheral region if vectors live in XIP. If the peripheral
  mutex covers the XIP bus path (depending on implementation), Core 1
  blocks on a mutex held by a preempted thread.

Worse case: Core 0 holds the mutex and calls into a peripheral that
performs a blocking operation (e.g., the UART model times out on a
transmit). Core 1 is starved for multiple quanta.

Additionally, the design puts peripherals behind a single coarse lock. PWM
registers are polled heavily by motor control firmware, typically from both
cores simultaneously. Lock contention will dominate.

**Proposed solution:**
- Sharding: one mutex per peripheral block (UART0, UART1, SPI0, ...) instead
  of one global lock. Acquire is on the hot-path struct, not the whole
  peripheral subsystem.
- Or: move peripheral state into `Arc<PeripheralShard>` with internal
  fine-grained locking / lock-free where appropriate.
- Exception vector fetch **must not** pass through any peripheral lock.
  Vectors live in ROM / SRAM / flash-via-XIP — all of those should be in
  the `SharedMemory` atomic-backed region, accessed lock-free.
- Document the constraint: peripheral handlers must be short and
  non-blocking. Add an assertion that peripheral handlers do not call back
  into `SharedMemory` paths that could recurse into a lock.
- Profile before committing: the HLD says "if profiling shows contention,
  we shard". Invert this: shard from day one; coalescing later is easier
  than splitting a hot lock under production load.

## ISSUE 9: `CortexM33.halted` / `.wfe_waiting` racy on cross-core write

**Severity:** IMPORTANT
**Section:** §2 (not addressed)
**Problem:**
`CortexM33` contains `halted: bool` and `wfe_waiting: bool` as plain
Rust bools (`crates/mdrp2354/src/core/mod.rs:39,41`). The HLD moves each
`CortexM33` into its own worker thread — good, that means the worker owns
its own bools. **But**:

1. `halted` is toggled by `halt()` / `wake()` (`core/mod.rs:150-164`).
   In the RP2350 multicore protocol, Core 0 wakes Core 1 via the
   `multicore_launch_core1` SIO FIFO handshake, then writes to Core 1's
   state to un-halt it. If the wake is expressed as Core 0 calling
   `self.cores[1].wake()` (as in single-threaded code today), Core 0's
   thread is now writing into Core 1's CortexM33 while Core 1's thread
   may be reading `halted` in its step loop (`core/mod.rs:69-71`). Data
   race on plain bool. UB.

2. `wfe_waiting` is set by the owning core's `wfe()` but read by the
   single-threaded `Emulator::step` wake check for the *other* core when
   SEV fires (`lib.rs:142-147`). In threaded mode, the wake check must
   move to each worker and read its own `wfe_waiting` plus the shared
   `event_flag`. The bool is fine if only the owning thread ever writes
   it — but we must ensure the cross-core wake protocol doesn't write to
   the other core's `wfe_waiting`.

3. `halted` is read by `Emulator::step` (`lib.rs:130`) to skip Core 1
   contention tracking. That read goes away in threaded mode, but
   elsewhere (debugger, test harness) still reads it cross-thread.

**Proposed solution:**
- Change both `halted` and `wfe_waiting` to `AtomicBool` on `CortexM33`.
  Owner thread uses `Relaxed` for writes and reads; other threads use
  `Acquire` / `Release` as appropriate.
- Cross-core wake goes through SIO (the real mechanism) or through an
  explicit message to the coordinator which then signals the target
  worker. Don't have thread A mutate thread B's `halted` directly.
- Similarly audit `stall_cycles`, `it_state`, `secure`, `dcp_data`,
  `pending_fault`, `rcp_salt*` for cross-core access patterns — most
  are per-core and owner-only in practice, but verify.

## ISSUE 10: Clock consistency — `clock_cycles` staleness is OK, but MTIME coupling isn't

**Severity:** NICE-TO-HAVE (for clock_cycles itself) / IMPORTANT (for MTIME coupling)
**Section:** §2, §6
**Problem:**
The HLD has `clock_cycles: Arc<AtomicU64>` advanced by the coordinator at
end-of-quantum. Worker at cycle N+5 reads clock=N. In isolation this is
fine — `DWT->CYCCNT` style reads tolerate this staleness; firmware using
cycle counters for loose timing doesn't care about sub-quantum precision.

**But** MTIME (`bus.sio.mtime`) is incremented once per `Emulator::step` in
single-threaded mode (`lib.rs:156`, `sio/mod.rs:397-411`). MTIME is the
RP2350 platform timer used by RTOS tick sources — accuracy matters for
scheduling. In threaded mode:

1. Advanced by coordinator at end-of-quantum by `Q` ticks? Quantum granular.
2. Or advanced by one worker? Which? Then the other worker reads stale.
3. Or shared `AtomicU64::fetch_add(1)` per cycle? That defeats the
   threading model — two cores racing fetch_add on the same cacheline.

MTIME compare match drives interrupts. If MTIMECMP = 150 and quantum = 150,
worker can be at cycle 140 locally while MTIME is at 0 (coordinator hasn't
advanced yet). The compare match fires one full quantum late. 150 cycles at
150 MHz = 1 µs. For most firmware fine; for tight control loops (motor
commutation), noticeable jitter.

**Proposed solution:**
- `clock_cycles` advances per-quantum from coordinator — accept staleness,
  document it.
- MTIME advances per-quantum from coordinator, by `Q` ticks. Document that
  MTIME resolution in threaded mode is `Q` cycles rather than 1.
- MTIME compare match check runs in the coordinator after each advance.
  Coordinator sets per-core `mtime_match_asserted` atomic flag with
  `Release`. Worker reads with `Acquire` in its pending-interrupt check
  (ISSUE 5).
- For users who need fine-grained MTIME (e.g., scheduling-critical RTOS),
  document that threaded mode's tick resolution is `Q` and they should
  either reduce `Q` or use single-threaded mode.

## ISSUE 11: `Emulator::reset()` writes to shared state without synchronization

**Severity:** IMPORTANT
**Section:** §8 thread lifecycle (not addressed)
**Problem:**
The HLD says `run_threaded` takes `&mut self`, spawns workers, runs, joins,
reassembles. Reset (`lib.rs:72-103`) writes to every field of `Bus`, including
the PPB array, `event_flag`, `rcp_salt`, `sio`, `pio`, `gpio_in`. Today this is
safe because there are no other threads.

In the proposed threaded model, if any worker thread is still running (e.g.,
previous `run_threaded` paniced and didn't join cleanly, or the user calls
`reset` from a signal handler, or there's a reset-pin doorbell from a
peripheral model), the writes race with worker reads.

Secondarily, the HLD's `split_for_threaded` / `reassemble_from_threaded`
protocol needs to explicitly guarantee that the split is a one-time operation
per `run_threaded` call and that no user-observable `&mut Emulator` method
can be called while workers are alive. Today there is no type-level guarantee
of this.

**Proposed solution:**
- `Emulator::run_threaded` takes `&mut self`. Rust's borrow checker prevents
  any concurrent `&mut self` method from running on the caller's thread. Good.
- But `Emulator` owns its workers' state via `Arc<SharedState>` — if the
  worker threads get a `Weak<...>` or hold strong refs that outlive the join,
  we have a problem. The HLD must specify: workers receive `Arc` on spawn,
  must drop all their refs before returning from the worker loop, and the
  join waits synchronously.
- Add a `debug_assert!` at the top of `run_threaded` that
  `Arc::strong_count(&state) == 1` before spawn and after join. Any deviation
  is a bug.
- Reset must only be callable when workers are not running. Since `reset`
  takes `&mut self` this is enforced by the borrow checker **as long as**
  `run_threaded` holds `&mut self` for its entire duration. Verify this in
  the design.

## ISSUE 12: Contention tracking state leaks across threaded runs

**Severity:** NICE-TO-HAVE
**Section:** §Non-goals ("No per-cycle bus contention modeling in threaded mode")
**Problem:**
The `Bus` struct has `contention_check_active`, `core0_port`,
`last_access_cycles`, `extra_wait_states`, `burst_mode` — all used for
single-threaded cycle-accurate contention modeling. The HLD says we don't
model contention in threaded mode, which is fine, but the fields still
exist on the shared `Bus` and would cause data races if any code path
touches them.

Easy fix: either gate those fields behind a mode enum on Bus, or just
ensure threaded-mode code paths never touch them. The risk is a future
patch adding a contention-check to a hot path and forgetting it's unsafe
in threaded mode.

**Proposed solution:**
- Split `Bus` (per ISSUE 4): `SharedBus` (memory, peripherals, SIO,
  PPB-array) has no contention fields. `ContentionTracker` is a separate
  struct used only in single-threaded mode and owned by `Emulator::step`
  directly.
- In threaded mode, `CoreBus` views of `SharedBus` don't expose any
  contention setter/getter. Type system prevents regression.

## ISSUE 13: RCP (Redundancy Coprocessor) salt — cross-core write without sync

**Severity:** IMPORTANT
**Section:** §2 (not addressed)
**Problem:**
`bus.rcp_salt: [u32; 2]` and `rcp_salt_valid: [bool; 2]`
(`crates/mdrp2354/src/bus/mod.rs:89-91`) are per-core but documented as
"shared state for cross-core writes" in the source. Grepping for usage
shows they're reset on boot but otherwise touched only by RCP coprocessor
handlers (`crates/mdrp2354/src/core/coprocessor.rs:74,144`). The RCP
protocol in pico-sdk uses cross-core salt-reveal via writes from one core
visible to the other; this is the security feature of RP2350.

Plain `u32` / `bool` — data race in threaded mode. The design does not
address this.

**Proposed solution:**
Convert to `[AtomicU32; 2]` and `[AtomicBool; 2]`. Use `Release` on write,
`Acquire` on read. The semantic is already cross-core by design; just needs
proper atomics.

## Overall assessment

The HLD proposes a sensible architecture (coordinator + 2 workers + quantum
barrier) but has not gone through the load-bearing details of how shared
state becomes safely shared. The atomic backing (ISSUE 1), missing
exclusive monitor (ISSUE 2), PPB refactor (ISSUE 4), and interrupt
dispatch (ISSUE 5) are **all mandatory** before a single line of threading
code is written; they are prerequisite refactors that affect single-threaded
code as well.

The easiest path forward is probably a Phase 0 before the HLD's Phase 1:

**Phase 0 (prerequisites):**
- Split `Bus` into `SharedBus` + per-core `CoreBus` / PPB access by explicit
  core ID (ISSUE 4, ISSUE 12).
- Implement exclusive monitor for LDREX/STREX (ISSUE 2).
- Convert cross-core fields (`event_flag`, `rcp_salt`, `halted`,
  `wfe_waiting`, `doorbell_pending`, `mtime_match_asserted`, SIO
  spinlock bits) to atomics — even in single-threaded mode this is fine
  because atomics on single thread are free (ISSUES 5, 7, 9, 13).

Then the HLD's Phase 1 (SharedMemory) / Phase 2 (ThreadedSio) / Phase 3+
lands on a clean base.

I'd block the HLD at v1.0.0 and request a v1.1.0 that addresses at minimum
the four CRITICAL items.
