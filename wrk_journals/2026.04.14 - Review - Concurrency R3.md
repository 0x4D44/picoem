## CRITICAL 1 — STREX is not atomic as described; two concurrent STREX can both "succeed"

### Where
Phase 0b.2 description (lines 78-81) and the implied execute-path behaviour.

### Exact break scenario
Core 0 and core 1 both hold a reservation on tag 0x1000 (both did LDREX):

```
time  core 0                              core 1
----  ----------                          ----------
t0    LDREX [0x1000]  -> v0, ex0 = v      LDREX [0x1000] -> v0, ex1 = v
t1    STREX new0 -> check ex0: valid
t2                                        STREX new1 -> check ex1: valid
t3    write32(0x1000, new0); ex0 = 0
t4    snoop peer: ex1 cleared
t5                                        write32(0x1000, new1); ex1 = 0 (already)
t6                                        snoop peer: ex0 already 0, return
```

Both STREX return success. new1 overwrites new0. A ticket-lock / lost-update
bug, undetectable except by firmware misbehaving later.

The HLD describes the monitor state machine ("LDREX sets it; STREX checks and
clears; any write from either core invalidates it") but gives no guarantee that
the STREX's three operations — (a) test monitor, (b) write memory, (c) clear
peer monitor — execute as one atomic step with respect to the *other core's*
STREX. In single-threaded mode this is automatic. In threaded mode it is not.

The `snoop_exclusive` function in the HLD only invalidates the *peer's* monitor
after the write. That does nothing to prevent the peer from having *already*
passed its own monitor check and being partway through its own write.

### Required fix
STREX must be implemented as a CAS on the shared memory word, predicated on
the local monitor being valid:

```rust
// Pseudocode for STREX addr, rt
if !self.exclusive_valid_for(addr) { return 1; } // fail
let expected = self.exclusive_captured_value;    // captured at LDREX
match shared.compare_exchange_word(addr, expected, rt, Release, Relaxed) {
    Ok(_)  => { self.clear_own_monitor();
                shared.snoop_invalidate_peer(addr, self.core_id);
                return 0; }      // success
    Err(_) => { self.clear_own_monitor(); return 1; }  // fail
}
```

This requires:
1. LDREX must *capture the loaded word value* into `CortexM33`, not just the
   tag. `exclusive_address: Option<u32>` in Phase 0b.2 is insufficient; the
   monitor must record `(tag, captured_value)`.
2. `SharedMemory` must expose a word-level `compare_exchange` primitive. For
   the AtomicU32-backed SRAM this is trivial; for byte-wide STREX/STREXH it's a
   CAS loop over the containing word.
3. The snoop only runs on CAS *success*.

Without this, the primary motivation for landing the monitor work (software
spinlocks) is defeated.

### Severity
**CRITICAL.** Spinlocks, mutexes, and every lock-free structure that compiles
to LDREX/STREX breaks under contention in threaded mode. The bug is
non-deterministic and will show up as sporadic state corruption.

## CRITICAL 2 — Cross-core IRQ delivery into the peer's NVIC is a data race

### Where
Phase 0b.1 (PPB move to CortexM33), Phase 0b.3 (atomize cross-core fields), and
the coordinator description (lines 189-195).

### Exact break scenario
Worker 0 is mid-quantum. Core 0 executes `STR` to a peripheral MMIO register —
e.g., a UART TX FIFO write. The peripheral mutex (`apb`) is taken; the write
causes TXE to assert. TXE is wired to IRQ N. IRQ N is enabled on *core 1* only
(firmware routed it there via core 1's NVIC ISER).

To raise that IRQ, the peripheral code must set bit N in *core 1's* NVIC ISPR.
After Phase 0b.1, core 1's NVIC lives inside `CortexM33` on worker 1's thread.
Worker 0's thread writes it. The NVIC registers (`iser`, `icer`, `ispr`,
`icpr`, `iabr`, `ipr[...]`) are plain `u32`/`u32[]` fields. Result: data race.

Worker 1 is concurrently reading `ispr`/`iabr` in its own interrupt-check path
inside `step()` on every instruction boundary. Concurrent unsynchronized R/W
on a plain `u32` is UB in Rust and will miscompile or tear on weakly-ordered
hosts.

Phase 0b.3's atomize list covers only `halted`, `wfe_waiting`, `event_flag`.
It does not cover NVIC state. The field-ownership table doesn't list NVIC
fields at all.

### Why the coordinator-only "timer ticks" story doesn't save us
The HLD defers *timer* ticks to the coordinator. But synchronous peripheral
writes during a quantum can raise IRQs immediately (UART TX complete, SPI
transfer done, DMA channel finished — all fire from MMIO paths, not timers).
Routing every possible IRQ-source write through a deferred queue is a
substantial redesign and is not what the HLD currently proposes.

### Required fix
Choose one of:

**(A) Atomize the cross-core-written NVIC fields.** The RP2350 NVIC has 32
   IRQs × 2 cores. Promote `ispr`, `icpr`, `iabr` (and whatever else a peer can
   write) to `AtomicU32`. Readers in `step()` load with Acquire; peripheral
   writers store with Release (or use `fetch_or` for pending-bit set). Add
   these to the Phase 0b.3 atomize table. Cheap, local, matches HW semantics.

**(B) Route all IRQ sets through a lock-free mailbox per core.** Peripheral on
   worker 0 pushes `(target_core, irq_num)` onto a ring. Coordinator drains the
   ring between quanta into the target core's NVIC. Adds up to Q cycles of
   latency on cross-core IRQs, which may or may not be acceptable depending on
   firmware expectations.

**(A) is strongly preferred** — it mirrors what real hardware does (the NVIC's
pending register is inherently atomic from the peripheral's perspective) and
it doesn't introduce a quantum-granularity latency that would need its own
validation.

Whichever is chosen, the field-ownership table must be extended to cover all
NVIC fields that any peripheral write path can touch on either core.

### Severity
**CRITICAL.** Every peripheral that fires an IRQ routed to the non-executing
core is affected. This is most peripherals in most firmware.

## CLARIFY 1 — Shutdown protocol relies on poison, but HLD doesn't say so explicitly

### Where
StopSignal description (lines 152-163), worker topology (lines 178-195).

### Exact sequence that's unclear
External caller invokes `stop.stop()`. Worker 0 is in its coordinator phase;
it observes `stop.is_stopped()` and decides to exit. Worker 1 is partway
through its quantum, will arrive at barrier 1 shortly.

If worker 0 simply returns without calling `barrier.wait()`, worker 1's
`fetch_add` lands at count=1 and it spins forever on generation change —
because worker 0 never increments count past 1.

`SpinBarrier::wait` only breaks its spin on (a) generation change or (b)
poison. It does **not** observe `StopSignal`. The only way to wake worker 1
is for worker 0 to call `barrier.poison()` before exiting.

The HLD says "workers check `stop.is_stopped()` at each barrier" (line 163) and
lists "check stop_signal" as a coordinator task (line 193), but never states
the termination protocol: *worker 0 must poison the barrier on stop, then exit*.
A careful implementer will infer this; a careless one will produce a deadlock
on shutdown.

### Required fix
Add one sentence to the StopSignal section:

> On detecting `stop.is_stopped()`, worker 0 calls `barrier.poison()` to
> release worker 1 before returning. Worker 1 observes `BarrierResult::Poisoned`
> and exits. `ThreadedEmulator::run` distinguishes stop-requested from panic by
> checking `stop.is_stopped()` before returning `ExitReason::Panic`.

Also: `ExitReason::Stopped` vs `ExitReason::Panic` disambiguation needs a rule.
If poison is the only wake path, both exit reasons go through poison; the
caller distinguishes by whether `stop_signal` was set externally versus set by
`catch_unwind`. Spell this out.

### Severity
**Clarification required, not a correctness bug in the design itself.**
Elevating to a blocker only if left unaddressed before Phase 4, since Phase 4
is when this gets built.

## CLARIFY 2 — SEV semantics: does own-core SEV set own `event_flag`?

### Where
Field-ownership table row for `event_flag` (line 97).

### The ambiguity
Armv8-M SEV signals an event to *all PEs in the multiprocessor system,
including the PE that executed SEV*. The consequence: an `SEV; ...; WFE`
sequence on a single core does **not** block — the first WFE consumes the
event the core set for itself.

The HLD's table row for `event_flag` reads: "Core clears own; SEV writes peer."
Writing *peer only* implies own-core WFE after own-core SEV would incorrectly
block until the peer SEVs back.

### Required fix
Either:
- Change the table row to "SEV writes own and peer; WFE consumes own", and
  confirm in the narrative that both stores happen when `SEV` executes, or
- If you intended "WFE is always treated as a hint and never blocks on own
  event," state that explicitly and accept it's not bit-accurate to Armv8-M.

### Severity
**Correctness bug if implemented literally from the table.** Likely to be
caught in differential testing but cheaper to fix in the design.

## Not critical, but worth recording

### NIT A — Exclusive monitor u64 encoding isn't specified

The field table says `AtomicU64 (tag + valid bit)`. `snoop_exclusive` casts to
u32 and masks with `0xFFFF_FFFC`. Works if valid bit is in bits 0..1 of the
low 32 (discarded by the mask). Works if valid bit is in bits 32..63 (not
touched by the tag compare, reaches `cur == 0` check correctly).

Nail down the encoding in Phase 0b.2 — e.g., `valid << 32 | tag`, with
"invalid" represented as all-zero. The snoop function already assumes this.

Not critical: any reasonable implementation works. But leaving it unspecified
invites one of two engineers picking a representation (e.g., a bumping
sequence number) that breaks the snoop's CAS.

### NIT B — Barrier releaser doesn't re-check poison on its fast path

In `SpinBarrier::wait`, the thread that's second-to-arrive (`n == 2`) resets
count, bumps generation, and returns `Released` without ever checking
`poisoned` on its way out. If a panic lands during that thread's fetch_add →
store interval, the released thread still reports Released while the system
is actually torn down.

Not critical: in practice the released thread is about to return to
coordinator code which checks `stop`/panic state anyway. But adding a
`if self.poisoned.load(Acquire) { return Poisoned; }` just before the final
`Released` is free and cleaner.

### NIT C — Generation wraparound on u32

`generation` is `AtomicU32`. At Q=150 and ~115 MHz per core, quanta happen at
~750k/s. Wrap at 2^32 ≈ 5700 seconds ≈ 95 minutes. ABA on generation
requires a thread to be paused for exactly 2^32 quanta while the other
advanced — impossible under the design (both threads forced to sync every
quantum). Not a real issue, but if it's free to widen to `AtomicU64`, do it.
