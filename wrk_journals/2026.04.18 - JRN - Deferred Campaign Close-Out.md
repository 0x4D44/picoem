### T1 — §3.7.9 resolution (web research)

Spawned a general-purpose agent to resolve the datasheet entry count while
the soak ran. Authoritative answer from **Raspberry Pi RP2350 Datasheet §3.8**:

- `PMP_REGIONS = 11` (synthesis parameter). 8 **dynamically configurable**
  (regions 0..7) + 3 **hardwired** (8..10, bootrom-configured) +
  5 hardwired OFF (11..15).
- `PMP_GRAIN = 3` — 32-byte granule, NAPOT-only.
- `PMP_HARDWIRED = 0x700`.

Material finding: the phase-1 A.2.1 addendum's "QEMU virt rv32 applies
non-zero pmp_gran by default" claim was likely mis-diagnosing the real
divergence. QEMU 10.2's `rv32` CPU does **not** expose `pmp-grain` as a
CPU property (probed empirically — all of `x-pmp-grain`, `pmp-grain`,
`pmp-num-regions`, `num_pmp` rejected by QEMU with "property not found").
QEMU defaults to G=0; silicon has G=3. Phase-1's "divergence" was actually
emu/QEMU vs silicon, not emu vs QEMU.

### T2 — PMP phase-2 scope decision

Decided against G=3 on the emulator because:
- No silicon-RISC-V diff oracle exists today (`test_rp2350_probe_*` is ARM
  only).
- G=3 desynchronises every `pmpaddr*` readback from QEMU (our only Hazard3
  ISA oracle).
- Silicon-matching can be deferred until a silicon-RISC-V oracle is built.

Phase-2 scope:
- `PMP_NUM_ENTRIES = 1 → 8` (matches dynamic count; entries 8..15 stay RAZ/WI
  to model cold-reset — we don't emulate bootrom PMP init).
- L-bit write gate (own-byte sticky + pmpaddr own-L + TOR cross-entry lock).
- `reset_pmp_csrs()` helper (for unit tests; see T9 for why it's NOT
  wired into the diff harness).
- Edge-case catalogue updated to cover phase-2 synthesised window.

### T5 — First fuzz run: 60 % failure rate

`--fuzz 5000 --class pmp --seed 42`: 3016/5000 FAIL.

Pattern all identical: csrrw `rd, csr, rs1` reads old CSR value into rd.
QEMU accumulates across tests, emu accumulates across tests — should be
in sync. They weren't.

### T6 — Root cause: fuzz pool contamination

Added diagnostic dump of emu pmp state on fuzz failures (via new
`pmpcfg()` / `pmpaddr()` accessors). First fail state:

```
emu pmp: cfg=[18181818 9c8d9c8f 0 0] ...
```

`cfg[1] = 0x9c8d9c8f` has **L=1 in every byte**. The VALUES pool
documented itself as "bit 7 and bit 15 and bit 23 and bit 31 clear on
every byte (`& 0x7F7F_7F7F`)" but actually contained `0xDEAD_BEEF` and
`0xCAFE_BABE` — both with L=1 in every byte. The comment's invariant
was a LIE; those two "chaotic pmpaddr" values were unfiltered when
picked for pmpcfg CSRs (33 % chance since 4/12 CSRs are pmpcfg).

**Fix:** `& 0x7F7F_7F7F` mask applied at the generator pick site — the
invariant now actually holds. Fuzz dropped to **75/5000 failures (1.5 %)**.

### T7 — Second attempt: reset_pmp_csrs in diff harness

Added `emu.core_riscv_mut(0).reset_pmp_csrs()` alongside `reset_diff_csrs`.
**Desynced the write-side rd read** — emu goes fresh, QEMU keeps state,
so every csrrw's rd1 (old value) diverges. 222 → 216/222 edges on the
retest. **Reverted.** Both sides must accumulate PMP identically; the
reset helper stays available for unit tests only.

### T8 — Narrow CSR pool to synthesised window

Tried excluding pmpcfg2/3 + pmpaddr8..15 from the fuzz CSR pool.
**Worse** (103/5000 vs 75/5000) — pool narrowing skewed the mix toward
test patterns that happen to exercise different WARL edges. Reverted.

### T9 — Scope-reduction decision

Mixed fuzz at the campaign regression seed (`--fuzz 10000 --seed
2703168085`) with Pmp at 300 bp: **9997/10000 PASS, 3 PMP failures.**

0.03 % is tiny but the campaign's acceptance gate was 10 000/10 000.
Phase-1 sat Pmp at 0 bp precisely because the L-bit-hole was too hard
to close cleanly; phase-2 shrank the hole from ~60 % to ~1.5 % but did
not eliminate it.

**Decision: drop Pmp weight back to 0 bp. Ship emu phase-2 correctness;
`--class pmp` stays as a manual bring-up path with ~1.5 % residual
divergence; mixed fuzz gate preserved at 10 000/10 000.**

Rebalance reverted (`Rv32iAlu` back to 3000, `Pmp` back to 0).
