### Stage 1 — FixtureSpec parser landed; reviewers found semantics bugs
Three reviewers (code-reviewer, devil's-advocate, applier) flagged that the
implementor's "literal rule" parsing produced over-conservative `unservable_when_high`
masks and incorrect `asserted_low_during_read` for fire-24-a. Root fix: discriminate
parser semantics by `chip_pins` field (24-pin vs 32-pin). Applier agent corrected:

- fire-24-a: `unservable_when_high == 1<<13`, `asserted_low_during_read == []`,
  `deasserted_high_during_read == [12, 15]`, `chip_pins == 24`.
- fire-32-a: `unservable_when_high == 1<<16`, `asserted_low_during_read == [15, 14]`,
  `deasserted_high_during_read == []`, `chip_pins == 32`.

Tests rewritten to assert HLD §4.1 example values (not parser output). Added
`from_flash_unknown_chip_pins` to lock down the chip_pins discriminator.
**Committed as de64969.**

### Stage 3 — wide-GPIO bus + fire-32-a binary; partial HLD §6.2 acceptance

**rp2350-emu (Stage 3A) — solid.** Companion `gpio_external_in_hi: AtomicU32` +
`gpio_external_mask_hi: u32` fields on `Bus`. `read_gpio_hi_in` merges the
high-half external value behind the existing mask logic; low-half path untouched.
3-thread `AtomicGpio` runtime mirrors the same. 4 new unit tests on `--features
threading,default`. rp2350-emu version bump 0.1.3 → 0.2.0; picoem-debug and
rp2350-emu-tui dependency constraints bumped accordingly. **3179/3179 tests pass
(default features), 3236/3236 pass (--features threading).**

**picoem-harness Stage 3B — built; HLD §6.2 acceptance NOT met.** The new
`seabios32_fixture_byte_correct` binary structure is correct: parses
`FixtureSpec`, sweeps `0..2^19` addresses, skips `(pin & spec.unservable_when_high) != 0`
patterns, expects `seabios[(addr) % 0x4_0000]`, supports `--smoke`, `--stride`,
`--continue-on-fail`. Smoke exercises the high-half bus path successfully (the
1024 PASS cases include addresses driving GPIOs 32, 33, 34 — A0..A2 in fire-32-a's
pin map — and they decode correctly through the new `set_gpio_external_in_hi` →
`read_gpio_hi_in` plumbing).

**However: the PIO oracle's trace evaluator and stim-vs-resolved comparison are
fire-24-a-shaped.** Diagnostic dump revealed:
- fire-32-a's PIO program is `IN X, 13; IN PINS, 19` (X = ROM_BASE >> 19); fire-24-a
  uses `IN X, 16; IN PINS, 16` (X = ROM_BASE >> 16). The Stage-G comment in
  `onerom_serving_oracle.rs` documents the `IN X, 16` assumption.
- The trace evaluator's `hi16 != 0x2000` filter at line 940 rejects every push
  whose pin bits 16/17/18 are set — exactly the fire-32-a address-space half we
  need.
- `expected_pin_bits = (stim_level & 0xFFFF) as u16` at line 463 is too narrow
  for fire-32-a's 19-bit pin pattern.
- Smoke result: 1024 PASS, 3072 NoResolve. PASS cases all have addr_idx < 1024
  (only A0..A9 driven, mostly through GPIOs 27..34 — high half — where the high-
  half wiring works correctly). Failures begin at A10=1 (GPIO17 set) — at that
  point the firmware does PIO-decode the address, but the oracle's filter rejects
  the push.

**This is oracle redesign territory, not a small picoem-harness fix.** Properly
fixing it requires:
1. Per-fixture PIO program shape detection (X-prefix bit count + IN-PINS-N
   width). Probably extends `FixtureSpec` with a small `pio_decode: PioDecodeSpec`
   field, or a sniffer that reads the firmware's PIO instr_mem after sync.
2. Fixture-aware `expected_pin_bits` width.
3. Possibly high-bank gpio_in plumbing for PIO sampling (currently `bus.gpio_in:
   AtomicU32` doesn't see GPIO 32..47; only the SIO `GPIO_HI_IN` register sees
   the harness stimulus today, and PIO doesn't go through that path).

These are out-of-scope for the OneROM Fixture Generalization HLD as written. The
HLD assumed the existing oracle would just work for fire-32-a after FixtureSpec
generalization — empirically not so. **Tracked as a Stage 4 follow-up:** "PIO
oracle generalization for fire-32-a-style multi-byte address pushes".

### Stage 2.5 — fire-24-a literal-pattern regression (rolled into Stage 3 commit)

A diagnostic agent investigating the Stage 3 fire-32-a sweep found a SECOND issue
that wasn't fire-32-a-specific: Stage 2's `compose_stim_level` and
`compose_ext_mask` always applied the `deasserted_high_during_read` overlay and
the narrow `addr_pins`-only mask. This broke `Case::from_raw` callers — chiefly
the fire-24-a CPU-serve byte-correctness sweep, which drives literal 16-bit
pin patterns and asserts `observed == chunk[pin_state]`.

**Pre-fix smoke:** rom_set 1 PASS=21, rom_set 2 PASS=5, rom_set 3 PASS=4. Total
286 / 1024.
**Pre-fix full sweep:** pass=71763 / wrong=59309 (vs Stage 1 baseline pass=131072 /
wrong=0).

**Fix:** add `is_literal: bool` to `Case` (set true by `from_raw`, false by
`from_addr`). Short-circuit BOTH `compose_stim_level` (returns `pin_pattern`
verbatim) and `compose_ext_mask` (returns `0xFFFF & !data_pin_mask`) when literal.
4 new unit tests pin the contracts. `onerom_stress_cpu_rp2350.rs` had a stale
rewrap that re-set `is_literal=true`; replaced with a direct copy.

**Post-fix smoke:** 1024/1024 PASS. **Post-fix full sweep:** pass=131072 / wrong=0.
Matches Stage 1 baseline exactly.

**Stage 2 reviewer/devil's-advocate gap:** the Stage 2 review pinned the
equivalence test at `Case::from_addr` only. The `Case::from_raw` semantic
(deasserted-high overlay vs literal) was not exercised by any unit test. The full
sweep regression was end-to-end-only catchable. Stage 2.5's 4 new tests close the
gap. Lesson: when a function fans out into multiple semantic branches via a
constructor flag, every branch needs its own unit test, not just the dominant
branch.

### Continuation triage — Stage 4 HLD boundary

Arthur asked how to continue after the Stage 3R partial acceptance handoff. I re-read
the fixture-generalization HLD, the top `tech_debt.md` entry, and the current oracle
code around the three known blockers. My recommendation remains option (b): accept
Stages 1-3R as the natural boundary of the existing HLD and write a separate Stage 4
HLD before touching the PIO oracle.

The technical reason is stronger than ordinary caution. The work is not just replacing
two constants. `picoem-common::pio` still exposes a 32-bit `gpio_in` sampling model
through `PioBlock::step_n` / `StateMachine::read_pins`, while fire-32-a needs GPIOs
32..34 to participate in `IN PINS`. The trace evaluator also assumes the fire-24
`IN X, 16; IN PINS, 16` resolved-address shape. Those two facts mean Stage 4 crosses
both harness evaluator logic and shared PIO-emulator contracts, so it deserves its own
acceptance criteria and review.

Emotional temperature: fairly calm, but I feel the usual pressure to "just fix the
three lines" because the failure mode is so crisp. That would be a trap. The high-bank
PIO sample path has enough blast radius that a quick patch could pass the fire-32 smoke
while quietly changing PIO semantics for other workloads. Better to slow down for one
proper HLD than create a brittle oracle fix.
