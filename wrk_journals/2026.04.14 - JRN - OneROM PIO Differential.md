## Session intent

Stand up an external differential oracle for our PIO engine using Piers
Finlayson's `epio` (standalone cycle-accurate RP2350 PIO emulator) as
reference. Shape 2 from the design conversation: a trace generator that
runs OneROM's real `setup_onerom` scenario through epio once, commits
the output as a golden trace, and a pure-Rust diff binary replays the
same stimulus through `mdpicoem-common::pio` comparing row-by-row.

### Sequence

- Stage A: `epio-sys` crate skeleton + submodules + first clang build
- Stage B: trace generator C shim + Rust binary
- Stage C: produce and commit the first golden trace
- Stage D: pure-Rust diff binary + glue DMA
- Stage E: triage divergences

## Stage B — done

### Shim notes — things apio.h taught me

Reading through `apio.h` before writing the shim surfaced three points
that would have bitten me if I'd charged ahead:

- **apio's global `_apio_emulated_pio` is defined behind
  `#ifdef APIO_EMU_IMPL`.** Only `epio/src/epio_apio.c` flips that
  flag. Our shim must NOT define it, or we'd get duplicate-symbol
  link errors. We just see the `extern` declaration at line 140 of
  `apio.h`.
- **`APIO_ASM_WFI()` becomes `return 0` in emulation mode.** So the
  trailing `while (1) { APIO_ASM_WFI(); }` at the end of
  `setup_onerom` exits on the first iteration — no infinite loop.
  Lift the function verbatim.
- **`APIO_LOG_SM(...)` is a no-op unless `APIO_LOG_ENABLE` is
  `#define`d to `printf`.** We don't define it, so logging is
  silent. No need to strip the log calls.

## Stage D — done

The diff binary (`crates/mdpicoem-harness/src/bin/onerom_pio_diff_rp2350.rs`)
landed, parses the trace, reconstructs `setup_onerom`'s init on our PIO
via the register-write interface (INSTR_MEM + per-SM regs + TXF preload
+ two force-executed pre-init instructions + JMP_TO_START force-execs
+ CTRL enable), replays the stimulus, and diffs cycle-by-cycle. Glue
DMA runs through the public bus interface (FSTAT / RXF1 / TXF2) — no
reach-in to the `pub(crate)` FIFO accessors. Force-execute's known
`gpio_in=0` bug doesn't bite for this scenario (PULL BLOCK + MOV X, OSR
don't touch pin state).

First run: FAIL with first-divergence at cycle 3.

## Stage E — triage (in progress)

### Bug 1 — `MOV X, PINS` ignored `IN_COUNT` (RP2350 addition)

`exec_mov` with source `PINS` called `read_pins(gpio_in)` and used the
full 32-bit rotated value. RP2350 (unlike RP2040) masks MOV PINS by
SHIFTCTRL.IN_COUNT. OneROM's SM0 uses IN_COUNT=1 to read only CS
(pin 8), expecting `X = 0` when CS is asserted; we were returning
`0xFFFFFFFE` (23 pullup bits + a zero in the rotated result), so SM0
never exited its CS-detect loop.

Fix: in `exec_mov`, when source == 0 (PINS), apply
`raw & ((1 << IN_COUNT) - 1)` for `IN_COUNT in 1..=31`; unchanged for
`IN_COUNT == 0` or `>= 32`. `crates/mdpicoem-common/src/pio/sm.rs`
lines ~645–654.

### Bug 2 — `MOV PINDIRS` unimplemented (RP2350 addition)

`exec_mov`'s destination 3 fell through to `_ => {}`. RP2350 added
`MOV PINDIRS` as destination 3 (writes the pin_dirs latch using the
OUT_BASE / OUT_COUNT window). RP2040 treats destination 3 as reserved.
OneROM's SM0 uses `MOV PINDIRS, !NULL` (opcode 0xA06B) to turn on the
data bus driver — without this, we'd never set pin_dirs for pins 0–7.

Fix: added destination 3 handling in `exec_mov` mirroring the `OUT
PINDIRS` logic.

### Bug 3 — `pin_values` reset default was 0, should be pullup-high

Once MOV PINDIRS worked, the first cycle where SM0 enabled the data
bus still diverged on *level*: epio showed 0xFF, we showed 0x00. The
datasheet calls this "implementation-defined at reset"; epio's
`epio_init_gpios` sets all GPIOs as input with level=1 and *retains*
the 1 in `gpio_output_state` when a pin flips to output. Choosing the
pullup-high convention to match. Updated two unit tests
(`test_pin_mapping_out`, `test_pin_mapping_wrap`) to explicitly zero
`pin_values` rather than relying on the implicit default. 74/74 PIO
tests green.

### Bug 4 — per-SM `pin_values` / `pin_dirs` didn't model shared pad

Root cause: OneROM splits pad control across two SMs — SM0 owns
PINDIRS (turns on the data bus), SM2 owns PINS (writes the data
byte). Real RP2350 routes both writes into the same block-level pad
latches. Our model kept per-SM `pin_values` / `pin_dirs` and the
merge used each SM's own pin_dirs as its write-mask, so SM2's
pin_values writes vanished because SM2 never set any pin_dirs.

Fix: moved the latches onto `PioBlock` as `shared_pin_values`
(reset `u32::MAX`, pullup convention) and `shared_pin_dirs` (reset
0). Threaded `&mut` refs to both through `execute_cycle` →
`execute_insn` → `exec_out`/`exec_mov`/`exec_set` and through
`force_execute`. Side-set remains per-SM (each SM has its own
sideset_base/count and sideset_pins/sideset_dirs latches); the
merge now starts from shared state and layers side-set on top.

Updated tests that assigned to `pio.sm[0].pin_values` directly to
write `pio.shared_pin_values` instead. 74 PIO tests still green.

After fix: first divergence moved forward (3 → 12) but the data
byte still didn't land at the right cycle.

### Bug 5 — `osr_count` init was 0, should be 32 (empty)

epio initialises `osr_count = 32` at boot ("Empty OSR indicated by
count of 32" — `epio.c:63`); real RP2350 does the same. We were
using `osr_count = 0`, so the autopull check `osr_count >= threshold`
was false on the first OUT instruction, skipping the pull and
emitting whatever garbage was in OSR (0). SM2 latched `0x00` onto
pins 0–7 eight cycles too early.

Fix: `StateMachine::new()` now initialises `osr_count = 32`. No test
regressions.

### Bug 6 — glue DMA was instantaneous (needed 4+4 cycle latency)

After bug 5, data byte appeared at our cycle 4, epio at cycle 12.
The difference is epio's DMA chain latency:
`epio_dma_setup_read_pio_chain(..., read_cycles=4, write_cycles=4)` —
8 cycles end-to-end from "SM1 pushed RX" to "SM2 TX has the
resulting byte". Our glue DMA popped-and-pushed in a single cycle.

Fix: rewrote `onerom_pio_diff_rp2350.rs`'s glue DMA as a small state
machine (`GlueDma { read_delay, write_delay, read_value, has_pending }`)
that mirrors `epio_dma_step`: new read trigger starts `read_delay=4`;
at `read_delay=0` we "fetch" (byte=0 since SRAM zero-init) and start
`write_delay=4`; at `write_delay=0` we push to SM2 TX. Writes checked
for TX-full with a retry.

### Result

`cargo run -p mdpicoem-harness --bin onerom_pio_diff_rp2350 --release`
reports **PASS — all 20 cycles match the committed trace**.

Trace milestones (now matched row-for-row):

| Cycle | Event |
|-------|-------|
| 0 | SM0 executes `MOV PINDIRS, NULL` — pad_oe stays 0 |
| 3 | SM0 executes `MOV PINDIRS, !NULL` — pad_oe = 0xFF (data bus enabled); pad_out = 0xFFFFFFFF (pullup) |
| 7 | SM1 autopush fires — RX FIFO gets `0x20000000` (ROM base in high half + zero address in low half) |
| 11 | DMA chain completes — SM2 TX FIFO gets `0x00000000` (byte 0 replicated) |
| 12 | SM2 autopulls + `OUT PINS, 8` — pad_out[0..7] = 0x00 visible on the data bus |
