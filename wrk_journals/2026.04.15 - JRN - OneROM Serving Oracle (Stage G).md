## Stage plan

Three stages, gated by working code + green tests + a fresh
manual run. Commit after each.

- **G.1 — Byte oracle.** `ServingOracle` + trace-driven verdict
  evaluator + single-case integration. Shadow captures SRAM at
  sync; one case (`0x1800`) runs through the state machine;
  observed byte must match `shadow[resolved_addr - SHADOW_BASE]`.
  Unit tests 1–5 from HLD §8.1.
- **G.2 — Address sweep.** Extend to 15 cases (walking 1s across
  A0..A10 + patterns). Case-to-case transitions via CS pulsing.
  `ServingOracle` accumulates `Vec<CaseResult>`.
- **G.3 — Timing envelope.** Per-case latency → ns via
  `bus.sys_clk_hz()`; envelope check `11 ≤ cycles ≤ 14`; report
  formatter with sys_clk_hz header, per-case table, summary
  min/max/mean, ROM-speed class, emulator-bounded caveat.
- **Validation sweep.** Independent agent diffs implementation
  against the HLD — iterate until 100% complete.

### PIO2 pad_out propagation — blocker for G.2

After CH1 pushes a byte (e.g. `0x00`) into `PIO2.TX0` and SM0's OSR
executes its `OUT PINS` (or equivalent OneROM pad-driving path),
`bus.pio[2].pad_oe` correctly flips to `0xFF` across D0..D7, but
`bus.pio[2].pad_out` stays at its reset value `0xFFFFFFFF`. Net effect
on the pins: D0..D7 reads as `0xFF` regardless of what byte CH1 pushes.

Consequence: every served byte in G.2's address sweep will observe
`0xFF` on the data bus; every case will trip the `WrongByte` verdict
with the shadow byte as `expected` and `0xFF` as `observed`. The
oracle logic is fine — the emulator is not serving the byte.

This needs to be investigated before G.2's sweep produces useful
verdicts. Suggested entry points:

- Re-use `onerom_pio_diff_rp2350` with the OneROM PIO2 program in
  isolation to see where pad_out diverges between QEMU/silicon and
  our PIO engine.
- Failing that, craft a focused unit test in
  `crates/mdrp2350/src/tests.rs` (or the PIO-specific test module)
  that pushes a byte through a minimal OUT-PINS-style program and
  asserts `pad_out` tracks the OSR.

Opening a new scratch journal for this is advisable; it's out of
scope for the G.1 patch set.

### Stage G.2 — Devil's advocate findings

Post-implementation devil's-advocate pass (2026-04-15) caught two
material issues. Both are recorded here so the fix rationale
survives long after the in-flight buffers drain.

- **Attack 3 — pipeline race (FIXED in G.2)**. `GAP_CYCLES` was
  `3`, but the glue DMA pipeline in `onerom_glue_dma.rs` is 8
  cycles deep (`DMA_READ_CYCLES + DMA_WRITE_CYCLES = 4 + 4 = 8`).
  A push issued in case N's tail would leak into case N+1's
  observation window, making `resolved_addr` readings lag by one
  case. Bumped `GAP_CYCLES` to `12` (= 8 + 4 slack cycles). The
  constant now carries a comment pointing at the arithmetic and
  the devil's-advocate note. Before the fix, the live sweep might
  have happened to pass verdict-class consistency by coincidence
  (one case's resolved_addr attributed to the wrong case); after
  the fix, each case's observation window is clean.

- **Attack 2 — shadow source is wrong (UNFIXED, blocker)**. HLD
  §3.1 assumes OneROM memcpys the ROM payload into SRAM at
  `0x20000000` before the sync point. That assumption is false
  for the `onerom-fire-24-a-rp2350-test-sdrr-0.bin` fixture: the
  SDRR header lives at `0x20080000` (`sdrr` magic in the first
  four bytes), and SRAM `0x20000000..0x20080000` is all zeros at
  sync. PIO1 *does* vary `resolved_addr` per stimulus — addresses
  like `0x20009xxx` are consistent with a correctly-working
  address pipeline — but those addresses land in the zero region
  below the SDRR header. The live result is `1 PASS + 14 AddrOOR`:
  the baseline PASSes by coincidence because `expected = 0x00`
  from the zero shadow matches `observed = 0x00` during the seed
  window; the other 14 cases resolve to `0x20009xxx`-ish
  addresses outside the shadow and correctly report `AddrOOR`.

  **The catastrophic failure mode we are specifically avoiding**:
  widening the shadow to cover `0x20009xxx` would yield
  shadow-bytes-all-zero. Once the parallel PIO2 `pad_out` fix
  lands, every case would fetch `0x00` → every case would pass a
  `0x00 == 0x00` comparison → a **15/15 FALSE GREEN** oracle
  that proves nothing. Accordingly, **we deliberately keep the
  current 8 KB shadow at `0x20000000` as a tripwire** until
  someone figures out where the real ROM payload lives for this
  fixture. No shadow widening in G.2.

  Options, to decide later (not in G.2):

  1. Parse the SDRR descriptor at `0x20080000` (`sdrr` magic in
     the first four bytes) to locate the `rom_table` pointer and
     shadow from there.
  2. Lift the ROM payload directly from the loaded `.bin` fixture
     bytes in memory (pre-mapping, before OneROM touches SRAM).
  3. Switch fixture from
     `onerom-fire-24-a-rp2350-test-sdrr-0.bin` to
     `onerom-fire-24-a-rp2350-1541.bin` (the 1541 fixture — likely
     has real ROM data, not a test null).
  4. Wait for the firmware to actually populate SRAM — the sync
     point may simply be too early.

- **Walking-1s bit-swap coverage is currently vacuous**. With the
  shadow uniformly zero, all walking-1 offsets return the same
  byte, so bit-swap bugs in the A0..A10 decode path are
  invisible. This is a direct consequence of Attack 2 — the
  walking-1s set is correct in principle; it just can't
  discriminate against a zero background. The moment the real
  ROM payload shadow is sourced, walking-1s coverage becomes
  meaningful again with no code change.

To make the tripwire visible to anyone running the binary, G.2
also adds a shadow-integrity diagnostic to
`onerom_serving_oracle_rp2350.rs`: after `new_at_sync`, the
binary counts unique bytes in the shadow and prints
`shadow @ 0x20000000..+0x2000: N unique bytes`. If `N == 1`, it
prints an extra `WARNING: shadow is uniform` line referencing the
blocker subsection below. Anyone looking at a live run sees the
tripwire before they try to interpret PASS verdicts.

### Shadow source investigation — blocker for meaningful G.2/G.3 verdicts

**Status**: UNFIXED, separate investigation track.

The HLD §3.1 shadow-capture assumption — that the ROM payload is
present at `0x20000000` by the time the Stage F sync point fires
— does not hold for the `test-sdrr-0` fixture. The symptom is a
uniformly-zero 8 KB shadow at `SHADOW_BASE`, which makes the
oracle unable to produce meaningful PASS verdicts even once the
PIO2 `pad_out` team lands their fix: the oracle would just be
comparing `0x00` against `0x00` for every case (the false-green
failure mode spelled out in the Attack 2 bullet above).

This blocker is **independent** of the PIO2 pad_out blocker
recorded earlier in this journal. Both must be resolved before
G.2/G.3 produces a meaningful green run; fixing only one is not
enough:

- PIO2 fixed, shadow source unfixed → 15 × `0x00 == 0x00`
  FALSE GREEN.
- Shadow source fixed, PIO2 unfixed → 15 × `WrongByte` with the
  correct `expected` bytes and `observed = 0xFF`, same as the
  G.1 outcome but across the full sweep.
- Both fixed → genuine PASS/FAIL discrimination per case.

Suggested next-step options are listed in the Attack 2 bullet
above (four variants: SDRR descriptor parse, fixture-bytes lift,
alternate fixture, later sync point). Recommending option 1 or 2
as the most fixture-agnostic — both produce a shadow independent
of whatever OneROM has or hasn't done to SRAM at the sync point
— but the call is for a future session. This subsection exists
so that call has a clear entry point.

A new scratch journal for this investigation is advisable when
someone picks it up; for now, G.2's job is tripwire visibility,
not tripwire removal.

  exits 0 iff all cases PASS.
- 4 new unit tests for `apply_envelope` (in-range, out-of-range,
  non-Pass pass-through) and `format_report_has_required_sections`.

Live sweep post-commit (with shadow fix in same commit):
- 0 PASS
- 4 WrongByte (real expected bytes at walking-1 offsets: 0x01, 0x02,
  0x04, 0x08 — pipeline returns 0xFF for those)
- 9 LatencyOutOfEnvelope (byte matched shadow but cycles outside
  [11..14])
- 2 residual AddrOOR (PIO1 produces wild addresses for those cases)

The WrongByte + LatencyOOE + AddrOOR distribution is the oracle
correctly surfacing three distinct classes of real pipeline bugs —

aimed for.

### Stage G.3 — devil's advocate post-commit review

Devil's-advocate pass verified:

  are correctly `#[cfg(test)]` gated — no release-build bloat.

Residual concerns (not blocking G.3, tracked for silicon oracle):

1. **Case 9 `cycles=3` outlier**: tight enough to suggest GAP_CYCLES=12
   may still let prior-case residue through the 3-cycle stability
   window in some cases. Silicon oracle cross-check will disambiguate.
2. **Caveat visibility**: the §5.4 emulator-bounded caveat appears only
   in `format_report`, not in the per-case incremental println. An
   operator reading only the scroll could misinterpret our ns numbers
   as silicon-calibrated. Low severity; defer.
3. **Test coverage gap plugged**: `run_case_applies_envelope_before_pushing_result`
   (added in this patch) proves the `run_case → apply_envelope → push`
   wiring via the "every stored result is a fixed point of apply_envelope"
   invariant.
