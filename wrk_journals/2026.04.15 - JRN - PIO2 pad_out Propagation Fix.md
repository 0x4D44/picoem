# PIO2 pad_out Propagation Fix

Date: 2026-04-15
Parent journal: `2026.04.15 - JRN - OneROM Serving Oracle (Stage G).md`
(the "PIO2 pad_out propagation — blocker for G.2" section).

## Symptom

`cargo run -p mdpicoem-harness --release --bin onerom_serving_oracle_rp2350`
reported the baseline case as
`WrongByte { expected: 0x00, observed: 0xFF }`. During the observation
window `PIO2.pad_out` stayed frozen at `0xFFFFFFFF` even though
`PIO2.pad_oe` correctly flipped to `0xFF` across D0..D7 and the glue
DMA counter confirmed CH1 had pushed a byte.

## Root cause (NOT in the PIO engine)

Contrary to the initial hypothesis, the PIO primitive
(`crates/mdpicoem-common/src/pio/`) is correct. The bug lives in the
harness-side glue DMA at
`crates/mdpicoem-harness/src/onerom_glue_dma.rs`.

OneROM's PIO2 layout at sync time (dumped via
`onerom_full_system_rp2350`):

| SM | Role           | Program                                | PINCTRL                       | Wrap |
|----|----------------|----------------------------------------|-------------------------------|------|
| 0  | CS handler     | `MOV PINDIRS,NULL` / wait-CS-low / `MOV PINDIRS,!NULL` / wait-CS-high | `OUT_BASE=16, OUT_COUNT=8` (via MOV PINDIRS) | 5→0 |
| 1  | Data writer    | `OUT PINS, 8` (at PC 6) with autopull  | `OUT_BASE=16, OUT_COUNT=8`    | 6→6 |

SM0 toggles the D0..D7 **direction** latch (hence `pad_oe` flipping
correctly). **SM1** is the actual data writer — it runs `OUT PINS, 8`
in a tight self-loop with `AUTOPULL=1, PULL_THRESH=8`, waiting for
bytes to arrive in its TX FIFO.

The real OneROM firmware arms DMA CH1 with
`write_addr = 0x50400014`, i.e. **TXF1** (SM1's TX FIFO at offset
`0x014`). This was visible in the harness trace:

    DMA CH1 armed at cycle 1: read=0x20000000 write=0x50400014 ...

But `tick_ch1` in the glue DMA hard-coded the destination as
`PIO_BASES[2] + PIO_TXF0` (= `0x50400010` = **TXF0**, SM0's TX FIFO).
Bytes therefore landed in SM0's FIFO, where SM0 — a CS handler using
`MOV X, PINS` — never read them. SM1 meanwhile stalled forever on
autopull, and `shared_pin_values` stayed at its `u32::MAX` reset,
propagating through `merge_pin_outputs` to `pad_out = 0xFFFFFFFF`.

The `ch1_push_count` increment was misleading: it counted successful
bus writes, not whether the byte reached the right SM.

## Fix

`crates/mdpicoem-harness/src/onerom_glue_dma.rs`:

1. `tick_ch1` now reads `self.ch[1].write_addr` — the channel's
   configured write target — instead of the hard-coded `TXF0` offset.
2. A new helper `decode_pio_tx_addr(addr) -> Option<(u32, u32)>`
   derives `(pio_base, sm_index)` from a PIO TXFn address so the
   FSTAT `TX_FULL` back-pressure check can use the correct SM bit.
   It validates the 12 recognised slots (PIO0..PIO2 × SM0..SM3) and
   returns `None` otherwise, in which case the push still happens but
   without the back-pressure retry (a TODO marks this as a followup
   when a non-PIO sink eventually exercises it).
3. `PIO_TXF0` is marked `#[cfg_attr(not(test), allow(dead_code))]`
   because the production path no longer references it — only the
   legacy chain tests still use it as a literal write-target argument.

## Regression tests

1. **PIO engine regression test** in
   `crates/mdrp2350/src/pio_tests.rs`:
   `test_pio_onerom_sm1_out_pins_8_autopull_drives_pad_out`. Reproduces
   the OneROM SM1 shape (`OUT PINS, 8` at PC 6, wrap 6→6, autopull
   threshold 8, `OUT_SHIFTDIR=right`, `OUT_BASE=16`, `OUT_COUNT=8`),
   pushes `0xAA` directly to TXF1, steps, and asserts
   `pad_out` bits 16..23 == `0xAA` and `pad_oe` bits 16..23 == `0xFF`.
   **This test passes on main** — it documents and guards the exact
   primitive shape OneROM relies on.

2. **Glue DMA integration test** in
   `crates/mdpicoem-harness/src/onerom_glue_dma.rs::tests`:
   `glue_dma_ch1_respects_write_addr_for_non_sm0_target`. Arms CH1
   with `write_addr = PIO2 + 0x014` (TXF1) and asserts via FSTAT that
   the byte lands in **SM1's** TX FIFO, not SM0's. **Fails on main**,
   passes post-fix.

## Validation

- `cargo test --release -p mdrp2350`: all pass (including the new
  regression test).
- `cargo test --release -p mdpicoem-harness --lib`: 270/270 pass
  (including the new glue DMA test).
- `cargo test --release -p mdpicoem-common`: 98 pass, 1 pre-existing
  flake (`pacer::tests::test_pacer_behind_detection`, timing-dependent,
  unrelated to PIO — last touched in Phase 2).
- `cargo run -p mdpicoem-harness --release --bin onerom_pio_diff_rp2350`:
  PASS — 20/20 cycles still match the committed synthetic trace.
- `cargo run -p mdpicoem-harness --release --bin onerom_serving_oracle_rp2350`:
  **baseline case now reports `verdict=Pass observed=0x00`** (was
  `WrongByte observed=0xFF`). The 14 other walk1/pattern cases still
  report `AddrOOR` — but that's the Stage G journal's known "baseline
  is degenerate" caveat: CH0 hasn't overwritten CH1.READ_ADDR yet at
  G.1 stimulus time, so the address pipeline is untested. Unblocked
  by this fix; out of scope for this patch.

## Follow-ups for the Stage G team

- G.2 walk1 A0..A10 cases all resolve to out-of-shadow addresses.
  My fix is orthogonal to this — `tick_ch0` (CH0 address pipeline)
  is untouched. The `AddrOOR` failures probably indicate either
  OneROM's PIO1 address-decoder program isn't forwarding what the
  harness expects, or CH0's 4-cycle read latency is mis-aligned with
  the G.2 cadence. Worth a separate investigation before G.3.

- The glue DMA's `None`-path fallback in `tick_ch1` silently pushes
  without back-pressure when `write_addr` isn't a recognised PIO TXFn
  slot. Strictly better than the pre-fix hard-coded behaviour (which
  always checked SM0 regardless of target), but a future non-PIO sink
  test could surprise itself. `TODO` marker is in place.
