## Stage 0 — Setup

**Complete.** Journal skeleton created. Research agent dispatched for
Stage 2 prep. Stage 1 team briefed.

### Research findings — PSRAM protocol (Stage 2 input)

- **Chip:** apmemory APS6404L-3SQR-SN (8 MB QSPI pseudo-SRAM).
- **Mode:** single-SPI only. Firmware never issues `0x38` (enter QPI).
- **Command set actually used (complete truth set for modelling):**
  - `0x66` — Reset Enable (50 μs busy-wait follows)
  - `0x99` — Reset (100 μs busy-wait follows)
  - `0x02` — Write (24-bit address + data)
  - `0x0B` — Fast Read (24-bit address + 8 dummy cycles + data)
- **Pinout (PicoGUS v4.0.0):** GPIO0=MISO, GPIO1=CS, GPIO2=SCK,
  GPIO3=MOSI. Driven by **PIO1** (single state machine, DMA-fed).
- **PIO sideset:** bit1=SCK, bit0=CS.
- **Fudge factor:** at high SPI rates, reads need +1 SCK cycle before
  data; firmware auto-detects via `test_psram` at boot.
- **Firmware version to pin:** `v4.0.0` (2026-04-06).
  `rp2040-psram` submodule SHA `7786c93e`.

No QPI state machine, no READ-ID, no wrap-boundary config to model.
Four commands + fixed timing. Stage 2 is smaller than feared.

## Stage 2 — External SPI PSRAM model

**Start/End:** 2026-04-14 / 2026-04-15
**Status:** complete, committed
**Agents:** impl-stage2, reviewer-stage2, apply-feedback-stage2,
devils-advocate-stage2

### Outcome

- New module `crates/mdrp2040/src/peripherals/` with `psram.rs`.
- `Psram` owns `Box<[u8; 8 << 20]>` + a `Phase` state machine (Idle /
  Cmd / WriteAddr / WriteData / ReadAddr / ReadDummy / ReadData /
  SilentNop). Pins hardcoded GPIO0=MISO, GPIO1=CS, GPIO2=SCK,
  GPIO3=MOSI per PicoGUS v4.0.0.
- Models exactly the 4-command APS6404L subset firmware uses: 0x66,
  0x99, 0x02, 0x0B (with 8-cycle dummy). No QPI, no READ-ID, no wrap
  config.
- Hooked into `Emulator::update_gpio()`: `psram.tick(pads)` runs after
  the PIO/SIO merge, optionally splicing MISO into `gpio_in` bit 0.
- Version bumps: `mdrp2040` 0.3.0 → 0.4.0, `mdpicoem-common` 0.3.0 →
  0.4.0 (new `PioBlock::any_sm_enabled` accessor).
- `cargo test -p mdrp2040` — 256/256 pass (240 baseline + 14 PSRAM + 2
  PIO-driven integration).

### Critical mid-stage fix — quantum-granularity integration

Initial implementation called `tick_pio(consumed)` (bulk) then
`update_gpio()` (once) per `Emulator::step()`. With step_quantum=64,
PSRAM only saw the final pin snapshot of each quantum → every
PIO-driven SCK edge slipped. Reviewer caught the architectural gap;
apply-feedback agent replaced the tail with a gated interleave:

```rust
if pio_idle {
    self.tick_pio(consumed);
    self.update_gpio();
} else {
    for _ in 0..consumed {
        self.tick_pio(1);
        self.update_gpio();
    }
}
```

`pio_idle := !pio[0].any_sm_enabled() && !pio[1].any_sm_enabled()`.
`paced_bench_rp2040` before/after: 118.4 → 119.1 MHz avg (within
variance). Added two PIO-driven tests proven to fail against the old
bulk path.

### Process notes / lessons

- Reviewer actually ran `cargo build`/`cargo test` this time (Stage 1
  lesson internalised) and caught the quantum-granularity bug that
  unit tests missed.
- Devils-advocate spotted the missed `mdpicoem-common` version bump;
  supervisor applied the one-line fix.

### Devils-advocate findings (logged in `tech_debt.md`, non-blocking)

1. PSRAM PIO-integration tests cover only 1 SCK edge per quantum —
   wouldn't catch a regression to "update_gpio twice per step".
   Needs a multi-edge-per-quantum stress test.
2. Enable-then-disable mid-quantum drops edges via the fast-path
   predicate. Pathological in real firmware; flagged for completeness.

### Notable design decisions

- **`Box<[u8; 8 << 20]>` via `vec! → into_boxed_slice → try_into`:**
  direct `Box::new([0u8; N])` blows the 1 MB Windows debug stack
  because the 8 MB array is materialised on the stack pre-move. Worth
  remembering if we add larger backing stores.
- **`pio_idle` gate:** the naive interleave regressed paced_bench by
  ~49% on pure-ALU workloads. Gating recovered the full throughput.
  Safe because when both PIO blocks are disabled, pin state cannot
  change during the peripheral-tick window.

## Stage 3 — DOSBox-X tap + trace format

**Start/End:** 2026-04-15 (single session)
**Status:** complete, committed
**Agents:** impl-stage3, reviewer-stage3, apply-feedback-stage3,
devils-advocate-stage3

### Outcome

- `third_party/dosbox-x-picogus-tap.patch` — 103-line unified diff
  against DOSBox-X master `f43ce61d`. Hooks `read_gus` / `write_gus`
  in `src/hardware/gus.cpp`. Env-gated via `PICOGUS_TAP_FILE`.
  Emits CSV: `# picogus-tap v1\nns,port,value,kind\n<rows...>`.
- `third_party/README.md` — apply / build / use instructions, pinned
  SHA, known limitations.
- `crates/mdpicoem-harness/fixtures/sample_gus.trace` — 19-event
  hand-crafted fixture covering all 4 `kind` values. Used by Stage 4
  replayer tests.

### Design choices

- **Hook `read_gus` / `write_gus`** (the `Bitu(port, iolen)` entry
  points in gus.cpp) rather than the wrappers — captures every GUS
  I/O path with zero duplication.
- **`PIC_FullIndex()` × 1e6 → u64 ns** with a monotonicity clamp
  (`static last_ns`) to defend against pause/resume backwards steps.
- **Reentrant guard** around the 16-bit read recursion so each
  logical access logs exactly one row.
- **Env var carve-out** — HLD bans env vars in *our* Rust code;
  DOSBox-X is third-party, debug-only, and lacks a cleaner
  mechanism. Documented in README.

### Devils-advocate findings (tech_debt, non-blocking)

1. **GUS DMA channel traffic may not be captured.** The tap covers
   `read_gus` / `write_gus` but GUS DRAM DMA transfers may bypass via
   `GUS::DMA_Callback` depending on DOSBox-X internals. If bypassed,
   patch samples never reach PicoGUS's PSRAM in replay → Stage 6 is
   silent. **Must resolve before Stage 6.** Three mitigation options
   in tech_debt.md.
2. Reentrant guard not exception-safe (low priority).

## Stage 4 — Trace replayer + GPIO injection

**Start/End:** 2026-04-15 (across a rate-limit-interrupted session)
**Status:** complete, committed
**Agents:** impl-stage4 (rate-limited mid-task), impl-stage4-finisher,
reviewer-stage4, apply-feedback-stage4, devils-advocate-stage4,
blockers-fix-stage4

### Outcome

- `crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs` (~1080 LOC)
  — single-binary harness that parses the PicoGUS CSV trace, advances
  the `mdrp2040::Emulator` to each event's target cycle, and pokes the
  Bus's new `external_gpio_in_override` / `external_gpio_in_mask`
  fields to synthesise an idealised ISA write waveform. Reads are
  skipped per HLD.
- CLI: `--flash`, `--trace`, `--duration`, `--post-roll` (default
  0.5 s for post-event firmware drain).
- `ReplaySummary` reports events fired / skipped / stalled, final
  cycle count (including post-roll), wall/sim ratio.
- Emulator constructed with `step_quantum=1` for per-cycle ISA
  waveform precision — essential because the synthetic cycle is only
  ~37 sysclks wide.
- Defensive: one-shot stall warning if the emulator wedges (e.g. no
  firmware loaded, cores HardFault to halt).

### Cross-crate infrastructure change (B1 fix)

Added `external_gpio_in_override: u32` + `external_gpio_in_mask: u32`
fields to `mdrp2040::Bus`. `Emulator::update_gpio` applies them AFTER
the SIO/PIO merge and PSRAM MISO splice — last-writer-wins on
masked pins. This is what lets the replayer's waveform survive
`update_gpio` calls within a step_quantum=1 loop.

`mdrp2040` version bump 0.4.0 → 0.5.0.

### Tests

- 3 new `mdrp2040` unit tests covering the override: default merge,
  override-wins-over-SIO, reset clears override.
- 4 new `picogus_diff_rp2040` tests: post-roll advances sink,
  post-roll zero = None, stall counter increments, end-to-end with
  real `Emulator` sink.
- 10 prior parser / replay / GPIO-poke tests retained.
- Totals: `mdrp2040` 259/259, `picogus_diff_rp2040` 17/17.

### Process notes / lessons

1. **First implementation agent hit Anthropic rate limit mid-task.**
   Recovered via a finisher agent that ran the build, found a
   dead-code warning + a `replay()` hang on no-firmware (cycle counter
   never advanced → spin forever), and fixed both.
2. **Devils-advocate caught 3 Stage-6 blockers the reviewer missed.**
   All three were masked by tests using a mock `IsaSink` that

### Deferred to tech_debt (not blocking Stage 5)

1. **Pin mapping cross-check vs polpo/picogus v4.0.0** — resolved in

## Stage 5 — I2S capture to WAV

**Start/End:** 2026-04-15 (single session)
**Status:** complete, committed
**Agents:** impl-stage5, reviewer-stage5, apply-feedback-stage5,
devils-advocate-stage5, cycle-counter-fix-stage5

### Outcome

- `crates/mdpicoem-harness/src/i2s_capture.rs` — Philips-I2S decoder
  (16-bit stereo, MSB-first, LRCLK low=left) + hand-rolled 44-byte
  canonical PCM WAV writer. Edge-triggered: shift on BCLK rising,
  finalise on LRCLK transition.
- `crates/mdpicoem-harness/src/picogus_pins.rs` — authoritative
  single source of truth for pin constants. Cross-checked against
  PicoGUS v4.0.0 firmware source: I2S DOUT=16, BCLK=17, LRCLK=18;
  PSRAM 0-3; ISA IOW=4, IOR=5, AD0..9=6..15; other ISA signals on
  19/21/26/27/28.
- Stage 4's worry that I2S would collide with ISA pins 26-28 was
  unfounded — different pins entirely.
- `picogus_diff_rp2040` binary: new `--out <path>` flag (default
  `crates/mdpicoem-harness/oracles/picogus_<trace_stem>.wav`) +
  `CapturingSink<S>` wrapper that ticks I2S after each inner step.
  Summary prints WAV path, file size, frame count, LRCLK edges,
  inferred sample rate.

### Critical mid-stage fix — cycle counter

Initial implementation had `I2sCapture.tick(pads)` increment a local
`cycle: u64` counter by 1 per call. With `step_quantum=1`, each
`Emulator::step()` advances one *instruction* (1–4 sysclks), not one
sysclk. Mock-sink tests masked this because their `step(n)` always
advanced exactly `n`. Devils-advocate caught it: inferred sample rate
would be multiplied by average-CPI (≈2×), so WAV header would be
stamped ~70–90 kHz instead of 44.1 kHz.

**Fix:** `tick` signature changed to `tick(pads, now_cycles: u64)`.
`CapturingSink::step` reworked to advance until `inner.cycles() ≥
target`, threading `inner.cycles()` into every tick. Dropped the
local `cycle` field entirely. Added:
- `capturing_sink_stamps_edges_in_sysclks_not_ticks` — synthetic 4-CPI
  mock sink, asserts inferred rate matches sysclk-based formula.
- `capturing_sink_cycle_matches_emulator_cycles` — real `Emulator`
  parked on `B .` (3-cycle loop), 8 steps, asserts observed cycle
  timestamps match `emu.cycles()` exactly (3, 6, …, 24).

### Devils-advocate findings (non-blocking follow-ups)

1. **`CapturingSink` perf:** `inner.step(1)` in a loop at

2. **Frame buffer unbounded** (~10 MB per minute of audio).
   Acceptable for 10-s HLD snippets; cap + warn before long soaks.
