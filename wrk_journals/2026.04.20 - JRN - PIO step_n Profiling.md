# PIO `step_n` Profiling — 2026-04-20

## Goal

The threaded `peripheral` and `stress` workloads flatline at ~64 MHz
regardless of `step_quantum` (vs 130/81 MHz serial respectively). Per
the `Threaded Perf Investigation` journal, the limiter is the PIO
worker thread: it ticks proportionally to `step_q`, so larger quanta
don't help, and at the per-quantum barrier the PIO worker gates
core 0 / core 1 / coord. The CPU side hits real-time and beyond
(threaded basic 275 MHz vs 150 MHz target), so closing the
peripheral gap is purely a PIO question.

The cost lives inside `PioBlock::step_n(step_q, gpio_in)`. We don't
yet know the breakdown — could be the SM decoder, the FIFO checks,
the GPIO pad merge, the IRQ flag updates, the SET/OUT/SIDE-SET pin
arbitration, or something else.

This journal tracks the profiling work and any optimisations that
follow.

## Plan

1. Read `PioBlock::step_n` and trace the per-cycle path.
2. Build a focused benchmark binary that drives the PIO worker
   (or `step_n` directly) under a saturating workload, with as
   little CPU/coord noise as possible.
3. Profile with samply on Windows.
4. Decide which knob to turn first based on what dominates.

## Microbench

`crates/mdpicoem-harness/src/bin/pio_microbench.rs` — drives a single
`PioBlock` with N SMs enabled, all running the same 2-instruction wrap
loop (SET PINS,1 / SET PINS,0) at clkdiv=1. Measures `step_n`
throughput. No threading, no barrier, no coord — just the inner loop.

## Baseline numbers

| sms | step_q  | MHz   | ns/sysclk |
|-----|---------|-------|-----------|
| 1   | any     | 137   | 7.30      |
| 4   | 4096    |  42   | 23.7      |

step_q has no measurable effect (as expected — `step_n` is just
naive `for { step }`). 1-SM at 137 MHz is the working number.

For sanity: in the threaded `peripheral` workload at sq=4096, the
bench reports ~64 MHz per-core. That implies ~30 μs of CPU work +
~30 μs of PIO work per quantum, plus barrier overhead. So PIO at
137 MHz isn't the *only* limiter — it's roughly co-equal with the
CPU side at that step_q. Halving PIO ns/sysclk would meaningfully
move the needle.

## Suspects in `step()` per sysclk (1 SM enabled)

Source: `crates/mdpicoem-common/src/pio/mod.rs:309-327` and
`pio/sm.rs:288-377`.

1. **`bump_pad_out_diag`** (mod.rs:422) — pure diagnostic, runs every
   sysclk, does pad_out diff against snapshot + bumps PSRAM-SPI edge
   counters.
2. **`merge_pin_outputs` trace! comparison** (mod.rs:399-408) — the
   `if out != self.pad_out || oe != self.pad_oe` check is dead in
   release builds (trace! compiles out) but the comparison still runs.
3. **`pc_visits` bump** (sm.rs:360-363) — pure diagnostic, per
   non-forced executed instruction.
4. **The 4-SM loop in `step()`** — three `clock_tick` calls returning
   false (disabled SMs) every sysclk.
5. **`merge_pin_outputs` doing per-SM side-set work** even when side-set
   isn't programmed (ss_count==0).

Each gets an A/B turn below.

## A/B results

Each row: 200M cycles × 3 runs averaged, `--sms 1 --step-q 4096`.
ns/sysclk is what matters; MHz follows.

| # | Variant | ns/sysclk | MHz   | Δ vs base |
|---|--------------------------------|-----------|-------|-----------|
| 0 | Baseline (production)          | 7.29      | 137   | —         |
| 1 | strip `bump_pad_out_diag`      | 6.69      | 149   | **−0.60 (−9%)** |
| 2 | strip `trace!` cmp in merge    | 7.41      | 135   | +0.12 (noise)   |
| 3 | strip `pc_visits` bump         | 7.28      | 137   | −0.01 (noise)   |
| 4 | bit-walk `sm_enabled_mask`     | 8.10      | 123   | +0.81 (slower!) |
| 5 | strip side-set per-SM loop     | 6.12      | 163   | **−1.17 (−16%)** |
| C | A1 + A5 combined               | 5.67      | 177   | **−1.62 (−22%)** |

## What this means

**The diagnostics are the cost.** `bump_pad_out_diag` (PSRAM-SPI edge
counters) and the per-SM side-set merge loop together account for
~22% of `step()` runtime. Both run every sysclk, even when PIO is
running the simplest possible program (no side-set, no SPI).

**A2/A3 are noise.** The compiler optimises away the dead `trace!`
comparison block (release_max_level_info strips trace!). `pc_visits`
is a single array index + wrapping_add — too cheap to measure.

**A4 (bit-walk) is slower.** The unrolled `0..4` loop is faster than
a smarter mask walk because the compiler can inline `clock_tick`'s
disabled-SM early return as a constant test per iteration. The
mask-walk's `trailing_zeros` + `mask &= mask - 1` overhead exceeds
the saved iterations for small enable counts.

## Translation to threaded `peripheral` workload

At sq=4096, the threaded peripheral bench reports ~64 MHz per-core.
A 22% drop in PIO ns/sysclk would reduce per-quantum PIO time from
~30 μs → ~23 μs. If PIO and CPU were strict ceiling-then-add, that
puts us at ~75-80 MHz peripheral — a meaningful but not transformative
gain. The CPU-side cost in threaded mode (SIO atomic on contended
GPIO cache line, irq_pending atomic on coord) is doing the rest of
the damage; that's a separate investigation.

## Recommendations

Two clean wins, both behaviour-preserving:

### R1 — gate `bump_pad_out_diag` behind a cfg flag

The function is purely PSRAM-SPI debug instrumentation (per its own
doc comment) — `pad_out_cs_falls`, `pad_out_cs_rises`,
`pad_out_sck_toggles`. None of it affects emulation state or device
correctness. Gate behind a `pio-pad-diag` feature; off by default.

Pros: zero runtime cost. Diagnostic still available with
`--features pio-pad-diag` for PicoGUS-style PSRAM debugging.
Cons: existing tests that assert on these counters need the feature
on (check `cargo test`'s reach into them).

Estimated PIO gain: ~9%.

### R2 — short-circuit side-set merge when no SM has it programmed

Add an `any_sideset_programmed: bool` cached on `PioBlock`,
recomputed on PINCTRL writes (sideset count = bits 31:29 of PINCTRL).
In `merge_pin_outputs`, skip the per-SM loop when the flag is false
and just write `pad_out = shared_pin_values` / `pad_oe = shared_pin_dirs`.

Pros: zero behaviour change for programs that use side-set. ~16% gain
for programs that don't (the common case). No feature flag bookkeeping.
Cons: small invariant to maintain on PINCTRL writes — needs a unit
test that exercises programmed-then-unprogrammed flips.

Estimated PIO gain: ~16%.

### Combined: ~22% PIO step_n speedup

If both land, threaded peripheral workload likely climbs from
~64 MHz → ~75-80 MHz at sq=4096. Worth it.

## What I'm NOT recommending

- **Bit-walking enabled SMs** — measured slower than the unrolled loop.
- **Stripping the `trace!` block** — compiler already eliminates it.
- **Stripping `pc_visits`** — too cheap to matter.
- **`step_n` bulk-advance optimisation** mentioned in mod.rs:332 — not
  warranted at the per-step cost we measured. The per-step cost is
  ~5-7 ns; we don't gain by bulk-shortcutting unless we can prove
  whole-instruction-no-pin-change cycles. Complex, risky, marginal.
- **Per-block parallelism** (3 PIO worker threads) — earlier
  discussion. Worth revisiting when we have a PicoGUS-class workload
  saturating multiple blocks; not needed for current `peripheral`
  workload's 1-block 1-SM shape.

## Status

**Implemented and merged.** Both R1 and R2 landed.

### R1 — `pio-pad-diag` feature in `mdpicoem-common`

- New feature flag, off by default.
- `bump_pad_out_diag` function and its call site in `step` are
  cfg-gated.
- Two unit tests in `pio/mod.rs` that assert on the diag counters
  are cfg-gated to require the feature.
- The four `pad_out_*` counter fields stay always-present so
  `picogus_diff_rp2040` continues to compile (it reads them; with
  feature off they read 0, with feature on the counters work).

### R2 — `any_sideset_programmed` cache on `PioBlock`

- New `pub(crate)` boolean field, default `false`.
- Recomputed by `PioBlock::recompute_any_sideset()` (`pub`) after
  any PINCTRL write through `write32`. Tests that bypass `write32`
  to set `sm[i].pinctrl` directly (4 sites in `pio/mod.rs`) call
  the helper themselves.
- `merge_pin_outputs` short-circuits to `pad_out = shared_pin_values`
  / `pad_oe = shared_pin_dirs` (and bumps the trace! comparison)
  when the flag is false. Per-SM side-set loop runs unchanged when
  any SM has it programmed.

### Verification

- `cargo test -p mdpicoem-common` — 113 passed (default).
- `cargo test -p mdpicoem-common --features pio-pad-diag` — 115 passed.
- `cargo test -p mdrp2350` — 1389 passed, 30 ignored.
- `cargo test -p mdrp2040` — 514 passed.

### Final perf

| Bench | Pre | Post | Δ |
|---|---|---|---|
| Microbench `step_n` (1 SM) | 7.29 ns/sysclk (137 MHz) | 6.02 ns/sysclk (166 MHz) | **−17%** |
| paced_bench threaded peripheral sq=4096 | 64 MHz | **75 MHz** | **+17%** |
| paced_bench threaded stress sq=4096 | 64 MHz | **75 MHz** | **+17%** |
| paced_bench threaded basic sq=4096 | 250 MHz | 250 MHz | 0 (no PIO) |

Microbench gain transfers cleanly to the threaded benches because the
PIO worker is gating the barrier. Basic is unchanged (no PIO active).

### Outstanding

- `peripheral` and `stress` are still well below serial (130 / 81 MHz).
  Remaining gap is on the CPU side in threaded mode — the
  every-iter `STR R1, [SIO_GPIO_OUT_XOR]` goes through a contended
  atomic on `gpio.out[0]` that the coordinator also reads, which is
  more expensive in threaded mode than serial. Separate investigation
  if that workload becomes important.

- `step_n` per-block parallelism (3 PIO worker threads) still on the
  table for PicoGUS-class workloads that saturate multiple blocks.
  Not warranted yet.
