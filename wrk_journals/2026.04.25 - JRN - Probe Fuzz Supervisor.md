## Pre-launch fix

`fuzz-runs/run-probe.sh` previously hardcoded the no-`--probe` invocation,
so with two probes attached `probe-rs auto_attach` would pick the first
one regardless of target type and fail roughly half the attaches
(documented landmine in CLAUDE.md). Patched to take an optional
`$1 = VID:PID:SERIAL` selector exactly like `run-m0plus-probe.sh` already
does. Diff:

```
+# Optional argument $1: probe selector (VID:PID:SERIAL) for when two probes
+# are attached. When omitted, auto_attach picks the only visible probe.
+PROBE_ARGS=()
+if [ -n "$1" ]; then
+  PROBE_ARGS=(--probe "$1")
+fi
...
-    --fuzz 200 --seed "$SEED" >> "$LOG" 2>&1
+    --fuzz 200 --seed "$SEED" "${PROBE_ARGS[@]}" >> "$LOG" 2>&1
```

Backwards-compatible: omitting `$1` still works for the single-probe case.

3. `kill -9` on the bash driver POSIX PIDs (75187, 76533) to stop
   re-spawning. After that, no new batch lines appeared in either log.

   a second `kill -9` round.

### Tech-debt followups (not actioning tonight)

The driver scripts assume rc=0 from the binary means "everything was
fine" but the binary returns rc=0 even when it skipped 76% of cases due
to USB transport errors. That's how a single transient blip turned into
a multi-batch cascade. Two complementary fixes would harden this:

1. **Binary side:** make `probe_diff_rp2350` / `probe_diff_rp2040` exit
   non-zero (or a distinct exit code, e.g. rc=3) when the
   skipped-case count exceeds a small threshold. That signals "probe
   went away" vs. "0 failures, all good".
2. **Driver side:** detect rc=2 (probe creation failed) and back off
   for ~30s before retrying. Right now rc=2 takes <1s, so the loop
   burns 60+ seeds per minute through dead-probe attaches.

Worth one short tech-debt session, but **not** mid-fuzz — these are
script changes that need careful testing, not improvisation while live
hardware is in a partially-wedged state.

## Tech-debt items raised this session

1. **Driver scripts lack PID-locking** — concurrent invocations of
   `run-probe.sh` / `run-m0plus-probe.sh` share `$LOG` and write
   the same `.$$.exe` BIN namespace. Multiple instances stomp.
   Fix: `flock` on a sentinel file at script entry, or `set -e`
   + `pgrep -f run-probe.sh` early-exit. Filed in the rc=2 backoff
   patch; no code change beyond that yet.
2. **`probe_diff_*` returns rc=0 in degraded "all-skip" mode** — a
   mid-run USB blip that flips the binary into "skip everything"
   shows as rc=0, hiding the failure from any retry-on-rc!=0 logic.
   Fix: exit non-zero (e.g. rc=3) if skipped > 50% of total. Not
   patched mid-fuzz to avoid kicking the running drivers.
3. **WinUSB endpoint cascade signature** — every cascade so far
   has the same shape: a single transient `read_status: bulk read
   failed` from probe-rs, then 100% of subsequent attaches return
   rc=2 until the OS-side endpoint state clears. Manifests within
   minutes after the first symptom. Reseat (USB unplug-replug) is
   the only reliable recovery; `probe-rs reset --chip RPxxxx` does
   not help. The 30s rc=2 back-off (added late on 04-25) does not
   actually clear the cascade — it just slows the spam rate. Worth
   investigating whether `probe-rs detach` or a timed `Sleep + USB
   port reset` API call (Win32 `CM_Reenumerate_DevNode` over the
   probe's device instance) could software-recover.
4. **No PID-lock means autonomous-loop or sibling-context driver
   restarts cascade silently.** Cascade #4 was almost certainly
   triggered by a stray `bash run-probe.sh` invocation from the
   prior context's recovery path, fighting with the existing
   driver bash. PID-lock would have made the second invocation
   exit with a clear "already running" message instead of going
   into a destructive race.
