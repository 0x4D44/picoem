# 2026.04.23 — PicoGUS continued: stack-test stub + silence diagnosis

## Context (continued from earlier 2026-04-23 journal)

Yesterday's dumper + 8 stub tests proved all primitives work (MULS,
loops, pointer chain, cross-core read, mult-accum). Yet the real
`GUS_sample_stereo` returns 0 every call across 740K IRQs with voice 1
holding VolLeft=21 and sample_cache full of real triangle data.

The one primitive NOT yet tested by stubs: **stack-based storage in
core 1 under IRQ**. The real function does `sub sp, #28` and stores
`accum[0]` / `accum[1]` to `[sp, #4]` / `[sp, #8]`. If those writes
end up somewhere that can't be read back — or the SP itself is wrong —
the accumulator stays 0.

## Hypothesis

Stack reads/writes from core 1 in IRQ context may land in a region the
emulator doesn't back properly, or may alias something else, so `str
[sp, #N]` followed by `ldr [sp, #N]` returns 0.

## Plan

1. **Stub 9 — stack roundtrip.** Replace `GUS_sample_stereo` with:
   `sub sp,#8; movs r0,#77; str r0,[sp,#0]; movs r0,#0;
    ldr r0,[sp,#0]; add sp,#8; bx lr`.
   Expected: WAV LEFT = 77>>1 = 38. If 0 → stack is broken on core 1
   in IRQ. If 38 → stack works at the 0-offset level.

2. **Stub 10 — stack-based accumulator loop.** Same as stub 8 but keep
   the accumulator on the stack (`str/ldr [sp, #4]` each iteration).
   Expected: same result as stub 8 (WAV LEFT ≈ 1100). If 0 → stack
   writes inside a loop are dropped.

3. If both pass, move to **firmware-side instrumentation** —
   modify `GUS_sample_stereo` to stash `accum[0]` after each voice at
   a known SRAM address. Rebuild. Probe. This will pinpoint which
   specific voice-loop iteration breaks.

### Step 3 — while stub 9 ran, re-read the real GUS_sample_stereo

Found a major clue in the function's return path (`pg-gus.dis:2180`):

```asm
20001022: mov  r2, ip             ; LEFT accum (32-bit)
20001024: ldr  r3, [pc, #712]     ; literal = 0xD00000C0
20001026: str  r2, [r3, #0]       ; INTERP1_ACCUM0 = r2
20001028: ldr  r0, [r3, #32]      ; r0 = INTERP1_PEEK_LANE0
2000102a: str  r7, [r3, #0]       ; INTERP1_ACCUM0 = r7 (RIGHT)
2000102c: ldr  r3, [r3, #32]      ; r3 = INTERP1_PEEK_LANE0
2000102e: lsls r0, r0, #16        ; low 16
20001030: lsrs r0, r0, #16        ;   (zero-extended)
20001032: lsls r3, r3, #16        ; high 16
20001034: orrs r0, r3             ; return = clamp(RIGHT)<<16 | clamp(LEFT)
20001036: add  sp, #28            ; epilogue
```

The firmware uses **INTERP1 lane 0 as the hardware CLAMP16 saturator**.
`GUS_Setup` (`pg-gus.dis:2946`) programs it once:

- `INTERP1_CTRL_LANE0 = 0x0040_C40E` — SHIFT=14, MASK_LSB=0,
  MASK_MSB=17, SIGNED=1, CLAMP=1.
- `INTERP1_BASE0 = 0xFFFF_8000` (-32768 — clamp lower bound).
- `INTERP1_BASE1 = 0x0000_7FFF` (+32767 — clamp upper bound).

In HW, writing ACCUM0 and reading PEEK_LANE0 yields
`clamp((accum0>>14), -32768, 32767)`.

In **our emulator**, the interpolator register block at
`crates/mdrp2040/src/bus/sio.rs:202` was a **pure backing store** — no
CLAMP/SHIFT/MASK logic. Reads of PEEK_LANE0 returned the raw backing
value at that register index, which firmware never writes — always 0.

**That's the silence cause.** Every call to `GUS_sample_stereo` returns
`clamp_right<<16 | clamp_left = 0<<16 | 0 = 0`.

### Step 4 — implemented INTERP0/INTERP1 PEEK/POP compute logic

In `crates/mdrp2040/src/bus/sio.rs`:

- Added `interp_lane_peek(core, which, lane)` — applies SHIFT (arith-
  metic if SIGNED), MASK to `[mask_lsb..=mask_msb]` (sign-extend from
  `mask_msb` if SIGNED), then either CLAMP to `[BASE0,BASE1]` signed
  (INTERP1 lane 0 when CTRL.CLAMP=1) or adds `BASE_L`.
- Added `interp_full_peek(core, which)` — lane0 + lane1 + BASE2.
- Dispatched read offsets 0x14/0x18/0x1C (POP_*) and 0x20/0x24/0x28
  (PEEK_*) within each INTERP block to the compute helpers. POP is
  currently aliased to PEEK — cross_input/cross_result accumulator
  side-effects aren't modelled yet; PicoGUS doesn't exercise POP on
  INTERP1.
- Unit test `interp1_signed_clamp_lane0` covers the PicoGUS config
  (small +/-, large +/-, per-core isolation).

Bumped `mdrp2040` 0.15.2 → 0.15.3.

### Remaining gap — not silence, but audio quality

The bimodal "rails-or-zero" output pattern is **not how real music
would look**. Suspects (for future iteration):

1. **I2S capture framing bug** (seen yesterday with stub 1: pushed 0xFF
   came out as L=127, R=-32768 — a 1-bit MSB shift + probable
   channel misalignment). The values like `-32748 = 0x8014` fit an
   I2S-framing hypothesis more than a clamp or mixer bug.
2. **INTERP1 ADD_RAW / CROSS_INPUT semantics** — I implemented the
   basic path only; if firmware or SDK code somewhere uses those bits,
   my impl may be wrong.
3. **5× PWM IRQ rate oddity** — sim produces ~120 kHz sample rate vs.
   expected 22.9 kHz. If the sysclk divergence also affects when
   voice-ramping arithmetic happens, the effective gain curve could
   jump instead of ramp.

None of these blocks the "get audio" milestone. They're tractable
follow-ups.

## Status

**Primary goal achieved — PicoGUS audio is no longer silent.**

The silence bug was: our RP2040 SIO interpolator was a pure register
backing-store — no SHIFT / MASK / SIGNED / CLAMP computation.
GUS_sample_stereo (`pg-gus.dis:2180`) uses INTERP1 lane 0 as a
hardware CLAMP16 saturator. Reads of INTERP1_PEEK_LANE0 always
returned 0 regardless of what firmware wrote to ACCUM0, so every
IRQ pushed 0 to the I2S TX FIFO.

Fix: implement PEEK/POP lane compute in
`crates/mdrp2040/src/bus/sio.rs` for INTERP0/INTERP1 × lane 0/1 ×
PEEK/POP/FULL. Version bump mdrp2040 0.15.2 → 0.15.3. Unit test
`interp1_signed_clamp_lane0` covers the PicoGUS CTRL value.
