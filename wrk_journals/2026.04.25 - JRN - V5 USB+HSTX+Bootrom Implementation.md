### Fact 1 — bootrom binary layout

- **File size.** `D:\language\mdrp2354\roms\rp2350\bootrom-combined.bin`
  is exactly **32768 bytes (32 KB)**, confirmed by `wc -c` and `stat`.
- **SHA256.** `c5f9c48c6539f043c423344a53ceaea3774dd1e4c337af49da741a5d259c84bc`
  (computed via `sha256sum`). Written to
  `D:\language\mdrp2354\roms\rp2350\bootrom-combined.bin.sha256`
  (one-line hex digest, no filename suffix). This is the **in-tree
  binary's** hash — provenance vs silicon is Fact 2's silicon-session
  follow-up; until the silicon SHA is captured, treat this digest as the
  "in-tree-canonical" pin, not the "silicon-canonical" pin.
- **ELF section layout** (from `arm-bootrom.dis` header at lines 5-14):
  - `.text`: VMA `0x0000_0000`, size `0x4a40` → covers `[0x0000, 0x4a40)`.
  - `.secure_gateways`: VMA `0x0000_7e00`, size `0x0200` → covers
    `[0x7e00, 0x8000)`. Last symbol at `0x7fe4 <s_varm_otp_wait_sbpi_done>`
    (`arm-bootrom.dis:8583`); last byte before tail data is `0x7ffc`.
  - **Disassembly gap**: `[0x4a40, 0x7e00)` — 12.7 KB — has no Arm
    symbol coverage in `arm-bootrom.dis`.
- **Back-half identity (the gap).** The file is non-zero across the
  entire gap. `xxd -s 0x4A40 -l 64` shows `01f0 26bb 0723 03f0 dbb9 0023
  60bf 7047 30b5 4018 4942 435c 0132 1c0a ad41 05d1` etc. — the bytes
  immediately after `.text` are still Arm Thumb-shaped (`30b5` = `push`,
  `7047` = `bx lr`). `xxd -s 0x5000 -l 64` shows the literal ASCII
  `UF2.` (`5546 320a` = "UF2\n") at offset `0x5034`. By offset `0x7000`
  the byte patterns no longer look like Thumb (`8442 0bc4 670c 6114
  01cc 7d14`) and are consistent with RISC-V (Hazard3) compressed +
  full-width encodings.
- **Best inference**: the front half (`0x0000..0x4a40`) is the Arm
  Secure-domain bootrom code per the ELF; the
  `[0x4a40, 0x7cd4)` gap holds the **RISC-V (Hazard3) bootrom code
  path + supporting tables/data** (UF2 magic at 0x5034 belongs to the
  boot scan path which is shared with the RISC-V image);
  `[0x7cd4, 0x7e00)` holds the **Arm `rom_func_table` data** (the
  well-known pointer at offset `0x14` of the vector table holds value
  `0x7cd4` — confirmed at `arm-bootrom.dis:53-54` `<_arm_well_known_rom_table_base>:
  7cd4`; an `xxd -s 0x7cd4 -l 64` dump shows the canonical pico-sdk
  rom_func_table format — 2-char ASCII codes `SR`, `GS`, `SC`, `LP`,
  `GP`, `GB`, `RB`, `FA` interleaved with offset/bitmask words —
  i.e. this region is Arm-side data, not RISC-V); and
  `[0x7e00, 0x8000)` is the Arm secure-gateways block (Secure ↔
  Non-Secure trampolines). This matches the public RP2350 bootrom
  layout — a single 32 KB image containing both Arm and RV32 bootrom
  paths plus the Arm rom_func_table. There is **no zero padding**
  anywhere in the file; the back half is genuine code/data.
- **Implication for Component 3**: this strengthens the
  no-stray-walker case for `resolve_rom_func`. The walker starts at
  `0x7cd4` (reached via the well-known pointer at vector-table
  offset `0x14`), iterates entries until the first NUL terminator
  (which lives strictly inside `[0x7cd4, 0x7e00)`), and therefore
  can never stray into the RISC-V byte range — the RV bytes are
  entirely behind the walker's start address.
- **Caveat**: no RISC-V disassembler is in `PATH` on this host
  (`which llvm-objdump` / `riscv32-unknown-elf-objdump` both fail), so
  the RV32 identification is by byte-pattern inspection, not full
  disassembly. The conclusion is "consistent with Hazard3, definitively
  not zero-padding," which is what Stage 0 Fact 1 needs to answer
  ("Arm Secure-only / RISC-V / padding").
- **`mdpicoem-common::memory::ROM_SIZE`** at
  `D:\language\mdrp2354\crates\mdpicoem-common\src\memory.rs:2` is
  `32 * 1024 = 32_768`. **Matches the bootrom binary size exactly.**
  `Memory::load_rom` at `memory.rs:60` clamps with
  `data.len().min(ROM_SIZE)` so a 32 KB image lands fully. No
  truncation; the **R4 fallback caveat does not fire** — no multi-file
  refactor needed.

### Fact 4 — current bus-fault semantics + breaker tests

- **Bus-fault semantics for `0x5*` unmodelled addresses**: confirmed
  **no fault**.
  `D:\language\mdrp2354\crates\mdrp2350\src\bus\mod.rs:2669` opens the
  `0x4 | 0x5` arm of `read32`. Lines 2722-2725 are the fall-through
  for unmatched bases: `warn_unmodelled_mmio(canonical)` then
  `*self.peripheral_regs.get(&canonical).unwrap_or(&0)` — a HashMap
  lookup that returns 0 by default. The `_` bus-fault catch-all at
  line 2748 (`self.atomics.set_bus_fault(...)`) is reached only by
  region values *outside* `{0x0, 0x1, 0x2, 0x4, 0x5, 0xD, 0xE}` — so
  `0x5010_*`, `0x5011_*`, `0x5060_*`, `0x400C_*` all hit the silent
  HashMap path, not the fault path. Adding stubs for these addresses
  flips a "warn-once + read 0 / store-and-read-back" surface into
  defined peripheral semantics, which is exactly the breaker pattern
  V5 HLD Fact 4 calls out.

- **Grep results across all six probes** (counts):

  - `D:\language\mdrp2354\crates\mdrp2350\src\tests.rs:6989-6992` —
    **Won't break.** This is the `bootrom_diagnostic_run` test
    (`tests.rs:6907`), which prints a diagnostic dump of memory at
    `0x5010_0000` via `emu.peek(addr)`. `emu.peek` resolves through
    `Memory::peek32` (`mdpicoem-common/src/memory.rs:214`), which
    dispatches on `addr >> 28` and only handles `0x0/0x1/0x2`; address
    region `0x5` falls into `_ => 0`. **No `Bus::read32` involvement
    and no assertion** — only `eprint!`/`eprintln!` calls. Safe.
  - `D:\language\mdrp2354\crates\mdrp2350\src\threaded\bus.rs:2082-2089`
    `ahb_read_unmapped_falls_back_to_legacy` — **WILL BREAK.** Writes
    `0x1234_5678` to `0x5060_0000` then asserts the read returns the
    same value. New `HSTX_FIFO` stub will silently consume FIFO writes
    and return `LEVEL=0`/empty status on read.
  - `D:\language\mdrp2354\crates\mdrp2350\src\threaded\bus.rs:2122-2134`
    `ahb_write_legacy_aliases` — **WILL BREAK.** Tests XOR/SET/CLR

    explicit assertions (`0xFF00_0000`, `0xFF00_0F0F`, `0xFF00_000F`).
    Stub will not preserve fallback storage semantics under the alias
    paths.
  - `D:\language\mdrp2354\crates\mdrp2350\src\threaded\bus.rs:2361-2370`
    `ahb_byte_write_rmw_through_word` — **WILL BREAK.** Word-write
    `0xAABB_CCDD` then byte-write `0xFF` at `+1`, asserting RMW yields
    `0xAABB_FFDD`. Stub will not preserve byte RMW semantics on FIFO.
  - `D:\language\mdrp2354\crates\mdrp2350\src\threaded\bus.rs:2372-2380`
    `ahb_halfword_write_rmw_through_word` — **WILL BREAK.** Same RMW

  - `D:\language\mdrp2354\crates\mdrp2350\src\threaded\bus.rs:2574-2587`
    `narrow_read8_and_16_ahb_fallthrough` — **WILL BREAK.** Writes
    `0xDEAD_BEEF` to `0x5060_0000` and asserts narrow byte/halfword
    extracts match (`0xEF`, `0xBE`, `0xBEEF`, `0xDEAD`). Stub will
    not return the written word.

- **Breaker count summary**: **5 tests will break** (all in
  `threaded/bus.rs`, all asserting on the `0x5060_0000` HSTX FIFO
  region). **0 tests will break** for USB regions (the only match was
  diagnostic eprintln). **0 tests will break** for HSTX_CTRL APB
  region (no in-tree references at all — consistent with HSTX_CTRL_BASE
  being an unresolved address).
- **Recommendation for Component 2 implementer**: choose between
  (a) **delete** the five `0x5060_0000` legacy-fallback tests as part
  of Component 2 — they were probing the exact behaviour the stub is
  intended to replace and lose meaning post-stub; or (b) **rewrite**
  them against another known-unmodelled AHB address (e.g. one of the

  retains coverage independent of HSTX FIFO. Recommend (a) — the
  legacy fallback path is being deliberately narrowed and a synthetic
  test on a different reserved address would just defer the same
  question. Record the deletion in the Component 2 commit message.

### Fact 5 — RESETS_POST_BOOTROM + W1C bit list

- **`RESETS_POST_BOOTROM` table at
  `D:\language\mdrp2354\crates\mdrp2350\src\bus\mod.rs:224-245`** —
  computed as `mask & !released` where `released` ORs in
  `RESET_PLL_SYS, RESET_PLL_USB, RESET_IO_BANK0, RESET_PADS_BANK0,
  RESET_TIMER0, RESET_TIMER1, RESET_SYSCFG, RESET_SYSINFO, RESET_UART0,
  RESET_SPI0, RESET_I2C0, RESET_ADC, RESET_PWM, RESET_DMA`. Anything
  *not* in `released` stays held.
- **`RESET_USBCTRL = 28`** at
  `D:\language\mdrp2354\crates\mdrp2350\src\bus\mod.rs:214` — **NOT in
  `released`**, therefore **held in reset post-bootrom**. ✓ Matches V5
  HLD §Fact 5 expectation.
- **`RESET_HSTX = 3`** at
  `D:\language\mdrp2354\crates\mdrp2350\src\bus\mod.rs:171` — **NOT in
  `released`**, therefore **held in reset post-bootrom**. ✓ Same.
- **Implication for stub bring-up**: both stubs land behind the
  RESETS Bus-level guard (`is_held_in_reset_base`, called at
  `bus/mod.rs:2677`). Firmware must clear the corresponding RESETS bit
  before any stub register read returns non-zero — which is exactly
  what pico-sdk's `runtime_init_bootrom_reset` does, so the standard
  init flow works as expected. Both Components 1 and 2 also need to
  add their bases to `reset_bit_for_base` (`bus/mod.rs:255`) per
  HLD V5 §"Bus integration" point 2.

   HLD's "likely 0x400C_C000" is unverified; older audit doc says
   `0x400C_0000`; no Rust constant exists. Component 2 cannot land

2. **SIE_STATUS W1C bit list is unavailable in-tree.** Component 1's
   W1C masking needs datasheet bit positions. Implementer must read
   RP2350 datasheet §12.6.5 during Stage 1; without it, the W1C mask
   is guesswork. This does NOT block Component 1 from starting (the
   register-surface, DPRAM, and IRQ-low parts are independent), but
   the W1C semantics must be backfilled before merge.
3. **Silicon SHA pin still pending.** Stage 0 Fact 1 R5 calls for an
   SWD-read SHA from real RP2354 silicon to compare against the
   in-tree binary. Until Arthur runs that on hardware, the pinned
   `bootrom-combined.bin.sha256`
   (`c5f9c48c6539f043c423344a53ceaea3774dd1e4c337af49da741a5d259c84bc`)
   is "in-tree-canonical" only. If silicon disagrees, every Component 3
   hook PC is wrong — but Component 3 doesn't depend on this for the
   `reboot` hook, since `resolve_rom_func` walks the table at runtime
   from whatever bytes are loaded.
4. **No RISC-V disassembler available on this host** to confirm the
   `[0x4a40, 0x7e00)` gap is genuinely Hazard3 code. Byte-pattern
   inspection is consistent with RV32C/RV32 but not definitive. Doesn't
   block any Stage 0 fact — the V5 HLD only asks "Arm Secure-only,
   RISC-V, or padding" and we've ruled out padding decisively.
