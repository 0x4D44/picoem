# 2026.04.23 — PicoGUS state-dump probing silence cause

## Context

Continuing from yesterday's `2026.04.22 - JRN - PicoGUS audio silence
chase post-PSRAM-fix.md`. At handoff we had:

- All trace events correctly replaying (drop rate 0.1%).
- `GUS_reset_reg = 0x07`, `ActiveChannels = 27`, PWM IRQ firing,
  audio_sample_handler running, 720K+ TXF pushes to I2S PIO1 SM3.
- WAV completely silent (peak=0, non-zero=0).

Arthur's direction: **path 1** — use ELF symbols from the rebuilt
firmware to peek `GUS_reset_reg`, `ActiveChannels`, `guschan[]` state
after run, isolate whether the GUS state is correct or wrong.

## Plan → actual

Plan: resolve ELF symbols, extend harness with a `PICOGUS_DUMP_GUS=1`
post-run dumper, run 4 s paced replay, diagnose from dump.

Actual: dump built cleanly; ran three replays; state is fully
internally-consistent but every I2S sample pushed is still exactly
zero. Narrowed silence cause to "`GUS_sample_stereo()` returns 0 every
call" despite voice 1 having non-zero VolLeft.

## What's still unexplained

- Voice 1 has VolLeft=21, sample_cache full of non-zero int16 data,
  yet `GUS_sample_stereo()` returns 0 on every single one of 740K calls.
- The function mathematically must produce non-zero output:
  `stream[0] += int16(0xff01) * 21 = -5355` per sample for voice 1
  alone; even after 27-voice summation and clamp16, result ≠ 0.
- Voice 1's first RampVol write lands at trace-ns=3,491,019,898.
  Final replay sim-ts = 3.798 s, so voice 1 had 307 ms of trace-time
  audible before end + 200 ms post-roll = ~0.5 s at 119 kHz PWM rate
  = ~60K PWM IRQs with stable voice 1 state. None produced non-zero
  sample.

## Oddity noticed (secondary)

Observed PWM IRQ rate: 740K pushes / 6.2 s sim = **119 kHz**. Expected
(at 27 channels, 370 MHz sysclk): 22.9 kHz. Ratio ≈ 5.2×.

If our emulator's effective sysclk is ~1.9 GHz from firmware POV (not
370 MHz), PWM wraps 5.2× faster. That would fit the observed rate but
is a clock-tree divergence separate from the silence issue. Not
investigated this session.

## Afternoon session — stub-based narrowing

Added a set of SRAM-patch stubs to the harness to replace or modify
`GUS_sample_stereo` in targeted ways. Each stub test confirms
or rules out a sub-system.

### Stub 1: `PICOGUS_STUB_GUS_SAMPLE_STEREO=0x20000cac`

Replace `GUS_sample_stereo` with `MOVS R0, #0xFF; BX LR` (returns 0xFF).

Result: WAV LEFT = 127 (= 255>>1), RIGHT = -32768. **Audio chain
delivers constant non-zero samples.** Confirms PWM IRQ → handler →
GUS_sample_stereo → R0 → TXF → PIO1 SM3 → I2S capture chain is all
functioning. Silence bug is definitively INSIDE `GUS_sample_stereo`.

(Side finding: our I2S capture reports values `x >> 1` — a 1-bit MSB
offset vs the pushed value. Secondary bug; does not affect decision
between "silent" and "non-silent".)

### Stub 2: `PICOGUS_PATCH_BYPASS_GATE=0x20000cc6`

NOP the `b.n 20001036` at the gate-fail arm, forcing the normal
mixing loop regardless of `GUS_reset_reg` state.

Result: WAV still completely silent (peak=0, non-zero=0). **The gate
check was not causing silence** — the mixing loop itself produces 0.

### Stub 3: `PICOGUS_STUB_RET_ACTIVE=0x20000cac:0x200176ac`

Replace the function with `LDR R0, =&ActiveChannels; LDRB R0, [R0]; BX
LR`. Tests whether core 1 can read core-0-written SRAM from within
an IRQ handler.

Result: WAV LEFT cycles between 7 (= 14>>1 during boot when
ActiveChannels=14) and 13 (= 27>>1 after trace writes the 0xDA data
for register 0x0E). **Core 1 reads core-0 SRAM cleanly.** No
cross-core visibility bug.

### Stub 4: `PICOGUS_STUB_MULT_TEST=0x20000cac`

Replace with `MOVS R0,#21; MOVS R1,#127; MULS R0,R1; BX LR`.

Result: WAV LEFT = 1333 = 2667>>1. **MULS works.** The ARMv6-M
multiplication path in our emulator is sound.

### Stub 5: `PICOGUS_STUB_CHAIN=0x20000cac:0x20017c3c:4:52`

Double-indirect load: `guschan[1]->VolLeft`.

Result: WAV LEFT = 11 for 11,673 samples (= ~22>>1, tracks the
observed VolLeft=21 at end — value wobbles by 1 between 21 and 23).
**Pointer-chain deref works** under IRQ context.

### Stub 6: `PICOGUS_STUB_LOOP_TEST=0x20000cac`

27-iteration tight loop: `MOVS/ADDS/SUBS/BNE` computing sum(1..27)=378.

Result: WAV LEFT = 189 (= 378>>1) for all 263K samples. **Simple loop
mechanics work** on core 1.

### Stub 7: `PICOGUS_STUB_SUM_VOLLEFTS=0x20000cac:0x20017c3c:27`

27-iteration loop with `LDMIA R2!,{R3}; LDR R3,[R3,#52]; ADDS R0,R0,R3`
summing `guschan[c]->VolLeft`.

Result: WAV LEFT = 11 for 11,673 samples. Matches voice 1's VolLeft
(~21-23) as sole non-zero contributor. **Multi-voice loop + chain
deref + accumulator works.**

### Stub 8: `PICOGUS_STUB_SUM_MUL_VL=0x20000cac:0x20017c3c:27`

27-iteration loop with `MULS R3,R4` multiplying VolLeft × const 100
before accumulating.

Result: WAV LEFT = 1100 = 2200>>1 = 100 × 22 (voice 1 sole contributor,
VolLeft transiently 22 between dump reads). **Per-voice mult-accumulate
works** — closest possible in-stub approximation of the real
`stream[0] += tmpsamp * VolLeft` loop.

## Revised conclusion — all building blocks work

Every primitive used by the real mixing loop works correctly when
exercised directly:

| Primitive | Tested via | Result |
|---|---|---|
| Function prologue + R0 return | Stub 1 | Works |
| Early-return gate branch | Stub 2 | Bypass doesn't fix silence |
| Core-1 SRAM read (LDRB) | Stub 3 | Works |
| MULS | Stub 4 | Works |
| Pointer chain (2-level LDR) | Stub 5 | Works |
| ADDS/SUBS/BNE loop | Stub 6 | Works |
| Multi-voice iter + accum | Stub 7 | Works |
| Mult-accum in loop | Stub 8 | Works |

Yet the real `GUS_sample_stereo` returns 0 on every one of 740K calls.

This means the silence cause must be something **specific to the real
function** that none of the standalone stubs reproduce — candidates:

1. **`tmpsamp = GetSample16()` path** — PSRAM SPI read via PIO1 SM0,
   called from IRQ context, possibly interacting badly with another
   core's concurrent PSRAM access (core 0 is also doing PSRAM writes
   during ISA event replay).
2. **Stack-based accumulator** — `sub sp, #28` + `str/ldr [sp, #N]`.
   If one of these stack operations is mishandled on core 1 under
   IRQ, accum stays 0.
3. **WaveUpdate/RampUpdate side effects** — both run after the mix
   add per voice; if either corrupts something subtle, next iteration
   might fail.
4. **Inlined control flow** — the compiled function heavily inlines
   generateSample; the resulting branch structure might trigger an
   emulator bug not visible in straight-line code.
5. **Interrupt re-entry / state save mismatch** — the observed 740K
   PWM IRQ rate is 5× expected (119 kHz vs 22.9 kHz). If IRQs are
   somehow re-entering or the NVIC state is weird, the handler might
   not complete normally.

## Next steps (in priority order)

1. **Firmware instrumentation path** — modify `GUS_sample_stereo` or
   `audio_sample_handler` to stash intermediate values
   (`tmpsamp`, per-iter `accum[0]`) at known SRAM addresses. Rebuild.
   Probe. This IS the diagnostic option that finally reveals the bug.
2. **Investigate the 5× PWM IRQ rate** — our sysclk may be effectively
   1.9 GHz from firmware's view. If that's the case, it explains the
   observed rate but would NOT by itself cause silence.
3. **Voice-1-only mixer stub** — hand-write a Thumb stub that exactly
   mirrors `generateSample` for voice 1 (16-bit sample + LoadSamples16
   + interpolation + mult-accum + WaveUpdate). Narrower scope than
   the real 27-voice inlined loop.

## Remaining hypothesis space

Silence cause is specific to something that happens during the real
mixing loop but NOT in the simpler stubs:

1. **Pointer-chain load** (`guschan[c]->field` via two LDRs) — stub 5
   tests this.
2. **Loop iteration counter** — maybe the `for (c=0; c < 27; ++c)`
   doesn't actually iterate, or exits immediately.
3. **Specific instructions** used inside the loop body (e.g., LSLS
   with large shift, BIC, conditional LDR, signed multiply-add).
4. **Stack use inside the function** — `sub sp, #28` + `ldr`/`str` on
   stack locals for accumulator. If stack writes go somewhere wrong
   on core 1, accum stays 0.

After stub 5 lands, next stubs to try:
- Return `accum[0]` of a minimal inline mixer (voice 1 only).
- Replace the function with a hand-written assembly that does exactly
  what generateSample does for voice 1 and returns the accumulated value.
