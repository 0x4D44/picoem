# Silicon Oracle Bug Fixes — Working Journal

Date: 2026-04-15

## Context

The new silicon oracles (`silicon_periph_diff_rp2350`, `silicon_cycle_oracle_rp2350`)
shipped today and immediately exposed two real emulator bugs against
live RP2354 silicon:

1. **PLL CS[31] LOCK forced to 1** — `crates/mdrp2350/src/bus/peripherals.rs:21`
   (and the same pattern lives in `crates/mdrp2040/src/bus/clocks.rs`,
   logged as the original tech-debt entry "RP2040 PLL LOCK always 1").
   Surfaced by the `pll_sys_lock_timing` scenario.

2. **PIO side-set unconditional `pad_oe`** —
   `crates/mdpicoem-common/src/pio/mod.rs:196` ORs the positioned
   side-set mask into `pad_oe` when `EXECCTRL.SIDE_PINDIR=0`. Per
   RP2350 §11.3.2.3 side-set in value-mode drives pin *values* only;
   direction must come from `SET PINDIRS` / `OUT PINDIRS` /
   `SIDE_PINDIR=1`. Surfaced by the `pio0_side_set_toggle` scenario.

Positive controls (`single_adds`, `pio0_nop_loop`) pass — the oracles
are measuring real signal, not systematic bias.

## Plan

Two parallel agent workstreams. Each agent must:

1. Write an HLD up-front under `wrk_docs/2026.04.15 - HLD - <topic>.md`.
2. Stop after the HLD; I review and iterate to sign-off before any code.
3. Implement, then run `/code-reviewer` on the diff.
4. Apply review with `/code-review-apply-feedback`.
5. Re-verify by running the relevant silicon oracle scenario (or an
   isolated unit test that encodes the same observable, when silicon
   isn't available in the loop).

Both bugs span chip crates: the PLL bug exists in both mdrp2350 and
mdrp2040; the PIO bug lives in `mdpicoem-common` so it affects both.
HLDs must address both chips.
