### Critical analysis: 256 KiB serving feasibility

The prompt asks for a fixture whose **all 256 KiB** serve byte-correctly
through the existing CpuServingOracle. Observed constraints:

1. The fire-24-a firmware variant is the only firmware we have, and we
   only have the binary. Source isn't in this repo and isn't
   vendor-submoduled.
2. Per ROM-set serving capacity is bounded by the firmware's
   `rom_table_size = 65536`. So one ROM set can hold at most 64 KiB of
   shadow. To serve 256 KiB you need ≥4 ROM sets.
3. Within one ROM set, the addressable space depends on how many GPIO
   pins the firmware actually treats as address. If the serve loop is
   `byte = rom_table[gpio_in & 0xFFFF]` and we drive any 16-bit GPIO
   state, all 64 KiB of one shadow is reachable. If the firmware
   filters by chip-select before the lookup, the addressable subset
   shrinks.

The 1541 fixture's existing 4 ROM sets × 64 KiB = exactly 256 KiB total
shadow. **If the firmware does direct 16-bit lookup on `gpio_in`, then
4 ROM sets × 64 KiB = 256 KiB is achievable with bank-switching via
SEL-pin reset cycles.** That's the working hypothesis.

### Decision: probe before committing to design

Before building anything, Stage 1.5 = empirical probe. Lift each of the
4 ROM sets from the existing 1541 fixture, look at the bytes, and
determine whether the shadow is a direct GPIO-indexed lookup or
a permuted table. This decides whether the bank-switching plan (4 sets
× 64 KiB) actually works or whether we need a wider pin map (firmware
change) and have to surface to Arthur.

### Stage 1.5 — probe results

Built `bin/probe_seabios_fixture_capability` (will keep it alive for the
duration of this work — disposable post-merge per the smoke-binary
pattern in CLAUDE.md). Ran against the 1541 fixture; key data:

- `walk1 baseline`: `addr_bits=0x1800` → `pin_state=0x9000` →
  `shadow[0x9000] = 0xA4`. **The predecessor journal recorded the same
  byte (`0xA4`) as the first served byte across 2048 case stimuli.**
- All 15 default cases match across rom_sets 0/1/3 (which appear to be
  three slightly-different copies of the C64 1541 Kernal); set 2 is a
  distinct payload (likely the 27C301 image mentioned in
  `onerom_stress_cpu_rp2350.rs`'s file header).
- Set CRC32s differ even though sampled bytes match: identical at the
  sampled GPIO states, divergent elsewhere.

**Verdict: shadow IS a direct GPIO-indexed lookup table.** The firmware's
serve loop is effectively `byte = rom_table[gpio_in & 0xFFFF]`. The
permutation between abstract `addr_bits` and physical `pin_state` lives
on the **stimulus** side — so the ORACLE's `stimulus_level` function
defines the permutation, and the FIXTURE shadow is a flat
GPIO-state-indexed array.

### 256 KiB feasibility analysis

With direct lookup confirmed, the ceiling is set by how many distinct
16-bit GPIO states the worker can drive. Per the fire-24-a pin map:

- Bits 0–7, 10, 11, 12, 14, 15: address pins (13 bits)
- Bit 13: CS1 (must stay 0 during serving — firmware tristates data
  pins when CS1 is high)
- Bits 8, 9: NOT in `ADDR_PINS` and NOT data pins; uncovered by the
  current oracle. Whether they're drivable as additional address bits
  depends on whether the firmware's serve loop touches them.

If we can drive ALL of bits {0..7, 8, 9, 10, 11, 12, 14, 15} (15 bits)
at CS1=0, that's 2^15 = 32 KiB unique states per ROM set. With 4 ROM
sets, that's **128 KiB total** — short of the 256 KiB target.

Drivable bits + ROM sets analysis:

| Address pins drivable | Per-set capacity | 4 sets | 256 KiB? |
|---|---|---|---|
| 13 (current ADDR_PINS) | 8 KiB | 32 KiB | NO |
| 15 (add bits 8,9 if firmware tolerates) | 32 KiB | 128 KiB | NO |
| 16 (impossible — bit 13 = CS1) | 64 KiB | 256 KiB | YES, if firmware ignores CS1 |

**Therefore 256 KiB through the existing fire-24-a firmware is
structurally on the edge.** The path that closes it is bit 13 (CS1)
behaviour: if the firmware serves regardless of CS1, all 4×64 KiB =
256 KiB is reachable. If CS1 must be low, we land at 128 KiB max.

### Design decision

Rather than reverse-engineer the firmware binary, the cheapest test is
to **try it**: build a 256 KiB fixture spanning 4 ROM sets, drive every
16-bit state through the harness, observe what serves correctly. If
it's 256 KiB → we're done. If it's 128 KiB → surface concrete data to
Arthur.

The build approach:

1. Each shadow stores the corresponding 64 KiB of SeaBIOS bytes,
   indexed by **GPIO state directly** (no permutation): `shadow_k[i] =
   seabios[k * 0x10000 + i]` for `k ∈ 0..4`, `i ∈ 0..0x10000`.
2. The validator drives `gpio_state = i & 0xFFFF` and asserts
   `served == shadow_k[i]` (= `seabios[k * 0x10000 + i]`).
3. For each ROM-set switch, reset the emulator and call
   `force_rom_set_index_via_sel_pins(emu, flash, k)`.

Critical assumption: the existing oracle's `stimulus_level` permutes
13-bit `addr_bits` through `ADDR_PINS`, so the existing API isn't a
1:1 fit for "drive raw 16-bit GPIO state". A new harness API will
likely be needed — orthogonal to existing 1541 callers, per the
prompt's "Additions only" rule.
