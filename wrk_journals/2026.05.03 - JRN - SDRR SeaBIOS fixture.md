### Critical analysis: 256 KiB serving feasibility

The prompt asks for a fixture whose **all 256 KiB** serve byte-correctly
through the existing CpuServingOracle. Observed constraints:

1. The fire-24-a firmware variant is the only firmware we have, and we
   only have the binary. Source isn't in this repo and isn't
   vendor-submoduled.
2. Per ROM-set serving capacity is bounded by the firmware's
   `rom_table_size = 65536`. So one ROM set can hold at most 64 KiB of
   shadow. To serve 256 KiB you need ≥4 ROM sets.
3. Within one ROM set, the addressable space depends on how many GPIO
   pins the firmware actually treats as address. If the serve loop is
   `byte = rom_table[gpio_in & 0xFFFF]` and we drive any 16-bit GPIO
   state, all 64 KiB of one shadow is reachable. If the firmware
   filters by chip-select before the lookup, the addressable subset
   shrinks.

The 1541 fixture's existing 4 ROM sets × 64 KiB = exactly 256 KiB total
shadow. **If the firmware does direct 16-bit lookup on `gpio_in`, then
4 ROM sets × 64 KiB = 256 KiB is achievable with bank-switching via
SEL-pin reset cycles.** That's the working hypothesis.

### Decision: probe before committing to design

Before building anything, Stage 1.5 = empirical probe. Lift each of the
4 ROM sets from the existing 1541 fixture, look at the bytes, and
determine whether the shadow is a direct GPIO-indexed lookup or
a permuted table. This decides whether the bank-switching plan (4 sets
× 64 KiB) actually works or whether we need a wider pin map (firmware
change) and have to surface to Arthur.

### Stage 1.5 — probe results

Built `bin/probe_seabios_fixture_capability` (will keep it alive for the
duration of this work — disposable post-merge per the smoke-binary

- `walk1 baseline`: `addr_bits=0x1800` → `pin_state=0x9000` →

  byte (`0xA4`) as the first served byte across 2048 case stimuli.**
- All 15 default cases match across rom_sets 0/1/3 (which appear to be
  three slightly-different copies of the C64 1541 Kernal); set 2 is a

  `onerom_stress_cpu_rp2350.rs`'s file header).
- Set CRC32s differ even though sampled bytes match: identical at the

**Verdict: shadow IS a direct GPIO-indexed lookup table.** The firmware's
serve loop is effectively `byte = rom_table[gpio_in & 0xFFFF]`. The
permutation between abstract `addr_bits` and physical `pin_state` lives
on the **stimulus** side — so the ORACLE's `stimulus_level` function
defines the permutation, and the FIXTURE shadow is a flat
GPIO-state-indexed array.

### 256 KiB feasibility analysis

With direct lookup confirmed, the ceiling is set by how many distinct
16-bit GPIO states the worker can drive. Per the fire-24-a pin map:

- Bits 0–7, 10, 11, 12, 14, 15: address pins (13 bits)
- Bit 13: CS1 (must stay 0 during serving — firmware tristates data
  pins when CS1 is high)
- Bits 8, 9: NOT in `ADDR_PINS` and NOT data pins; uncovered by the
  current oracle. Whether they're drivable as additional address bits
  depends on whether the firmware's serve loop touches them.

If we can drive ALL of bits {0..7, 8, 9, 10, 11, 12, 14, 15} (15 bits)
at CS1=0, that's 2^15 = 32 KiB unique states per ROM set. With 4 ROM
sets, that's **128 KiB total** — short of the 256 KiB target.

Drivable bits + ROM sets analysis:

| Address pins drivable | Per-set capacity | 4 sets | 256 KiB? |
|---|---|---|---|
| 13 (current ADDR_PINS) | 8 KiB | 32 KiB | NO |
| 15 (add bits 8,9 if firmware tolerates) | 32 KiB | 128 KiB | NO |
| 16 (impossible — bit 13 = CS1) | 64 KiB | 256 KiB | YES, if firmware ignores CS1 |

**Therefore 256 KiB through the existing fire-24-a firmware is
structurally on the edge.** The path that closes it is bit 13 (CS1)
behaviour: if the firmware serves regardless of CS1, all 4×64 KiB =
256 KiB is reachable. If CS1 must be low, we land at 128 KiB max.

### Design decision

Rather than reverse-engineer the firmware binary, the cheapest test is
to **try it**: build a 256 KiB fixture spanning 4 ROM sets, drive every
16-bit state through the harness, observe what serves correctly. If
it's 256 KiB → we're done. If it's 128 KiB → surface concrete data to
Arthur.

The build approach:

1. Each shadow stores the corresponding 64 KiB of SeaBIOS bytes,
   indexed by **GPIO state directly** (no permutation): `shadow_k[i] =
   seabios[k * 0x10000 + i]` for `k ∈ 0..4`, `i ∈ 0..0x10000`.
2. The validator drives `gpio_state = i & 0xFFFF` and asserts
   `served == shadow_k[i]` (= `seabios[k * 0x10000 + i]`).
3. For each ROM-set switch, reset the emulator and call
   `force_rom_set_index_via_sel_pins(emu, flash, k)`.

Critical assumption: the existing oracle's `stimulus_level` permutes
13-bit `addr_bits` through `ADDR_PINS`, so the existing API isn't a
1:1 fit for "drive raw 16-bit GPIO state". A new harness API will
likely be needed — orthogonal to existing 1541 callers, per the
prompt's "Additions only" rule.

### rom_set 3 metadata unlock

The 1541 template's four ROM sets are authored as four DIFFERENT chip
variants — sets 0/1/2 are 1541 ROM revisions (CS=GPIO13, data=GPIO16..23,
the standard fire-24-a pin map), and set 3 is a 27C301 EPROM image with
a different pin layout (CS=GPIO0, data=GPIO26 per the file header of
`onerom_stress_cpu_rp2350.rs`). Each set's `roms[]` pointer at
descriptor offset `+0x08` points at its OWN `sdrr_rom_info_t` declaring
the chip variant.

Set 3's pointer in the template is `0x1000_C204`, which lands on the
array LENGTH cell (`u32 = 0x00000004`) preceding the four
`sdrr_rom_info_t*` entries — when the firmware dereferences this as a
`sdrr_rom_info_t*`, it casts the integer 4 to a pointer and faults.

The builder patches sets 1, 2, 3 to share set 0's `+0x08..+0x0B` value
(`0x1000_C210` — set 0's `roms[]` array entry). All four sets then
route through set 0's chip-variant — i.e. the 1541 pin map (CS=GPIO13,
data=GPIO16..23). This is correct for the SeaBIOS use case where
Stream B drives raw 16-bit GPIO patterns through CS1=GPIO13 and
doesn't care about the underlying chip-variant identity. **It is NOT
a generic "all sets through the same code path" fix** — it
specifically forces the 1541 pin map onto sets that were authored for
other chip variants. A different fixture template (e.g. test-sdrr-0)
would need its own analysis before this patch could be applied to it.

### Architectural ceiling: 128 KiB byte-correct per fixture

The first full sweep produced `pass=131072 / wrong=0 / no_stable=0 /
not_driven=0 / latency_oor=0 / skipped_cs1=131072` across 4 ROM sets.

Math: each ROM set's shadow is 64 KiB indexed by 16-bit GPIO pin
state. CS1 occupies bit 13. Per ROM set, 32 768 pin states have
CS1=low (reachable) and 32 768 have CS1=high. A `--probe-cs1` mode
empirically confirmed (10 cases each at CS1=high vs CS1=low) that the
firmware drives `DataPinsNotDriven` for every CS1=high case. So:

- Per ROM set: 32 KiB byte-correct verifiable (CS1-low pin states)
- 4 ROM sets via SEL-pin switching: 128 KiB byte-correct verifiable
- Remaining 128 KiB shadow positions: bytes are PRESENT in the
  fixture but UNSERVABLE through the firmware's serve loop.

This is a hard ceiling of the existing fire-24-a SDRR firmware
binary. To serve all 256 KiB of SeaBIOS through OneROM in one fixture
requires either:

1. A different SDRR firmware variant with a wider pin map (e.g. a
   build configured for the 27C-series 256 KiB EPROMs the README
   mentions). We don't have that firmware variant in this repo.
2. A two-fixture or eight-rom-set topology, where Stream B's worker
   reloads the emulator with a different fixture for the upper 128
   KiB. That's an architectural change in Stream B (mddosem-side).

**Surfaced for triage in the close-out.** The deliverable is the
128-KiB-capable fixture + builder + validator, with the gap clearly
documented.

## Close-out / for Arthur

**Stream A delivers a 128 KiB-byte-correct fixture, not a 256 KiB one.**
The literal acceptance criterion ("all 256 KiB serve byte-correctly")
is unmet because the fire-24-a SDRR firmware tristates D0..D7 at
CS1=high — empirically confirmed by `--probe-cs1-thorough` (256/256
random cases on the varied-content rom_set 1 → all
`DataPinsNotDriven`). With CS1 reserved as bit 13, only 32 768
pin states per ROM set are reachable, × 4 ROM sets = 128 KiB max.

The deliverable that DOES land cleanly:

- `onerom-fire-24-a-rp2350-seabios-cpu.bin` (320 KiB SDRR envelope,
  CRC32 0xBC604E79). All 256 KiB of SeaBIOS bytes are laid into the 4
  ROM-set shadows. The lower 128 KiB (the CS1-low half of each shadow)
  is reachable and serves byte-correctly.
- `build_seabios_fixture` (Rust binary, 395 lines incl. inlined
  SHA-256). Reads template + SeaBIOS image, patches descriptor

- `seabios_fixture_byte_correct` validator. Full sweep produces
  pass=131 072 / wrong=0 / discriminating_pass=72 351 (i.e. 72 351 of
  the 131 072 verified bytes are non-modal — the rest are trivial
  zero-matches in the all-zero chunk 0). `--probe-cs1-thorough` mode
  empirically confirms the firmware tristate at CS1=high.
- 7 unit tests on the new public API (`parse_rom_set_layout`,
  `Case::raw_pin_state[_unmasked]`, `stimulus_level_raw[_unmasked]`).
  564/564 mdpicoem-harness lib tests pass; 3175/3175 mdrp2350 tests
  pass; no regressions in the 1541 fixture path.

**Triage decision needed on the upper 128 KiB:**

Three viable options, in increasing cost:

1. **Accept 128 KiB and let Stream B handle the upper half via
   cached fallback or a second fixture.** Cheapest; ships today; the
   boot path may even work because SeaBIOS doesn't fetch every byte
   during boot (only a subset of the 256 KiB region is actually
   touched). HLD §Acceptance criterion 3 phrasing — "across the full
   256 KB image's actually-fetched bytes" — already hedges this way.

2. **Build a second fixture variant** (`-seabios-upper-cpu.bin` etc.)
   that maps the upper 128 KiB and arrange Stream B's worker to
   re-init the emulator with the right fixture per address window.
   Adds emulator-reload latency (~3 ms per swap) and requires Stream
   B-side worker logic to track which window is loaded. Doable in this
   repo if Arthur wants Option 2 by default.

3. **Source a wider-pin-map SDRR firmware variant** (different PCB
   variant, e.g. one with no CS1/CS2/CS3 aliasing onto address pins).
   Requires Piers's SDRR build tooling — not in this repo. Out of
   Stream A's scope per the prompt.

**Recommend Option 1 with Stream B awareness.** The HLD's
acceptance-3 phrasing is already "actually-fetched bytes", and the
demo narrative ("emulator-on-emulator-on-emulator") does not require
that EVERY byte come through OneROM — only that the boot path works.
If a later push wants 100 % live OneROM coverage, Option 2 follows-up.

## Per-byte serve cost (informational)

Per the prompt's "Report wall-clock harvest time (informational)" bullet:

- `seabios_fixture_byte_correct` full sweep wall-clock: ~1.2 s total
  across 4 ROM sets, ~131 072 verified cases (CS1=low half) plus 131
  072 fast-skipped cases (CS1=high). Per-set: rom_set 0 ≈ 434 ms, sets
  1/2/3 ≈ 240–270 ms each. Fastest 32 KiB sweep ≈ 7.4 ms /
  case = 7.4 µs per per-case operation (which includes per-case
  gap-drive + stim-drive + observation + verdict + `tally`). Worst is
  rom_set 0 at ≈ 13.3 µs/case (the all-zeros chunk takes longer
  because phase-2 sync degrades to PC-only checking).
- These figures are validator-bounded, not Stream-B-runtime-bounded.
  The HLD's 80–200 ns/byte budget for Stream B's continuous-serve
  worker is ~50–100× faster than this validator: the validator does
  per-case `Emulator::run` + `glue.tick` + verdict eval + result
  collection, none of which Stream B's tight loop will pay.
