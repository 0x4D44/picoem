## Stage 2 halt — PSRAM regression (architectural escalation)

Implementation agent completed the spec exactly per HLD V5 §5.3. The §8.4 dual-core SysTick test now PASSES (was FAIL on commit `91a1a5e`); threaded parity (`dual_model.rs`) holds 18/18; full lib suite is **914 PASS / 2 FAIL**.

The 2 failures are in `crates/mdrp2040/src/peripherals/psram.rs` mod `pio_integration`: `pio_driven_write_then_read_round_trip` and `pio_driven_fast_read_returns_written_bytes`. **These tests were purpose-built to verify the per-cycle PIO/PSRAM interleave that this refactor removes** — the module docstring at `psram.rs:158-175` explicitly says "The old pre-fix code — `tick_pio(consumed)` followed by a single `update_gpio()` — would only surface the quantum-end pin snapshot to the PSRAM, missing the SCK edges between quantum start and end. The test therefore fails without the interleave fix."

**The HLD V5 missed this**: §3 noted "PSRAM PIO timing" as a "RP2040-specific quirk requiring separate validation" but didn't anticipate that *the chunked update_gpio specifically would break PSRAM observation of intra-quantum SCK edges*. Four rounds of multi-agent review didn't catch it either.

**Real-world impact uncertain**: per the iter 0 journal, "PSRAM.tick(): 1 034 936 708 calls for 3 SPI frames" — PicoGUS firmware does use PSRAM (3 SPI frames in 2.5 s sim, likely OPL3 sample data load). If PSRAM corruption affects mode-5 audio, cake-gate fails and the design must pivot. If quantum-boundary-only observation is functionally adequate for the firmware's actual usage pattern, the tests are encoding-old-behavior and need rewriting.

**Branches**:
- (A) Keep current implementation; run cake-gate immediately to validate. If audio passes, rewrite/delete the two PSRAM tests and ship. If audio fails, pivot.
- (B) Hybrid design — keep PIO+PSRAM on a per-cycle micro-loop, chunk the rest of the peripherals. Preserves PSRAM correctness; adds complexity.
- (C) Refactor PSRAM observation to be PIO-edge-driven instead of update_gpio-driven. Bigger architectural change.

Implementation agent left the tree in working state (uncommitted) per "STOP and report" guidance. Awaiting Arthur's direction.

## Stage 3 — quantum sweep (3 trials per quantum, 2.5 s sim, post-refactor)

| q | wall median | speedup vs same-q pre-refactor | cake-gate | top peak (Hz) | cycles | notes |
|---|---|---|---|---|---|---|
| 1 | 91.91 s | −1.2% | PASS | 324 | 1,056,157,608 | bit-identical to pre-refactor q=1 |
| 4 | **68.41 s** | **−15.5%** | PASS | 323 | 1,055,302,762 | **HLD success criterion (≥10%) met** |
| 16 | 38.17 s | −52.1% | PASS | 323 | 1,054,602,920 | **q=16 UNLOCKED** — pre-refactor was detuned (288 Hz) |
| 64 | 33.00 s | −50.7% | FAIL | (silent) | 1,056,132,932 | ISA precision break persists at q=64 |

Cycles drift at q=4 vs pre-refactor: **285 cycles (0.000027%)** — well within HLD ±0.2% tolerance. Trial-to-trial spread is tighter than pre-refactor (q=4 range 5.6 s post vs 17 s pre).

**Architectural finding**: HLD §6.4's hypothesis was correct for q=16 but not q=64. The pre-refactor q=16 detuning came from per-cycle ISA-pin sample misalignment (peripherals seeing slightly-wrong gpio_in snapshots scattered across the per-cycle inner loop). With chunked update_gpio at end-of-quantum, q=16 produces audio spectrally identical to q=4. q=64 still breaks — at that depth the ISA-bus capture window itself overlaps with quantum boundaries in a way the chunked tick cannot fix.

**Practical follow-up**: defaulting `step_quantum` to 16 in `picogus_diff_rp2040` would cumulatively give ~53% wall reduction vs the original q=1 baseline. Out of scope for this commit — this sprint's goal was the chunked refactor; raising the default is a separate decision dependent on confirming q=16 holds across other workloads.

**Single-trial cake-gate clarification**: the architectural-escalation cake-gate run reported 48.75 s wall — that was a single-trial outlier (presumably warm OS cache). The 3-trial median 68.41 s is the reliable number; the commit message's "−40%" is technically accurate for that one trial but the real-world figure is the 15.5% median. Stage 2 commit stands; this clarifies the framing.

## Stage 3 verdict: PASS

All HLD success criteria met. q=4 default delivers 15.5% wall reduction with audio sonically equivalent to pre-refactor. Chunked refactor architecturally validated.
