### T+12min (08:15) — **NEW FINDING: `pwm_wrap_irq` periph divergence**

```
iter=0 seed=5831149830256 oracle=periph case=pwm_wrap_irq
  detail=MMIO 0x400A80F4 mask=0x00000001: HW=0x00000000 EMU=0x00000001 (xor=0x00000001)
```

- Address `0x400A80F4` = `PWM_BASE + 0xF4` = PWM `INTR` (raw interrupts); bit 0 = slice-0 wrap IRQ latch.

- Not in `tech_debt.md`. #### Agent diagnosis (T+20min)

- **Not a regression.** `pwm.rs` working-tree diff is a unit test (`fractional_div_integer_2_per_cycle_dispatch_matches_bulk`) with zero runtime-logic change. Close-out journal `:304` explicitly calls out that `pwm_wrap_irq` was **intentionally untouched**.
- **Emulator side is correct.** `latch_wrap` at `crates/mdrp2350/src/peripherals/pwm.rs:233` unconditionally latches INTR on wrap. This matches datasheet semantics: INTR is *raw* status; INTE only gates routing to NVIC. PicoGUS HLD `2026.04.16:139` cites the same ("`INTR[4]` must latch once the counter wraps"). Emulator runs ~155–180 sysclks against TOP=100 DIV=1 → correctly wraps and latches.
- **Root cause — scenario bug (same family as A.2.3).** Setup `S_PWM_WRAP_IRQ` (`silicon_scenarios.rs:967`) writes in order: `RESETS_CLR_ALL → CSR=EN_BIT → TOP=100 → EN=1`. On silicon `CSR_EN` and `EN[0]` are the **same physical bit** (A.2.3's key discovery). So `CSR=EN_BIT` enables PWM *immediately* — then DAP latency to the `TOP=100` write ticks N sysclks at the previous TOP, with CTR carried over from the previous scenario (Fisher-Yates shuffle → nondeterministic which scenario preceded). Emulator with split `CSR_EN`/`EN[0]` storage only starts ticking at the `EN=1` step with CTR=0 and TOP=100 — deterministic wrap. Result: silicon INTR state depends on setup-phase randomness; emulator INTR is deterministic.
- **Fix pattern already exists.** `S_PWM_FRACTIONAL_DIV` template at `silicon_scenarios.rs:1013` adds explicit `CTR=0` reset + `EN=1 → CSR=0` ordering. Same three-line edit, different scenario.
- **Recommendation**: flag to concurrent PWM agent (they own the fix template + wave); no `tech_debt.md` bucket needed. Handoff note below.

### Consolidated novel finding — scenario state-leakage under soak-shuffle

All three novel periph failures (`pwm_wrap_irq`, `pio0_nop_loop`, `pio0_int_routing_split`) share a single root cause: the silicon-side DUT retains per-peripheral hardware state across the scenarios within one soak iteration (Fisher-Yates shuffle → no deterministic order), while the emulator side reconstructs a fresh `EmulatorBuilder::new(...)` per scenario at `silicon_scenarios.rs:2382`. The orchestrator `reset_and_halt`s only between **iterations**, not between **scenarios** (`test_rp2350_silicon.rs:1011-1020`, `silicon_scenarios.rs:2343-2348`). `first_scenario=true` is only the *first* case in the shuffled list.

Per peripheral, the leaked state is:

- **PWM**: slice-`CSR_EN` == `EN[0]` (single physical bit on silicon) + `CTR` accumulates. `pwm_wrap_irq` hits this because the setup enables slice-0 before `TOP`, ticking at the previous scenario's `TOP`.
- **PIO**: `instr_mem[]` bytes and each SM's `sm.pc` + `irq_flags` persist. `pio0_nop_loop` reads `SM0_ADDR` with whatever the prior scenario left there; `pio0_int_routing_split` fails to set `IRQ_FLAGS[0]` because the SM never reaches slot 0 where `IRQ SET 0` lives.

This is the same class of defect the 2026-04-18 A.2.3 PWM close-out (`wrk_journals/2026.04.18 - JRN - Residual A.2.3 PWM Close-Out.md`) patched for `pwm_fractional_div`. That fix pattern (explicit setup state-reset in scenario setup table) applies directly to all three.

Emulator side is correct in every case. No `mdrp2350` code changes needed.
