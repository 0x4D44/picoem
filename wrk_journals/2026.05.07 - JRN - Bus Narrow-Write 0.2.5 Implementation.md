## Scope (three fixes)

1. **Smoke verdict criterion 5 fix.** The formula
   `((SHADOW_BASE + addr_word) & 0xFF) ^ 0x55` was wrong — assumed
   OneROM's `lift_addr_from_pins` is identity. Empirically the harness
   FAILS even on correct serving. Replace with: "pin byte during the
   dwell window matches the byte from at least one CH1 push edge during
   that same dwell." Same brief intent, expressed in observables
   without needing the firmware's lift function.

2. **PIO RXF read-side-effect hazard introduced by 0.2.4.** The
   standard RMW pattern reads the old word; PIO RXF (offsets
   `0x020..=0x02C`) pops the FIFO on read. Narrow writes to RXF would
   spurious-drain. Add a 1-line carve-out in the new PIO arm to drop
   narrow RXF writes (silicon-correct: RXF is read-only on write).

3. **RESETS narrow-write drops.** Per HLD §3 — same subword-alias RMW
   as the PIO 0.2.4 fix, applied to `Bus::write8` and `Bus::write16`
   for `0x4002_0000`.

Plus: documentation update (HLD §9 on rp2040 byte-replicate vs rp2350
zero-extend convention divergence), version bump 0.2.4 → 0.2.5,
CHANGELOG entry.

### Stage 3 outcomes — TXF-only-widen redesign

Replaced both `Bus::write8` PIO arm (`bus/mod.rs:2135-2178`) and `Bus::write16` PIO arm (`bus/mod.rs:2880-2903`) with the rp2040-emu-style TXF-only widen. All non-TXF narrow writes are dropped. The Stage 1 RXF carve-out range (`0x020..=0x02C`) is now redundant — RXF is dropped because it sits outside the TXF range — but the regression test stays as future protection.

**TXF widening uses zero-extension** `(val as u32) << (byte_idx * 8)` for AHB5 byte-strobe semantics. rp2040-emu (AHB-Lite) uses byte-replication. Different bus generation, same observable for OneROM (only the bottom byte goes onto the data pins).

**New regression tests in `crates/rp2350-emu/src/pio_tests.rs:846-957`:**
- `pio_narrow_writes_to_fdebug_dont_corrupt` — seeds FDEBUG via SET-alias, asserts narrow byte-0 + halfword-1 leave it intact.
- `pio_narrow_writes_to_ctrl_dont_trigger_sm_restart` — force-executes JMP 5 to set PC=5, narrow byte-1 with 0xF0 leaves PC=5; full-width parity case proves the trigger works when issued correctly.
- `pio_narrow_writes_to_sm_instr_dont_force_execute` — narrow byte-0 0x07 to SMn_INSTR does not advance PC to 7 / does not force-execute.

**Lane coverage:** existing `pio_narrow_writes_widen_to_32_bit` extended to lanes 2/3 byte and halfword lane 1.

**Smoke verdict:** post-loop guard tightened from `pin_matches == 0` to `pin_matches < 2` with a diagnostic explaining the parallel to criterion 4's distinct-src cardinality requirement. SmokeVerdict::Pass + criterion-5 doc updated.

**Empirical:** harness exits 0 with `SMOKE TEST PASS — ... 2/5 sweep addresses produced the correct data byte on D0..D7 with PIO2 driving`. The 2/5 still satisfies `>= 2` (right at the boundary — future regressions reducing dwell-match count would now correctly fail).

**Lib pass:** `3662 passed; 0 failed; 27 ignored` (release).

Committing Stage 1+3 implementation work as one atomic change before Stage 4 (docs + version bump).

### Stage 2 outcomes — reviewers found a deeper issue

The standard subword-alias RMW pattern (used by UART/SPI/I2C) doesn't transfer cleanly to PIO because PIO has a much larger side-effect surface. Both reviewers independently flagged this; combined findings:

| Source | Register | Failure mode under naïve RMW |
|---|---|---|
| code-reviewer | PIO FDEBUG (`0x008`, W1C) | RMW reads live state, splices, writes back — every set bit in unchanged byte lanes is interpreted as "clear this bit," zeroing FDEBUG outside the targeted byte. |
| code-reviewer | PIO IRQ (`0x030`, W1C) | Same as FDEBUG. |
| devils-advocate | PIO SMn_INSTR (`0x0D8`/`0xF0`/`0x108`/`0x120`) | `write32` invokes `force_execute` which immediately runs the synthesized opcode. Narrow STRB executes `(last_insn[31:8] | val)` instead of silicon's `(0x0000 | val)`. |
| devils-advocate | PIO CTRL byte 1 (`0x000`) | SM_RESTART bits at `[7:4]` are self-clearing actions. Narrow write to byte 1 of CTRL synthesizes `SM_RESTART = val`, restarting state machines that weren't supposed to be touched. |
| devils-advocate (concern) | PIO SMn_SHIFTCTRL byte 3 | FJOIN_TX/RX bits at `[31:30]` trigger FIFO-content drop on apply. Narrow byte-3 write would normally preserve FJOIN through the read, but a flipped value would silently flush. |
| devils-advocate (correction) | PIO IRQ_FORCE (`0x034`) | Reviewer flagged this; devils-advocate confirmed safe — IRQ_FORCE `read32` returns 0, so RMW degenerates to `(val << shift)` and `irq_flags |= val` only touches the targeted byte. Not a blocker. |
| devils-advocate | Cargo.toml + CHANGELOG | Still at `0.2.4`, no `0.2.5` entry. Per HLD this needs bumping. |

**Decision (supervisor):** abandon the "RMW everywhere with RXF carve-out" approach for PIO. Adopt the rp2040-emu philosophy: TXF-only widen, drop everything else. Same behaviour as pre-0.2.4 for non-TXF registers, plus the OneROM CH1 fix for TXF. Sidesteps every side-effect hazard above with one design change.

The RESETS arm stands as-is — RESETS has only one writable register (`RESET` at offset `0x000`), no side-effect-on-read, and the RMW pattern composes cleanly there.

### Stage 2 also identified

- Smoke verdict's `pin_matches >= 1` is too loose (could pass with only baseline matched). Tighten to `>= 2` to mirror criterion 4's distinct-src-addrs cardinality.
- TXF tests cover lanes 0 and 1 only; should add lane 2/3 to lock down the `byte_idx*8` shift.
- Symmetric narrow-read RXF hazard exists (`Bus::read8`/`read16` of RXF address pops the FIFO, then byte-extracts). Out of scope for 0.2.5 narrow-write work but flagged for future.
- Out-of-scope for 0.2.5: full rp2040-style philosophy refactor of every per-aperture arm (the 2026-04-17 unified-dispatch HLD covers that).
