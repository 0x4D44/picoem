# 2026-04-17 — PicoGUS Silent Audio Diagnosis (Trace Oracle)

**Author:** diagnosis agent
**Scope:** Why does `picogus_diff_rp2040`'s captured WAV decode as silence (peak=0, RMS=0) despite valid I2S framing (header rates plausible, LRCLK edges count matches frames)? Add permanent tracing infrastructure so this class of bug is observable in <5 minutes next time.

## Context

Stream 5 (`ca8fde0`) declared "audio path is functionally faithful to silicon behavior on the trace oracle". The post-fix WAV (`wrk_scratch/picogus_monkey_island_fresh.wav` etc.) reports 42,587 Hz / 24,392 stereo frames / 0.573 s — *header is valid*, but every sample byte is zero.

Validated to date: I2S framing (BCLK + LRCLK + per-frame bit count). NOT validated: that the PCM bits coming out of PIO1 SM3 SDATA are non-zero.

## Code path read (Phase 1)

Expected data journey:
1. PWM slice 4 wraps at the audio sample rate.
2. PWM IRQ handler in firmware fires `audio_sample_handler()` (`gusplay.cpp:81`).
3. Handler computes `sample = GUS_sample_stereo()` and writes it to `audio_pio->txf[PICO_AUDIO_I2S_SM]` — i.e. PIO1 SM3 TX FIFO at `0x5030_001C`.
4. PIO1 SM3 (autopull enabled, threshold 32, OUT_SHIFTDIR left = MSB first) auto-refills OSR from TX FIFO and shifts `OUT PINS,1` onto GPIO16 (PINCTRL.OUT_BASE=16, OUT_COUNT=1).
5. Side-set on SM3 drives BCLK (GPIO17) + LRCLK (GPIO18) via SIDESET_BASE=17, SIDESET_COUNT=2.
6. `update_gpio` in `mdrp2040::lib.rs:516`: `out = (out & !pio_mask) | (pio.pad_out & pio_mask);` — PIO bits override SIO wherever `pad_oe` is set. PIO1 `pad_oe` was confirmed `0x0007_000e` → bits 16, 17, 18 set ✓.
7. `IsaSink::pad_state()` returns `bus.gpio_in`; `CapturingSink::step` calls `capture.tick(pad, cycles)`.
8. `I2sCapture::on_bclk_rising` shifts DOUT bit into 16-bit accumulator MSB-first; `on_lrclk_edge` finalises the in-flight accumulator as either Left or Right per LRCLK level.

If LRCLK edges arrive at ~85 kHz (correct for 42 kHz stereo) but every accumulator finalises as `0x0000`, then by elimination either: (a) DOUT is permanently 0 — meaning either pad_oe doesn't claim bit 16, or `pad_out[16]` is never set; OR (b) the data being shifted is genuinely zero.

## Phase 2 — tracing added

All `tracing` crate, `debug!`/`trace!` so release builds compile to nothing:

| File | Event | Level | Reason |
|---|---|---|---|
| `crates/mdpicoem-common/src/pio/mod.rs` (TXFn write paths) | `txf_write` (sm, val, push_ok, occupancy) | `debug!` | One per audio sample (~44 kHz) — fine for diag, never in release. Tells you exactly what the firmware is pushing into each SM's TX FIFO. |
| `crates/mdpicoem-common/src/pio/mod.rs` (`merge_pin_outputs` end) | `pad_change` (old_out, new_out, old_oe, new_oe) | `trace!` | Per `step()` per PIO block when `pad_out` or `pad_oe` differ. High volume — `trace!` keeps it out of `RUST_LOG=debug` runs unless the operator specifically asks for it. |
| `crates/mdpicoem-devices/src/i2s_capture.rs` (`on_lrclk_edge`) | `lrclk_edge` (cycle, channel, accumulator, bit_count, edges_seen) | `debug!` | Two per stereo frame (~85 kHz at 42 kHz audio). Direct visibility into what bits the capture latched per half-frame. |
| `crates/mdpicoem-devices/src/i2s_capture.rs` (`on_bclk_rising`) | `bclk_rising_latch` (dout, bit_count, accumulator) | `trace!` | One per BCLK rising edge (~1.5 MHz). Use only when `lrclk_edge` shows the accumulator latching the wrong value and you want the per-bit timeline. |

Targets are `mdpicoem_common::pio` and `mdpicoem_devices::i2s_capture` so `RUST_LOG` filters cleanly.

## Phase 3 — diagnosis run

Built debug binary (`cargo build --bin picogus_diff_rp2040`) — release strips `debug!`/`trace!` per the workspace's `release_max_level_info` policy. Copied to `/tmp/picogus_diff_dbg.exe` per CLAUDE.md "Running alongside concurrent builds" advice.

```bash
RUST_LOG=mdpicoem_common::pio=debug,mdpicoem_devices::i2s_capture=debug \
```

### Result

Trace volume: 363,680 lines.

`txf_write` per SM:
```
345830 sm=0   (PIO1 SM0 = PSRAM SPI commands — varied, expected)
  8914 sm=3   (PIO1 SM3 = I2S audio data — ALL ZEROS)
```

Distinct values pushed to PIO1 SM3:
```
val=0x00000000
```
(Single distinct value across all 8,914 pushes.)

LRCLK edge distinct accumulator finalisations:
```
accumulator=0x0000   (8,930 of 8,931 edges)
accumulator=0x0001   (1 phase-startup straggler)
```

### Definitive verdict

**Neither H1 nor H2 as originally framed.** The I2S framing is correct (BCLK / LRCLK / SDATA all reach the capture). The SM3 OUT path is correct (it shifts every bit of every pushed word out to GPIO16, and PIO1's `pad_oe` includes bit 16 so the shift reaches `gpio_in`). What's wrong is **the data itself**: the firmware's PWM-IRQ handler `audio_sample_handler()` (`gusplay.cpp:81`) pushes 32-bit `0x00000000` to PIO1 SM3 TXF on every fire. So the I2S stream is technically valid silence — i.e. the WAV is a faithful capture of what the firmware actually transmitted.

Root cause is upstream of the I2S path: `GUS_sample_stereo()` returns 0 because the GUS audio engine has not started producing samples within the simulated window. Likely contributors (in priority order, none investigated by this agent):

1. **Cross-references the existing PicoGUS ISA capture coverage table** in the harness output — captured/fired ratio is **0% in deciles 0–50%**, jumping to 23–42% only in deciles 50–100%. The GUS register writes that programmed DMA / playback geometry are likely in the early deciles and were silently dropped (the trace-replay→ISA-pin path drops 81% of writes overall, per the existing diag). With no DMA setup, GUS_sample_stereo returns mute.
2. PWM-IRQ handler may fire before GUS playback init completes (the trace-fast-forward gets PicoGUS to PLL-reprogram + I2S-init quickly, but the GUS DMA arming sits later in the firmware's init).
3. Possible audio-volume / mixer state still at default mute.

These are all **firmware-state / replay-coverage** problems, not emulator bugs. The session-recap claim "audio path is functionally faithful" is technically true *for the framing layer* — and now we have a permanent oracle to spot the data-layer regression next time without manually `xxd`-ing the WAV.

## Reproduce next time

```bash
# Keep release fuzzers happy by copying the debug binary first.
cargo build --bin picogus_diff_rp2040
cp target/debug/picogus_diff_rp2040.exe /tmp/picogus_diff_dbg.exe
RUST_LOG=mdpicoem_common::pio=debug,mdpicoem_devices::i2s_capture=debug \
  /tmp/picogus_diff_dbg.exe \
    --trace crates/mdpicoem-harness/fixtures/monkey_island_theme.trace \
    --flash third_party/picogus/picogus-v4.0.0.bin \
    --bootrom roms/rp2040/bootrom-rp2040-b2.bin \
    --duration 0.5 --post-roll 0.05 \
    --out /tmp/diag.wav 2> /tmp/diag.log

# Quick triage:
sed 's/\x1b\[[0-9;]*m//g' /tmp/diag.log | grep txf_write | grep -oE 'sm=[0-9]+' | sort | uniq -c
sed 's/\x1b\[[0-9;]*m//g' /tmp/diag.log | grep txf_write | grep 'sm=3' \
  | grep -oE 'val=0x[0-9a-f]+' | sort -u
```

If "distinct values pushed to SM3" is just `val=0x00000000` → firmware is muted, NOT an emulator audio-path bug.

If pushes look healthy but `lrclk_edge accumulator=` is always zero → DOUT pad isn't reaching `gpio_in`; check PIO1 `pad_oe` bit 16 and `update_gpio` ordering.

If LRCLK edges aren't firing at all → SM3 never consumes the FIFO; check autopull / sideset / clkdiv / SM enable bit.

## Proposed fix

**Trivial fix for the symptom:** none — the WAV is correctly capturing what the firmware actually produces.

**Real fix for the upstream cause:** investigate why the GUS init sequence (DMA channel setup, mixer un-mute) isn't in our trace-replay's effective-write set. Almost certainly tied to the 81% drop rate the existing harness already reports on `picogus_diff_rp2040` ISA coverage. Distinct work item — out of scope for this diagnosis.

**Non-trivial because:**
- The "missing GUS init" might be ISA writes the trace-replay didn't deliver in time (rate-limit / timing issue), OR ISA writes the firmware never made because trace-replay didn't satisfy some earlier handshake. Either way it requires walking the GUS state machine in the firmware against the trace coverage table.
- Could also be a real RP2040 emulator bug (e.g. ROSC vs PLL fast-forward causing the firmware to skip an init phase). Distinguishing these requires comparing the captured WAV against silicon, which is the PicoGUS silicon-oracle-MVP work item already on the list.

## Risks / follow-ups

- The PIO `txf_write` `debug!` line evaluates `format_args!` only when the level is enabled (zero cost when off), but be aware the entire PIO MMIO write path now has a `tracing::debug!` macro inserted; even at `release_max_level_info` the macros expand to `{}` so no perf hit.
- `pad_change` is `trace!` — fires on every PIO block step when pads differ. At full RUST_LOG=trace this will swamp the log; never enable workspace-wide. Filter narrowly: `RUST_LOG=mdpicoem_common::pio=trace`.
- Did not touch the MMIO bus trace (`emit_mmio_trace`) per HLD direction.
- Did not extend tracing into the SM `execute_cycle` hot path per HLD direction.
