## Summary

The structural direction (per-core host thread, coordinator-owned Pacer, quantum barrier) is sound. The two failure modes I want to flag loudest:

1. **The "one Emulator, two modes" API is the wrong shape.** The shared-state layout and the lockstep layout are structurally different types — trying to make a single `Emulator` be both via `split_for_threaded` / `reassemble_from_threaded` pays you in complexity forever to save a constructor. See ISSUE 1.
2. **"Used in BOTH modes" for ThreadedSio and SharedMemory is a net cost, not a net win.** The HLD claims unification simplifies. It does the opposite: lockstep tests pay lock-free overhead, every existing `Memory`-using test changes, and the reference path slows down. See ISSUES 6, 7, 9.

The remaining issues are correctness / cleanliness detail that would bite in review. Numbered per the user's prompt.

## ISSUE 1: Two modes on one `Emulator` is the wrong shape
**Severity:** CRITICAL
**Section:** §1 "Two entry points on Emulator", §8 "Thread lifecycle"
**Problem:**
The HLD makes `Emulator` carry both behaviours, with `split_for_threaded()` moving fields into `Arc<…>` on entry to `run_threaded()` and `reassemble_from_threaded()` moving them back on exit. This is the classic "mode flag on an object" anti-pattern implemented via state shuffle. Consequences:
- `Emulator`'s fields are either borrowed-mut or `Arc<…>` depending on *which method the caller last called*. The type system can't tell you which; you rely on discipline.
- "Restores state after return" requires the split and reassembly to be exact inverses. Any future field added to `Bus`, `Sio`, or `Memory` is a silent footgun: forget to reassemble one field and you get stale state on the next `run()`.
- Every peripheral or Bus method that can run in either mode needs to tolerate both ownership shapes, or the struct carries dual storage.
- Caller-visible oddity: after `run_threaded()` returns, is the Pacer's `Arc<PacerStats>` the same `Arc` as before? What about `Arc<SharedMemory>` if the caller cloned it? (See ISSUE 10.)

**Proposed solution:**
Make the two modes two types, sharing *data* but not *runtime surface*.

```rust
// Lockstep. Cycle-accurate. What most tests use.
pub struct Emulator { cores: [CortexM33; 2], bus: Bus, clock: Clock }
impl Emulator {
    pub fn run(&mut self, cycles: u64) -> u64;
    pub fn step(&mut self) -> u64;
    // Consume self, hand ownership to the threaded runtime:
    pub fn into_threaded(self) -> ThreadedEmulator;
}

// Threaded. Shared state.
pub struct ThreadedEmulator { /* Arc<SharedMemory>, Arc<Mutex<Peripherals>>, etc. */ }
impl ThreadedEmulator {
    pub fn run(&mut self, pacer: &mut Pacer, stop: &StopSignal) -> RunStats;
    pub fn into_lockstep(self) -> Emulator;  // for reverse path if needed
}
```

Now the type system enforces which ownership shape you're in. `split` / `reassemble` become `into_threaded` / `into_lockstep` — single-point, lossless conversions, not per-call pivots. No dual storage. No "some fields are Arc sometimes". Tests that stay lockstep never touch `Arc<_>` machinery.

Second-order benefit: `paced_bench --threaded` becomes `Emulator::new(cfg).into_threaded().run(...)`, which reads straightforwardly.

## ISSUE 2: Ownership semantics of `run_threaded(&mut self, …)` don't express what actually happens
**Severity:** IMPORTANT
**Section:** §8 "Thread lifecycle"
**Problem:**
`run_threaded(&mut self, pacer, duration)` takes `&mut self`. Inside, it spawns threads that own `Arc`-cloned handles into fields that logically belong to `self`. While the workers run, `self` is *not* mutably borrowable (Rust correctly prevents this because `run_threaded` has `&mut self`), but those workers are mutating `self`'s fields concurrently.

This is technically sound if `split_for_threaded()` genuinely moves the fields *out* of `self` (replacing them with placeholders) before spawning — but the HLD doesn't say that, and doing so would require every `Bus`/`Memory` field to have a cheap placeholder. If it instead holds `Arc`s that alias `self`'s data, and `self` is `Send` (which it will need to be), you have aliasing through a shared-mutable reference that the borrow checker can't see because it goes through `Arc`. That's not unsound (Arc + atomics is fine), but it *is* confusing: `&mut self` stops meaning what it normally means.

This is another symptom of ISSUE 1 — two types cleanly separate "I own this data mutably" from "I hand this data to threads."

**Proposed solution:**
If you adopt ISSUE 1's split, the question vanishes: `ThreadedEmulator::run(&mut self, …)` holds `Arc`s as fields; the workers get clones; when they join the `Arc`s come back to refcount 1. No ambiguity about what `&mut self` protects.

If you *must* keep a single `Emulator`, take `run_threaded` by value of a temporary context object:

```rust
pub fn run_threaded(self, pacer: &mut Pacer, stop: &StopSignal) -> (Self, RunStats);
```

so the signature reflects "I consume this emulator, spin it up threaded, and give it back." Ugly, but honest.

## ISSUE 3: `Bus` API must move from `&mut self` to `&self` for reads in threaded mode — and this is invasive
**Severity:** IMPORTANT
**Section:** §3 "Memory model", §4–5 (Bus/peripherals split)
**Problem:**
Current `Bus::read16(&mut self, addr)` takes `&mut self` because:
- it updates `last_access_cycles`, `extra_wait_states`, `contention_check_active`, `core0_port`, `bus_fault`, `bus_fault_addr`, `peripheral_regs` (HashMap), PIO state, `pending_fifo_event`, `gpio_hi_noise_state` LFSR, etc.
- these are per-access side effects the interpreter consumes on every instruction.

In threaded mode, *none* of that per-cycle bookkeeping is meaningful (§2 explicitly disavows bus-contention modelling; §2 also says "No per-cycle bus contention modeling in threaded mode"). But if `Bus::read16` still takes `&mut self`, you can't call it from two threads on an `Arc<Bus>` without a mutex over the whole bus — which defeats the point.

The HLD glosses this: it says "Bus splits cleanly" but doesn't show the execute.rs change. Every `bus: &mut Bus` in `core/execute.rs`, `core/execute_thumb32.rs`, `core/execute_fpu.rs`, `core/exceptions.rs`, `core/decode.rs` currently takes `&mut Bus`. I counted: ~62 call-sites across 5 files. Changing these to a trait or a new type is *not* a small refactor.

**Proposed solution:**
Introduce a `BusAccess` trait that is the *only* thing execute.rs talks to:

```rust
pub trait BusAccess {
    fn read8 (&mut self, addr: u32) -> u8;
    fn read16(&mut self, addr: u32) -> u16;
    fn read32(&mut self, addr: u32) -> u32;
    fn write8 (&mut self, addr: u32, val: u8);
    // etc. Also: bus_fault(), last_access_cycles() as needed
}
```

Keep `&mut self` in the trait. Two implementations:

- `impl BusAccess for LockstepBus` — today's `Bus` renamed. Tracks contention, wait states, etc.
- `impl BusAccess for ThreadedBusView<'_>` — a temporary view struct holding `&Arc<SharedMemory>`, `&Arc<Mutex<Peripherals>>`, `core_id: u8`. Its `read*`/`write*` do atomic loads, take the mutex on peripheral paths, no contention tracking.

execute.rs becomes generic: `fn thumb16_ldr_literal<B: BusAccess>(&mut self, opcode: u16, bus: &mut B) -> u32`. This is the smallest possible change to the CPU interpreter — a type parameter — and it lets the threaded path reuse the *same* code. No changes to 62 call-sites.

This also addresses the prompt's "can we keep the mut-taking API?" — yes, via `&mut ThreadedBusView` which is locally mutable (tracks per-core active core, a mutable cursor for peripheral batch) even though its fields point at shared data.

## ISSUE 4: The Bus split (SharedMemory vs Peripherals) ignores how Bus is actually structured today
**Severity:** IMPORTANT
**Section:** §2 "Shared state layout"
**Problem:**
HLD shows:
```
memory: Arc<SharedMemory>
peripherals: Arc<Mutex<Peripherals>>
```
But today's `Bus` (lines 16–96 of `bus/mod.rs`) owns: `Memory`, a `peripheral_regs: HashMap<u32,u32>`, the QMI register file, clock-tree state, PLL register images, XIP SRAM, boot RAM, PIO blocks, SIO (which itself owns MTIME, FIFOs, etc.), PPB[2], `resets_state`, `flash_loaded`, `gpio_hi_noise_state` (per-read LFSR), plus cycle bookkeeping. That's not two categories. It's at least:

1. **Backing store** — ROM/SRAM/XIP/boot_ram/xip_sram bytes (Arc<SharedMemory> candidate).
2. **Register files** — QMI regs, clock regs, PLL regs, `peripheral_regs`, `resets_state` (needs Mutex or sharding).
3. **Per-core state** — PPB[2] (see ISSUE 5).
4. **Cross-core shared logical state** — SIO (FIFOs, spinlocks, doorbells, MTIME, divider, interp) — needs lock-free (ISSUE 7).
5. **PIO blocks** — currently `pub pio: [PioBlock; 3]` — mutated by `Emulator::step()` with `for pio in &mut self.bus.pio { pio.step(gpio_in); }`. Where do these live?
6. **Cycle-tracking transient** — `last_access_cycles`, `extra_wait_states`, `core0_port`, `contention_check_active`, `burst_mode`. Per-core in threaded mode, meaningless if not tracked.
7. **Fault signalling** — `bus_fault`, `bus_fault_addr`, `event_flag[2]`, `rcp_salt[2]`, `rcp_salt_valid[2]`. Cross-core shared small state.

The HLD's two-bucket split (memory + peripherals) is too coarse. In particular the coordinator needs access to (5) to tick PIO, and to (4) to tick MTIME (`sio.tick_mtime()` is called from `Emulator::step` today — who calls it in threaded mode?). If both workers and the coordinator mutate Sio, it *must* be the lock-free version from day one.

**Proposed solution:**
Enumerate the buckets explicitly in the HLD and name the owner of each:
- `Arc<SharedMemory>`: just the byte arrays.
- `Arc<ThreadedSio>`: already lock-free (FIFOs, spinlocks, doorbells, MTIME). MTIME ticked by coordinator.
- `Arc<Mutex<PeripheralRegs>>`: CLOCKS/PLL/QMI/RESETS/peripheral_regs HashMap/PIO blocks. PIO stepped by coordinator. Lock held briefly per access.
- Per-worker `LocalTransient`: `last_access_cycles`, `extra_wait_states`, `bus_fault`, `bus_fault_addr` — not shared, lives in the `ThreadedBusView`.
- `Arc<AtomicU32 × 2>` for `event_flag`, `rcp_salt`, `rcp_salt_valid` (small, shared, cheap as atomics).
- PPB: per-thread — see ISSUE 5.

Without this enumeration, Phase 1 (SharedMemory) will land, Phase 2 (ThreadedSio) will land, and then Phase 3 will discover that PIO, clock tree, and peripheral_regs don't fit either bucket. Mapping now avoids redesign later.

## ISSUE 5: PPB (per-core NVIC/SCB/MPU/SAU) belongs with `CortexM33`, not with `Bus`
**Severity:** IMPORTANT
**Section:** §2 "Shared state layout", §3–5 (Bus split)
**Problem:**
Today `pub ppb: [ppb::Ppb; 2]` lives on `Bus`. This is a lockstep-era convenience: the bus knew which core was active (`active_core()` flag on Bus) and indexed into `ppb[active]`. In threaded mode, each worker owns its `CortexM33`. The PPB state is *strictly per-core* (each core has its own NVIC, SCB, VTOR, MPU, SAU, SHPR, CFSR, …). It should travel with the core, not with the bus.

The HLD doesn't address this. If PPB stays on Bus, then:
- `Bus` must expose per-core PPB access across thread boundaries. That means either `[Mutex<Ppb>; 2]` (contended only when another core reads your PPB, which is rare but possible) or `[Arc<Mutex<Ppb>>; 2]` in the bus view.
- The `active_core()` helper on Bus becomes meaningless in threaded mode — each worker must pass its core_id explicitly.

Moving PPB to `CortexM33` is cleaner, matches the hardware (PPB is per-core in silicon), and removes one cross-thread sharing concern.

**Proposed solution:**
Move `Ppb` into `CortexM33` as `pub ppb: Ppb`. Rework region-0xE dispatch on Bus to delegate to the *calling* core's Ppb, not the bus-held one. Concretely, add a `core_id: u8` to the `BusAccess` trait methods (or carry it on `ThreadedBusView`) and have region-0xE reads go to `&mut core.ppb`. The only cross-core PPB concern is SEV broadcast (already uses `event_flag[2]`) and that doesn't need PPB.

This change is *independent of threading* and should land before the threading work as a cleanup commit. Lockstep path also benefits: no more `self.bus.ppb[self.active_core()]` indirection.

## ISSUE 6: Replacing `Memory` with `SharedMemory` is invasive — tests directly touch `bus.memory`
**Severity:** IMPORTANT
**Section:** §Phase 1, "Files changed" table
**Problem:**
Grep across the workspace:
- `crates\mdrp2354\src\tests.rs`: 14 direct uses of `bus.memory.sram_*` / `rom_*` / `xip_*`.
- `crates\mdrp2354\src\lib.rs`: 6 uses (construction, load, peek/poke).
- `crates\mdrp2354\src\bus\mod.rs`: many uses via `self.memory.*`.

If `Memory` becomes `SharedMemory` with `[AtomicU8]` backing, every `sram_read32(offset) -> u32` signature stays the same, but every test that does `memory.sram_write8(…)` on a borrowed `&mut Memory` now writes through `&SharedMemory` + atomics. That part is fine. The *painful* part is:

- `Memory::new()` returns a `Vec<u8>`-backed struct today. Tests construct `Memory` directly? Grep says no — tests go through `Emulator`. OK.
- But: `load_rom(&mut self, data: &[u8])` currently does `self.rom[..len].copy_from_slice(&data[..len])`. If `rom` becomes `Box<[AtomicU8]>` (HLD §3 says "rom: Box<[u8]>, read-only, no atomics needed" — OK, rom is fine). For `sram` and `xip`, loading into `[AtomicU8]` needs a byte-by-byte store loop. Not hard, but every `load_*` path changes.
- `peek32` / `poke32` on `Memory` (used by `Emulator::peek` / `poke`) now call atomic load/store. The `&self` signature is great, but `poke` takes `&mut self` today — could become `&self` (mild API churn that callers won't notice).

More importantly: **the `Memory` → `SharedMemory` rename is not just a field swap — it is a semantic change.** Today `bus.memory.sram_write32(...)` is a `&mut` operation that the borrow checker serializes. Tomorrow it's a shared-reference atomic store that *doesn't* serialize with reads from another thread. Any test that relies on "I wrote X then read X and no concurrent thread exists" is fine; any helper that assumed exclusivity (e.g., `sram_write8` + `sram_read8` as an RMW) is *not* fine — you now need `fetch_update` or `compare_exchange`. I don't see such a helper in `memory/mod.rs` today, but the SRAM SET/CLR/XOR alias logic in `Bus::write8` (lines 555-570) *does* RMW: `let old = self.memory.sram_read8(offset); ... self.memory.sram_write8(offset, new_val);` — that becomes a race between cores if both hit the same byte via the atomic alias.

**Proposed solution:**
1. Audit every Bus RMW path (the SET/CLR/XOR alias handling in write8/16/32, the QMI RMW, the CLOCKS/PLL/PLL_USB subword paths) — they currently rely on `&mut` serialization. In threaded mode they need either `fetch_update` (for bytes in the atomic arena) or to go through the peripherals mutex (for register-file RMWs). Document which is which.
2. Keep `Memory`'s API surface stable (`sram_read32`, etc.) but change *only* the backing store and method receiver (`&self` instead of `&mut self` for writes to the atomic arena). Most callers won't notice.
3. Don't rename `Memory` → `SharedMemory`. Rename is noise; the type is still "the byte backing store." The Arc-ness is visible at the ownership site (`Arc<Memory>`), not in the type name.

## ISSUE 7: "Used in BOTH modes" for ThreadedSio is a cost, not a win
**Severity:** IMPORTANT
**Section:** §Phase 2 "Threaded SIO"
**Problem:**
The HLD claims Phase 2 replaces SIO internals with `ThreadedSio` (crossbeam `ArrayQueue`, AtomicU32 spinlocks, atomic doorbells) and uses it "in BOTH modes." Motivation: one code path.

But measure the cost. Today's `Fifo::push/pop` (sio/mod.rs:32-51) is: array index, wrapping add, count bump. Inlinable, a handful of instructions. `crossbeam_queue::ArrayQueue::push` uses a compare-exchange loop with SeqCst/AcqRel fences. Even uncontended, that's 3-5x the cycle cost on x86, and a pipeline-disrupting LOCK prefix. Per-FIFO op this is nothing, but:

- The lockstep path is our **cycle-accurate reference for QEMU differential fuzzing** (per CLAUDE.md). Slowing it down has a direct cost: fewer fuzz iterations per wall-clock second.
- The per-cycle `self.bus.sio.tick_mtime()` and many doorbell / spinlock state reads on the hot SIO path in lockstep get fatter for no benefit.
- `crossbeam` and its transitive deps appear in the cycle-accurate binary too.

The "one code path" argument is only a win if the two-path alternative is complex. Here, the two paths share 95% of the Sio logic (divider, MTIME, interp, doorbells) — only the FIFO and spinlock primitives differ. That difference is easy to abstract behind a `FifoImpl` trait or a `cfg`-gated type alias.

**Proposed solution:**
- Keep lockstep SIO on `VecDeque`/`u32` bitmask. Its semantics are serialized-by-design.
- Introduce a `ThreadedSio` that wraps the same logical registers but uses lock-free primitives, used *only* by the threaded runtime.
- Share logic where possible (e.g., the MTIME math, interp backing store) via helper types or free functions. Don't force one implementation where two different hardware contracts exist.

This is the same point ISSUE 1 makes: threaded and lockstep are different enough that "unify" actively harms the simpler path.

## ISSUE 8: `crossbeam` dependency — the HLD itself flags it and doesn't decide
**Severity:** NICE-TO-HAVE
**Section:** §Risks item 2
**Problem:**
The HLD lists "Alternative: hand-roll SPSC ring buffer (~100 lines)" as a risk and then punts. A decision is owed before the commit lands. `crossbeam = "0.8"` pulls in `cfg-if`, `crossbeam-utils`, potentially `loom` for testing, and `scopeguard`. For a core emulator crate that's currently dep-light (`mdrp2354` has no third-party runtime deps visible in the grep — just `std`), this is a meaningful increase in supply-chain surface.

For the use case (exactly one producer + exactly one consumer per FIFO, exactly 8 entries, u32 payload), `ArrayQueue` is overkill. A hand-rolled bounded SPSC ring with two AtomicU8 head/tail indices and `[AtomicU32; 8]` storage is ~60 lines, has no external deps, and is easier to audit for the relaxed/acquire/release ordering we actually need.

**Proposed solution:**
Hand-roll the SPSC ring. The hardware FIFO is strictly 1-to-1 per direction (core 0 → core 1 and core 1 → core 0) — it is literally the SPSC case. No need for MPMC machinery. Put it in `sio/spsc.rs`, ~80 lines, zero deps.

If the spinlock and doorbell logic also needs crossbeam (it doesn't — `[AtomicU32; 32]` + atomic ops is stdlib), we're done without the dep.

## ISSUE 9: Shared `AtomicU64` clock vs lockstep `u64` clock — pay the cost or fork the path
**Severity:** NICE-TO-HAVE
**Section:** §2 "Shared state layout", §6 "Quantum barrier"
**Problem:**
Today `Clock { cycles: u64, sys_clk_hz: u32 }` is hit on every `Emulator::step()` (`self.clock.tick()`, line 129 of lib.rs). Hot path. Atomic loads on x86 are cheap, but atomic *stores* (especially with `Release` semantics) are more expensive than a plain increment on an already-hot cache line — and this is one of the hottest writes in the entire emulator.

If we unify to `Arc<AtomicU64>`, the lockstep path pays for synchronisation it doesn't need. If we don't unify, we have `Clock { cycles: u64 }` and `ThreadedClock { cycles: Arc<AtomicU64> }` — which is fine.

In threaded mode only the coordinator advances `clock_cycles` (per the HLD §6) and workers read it rarely, so `Relaxed` is fine and the write side is amortised over a quantum. The cost is negligible *there*. But if we use the same type for both modes, the lockstep per-cycle write pays for atomicity.

**Proposed solution:**
Split `Clock` and `ThreadedClock` per ISSUE 1. Lockstep keeps the plain u64 increment. ThreadedClock uses `AtomicU64::fetch_add(quantum, Relaxed)` once per quantum on the coordinator thread. No per-instruction atomic cost on either path.

## ISSUE 10: Public API surface after this change is too wide
**Severity:** IMPORTANT
**Section:** §Files changed, §Phase 1–3
**Problem:**
After the HLD lands, a downstream crate (OneROM integration in 6 months) sees in `mdrp2354`'s public API:

- `Emulator`, `EmulatorBuilder`, `Config`
- `CortexM33`, `Bus`, `Memory`/`SharedMemory`, `Clock`, `Sio`/`ThreadedSio`
- `Pacer`, `PacerStats`, `PacerSnapshot`
- `Peripheral` trait, `Peripherals` (new), `QuantumBarrier` (new)
- `StopReason`, `ROSC_FREQ_HZ`

The HLD doesn't say which of the new types are `pub`. Based on "Files changed" (`threaded.rs` is new, `Emulator::run_threaded` is public) the minimum-exposure story would be:

- Keep `Bus`, `Memory`, `Sio`, `Clock` as internals or `#[doc(hidden)]` — no external consumer should be poking at them.
- `ThreadedSio`, `SharedMemory`, `QuantumBarrier`, `Peripherals` should never be named by downstream code — they're implementation details of `run_threaded()`.
- `Emulator::run`, `Emulator::run_threaded`, `Pacer`, `PacerStats`, `Config` are the actual API.

Right now `lib.rs` does `pub use self::bus::Bus; pub use self::memory::Memory; pub use self::sio::Sio;` — all internals exposed. If we add `ThreadedSio` and `SharedMemory` and keep the same convention, we export even more implementation detail. That's the opposite of what a library should do.

Also: `Emulator.cores: [CortexM33; 2]`, `Emulator.bus: Bus`, `Emulator.clock: Clock` are all `pub` fields. In the threaded design, `bus` doesn't exist as a single `&mut`-able thing. If we keep the pub-fields shape, threaded mode forces a breaking change to the public field layout. That's a decision to make deliberately, not by accident.

**Proposed solution:**
1. Decide now which types are public API:
   - **Public**: `Emulator`, `ThreadedEmulator` (per ISSUE 1), `Config`, `Pacer`, `PacerStats`, `PacerSnapshot`, `Peripheral` trait, `StopReason`, `ROSC_FREQ_HZ`. That's it.
   - **Internal** (`pub(crate)` or behind `#[doc(hidden)]`): everything else.
2. Replace `pub` fields on `Emulator` with accessor methods. This was going to hurt anyway (threaded mode can't expose `bus: Bus`), so bite the bullet in the refactor that's already touching these types.
3. Write the 6-month-from-now caller's view before writing the implementation. If OneROM only needs `Emulator::new + load_flash + load_bootrom + run + peek + gpio_read`, that's the API. Everything else should be private.

## ISSUE 11: `run_threaded(pacer, duration: Duration)` — wrong unit and wrong signature
**Severity:** IMPORTANT
**Section:** §1 "Two entry points on Emulator", §7 "Pacer integration"
**Problem:**
Two problems:

(a) **Units.** Why `Duration`? The emulator knows cycles. The Pacer converts cycles to wall time. Callers will know one of two things: "run until this timer fires in the firmware" (cycles) or "run for this much real time" (wall seconds). Today's `run(cycles: u64)` is cycles. Switching to `Duration` for threaded mode means callers can't express cycle-count goals. And they *want* cycle-count goals: `paced_bench` measures MHz, which is cycles/second, and needs a cycle target to know when to stop.

If the intent is "wall-clock limited", that's `run_for(Duration)`. If it's "run until this many cycles", that's `run(cycles: u64)`. These are two different ops and both are reasonable. The HLD conflates them.

(b) **`&mut Pacer` parameter.** `Pacer` today is `x86_64`-only (see `pacer.rs:253`: `#[cfg(target_arch = "x86_64")] pub struct Pacer`). Making `run_threaded` take `&mut Pacer` means `run_threaded` is also `x86_64`-only. Is that intended? It's probably fine for now (the threaded path is a performance feature and OneROM runs on x86_64 hosts), but it should be stated explicitly, and `run_threaded` should be `#[cfg(target_arch = "x86_64")]` to match.

Also: coupling the Pacer into the API means downstream consumers who don't want pacing (they want max-speed threaded execution for tests) can't use `run_threaded`. Should there be a non-paced variant?

**Proposed solution:**
```rust
#[cfg(target_arch = "x86_64")]
impl ThreadedEmulator {
    /// Run until `cycles` emulated cycles have executed. Pacer controls real-time.
    /// Returns cycles actually executed (may be < requested if stop signal fired).
    pub fn run(&mut self, cycles: u64, pacer: &mut Pacer, stop: &StopSignal) -> u64;

    /// Run as fast as possible, no real-time pacing. For tests.
    pub fn run_unpaced(&mut self, cycles: u64, stop: &StopSignal) -> u64;
}
```

Caller who wants wall-clock runs computes `cycles = sys_clk_hz * duration.as_secs_f64()` and passes that. Or we add `run_for(Duration, pacer, stop)` as a thin wrapper. But the primitive should be cycles — matches the lockstep API, matches what the caller actually wants to measure.

## ISSUE 12: No cancel / shutdown mechanism — `Duration` is the only exit
**Severity:** CRITICAL
**Section:** §1 "Two entry points on Emulator" (nothing further mentioned)
**Problem:**
`run_threaded(pacer, duration)` blocks until duration elapses. The HLD has no story for:

- Ctrl-C during `run_threaded`. In `paced_bench`, Ctrl-C today interrupts the loop between quanta. In threaded mode, the coordinator loop is the one running on the caller's thread — can the caller register a signal handler? Does it work? What about on the worker threads?
- Early stop because firmware reached a breakpoint (`StopReason::Breakpoint` is in `lib.rs:29` — today's single-threaded `run()` doesn't use it, but future code will).
- Early stop because firmware hit `WFI` on both cores (deadlocked / done). Today's single-threaded `run()` has `StopReason::Wfi` in the enum but doesn't use it. In threaded mode, "both cores WFI with no pending interrupts" is a legitimate exit — we should return, not spin on the Pacer.
- Fault. `StopReason::Fault` — bus fault on one core should probably pause both and report.
- Host panic. HLD says "No graceful thread crash recovery — panic in a worker panics the process." That's wrong for a library. A panicking worker should poison a shutdown flag, the other worker should drain, and `run_threaded` should return with an error. Panicking the host process of a library consumer is a support nightmare.

**Proposed solution:**
Introduce a stop signal the caller can share with `run_threaded`:

```rust
pub struct StopSignal(Arc<AtomicU8>);  // 0=run, 1=stop-requested
impl StopSignal {
    pub fn new() -> Self;
    pub fn stop(&self);
    pub fn is_stopped(&self) -> bool;  // for workers to check
}
```

The coordinator checks the signal at each quantum boundary. Workers check at top of each quantum. `run_threaded` returns `RunStats { cycles_run: u64, stop_reason: StopReason }`. Caller can register a Ctrl-C handler that calls `signal.stop()`. Worker panics are caught via `std::thread::catch_unwind` at the worker entry, convert to `StopReason::Fault`, signal the coordinator.

`Duration` becomes one of several stop conditions, not the only one.

---

## Meta-observation: the HLD is good at the mechanism, light on the contract

The HLD describes the *mechanism* (barrier protocol, atomic backing, mutex on peripherals) in good detail. What it under-specifies is the *contract* — the public API shape, the ownership story, the per-phase invariants, the stop semantics. The issues above cluster around that gap.

Biggest lever: **resolve ISSUE 1 first.** Most of the other issues (2, 3, 6, 7, 9, 10) become easier or disappear once threaded and lockstep are clearly separate types with a one-way (or two-way, reversible) conversion. The temptation to "have one Emulator that does both" is understandable but it's the source of the complexity, not the solution to it.

Second-biggest lever: **ISSUE 12.** A library that can't be stopped early is broken for downstream use. Add the stop signal in Phase 3, not as an afterthought.

Third: **ISSUE 10 + 5.** Before threading lands, do a separate "API cleanup" pass that moves PPB to CortexM33 and makes Emulator's public API minimal. Threading becomes additive instead of a breaking rework.
