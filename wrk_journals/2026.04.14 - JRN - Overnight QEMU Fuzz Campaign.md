## Driver design

Three bash loops under `fuzz-runs/`, each batch picks a fresh random seed so
we cover different random sequences across the night rather than a single
giant run of one seed. Each oracle streams to its own log under
`fuzz-runs/*.log`. Batches:

| Oracle | `--fuzz` per batch | Expected duration/batch | Target batches |
|---|---|---|---|
| M33 (QEMU)   | 30 000 | 30–60 min (parallel) | ~8  |
| M0+ (QEMU)   | 50 000 | 30–45 min (parallel) | ~8  |
| RP2354 (HW probe) | 200 | ~24 min | ~20 |

HW probe added after start on Arthur's prompt — RP2354 silicon on a Pico
debug probe catches things QEMU doesn't model (SRAM bank contention, real
cycle counts, PLL/ROSC timing). Smoke test: 2000 tests in 366s, no
failures. `--cycles` flag deliberately omitted: the three catalogued
cycle-count mismatches in `tech_debt.md` (bank contention, backward
branch, PUSH minimum) would be noise, not signal.

RP2040 stays QEMU-only: `probe_diff_rp2040` is a stub, no M0+ board on
the rig.

Both loops re-check `fuzz-runs/deadline` before launching each batch, so
I can stretch or shorten the window by editing one file.

## Known carry-in items (from `tech_debt.md`)

Worth watching for these specifically during diagnosis:

- **mdrp2350 CPS bit-swap** — bits I/F currently reversed vs ARM ARM.
  No fuzz hit expected because PRIMASK flagging in CPS wasn't compared,
  but keep an eye on any PSR-adjacent divergence.
- **mdrp2350 banked SP staleness** in `enter_exception`/`exit_exception`.
  Fuzz harness doesn't run exception flows, so unlikely to hit here.
- **qemu_diff_m0plus filters every 32-bit Thumb**. BL/MRS/MSR/barriers are
  therefore **not** covered by tonight's campaign — unit-test-only still.

## Plan

1. Launch both runners in the background.
2. Tail logs through Monitor for `[FAIL]` / `panicked`.
3. ScheduleWakeup every ~45 min to spot-check progress; update this journal.
4. On any failure:
   - Capture seed + offending test case from the log.
   - Kill only the affected oracle; the other keeps fuzzing.
   - Delegate repro + root-cause to an investigation agent.
   - Code-review the fix via a second agent before applying.
5. At deadline: stop both loops, write a final summary with batch-level
   throughput and any fixes landed.

### 00:01 — M0+ runner entered hot failure loop

Batches 5–25 on M0+ all rc=127 within ~20 s (≤ 2 s each, no real fuzz
work done). Root cause found via `ps -W` + `netstat -ano`:

- Every dying M0+ batch was leaving its QEMU process orphaned on
  port 3334 (`qemu-system-arm.exe` would outlive its oracle).
- Zombies accumulated: by 00:01 there were **three** QEMUs bound to
  `*:3334` with SO_REUSEADDR-style behaviour (multiple LISTEN lines
  for the same port).
- New oracle connects to `localhost:3334` → OS chooses one of the
  zombie QEMUs → GDB never responds → `os error 10060` → oracle
  exits → bash loop spawns another → worse.

Verified: `target/release/qemu_diff_m0plus.exe` is fine on disk. Manual
invocation reproduces `fatal: A connection attempt failed ... (os error
10060)`.

No emulator-side work emerged from the night. Campaign did, however,
surface useful operational debt:

1. **QEMU zombies on ports 3333/3334** accumulate when a batch's
   oracle dies abnormally. When enough build up, new batches connect
   to a dead QEMU and timeout → hot failure loop. Fix: oracles should
   kill their spawned QEMU on every exit (clean or abnormal), and/or
   the runner should pre-clean port 3334/3333 before each batch.
   This is what turned a transient Defender exe-lock at 23:39 into a
   total M0+ loss overnight.
2. **Windows process-kill fragility from Git Bash**. `taskkill`,
   `powershell Stop-Process`, and `kill -9 <WINPID>` all have failure
   modes under system load. The only reliable method found was
   `kill -9 <POSIX_PID>` after walking the PPID tree via `ps -W`.
   Worth documenting as a runbook item.
3. **Probe runner updated (by Arthur/linter mid-run) to copy the .exe
   to a PID-qualified location** (`fuzz-runs/probe_diff_rp2350.$$.exe`)
   so a concurrent `cargo build` can replace `target/release/...`
   while the fuzzer holds the old copy. Sensible pattern; worth
   applying to `run-m33.sh` / `run-m0plus.sh` too.
4. **M0+ coverage gap**. Tonight contributed nothing material beyond
   the pre-existing per-PR smoke. Re-running (with item 1 fixed) is a
   small effort and would close the M0+ side.
