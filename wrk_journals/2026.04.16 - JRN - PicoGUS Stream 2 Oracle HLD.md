# 2026.04.16 — JRN — PicoGUS Stream 2: Silicon Oracle HLD

## Summary

Stream 2 of the parallel PicoGUS audio-path investigation. Designed a
firmware-level silicon-differential oracle for PicoGUS v4.0.0 running on
live RP2040 silicon vs. `mdrp2040`. Delivered as HLD only (no
implementation). The oracle complements — does not replace —
`probe_diff_rp2040` (ISA-level per-instruction) and will serve as
post-fix validation for the PWM `EN`/`CSR.EN` aliasing bug Stream 1
identified, plus general integration coverage for similar-shaped
bugs.

HLD: `wrk_docs/2026.04.16 - HLD - PicoGUS Silicon Oracle.md`.

## Major design decisions

1. **Observables-level diff, not instruction-level.** Running
   ~30 MHz of emulated firmware one instruction at a time over SWD
   is impractical (weeks per oracle run at probe-rs's ~1 kHz step
   rate). The oracle samples at **sync points** — pre-declared
   trace-event indices where both sides halt and diff peripheral +
   pin state.
2. **Sync plans are committed fixture data, not regenerated
   per-run.** Frozen `.sync` CSVs alongside each trace. Removes a
   source of nondeterminism and makes the oracle reproducible.
   Regeneration is a separate `--regenerate-sync` offline command.
3. **I2S observation uses a spare PIO0 SM** (option (a) from the
   brief), not an external logic analyser. PicoGUS's ISA-tap uses
   PIO0 SM0-SM1 (from the firmware's `isa_io.pio`), so SM2 or SM3
   is free. Avoids a hardware dependency we can't confirm we have.
4. **PSRAM content diff is Phase 3, not MVP.** Readback requires a
   firmware-cooperative helper (hijacks core 0, mutates SM0
   scratch). MVP validates the PWM fix without PSRAM content — the
   PWM path is upstream of PSRAM anyway — and Phase 3 quantifies
   the helper's residual FIFO drift before committing to PSRAM
   content as a hard-diff observable.
5. **ISA replay is core-1-hosted in Phase 2+ and host-SWD-driven
   for MVP.** MVP's 5-event smoke doesn't need the core-1 driver;
   SWD writes at ~5 ms/event cover it. Phase 2's ~100-event
   traces need the core-1 driver for timing fidelity (300 ns IOW
   pulses — far below SWD latency). Separating MVP from full
   infrastructure unblocks the post-fix-validation story without
   gating on the driver's fidelity validation.
6. **No DWT CYCCNT** — M0+ doesn't have it. Use SysTick windows
   with soft assertion, matching `silicon_periph_diff_rp2040`'s
   convention (±5% tolerance on window width).
7. **First-divergence-per-category reporting.** Same shape as
   `CaseOutcome` in `silicon_oracle.rs`; category order is
   deterministic (DMA → PIO → PWM → NVIC → I2S → SysTick →
   PSRAM-Phase-3). Easy to read, easy to diff across runs.
8. **Ordered as oracle #13 in `CLAUDE.md` §Testing Topology.**
   Slots after `smoke_per_core_cyccnt_rp2350` (#12). Same gating
   language: requires probe + board, not for CI.

## Open questions

1. **Does the PicoGUS ISA-tap firmware's PIO program reserve SM2 /
   SM3?** HLD assumes not based on the firmware source referenced
   by the picogus_pins module doc; needs confirmation before Phase
   2. If firmware owns all 4 SMs on PIO0, the I2S edge-capture tap
   has to move to PIO1 SM2 / SM3 — that block is already used for
   PSRAM (SM0) and I2S output (SM3), so we'd need SM1 or SM2.
   Looks feasible from the pin map; needs a firmware source check.
2. **What's the acceptable overhead per sync point?** Estimated
   ~20 ms per-side (probe-rs halt + reads). A long-run (1-hour
   soak) at one sync point per 10 ms of trace would be 3.6M sync
   points → ~72 000 s = 20 h of overhead alone. If that's too
   much, sync points must be sparser or the readback batched into
   one big `read_8_bulk` per sync point.
3. **How load-bearing is the core-1 driver for Phase 2?** If
   probe-rs gets faster on the bulk read path (probe-rs 0.32
   lands with bulk MI?), host-SWD-driven ISA replay might
   actually be adequate for Phase 2. Revisit before committing
   Phase 2 asm.
4. **Should `picogus_silicon_diff_rp2040` share its binary name
   prefix with `picogus_diff_rp2040` or not?** Shared prefix
   (picogus_*) groups them in the harness dir; `silicon_` prefix
   groups it with the other probe-rs binaries. Current HLD uses
   `picogus_silicon_diff_rp2040` for both affinities — a bit
   verbose. Open to renaming to `silicon_picogus_diff_rp2040` if
   that reads better.
5. **Firmware "I'm alive" mailbox location.** HLD proposed using
   existing firmware landmarks (spinlock at `SIO+0x2A00..`, PIO
   TXFs) rather than patching firmware. That's the safe default,
   but a firmware-cooperative mailbox would be more direct. Defer
   to Phase 3.

## Assumptions to revisit

- **`probe_diff_rp2040` isn't broken** — the HLD references it as
  the ISA-level oracle. Haven't run it myself this session;
  trusting its published behaviour.
- **`mdpicoem-devices::I2sCapture` can cheaply expose a
  `snapshot()` accessor** — didn't read the full module, just
  confirmed it exists and tracks per-cycle pin state. If it only
  emits PCM and nothing else, the Phase 2 snapshot API is a
  non-trivial addition to that crate.
- **PicoGUS v4.0.0 flash image is what silicon will boot.** HLD
  assumes the firmware at `third_party/picogus/picogus-v4.0.0.bin`
  is the pinned target; this matches Stream 1's notes and the
  `VERSION` file.
- **RP2040 silicon actually implements per-core NVIC pending bits
  at `0xE000_E200` in the manner the HLD assumes.** `mdrp2040` models
  it that way; silicon is per-core per datasheet. Not personally
  verified on hardware — the existing `silicon_isr_diff_rp2040`
  presumably already exercises this.

   fixtures. Keep under `fixtures/picogus-stream2/pwm_smoke.*`.
   Generate the expected observables by running the fixture through
   the (post-fix) emulator and transcribing the resulting state at
   each sync point.

   probe attach, firmware load, MVP's SWD-bit-bang ISA driver, the
   5 observable read functions (DMA, PIO, PWM, NVIC, SysTick),
   diff formatter.
5. Validate the oracle FAILs on pre-fix `main` and PASSes on the
   branch with the PWM fix. This is the MVP exit criterion.
6. Only then start on Phase 2 (core-1 driver + I2S edge capture).
