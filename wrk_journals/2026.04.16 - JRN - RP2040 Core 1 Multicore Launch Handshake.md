# RP2040 Core 1 Multicore Launch Handshake — Sprint Journal

**Date:** 2026-04-16
**Team:** Supervisor (Claude Opus 4.6) + subagent specialists (research, Explore, implementer, code-reviewer, devil's advocate).
**Scope:** `crates/mdrp2040` only. `crates/mdrp2350/**` strictly off-limits (concurrent agent).

## Goal

Implement the pico-sdk `multicore_launch_core1` 6-word FIFO handshake in mdrp2040 so SDK-based RP2040 firmware can wake core 1 at the intended entry. Current placeholder at `lib.rs:514 maybe_wake_core1` wakes core 1 at its reset vector on any non-zero `SIO_FIFO_WR` push — close enough for a single-core wake test, wrong for any SDK-compliant firmware.

## Phases executed

### Phase 0 — Research

Dispatched a research subagent to transcribe both sides of the protocol with citations:
- pico-sdk 2.1.1 `src/rp2_common/pico_multicore/multicore.c:171-203` (sender `multicore_launch_core1_raw`).
- pico-bootrom-rp2040 b2 `bootrom/bootrom_rt0.S:313-391` (receiver `wait_for_vector`, `send_and_then`, `receive_and_check_zero`, `core1_launch`).

Sources saved to `wrk_scratch/multicore-research/` for implementer re-verification.

Sender sequence: `{0, 0, 1, vtor, sp, entry}`. On `cmd==0`, drain fifo_to_core0 + SEV before push; always push-blocking then pop-blocking; advance on `cmd == response`, else restart to seq=0.

Receiver in bootrom: drains its RX, sends literal 0, waits for non-zero word that must equal 1 (else restart), then echoes each received word while storing VTOR / MSP / entry, finishing with `blx r0`.

From sender's POV, steady-state echoes look like "receiver echoes the received word" for every slot — even though the bootrom's first send is a literal 0.

### Phase 1 — HLD authorship with team review (4 iterations)

HLD drafted by supervisor at `wrk_docs/2026.04.16 - HLD - RP2040 Core 1 Multicore Launch Handshake.md`. Three-reviewer team ran 3 rounds:
- **Reviewer A** — architecture / layering critic.
- **Reviewer B** — correctness / implementation critic.
- **Reviewer C** — devil's advocate.

Versions saved as `V1.md` through `V4.md` for traceability.

**Round 1 (V1 → V2)** fixed 7 significant issues:
- "FSM runs unconditionally" layering smell (A#1, C#4) — gated on core-1-halted.
- Drain-fifo-to-core1-at-wake wrong on restart paths (A#3, C#2) — switched to FSM-consumes, no push to fifo_to_core1 during handshake.
- `step_quantum=64` broke the timing argument (C#3) — rewritten against verified DEFAULT_STEP_QUANTUM.
- IPSR/xPSR.T/PRIMASK leak across T5 re-launch (C#10) — widened `reset_control_for_launch`.

**Round 2 (V2 → V3)** fixed a blocker B found:
- V2 cached `Bus.core1_halted` refreshed once per quantum; T1 writes via `mmio_write32` before first `step()` so stale `false` bypassed the FSM entirely. **Fix:** replace cache with `armed: bool` on `MulticoreHandshake`, default `true`, flipped synchronously at every halt/wake transition via `Emulator::halt_core1` / `wake_core1` wrappers. Closes both the pre-first-step hazard and C's mid-quantum-post-wake hazard in one change.

**Round 3 (V3 → V4)** caught a compilation blocker:
- `halt_core1`/`wake_core1` needed `pub` for integration tests in `crates/mdrp2040/tests/multicore.rs` to link. V3 left visibility unspecified.
- Clarified `reset_control_for_launch` runs in the launch consumer, not inside `wake_core1` (addressing C's misreading).

**Final convergence:** all three reviewers signed off on V4.

### Phase 2 — Implementation (TDD)

Implementer subagent delivered against V4:
- `crates/mdrp2040/src/bus/sio.rs` — `MulticoreHandshake`, `Core1Launch` (pub), FSM in `fifo_wr`, pub getters `is_handshake_armed` / `handshake_seq` / `take_pending_launch` / `set_handshake_armed`, FSM reset wired in `Sio::reset()`.
- `crates/mdrp2040/src/core/mod.rs` — `reset_control_for_launch()` resetting control / psp / xpsr (T=1) / primask. IPSR is the low 9 bits of xpsr; the `xpsr = 1<<24` write clears it by construction (no separate field).
- `crates/mdrp2040/src/lib.rs` — `pub halt_core1` / `wake_core1` wrappers; routed `Emulator::reset`, `direct_boot_from_flash`, `EmulatorBuilder::build` through the wrappers; `maybe_wake_core1` body replaced with launch consumer.
- `crates/mdrp2040/tests/multicore.rs` **(new)** — T1..T9 per HLD §3. Each test pins a `B .` self-loop at the target entry so post-wake PC asserts remain deterministic under single-step advancement.
- `crates/mdrp2040/tests/firmware.rs` — `core1_stays_halted_until_fifo_wake` rewritten to assert new handshake semantics (single non-zero push keeps core 1 halted; full 6-word sequence wakes correctly).
- Version: `mdrp2040` 0.11.1 → 0.12.0.

Deviations from HLD noted by implementer (both minor and mechanically faithful):
1. Tests plant a self-loop rather than asserting PC == `entry & !1` after `step()` (because the same `step()` that consumes `pending_launch` also runs one core-1 instruction, advancing PC past the entry).
2. IPSR reset is incidental via `xpsr = 1<<24`, not a separate field write.

### Phase 5 — Devil's advocate on landed code

Independent devil's advocate subagent probed the implementation (not the HLD) for races and drift paths. **No blocker bugs introduced by this PR.** Surfaced:

- **Pre-existing HardFault-lockup path** at `crates/mdrp2040/src/core/exceptions.rs:65, :130` sets `self.halted = true` directly without routing through `halt_core1`. If core 1 locks up, `armed` drifts false-ly, future handshake attempts bypass the FSM and leave words in `fifo_to_core1`. Not introduced by this sprint; worth a tech_debt note. Currently tests don't trigger it.
- **T5 doesn't verify R0..R12 preservation** across rehalt — doc-comment promises aren't tested. Nit.
- **Quantum>1 race analysis: clean.** `maybe_wake_core1` fires after every core-0 step, so `pending_launch` is consumed the same iteration it's emitted, and `wake_core1()` flips `armed=false` before any subsequent same-quantum write.

#### End-to-end smoke on real PicoGUS v4.0.0 firmware

Added a small diagnostic print to `picogus_diff_rp2040` summary: `Core 1 halted` + `Core 1 PC`. Re-ran per HLD §3.4 command.

**Result (zero stalls, firmware completes cleanly):**
```
=== picogus_diff_rp2040 summary ===
Events total:     19
Writes fired:     16
Reads skipped:    3
Duration capped:  false
Stall events:     0
Final sim time:   1500000 ns (0.002 s)
Post-roll:        250000000 cycles (2.000 s @ 125000000 Hz)
Final cycles:     250187501
Core 1 halted:    true
Core 1 PC:        0x100001f6
```

**Unexpected finding:** core 1 remains halted at its reset PC (0x100001f6 = flash+0x100). Handshake was never triggered by PicoGUS.

Diagnostic dive: temporarily added a `diag_fifo_wr` Cargo feature with an `eprintln!` in `Sio::fifo_wr` to log every FIFO write. Re-ran against real PicoGUS v4.0.0 through `picogus_probe_pc` for 5M steps (~2.6s sim time at 125 MHz). Core 0 reaches the SDK main idle loop at `0x2000d628` (`busy_wait_us_32` TIMER polling inside `while(true) { sleep_ms(100); }`) — consistent with the prior PicoGUS End-to-End Bring-up journal's Phase B observation. **Zero `[diag] fifo_wr core=0` lines in the entire trace.** Diagnostic feature reverted before commit.

**Conclusion:** PicoGUS v4.0.0 does not invoke `multicore_launch_core1` (nor `_raw` / `_with_stack`) during the first 2.6 seconds of runtime against `sample_gus.trace`. Core 0 completes full init, programs PIO1 SM0 and DMA channels (per prior probe), reaches the main idle loop, and enters the ISA-event-driven service loop — all without ever writing to `SIO_FIFO_WR`. PicoGUS either:
- Uses a different core-1 bring-up mechanism (e.g., raw VTOR/SP poke + direct entry — but we'd still observe SOME SIO FIFO traffic if it used any SDK multicore path), OR
- Is single-core for the mode selected by the default handshake (boot mode may vary per `pgusinit /mode x`), OR
- Waits for an ISA command in the trace that we don't provide (our `sample_gus.trace` has 19 events triggering pgusinit-style register probes only).

**Acceptance for this sprint:**
- Unit+integration: **PASS** — 536/536 green, including the full 9-test multicore suite that pins every invariant HLD §5 specifies.
- End-to-end smoke: **zero stall events** (strict acceptance criterion from prompt) ✓. Core-1-wakes (weak acceptance) **not observed** — but because PicoGUS doesn't exercise the launch path, not because of our implementation. The implementation is verified correct by T1-T9.

The deliverable (SDK-handshake-in-emulator) is complete and correct. The PicoGUS-specific wake question is downstream of this sprint and belongs to the PicoGUS End-to-End Bring-up Phase C or later.

## tech_debt.md updates landed

- **Struck:** "RP2040 core 1 SDK handshake not parsed".
- **Downgraded:** "PicoGUS: no I2S output" — was listed as three sequential blockers (TIMER → core-1 handshake → DMA). TIMER done in a prior sprint; core-1-handshake infrastructure now landed; **DMA remains**. But note: PicoGUS itself may not use the core-1 handshake we just built, so the "core-1 launch" gate line no longer cleanly applies to PicoGUS — only to *other* SDK firmware that does use it.
- **Added:** `entry & !1` silent Thumb-bit strip (mirrors existing `direct_boot_from_flash` convention). Silent on malformed entries.
- **Added:** SCR.SLEEPDEEP not cleared on core 1 wake (real bootrom `bootrom_rt0.S:367-368` clears it; we don't, matching `direct_boot_from_flash` scope).
- **Added:** SIO `addr & 0xFFF` mask lets atomic aliases hit unmapped offsets (`0xD000_2054` etc. reach `fifo_wr`). Pre-existing; not introduced by this sprint.
- **Added:** HardFault-lockup in `exceptions.rs` sets `halted=true` without routing through `Emulator::halt_core1`; can drift `sio.handshake.armed` on core-1 lockup (surfaced by Phase 5 devil's advocate).
