Reviewer: design-review (concurrency/correctness focus)

## Summary

V2 addresses Round 1's four CRITICAL items: AtomicU32 backing, cross-core
exclusive monitor, PPB moved to `CortexM33`, and atomicization of
`halted`/`wfe_waiting`/`event_flag`. It also swaps `std::sync::Barrier`
for a hand-rolled `SpinBarrier` and drops the `crossbeam` dependency in
favour of a hand-rolled SPSC ring.

A careful walk-through uncovers three remaining CRITICAL issues that are
not yet resolved, plus two IMPORTANT and two NICE-TO-HAVE issues. The
two that will bite hardest in real firmware are:

1. `fence(AcqRel)` is not strong enough for DMB. DMB on Armv8-M forbids
   store→load reordering; `fence(AcqRel)` in the Rust/C++ model does
   not. Dekker-style mutual exclusion breaks.
2. The exclusive monitor as described (Relaxed snoop, no fence between
   tag-set and LDREX load) has a tag-visibility race: a concurrent
   writer may miss the tag and leave the monitor valid across a
   conflicting write, so STREX returns success with a torn value.

The SpinBarrier itself is correct for 2 threads. The SharedMemory CAS
loop converges. Relaxed-everywhere-plus-AcqRel-fences is correct for
load-load / store-store / load-store but not store-load. Findings
below.

## ISSUE 1: DMB → fence(AcqRel) loses store-load ordering
**Severity:** CRITICAL
**Section:** §"Memory fence translation"
**Problem:**
Armv8-M DMB is a full memory barrier: it forbids reordering of ANY
memory access before the barrier with ANY memory access after, as
observed by other agents (ARM DDI 0553, §B7.4). That includes
store-load pairs.

Rust/C++11's `fence(AcqRel)` is *weaker* than `fence(SeqCst)` on
exactly one axis: store-load reordering. An `AcqRel` fence is both an
Acquire fence (no load-load reorder across) and a Release fence (no
store-store reorder and no load-store reorder across), but it does NOT
give the StoreLoad ordering that SeqCst provides. On x86 this is
visible in codegen: `fence(AcqRel)` emits nothing (TSO already gives
Load-Load / Load-Store / Store-Store); `fence(SeqCst)` emits `mfence`.
The absence of `mfence` lets the x86 store buffer reorder a prior
store past a subsequent load, which is exactly the reordering DMB
forbids on real M33.

Concrete breakage scenario (Dekker's algorithm; also realistic: any
"test-and-set then spin on peer flag" pattern, which pico-sdk's
multicore bootstrap and several RTOS idle hooks use):
```
Core 0:  *my_flag = 1; DMB; if (*their_flag == 0) { enter critical }
Core 1:  *their_flag = 1; DMB; if (*my_flag == 0) { enter critical }
```
Real M33: DMB orders my_flag=1 with subsequent load of their_flag.
At most one core sees the other's flag as 0. Mutual exclusion holds.

V2 emulator: fence(AcqRel) does not order the store with the load. On
x86 the prior store sits in the store buffer past the load; on aarch64
host the same holds. Both cores may observe the other's flag as 0 and
both enter the critical section.

This is the same bug Round 1's ISSUE 3 raised (recommending SeqCst),
marked IMPORTANT there. It remains unfixed in V2 and is worth a
CRITICAL bump because every piece of firmware that uses DMB assumes
store-load ordering from it.

**Proposed solution:**
- DMB → `fence(SeqCst)`.
- DSB → `fence(SeqCst)` (DSB has waits-for-completion semantics that
  the interpreter cannot emit, but SeqCst is strictly stronger than
  AcqRel and is the closest Rust can express).
- ISB → `fence(SeqCst)` (V2 already does this, good).

Cost on x86: one `mfence` per DMB execution. In paced_bench loops,
DMB frequency is low (only around spinlock/fifo/bootrom handshake) so
this is amortized fine. In tight spin loops that use DMB-heavy
patterns we may lose a few percent throughput; this is the cost of
correctness and is the same cost QEMU MTTCG pays.

Document explicitly: "DMB/DSB/ISB translate to SeqCst fences. This
is slightly stronger than DMB requires (DMB is equivalent to SeqCst
across matched fences on both sides anyway) but uniformly gives
Armv8-M-correct semantics."

## ISSUE 2: Exclusive monitor snoop is racy without Release-on-set / Acquire-on-snoop
**Severity:** CRITICAL
**Section:** §"Exclusive monitor (cross-core aware)"
**Problem:**
V2 describes:
- LDREX: writes `exclusive[core]` to the tagged address, then loads
  the value.
- On any write: reads `exclusive[other]`, clears if it matches.
- STREX: if `exclusive[self]` still matches, CAS the value and clear.

The HLD implies Relaxed for the snoop load ("one atomic load per
write") and does not specify ordering between tag-set and LDREX-load.
This admits a tag-visibility race.

Walk-through:
```
Core 0 LDREX X:
   T0: exclusive[0].store(X, Relaxed)
   T1: val = sram[X].load(Relaxed)

Core 1 STR X (concurrent):
   U0: sram[X].store(new, Relaxed)
   U1: if exclusive[0].load(Relaxed) == X { exclusive[0].store(0) }
```

Under a weakly-ordered host model (even x86 allows some store-load
reorder between independent addresses via the store buffer; aarch64
allows more), the Relaxed ops on different addresses have no
interthread ordering.

Bad interleaving:
- Core 1 does U1 before Core 0's T0 is visible to Core 1's cache:
  Core 1 sees `exclusive[0] == 0`, does nothing.
- Core 1 does U0: sram[X] = new.
- Core 0 does T1: sees the new value (or, with Relaxed, possibly the
  old value — single-copy-atomic guarantees non-torn, not fresh).
- Core 0 does STREX X: checks `exclusive[0]` == X (still tagged from
  T0), finds its own tag, succeeds. Writes Core 0's computed value.

Result: both Core 0 and Core 1 issued "atomic updates" to X; Core 0's
STREX succeeded on stale data. Software spinlock double-acquire, RMW
race on shared counter, pico-sdk multicore bootstrap state corruption.
This is precisely the class of bug LDREX/STREX exist to prevent.

Contrast with real M33: the hardware monitor tagging is coherent with
the memory subsystem; a STR from Core 1 that hits Core 0's tagged
granule clears Core 0's monitor before or simultaneously with the
write becoming visible. STREX on Core 0 then fails and loops.

**Proposed solution:**
Two fixes in combination:

(a) Tag-set and LDREX-load must be ordered on the issuing core:
```rust
// LDREX X:
self.exclusive[core].store(tag(X), Release);  // publish the tag
fence(Acquire);                                // prevent subsequent
                                               // load from reordering
                                               // backwards (belt-and-braces)
let val = sram[word_idx].load(Acquire);        // or Relaxed + fence
```

(b) Write path must Acquire the tag before/during the write:
```rust
// on any shared write at addr:
sram[word_idx].store(new, Release);           // make write visible
for peer in 0..2 {
    // Acquire pairs with (a)'s Release, so if peer tagged before
    // our write, we see the tag and can invalidate.
    let peer_tag = exclusive[peer].load(Acquire);
    if peer_tag == tag(addr) {
        let _ = exclusive[peer].compare_exchange(
            peer_tag, 0, AcqRel, Relaxed);
    }
}
```

This gives: if peer did LDREX before our STR globally-ordered, the
tag is visible (Release-Acquire). If our STR happened first, peer's
subsequent LDREX sees a value that is consistent with having written;
peer's STREX value-CAS must then use Acquire on the word load, which
pairs with our Release store, so peer's CAS either succeeds on the
new value or sees the value changed and retries. Either way, no
stale-data STREX-success.

Alternatively and simpler: make the exclusive state `AtomicU32` with
`AcqRel` on all operations (Release on set/clear, Acquire on the
snoop). Pay the Acquire fence cost on every shared-memory write.
Measure.

Either way, V2's "Relaxed snoop, one branch" is not safe.

## ISSUE 3: WFI in threaded mode has no specified wake path — deadlock risk
**Severity:** CRITICAL
**Section:** §"Thread topology", §"Implementation phases" (not addressed)
**Problem:**
V2 does not specify what a worker does when its core executes WFI
(Wait-For-Interrupt). Three plausible implementations, all broken in
different ways:

Option A — spin-skip: worker detects WFI, treats remaining quantum
cycles as a no-op, arrives at barrier. Worker 0's coordinator work
ticks MTIME, checks pending interrupts, sets per-core interrupt-
pending flag. Next quantum, worker sees flag, exits WFI.

Option A works IF the coordinator can advance MTIME and deliver the
only interrupts the WFI-waiting core cares about. It fails for
firmware that WFIs waiting for a GPIO edge or a UART RX IRQ — those
come from the peripheral mutex side, not the coordinator. Worker 0
doing the coordinator work is not monitoring peripheral state for
Core 1's wake. Firmware hangs indefinitely: both workers hit WFI,
both hit barrier, worker 0's coordinator advances MTIME past any
MTIMECMP without a hit, never exits. In single-threaded today we
also hang, but the user's stop signal or Ctrl-C reaches the single
loop. In threaded we must ensure the stop signal is checked each
quantum (V2 does — good) so the hang is at least killable.

Option B — park-worker: worker uses `std::thread::park` on WFI and
relies on another thread to `unpark`. If Core 0 is parked and Core 1
needs to exit its own WFI, Core 1 must call `core0.unpark()` from
inside its worker — but that crosses thread boundaries and requires
an Arc<Thread>. Worse, Core 0 parked means Core 0 never reaches the
barrier. **Barrier deadlock**: worker 1 finishes its quantum, waits
at barrier, worker 0 is parked forever waiting for an event that no
one will deliver because the coordinator work happens on worker 0
itself. Deadlock.

Option C — worker 1 WFI wakes only from coordinator on worker 0:
specify that peripheral model runs on worker 0 during coordinator
phase, sets interrupt flags for both cores, then both workers
unblock. Same as Option A with a loose timing guarantee. Acceptable,
but MUST be specified.

The current HLD does not pick one. This needs to be explicit because:
- Peripheral models run on the main thread (per V2's sharded mutexes
  implying access from either worker), not on worker 0 alone.
- If a peripheral model on worker 1 raises an interrupt to Core 0,
  worker 0 must observe it; the observation point is the worker-0
  inner loop, which is busy executing Core 0 until WFI.
- On WFI, worker 0 must poll shared interrupt state until wake, which
  means worker 0 still hits the barrier each quantum. This is
  Option A.

**Proposed solution:**
Specify Option A explicitly:
- WFI sets `halted = true` on the worker's CortexM33 (already atomic
  per V2).
- Worker's inner loop: if halted, skip to end of quantum (cycle
  counting advances, but no decode/execute).
- Worker hits barrier as normal.
- Cross-core event handling (on worker 0, between quanta) checks:
  (a) peripheral model pending interrupts, (b) MTIME compare match,
  (c) SEV/doorbell/FIFO events. For each core with a pending
  interrupt, clear its `halted` atomic.
- Next quantum: worker sees `halted == false`, resumes normal step.

Document the latency: WFI wake takes up to 1 quantum (typically
1 µs at Q=150). This matches the accuracy trade-off V2 already
accepted.

Add an explicit deadlock guard: if the coordinator sees both workers
halted for N consecutive quanta AND no pending-interrupt sources are
ticking (MTIME disabled, no peripheral activity), log a warning and
break. Do not hang indefinitely. This is a useful "firmware bug"
signal rather than a "our emulator is deadlocking" footgun.

## ISSUE 4: write16 CAS loop not shown; u16/u32 mis-alignment handling unspecified
**Severity:** IMPORTANT
**Section:** §"Shared memory: AtomicU32 backing"
**Problem:**
V2 shows `write8` as a CAS loop but omits `write16`. `write16` is
essential — plenty of firmware does 16-bit stores to peripheral and
shared memory. For an aligned u16 write (`addr & 2 == 0 or 2`), the
u16 occupies one half of a word; the other half must be preserved.
Same CAS-on-word pattern needed. Easy fix — spell it out.

More importantly: what about **misaligned** u16/u32 access? Armv8-M
can take a UsageFault if CCR.UNALIGN_TRP is set. If unset (default
boot state on M33), it splits into multiple accesses at the bus
fabric level. Our current `Bus::read32` / `write32` split the
address into two word accesses for misaligned cases. V2's SharedMemory
operates on `(addr >> 2)` indices with no misalignment path shown.

Concretely:
- `read32(addr)` with addr&3 != 0: V2 shows `sram[(addr >> 2)]`. That
  ignores the low 2 bits entirely and loads a single aligned word,
  giving garbage semantics.
- `write32(addr, val)` at addr=0x1001: hits the wrong word.

Cortex-M33 actually faults on misaligned u32 by default (CCR.UNALIGN_TRP
can be cleared, but at reset it is set — pg B3-614 of the ARMv8-M
ARM). Still, `read16`/`write16` at odd addresses is trickier: half
byte in one word, half in another; must atomic-CAS twice if crossing
a word boundary.

**Proposed solution:**
- Spell out `write16`:
```rust
pub fn write16(&self, addr: u32, val: u16) {
    debug_assert_eq!(addr & 1, 0, "misaligned u16 not supported");
    let word_idx = (addr >> 2) as usize;
    let shift = (addr & 2) * 8;
    let mask = 0xFFFFu32 << shift;
    let new_half = (val as u32) << shift;
    let mut current = self.sram[word_idx].load(Relaxed);
    loop {
        let desired = (current & !mask) | new_half;
        match self.sram[word_idx].compare_exchange_weak(
            current, desired, Relaxed, Relaxed
        ) {
            Ok(_) => return,
            Err(actual) => current = actual,
        }
    }
}
```
- Explicitly document: u16/u32 must be naturally aligned; misaligned
  accesses raise UsageFault before reaching SharedMemory. Route
  alignment check through the existing CCR-driven path on CortexM33.
- Unaligned bytes / u16 crossing a u32 boundary: two CAS loops on
  adjacent words. Not atomic across the two halves — this is
  consistent with Armv8-M, which does not require atomicity for
  misaligned accesses.

## ISSUE 5: Byte-write CAS is an artificial RMW; masks genuine firmware race on a byte's worth
**Severity:** NICE-TO-HAVE
**Section:** §"Shared memory: AtomicU32 backing"
**Problem:**
Real Cortex-M33: two cores concurrently issuing `STRB [a], r0` and
`STR [a&~3], r1` observe a bus-fabric-level race where the winning
byte is undefined. Firmware doing this has a race bug and will see
non-deterministic results.

V2 emulator with CAS loop:
- write32 = single atomic store (Relaxed).
- write8 = CAS loop that merges the byte with the current word.

Interleaving: write32 lands first, then write8's CAS sees the new
word, merges its byte, writes. Result: byte comes from the write8,
other bytes come from write32.

Reverse interleaving: write8's CAS loads, computes, CAS; write32
happens after. CAS may have succeeded before write32, then write32
stomps the whole word. Result: all 4 bytes from write32.

So the emulator presents a specific deterministic resolution that
real HW does not guarantee. This is not a correctness bug per se —
firmware that relies on one ordering over the other has a race on
real HW too — but it means the emulator may "pass" for buggy
firmware that happens to work under our resolution and fail in the
field on real silicon.

**Proposed solution:**
This is fine for now. Document in the HLD: "u8/u16 writes use CAS
loops and present a deterministic resolution under byte-vs-word
concurrent write. Real hardware's resolution is bus-fabric-dependent
and non-deterministic. Firmware that races byte and word writes to
the same granule has a race bug either way; the emulator's
deterministic resolution should not be relied on." If anyone complains
later, consider randomizing the CAS loop delay in debug builds to
surface firmware races.

## ISSUE 6: SIO "sides" naming invites consumer-on-producer-side confusion
**Severity:** NICE-TO-HAVE
**Section:** §"SIO: threaded-only redesign"
**Problem:**
V2's `fifo_01` and `fifo_10` names are convention-dependent. "01" is
ambiguous: "producer=0, consumer=1" (intended) vs. "FIFO between 0
and 1" (symmetric reading). Existing Sio code uses the clearer
`fifo_to_core1` and `fifo_to_core0`. With `01`, a reviewer asks (as
this review's brief did): "what if Core 0 reads `fifo_01` which is
its own input?" It isn't — Core 0's input is `fifo_10` (Core 1 to
Core 0) — but the name invites the mistake.

Worse, if Phase 2 implementation accidentally uses `fifo_01` for
Core 0's RX path, the SPSC ring becomes MPMC (two producers / two
consumers on one ring) and the lock-free guarantees evaporate.

**Proposed solution:**
Rename to match the existing, clearer convention:
```rust
pub struct ThreadedSio {
    fifo_to_core1: SpscRing<u32, 8>,  // c0 produces, c1 consumes
    fifo_to_core0: SpscRing<u32, 8>,  // c1 produces, c0 consumes
    ...
}
```
Document at the top of the file: "Each FIFO is strict SPSC. Core N's
only interactions: push to `fifo_to_core_OTHER` via FIFO_WR, pop from
`fifo_to_core_N` via FIFO_RD. Any other access pattern breaks the
SPSC invariant." Add debug_assert guards on the push/pop methods
that check the producer/consumer core id if we can thread it through
cheaply.

Additionally: confirm in the type definition that `SpscRing` has
`Sync` but pushes only accept `&self` from the "producer side" and
pops only accept `&self` from the "consumer side". Hand-rolled SPSC
typically uses `UnsafeCell` for the buffer; encapsulate so the
wrong-side call is a compile error, not a runtime footgun.

## ISSUE 7: Coordinator/worker-0 fold — exclusive monitor + pending events not cleared on into_threaded/into_emulator
**Severity:** IMPORTANT
**Section:** §"API: two types, one conversion", §"Implementation phases" (not addressed)
**Problem:**
V2 describes `into_threaded(self) -> ThreadedEmulator` and
`into_emulator(self) -> Emulator` as state-preserving moves. State
preservation is generally correct, but three categories of state
have different semantics across a mode boundary:

1. **Exclusive monitor** (`exclusive_address` per CortexM33): the
   monitor is a hardware-physical property tied to the live execution
   context. Armv8-M clears it on exception entry, context switch, or
   any "barrier event". Handing an `Emulator` off to a
   `ThreadedEmulator` and back is equivalent to a context switch —
   the monitor must be cleared on transition. Otherwise, firmware
   mid-LDREX/STREX pair at the transition point resumes with a
   potentially-invalid tag and a STREX that succeeds or fails
   inconsistently.

2. **Pending SIO events** (`pending_fifo_event`, doorbells,
   `mtime_match_asserted`): these are edge-triggered. If
   `into_threaded` is called with a pending but not-yet-delivered
   FIFO event, the event must be preserved. V2 is silent.

3. **In-flight RMW / stall_cycles**: if the source Emulator was
   mid-instruction (single-threaded steps are atomic at the
   instruction boundary, so this shouldn't happen), we're fine. But
   confirm that `into_threaded` can only be called between
   instructions — the type signature (by-value `self`) already
   implies this, but it's worth stating.

**Proposed solution:**
Specify in V2:
- `into_threaded`:
  - Clear `exclusive_address` on both cores.
  - Preserve all pending SIO events; document that quantum 0 of
    threaded mode will drain them via the coordinator.
  - Assert that the source Emulator is not mid-step (i.e., that the
    last `run()` returned normally, not via panic-catch).
- `into_emulator`:
  - Clear `exclusive_address` on both cores (same justification).
  - Clear `wfe_waiting` (edge-triggered — the WFE that was pending
    was pending in threaded-mode semantics; single-threaded re-enters
    WFE next step if still needed).
  - Preserve `halted`, `event_flag`, SIO state.
  - Assert worker threads have joined (Arc::strong_count check).

Add a test: round-trip emulator through `into_threaded().into_emulator()`
mid-execution and verify that firmware runs identically to the
single-threaded baseline (except for cycle-count drift during the
threaded window).

## ISSUE 8: SpinBarrier generation.store(Release) + count.store(Relaxed) ordering edge case
**Severity:** NICE-TO-HAVE
**Section:** §"Custom spin-barrier (not std::sync::Barrier)"
**Problem:**
Walking the barrier carefully for 2-thread correctness, the code is
sound. One micro-concern:

```rust
if n == 2 {
    self.count.store(0, Relaxed);                        // (a)
    self.generation.store(my_gen.wrapping_add(1), Release); // (b)
}
```

(a) is Relaxed. (b) is Release. On the releaser's thread, (a) is
program-ordered before (b), so by single-thread reasoning (a) happens
before (b). On another thread doing the next-pass Acquire read of
generation and then Acquire fetch_add of count: the release-acquire
chain orders (b) with the other thread's load; (a)'s reset-to-0
piggy-backs on (b)'s Release via the sequenced-before relation.

So semantically fine. But it is a subtle point that depends on the
"Release fence carries program-order-prior Relaxed writes" rule. A
future refactor that reorders (a) and (b), or adds another Relaxed
write between fetch_add and the store, could break silently.

More substantively: for N-thread generalization (we have 2 threads
now, but the code is written generically), the `if n == N` check is
needed and the Relaxed `count.store(0)` must happen before the
Release `generation.store`. A future version where someone extends
this to 3+ threads could easily flip the order.

**Proposed solution:**
- Inline-comment the ordering constraint: `// MUST reset count
  before publishing generation; the Release store below publishes
  both writes as a pair. Reordering breaks the barrier.`
- Use `fetch_add(1, AcqRel)` on the count path (already the case) but
  consider `swap(0, Release)` rather than `store(0, Relaxed)` +
  `store(gen, Release)` — one atomic op instead of two. Micro-opt.
- Add a loom test for the barrier. V2 §"Validation strategy" already
  lists this. Don't ship threaded mode without it.

## ISSUE 9: Cross-core writes to CortexM33 fields during coordinator phase
**Severity:** IMPORTANT
**Section:** §"Thread topology", §"Interrupt dispatch" (not addressed)
**Problem:**
V2 folds the coordinator into worker 0. Between barriers, worker 0
"handles cross-core events". Concretely, what does "cross-core events"
include?
- Timer/MTIME tick + compare-match dispatch.
- WFI/WFE wake on event delivery.
- Draining `pending_fifo_event` and setting the receiver's
  `event_flag`.
- Delivering pending NVIC interrupts to each core.

All of these involve worker 0 **writing to state that worker 1 owns
during its quantum**: worker 1's CortexM33 (`halted`, `wfe_waiting`,
NVIC pending bits, exception_pending). V2 atomizes `halted`,
`wfe_waiting`, `event_flag` — good. But NVIC pending bits live in
the PPB (now per-core on CortexM33 per V2's refactor). If worker 0
writes `core1.ppb.nvic_iser[x]` during coordinator phase, that is a
cross-thread write to a struct that is otherwise only touched by
worker 1 during its quantum. The quantum has ended (barrier 1), so
worker 1 is at barrier 2 waiting — no concurrent read. OK in
principle. But **PPB fields must be atomic where cross-core writes
happen**.

Specifically:
- NVIC pending (set by coordinator when a peripheral raises an IRQ).
- VTOR: per-core, written only by its owner — plain u32 is fine.
- CPACR (FPU enable): per-core, plain u32 is fine.
- MPU regs: per-core, plain — fine.

The single issue is **NVIC pending**: coordinator writes, worker
reads next quantum. Needs AtomicU64 (64 IRQs on RP2350) with
Release/Acquire.

**Proposed solution:**
Add to the Phase 0b prerequisite-refactor list:
- NVIC pending bits: `AtomicU64` (per core, on CortexM33.ppb).
- NVIC iser/icer: AtomicU64 if readable from other side; otherwise
  plain — audit. Coordinator might read enable mask to decide
  delivery.
- SCB ICSR.VECTPENDING: updated by coordinator, read by worker.
  Atomic.
- Any other PPB field that coordinator modifies on behalf of the
  target core.

Also: barrier 2 provides the Release-Acquire on `generation` that
publishes all of worker 0's coordinator-phase writes to worker 1
when worker 1 resumes. So Relaxed atomics in the PPB would suffice,
piggy-backing on the barrier's Release. But this tightly couples
correctness to the barrier topology. Prefer Release/Acquire on the
PPB atomics directly — robust to future topology changes, and
essentially free on x86.

## Overall assessment

V2 is a substantial improvement over V1 and correctly addresses the
four CRITICAL items from Round 1. The remaining CRITICAL issues
(DMB strength, exclusive monitor tag-visibility, WFI-in-threaded-mode
semantics) are all precisely specifiable and fixable without architectural
upheaval. None require restructuring the coordinator-folded-into-worker-0
design or the SharedMemory backing.

Recommended next revision (v2.1):
- Fix ISSUE 1 (DMB → SeqCst) and ISSUE 2 (monitor Release/Acquire) as
  correctness-critical in-text changes.
- Specify ISSUE 3 (WFI semantics) in §"Thread topology" — this is the
  biggest unspecified behavior.
- Spell out `write16` (ISSUE 4), rename `fifo_0N` to `fifo_to_coreN`
  (ISSUE 6), document mode-transition clearing (ISSUE 7), add NVIC-
  pending atomics to prerequisites (ISSUE 9).
- Add loom tests for SpinBarrier and SpscRing (ISSUE 8, already
  implicit in V2's validation strategy — make it explicit that these
  tests block Phase 2 / Phase 3 from merging).

After v2.1 I would un-block the HLD and recommend proceeding to
Phase 0a (workload validation) as the gate on all subsequent work.
