## Starting state (supervisor-probed 2026-04-16)

Real PicoGUS v4.0.0 firmware under `picogus_diff_rp2040`:
- Boots cleanly, 0 stall events across 6.6 G sysclks (100 M steps).
- Core 0 parks forever at SRAM `0x20012ba6`.
- Disassembly matches pico-sdk `adc_init`:
  ```
  0x20012ba2: STR  R1, [R2]       ; ADC_CS = EN
  0x20012ba4: MOVS R1, #0x80
  0x20012ba6: LSLS R1, R1, #1     ; R1 = 0x100 (CS_READY mask)  <-- PC sampled here
  0x20012ba8: LDR  R3, [R2]
  0x20012baa: TST  R3, R1
  0x20012bac: BEQ  0x20012ba8     ; loop until READY
  ```
- `R2=0x4004c000` (ADC_BASE), `R1=0x100` (READY mask), `R3=0x00000001`
  (EN set, READY clear). Core 1 halted at reset PC.
- All PIO SMs disabled, DMA channels zero, I2S pins dormant — firmware
  never reached audio bring-up.

Root cause: `crates/mdrp2040/src/peripherals/adc.rs` only sets
`CS_READY` inside `complete_conversion`. SDK's `adc_init()` writes EN
without a START bit and spins on READY. Real silicon asserts READY
after ADC power-up (~200 µs); we never assert it. Phase 3 test corpus
covered the conversion flow but not this init gate.

`sys_clk_hz` reads 370 MHz, which is correct (PicoGUS overclocks).

### Phase B — Diagnose post-ADC stall

**Status:** complete. Full report: `wrk_scratch/phase-b-diagnosis.md`.

**Input hypothesis (HYP-IDLE):** firmware is in `while(true)
sleep_ms(100)` because it called `multicore_launch_core1(...)` and is
waiting for core 1 to service ISA; core 1 stays halted because our
`maybe_wake_core1` placeholder doesn't parse the SDK handshake.

**Verdict: PARTIALLY REFUTED.** Step (a) holds — core 0 is in the
sleep loop at a function tail-called from `0x20002220`. Step (b) is
WRONG — firmware **never writes to SIO_FIFO_WR** (`0xD0000054`).
mmio_trace over 150M cycles: zero FIFO writes. The SDK's 6-word
handshake is never attempted.

**Critical implication:** the concurrent core-1 multicore_launch
handshake team's work is **no longer the next blocker**. (Still worth
completing for correctness, but not on the critical path to audio.)

**What firmware actually does (from trace + disassembly):**
- Function at `~0x200021EA` sets up PIO1 + DMA CH0/CH1 + spinlock
  descriptor at `0x2001D32C`.
- BL's into `0x2000_160C` (the `while(1) sleep_ms(100)` wrapper) at
  `0x20002220`.
- Never returns.

Likely candidates for what this function is:
1. PicoGUS `test_psram()` auto-detect — fails against our PSRAM model,
   returns with an "error" idle state.
2. PicoGUS v4.0.0 main architecture may be IRQ-driven on core 0 (no
   core-1 task), with the infinite sleep being main's intentional idle.
3. A pico-sdk `runtime_init` hook that was supposed to chain into more
   init but didn't.

**Secondary findings:**
- `target/release/mmio_trace_rp2040.exe` was stale at start of
  diagnosis — supervisor note: always force-rebuild after a code
  change on Windows, `--touch` the source or `cargo clean -p` the bin
  crate.
- PIO1 INSTR_MEM read-as-zero is architectural per datasheet §3.7
  (write-only registers). Not a bug. Our model matches silicon at
  `mdpicoem-common/src/pio/mod.rs:334`.
- ADC Phase A fix is CONFIRMED working from trace — fewer than 250
  accesses to any PC in `0x20012B??` range across 150M cycles.

**Next phase:** identify function at `0x200021EA` against upstream
PicoGUS source; confirm architecture (single-core vs dual-core
vs IRQ-on-core-0); determine actual blocker for audio output.

### Phase C — Identify function at `0x200021EA` + PicoGUS architecture

**Status:** complete. Full report: `wrk_scratch/phase-c-architecture.md`.

**Key findings:**
1. PicoGUS v4.0.0 (GUS variant) is **dual-core, IRQ-driven**.
   `multicore_launch_core1(&play_gus)` IS in firmware (12 hits at
   flash `0x1001A6E8`). Core 1 runs voice synth + PSRAM.
2. Function at `0x200021EA` is mid-`main()`. Firmware traps BEFORE
   the multicore launch because **`test_psram()` returns failure** →
   `err_blink()` parks forever.
3. `test_psram` writes 1 MB via `DMA_SIZE_8` writes to PIO1 TXF0,
   reads back via `DMA_SIZE_8` reads from PIO1 RXF0. Reads return 0.

### Phase D — PIO narrow-write dispatch fix

**Status:** HLD signed off; implementer dispatched.

HLD: `wrk_docs/2026.04.16 - HLD - mdrp2040 PSRAM test_psram Compatibility.md`.

**Root cause 1 — PIO narrow-write drop:** `Bus::write8`
(bus/mod.rs:1078) blanket-drops ALL byte-width writes to PIO
registers, including TXF0. Since rp2040-psram uses `DMA_SIZE_8`
writes to PIO1 TXF0, every DMA transfer is silently lost.
Fix: add PIO TXF0-3 dispatch with ARM AHB byte-replication.

**Root cause 2 — DMA AL1 trigger missing:** `CH_AL1_TRANS_COUNT`
(offset 0x1C) is the Alias 1 trigger register per RP2040 §2.5.7, but
our `channel_write32` grouped it with non-trigger TRANS_COUNT arms.
Firmware writes to `al1_transfer_count_trig` to start DMA, so channels
never triggered despite being configured. Fix: move to trigger arm.

Both fixes are required — PIO narrow-write lets bytes reach TXF, DMA
trigger lets DMA actually fire.

**Supervisor verification:** after both fixes, firmware PC advances
from `err_blink` into `test_psram` at `0x200130f8`. test_psram runs
but takes ~1 hour wall time (38G cycles for 1 MB at PIO clkdiv=474).

**Committed as `699a047`.**

### Phase E — SRAM patch + first WAV capture

**Status:** MILESTONE ACHIEVED.

test_psram is correct but takes ~1 hour. Applied a runtime SRAM patch
(write `MOVS R0, #0; BX LR` at 0x20012FA4 after .data copy) to both
`picogus_probe_pc` and `picogus_diff_rp2040`. test_psram returns 0
immediately; firmware proceeds past PSRAM init.

**Results with SRAM-patched firmware:**
- **Core 1 launched** (`halted1=false`). `maybe_wake_core1` placeholder
  worked — any non-zero FIFO push from core 0 woke core 1.

- **PIO1 SM0** (PSRAM SPI) + **PIO1 SM3** active.
- **I2S pins output-enabled:** BCLK(17), LRCLK(18), DOUT(16) all
