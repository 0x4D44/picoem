## Starting state (supervisor-probed 2026-04-16)

Real PicoGUS v4.0.0 firmware under `picogus_diff_rp2040`:
- Boots cleanly, 0 stall events across 6.6 G sysclks (100 M steps).
- Core 0 parks forever at SRAM `0x20012ba6`.
- Disassembly matches pico-sdk `adc_init`:
  ```
  0x20012ba2: STR  R1, [R2]       ; ADC_CS = EN
  0x20012ba4: MOVS R1, #0x80
  0x20012ba6: LSLS R1, R1, #1     ; R1 = 0x100 (CS_READY mask)  <-- PC sampled here
  0x20012ba8: LDR  R3, [R2]
  0x20012baa: TST  R3, R1
  0x20012bac: BEQ  0x20012ba8     ; loop until READY
  ```
- `R2=0x4004c000` (ADC_BASE), `R1=0x100` (READY mask), `R3=0x00000001`
  (EN set, READY clear). Core 1 halted at reset PC.
- All PIO SMs disabled, DMA channels zero, I2S pins dormant — firmware
  never reached audio bring-up.

Root cause: `crates/mdrp2040/src/peripherals/adc.rs` only sets
`CS_READY` inside `complete_conversion`. SDK's `adc_init()` writes EN
without a START bit and spins on READY. Real silicon asserts READY
after ADC power-up (~200 µs); we never assert it. Phase 3 test corpus
covered the conversion flow but not this init gate.

`sys_clk_hz` reads 370 MHz, which is correct (PicoGUS overclocks).

## Phase log

### Phase A — ADC CS.READY init-gate fix

**Status:** HLD signed off; implementer dispatched.

HLD: `wrk_docs/2026.04.16 - HLD - mdrp2040 ADC READY Init Gate.md`.

HLD review turns (supervisor):
- **Round 1** — design agent chose Option A (synchronous latch on EN 0→1
  in `write32(CS)`). Reasoning solid; §3 §4 cleanly rule out Option B
  (fast-path gate would leave `Adc::tick` uncalled during `adc_init()`'s
  spin) and Option C (no silicon oracle for power-up delay, would force
  retuning Phase 3 tests). Accepted §5 (EN 1→0 clears READY) and §6
  (mid-conversion EN clear aborts) as defensive symmetry.
- **Round 2 — clarifications requested:** (a) integration-test success
  mechanism (BKPT on ARMv6-M escalates to HardFault with no vector
  table installed — ambiguous). (b) concrete regression sweep, not a
  hand-wave.
- **Round 2 — applied:** (a) `B .` sentinel at `0x2000_0010`, matching
  `gpio_blink_program_drives_pin0_high` idiom at `tests/firmware.rs:12`.
  (b) 21-test audit table: zero existing assertions need updating;
  latch-then-`maybe_start`-clear ordering preserves all Phase 3 end
  states. **Signoff.**

Scope summary:
- Only file changed: `crates/mdrp2040/src/peripherals/adc.rs` + its
  tests + `crates/mdrp2040/tests/firmware.rs` + version bump.
- Explicitly not touched: `lib.rs`, `bus/sio.rs`, any mdrp2350 file.

**Implementation** landed: `adc.rs` `write32(CS)` gained EN 0→1 synchronous
READY latch, EN 1→0 clear, and mid-conversion abort. 6 new unit tests
+ 1 new integration test (`adc_init_sdk_pattern_exits_ready_poll`).
`mdrp2040` 0.11.0 → 0.11.1. 522 tests green, zero warnings.

**Code review:** ACCEPT. Full review at `wrk_scratch/phase-a-adc-review.md`.
Zero MUST-FIX, zero SHOULD-FIX. Two cosmetic nits explicitly marked
"no action needed". No apply-feedback cycle required.

**Supervisor verification (HLD Acceptance C):** passed. Re-ran
`picogus_probe_pc` against real v4.0.0 firmware — core 0 PC moves from
the ADC-init stall at `0x20012ba6` to a **new** site at `0x2000d628`
(TIMER polling loop). Firmware advanced clean through ADC init.

**New observations surfaced by the re-probe (Phase B input):**
- Core 0 now parks in pico-sdk's `busy_wait_us_32` loop reading
  TIMERAWL. Caller LR = `0x20001615`, pointing at a `B .` that wraps
  back to `MOVS R0, #100; BL busy_wait_ms` — i.e. `while(true) {
  sleep_ms(100); }`. Looks like PicoGUS's main idle loop.
- **PIO1 SM0 is now enabled and running** (CTRL=0x1, SM0 active,
  clkdiv=0x1da00). PIO0 still idle.
- **DMA CH0 programmed** to transfer from flash `0x20016acc` → PIO1
  TXF0 (`0x50300010`), TRANS=7 — a short transfer. **DMA CH1**
  programmed from PIO1 RXF0 (`0x50300020`) → SRAM `0x20041e74`,
  TRANS=1.
- PIO1 INSTR_MEM reads all zeros despite SM0 running an `instr=0x105a`
  — suggests the INSTR_MEM read path via MMIO isn't mirroring writes
  correctly (secondary — not a Phase-A regression, pre-existing).
- Core 1 still halted at reset PC (consistent with the concurrent
  core-1 team's blocker being the actual next gate).
