## §6 — The WorkerBus monomorphization misconception

Before Stage 8 we hypothesised that a large fraction of the remaining gap was a monomorphization artifact: functions generic over `CoreBus` (e.g. `CortexM33::step_no_atomics<B: CoreBus>`) supposedly record separate branch counters per `B` instantiation (`Bus` vs `WorkerBus`). The Stage 8a agent added 99 WorkerBus-backed smoke tests specifically to exercise the `WorkerBus` mono of paths already covered via `Bus`.

**The hypothesis was wrong.** `cargo llvm-cov --branch` (the unstable `--branch` flag) aggregates branches across monomorphizations — it reports source-level control flow, not LLVM IR basic-block edges. The 99 WorkerBus smokes increased mdrp2350 branch coverage by **only 6 branches** (89.72% → 89.90%), and those 6 were genuinely `WorkerBus`-unique (held-in-reset narrow FIFO arms in `threaded/bus.rs`, which jumped from 90.9% to 97%).

The 333 residual uncovered branches in `mdrp2350` library files are therefore **real source-level gaps** in specialised paths: SSAT/USAT saturation variants, VFP edge flags (IXC/IOC/UFC/OFC/DZC combinations), STKOF/SPLIMVIOL stack-limit faults, unmapped-MMIO arms reached only via specific address patterns, and similar narrow-scope corners. Closing them requires a targeted test per path, not a bulk sweep.

## §7 — Why we stopped short of 98%

Three categories of blocker:

1. **Architectural ceilings** (documented inline in commits):
   - `mdrp2350/peripherals/i2c.rs` at 61.54% — 20 missed branches in the ACK-read/write arms. `ALWAYS_ACK_ADDRS` is empty-set by design (see the peripheral's "Bus-scan ACK model" comment); populating it would change behaviour. 20 branches unreachable.
   - `mdrp2350/peripherals/i2c.rs` / `spi.rs` / `uart.rs` / other peripherals — collectively ~40 branches guarded by `debug_assert!`, tautological `&&` short-circuits against hardware-bounded fields (e.g. `shift>=32` on a 5-bit field, `treq<64` on a 6-bit field), and `_ => unreachable!()` arms on alias matches where the alias value is `(addr>>12)&3 ∈ 0..=3`.
   - `mdrp2350/core/mod.rs`, `threaded/emulator.rs` — WFI/WFE-wait false arms requiring live firmware executing the exact instruction; `#[ignore]`d stress tests don't merge their profdata.
   - `mdpicoem-harness/src/lib.rs` — test-assertion format-args split branches and `run_fpu_smoke_test` hardcoded-correct error arms.

2. **Reachable but unwritten** (~300 branches in `mdrp2350`, ~80 in `mdrp2040`, ~30 in `mdpicoem-harness/lib.rs`):
   - Specific SSAT/USAT encodings, FPU flag-bit corners, SCB/SHPR/NVIC priority-level edges, PPB MPU/SAU register-alias paths, DMA trigger-alias permutations, bus-fault escalation variants.
   - Each requires a focused test case. No architectural blocker — just time.

3. **Rate-limit + time budget**:
   - Three concurrent Stage 8 subagents hit the platform rate limit (`You've hit your limit · resets 4:40pm`) simultaneously, finishing with only the partial `mdpicoem-devices/i2s_capture.rs` work. Subsequent inline work closed 9 more reachable branches in mdrp2040 lib.rs and registers.rs.

## §8 — What a follow-up push to 98% would look like

Realistic path forward — roughly 300-400 more branches to close, estimated 10-15 focused test-writing hours:

1. **mdrp2350 exceptions.rs + core/mod.rs**: write explicit tests for STKOF, SPLIMVIOL, MemFault, UsageFault NOCP/INVSTATE, BusFault IBUSERR/PRECISERR/IMPRECISERR, lazy FP save success and abort paths. Expected gain: ~30 branches.
2. **mdrp2350 execute_fpu.rs**: systematically walk FPSCR flag combinations, denormal-with-FZ variants, rounding-mode RMode matrix for every op. Expected gain: ~20 branches.
3. **mdrp2350 execute_thumb32.rs**: walk every remaining wide-encoding arm (particularly ADR T1/T2/T3, SSAT/USAT encoding variants, all parallel-arithmetic `SEL` permutations). Expected gain: ~15 branches.
4. **mdrp2350 bus/mod.rs**: DMA-triggered MMIO paths, specific reserved-address buckets, Secure/NonSecure alias windows. Expected gain: ~25 branches.
5. **Harness**: focused tests for `riscv_gen.rs` branch-form generator options, `harness/lib.rs` remaining format branches. Expected gain: ~25 branches.
6. **`cfg(coverage_nightly, coverage(off))` annotations** for the architectural ceiling cases in §7.1, with per-annotation justification. Expected gain: ~60 branches (or equivalent, by shrinking the denominator).
7. **mdrp2040 residuals** (bus/ppb, adc, uart, spi small corners): Expected gain: ~20 branches.

Total estimated gain: ~195 branches → would take us to ~95.5%. Getting the final ~2.5% (~135 branches) is the hardest mile — requires either more `coverage(off)` annotations or tests for genuinely obscure paths.

## §9 — Observations worth keeping

- **`cargo +nightly llvm-cov` ICE's with incremental compilation on this workspace.** Set `CARGO_INCREMENTAL=0` for every coverage run. Symptom: `on_disk_cache.rs:663` panic inside `try_mark_green`. Four ICE dumps in the repo root (`rustc-ice-*.txt`) can be deleted; they're stale.
- **`llvm-cov --branch` is unstable and aggregates across monomorphizations**, contrary to what one might expect. The `[True: 0, False: 0]` phantom entries in `--text` output are compiler-elided branches (bounds checks, format-args splits inside `tracing::` macros) that don't count against the percentage.
- **Multi-agent coordination works when file ownership is strict.** Four to five parallel agents ran cleanly per stage by partitioning which `tests.rs` / which new file each owned. Conflicts only happened when I accidentally asked two agents to append to the same file.
- **Rate limit is shared across the account.** Spawning three agents at once burned through the limit; future work should throttle to two or queue sequentially.
