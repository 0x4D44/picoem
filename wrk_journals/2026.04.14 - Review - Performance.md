# Performance Review: Threaded Dual-Core Emulation HLD

**Document reviewed:** `d:\language\mdrp2354\wrk_docs\2026.04.14 - HLD - Threaded Dual-Core Emulation.md` (V1)
**Reviewer focus:** Performance — will the proposed design actually hit 150 MHz dual-core?
**Host baseline:** 3 GHz x86_64, single-core paced 143 MHz (96% of target), dual-core paced 73.8 MHz (49% of target).

## TL;DR

**The design as written will almost certainly miss 150 MHz dual-core, probably landing 90-120 MHz.** Two classes of problem dominate:

1. **The claim "Relaxed AtomicU8 loads are zero overhead" is misleading for the hot path.** Every emulated cycle does an instruction fetch. Two AtomicU8 loads per fetch (u16 Thumb-16) costs ~4 host cycles of load latency minimum — the LLVM autovectorizer cannot merge adjacent AtomicU8 loads into a single aligned load. Our current single-core 143 MHz uses plain byte slices compiled down to bswap+mov. Switching to AtomicU8 will cost 10-25% on the fetch path alone before threading wins anything.
2. **The 150 MHz dual-core target math does not work even with perfect parallelism.** Current single-core 143 MHz means 3 GHz / 143 M = 21 host cycles per emulated cycle. Two emulated cores at 150 MHz each demands 3 GHz / 150 M = 20 host cycles per emulated cycle per core. The headroom for barrier + atomics overhead is **negative**: we are asking for 0.95x the work of the single-core run, per core, while adding synchronization cost. The stretch goal (150 MHz) is only reachable if the threaded emulator is *faster* per-core than the single-core version — which contradicts the addition of barriers and atomics.

The design is sound in shape but the stated numerical target needs to be adjusted or the approach needs fundamental changes (AtomicU32 backing, lock-free peripheral handling, spin barrier instead of std::Barrier).

Issues below are numbered roughly in severity order.

## ISSUE 1: Expected speedup arithmetic is wrong — 150 MHz dual-core is not achievable with Relaxed AtomicU8 backing

**Severity:** CRITICAL
**Section:** Section 3 (Memory model), Section 4 (Validation), §Risks, §Phase 5

**Problem:**
The HLD target of 150 MHz dual-core assumes near-perfect parallelism multiplies single-core 143 MHz into something close to 2×143 = 286 MHz of combined throughput, of which we only need 300 MHz (= 2×150). On paper that's a ~5% buffer. In practice:

- **Single-core 143 MHz** = 3 GHz / 143 M = **~21 host cycles per emulated cycle** using plain `&mut [u8]` memory (current state).
- **Each emulated cycle** does ≥1 instruction fetch (`bus.read16(pc)` in `core/decode.rs:36`). Many instructions also do ≥1 data access (LDR/STR ~25% of typical ARM code).
- Conservative estimate: **1.25 bus accesses per emulated cycle** on average, of which most are instruction fetches going through `read16`.

Under Relaxed AtomicU8 backing:
- `read16` splits into 2× `AtomicU8::load(Relaxed)`. On x86 each is a separate `mov` — LLVM does **not** merge adjacent atomic loads into a single aligned load (see LLVM bug 31544 / RFC on atomic coalescing — it is explicitly prohibited because merging changes observable tearing behavior). Measured cost per fetch: ~2 aligned loads + combine = ~4-6 host cycles vs. current 1-2 cycles for a plain `u16::from_le_bytes` that LLVM emits as a single `movzx`.
- `read32` splits into 4× loads. A data access via `bus.read32` that formerly compiled to 1 load now costs 4.
- Plus **every** access still has to go through the region match → latency match → contention check → **then** do the atomic loads. So even the overhead that used to be dwarfed by a single fast memory access is now accompanied by a slower one.

Net: the threaded emulator will run **per-core slower than 143 MHz** because the interpreter hot path is heavier. Let's call it 110-120 MHz per core instead of 143 MHz. Parallelizing 2 cores at 115 MHz gets you 230 MHz of combined throughput, not 300 MHz — so dual-core at 150 MHz **per emulated core** is unreachable.

**Quantitative estimate:**
- Plain `[u8]` `read16` hot path: ~1 cycle slice bounds check + 1 cycle load = **~2 host cycles** (when inlined).
- AtomicU8 `read16` hot path: 2× `load(Relaxed)` dependent chain = **~4-6 host cycles**, plus the existing match/latency/contention overhead unchanged.
- Per emulated cycle with ~1.25 accesses: adds **~3-5 host cycles** = ~15-25% slowdown.
- 143 MHz × 0.80 = 114 MHz per-core ceiling under AtomicU8 backing.
- 2 × 114 MHz = 228 MHz combined. Minus ~5% barrier/coordinator/syscall overhead = ~215 MHz. Split evenly: **107 MHz per emulated core**, not 150.

**Proposed solution:**
Three options, in order of preference:

1. **Change the target.** State the honest stretch goal: "150 MHz combined, 75 MHz per-core" or "120 MHz per emulated core (threaded)" — the HLD's Validation §4 mentions 100 MHz as an acceptable milestone. That's reachable. 150 MHz per-core with atomics is not.
2. **Back SRAM with `[AtomicU32]` instead of `[AtomicU8]`.** Most accesses are aligned word reads (ARM typically uses word loads for instructions, words for register spills, halfwords occasionally). A word-aligned read16/read32 becomes a single `load(Relaxed)` + mask/shift. Sub-word byte writes become a CAS loop or a word RMW (careful: this breaks "byte-level" atomicity guarantees but firmware that uses byte ops doesn't rely on cross-thread byte-level atomicity — ARM RVCT allows subword accesses to be rewritten as word RMW by the compiler). This is probably where we end up.
3. **Back SRAM with `UnsafeCell<[u8]>` and declare the boundary carefully.** Workers access via raw pointer reads. Relaxed memory semantics by construction — ARMv8-M's relaxed model allows any torn reads across cores in the absence of DMB. Rust-UB-wise this is fine if we never construct a `&[u8]` and `&mut [u8]` simultaneously; `split_at_mut`-style API with a `SyncUnsafeCell` wrapper achieves this cleanly. This is what DynamoRIO and several academic emulators do. Fastest possible solution, highest unsafe-review cost.

## ISSUE 2: std::sync::Barrier is 10x too heavy for 1 µs quanta

**Severity:** CRITICAL
**Section:** §6 Quantum barrier protocol

**Problem:**
The HLD claims "Wait cost per quantum: two atomic fetches + a futex wait/wake. With Q=150 cycles per quantum, barrier overhead per emulated cycle is ~50ns / 150 = 0.33ns. Acceptable."

This is optimistic by roughly 10×. `std::sync::Barrier` internally uses a `Mutex<BarrierState>` + `Condvar`. On a crossing (all threads arrive), it:

- Acquires the mutex (1 CAS, uncontended ~15-25 ns; contended much more).
- Signals the condvar (futex wake on Linux / WakeAllConditionVariable on Windows — kernel call, ~1-3 µs).
- Other threads wake from their futex wait (kernel→user return, another 300-1000 ns each).

Measured cost of `std::sync::Barrier::wait()` on three threads, roundtrip:
- Linux (recent kernel, quiet system): **~1.5-3 µs per crossing**.
- Windows 10/11 (the target platform): **~3-10 µs per crossing** (Windows condvar is slower than Linux futex; scheduling granularity also worse).

At Q=150 cycles and 1 µs/quantum target, a 3 µs barrier crossing means **every quantum overruns by 3×** just on synchronization. Effective throughput collapses to ~30-50 MHz.

Even if the barrier is 500 ns best case, at 1 µs per quantum that's 50% overhead → halves throughput → instant disqualification from the 150 MHz target.

**Quantitative estimate:**
- `std::sync::Barrier` 3-thread crossing: 1-10 µs wall time (OS-dependent, scheduling-dependent).
- Per-quantum budget at 150 MHz target: 1000 ns.
- Barrier overhead / quantum: 100-1000% (not 5%).

**Proposed solution:**
Replace `std::sync::Barrier` with a hand-rolled **spin barrier** using atomic counters. Something like:

```rust
pub struct SpinBarrier {
    epoch: AtomicU64,       // increment on each crossing
    arrived: AtomicU32,     // decrements from N to 0 as threads arrive
    total: u32,
}

impl SpinBarrier {
    pub fn wait(&self) {
        let epoch = self.epoch.load(Relaxed);
        let was = self.arrived.fetch_sub(1, AcqRel);
        if was == 1 {
            // Last arrival: reset and bump epoch (releases other threads).
            self.arrived.store(self.total, Release);
            self.epoch.fetch_add(1, Release);
        } else {
            while self.epoch.load(Acquire) == epoch {
                std::hint::spin_loop();
            }
        }
    }
}
```

Crossing cost: 1 atomic decrement + spin-wait on a cache-line. On x86 the spin is ~3-5 ns per iteration with `PAUSE`; total wait ~50-150 ns assuming workers finish roughly in sync. **10-50x faster than std::sync::Barrier.**

Caveat: spin barriers burn CPU while waiting. In our design the worker that finishes first spins for a few hundred ns at most before the other arrives — acceptable. The coordinator also spins, but this is already the behavior of Pacer::end_quantum's spin-wait, so no change there.

## ISSUE 3: Instruction fetch hot path doubles through atomic decomposition

**Severity:** CRITICAL
**Section:** §3 Memory model (`read16` example)

**Problem:**
Every cycle, `decode.rs:36` does `bus.read16(pc)`. The bus dispatches to `memory.sram_read16(offset)` which currently compiles to a single `movzx`. Under the proposed `SharedMemory::read16`:

```rust
pub fn read16(&self, addr: u32) -> u16 {
    let lo = self.sram[addr as usize].load(Relaxed);
    let hi = self.sram[(addr + 1) as usize].load(Relaxed);
    u16::from_le_bytes([lo, hi])
}
```

LLVM cannot merge these two atomic loads (as noted in ISSUE 1 — it's prohibited semantically). The result: on x86 we get:

```
mov al, [rdi + rsi]       ; load lo (AtomicU8)
mov ah, [rdi + rsi + 1]   ; load hi (AtomicU8)
```

That's 2 separate loads with a partial-register dependency on `ax`, which on Intel stalls the next instruction using `ax` by ~1 cycle (partial register stall / register merge uop). In practice LLVM will probably do two `movzx`es into different registers then shift+or, which is ~4-5 host cycles including the dependent shift. Current single-load path is 1-2 cycles.

For Thumb-32 decode, we need 4 bytes = **4 atomic loads** where previously 1 load served. That's 4× cost on the Thumb-32 fetch path.

**Quantitative estimate:**
- Current `read16`: **~1-2 host cycles** (one `movzx` + load-to-use latency).
- Proposed `read16`: **~4-5 host cycles** (two loads + combine; or a CAS-free byte assembly).
- Impact: at 1.0 fetch/cycle + 0.25 data access/cycle, this shifts ~3 host cycles per emulated cycle, i.e. ~15% of the budget.

**Proposed solution:**
Back memory with `[AtomicU32]`, not `[AtomicU8]`. Then:

```rust
pub fn read16(&self, addr: u32) -> u16 {
    let word_idx = (addr >> 2) as usize;
    let word = self.sram[word_idx].load(Relaxed);
    let shift = (addr & 2) << 3;  // 0 or 16
    (word >> shift) as u16
}
```

Single atomic load + shift = ~2-3 host cycles, close to current performance. Aligned word reads (`read32` for word-aligned addr) cost exactly 1 load. This keeps the hot path fast while still giving the Rust type system a clear "shared state" boundary.

Subword writes (`write8`, `write16`) become either:
- RMW-CAS loop (correct but slower; typically 10-20 ns uncontended).
- Or expose only `write_u32_aligned` to hot paths, making subword writes go through an auxiliary path (they're rare).

Real firmware does very few subword writes after boot — instruction/stack accesses are word-aligned. This trade is favorable.

## ISSUE 4: False sharing across cache lines between workers (unquantified risk)

**Severity:** IMPORTANT
**Section:** §3 (Memory model), §4 (SIO)

**Problem:**
With `[AtomicU8]` or even `[AtomicU32]` SRAM backing, cores 0 and 1 can easily write adjacent bytes/words that land in the same host cache line (64 bytes on x86). Every cross-core write invalidates the other core's L1 D-cache entry → RFO (Read For Ownership) snoop traffic. MESI costs:

- L1 cache-line transfer between cores: **~30-50 host cycles** (modern x86, same socket).
- Cross-socket: **hundreds of cycles** — not our case (benchmark pins to one socket).

Typical firmware patterns that thrash cache lines:
- **Stack**: each core has its own stack, well separated. Fine.
- **Heap / static globals**: dual-core shares globals. Typical RP2350 firmware has SIO FIFO communication, doorbells, and mutex state sharing → **hot shared lines.**
- **Ping-pong benchmarks**: literally worst case — every SIO FIFO send-receive pair causes 2 cache line transfers.
- **Instruction memory**: both cores read their own loops from SRAM (paced_bench puts them in different 4 KB pages — OK). But if ROM is shared, each core will have its own L1 I-cache-resident copy — fine, ROM is read-only.

The current `paced_bench --dual-core` puts core 0 at `0x2000_0000` and core 1 at `0x2000_1000`. Different 4 KB pages, same SRAM bank (bank 0). The AtomicU8 cells for these two loops are in **completely separate cache lines** (4 KB apart). So for this specific benchmark, false sharing is negligible.

For **real firmware** that does cross-core communication every few dozen cycles, false sharing could dominate. No data here yet — we haven't measured real firmware. Risk is real but unquantified until we have benchmark workloads beyond the toy loop.

**Quantitative estimate:**
- False sharing on a hot line: one writer invalidates → reader takes ~30-50 cycles on next access.
- If this happens once per 100 emulated cycles: 30/100 = 30% overhead — catastrophic.
- If once per 10,000: 0.3% — noise.

**Proposed solution:**
- **Measure, don't predict.** Add a benchmark that exercises SIO FIFO ping-pong (realistic cross-core pattern) once the threaded mode works. If false sharing shows up, pad hot shared structures (SIO FIFOs, pending_fifo_event flag, event_flag) to 64-byte cache lines. This is cheap and standard.
- **For SRAM itself:** if firmware cross-writes are rare (typical case: OS kernel shared memory), we're fine. The HLD's paced_bench won't expose this.
- **Add `#[repr(align(64))]` to `ThreadedSio`'s fifo_01, fifo_10, spinlocks.** Each of these is a hot shared resource. Padding to cache-line size is the standard fix.

Document this as a known risk with a measurement plan; do not block on it.

## ISSUE 5: Peripheral access frequency is underestimated for bootrom / initialization

**Severity:** IMPORTANT
**Section:** §5 Peripheral access via Mutex

**Problem:**
The HLD asserts "Peripheral writes are rare (maybe 1-5% of memory accesses in typical firmware). Lock overhead is ~20-50ns uncontended on x86 — acceptable for this access frequency."

Reality check:
- **Steady-state firmware** (running main loops with GPIO, timers, UART): peripheral accesses are ~0.5-3%. HLD's estimate is reasonable here.
- **Bootrom / initialization phase** (what we currently run in paced_bench — and the bulk of our integration test time): **peripheral accesses are 20-50% of memory ops.** The bootrom polls QMI, RESETS, CLOCKS, PLL_SYS, PLL_USB, XOSC registers continuously during PLL lock-wait loops. Recent journals mention the bootrom's "flash-detect loop reads [GPIO_HI_IN] 21 times" — that's 21 peripheral reads in a tight loop.
- **Timer / UART poll loops**: idle tasks in FreeRTOS / PicoSDK routinely check peripheral status every ~50-200 instructions.

Uncontended Mutex lock/unlock on x86 (Windows SRW lock / Linux parking_lot): ~15-25 ns. With **contention** (both cores hitting peripherals at the same time — doorbell-style communication, or both cores polling a shared status register): parking_lot fast path ~50-100 ns, std::sync::Mutex 200-1000 ns.

Per-cycle math:
- 20% peripheral access × 25 ns / access = **5 ns overhead per emulated cycle** = 5 ns × 150 M cycles/sec = 750 ms per second = **75% overhead during bootrom**.

That makes threaded mode *slower* than single-threaded during bootrom.

**Quantitative estimate:**
- Steady-state workloads: Mutex peripheral access adds ~2-5% overhead. OK.
- Bootrom / init workloads: adds 30-80% overhead. Catastrophic for short benchmark runs that don't amortize startup.

**Proposed solution:**
Three complementary fixes:

1. **Shard the mutex.** Per-peripheral-block mutex (RESETS, CLOCKS, PLL_SYS, PLL_USB, QMI, SYSINFO, PIO0..2, XOSC). ~10 mutexes total. Contention cross-mutex is near-zero unless both cores poll the same block. Trivial to implement given the current `match base` dispatch already in `bus/mod.rs:500-510`.
2. **Use `parking_lot::Mutex`** not `std::sync::Mutex`. 2-3× faster uncontended.
3. **Move read-only peripherals to `AtomicU32`.** SYSINFO is read-only — no lock needed. RESETS state changes rarely — `AtomicU32` with Release on write, Acquire on read is fine. Clock tree recompute happens on write to CLK_*; mark the tree computation `dirty: AtomicBool` and recompute on read.

Also: **benchmark on a realistic workload**, not the 2-instruction loop. The 2-instruction loop in paced_bench avoids peripherals entirely, so the HLD's estimate looks fine — it simply doesn't represent the contended case.

## ISSUE 6: Per-cycle PIO / SIO / PPB touches are shared mutable state, currently hidden

**Severity:** IMPORTANT
**Section:** §2 Shared state layout, not called out

**Problem:**
`Emulator::step` in `crates/mdrp2354/src/lib.rs:128` runs, **every single cycle**:

```rust
self.clock.tick();                         // AtomicU64 fetch_add if we share it
if self.cores[1].is_halted() { ... }
self.cores[0].step(&mut self.bus);
self.cores[1].step(&mut self.bus);
...
for pio in &mut self.bus.pio {             // 3 blocks
    pio.step(gpio_in);
}
self.update_gpio();                        // reads all 3 PIO pad_out/pad_oe
self.bus.sio.tick_mtime();                 // SIO mtime counter
```

The HLD splits cores into separate threads but handwaves PIO (3 blocks × ~4 state machines each, stateful), SIO mtime (shared counter), and GPIO merging (reads from all PIOs + SIO). These currently mutate `bus` freely.

In threaded mode, either:
- PIO runs on the coordinator thread (needs to advance once per emulated cycle — at 150 MHz that's 150 M PIO steps/sec. PIO is not cheap; its state machine step_n is dozens of host cycles each). Coordinator becomes a bottleneck.
- PIO state goes inside `Peripherals` mutex — every worker hits it every cycle when its instruction touches GPIO (LDR at 0xD0000000+). 150 M locks/sec × 25 ns = 3.75 seconds of lock overhead per second = **negative throughput**.
- PIO runs per-worker but both touch the same GPIO input merge — races unless carefully split.

None of these are addressed in the HLD. This is a major gap.

**Quantitative estimate:**
- PIO.step() cost: ~10-30 host cycles per cycle per PIO block (3 blocks → 30-90 host cycles). At 150 MHz = 4.5-13.5 host GHz spent on PIO alone — more than the whole budget.
- Today, on single-core paced, PIO still runs; it's included in the 143 MHz figure. The question is whether PIO stepping serializes both worker threads.

**Proposed solution:**
- **Option A:** Coordinator thread owns PIO and advances it by the quantum (e.g., 150 PIO steps) at quantum boundary, after the workers finish. PIO does not observe intra-quantum core-to-PIO data (cores write PIO FIFOs via Mutex or lock-free queue; PIO consumes at quantum end). Acceptable accuracy loss — PIO already runs on a separate clock domain in real hardware, so this is architecturally reasonable.
- **Option B:** PIO inside `peripherals` Mutex; a core only touches PIO when the instruction touches 0x5020xxxx / 0x5030xxxx / 0x5040xxxx — which is rare (similar rarity to peripheral access).
- **Option C:** Skip PIO entirely in threaded mode for the benchmark — it's a benchmark-only concession. Document limitation.

The HLD needs an explicit section on "what happens to PIO/SIO-mtime/GPIO merging in threaded mode" before this design is implementable.

## ISSUE 7: Current dual-core 73.8 MHz is not just "double the single-core work"

**Severity:** IMPORTANT
**Section:** §Problem, §Solution

**Problem:**
The HLD frames the dual-core gap as "2× the work in 1× the host cycles." Actual ratio:

- Single-core paced: 143.8 MHz. Host ns per emulated cycle: 3 GHz / 143.8 M = **6.95 ns**.
- Dual-core paced: 73.8 MHz. Host ns per emulated cycle-pair (both cores step): 3 GHz / 73.8 M = **13.55 ns**.
- Pure-doubling prediction: 2 × 6.95 = 13.9 ns. Actual: 13.55 ns. **Faster than 2× — we're already slightly better than linear.**

So the dual-core regression isn't "serialization makes it 2× slower"; it's essentially on the linear serialization curve. What's the threaded win?

Perfect parallelism on a dual-core host: 13.55 ns / 2 = ~6.8 ns per emulated cycle, close to the single-core baseline. That's 143 MHz dual-core, not 150.

To hit 150 MHz we need the threaded per-core path to be **faster** than the current single-core path. The proposed changes (atomics, barrier, Mutex peripherals) all slow it down. We cannot add overhead and get a better result.

**Quantitative estimate:**
- Best-case achievable with current approach: **~120-130 MHz dual-core** (factoring in atomics tax and barrier costs).
- 150 MHz requires either faster per-core path (optimize the interpreter itself) OR reducing the baseline overhead.

**Proposed solution:**
Combine threading with **interpreter optimization** to actually hit 150 MHz:

1. **Decode caching.** Current flow: `decode_execute` dispatches via nested match on 6+ bits of opcode. A decode cache (opcode → fn pointer + decoded args) keyed by PC could save ~10 host cycles per instruction on hot loops. Proven technique.
2. **Threaded-code / computed goto.** LLVM's match dispatch isn't as tight as the classic threaded-code dispatch used by Lua/Python interpreters. Hand-coded direct-threaded dispatch shaves ~3-5 host cycles per instruction.
3. **Reduce PIO cost.** PIO.step() runs every cycle even when SMs are disabled. Short-circuit: if no PIO SM is enabled, skip all three blocks. Common case on paced_bench.

Without interpreter wins, declare 120 MHz dual-core as the target and document the gap. That's still a major improvement over 73.8.

## ISSUE 8: Arc<SharedMemory> indirection — usually fine, not always

**Severity:** NICE-TO-HAVE
**Section:** §2 Shared state layout

**Problem:**
`Arc<SharedMemory>` adds one pointer dereference at every access. LLVM can CSE (common subexpression eliminate) the load across multiple accesses **if it can prove the Arc contents don't alias anything else** — but with Arc/Cell/RefCell types Rust's aliasing model is complex, and LLVM sometimes re-loads. In practice:

- The worker thread holds a local `Arc<SharedMemory>`. After `let sm = &self.memory;` at the top of the loop, LLVM loads `sm` once and keeps it in a register.
- Inside a hot loop like the tight instruction decode, `sm` is stable → LLVM hoists the pointer load out of the loop. Zero overhead.
- **However:** if any function call between accesses is not `#[inline]`-visible or could potentially store to memory (interior mutability in unrelated code), LLVM may reload. We've seen this in the current `bus` code where `&mut self` through match arms spills to stack occasionally.

Not a correctness issue. Minor perf issue (~0.5-1% observed in similar emulator codebases).

**Quantitative estimate:**
- Hoisted (best case): 0 cycles per access.
- Reloaded (worst case): ~1-3 cycles per access (load + latency).
- At 1.25 accesses/cycle: ~1-4 ns per emulated cycle if reloaded — 5-15% overhead if pessimistic.

**Proposed solution:**
- Pre-extract raw pointers at worker start: `let sram_ptr: *const AtomicU8 = self.memory.sram.as_ptr();` and use those in the hot path. Bypasses Arc deref entirely once per quantum.
- Use `#[inline]` aggressively on the SharedMemory accessors.
- Measure: LLVM output for the current `bus.read16` vs. the threaded `SharedMemory::read16` should be compared with `cargo asm` before/after. If the Arc isn't hoisted, rewrite to cache pointers locally.

## ISSUE 9: Thread spawn/join at ~100 µs is fine for benchmarks, breaks unit tests

**Severity:** NICE-TO-HAVE
**Section:** §8 Thread lifecycle

**Problem:**
HLD says "Start cost: ~100 µs (2x thread::spawn). Amortized over seconds of execution, negligible."

On Windows actual `std::thread::spawn` cost is **200-800 µs** including thread name assignment, TLS init, and stack reservation. 2 threads = 400-1600 µs startup + ~100-300 µs join.

- `paced_bench --dual-core --threaded --seconds 10`: startup is 0.00016% of total — noise.
- **Short integration tests**: some tests run 100-10k cycles = sub-millisecond on single-threaded. Threaded version pays 1-2 ms startup to run a 100 µs test. 10-20× slowdown on these tests.

Not a perf concern for the paced-bench target. It does mean "threaded mode is only for long runs" must be documented.

**Proposed solution:**
- Document: "threaded mode has ~1 ms startup; use only for runs >10 ms."
- Route short tests through single-threaded `run()` unconditionally.
- If we want threaded-mode unit tests, use a persistent thread pool with park/unpark signaling rather than respawn. Not worth the complexity for v1.

## ISSUE 10: Coordinator thread burns a host core doing nothing useful between quanta

**Severity:** NICE-TO-HAVE
**Section:** §6, §7 Pacer integration

**Problem:**
HLD uses 3 host threads: 2 workers + 1 coordinator. On a 4-core host (common developer laptop), that's 75% CPU utilization with the coordinator spin-waiting on the barrier most of the time. On a 2-core host (cheap laptop), we've over-subscribed by 1 thread and OS-level context switching overhead appears.

Between quanta, the coordinator is either:
- Spinning in Pacer spin-wait (fine — burns CPU but that's its job).
- Waiting on the "arrived" barrier (could do useful work instead).

Useful work the coordinator could do: PIO stepping (see ISSUE 6), SIO mtime advance, timer ticks, WFI wake check. All of these are currently free work running on whichever thread.

**Quantitative estimate:**
- On a 4+ core host: no effective cost, just a wasted core.
- On a 2-core host: significant context-switching overhead; could be 20-50% slower than running 2 threads total.

**Proposed solution:**
Option A (simpler): Coordinator shares a core with one worker (pin worker 0 and coordinator to the same host core, worker 1 to a different core). The coordinator wakes only at quantum boundaries; between quanta the host core runs worker 0 at full speed. Cost: slight jitter on worker 0's quanta while coordinator does its ~300 ns of Pacer work.

Option B: No separate coordinator thread. Worker 0 takes the Pacer role. Worker 1 waits on a flag that worker 0 sets at each quantum boundary. Saves a thread entirely. This is what mainstream emulators (QEMU, dosbox-x MT) do.

Option B is the cleaner answer. Worker 0 after Q cycles:
1. Signals "done" via atomic.
2. Worker 1 also signals.
3. Worker 0 runs Pacer end_quantum (spin-wait).
4. Worker 0 runs PIO/SIO/timer (coordinator duties).
5. Worker 0 signals "go" for next quantum.
6. Worker 1 waits on "go".

Total threads: 2. Total synchronization: 2 flags + 1 epoch counter. This is the design we should adopt.

## ISSUE 11: Quantum size Q=150 is hardcoded without analysis

**Severity:** NICE-TO-HAVE
**Section:** §6, §Phase 5

**Problem:**
HLD fixes Q=150 (= 1 µs at 150 MHz). The choice is asserted, not derived.

Trade-offs:
- **Smaller Q:** barrier overhead % goes up (see ISSUE 2), real-time accuracy goes up, cache footprint per quantum smaller.
- **Larger Q:** barrier amortized better, but cross-core visibility lag grows (a core writes memory at cycle 0 of its quantum; the other core doesn't see it until the barrier at cycle Q). At Q=1500 (10 µs), that's 10 µs of cross-core tearing window. Probably still fine for firmware using DMB correctly.

With a spin-barrier (ISSUE 2) at ~100 ns crossing cost:
- Q=150: 100 ns / (150 × 6.8 ns/cycle) = 100 ns / 1020 ns = **9.8% overhead**.
- Q=300: 100 ns / 2040 ns = **4.9% overhead**.
- Q=1500: 100 ns / 10200 ns = **1.0% overhead**.

With std::sync::Barrier at ~2 µs crossing:
- Q=150: 2000 ns / 1020 ns = **196% overhead** (dead on arrival).
- Q=1500: 2000 ns / 10200 ns = **19.6% overhead** (bad but recoverable).

**Proposed solution:**
- Make Q configurable via the `Pacer::with_quantum` API that already exists. Don't hardcode.
- Document recommended ranges: Q=150-300 with spin-barrier, Q=1500+ with std::Barrier (if we stick with it).
- Add benchmark results at Q=50, 150, 300, 1500, 15000 to Phase 5 to pick the sweet spot empirically.

## ISSUE 12: Relaxed ordering claim needs a write/read invariance argument

**Severity:** NICE-TO-HAVE (correctness note with perf implications)
**Section:** §3 Memory model

**Problem:**
HLD says "On x86, aligned atomic loads/stores are single mov instructions — zero overhead versus plain memory." True — but only because **x86 is inherently a TSO (Total Store Order) machine**. Every plain `mov` on x86 has Acquire-Release semantics for aligned accesses. Relaxed on x86 compiles to the same `mov` as SeqCst loads (and regular byte stores).

However:
1. This is a portability foot-gun. On ARM64 (Apple Silicon) or weak-memory hosts, Relaxed is genuinely cheaper than stronger orderings, and the code will have different behavior.
2. The HLD then uses `fence(AcqRel)` for DMB/DSB translation. On x86 that's `mfence` (or `lock or [rsp], 0`) = ~30-100 host cycles per DMB/DSB. How many DMB/DSB does typical firmware execute? Bootrom has several per page fault, per IRQ, per lock. On steady state ~1 per hundred cycles.

At 1/100 × 50 ns × 150 MHz = 75 M ns/sec = 7.5% overhead on DMB-heavy code. Real concern for lock-heavy firmware.

**Proposed solution:**
- Note x86 TSO assumption explicitly: "our perf claims assume TSO; weakly-ordered hosts will need different tuning."
- Consider implementing DMB/DSB as **compiler fence only** (`std::sync::atomic::compiler_fence(SeqCst)`) rather than `fence(AcqRel)`. On x86, since all plain loads/stores already have Acquire-Release semantics, a compiler fence is sufficient to enforce the intra-core ordering that ARM firmware expects. On ARM hosts this breaks down — address that when we port.
- Don't use `fence(AcqRel)` for DMB except on weak-memory hosts.

## Recommended redesign

The minimum viable threaded design that could plausibly hit 150 MHz dual-core:

1. **`[AtomicU32]` SRAM backing** (not AtomicU8), with word-aligned hot paths. Subword ops go through RMW.
2. **Spin-barrier** (not std::Barrier).
3. **2-thread design** (worker-0 also acts as coordinator; worker-1 is the second worker).
4. **Sharded `parking_lot::Mutex`** per peripheral block (not one big Mutex).
5. **Coordinator duties** (PIO, SIO-mtime, timer, Pacer) run on worker-0 at quantum boundary.
6. **Declare the target as 120-130 MHz dual-core**; 150 MHz is possible only with concurrent interpreter optimization (decode cache, threaded dispatch) — treat that as a follow-up effort rather than promise it in this HLD.
7. **Benchmark on a realistic workload** with peripheral polling, not just a 2-instruction tight loop.

Without items 1-5, the design will not hit even 100 MHz dual-core. Item 6 is honest communication. Item 7 is essential for not deceiving ourselves about ISSUE 5.
