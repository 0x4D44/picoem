Trace-level analysis of my fix (spi_psram_fudge program):

- `osr_count=32` after SM_RESTART → first `OUT X, 8` triggers
  autopull, correctly assigns `X=8, Y=0` for reset_en cmd
  `[8, 0, 0x66]`.
- But `exec_out` has only a **pre-shift** autopull check (no
  post-shift), so after the 8-iteration writeloop consumes OSR
  progressively, the SM wraps back to `begin`, does pre-shift pull,
  finds TX FIFO empty (firmware pushed exactly 3 bytes), and stalls.
- That stall is mechanically *correct* (SM idles between commands),
  but the DMA write channel has already finished its 3-byte transfer,
  so `pio_spi_write_read_dma_blocking` should return. Something in
  the mid-path is still holding firmware.

Pre-fix behavior that let firmware progress farther:
- `osr_count=0` after SM_RESTART → first `OUT X, 8` reads 8 zero
  bits from empty OSR, assigns `X=0`. Second `OUT Y, 8` autopulls
  and picks up byte 1, assigns `Y=8`. Commands decode backwards.
- With X=0, writeloop runs 0 iterations. With Y=8, readloop runs 8
  iterations, firing 8 autopushes per "command" (silently dropped
  pre-fix because no consumer drains RX). SM completes each command
  cycle via wrap and stalls at begin — same *stall location as
  post-fix*, but via a different path that happens to avoid the
  interaction with DMA wait.

## 19:00 — 5 s replay completed. Sim reached 3.798 s (past voice activation), WAV still silent. Real root cause found: ISA pacing.

5 s replay took **184 s wall** (not 45 min — emulator flies through
the post-DRAM sparse phase). Voice-control register writes DO show
up in the event-capture coverage:

```
(0x343 <- 0x00)               10          3         0    70.0%  voice control
(0x343 <- 0x01)                5          1         0    80.0%  freq ctrl
(0x343 <- 0x04)                5          0         0   100.0%  start addr HI ← MISSED
(0x343 <- 0x05)                5          5         0     0.0%  start addr LO
(0x343 <- 0x0d)               10          3         0    70.0%  volume ctrl
total                     720503      97491   (drop 86.5%)
```

Firmware is only capturing 13.5% of fired ISA events — **key
registers like 0x04 (start-addr-HI) are missed every time**, so the
voice is pointed at the wrong PSRAM address and emits zeros. Not an
emulator correctness bug per se; a replayer-pacing bug.

### Root cause — PIO ↔ firmware IOW handshake

Read `third_party/picogus/upstream/sw/isa/isa_io.pio`. The `iow`
program is a two-sided handshake:

```
restart:
    wait 1 gpio IOW_PIN        ; rising edge
    wait 0 gpio IOW_PIN        ; falling edge
    jmp pin restart            ; skip during DMA
    in pins, 10 [3] side 0b10  ; read 10 addr bits, autopush-pending
    nop [3]         side 0b10
    in pins, 8      side 0b10  ; read 8 data bits → autopush @ 18 bits
    out X, 32       side 0b00  ; STALL on empty TX FIFO; firmware pushes
    jmp !X restart  side 0b00  ; X==0 → ignore event
    out null, 32    side 0b01  ; STALL again (IOCHRDY low); firmware
    nop             side 0b00  ;   completes cycle by pushing null drain
```

PIO autopushes every event, then stalls waiting for firmware to
respond via TX FIFO. If the replayer fires the next IOW falling edge
before firmware completes the handshake, PIO is still mid-stall and
misses the new edge.

Default `drive_write_cycle` timing: 12+12+25+12 = 61 sysclks per event
(165 ns @ 370 MHz). Firmware handshake cost is much higher than that.

### Fix — pace the replayer

Set `PICOGUS_IDLE_CYCLES=500` and `PICOGUS_DATA_HOLD=200`. Re-ran 5 ms:

| Metric                          | Default 61-cyc pace | 500+200-cyc pace |
|---------------------------------|---------------------|------------------|
| Captured / fired                | 78,334 / 654,498    | 632,248 / 654,498 |
| Drop rate                       | 88 %                | **3.4 %**         |
| Wall time                       | 2.8 s               | 68.8 s            |
| PSRAM non-zero bytes            | (not measured)      | 65,185 / 8M       |

96.6 % capture rate with the conservative pacing. **Kicking off the
5 s paced replay now** — expected ~45 min wall.

### Still-pending worries (if WAV remains silent past voice activation)

1. **PWM IRQ** (slice 4 @ ~30 kHz) must fire `audio_sample_handler`
   which calls `GUS_sample_stereo()` and writes to I2S PIO TXF. If
   our PWM model doesn't generate wrap-IRQs correctly, no samples
   ever get produced.
2. **GUS voice-processing** (in-firmware gus-x.cpp) runs a large
   mixing loop — if any dependency (PIC ISR, per-voice state init)
   isn't fully set, `GUS_sample_stereo()` can return 0 even with
   voices logically active.
3. **audio_pio** (I2S SM config) — LRCLK is clocking at 29–44 kHz in
   observed traces, so I2S SM is running. DMA-free path (direct CPU
   push via IRQ) has no DMA to worry about.

## 19:10 — Full paced replay. Still silent. "Bytes read: 0" is the smoking gun.

5 s replay with `PICOGUS_IDLE_CYCLES=500 PICOGUS_DATA_HOLD=200
--pre-roll 2.0` — overall drop rate 0.1 %, but critical rare events
still dropping:

- `0x343 <- 0x4C` (reset-reg select): **2/3 captured** — but only the

Added PWM + PSRAM diagnostics to the harness. Two discoveries:

### Discovery 1 — PWM IRQ IS firing correctly

Once the register offsets were right:

```
PWM slice4 CSR:   0x00000001  EN=1
PWM EN:           0x1f  INTR: 0x0f  INTE: 0x10  INTS: 0x00
```

INTE bit 4 IS set (PWM IRQ enabled for slice 4) and slice 4 is
counting. INTS=0 at sampling time because handler just cleared INTR
bit 4. LRCLK edges confirm the I2S SM is consuming whatever
`audio_sample_handler` writes — so the IRQ chain is live.

### Discovery 2 — PSRAM `Bytes read: 0`

```
--- PSRAM diagnostics ---
Bytes written:     102898
Bytes read:        0
CS# falling edges: 102901  (== SPI frames started)
```

**Firmware is not reading PSRAM at all** across the entire run, even
though PWM IRQ is firing and audio_sample_handler is running.

That's only consistent with `GUS_sample_stereo()` taking the early
`return 0` at `(GUS_reset_reg & 0x03) != 0x03` — i.e. the reset
register never reached the "normal ops + DAC enabled" (0x07) state.

Cross-check with the trace: the reset-release sequence at t=300 µs
is `0x343<-0x4c` followed immediately by `0x345<-0x07`. The 0x07 write
was captured, but if the paired 0x4C select was the one that dropped
(2/3 captured), 0x07 ends up in whatever register was selected just
before — which happened to be 0x0e (active channels), so the write
mis-programmed ActiveChannels instead of releasing reset. Reset
register stays at 0x01 (from the t=100 µs write), and
`(0x01 & 0x03) != 0x03` → early return, no PSRAM reads, silent WAV.

On a 1 ms trace window the strong pacing got **3/3** 0x4C writes
captured, total drop 0.1 %. Kicking off the full 4 s paced replay

**But WAV is still silent.** Peak=0, non-zero=0.

### Why — the trace's DRAM upload is incomplete

The Monkey Island trace writes **102,898 bytes** of DRAM data (port
`0x347`) at PSRAM addresses 0 to ~103 K. All uploads land in the
first 5.4 ms of trace time — none afterwards.

But voice 0 at t=3.486 s is configured with:
- `WaveStart MSW` = 0x00ff → bits 17..29 = 0x01FE_0000
- `WaveStart LSW` = 0x9400 → bits 0..16 = 0x0001_2800
- `WaveStart` = 0x01FF_2800
- `useAddr = WaveStart >> WAVE_FRACT(10)` = 0x7FCA0 ≈ 523,424

**Voice 0 reads at PSRAM offset 523 K. Trace only uploaded bytes
0–103 K. Voice is reading uninitialised zero memory.**

The trace was captured mid-game from real hardware — the game had
already loaded ~1 MB of GUS PATCH data into DRAM before the trace
started. Our PSRAM emulator starts empty, so the voice plays
silence.

### Workaround — pre-seed PSRAM with a triangle-wave pattern

Added `PICOGUS_PSRAM_PRESEED=1` to the harness: fills the entire
8 MB PSRAM with an 8-bit triangle wave (period 256) before firmware
boots. Any voice pointed at any address finds non-zero sample data.

**Firmware pushes every sample as exact 0 to the I2S TX FIFO.** That
narrows the remaining cause to one thing: `GUS_sample_stereo()` is
returning 0 on every call.

### Analysis — why zero

`GUS_sample_stereo()`:
1. If `(GUS_reset_reg & 0x03) != 0x03` → early return 0
2. Otherwise loop `guschan[c]->generateSample(accum)` for `c < ActiveChannels`
3. clamp16 + combine to stereo

Capture coverage confirms firmware received:
- `0x345 <- 0x07` (reset=normal + DAC + IRQ) — **1/1** captured
- `0x345 <- 0xda` (ActiveChannels = 27) — **1/1** captured
- All 14 voice control registers 0x00..0x0d for voice 0 — **100%** captured

So `GUS_reset_reg` should be 0x07 and `ActiveChannels` should be 27.

Two most likely remaining causes:
1. **Firmware state is correct but voice volume math degenerates** — e.g. voice 0 configured with `RampEnd=0x30` (index 430 into `vol16bit`) where `vol16bit[430] ≈ 0` as int16 truncation. Voice 1's `RampEnd=0x80` should give `vol16bit[1904] ≈ 21` — audible — but TXF still shows 0.
2. **Emulator-level bug in M0+ core 1 exception path or VTOR handling** — PWM IRQ fires but the handler that runs isn't `audio_sample_handler`, or it runs but something corrupts `GUS_reset_reg` / voice state between handler invocations.

Settling which of these is the root cause requires either:
- Resolving firmware `.data` addresses for `GUS_reset_reg` / `myGUS.ActiveChannels` / `guschan[].WaveCtrl` so the harness can peek them directly (no ELF/map file in `third_party/picogus` — would need to rebuild firmware from source to generate one)
- Adding core-1 vector-table and exception-entry diagnostics to the emulator
