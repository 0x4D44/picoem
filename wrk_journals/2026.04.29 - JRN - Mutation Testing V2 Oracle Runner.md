## Goal

V2's deliverable per the V1 triage HLD §8: convert V1's hypothesised bucket
distribution (87.3 % Bucket 3 / 12.0 % Bucket 4 / 0.7 % Bucket 2 / 0 % Bucket 1)
into measured ground truth using a per-mutant oracle replay. Take the 707
"missed" mutants from V1, apply each patch, run the appropriate differential
oracle (qemu_diff_m33 / qemu_diff_m0plus / softfloat_diff), classify each as
oracle-caught (real Bucket 3) or oracle-survived (genuine Bucket 2 gap).

Acceptance criterion: a per-mutant CSV/JSON report with file, line, mutant
description, oracle, oracle-result (caught / survived / errored), plus a
follow-up triage note pointing at any genuine Bucket-2 gaps.

## State of play coming in

V1 sweep ran 2026-04-26 → 2026-04-27 (13h 17m). Headline numbers:
- 4390 mutants total (incl. baseline)
- 3626 caught by `cargo test`
- 707 missed
- 53 timeouts
- 3 unviable
- 1 baseline OK

But: `mutants.out/` is gitignored and was not preserved. We need to regenerate
the missed.txt from a fresh sweep before V2 can run. Per V1 calibration:
~10.9 s per mutant, so ~13h re-run on this machine, single-worker.

## Approach

Two-track work for today:

**Track A (long-running, background)**: Re-run the V1 sweep to regenerate
`mutants.out/missed.txt`. ~13h overnight on this machine. Single-worker
config validated in V1.

**Track B (foreground)**: Design and prototype the V2 runner. cargo-mutants
exposes `--list --json --diff` which prints per-mutant patches. The runner
can apply them itself; we don't need to integrate with cargo-mutants'
internals. Prototype against a hand-picked slice of survivors (pulled from
V1 triage HLD §3 examples) so we have a working pipeline before the
overnight sweep finishes.

## Stage plan

1. **Stage 1** — Get JSON catalogue of all 4389 mutants with diffs. Confirm

3. **Stage 3** — Build the V2 runner skeleton. Inputs: (a) the JSON catalogue,
   (b) a list of missed-mutant identifiers. Outputs: per-mutant classification

5. **Stage 5** — Prototype against ~10 mutants pulled from §3 of the V1

6. **Stage 6** — When Track A completes, run V2 over all 707 missed mutants.

7. **Stage 7** — Triage write-up + V2 HLD.

`cargo mutants --list --json --diff` produces 4480 mutants with file/line/col

(7.4 MB). Genres: BinaryOperator (3547), MatchArm (435), FnValue (357),
UnaryOperator (137), MatchArmGuard (4). 584 multi-line spans (almost all
`FnValue` and `MatchArm`).

Mutant count is **91 higher** than V1's 4389, because the source has churned
since V1 commit (Apr 26). Today's QEMU M0+ Thumb-32 oracle work added
encoding handlers and the residue-test push (stages 1-5) added unit tests
that don't generate mutants but kept the source surface growing.

Column semantics verified: 1-based byte offsets; slice `[start_col-1, end_col-1)`
on the start line. Multi-line spans (e.g. `replace fn body with true`) need

Per-mutant patch path: bypass the diff (its `+++` header is the mutation
description, not a path — non-standard, won't apply via `git apply`); just
splice byte range with `replacement` string from the JSON.

### Stage 2 — Oracle smoke + routing (complete)

| Source file                          | Oracle             | CLI flags              |
|---                                   |---                 |---                     |
| `mdrp2350/core/execute_thumb32.rs`   | `qemu_diff_m33`    | `--classes base`       |
| `mdrp2350/core/execute_fpu.rs`       | `softfloat_diff`   | `--mode all`           |
| `mdrp2350/core/execute.rs`           | `qemu_diff_m33`    | `--classes base`       |
| `mdrp2350/core/decode.rs`            | `qemu_diff_m33`    | `--classes base`       |
| `mdrp2040/core/execute.rs`           | `qemu_diff_m0plus` | (none)                 |
| `mdrp2040/core/execute_wide.rs`      | `qemu_diff_m0plus` | (none)                 |
| `mdrp2040/core/decode.rs`            | `qemu_diff_m0plus` | (none)                 |

**Two oracle env quirks observed:**

1. **`qemu_diff_m33 --classes fpu` is broken on QEMU 8.2 / mps2-an505**.
   All FPU cases respond with EAGAIN on the GDB pipe — `[RECOVER] GDB error
   on FUZZ:FPU_ARITH:0 VMUL ... QEMU error: Resource temporarily unavailable
   (os error 11)`, then `[SKIP]`. The run never terminates within bounded
   wall-clock; observed 30 cases skipped over 90 s. Pin `--classes base` for
   V2 to dodge it. FPU semantics are owned by `softfloat_diff` anyway, so the
   only loss is FPU dispatch / encoding mutations in `execute_thumb32.rs` —
   if any survive `--classes base` they may be Bucket-3 misclassifications.
   Note for V2 follow-up: investigate whether QEMU 10.2 (in CI) has the
   same issue; if not, V2.1 can switch back to `--classes all`.

2. **Port 3334 conflict with concurrent fuzz workloads.** Another agent's
   `qemu_diff_m0plus_fuzzer --fuzz 100000` (PID 3457098) is holding GDB
   port 3334 right now. M0+ oracle runs return `fatal: Resource temporarily
   unavailable (os error 11)`. Wait for that fuzz to finish (~30 min from
   11:32 → ~12:02) before running M0+ V2 cases, or arrange port isolation.

**Smoke-test wall-clock ladder for `qemu_diff_m33 --classes base`:**
- fuzz=10  → 2.4 s
- fuzz=50  → 3.8 s
- fuzz=200 → 19 s
- fuzz=1000 → 93 s

For V2 first-pass classification we want fuzz high enough that any mutation
that breaks an instruction's semantics is statistically near-certain to be
caught, but low enough that survivors don't inflate wall-clock. Plan: fuzz=200
first pass; deeper fuzz=2000 pass on the survivors.

### Stage 3 — Runner prototype (complete)

`scripts/v2_mutation_runner.py` (~200 LOC, Python; working dir
`mutation/v2/` — gitignored, holds catalog/results/logs).
Per-mutant pipeline:
1. Read mutant from catalog by `name`.
2. Compute byte offsets from span; splice `replacement`.
3. `cargo build --release -p mdpicoem-harness --bin <oracle>` — incremental.
4. Run oracle binary with `--fuzz N` plus per-oracle CLI quirks.
5. `try/finally` revert: write original bytes back even on error.
6. Append JSONL record to `mutation/v2/results.jsonl`.

**Validation**: ran one M33 mutant
(`crates/mdrp2350/src/core/execute.rs:11:40: replace + with - in add_with_carry`)
end-to-end. Result: `oracle_caught` (exit=1, wall=110 s, fuzz=1000). Pipeline
works.

Wall-clock breakdown of the validation run:
- Cargo incremental rebuild + relink: ~18 s
- `qemu_diff_m33 --classes base --fuzz 1000`: ~93 s
- File revert: ~0 s

The build cost is unavoidable at this layer (cargo rebuilds `mdrp2350` lib
when its source changes, then relinks the harness binary). The oracle cost
is the variable; first-pass fuzz=200 gives ~19 s, dropping wall to ~37 s/mutant.

**Sweep cost projection at fuzz=200:** 707 missed × 37 s ≈ 7.3 hours
sequential. Plus ~3 hours for a fuzz=2000 deep pass on the
~100-or-so first-pass survivors. Total ~10 hours, doable overnight.

### Stage 4 — Sweep regeneration kickoff (failed; rerun pending)

Kicked off `cargo mutants --jobs 8 --output mutation/v2/sweep/` in background.
**Baseline failed in 27 s** with two real failing unit tests:

```
tests::stage2_thumb32_residue::bfc_full_width_clears_word
  → execute_thumb32.rs:349:29 "attempt to shift left with overflow"
tests::stage3_bus_residue::coresight_trace_halfword_read_dispatches_through_byte_path
  → bus/mod.rs:2123:9 "PPB address 0xE0041100 reached Bus::read16 — use
     CortexM33::bus_read16 wrapper"
```

Both tests post-date V1 (commit `e9bc224` "tests: stage 2 ... Thumb-32" on
Apr 28; commit `00e82a8` "tests: stage 3 ... bus + peripherals" same day).
V1's sweep on Apr 26 didn't see them. Both look like **real production
bugs surfaced by the residue-coverage push** that didn't get fixed:

1. **BFC width=32 shift overflow**: `1u32 << 32` is UB in Rust; the
   production code at `execute_thumb32.rs:349` does this when width=32
   (legal encoding: lsb=0, msb=31). The test comment even acknowledges it
   ("the implementation behaviour at width=32 is unspecified"). Real fix:
   special-case width=32 to use `u32::MAX`, or compute the mask as
   `((1u64 << width) - 1) as u32` to widen.
2. **Coresight trace read16 path**: `bus/mod.rs:2123` panics when a PPB
   address reaches `Bus::read16` directly (instead of going through
   `CortexM33::bus_read16`). The test exercises that exact path. Either
   the test setup is wrong or the panic message is over-strict.

**Decision**: skip both tests in cargo-mutants for V2. Adding
`-- --skip bfc_full_width_clears_word --skip coresight_trace_halfword_read_dispatches_through_byte_path`
to the cargo-mutants command. This means mutations covered exclusively by
either test will appear as missed and feed into V2 — that's correct: those
mutations are not currently caught by the test, so they belong in the
"missed" set. Will surface to Arthur as a tech-debt item: production bug
in `execute_thumb32.rs:349`, plus test/check tension in `bus/mod.rs:2123`.

**cargo-mutants `--` separator quirk**: with one `--` after `cargo mutants`,
the args are passed to `cargo test` directly (not to libtest). `cargo test
--skip name` is rejected (cargo doesn't understand `--skip`; libtest does).
The fix is **double `--`**: `cargo mutants ... -- -- --skip name1 --skip name2`.
The first `--` separates cargo-mutants from cargo test args; the second
becomes `cargo test ... -- --skip name1 --skip name2` which is the correct
way to pass libtest flags. Verified working — observed in debug log:
`cargo test --verbose --package=... -- --skip bfc_full_width_clears_word
--skip coresight_trace_halfword_read_dispatches_through_byte_path`.

### Stage 5 — Runner validation (complete)

Hand-picked 5 mutations representing the four oracle paths + a Bucket-4
expected-survivor test:

| # | Mutant                                                                            | Oracle           | Expected | Result            | Wall  |
|---|---                                                                                |---               |---       |---                |---:   |
| 1 | `execute.rs:11:40 + → -` (M33 add_with_carry)                                     | qemu_diff_m33    | caught   | oracle_caught     | 110 s |
| 2 | `execute.rs:11:5 fn body → (0,true,true)` (M33 add_with_carry, multi-line)        | qemu_diff_m33    | caught   | oracle_caught     |  66 s |
| 3 | `execute_fpu.rs:182:19 \|\| → &&` (M33 fp_add)                                    | softfloat_diff   | caught   | oracle_caught     |  20 s |
| 4 | `execute_fpu.rs:24:27 & → \|` (M33 vfp_sd, inner mask)                            | softfloat_diff   | caught   | oracle_caught     |  22 s |
| 5 | `execute_fpu.rs:26:15 \| → ^` (M33 vfp_sd, disjoint-bit-field outer compose)      | softfloat_diff   | survive  | oracle_survived   |  25 s |
| 6 | `execute_fpu.rs:26:15 \| → &` (M33 vfp_sd, disjoint-bit-field outer compose)      | softfloat_diff   | caught   | **oracle_survived** |  24 s |
| 7 | `execute.rs:23:40 + → -` (M0+ add_with_carry)                                     | qemu_diff_m0plus | caught   | oracle_caught     |  47 s |

**Both core paths work end-to-end.** Wall-clock variance is dominated by
oracle choice: softfloat_diff is ~3× faster than QEMU oracles (no QEMU
spawn). Multi-line FnValue replacement (mutant #2) handled correctly by
byte-offset splice across 4 lines.

**Unexpected V2 finding (case 6)**: `vfp_sd: | → &` was expected to break
the encoding (`(vd<<1) & d` always evaluates to `0` since `vd<<1`'s LSB is
always `0`), but softfloat_diff didn't catch it. Reason: **softfloat_diff
exercises the IEEE-754 helpers (`fp_add`, `fp_sub`, `fp_div`, `fp_fma`,
`fp_unary`) directly with `f32` operands; it does not run actual VFP
instructions, so encoding helpers (`vfp_sd`, `vfp_sn`, `vfp_sm`,
`fpscr_set_nzcv`) are never exercised.** Their dispatch path requires a
QEMU FPU oracle or silicon FPU oracle. Given QEMU 8.2's FPU class is
broken in this environment, **encoding-helper mutations in
`execute_fpu.rs` will surface as oracle_survived in V2**, but they would
be caught by `qemu_diff_m33 --classes fpu` (when QEMU 10.2 / fixed env)
or by silicon FPU validation (`silicon_periph_diff_rp2350` /
`silicon_isr_diff_rp2350` exercise FPU stacking but not single-instruction
encoding).

**Implication for V2 triage**: a vfp_sd-style "oracle_survived" verdict in
V2 doesn't cleanly distinguish Bucket-4 (genuine equivalent) from Bucket-2
(real oracle gap exposed by the QEMU 8.2 FPU-class breakage). V2 will need
a follow-up note in the report calling these cases out by inspection
rather than measurement, OR a V2.1 with the FPU class restored. For now,
list them as "ambiguous: covered only by qemu_diff_m33 fpu (broken env)".

### Stage 6 — V2 first-pass (in progress, parallel with sweep)

Started 2026-04-29T12:10:59Z, **before** the sweep finishes — taking the
growing missed.txt as input with `--skip-done` so the runner picks up
new entries on subsequent re-launches without re-testing completed
mutants. Initial run sees 281 missed entries; the sweep will append
more before it concludes.

`scripts/v2_mutation_run.sh first-pass` is the launcher. nohup + setsid
+ disown so the V2 process survives the parent shell.

**Resource sharing**: cargo-mutants snapshots source at startup, then
runs all per-worker builds in `/tmp/cargo-mutants-*/target/`. V2 modifies
source in-place in the checkout and rebuilds in `target/release/`. The
two are isolated at the cargo target level — V2 can run in parallel with
the sweep without polluting either side. CPU/IO compete (28 cores absorb
it) but are not a correctness concern.

**First V2 finding — `classify_is_pure` cluster (mdrp2040/decode.rs)**:

V1 reported 0 survivors in `mdrp2040/decode.rs`. V2 reports **36/36
survived oracle** so far. Re-classification on inspection: the classifier
functions (`classify_is_pure`, `classify_thumb16_pure`,
`classify_thumb16_misc_pure`, `classify_thumb32_pure`) are **dead code
in the current mdrp2040 build**. The commit that added them
(`42ee533` "mdrp2040: port RP2350 decode cache") says explicitly:

> is_pure fast-path (skip Bus side-effects when decode is pure)
> deferred for a follow-up iteration.

Trace: `classify_is_pure` writes `FLAG_PURE` into `DecodedOp.flags`;
`is_pure()` reads it; **but nothing in the production code reads `is_pure()`
on mdrp2040** (`grep -rnE "\.is_pure|is_pure\(\)" crates/mdrp2040/`
returns zero hits). The mdrp2350 sibling does have one consumer
(`mdrp2350/core/decode.rs:284`) plus a tests.rs assertion suite.

Verdict: **all 79 mutants on the mdrp2040 classifiers are Bucket 4**
for the current codebase — the function output isn't observable, so
no oracle can catch them. They become Bucket 3 the day the deferred
fast-path consumer lands (it will route past Bus side-effects when
`is_pure()` is true, so wrong classification will diverge the QEMU
end-state diff).

The V2 oracle replay is doing exactly what it was built to do — telling
us that "82 % of V1's survivors are oracle-caught" was the wrong frame
for *this* file: the mutations are equivalent under the current
observability contract, not "caught by oracle but missed by tests".

**Proposed actions (queued for V3 / follow-up)**:
- Direct unit tests for the classifier functions matching the mdrp2350
  test pattern in `crates/mdrp2350/src/tests.rs` (already covers it
  for the M33 sibling). Pure functions of 16-bit / 32-bit opcode bits;
  trivial to enumerate.
- OR: gate the classifier with `#[cfg(feature = "fast_path")]` until
  the consumer lands. Avoids carrying observability gaps.
- OR: `#[mutants::skip]` annotations until consumer lands. Lowest-cost
  noise reduction; doesn't fix the underlying gap.
