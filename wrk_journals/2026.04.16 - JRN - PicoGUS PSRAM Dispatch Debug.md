## Goal

Close in on **why the PicoGUS firmware never dispatches DRAM writes to
PSRAM** despite 127 K valid autopushes reaching the PIO0 RX FIFO.

End state: a definitive, data-backed answer to *whether* the blocker is
(1) capture-loss of critical setup events (0x343 register-select,
0x344 address word) **or** (2) the firmware reaching the dispatch
stage but the DMA→PIO1 TXF0 path silently failing.

## Starting state

Three PIO bugs landed earlier today:
- INT routing (`4944d3d`)
- Per-SM alias dispatch (`b239366`)
- ISA mux timing (`81873b9`)

Net effect: 127 K ISA events autopushed with correct addr/data (25 % of
514 K fired). PSRAM still 0 non-zero bytes. PIO1 SM0 TX FIFO never
written. Two live theories:

1. **Capture loss** — critical setup events among the missing 75 %, so
   firmware sees DRAM writes with stale/no register context.
2. **DMA-side gap** — firmware reaches dispatch, but DMA → PIO1 TXF0
   path silently fails (channel config quirk, trigger alias, etc.).

#### Theory 2: **DEAD**

Firmware reaches DMA dispatch. DMA CH0 programmed with
`WRITE_ADDR=0x50300010` (PIO1 TXF0), TREQ=8 (PIO1-TX0), EN=1,
`ever→TXF=0x1`, xfers=**143 324**, DREQ seen YES. Verdict:

> `ENGINE SERVED, PIO DIDN'T CONSUME (CH0 xfers=143324) —
> investigate PIO1 SM0 pull/shift or TX FIFO sink plumbing`

CH1 = 0x50300020 → SRAM (PSRAM RX path, 2 triggers), CH2 also
configured for TXF0 (chain-to, never triggered).

PIO1 SM0 PC=0x19, running, autopull enabled, PULL_THRESH=8. FSTAT
says TX empty. PSRAM CS falling edges = 2 (i.e. 2 SPI frames ever
started). PSRAM buffer all zero. So 143 K DMA byte-writes to PIO1
TXF0 are going *somewhere* but not driving the PSRAM SPI program.
This is a **new class of bug** not on either theory.

#### Theory 1: **inconclusive — diagnostic decode bug**

Reconciliation invariant holds:
`captured(0) + misattr(126 863) + orphans(0) = 126 863 == autopush_count`.

But `captured = 0` everywhere and `misattr = 126 863` everywhere
is a tell. 100 % misattribution means every physical push decoded
to an (addr, data) pair that didn't match the event we just fired.

Root cause: **the decode formula in the harness is wrong**. PIO0
SM0 `SHIFTCTRL=0x012b0000` → `IN_SHIFTDIR=0` (shift left). The
autopushed ISR layout with left-shift across two INs (10 then 8
bits) is:

```
ISR = (addr & 0x3ff) << 8 | (data & 0xff)
```

So correct decode is `data = word & 0xff; addr = (word >> 8) & 0x3ff`.

The HLD and implementation used the right-shift formula (`addr =
(word >> 14) & 0x3ff; data = (word >> 24) & 0xff`), which is wrong
for this SM.

Secondary signal worth keeping: clustering table shows **zero
captures in deciles 0–4** (firmware boot), then captures ramp to
20–40 % in deciles 5–9. Theory 1 as framed ("setup events lost
because PIO can't keep up") may be partially alive for the
second-half captures, but we can't tell until the decode is fixed.

### Phase 6 — TX-FIFO push-drop theory **REFUTED** (complete)

Instrumented `PioFifo` with `push_success` / `push_drop` counters.
Diagnostic output:

```
PIO1 SM0 TX: push_ok=143324     push_drop=0
```

**Zero drops.** All 143 K DMA byte-writes successfully landed in the
PIO1 SM0 TX FIFO. The DMA → `bus.write8` → byte-replicate →
`PioBlock::write32` → `tx_fifo.push` path is working correctly.

But PIO1 SM0 TX FIFO level at end = 0 (empty) — so SM0 consumed all
143 K pushes. Yet:
- CS falling edges: 2 (should be tens of thousands)
- MOSI (GPIO3) pad_out = 0
- PSRAM non-zero: 0

**New hypothesis:** PIO1 SM0's program fires 2 SPI transactions
successfully (initial PSRAM init / chip-id reads, perhaps), then
enters a state from which it can't escape — possibly:
- Waiting on MISO (GPIO0) feedback that our PSRAM model never
  drives.
- Waiting on an IRQ/cross-SM signal that never asserts.
- SM0's program has a loop we don't understand that gates further
  work on some external condition.
- Our PIO model fails to wire sideset/out to GPIOs for *some*
  program shapes even though CS worked for the first two frames.

### Phase 9 — JMP X-- / Y-- bug FIXED

**Root cause:** `crates/mdpicoem-common/src/pio/sm.rs:576-586` decremented
`self.x` / `self.y` **unconditionally** inside the condition body, then
returned "was-nonzero" as the jump decision. Correct semantic per RP2040
datasheet §3.4.4: decrement ONLY on the taken branch.

With the bug, `X=0` at loop exit would wrap to `0xFFFFFFFF` on the
fall-through cycle and the *next* re-entry would see X as `0xFFFFFFFE`.
Any loop using `JMP X--` as "loop-N-times-then-fall-through" would
iterate forever.

Fix (3 lines per condition):
```rust
// Before
let was_nonzero = self.x != 0;
self.x = self.x.wrapping_sub(1);
was_nonzero
// After
let was_nonzero = self.x != 0;
if was_nonzero {
    self.x = self.x.wrapping_sub(1);
}
was_nonzero
```

Same change for Y--. Three RED unit tests added and witnessed (X=3 loop
exits at X=0, Y=2 loop exits at Y=0, X=0 fall-through without wrap).

**Test counts post-fix:** mdpicoem-common 115/0, mdrp2040 513/0,
mdrp2350 893/0, mdpicoem-harness lib 311/0. No existing test flipped.

### Phase 8 — SMOKING GUN: infinite JMP X-- inner loop

Instrumentation added: per-slot PC visit counters + pad_out transition
counters. The run reveals:

```
PIO1 SM0 PC visits (slots 0x0e..0x1f):
  [0x16]=1   [0x17]=1   [0x18]=1           (entry visited ONCE)
  [0x19]=1,146,584   [0x1A]=1,146,584     (inner loop)
  [0x1B]=0   [0x1C]=0   [0x1D]=0   [0x1E]=0   [0x1F]=0  (never reached)
```

SCK toggles = 2,293,168 = 2 × 1,146,584. So sideset DOES apply to
`pad_out` per instruction — that path is fine.

The inner loop at slots 0x19/0x1A runs 1.14 M iterations without ever
exiting. Slot 0x1A is `JMP X-- 0x19`. Per RP2040 datasheet §3.4.4,
`JMP X--` jumps IF X != 0 and decrements X. If X == 0, it should fall
through without decrementing. Since the loop never exits over 1.14 M
iterations, our emulator's `JMP X--` must be either always-jumping or
failing to observe X reaching 0.

Dispatched: agent to write RED unit tests exercising JMP X-- / Y--
termination, locate the bug, fix minimally, and rerun the harness.

### Phase 5 — Re-run with corrected decode (complete)

After the left-shift decode fix landed (harness `0.27.1`,
`(addr, data) = (word >> 8 & 0x3ff, word & 0xff)`), clean Theory 1
data:

| Port class | fired | captured | drop% |
|---|---|---|---|
| 0x343 `<- 0x43` (DRAM-low reg) | 102 898 | 24 705 | 76.0 % |
| 0x343 `<- 0x44` (DRAM-high reg) | 102 898 | 24 320 | 76.4 % |
| 0x344 `addr_lo` | 205 836 | 26 206 | 87.3 % |
| 0x344 `addr_hi` | 205 836 | 31 100 | 84.9 % |
| 0x347 `<- data` (DRAM byte) | 102 898 | 20 459 | 80.1 % |

Reconciliation invariant clean:
`captured(126 848) + misattr(15) + orphans(0) = 126 863 == autopush`.

**Theory 1 is dead.** Setup events (`0x343 <- 0x43/0x44`) capture at
~24 %, data events (`0x347`) at ~20 %, 16-bit address writes (`0x344`)
at ~13-15 %. All roughly comparable — no differential loss that would
make the firmware see data writes without address context. The 80 %
overall drop is a uniform effect, dominated by:

1. First 50 % of the trace has **zero** captures (firmware boot +
   PSRAM init — PIO0 SM0 isn't enabled yet).
2. During the live period (deciles 5–9), ~38 % of fires are
   captured; the remaining ~62 % are lost to PIO clkdiv=2 and
   firmware ISR drain rate not keeping up.

Both effects are expected given the hardware model. Neither class is
specifically disadvantaged.

So: the firmware **does** see the setup sequences (24 % is plenty of
`0x43 + 0x44 + addr + data` triplets to program the DRAM address
register), but PSRAM is still empty. The blocker is downstream of
capture — at the DMA→TXF0 sink or the PIO1 SM0 pull.
