## Goal

Extend `paced_bench_rp2040` and `paced_bench_rp2350` with four (RP2040) /
five (RP2350) named workloads that span the cost envelope from floor
(single-core ALU, no peripherals) to realistic worst case (dual-core
same-bank + active PIO + SIO GPIO toggling). Remove `--dual-core` flag
(workloads now own their core count).

## Stage 0 — HLD corrections

Six changes applied to the HLD before implementation:

1. **`peripheral` loop shape fixed** — added ALU back in (was
   `STR + B`, now `ADDS + STR + B`). Code sketch now matches prose.
2. **`contention` directionality clarified** — added explicit note
   that contention cycles are counter-only and don't consume host
   compute, so unpaced MHz under contention will be *higher* than a
   naive 2× scaling predicts. This was wrong in the draft.
3. **`contention` bank layout tightened** — specified core 1 at
   `0x2000_0040` (16 words past core 0, same bank), noted the
   `.wrap`-bank pattern causes ~half-rate contention firing, placed
   stacks in scratch banks to keep push/pop out of the fetch signal.
4. **`stress` per-core layout specified** — core 0 runs peripheral
   pattern, core 1 runs ALU pattern, both in bank 0. Asymmetric on
   purpose (symmetric SIO would serialise and hide contention).
5. **Setup complexity acknowledged** — HLD now says ~30–50 lines of
   MMIO writes per bench, factored into
   `setup_pio0_sm0_wrap` / `setup_gpio_output` helpers. Also
   added rustdoc warning on `mmio_read32` about side-effect reads.
6. **Verification rewritten** — dropped the bogus "monotonic
   `basic > peripheral > contention > stress`" claim. Pivoted to
   paced verdict as the primary user-facing signal, with expected
   unpaced MHz pattern as diagnostic-only context.

Also softened the M33 QEMU-NVIC claim in `tech_debt.md` from "known
weaker" to "believed to be less mature, needs confirmation".

Status: **complete**. Committed as `8d99752`.

### Devil's-advocate findings

**BLOCKER** — RP2350 `contention`/`stress` cannot exercise bank
contention. `crates/mdrp2350/src/lib.rs:151-180` runs cores
**sequentially** (each drains quantum, then the other) — no
per-instruction interleave like RP2040's `lib.rs:211-241`. Grep
of `note_sram_access` / `contention_check_active` / `core0_bank_
touched` in `crates/mdrp2350/` returns zero production-path hits.
Comment at `paced_bench_rp2350.rs:335` claiming otherwise is a
lie. Measured RP2350 `contention` is a clean 0.5× `basic` —
precisely what "two cores serialised with no cross-talk" gives.

**COMPILE-SAFETY** — Commit `5f0e118`'s `lib.rs` changes include
ext-mask merges in `reset()` and `update_gpio()` that reference
fields (`external_gpio_in_override`/`mask` on rp2040,
`gpio_external_in`/`mask` on rp2350) **not defined in this commit**.
They live on the concurrent PicoGUS engineer's uncommitted
`bus/mod.rs` work. Compiles on the current working tree only
because those fields are there unstaged; on a clean checkout of
`5f0e118`, mdrp2040 and mdrp2350 won't build.

Regression verdict on RP2040 `basic` 210.9 → 166.6 MHz: **drift +
noise, not this PR**. Between `0ef90d2` and `5f0e118`, at least
one PicoGUS commit (`3396c93`) adds per-quantum PSRAM tick work
inside `update_gpio`. Single-run variance on Windows unpaced
±5–10%. No regression attributable to this PR.

Workload mechanics otherwise sound: PIO SM0 runs, SIO `STR
[GPIO_OUT_XOR]` reaches `sio_write32`, literal-pool offsets
correct (LDR from PC=0x2000_0004 → literal at 0x2000_000C where
bench pokes SIO address), core-1 wake handled per-chip.

Additional:
- **D1** — RP2350 core-1 stack top `0x2008_2000` is one past SRAM9
  end (`0x80000-0x81FFF`). First push would fail silently. Move
  to `0x2008_1FFC`.
- **D2** — RP2350 `Stress` comment "exercises the contention
  accounting on core 1" is false. Fix comment.
- **D3** — RP2350 `contention` reports exactly half `basic` —
