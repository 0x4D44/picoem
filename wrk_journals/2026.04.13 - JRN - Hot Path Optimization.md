# Journal: Hot Path Optimization

**Date:** 2026-04-13
**Feature:** Reduce emulator dispatch overhead identified by flamegraph
**Status:** IN PROGRESS

## Flamegraph Findings

Profiled unpaced at ~85 MHz (no PGO, debug=2, lto=false). Key self-time:

| Category | Self % | Notes |
|---|---|---|
| `CortexM33::step()` | 31% | Half is core 1 halted check (called for nothing) |
| `condition_passed()` | 21% | Pure leaf, called every cycle |
| Bus fetch path | 20% | contention + bank calc + wait for every read16 |
| `execute_thumb16()` | 9% | Actual instruction work |
| `decode_execute()` self | 5% | Decode dispatch |

Actual instruction execution is only 9% of time. 72% is dispatch overhead.

## Three Optimization Targets

### Opt 1: Skip core 1 step() when halted (~15% expected recovery)
Currently Emulator::step() unconditionally calls cores[1].step() even when
halted. Each call is a function call + halted check + return. At ~80M cycles/sec,
this is ~15% of all samples.

Fix: check `cores[1].is_halted()` in Emulator::step() before calling.

### Opt 2: Inline/optimize condition_passed() (~10-21% expected recovery)
Called every cycle as a separate function. Check if #[inline(always)] is present.
If not, add it. If already inlined, examine the condition evaluation logic for
unnecessary work (e.g., a 15-arm match when only a few conditions are common).

### Opt 3: Fast-path bus read for common case (~5-10% expected recovery)
Every instruction fetch goes through check_contention → bank_for_address →
sram_bank_wait → actual read. For single-core SRAM with no contention, most
of this is wasted. A fast path could bypass the full dispatch.
