# Devil's Advocate Review R3

Date: 2026-04-14
Target: `wrk_docs/2026.04.14 - HLD - Threaded Dual-Core Emulation.md` (v3.0.0)
Reviewer posture: find remaining CRITICAL issues that should block acceptance.
Prior rounds: Performance, Concurrency R2, Senior Rust R2, Devils Advocate R1/R2.

## TL;DR

V3 addressed the honest throughput target, the Phase 0a decision gate, the
field-ownership table, panic/WFI/stop handling, SeqCst for DMB/DSB, and
exclusive-monitor ordering. It is substantially improved.

**However, five issues still rise to CRITICAL** — they are not cosmetic, and
they will each burn implementation weeks or produce a false-positive Phase 0a
"go" that leaks into Phase 1+. Fixes are small edits to the HLD, not rewrites.

Below, in priority order.

---

## CRITICAL-1: Phase 0a's workload and gate measure the wrong thing

This is the most important finding. The gate is:

> "If core 1 active ratio ≥ 20% on representative workloads, proceed to
> Phase 0b."

Two problems:

**(a) The synthetic workload is ADDS-in-a-loop with no coupling.** The existing
`paced_bench.rs` dual-core mode (the only actually-existing dual-core workload
in the tree; `d:\language\mdrp2354\crates\mdrp2354-test-harness\src\bin\paced_bench.rs:88-100`)
is two independent infinite `ADDS Rx, Rx, #1` / `B .-2` loops in separate SRAM
banks:

```
emu.poke(0x20000000, 0x1C40_2001);  // core 0: MOVS R0,#1 | ADDS R0,R0,#1
emu.poke(0x20001000, 0x1C49_2101);  // core 1: MOVS R1,#1 | ADDS R1,R1,#1
```

Zero shared-memory writes, zero SIO FIFO, zero doorbells, zero MTIME consumers,
zero spinlocks. This is literally the best possible case for threading — it's
the control, not the test. If the HLD intends Phase 0a to measure
`paced_bench --dual-core` as-is, both "core 1 active ratio" is 100% and the
Phase 0a gate says "go" regardless of whether real firmware ever will.

**(b) "Core 1 active ratio ≥ 20%" is orthogonal to the bottleneck.** Consider
the case where core 1 spends 40% of its cycles spinning on a
`SIO_SPINLOCK` (which lives in `Sio`, which in threaded mode lives behind
whatever protects the shared SIO struct, which is the hot one). Core 1 is
"active" by the proposed metric, but every cycle it's adding cross-core
coherence traffic on a single cacheline. The threaded implementation
serializes on spinlock access, barriers run at zero useful work, and 2x
becomes 0.8x. The gate waves it through.

**What Phase 0a must actually measure, minimum:**

1. Core 1 active ratio (kept).
2. Cross-core shared-memory write rate per quantum (W/R to SRAM written by the
   other core within the quantum — this drives MESI traffic).
3. SIO access rate per core (spinlocks, FIFOs, doorbells — these serialize
   under `ThreadedSio`).
4. PPB cross-core access rate (rare but catastrophic if present: e.g. one
   core writing another's NVIC pending).

And the gate must be compound: core 1 active ≥ 20% **AND** SIO contention
rate per quantum is bounded **AND** cross-core SRAM write rate is below
the level where 5–15% coherence hit blows the budget.

**Fix:** rewrite §"0a. Workload study" to enumerate the four metrics above,
define thresholds for each, and explicitly state that
`paced_bench --dual-core` is disqualified as "representative workload"
because it has no cross-core coupling.

## CRITICAL-2: The Phase 0a synthetic workload doesn't exist

> "A dual-core synthetic: bootrom launches core 1 via SIO FIFO, both cores
> execute a hand-written Thumb loop with realistic memory access patterns
> (loads, stores, ADDS, conditional branches, SIO sync)."

Who writes this, and over what calendar time? It is not in the 7–9 week
schedule. Phase 0a says "1 wk" for "Workload instrumentation + study." Writing
a realistic dual-core Thumb test that actually exercises shared SRAM, FIFO
send/recv, spinlock-guarded critical sections, and mtime-based scheduling is
itself several days of careful engineering — and until it exists, the
"bootrom + synthetic" becomes "bootrom alone", whose dual-core behaviour
today (per `crates/mdrp2354/src/tests.rs:5701`) is "core 1 sleeps in WFE after
bootrom init". Core 1 active ratio on bootrom-alone is ~0%.

If Phase 0a is run against bootrom alone, the gate fails and we shelve.
If Phase 0a is run against the non-existent synthetic, we build the
synthetic first (favourable test data; see Arthur's review prompt §6),
get a "go", then discover the real workload is nothing like it.

**Fix:** Either (a) budget Phase 0a as 2 weeks including synthetic workload
authorship with explicit acceptance criteria for what the synthetic must
stress, or (b) make the gate contingent on finding ANY existing workload
(even OneROM's fixture crate if partially written) that has non-trivial
cross-core activity. Don't let "we'll write the benchmark later" ride.

## CRITICAL-3: x86_64-only Pacer is silently load-bearing; threaded target
            is explicitly "x86_64 host, Windows"

Arthur asked about host-environment assumptions. The HLD is silent on host
architecture. Reality (from the codebase):

- `Pacer` is `#[cfg(target_arch = "x86_64")]` — whole struct gated
  (`crates/mdrp2354/src/pacer.rs:253`).
- `paced_bench` thread pinning is `#[cfg(target_os = "windows")]` using raw
  `SetThreadAffinityMask` (`crates/mdrp2354-test-harness/src/bin/paced_bench.rs:7-46`).
- TSC calibration is `rdtscp` + `Instant::sleep(50ms)`, and `require_constant_tsc()`
  panics on CPUs without invariant TSC.
- Senior Rust R2 §335 flagged `core_affinity` is needed and named macOS as
  "no supported API".

The HLD describes `Worker 0 (pinned)` / `Worker 1 (pinned)` as a structural
element of the topology (§"Thread topology"). The pinning mechanism is
undefined. macOS cannot pin at all without Mach-specific `thread_policy_set`
calls that Apple discourages; `core_affinity` crate silently no-ops on macOS.
On Windows, `SetThreadAffinityMask` on two threads pinned to hardware cores
0 and 1 interacts non-obviously with the TSC calibration: if the scheduler
briefly migrates a worker despite the affinity mask (which it can, under
system load), `rdtscp` returns a value from a different TSC domain in one
quantum. The single-threaded Pacer does not face this; threaded does.

This is not fatal, but the HLD should commit to:

1. **Supported host platforms explicitly.** "x86_64 Windows primary; Linux
   best-effort; macOS declared out of scope." (Or pick your poison.)
2. **Pinning strategy stated.** `core_affinity` crate, or hand-rolled
   per-OS behind `cfg`. Phase 3 in the schedule.
3. **Pacer owns calibration of worker 0 only.** Worker 1 doesn't time.
   Calibration runs on worker 0's core. If the calibration thread migrates,
   the whole calibration is garbage — already true today but harder to
   notice single-threaded.

Without this, the implementation in Phase 5 will hit a wall of
"why does per-core MHz vary 10% between runs on the same machine"
and blame cache coherence when the culprit is TSC sync.

**Fix:** Add a "Host environment" section to the HLD with platform matrix,
pinning strategy, and an explicit note on TSC domain assumptions
(same-socket x86_64 = one TSC domain = safe; multi-socket = unsafe;
ARM host = Pacer doesn't work at all).

## CRITICAL-4: Subsystems missing from the thread-topology diagram

The HLD §"Thread topology" shows two workers stepping cores, and worker 0
doing "dispatch cross-core events: SEV wakes, timer ticks, WFI wake check,
check stop_signal." That's it.

What today's single-threaded `Emulator::step` does every cycle
(`crates/mdrp2354/src/lib.rs:126-156`) that the HLD does NOT place:

1. **PIO**: `for pio in &mut self.bus.pio { pio.step(gpio_in); }` — three
   PIO blocks step every system cycle. `PioBlock::step` drives state
   machines, FIFO depth, IRQ assertion. PIO is a per-cycle coroutine.
   Who steps PIO in threaded mode? Worker 0? Both workers? A third thread?
   Not specified. Each answer has real cost (worker 0 overhead is
   ~10μs/ms worst case; third thread means three cores needed).
2. **GPIO merge**: `self.update_gpio()` — merges SIO out + PIO out into
   `gpio_in`. Same question. `gpio_in` is read by BOTH cores (and by
   PIO itself — the PIO step above feeds from it). This is a classic
   "who computes the latch" problem and the HLD doesn't answer it.
3. **MTIME**: `self.bus.sio.tick_mtime()` — SIO MTIME is a RISC-V-style
   64-bit counter with per-core compare values and per-core interrupt
   (`crates/mdrp2354/src/sio/mod.rs:395-411`). In threaded mode, mtime
   is cross-core state (one counter, two consumers). Does it live in
   `ThreadedSio`? Yes implicitly, but then who increments it? Worker 0
   once per quantum? That's no longer per-cycle granularity.
4. **SIO integer divider**: `crates/mdrp2354/src/sio/mod.rs:90`. Per-core,
   stateful: firmware writes DIVIDEND/DIVISOR, waits N cycles, reads quotient.
   The `divider: [Divider; 2]` array is per-core but lives on the shared
   SIO struct. Under `ThreadedSio`, this migrates — but the HLD's
   `ThreadedSio` sketch says only FIFOs + spinlocks + sticky flags.
   Divider is missed.
5. **SIO interpolators**: `interp: [[u32; 32]; 2]` at
   `crates/mdrp2354/src/sio/mod.rs:104`. Per-core interpolator state.
   Same miss as divider.
6. **Doorbells**: `doorbell_pending: [u8; 2]`. These are cross-core
   interrupts (one core writes DOORBELL_OUT_SET on core N to pend an
   IRQ on core 1-N, per `crates/mdrp2354/src/sio/mod.rs:216-218`).
   Doorbells are NVIC-pending triggers. In threaded mode, they are
   cross-core NVIC pokes — exactly the scary case the HLD handwaves as
   "dispatch cross-core events". But doorbells can fire on the *inner*
   step, not only at quantum boundaries — the other core may
   immediately take the interrupt, drop out of WFI, etc. If resolution
   is deferred to quantum boundary, you introduce up to Q cycles of
   latency before the peer sees the doorbell, which is visible firmware
   behaviour (firmware can measure this by reading mtime).

**Fix:** Add §"Cross-core event model" to the HLD that specifies, for each
of {PIO step, GPIO merge, MTIME tick, divider state, interp state,
doorbell pend}, (1) where the state lives, (2) who modifies it, (3) when
changes become visible to the peer. "Every quantum boundary" is the
default answer, but for doorbells and mtime, the firmware observability
of Q-cycle latency needs a stated tolerance ("we accept up to 150 cycles
of inter-core IRQ latency" — is that OK for OneROM?).

## CRITICAL-5: Peripherals lock-order invariant is stated without
            enforcement mechanism

> "**Lock order (documented, enforced by `debug_assert`):**
> `clocks` < `qmi` < `resets` < `apb` < `ahb`."

How is a `debug_assert` enforcing this? A `debug_assert` fires when a
condition is false. Which condition? There are two possible mechanisms
and the HLD doesn't say:

(A) Each `lock()` call asserts that no higher-ordered mutex is currently
held by this thread. This requires thread-local state tracking "which
sharded mutexes does this thread hold", a ~40 LOC RAII wrapper, and
a discipline of routing ALL lock acquisitions through it. If any code
calls `.lock()` directly, the discipline breaks. That's a hot path —
every peripheral register read takes a mutex — so the overhead adds to
the per-instruction cost.

(B) A static lattice check, which only works if all lock orderings are
statically analyzable. They are not: `Bus::read32` dispatches on
address at runtime, so the lock held per call is dynamic.

Without specifying which, this is TBD in disguise. Worse, the
**non-debug build has no protection at all** — two threads can deadlock
in release mode with only `debug_assert` guarding order, and this is
explicitly the scenario where deadlock must not happen (real-time
threaded emulator, production).

**Fix:** Commit to mechanism (A) with a thread-local lock-order vector
and a `#[must_use]` RAII guard. Acknowledge in the HLD that the
sharded-mutex hot path adds a per-lock overhead (several ns) and that
peripheral-heavy firmware will feel it. Also note: with five mutexes
and 5! = 120 orderings, the claimed linear order is just a choice —
document WHY `clocks < qmi < resets < apb < ahb` (the stated rationale
"matches boot sequence" is backwards: boot-order determines which lock
is acquired first in a sequence, not which lock must sit earlier in
a partial order).

Alternative worth considering: skip the lattice; use one peripherals
mutex and measure. If contention is the bottleneck, re-shard. This is
the path Senior Rust R2 already hinted at. Premature sharding is
premature optimisation. The HLD's "If profiling shows a single mutex
is hot, split further" is good — but the HLD still proposes five
mutexes up front. Pick one: coarse to start, split on evidence.

## Non-critical issues I'll note briefly (not blockers)

- **"We proceed based on bootrom data"** combined with "bootrom data
  shows core 1 in WFE after init" (tested at `tests.rs:5701`) means
  bootrom alone fails the 20% gate. The HLD acknowledges the
  chicken-and-egg but doesn't commit to what that means for Phase 0a's
  go/no-go: will we accept bootrom-does-not-activate-core-1 as a "no"?
  Probably yes, and then CRITICAL-2 bites us for the synthetic that
  saves the proposal.
- **"Phase 0a — Workload instrumentation + study (1 wk)"** with zero
  instrumentation framework in place today is tight. This is a cycle
  profiler for the emulator that emits per-quantum histograms of
  decode/execute/WFI/contention/peripheral fractions. Worth writing, but
  not a freebie week.
- **Loom tests and TSan CI**: bullet in validation, but no line item
  on the schedule. Senior Rust R2 §335 already flagged TSan adds CI
  runtime (~2–3x for integration tests under TSan). This is not
  "add as part of Phase 3" handwaveable.
- **Memory type mismatch — easy to get wrong.** `Memory.sram` is
  `Vec<u8>` today. The HLD replaces with `Box<[AtomicU32]>`. Every
  unaligned u8/u16 access (of which there are many in Cortex-M
  firmware) becomes atomic-load + shift + CAS-loop-store. The
  HLD acknowledges this but the 5–15% coherence estimate does not
  include u8/u16 CAS-loop overhead on hot byte-accesses, which can
  be ≥50% more expensive than plain. Tentative: add
  "byte/halfword access overhead" as a separate line item to the
  throughput model and re-check the math.
- **XIP conflation.** HLD: `xip: Box<[AtomicU32]>, // if writable via QMI`.
  XIP (flash) is 16MB nominal, read-mostly, writes go through QMI.
  XIP SRAM (16KB at 0x1C00_0000) is a separate region that IS
  writable directly. Today these are handled separately
  (`bus/mod.rs:50-52`). The HLD treats them as one. Minor but will
  surface in Phase 1.
- **ExitReason::BothWfi**. The coordinator's "no external wake source"
  test is "no peripheral has an active timer that will fire before
  `duration` elapses." This requires enumerating every
  "will-eventually-fire" source: MTIME compare match (per-core),
  SysTick (per-core PPB), any future timer peripheral, USB SOF,
  watchdog. Phase 5 bullet says "WFI deadlock handling" — this is
  a design problem, not a bug-fix problem. Move it earlier or commit
  to the conservative over-approximation (if anything could possibly
  fire, don't early-exit) and accept that BothWfi becomes rare.

## Does an easier alternative still exist? (Arthur's question 9.)

Round after round we've kept saying "decode cache as follow-up". V3 still
does: "Hitting 150 MHz per core requires additional interpreter work (decode
cache or targeted JIT). That is a **follow-up**." That's fine, but:

The HLD presents the comparative case implicitly, not explicitly. Where
is the estimate "decode cache alone gets us single-core to X MHz; threading
alone to Y MHz; both to Z MHz"? Phase 0a is a gate for threading, but it's
not a gate *against* decode cache. If Phase 0a says no, HLD says "do decode
cache instead." But we don't have a Phase 0a equivalent for decode cache
— no workload study, no threshold. The HLD should either:

(a) Add a parallel Phase 0a' for decode cache ("measure decoder time as
fraction of total; if ≥ 30%, decode cache is viable"), or
(b) Commit that decode cache is always viable follow-up, threading is
the high-risk-high-reward pre-requisite question.

My gut: decode cache is much lower risk, probably 2x alone on tight loops,
and stackable with future threading. If I'm Arthur making the call in three
weeks after Phase 0a instrumentation ships, I want the HLD to give me a
clean A/B comparison, not "threading or shelve."

## Success metric (Arthur's question 10.)

> "`paced_bench --threaded --dual-core` must show ≥110 MHz per core."

The existing `paced_bench --dual-core` is two disjoint `ADDS` loops in
different SRAM banks (see CRITICAL-1). If the threaded implementation
passes that and only that, we declare success, then shove OneROM at it
and it fails because real workloads have coherence traffic. The metric
must be against the representative workload from Phase 0a, not the
ADDS-loop synthetic.

## Bottom line

V3 is closer to implementable than V2, but Phase 0a's gate and its
workload are the Achilles heel: it's a gate that can't reject bad
proposals because the metric and the test don't measure what will
matter. Fix the five criticals above and this can proceed. Without
fixing at least CRITICAL-1 and CRITICAL-2, Phase 0a is theatre and we'll
end Phase 5 with a 110 MHz threaded run on ADDS loops that doesn't hold
up on anything real.

## Recommended HLD revisions (minimal set to unblock)

1. Rewrite §"0a. Workload study" with four explicit metrics and
   compound gate (CRITICAL-1).
2. Extend Phase 0a to 2 weeks to include synthetic workload
   authorship with defined cross-core stress requirements (CRITICAL-2).
3. Add §"Host environment" specifying x86_64, pinning mechanism,
   platform support matrix (CRITICAL-3).
4. Add §"Cross-core event model" covering PIO, GPIO merge, MTIME,
   divider, interp, doorbell (CRITICAL-4).
5. Specify lock-ordering enforcement mechanism (A) with thread-local
   discipline OR drop to single Peripherals mutex until measurement
   justifies splitting (CRITICAL-5).

None of these require re-architecture; all are clarifications of
what's already implied. Total HLD delta: perhaps +80 lines.
