# 2026-04-22 — PicoGUS firmware rebuild with UART stdio

## Goal

Rebuild `picogus-v4.0.0` from source with `pico_enable_stdio_uart(target 1)` so that `printf`/`puts` in the firmware drain through our UART TX tap (landed yesterday in `crates/mdrp2040/src/peripherals/uart.rs`) and tell us why the GUS reset gate (`(GUS_reset_reg & 0x03) != 0x03` at `gus-x.cpp:1734`) never opens during MIDI replay.

Side benefit of rebuilding: we get the **.elf with symbols**, which lets us locate `GUS_reset_reg` (and every other static) in SRAM without shot-in-the-dark probing.

### Step 11 — firmware-side tracing: `printf` in GUSReset + write_gus

Rebuild the firmware with three targeted printfs:
1. End of `GUSReset()`: prints `[rst] gRegData=0xNNNN  PP->CC` showing the driver intent, the old reg, the new reg.
2. `write_gus` case 0x103 (register select): prints `[103] sel=0x<val>`.
3. `write_gus` case 0x105 (data-high write): prints `[105] sel=0x<sel> data=0x<gRegData>`.

Plain `printf` — `LOG_MSG` is only compiled in on `-DDEBUG` and that would spam every subsystem. Three targeted lines tell us everything about reset-register traffic.

Result on a 2 s replay:
```
[103] sel=0x4C                <- select reset reg
[105] sel=0x4C data=0x0000    <- first write = 0 → reset
[rst] gRegData=0x0000  00->00
[103] sel=0x4C                <- select reset reg again
[105] sel=0x4C data=0x591D    <- second write → reset reg = (0x591D >> 8) & 7 = 0x59 & 7 = 0x01
[rst] gRegData=0x591D  00->01
[103] sel=0x44                <- moves on to DMA regs etc.
...
```

**Headline:** only two GUS-reset register writes happen during the first 2 s of replay — `0x00` then `0x01`. The driver then moves on to other registers and never writes `0x07`. `GUS_reset_reg` is stuck at `0x01`, audio gate stays closed.

The `0x591D` value is a 16-bit word where only the top byte is the actual reset-reg data. Bits: `0x59 = 01011001`. Mask with `7` → `0x01` = master-reset-released, DAC off, IRQ off. Low byte `0x1D` is a stale previous 0x104 write (data-low) that this 0x105 write OR's with `val << 8`.

### Finding — root cause class

The trace contains the correct `0x07` write at ns=300 000. The firmware never sees it as a reset-register write reaching `GUSReset()`. Event loss / data corruption is happening somewhere between the harness's `drive_write_cycle` and the PIO's output-to-firmware hand-off.

Candidates (not yet disambiguated):
1. PIO RX FIFO overflow: trace fires 143k events in the first 1 ms. The PicoGUS firmware's `handle_iow` loop runs on one core and must keep up; if it can't, FIFO (4 deep) drops.
2. Harness `drive_write_cycle` timing too tight: for same-ns event clusters the harness fires events back-to-back with no `advance_to_sim_ns` delay. `WRITE_IDLE_CYCLES=12` between them may not give the PIO program time to restart its `wait 0 gpio IOW` after the handshake cycle.
3. Harness / emulator PIO model has a model bug where the address and data phases aren't cleanly separated (`drive_pins` timing against `in pins, 10` / `in pins, 8`) — but this worked for the very first event at ns=0, so whatever happens is a state-drift issue across events, not a static miswiring.

Candidate 2 is the most likely given that `PICOGUS_IDLE_CYCLES=1000` demonstrably captured more events correctly. Both the address and data should be quiescent on the GPIO lines for long enough between writes that the PIO program can fully wrap back to `wait 1 gpio IOW_PIN` → `wait 0 gpio IOW_PIN` before the next event's falling edge.

### Step 16 — trace ns-cluster analysis

The trace's internal time resolution is coarse (captured from DOSBox-X's PIC clock). Count events by ns timestamp:

```
  217490 2135700     ← 217K events at one timestamp!
  106310 867000
   85410 4320800
   36700 500000
```

**One cluster has 217 490 same-ns events.** Our harness fires events at `target_ns` with `advance_to_sim_ns` — events in the same cluster fire back-to-back with only `drive_write_cycle`'s internal ~60-cycle timing between them. The PIO RX FIFO is 4 deep; at that rate any slow-write event that makes firmware pause (GUSReset, PSRAM SPI, etc.) causes FIFO overflow within microseconds and every subsequent event in the cluster is dropped.

The event-loss is confined to within-cluster because ns-to-ns time (even 100 µs) is ample drain time.

### Step 17 — PIO autopush stall fix attempt

Our emulator's PIO (`mdpicoem-common/src/pio/sm.rs:720`) **silently drops** autopush when RX FIFO is full. Real RP2040 PIO stalls the SM (datasheet §3.5.4). Fixed to stall. All 113 `mdpicoem-common` tests still pass.

But when combined with harness-side backpressure the combined flow deadlocks — harness backpressure loop waits for FIFO level to drop, but the stalled PIO can't advance past `in pins, 8` until the firmware pops, and the harness is blocking firmware by not advancing sim-time. The stall fix is correct, but the harness timing around it needs more work. Reverted the stall fix with a comment; left it as a known divergence from real HW.

### Step 18 — harness backpressure knobs

Added env-var tunables to `drive_write_cycle`:

- `PICOGUS_IDLE_CYCLES` — cycles between events (Phase 0 + Phase 3 idle).
- `PICOGUS_ADDR_HOLD` / `PICOGUS_DATA_HOLD` — phase durations.
- `PICOGUS_BACKPRESSURE_THRESHOLD` (default 2 of 4) — drain if RX FIFO level ≥ this before firing.
- `PICOGUS_BACKPRESSURE_STEP` / `PICOGUS_BACKPRESSURE_MAX` — step granularity and cap.

Added `pio0_sm0_rx_fifo_level` / `pio0_sm0_rx_fifo_drops` methods to `IsaSink` trait, forwarded from `Emulator` via the new `StateMachine::rx_fifo_level()` / `rx_fifo_drops()` accessors.

### Step 19 — confirmed fix

`PICOGUS_BACKPRESSURE_THRESHOLD=0 PICOGUS_IDLE_CYCLES=5000` + 400 µs of trace replay:

**`GUS_reset_reg = 0x07` at probe.** The trace's `0x07` reset write DID reach `GUSReset()`. The bug was purely `WRITE_IDLE_CYCLES=12` being too tight for same-ns clusters; 5000 cycles (≈ 13.5 µs sim-time at 370 MHz) between events is enough for the firmware's `handle_iow` path to drain a slow write (e.g. `GUSReset` takes ~1-2 kcycles).

This establishes:
- Root cause of silence: PIO RX FIFO overflow on within-cluster event fast-fire.
- Work-around: `PICOGUS_IDLE_CYCLES=5000` knob, no emulator model changes required.
- Proper fix (for a future session): PIO autopush stall + ISA bus IOCHRDY feedback to harness.

### Step 23 — 50 ms run completed (20 min wall)

Results from `--duration 0.05 --post-roll 1.0 PICOGUS_IDLE_CYCLES=5000`:
- `probe 0x2001d976 = 0x07` — reset gate opens ✓
- `pio0 sm0 rx fifo drops: 0` — FIFO never overflows ✓
- `writes_fired: 514502` — harness fired every trace event ✓
- **But `PIO0 SM0 autopush_count: 20`** — only 20 events actually reached the firmware through PIO ✗
- **`PSRAM Bytes written: 0`** — wavetable uploads never landed ✗
- **WAV: all zeros** — 420 k samples, 0 non-zero, peak 0 ✗

Root cause (different from what the 400 µs run suggested):

Firmware's `handle_iow` dispatches port `0x347` (DRAM write) through `write_gus` case 0x107 → `psram_write8` → `pio_spi_write_dma_blocking`. This **blocks firmware** until the PSRAM PIO TX DMA drains. The PSRAM PIO (PIO1 SM0) is **stalled at PC=0x19** (`OUT PINS, 1`, `EXEC_STALLED=1`) — firmware pushed 13 bytes to TX FIFO but PIO consumed 0 (`CS falls: 0`, `SCK toggles: 0`, `MOSI=1 cycles: 0`). So firmware hangs on the first `psram_write8`.

With firmware hung, IOCHRDY stays low (PIO0 SM0 is still in its `out null, 32` side 0b01 handshake from the last captured event). On real hardware, the ISA host would see IOCHRDY=low and wait to complete the outb. **Our harness doesn't honor IOCHRDY** — it keeps driving Phase 0-3 at fixed timings. So the remaining 514 482 events' IOW falling edges happen during "IOCHRDY busy" windows and are silently missed by PIO0 SM0.

This matches `autopush_count = 20` (only the first 20 events fired before firmware hung on the first 0x347 write).

**Net: the dropped-events-per-ns-cluster bug is fixed. The new blocker is a PSRAM PIO model issue (why is `OUT PINS, 1` at PC=0x19 stalled with data in TX FIFO?) combined with the harness not honoring IOCHRDY.**
