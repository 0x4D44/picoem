## Technical concern

This generated fixture is byte-correct for servable pin patterns, but it is not
a viable drop-in mddosem BIOS as-is. Fire-32-a still aliases source A16 with
active-low CS2 on GPIO16. For a 128 KiB x86 BIOS, the reset vector lives in the
A16-high half (`offset 0x1FFF0`), exactly the half this fixture treats as
unservable.

I tried an explicit `"cs2": null` variant in a throwaway OneROM JSON. It did not
change the generated metadata: `sdrr-info` still reported CS states
`Active Low/Active Low/Not Used`.

## Correction: A16 Is Addressable On 27C010

I revisited the Fire-32-a 27C010 pin interpretation after Arthur challenged the
CS2/A16 conclusion. The original concern above was wrong for the selected
27C-series ROM type.

Evidence from the live OneROM runtime:

```text
rom_type=15 (27C010)
piorom_config.cs_base=14
piorom_config.num_cs=2
PIO2 SM0 PINCTRL input base=14
```

That means the running firmware is watching GPIO14/GPIO15 (`/OE` and `/CE`) as
the active-low read gates. GPIO16 remains A16. The metadata still has a
socket-generic `cs2` field on GPIO16, but for 27C010 that field is not the
serve gate.

The apparent first-case failure after removing the artificial GPIO16-high gap
was a picoem glue DMA modelling bug. CH0 wrote the same CH1 `READ_ADDR` value
twice (`0x20000000` for the gap and for address 0), and the harness suppressed
the second CH1 fetch because the address value had not changed. Real DMA treats
that as another transfer event. I fixed the glue model so a CH0 write event can
start a duplicate-address CH1 fetch, and added a regression test for that.

## 2026-05-04 - 512K SDRR shadow vs 128K EPROM clarification

Arthur challenged why the generated SDRR appears to use a 512 KiB image when the
BIOS and EPROM target are 128 KiB. I checked the corpus JSON and OneROM
metadata. The corpus config declares `27C010`, and `sdrr-info` reports the ROM
type as `27C010`, but the ROM set size as `524288` bytes.

Root cause: OneROM's RP2350 32-pin generator/runtime models the full 19-bit
socket address space for every 32-pin RP2350 ROM set. The generated Rust returns
`2_usize.pow(19)` for `(32, McuFamily::Rp2350)`, and `sdrr/src/rp235x.c`
explicitly rejects 32-pin ROM sets whose size is not `512 * 1024`. The 128 KiB
SeaBIOS payload is therefore mirrored through the 512 KiB socket shadow; high
socket bits beyond the 27C010 address lines do not create new source content.

Emotional temperature: this is a good catch from Arthur. The current package is
functionally correct, but the README should be clearer that the SDRR artifact is
a 512 KiB OneROM shadow envelope serving a 128 KiB 27C010, not a 512 KiB EPROM.

## 2026-05-04 - Corpus naming clarity

Arthur asked whether the corpus naming is clear enough to distinguish original
SeaBIOS images from OneROM SDRR carrier images. I checked the current committed
layout. `bios-128k.bin` and `bios-256k.bin` both contain SeaBIOS markers, while

stronger layout is to separate direct emulator BIOS inputs from OneROM SDRR
artifacts by directory and filename, for example `roms/bios/seabios/` for plain
SeaBIOS `.bin` images and `roms/onerom-sdrr/...` for generated hardware carrier
firmware.

Emotional temperature: pleased Arthur spotted this now. Renaming before mddosem
depends on these paths is cheap; renaming after integration would create churn.
