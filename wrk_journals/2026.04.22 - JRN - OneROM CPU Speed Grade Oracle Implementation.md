### 2026-04-22 — Phase 0 fourth pass: the real cause

Arthur: "P3". Delegated empirical verification agent. Finding is non-obvious and material:

**The 1541 failure is not a library bug. The firmware boots the wrong ROM set.**

Register dump at sync in the 1541 fixture:
- PC = 0x1000_09A6 (correct — CS wait loop)
- R8 = R9 = 0x1 → CS mask = bit 0 = **GPIO0**
- R5 = 0xD000_0010 (SIO_GPIO_OUT), R1 = 0x0400_0000 → data drive = bit 26 = **GPIO26**
- SIO_GPIO_OE = 0 — D0..D7 on GPIO16..23 never enabled.

This is **ROM set 3**, not ROM set 0. ROM set 3 is a 27C301-type image (`1540-e000.325303-01.bin`) with a completely different pin layout.

Why set 3? The firmware selects ROM via image_sel jumpers; default (`image_sel = 0xFF`) clamps to the last set (index 3 in the 4-set 1541 fixture). The stress binary's `ROM_SET_INDEX = 0` is a harness-side constant, never written to runtime_info — so the firmware ignores it.

Agent's proof: decoded `sdrr_rom_info_t` for all ROM sets in both fixtures. ROM set 0 in the 1541 fixture has `rom_type=2 (2364), CS1=ActiveLow, CS2/CS3=NotUsed` — **identical** to test-sdrr-0's default set. The library's constants are correct for it.

The 140 "passes" are spurious: 114 have `expected=0xAA` (residual bus float triggering zero-byte-trust timeout) + 20 `expected=0xFF`. No real serve is happening because ROM set 3's firmware drives GPIO26, not GPIO16..23.

**Under `ThreadedEmulator`, the CPU's serve-loop `strb r1, [r5]` writes the data byte to GPIO bits 0..7 instead of bits 16..23.** Under serial `Emulator::step` (same firmware, same register state), it writes correctly to bits 16..23.

### 2026-04-23 — Phase 3 closeout: byte-replication fix + sub-quantum stim visibility

Two bugs nailed down, both in `crates/mdrp2350/src/threaded/bus.rs`:

**Bug 1 — SIO GPIO_OUT byte-replication missing.** Agent A's audit found it: the threaded `WorkerBus::write8` / `write16` arms for `0xD` (SIO) did a generic read-modify-write, whereas the serial `Bus::write8` at `bus/mod.rs:1973` specifically replicates the narrow write across all four lanes for GPIO_OUT / GPIO_OE / GPIO_HI_OUT / GPIO_HI_OE family offsets (real RP2350 silicon latches the full 32-bit bus without byte-lane enables). OneROM's serve loop uses `strb r1, [r5]` where `r5 → SIO_GPIO_OUT` — on serial, that lights up GPIO16..23 (the data-bus pads) regardless of byte offset. On threaded, the narrow RMW put the byte into lane 0 only. Shadow of 0xA4 read as 0x00 from pin 16..23, oracle failed even at 500 ns.

Fix: both `write8` and `write16` now call `crate::bus::Bus::is_sio_gpio_out_replicating_reg(reg_offset)` (same predicate as serial) and branch to replicated write when it fires. `u32::from(val) * 0x0101_0101` for byte, `* 0x0001_0001` for halfword.

**Bug 2 — quantum-stale stim at CPU read.** Coordinator's `update_gpio` merges external stim into `AtomicGpio::in_` only at quantum boundary. CPU serve loop tight-reads GPIO_IN; between quantum merges, the cached `in_` lags by up to one quantum (~427 ns at 150 MHz, `step_quantum=64`). Stim writes from host-thread driver landed in `AtomicGpio::external` correctly, but CPU didn't see them until the next coord merge.

Fix: new `WorkerBus::gpio_in_fresh()` helper rebuilds the overlay at read time — base from quantum-coherent `in_` with external-mask bits cleared, then OR in fresh `(ext_val, ext_mask)` from `read_external()`. Wired into both `sio_read32(0x004)` and the `CoreBus::gpio_read_in` path. Correct when external mask is stable across the read window (holds for every oracle in this family).

**Measurement methodology fixes** (Arthur's pushback drove these):

- Dropped `MIN_PROGRESS_CYCLES` stall filter from 128 → 1 (just detect zero-delta stalls) after Arthur questioned "20-core CPU, 4 busy threads — why ms-long Windows switches?". Root cause was `DRIVER_CHUNK_QUANTA=1024` — the per-chunk `run_quanta` teardown punched ~30 µs dead zones into the driver loop at deterministic cadence. Bumped to 1,048,576 and the dead zones evaporated.
- `DRIVER_HOST_CORE` moved from 7 → 8. Originally on the SMT sibling of core 6 (measurement thread); two threads sharing one physical core trampled each other's stim/sample timing. Separate physical cores, problem gone.
- Sample scaling: Arthur's insight "just run longer". Added `--all-rungs` flag so one run crosses the full ladder; at `--sweeps-per-threshold 50`, 2048 × 50 = 102,400 samples per rung — the inflection at 500 ns becomes unambiguous.
