### 2026-04-22 — Phase 0 first pass: partial decode, verification caught a gap

First agent reported "both fixtures have identical pin profiles at 0x80FC". Verified directly with hex dump — the claim is byte-accurate for the struct at 0x80FC, but that's the **MCU-level / base pin profile**, not per-ROM-set config. The `onerom_stress_cpu_rp2350.rs` note ("1541 has CS on GPIO0") describes a per-ROM-set override that lives elsewhere.

Direct comparison of the full fixtures shows divergence at:
- `0x7F20..0x7F24` (4 bytes) — build-date stamp per ASCII
- `0xC000..0xC328` — `ONEROM_METADATA` block with per-ROM-set descriptors
  - `0xC100 +0x04`: ROM-set count (6 for test-sdrr-0, 4 for 1541)
  - `0xC104 +0x08`: pointer into a descriptor array at `0xC100`
  - `0xC200+`: ROM-set descriptor array with per-set flags, name pointers, and at least one per-set pin-index field
  - `0xC230+`: ROM name strings ("1540-e000.325303-01.bin", "1541-c000...", "1541-e000.901229-05.bin", "1541-e000.901229-06AA.bin")
- `0x010000+`: ROM data (expected).

Also noticed: the stress binary labels `ROM_SET_INDEX=0` as "1541 $E000 kernal (901229-06AA)", but the name-table order at 0xC230+ suggests the 06AA image is at index 3, not 0. Either the label in the binary is wrong, or ROM_SET_INDEX is not a zero-based array index.

**Next:** delegate a focused agent to:
1. Find the `sdrr_rom_set_t` C struct in vendor headers (`config_base.h`).
2. Fully decode the per-ROM-set descriptors for both fixtures.
3. Identify where the per-ROM-set CS override lives.
4. Produce the final Rust spec covering both base profile AND per-ROM-set overrides.

### 2026-04-22 — Phase 0 third pass: disassembly empirical check

Third agent extracted and disassembled both serve loops:

**1541 (0x1000_09A4..=0x1000_09B0):**
```
ldrh   r0, [r4]         ; load halfword from gpio_in low 16
eor.w  r10, r0, r8      ; r10 = r0 ^ r8   (expected-CS-state XOR)
tst.w  r10, r11         ; AND with CS-bit mask
beq    0x10000976       ; branch if selected
b      0x100009a4       ; loop
```

**test-sdrr-0 (0x1000_0926..=0x1000_0930):**
```
strb   r1, [r5]         ; drive data byte
ldrh   r0, [r4]         ; load halfword from gpio_in low 16
tst.w  r0, r11          ; AND with CS-bit mask
ldrb   r1, [r2, r0]     ; shadow lookup
beq    0x10000926       ; loop
```

Both use `r11` as the CS-mask register. The agent's conclusion: r11 is the same value in both (0x2000 = bit 13) because both firmwares are baked from the same source tree with identical `sdrr_pins_t`.

**Caveat:** the agent didn't trace r11's init site to confirm the value — that's an assumption, but a plausible one given the metadata match.

### 2026-04-22 — Phase 0 fourth pass: the real cause

Arthur: "P3". Delegated empirical verification agent. Finding is non-obvious and material:

**The 1541 failure is not a library bug. The firmware boots the wrong ROM set.**

Register dump at sync in the 1541 fixture:
- PC = 0x1000_09A6 (correct — CS wait loop)
- R8 = R9 = 0x1 → CS mask = bit 0 = **GPIO0**
- R5 = 0xD000_0010 (SIO_GPIO_OUT), R1 = 0x0400_0000 → data drive = bit 26 = **GPIO26**
- SIO_GPIO_OE = 0 — D0..D7 on GPIO16..23 never enabled.

This is **ROM set 3**, not ROM set 0. ROM set 3 is a 27C301-type image (`1540-e000.325303-01.bin`) with a completely different pin layout.

Why set 3? The firmware selects ROM via image_sel jumpers; default (`image_sel = 0xFF`) clamps to the last set (index 3 in the 4-set 1541 fixture). The stress binary's `ROM_SET_INDEX = 0` is a harness-side constant, never written to runtime_info — so the firmware ignores it.

Agent's proof: decoded `sdrr_rom_info_t` for all ROM sets in both fixtures. ROM set 0 in the 1541 fixture has `rom_type=2 (2364), CS1=ActiveLow, CS2/CS3=NotUsed` — **identical** to test-sdrr-0's default set. The library's constants are correct for it.

Agent's stress-log histogram:
| Verdict | Count |
|---|---|
| Pass | 140 |
| DataPinsNotDriven | 1024 |
| LatencyOutOfEnvelope | 884 |

The 140 "passes" are spurious: 114 have `expected=0xAA` (residual bus float triggering zero-byte-trust timeout) + 20 `expected=0xFF`. No real serve is happening because ROM set 3's firmware drives GPIO26, not GPIO16..23.

Agent also produced two small verification binaries (`verify_1541_cs_polarity.rs`, `decode_1541_cs_states.rs`) under `crates/mdpicoem-harness/src/bin/`. These are investigation tools — keep or delete TBD.

### Implication for phasing

1. The library's constants work for BOTH fixtures' ROM set 0. No parameterisation needed.
2. The fix for the stress binary (and for our speed-grade oracle) is to **force `rom_set_index = 0` at boot** — patch runtime_info SRAM or drive image_sel pins before sync.
3. The tech-debt item in `onerom_stress_cpu_rp2350.rs:27-47` was misdiagnosed.

**Revised plan: collapse Phase 1.** Drop the parser + parameterisation. Replace with a tiny "force ROM set 0 at boot" helper. Speed-grade oracle then builds on the existing library.
