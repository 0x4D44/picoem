## Plan at a glance

Four independent additions to the `mdrp2354-test-harness` crate:

- **C** — Long-multiply and DSP fuzz generators (low risk, ~200 LOC)
- **D** — POP {PC} / `probe_only` flag (low risk, ~80 LOC)

Order: C → D → B → A. Commit atomically after each stage.

### 2026-04-13 — Stage D feedback applied

Review surfaced three items — two correctness, one cosmetic:

1. **PUSH fuzz coverage regression.** Stage D originally split the
   push/pop inner loop three ways (`rng.range(0..3u8)` → PUSH / POP /
   POP_PC). Because `qemu_diff` filters `probe_only` tests before
   running, only two of those three slots were actually reaching QEMU,
   dropping effective PUSH coverage from ~50% (pre-Stage-D) to ~33%.
   Fixed by switching to a 4-bucket weighted distribution — PUSH gets
   slots 0 and 1 (50%), POP without PC gets slot 2 (25%), POP with PC
   (probe_only) gets slot 3 (25%). Post-filter PUSH rate is back to
   ~67% of runnable tests, matching the pre-Stage-D absolute rate.

2. **T32 LDM.W with PC missing from fuzz.** The Stage D POP {PC} work
   covered T16 only. T32 LDM.W can also load PC (bit 15), and that
   path has the same "absolute address can't round-trip between QEMU
   and the emulator" property. Added a 25% coin in
   `generate_fuzz_t32_mem` — when loading (not storing), in IA mode,
   coin succeeds — set bit 15 of the reglist and mark `probe_only`.
   The PC slot holds `EMU_TEST_SLOT + 4 | 1`; everything else stays
   random. DB mode is deliberately skipped because its reverse memory
   layout doesn't cleanly match the "PC comes last" property needed to
   keep the existing mem_pre loop simple.

3. **Comment drift in `fuzz_generates_expected_count`.** Added an
   inline note that push/pop is one class whose body now has four
   internal variants, so the asserted class count of 5 still holds.

Verification:

- `cargo build -p mdrp2354-test-harness --release` — clean, zero
  warnings.
- `cargo test -p mdrp2354-test-harness --lib` — all tests pass.
- `cargo run --bin qemu_diff -- --fuzz 100 --seed 1` — filter banner
  prints with the new higher probe_only count (combining POP_PC and
  T32 LDM+PC), no new failures in the probe-filtered classes.

**Tech debt logged** (not fixed this stage — see top of file):

- **POP {PC} cycle count hardcoded.** The targeted POP {PC} test and
  the new POP_PC fuzz variants all use the existing probe-diff
  harness, which assumes a constant cycle count. POP with PC on M33
  has a pipeline-flush penalty that the emulator currently doesn't
  model. `qemu_diff` doesn't look at cycles and `probe_diff` has no
  POP-PC comparison today, so the mismatch is latent — it only
  surfaces when someone adds POP {PC} to `probe_diff --cycles`.
- **Targeted POP {PC} asymmetric with ADR.** ADR gets 7 targeted
  edge cases (zero offset, max offset, alignment, low Rd, high Rd,
  etc.) while POP {PC} gets a single "empty reglist + PC" test. The
  fuzz variants compensate in bulk but the targeted coverage is
  thinner than its sister probe_only classes. Follow-up is to add
  parameterised POP {PC} edge cases (1-reg + PC, 8-reg + PC,
  register numbered high, etc.) once the cycle-count story is
  resolved.

**Committed** as ded7e49 ("Stage D: probe_only flag for address-

## Real bugs found during this work

1. **PARADD emulator bugs** (SAX, ASX, USUB16 halving) — surfaced
   by Stage C fuzz coverage.
2. **NaN sign bit** — emulator produces 0xFFC00000 (negative quiet
   NaN), ARM spec requires 0x7FC00000 (positive). Surfaced by Stage A.
3. **Pre-existing LDM writeback** mismatches — visible in all fuzz
   runs but predates this work.
