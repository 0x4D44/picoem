### Phase 2 — parallel streams (user-directed)

**Stream 1 — PicoGUS source ingestion (agent aa2070e593def238d).** COMPLETE.
- Upstream confirmed: `github.com/polpo/picogus` tag `v4.0.0`, SHA-256 verified against our `VERSION` manifest.
- Shallow clone into `third_party/picogus/upstream/` (untracked; submodule decision pending).
- GUS build config: `USE_IRQ` off, `POLLING_DMA` off, `AUDIO_CALLBACK_CORE0` off, `PSRAM_CORE0` on — so core 1 runs `play_gus` via a **PWM-IRQ-driven audio sample handler**.
- Audio pipeline: `PWM slice 4 wrap (~every 8400 sys_clk) → PWM_IRQ_WRAP → audio_sample_handler (gusplay.cpp:81) → pio1_hw->txf[3] = GUS_sample_stereo() → PIO1 SM3 shifts I2S out GP16/17/18`. No DMA on the I2S path — CPU-driven from the PWM wrap ISR.
- **Smoking gun identified:** `crates/mdrp2040/src/peripherals/pwm.rs:310-316` + `:168` — emulator treats `PWM_EN` (0x40050000+0xa0) as separate storage from per-slice `CSR.EN`. Per RP2040 datasheet §4.5.3.18, `PWM_EN` is an **alias of the eight `CSRx.EN` bits** (same storage). Pico-SDK's `pwm_set_enabled()` writes `CSR.EN` only, so `PwmRegs::en` stays `0` → `is_idle()` returns true → `tick_peripherals` fast-path skip → PWM never advances → `INTR[4]` never latches → `audio_sample_handler` never runs → silence.
- All 11 observed PCs map to MIDI/ISA paths (not audio) — consistent with "core 1 runs PWM_IRQ handler, which doesn't fire, so core 1's visible behavior is just the MIDI pump."
- Notes: `wrk_scratch/picogus-stream1-symbols.md`. Journal: `wrk_journals/2026.04.16 - JRN - PicoGUS Stream 1 Source Ingestion.md`.
