## Plan

Re-reading how `--duration` works: it caps `ev.ns` (trace-ns), not
sim time. Pre-roll adds sim-time padding. So to get all 30s of
trace events including the music section, we want:

- `--pre-roll 2.0` (firmware boot / warm-up)
- `--duration 30.0` (all events)
- `--post-roll 0.5` (I2S drain)

Kicked off in background (binary copied to `/tmp/picogus_replay.exe`):

Env: `PICOGUS_STUB_TEST_PSRAM=0x2001309c PICOGUS_IDLE_CYCLES=5000`.

## Aside: audio I2S sample rate is 44100, not 22050

While the replay runs, disassembled `audio_i2s_minimal_setup` and
traced its caller in `_Z8play_gusv` at `pg-gus.dis:14342`. The second
argument (sample rate target) is a PC-relative literal
`0x0000AC44 = 44100`. So **I2S LRCLK should be 44100 Hz**, not the
22050 Hz I'd assumed from the GUS voice-count math.

GUS voices render at `sample_rates[voice_count-1]` — 22050 Hz for 27
active voices. The IRQ fires at 22050 Hz, pushes one stereo frame per
call. The I2S is at 44100 — firmware must be duplicating each frame
or there's FIFO underrun. Either way, the WAV is stamped with the
inferred LRCLK rate, so pitch should be correct.

Prior journal estimate of "sim produces ~120 kHz vs. expected 22.9 kHz"
→ expected was really 44100, and 120/44.1 ≈ 2.7×, not 5×. Less
dramatic but still off. Not a blocker for audio content correctness
since WAV rate is stamped from observed LRCLK.

## Step 2 — Firmware expects SYS_CLK = 370 MHz

Found the PWM / I2S divider math in upstream source
`third_party/picogus/upstream/sw/gusplay.cpp:95-107`:

```
clocks_per_sample = round(SYS_CLK * 32 * channels / 19.7568 MHz)
pwm_set_wrap(pwm_slice_4, cps - 1);         // IRQ rate
pio_sm_set_clkdiv_int_frac(audio_pio, ..., cps * 4)  // I2S rate
```

The GUS "master clock" is 19.7568 MHz; for N channels active, sample
rate = GUS_CLOCK / (32 * N). With 27 channels: 22866 Hz (≈ 22050).

For `audio_sample_handler` to fire at 22050 Hz, PWM wrap must be
SYS_CLK / 22050. The firmware bakes this into a runtime formula with
constants derived from RP2_CLOCK_SPEED. Both rebuild and stock
firmware compute `cps = 16181` for N=27 after all the reduction.

- At SYS_CLK = 370 MHz: wrap rate = 370e6 / 16181 = 22865 Hz ✓
- At SYS_CLK = 125 MHz (our emulator default): wrap rate = 7725 Hz ✗

**So the firmware is designed for a Pico 2 overclocked to 370 MHz.
Our emulator runs the RP2040 at 125 MHz by default, so PWM IRQ rate
is 3× too slow.**

UART boot output confirmed from the live replay:
```
[uart] fixed 44k output: 0
[uart] GUS channels: 27
```

So 27 voices, fixed-44k mode OFF → voice render rate =
`sample_rates[26] = 22050` (from the table I confirmed at file offset
0x15cbc). If IRQ fires at 7725 Hz but voice render expects 22050 Hz,
each "voice slot" fires only 1/3 as often as intended — voices
advance their WaveAddr at 1/3 the expected rate.

**That's consistent with the "infrasonic output, 0.75 Hz triangle"
from the prior journal**: audio time is roughly 3× dilated.

Whether our emulator's actual sys_clk is 125 MHz (no firmware
reprogramming) or something else (post-PLL setup) is something I
need to verify after the replay finishes — by reading the
inferred LRCLK rate from the WAV output.

## Step 3 — firmware PLL programming: targets 370 MHz

Confirmed from `pg-gus.dis` at `main+0x38` (`0x200017a0`):

```
pll_init(pll_sys=0x40028000, refdiv=2, vco_freq=0x42294180=1110 MHz,
         post_div1=3, post_div2=1)
```

VCO = 1.11 GHz, divided by 3×1 → **sys_clk = 370 MHz**. Our emulator's
clock-tree model in `crates/mdrp2040/src/bus/clocks.rs` does recompute
on PLL register writes (covered by `clocks_sys_via_pll_sys` test), so
sim sys_clk *should* be 370 MHz after firmware boots. Good.

## Step 4 — sanity-check prior WAV rates (no fresh replay needed)

Previous 4-second-trace replays are still on disk at /tmp:

```
interp_fix_v2.wav   rate=25348 Hz, 370172 frames  (pre-Philips, clipped)
dump_gus_4s.wav     rate=25536 Hz, 346722 frames  (post-Philips)
```

25.3-25.5 kHz is 15% over target 22050 but the same order of magnitude.
So sys_clk in sim IS roughly 370 MHz, and LRCLK comes out near the
designed 22050 — matching the PicoGUS PWM/PIO divider formula.

**The prior "~120 kHz LRCLK" claim in yesterday's journal was wrong.**
I had mis-derived it. Actual LRCLK is ~25 kHz = 1.15× target, not 5×.
Audio timing is therefore only off by a small factor, not a huge one.

And re-examining the "infrasonic" interpretation — the prior journal
said "10 half-cycles across 6.7 s → 0.75 Hz". But 15K active frames
at 25 kHz = 0.6 s, not 6.7 s — so the 10 half-cycles are actually
over 0.6 s = 16.7 Hz, not 0.75 Hz. Still low for music, but not
infrasonic.
