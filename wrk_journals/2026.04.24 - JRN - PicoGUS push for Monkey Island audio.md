## Aside: audio I2S sample rate is 44100, not 22050

While the replay runs, disassembled `audio_i2s_minimal_setup` and
traced its caller in `_Z8play_gusv` at `pg-gus.dis:14342`. The second
argument (sample rate target) is a PC-relative literal
`0x0000AC44 = 44100`. So **I2S LRCLK should be 44100 Hz**, not the
22050 Hz I'd assumed from the GUS voice-count math.

GUS voices render at `sample_rates[voice_count-1]` — 22050 Hz for 27
active voices. The IRQ fires at 22050 Hz, pushes one stereo frame per
call. The I2S is at 44100 — firmware must be duplicating each frame
or there's FIFO underrun. Either way, the WAV is stamped with the
inferred LRCLK rate, so pitch should be correct.

Prior journal estimate of "sim produces ~120 kHz vs. expected 22.9 kHz"
→ expected was really 44100, and 120/44.1 ≈ 2.7×, not 5×. Less
dramatic but still off. Not a blocker for audio content correctness
since WAV rate is stamped from observed LRCLK.

## Step 2 — Firmware expects SYS_CLK = 370 MHz

Found the PWM / I2S divider math in upstream source
`third_party/picogus/upstream/sw/gusplay.cpp:95-107`:

```
clocks_per_sample = round(SYS_CLK * 32 * channels / 19.7568 MHz)
pwm_set_wrap(pwm_slice_4, cps - 1);         // IRQ rate
pio_sm_set_clkdiv_int_frac(audio_pio, ..., cps * 4)  // I2S rate
```

The GUS "master clock" is 19.7568 MHz; for N channels active, sample
rate = GUS_CLOCK / (32 * N). With 27 channels: 22866 Hz (≈ 22050).

For `audio_sample_handler` to fire at 22050 Hz, PWM wrap must be
SYS_CLK / 22050. The firmware bakes this into a runtime formula with
constants derived from RP2_CLOCK_SPEED. Both rebuild and stock
firmware compute `cps = 16181` for N=27 after all the reduction.

- At SYS_CLK = 370 MHz: wrap rate = 370e6 / 16181 = 22865 Hz ✓
- At SYS_CLK = 125 MHz (our emulator default): wrap rate = 7725 Hz ✗

**So the firmware is designed for a Pico 2 overclocked to 370 MHz.
Our emulator runs the RP2040 at 125 MHz by default, so PWM IRQ rate
is 3× too slow.**

UART boot output confirmed from the live replay:
```
[uart] fixed 44k output: 0
[uart] GUS channels: 27
```

So 27 voices, fixed-44k mode OFF → voice render rate =
`sample_rates[26] = 22050` (from the table I confirmed at file offset
0x15cbc). If IRQ fires at 7725 Hz but voice render expects 22050 Hz,
each "voice slot" fires only 1/3 as often as intended — voices
advance their WaveAddr at 1/3 the expected rate.

**That's consistent with the "infrasonic output, 0.75 Hz triangle"
from the prior journal**: audio time is roughly 3× dilated.

Whether our emulator's actual sys_clk is 125 MHz (no firmware
reprogramming) or something else (post-PLL setup) is something I
need to verify after the replay finishes — by reading the
inferred LRCLK rate from the WAV output.

## Step 8 — The FFR→pitch math

Traced through `third_party/picogus/upstream/sw/gus/gus-x.cpp`:

```c
// WriteWaveFreq(val):
WaveAdd = (val >> 1) << (WAVE_FRACT - 9);      // WAVE_FRACT = 10
// Per-IRQ step:
WaveAddr += WaveAdd;
useAddr = WaveAddr >> WAVE_FRACT;               // byte index
```

So with WAVE_FRACT=10:
- `WaveAdd ≈ FFR & ~1`
- `byte_rate = FFR * IRQ_rate / 1024`
- For FFR=123 at 27 voices (IRQ=22865): byte_rate = 2720 bytes/sec

On real GUS (WAVE_FRACT=9) the equivalent formula gives exactly the
same byte rate — the WAVE_FRACT=10 is "extra bits of precision"
without a rate change. Confirmed by re-derivation: both give
`byte_rate = FFR * IRQ / 1024`.

**So our emulator is faithful to both picogus and real GUS semantics
for the FFR values in the trace.**

## Step 9 — Why the audio sounds pitched down

For a 16-byte single-cycle waveform at FFR=123: tone = 2720/16 = 170 Hz.
For a 8-byte waveform: 340 Hz. For a 32-byte waveform: 85 Hz.

The trace's max FFR=123 is consistent with monophonic low-bass output
if the waveforms are in typical sizes. For middle-range (500+ Hz)
melody tones, FFR would need to be much higher, or waveforms much
shorter (like 4-8 bytes).

The observed dominant frequencies (30-150 Hz) fit the math given FFR
values and typical waveform sizes.

**Possible explanations:**
1. The trace contains the introductory "building up" section of the
   theme before the melodic lead comes in — bass lines only.
2. The game's DOSBox-X driver produces FFR values tuned for
   DOSBox-X's own GUS emulator, which may use different precision
   (e.g., WAVE_FRACT=9 with no compensating `>>1`, giving 2× pitch).
3. The patches uploaded to GUS DRAM are longer than "single-cycle"
   waveforms, making FFR effectively a "playback speed" knob rather
   than a "note frequency" knob — and the music pattern in the
   patches is itself low-bass.

To know for certain, we'd need to hear stock PicoGUS hardware
playing the exact same trace — no way to do that from this box.

**Max FFR across all 246 WaveFreq writes is 0x7b = 123.** That is

### Hypothesis revision

The trace was captured from a scene that programmed very small
FFR values. Two equally plausible explanations:

1. **The trace isn't the Monkey Island opening theme.** It may be
   from a dockside ambience scene or pre-music splash — the
   "Start of Monkey Island" the user remembered could mean
   `MI1.EXE` launch, not the title music. GUS drivers routinely
   run at minimum state during loading screens.
2. **DOSBox-X's picogus-tap v1 may have missed register writes.**
   The 8-bit vs 16-bit ISA write capture could be dropping the

   trace but the high byte is `0x00` in every case (max value

**Evidence RULES OUT (2):** file-wide scan confirms the trace DOES
carry genuinely-16-bit values elsewhere:

- All 0x344 writes across the entire trace: max value = 65535 (0xFFFF)

So 16-bit capture is working — the TAP tool carries `0xFFFF` just
fine for other registers (probably WaveStart/End MSW writes).
The FFR values are small because **the game wrote them small**.

That collapses this into only hypothesis (1): the trace was
captured from a scene that simply does not play the Monkey Island
theme. The captured audio is what PicoGUS would play back — a
low-pitched ambient hum with faint envelope modulation — and is

### Re-examining the pitch math with voice 1

Voice 1 has a 21254-byte waveform, never looped (WCTRL_LOOP=0 in
the last WaveCtrl). FFR max = 123.

- WaveAdd ≈ 122 → byte_rate = 122 × 22866 / 1024 = 2724 bytes/sec
- Sample playback time: 21254 / 2724 = 7.8 seconds
- If this sample was originally recorded at ~22050 Hz (standard
  SNES/AdLib-era rate), 1:1 playback would take 0.96 s. We're
  playing it ~8 × slower → 3 octaves pitch-down.

For FFR=20 (the mean): playback 25 × slower → 4.6 octaves down.

So the emulator IS playing the correct bytes but at a pitch
3–5 octaves below the intended rate.

### Why the rate mismatch?

Three possibilities:

1. **Real picogus produces the same low pitch.** Game was just
   designed for low-pitch output. Unlikely — this is supposed to
   be the Monkey Island theme.
2. **Picogus author's WAVE_FRACT scaling is wrong.** The factor
   `WaveAdd = (val>>1) << (WF-9)` gives WaveAdd ≈ val for WF=10.
   If the correct scaling were `WaveAdd = val << (WF-6)` (e.g.
   real GUS fractional width is 6, not 9), byte_rate would be
   16 × higher, and FFR=40 would give 14000 bytes/sec — musical.
   But PicoGUS is a shipping product, so this can't silently be
   wrong.
3. **The trace was captured from DOSBox-X running at an internal
   rate that produced different FFR semantics than real GUS.**
   DOSBox-X exposes an `fixed_44k_output` toggle, and if the
   trace captures a game that assumed fixed_44k=true (scaling
   WaveAdd down) and we replay it on a picogus configured with
   fixed_44k=false (no scaling), the math mismatches.

### The fixed_44k hypothesis (most likely)

PicoGUS code (gus-x.cpp:417–419):
```cpp
if (myGUS.fixed_44k_output) {
    WaveAdd = ((WaveAdd * sample_rates[ActiveChannels-1]) + (44100>>1)) / 44100;
}
```

For ActiveChannels=27, sample_rates[26]=22866:
- fixed_44k=true: WaveAdd *= 22866/44100 = *0.519 (halves)
- fixed_44k=false: WaveAdd unchanged

So toggling fixed_44k_output doesn't 8-to-16× the rate. The
theory doesn't fit the magnitude.
