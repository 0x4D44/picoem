# OneROM PIO Oracle Fire-32 HLD Journal

Date: 2026-05-04

## Design session

Arthur asked for a separate HLD for the Stage 4 fire-32-a PIO oracle
generalization, with the explicit reminder to keep it simple and avoid
feature flags, environment variables, migration ceremony, and old-code
support. I read the current fixture-generalization HLD, the Stage G serving
oracle HLD, the top `tech_debt.md` entry, and the current `ServingOracle`,
`PioBlock`, serial GPIO, and threaded GPIO code around the known failure.

The important design correction is that the high-bank problem is not a reason
to make the PIO state machine 64-bit. Official RP2350 docs say each PIO
instance still sees a 32-pin window; `GPIOBASE` chooses whether that window is
physical GPIO0..31 or GPIO16..47. That gives us a smaller and cleaner design:
model `GPIOBASE`, pass a physical 48-bit sample to RP2350 PIO blocks, project
that sample into the block's local 32-bit window, and change the oracle to
match the full expected resolved address.

I deliberately rejected a PIO bytecode sniffer. It would look clever, but for
the two fixtures we actually have, the address window is derivable from
`FixtureSpec.addr_pins`. This keeps the solution close to the immediate bug
and avoids building an analyzer for hypothetical future PIO programs.

Emotional temperature: steady, but alert. This is exactly the kind of problem
where a three-line `u16 -> u32` patch is tempting and wrong. The design feels
small enough to implement safely while still honest about the emulator-crate
blast radius.
