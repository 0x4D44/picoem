# Senior Rust Review — Threaded Dual-Core Emulation HLD

Reviewer: senior Rust systems engineer, first-pass fresh eyes.
Document under review: `d:\language\mdrp2354\wrk_docs\2026.04.14 - HLD - Threaded Dual-Core Emulation.md`
Date: 2026-04-14

## Executive take

The HLD is unusually good for a round-2 document: honest about the ceiling (120–130 MHz, not 150), has a genuine go/no-go gate (Phase 0a), front-loads the hard prerequisite refactors, and names the specific `std::sync::Barrier` vs spin-barrier trade-off with a number. The backing-store choice (`[AtomicU32]` vs per-byte atomics) is the right call and the reasoning (Armv8-M single-copy atomicity) is load-bearing and correct.

But there are places where the document is deceptively clean. The conversion API (`into_threaded` / `into_emulator`) hides most of the actual migration complexity behind an ellipsis; the Pacer reference in `run(...)` doesn't reconcile with the "fold coordinator into worker-0" topology; the SPSC-vs-crate decision is argued on the wrong axis; the error/panic model is missing entirely; and the Loom coverage is significantly overclaimed.

I would still ship this design, but with the issues below landed either in the HLD or as follow-up notes before Phase 1 begins.

---

## ISSUE 1: `into_threaded()` / `into_emulator()` hides the hard part
**Severity:** IMPORTANT
**Type:** DESIGN

**Problem:** The public API shows `pub fn into_threaded(self) -> ThreadedEmulator { ... }` with a `...` where the entire migration lives. That ellipsis is the whole project. `Emulator` owns `Bus` by value, and `Bus` owns `Memory`, `Sio`, PIO blocks, peripheral register hashmap, clock-tree caches, boot RAM, XIP SRAM, event flags, RCP salt state, resets state, PLL register images, and ~20 more fields (see `crates\mdrp2354\src\bus\mod.rs:16-96`). The threaded topology requires partitioning that into:

- `Arc<SharedMemory>` — SRAM/ROM/XIP, backing changes from `[u8]` to `[AtomicU32]` (not just a wrap, a *reinterpretation* of every existing byte)
- `Arc<ThreadedSio>` — different struct, different FIFO impl, different event-signalling model from the current `pending_fifo_event: Option<usize>` side-channel
- `Arc<Mutex<...>>` sharded per-peripheral-block
- Per-core bits that move off `Bus` onto `CortexM33` (PPB, RCP salt per prereq 0b.4, exclusive monitor)

The real conversion is (a) allocate a new `SharedMemory` sized correctly, (b) copy-convert every SRAM byte into the atomic word representation, (c) split `Bus` into shared/per-core pieces and route each to the right owner, (d) deal with `pending_fifo_event` which currently lives on `Sio` and needs a cross-thread replacement. That is not one method. It is a module.

Also — and this is the subtle one — `into_threaded` / `into_emulator` as a round-trip implies symmetry. It isn't symmetric. Going back requires collapsing two independent core states and a snapshot of shared memory into a single-threaded `Bus` with a coherent bus-fault flag, a coherent `core0_port` contention state, etc. That only works if neither worker is running, which is fine, but the method signature gives no hint that this is a stop-the-world operation that has to flush FIFO drains, resolve in-flight STREX, and handle "one core has panicked, the other hasn't observed it yet."

**Proposed solution:** In the HLD, replace the `...` with a prose paragraph that names the four transformations above and explicitly calls out the asymmetry. Also consider whether you actually need the round-trip. I would argue you don't: `Emulator` is for correctness validation, `ThreadedEmulator` is for throughput. Mixing them mid-run is a footgun ("was this bug caused by the last `into_emulator`?"). Make it one-way: `Emulator::into_threaded` exists; `ThreadedEmulator::into_emulator` does not. If you need to validate threaded state against the single-threaded reference, build a diff tool that compares snapshots — don't make mode-swap part of the type system.

## ISSUE 2: The Pacer/worker interaction is under-specified
**Severity:** IMPORTANT
**Type:** DESIGN

**Problem:** Two things contradict:

1. The API shows `pacer: &mut Pacer` passed into `ThreadedEmulator::run`.
2. The topology shows worker 0 calling `pacer.spin_wait()` on its own host thread.

`Pacer` today (see `pacer.rs:254-371`) is `!Sync` in practice: it owns `quantum_start_tsc: u64`, `first_begin_tsc: Option<u64>`, etc. that mutate every quantum. For worker 0 to call `spin_wait()`, worker 0 needs `&mut Pacer`. That means either:

- `ThreadedEmulator::run` stays on the caller's thread, *is* worker 0, and spawns only one auxiliary thread for core 1 — in which case "2 worker threads" is misleading and the spawned thread is just one worker
- Or the Pacer is moved into worker 0's closure and the caller loses access for the duration of the run

Either is fine but the HLD doesn't commit. This matters because the caller's expectations around "can I read pacer stats while a run is in progress?" flow from this. The current single-threaded `PacerStats` is already `Arc<PacerStats>` (pacer.rs:315) which suggests the intent is "stats readable from outside." Good — but then the `Pacer` itself (mutable state) has to live inside the run scope.

Related: `first_begin_tsc: Option<u64>` is set once on first call. Between a `run()` that finishes and a subsequent `run()`, is that reset? The HLD doesn't say, and the bench harness currently depends on it *not* being reset so that "real-time elapsed since first quantum" is cumulative. Threaded runs may have multiple `run(duration)` invocations, so this matters.

**Proposed solution:** Commit explicitly. I'd recommend: `ThreadedEmulator::run` borrows the caller's thread, spawns one worker for core 1, becomes worker 0 itself. Signature:

```rust
pub fn run(&mut self, pacer: &mut Pacer, duration: Duration, stop: &StopSignal);
```

Note `&StopSignal` not `Arc<StopSignal>` — the caller already holds the `Arc`; the run just needs a borrow. Internally it clones the Arc for worker 1. This also avoids the subtle trap of a caller dropping their `Arc<StopSignal>` mid-run.

## ISSUE 3: The "hand-roll a 100-LOC SPSC ring" decision is argued on the wrong axis
**Severity:** IMPORTANT
**Type:** RUST IDIOM / MAINTENANCE

**Problem:** The HLD justifies rolling your own SPSC on three grounds: (a) "simpler to audit," (b) "no supply chain surface," (c) "no cfg-if, no scopeguard, no allocator polyfill." None of these survive scrutiny:

- **Audit cost.** `crossbeam-queue`'s `ArrayQueue` is MPMC and overkill, yes — but `rtrb` (SPSC, no-std, zero deps, ~500 lines, Loom-tested, dual-licensed MIT/Apache) is the actual comparison. You are proposing to write, Loom-test, and maintain forever a lock-free SPSC ring with weak-memory ordering constraints, to save ~500 LOC of *already-Loom-tested* third-party code. That is a bad trade. SPSC rings are one of the classic categories where hand-rolling looks trivial and ships with subtle bugs — wrap-around counter issues, acquire/release mismatches on the wake path, false sharing on the head/tail atomics. The reason the Rust ecosystem converged on a handful of queue crates is precisely that everyone who tried to hand-roll one got bitten.

- **Supply chain.** `rtrb` has zero dependencies. You are paying zero supply-chain cost to use it. The "avoid cfg-if" argument is about `crossbeam`, which is a different tool.

- **Correctness-under-Loom.** The HLD says "Loom tests for SIO ring + barrier." Great. But Loom is a model checker — it catches bugs *it is told to look for*. The author of `rtrb` has already run every ordering combination through Loom and fixed whatever came out. You will ship version 0.0.1 of your ring with no history of real-world hammering.

There is also a *second* SPSC that the HLD hasn't named: the cross-core event wakeup path (`pending_fifo_event: Option<usize>` on `Sio` today — `sio\mod.rs:89`). That's another lock-free signal under a different access pattern. Hand-rolling two of these is two chances to ship a weak-memory bug.

Counter-case for hand-rolling: if the SIO FIFO semantics are weirdly specific (sticky WOF/ROE flags, for instance) and don't map cleanly onto a generic SPSC. The HLD does flag "sticky WOF/ROE flag semantics that match hardware." Fair. But the flags are per-core state *outside* the ring — the ring itself is just u32 payloads push/pop. Use `rtrb` for the data path, keep the flag logic as plain `AtomicBool` adjacent to it.

**Proposed solution:** Depend on `rtrb`. If auditability matters, vendor a specific pinned version into `crates/mdrp2354-spsc` (copy the code, note the upstream version and commit). You get the Loom tests, the real-world hammering, *and* you control the supply chain exactly as you would a hand-roll. Net result: same supply chain posture, dramatically less implementation risk.

If the decision is truly "no external code," at minimum write the ring as its own crate with its own tests and let the main emulator consume it. Don't inline 100 LOC of concurrency-critical code into `sio/threaded.rs`.

## ISSUE 4: Error handling and panic propagation are not addressed
**Severity:** IMPORTANT
**Type:** ERROR HANDLING

**Problem:** The word "panic" appears once in the HLD, dismissively: "No graceful crash recovery. Worker panic → process abort, same as single-threaded." That's the entire error strategy. Problems:

- Single-threaded panic in this codebase is NOT "process abort." It's the standard Rust unwind, which returns up through `Emulator::run` → the test harness → the caller. The caller can catch it with `std::panic::catch_unwind`, the test runner reports the failing case with a backtrace, and crucially *the harness binary keeps running to the next test*. Our current fuzz-diff harness relies on this.
- In the threaded design, if worker 1 panics inside `core1.step(mem, ...)`, the default thread panic behavior is (a) the panic unwinds worker 1's stack, (b) worker 1 drops its borrows of `Arc<SharedMemory>` etc., (c) worker 0 hits the barrier forever because `count` never reaches 2. Deadlock. The harness becomes unkillable. This is strictly worse than single-threaded.
- A panic in worker 0 (the one holding the Pacer and doing cross-core events) is worse still: the caller's thread is now stuck mid-barrier with a poisoned state.

**Proposed solution:** Threading demands a deliberate panic strategy. Options:

1. **Catch-and-signal:** each worker wraps its quantum loop in `catch_unwind`. On panic, the worker sets `StopSignal` and increments an "arrived" counter on the barrier in a "poisoned" generation, so the sibling wakes and exits. The join handle returns the panic payload. `ThreadedEmulator::run` resumes the panic on the caller's thread. This preserves the existing "panics propagate to test harness" contract.
2. **Abort-on-panic:** set `panic = "abort"` in the relevant profile. Simple, but this is wrong for our workflow because we run fuzz-diff harnesses that need to survive individual failures.

Go with (1). Also write one regression test: `ThreadedEmulator` running firmware that deliberately faults core 1 in a way that panics inside our emulator — assert the caller sees the panic, not a deadlock.

Related: `Emulator::step` today has `bus.bus_fault()` handling mid-flow (lib.rs:135-158 + core/mod.rs:81-103). That path needs to survive threading, and the HLD doesn't describe how two cores' concurrent bus faults interact with the single `bus_fault: bool` / `bus_fault_addr: u32` on `Bus`. Today those are unambiguously "whichever step is currently executing." Under threading, both cores can fault in the same quantum.

## ISSUE 5: Observability / debuggability story is missing
**Severity:** IMPORTANT
**Type:** MAINTENANCE

**Problem:** 6 months from now, someone is staring at a firmware run that hangs after 4.2 seconds. Was it a livelock between cores? A STREX that never succeeded? An FPU-induced panic that turned into a deadlock? The HLD gives zero guidance on how they'd diagnose this.

Single-threaded debugging is easy because every state transition is linearized in one step loop. Threaded debugging requires deliberate investment:

- Some form of per-worker event log (enter quantum, exit quantum, SIO push, WFE sleep, spinlock acquire/release, exclusive monitor set/cleared) that can be dumped post-mortem
- A "freeze" mechanism: caller signals stop, both workers park at the next barrier, the caller can then read both cores' state atomically
- Metrics: PacerStats today (pacer.rs:6+) is well-structured. The threaded version needs at minimum: time-per-quantum per worker, barrier wait time, SIO contention stats, peripheral mutex contention stats

None of this is in the HLD.

**Proposed solution:** Add an "Observability" section. At minimum, require: (a) `tracing` crate spans per quantum per worker (feature-gated so release builds pay nothing), (b) a `ThreadedStats` struct that's `Arc`'d alongside `PacerStats` and tracks barrier-wait ns, peripheral-mutex-wait ns, FIFO full/empty events, (c) a `freeze_and_inspect(&mut self, f: impl FnOnce(&Emulator))` that lets the caller temporarily view a single-threaded view of the state.

The cheapest path here is actually `tracing` spans plus one `ThreadedStats`. Adding it costs a day. Debugging without it costs a week the first time something weird happens.

## ISSUE 6: Prior art — you're reinventing `rayon::ThreadPool` adjacent to crossbeam scoped threads
**Severity:** NICE-TO-HAVE
**Type:** RUST IDIOM

**Problem:** The topology described (two pinned workers, barrier-synchronized per quantum, one of them doubles as coordinator) is close to — but not exactly — the `crossbeam::thread::scope` pattern with a shared barrier. The HLD hand-rolls the spawn/join dance. That's fine, but doesn't flag the standard-library path.

The bigger prior-art miss is that the pattern "two threads, tight barrier-synchronized inner loop, shared arena" is exactly what multi-threaded deterministic-replay systems do (PANDA, rr's multi-core mode, Dolphin's dual-core JIT). The quantum-synchronized model with a shared memory arena is well-trodden. Specifically:

- The quantum size trade-off: smaller quantum → more barrier crossings → more sync overhead; larger quantum → less real-time fidelity and more per-core drift before cross-core visibility. The HLD mentions Q=150 (1 µs) but doesn't justify it against this trade-off curve. Dolphin uses ~1000-cycle quanta. What's the cycle range where threading is a net win vs lockstep?
- False-sharing mitigation: the HLD mentions it in passing ("pad to cache line" in the Risks section) but doesn't specify where. `SpinBarrier`'s two atomics will definitely false-share with each other on current x86. They need `#[repr(align(64))]` around each atomic, or better, the whole barrier in its own cache line. Same for `ThreadedSio`'s head/tail.

**Proposed solution:** Use `crossbeam::thread::scope` for the spawn/join (one dep, tiny, widely used, solves lifetime issues around `Arc` passing cleanly). Add a brief "prior art" paragraph citing dual-core emulators that chose similar quantum-based approaches and their quantum choices. Add explicit cache-line padding in the `SpinBarrier` and `ThreadedSio` struct definitions. I'd also add a quantum-sweep as part of Phase 5 validation: run the same workload at Q ∈ {50, 100, 150, 300, 1000} and pick the knee.

## ISSUE 7: Loom coverage is overclaimed
**Severity:** IMPORTANT
**Type:** TESTING

**Problem:** "Loom tests for SIO ring + barrier. Write `loom::model` tests for the SPSC queue and SpinBarrier. Catches ordering bugs that show up under weak memory models." Plus the risk: "Loom coverage gap — Loom tests the synchronization primitives; it doesn't test that we correctly classified every access as shared vs per-core."

That second sentence is the actual problem, and "Thread Sanitizer on Linux (WSL2) catches those" understates the effort. TSan on a full emulator run is expensive (10-30x slowdown, massive memory), and it catches *actual* races during the instrumented run — not races that happen only under specific firmware. You'd need to run TSan continuously against a representative firmware suite, and TSan reports are notoriously finicky to triage.

Three gaps not named:

1. **Loom doesn't scale to real code.** You can Loom-test the SpinBarrier in isolation, but you cannot Loom-test `SharedMemory::read32` being called from a real instruction executor because Loom has to enumerate all interleavings and real instruction streams have too many. This means Loom tests validate the primitives you'd have gotten for free by using `rtrb` and `std::sync::Barrier`. The *unique* concurrency in this design (the `SharedMemory` atomic-word SRAM, the exclusive monitor cross-core snoop, the FIFO + event flag pair) is the stuff Loom can't cover at full scale.

2. **Model validation vs oracle validation.** The "Dual-run differential test" (validation step 4) says "Assert state at every SIO sync point matches." That is the *only* strong oracle in the plan. It needs to be the cornerstone, not item 4 of 5. And it needs to specify: what counts as a "sync point"? A SIO FIFO push? A spinlock release? The HLD owes a concrete definition so the oracle is reproducible.

3. **Missing: stress-with-deterministic-seed.** The existing QEMU fuzz-diff harness (per CLAUDE.md) is the project's strongest oracle today. Nothing in the HLD extends it to threaded mode. That's the highest-leverage addition to validation.

**Proposed solution:**

- Drop the expectation that Loom is validating the system. Reframe: "Loom validates our bespoke synchronization primitives *if we write any*. Strongly prefer using well-tested primitives and skip Loom entirely."
- Promote the dual-run differential test to validation #1 and define sync points precisely: any write to shared memory visible across cores, any FIFO push/pop, any spinlock state transition, any IRQ delivery.
- Add: "Threaded fuzz-diff harness: run same firmware under `Emulator` and `ThreadedEmulator`, compare post-quantum state. 100K iterations per phase before merge." The seeds are reproducible, the harness already exists in spirit.
- Add ThreadSanitizer as a CI job (even at 10-30x slowdown), not just a Risks-section handwave. Pick one smoke test, run it under TSan in CI, fail the build on new races.

## ISSUE 8: `SharedMemory` abstraction has a subtle correctness issue around u16/u8 writes
**Severity:** CRITICAL
**Type:** DESIGN

**Problem:** The `write8` CAS loop in the HLD:

```rust
let mut current = self.sram[word_idx].load(Relaxed);
loop {
    let desired = (current & !mask) | new_byte;
    match self.sram[word_idx].compare_exchange_weak(
        current, desired, Relaxed, Relaxed
    ) { ... }
}
```

This is a classic "looks right, is wrong in the presence of the exclusive monitor" pattern. Consider:

1. Core 0 does `LDREX r0, [addr]` — sets `exclusive[0] = addr`, reads word W0.
2. Core 1 does `str.b #v, [addr+1]` — the HLD proposes the CAS loop, which does a non-exclusive RMW that modifies the word W0 → W0'.
3. The HLD says "A write to that address from *any* core clears both cores' monitors." OK. But *when* exactly does the clear happen relative to the CAS loop?
4. If the clear is "after the CAS succeeds," then between the CAS and the clear, core 0 can do `STREX` against stale data that sees `exclusive[0]` still set and believes its exclusive is intact. Classic ABA-ish hazard.
5. Separately: the HLD's "overlaps a core's exclusive range" logic is specified as exact-address match (`exclusive[core_id].load == addr_tag`). The Armv8-M spec defines exclusive granularity as at least 8 bytes up to a page. What's our granularity? Word? Cache-line? This must be pinned.

Second issue, also on the CAS loop: `Relaxed` ordering on both success and failure paths is correct for the raw store but wrong if this same SRAM region is being used to build cross-core synchronization (which it will be — every pico-sdk spinlock lives in SRAM). The HLD has a separate fence-translation path for DMB/DSB, but that only fires on explicit fences. Without an explicit DMB, Armv8-M guarantees store ordering on aligned word accesses on the same CPU. The `Relaxed` atomics preserve per-thread ordering from the emulator core's perspective only if the emulator's *host* is TSO (x86). On ARM64 hosts, this is broken. You mentioned the target is x86_64 host, but code you're writing now may run on ARM64 dev machines (Apple Silicon, some Linux ARM hosts) tomorrow.

**Proposed solution:**

1. Document the exclusive-monitor granularity choice explicitly (I recommend: 4-byte word, matching `[AtomicU32]` layout — simplest and Armv8-M-compliant). State it in the HLD.
2. In the exclusive-monitor-clear path, do the clear *before* the successful CAS publishes, not after. Use `Ordering::Release` on the store that does the byte write, and make the exclusive-monitor snoop use `Acquire` loads. Alternatively, and simpler: require all cross-core visible writes to go through a single `write_word_with_monitor_clear` helper that does the CAS under a fence.
3. On ordering: for the SRAM CAS loops, use `Ordering::Release` on success and `Ordering::Acquire` on failure. Yes it's more expensive. The fix for "still too slow" is Phase 5 profiling, not incorrect ordering.
4. Add a target-triple note: "Threaded mode is tested on x86_64-pc-windows-msvc and x86_64-unknown-linux-gnu. ARM64 host support requires re-validation of memory orderings."

This one is CRITICAL because getting it wrong means intermittent heisenbugs in firmware that will be blamed on the guest code.

## ISSUE 9: The `DMB/DSB/ISB` → host-fence translation is incomplete
**Severity:** IMPORTANT
**Type:** DESIGN

**Problem:** "DMB → AcqRel fence. DSB → same (stronger semantics in guest ISA but host can't express). ISB → SeqCst fence + potentially flush decode cache."

Two issues:

1. **DSB is strictly stronger than DMB in the guest.** DMB is a memory barrier; DSB is a system barrier that also waits for outstanding explicit *and implicit* memory accesses (including cache maintenance, TLB ops) to complete. In a bus-cycle-accurate single-threaded emulator, the distinction is modeled by the stall cycle count. In threaded mode, if you conflate DSB → AcqRel, you lose the guarantee that all pending peripheral side-effects from this core have committed before subsequent instructions run. Specifically: if core 0 does `MMIO write` → `DSB` → `bl cross_core_ping`, core 1 observing the FIFO ping must also see the MMIO side-effect. With just AcqRel this breaks if the peripheral mutex ordering is not also SeqCst.

2. **ISB on Armv8-M is "flush any prefetched instructions, re-fetch from memory."** Once you add a decode cache (the follow-up work mentioned), ISB must invalidate it. The HLD hand-waves this as "potentially flush decode cache (once we add one). For now, AcqRel." That's a time bomb — when the decode cache lands, every existing ISB in every existing firmware starts silently ignoring it unless the decode cache implementer remembers to hook the translator. Encode the dependency now.

**Proposed solution:** Make the fence translation an enum with explicit cases:

```rust
enum HostFence {
    Acquire,
    Release,
    AcqRel,
    SeqCst,
    /// In addition to a memory fence, invalidate decode cache on this core.
    DecodeInvalidate,
}

impl HostFence {
    fn emit(self) { /* ... */ }
}
```

Map DMB → `AcqRel`, DSB → `SeqCst` (yes it's more expensive; correct > fast), ISB → `SeqCst` + `DecodeInvalidate`. Leave `DecodeInvalidate` as a no-op until the decode cache lands, but wire it up now so it's obvious what needs to change.

## ISSUE 10: `signal_sev` and event-flag coherence across threads
**Severity:** IMPORTANT
**Type:** DESIGN

**Problem:** Today `Bus::signal_sev()` (bus/mod.rs:354-358) just sets both booleans. The HLD's prereq 0b.3 says "atomicize cross-core fields on `CortexM33`: `halted`, `wfe_waiting`, `event_flag`." Good. But the wake-up semantics aren't specified:

```rust
// Current in lib.rs:142-147:
for i in 0..2 {
    if self.cores[i].wfe_waiting && self.bus.event_flag[i] {
        self.bus.event_flag[i] = false;
        self.cores[i].wfe_waiting = false;
    }
}
```

In threaded mode, both workers are spinning on their quantum. When core 0 issues SEV:

1. It writes `event_flag[1] = true` (atomically).
2. Core 1 is currently sleeping (spinning with `wfe_waiting = true`). It needs to notice.

The HLD's topology has "worker 1 just waits" at the barrier — but that's a *barrier* wait, not a WFE wait. A core that has executed WFE is supposed to drop power until woken. In threaded emulation, WFE-waiting is a state the worker enters and stays in across quanta. The HLD doesn't specify whether:

- Worker 1 keeps crossing the barrier every quantum even when WFE-waiting, just stepping zero instructions, or
- Worker 1 parks on a separate condvar/event when WFE-waiting and doesn't participate in barriers, or
- Some other scheme

Option A wastes power and defeats the point of WFE (though for emulation correctness it's simplest). Option B introduces a coordinator that may miss signals if the SEV happens between the park and the check (classic lost-wakeup).

The single-threaded case doesn't have this problem because signal_sev and the WFE-check both run in the same host thread.

**Proposed solution:** Commit to Option A in the HLD: "A WFE-waiting worker still crosses the barrier; its quantum simply steps zero instructions. This matches the single-threaded emulator's behavior and avoids lost-wakeup hazards. Throughput cost is negligible (barrier crossing is <100 ns; real-world WFE periods are µs-to-ms)." This makes the threading model much easier to reason about and preserves the invariant that both workers are always lockstep at barrier boundaries.

## ISSUE 11: Sharded peripheral mutexes have a deadlock hazard
**Severity:** IMPORTANT
**Type:** DESIGN

**Problem:** The peripheral shards:

```rust
pub struct Peripherals {
    apb:      Mutex<ApbPeripherals>,
    ahb:      Mutex<AhbPeripherals>,
    clocks:   Mutex<ClocksPll>,
    qmi:      Mutex<QmiRegs>,
    resets:   Mutex<ResetsState>,
}
```

A single instruction can touch multiple mutexes if it has side-effects that cross peripheral blocks. Examples on this chip:

- A write to RESETS un-resets a peripheral, which clears PLL locked bits (CLOCKS mutex) and may re-init QMI state.
- A write to CLK_SYS_CTRL touches CLOCKS, but the pacer callback on next quantum reads `bus.sys_clk_hz()` which may cross into PLL registers.
- QMI writes can indirectly affect XIP, which lives in SharedMemory (not mutexed but CAS'd).

If instruction A holds `clocks` and tries to take `resets`, and instruction B on the other core holds `resets` and tries to take `clocks`, you deadlock. Lock ordering is not specified.

Secondary concern: today `Bus` owns the clock tree cache (`clock_tree: ClockTree`, bus/mod.rs:66) and the `recompute_clock_tree` method spans CLOCKS + PLL registers (bus/mod.rs:155-185). Shard it and the recompute becomes a multi-lock critical section.

**Proposed solution:**

1. State lock ordering explicitly in the HLD: "Mutexes must be acquired in this order: `resets` → `clocks` → `qmi` → `apb` → `ahb`. Any code path that takes two must take them in that order." This is a discipline, not a mechanism, but it's the pragmatic approach for ~5 mutexes.
2. Consider a `debug_assert_lock_order!` macro using a per-thread TLS counter that panics if you violate ordering in debug builds. Zero cost in release. Catches all real violations the moment they happen.
3. For `recompute_clock_tree`: decide if the cached `ClockTree` snapshot lives outside the mutexes (updated by the single task that last touched a clock register, published via `Arc<ArcSwap<ClockTree>>` or just `AtomicU32` for each derived frequency). This is almost certainly right — clock-tree reads are hot (pacer reads every quantum) and writes are rare.

## ISSUE 12: Reversibility of bool → AtomicBool refactor affects the existing test surface
**Severity:** NICE-TO-HAVE
**Type:** MAINTENANCE

**Problem:** Prereq 0b.3 atomicizes `halted`, `wfe_waiting`, `event_flag`. The existing test suite has ~50 references to `bus.event_flag[i]` as direct `bool` reads/writes (see `tests.rs:5500-5649`). Every one of those becomes `bus.event_flag[i].load(Relaxed)` / `.store(..., Relaxed)`. That's a mechanical change but it's noisy in diffs and you lose the ability to use them in boolean expressions without a helper method.

**Proposed solution:** Wrap the atomics in a small helper type with `.get()` / `.set()` methods that does the Relaxed load/store inline. Tests read `bus.event_flag[1].get()`, production code uses the same API. Keeps diffs clean, gives you a single chokepoint for ordering changes later. Pattern:

```rust
#[repr(transparent)]
pub struct AtomicFlag(AtomicBool);
impl AtomicFlag {
    pub fn get(&self) -> bool { self.0.load(Ordering::Acquire) }
    pub fn set(&self, v: bool) { self.0.store(v, Ordering::Release) }
    pub fn take(&self) -> bool { self.0.swap(false, Ordering::AcqRel) }
}
```

Three-line type, idiomatic, testable, and documents intent better than scattered `.load(Relaxed)` calls.

## ISSUE 13: Hidden work items not in the phase plan
**Severity:** IMPORTANT
**Type:** DESIGN

**Problem:** Several things the design requires aren't in the 5-week phase plan:

1. **Loom test suite build-up.** Writing meaningful Loom tests is not a weekend task. Plan 2-3 days per primitive being Loom-tested. If you keep the hand-rolled SPSC, that's a week on its own.
2. **Thread pinning.** The HLD mentions "pinned to core X" but doesn't say how. On Windows, `SetThreadAffinityMask`; on Linux, `sched_setaffinity`; on macOS, no supported API. That's a `core_affinity` crate dep or ~50 LOC of conditional `unsafe`. Add it to Phase 3.
3. **Priority elevation.** "Both cores are pinned at HIGH priority" — this requires `SetThreadPriority` on Windows (requires UAC in some configs), `nice`/real-time on Linux. This also needs a crate or platform-specific code.
4. **TSC clock source on the worker thread.** Pacer's `rdtsc` today is called from whatever thread calls `begin_quantum`. On multi-socket systems, TSCs are not guaranteed synchronized across sockets. With pinned threads on different cores (same socket), usually fine on modern CPUs; worth documenting.
5. **`ThreadedEmulator` integration with `mdrp2354-test-harness` (the QEMU diff harness).** If we want threaded mode validated against QEMU (and we do), the harness needs a threaded path too. Not in the phase plan.
6. **Conversion cost of copying all SRAM into `[AtomicU32]`.** 520 KB × 2 cores × byte-by-byte = ~2 million atomic ops on `into_threaded`. Measurable on startup. At minimum, convert with a direct `u32::from_le_bytes` over the underlying `[u8]` into the new `[AtomicU32]` in one pass, not via the write8 CAS loop.

**Proposed solution:** Add a "Hidden work" bullet list to Phase 0b that names these. Most are small; naming them prevents them from being discovered in Phase 3 and blowing the schedule.

## ISSUE 14: Single-threaded path keeps `active_core()` — is there a cleaner invariant?
**Severity:** NICE-TO-HAVE
**Type:** RUST IDIOM

**Problem:** Prereq 0b.1 removes `Bus::active_core()` entirely. Good. But the HLD says "Refactor so each `CortexM33` owns its PPB. Bus no longer has `active_core()`." In practice, `active_core()` is used for more than just PPB indexing today — it's used in SIO reads (`bus.active_core()` passed into `self.sio.read32(word_offset, core)`, bus/mod.rs:521-522), event-flag handling, etc.

The current `active_core()` is *also* a hack around Rust borrow checking: the core's `step` method takes `&mut Bus`, but the bus needs to know which core is calling. The natural idiom would be to make the core ID a parameter of bus operations: `bus.read32(core_id, addr)`. Boring but type-safe, and it evaporates all the "which core is active" state.

**Proposed solution:** When doing prereq 0b.1, go further. Change `Bus` operations from `fn read32(&mut self, addr: u32)` to `fn read32(&mut self, core: CoreId, addr: u32)`. `CoreId` is a newtype around `u8` with `CoreId::CORE_0` and `CoreId::CORE_1` constants. Every existing `self.active_core()` call at the bus layer becomes the parameter. Every peripheral read that cares about which core is calling gets the ID through the call chain. This is boring, mechanical, high-touch work — but the single-threaded refactor and the threaded refactor *both* want it, and doing it once means the threaded code is just "each worker passes its `CoreId` on every bus call." No shared active-core state to manage.

Estimated touch: ~300 call sites across bus/mod.rs, sio, PPB. 2 days of tedious but low-risk edits, saves a week of threading-era bugs.

## ISSUE 15: `StopSignal` — minor, just use `Arc<AtomicBool>`
**Severity:** NICE-TO-HAVE
**Type:** RUST IDIOM

**Problem:** `StopSignal` is a wrapper around `AtomicBool` with a constructor that returns `Arc<Self>`. That's an odd API. It forces every caller into `Arc`, even tests that just want a local one. The `new` returns `Arc<Self>` which means the bare `StopSignal` type can't easily be held by value. Plus the memory orderings (`Release`/`Acquire`) for a stop flag are overkill — `Relaxed` is sufficient for "has stop been requested" (it's not a synchronization primitive for data, it's a boolean).

**Proposed solution:** Just use `Arc<AtomicBool>` at the call site. Delete the `StopSignal` newtype, or if you want the name, make it:

```rust
pub struct StopSignal(AtomicBool);
impl StopSignal {
    pub const fn new() -> Self { Self(AtomicBool::new(false)) }
    pub fn stop(&self) { self.0.store(true, Ordering::Relaxed) }
    pub fn is_stopped(&self) -> bool { self.0.load(Ordering::Relaxed) }
}
```

Caller wraps in `Arc` at the callsite if they need sharing. Tests hold `StopSignal` by value.

## ISSUE 16: Phase 0a decision threshold is undercalibrated
**Severity:** NICE-TO-HAVE
**Type:** DESIGN

**Problem:** "if core 1 is >80% idle (typical for asymmetric firmware), threading gains are below 20%. Shelve." That's a reasonable heuristic but the threshold numbers aren't derived. Amdahl's law on this would say: if core 1 is active X% of the time, theoretical dual-core speedup is (1 + X). For X=20%, speedup = 1.2x. The HLD claims this is <20% gain, which is true. But the threshold should be framed in terms of the goal, not a fixed percentage. If the goal is 2x throughput (as stated in the problem), we need X ≥ 100% — which never happens; both cores being maxed is the upper bound. More realistic: X ≥ 60% gives 1.6x, which is probably worth the engineering cost. X ≥ 80% gives 1.8x, close to the claim.

More importantly, the measurement plan doesn't specify *which* firmware. "Bootrom + representative OneROM firmware" — is this one specific build? Multiple profiles (idle, compute-heavy, IO-heavy)? The decision isn't "threading for OneROM," it's "threading across the realistic workload mix."

**Proposed solution:** Pre-specify the workload set. At minimum: (a) bootrom through XIP cache fill, (b) an RTOS context-switch benchmark, (c) a compute-bound test (FFT or crypto loop on both cores), (d) an idle-heavy test (one core WFI, one core polling). Phase 0a measures all four, reports the dual-core activity ratio for each, and the decision is "proceed if any of these shows >40% both-core activity *and* is a workload we care about for this emulator."

Also: add a measurement. "Single-threaded paced throughput with core 1 halted: 143 MHz. Single-threaded paced throughput with both cores active: 73 MHz." The HLD already has these. But the Phase 0a measurement needs to add *"and here is the theoretical threaded ceiling given current both-core activity ratio."* That's the number that makes go/no-go clear.

## ISSUE 17: No rollback/abandonment plan if Phase 3/4 doesn't deliver
**Severity:** NICE-TO-HAVE
**Type:** DESIGN

**Problem:** The phase plan says "Each phase bails cleanly if blocking issue found." Nice sentiment, but concretely: Phase 0b lands the PPB-per-core, the atomicization, the proper LDREX/STREX. These are single-threaded-correct improvements — good. But Phase 1 adds `SharedMemory` with `Arc<[AtomicU32]>` backing. If Phase 3 reveals that threaded throughput is only 1.3x (not 2x), do we revert Phase 1 and the atomic SRAM? Or keep it in the codebase as dead weight?

Atomic SRAM on the single-threaded path has a cost — every `[u8]` access becomes an atomic load + bit extract. On x86 this is nearly free for aligned u32, but u8/u16 reads become word-load + shift, which may hurt single-threaded perf. The HLD claims "Existing single-threaded tests keep passing" but doesn't claim "single-threaded throughput unchanged."

**Proposed solution:** Add to Phase 1 acceptance criteria: "single-threaded `paced_bench` throughput regression <5% vs pre-refactor baseline." If the refactor costs single-threaded throughput significantly (say, >10%), that's a signal to either keep `[u8]` backing for the non-threaded path or revert. Measure it explicitly; don't discover it in Phase 5.

Also, add an abandonment clause: "If Phase 3 demonstrates <1.5x dual-core speedup, revert Phases 1-2 and pursue decode cache instead." Having the escape hatch written down avoids sunk-cost bias six weeks in.

## Minor / stylistic notes (not worth numbering)

- `pub fn run(&mut self, pacer: &mut Pacer, duration: Duration, stop: Arc<StopSignal>)` returns `()`. Should return something — at minimum cycles executed, at best a `RunResult { cycles_executed, stop_reason, panic: Option<PanicPayload> }`. The single-threaded `run` returns `u64`; don't regress.
- `into_threaded` / `into_emulator` — if you keep both, name them so asymmetry is clear: `Emulator::make_threaded() -> ThreadedEmulator` and `ThreadedEmulator::stop_and_collect() -> Emulator`. The `into_X` convention implies costless reinterpretation, which this isn't.
- The HLD does not mention `#[must_use]` on `StopSignal::stop()` return values, run-result types, etc. Worth adding on any new type where forgetting to check is common.
- `xip: Box<[AtomicU32]>, // if writable via QMI, else plain` — QMI can absolutely cause XIP cache line fills that visibly modify XIP SRAM. Default to AtomicU32; only declare it "plain" if you can prove it's read-only in every firmware.
- The HLD is signed off with "Total: ~5 weeks." After the issues above (properly plumbing panics, proper fence translation, `CoreId` threading, rtrb integration, lock ordering, observability, ThreadSanitizer CI), I'd estimate 7-9 weeks. That's not a criticism — it's healthier to enter the project with a realistic schedule than to slip.
