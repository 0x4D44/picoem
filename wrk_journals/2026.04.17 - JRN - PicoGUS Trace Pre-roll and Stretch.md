# 2026-04-17 — PicoGUS Trace Pre-roll and Stretch

**Role:** IC. Arthur collaborating.

## Starting state

The PicoGUS silent-audio diagnosis (see `2026.04.17 - JRN - PicoGUS Silent Audio Diagnosis.md`) landed permanent PIO TXFn + I2S-capture tracing and proved the captured WAV is a faithful recording of silence — firmware pushes `0x00000000` to PIO1 SM3 on every PWM-IRQ fire because the GUS audio engine was never armed.

Harness capture coverage diagnostic shows the smoking gun: trace deciles 0-50% have **0%** PIO0 SM0 capture rate, 50-100% jump to ~40% steady state. Reading: firmware's PIO0 SM0 ISA-sniffing state machine isn't online yet during the first half of the trace, so the GUS init handshake writes sail past an unconfigured SM and the firmware never hears "start playing."

## Hypothesis

The trace (from a patched DOSBox-X playing Monkey Island) starts at `ns=0` with the PC already booted and hammering ISA ports. But in the emulator, `t=0` = firmware-boot-start. The two timelines are mis-aligned.

Two tiny knobs that should fix this without a real silicon oracle:

1. **`--pre-roll <secs>`** — advance the emulator for N sim-seconds *before* firing the first trace event. Lets firmware finish boot and arm PIO0 SM0 before the DOS side starts writing.
2. **`--trace-stretch <factor>`** — multiply every `ev.ns` by a constant. Opens the gap between back-to-back writes so the PIO has more headroom. Useful if residual ~60% drop after pre-roll is a PIO timing issue.

Both are ~10-line edits to the replay loop at `picogus_diff_rp2040.rs:646-693`.

## Trace shape (confirmed)

- First event at `ns=0`, last at `ns=29,991,219,767` → **30 seconds** of DOSBox-X wall-clock.
- 523,902 events total → ~17.5k events/sec average; probably front-loaded with GUS init.
- Prior run with `--duration 3`: `Final sim time = 5.41 ms`, `duration_capped = true`. Implies there's a large gap in the trace — events 1..N are dense in the first 5.4 ms, then the next event is past 3 s (which hits the cap).

**Stretch-2 adds effectively nothing on top of pre-roll.** The residual 60% drop rate is structural, not a rate-limit issue. Confirms:
- Drops aren't due to inter-event gaps being too tight (stretching them didn't help).
- Drops aren't due to firmware-side PIO arming latency (pre-roll made the decile profile uniform).
- Drops are probably architectural — write16 gets split into two back-to-back 8-bit cycles at adjacent ports; the `WRITE_*_CYCLES` constants inside a single event (49 cycles total) don't change with stretch.

Core 1 PCs for the three runs all differ slightly — inherent nondeterminism at 1.3 B-cycle scale, or the stretch shifting when firmware polls its I2S buffer relative to PIO capture events.

### Trace shape — not what I thought
Re-analysed `monkey_island_theme.trace`:
- 514,502 events crammed into the first **5.41 ms** (that's ~95 million events/sec — wildly non-realtime; DOSBox-X must have captured with dynamic-core speed or a relative-clock bug).
- Events 514,502 to ~514,666: a 164-event dribble between 3.00 s and 3.80 s.
- Largest gap: **3.979 s** silence between events 514,666 (at 3.798 s) and 514,667 (at 7.777 s).
- Trickle of ~400 more events from 7.8 s to 29.99 s.

So the "30-second trace" is really a 5.41 ms blast followed by 30 seconds of mostly silence. This has a big consequence for `--trace-stretch`: in the init burst, event gaps are ~108 ns apart, but each `drive_write_cycle` call consumes `WRITE_IDLE + WRITE_ADDR_HOLD + WRITE_DATA_HOLD = 12+12+25 = 49 cycles` (~392 ns at 125 MHz, ~132 ns at 370 MHz). **The harness is already rate-limiting the init burst to ~2.5 Msps through its own timing constants — trace-ns gaps smaller than that are invisible to `advance_to_sim_ns`.**

That's why stretch=2 did nothing: doubled 108→216 ns, still < 392 ns minimum. Need stretch ≥ 4× at 125 MHz before stretch starts actually opening gaps in the init burst. Kicked off stretch=10 experiment in background (`wrk_scratch/pre3_str10.*log`).

### `--pre-roll 3 --trace-stretch 10` — theory refuted

| Metric | Pre-roll only | Stretch 2 | Stretch 10 |
|--------|---------------|-----------|------------|
| Total drop% | 60.1% | 60.4% | **60.1%** |
| 0-10% decile capture | 39.2% | 36.6% | 39.1% |
| Other deciles | ~40% | ~40% | ~40% |
| PIO0 SM0 autopushes | 287,802 | 285,895 | 287,973 |
| WAV size | 557 KB | 558 KB | 562 KB |
| Frames | 139,294 | 139,424 | 140,469 |
| Sample rate | 39,982 Hz | 39,958 Hz | 39,762 Hz |
| WAV non-zero samples | **0** | **0** | **0** |
| Wall time | 161 s | 163 s | 169 s |

**My "gaps below harness minimum" theory was wrong.** Even at stretch=10 — where inter-event gaps in the init burst become 1,080 ns (≫ harness minimum 392 ns) — the drop rate stays at 60.1%. The ~40% capture cap is therefore **not** a rate-limiting issue at the bus timing layer.

The residual 60% drop must be structural inside the PIO0 SM0 program itself or the firmware's autopush configuration. Candidates for follow-up:
- Autopush-threshold aliasing: PIO pushes every N bits but the actual ISA waveform only matches the PIO's sampling pattern ~40% of the time
- PIO program has a setup/reset phase that only completes for a fraction of writes
- Firmware side software-drops ~60% of captured words (but this would show up as "captured" in the coverage metric, so unlikely)

Played the entire 30-second trace for the first time. All 523,902 events fired (up from 514,502 capped at `--duration 3`). The extra 9,400 writes are the sparse trickle from 3 s to 30 s trace-domain — mostly 0x343 / 0x345 control register pokes (GUS voice config) and a few 0x342 voice-select writes.

**838,373 frames of pure silence.** Even with the full trace played and pre-roll giving firmware a clean boot window, the GUS audio engine never emits a non-zero sample. The lower average sample rate (24,959 Hz vs 39,982 Hz) suggests firmware downshifts the PWM somewhere during the 30 s run — possibly an idle-mode transition after the init burst.

The 9,400 extra writes in the trickle do reach firmware (drop rate stays at the same 60.1%), so the trace events after 3 s are being received as expected. They just don't unblock the audio engine.

## Findings so far

1. **`--pre-roll 3` is a genuine fix** for the trace-replay / firmware-boot skew. Decile-0-50% capture jumped from 0% → ~40%, total PIO0 SM0 autopushes doubled (135k → 287k), audio-duration 6× (0.57s → 3.48s).
2. **`--trace-stretch` has zero effect on drop rate on this trace** — confirmed across stretch=1, 2, and 10. My initial theory that stretch=2 didn't work because 216 ns gaps were still under the 392 ns harness minimum was testable: at stretch=10 (1,080 ns gaps), drop rate was still 60.1%. So the residual 60% drop is **not** a bus-timing issue at all. Architectural, at the PIO autopush / firmware handling layer.
3. **Audio is still silent** even with the full 30-second trace replayed (838,373 frames, all zeros). Firmware is now receiving 2.2× more writes than baseline and the complete trace content plays through — but `GUS_sample_stereo()` still returns 0. Something in the GUS init handshake is still incomplete. Leading suspect: **the firmware needs to *read* state from the DOSBox-X guest that we can't replay** (the header comment warns: "the DOSBox-X guest already materialised whatever status value it cared about; we're driving the real firmware open-loop"). This would explain why no amount of write-replay fidelity fixes it.
4. **Residual 60% drop is structural**, not rate-related. Hypotheses for follow-up: write16 split into back-to-back 8-bit cycles whose intra-pair `WRITE_IDLE` might be too tight; PIO program's autopush threshold creating aliasing; or intentional firmware sampling of only-every-other-write in a read-modify-write loop.

## Follow-ups for next session

- **Skip the `--bus-idle` idea.** Stretch=10 proves bus-timing isn't what's capping capture. A wider per-event idle window would not move the needle.
- **Figure out how to replay reads.** The header comment admits we skip them; that's probably the real blocker for GUS init. Would need either: (a) a richer trace format that records return values, or (b) a firmware patch that plumbs fake responses.
- **Follow up with the silent-audio team:** pre-roll = 3 is now effectively required to reproduce "firmware gets past init," so any future work on the audio-engine-wiring side should adopt this flag in its repro.
