## Context

gap (78.8 → 247 MHz unpaced) caused by per-instruction peripheral
ticks in `mdrp2040::Emulator::step()`. Root cause traced to the
unimplemented `step_quantum` field (tech_debt.md:137-148). Arthur
authorised the fix; this supervises an agent team to implement it.

## Stages 2 & 3 — Code review + Devil's advocate

Launched in parallel against commit `0ef90d2`.

### Code reviewer findings (all non-blocking)

- **[MINOR]** `lib.rs:226` — `run()` docstring still says "may overshoot
  by at most one instruction"; should be "up to `step_quantum - 1`
  cycles."
- **[MINOR]** `lib.rs:180` — `start + step_quantum` is non-wrapping
  while the rest of the arithmetic uses wrapping. Inconsistent; match
  mdrp2350 by keeping the same wrapping semantics.
- **[MINOR]** `lib.rs:177-207` — docstring says "Mirrors
  mdrp2350::Emulator::step"; actually only the peripheral-tick model
  mirrors. The schedules differ (core-interleaved here, core-serial
  there — chosen deliberately to preserve mdrp2040's bank-contention
  model).
- **[NIT]** Five `EmulatorBuilder::new(...).step_quantum(1).build()`
  boilerplates in `pio_tests.rs` could share a helper. Cosmetic.

### Devil's advocate findings

- **#1 Halted-core-0-freezes-core-1**: Devil's advocate called this a
  new regression. On inspection: **not a regression**. OLD `step()`
  also returns 0 when core 0 halted (c0=0), so `run()` hit the
  `consumed == 0` break in the same situation. Both old and new
  behaviors stall under that scenario; the only micro-difference is
  that old code stepped core 1 one instruction before returning.
  Legitimate pre-existing issue — out of scope for this HLD.
- **#2 `target` non-wrapping**: same as code reviewer — will fix.
- **#3 Overshoot**: false alarm per their own analysis.
- **#4 PIO IN PINS staleness**: **real behavior change** for mdrp2040.
  Old code ticked PIO per-instruction with fresh `gpio_in` each time;
  new code ticks once per quantum with stale `gpio_in` from previous
  quantum end. Matches mdrp2350's established model. HLD should flag.
- **#5 Pacer drift / throughput undercount**: real. `paced_bench_rp2040`
  uses `n += qc` (asked) instead of `n += consumed` (actual); at
  `qc=125, step_quantum=64`, `run(125)` delivers ~128 cycles. Only
  ~2% undercount in paced_bench, but ~22% in `mdrp2040app/sim.rs`
  where `qc=150` and the pacer-reported MHz doesn't account for
  overshoot. Fix the bench in this session; leave `sim.rs` fix for a
  separate session (it's a pacer-API design question).
- **#6 Test coverage**: legitimate but separate scope. Defer.
- **#7 HLD wording**: minor, fold into stage 4.

- HEAD is `0ef90d2`; step() intact.

  scope).

- `cargo test -p mdrp2040app --release`: 1 passed.
- **Three unpaced runs at default settings**: 210.6 / 211.8 / 210.4
  MHz (~0.7% variance). Host/emu cycle: 14.5–14.6.
- **Paced at default**: 119.7 MHz (95.8% of 125 MHz target),
  **REAL-TIME MARGINAL** (0.05% behind). Was CANNOT SUSTAIN before.
- **65.6 MHz reproduced**: `--quantum 20` gives 65.6 MHz exactly.
  Throughput scales ~1/quantum because per-quantum peripheral-tick
  overhead dominates at small quanta. Full scaling: quantum=8 → 26,
  16 → 52, 20 → 65.6, 25 → 81.4, 125 → 211. Expected behavior.

**Conclusion**: Stage 1 is working as designed at default quantum=64.
Arthur's 65.6 MHz observation was with `--quantum 20`, deliberately
stress-testing small-quantum behavior. Worth an HLD note about
quantum-to-throughput scaling.
