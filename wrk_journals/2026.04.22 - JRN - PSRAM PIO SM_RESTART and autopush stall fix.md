# 2026.04.22 — PSRAM PIO autopush stall + SM_RESTART shift-count fix

## Context

Continuing from the firmware-rebuild session journal
(`2026.04.22 - JRN - PicoGUS firmware rebuild with UART stdio.md`). That
session's 50 ms replay produced silent WAV (`Non-zero bytes: 0`,
`autopush_count: 20` out of expected 500k+ events). The rebuilt firmware
was reaching the trace replay but firmware blocked on the first
`psram_write8` → `dma_channel_wait_for_finish_blocking`, PIO1 SM0 stuck
at `PC=0x19` with `EXEC_STALLED=1`, `pad_out_cs_falls=0`, and no PSRAM
bytes written.

This session: characterized the stall, found two independent PIO bugs,
fixed them, and saw firmware process **654k events with 65k PSRAM
bytes written** on a 5 ms replay.

## Findings

### Bug 1 — silent autopush drop breaks PSRAM SPI reads

`crates/mdpicoem-common/src/pio/sm.rs` `exec_in` used to retain the ISR
when autopush would fire but RX FIFO was full (comment: "real RP2040
stalls... we drop silently — known divergence").

**Why it broke PSRAM:**
- `psram_read(count=16)` executes 128 `IN PINS, 1` in the PIO SPI
  program. Expected: 16 autopushes into RX FIFO, drained in parallel
  by DMA CH1 (16-byte dst).
- Observed (pre-fix): only 4 autopushes. 109 dropped silently.
- Root cause: each `IN PINS, 1` shifts a new bit into ISR and bumps
  `isr_count` (capped at 32). When the first autopush can't fit,
  `isr_count` stays ≥ 8 but the ISR keeps shifting new bits in.
  Subsequent autopushes pick up whatever 32-bit snapshot of ISR is
  current, so autopush fires roughly every 32 IN PINS instead of every
  8 — and each push carries a 32-bit word instead of the 8 discrete
  bytes the driver expects. DMA drains `floor(128/32) = 4` bytes
  instead of 16, and firmware's `dma_channel_wait_for_finish_blocking`
  waits forever.

**Fix:** `exec_in` now checks for a pending autopush BEFORE shifting.
If ISR is already ≥ threshold AND RX is full: stall with
`StallKind::Push` (no new shift, PC doesn't advance). The stall
resolves when DMA drains RX. Matches RP2040 datasheet §3.5.4.

After fix: 13 autopushes (up from 4), DMA drained all delivered bytes.
But firmware still blocked — revealed Bug 2.

### Bug 2 — `SM_RESTART` sets `osr_count = 0`, breaking first-OUT autopull

`crates/mdpicoem-common/src/pio/mod.rs` `write_ctrl` cleared shift
counters to 0 on `SM_RESTART`. But `StateMachine::new()` already uses
the convention `osr_count = 32` ("OSR empty, autopull fires on first
OUT") — matching the epio reference and real RP2040/RP2350 behaviour.

**Why it broke PSRAM:**
- SDK flow: `pio_sm_init` → `pio_sm_restart` → `pio_sm_set_enabled` →
  firmware's first DMA push.
- rp2040-psram program opens with `begin: out x, 8`. With
  `osr_count = 0`, autopull check (`osr_count >= pull_thresh`) fails,
  so OUT X reads 8 bits of OSR-initial-zero → **x = 0**, not the `8`
  the firmware pushed. Every subsequent OUT is off by one byte.
- Cascaded effect: `reset_en` command `[8, 0, 0x66]` executes as
  `x=0, y=8, writeloop 1 iter with garbage bit, fall to readloop with
  y=8`. PSRAM never sees the real reset command; the 8-bit "read"
  phase is a phantom; next `begin` wraps with OSR holding stale
  zero-byte 2.
- Added a one-line `eprintln` trace behind `MDPIOLOG=1` in
  `exec_out`'s destination-X/Y branches to confirm: first `OUT X, 8
  = 0x0`, then `OUT Y, 8 = 0x8` — the `8` that should have landed in
  X shifted into Y. Debug print reverted after diagnosis.

**Fix:** `SM_RESTART` now sets `osr_count = 32` (keeping `isr_count = 0`
for ISR-empty). First OUT X correctly triggers autopull, picks up
byte 1, and PSRAM reset sequence runs end-to-end.

### Bug 3 — `pio-pad-diag` feature not enabled in harness

`crates/mdpicoem-harness/Cargo.toml` didn't enable the
`pio-pad-diag` feature on `mdpicoem-common`, so the PSRAM-SPI
pad-edge counters (`pad_out_cs_falls`, `sck_toggles`,
`mosi_writes_of_1`) stayed at 0 and masked the real activity. Flipped
to `features = ["pio-pad-diag"]`; now the counters reflect true CS /
SCK / MOSI transitions during SPI frames.

## Remaining — WAV still silent

Even with PSRAM fully functioning and 654k ISA events processed, the
output WAV is `peak=0, non-zero=0`. The GUS voice processor /
I2S output path isn't producing audio samples. Candidates for the next
session:

1. **Voice enable not set** — even though reset is released (0x07), the
   GUS voice control registers may not have been written yet in the
   first 5 ms of trace.
2. **I2S PIO1 SM3 or DMA refill path** not getting sample data. Sample
   rate inferred is 32.5 kHz from LRCLK, so I2S itself is clocking —
   just not getting non-zero samples from the audio mixer.
3. **Audio callback (PWM/timer-IRQ → `GUS_sample_stereo`)** may not be
   firing, or the mixer is reading the wrong PSRAM address.

Worth trying: a 50 ms or 200 ms replay (the original overnight target)
to let voices get activated deeper into the trace. Add per-decile
`autopush_count` tracking to see where the flow might choke.
