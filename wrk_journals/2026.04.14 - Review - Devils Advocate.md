# Devil's Advocate Review: Threaded Dual-Core Emulation HLD

**Reviewer:** Claude (devil's advocate mode)
**Date:** 2026-04-14
**HLD under review:** `d:\language\mdrp2354\wrk_docs\2026.04.14 - HLD - Threaded Dual-Core Emulation.md` v1.0.0

## Executive summary

The HLD has one foundational problem and a long tail of missing scope. The foundational problem is **the arithmetic doesn't work the way the HLD implies it does**: threading divides work across two host cores, but each emulated core still runs as a single interpreter on one host core. Threading cannot lift per-core throughput above the single-core ceiling of 143 MHz — so the *aggregate* number gets to ~286 MHz, which looks great in the benchmark but doesn't actually hit "150 MHz per core" as real-time targets demand for most firmware.

The long tail: exceptions, coprocessors (FPU, DCP, RCP, CPACR), faults, halt/reset, the rest of the 4 GB address space, PPB register files, contention arbitration, thread-affinity on hosts with fewer cores, and how SEV is delivered across threads are all unaddressed. Several of these are not "nice to have" — they are load-bearing for the existing test suite and bootrom work.

I think the right move is to **shelve the HLD, run a workload study on real OneROM firmware first, and revisit only if the data says threading actually helps.** If OneROM is WFI-dominant on core 1 (as is typical for asymmetric firmware), the threaded design buys us ~0% on the workload that matters.

## ISSUE 1: Threading cannot raise per-core throughput above the single-core ceiling
**Severity:** CRITICAL
**Type:** WRONG PREMISE

**Problem:** The HLD's problem statement says "dual-core paced throughput on a 3 GHz host: 73.8 MHz (49% of target). Single-core is 143.8 MHz (96%)." The implicit claim is that threading closes this gap toward 150 MHz. It doesn't — not for the metric that matters.

Single-core throughput (143.8 MHz) is already near the interpreter's per-core ceiling. With perfect parallelism and zero synchronisation overhead, threading produces:
- Core 0: 143 MHz on host core A
- Core 1: 143 MHz on host core B
- Combined: 286 MHz "emulated cycles per wall second"

But "150 MHz" is a per-emulated-core clock target, not an aggregated budget. Each core still ticks at 143 MHz, which is `<` target. The HLD's Phase 5 success criterion is "`>=`100 MHz actual, 150 MHz stretch" — this conflates aggregate throughput with per-core rate.

If firmware runs only on core 0 (common — many RP2350 apps wake core 1 briefly for specific work), threading doesn't touch the critical path. Core 0 still runs at 143 MHz. Core 1's thread is idle. Net gain: zero.

**Proposed solution:** Rewrite the problem statement with explicit per-core targets and explicit aggregate targets. State the threading speedup as "at most 2x aggregate, 1x per core." Then decide whether the target is per-core 150 MHz (in which case threading doesn't solve it — we need JIT or cached decode) or aggregate 2×150 MHz (in which case threading solves it but the problem should have been framed that way from the start).

## ISSUE 2: Workload assumption is unvalidated
**Severity:** CRITICAL
**Type:** UNSTATED ASSUMPTION

**Problem:** The entire performance argument is based on two busy loops of `MOVS/ADDS/B` (see `d:\language\mdrp2354\crates\mdrp2354-test-harness\src\bin\paced_bench.rs:79-100`). Real firmware is nothing like this. RP2350 firmware typically has:
- Core 0 doing main work, core 1 WFI-waiting or polling a FIFO
- SIO FIFO ping-pong (serialising — gains nothing from threading)
- Spinlock contention around shared data (serialising — threading hurts)
- Peripheral access bursts (serialising through the `Mutex<Peripherals>` in the HLD)
- Interrupt-driven wake cycles (short bursts, long idle)

The HLD assumes symmetric steady-state dual-core execution. It admits no workload study. There's no data on OneROM firmware's actual core-utilisation profile.

If OneROM firmware is asymmetric (80% core 0 busy / 20% core 1 active), threading buys ~20% aggregate throughput, not 2x.

**Proposed solution:** Before writing a line of threading code, instrument the existing single-threaded emulator to measure, on actual OneROM firmware:
1. Per-core active-vs-WFI cycle breakdown
2. Cross-core memory sharing frequency
3. SIO FIFO/spinlock traffic rate
4. Peripheral-access rate (bounds Mutex contention)

If core 1 is WFI more than ~40% of the time, the HLD's speedup model is wrong and threading should be deferred until we have a workload that benefits.

## ISSUE 3: The alternatives are not evaluated
**Severity:** IMPORTANT
**Type:** MISSING SCOPE

**Problem:** The HLD dismisses alternatives in one sentence each ("Neither PGO nor inline annotations move the needle meaningfully") without data. It never considers:
- **Cached decode / interpreter threading (computed goto).** Cortex-M3/M4/M33 decoders commonly see 3-5x speedup from cached decode. The HLD admits we're "already near the single-threaded ceiling" with no profiling evidence.
- **Hot-loop JIT** for tight inner loops detected at runtime. The "What this does NOT do" section mentions "JIT would be 5-10x" — so we *know* the bigger win is there.
- **Compile-time instruction specialisation** (macro-generated dispatch per opcode).
- **Reducing per-step overhead**: the `Bus::step` path has contention tracking, SIO tick, GPIO merge, MTIME, PIO stepping — all run unconditionally. Many workloads don't need PIO at all.
- **Asymmetric partitioning**: "coordinator thread runs core 0, worker runs core 1" avoids the 3-thread barrier entirely.

A 2x threaded speedup on a partially-utilised dual-core workload looks worse than a 3x cached-decode speedup on a fully-utilised single-core workload.

**Proposed solution:** Add a section comparing expected speedup, implementation cost, and correctness risk for each alternative, with measured or cited evidence. Specifically, profile the current interpreter to find where the 143 MHz wall actually is — is it decode, dispatch, bus overhead, or something else? That profile should *precede* the decision to thread.

## ISSUE 4: Thread affinity on hosts with fewer than 3 cores
**Severity:** IMPORTANT
**Type:** EDGE CASE

**Problem:** The HLD (Risks section) says "worker threads ideally pin to specific host cores." The existing `win::boost_and_pin` in `paced_bench.rs:31-45` pins ONE thread to ONE core. The HLD needs **three** host cores (coordinator + 2 workers). What happens on:
- A 2-core / 4-thread laptop? Two workers pinned to distinct cores leaves the coordinator competing with one of them.
- CI with `numactl` constraints?
- WSL2 (which reports host cores but has its own scheduler layer)?
- A cloud VM with 2 vCPUs?

If all three threads end up on two cores, the barrier becomes a context-switch storm: worker 0 stalls waiting for the barrier while worker 1 has to preempt it to make progress. Throughput collapses *below* single-threaded.

The HLD also implicitly assumes `HIGH_PRIORITY_CLASS + TIME_CRITICAL` (copied from `paced_bench`) works for multiple threads. Three TIME_CRITICAL threads with overlapping affinity is a scheduling pathology.

**Proposed solution:**
1. Enumerate host logical cores at startup. Require at least 3; fall back to single-threaded mode silently if fewer (or refuse to run threaded).
2. Detect WSL2 / virtualised / constrained environments and bail out to single-threaded.
3. Do NOT set TIME_CRITICAL on worker threads; reserve that for the coordinator (or nobody).
4. Document the minimum-host requirement in the public API: "`run_threaded` requires at least 3 logical cores; call `run` on lower-end hosts."

## ISSUE 5: Per-core PPB register file is not addressed
**Severity:** CRITICAL
**Type:** MISSING SCOPE

**Problem:** `Bus::ppb: [Ppb; 2]` holds per-core NVIC, SCB, SysTick, MPU, SAU state. Exception entry/exit (`d:\language\mdrp2354\crates\mdrp2354\src\core\exceptions.rs:86-94`) does:
```rust
let vtor = bus.ppb[bus.active_core()].vtor;
let vector = bus.read32(vtor.wrapping_add((exc_num as u32) * 4));
// ...
bus.ppb[bus.active_core()].clear_active(active_exc as u16);
```

This is mutated on every exception by `active_core()`, which is derived from a *flag* (`contention_check_active`) that toggles between core 0 and core 1 steps in `Emulator::step`. In the threaded model:
- `active_core()` becomes non-sensical — both cores run concurrently, there is no single "active" core.
- `ppb[0]` is accessed by thread 0, `ppb[1]` by thread 1 — so in principle they can live on per-core state. But **`bfar`, `cfsr`, `hfsr`, `shcsr`, `mmfar`, `cpacr` are all read/written within the bus fault path** of `step()`.

The HLD says "accept bus-fault path through the Mutex" but never calls this out. Every exception taken by either core hits `bus.ppb[active_core()]`. How?

**Proposed solution:**
- Move `ppb: [Ppb; 2]` out of `Bus` and into per-core state (store one `Ppb` inside `CortexM33` or a parallel per-core struct owned by each worker thread).
- Remove the `active_core()` flag entirely — each thread knows its own core ID statically.
- Document which code paths currently use `active_core()` and audit each one for the new ownership model.

## ISSUE 6: Coprocessor state ownership is unclear
**Severity:** IMPORTANT
**Type:** MISSING SCOPE

**Problem:** Per-core coprocessor state is split across:
- `CortexM33.dcp_data: [u32; 2]` — DCP transfer registers (moves with core, fine).
- `CortexM33.regs.s: [f32; 32]`, `fpscr: u32` — FPU state (moves with core, fine).
- `Bus.rcp_salt: [u32; 2]`, `rcp_salt_valid: [bool; 2]` — RCP salts (shared state in `Bus`).
- `Bus.ppb[core].cpacr` — per-core coprocessor access control (see Issue 5).

Look at `d:\language\mdrp2354\crates\mdrp2354\src\core\coprocessor.rs:104-116`:
```rust
(8, 0) => { bus.rcp_salt[0] = self.regs.r[rt]; bus.rcp_salt_valid[0] = true; }
(8, 1) => { bus.rcp_salt[1] = self.regs.r[rt]; bus.rcp_salt_valid[1] = true; }
```
Core 1 can write `rcp_salt[0]` — this is deliberate cross-core RCP API. In threaded mode both workers will simultaneously reach into this array. The HLD mentions neither RCP nor any mechanism for cross-core register mutation outside the SIO.

**Proposed solution:** Inventory every cross-core mutable field in `Bus` (at minimum: `rcp_salt`, `rcp_salt_valid`, `event_flag`, `ppb[other_core]`) and decide per-field whether to (a) move into per-core state, (b) wrap in an atomic, or (c) accept the Mutex cost. `rcp_salt` is touched rarely — atomics are overkill; put it in the SIO-shared state struct.

## ISSUE 7: DMB/DSB/ISB semantics are hand-waved
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION

**Problem:** The HLD says:
> firmware that needs ordering uses DMB/DSB, which we translate to host `fence(AcqRel)`.

The current DMB/DSB/ISB implementation is a `1` cycle cost and nothing else (`d:\language\mdrp2354\crates\mdrp2354\src\core\execute_thumb32.rs:864-866`). There are no fences. So:

1. The HLD's correctness argument ("firmware that needs ordering uses DMB/DSB") is contingent on a code change that isn't in the HLD's Files Changed list.
2. ARMv8-M `DSB` orders both memory and **system register** operations (e.g., completion of prior MPU/SAU changes). `AcqRel` doesn't cover the latter.
3. `ISB` on ARMv8-M invalidates the prefetch buffer and ensures context-changing effects are visible. In a threaded emulator, there's no prefetch buffer to invalidate, but `ISB` is often used after code modification. See Issue 8.
4. Relaxed atomics on `[AtomicU8]` don't establish any cross-thread happens-before. Even `DMB` → `fence(AcqRel)` doesn't help: the *surrounding* loads and stores are Relaxed. A Rust `fence(AcqRel)` on its own is largely a no-op on x86; it only matters if paired with `Release` stores / `Acquire` loads on the other side. The HLD's model has neither.

**Proposed solution:**
- Spell out the memory model explicitly: which operations are `Relaxed`, which are `Release`/`Acquire`, and where fences go.
- Probably safer to use `Release` stores and `Acquire` loads on the atomic bytes (x86 cost: zero; ARM host cost: real but we're not on ARM host).
- Clarify what DMB/DSB/ISB map to, including system-register ordering semantics that `AcqRel` doesn't cover.

## ISSUE 8: Self-modifying code and ISB
**Severity:** IMPORTANT
**Type:** EDGE CASE

**Problem:** The bootrom writes code into SRAM and then executes it. Even single-threaded, we don't currently have an I-cache, so this works. In threaded mode:
- Core 0 writes instruction bytes to SRAM via `Relaxed` store.
- Core 0 executes `ISB` (currently: a no-op).
- Core 0 branches into the new code.

With `Relaxed` stores and a no-op ISB, core 1 may or may not see the new instructions when it later reaches them. On x86 hosts, aligned writes followed by branches are fine in practice, but the *emulator* has no explicit guarantee. And the bootrom specifically uses `ISB` after unlocking code-modifying regions; firmware relies on it.

If we model ISB as `fence(AcqRel)` on both the writing and reading core, we get correct behaviour at huge cost. If we don't, we have a correctness hole that only fires on stress tests.

**Proposed solution:** Document that within-core SMC works naturally (no I-cache, same thread); cross-core SMC requires a fence. Implement ISB as at minimum `fence(Release)` on the executing core. Check whether the bootrom's SMC paths are single-core (if yes, we're fine); if any firmware does cross-core SMC, we need cross-core fence.

## ISSUE 9: Per-cycle bus contention accuracy loss is bigger than stated
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION

**Problem:** The HLD says "no per-cycle bus contention modelling" and treats this as minor. But the contention model is tested by `bank_conflict_test` and is part of the cycle-accuracy contract. Looking at `Bus::arbitrate_pair`, `check_contention`, `begin_contention_check`, and the `active_core` flag — this is a deliberate, invasive design for lockstep execution.

In threaded mode:
- `active_core()` returns garbage (it's a flag, not a real per-core identity).
- `core0_port` is recorded by whichever thread happens to step first, then read by whichever thread steps second. Racy and meaningless.
- `contention_check_active` is set by `Emulator::step`, which doesn't run.

So it's not just "no per-cycle contention modelling" — the entire contention subsystem has to be gated out. The HLD says "remove mut access" but doesn't describe how the contention-checking path is replaced or guarded.

**Proposed solution:** Explicitly state: in threaded mode, `arbitrate_pair`, `check_contention`, `clear_contention_state`, and `begin_contention_check` are dead code. The `active_core()` accessor must be replaced by an explicit per-thread core ID passed into `bus.read/write` (likely via a `BusView` type per thread). This is not a trivial refactor — many call sites use `bus.active_core()`.

## ISSUE 10: The rest of the 4 GB address space
**Severity:** CRITICAL
**Type:** MISSING SCOPE

**Problem:** The HLD's `SharedMemory` has only `sram`, `rom`, `xip`. The real bus handles:
- `0x0000_0000..0x0000_8000` — ROM (read-only, easy)
- `0x1000_0000..0x1400_0000` — XIP flash (present — but `xip_cache_offset` is mutable state)
- `0x1C00_0000..0x1C00_4000` — XIP SRAM (4 KB, mutable)
- `0x2000_0000..0x2008_0000` — SRAM (present)
- `0x4000_0000..0x5000_0000` — APB peripherals (RESETS, CLOCKS, XOSC, PLL_SYS, PLL_USB, QMI, PIO0-2 …)
- `0x5000_0000..0x6000_0000` — AHB peripherals
- `0xD000_0000..0xE000_0000` — SIO (core-local reads — CPUID, GPIO, divider …)
- `0xE000_0000..0xE001_0000` — PPB (per-core)
- `0xEFFF_F000..0xF000_0000` — boot RAM (4 KB, used by bootrom for secure stack)
- `peripheral_regs: HashMap<u32, u32>` — catch-all for stubbed registers

The HLD covers SRAM/ROM/XIP. What about everything else?
- `boot_ram` is mutable, actively used by secure stack — needs atomic or Mutex.
- `xip_cache_offset`, `clk_ref_ctrl`, `clk_sys_ctrl`, `clk_sys_div`, `pll_sys_regs`, `pll_usb_regs`, `qmi_regs`, `gpio_hi_noise_state`, `peripheral_regs: HashMap` — all live on `Bus`, all mutable, all currently single-cycle. Putting a Mutex around "peripherals" makes every access to any of these a mutex acquire.
- The `HashMap<u32, u32>` catch-all resizes on inserts — cannot be accessed under a read-only borrow.
- `recompute_clock_tree` mutates `clock_tree` after PLL writes — triggered from register writes from either core.

**Proposed solution:** List every field of `Bus` and classify: per-core / shared-atomic / shared-mutex / shared-RwLock. Replace the `HashMap` catch-all with a fixed-size array keyed by region (or make it immutable-populated at construction time). Be explicit about `boot_ram`'s thread model.

## ISSUE 11: SEV and event_flag cross-thread delivery
**Severity:** IMPORTANT
**Type:** EDGE CASE

**Problem:** In single-threaded mode, SEV (`d:\language\mdrp2354\crates\mdrp2354\src\bus\mod.rs:355-358`):
```rust
pub fn signal_sev(&mut self) {
    self.event_flag[0] = true;
    self.event_flag[1] = true;
}
```
The wake check runs in `Emulator::step` after both cores stepped. In threaded mode, SEV from core 0 must wake core 1 **within the current quantum** for firmware that uses `WFE` as a lightweight sleep. But core 1's thread is running its own quantum — it won't check the event flag until the quantum ends (in the best case) or when it naturally reaches `WFE` again.

Also: the HLD's ThreadedSio replaces the FIFO, but the FIFO push sets `event_flag[receiver]` via `pending_fifo_event` — that's handled in `Bus::write32` (around line 984). If FIFO moves into `ThreadedSio` but event_flag lives elsewhere, what wires them?

**Proposed solution:**
- `event_flag` must be `[AtomicBool; 2]` shared between threads.
- SEV is a `Release` store; WFE wake check is an `Acquire` load.
- WFE implementation needs to spin-check (or condvar-wait) the flag, not just set `wfe_waiting = true` and return.
- Quantum size affects SEV latency. For a core-1-WFI firmware, this determines minimum interrupt-to-wake time.

## ISSUE 12: Per-core halt/wake and reset interactions
**Severity:** IMPORTANT
**Type:** EDGE CASE

**Problem:** `CortexM33.halt()` is used to hold core 1 during boot. In single-threaded mode, `Emulator::step` checks `if self.cores[1].is_halted()` and skips it (`lib.rs:130-132`). In threaded mode:
- Worker thread 1 is spawned at `run_threaded` entry. If core 1 is halted, what does the thread do? Idle-wait? Exit and respawn on wake? Spin on `halted`?
- Who calls `core_mut(1).wake()`? In single-threaded mode, it's external code or the SIO doorbell path. In threaded mode, that mutation is on the coordinator or worker 0, and needs to cross to worker 1.

Plus the unstated reset question: `run_threaded` takes `&mut self`, so `reset()` can't be called concurrently. Fine. But what if `run_threaded` returns mid-execution (via duration expiry) and the caller immediately calls `reset()`? The workers have been joined by then — fine — but what about the FIFO/spinlock state owned by `Arc<ThreadedSio>`? The reset path clears `sio.reset()`, but the `Arc<ThreadedSio>` may still be referenced by dropped worker closures (until they actually drop). Fine for correctness but confusing.

And the bigger problem: the bootrom explicitly halts core 1 (`core_mut(1).halt()`). The HLD's worker-per-core design implies both workers run from quantum one. That's backwards — worker 1 should idle until core 1 is woken.

**Proposed solution:**
- Worker 1 starts in a "halt-wait" state — blocks on a condvar until `wake()` is called via a cross-thread path.
- Document that `reset()` while `run_threaded()` is running is impossible by borrow check, and make the reset path tear down `Arc<ThreadedSio>` cleanly.
- Consider whether spawning worker 1 lazily (on first wake) is cleaner than always-spawn-then-park.

## ISSUE 13: Fault isolation between cores is unstated
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION

**Problem:** If core 0 takes a HardFault, core 1 keeps running on real silicon. In our emulator, we call `bus.ppb[bus.active_core()].hfsr |= 1 << 30;` and deliver the exception. In threaded mode:
- A panic in worker 0 propagates through `std::thread::spawn` and becomes `thread::Result::Err` at join time. The HLD says "no graceful crash recovery — panic in a worker panics the process."
- What about a HardFault that is NOT a panic — just a firmware bug that the emulator delivers correctly? Worker 0 stays alive, worker 1 is unaffected. Good. But the coordinator needs to know something happened to track stats. How?
- What if core 0 locks up (infinite HardFault-in-HardFault)? Worker 0 burns its quantum doing exception stacking forever. Worker 1 finishes its quantum and waits on the barrier. Deadlock? No — worker 0 also hits the barrier at quantum end. Fine. But this is not articulated.

**Proposed solution:** Add a section "Fault model in threaded mode" — clarify panics vs emulated faults, guarantee that an emulated fault on one core does not stall or corrupt the other, and describe what happens if one worker panics (coordinator aborts both).

## ISSUE 14: Peripheral Mutex contention is probably hotter than stated
**Severity:** IMPORTANT
**Type:** UNSTATED ASSUMPTION

**Problem:** HLD says "peripheral writes are rare (maybe 1-5% of memory accesses)." This is a guess. Reality:
- Bootrom hammers RESETS, CLOCKS, PLL_SYS, QMI, SIO/GPIO in init.
- PIO-heavy applications poll PIO registers frequently from both cores.
- Timer-interrupt-driven firmware touches NVIC/SCB registers on every interrupt entry.
- Firmware polling a UART status register touches APB on every poll.

Additionally, `bus.read32` on APB regions goes through the peripheral bank → any concurrent read from core 0 and core 1 serialises through the Mutex. A simple ping-pong between two cores where both poll a peripheral register becomes one-at-a-time.

Worse: the HLD's Mutex design takes the lock per access. It doesn't mention that the lock is *uncontended* only if the other thread is currently in SRAM. Real firmware interleaves SRAM and peripheral access, so the Mutex will be contended.

**Proposed solution:** Either (a) shard peripherals by block (SIO, PPB, CLOCKS, RESETS, QMI, PIO0-2, etc.) — 10-ish mutexes — or (b) do a proper actor / message-passing design for peripherals. Decide *before* implementing, because retrofitting sharding changes every peripheral-access site.

Better: *measure* the peripheral-access rate in OneROM firmware (Issue 2) before deciding.

## ISSUE 15: Cycle counts can't diverge by "up to 1 quantum" — they can diverge much more
**Severity:** NICE-TO-HAVE
**Type:** UNSTATED ASSUMPTION

**Problem:** HLD says "cycle count may drift by up to 1 quantum per contended access." But workers process instructions of varying lengths within a quantum. With Q=150 cycles and instructions averaging 1-2 cycles, each worker executes 75-150 instructions per quantum — each of which might have stalled under the single-threaded model but doesn't here. Aggregate drift over a multi-second run can be 1000s of cycles.

This matters for: (a) firmware that checks `DWT->CYCCNT` or MTIME for timing, (b) any test harness that compares cycle counts between modes.

**Proposed solution:** Soften the claim. Say "cycle counts diverge; do not rely on them for timing validation in threaded mode." Recommend SIO sync points as the only comparable state between modes.

## ISSUE 16: Testing for race conditions has no plan
**Severity:** IMPORTANT
**Type:** MISSING SCOPE

**Problem:** HLD's validation strategy is three bullets. It runs a small dual-core firmware and asserts final state matches. That tests nothing about races — it only tests the happy path. Every sequential run of a race-free path would pass this test.

What actually tests races:
- **Loom** (concurrency-checking library for Rust) — but Loom requires instrumented atomics and won't work with our `Relaxed` SharedMemory wholesale.
- **Thread Sanitizer** — Rust support is unstable, Windows support is non-existent.
- **Stress testing** — run the same test 10000 times with `cargo-stress` or similar. Catches many races by sheer repetition.
- **Manual audit** — every `*mut`, every `AtomicU8::load(Relaxed)`, every cross-core write, reviewed by a paranoid human.

The HLD mentions "race-safety audit" as a Risk but no concrete plan. "The type system helps" — but `Arc<SharedMemory>` with interior atomics means the type system is permissive by design.

**Proposed solution:**
- Run validation suite under stress (100+ iterations with different seeds, different quantum sizes).
- Build a stress harness that injects thread scheduling jitter (OS-level thread.yield, random sleeps).
- Document a manual audit checklist for every mutable field in `Bus` / `Sio` after the refactor.
- Consider adding an `x86_64-unknown-linux-gnu` CI job with ThreadSanitizer for subset of tests.

## ISSUE 17: The `--threaded` flag is an unnecessary commitment
**Severity:** NICE-TO-HAVE
**Type:** MISSING SCOPE

**Problem:** The HLD says "No env vars, no feature flags. Mode selected via which method the caller invokes." But then adds `--threaded` to `paced_bench`. The dual-run differential test section says "run the same firmware in both modes and compare state." How is that wired — a second flag? A test that internally calls both?

Also, the HLD plans `run_threaded()` as `&mut self`, which means a harness that wants to flip between modes inside one test has to split state then reassemble then re-split. Not great.

**Proposed solution:** Either commit to API-only selection (no flag), OR add the flag and document it's for bench/test harnesses only. Don't do both without clarity.

## ISSUE 18: crossbeam dependency is not justified
**Severity:** NICE-TO-HAVE
**Type:** MISSING SCOPE

**Problem:** HLD adds `crossbeam = "0.8"` to a crate that today has zero concurrency dependencies. Transitive surface: `crossbeam-channel`, `crossbeam-utils`, `crossbeam-epoch`, etc. — many crates, non-trivial compile time.

The HLD alternatively mentions "hand-roll SPSC ring buffer (~100 lines)." For 8-entry FIFOs that wake at most once per quantum, a hand-rolled SPSC is not just possible but probably better. The existing SIO FIFO is `VecDeque<u32>` with 8-entry cap — rewriting as SPSC ring is trivial.

Bigger question: is `ArrayQueue` really lock-free? Yes, but crossbeam's ArrayQueue uses a CAS loop that's not actually faster than a mutex-protected VecDeque at low contention (the SIO FIFO is a single writer / single reader per direction — SPSC, which can be fully lock-free with two atomics).

**Proposed solution:** Default to hand-rolled SPSC ring. Only take the crossbeam dependency if measurement justifies it.

## ISSUE 19: No recovery plan if measurement fails the target
**Severity:** OPEN QUESTION
**Type:** MISSING SCOPE

**Problem:** Phase 5 says "must show `>=`100 MHz actual, 150 MHz stretch." What happens if after all this work we measure 90 MHz? The HLD has no decision gate. Do we keep the threaded code? Revert it? Ship with single-threaded only? Invest more in peripheral sharding?

The HLD treats threading as a deterministic 2x speedup. It isn't — it's an experiment with an uncertain outcome that also costs us cycle accuracy.

**Proposed solution:** Define concrete exit criteria for each phase:
- Phase 3: barrier + minimal spawn. If overhead > 10% on a null workload, stop — we're not going to recover it.
- Phase 4: with Pacer. If the per-core rate drops below single-threaded by more than 5%, stop.
- Phase 5: aggregate rate `>=`100 MHz. If we hit 85 MHz, we've failed — decide whether to invest in sharding or ship single-threaded.

State what "ship single-threaded" means for the current roadmap.

## ISSUE 20: The foundational question — do we need threading at all?
**Severity:** CRITICAL
**Type:** WRONG PREMISE

**Problem:** Pulling back: the HLD was written because dual-core paced mode underperforms on a benchmark of two tight loops. But:

1. Real OneROM firmware may not execute both cores hot.
2. Per-core throughput cannot exceed single-core throughput, so if the real target is 150 MHz per core we still don't hit it.
3. The cost of threading (code complexity, cycle-accuracy loss, race surface, 3-host-core requirement, peripheral Mutex, `ppb` split, RCP cross-writes, SEV cross-thread delivery, etc.) is large.
4. There is an alternative (JIT / cached decode) that explicitly gives `5-10x` by the HLD's own admission.

**The question the HLD doesn't ask:** what if we shipped the current single-threaded emulator, flagged dual-core paced as "aggregate-limited, interleaved execution, not cycle-accurate per-core at `>=`150 MHz," and spent this engineering budget on cached decode / JIT instead?

Threading would still be a reasonable add later if (a) workload study says core 1 is hot enough to benefit and (b) we hit our single-core ceiling even after JIT. Otherwise we're building parallel plumbing to run a feature that rarely matters, while the *actual* bottleneck (per-core interpreter rate) goes unaddressed.

**Proposed solution:** Before starting implementation: spend ~2 days on (a) profiling the current interpreter to confirm where the 143 MHz wall actually is, (b) measuring OneROM firmware's per-core utilisation. If profile says "dispatch overhead 40%, decode 30%, ALU 15%, bus 15%," the answer is computed goto / cached decode — not threading. If OneROM uses core 1 < 30% of the time, the answer is "ship single-threaded and document the aggregate limit" — not threading.

If both measurements justify threading, write a v2 HLD with this data in the problem statement and revisit the design (probably as something leaner than 3 threads + barrier + mutex).

---

## Summary of recommended actions (in priority order)

1. **Don't start implementation yet.** Profile the interpreter and instrument real firmware first (Issues 2, 3, 20).
2. **Reframe the target** as per-core vs aggregate; decide which one matters (Issue 1).
3. **Fully inventory shared state.** Bus has more mutable cross-core state than the HLD acknowledges: `ppb[]`, `rcp_salt[]`, `event_flag[]`, `clk_*`, `pll_*`, `qmi_regs`, `xip_cache_offset`, `peripheral_regs`, `boot_ram`, `gpio_hi_noise_state`, and more (Issues 5, 6, 10).
4. **Define the memory model explicitly** — not just "we use atomics and AcqRel fences" (Issues 7, 8, 11).
5. **Specify minimum-host requirements** and behaviour on hosts that can't meet them (Issue 4).
6. **Define exit criteria** for each phase and what "ship without threading" looks like if metrics don't justify it (Issue 19).
7. If the profile *does* justify threading: write a v2 HLD that addresses Issues 5-14 explicitly before writing code.
