# 2026-04-24 — Dual Serial/Threaded Execution Model: Kickoff

## Goal

Expose both serial and threaded dual-core execution models as a runtime choice on
`Emulator::builder()`, for both RP2350 and RP2040. Workload determines which is faster
(threading has fixed sync overhead that only amortizes above some workload weight),
so the caller — bench, app, harness — picks per use. Compile-time feature flag was the
wrong seam; we need runtime selection so one binary can A/B both models.

## Context entering this work

- **RP2350**: threaded module tree under `crates/mdrp2350/src/threaded/` (14 files,
  ~360 KB) was merged to `main` on 2026-04-19 **behind a disabled `threading` feature
  flag** pending "architectural re-alignment with main's bus design". That
  re-alignment was deferred at merge time — finishing it is part of this work.
- **RP2040**: still pure serial per-instruction interleaving (`crates/mdrp2040/src/lib.rs:324`).
  No threaded module. CLAUDE.md currently says *"do not invest further on mdrp2040"*,
  but the "need both models" realization argues for parity — with the wrinkle that
  RP2040's bank-contention model (`core0_port` flag threaded serially into core 1's
  step) doesn't compose with threaded execution. Resolution deferred to HLD.

## Open questions for HLD

- Selector API shape: `.execution(ExecutionModel::Serial | ExecutionModel::Threaded)`
  builder option vs. two distinct constructor entry points?
- RP2040 threading + bank contention: drop contention in threaded path (documented),
  or atomicize `core0_port`? Lean: drop. Contention cycles are virtual anyway
  (they don't consume host compute) and threading is the future.
- Does the RP2350 `threaded/` tree need to stay a sibling module, or should the
  selector push it into a trait object / enum dispatch inside `Emulator`?
- Test strategy: do we run unit tests through both models (default-run both), or
  gate by env? Leaning default-run both so regressions surface.

## Research findings (2026-04-24 afternoon)

Two research agents returned. Key findings that reshape the HLD:

### RP2350 threading is stale, NOT gated off

- `Cargo.toml` has **no `threading` feature** defined — the 2026-04-19 merge
  journal claim of "merged behind a disabled feature flag" is wrong.
- `pub mod threaded;` in `lib.rs` is **unconditional**. What IS gated is
  `cfg(all(target_arch = "x86_64", target_os = "windows"))` on `emulator.rs` +
  `timings.rs` in `threaded/mod.rs:24,29` — platform-only, not opt-in.
- Threaded worker bodies reference CortexM33 fields (`ppb`, `atomics`,
  `decode_cache`) and generic `step<B: CoreBus>` that no longer exist on main.
  The merge journal's estimated 2–3 hour "Phase 5 Team B rewrite" was never
  executed. That rewrite is now part of Stage 1.
- Only `threading_micro` + `threaded_probe` harness binaries reach the threaded
  path today.
- `tech_debt.md` flags `SpinBarrier::wait` has no watchdog (worker stall →
  silent deadlock).

### RP2040 contention is virtual + step_quantum is stubbed

- `contention_check_active` adds +1 virtual cycle; no host compute cost
  (`crates/mdrp2040/src/bus/mod.rs:650–658`).
- `step_quantum` builder field is unused by `step()` — `tech_debt.md:371–398`
  flags this as pending convergence to a quantum model.
- `paced_bench_rp2040` already has `Contention` + `Stress` workloads ideal for
  A/B validation.
- No existing threading work.

### Decisions recorded in HLD

- Drop contention in threaded RP2040 path (documented).
- Adopt quantum model in threaded RP2040 from the start (kill two birds).
- Do NOT promote `SpinBarrier`/SPSC/atomics to `mdpicoem-common` yet —
  duplicate first, extract after both implementations exist.
- Enum dispatch on `Emulator::inner`, not trait objects.
- `ExecutionModel` enum as builder selector. `build()` returns
  `Result<Emulator, ConfigError>`; Threaded on unsupported platform returns
  `Err(ThreadingUnavailable)`.
- `threading` cargo feature, default ON.
- Fold `SpinBarrier` watchdog into Stage 1 (we're touching `barrier.rs` anyway).

## Arthur's data-backed confirmation (2026-04-24 late)

Arthur: "We do build right now. Serial is faster for OneROM in CPU mode than
threaded."

This is the crossover measurement the devils-advocate demanded. OneROM in CPU mode
is a real workload we care about, and Serial wins on it. The premise (both models
have workload-dependent advantages → need runtime selector) is data-supported.
Architecting dual-support is justified.
