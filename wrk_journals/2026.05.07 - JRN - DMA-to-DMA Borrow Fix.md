# DMA-to-DMA Borrow Fix — Implementation Journal

Date: 2026-05-07
Branch: main
Crate: rp2350-emu (0.2.2 → 0.2.3)

## Summary

Fix `Bus::tick_dma` cross-borrow trap that silently dropped any DMA-issued
bus write whose destination fell inside the DMA register aperture
(`0x5000_0000..0x5000_3FFF`). DMA chains that update one channel's
registers from another — e.g. `CH0.WRITE_ADDR = CH1.READ_ADDR`, the
OneROM SDRR firmware idiom — appeared to fire and decremented
`TRANS_COUNT` but never updated the target register. CH1 read from a
stale firmware-initialised address every transfer.

## Root cause

`Bus::tick_dma` (`crates/rp2350-emu/src/bus/mod.rs:3330`):

```rust
pub fn tick_dma(&mut self) {
    let mut dma = std::mem::take(&mut self.dma);  // (a) self.dma <- Dma::default()
    dma.tick(self);                                 // (b) tick re-enters bus
    dma.route_irqs(&self.atomics);
    self.dma = dma;
}
```

The `mem::take` is there to avoid the cross-borrow that would otherwise
arise when `Dma::tick(&mut self, bus: &mut Bus)` needs both `&mut Dma`
(extracted from Bus) and `&mut Bus` (which still owns a `Dma` field).
Pre-fix, while `dma.tick(self)` ran, `self.dma` held an empty
`Dma::default()` stand-in.

When `Dma::issue_transfer` issued `bus.write32(write_addr, value, 0)`
and `write_addr` landed in the DMA aperture, `Bus::write32` dispatched
through its `DMA_BASE => self.dma.write32(...)` arm
(`crates/rp2350-emu/src/bus/mod.rs:3145`). That call landed on the
empty stand-in. Stand-in was discarded when `tick_dma` returned. The
register update was lost.

Read direction was symmetrically broken: a DMA self-read returned 0
(empty stand-in's register state) instead of the live value.

## Why existing tests missed it

- `dma::tests::two_channels_share_dreq_both_fire` and the quantum-
  invariance suite both write to scratch SRAM, never to the DMA
  aperture.
- `onerom_full_system_rp2350` smoke harness pre-filled SHADOW with
  `(addr & 0xFF) ^ 0x55` and drove a single all-zero address pin
  pattern for the entire post-sync window. With CH1.READ_ADDR frozen
  at firmware-init `SHADOW_BASE + 0`, the verdict checks
  (`last_src_addr ∈ SHADOW range` and byte-pattern equality) passed
  trivially: SHADOW[0] = 0x55 = expected. False confidence — the smoke
  ran end-to-end and asserted "something about bytes" but the bytes
  were independent of CH1.READ_ADDR ever updating.

## Fix shape

Routed inside `Dma::issue_transfer`, not `Bus::write32`. Three reasons
the brief's options A–C all bottomed out unsatisfactorily:

- **Split-borrow at Bus** — `Bus::write32_during_dma_tick(addr, val,
  &mut Dma)` and friends require duplicating bus dispatch (or threading
  an `Option<&mut Dma>` through every callsite).
- **`RefCell<Dma>`** — panics. The outer `borrow_mut` in `tick_dma`
  holds for the entire `dma.tick(bus)` call; any inner DMA-aperture
  write would attempt a second `borrow_mut` and trip the runtime check.
  Same logical problem as the original cross-borrow, just relocated.
- **Thread-local override pointer** — unsound. `&mut Dma` is already
  live on the stack inside `Dma::tick`; routing back through a `*mut
  Dma` aliases the same mutable reference, undefined behaviour under
  Rust's aliasing rules even though it would "work" in practice.

The DMA-aperture detection sits naturally inside `Dma::issue_transfer`
because that's where `&mut self` (the live `Dma`) is in scope. Two
helpers — `dma_routed_read` and `dma_routed_write` — branch on
`is_dma_aperture(addr)` and dispatch through `self` for self-accesses,
falling back to `bus.read*` / `bus.write*` for everything else. The
aperture branch still calls `bus.invalidate_reservation_at` and
`bus.emit_mmio_trace` so LR/SC reservation invalidation and MMIO trace
consumers see the same wire-format event the silicon path would have
produced.

DMA-aperture footprint: `(addr - DMA_BASE) < 0x4000` (one 4 KB page +
three APB-alias mirrors). All DMA registers fit in the bottom 0xC00
bytes, so the bound is loose-but-correct.

Sub-word DMA-to-DMA writes are `debug_assert!`d as size=4 only. No V1
corpus case exercises narrow self-writes; the registers are 32-bit per
datasheet. If a future scenario needs it, the assertion will trip in
dev builds and the path can be expanded with a peripheral-style RMW.

## Regression test

`dma::tests::dma_to_dma_write_during_tick_lands_on_live_dma` in
`crates/rp2350-emu/src/dma.rs`. Deposits a distinguishable address
through PIO0 RXF0 → CH0 → CH1.READ_ADDR; pre-positions a marker word
at the deposited address and a different placeholder word at CH1's
firmware-initial read address; runs one `tick_dma`; asserts the
scratch cell holds the marker (proving CH1 read from CH0's deposit),
not the placeholder.

Verified the test FAILS on master (pre-fix code reads `0xBAAD_BAAD`
from the placeholder, with the diagnostic naming the bug) and PASSES
with the fix.

## Smoke harness tightening

`crates/picoem-harness/src/bin/onerom_full_system_rp2350.rs` —
extends the post-sync window from 40 cycles to 200, drives an
address-pin sweep across 5 distinct A0..A12 words (constrained to
A11=A12=1 to honour the CS2/CS3-deasserted serving window per the
fixture pin map), holds each word for 40 master-clock cycles, captures
the active address-pin word per CH1 push edge, and adds a 4th verdict
criterion: distinct `last_src_addr` count must be > 1 across the
window. Diagnostic on failure names the bug ("stuck at 0x{addr:08X}",
references `Bus::tick_dma` mem::take borrow trap, points at the new
regression test).

Verified on the buggy code path (temporarily reverted the fix in
`Dma::issue_transfer`, re-ran the harness): SMOKE TEST FAIL with
"only ever took 1 distinct value(s) (stuck at 0x20000000)". With the
fix restored: SMOKE TEST PASS — "17 CH1 push edges across 2 distinct
src addresses". Both directions confirmed.

The number of distinct addresses captured (2 of 5 driven) is bounded
by the firmware reaching its post-init WFI loop at cycle ~9300,
which terminates the harness's observation window before the full
sweep schedule completes. Two distinct values is sufficient to satisfy
the > 1 criterion; if future runs need more coverage, extending the
WFI break gate during the post-sync window would let all 5 sweep
positions land.

## Out-of-scope notes

**Peer bug in rp2040-emu.** `crates/rp2040-emu/src/bus/mod.rs:1901-1906`
has the identical `mem::take` pattern in its own `tick_dma`. Same
shape, same hazard. Not fixing in this change per the brief's "don't
go hunting" directive — but if/when the rp2040 PicoGUS chain or any
rp2040 DMA-to-DMA idiom regresses, this is the first place to look.
The `Dma::issue_transfer` fix translates 1:1 across crates.

**Downstream impact.** mddosem's `--one-rom` mode currently routes
every BIOS byte through a 660-line workaround shim that exists only
because of this bug. Per the brief, once `rp2350-emu` 0.2.3 publishes,
that shim becomes deletable per `wrk_docs/2026.05.07 - HLD - OneROM
drop GlueDma adopt rp2350-emu 0.2.2.md` (in mddosem) and unlocks a
100–200× per-byte speedup.
