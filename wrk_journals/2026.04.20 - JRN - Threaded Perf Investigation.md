# Threaded Perf Investigation — 2026-04-20

## Problem

Threaded `paced_bench_rp2350 --workload basic --step-quantum 4096 --unpaced`
executes at **~25 MHz per core**; serial equivalent hits **~154 MHz**. A 6×
per-core slowdown on a workload that's just a 2-instruction tight loop.

## Prior state (committed as 718f2ad)

Three architectural fixes applied — all pass 134 threaded tests, none moved
the throughput needle:

1. **Hybrid spin+park barrier** (`threaded::barrier::SpinBarrier`,
   `SPIN_BUDGET = 128` ≈ 2.5 μs). Idle workers now `Condvar::wait` after a
   short spin instead of burning the whole quantum on `pause` loops.
2. **Worker body hoist** (`threaded::emulator::core_worker_body`): `is_halted`
   sampled once per quantum; `is_wfe_waiting` check moved to post-step.
3. **`CortexM33::step_no_atomics`** fast path: skips the 3 per-step atomic
   loads (`is_wfe_waiting`, `is_halted`, `take_irq_pending`) on `CoreAtomics`.
   Worker already handled these at quantum boundary.

## What I eliminated this session

### Host-core contention — NOT the issue

| Thread mask | basic sq=4096 |
|---|---|
| `[0,1,2,3]` (default) | 25 MHz |
| `[4,5,6,7]` (all P-cores, away from bench main at core 2) | 25 MHz |
| **No pinning at all** (`pin_to_host_core` stubbed to no-op) | **25 MHz** |

Host is Intel Core Ultra 9 285HX, 24 cores / 24 threads. Bench main pins
to core 2. Workers pinned or not — throughput is identical. The cap is
**structural to the threaded emulator**, not a scheduling or contention
artefact.

### Barrier spin — NOT the bottleneck for core 0's rate

Samply pre-fix showed 60% of *aggregate* worker CPU time in
`pause; jmp` barrier spin. Fix #1 replaced that with `Condvar::wait`.
Post-fix samply shows worker 5 (productive) with healthy distribution —
top 5 hot addresses cover only 18% of its samples — and the 25 MHz cap
is unchanged. So the three idle workers' spin was burning CPU without
slowing core 0.

### Per-step cross-thread atomics — NOT the bottleneck

Fix #3 (`step_no_atomics`) eliminates 3 atomic loads per instruction.
Result: unchanged 25 MHz. The coord-written `irq_pending` line, which
I hypothesised was bouncing into core 0's cache every step, is not the
limiter.

## What I know about the hot path

From samply's un-symbolicated profile (addresses only), productive
worker (thread 5) hot spots cluster in 0x2bxxx–0x2dxxx, a single
contiguous code region. Two identifiable patterns:

- **Decode cache hit path** at 0x2bd1a–0x2bd37:
  ```
  movl  %r15d, %ecx      ; PC
  shrl  %ecx              ; PC >> 1
  andl  $0x3fff, %ecx     ; 14-bit index (16384 entries)
  movq  0x10(%rbx), %rax  ; decode_cache base
  leaq  (%rcx,%rcx,2), %rcx ; stride × 3 (24 bytes/entry)
  cmpl  %r15d, (%rax,%rcx,4) ; tag check
  jne   <miss>
  ```
  Tag-hit + opcode load, standard fast path.

- **execute_thumb16 prologue** at 0x2d150–0x2d186: pushes 7 callee-saved
  regs + `sub $0x20, %rsp`, then `movzwl dx; shrl 11; cmpw 0x1c;
  jmpq *` — a jump-table dispatch on the top 5 bits of the opcode.

Neither of these should be meaningfully slower under WorkerBus vs Bus —
they're all register work after the cache hit.

## Current hypothesis

The decode cache WORKS (cache hit assembly is there). But something in
the executor's critical path is a constant-factor slower under
`step_no_atomics + WorkerBus` than under `step + Bus`. Candidates I
haven't eliminated:

1. **Decode cache MISS path** happening more often than I expect. If
   even 10% of fetches miss and go through `WorkerBus::read16` (which
   does `Arc` indirection + `AtomicU32::load`), that's 10× cost per miss
   vs serial's non-atomic fetch. A 10% miss rate at 100ns/miss would add
   ~10ns/instruction — accounting for ~half the gap.
2. **Per-step field writes on WorkerBus state** — `active_pc`,
   `last_fetch_addr`, `burst_mode`, `extra_wait_states` — that the serial
   `Bus` also has but which might compile differently due to containing
   `Arc<SharedState>` neighbour.
3. **`pending_cache_invalidations.is_empty()` check** in the worker loop.
   This is a `Vec::is_empty()` on a `Vec` embedded in `WorkerBus`. The
   serial path does something different for cache invalidation. Should
   check whether this branch is taken hot.

## BREAKTHROUGH — the "25 MHz cap" is paced_bench overhead, NOT the executor

Wrote `threaded_probe` (new bin at
`crates/mdpicoem-harness/src/bin/threaded_probe.rs`) that strips
everything not the executor: no Pacer, no monitor thread, no stats
tracking, no workload variety, no pacing loop. Just a fresh
`Emulator` with `basic` workload, promoted to `ThreadedEmulator`, and
`run_quanta` called with enough n to do 150M cycles.

Results (3 runs, MHz per-core via `core_cycles` snapshot delta):

| Runtime | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| serial | 231 | 234 | 233 |
| threaded sq=64 | 97 | 94 | 73 |
| threaded sq=256 | 216 | 249 | 217 |
| threaded sq=1024 | 307 | 314 | 291 |
| threaded sq=4096 | 251 | 246 | 253 |
| threaded sq=16384 | 287 | 286 | 295 |

**Threaded at `sq=1024` hits ~300 MHz — *beating* serial (232).**
`sq=64` is barrier-bound (3× slower than serial), but from `sq=256`
onwards threaded is competitive or faster.

Compare to paced_bench_rp2350 on the same workload:
- serial: 154 MHz   (probe: 232 — paced_bench costs ~34% of serial throughput)
- threaded sq=64: 25 MHz   (probe: ~90 — paced_bench costs ~72%)
- threaded sq=4096: 25 MHz   (probe: 250 — paced_bench costs ~90%)

The threaded path is MUCH more sensitive to paced_bench's overhead
than serial. Candidates in `paced_bench_rp2350` to investigate:

1. `Pacer` setup + monitor thread — runs continuously, reads atomics
2. Main thread pinning to core 2 with `HIGH_PRIORITY_CLASS /
   TIME_CRITICAL` — conflicts with default worker mask `[0,1,2,3]`
   placing PIO worker on core 2
3. Stats/monitor atomic updates per quantum
4. Per-loop-iter `start.elapsed()` TSC reads in the outer while

This changes the whole investigation. The executor is fine. The
bench wrapper is the problem.

## ROOT CAUSE FOUND — `target` not seeded from `core.cycles()`

Added per-`runtime.run` chunk timing inside `paced_bench_rp2350` and
got the smoking gun:

```
runtime.run(150000000) took 541.8 ms (first call)
runtime.run(150000000) took 32.4 ms (subsequent)
runtime.run(150000000) took 26.2 ms (subsequent)
... ~150 more at 25-38 ms each ...
```

Call 1 does real work (540 ms for 150M cycles ≈ 275 MHz). Calls
2..N finish in ~30 ms each — way too fast to be doing real work.

Checked `threaded::emulator::core_worker_body` and found:

```rust
let mut target: u64 = 0;
for _ in 0..n {
    target = target.wrapping_add(step_q as u64);
    ...
    while ... && core.cycles() < target { core.step(...) }
    ...
    barrier.wait();
}
```

`target` is a LOCAL, zeroed at the top of each
`core_worker_body` invocation. But `core.cycles()` is PERSISTENT on
the `CortexM33` struct across `run_quanta` calls. After call 1,
`core.cycles() = 150_003_713`. Call 2 enters the loop with
`target = 0`; first iteration sets `target = 4096`; the guard
`core.cycles() < target` is `150_003_713 < 4_096` → false; the
inner `while` skips all instructions. Same for all 36623 quanta in
that call — workers just cycle the barrier with no work.

**Fix**: seed `target` from `core.cycles()` at worker entry:

```rust
let mut target: u64 = core.cycles();
```

One-line change. All 134 threaded tests still pass.

## Results after the fix

| workload | sq=64 | sq=256 | sq=1024 | sq=4096 |
|---|---|---|---|---|
| **basic** (serial 164) | 25→75 | 25→250 | 25→275 | 25→250 |
| **contention** (s 93) | 25→100 | 25→200 | 25→275 | 25→275 |
| **stress** (s 81) | 19→38 | 19→64 | 25→50 | 21→64 |
| **peripheral** (s 130) | 19→38 | 19→56 | 21→50 | 21→64 |
| **fpu-heavy** (s 256) | 25→75 | 25→375 | 25→425 | **25→450** |

Threaded fpu-heavy at sq=4096 = **450 MHz** vs serial 256 MHz.
Threaded basic at sq=1024 = **275 MHz** vs serial 164 MHz.
Threading now wins on every CPU-bound workload at sq≥256.

`stress` and `peripheral` (dual-core + PIO) still underperform
serial because both cores + PIO contend — that's expected for a
genuinely parallel workload hitting synchronization, not a bug.

## Hypothesis post-mortem

Everything I tried earlier this session — hybrid barrier, worker
hoist of atomics, `step_no_atomics` — was guided by a samply
profile that showed 60% of aggregate worker CPU time in barrier
spin. That was a real observation, but a *consequence* of the
`target` bug, not its cause: with calls 2..N doing no work, three
idle workers and one idle-cycles productive worker all piled into
the barrier with nothing between, so 60% of aggregate CPU went
there. The barrier was spinning because the executor wasn't
running. My fixes reduced the symptom (idle workers now sleep) but
didn't touch the cause.

The committed speculative changes (718f2ad) are still
architecturally sound and pass all tests — idle cores sleeping is
legitimately better than spinning, and `step_no_atomics` still
shaves ~3 atomic loads per instruction. They just weren't the
fix for this regression.
