- `MRS Rd, PRIMASK` (sysm=16): QEMU R*=0x1 vs EMU=0

### 2026-05-03T03:22 — agent report: known harness gap, NOT a regression

Investigation agent returned in ~3 min with a clean diagnosis. **Root
cause: harness bug, sub-class missing-port-of-fix.** The 3040 failures
are *spurious* — not emulator divergences, but QEMU's persistent CPU
state leaking across tests because the M33 oracle has no PRIMASK/MSP
reset primer.

**Why "M0PLUS" appears in M33 log:** the class is generated by
`thumb32_gen::generate_fuzz_m0plus_t32` and folded into the shared
`base_alu` bucket at `crates/picoem-harness/src/lib.rs:4999`. Both
oracles consume the same bucket — intentional cross-coverage of the
M0+ Thumb-32 subset on M33. Class name is just where the cases were
authored.

**Where sync happens (or doesn't):**
- M0+ oracle steps a primer `MSR PRIMASK, R0` (R0=0) before every test
  at `crates/picoem-harness/src/bin/qemu_diff_m0plus.rs:386-401`.
- M33 oracle has *no equivalent*. Per-test setup at
  `crates/picoem-harness/src/bin/qemu_diff_m33.rs:457-464` writes only
  R0–R12, SP, LR, PC, XPSR. PRIMASK and the banked MSP/PSP carry over
  from the previous test's QEMU state. Our emulator builds a fresh
  `CortexM33::new()` per test, so the divergence is structural.

**Regression status:** Pre-existing gap. Commit `d29dc41` (2026-05-01)
added the primer to `qemu_diff_m0plus.rs` only; the same fix never got
ported to the M33 oracle. The 2026-05-01 campaign journal already
classified `M0PLUS_T32_MRS` as a *known deterministic baseline* and
flagged not to count it as a novel divergence. So this overnight run
re-discovered an already-tagged issue.

**Fix direction (deferred to daytime):** port the primer pattern from
`qemu_diff_m0plus.rs` to `qemu_diff_m33.rs`, but the M33 needs more
than just PRIMASK — also FAULTMASK, BASEPRI, CONTROL, banked MSP/PSP.
That's six MSR encodings and CONTROL changes affect privilege /
SP-bank, with risk of breaking other M33 classes if botched. **Not
appropriate to dispatch unsupervised at 03:30 with Arthur asleep.**
Recording it here and leaving the fix to a daytime session.

**Decision:** allow the campaign to continue producing the same 3040
known-spurious failures on each M33 batch, plus useful signal on every
other class. Adjusted M33 failure tally going forward will subtract
the M0PLUS_T32_MRS contribution.

|---|---|---|---|

| Daytime confirmation (post-primer binary) | 173K `--fuzz 5000 --classes=base` | 248 | 0.143% |

Exactly matches the rate the `377ed6e` commit message predicted
("drops … to 0.143%"). The 248 residual is the **separate**
`MRS Rd, MSP/PSP` gap the commit message itself flags. Two
underlying causes compound here:

1. **EMU side:** `set_reg(13, EMU_TEST_STACK)` only updates
   `regs.r[13]` — it does not sync the banked `regs.msp`. The MRS
   instruction reads `regs.msp` directly
   (`crates/rp2350-emu/src/core/execute_thumb32.rs:1168`). After
   harness setup, `regs.msp` is still 0 from `CortexM33::new()`,
   so `MRS Rd, MSP` returns 0. The `regs.msp` cache only gets
   sync'd at exception entry/exit via `sync_sp_to_banked()` —
   architecturally fine for normal program execution (which never
   observes the staleness), but the fuzzer issues MRS in
   contexts the architecture doesn't normally reach.
2. **Harness side:** Even if (1) were fixed, `MRS Rd, MSP` would
   still diverge because EMU and QEMU use different stack
   addresses (`EMU_TEST_STACK = 0x2004_0000` vs
   `QEMU_TEST_STACK = 0x0004_0000`) and the comparator does
   absolute compare for R0-R12 (no addr_reg translation for
   sysm=8/9). On the M0+ oracle this is invisible because both
   sides share `0x2000_1000` — that's why the M0+ MRS class is
   clean.

**Fix direction (deferred):** smallest correct fix is two-part —
(a) `MRS` reads from `r[13]` when the requested bank is active
(architecturally correct: when SPSEL=0, MSP *is* SP; trivially
correct, single match-arm), and (b) test-case generator marks Rd
as an address register when sysm ∈ {8, 9} so the comparator
translates. Estimated ~30 min of work + a 100K-case soak.
**Recording as a new follow-up (item 4 below) rather than
attempting tonight** — it's the actual remaining blocker on M33
ISA cleanliness, and the journal's "extend the primer" framing
was insufficient.

### Follow-up 2 — probe-wedge investigation: complete

Investigation agent found the root cause is upstream **probe-rs
issue [#1849](https://github.com/probe-rs/probe-rs/issues/1849)**,
open in our pinned 0.31.0. Wedge happens deterministically when a
prior process exits without calling `DAP_Disconnect` (panic, kill
-9, or our 04-25 cascade). `nusb`'s `claim_interface` succeeds
(kernel-level — that's why `probe-rs list` and PnP look healthy),
but the first OUT/IN exchange in `find_packet_size`
(`third_party/probe-rs-0.31.0-mdrp-patched/src/probe/cmsisdap/commands/mod.rs:307-335`)
times out 16× because the WinUSB bulk endpoint is left in a stuck
or HALT state. Probe firmware is fine; it's the host-side endpoint
state that needs reset.

Three remediation options ranked by feasibility:

1. **`pnputil /restart-device` from a one-shot elevated PowerShell**
   (lowest risk, requires UAC click once per night, ~1h to wire
   into `probe-watch.sh`). Likely high probability of working
   because re-enumeration is effectively a soft replug.
2. **Vendor a `clear_halt(out_ep)` + `clear_halt(in_ep)` patch**
   into `third_party/probe-rs-0.31.0-mdrp-patched/`'s
   `CmsisDapDevice::V2` open path, right before the existing
   `drain()` (~20 lines, no admin needed, mirrors the existing
   `select_ap_and_ap_bank` patch we already maintain). Could
   upstream as the fix for #1849 if it works.
3. **`nusb::Device::reset()` shim** wrapper at startup of every
   `probe_diff_*` / `test_silicon` invocation (issues a USB port
   reset via the Windows kernel, no admin). Higher complexity
   risk.

**Recommended first action next time the probes wedge:** try
option (1) with the one-liner

```powershell
Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -match 'VID_2E8A&PID_000C' } |
  ForEach-Object { pnputil /restart-device $_.InstanceId }
```

from an elevated PowerShell. If it recovers them, wire into the
watcher. If it doesn't, that disproves the WinUSB-stall hypothesis
and points at probe firmware (which truly needs replug) — useful
diagnostic either way. Existing `RUNBOOK.md` wedge section (lines
267-353) stays as the fall-back recipe.
