# JRN — OneROM PIO Serial Speed-Grade Oracle

**Date**: 2026-04-24
**Context**: Yesterday we shipped `onerom_cpu_speed_grade_serial_rp2350` —
a cycle-count ladder oracle for CPU mode. Today Arthur asked for the
PIO-mode equivalent after reviewing the comparative data.
**Supervisor**: Claude Opus 4.7 (1M)
**Mode**: Agent-team supervision with structural devil's advocate role.

## The ask

Build the serial PIO cycle-count oracle — mirror of
`onerom_cpu_speed_grade_serial_rp2350` against the PIO serve path.

## The bigger question (for DA)

The CPU stress oracle reports `mean=80 ns` emulated per byte; PIO stress
reports `mean=226 ns`. This is **counterintuitive** — on real silicon,
PIO mode is the whole point of hardware-paced serving and should be
*faster* than CPU mode, not 3× slower. Either:

- (a) The emulator's PIO cycle model is pessimistic / miscounted.
- (b) The PIO firmware path genuinely takes more cycles than CPU
      (unlikely from first principles — PIO state machines are
      single-instruction-per-cycle).
- (c) Our "mean=226 ns" includes per-case machinery the CPU number
      doesn't (unlikely, same `compute_histogram` code).

Building a PIO serial cycle-count oracle surfaces the distribution but
**won't answer why it's 3× CPU**. That needs either silicon data
(`onerom_pio_diff_rp2350` vs hardware) or model inspection.

**Plan**: DA challenges the premise before we code. If DA surfaces
something structural, we adjust. Otherwise proceed with the mirror.

### Stage A1–A2 — silicon infrastructure survey + DA well-posedness check (done)

**Infrastructure survey** — Explore agent found:
- `silicon_cycle_oracle_rp2350` measures CPU instruction sequences via K-delta mailbox protocol. **Not applicable** to pin-event latency (no event-wait logic).
- `silicon_periph_diff_rp2350` does end-state diff after fixed CYCCNT window. Could be abused with binary-search across window sizes, but isn't latency-to-event shaped.
- `onerom_pio_diff_rp2350` diffs against `epio` trace (Wokwi emulator), NOT silicon. Probe-rs lacks cycle-by-cycle GPIO readback.
- `onerom_serving_oracle_rp2350` (Stage G) measures serve latency in emulator — could be extended to silicon with ~150 lines probe-rs glue.
- **Analytical cycle counting from PIO assembly + datasheet DMA is zero-cost**: PIO = 1 cycle/instr by architectural guarantee (RP2350 datasheet); DMA = 4 read + 4 write sysclks (datasheet-fixed, `onerom_glue_dma.rs:10-32`).

**DA round 2** — substantive pushback against Plan C:
- **The "3× CPU/PIO anomaly" is architecturally explainable, not a bug**:
  CPU serve = 5-instr ARM loop → floor ~7 cy (matches `CPU_ENVELOPE_CYCLES = 7..=60`).
  PIO serve = 8 cy DMA pipeline + ~7 cy PIO SM program → floor ~15 cy (matches `ENVELOPE_CYCLES = 15..=45`).
  DMA framing cost dominates for single-byte serves; PIO wins only on bulk/streamed transfers. PIO > CPU for single-byte is expected behaviour.
- **Silicon measurement has a time-anchor trap**: on a real 6502 jig the 6502 crystal is async to RP2354 sysclk, injecting ±1 sysclk domain-crossing jitter. Would need all-sysclk-domain test rig (drive stim from RP2354 itself) to get sysclk-to-sysclk measurement.
- **Analytical count IS silicon-grade**: PIO 1 cy/instr + DMA 4+4 are architectural/datasheet guarantees, not modelling choices.
- **Brave testable prediction**: silicon PIO p50 = 140–170 ns (21–25 cy), min ≈ 100 ns (15 cy), CPU p50 = 50–65 ns (8–10 cy). If silicon shows PIO p50 < CPU p50, DA is wrong.

### Stage A3 — analytical cycle count (done)

**Key finding**: authoritative source is Piers Finlayson's own test at
`crates/epio-sys/third_party/epio/test/onerom.c:44` — `assert_int_equal(cycles, 12)`
for byte-in-TX-FIFO. PIO = 1 cy/instr (architectural); DMA = 4+4 cy
(datasheet). Analytical floor ≈ 13 cy pin-to-pin; steady-state p50 ≈ 29-35 cy;
max ≈ 45 cy. **Matches emulator `ENVELOPE_CYCLES = 15..=45` and stress
distribution (min=126/p50=233 ns → 19/35 cy buckets).** Model is architecturally
plausible.

### Stage A3-DA — audit of analytical count (done)

DA audited and sustained 4 of 7 challenges:
- **Topology gap**: Piers' test uses PIO0 single-block; real firmware uses
  PIO1+PIO2 cross-block (`PIO1.CTRL=0x01`, `PIO2.CTRL=0x03`). Unknown
  cross-block DMA cost.
- **Reference point**: epio measures "byte in TXFIFO"; stress oracle measures
  "pin stable for 3 consecutive cycles". ~5 cy offset — analytical floor (13)
  and stress floor (19) are NOT the same measurement.
- **GPIO synchroniser**: RP2350 datasheet §9.5 — 2-FF input sync adds +2 cy
  uniformly on silicon. Not in emulator, not in epio.
- **"SM1 always keeps pipeline full"** was overstated. SM1 produces 1 RX word
  per 8 cy; CH0 drains 1 word per 8 cy. Exactly matched. Tri-modal
  distribution is phase-lock artefact.

Overruled: `OUT PINS, 8` is 1 cycle (parallel pin drive) — verified.

**DA verdict**: analytical not grounded enough for *silicon-anchored* ladder
rungs. DA's silicon recommendation (`silicon_cycle_oracle_rp2350`) doesn't
fit — that oracle measures CPU instruction sequences, not PIO pin events.

### Stage A4 — goal reframe (2026-04-24)

**Arthur reframed**: the goal is not "silicon parity validation." The goal
is "what EPROM speed-grade does the emulator's PIO mode self-report as?"
(like -90, -120, -150 ns conventions). This is an *emulator self-characterisation*,

## Final outcome

**The emulator's OneROM PIO mode is a -250 ns part on the 1541 $E000 fixture.**

| Rung (ns) | Errors | Verdict |
|---|---|---|
| 300 | 0 | PASS |
| 250 | 0 | PASS |
| 200 | 2046 | FAIL |

Cycle distribution (3 discrete buckets): 19 cy (1 case), 30 cy (1 case), 35 cy (2046 cases). The two sub-envelope outliers (19, 30 cy) are likely warm-up artefacts — cold PIO1 SM1 pipeline before steady-state back-pressure develops. **Not representative serving capability; do not over-interpret.**

Comparison to CPU mode (from 2026-04-23 work):
- CPU serial cycle oracle: top rung 50 cy PASS, equivalent to ~-333 ns in same convention. Mean 12 cy (~80 ns). Distribution has a long tail from zero-byte-trust fallback (max at 40 cy ≈ 266 ns).
- PIO serial ns oracle: grade -250 ns, mean 226 ns (34 cy), tight tri-modal distribution.

**Ordering**: single-byte PIO (226 ns mean) is ~3× slower than single-byte CPU (80 ns mean) in this emulator — architecturally expected for DMA-framed single-byte serves (DA Stage 1 finding validated by Stage A3 analytical count).

## Known caveats (silicon comparison, documented for future-us)

Today's work measures the emulator's self-reported PIO speed-grade. It does **NOT** validate against real RP2354 silicon. Three gaps stand between this -250 grade and a silicon claim:

1. **Topology**: Piers' `onerom.c` reference uses PIO0 single-block; real firmware uses PIO1+PIO2 cross-block. Cross-block DMA adds unknown (probably small) additional cycles.
2. **Measurement reference point**: epio measures "byte in TX FIFO"; stress oracle measures "pin stable for 3 consecutive cycles". ~5 cy offset between those interpretations.
3. **GPIO input synchroniser**: RP2350 datasheet §9.5 — 2-FF sync chain adds ~2 cy uniformly. Neither emulator nor epio model this.

Plausible silicon grade: ~-300 ns (emulator -250 + ~7 cy / ~47 ns uncertainty). To convert this to an actual claim requires silicon measurement via external logic analyser or firmware instrumentation — out of scope for today.
