# OneROM Shadow Source Investigation — Journal

Date: 2026-04-15
Parent: `wrk_journals/2026.04.15 - JRN - OneROM Serving Oracle (Stage G).md`
  (Stage G.2 "Shadow source investigation" blocker subsection).
Scope: identify where the OneROM ROM payload lives at sync time and
  fix `ServingOracle::new_at_sync` so the shadow holds real ground
  truth, not an empty tripwire value.

## Root cause

Two compounding errors in HLD §3.1:

1. **Wrong shadow-anchor address.** HLD §3.1 claimed OneROM memcpys
   the ROM image to SRAM base `0x20000000` before the sync point.
   The RP2350 build does place `_ram_rom_image_start` there (confirmed
   via `sdrr/link/common.ld` + `sdrr_runtime_info.rom_table` read from
   SRAM at `0x20080000` — value `0x20000000`, size `0x10000`). But:

2. **Preload DMA never lands on our emulator.** The RP2350 firmware
   issues a DMA-driven `memcpy(rom_table, set->data, 65536)` via
   `preload_rom_image`. Our emulator's DMA model does not execute that
   channel's program — stepping even 1 000 000 cycles past sync leaves
   `SRAM[0x20000000..+0x10000]` entirely zero. The snapshot has no
   truth to read.

A third, smaller mistake: **shadow width was 8 KB** but PIO1 resolves
into the full 64 KB pre-processed address-permutation table (observed
`0x2000_0000..0x2000_B000` across the 15-case sweep). An 8 KB shadow
tripped `ResolvedAddrOutOfRange` on 14/15 cases even with a correct
anchor.

## Evidence

Added a temporary diagnostic block to
`onerom_serving_oracle_rp2350.rs` (reverted before the final commit):

- `runtime_info @ 0x20080000`: `magic="sdrr" size=60 image_sel=0x07
  rom_set_index=0x01 rom_table=0x20000000 rom_table_size=65536`.
- All 8 KB SRAM regions from `0x20000000` through `0x20070000`
  report 1 unique byte (all zeros) at sync and 1M cycles past sync.
- Only `0x20080000..+0x2000` (the runtime_info slab) has variation
  (38 unique bytes) — populated by CPU writes, not the broken DMA.
- Fixture flash at `0x50000..+0x10000` (set[1] data, picked by
  `rom_sel = 7 % 6 = 1`) has 64 unique bytes with the pattern
  `0x00 0x00 0x00 0x00 0x20 0x20 0x20 0x20 0x10 0x10 0x10 0x10 ...`.

Source references used: upstream `piersfinlayson/one-rom` repo —
`sdrr/include/config_base.h` for the struct layouts (`sdrr_info_t`,
`onerom_metadata_header_t`, `sdrr_rom_set_t`, `sdrr_runtime_info_t`)
and `sdrr/link/common.ld` for the memory map.

## Fix

`ServingOracle::new_at_sync` now **lifts the shadow from the loaded
flash byte array** via SDRR struct parsing, instead of reading SRAM.
This reads the exact bytes `preload_rom_image` *would* copy if the
DMA ran — sidestepping the emulator-side DMA defect entirely.

Implementation path (all in
`crates/mdpicoem-harness/src/onerom_serving_oracle.rs`):

- Added `pub(crate) fn lift_shadow_from_flash(flash: &[u8],
  rom_set_index: u8) -> Option<Box<[u8; SHADOW_SIZE]>>` — pure
  parser, unit-testable without an emulator.
- Signature of `new_at_sync` changed from `(bus)` to `(bus, flash)`;
  reads `rom_set_index` from `SRAM[0x80006]` and calls the parser.
  Falls back to a zero-filled shadow on parse failure — the binary
  tripwire catches that.
- `SHADOW_SIZE` widened from `0x2000` (8 KB) to `0x1_0000` (64 KB) to
  cover the full `rom_table` span PIO1 resolves into. `SHADOW_BASE`
  stays at `0x2000_0000`.
- Binary's shadow-integrity tripwire now samples
  `oracle.shadow()` (new accessor) instead of SRAM.

Tests:

- Replaced the SRAM-capture test (`rom_shadow_captures_sram_at_build_time`)
  with three flash-parser tests: happy path, out-of-range index
  rejection, truncated-flash rejection.
- Added `walking_1s_distinctness_from_real_fixture` — loads the
  real `test-sdrr-0.bin` fixture, lifts the shadow, asserts
  `>= 5` unique values among the walking-1 offsets
  `[0x001, 0x002, 0x004, ..., 0x400]`. Live fixture has exactly
  6 unique walking-1 bytes.

All 13 `onerom_serving_oracle` unit tests green.

## Follow-ups for the Stage G team

1. **PIO1 `0xB0002000` resolves** (cases 10, 11) — two addresses
   consistently resolve to `0xB0002000`, well outside the SRAM
   rom_table. Likely a shift-direction or byte-swap artifact in
   PIO1's pin-to-word assembly. This is the PIO differential
   oracle's domain, not the serving oracle's — file separately.

2. **LatencyOOE dominance** — the emulator's latencies (3-10
   cycles) run below `piorom.c`'s 11-14 envelope. Expected: the
   glue DMA's 4+4 pipeline is faster than silicon's DMA+PIO chain.
   HLD §5.4 already notes this as an "emulator-bounded" caveat.
   Not a bug in this patch; will surface in G.3's dedicated
   latency report.

3. **Preload DMA gap in the emulator** — the broader emulator
   issue that motivated this workaround: the RP2350 DMA program
   used by `preload_rom_image` is not executed by
   `mdrp2350::bus::Dma`. Worth a separate investigation once the
   Stage G oracles stop being blocked on it. For now, lifting
   from flash is the right call — it's the canonical ground truth
   regardless of DMA behaviour.

4. **False-green guard stays load-bearing** — the binary's
   shadow-integrity tripwire + the walking-1s distinctness unit
   test both remain as the first-line defence against an empty
   shadow. A future fixture switch (e.g. selecting set 0 =
   `zero8192.rom`) would immediately fail both guards.
