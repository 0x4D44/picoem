### 2026-04-22 A.2a results

**Procedure executed:** built `probe_verify_rp2350` in **debug profile** (release strips DEBUG/TRACE at compile time via the workspace-wide `release_max_level_info` feature on `tracing`; release output contained only INFO/WARN lines and was insufficient for H1/H2 discrimination). Debug build copied to `%TEMP%\probe_verify_rp2350_dbg.exe` and run 3× in PowerShell with `RUST_LOG=probe_rs=trace`. All three runs exited 1 (as expected — the fail path is what we're measuring). Raw logs: `wrk_debug/trace-probe-verify-rp2350.run{1,2,3}.{stdout,stderr}.log` (~66 KB stderr each). Extracted key lines: `wrk_debug/trace-probe-verify-rp2350.key-lines.log`.

**Hypothesis ruling: H1 confirmed (permanent hybrid DP). Confidence: HIGH.**

The RP2354 DP reports DPv2, not DPv3, and does so consistently. Across all three runs the DPIDR read returns the identical value `0x10212927`, which the INFO line decodes as `Debug Port version: DPv2 MinDP: Implemented`. Quoting run 1:

> `Result of DPIDR read: 0x10212927`
> `Debug Port version: DPv2 MinDP: Implemented`

Runs 2 and 3 are byte-identical on these two lines. Run 1 further shows DPIDR being read **three times** during a single attach (at `debug_port_connect`, `debug_port_start`, and again before AP access) — all three return the same `0x10212927` DPv2 value. This rules out H2 (transient first-read then steady-state DPv3): there is no steady-state DPv3 value to converge to, only DPv2. Patched arm fires exactly as predicted ("`ApV2 access on DPv1 cache; upgrading to DPv3`"), writes `SELECT = 0x2df0` / `DP_BANK_SEL = 5` as DPv3 encoding, and the subsequent AP IDR read returns `IDR { … CLASS: Undefined, … TYPE: JtagComAp }` — decoding to `0x0000_0000`, exactly the "SELECT landed at an address that doesn't exist on this DP" signal in the HLD's §3.3 row-1 description. The Track A `(V2, DPv1)` cache-upgrade arm is actively harmful on this target — it forces DPv3 SELECT encoding on a genuine DPv2 DP, which decodes to `APSEL=0x00, APBANKSEL=0x9` and reads a non-existent register as 0.

**Recommended A.2b option per HLD §4:** Option A-prime with the **H1 fix shape** (new `src/vendor/raspberrypi/sequences/rp235x.rs` with `debug_port_setup` / `debug_port_start` overrides that do dormant+alert+SWD-activation and probe DPIDR1/BASEPTR0 directly; treat ADIv6 as confirmed if BASEPTR0.valid=1 despite DPIDR.version=2). Same commit removes the Track A `(V2, DPv1)` arm and sentinel WARN — on H1 that arm is not just dead code, it is actively wrong and must go. Estimated 3–5 h per HLD §4.3.

**Surprises / ambiguities for lead:**

1. **Pre-trace ranking inversion.** HLD §2.1 had H2 at prior 0.75 and H1 at 0.15, based on the `probe_diff_rp2350 --fuzz 4000` 4000/4000 PASS evidence. Trace firmly favours H1. The 4000/4000 PASS must have a different explanation — possibly that `probe_diff_rp2350` is only hitting ISA-path AP accesses that happen to work under the DPv3-forced-SELECT on a DPv2 DP (`SELECT=0x2df0` decodes on DPv2 as `APSEL=0x02, APBANKSEL=0xD` which might alias to a real AP by coincidence), or that its read path never exercises `memory_interface()` on the V2 AP. Worth a one-line check before A.2b lands: does `probe_diff_rp2350`'s fuzz loop actually hit `MemoryAp::new` at the `0x2000` base? If yes, we have an unexplained data point; if no, the `--fuzz 4000` PASS is simply not comparable to `probe_verify_rp2350`'s failure surface.
2. **Debug-build requirement.** The HLD's §3.2 procedure assumes release `RUST_LOG=probe_rs=trace` produces useful output, but the workspace's `release_max_level_info` feature strips TRACE/DEBUG at compile time. A future trace-capture task should be dispatched with "use debug build" baked in, or the HLD should flag this. Time cost was ~90 s for a debug build + a second copy+run — manageable but non-obvious to an unbriefed agent.
3. **BASEPTR0 / DPIDR1 not in the captured trace.** The current probe-rs path on a target presenting DPv2 never reads BASEPTR0 or DPIDR1 — those are ADIv6-only DP registers (bank 1+). To confirm H1's premise that RP2354 is a true ADIv6 DP that merely reports version=2 for multidrop compatibility, the A.2b implementation agent should add a `select_dp(bank=2)` + `read_dp_register(BASEPTR0)` probe and include that raw value in the journal. If `BASEPTR0.valid = 0` on RP2354 too, H1's fix shape changes (it would mean RP2354 is genuinely a DPv2 target with V2-address-shaped APs via a proprietary protocol, not a mis-reporting ADIv6). HLD §4.2's H1 patch shape handles this correctly already — flagging here so lead knows the first thing A.2b must do is confirm BASEPTR0.valid.
