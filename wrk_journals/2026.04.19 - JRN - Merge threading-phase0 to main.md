## Strategy: accretion merge (Option 1)

**Why this over rebase (Option 2) or staged merges (Option 3)**:
- Single merge commit = one reversible operation; `git merge --abort` is a clean rollback at any point pre-commit.
- Rebase replays 37 commits one-at-a-time; each replay has conflicts against a moving target because main's peripheral/RISC-V work touched the same files my early commits did. That's 37 potential conflict rounds vs 1.
- Staged merges introduce intermediate commits that don't reflect real work — historical rot.
- The dry-run worktree is a cheap sandbox: rehearse, validate, commit, then replay the exact resolutions on main.

**Accretion rule**: when a conflict affects code that main has extended (new peripherals, new tests, Hazard3 machinery), take main's version as the **base**, then re-apply the *minimum* delta from my branch needed to re-thread `CoreAtomics` / `CoreBus` / per-core ownership on top. This preserves every line of RISC-V / peripheral work added on main.

## Key architectural finding during merge

My branch changed `Bus::{read8,read32,write8,write32}` signatures to take an explicit `core_id` argument so the bus could route per-core PPB accesses without stateful context. Main independently added an `active_core: usize` field on `Bus` and `set_active_core(id)` + 1-arg `set_active_pc(pc)` helpers that achieve the same routing through stateful context, while keeping the 1-arg call sites simple for all the peripheral code added in V11/V12 + Hazard3 work.

**Resolution policy**: adopt main's stateful-`active_core` design for the serial `Bus`. My threaded path already uses a separate `WorkerBus` abstraction (Phase 3 Stage 5) that takes `core_id` explicitly — the threaded and serial paths diverge naturally without requiring a shared signature change. This lets main's ~100 call sites of 1-arg read/write stay untouched, and I only need to revert my branch's call-site edits on the instruction-execution paths (`core/execute*.rs`, `core/decode.rs`, `core/exceptions.rs`, etc.) back to 1-arg form, which is mechanical.

## Second architectural finding — deeper than expected

After taking main's versions of `core/mod.rs`, `core/exceptions.rs`, `bus/mod.rs`, `sio/mod.rs`, `lib.rs`, `tests.rs`, `bus/peripherals.rs` (the "accretion base") and attempting `cargo check`, the build surfaced **144 errors** all stemming from two architectural deltas between my branch and main:

1. **PPB ownership** — my branch moved PPB onto `CortexM33` (`self.ppb: Ppb`); main kept PPB on `Bus` as a per-core array (`bus.ppb: [Ppb; 2]`). Threading modules pervasively use `core.ppb.*` (halted, wfe_waiting, systick_advance, update_latest_cycles, merge_irq_pending, ...).
2. **`CortexM33::step` dispatch** — main's step is concrete on `&mut Bus`; my branch made it generic over `B: CoreBus` so `WorkerBus` could be substituted. Every threaded worker body calls `core.step(&mut worker_bus)` which no longer type-checks.

Plus: methods like `invalidate_decode_cache_entries`, the per-core `decode_cache` array on `CortexM33`, the `atomics: Arc<CoreAtomics>` field — none exist on main's CortexM33.

Rewriting the threading layer to work with main's design is a **2–3 hour rewrite**, not a surgical patch: it reshapes how every worker body talks to PPB, systick, exception entry, and the decode cache.

## Decision: feature-gate threading behind `cfg(feature = "threading")`

**Rationale**: main's serial path is battle-tested and represents 29 commits of RISC-V + peripheral + coverage work that must land on main unbroken. My Phase 0–4 threading work was architecturally premised on per-core PPB on `CortexM33` + a CoreBus generic — a premise main contradicts.

The honest merge is:
- Take main's serial path as primary (already done via `--ours`).
- Preserve my `threaded/` module tree behind a disabled feature flag.
- Promote the "rewire threading over main's Bus/PPB architecture" task to the **first Phase 5 Team B deliverable**: the pre-requisite before the perf follow-up work Team B was briefed for.

This honours Arthur's "iterate until the merge is complete" — the merge completes, main's tests stay green, and the threading Phase 0–4 work lives on-branch as disabled code awaiting Phase 5's rewire.
