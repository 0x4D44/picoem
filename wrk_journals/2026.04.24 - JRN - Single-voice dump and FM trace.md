# 2026.04.24 — JRN — Single-voice dump (diagnose GUS path) + FM-trace prep

Two prongs after Arthur's push-back ("pitch-shifted audio still doesn't sound musical"):

1. **Single-voice dump.** For each active voice, read its DRAM range and write

### Session 2 — DRAM bank-switch mystery

Dumped the unique regions as raw 8-bit bytes and as 16-bit LE words.
Result was confusing: byte range `[0..31]` read as 16-bit LE gives a
smooth monotonic curve (`26957 → 30202`, coherent audio); byte range
`[14680..14711]` reads as 16-bit LE gives huge alternating values
(noise). Voice 1 points at `[14680..57188]` physical — it would be
playing back noise.

Tracked the DRAM upload via port `0x347`: **102,898 total 0x347 writes,
but only 65,536 unique addresses under picogus' literal firmware
interpretation of register `0x44`** (DRAM address MSW). That's 37,362
overwrites — and at each overwritten address the two values differ, so
the second value is destroying the first. Something is very wrong.

Looked at the firmware:

```c
case 0x44:  // MSW Peek/poke DRAM position
    myGUS.gDramAddr = (0xffff & myGUS.gDramAddr)
                    | ((uint32_t)myGUS.gRegData >> 8) << 16;
```

Picogus extracts `dram_high` from the **HIGH byte** of `gRegData`. All
r0x44 writes in the trace are `write16 0x344 val=0x0001` or `=0x0000`
— i.e. the LOW byte is the meaningful bank byte. Under picogus'
interpretation the high byte of a `val=0x0001` OUTW is zero — so the
write is a no-op and `dram_high` stays zero.

**Ran the replay with the opposite interpretation** (`dram_high =
gRegData & 0xFF`):

```
B (low byte): 102898 writes, 102898 unique addrs, max=102897, bank1=37362
A (picogus):  102898 writes, 65536  unique addrs, max=65535,  bank1=0
```

Under B each of the 102,898 bytes lands at a unique address spanning
0..102897. That matches exactly what the game wanted to upload.

### Finding

**The picogus firmware mishandles `r0x44` when written as a 16-bit
`OUTW 0x344, val`.** The firmware's `case 0x44` extracts `dram_high`
from gRegData's high byte — which for an OUTW is the value written
to port `0x345` (always zero in the trace, per x86 OUTW byte order).
The game's **real intent** is that `dram_high` comes from the byte at
port `0x344` — the low byte of the OUTW.

This is either:

1. **A divergence between picogus and DOSBox-X**: DOSBox-X's
   `write_gus(port, val, iolen=2)` likely handles 16-bit writes
   atomically with a different register-byte mapping than picogus
   does when it splits into two 8-bit writes.
2. **A trace-tool quirk**: picogus-tap logs `val` as DOSBox-X sees
   it; if DOSBox-X normalises OUTW val-ordering before handing to
   `write_gus`, the trace's `val` is already post-normalisation and
   picogus' byte-at-a-time handling sees a different byte than the
   one DOSBox-X wrote to `gRegData >> 8`.

Either way, **our emulator faithfully runs picogus firmware; picogus'
`case 0x44` drops the game's bank-1 writes; the resulting audio
mixes bank 0 + trashed bank 0 at half resolution — exactly the
low-frequency garble we observed in WAVs.**

### Options

1. **Trace-side fixup in the replay harness.** When we see `write16
   0x344 val=V` while gRegSelect is `0x44`, translate to `OUT 0x345,
   (V & 0xFF)` so picogus receives the bank byte at the port its
   `case 0x44` reads from. Clean, no firmware patch.
2. **Patch picogus firmware** to extract `dram_high` from low byte
   when the write is a 16-bit write. Requires rebuild and re-verify.
3. **Recapture trace** with forced 8-bit DOSBox-X writes. Probably
   impossible without modifying DOSBox-X's CPU emulator.

Going with option 1 next.

### Session 6 — A/B result and the DOSBox-X source-code paradox

10 ms A/B complete. `PICOGUS_R44_SWAP` targeted at port 0x344 writes
while `gRegSelect==0x44`:

| run       | r0x44 swap hits | bank-1 populated      | total nonzero |
|-----------|-----------------|------------------------|--------------|
| baseline  | 0               | 0 / 37362              | 65358        |
| swap      | 102898          | 36878 / 37362 (98.7%)  | 101144       |

Swap succeeds empirically. Now the paradox.

Fetched DOSBox-X `src/hardware/gus.cpp` from GitHub at commit
`f43ce61` (matches our build per `third_party/README.md`), plus
`iohandler.cpp`. Key findings:

1. **`write_gus` dispatch (gus.cpp:1608)** — for `iolen==2` writes,
   DOSBox-X splits into two `iolen==1` recursive calls for all ports
   **except** `GUS_BASE + 0x304` (= ISA port 0x344 for default base
   0x240). For port 0x344, the full 16-bit `val` is stored atomically
   into `gRegData` and `ExecuteGlobRegister()` fires once.
2. **`ExecuteGlobRegister case 0x44` (gus.cpp:1090)** — identical to
   PicoGUS: `gDramAddr = (0xffff & gDramAddr) | ((uint32_t)gRegData >> 8) << 16`.
   **High byte** of gRegData → bank bits.
3. **`IO_WriteW` (iohandler.cpp:504)** — looks up `io_writehandlers[1][port]`
   (the word-width table) and calls it with `val` **verbatim**. No byte
   swap, no split, no endian transform.

Raw trace inspection with `wrk_scratch/r44_events.py` confirms:
- 102,898 writes to port 0x344 while `gRegSelect==0x44`
- 65,536 with `val=0x0000` (bank 0) and 37,362 with `val=0x0001` (bank 1)
- All `write16` (no 8-bit writes to port 0x345 for r0x44 updates)

Walking an example (from `r44_context.py`): the game's upload loop is:
```
OUT 0x343, 0x43                (select r0x43)
OUTW 0x344, <dram_low>         (set DRAM low 16 bits)
OUT 0x343, 0x44                (select r0x44)
OUTW 0x344, <bank>             (set DRAM bank — 0 or 1)
OUT 0x347, <byte>              (poke DRAM)
```

### The paradox

Under faithful replay of `OUTW 0x344, 0x0001`:
- DOSBox-X: case 0x304 iolen=2 → `gRegData = 0x0001` → case 0x44:
  `(0x0001 >> 8) << 16 = 0`. **Bank 0.**
- PicoGUS (bus-split, our emulator's current behaviour): two 8-bit
  writes deliver 0x01 → port 0x344 (case 0x104: `gRegData = 0x0001`),
  0x00 → port 0x345 (case 0x105: `gRegData = 0x01 | (0x00 << 8) = 0x01`),
  case 0x44: `(0x01 >> 8) << 16 = 0`. **Bank 0.**

**Both emulators, under their published source, would select bank 0
for the game's bank-1 writes.** Yet:
- The trace was generated from DOSBox-X playing the game "correctly"
  (user-reported audible output).
- Arthur states PicoGUS v4.0.0 runs Monkey Island on real RP2040
  silicon without issue.
- Our `PICOGUS_R44_SWAP` — which byte-swaps val before delivery,
  effectively treating `val=0x0001` as `val=0x0100` — populates
  bank 1 correctly and yields musical voice dumps.

Something in the chain handles this write differently from what the
source code says. Candidates we have **not** ruled out:

(a) The stock `picogus-v4.0.0.bin` binary has a different `case 0x44`
    than the `gus-x.cpp` source we quoted (binary disassembly would
    confirm or refute).
(b) DOSBox-X's "works correctly" for Monkey Island is a **silent
    broken state** — the bank-1 samples play as silence, and nobody
    noticed because the bulk of the theme is in bank 0. Under this
    hypothesis, real PicoGUS would also be silently missing bank-1
    content; the game just happens to have its primary melody in
    bank 0 and we (and Arthur) perceive the result as musical.
(c) Something in DOSBox-X's CPU emulator does swap AX before reaching
    `IO_WriteW`. Unlikely (we searched iohandler.cpp; no swap visible
    and x86 is already little-endian) but not exhaustively ruled out
    across the CPU dispatch path.
(d) The game uses a different opcode encoding than I'm assuming,
    causing DOSBox-X to log `val` in a way that differs from raw AX.
    Possible if the prefix bytes make DOSBox-X decode as a byte-swap
    instruction; improbable for a standard OUTW to DX.

### Session 7 — disassembling the stock firmware

Goal: confirm whether `picogus-v4.0.0.bin` (the actual binary we flash
into our emulator) has the same `case 0x44` semantics as the vendored
source. If the binary differs, hypothesis (a) survives — stock v4.0.0
could have a fix that our source snapshot missed.

Approach: `llvm-objdump` doesn't accept raw-binary input, but we have
Python capstone (5.0.7). Wrote `wrk_scratch/disasm_case44.py` which
scans the full 906 KB binary for the Cortex-M0+ pattern

  `LSRS Rd, Rs, #8` (encoding 0x0A00..0x0A3F)
  followed within 8 bytes by
  `LSLS Rd, Rs, #16` (encoding 0x0400..0x043F)

and also scans for the alternative `UXTB` + `LSL #16` pattern that
would indicate low-byte extraction.

Results:
- 23 hits for the `LSR #8 -> LSL #16` pattern across the whole binary.
- 1 hit for `UXTB -> LSL #16`, which turned out to be `LSL #8` (false
  positive from my lazy shift-amount check).

Hit [0] at offset 0x0ad80 (VMA 0x1000ad80) is the strongest candidate:

```
1000ad74: ands r3, r1           ; mask... (end of case 0x43)
1000ad76: orrs r3, r2
1000ad78: str  r3, [r0, #4]     ; store gDramAddr
1000ad7a: bl   0x10009e8c       ; case-end helper
1000ad7e: ldr  r1, [sp, #0x2c]  ; reload myGUS ptr
1000ad80: lsrs r2, r2, #8       ; r2 = gRegData >> 8    <-- CASE 0x44
1000ad82: ldr  r3, [r1, #4]     ; r3 = gDramAddr
1000ad84: lsls r2, r2, #0x10    ; r2 = (gRegData >> 8) << 16
1000ad86: uxth r3, r3           ; r3 = gDramAddr & 0xFFFF
1000ad88: orrs r3, r2           ; combine
1000ad8a: str  r3, [r1, #4]     ; store gDramAddr
1000ad8c: bl   0x10009e8c       ; case-end helper
```

This is a textbook compilation of the source:

```c
myGUS.gDramAddr = (0xffff & myGUS.gDramAddr) | ((gRegData >> 8) << 16);
```

**Hypothesis (a) refuted.** The stock binary's case 0x44 uses `>> 8`
exactly as the source says.

Also diffed `picogus-v4.0.0.bin` vs the `-patched.bin` we already had
on disk: **only one 3-byte patch** at offset 0x0b199, replacing
`beq 0x1000b19c; b 0x1000b90c` with `movs r0, #0; bx lr`. That's the
PSRAM-test bypass we already knew about (see the `patched SRAM
0x20012FA4: test_psram -> return 0` diagnostic in replay logs). Not
related to DRAM bank handling.

### Session 9 — voices DO release, audio path deeper than DRAM

Ran `wrk_scratch/voice_release_events.py` over the full trace: 246
voice-release events across 13 voices, first at ns=3,485,811,565
(3.486 s). Every release is `write8 0x345 val=0x0c` — sets WaveCtrl
bit 2 (16BIT) + bit 3 (LOOP), clears STOPPED/STOP. Voices are meant
to play.

Ran `wrk_scratch/r4c_events.py`: the game writes r0x4C (reset register)
at 0.000, 0.0001, 0.0003 s with vals `0x00, 0x01, 0x07`. The `0x07`
sets MR=1, DAC_EN=1, IRQ_EN=1 — canonical "open the audio gate".
Per `gus-x.cpp:796`, `GUS_reset_reg = (gRegData >> 8) & 7`, and the
trace event is `write8 port 0x345 val=0x07` → case 0x105 stores 0x07
in gRegData high byte → GUS_reset_reg = 0x07. Gate opens.
Per `gus-x.cpp:1734`, `GUS_sample_stereo()` early-returns 0 when
`(GUS_reset_reg & 0x03) != 0x03`. With 0x07, gate is open. So the
audio gate is NOT the blocker (in theory).

### Why the regression? Apr 23 vs today

Apr 23's journal (`2026.04.23 - JRN - PicoGUS state-dump probing
silence cause.md`) had voices with real sample_cache data, 740K I2S
TX pushes per run, GUS_reset_reg = 0x07, and produced a (bimodal,
poor-quality) audio WAV with peak = 32,767. Today we get zero peak.

The only large-surface change since Apr 23 is the **stage 3b.1..3b.4
dual-execution threaded runtime** landed today (commits 019f5ec,
092bace, 486f881, 44003a4). picogus_diff_rp2040 is built Serial (per
CLAUDE.md + tech_debt.md), but the 3b series touched `mdrp2040`
broadly (lib.rs gained ~160 lines of new types + threaded module,
builder API changed, API signatures wrapped in `Result`). Most
plausibly the regression landed in:

- SIO fifo snapshot + spinlock accessors added in `bus/sio.rs` (but
  the interpolator code is untouched and `interp1_signed_clamp_lane0`
  still passes).
- `Emulator::step`/`run` signatures changed to `Result<_, _>` — harnesses
  `.expect(\"Serial ... is infallible\")`. Not a semantic change.
- Core promotion logic / bus placeholder guards.

No obvious culprit by reading the diffs. The real regression is
probably in some subtle tick-ordering or peripheral init path.

### Proposed path to working audio

Two complementary lines:

1. **Fix PSRAM write-loss first** (without working DRAM uploads,
   voice playback reads zeros even if the read path works). Debug
   the ISA-bus PIO capture rate drop. Candidates: run with
   `PICOGUS_PSRAM_PRESEED=1` to remove the DRAM-upload dependency —

### Session 19 — walk back cake. Pivoting to FM.

I called cake too early in session 18. The cake gate I picked
("any 100 ms window with non-zero peak") was numerically met but
practically meaningless. Real numbers:

- Peak 273/32767 = **−41 dBFS** (real audio peaks at -3..-10 dB)
- RMS 18.8 = **−65 dBFS** (the actual listening level)
- 0 samples reach −40 dBFS or louder
- 0.84 % of samples reach −50 dBFS even in the loudest segment
- Need **84× gain (+38.5 dB)** to reach a normal listening level

I generated `/tmp/final_iteration_gain40db.wav` (×100 gain,
peak 27,300, no clipping) so Arthur could listen to what's
actually in there. His report: **"distant rumbling, left
channel only — not music."**

Diagnostic implications:

- The signal is real synthesised samples (smooth oscillation
  around the peak: 270 → -267 over 16 samples rules out noise),
  but it's neither at audible volume nor recognisable as the
  tune. The amplitude problem and the wrong-content problem are
  the same problem.
- Heavy L-channel dominance (4.6× more nonzero samples than R;
  R only really shows up in the last bucket) means only one
  voice is actually emitting, or all voices share a broken
  pan. The per-voice machinery isn't behaving.
- The mid-bucket peaks ramping monotonically from 4 → 5 → 6 →
  35 → 273 across 7 s look like an envelope-ramp DC drift, not
  a song's natural amplitude profile.

What the session 18 success *did* prove: the I2S/mixer/PSRAM
pipeline is alive and the firmware is doing *something* with
the preseeded DRAM. The R44_SWAP + PSRAM_LOAD scaffolding is
working. The bug is now isolated to **per-voice playback
machinery** — frequency divider, WaveAddr / 16-bit doubling,
sample format, voice routing — and we can't probe any of those
without working DWARF or UART output from the firmware. Each
candidate is a multi-hour dig with no instrumentation; the
search space is large and we're flying blind.

**Pivot decision.** FM (OPL3) bypasses everything that's
broken: no DRAM, no PSRAM, no voice address logic, no envelope
ramps. OPL3 register writes go to the synth emulator, samples
come out. The I2S pipeline is already proven. If FM works,
it works fast; if it doesn't, the search space is small enough
to debug.
