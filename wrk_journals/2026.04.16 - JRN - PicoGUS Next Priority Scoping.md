# 2026-04-16 — PicoGUS Next Priority Scoping (Team Lead Journal)

**Role:** Team lead. Supervising agents; not doing the scoping myself.

## Prior context

Two PicoGUS fixes shipped today:
- `d1892db` — PWM_EN alias of per-slice CSR.EN (audio path unblocked).
- `2c6b894` — PWM fractional divider port from RP2350 5eac6a1 (latent correctness).

Audio path flows (9,521 WAV frames per run). But the sample rate is ~14.9 kHz (emulator) vs 44.1 kHz (silicon target) because the firmware reprograms the PLL from 125 MHz default to 370 MHz, and our emulator doesn't currently model that reprogram — producing a 2.96× rate gap plus a producer/consumer FIFO-drop mismatch.

## Question

What's the right next target for PicoGUS debug+fix work?

Three candidates on the table:
1. **PLL reprogram** — close the sample-rate gap directly. CLAUDE.md says "Clock tree is mutable at runtime" — but is that fully wired, or is the PLL write a no-op?
2. **Other PicoGUS modes** — OPL2 FM synthesis, Sound Blaster DSP, CMS/GameBlaster. Each probably has its own set of lurking emulator gaps.
3. **Silicon oracle MVP** — `wrk_docs/2026.04.16 - HLD - PicoGUS Silicon Oracle.md` is ready; needs HW bandwidth.

## Plan

## Running log

### Scoping (agent via Explore) — COMPLETE, finding flipped
- PLL_SYS register writes ARE wired. `bus/mod.rs:759-769` triggers `recompute_clock_tree()` on writes to PLL_SYS offsets 0x00/0x04/0x08/0x0C (CS / PWR / FBDIV_INT / PRIM).
- ClockTree math for PLL_SYS VCO + POSTDIV is implemented in `clocks.rs:78-89`.
- PWM reads updated `sys_clk_hz` from the recomputed ClockTree each tick.
- **But observed sys_clk stays at 125 MHz** — consistent with our measured 14.9 kHz PWM wrap rate. So the reprogram path IS wired but ISN'T taking effect.
- Probable fault surfaces (in priority order):
  1. **PLL_SYS_CS.LOCK bit** — firmware waits for it; if our emulator never sets it, firmware never commits to PLL and skips the SRC switch.
  2. **CLK_SYS_CTRL.SRC mux** — firmware switches to PLL after LOCK; if our emulator ignores this, clk_sys stays on ROSC/XOSC.
  3. **Atomic-alias writes** (XOR/SET/CLR at +0x1000/+0x2000/+0x3000 on PLL_SYS) — pico-sdk often uses these; we may only handle plain writes.
  4. **PLL_PWR.PD/VCOPD bits** — firmware powers PLL up; if we don't track power state, LOCK can't sensibly fire.
  5. **Firmware exits overclock sequence early** (e.g. faults, hits an emulator gap, XOSC never stable) — the whole reprogram never happens.
- Full scoping: `wrk_scratch/picogus-pll-scoping.md`.

### Direction change
Stop evaluating "priority": the actual bug is clearly inside the (wired-but-broken) PLL reprogram flow. Launching diagnostic agent to instrument the flow and identify the precise breakage.

### Diagnostic round — COMPLETE, finding flipped AGAIN
- **Agent a6ecade67774374ec** instrumented the PLL reprogram path and captured a full trace.
- **The emulator's PLL reprogram is WORKING CORRECTLY.** Firmware writes all four PLL_SYS registers in canonical pico-sdk order (CS, FBDIV_INT, PWR, PRIM). PLL_LOCK_DELAY_SYSCLKS=2000 fires correctly. Firmware spin-reads PLL_SYS_CS for 2000 cycles, sees LOCK=1. Then writes CLK_SYS_CTRL.SRC=PLL_SYS_AUX and `ClockTree::sys_clk_hz` recomputes to **370,000,000**. Then CLK_PERI → PLL_USB @ 48 MHz. All correct per `overclock.h:34-67`.
- **The real bug is in the HARNESS, not the emulator.** `crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs:128` has `const DEFAULT_SYS_CLK_HZ: u32 = 125_000_000;` used for `I2sCapture::new(sys_clk, …)` (line 1321), `replay(… sys_clk …)` (line 1325), and all `ns_to_cycles(ev.ns, sys_clk_hz)` downstream calls. Treats sys_clk as a static snapshot taken at harness start.
- **Consequence:** captured LRCLK = 13,655.5 Hz is measured in the wrong time domain. Scaled by 370/125 → 40,420 Hz, within 9% of silicon target 44,100 Hz (residual is boot-phase captured at lower pre-reprogram clock).
- Notes: `wrk_scratch/picogus-pll-diagnosis.md`. Instrumented trace log: `wrk_scratch/picogus-pll-trace.stderr.log`.

### Fix plan
Smallest fix: in `picogus_diff_rp2040.rs`, read `emu.bus.clock_tree().sys_clk_hz()` dynamically rather than use the compile-time constant. Two sub-options:
- **(a) Snapshot post-init** — stash sys_clk at a mid-run point and use that for final frequency reports. Fixes the headline measurement; leaves residual 9% error from boot-phase.
- **(b) Per-cycle dynamic** — pace/measure by current sys_clk each time around the loop. More invasive but accurate across the full run.

Launching implementer with instructions to evaluate which is minimal and correct, then implement.

### Implementation — COMPLETE
