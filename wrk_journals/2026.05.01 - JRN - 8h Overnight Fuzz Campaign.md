# 8h Overnight Fuzz Campaign — 2026-05-01

Supervisor journal for an 8-hour overnight differential-fuzz session driving
both QEMU oracles in parallel:

- `qemu_diff_m33` — RP2350 / Cortex-M33 vs `mdrp2350`
- `qemu_diff_m0plus` — RP2040 / Cortex-M0+ vs `mdrp2040`

The user kicked the campaign off at "10pm" wall clock with an 8-hour budget.
System clock at start: `2026-05-01T10:20:17+01:00` (the wall-time mismatch is
benign — we run for 8h from start, regardless of which clock it ties to).
**Deadline: now + 8h.**

## Pre-flight state

- Branch: `main`, last commit `6e6b5c5 wrk_journals: V3.1 + V4 closure marker`.
- Working-tree changes (NOT mine — multi-agent WIP I respect-and-rebuild
  through):
  - `crates/mdpicoem-harness/src/bin/qemu_diff_m0plus.rs` — adds a
    `QEMU_M0PLUS_PRIMER_SLOT` (`MSR PRIMASK, R0` with R0=0) stepped before
    every test, to clear PRIMASK leak between cases. QEMU's CPU state
    persists across single-step runs, EMU rebuilds per test → without the
    primer, an MSR-PRIMASK from a prior test leaks into the next, and a
    later `MRS Rd, PRIMASK` then diverges.
  - `crates/mdpicoem-harness/src/lib.rs` — defines `QEMU_M0PLUS_PRIMER_SLOT`
    at `0x2000_0080` (in the vector-table reservation, IRQ slot we never
    raise).
- Untracked WIP docs (also not mine): `D9 Forward-Scaffolding Handover Brief`
  and `RP2040 FLAG_PURE Consumer Removal V1` HLD.

Source mtimes show the M0+ harness source is newer than its compiled binary,
so we **must rebuild before fuzzing** — otherwise we'd test stale code.

## Plan

1. `cargo build --release -p mdpicoem-harness` — clean rebuild, fail-fast on
   any WIP-induced compile errors.
2. Linux-adapted launcher inline (the existing `fuzz-runs/run-m33.sh` /
   `run-m0plus.sh` are Windows `.exe` flavoured); copy binary to PID-tagged
   path so concurrent rebuilds can't race the running fuzzer; loop seeded
   batches until deadline.
3. Spawn both oracles in the background.
4. Wake at staged intervals (1h, 2h, 4h, 6h, 8h-end), each time:
   - tail the log for fresh `[FAIL]` / `[ERROR]` / panic markers,
   - count batches completed,
   - append a journal entry.
5. On any failure, hand the seed + class to an investigation agent.
6. Final summary at deadline.

**Problem.** M33 batch 1 hit the FPU class and is grinding through SKIP/recover
loops on every FPU instruction (QEMU 8.2.2 `mps2-an505 cortex-m33` disconnects
its GDB stub on every `VADD`/`VSUB`/`VMUL` etc.). Each recovery respawns QEMU
end-to-end. Throughput on the FPU path is roughly **56 cases/min**, against
180 000 FPU cases per batch (6 FPU classes × 30 k). At that rate batch 1 alone
would take ~53h — the whole 8h would burn on one batch's FPU-recovery
treadmill, with no useful coverage from any class except whichever ran first.

The 3012 M33 FAILs are 100 % `FUZZ:M0PLUS_T32_MRS` — the same PRIMASK-leak
family the in-flight WIP fixes for the M0+ oracle. The WIP only touched
`qemu_diff_m0plus.rs`, so the leak persists in M33. Pre-existing; flagging
for the WIP author. The class is folded into `base_alu` (lib.rs ~5018), so
even `--classes=base` will still see it.

**Action.** Killed the M33 driver+fuzzer+QEMU; preserved batch 1 log to
`fuzz-runs/m33.batch1-fpu-stuck.1140.log` (583 KB); patched
`fuzz-runs/run-m33-linux.sh` to add `--classes=base`; relaunched with the
**original deadline preserved** (so M33 still ends at 18:37). M0+ left
untouched — it was healthy.

New M33 PIDs: driver 3910142 / fuzzer 3910180 / QEMU 3910182. First batch
restarted 11:40:36 with `seed=21896858411022 classes=base`.

**Carry-forward**: at end of campaign, count M33 `M0PLUS_T32_MRS` FAILs as
the deterministic baseline; only divergences outside that class count as
genuine regressions.

**Mark-ups for follow-on work**

1. **`qemu_diff_m33` PRIMASK-leak primer.** The WIP author should extend
   the `QEMU_M0PLUS_PRIMER_SLOT` pattern from
   `crates/mdpicoem-harness/src/bin/qemu_diff_m0plus.rs` to
   `qemu_diff_m33.rs`. The same MRS-PRIMASK divergence reproduces under
   M33 because the M0PLUS-prefixed classes are folded into `base_alu`
   (lib.rs ~5018) and the M33 oracle exercises the same PRIMASK-persists-
   across-step QEMU behaviour. Without the primer, M33 will continue to
   emit ~2 000–3 000 deterministic FAILs per 30 k batch — making real
   divergences hard to spot in the log.
2. **QEMU 8.2.2 + cortex-m33 + FPU.** Every FPU-class fuzz instruction
   (`VADD`/`VSUB`/`VMUL`/`VDIV`/`VABS`/`VMOV` etc.) disconnects the QEMU
   GDB stub with "failed to fill whole buffer". Either need a different
   QEMU build, a different machine model (mps2-an505 may not enable VFP
   on this QEMU), or to take the FPU oracle off QEMU entirely and rely on
   `silicon_periph_diff_rp2350` + unit tests. Until that's resolved,
   running M33 with `--classes=base` is the only sensible default for
   the QEMU oracle.
3. **M33 edge-case mode pre-existing FAILs (not chased here).** Default
   `qemu_diff_m33` (no `--fuzz`) emits two deterministic edge-case
   divergences I noted but did not investigate:
   - `LDM R0!, {R0, R1} (Rn in list): R0 addr delta: QEMU=0xfffffeaa EMU=0xdffffeaa` — looks like an Rn-in-loaded-list writeback bug (writeback should be UNKNOWN/skipped per ARM, both sides choose differently).
   - `MRS R1,BASEPRI (sysm=17): R1: QEMU=0x40 EMU=0x00` — same persistence-across-steps story as PRIMASK; primer fix would also catch this.

## Outcome

8 hours of differential fuzz; ~27.6 M tests across two QEMU oracles;
**zero novel divergences in either emulator.** The M0+ campaign produced
a clean `0 FAIL / 0 RECOVER` baseline across 14.6 M tests — strong
evidence that the in-flight WIP PRIMASK primer is correct and complete on
the M0+ side. The M33 campaign reproduced the known baseline noise but
revealed no new emulator bugs in the ALU/memory/exception paths covered
by `--classes=base`.

The campaign also surfaced two pre-existing harness-side issues that the
WIP author / a follow-on agent should address (M33-side PRIMASK primer,
QEMU-FPU GDB disconnect) — both captured in the mark-ups above.

No emulator-side fixes were applied during this run. No emulator code was
modified at all — every change was to the campaign drivers
(`fuzz-runs/run-m33-linux.sh`, `fuzz-runs/run-m0plus-linux.sh`) and this
journal.
