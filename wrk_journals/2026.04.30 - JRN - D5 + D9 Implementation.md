### Lessons / observations from this session

- **Stale gitStatus is dangerous.** The system context's gitStatus
  block at session start showed only the original recent commits
  ending at `919ea09`. The repo had 8 newer commits and 4 newer
  journals from concurrent agent sessions. A `git log --oneline -10`
  + `git status` at the start of any team-lead coordination is the
  cheapest possible insurance against rework — should be a hard
  precondition before HLD review or agent dispatch.
- **Trust LLD review less when both eyes copy the same misread.** I
  approved the W2 (b) field-access rewrite confidently with reasons
  that turned out to be invalid: both the LLD author and I conflated
  `ThreadedEmulator::shared()` (public, load-bearing) with
  `WorkerBus::shared()` (deleted). For high-stakes test-rewrite
  decisions, grep the actual call sites before approving.
- **Worktree isolation would have flagged the prior commit early.**
  An isolated worktree based on `main` HEAD at dispatch time would
  have shown W2 the prior commit immediately on first grep. Mixing
  isolation with stale context only sometimes catches the gap.
- **Multi-agent coordination needs git-state checks at every
  handoff, not just session start.** The prior session shipped
  `46e523f` between when I ran `git log` originally (during the
  earlier "Sweep findings resolution" turn) and when I dispatched
  W1+W2. A git check immediately before dispatch would have caught
  it.
- **`/code-reviewer` skill plus team-lead applied fix worked
  cleanly.** W1's review caught a real stale doc-comment that the
  bench would not have caught. Net cost: one token + one
  re-verification pass. Worth the discipline.
- **Stop-and-report when the world has moved.** W2's behaviour was
  exemplary: detected the prior commit, verified divergences,
  refused to push through with destructive operations. The
  alternative (silent rebase / re-do) would have churned audit
  history.
