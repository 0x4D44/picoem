### Build warnings — mdrp2040 lib test

```
warning: unnecessary parentheses around method argument
  --> crates\mdrp2040\src\tests.rs:5178:32

warning: function `SSPICR_OFFSET` should have a snake case name
  --> crates\mdrp2040\src\tests.rs:5361:8
```

**Investigation.**

1. `(1 << 9)` parens at 5178 — trivially redundant. Direct cleanup.
2. `SSPICR_OFFSET()` helper at 5361 was a four-line `#[inline] fn () -> u32 { 0x020 }` that returns the SPI interrupt-clear offset. Grep confirms `crate::peripherals::spi::SSPICR` already exists as `pub const SSPICR: u32 = 0x020;` (`spi.rs:75`) and is the canonical name used everywhere else in `spi.rs` (line 292, 336, 573). The local helper was duplication.

**Fix.** Imported `SSPICR` into the test module's `use` and deleted the helper. Single call site (`s.write32(SSPICR_OFFSET(), ...)`) became `s.write32(SSPICR, ...)`. Same numeric value, removes redundant code, kills the warning at its source.

### Clippy warnings — additional real-defect suspects

Beyond the 114-stylistic baseline, four clippy warnings looked like
real signals worth investigating:

#### `drop_non_drop` — `crates/mdrp2350/src/threaded/emulator.rs:641`

```rust
} else {
    // At least one PIO worker panicked — drop all three blocks
    // (including any Ok returns) per HLD V5 §2.7.
    drop((bl0, bl1, bl2));
    self.pio_blocks = None;
}
```

The comment block 30 lines above already documents that the Ok blocks
"simply go out of scope at end of function (drop site)" — i.e. the
explicit `drop()` is redundant. Clippy's "Dropping such a type only
extends its contained lifetimes" is correct: a tuple of `Option<T>` has
no `Drop` itself, and the inner `Option<PioBlock>`s drop the same way at
end-of-scope as via `drop(...)`.

**Fix.** Removed the `drop()` call and rewrote the inline comment to
match the upstream commentary ("leave all three blocks ... to drop at
end-of-scope here").

#### `zombie_processes` — `crates/mdpicoem-harness/tests/qemu_process_drop.rs:274`

The `socket_freed_after_external_kill` test deliberately spawns a child
fuzzer process and externally kills it via `OpenProcess` +
`TerminateProcess` (mirrors `taskkill /F`), then asserts that the GDB
port is freed. After the kill it never `wait()`s the child, so the
kernel handle leaks until end-of-test-process. Test is `#[ignore]` and
manual-only, so the leak is benign — but trivially fixed by reaping
explicitly.

**Fix.** `let mut child` (instead of `let child`) and `let _ =
child.wait();` after the port-release assertion. The
externally-terminated process exits cleanly via `wait()`.

#### `empty_lines_after_outer_attribute` — `crates/mdpicoem-harness/src/thumb32_gen.rs:24`

```rust
#[allow(dead_code)]

// When test generators are added later, they'll use:
//   use crate::*;
```

The `#[allow(dead_code)]` doesn't attach to anything — there's an empty
line, then a comment, then the actual `pub const`s (which are reachable
from elsewhere, not dead). Module already has a `#![allow(...)]` inner
attribute at lines 18–22 covering the genuine intentional patterns;
this orphan was almost certainly meant for a placeholder item that was
never written.

**Fix.** Deleted the orphan attribute. When real test generators land,
their dead-code suppression should attach to the specific item or
extend the existing module-level `#![allow(...)]`.

#### `empty_line_after_doc_comment` — `crates/mdrp2350/src/threaded/emulator.rs:2724`

A 13-line `///` doc block at lines 2712–2724 plus a `// ----- HLD V5 §4
item 6: OneROM-shape soak ----` divider at 2710 documented a soak test
(`stress_onerom_60s`). But the test it documents is at line 3040 — at
some point a `mod stage5_coverage { ... }` block (lines 2729–3038) got
inserted between them, orphaning the doc.

`git log -S "stress_onerom_60s"` shows the test was added by `786f4e1`
("threaded: Final — stress_onerom_60s + oracle smoke"); the function
still exists at line 3040, so this isn't a missing-function defect — it's
documentation that got displaced when `stage5_coverage` was inserted.

**Fix.** Moved the divider + doc comment down to immediately precede
`#[test] fn stress_onerom_60s` (their original textual position relative
to the function). The doc is back on its function, and the warning is
gone — without removing or changing any code, just relocating the doc
block.

#### `empty_line_after_doc_comment` — `crates/mdrp2040/src/tests.rs:4924`

```rust
/// UART0/UART1 RX DREQ arms (bus/mod.rs:1638, 1644). RX is not
/// otherwise stimulated, but uart's `rx_dreq` fires iff enabled +
// rx_fifo non-empty — the `is_enabled()` check alone means both
// false arms already run for disabled UARTs, and the true path
...
```

The first two lines use `///` (rustdoc), then the rest of the block
switches to `//`. There's no item below to attach the doc to — the
block is a free-floating explanation of why a particular UART RX-DREQ
arm is intentionally unreachable in Phase 2 emulator scope. Whoever
wrote it appears to have started in `///` and corrected to `//` mid-way
without going back to fix the first two.

**Fix.** Demoted the leading `///` lines to `//`. The block is now
uniformly a regular comment, which matches its intent (it documents
*why a code path is intentionally unreachable*, not an item).
