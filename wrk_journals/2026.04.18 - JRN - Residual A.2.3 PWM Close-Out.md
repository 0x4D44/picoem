# Residual A.2.3 PWM Fractional Divider — Close-Out

**Date:** 2026-04-18
**Parents:**
- `wrk_journals/2026.04.17 - JRN - Silicon Oracle Residuals Fix Wave.md` (parent wave)
- `wrk_docs/2026.04.17 - HLD - Residual A.2.3 PWM Fractional Divider Fix.md` (parent HLD)
- `tech_debt.md` entry "Silicon oracle scenario `pwm_fractional_div` — self-gated sled design fails silicon verify" (replaced by this close-out)

## Outcome

**`pwm_fractional_div` PASSES on RP2354 silicon.** Probe `E46410955F614129`,
mask `0xFC00`, both sides bucket to `0x400` (silicon raw CTR ≈ 1537,
emulator raw CTR = 1027).

## What was wrong (revised diagnosis)

The parent residual's reverted attempt produced `HW=0xFE82, EMU=0x4C` —
silicon's PWM-enabled window appeared to be ~130k sysclks vs emulator's
~150 sysclks. The parent HLD listed four hypotheses, all of which turned
out to be incomplete. The actual root cause was simpler:

**PWM CTR persists across scenarios on silicon.** Silicon's PWM `CHn_CTR`
is a free-running 16-bit hardware counter that the runner never resets
between scenarios. The previous catalogue-order scenario (`pwm_wrap_irq`)
leaves PWM enabled and ticking; by the time `pwm_fractional_div`'s setup
table runs, CTR has accumulated thousands of ticks across DAP latency.
The emulator side, in contrast, gets a fresh `EmulatorBuilder::new(...)`
per scenario and starts CTR at 0. That asymmetry — *not* the divider
formula, *not* the sled's STR-disable failing to propagate — was the
load-bearing defect.

## What this wave actually changed

Three changes in `crates/mdpicoem-harness/src/silicon_scenarios.rs`,
plus one regression test in `crates/mdrp2350/src/peripherals/pwm.rs`.

### 1. Setup explicitly resets PWM state

```rust
const S_PWM_FRACTIONAL_DIV: &[(u32, u32)] = &[
    (RESETS_RESET + ALIAS_CLR, RESETS_CLR_ALL),
    (PWM_EN_OFFSET, 1),         // emulator side: EN[0]=1 (silicon: physical bit transient)
    (PWM_SLICE0_CSR, 0),        // PWM off on both sides
    (PWM_SLICE0_CTR, 0),        // explicit CTR reset (the load-bearing fix)
    (PWM_SLICE0_TOP, 0xFFFF),
    (PWM_SLICE0_DIV, 0x0020),
];
```

The write order `EN=1` *then* `CSR=0` is deliberate — see the comment on
`S_PWM_FRACTIONAL_DIV` for the dance with the emulator's split-storage
of `CSR_EN` vs `EN[0]` (separate tech-debt item, untouched here).

### 2. Self-gated sled

`SLED_PWM_FRACTIONAL_DIV_HW` brackets a 1024-iter spin with `STR CSR=1`
(start) and `STR CSR=0` (stop). Both silicon and emulator measure
PWM-enabled cycles between the two `STR`s.

A subtle bug in the encoding (movw `i` bit) was caught during the EMU-side
test: my first draft had `0xF648` for `movw r3, #0x8000` (which encodes
`#0x8800`); the correct encoding is `0xF248`. Cross-referenced against
`SLED_TIMER1_ALARM0_FIRE_AND_CLEAR_HW` which has the same constant.
Spotted at the unit-test level, never reached silicon.

### 3. Coarse mask `0xFC00` on the CTR observable

Even with the self-gated sled, silicon CTR (≈1537) and emulator CTR
(≈1027) diverge by ~500 ticks on the 1024-iter spin. The gap is
**not** a divider-formula bug — it tracks the per-iter cycle accounting
gap between silicon's M33 and the emulator's M33 model (silicon takes
~3 cyc/iter for `subs+bne`; emulator ~2 cyc/iter), plus a fixed
STR-to-APB latency differential. Both sides bucket to `0x400` under
`0xFC00`.

A real divider bug (formula error doubling or halving the tick rate)
would shift CTR into a different 1024-wide bucket, which the mask
still catches. The mask design + threat model is documented at
`O_PWM_FRACTIONAL_DIV` and on `SLED_PWM_FRACTIONAL_DIV_HW`.

### 4. Regression coverage

- `fractional_div_integer_2_per_cycle_dispatch_matches_bulk` in
  `crates/mdrp2350/src/peripherals/pwm.rs` pins the per-cycle
  (`step_quantum=1`) dispatch behavior, complementing the existing
  bulk-tick test. Catches future emulator changes that break
  `tick(1, ...)` while keeping `tick(N, ...)` working.
- `test_pwm_fractional_div_sled_on_emu` in `silicon_scenarios.rs`
  cross-executes the sled in the emulator and pins `CTR == 1027`.
  If a future emulator change drifts the per-cycle PWM tick path, this
  test catches it locally before silicon's mask absorbs the drift (or,
  worse, before the drift blows past the mask and surfaces as a HW≠EMU
  FAIL that masquerades as a silicon issue).
- `pwm_fractional_div` added to the `test_custom_sled_opt_in_roster`
  allow-list and `test_validate_custom_sled_accepts_shipped_sleds`.

### 5. Diagnostic CSR observation

Added `(PWM_SLICE0_CSR, 0x01)` to `O_PWM_FRACTIONAL_DIV`. This proves
the sled's final `STR CSR=0` actually landed before BKPT. Confirmed
PASS on silicon during this wave — disposing of the parent HLD's
Hypothesis #1 (silicon's `STR CSR=0` doesn't propagate before BKPT).

## What this wave intentionally did NOT change

- **Emulator's PWM `tick()` formula** (`pwm.rs:353-396`). The Stage A
  `5eac6a1` formula is correct under both bulk and per-cycle dispatch;
  unit tests pin both.
- **Emulator's split storage of `CSR_EN` vs `EN[0]`** (`pwm.rs:146-162`).
  Genuine tech-debt; documented separately in `tech_debt.md` with a
  fix sketch. The new setup-write ordering sidesteps it for this one
  scenario but doesn't paper over it for future scenarios.
- **Emulator's M33 cycle accounting for STR-to-APB and tight backward
  branches** (`execute.rs:500, 839`). Genuine tech-debt; documented
  separately in `tech_debt.md` with a fix sketch pointing at the cycle
  oracle calibration table as the lever. The mask-based scenario
  workaround is the short-term mitigation.
- **`gate_peripheral_hw` PWM branch.** I drafted one as belt-and-braces,
  then removed it — a gate write would clobber the diagnostic CSR
  readback that proves the sled's STR landed. The sled does its own
  gating and the diagnostic verifies it; an additional gate would be
  premature abstraction (no other PWM scenarios need it today).

## Wave-scope reflection

The most interesting finding — same as the parent wave's note — is that
the parent HLD's four hypotheses were all wrong (or at best peripheral
to the actual cause). The real defect was structural: silicon CTR
persisting across scenarios. None of the four hypotheses listed in the
tech_debt entry were on the critical path. A "first-step math: where
does HW=0xFE82 actually come from numerically?" question would have
surfaced "this is much larger than any reasonable single-sled window"
faster than chasing STR-propagation hypotheses.

The diagnostic CSR observable I added is now confirmed-passing on
silicon, which retroactively justifies the parent wave's recommended
"diagnostic-first" path. It also gives us a regression guard: if a
future emulator/probe change ever breaks STR-disable-before-BKPT, the
diagnostic will surface it as a separate FAIL row instead of a confused
CTR mismatch.
