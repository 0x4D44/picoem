# JRN — OneROM Emulator Perf Results Consolidation

**Date**: 2026-04-24
**Scope**: All OneROM serve-path performance data gathered across 2026-04-23
  (CPU serial oracle shipped) + 2026-04-24 (PIO serial oracle shipped).
**Source journals**:
- `2026.04.23 - JRN - OneROM CPU Serial Speed-Grade Oracle.md`
- `2026.04.24 - JRN - OneROM PIO Serial Speed-Grade Oracle.md`
**Fixtures measured**: 1541 $E000 kernal ROM set 0
  (`onerom-fire-24-a-rp2350-1541-cpu.bin` for CPU,
   `onerom-fire-24-a-rp2350-1541.bin` for PIO).

## 1. Headline grades

| Mode | Grade (emulator self-characterisation) | Silicon baseline |
|---|---|---|
| **OneROM CPU** | **-90 ns** (80 ns emulated mean) | ~90 ns (published) |
| **OneROM PIO** | **-250 ns** (on this fixture, emulator self-report) | unknown — Piers asserts PIO > CPU |

Headline numbers are **steady-state serve time in emulated sysclk time** at
150 MHz, measured through the `CpuServingOracle` / `ServingOracle` per-case
APIs. These are the numbers a consumer **running inside the same emulator
thread** would see (no cross-thread coherency tax).

## 2. Measurement modes — what each number means

Three different ways to measure emulator serve-time, answering different questions:

| Mode | What it measures | Host overhead | Honest for |
|---|---|---|---|
| **Emulated cycle time** (`stress_*` and `serial_*`) | Sysclk cycles the emulator's model says elapse between CS-low and byte-stable | None (not wall-clock) | Comparing emulator vs silicon spec |
| **Single-thread wall-clock** (emulator step loop on host, serial driver) | Wall-clock ns for the emulator to simulate one serve + stepping overhead | Per-case step-loop cost (~us range) | Measuring emulator simulation throughput |
| **Multi-thread wall-clock** (`threaded` oracle, cross-thread consumer) | Wall-clock ns a concurrent host-thread consumer waits for a byte | Barrier + atomics + OS scheduler | Measuring what a real external consumer on this host sees |

## 3. CPU mode — all numbers

### 3.1 Emulated cycle time (stress + serial oracles, same measurement)

From `target/release/onerom_stress_cpu_rp2350.exe` and
`target/release/onerom_cpu_speed_grade_serial_rp2350.exe` (they report in
ns and cycles respectively; cross-check confirmed exact match @ 150 MHz):

| Stat | Cycles | ns @ 150 MHz |
|---|---|---|
| min  | 7  | 46  |
| p50  | 9  | 60  |
| mean | 12 | 80  |
| p95  | 40 | 266 |
| p99  | 40 | 266 |
| max  | 40 | 266 |

Unique cycle buckets: **5**. Distribution has a long tail anchored at cy=40
(`ZERO_BYTE_TRUST_TIMEOUT_CPU = 40`) — these are cases where the CPU was
already driving 0x00 before the stim, so the oracle accepts steady 0x00 after
40 ticks rather than a visible transition (HLD §9). Inflates p95/max without
reflecting the serve path's hot path.

### 3.2 Serial ladder (cycle-count, HLD V2, shipped 2026-04-23)

Default ladder `[50, 30, 20, 13, 10]` cy:

| Rung (cy) | Rung (ns) | Errors | Verdict |
|---|---|---|---|
| 50 | 333 | 0    | PASS |
| 30 | 200 | 218  | FAIL |
| 20 | 133 | 218  | FAIL |
| 13 |  87 | 218  | FAIL |
| 10 |  67 | 233  | FAIL |

**13 cy ≈ 87 ns** is the silicon-anchored claim: CPU serve loop is 5 ARM
instructions → ~7 cy floor, `CPU_ENVELOPE_CYCLES = 7..=60` matches
first-principles. The 218-case cluster at the zero-byte-trust point makes
most non-top rungs fail ≈ uniformly.

### 3.3 Threaded wall-clock ladder (HLD original, `onerom_cpu_speed_grade_rp2350`)

Ladder `[500, 400, 300, 250, 200, 150, 120, 100]` ns, step-quantum 1024,
3 sweeps per rung, 6144 samples per rung:

| Rung (ns) | Errors / 6144 | Verdict |
|---|---|---|
| 500 | 0  | PASS |
| 400 | 0  | PASS |
| 300 | 41 | FAIL |
| 250 | 43 | FAIL |
| 200 | 51 | FAIL |
| 150 | 40 | FAIL |
| 120 | 50 | FAIL |

**Reliable cliff at 400 ns**. Serve-loop throughput probe on same run:
181 MHz emulated rate = 5.53 ns per emul cy wall-clock. Elapsed 5.92 s.

### 3.4 Single-thread wall-clock (stress oracle's host measurement)

Wall-clock per case (host-side, `stress_cpu`):

| Stat | us |
|---|---|
| min  | 2.400 |
| p50  | 2.800 |
| mean | 3.068 |
| p95  | 4.900 |

Serve-loop probe from the threaded oracle run: 181 MHz emulated = 5.53 ns
per emul cy wall-clock. At 12 cy mean per serve → **66 ns wall-clock per
byte in steady-state single-thread mode** (faster than silicon, because the
host's GHz-class CPU outpaces the 150 MHz emulated target).

## 4. PIO mode — all numbers

### 4.1 Emulated cycle time (stress + serial oracles, cross-check matches exactly)

From `onerom_stress_pio_rp2350.exe` and
`onerom_pio_speed_grade_serial_rp2350.exe`:

| Stat | Cycles | ns @ 150 MHz |
|---|---|---|
| min  | 19 | 126 |
| p50  | 35 | 233 |
| mean | 34 | 226 |
| p95  | 35 | 233 |
| p99  | 35 | 233 |
| max  | 35 | 233 |

Unique cycle buckets: **3** — `19: 1 case, 30: 1 case, 35: 2046 cases`. Very
tight tri-modal distribution, not a normal spread. Top bucket dominates
(2046 / 2048 cases = 99.9%). The two sub-envelope outliers (19 cy, 30 cy)
are likely cold-pipeline warm-up artefacts — the first cases before PIO1
SM1's steady-state back-pressure develops. **Do not interpret as
"2 cases served faster than envelope"** — they are not representative.

## 5. CPU vs PIO side by side

### 5.1 Emulated cycle time (the honest comparison)

| Stat | CPU (cy) | CPU (ns) | PIO (cy) | PIO (ns) | Ratio PIO/CPU |
|---|---|---|---|---|---|
| min  | 7  | 46  | 19 | 126 | 2.7× |
| p50  | 9  | 60  | 35 | 233 | 3.9× |
| mean | 12 | 80  | 34 | 226 | 2.8× |
| p95  | 40 | 266 | 35 | 233 | 0.9× |
| max  | 40 | 266 | 35 | 233 | 0.9× |

**PIO is 2.7–3.9× slower than CPU at typical cases, comparable at p95/max.**
PIO's tight distribution has less tail; CPU has long tail from zero-byte-trust.

### 5.2 Speed-grade summary

| Mode | Serial ladder top pass | EPROM grade equivalent |
|---|---|---|
| CPU | 50 cy = 333 ns | -333 ns (but 13 cy = 87 ns tail-excluded → **~-90 ns** effective) |
| PIO | 250 ns                 | **-250 ns** |

The CPU number has a discontinuity: the zero-byte-trust tail at 40 cy
pushes the top-rung-PASS boundary to 50 cy = 333 ns, but the hot path is
genuinely 12 cy mean / 9 cy p50. Depending on interpretation, CPU is
either a "-90 part" (hot path) or a "-333 part" (worst-case with
zero-byte-trust cases counted). PIO has no such tail mechanism.

### 5.3 Why PIO is slower than CPU for single-byte serves

Architectural, not a model bug. Decomposition:

- **CPU serve** = 5-instruction ARM loop (STRB / LDRH / TST / LDRB / BEQ)
  running in a tight polling loop → floor ~7 cy.
- **PIO serve** = 8 cy DMA pipeline (4 read + 4 write, RP2350 datasheet)
  + ~7 cy PIO SM program (address capture, autopush, OUT PINS) → floor
  ~15 cy (matches `ENVELOPE_CYCLES = 15..=45`).

DMA framing cost dominates for single-byte access. PIO's win over CPU is
on **bulk/streamed transfers** where the pipeline stays full and
amortises the framing. Single-byte probe-style serves are framing-dominated.

Silicon-grade analytical reference: Piers Finlayson's epio test
(`crates/epio-sys/third_party/epio/test/onerom.c:44`) asserts **12 cy** for
byte-in-TXFIFO on a simplified PIO0 single-block layout. +1 cy for
`OUT PINS, 8` = 13 cy pin-to-pin = 87 ns @ 150 MHz. Emulator's 19-cy min
is 6 cy above this floor — some of which is the stress oracle's
"pin-stable-for-3" detection vs epio's "byte-in-TXFIFO" reference point
(~5 cy difference).

## 6. Wall-clock floor across modes

What the emulator can actually do on *this host*, reading bytes at host speed:

| Topology | CPU (wall-clock ns/byte) | PIO (wall-clock ns/byte) |
|---|---|---|
| **Inside emulator** (steady-state, no cross-thread) | **66 ns** | **~190 ns** (derived: 34 cy × 5.53 ns/cy) |
| **Cross-thread consumer** (threaded oracle) | **400 ns reliable** (cliff 300–400) | **not measured** |
| **Per-case host driver** (stress oracle, `us/case`) | 2.8 us/case | 6.0 us/case |

The cross-thread PIO number is a known gap — mirror of the threaded CPU
oracle not yet built.

## 7. Silicon comparison — what we know and don't know

### 7.1 Known silicon baselines

- **OneROM CPU on silicon**: ~90 ns, published number. Matches emulator
  CPU mean (80 ns) within measurement error. Model validated.
- **OneROM PIO on silicon**: unknown. Piers asserts PIO > CPU (PIO is faster),
  but we have no measured silicon PIO latency number in-tree.

### 7.2 Analytical ground-truth (from Piers' epio reference)

- epio test `onerom.c:44` asserts 12 cy CS-low to byte-in-TXFIFO on
  simplified PIO0 single-block model.
- +1 cy for `OUT PINS, 8` pin drive = 13 cy pin-to-pin = **87 ns @ 150 MHz**
  (silicon floor, pipeline empty).

### 7.3 Three known gaps between emulator self-report and silicon

Documented in 2026-04-24 PIO session journal:

1. **Topology**: Piers' test uses PIO0 single-block; real firmware uses
   PIO1+PIO2 cross-block (`PIO1.CTRL=0x01`, `PIO2.CTRL=0x03`). Cross-block
   DMA may add unknown (probably small) additional cycles.
2. **Measurement reference point**: `epio_wait_tx_fifo` measures "byte in
   TXFIFO"; stress/serial oracles measure "pin stable for 3 consecutive
   cycles". ~5 cy offset between the two interpretations.
3. **GPIO input synchroniser**: RP2350 datasheet §9.5 — 2-FF sync chain adds
   ~2 cy uniformly on silicon. Emulator does not model this; neither does
   epio. Silicon will be +2 cy vs both.

Net: plausible silicon grade is **emulator self-report + ~7 cy (~47 ns)**
→ silicon CPU grade ≈ -137 ns (but published spec is -90 ns, so the
stress-vs-epio measurement offset may partially cancel); silicon PIO grade
≈ **-300 ns**.

### 7.4 What silicon measurement would require

Not yet built. Options ranked by feasibility:

- **External logic analyser** watching addr + data pins. Accurate, needs LA
  hardware, not in-repo.
- **Firmware-instrumented measurement**: add CYCCNT stamping to OneROM
  firmware on CS-low and byte-ready, host reads mailbox. Firmware change,
  bigger work.
- **RP2354-as-both-target-and-driver**: core 1 runs OneROM firmware, core 0
  runs stim + measure loop, both sysclk-domain. ~200 lines firmware-side
  + harness. Genuinely new binary.

`silicon_cycle_oracle_rp2350` was considered but does NOT fit —
it measures CPU instruction sequences via K-delta mailbox protocol, no
hooks for PIO pin-event timing.

## 9. Caveats — things these numbers do NOT say

- **Not silicon-parity claims.** The serial oracles self-characterise the
  emulator. The 2026-04-24 DA round established that PIO `ENVELOPE_CYCLES`
  is explicitly "emulator-bounded, not silicon-calibrated" per its own
  source (`onerom_serving_oracle.rs:78`). CPU envelope is silicon-anchored
  (13 cy claim).
- **One fixture, one walk.** Real EPROM speed-grades encode operating
  envelopes (temperature × voltage × process). These numbers characterise
  the emulator at 150 MHz sysclk on the 1541 $E000 fixture, 2048-case
  A11=A12=1 sweep. Not a part-grade in the silicon sense.
- **Steady-state only.** All measurements run with the rest of the system
  idle (no CPU-vs-PIO bus contention, no DMA-from-elsewhere, no interrupts).
  Real workloads will be worse.
- **Threaded numbers are host-specific.** The 400 ns CPU cliff is
  Windows + this specific host's barrier + atomic behaviour. A Linux RT
  kernel or different CPU family would move the cliff.

## 10. Open questions / follow-ups

- **Silicon PIO measurement** (see §7.4). Needed to convert emulator -250 ns
  into a real-silicon PIO grade.
- **PIO threaded speed-grade oracle** (mirror of CPU threaded). Would give
  the cross-thread wall-clock number for PIO mode. ~900 lines, day's work.
- **Why 2 outliers?** The min=19 and cy=30 cases in PIO stress are
  suspected cold-pipeline warm-up. Could be confirmed by shuffling case
  order — if they're always positions 0-1, warm-up confirmed; if
  position-independent, something else is going on.
- **Does CPU tail = 40 cy zero-byte-trust cases look the same on silicon?**
  The 218-case cluster at cy=40 is an emulator mechanism. Real silicon
  CPU-mode would genuinely take some time to serve 0x00 bytes the CPU was
  already driving — but whether the distribution clusters at 40 cy
  specifically is emulator-convention. Probably harmless but worth noting.

## 11. Bottom line

- **Emulator CPU mode = -90 ns equivalent.** Matches silicon spec within
  measurement. Model validated.
- **Emulator PIO mode = -250 ns on 1541 $E000 fixture.** Self-reported.
  Silicon unknown — Piers asserts PIO > CPU on silicon, so if PIO silicon
  is truly < 90 ns, emulator is significantly slower than silicon for PIO
  mode (architecturally explainable by DMA framing cost on single-byte
  serves; emulator-specific penalties might also contribute).
- **Single-byte PIO in emulator is 2.8× slower than single-byte CPU**
  (emulated mean 226 ns vs 80 ns). Architecturally expected for DMA-framed
  single-byte serves; PIO wins on bulk/streamed transfers (not measured).
- **On a host, threaded wall-clock is 4.4× worse than emulator-internal**
  for CPU (400 ns vs 80 ns). PIO equivalent not measured but expected to
  be similar ratio on top of PIO's emulated 226 ns.

End.
