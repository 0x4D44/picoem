# 2026-04-16 — PicoGUS Stream 3: PWM EN/CSR.EN alias fix

## Context

Team lead green-lit a targeted fix after devil's-advocate verification.
`crates/mdrp2040/src/peripherals/pwm.rs` was treating `PWM_EN` (offset
0xA0) as separate storage from per-slice `CSR.EN` (bit 0 of each
`CHn_CSR`). Per RP2040 datasheet §4.5.3.18 these share physical
storage — writing `CSR.EN` must show up in `PWM_EN`, and vice versa.

pico-sdk's `pwm_set_enabled()` writes only `CSR.EN`, so the emulator's
`en` field stayed at zero, `is_idle()` returned true, and the PWM
peripheral never advanced from the `Emulator::step` fast path. PicoGUS's
PWM-IRQ-driven audio sample handler therefore never fired.

## Implementation (TDD)

### Step 1: failing test

Added `csr_en_alone_advances_slice_and_mirrors_into_pwm_en` to the
module's `tests`. It writes `CSR.EN` on slice 4, ticks, and asserts
both the CTR advanced and that reading 0xA0 returns `1 << 4`.

Confirmed FAIL against pre-fix code:

```
test peripherals::pwm::tests::csr_en_alone_advances_slice_and_mirrors_into_pwm_en ... FAILED
  assertion `left == right` failed: slice 4 CTR must advance with only CSR.EN set
    left: 0
   right: 50
```

### Step 2: fix

`crates/mdrp2040/src/peripherals/pwm.rs`:

1. Removed the `en: u8` field from `PwmRegs`.
2. Added `pwm_en_view()` that synthesises the 0xA0 read value from
   `slices[i].csr & CSR_EN` for i ∈ 0..8.
3. `read32(EN)` now returns `pwm_en_view() as u32`.
4. `write32(EN, …)` applies the RMW alias to the synthesised view and
   fans out: for each bit i of the result, set or clear `CSR_EN` on
   `slices[i].csr`. This keeps the four alias codes (normal, XOR,
   BITSET, BITCLR) identical to the rest of the peripheral.
5. `is_idle()` now checks `pwm_en_view() == 0` (plus the existing INTR
   / INTF+INTE conditions).
6. `tick()` dropped the `globally_enabled` gate — CSR.EN is now the
   single source of truth.
7. Module docs updated to call the 0xA0 entry an alias.

### Step 3: test inversions

Per devil's advocate:

- `disabled_slice_does_not_advance` — kept name, rewrote intent. Now
  asserts that writing `PWM_EN = 0` after enabling via CSR clears
  `CSR.EN` on every slice (the alias behaviour) and the slice halts.
- `globally_enabled_without_csr_en_does_not_advance` — deleted. Under
  the alias model its premise is wrong: writing PWM_EN IS writing
  CSR.EN. Replaced by `pwm_en_clearing_a_bit_clears_matching_csr_en`
  which tests the new invariant: PWM_EN BITCLR clears the matching
  slice's CSR.EN and the slice stops advancing.

Two other small test updates: `reset_defaults_all_slices_idle`,
`en_bitset_alias`, `en_bitclr_alias` each referenced the removed
`p.en` field — now call `p.pwm_en_view()`.

### Step 5: version bump

`crates/mdrp2040/Cargo.toml` 0.15.0 → 0.15.1 (patch: behavioural fix,
no public API change — `en` was a private field). Cargo.lock updated
as a side effect of the rebuild.

## No surprises

The fan-out semantics worked first time. The only subtlety is that
`SLICE_CSR` writes also wipe the `PH_ADVANCE` / `PH_RETARD` transient
bits, but that's independent of the EN aliasing and unchanged.

Note: `tick_peripherals` fast-path skip used to fire for a PWM where
firmware had enabled via CSR.EN but not PWM_EN — that's the exact
symptom PicoGUS hit. With `is_idle()` now derived from CSR.EN directly,
the slow path runs whenever any slice is actually running.
