# Journal: Pacer Wall-Clock Accounting + Overhead Calibration

**Date:** 2026-04-13
**Feature:** Fix pacer measurement bias + pre-compensate per-quantum overhead
**Status:** COMPLETE — 42/42 design items verified

## Problem

The pacer reported 146.2 MHz but the real rate was 135.2 MHz — an 8% bias.
Two causes, one underlying gap:
1. `emulated_mhz()` divided by `emulation_ns + spin_ns`, missing inter-quantum
   overhead (loop plumbing, atomic stats updates, rdtscp latency)
2. `quantum_tsc_ticks` was computed assuming perfect 1µs quanta, but real
   quanta took ~1.08µs, so we fit 925K quanta/sec instead of 1M

## Solution Shipped

1. **`wall_ns` tracking** — PacerStats gains an atomic cumulative wall-clock
   nanosecond counter. Updated each quantum from `final_tsc - first_begin_tsc`.
   Derived metrics (emulated_mhz, utilization, headroom) use wall_ns as
   denominator. `total_ns()` removed as a leaky abstraction.

2. **Overhead calibration** — `calibrate_overhead()` runs 5 batches of 2000
   no-op quanta (exercising the same atomic updates AND `tsc_to_ns` math as
   production) and returns the minimum measured overhead. Clamped to nominal/4
   to survive pathological calibration runs. Called from `with_quantum`;
   subtracted from nominal to get the final `quantum_tsc_ticks`.

3. **Three-tier verdict** — both `mhz_ratio >= 99%` AND `behind_rate < 0.1%`
   required for OK. Lowered thresholds (95% / 1%) for MARGINAL. Otherwise
   CANNOT SUSTAIN.

## Results (PGO + priority/affinity + wall_ns + calibration)

| Config | Reported | Actual | Gap |
|---|---|---|---|
| Plain release | 100.4 | 94.5 | 6% |
| PGO only | 124.3 | 114.5 | 8% |
| PGO + pin (pre-fix) | 146.2 | 135.2 | 8% |
| **Final (all fixes)** | **143.1** | **143.1** | **0% ✓** |

- **Measurement bias eliminated** — reported = actual
- **Overhead recovered ~8pp** — from 90% actual (pre-fix) to 95.4% actual
- **Verdict: REAL-TIME MARGINAL** — 95.4% of target, 0.08% behind
- **Remaining 4.6%** = 0.08% × ~55µs preemption events = residual OS noise

Honest MARGINAL rather than flattering OK — this is the right answer for the
hardware environment (laptop, Windows, HIGH not REALTIME priority).

## Deferred / Skipped

- **Max-stall tracking** (devil's advocate I4): the scenario raised (2-sec
  stall in 10-sec run) is already caught by the mhz_ratio criterion. Not a
  correctness gap; diagnostic nice-to-have.
- **In-quantum rdtsc sampling**: would let us separate "really emulating"
  from "preempted while notionally emulating". Adds hot-path overhead for
  marginal diagnostic value. Documented as a known upper-bound limitation in
  `utilization()`'s doc comment.
- **Thread affinity in core crate**: stays caller's responsibility. The
  paced_bench binary sets it via raw Windows FFI.
