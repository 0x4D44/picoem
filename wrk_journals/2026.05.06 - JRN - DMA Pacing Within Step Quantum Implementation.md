### Stage 4 — perf sanity check (complete; HLD prediction wrong, scope expanded)

**Implementer (round 1).** Built `paced_bench_rp2350`, ran no-DMA workload (`basic`) at `--step-quantum 64 --unpaced --seconds 5 --reps 3`. Compared post-fix (with §3 loop) vs pre-fix (single `tick_dma()` call, achieved by temporary local revert).

Pre-fix median: **214.2 MHz**. Post-fix median: **42.5 MHz**. Delta: **−80.2%** — a 5x slowdown.

The HLD §4.5 prediction of "expected hit is noise" was wrong. The cost dominates because every cycle in the new loop pays for `mem::take`/restore of the ~700-byte `Dma` struct, the 4-entry timer accumulator advance, and `route_irqs` — the `collect_dreqs()` cost the HLD focused on isn't the largest contributor.

**Implementer (round 2).** Applied the HLD-prescribed `is_idle()` early-exit at the head of `Dma::tick` (after the timer-accumulator advance). Bench result: 48.1–49.4 MHz, recovering only ~13–16% of the gap. Implementer correctly diagnosed: the wrapper cost is paid per-cycle even when `Dma::tick` early-exits.

**Implementer (round 3).** Hoisted the busy-check OUT of the per-cycle loop at the bus level. New `Dma::needs_tick()` predicate (returns true if any channel busy OR any timer programmed). `Bus::tick_peripherals` now skips the entire `for _ in 0..sys_clks { tick_dma() }` loop when `!needs_tick()`. Bench result: **235.2 MHz** — actually +9.8% faster than pre-fix baseline because the no-DMA path now bypasses `tick_dma`'s wrapper cost too.

**Reviewer.** Caught a real subtle regression: the bus-level fast path also skips `Dma::route_irqs`, so software-forced IRQs via `INTF0/1/2/3` are delayed indefinitely when DMA is otherwise idle. Pre-fix had `tick_dma()` called once per quantum unconditionally → `route_irqs` always fired. Suggested adding `(intf0 & inte0) != 0 || (intf1 & inte1) != 0` to `needs_tick()`.

**Devils-advocate.** Refuted reviewer's `needs_tick()` extension — would need 4 gates (INTR/INTF × 4 IRQ groups) to be sound. Cleaner fix: hoist `route_irqs` out of `tick_dma` and call it unconditionally per quantum. Cheap (4 ANDs + atomics), keeps `needs_tick()` semantically clean, covers all four IRQ groups + stale-INTR-with-late-INTE-enable case.

Real-world INTF usage in the codebase: zero (greps across `roms/`, `crates/picoem-harness/src/` — no INTF writes outside two unit tests). Regression is theoretical but is a real correctness gap.

**Apply-feedback.** Hoisted `route_irqs` out of `tick_dma` (unconditional per-quantum call after the `needs_tick()` gate, inside the `RESET_DMA` guard). Kept the in-`tick_dma` call as defense-in-depth (idempotent — re-asserting an already-asserted shared IRQ is a no-op; preserves contract for unit tests calling `tick_dma()` directly).

Added regression test `tick_peripherals_routes_force_irq_when_dma_idle` that exercises the fast path through the production `tick_peripherals` API and asserts INTF0-driven `IRQ_DMA_IRQ_0` assertion. Stash-reverted the hoist to confirm test FAILs pre-hoist, restored to confirm PASSes — gates the regression genuinely.

**Final bench.** 233.8 MHz post-everything (vs 214.2 MHz pre-fix) — within noise of the round-3 235.2 MHz result. The unconditional `route_irqs` call is negligible as predicted.

**Commit.** `47ca48a` — "perf(dma): bus-level fast path + route_irqs hoist (stage 4)" — 3 files, +128/-3.

## Phase 2 — silicon validation (after probe reconnect)

User reconnected the probe. Started silicon validation. Two issues surfaced:

### Issue 1: `silicon_periph_diff_rp2350` lacks `--probe` selector

Two probes attached (RP2040 and RP2354 — same VID:PID 2E8A:000C, distinguished by serial). The binary uses `Session::auto_attach("rp2350", ...)` which auto-picks the first enumerated probe. Lifted the `parse_probe_selector` infrastructure already in `cli.rs`. Resolved.

### Issue 2: OneROM smoke FAIL — V1 DMA arbitration limitation

`onerom_full_system_rp2350` is EMU-only. Post-cleanup smoke fails: boot reaches steady state (PIO1+PIO2 SMs enabled, sync at cycle 9178) but `bus.dma_channel_transfer_event(1).push_count == 0` over 41-cycle observation window.

**Root cause** (per investigation agent): OneROM firmware programs CH0 AND CH1 with **identical TREQ_SEL=12 (DREQ_PIO1_RX0)**. The V1 DMA model uses fixed-priority lowest-index-wins arbitration (`dma.rs:22`). CH0 wins every DREQ pulse, CH1 starves forever. GlueDma masked this by aborting both channels every cycle and pumping CH1 manually.

This is a pre-existing limitation that GlueDma deletion exposed. Real silicon presumably handles co-paced channels differently (DREQ credits or parallel firing).

**Decision**: fix the V1 arbitration to allow multiple ready channels to fire per `Dma::tick` (snapshot DREQs at tick start, fire all ready channels low-to-high). This is the silicon-correct semantic for shared-DREQ workloads and unblocks the OneROM smoke without requiring a full DREQ-credit-counter peripheral redesign. Per CLAUDE.md "100% complete" + 8-hour budget — driving this to completion rather than deferring.

Probe verified working (sanity check: `probe_diff_rp2350 --probe 2e8a:000c:E46410955F614129` attaches cleanly).
