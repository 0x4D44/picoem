### Finding 3 — trace sequence review

Pulled the first 350 µs of `monkey_island_theme.trace`:

```
0     ,0x343,0x4c,write8    select RESET reg
0     ,0x345,0x00,write8    data high = 0x00  → GUS_reset_reg=0
100000,0x343,0x4c,write8
100000,0x345,0x01,write8    data high = 0x01  → GUS_reset_reg=1
200000,0x240,0x40,write8    mixer
200000,0x24b,0x42,write8    IRQ / DMA selects
250000,0x240,0x00,write8
250000,0x24b,0x41,write8
300000,0x343,0x0e,write8    select reg 0x0e (NOT reset)
300000,0x345,0xda,write8    data high = 0xda  → reg 0x0e takes 0xda
300000,0x343,0x4c,write8    re-select RESET reg
300000,0x345,0x07,write8    data high = 0x07  → GUS_reset_reg=?
```

Revised hypothesis. The intermediate 0xda write goes to reg 0x0e,
NOT the reset reg. `GUSReset()` is only called when gRegControl ==
0x4c. So we have:
- p_GUS_reset_reg = 0x01
- gRegData after reg 0x0e = 0xda writes: high byte = 0xda, low byte
  unchanged (maybe 0)
- Then 0x4c selected, write high = 0x07 → gRegData = 0x0700
- GUSReset: GUS_reset_reg = 0x07. p & 1 = 1, new & 1 = 1, mask does
  NOT apply. GUS_reset_reg stays 0x07. ✓

So the sequence SHOULD correctly set GUS_reset_reg = 0x07, opening
the audio gate. But audio is silent.

This rules out the "DOS-classic two-step reset masking" hypothesis
from yesterday.

### Finding 5 — the mystery

**No byte in SRAM follows the expected `0 → 1 → 7` transition.**
Yet the PicoGUS source says `GUSReset()` should produce:

- after 0x00 write: `GUS_reset_reg = 0`
- after 0x01 write: `GUS_reset_reg = 0x01`
- after 0x07 write: `GUS_reset_reg = 0x07`

Source analysis re-verified at `gus-x.cpp:782-889`. Reset-exit mask
at line 868 only fires when `p & 1 == 0` OR `new & 1 == 0`; for our
transition `p=0x01, new=0x07` neither holds, so `GUS_reset_reg`
stays 0x07.

So either:
- GUS_reset_reg lives somewhere outside the 264 KB SRAM scan
  (unlikely — `static uint8_t` lands in `.bss`), OR
- Our emulator's firmware is not reaching that codepath even though
  the t=300000 event drove the right writes through PIO, OR
- Something else in the firmware overwrites `GUS_reset_reg` back to
  `0x01` between t=300 µs and t=2 s.

The 19 fresh 0x01 bytes at `--duration 0.00015` include stack
slots (0x20041E52..99) and a handful of `.bss`-like addresses.
Three survive into the full run at 0x01:
- `0x2001d60a` — candidate, but flat-lines at 0x01, never reaches
  0x07.
- `0x20040f46`, `0x20040f6a` — stack, holding pointer bytes.

### Finding 7 — the real bottleneck: PSRAM throughput

Scrolled the `--- PSRAM diagnostics ---` block in the harness
summary. Key numbers:

```
Non-zero bytes:    2032 / 8388608       (only 2 KB of PSRAM populated!)
CS# falling edges: 61304                (61k SPI frames started)
PIO1 SM3 TX:       push_ok=152984  push_drop=152955
```

**50 %+ of PSRAM PIO pushes are dropped.** The trace uploads ~103k
sample bytes via port 0x347 during the first 10 ms, but our PSRAM
bit-bang PIO can't keep up — the firmware's PIO TX FIFO overflows
and bytes get silently dropped.

`GUSChannels::generateSample` (`gus-x.cpp`) reads voice samples
out of PSRAM. If half the sample bytes never landed, voices
produce silence (or catastrophic garbage that `clamp16` turns
into zero). `GUS_reset_reg` could well be `0x07` — but with
empty sample memory, channels generate 0 regardless.

This matches the observed I2S behaviour:
- LRCLK edges tick regularly → DMA chain is alive, audio handler
  fires, `GUS_sample_stereo` returns a value every sample
- All samples are zero → voices have no data to replay

So the real fix isn't in the reset-reg analysis — it's our
emulator's PSRAM model being slow enough that PIO TX pushes
overflow. Either the PIO1 SM3 execution rate is modelled too
slowly, or the PSRAM SPI handshake is holding the TX side up.

### Finding 8 — PIO1 SM3 is the I2S output, not PSRAM

Cross-checking `sw/CMakeLists.txt:87`: `PICO_AUDIO_I2S_PIO=1`. So
PIO1 hosts:
- SM0: PSRAM SPI (429 k pushes, 0 drops — fine)
- SM3: I2S output (152 k ok, 152 k drop)

Revised interpretation. SM3's "drops" are `audio_sample_handler`
pushing zero-valued samples into the I2S TX FIFO faster than the
PIO can shift them out. The PIO drains at the sample rate; if the
handler runs at ~2× that, every other push overflows. These
drops are symptom, not cause — every push value is `0` because
`GUS_sample_stereo()` always returns `0`.

So the I2S drops don't corrupt audio (nothing to corrupt — all
zeros). They just confirm the handler is running relentlessly
against a silent source. PSRAM SM0 has 0 drops.

### Finding 9 — BREAKTHROUGH: GUS_reset_reg IS at 0x2001d60a

Made the `bytes_written` / `bytes_read` PSRAM counters public and
added them to the harness diagnostics. Without poking, `bytes_read
= 0` — the firmware never calls any channel's `generateSample`.
That's the smoking gun: **`GUS_sample_stereo`'s early-return is


|--------------|:----------:|

| `0x20040dcd` |     0      |
| `0x2001d60a` |    **459** |

`0x2001d60a` IS `GUS_reset_reg`. The other two 0x07 bytes are
some other variable that just happens to change the same way.

### Finding 10 — the real bug

Our observation at `--duration 2.0` was:
`0x2001d60a = 0x01` (NOT `0x07`)

Per the PicoGUS source at `gus-x.cpp:868`:

```c
if ((GUS_reset_reg & 1) == 0 || (p_GUS_reset_reg & 1) == 0) {
    GUS_reset_reg &= 1;
}
```

For the 0x07 write: `new = 7` and `p = 1` (the value of
`GUS_reset_reg` at entry after the prior 0x01 write). Both have
bit 0 set, so the mask should **not** apply and `GUS_reset_reg`
should stay 0x07.

But we observe 0x01 at end of run. Only way this happens is if
`p = 0` at entry to the 0x07 invocation — which means GUSReset is
being called with a STALE previous-value. The firmware code saves
`p_GUS_reset_reg = GUS_reset_reg` at function entry and reads
from the static variable. If the static's value has been
zeroed between calls (or never left 0 to begin with), the mask
applies and we land at `0x07 & 1 = 0x01`.

So either:
- Our emulator is running GUSReset with gRegData=0 somewhere
  extra between the 0x01 and 0x07 writes — dropping
  GUS_reset_reg back to 0 silently.
- Our emulator is running the GUSReset for the 0x07 write with
  stale register state for some reason.
- The compiler has inlined `GUS_reset_reg` into a register copy
  that's stale on the second call.

To isolate this would need either: (a) symbol-aware MMIO trace
for every GUSReset call, (b) rebuilt firmware with `LOG_MSG`
enabled.

+ 2 s extra post-roll. The poke survives the replay; during the
extra post-roll window the audio handler runs with the gate open
and should produce audible MIDI output from the already-
programmed voices.

Short-test probe (`--duration 2.0 --extra-postroll 0.1
--watch 0x2001d60a`):

```
[watch] total transitions: 0

Non-zero samples in WAV: 0
```

The poke sticks — **the byte is never written back during the
100 ms extra post-roll** (0 transitions). Gate stays open.
PSRAM DOES get read (459 bytes). Yet the WAV is still silent.

Interpretation. At `--duration 2.0` the trace only has reached
~5 ms of trace time (DRAM sample upload). No MIDI note-on events
have fired. All 14 GUS voices are still in post-reset "stopped"
state (WriteWaveCtrl bit 0 set by the full reset block at
`gus-x.cpp:810`), so `generateSample` short-circuits without
reading voice data even though the outer gate is open. The 459
reads are probably ramp/LUT table traffic.

The real test is full 30 s trace + `PICOGUS_REPOKE=1` + long
extra post-roll — programmed voices from later MIDI events
should then play when the gate opens. **Run pending.**

### Finding 13 — poke-during-replay breaks PSRAM writes

Added `PICOGUS_POKE_DURING_REPLAY=1` to apply the poke list
after every `advance_to_sim_ns` call during replay (so the gate
stays open as MIDI notes are being programmed). Expected this
to let voices play during the trace window.

Result — WORSE:

```
Bytes written:    0    (PSRAM got nothing!)
Bytes read:       0
cycles stalled at PC=0x19: 817460895   (PIO1 SM0 stuck)
```

Poking `0x2001d60a = 0x07` during replay **stops PSRAM writes
entirely**. PIO1 SM0 (PSRAM SPI) stalls at program PC 0x19 and
never advances. Hypothesis: `0x2001d60a` is aliased to something
in the PSRAM SPI state path (maybe a pin-number field inside the
`psram_spi_inst_t` struct, e.g. `pin_cs`), and setting it to
`0x07` changes the SPI routing so data never reaches the PSRAM
model. This is consistent with firmware having resolved pin_cs
into the PIO config at init — changing the struct field doesn't
affect the running PIO, but the PSRAM PIO program itself reads
from a different runtime path that IS affected.

So `0x2001d60a` is NOT unambiguously `GUS_reset_reg`. The
opening-the-gate behaviour we saw earlier (bytes_read jumping
from 0 to 459 with end-poke) must have a different explanation —
possibly the final trace write pattern combined with the poke
happens to produce a brief gate opening before firmware state
catches up.
