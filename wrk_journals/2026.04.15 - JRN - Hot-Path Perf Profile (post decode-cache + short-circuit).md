## Tooling pipeline

Windows 11 host, x86_64-pc-windows-msvc. `paced_bench_rp2350` built under a dedicated `profiling` profile (inherits `release`, `debug = 2`, `lto = false`, `strip = false`).

Path taken to get a useful profile:

1. **samply 0.13.1** — records cleanly (`paced_bench_rp2350 --unpaced --seconds 5 --workload basic` → `bench-basic.json.gz`, 36 KB, 5021 samples on the main thread). Matches the journal baseline within sampling noise — 99.9 MHz / 30.75 h/e vs. journal 101.4 MHz / 30.28 h/e.
2. **Symbol resolution — blocked.** samply's wholesym crate does not extract Rust function names from the MSVC PDB that rustc emits. Only 22 placeholder symbols (`fun_4944`, `fun_cb70`, …) across 238 sampled addresses in our exe. PDB is 2.24 MB and `strings(1)` finds zero Rust identifiers — samply's PDB reader isn't picking up the S_GPROC32 records. Known-limitation territory; not worth chasing.
3. **Pivot: cargo-flamegraph** — installed (`cargo install flamegraph`), but blondie errors with `NotAnAdmin` on Windows ETW access. Needs an elevated shell. Bounced.
4. **Pivot: pdbparse / pefile in Python** — construct (a pdbparse dependency) won't build on Python 3.14 (`imp` module removed in 3.12). Bounced.
5. **Pivot that worked: PDB RVA-range correlation + `llvm-objdump`.** samply's `--unstable-presymbolicate` emits a `bench-basic.json.syms.json` sidecar with the 22 extracted RVA ranges. Those ranges are real (they match compiler-emitted function boundaries), even though the names are placeholders. Correlating hot sample RVAs into those ranges groups the 5021 samples into tight buckets. Then `llvm-objdump -d --start-address=...` on each hot RVA identifies the function by its machine-level structure (register offsets accessed on `self`, jump tables, calls to known helpers).

## Hotspot distribution

**Three functions account for 94.8 % of samples.** Everything else is ≤ 1.5 %.

| Self-time | Size | Function (inferred) | Identifying evidence |
|---:|---:|---|---|
| **45.4 %** | 1330 B | `CortexM33::decode_execute` | `(pc >> 1) & 0x3FFF` cache slot compute at PC + 0x7c on `self`; `leaq (%rcx,%rcx,2)` picks the 12-byte `DecodedOp` stride; tag compare vs. PC; IT-state load at offset 0x159; 16-way condition-code jump table on xPSR |
| **32.0 %** | 4302 B | `CortexM33::execute_thumb16` | `cmpw $0x1c, %cx; ja <default>; movslq (%rdx,%rcx,4), %rcx; jmpq *%rcx` at 0xcb89 — the 5-bit `opcode >> 11` jump table. Size matches the match plus all inlined Thumb-16 handler bodies |
| **17.4 %** | 1062 B | `Emulator::step` | Three `tick_pio` calls at base offsets 0x568 / 0x7d4 / 0xa40 (stride 620 B = `PioBlock`, matches `pio: [PioBlock; 3]` on `Bus`); core-halted checks; event-flag / wake-check tail |

Sub-1 % entries (`fun_19e80`, `fun_13150`, `fun_1cb60`, …) trace through the same three hot callers. `fun_13150` is `tick_pio` itself at only 0.6 % self — its early-out on the per-block `enabled` flag is already skipping the real work when PIOs are idle. What remains in `Emulator::step` is the surrounding bookkeeping.

## Reading through the threading lens

**17.4 % in `Emulator::step` is a red herring for us.** It's per-iteration plumbing — contention setup, three `tick_pio` call-and-early-outs, event-flag / wake-check polling — that disappears once cores run in separate threads (each core calls its own `decode_execute`; `tick_pio` moves to its own thread; per-step interleaving goes away). Optimizing this sinks effort into a path scheduled for demolition. **Deprioritize.**

**45.4 % in `decode_execute` is where to focus.** Per-instruction dispatch overhead that survives threading unchanged. The disassembly shows the cache lookup + tag compare is already lean (~10-15 host cycles); the bulk is everything around it — IT/cond machinery, PC increment, `execute_thumb16` / `execute_thumb32` call boundary, cycle bookkeeping.

**32.0 % in `execute_thumb16` is the boundary.** The 5-bit `opcode >> 11` jump table is fundamentally lean at runtime — LLVM already lowers it to a single indirect jump. But the handler for a given decoded op is a **pure function of its bytes**, already resolved at cache miss. Re-dispatching on every hit is redundant work. Hoist the match to populate time and the 32 % shrinks by the cost of the jump table + the `execute_thumb16` function-call frame.
