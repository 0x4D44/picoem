# OneROM Full-System Oracle — Implementation Journal

Date: 2026-04-14
Parent design (to be written): `wrk_docs/2026.04.14 - HLD - OneROM Full-System Oracle.md`
Prior work: OneROM PIO Differential oracle (journal
`2026.04.14 - JRN - OneROM PIO Differential.md`) closed the PIO-engine
diff. This journal tracks the follow-up: run the real OneROM firmware
binary through our Cortex-M33 end-to-end and validate observable pin
behaviour.

## Ambition

Load a prebuilt OneROM `.bin` (likely
`onerom-fire-24-a-rp2350-test-sdrr-0.bin`) into our emulator's XIP
flash, boot through the RP2350 bootrom → second-stage → OneROM's
`main()` → clock / PIO / DMA init, reach a settled state, drive the
same CS + address stimulus the PIO oracle uses, observe the data byte
on the output pins. Either match a pre-captured trace (if we can
generate one from a reference) or at minimum prove the full stack
works (smoke test).

## Starting state

All Stage A–E work from the PIO differential oracle is committed
(in the working tree). That gives us:

- A clang-based `epio-sys` crate already wired up for vendored C.
- A PIO engine that agrees with `epio` on Piers' sample `setup_onerom`.
- A diff-harness pattern for PIO-level comparisons.

What we haven't tested: **any of OneROM's real firmware touching our
CPU.** The entire Phase 1–7 CPU emulator plus bus/flash/coprocessor
stack is about to get its first end-to-end workload.

## Open investigation — before the LLD

Three questions to answer before committing to a design:

1. **`.bin` contents.** Is it a raw XIP flash image (load at
   `0x10000000`)? Does it include the second-stage bootloader
   (the 256-byte block at the start of flash)? Is there a separate
   UF2 envelope?
2. **OneROM init footprint.** Which subsystems does `main()` touch
   before it enters its serving loop? Reading `sdrr/src/main.c` and
   `sdrr/src/rp235x.c` in the vendored repo should be enough to
   enumerate: clocks, GPIO bank, DMA config, PIO upload, wait for CS.
3. **Real OneROM PIO program vs Piers' sample.** Piers' own comment
   in `test/onerom_programs.h` says "Note that the latest One ROM
   algorithm may be different to this." That changes the oracle
   story — if the real firmware loads a different PIO program, the
   trace we already committed won't match cycle-for-cycle. Need to
   decide: regenerate trace, smoke-test-only, or stand up a
   lens-native reference.

### Investigation findings

- **`.bin` format.** Raw flash image. Word 0 = `0x20082000` (initial
  SP, SRAM top), word 1 = `0x100013A9` (Thumb reset vector). Standard
  ARM Cortex-M vector table at flash offset 0. No Picoboot IMAGE_DEF
  envelope (which is what the RP2350 bootrom would normally expect).
  458 752 bytes total.
- **OneROM init footprint.** `sdrr/src/main.c` (630 lines) boots a
  clock tree to 150 MHz or overclocked, configures PADS + IOBANK0,
  loads PIO programs *conditionally* (only when `FIRE_SERVE_PIO` is
  active — controlled by a build-time `RP_PIO=1` define or by
  runtime overrides), configures a 2-channel chained DMA, then
  enters `while(1) WFI;`. The test-fixture variant may default to
  **`FIRE_SERVE_CPU`** — CPU polls GPIO in a loop and writes data
  bytes directly, with no PIO/DMA at all.
- **Piers' sample vs real.** Confirmed the architectural shape
  matches (3 SMs + 2 chained DMAs), but the real bytecode differs.
  Handed off to the LLD as "Branch B" (smoke-test oracle).

### Bootrom bypass

First boot attempt got ~27 000 cycles into the real bootrom, then
PC fell to `0x00000028` — inside the bootrom's metadata block
(literally the string `"4 Raspberry Pi Ltd"`), not code. The RP2350
bootrom's secure-boot path rejects OneROM's raw-vector-table image
format and ends up in a fault state our emulator can't recover from.

Workaround (documented in LLD §9): skip the bootrom, read SP + PC
from the first 8 bytes of the `.bin` and load core 0 directly.
This is dirty but unblocks the rest of Stage F. A proper fix
would be to make our bootrom tolerate non-IMAGE_DEF images, or to
vendor a second-stage bootloader that loads the `.bin` on the
bootrom's behalf.

### Bug 7 — CLOCKS register layout was RP2040, not RP2350

After the bypass, PC settled into a tight loop at `0x10002072` /
`0x10002074`, polling a 32-bit register at `R1 + 0x44` for bit 1
to set. Disassembly:

```
0x2072: LDR R3, [R1, #68]
0x2074: LSLS R3, R3, #30        ; shift bit 1 to bit 31
0x2076: BPL -8                  ; loop until bit 1 set
```

Decoded the constant pool to find `R1 = 0x40010000` (CLOCKS block).
Offset `+0x44` on RP2350 is `CLK_SYS_SELECTED` — the register that
reflects which source is active for `CLK_SYS`. OneROM waits for PLL
to become the selected source.

Our `crates/mdrp2350/src/bus/peripherals.rs` had the RP2040 CLOCKS
layout: `CLK_SYS_CTRL=0x60 / DIV=0x64 / SELECTED=0x68`. The RP2350
adds GPOUT4–7 blocks before `CLK_REF`, shifting `CLK_SYS` earlier:
`CTRL=0x3C / DIV=0x40 / SELECTED=0x44`.

Fix: updated `clocks_read` / `clocks_write` in `peripherals.rs` and
all nine affected assertions across `crates/mdrp2350/src/tests.rs`
(`0x4001_0060/64/68` → `0x4001_003C/40/44`). 554 tests still pass.

### After the CLOCKS fix: OneROM boots to WFI

Second boot attempt gets past the CLK_SYS_SELECTED poll. PC settles
at `0x10001404` — disassembly reveals:

```
0x10001400: BL 0x10005090       ; (a very long branch — main or init call)
0x10001404: WFI
0x10001406: B 0x10001404        ; if WFI ever wakes, go back
```

CPU has finished its startup sequence and entered the "wait for
interrupts" loop. Init ran. CPU is idle.

### But PIO never got configured

Diagnostic dump at the cycle cap:

```
FINAL STATE:
  cycles      = 10 000 384
  core 0 pc   = 0x10001404
  PIO0.CTRL   = 0x00000000

PIO0 DIAGNOSTICS:
  CTRL       = 0x00000000
  FSTAT      = 0x0F000F00     (all TX empty, all RX empty — defaults)
  FLEVEL     = 0x00000000
  INSTR_MEM[0..8] all zero

CLOCKS DIAGNOSTICS:
  CLK_SYS_CTRL = 0x00000001
  CLK_SYS_SELECTED = 0x00000002   (PLL_SYS selected)
  sys_clk_hz (computed) = 150000000
```

CLOCKS is fully configured at 150 MHz. But PIO0 is entirely
untouched — zero instructions loaded, no SMs enabled, no FIFOs
populated. OneROM's firmware finished its init without ever
writing a PIO program.

Two likely causes:

1. **`FIRE_SERVE_CPU` mode.** `sdrr/src/main.c` defines
   `.fire_serve_mode = FIRE_SERVE_CPU` when `RP_PIO != 1` at build
   time. The `test-sdrr-0` variant may have been built without
   `RP_PIO=1`. Runtime overrides can also flip the mode based on
   `override_value[0] & (1<<4)` in the firmware metadata — that's
   where we'd need to dig next.
2. **Early exit via `limp_mode`.** If image-select pins aren't in a
   valid state (our GPIO input reads are zero / default), OneROM
   may fall through to a "limp" mode that blinks an LED but
   doesn't configure PIO. `sdrr/src/main.c:171` has
   `void limp_mode(limp_mode_pattern_t pattern)`.

### Current blocker

- a. Building OneROM ourselves with `RP_PIO=1` explicitly, producing

- b. Reading the shipped `test-sdrr-0` runtime_info struct at the

- c. Picking a different release `.bin` where the mode is known, or
- d. Building OneROM from source locally with `RP_PIO=1`.

## Trace-driven diagnosis session

After landing the LLD we dug into the WFI at 0x10001404 — suspecting
it was `FIRE_SERVE_CPU` mode, but Arthur called it for what it is:
an emulator bug we haven't exercised before. Verified by checking
`sdrr/src/rom_impl.c`: in `FIRE_SERVE_CPU` mode the CPU enters a
tight hand-written polling loop (`ALG1_ASM_UBFX` in
`sdrr/src/rom_asm.h`) that never terminates — no WFI, no returns.
If we're at WFI, main() must have *returned*, which the real code
never does.

### Per-instruction trace (step_quantum = 1)

Rebuilt the harness with `EmulatorBuilder::step_quantum(1)` so
`emu.run(1)` advances exactly one Cortex-M33 instruction (the new
quantum feature defaults to 64, hiding the per-instruction flow).
Enabled a dense 250-entry ring buffer covering the last cycles
before WFI.

The last 40 cycles tell the story cleanly:

```
cycle  7097  0x100013FE -> 0x10001400   ; reset-handler epilogue
cycle  7098  0x10001400 -> 0x10005090   ; BL main (or main's body)
cycle  7099  0x10005090 -> 0x10005092   ; LDR  R3,[R0,#0x2C]
cycle  7101  0x10005092 -> 0x10005094   ; LDRB R2,[R3,#0x14]
cycle  7103  0x10005094 -> 0x10005096   ; CBZ  R2,0x50BA  (not taken)
cycle  7104  0x10005096 -> 0x10005098   ; LDR  R1,[R3,#0x18]
cycle  7106  0x10005098 -> 0x1000509A   ; PUSH {R4,R5,R6,LR}
cycle  7111  0x1000509A -> 0x1000509C   ; MOV  R4,R0
cycle  7112  0x1000509C -> 0x1000509E   ; LDR  R0,[R1,#8]
cycle  7114  0x1000509E -> 0x100050A0   ; LDR  R0,[R0,#0]
...  (missing cycles — body of function runs)
cycle  7133  0x100050B8 -> 0x10001404   ; POP {R4-R6,PC} → return
```

The instruction at `0x100050B8` is `70 bd` = `POP {R4,R5,R6,PC}` —
a normal function epilogue. LR was `0x10001405` at entry (saved by
BL at `0x10001400`), so the POP pulls `0x10001405` into PC → the
core lands at `0x10001404`, the reset-handler's fallback WFI loop.

Register dump at the WFI confirms:

```
PC  = 0x10001404    SP  = 0x20081FF8
IPSR = 0x00000000   (thread mode — no exception in flight)
R0  = 0x00000002    R1  = 0x1000C100    R2  = 0x00000002
R3  = 0x1000C100    R4  = 0x10000200    LR  = 0x10001405
```

SP moved 8 bytes from its reset (`0x20082000 → 0x20081FF8`). Thread
mode, no fault.

XIP readback verified our bus serves the right instruction bytes
for the relevant PCs — `0x100050B8 = 0xBD70` matches the `.bin`.
Not a memory corruption.

### Conclusion

**main() runs ~7 000 cycles of init, calls deeply into many
sub-functions (the full-trace view shows jumps across ~20
functions in the `0x10001000`..`0x10005000` range), and then
returns cleanly via POP at `0x100050B8`.** On real hardware main
never returns — it enters the serving loop which loops forever.
On our emulator something in the init flow takes an early-return
branch that shouldn't be taken.

### Current unknowns — specifically, *which* function's conditional
is wrong

The trace shows main traversing ~20 distinct functions before it
returns. To localise the divergence we need to know *which*
intermediate function made the return decision. That is a matter
of:

- Dumping register state at each `BL` entry and each return, to
  see where a sub-call returns with an "error" sentinel that main
  treats as a hard stop.
- OR correlating each PC in the trace to source lines (would need
  OneROM's ELF/map file to resolve; the `.bin` alone only gives
  raw bytes).

A fast approach: build OneROM's firmware from source with map +
elf output, then tie the trace PCs to C source locations. That
surfaces the exact failing function in one pass. Alternative:
cross-compile `.bin` disassembly with `arm-none-eabi-objdump` and
grep for function symbols — but the shipped `.bin` has no symbol
table.

## Course correction — 2026-04-15

Before building OneROM from source I re-read the previous diagnosis
against the sdrr source (cloned from `piersfinlayson/one-rom` — that
is the upstream repo; `sdrr` is a subdirectory, not a standalone
repo as I'd initially searched for). Two load-bearing assumptions in
the earlier session were wrong:

### 1. main() returning is the *expected* behaviour

`sdrr/src/vector.c:173-184` reads:
```c
main();
#if defined(RP235X)
    // Main has returned - which means we are doing byte serving with PIOs.
    ora_launch_plugins(&sdrr_info);
    while(1) { __asm volatile("wfi"); }
#endif
```

Confirmed by `sdrr/src/piodma/piorom.c:2046` — in non-DEBUG builds
`piorom()` intentionally `return 0`s after kicking the PIO chain
off, control unwinds back through `main_loop → main → Reset_Handler`,
and the Reset_Handler's `while(1) wfi` *is* the terminal state.
There is no bug to find here — we'd been chasing the wrong ghost.

### 2. The trace window captured ora_launch_plugins, not main

The `dense` ring buffer was 250 entries. At the moment we stopped
on WFI (cycle 7137) the buffer covered cycles ~6888-7137 — i.e. the
tail end of execution. What looked like "main runs 34 instructions
and returns" was actually:

- cycle 2522 `0x100013FA → 0x100010C4`: BL main (main is at
  `0x100010C4`, not `0x10005090`)
- cycles 2522-7087: main runs ~4 500 cycles across ~20 functions
- cycle 7087 `0x1000121E → 0x100013FE`: return from main
- cycle 7098 `0x10001400 → 0x10005090`: **BL ora_launch_plugins**
- cycles 7099-7132: ora_launch_plugins runs ~34 cycles
  (checks `sdrr_info.metadata_header->rom_set_count`, finds no
  plugins, walks out)
- cycle 7133: POP `{R4-R6,PC}` → 0x10001404 (WFI)

The `LDR R3,[R0,#0x2C]` at the function entry the previous agent
thought was main is actually `info->metadata_header` (metadata_header
is at offset 0x2C in sdrr_info_t). The `LDRB R2,[R3,#0x14]` is
reading `metadata_header->rom_set_count` (per
`config_base.h:780-783`). With R0 = sdrr_info, this is
ora_launch_plugins, which does exactly that pointer walk at its
head.

### 3. Real OneROM uses PIO1 + PIO2, not PIO0

`sdrr/src/piodma/piorom.c:422-430`:
```c
#define BLOCK_ADDR    1   // PIO1 — address reader
#define BLOCK_DATA    2   // PIO2 — data writer / CS handler
#define BLOCK_MONITOR 0   // PIO0 — unused in typical serving mode
```

Our Stage F LLD §5 said "poll PIO0.CTRL on block 0". That only
ever matches the synthetic sample in `test/onerom_programs.h`, not
the real firmware. Real OneROM never touches PIO0 during ROM-serving
init.

### 4. INSTR_MEM readback is write-only

`crates/mdpicoem-common/src/pio/mod.rs:271-272`:
```rust
// INSTR_MEM0-31: write-only
0x048..=0x0C4 => 0,
```

RP2350 / RP2040 datasheet behaviour. Harness diagnostics reading
INSTR_MEM[0..8] via `pio[n].read32(0x048 + i*4)` will always see
zeroes, even when the underlying storage is populated. Added
`pub fn instr_mem(&self) -> &[u16; 32]` to `PioBlock` as a debug-only
accessor so the harness can verify program loading.

### Instrumented harness — periodic state sampler

Added a 16-cycle-interval periodic snapshot of (RESETS, PIO0/1/2
CTRL, PIO0/1/2 INSTR[0], CLK_SYS_CTRL, CLK_SYS_SELECTED). Logs diff
events tagged with cycle + PC. This produced the crucial run log:

```
cycle  2560  pc=0x1000151A  RESETS      0x1FFFFFFF -> 0x1FFFFEFF  (bit 8 = JTAG)
cycle  2576  pc=0x10001C10  RESETS      0x1FFFFEFF -> 0x1FFFFCBF  (+ bits 6 IOBANK0, 0 ADC)
cycle  5440  pc=0x1000202A  RESETS      0x1FFFFCBF -> 0x1FFFBCBF  (+ bit 14)
cycle  5520  pc=0x10002078  CLK_SYS_CTRL/SEL → 0x01 / 0x02 (PLL_SYS selected)
cycle  5584  pc=0x10004C4A  RESETS      0x1FFFBCBF -> 0x1FFFBCBB  (+ bit 2 DMA)
cycle  6432  pc=0x100038AE  RESETS      0x1FFFBCBB -> 0x1FFF84BB  (+ bits 11 PIO0, 12 PIO1, 13 PIO2)
cycle  7072  pc=0x1000121A  PIO1.CTRL   0x00 -> 0x01  (SM0 enabled — address reader)
cycle  7072  pc=0x1000121A  PIO2.CTRL   0x00 -> 0x03  (SM0+SM1 enabled — data writer)
```

### Final PIO state after boot

```
PIO1 (BLOCK_ADDR):
  CTRL  = 0x01
  FLEVEL = 0x40  (RX0 level = 4 words — SM is running and pushing)
  INSTR[0..1] = 4230 4010  (address reader bytecode)

PIO2 (BLOCK_DATA):
  CTRL  = 0x03
  FLEVEL = 0x00
  INSTR[0..6] = A063 A020 0041 A06B A020 0024 6008

PIO0 (BLOCK_MONITOR):
  All-zero. Expected — OneROM doesn't use PIO0.
```

The PIO2 program fragment matches several instructions from the
synthetic `setup_onerom` trace we committed (`A063 A020 0041 A06B
A020 0024`), confirming the real firmware uses the same control
pattern for the data-serving SM. PIO1's `4230 4010` is the address-
reader half that was also in the synthetic sample (`0x4230 0x4010`);
Piers' real design splits the algorithm across two blocks instead
of consolidating on one.
