## Goal

Close out the three open bug classes the Stage G serving oracle surfaced on
2026-04-15:

1. **4 × WrongByte** — walking-1 A0–A3 cases resolve in-shadow but PIO2
   returns `0x00` instead of the SDRR permutation bytes `0x01/0x02/0x04/0x08`.
2. **2 × AddrOOR** — walking-1 A8/A9 (addr=0x1900, 0x1A00) resolve to
   `0xB0002000`, outside the 64 KB shadow. Suspected PIO1 shift/byte-swap.
3. **9 × LatencyOutOfEnvelope** — 3–10 cycles observed vs the 11–14 cycle
   envelope `piorom.c` documents. Known emulator-bounded caveat; may shift
   once #1 and #2 are fixed.

End state: `onerom_serving_oracle_rp2350` reports a meaningful sweep where
- WrongByte verdicts reflect real byte-pipeline failures (not empty-SRAM
  false zeros);
- AddrOOR verdicts are gone (or reduced to a single cleanly-diagnosed case);
- LatencyOOE either falls inside the envelope or is documented with a
  concrete structural reason.

## Starting hypothesis (to confirm / falsify Phase A)

**H1 — byte-pipeline empty-SRAM** (supervisor's leading theory):
- Stage G shadow is lifted from flash-parsed SDRR → lives in oracle memory.
- Glue DMA CH1 reads from emulator **SRAM** at the resolved address.
- `preload_rom_image` DMA is stubbed on mdrp2350 — SRAM stays zero.
- Net: every CH1 byte read returns `0x00`, producing the uniform-zero
  serving pattern.
- Candidate fix: have the harness memcpy the flash-parsed shadow into
  emulator SRAM at sync (the "memcpy workaround" — emulates what the real
  preload DMA would have done). 5-line fix, unblocks all 13 non-AddrOOR
  cases.

**H2 — PIO1 high-bit shift artifact (AddrOOR):**
- A8/A9 stimuli set high-order address bits the other walking-1 cases
  don't. PIO1's IN PINS / OSR shift produces `0xB0002000` consistently.
- Orthogonal to H1. Wait until H1 is resolved so we can see if more cases
  leak into AddrOOR or if the 2 known ones are the full set.

**H3 — LatencyOOE:**
- Partly emulator-bounded (documented in HLD §5.4).
- May shift once H1 lands; probably still out of envelope. Treat as
  last-priority; may require structural work or a caveat update.

**Bisect evidence:**
- `a8a2ef5` (Stage G tip): 0 / 4 WB / 2 AOOR / 9 LOOE / **0 NR** — confirms
  Stage-G pattern exists.
- `82d2f43` committed-only: 0 / 4 WB / 2 AOOR / 9 LOOE / **0 NR** —
  identical. No committed PIO change caused the regression.
- Full dirty tree: 0 / 0 / 0 / 1 / **14 NR** — regression reproduces.
- Dirty tree with only `dma.rs` reverted: Stage-G pattern returns.

**Culprit:** uncommitted `crates/mdrp2350/src/dma.rs` (+121/-15). It is a
correct V6 CTRL bit-field fix that adds RP2350's `INCR_READ_REV [5]` and
`INCR_WRITE_REV [7]` and shifts `INCR_WRITE`, `RING_SIZE`, `RING_SEL`,
`CHAIN_TO`, `TREQ_SEL`, `IRQ_QUIET` each up by 2 bits.

**Mechanism:** The OneROM oracle's glue DMA constructs CH0 CTRL words
with literal RP2040-style bit positions. Under the corrected V6 layout
those values now decode to wrong `CHAIN_TO` / `TREQ_SEL` fields — CH0
never chain-triggers CH1 on the correct target, or it waits on a bogus
DREQ. PIO1 therefore never pushes → CH0 never forwards → CH1.READ_ADDR
stays stale → glue returns NoResolve.

**Important:** the dma.rs change is correctness-positive. The fix is
updating the OneROM oracle to the new layout, NOT reverting dma.rs.

### Phase A2 — Realign OneROM CTRL layout (complete)

Implementer agent pushed back on the supervisor framing — correctly. The
harness does NOT construct CTRL words in the production path. `GlueDma`
is a software pump that *observes* firmware-written CTRL_TRIG via
masked readback. Firmware uses V6 positions natively.

**Actual root cause (restated):**
- Pre-V6: emulator misdecoded firmware's `TREQ_SEL=12` (DREQ_PIO1_RX0)
  as `TREQ_SEL=48` (DREQ_ADC, never asserts) → real DMA idled on
  CH0/CH1 → glue pump had exclusive ownership → Stage-G pattern.
- Post-V6: emulator correctly decodes `TREQ_SEL=12` → real DMA races
  the glue pump for PIO1 RX drainage → pump starves → 14 × NoResolve.

**Fix:** `GlueDma` issues a `CHAN_ABORT` for `GLUE_DMA_CHAN_MASK` (CH0 |
CH1) at both (a) `prime_after_sync` entry (closes the first-tick window
where `emu.run(1)` would otherwise consume a DREQ before abort lands)
and (b) every `tick()` head. This keeps the real DMA's `BUSY` clear on
the two glue-owned channels without touching mdrp2350.

**Test:** new regression test in `onerom_glue_dma.rs` programs CH0 with
FORCE TREQ, runs emu+glue alternately for 32 sysclks under the
production driver pattern, asserts `trans_count` unchanged and BUSY
stays clear. Also pins V6 CTRL bit layout via
`assert_eq!(ctrl, 0x007E_0059)` — any future dma.rs bit-layout shift
lights up this test with a specific expected-vs-actual value.

Review cycle (code-reviewer skill):
- Verdict: REQUEST CHANGES, one SHOULD-FIX.
- SHOULD-FIX: production driver runs `emu.run(1)` before `tick()`;
  first tick would have leaked one real-DMA transfer per re-arm. Fix:
  move/mirror the abort into `prime_after_sync` too.
- Apply-feedback landed cleanly: un-underscored `bus` in
  `prime_after_sync`, added the abort write, restructured the
  regression test to mirror the production driver pattern exactly
  (prime → run/tick loop with no pre-loop `dma.tick` papering).

**Validation:**
- `cargo test -p mdpicoem-harness --lib`: 312/312 green.
- Oracle sweep post-apply: **0 PASS / 5 WrongByte / 2 AddrOOR /
  8 LatencyOOE / 0 NoResolve**. NoResolve regression fully cleared.
- Stage G reference was 0/4/2/9/0. A5 (walk1, addr=0x1820) shifted
  LatencyOOE → WrongByte; reviewer called it strictly-more-informative

### Phase E — LatencyOOE triage (complete, option E.1)

Plan agent triaged all 8 LOOE cases against `/tmp/onerom_post_d2b_applied.txt`. Composition:

- **7 × (a) coincidental-zero false-LOOE.** Cases 1, 2, 4, 9, 10, 14, 15.
  All have `resolved == 0x2000_B000` (the D.1 gpio-latency collapse
  sink) AND `shadow[collapse_sink] == 0x00` AND `observed == 0x00`.
  Byte match is coincidental because the *stimulus* never reached
  PIO1 correctly (D.1 escalation); shadow happens to be zero at the
  collapse sink. Cycles clamp at `MIN_FRESH_ARRIVAL_CYCLE=8` (floor)
  or run longer on residual stale bytes (A2 cycles=20 is a variant
  of this, not a genuine latency measurement).
- **1 × (b) genuine emulator-bounded below-envelope.** Case 5 (A3)
  resolves to `0x20009020` (correct in-shadow), serves `0x04`
  (correct byte), latency `9` cycles — 2 cycles under the 11..=14
  envelope. Root cause: `onerom_glue_dma.rs` models a minimal 4+4
  DMA pipeline but does NOT model PIO2 SM1's `OUT PINS, 8` shift
  or pad-out propagation cycles. Extending the glue DMA to
  cycle-accurate PIO2 timing is multi-day work, outside this
  wave's scope. **This is exactly the HLD §5.4 "emulator-bounded"
  caveat** — documentation, not a bug to fix.

**Disposition: E.1 (accept and document).** Rejected E.2 (new
`CoincidentalZeroMatch` verdict) as premature — the collapse sink
0x2000_B000 disappears post-D.1, making the heuristic dead code
for the wrong reason. Rejected E.3 (fix A3's 1-2 cycle gap) as
out-of-budget — requires cycle-accurate PIO2 modelling.

No code changes in Phase E. This journal is the documentation
artefact; the Stage G HLD §5.4 caveat already covers the class.
