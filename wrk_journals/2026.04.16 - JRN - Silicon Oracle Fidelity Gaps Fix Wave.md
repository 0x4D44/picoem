### A-PWM report (completed, 2026-04-16 ~17:55 UTC)

**Brief correction from the agent:** 0x400A_8008 is `PWM_SLICE0_CTR` (counter), not CH0_CSR. The observable mask 0x64 was decimal 100 — the "ctr should be 100 after N sysclks" assertion. My brief's bit-layout interpretation was wrong; agent recognised and re-framed. Noted — will propagate correction to devil's advocate briefing.

**Root cause:** Phase 3.2 fractional accumulator had divisor direction inverted. RP2350 CH_DIV is a divisor: counter advances at `sys_clk / divisor`. The old code computed `advance = INT × cycles` (multiplies — counter ticks = divisor × sys_clks). Fix: `advance = (frac_accum + cycles × 16) / divisor` with `divisor = raw 12-bit INT*16+FRAC` from the DIV register. For DIV=0x0010 (INT=1, divisor=1.0) multiply and divide happen to agree, which is why all existing unit tests using DIV_RESET passed and masked the bug.

**Files changed:** `crates/mdrp2350/src/peripherals/pwm.rs` lines ~328–338 (formula swap) and lines ~520–535 (new test). PWM module path = `src/peripherals/` not `src/bus/` — confirmed.

**New test:** `peripherals::pwm::tests::fractional_div_integer_2_advances_at_half_rate` — mirrors scenario (TOP=0xFFFF, DIV=0x0020, EN=1), asserts CTR=100 after 200 sys_clks.

**Test verdict:** `cargo test -p mdrp2350 --lib` → 890 pass, 0 fail, 2 ignored.

**Notes flagged:**
- Changed `frac_accum` semantics: was 0..15 (4-bit fraction residue), now 0..(divisor-1). Uses u16, safe to divisor=0xFFF.
- `cycles × 16` overflow guard: safe for cycles < 268M per `tick()` call (step_quantum in practice ≤ 64).

### A-PIO report (completed, 2026-04-16 ~18:15 UTC)

**Major finding:** RP2350 and RP2040 have different PIO INT register offsets. Phase 4 (commit `8bb7614`) implemented the INT block at RP2040 offsets (INTR 0x128, IRQ0_INTS 0x134) in the shared `PioBlock` — wrong for RP2350.

RP2350 authoritative layout (datasheet Table 1016):
- 0x134 = `RXF0_PUTGET3` (FIFO debug — absent on RP2040)
- 0x16C = INTR
- 0x170 = IRQ0_INTE
- 0x174 = IRQ0_INTF
- 0x178 = IRQ0_INTS
- 0x17C = IRQ1_INTE
- 0x180 = IRQ1_INTF
- 0x184 = IRQ1_INTS

Extra RP2350 registers (16 × RXFn_PUTGET + GPIOBASE) push the INT block 68 bytes later. Also: RP2350 INTR bit layout is IRQ flags at [15:8], TXNFULL [7:4], RXNEMPTY [3:0] — not `<< 0` like RP2040.

## Stage A — review wave

### Review: A-SIO (completed, 2026-04-16 ~18:20 UTC)

Reviewer confirmed register offsets against datasheet (MTIME map correct, core-local MTIMECMP correct). Three non-trivial findings:

**CRITICAL** — RISCV_SOFTIRQ is a split SET/CLR register per Table 79: bits [1:0] are SET (write-1-to-set), bits [9:8] are CLR (write-1-to-clear). Current implementation applies `|= val & 0x3` and silently drops any write to bits 8/9. Firmware writing bit 8 to clear a latched flag gets a permanently stuck interrupt. **The A-SIO agent flagged this as "deferred" but it's actually a functional silicon divergence that must be fixed before commit.**

**HIGH** — DIV_CSR still echoes a live DIRTY bit at 0x078. If silicon truly reads 0x00 across the reserved 0x060–0x078 range (RAZ per ARM bus fabric convention and the scenario's HW=0x00 reading), then the backing-store DIRTY echo is wrong. Reviewer flags this as "architecturally unsound — reserved means RAZ/WI". Needs Arthur's call: RAZ the whole range or keep the partial echo. Scenario evidence favours full RAZ.

**MEDIUM** — MTIME_CTRL reset value per Table 80 is `0xF` (EN=1 + DBGPAUSE_CORE0=1 + DBGPAUSE_CORE1=1 + DBGPAUSE_CORE0_NS=1). Emulator inits to 0, meaning MTIME is disabled at reset until firmware writes it. This is a real gap — firmware that reads MTIME without writing first gets silicon-divergent behaviour.

**LOW** — no cold-read assertion for DIV_CSR post-reset. Add one to prevent regression of the "nonzero at init" pattern.

**Must-fix punch-list for apply-feedback:**
1. Implement RISCV_SOFTIRQ write-to-clear via bits [9:8] (+ test).
2. Drop DIV_CSR.DIRTY from 0x078 read arm (strict RAZ across 0x060–0x078).
3. Fix `mtime_ctrl` init/reset to `0xF`.
4. Add cold-read test for DIV_CSR post-reset.

**Questions for Arthur** (may be answered without silicon access):
- Silicon reads across 0x060–0x078: all-RAZ or just 0x078? Current scenario tests only 0x078 with mask 0x3. Reviewer recommends strict RAZ.
- Silicon trace for RISCV_SOFTIRQ CLR bit 8: not available from existing scenarios.

### Review: A-PWM (completed, 2026-04-16 ~18:25 UTC)

Formula verified mathematically correct. One blocker + test coverage gaps.

**BLOCKER** — `frac_accum` is NOT reset when firmware rewrites `SLICE_DIV`. Mid-run `CH_DIV` reprogramming (common for PWM frequency sweeps) can leave a stale residue valid under the old divisor but illegal (>= new divisor) under the new one, causing a phantom counter advance on the next tick. Concrete example from the reviewer: old div=51, `frac_accum`=49 residue. New div=32 → first 1-cycle tick computes `(49+16)/32 = 2`, but a fresh accumulator would give `(0+16)/32 = 0`.

Fix: one-line change in `SLICE_DIV` write handler — `self.slices[slice].frac_accum = 0` alongside the `div` assignment.

**Test gaps** (not BLOCKER but worth closing):
- No fractional-divisor test (INT=3, FRAC=3 — divisor=3.1875). Regressors that round wrong on non-integer divisors still pass current tests.
- No DIV=0 "counter stops" unit test. Guard is present; no regression pin.
- No mid-run CH_DIV reprogram test — would double as the blocker's regression test.

**Must-fix punch-list for apply-feedback:**
1. Reset `frac_accum` on SLICE_DIV write.
2. Add mid-run CH_DIV reprogram test (doubles as regression guard).
3. Add fractional-divisor test (INT=3, FRAC=3).
4. Add DIV=0 no-panic test.

**Open question for Arthur:** Do `SLICE_CTR` writes (firmware preloading the counter) also flush `frac_accum`? Silicon-accurate behaviour unclear; reviewer flagged as unknown.
