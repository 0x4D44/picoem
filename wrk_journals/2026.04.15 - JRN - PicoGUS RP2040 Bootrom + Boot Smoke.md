## Log

### 2026-04-15 09:00 — diagnosis

Reproduced the stall at cycle 8209. Confirmed root cause by static
analysis + tracing:

1. `mdrp2040::Emulator::reset()` reads SP from ROM[0] (`0x20042000`)
   and the reset vector from ROM[4] (`0x10000001`), then sets PC to
   the flash base (boot2's first instruction, `PUSH {LR}`).
2. LR is initialised to 0 in our `Registers::new()` (real silicon
   starts LR=0xFFFFFFFF; either way the value is not a valid return
   address for boot2).
3. boot2 executes cleanly for ~8200 cycles — it configures XIP_SSI
   as expected, no decode bugs. At the end, `POP {PC}` pops the bogus
   LR we pushed.
4. PC lands in the synthetic bootrom's data words (SP + reset vector
   at ROM offsets 0/4), which happen to decode as benign Thumb
   instructions, then falls through to the ROM-wide `B .` trap
   halfwords. Both cores end up stuck in the self-loop at a fixed
   address; the cycle counter freezes because nothing else is driving
   the bus.

Diagnosis confirms the tech-debt hypothesis — missing real bootrom.
Fix path is Option 1 (vendor `b2.bin`).

### 2026-04-15 10:00 — --bootrom works; bootrom drops firmware into USB MSC

Harness runs now advance past the cycle-8209 stall. Final-cycle count
jumps from 8209 (pre-bootrom) to 6.4 M (post-bootrom), a ~785× increase.
But I2S output still silent.

Probed PC trajectory. Firmware settles in the bootrom's `async_task_worker`
at `0x20d8` — the USB MSC idle loop. Tracing why:

- Bootrom `main()` at `0x24d0` samples `SIO.GPIO_HI_IN` (offset `0x008`)
  9 times to detect whether an RP2040 QSPI flash chip is attached:
  it shifts right by 1 (QSPI_SS bit) and counts. If ≥ 5 samples have
  SS high, it proceeds with flash boot; otherwise → USB MSC.
- Our `mdrp2040::bus::sio::read32` returns 0 for offset `0x008` (no
  QSPI pad model). Result: bootrom always enters USB MSC.

Ways forward:
1. Model the QSPI pads + minimum SSI commands (JEDEC ID, READ) so the
   bootrom's detection + boot2 CRC validation actually pass. ~2 hours.
2. Skip the bootrom boot flow — direct-boot into firmware's own reset
   handler at `flash+0x104`. Keeps the ROM function table available
   (so `rom_func_lookup` resolves), bypasses the flash-detect stall.
   Standard emulator shortcut. ~15 minutes.

Chose option 2. Added `Emulator::direct_boot_from_flash(vtor_offset)`
to `mdrp2040` lib (sets SP/PC on both cores from the vector table)
and invoked it from `picogus_diff_rp2040` after `reset()`.

### 2026-04-15 10:30 — firmware boots past init, then panics

Direct-boot works: PC immediately enters the firmware's reset handler
at `0x100001F6`, executes the standard pico-sdk `.data` copy loops
(14k+ iterations), zero-fills BSS, and calls three runtime init
functions (`blx r1`).

Within the first runtime call (`0x20000110`), firmware executes ~21500
instructions and then takes an exception. Exception entry: PC jumps to
bootrom's `_dead` at `0x30`, LR=`0xFFFFFFF9` (EXC_RETURN handler+MSP).
Traced the fault: firmware hit `BKPT #0` at `0x200035ac` after
`bl 0x20000298` — which matches a pico-sdk `panic()` pattern. Decoded
the panic format string: **"hardware alarm %d already claimed"** with
`r0=1` passed as `%d`.

This is firmware's own assertion in `hw_claim_or_assert()`. Possible
causes:
- BSS not fully zeroed (our zero-fill only covers 0x3EC bytes from
  0x20004018 to 0x20004404 — rest of BSS relies on SRAM-starts-zero,
  which we provide via `vec![0u8; SRAM_SIZE]`).
- Firmware claims alarm 1 twice in setup (unlikely).
- A peripheral register our emulator stubs incorrectly feeds
  non-zero into the alarm-claim logic.

Tried BKPT-as-NOP: firmware sits in `B .` after the bkpt (deliberate
halt loop after panic). No forward progress.

### 2026-04-15 11:00 — pivot: hand-crafted I2S test firmware

Debugging the PicoGUS-specific panic is a rabbit hole (no symbols, no
source visibility into call chain above the panic). Arthur's acceptance
is "produce some sort of startup chime" — which we can meet more
reliably by writing a small hand-crafted firmware that drives I2S
directly, bypassing the pico-sdk runtime entirely.

Plan (revised, simpler than original):
1. Keep BKPT reverted to HardFault.
2. Add `roms/rp2040/gen_i2s_chime.py` analogous to `gen_blinky.py`:
   generates a 60-byte Thumb-16 program that toggles GPIO 16/17/18 via
   SIO writes to produce a BCLK/LRCLK/DOUT waveform. Pairs with the
   synthetic `bootrom.bin` layout.
3. Wire direct-boot to detect "not an SDK vector table" and skip, so
   our synthetic bootrom's reset-vector boot path still works for
   hand-crafted flash images.

### 2026-04-15 11:30 — chime firmware works end-to-end

- `roms/rp2040/gen_i2s_chime.py` generates `i2s_chime.bin` (60 bytes)
  and a companion `bootrom-i2s-chime.bin` (16 KB synthetic stub).
- Updated `picogus_diff_rp2040` direct-boot path: now checks that
  `flash+0x100` contains a plausible SDK vector table (SP in SRAM,
  PC in flash). Skips direct-boot when not present, letting the
  synthetic bootrom boot via `flash+0x000`. Preserves both boot
  paths — SDK firmware and hand-crafted.
- Result: harness run with chime firmware produces a non-empty WAV.
  32 stereo frames, 64 LRCLK edges. Sample inspection:
  ```
  #0: L=     0  R=    -1
  #1: L=    -1  R=    -1
  #2: L=    -1  R=     0
  #3: L=     0  R=     0
  #4: L=     0  R=    -1
  ...
  ```
  Pattern repeats with period 4 (derived from bit 2 of the half-frame
  counter → slow square wave). 24 of 32 frames non-zero.
