# M33 PRIMASK / BASEPRI / FAULTMASK Primer Extension — 2026-05-02

Working journal for extending the QEMU M0+ PRIMASK-reset primer pattern to
the M33 oracle (`qemu_diff_m33.rs`).

## Context

The 8h overnight fuzz campaign (2026-05-01) generated ~24 000 deterministic
`FUZZ:M0PLUS_T32_MRS` FAILs across 12 batches of `qemu_diff_m33`, all from
the same QEMU-side persistence-across-single-step issue:

- QEMU's CPU state persists across `gdb step` calls.
- The EMU side rebuilds a fresh `CortexM33::new()` per test (PRIMASK=0).
- An earlier test that did `MSR PRIMASK, Rn` with Rn != 0 leaks PRIMASK=1
  into a subsequent test's `MRS Rd, PRIMASK`, producing a deterministic
  diff.

The WIP author already shipped a fix on the M0+ side
(`crates/mdpicoem-harness/src/bin/qemu_diff_m0plus.rs`):

- `QEMU_M0PLUS_PRIMER_SLOT` at `0x2000_0080` in lib.rs
- `PRIMER_BYTES` = `[0x80, 0xF3, 0x10, 0x88]` — `MSR PRIMASK, R0` Thumb-32
- `setup_vector_table` writes it once.
- `run_qemu_side` steps it before each test (with R0=0 from defaults),
  then applies per-test register overrides, then re-aims PC at the test
  slot and steps the actual instruction.

The same family also produces a `MRS R1, BASEPRI` (sysm=17) divergence on
the M33 side — flagged in the campaign journal but not chased there.
Today's fix extends the primer to also reset BASEPRI and FAULTMASK so both
baselines collapse together.

## Plan

1. Add `QEMU_M33_PRIMER_SLOT` constant in `crates/mdpicoem-harness/src/lib.rs`.
   Park it inside the M33 vector-table region at `0x1000_0080` — same
   "in the IRQ-vector reservation" choice as the M0+ side.
2. In `qemu_diff_m33.rs`:
   - `PRIMER_BYTES` = 12 bytes = three back-to-back Thumb-32 MSR instructions
     (PRIMASK, BASEPRI, FAULTMASK). All operate on `R0` (which is 0 from
     the per-test default reset).
   - `setup_vector_table` writes the primer.
   - `run_qemu_side` steps the primer 3 times before applying per-test
     register overrides; then re-aims PC at `QEMU_TEST_SLOT` for the
     actual test step.
3. `cargo build --release -p mdpicoem-harness`, copy binary to a fuzz-runs
   path so concurrent rebuilds don't trip on the live binary.
4. Smoke: `--fuzz 1000 --classes=base`. Expect `M0PLUS_T32_MRS` FAILs to go
   from ~6.6 % to ~0.
5. Confirmation: `--fuzz 5000 --classes=base`, log to journal.
6. Final summary.

## Encoding notes

ARMv8-M Thumb-32 `MSR Sn, Rn` encoding (B5.4.6 / T1):
- `1111 0011 100s rrrr 1000 mmmm ssss ssss`
  - hw0 = `0xF380 | (Rn << 0)` ... actually full layout:
    `hw0 = 1111 0011 100(S) Rn` with S = secure-write flag, Rn = source reg.
  - hw1 = `1000 1111 SYSm[7:0]` — top nibble fixed `0x88` for the standard
    "no mask, write all" case, `SYSm` selects the special register.
- For our R0 source (Rn=0), hw0 = `0xF380`. Little-endian bytes: `0x80, 0xF3`.
- hw1 selectors:
  - PRIMASK: SYSm = 16 → hw1 = `0x8810` → bytes `0x10, 0x88`
  - BASEPRI: SYSm = 17 → hw1 = `0x8811` → bytes `0x11, 0x88`
  - FAULTMASK: SYSm = 19 → hw1 = `0x8813` → bytes `0x13, 0x88`

So PRIMER_BYTES (LE):
- PRIMASK:   `0x80, 0xF3, 0x10, 0x88`
- BASEPRI:   `0x80, 0xF3, 0x11, 0x88`
- FAULTMASK: `0x80, 0xF3, 0x13, 0x88`

Total 12 bytes, 3 single-step calls.

## Risk check

- `MSR PRIMASK/BASEPRI/FAULTMASK, Rn` on ARMv8-M B5.2 doesn't update APSR,
  so `xpsr_pre` survives the primer. (Same property used by the M0+ primer.)
- Privilege: at reset / cold register state, CPU is privileged Thread mode,
  which is allowed to write all three. The default `tc.xpsr_pre` doesn't
  set IPSR or any mode bits.
- M33 oracle has multi-step tests (`tc.opcode2.is_some()` → 2 steps; FPU
  builds variable-length sequences). The primer adds 3 fixed steps before
  whatever the test does; `n_steps` accounting in `run_qemu_side` is for
  the test itself and is unaffected.
- VTOR / vector table: M33 oracle writes the vector table at
  `VECTOR_TABLE_BASE = 0x1000_0000` (only SP + reset). `0x1000_0080` falls
  inside the architectural vector-table reservation but the M33 oracle
  never raises an IRQ that would dispatch through that slot, so it's free
  for our primer code.

## Timeline

### Code changes (T+0)

- `crates/mdpicoem-harness/src/lib.rs`: added
  `pub const QEMU_M33_PRIMER_SLOT: u32 = 0x1000_0080;` next to the M33
  test-slot/scratch/stack constants, with a doc-comment mirroring the
  M0+ counterpart.
- `crates/mdpicoem-harness/src/bin/qemu_diff_m33.rs`:
  - `PRIMER_BYTES: [u8; 12]` and `PRIMER_STEPS: usize = 3` constants.
  - `setup_vector_table` now writes the primer to `QEMU_M33_PRIMER_SLOT`
    after writing the SP/reset vector and the CPACR enable.
  - `run_qemu_side` now sets `PC = QEMU_M33_PRIMER_SLOT` in the defaults
    block, executes 3 `gdb.step()` calls to step the primer, then applies
    `tc.reg_pre` and (for FPU tests) the FPU preconditions, and finally
    re-aims `PC = QEMU_TEST_SLOT` before stepping the actual test.

Per-test cost: 3 extra `gdb.step()` calls + 1 extra `write_reg(PC, …)`.
For typical batch sizes that's ~+0.5–1 ms per test, well under noise.

### Smoke (T+0 + 8 min): `--fuzz 1000 --classes=base --seed 42`

Result: **34 624 PASS / 55 FAIL / 0 SKIP** out of 34 679 cases. FAIL rate
drops from the overnight ~6.6 % baseline to **0.16 %** — primer working
as designed for PRIMASK/BASEPRI/FAULTMASK.

**All 55 remaining FAILs are `sysm=8` (MSP).** Diff signature is
identical for every one: `Rd: QEMU=0x00040000 EMU=0x00000000`. That's
`QEMU_TEST_STACK = 0x0004_0000` vs zero. So:

- QEMU side: `MRS Rd, MSP` returns the value of MSP, which equals the
  SP we wrote in `run_qemu_side` (since the CPU is privileged-thread
  with `CONTROL.SPSEL=0`, MSP _is_ the active SP at reset).
- EMU side: `MRS Rd, MSP` returns 0.

This is a **pre-existing mdrp2350 bug**, independent of the primer.
`fuzz-runs/m33.log` (overnight campaign) already contained 18 023
`sysm=8` FAILs across the 12 batches — they just got lumped into the
~24 000 `M0PLUS_T32_MRS` total alongside the PRIMASK leak, and were
hidden by it. With PRIMASK/BASEPRI/FAULTMASK silenced, MSP is what's
left.

Likely root cause (to investigate, not fix in this scope):
`mdrp2350::core::execute_thumb32::*` MRS implementation for SYSm=8
reads a banked-MSP storage field, but the harness's per-test SP setup
(`setup_reg(REG_SP, …)` → `CortexM33` SP register) writes the active
stack pointer rather than the banked MSP slot. When `CONTROL.SPSEL=0`
those two _should_ alias, but evidently don't, in the EMU's register
model. Ticket-worthy follow-up.

**Decision**: this is out of scope for the primer fix. Document and
move on to confirmation. The remaining 0.16 % FAIL rate is a clean,
single-class signal that highlights a real bug rather than masking
fuzz-coverage noise.

### Confirmation (T+0 + ~50 min): `--fuzz 5000 --classes=base --seed 1337`

Result: **173 056 PASS / 247 FAIL / 0 SKIP** out of 173 303 cases —
**0.143 % FAIL rate**. Confirms the smoke result (55/34 679 = 0.158 %)
under a 5x larger sample at a different seed. The residual is the
known `sysm=8 (MSP)` bug; no novel signal emerged.

A separate small probe run (`--fuzz 200 --seed 999`, 6939 cases, 8
FAILs = 0.115 %) inspected the per-FAIL detail directly — every one
matched the same signature (`MRS Rd, MSP` → `QEMU=0x00040000` /
`EMU=0x00000000`).

## Follow-up work (out of scope for this fix)

1. **MSP banking bug in mdrp2350.** `MRS Rd, MSP` (SYSm=8) returns 0 on
   the EMU side when `setup_reg(REG_SP, …)` has set the active SP. In
   privileged-thread mode with `CONTROL.SPSEL=0`, MSP is the active SP,
   so the harness's SP write _should_ be readable through MSP. The
   most likely place to look is the SYSm decode in
   `mdrp2350::core::execute_thumb32` — confirm whether MRS routes to a
   banked-MSP storage field that's never written by the SP setter, vs
   the active-SP register the harness wrote to.
2. **Other M33 edge-case FAILs from the overnight kickoff.** The
   default `qemu_diff_m33` (no `--fuzz`) still emits an `LDM R0!,
   {R0, R1}` Rn-in-list writeback divergence (architecturally
   UNKNOWN; both sides choose differently). Independent of the
   primer.
3. **QEMU 8.2.2 + cortex-m33 + FPU** still drops the GDB stub on every
   FPU instruction. `--classes=base` remains the only sensible
   default for the QEMU oracle until that's resolved.
