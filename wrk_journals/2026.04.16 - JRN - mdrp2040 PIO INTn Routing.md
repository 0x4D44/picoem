# mdrp2040 PIO INTn Routing — Implementation Journal

Date: 2026-04-16
Author: Claude (Opus 4.6)
HLD: `wrk_docs/2026.04.16 - HLD - mdrp2040 PIO INTn Routing.md`

## Goal

Port mdrp2350's PIO INTn routing fix (commit `8bb7614`) to mdrp2040.
Unblocks PicoGUS audio: firmware ISA handler will fire on PIO0 RX
FIFO RXNEMPTY instead of silently waiting forever.

## Approach

Red-green TDD. The shared `mdpicoem-common::PioBlock` already has
`int0_inte`/`int1_inte`/`raw_intr()`/`int0_ints()`/`int1_ints()`
implemented. Only `mdrp2040::Emulator::tick_pio_and_route_irqs_single`
needs updating.

## Stage log

### Stage 1 — RED

**Status:** complete.

Added `pio0_int0_intf_forces_nvic_line_7_only` to
`crates/mdrp2040/src/tests.rs` in the `phase1_wave1` module. Test
forces PIO0 INT0_INTF bit 0 via MMIO write to offset `0x130`, expects
NVIC line 7 (PIO0_IRQ_0) to fire and line 8 (PIO0_IRQ_1) to stay
clear.

First run: `cargo test -p mdrp2040 pio0_int0_intf` → FAILED. Old code
in `tick_pio_and_route_irqs_single` only consults `pending_irqs()`
(`irq_flags`), never reads `int0_intf` — so the NVIC bit was never
set. RED confirmed.

### Stage 2 — GREEN

**Status:** complete.

Replaced the over-route block in `crates/mdrp2040/src/lib.rs:409-428`
with a per-line dispatch that fires NVIC line N when the
corresponding `int{0,1}_ints()` is non-zero. Mirrors mdrp2350
`route_pio_irqs` from commit `8bb7614`.

Two existing tests pinned the over-route behaviour and needed
updating:
- `pio0_irq_flag_bit0_routes_to_nvic_line_7` — now sets
  `INT0_INTE = 0x001` (offset `0x12C`) before forcing the IRQ flag.
- `pio1_irq_flag_bit1_routes_to_nvic_line_10` — now sets
  `INT1_INTE = 0x002` (offset `0x138`).

Deleted `pio_irq_flag_bit2_over_routes_to_both_nvic_lines` —
replaced by the new INTF test plus the two updated INTE tests.

Subtle test-only quirk: forcing INTF without enabling any SM keeps
`pio_all_idle()` true, taking the fast path that skips IRQ routing.
Test enables PIO0 SM0 to mirror the production case (PicoGUS
ISA SM is always enabled when the IRQ matters).

Test results:
- `cargo test -p mdrp2040 phase1_wave1`: 12 passed, 0 failed
- `cargo test -p mdrp2040`: 505 unit + 24 integration tests, all green

Updated `tech_debt.md` entry "PIO INTn_INTE routing not modelled" to
RESOLVED, noted the residual `pio_all_idle()` fast-path corner.

### Stage 3 — End-to-end PicoGUS verification

**Status:** complete; **the IRQ fix is correct but not the PicoGUS
blocker.**

Ran `picogus_diff_rp2040` with `monkey_island_theme.trace` (523,902
events, 30s span, capped at 5s = 514,667 writes fired). Added rich
diagnostics dumping PIO0 INTE/INTS/INTR + NVIC pending after the run.

Result: PSRAM still has 0 non-zero bytes; WAV still all-zero samples.
But the diagnostics revealed why my hypothesis was wrong:

```
Core 0 PC:        0x20001c42  (NOT in sleep_ms — actively running)
Core 1 PC:        0x200073d8  (synth function)
PIO0 SM enabled:  0x7         (SMs 0/1/2 — ISA infrastructure up)
PIO0 INT0_INTE:   0x004       (firmware enabled IRQ flag 2 ONLY)
PIO0 INT0_INTS:   0x000       (no source matches the mask)
PIO0 INTR:        0xf00       (TXNFULL=0xF, RXNEMPTY=0)
NVIC[0].pending:  0x00000001  (TIMER only — no PIO IRQ)
```

Critical observations:

1. **The firmware does NOT enable RXNEMPTY routing on PIO0.** It only
   sets `INT0_INTE = 0x004` (IRQ flag 2 — likely an inter-SM
   signalling line, not the ISA ingestion path).
2. **PIO0 RXNEMPTY = 0** — the PIO RX FIFO is always empty despite
   514,667 ISA events firing. Either DMA drains it instantly, the
   PIO program isn't autopushing, or the PIO program doesn't match
   our synthetic ISA waveform.
3. Core 0 PC has changed significantly from the earlier journal
   observation (`sleep_ms`) — it's now actively running at
   `0x20001c42`, suggesting earlier work fixed several upstream
   blockers.

The IRQ routing fix is **correct, well-tested, and a real
improvement to the emulator** (resolves the tech_debt entry, fixes
the over-route inaccuracy). It just isn't the actual blocker for
PicoGUS audio. The next investigation is the ISA ingestion path —
where the 514,667 events go and why they don't reach PSRAM. That's
separate work.
