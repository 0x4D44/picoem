## Phase A — exploration (done)

### A1 — GlueDma reuse landscape

- `crates/mdpicoem-harness/src/bin/onerom_pio_diff_rp2350.rs` lines 204-259 has a working but hard-coded glue DMA:
  ```rust
  struct GlueDma { read_delay: u8, write_delay: u8, read_value: u32, has_pending: bool }
  const DMA_READ_CYCLES: u8 = 4;
  const DMA_WRITE_CYCLES: u8 = 4;
  ```
  Hard-codes SM1 RX → SM2 TX on PIO0, byte mode, zero SRAM. Not reusable as-is — needs parameterisation (source/sink SM indices and block IDs, bit mode, SRAM source address).
- DMA is a stub in the emulator (`crates/mdrp2350/src/bus/mod.rs:1142-1154`): writes to `0x50000000..` fall through to a `peripheral_regs` HashMap and can be polled back via `emu.bus.read32()`. No engine action on `CTRL_TRIG`.
- **Implication:** we need a fresh, parameterised glue DMA in the new harness. It has to support the two-channel chain (CH0 forwards addr from PIO1.RX0 to CH1.read_addr; CH1 fetches byte from SRAM at that addr and writes to PIO2.TX0). Use `peripheral_regs` polling at `0x50000000 + 0x40*n + {0x00, 0x04, 0x08, 0x0C}` to detect config/trigger.

### A2 — PIO SM_REG layout and accessors

- Per-SM block: stride `0x18`, starting at `0x0C8` inside a PIO block. Layout:
  `CLKDIV (+0x00), EXECCTRL (+0x04), SHIFTCTRL (+0x08), ADDR (+0x0C, RO), INSTR (+0x10), PINCTRL (+0x14)`.
- Our `StateMachine` stores `clkdiv_int/clkdiv_frac`, `execctrl`, `shiftctrl`, `pinctrl`, `pc`, `last_insn` — **all already reachable via `bus.pio[b].read32(sm_offset)`**. No new accessors needed for these.
- `DBG_PADOUT (0x03C)` and `DBG_PADOE (0x040)` already expose merged `pad_out` / `pad_oe` via `read32`.
- `PioBlock::instr_mem()` (added this working tree) covers INSTR_MEM readback.
- The committed trace `oracles/onerom_2364.trace` uses 4 columns per SM: `clkdiv execctrl shiftctrl pinctrl`. `ADDR` and `INSTR` are dynamic state, not logged.

### A3 — test-sdrr-0 pin map (from the bundled fixture)

Parsed directly out of `crates/mdpicoem-harness/fixtures/onerom-fire-24-a-rp2350-test-sdrr-0.bin` at file offset `0x80FC` (where `sdrr_pins_t` lives):

- `chip_pins = 24`, `bit_mode = 8`
- **Data bus D0..D7 → GPIO 16..23** (not GPIO 0..7 as the HLD §7 draft assumed).
- Address bus: A0..A7 = GPIO {7,6,5,4,3,2,1,0} (reversed), A8..A9 = GPIO {10,11}, A10 = 14, A11 = 15, A12 = 12. A13..A15 unused (0xFF).
- **CS1 = GPIO 13**, CS2 = GPIO 12, CS3 = GPIO 15. /OE = 13, /CE = 15.
- Status LED = GPIO 26.

The sdrr_info_t flash struct has NULL pointers where the runtime_info copy lives — those resolve in RAM after Reset_Handler's memcpy. `.sdrr_runtime_info` stays flash-resident, so fire_serve_mode and bit_mode can be read via the emulator's bus after reset (A3 did not resolve them directly from the .bin). Empirically the run already lands in FIRE_SERVE_PIO.

### Key correction vs HLD §7

HLD §7 said "CS on pin 8, address on 9-20, data on 0-7". That's the synthetic `setup_onerom` sample, not the real firmware. Real stimulus needs:
- Drive **one of CS1/CS2/CS3** low (pick CS1 = GPIO 13 for the MVP — it's the /OE line per the table).
- Drive address bits on the scattered `addr[]` pins above.
- Observe data on **GPIO 16..23**.

## Phase B — plan (done)

Architect's plan landed. Key decisions:

- **Module layout**: three new modules in `crates/mdpicoem-harness/src/` (`onerom_sync.rs`, `onerom_snapshot_fmt.rs`, `onerom_glue_dma.rs`). Main binary stays the narrative "boot → sync → dump → drive → observe" flow.
- **F.2**: `is_synced(bus) -> bool`, `capture_snapshot(bus, cycle) -> SyncReport` with typed `PioSnapshot` / `SmSnapshot`. Readback-safe paths only (no RXF pops).
- **F.3**: `format_snapshot` emits trace-shaped + table-shaped output. `decide_oracle_branch` does shape + bytecode checks, almost certainly lands on `B_SmokeTest`.
- **F.4 glue DMA**: two-channel parameterised pump, trigger detection via polling `peripheral_regs` at `DMA_BASE + 0x40*n + 0x0C`, 4+4 cycle latency. Byte replication for bit_mode=8.
- **F.4 stimulus/observation**: re-apply stimulus to `bus.gpio_in` every cycle (don't rely on set-once). CS1=GPIO13 low, CS2/CS3=high, address=0 MVP. Observe data on GPIO 16..23. Pass = stable byte within cycles 8..30 post-CS with PIO2 pad_oe driving all 8 data lines for ≥3 consecutive cycles.
- **Unit tests**: 5 concrete cases covering glue DMA arming, retrigger, 8-cycle latency, snapshot readback cleanliness, oracle-branch decision.
- **Top risks**: PIO1 RX FIFO never populating if stimulus pin map is wrong; DMA trig values predating sync (initialise `last_trigN` on sync, not on startup); SRAM source may live in XIP; PIO2 pad_oe timing window.

Full plan stored for the implementation agent. Moving to Phase C.

### Flags from the implementation agent (worth acting on)

1. **The smoke PASS is weak.** 0xFF at rel_cycle 8..10 is ambiguous — it can mean "PIO2 OSR still holds its reset value of all-1s" rather than "DMA fed a real byte". No `DMA CH{n} armed at cycle N` events were logged during the run, which confirms the CPU never wrote CTRL_TRIG during the post-sync stimulus window. The CPU is already in WFI at `0x10001404` by the time we sync.

2. **The `prime_after_sync` logic is probably inverted.** If OneROM programs the DMA *before* PIO enable (which the sync event detects), then by sync time CTRL_TRIG has already been written — priming "last-seen" to the current value means the glue DMA then waits forever for a NEW write that will never come. The glue DMA should treat a pre-sync non-zero CTRL_TRIG as "already armed, start pumping immediately".

3. **`bus.gpio_in` is already `pub`.** The plan's proposed `gpio_in_mut` accessor was unnecessary; no emulator-crate changes were needed.

4. **RX FIFO unreachable from harness tests.** Test #3 covers only the CH1 half of the chain in isolation — RX FIFO is `pub(crate)` in `mdpicoem-common` and routing a real push through the MMIO interface needs a tiny PIO program. Documented in the test's comment block.

5. **`parse_trace` duplicated** in `onerom_snapshot_fmt.rs` vs the existing copy in `onerom_pio_diff_rp2350.rs`. Marked `TODO: dedupe`.

## Phase D — code review (done)

Reviewer confirmed the two self-flagged risks were real bugs and found one more, plus major + minor items. Verdict: **NEEDS WORK**.

Critical:
1. `prime_after_sync` logic inverted: firmware programs DMA *before* PIO enable, so the channel is already armed at sync time — but we were treating the observed trigger value as "last-seen" and then waiting for a new edge that never comes.
2. Harness stimulus `bus.gpio_in = ...` was being *destroyed* by `Emulator::update_gpio` on the very next step. The inline comment said "re-apply each cycle" which treats the symptom, not the cause; the actual bug is that `update_gpio` overwrites `gpio_in` without preserving any external-input path.
3. `evaluate_smoke_test` declared PASS on `pad_oe==0xFF` + 3-cycle stable value — trivially satisfiable by PIO2's reset state without any DMA pumping. Needs a "glue DMA actually pushed a byte" precondition.

Major:
- End-to-end chain test was actually only arming CH1 and asserting CH1 output; CH0→CH1 handoff not covered.
- `parse_trace` duplicated between `onerom_snapshot_fmt.rs` and `onerom_pio_diff_rp2350.rs` — extract a shared module.
- Pin-map collision: `GPIO_CS2=12` / `GPIO_CS3=15` overlap with `ADDR_PINS` entries for A12/A11. Fixture reality, not a bug, but needs a comment.

Minor/Nits: `OracleBranch::A_*` naming hack, `eprintln!` spam in tests, FSTAT bit arithmetic inline, stale "INSTR_MEM not visible" comment.

## Outcome

F.1, F.2, F.3, F.4 are all done. The OneROM full-system oracle:

1. **F.1**: boots unmodified OneROM firmware through bootrom bypass, clock init, reset deassert, PIO program upload, SM enable, through main() return, into the Reset_Handler's terminal WFI. Previously believed to have a bug — in reality it was working all along.
2. **F.2**: detects the PIO-ready sync point (`PIO1.CTRL & 0xF != 0 && PIO2.CTRL & 0xF != 0`) and captures a full PIO1/2 snapshot at that cycle.
3. **F.3**: formats the snapshot in trace-file-shape + human-readable table, parses the committed `onerom_2364.trace` oracle, and decides the oracle branch (`SmokeTest` here — architecture matches, bytecode differs).
4. **F.4**: stands up a two-channel harness-side glue DMA that pre-arms from existing CTRL_TRIG values at sync, drives CS1 low + address=0 + CS2/3 high via a new bus-level external-input override, pumps 2 byte transfers through CH1 during the 41-cycle observation window, and verifies stable byte 0xFF on GPIO 16-23 with PIO2 driving all 8 data lanes.

### Emulator-crate changes (kept surgical)

- `mdrp2350`: added `Bus::gpio_external_in` + `Bus::gpio_external_mask` fields; `update_gpio` overlays them after computing internal `gpio_in`. Two unit tests for the override semantics.
- `mdpicoem-common`: `PioBlock::push_rx` test-hook gated behind `#[cfg(any(test, feature = "test-hooks"))]`.

No changes to `mdrp2040` / `mdrp2040app`. No changes to the PIO engine semantics. No changes to the clock tree.

### Follow-ups not in scope for this session

- **Byte correctness**: the MVP accepts 0xFF as-observed; proving the byte matches a specific expected value requires locating OneROM's in-RAM `rom_table` post-preload and knowing the ROM payload of `test-sdrr-0`. Worth a dedicated micro-stage if we want to catch wrong-byte bugs.
- **Address sweep**: single-address MVP proves the chain pumps once. Iterating over `A0..A12` would validate the address-decode half (PIO1 SM0 + CH0 forwarding) end-to-end and catch address-bit-swap bugs.
- **The `parse_trace` migration is reasonably clean**, but the shared `onerom_trace` module now has three test cases covering both the instrs-only and full-parse paths. Enough for today; third caller will tell us if the API needs work.
- `crates/mdpicoem-common` has one pre-existing flaky pacer test (`test_pacer_behind_detection`) — unrelated to this session; flagged only for visibility.
