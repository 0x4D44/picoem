## SeaBIOS EPROM Size Question

Arthur asked whether SeaBIOS genuinely needs a 256 KiB EPROM, noting that the
original PC BIOS was much smaller and maybe 32 KiB around the 486 era.

Local byte check:

- `crates/picoem-harness/fixtures/sources/seabios-256k.bin` is exactly
  262144 bytes.
- First nonzero byte is at `0x14200`; last nonzero byte is at `0x3FFFE`.
- The first 64 KiB chunk is entirely zero, but the nonzero span is still about
  180 KiB, so this exact image is not a trivial 128 KiB truncation.

Working conclusion: 256 KiB is required for this checked-in SeaBIOS binary and
the current OneROM JSON declares a 27C020 deliberately. It is not a historical
requirement for 486-era BIOS generally, and likely not a hard SeaBIOS
requirement if we rebuild SeaBIOS with a smaller configuration.

Emotional temperature: curious. This is a good challenge because the fixture
work may have inherited a QEMU-style image size without asking whether the
hardware story really needs it.

## Smaller SeaBIOS SDRR Feasibility

Arthur asked how hard it would be to convert a hypothetical 128 KiB or 64 KiB
SeaBIOS build into SDRR.

Working answer:

- Proper fire-32-a route: easy once the smaller BIOS binary exists. Author a
  OneROM JSON with the smaller EPROM type (`27C010` for 128 KiB; likely
  `27C512` for 64 KiB if supported), run the existing `sdrr-gen` + `onerom-fw`
  recipe, then validate with `sdrr-info`.
- Repo integration is modest but not zero: the current `seabios32` validator
  hardcodes the 256 KiB source size, 27C020-style 512 KiB shadow, and 19 address
  pins. It needs a small generalization for variable source size and fixture
  address width.
- Fire-24-a template patching is faster for a harness-only artifact but keeps
  the 24-pin CS/address compromises. It is not the clean route for a faithful
  EPROM replacement story.

Emotional temperature: cautiously optimistic. The SDRR conversion itself looks
like the easy part; producing and proving a smaller SeaBIOS that still boots the
target workload is the real uncertainty.

## Correction: Fire-32-a 27C010 A16

Later investigation overturned the earlier caveat in this handoff. For
27C010/27C020/27C040, OneROM's live PIO runtime uses `/CE` and `/OE` as the
read gates (`cs_base=14`, `num_cs=2`), and GPIO16 remains A16. The generic
`cs2` metadata name describes the socket slot, not the selected 27C010 runtime
semantics.

The apparent A16-high limitation was caused by the picoem glue DMA suppressing
duplicate CH1 `READ_ADDR` values. The 128 KiB fixture now validates all 524288
fire-32-a pin patterns, with zero unservable skips, and covers all 131072
SeaBIOS source offsets.

Emotional temperature: corrected and calmer. This is exactly why Arthur's push
back mattered; the runtime config was a better oracle than the metadata label.

## SeaBIOS Size Investigation

Arthur asked for a deeper investigation of plausible SeaBIOS sizes.

Primary-source findings:

- Upstream SeaBIOS `CONFIG_ROM_SIZE` accepts a size in KiB, with `0` meaning
  auto-size.
- SeaBIOS `checkrom.py` auto-sizes to 64 KiB, 128 KiB, or 256 KiB based on raw
  payload size.
- SeaBIOS Kconfig says current SeaBIOS fits easily in 256 KiB, while 128 KiB
  generally requires disabling features such as XHCI.
- QEMU carries both `config.seabios-256k` and `config.seabios-128k`.

Build probes in WSL under ignored `target/seabios-size-research/seabios`
(`coreboot/seabios@8fcd351`, GCC 13.3, `PYTHON=python3`):

| Probe | Final ROM | Raw payload | Result |
|---|---:|---:|---|
| Upstream default auto-size | 256 KiB | 180448 bytes | PASS |
| QEMU `config.seabios-128k` | 128 KiB | 97984 bytes | PASS |
| QEMU 128K config forced to 64K | 64 KiB | 97984 bytes | FAIL |
| `allnoconfig`, QEMU, 64K | 64 KiB | 37952 bytes | PASS, but unusably stripped |
| 64K with `BOOT`, IRQ, keyboard, RTC but no `DRIVES` | 64 KiB | 45280 bytes | PASS, cannot boot disks |
| 64K with `DRIVES` but no ATA/floppy | 64 KiB | 79840 bytes | FAIL |
| 64K with basic boot/drives/ATA/floppy/keyboard/IRQ | 64 KiB | 88512 bytes | FAIL |

Working conclusion:

- 256 KiB is the comfortable modern SeaBIOS size.
- 128 KiB is genuinely plausible and has an official QEMU profile. It keeps
  useful legacy BIOS functionality: boot, ATA, floppy, CD-ROM boot, option ROMs,
  PnP, APM, SMBIOS, MP/PIR tables, serial/LPT, keyboard, and IRQ support, while
  cutting USB, AHCI, NVMe, virtio, Xen, ACPI, SMM, and PCI BIOS.
- 64 KiB is only plausible for a non-useful or highly special-purpose SeaBIOS.
  The moment `DRIVES=y` enters the config, current upstream SeaBIOS exceeds
  64 KiB. For PicoEm BIOS-serve work, 64 KiB is a trap.

Emotional temperature: satisfied. This answers the gut-feel question with
actual build numbers: chase 128 KiB if we want period-ish EPROM sizing; do not
spend time on 64 KiB unless the target is a deliberately tiny stub, not SeaBIOS
as a usable BIOS.

commands, hashes, and validation output.
