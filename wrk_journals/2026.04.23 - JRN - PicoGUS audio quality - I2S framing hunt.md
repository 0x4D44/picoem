# 2026.04.23 — PicoGUS audio quality: I2S-framing hunt

## Context (continued from earlier 2026-04-23 journal)

Interpolator CLAMP16 fix (commit `b4c532c`) broke the silence:
4-second Monkey Island replay now produces peak 32767, ~11k non-zero
samples, with the non-zero window aligned to voice-1 activation at
trace-ns 3.49 s.

Remaining problem — audio is **bimodal**: every non-zero sample sits
either at the clamp rails (|x| > 30 000) or near zero (|x| < 1 000),
with essentially nothing in between. Only 27 sign transitions across
11 246 non-zero samples. This is not what a GUS rendering of the
Monkey Island theme should look like.

Strong prior evidence from yesterday's stub-1 experiment: pushing a
constant `0xFF` to the I2S TX FIFO came out of the WAV as
`L=127, R=-32768`. `127 = 0xFF >> 1` → 1-bit MSB shift. `-32768 = 0x8000`
→ canonical "MSB-set" value, suggesting channel misalignment. Between
those two observations, the I2S capture path is a prime suspect for
the bimodal quality issue, independent of any mixer bug.

## Hypothesis

The I2S capture in the harness (or the PIO-side I2S TX implementation)
is off by 1 bit and/or misaligned between L/R channels. That would
map legitimate mid-range mixer output to rail-ish or zero-ish values
depending on which bit position the sign bit lands in.

## Plan

1. Locate the WAV capture path in `picogus_diff_rp2040.rs` and the
   PIO1 SM3 TX setup / autopush logic.
2. Cross-check bit ordering: PicoGUS pushes a packed `(RIGHT<<16)|LEFT`
   32-bit word; I2S is typically MSB-first, 16-bit per channel; figure
   out exactly where each bit lands in our capture.
3. Add a stub that pushes a handful of known 32-bit patterns (e.g.
   `0x0001_0002`, `0x7FFF_8001`, `0x8000_0000`) and see how they come
   out of the WAV.
4. Fix whichever side is wrong.

## Work log

### Step 1 — found ground truth for the PIO timing

`target/picogus_refs/audio_i2s.pio` (standard `pico-extras` program).
Config: `shift_left=true` (MSB first), autopull threshold 32. Side-set
pin 0 = BCLK, pin 1 = LRCLK. Comment declares the FIFO word layout as
`| 31:16 ws=0 | 15:0 ws=1 |`.

Walking the program reveals **Philips one-BCLK-delay** timing:

- Bits 31..17 latched with LRCLK=1 (15 bits, inside `bitloop1`).
- Bit 16 latched with LRCLK=0 (immediately after LRCLK fell).
- Bits 15..1 latched with LRCLK=0 (15 bits, inside `bitloop0`).
- Bit 0 latched with LRCLK=1 (immediately after LRCLK rose).

So each 16-bit channel word is 15 bits on its "own" LRCLK side +
1 LSB bit on the *other* side. The LRCLK edges happen **one BCLK
before** the next word's MSB.

### Step 2 — confirmed the bug arithmetically

Our I2sCapture (`crates/mdpicoem-devices/src/i2s_capture.rs`) is a
**naive non-Philips receiver**: it commits 16 bits per LRCLK window
directly. The 16 bits captured during LRCLK=1 actually belong to:
LSB of previous LEFT (bit 0, 1 bit) + top 15 bits of current RIGHT
(bits 31..17, 15 bits). Similarly for LRCLK=0.

For firmware packing `(RIGHT<<16) | LEFT`, the naive receiver reads:
- `R_heard = (LSB_prev_LEFT << 15) | (RIGHT >> 1)`
- `L_heard = (LSB_prev_RIGHT << 15) | (LEFT >> 1)`

Plugging in the stub-1 observation (constant TXF=`0x000000FF`, so
RIGHT=0 LEFT=255):
- `R_heard = (1 << 15) | (0 >> 1) = 0x8000 = -32768` ✓
- `L_heard = (0 << 15) | (0xFF >> 1) = 0x7F = 127` ✓

Matches observed values exactly. The I2S framing diagnosis from
yesterday is now fully explained.

### Step 3 — Philips-aware fix for I2sCapture

Strategy: accumulate 15 bits during each LRCLK window, then on the
next LRCLK edge mark the accumulator as `finalizing`. The very next
BCLK-rising after that edge latches the LSB and commits the 16-bit
word to the channel active during those 15 MSBs. Then the new
window starts fresh for the new channel.
