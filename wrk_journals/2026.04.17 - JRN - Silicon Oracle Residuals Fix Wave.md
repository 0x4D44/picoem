### 2026-04-17 — Round 1 agent returns

- **MTIME (A.2.1):** HLD landed clean. Root-cause verdict is emulator-only: `Sio::tick_mtime_n` gates only on EN, ignores `MTIME_CTRL.FULLSPEED` (bit 1, reset 0). Per RP2350 datasheet Table 80 + §3.1.8, MTIME must source from `TICKS.RISCV` edges when FULLSPEED=0. TICKS block is already fully modelled (`peripherals/ticks.rs`, 19 tests), just missing a `take_riscv_edges` drain + a FULLSPEED-branch in SIO. Good incidental catch: parent HLD's "WATCHDOG_TICK" naming is RP2040 legacy; on RP2350 it's the RISCV tick domain. **Approved** with two supervisor refinements baked into the implementation brief: (1) retire the legacy `tick_mtime()` per-edge helper entirely (one entry point — `tick_mtime_from_ticks`), (2) sweep all "FRACT" references before finalising (HLD flagged one at sio/mod.rs:635). Implementation agent dispatched.

- **UART (A.2.2):** Auth failure on first attempt ("Not logged in · Please run /login", ~1000 tokens — never read any files). Re-dispatched.

- **DMA (C.2.1):** Auth failure on first attempt (same profile). Re-dispatched.

- **PWM (A.2.3):** HLD landed with a significant framing shift. Math in §1.4 proves the emulator's fractional-divider is correct: 152 sysclks / divisor 2.0 = 76 advances, `76 & 0x64 = 0x44` = reported EMU. The parent A.2 HLD's three candidates (frac_accum reset on EN-write, rounding off-by-one, extra setup tick) are all wrong. Real issue: **measurement window asymmetry** — silicon PWM ticks from DAP-write of `CSR_EN=1` through setup-remainder, sled, `gate_peripheral_hw` (no PWM branch), and CTR readback (thousands of sysclks of DAP latency), while emulator only ticks during `actual_sysclks`. The silicon HW drift 0x04→0x40→0x64 is host DAP-timing noise, confirmed by git log showing zero PWM changes across readings. Bonus latent-bug catch: observe tuple mask `100=0x64` is non-contiguous (`0b0110_0100`) — PASSes by coincidence. Proposed fix is **scenario-only, no emulator change**: custom sled self-gates the window (CSR_EN=1 first, CSR_EN=0 last-before-BKPT); mask becomes `0xFFFF`. **Approved** with three supervisor notes: (1) use existing sled-authoring pattern per `SLED_TICKS_TIMER0_RETARGET_HW` for Thumb immediate encodings (HLD placeholders are not authoritative), (2) verify `validate_custom_sled` exists before test references it, (3) pin the expected CTR in the catalogue comment. Out-of-scope finding deferred: the emulator's split storage of `PwmRegs::en` vs `slice.csr & CSR_EN` violates datasheet Table 1137's "one physical bit aliased two ways" rule — tracked as future tech_debt. **Queued behind MTIME for silicon-verify probe serialisation.**

### 2026-04-17 — Round 2 agent returns (UART + DMA)

- **UART (A.2.2):** HLD landed with a sharp re-diagnosis. Baud math: IBRD=81, FBRD=24 → 115,207 baud → 13,020 sysclks byte-time at 150 MHz. Budget is 60,000 (4.6× byte-time). **Timeout is NOT the problem.** Real root cause: `reset_and_halt` stops CPU at reset vector before bootrom runs. At hardware reset `CLK_PERI_CTRL.ENABLE=0` (datasheet §8.1.3), so silicon UART gets no clk_peri → shift register can't advance → BUSY latched forever. Emulator seeds `peri_clk_hz=150MHz` unconditionally and never checks the ENABLE gate (the existing warn-once at `bus/peripherals.rs:194` flags this as unmodelled). Fix: scenario prepends `(CLK_PERI_CTRL, 1<<11)` — matches what real firmware does via `runtime_init_clocks`. No emulator change (fixing CLK_PERI gating would break SPI/I2C/ADC/PWM scenarios; deferred to tech_debt). **Approved**; queued behind MTIME.

- **DMA (C.2.1):** HLD landed with the most structurally important finding of the wave. Emulator inherited the **RP2040 global-register block wholesale** in Phase 3 DMA (commit `4cc7906`). Datasheet §12.6.6 (`wrk_scratch/rp2350_ds.txt:75329`): RP2350 shifted the whole block up 0x20 bytes because of new INTE2/INTF2/INTS2/INTE3/INTF3/INTS3 groups. So emulator `REG_TIMER0 = 0x420` (RP2040) but silicon TIMER0 = 0x440 (RP2350). Emulator+sled both use 0x420, self-consistent → false green under cargo test. Silicon reads `0x5000_0420` as reserved padding → TIMER0 stays at reset → DREQ_TIMER0 never asserts → BUSY never clears. Why only `dma_timer_paced` fails: it's the only scenario that touches DMA_TIMER (other 2 use TREQ_SEL=63 FORCE, bypass DREQ matrix). Parent HLD's bootrom-init hypothesis cleanly falsified. Fix: shift offsets in `dma.rs` from 0x420+ to 0x440+; update sled MOVW immediate. Storage-only for new IRQ2/IRQ3 (tech_debt for routing). Self-caught math slip in the HLD's MOVW derivation flagged for impl agent to re-derive from encoding tables. **Approved** (4 open questions answered: storage-only IRQ2/IRQ3, skip pre-fix diagnostic, existing cadence test adequate, impl agent to grep for IRQ_DMA_IRQ_2/3 references); queued behind MTIME + UART + PWM.

**Lessons learned (wave-scope):**

1. **Parent hand-off HLDs are hypotheses, not designs.** 3 of 4 per-residual agents found the parent HLD's framing was wrong in substantive ways: MTIME's "WATCHDOG_TICK" was RP2040 carryover for FULLSPEED; PWM's 3 candidate fixes were all wrong (emulator was correct); UART's 4 candidates were all wrong (clk_peri gating, not timing); DMA's bootrom-init hypothesis was structural register-offset shift. Per-residual agents doing first-step-math / scope-narrow-down caught all 4 reframes. Worth repeating.

2. **Multi-agent working-tree is hostile to stop-and-commit patterns.** Two work-loss incidents this session: (a) supervisor's stash pop silently partial-failed, dropping 3 mdrp2350 files; (b) UART agent's unstaged work got swept by a concurrent agent's git operation at identical-second mtime. Self-commit contract (agent runs `git add <specific paths> && git commit` atomically in one Bash call, no gap) is the only safe pattern. Applied successfully for UART, PWM, DMA.

3. **Rate-limit mid-implementation is an outcome to plan for.** PWM agent hit the rate cap partway through /code-reviewer; supervisor had to take over, verify silicon (FAIL), and close with tech_debt. Next time, agents should commit the safest incremental unit (e.g., just the emulator unit test before attempting silicon fix) so rate-limit doesn't leave work stranded.

4. **Concurrent-agent commits can bundle unrelated work.** A.2.1 MTIME's fix landed in `7a32598 riscv-hazard3: QEMU harness` because a concurrent agent ran a broad-stage commit on a racing tree. Content correct, attribution wrong — not rewriting history.
