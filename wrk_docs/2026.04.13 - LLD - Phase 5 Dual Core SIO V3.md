# Phase 5: Dual Core + SIO — Low-Level Design

Version: 0.3.0
Date: 2026-04-13
Parent: HLD Section 15, Phase 5
Depends: Phase 4 complete (bootrom + flash boot working)

## 1. Purpose

Enable both Cortex-M33 cores to run simultaneously. Core 1 boots the real
bootrom, enters the bootrom's FIFO-polling wait loop, and can be launched by
Core 0 via the standard Pico SDK `multicore_launch_core1` protocol.
Implement the remaining SIO block features: inter-processor FIFO, hardware
spinlocks, integer divider, doorbells, platform timer, interpolator stubs,
and the RCP coprocessor encoding and salt propagation needed for the
bootrom's Core 1 path to exit its wait loop.

### Milestone

Integration test: load bootrom + dual-core test binary → both cores execute
the bootrom from the reset vector → Core 0 reaches its application, runs
the launch protocol, and sends the launch sequence via FIFO → Core 1 escapes
`wait_for_rcp_salt` (via the RCP salt validity mechanism), wakes from WFE,
processes the launch sequence, and branches to its application entry → each
core sets a distinct GPIO pin → test asserts both pins in SIO GPIO_OUT AND
that Core 1's PC is outside the bootrom.

### What exists today

| Component | Status | Gap for Phase 5 |
|-----------|--------|-----------------|

| CPUID (0x000) | Returns `active_core()` | Forward `core_id` parameter after refactor |
| GPIO (low) | Inline in Bus dispatch | Move fields and dispatch to Sio |
| GPIO_HI_OUT / HI_OE | Silently ignored | Document as known limitation |

## 2. Design

### 2.1. SIO struct refactor

Move GPIO state (`gpio_out`, `gpio_oe`, `gpio_in`) from Bus into Sio. Make
Sio handle region-0xD 32-bit register dispatch via
`read32(offset, core_id)` and `write32(offset, val, core_id)`. Move `Sio`
from `Emulator` into `Bus` (removing `pub sio: Sio` from Emulator entirely).

GPIO_HI_IN (offset 0x008) stays on Bus because `read_gpio_hi_in()` needs
`flash_loaded`. Bus handles that one offset directly before delegating the
rest. Apply the same carve-out for sub-word reads via `offset & !3 == 0x008`.

```rust
// Bus::read32 for region 0xD:
0xD => {
    let reg_offset = addr & 0xFFF;
    if reg_offset == 0x008 {
        self.read_gpio_hi_in()
    } else {
        let core = self.active_core();
        self.sio.read32(reg_offset, core)
    }
}
```

**Address masking:** change all four SIO dispatch sites (`read8`, `read16`,
`read32`, `write32`) from `addr & 0x0FFF_FFFF` to `addr & 0xFFF`. Collapses
both Secure (0xD0000000) and Non-Secure (0xD4000000) aliases to the same
register. All RP2350 SIO registers live below 0x200; 12-bit masking is
sufficient.

**Sub-word SIO access:** `read8` and `read16` call
`self.sio.read32(offset & !3, core)` and extract the byte/halfword from the
returned 32-bit value (same pattern as PPB sub-word). `write8`/`write16`
continue to silently ignore SIO (pre-existing behavior; bootrom and SDK
use word-aligned SIO writes). Sub-word reads of side-effecting registers
(FIFO_RD, SPINLOCK*N*) are unnecessary for real code and are not
recommended — document as a known caveat rather than adding a guard.

**Helper decomposition:** `Sio::read32` / `Sio::write32` delegate to
per-subsystem helpers: `gpio_read`, `gpio_write`, `fifo_read`, `fifo_write`,
`spinlock_read`, `spinlock_write`, `divider_read`, `divider_write`,
`doorbell_read`, `doorbell_write`, `mtime_read`, `mtime_write`,
`interp_read`, `interp_write`.

**SIO reset:** `Sio::reset()` method that reinitializes all fields (clears
FIFOs, spinlocks, divider state, doorbell pending, MTIME, interpolator
backing store, GPIO state). Called from `Emulator::reset()` alongside
the other subsystem resets.

**External access changes:** `emu.bus.gpio_out` → `emu.bus.sio.gpio_out`.
`tests.rs` has exactly 4 lines to update (verified by grep: lines 5306,
5320, 5332, 5333). Other crates (`mdrp2354-test-harness`, `mdrp2354-debug`,
`mdrp2354-periph`, `mdrp2354-pio`) have been grepped and contain no GPIO or
SIO references.

### 2.2. Inter-processor FIFO

Two 8-entry circular buffers, one per direction.

```rust
struct Fifo {
    buf: [u32; 8],
    head: u8,
    tail: u8,
    count: u8,
}

// In Sio:
fifo_to_core1: Fifo,  // Core 0 writes here; Core 1 reads here
fifo_to_core0: Fifo,  // Core 1 writes here; Core 0 reads here
fifo_wof: [bool; 2],  // sticky write overflow, per core
fifo_roe: [bool; 2],  // sticky read underflow, per core
```

| Offset | Register | Read | Write |
|--------|----------|------|-------|
| 0x050 | FIFO_ST | Status (see below) | W1C: `val & 0x4` clears WOF; `val & 0x8` clears ROE |
| 0x054 | FIFO_WR | — | Push to OTHER core's RX queue |
| 0x058 | FIFO_RD | Pop from THIS core's RX queue | — |

**FIFO_ST bits (for calling core):**
- Bit 0 (VLD): this core's RX queue has data
- Bit 1 (RDY): other core's RX queue has space
- Bit 2 (WOF): sticky write overflow (W1C)
- Bit 3 (ROE): sticky read underflow (W1C)

W1C semantics match RP2040/RP2350 hardware: only bits written as 1 are
cleared. (V2 specified "any write clears"; V3 corrects to W1C.)

**Empty read**: returns 0, sets ROE for the reader.
**Full write**: data dropped, sets WOF for the writer.

**Event signaling on write:** on a successful FIFO_WR (non-overflow), also
set `bus.event_flag[other_core] = true`. This matches RP2350 hardware
behavior (FIFO writes wake WFE) and provides a safety net for code paths
that rely on FIFO-triggered wake. Event infrastructure (§2.8) is added in
Stage A1, so Stage A2's FIFO can wire event signaling without creating an
unvalidated transient.

### 2.3. Hardware spinlocks

32 shared locks. Store as a `u32` bitmask — one bit per lock.

```rust
spinlock_bits: u32,  // bit N = SPINLOCK<N> claimed
```

| Offset | Register | Read | Write |
|--------|----------|------|-------|
| 0x100 + 4*N | SPINLOCK<N> (N=0..31) | If bit N clear → set it, return `1 << N`. Else return 0. | Clear bit N (ignore value) |
| 0x05C | SPINLOCK_ST | `spinlock_bits` | — |

Return `1 << N` on successful claim (matches RP2350 hardware — SDK code may
use the bitmask value directly). Any write releases.

**Fairness note:** Core 0 steps first and wins all contested claims.
Accepted as a valid arbitration model; no deadlock possible.

### 2.4. Integer divider

Per-core hardware divider. Immediate computation. CSR.READY always 1.

```rust
struct Divider {
    dividend: u32,
    divisor: u32,
    quotient: u32,
    remainder: u32,
    signed: bool,
    dirty: bool,
}
// In Sio:
divider: [Divider; 2],
```

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x060 | DIV_UDIVIDEND | Write: store, mark unsigned. Read: return dividend. |
| 0x064 | DIV_UDIVISOR | Write: store, compute unsigned Q/R, mark DIRTY. |
| 0x068 | DIV_SDIVIDEND | Write: store, mark signed. |
| 0x06C | DIV_SDIVISOR | Write: store, compute signed Q/R, mark DIRTY. |
| 0x070 | DIV_QUOTIENT | Read: quotient; clears DIRTY after QUOTIENT+REMAINDER both read. Write: set directly. |
| 0x074 | DIV_REMAINDER | Read: remainder; clears DIRTY after both read. Write: set directly. |
| 0x078 | DIV_CSR | Bit 0 READY (always 1). Bit 1 DIRTY (see note). |

**DIRTY semantics**: set on any write to div registers. Cleared after the
reader reads both QUOTIENT and REMAINDER. Track via a small `reads_pending`
counter in the Divider struct. This matches the SDK's save/restore
protection for divider state across context switches.

**Division by zero** (RP2350):
- Unsigned: quotient = 0xFFFFFFFF, remainder = dividend
- Signed: quotient = 1 when dividend < 0 else -1, remainder = dividend

**Why immediate is correct**: the SDK relies on hardware auto-stall when
reading results before completion; it does NOT insert explicit delays. With
immediate computation, results are always "already done" when read, so the
auto-stall path is never taken and cycle counts are off by up to 8 per
division. Functionally correct; cycle-accurate timing is Phase 8.

### 2.5. Doorbells

4 doorbell bits per core (RP2350 DOORBELL_* registers are 4 bits wide).

```rust
doorbell_pending: [u8; 2],  // lower 4 bits significant
```

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x180 | DOORBELL_OUT_SET | Write: `doorbell_pending[1 - core] \|= val & 0xF` |
| 0x184 | DOORBELL_OUT_CLR | Write: `doorbell_pending[1 - core] &= !(val & 0xF)` |
| 0x188 | DOORBELL_IN_SET | Read: `doorbell_pending[core]` |
| 0x18C | DOORBELL_IN_CLR | Write: `doorbell_pending[core] &= !(val & 0xF)` |

**IRQ delivery is NOT implemented.** The NVIC in `bus/ppb.rs` is a stub
that accepts writes and returns 0 on reads — there is no per-IRQ pending
bit storage. Phase 5 provides register round-trip only. Adding NVIC ISPR/
ICPR storage is out of scope; any test that needs to check IRQ delivery
must validate the doorbell_pending state directly via
`emu.bus.sio.doorbell_pending[core]`.

### 2.6. Platform timer (MTIME)

64-bit counter + per-core 64-bit compare. Edge-triggered match flag.

```rust
mtime: u64,
mtime_ctrl: u32,
mtimecmp: [u64; 2],
mtime_match_asserted: [bool; 2],  // edge-triggered match latch
```

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x1A0 | MTIME_CTRL | Bit 0 = enable. Other bits TBD. |
| 0x1A8 | MTIME (low) | R/W low 32 bits |
| 0x1AC | MTIMEH (high) | R/W high 32 bits |
| 0x1B0 | MTIMECMP0 (low) | Core 0 compare, low 32 |
| 0x1B4 | MTIMECMP0H | Core 0 compare, high 32 |
| 0x1B8 | MTIMECMP1 (low) | Core 1 compare, low 32 |
| 0x1BC | MTIMECMP1H | Core 1 compare, high 32 |

Offsets are best-effort against RP2350 datasheet — verify during
implementation; adjust as needed without a design change.

Increment in `Emulator::step()` after the wake check:
```rust
if self.bus.sio.mtime_ctrl & 1 != 0 {
    let new_mtime = self.bus.sio.mtime.wrapping_add(1);
    self.bus.sio.mtime = new_mtime;
    for core in 0..2 {
        let match_now = new_mtime >= self.bus.sio.mtimecmp[core];
        if match_now && !self.bus.sio.mtime_match_asserted[core] {
            self.bus.sio.mtime_match_asserted[core] = true;
            // IRQ delivery deferred (see §2.5). Match state is observable
            // via the mtime_match_asserted array for tests.
        }
        if !match_now {
            self.bus.sio.mtime_match_asserted[core] = false;
        }
    }
}
```

Edge-triggered: fires once on the `<` → `>=` transition. Clears on
wraparound or on MTIMECMP rewrite to a value `> mtime`. Matches
real hardware behavior (which would be a one-shot pending bit in the NVIC).

**Prescaler simplification:** MTIME increments once per system clock cycle
when enabled. Real RP2350 uses a TICKS peripheral for 1 MHz prescaling;
we don't model TICKS. Acceptable for Phase 5 — the bootrom doesn't depend
on MTIME units, and `time_us_64()` will advance "faster than real" but
monotonically.

### 2.7. Interpolator stubs

Two interpolators per core (INTERP0 at 0x080–0x0BC, INTERP1 at 0x0C0–0x0FC),
16 words each = 32 words per core. Register backing store only.

```rust
// [core][reg] where reg = (offset - 0x080) >> 2, range 0..32
interp: [[u32; 32]; 2],
```

No computation — reads return last-written value. Full interpolator
arithmetic is Phase 7.

### 2.8. Event state, WFE, SEV

The bootrom's Core 1 wait loop uses WFE. The SDK's `multicore_launch_core1`
sends SEV. Hints must stall/wake rather than NOP.

**Shared state on Bus** (added in Stage A1, wired up in B1):
```rust
pub event_flag: [bool; 2],  // per-core ARM event register
```

**Per-core state on CortexM33**:
```rust
pub(crate) wfe_waiting: bool,
```

**WFE**: if `bus.event_flag[self.core_id]` is set → clear it, return 1
cycle. Else → `self.wfe_waiting = true`, return 1 cycle.

**SEV**: set `bus.event_flag[0] = true; bus.event_flag[1] = true`
(broadcast to both cores; ARM ARM specifies "all PEs including the
issuer").

**FIFO_WR auxiliary event**: on a successful FIFO write, also set
`bus.event_flag[other_core] = true` (see §2.2).

**Core step gate**: `CortexM33::step()` adds `if self.wfe_waiting { return; }`
as the FIRST check, before the existing `halted` and `stall_cycles`
checks. A WFE-sleeping core is frozen — no decrement, no fetch, no bus
access.

**Emulator wake check**, in `Emulator::step()` after both cores step:
```rust
for i in 0..2 {
    if self.cores[i].wfe_waiting && self.bus.event_flag[i] {
        self.bus.event_flag[i] = false;
        self.cores[i].wfe_waiting = false;
    }
}
```

Order within `Emulator::step()`:
1. `clock.tick()`
2. `bus.clear_contention_state()`
3. `cores[0].step(&mut bus)`
4. `bus.begin_contention_check()`
5. `cores[1].step(&mut bus)`
6. Wake check (code above)
7. MTIME increment (§2.6)

MTIME runs AFTER the wake check so a compare-match on the current cycle
cannot affect the same-cycle wake decision.

**Event flag reset**: `Emulator::reset()` clears `event_flag[0..2]`.

**WFE latency model**: the step gate returns without consuming a cycle
while sleeping. Wall time (MTIME) continues to advance. Wake latency is
1 emulator tick. This is a modeling simplification — real hardware has
some internal cycle cost to a sleeping core — and is acceptable for
functional testing.

### 2.9. Hint instruction dispatch

Current state:
- **Thumb-32** (`execute_thumb32.rs` line 845–857): `thumb32_misc_control`
  decodes the hint subcode via `hint = hw1 & 0xFF` and has distinct arms
  for NOP/YIELD/WFE/WFI/SEV, all returning 1. Does not receive `bus`.
  Called from `thumb32_branch_misc` (line 778) which takes `_bus` and
  discards it.
- **Thumb-16** (`execute.rs` line 724–735): hint branch does NOT decode the
  subcode — all hints return 1. Function signature already takes `bus`.

**Required changes (Stage B1):**

1. `execute_thumb32.rs` line 778: rename `_bus` → `bus`, pass to
   `thumb32_misc_control`.
2. `execute_thumb32.rs` line 845: add `bus: &mut Bus` parameter.
3. `execute_thumb32.rs` hint arms (lines 852–854):
   ```rust
   0x02 => self.wfe(bus),
   0x03 => 1,                        // WFI remains NOP
   0x04 => { bus.signal_sev(); 1 },  // SEV broadcast
   ```
4. `execute.rs` line 730–733: decode `(opcode >> 4) & 0xF`:
   ```rust
   let hint_op = (opcode >> 4) & 0xF;
   match hint_op {
       0x0 | 0x1 => 1,                       // NOP, YIELD
       0x2 => self.wfe(bus),                 // WFE
       0x3 => 1,                             // WFI (NOP)
       0x4 => { bus.signal_sev(); 1 },       // SEV
       _   => 1,                             // Reserved
   }
   ```
5. New methods:
   - `CortexM33::wfe(&mut self, bus: &mut Bus) -> u32`
   - `Bus::signal_sev(&mut self)` → sets both event flags

No borrow conflicts — `bus.signal_sev()` only mutates `bus.event_flag`
and `self.wfe(bus)` only reads `bus.event_flag[self.core_id]` and mutates
`self.wfe_waiting`. Both paths already have exclusive `&mut bus`.

### 2.10. Core 1 boot

Change `Emulator::reset()` to boot both cores:

```rust
pub fn reset(&mut self) {
    let initial_sp = self.bus.memory.rom_read32(0);
    let reset_vector = self.bus.memory.rom_read32(4);
    for id in 0..2 {
        self.cores[id] = CortexM33::with_id(id as u8);
        self.cores[id].regs.msp = initial_sp;
        self.cores[id].regs.r[13] = initial_sp;
        self.cores[id].regs.set_pc(reset_vector & !1);
        self.cores[id].regs.xpsr = 1 << 24;
    }
    self.bus.clear_bus_fault();
    self.bus.ppb = [Default::default(), Default::default()];
    self.bus.event_flag = [false; 2];
    self.bus.rcp_salt = [0; 2];
    self.bus.rcp_salt_valid = [false; 2];
    self.bus.resets_state = 0x1FFF_FFFF;
    self.bus.sio.reset();  // clear FIFOs, spinlocks, divider, MTIME, etc.
    self.clock = Clock { cycles: 0, sys_clk_hz: self.clock.sys_clk_hz };
}
```

Both cores start at the same reset vector. The bootrom reads CPUID (SIO
0x000) to differentiate. Core 1 branches to `core1_boot_path` (0x1c6),
runs through `wait_for_rcp_salt` (0x1c4), and is stuck WFE-polling
`rcp_canary_status pc` until §2.11's RCP mechanism transitions Core 1's
salt validity.

**Pico SDK launch protocol** (SDK side, for reference only):
1. Core 0 drains its RX FIFO.
2. Core 0 sends `{0, 0, 1, vtor, sp, entry}` one word at a time:
   push, SEV, read echo, compare; restart on mismatch.
3. Core 1 (inside the bootrom, after exiting `wait_for_rcp_salt`) runs
   the handshake: receive each word, echo it, verify the sequence, then
   set VTOR, SP, and branch to `entry`.

The emulator does not implement either side — our responsibility is making
FIFO, WFE/SEV, and RCP salt propagation work correctly so the real bootrom
and the test binary can drive the protocol.

### 2.11. RCP coprocessor decoding and salt propagation (Stage B2)

**The critical blocker for Core 1 boot.** The RP2350 RCP coprocessor
instructions use ARM T32 coprocessor encodings that the current `cp7_rcp`
handler does not recognize.

**Encoding classes in the real bootrom** (verified against
`roms/arm-bootrom.dis`):

| Mnemonic | Example | Encoding class | hw0 high byte |
|----------|---------|----------------|---------------|
| `rcp_canary_get`   | `fe16 373c` at 0x8c | MRC2 (CP7) | 0xFE |
| `rcp_canary_check` | `fe06 273c` at 0x9a | MCR2 (CP7) | 0xFE |
| `rcp_canary_status pc, nodelay` | `fe30 f710` at 0x1d2 | MRC2 (CP7, Rt=15) | 0xFE |
| `rcp_salt_core0` | `fc41 0780` at 0x3998 | MCRR2 (CP7, CRn=1) | 0xFC |
| `rcp_salt_core1` | `fc43 2781` at 0x399c | MCRR2 (CP7, CRn=3) | 0xFC |
| `rcp_iequal`     | `fc43 2770` at 0x1ee | MCRR2 (CP7, different opc1) | 0xFC |

The current handler uses `(hw0 >> 12) & 0xF == 0xE && hw1 & (1 << 4) != 0`,
which matches only the 0xEE prefix. It never fires for real bootrom
instructions — they all fall through silently. Phase 4 works because
`rcp_canary_status` is a silent NOP, and the bootrom's subsequent flag
checks happen to be satisfied by flags left over from preceding
instructions (lucky coincidence).

Core 1's wait loop at 0x1c4–0x1d6:
```
1c4 <wait_for_rcp_salt>: wfe
1c6 <core1_boot_path>: ...
1d2:  rcp_canary_status pc, nodelay
1d6:  bpl.n 1c4           ; bpl = branch if N==0
```

`bpl.n` loops back if N=0, exits if N=1. Core 1 needs `rcp_canary_status`
to return N=0 while its salt is invalid (loop), and N=1 after Core 0 has
validated the salt (exit).

Core 0's canary_status sites (0x38b8 and 0x3990) run BEFORE Core 0 executes
`rcp_salt_core0`/`rcp_salt_core1` at 0x3998/0x399c, so they need the
"invalid" (N=0, V=0) result.

#### 2.11.1. Cross-core salt state on Bus

Move `rcp_salt` off CortexM33 and onto Bus:

```rust
// On Bus:
pub rcp_salt: [u32; 2],
pub rcp_salt_valid: [bool; 2],
```

Remove `pub(crate) rcp_salt: u32` from CortexM33. Update
`test_cp7_rcp_salt_roundtrip` in `core/coprocessor.rs`: read from
`bus.rcp_salt[0]` instead of `cpu.rcp_salt`.

Both fields are cleared in `Emulator::reset()` (§2.10).

#### 2.11.2. Extended RCP handler

Add `bus: &mut Bus` to `cp7_rcp`. Update the `thumb32_coprocessor` dispatcher
to pass bus to `cp7_rcp` (it already passes bus to `fpu_execute`, so the
pattern exists).

```rust
fn cp7_rcp(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
    let hw0_high = (hw0 >> 8) & 0xFF;

    match hw0_high {
        0xEE | 0xFE => self.cp7_mcr_mrc_family(hw0, hw1, bus),
        0xEC | 0xFC => self.cp7_mcrr_mrrc_family(hw0, hw1, bus),
        _ => 1,
    }
}

fn cp7_mcr_mrc_family(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
    let is_cdp = hw1 & (1 << 4) == 0;
    if is_cdp {
        return 1;  // CDP / CDP2: accept silently
    }
    let is_mrc = (hw0 >> 4) & 1 != 0;   // L bit
    let rt = ((hw1 >> 12) & 0xF) as usize;
    let core = bus.active_core();

    if is_mrc {
        if rt == 15 {
            // rcp_canary_status pc: write NZCV into APSR.
            // N = salt_valid[core], Z=0, C=0, V=0.
            let n = if bus.rcp_salt_valid[core] { 1u32 << 31 } else { 0 };
            self.regs.xpsr = (self.regs.xpsr & 0x0FFF_FFFF) | n;
        } else {
            // rcp_canary_get: return salt XOR deadbeef (stub value)
            self.regs.r[rt] = bus.rcp_salt[core] ^ 0xDEAD_BEEF;
        }
    } else {
        // MCR2: rcp_canary_check assertion — accept silently (never fault)
    }
    1
}

fn cp7_mcrr_mrrc_family(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
    // hw0[3:0] encodes CRn; hw1[15:12] = Rt; hw1[11:8] = coproc; hw1[7:4] = opc1
    let crn = (hw0 & 0xF) as usize;
    let l_bit = (hw0 >> 4) & 1;

    if l_bit != 0 {
        // MRRC2 from CP7: not used by bootrom, NOP
        return 1;
    }

    // MCRR2 to CP7. Dispatch by CRn:
    //   CRn=1 → rcp_salt_core0 (set salt + validity for core 0)
    //   CRn=3 → rcp_salt_core1 (set salt + validity for core 1)
    //   others → rcp_iequal, rcp_bvalid, etc. — silent assertion NOPs
    let rt  = ((hw1 >> 12) & 0xF) as usize;
    let rt2 = (hw0 & 0xF) as usize; // RP2350 uses different field; TBD at impl time
    match crn {
        1 => {
            bus.rcp_salt[0]       = self.regs.r[rt];
            bus.rcp_salt_valid[0] = true;
        }
        3 => {
            bus.rcp_salt[1]       = self.regs.r[rt];
            bus.rcp_salt_valid[1] = true;
        }
        _ => {
            // rcp_iequal / rcp_bvalid etc.: silent NOP (stub assertions)
        }
    }
    1
}
```

**Key correctness properties**:

1. **Rt=15 MRC2 writes APSR, NOT r[15]**. This is the single most
   important bug fix — without it, any `rcp_canary_status pc` would
   corrupt PC. (Phase 4 gets away with the current silent NOP because
   the instruction never fires.)
2. **State-dependent flag output**. `rcp_salt_valid` flips only when the
   corresponding `rcp_salt_core<N>` MCRR2 executes. Core 1's wait loop
   exits when its salt is marked valid.
3. **MCRR2 encoding distinct from MCR2**. V2's `(hw0 >> 12) & 0xF == 0xF`
   match was too broad — it would have classified `rcp_iequal` (0xFC
   prefix) as MCR2, incorrectly routing it to the salt-write path. V3
   narrows to `(hw0 >> 8) & 0xFF` with two explicit arms (0xEE/0xFE for
   MCR family, 0xEC/0xFC for MCRR family).
4. **Phase 4 regression minimized**. Core 0's canary_status sites (0x38b8,
   0x3990) run with `rcp_salt_valid[0] == false`, so they get N=0, V=0
   — which satisfies all three subsequent flag checks (`bvc`, `bvs`, `bmi`)
   that currently pass via lucky-coincidence flags. The post-fix path
   reaches the same basic blocks.

**Known uncertainties to resolve during implementation:**

- CRn encoding for `rcp_salt_core0` vs `rcp_salt_core1`. The LLD uses CRn=1
  and CRn=3 based on the bootrom disassembly (`fc41` and `fc43`), but this
  should be cross-checked against the pico-bootrom-rp2350 source.
- MCRR2 Rt/Rt2 field positions. Phase 5 only stores Rt and discards Rt2,
  which is sufficient for the salt-validity bit flip but loses the second
  salt word. If the real handshake requires a 64-bit salt, implement Rt2
  extraction at that point.
- Whether `rcp_canary_check` (MCR2 Rt=any) needs to set a bit. Currently
  modeled as silent NOP. If the bootrom has a path where a check-then-get
  round-trip is expected, we'll discover it in the iterative Core-1 boot
  trace.

**Phase 4 regression test plan**: after implementing 2.11.2, re-run
`test_flash_boot_blinky`. Expected: unchanged cycle count (or very close),
Core 0 still reaches main() and sets GPIO 25. Any deviation means the new
RCP behavior affected Core 0's path — trace and adjust.

## 5. Test binary for integration

No dual-core binary exists in `roms/` — only `gen_blinky.py` and
`bootrom-combined.bin`. Add `roms/gen_dualcore.py`.

**Approach**: extend the hand-assembly style of `gen_blinky.py`. The test
binary contains only Core 0's code (the real bootrom handles Core 1 until
launch). After launch, a small stub runs on Core 1.

- **Core 0 code**:
  - Wait for Core 1 to be ready (poll FIFO_ST RDY bit — should be set
    once Core 1 exits `wait_for_rcp_salt`; in practice, after Core 0
    finishes its own init and reaches the app, Core 1 is already there).
  - Drain RX FIFO by reading FIFO_RD until VLD=0.
  - Send `{0, 0, 1, vtor, sp, entry1}`:
    - For each word: wait for FIFO_ST.RDY, write FIFO_WR, execute SEV,
      wait for FIFO_ST.VLD, read FIFO_RD, compare to sent value,
      restart on mismatch.
  - After launch succeeds: set GPIO 25, infinite loop.
- **Core 1 code** (at entry1, in flash/XIP):
  - Set GPIO 0, infinite loop.

Estimated helper additions to the Python script: ~200–300 lines, including
a new `thumb_sev()` helper, FIFO poll loops, compare-and-restart state
machine. The simplified version can skip the restart logic (assume no
mismatches) — ~150 lines for a working-path-only test.

**Fallback**: if hand-assembling proves too complex, install the Pico SDK
toolchain and build an official multicore example. Either path is
acceptable; document the choice in the implementation journal.

**Integration test assertions:**
- `bus.sio.gpio_out & (1 << 25) != 0`
- `bus.sio.gpio_out & 1 != 0`
- `cores[1].regs.pc() >= 0x1000_0000` (Core 1 in flash/XIP, not bootrom)
- `cores[1].is_wfe_waiting() == false`

## 7. Known Limitations

- **No divider latency.** Results immediate. Cycle count off by up to 8 per division. Phase 8.
- **No interpolator computation.** Register store only. Phase 7.
- **GPIO_HI_OUT / GPIO_HI_OE.** Writes accepted and silently dropped; reads return 0.
- **No NVIC pending-bit storage.** Doorbell and MTIME register states round-trip correctly, but IRQ delivery does NOT fire because `bus.ppb[core]` has no ISPR/ICPR backing store. Tests must observe doorbell/MTIME state via direct field access. Adding NVIC pending-bit storage is deferred to a later phase.
- **MTIME prescaler not modeled.** MTIME ticks once per system clock. `time_us_64()` advances faster than real.
- **WFI treated as NOP.** Bootrom uses WFE; WFI sleeping (requires pending-IRQ check) is not modeled.
- **Zero-latency FIFO.** Core 0's FIFO_WR is visible to Core 1 in the same emulator tick. SDK uses WFE/SEV synchronization so protocol correctness is unaffected; relevant only for pathological polling loops.
- **Spinlock fairness.** Core 0 always wins contested claims (it steps first). No deadlock; pathological livelock theoretically possible but not observed.
- **RCP canary/check/get are stubbed.** `rcp_canary_check` is a silent NOP assertion; `rcp_canary_get` returns `rcp_salt ^ 0xDEAD_BEEF`; `rcp_canary_status pc` writes `N = rcp_salt_valid[core]`, V=0, Z=0, C=0. Other RCP instructions (`rcp_iequal`, `rcp_bvalid`, `rcp_count_*`) are silent NOPs. Sufficient for bootrom Core 1 boot; not a faithful RCP implementation.
- **MCRR2 Rt2 discarded.** Only the first source register is stored to `rcp_salt`. The hardware treats salt as a 64-bit value; we collapse to 32-bit, which is enough for the salt-validity check to flip Core 1's flag.
- **No TrustZone differentiation.** Secure and NS SIO aliases map to the same state.
- **CP0 GPIOC coprocessor unchanged.** Pure stub (returns 0, ignores writes). Bootrom uses memory-mapped SIO instead. Not regressed, not fixed.
- **NSACR writes silently ignored** (pre-existing). Not known to affect bootrom/SDK.

## 8. Risk Assessment

**Highest risk: §2.11 RCP fix producing unexpected flag transitions in
Core 0's path.** V3's state-dependent model (N = `rcp_salt_valid[core]`,
V=0) is designed to match Core 0's expected flag values before salt init
(N=0, V=0 satisfies `bvc`, `bvs`, `bmi` sites at 0x38bc / 0x3994 / 0x3996).
But this is an analytical prediction, not an empirical one. **Mitigation**:
Stage B2 re-runs `test_flash_boot_blinky` before the Core-1 integration
test. If Phase 4 regresses, trace Core 0's new execution path and adjust
the flag values or the canary_check handler behavior. Expect ≤2 iterative
fixes similar to Phase 3/4 bootrom debugging.

**Medium risk: MCRR2 Rt/Rt2 field positions.** The LLD assumes hw1[15:12]
is Rt and treats rt2 as unused. Real MCRR/MRRC T32 encoding places Rt2 in
hw0[3:0]. For Phase 5, the validity-bit flip is sufficient; losing the
salt value itself is acceptable (our canary_get stub already returns
garbage). **Mitigation**: if Core 1 boot fails with "invalid salt value
read back" somewhere after escaping the wait loop, extract Rt2 from
hw0[3:0] and store both words.

**Medium risk: CRn encoding for salt_core0 vs salt_core1.** The LLD
assumes CRn=1 → core 0 and CRn=3 → core 1 based on `fc41` and `fc43` in
the bootrom disassembly. This is an inference, not a citation from the
pico-bootrom-rp2350 source. **Mitigation**: cross-check against the
bootrom source during B2 implementation. If wrong, swap the mapping — a
1-line fix.

**Medium risk: Test binary hand-assembly complexity.** §5 estimates
~150–300 lines of Python. The SDK launch protocol has error-recovery logic
(restart on echo mismatch) that's non-trivial to hand-assemble. **Mitigation**:
fallback to Pico SDK build. Either path is acceptable.

**Low risk: SIO refactor.** PPB pattern is proven. ~20 line moves plus
4 test lines. Existing tests catch regressions.

**Low risk: FIFO, spinlocks, divider, doorbells, MTIME, interpolator stubs.**
Independent, self-contained, well-defined semantics. Each has unit tests.

**Low risk: WFE/SEV correctness.** Clean state model on Bus. Unit-testable
in isolation before B2 brings Core 1 online.

**Pre-existing risk (documented, not fixed in Phase 5): `active_core()`
boolean hack.** Relies on `contention_check_active` flip between Core 0
and Core 1 steps. Phase 5's wake check runs with the flag left over from
Core 1's step but never queries `active_core()`, so the hack is preserved.
Any future code that adds cross-core logic AFTER Core 1's step must not
assume `active_core()` returns the correct value.
