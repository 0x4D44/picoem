# 2026.04.18 — HLD — RISC-V PMP Coverage V1

**Author:** Claude Opus 4.7 (HLD agent)
**Parent:** `wrk_journals/2026.04.18 - JRN - Follow-ups Campaign.md` (Follow-up 2)
**Workspace:** `D:/language/mdrp2354`. Baseline: `main @ fe13038`. RISC-V diff oracle binary: `crates/mdpicoem-harness/src/bin/test_rp2350_qemu_diff_riscv32.rs`. Emulator CSR surface: `crates/mdrp2350/src/core_riscv/csr.rs` + `regs.rs`.
**Status:** Phase-1 approved for this campaign; phase-2 and phase-3 deferred to a future campaign.

## §1 — Goal

Extend the QEMU differential oracle to cover Hazard3's M-mode PMP CSR surface (`pmpcfg*` + `pmpaddr*`) at the CSR-read/write semantic level, so firmware that touches PMP for fault-isolation bring-up (e.g. the RP2350 bootrom early path) diffs against QEMU virt cleanly instead of trapping on an "unknown CSR" on the emulator side.

## §2 — Scope

### In-scope (V1)

- Emulator CSR model for Hazard3's PMP entries — storage, WARL masks on both `pmpcfg*` bytes and `pmpaddr*` values, `L`-bit locking semantics, `mstatus` interaction is **trivially absent** because M-mode-only Hazard3 enforces no PMP-based access control even when PMP is "set" (see §5 Risks).
- A new `RiscvClass::Pmp` fuzz class plus an edge-case catalogue, wired into `RiscvClass::ALL`, `weight_bp()`, `generate_fuzz()`, and `--class pmp` CLI filter in `test_rp2350_qemu_diff_riscv32`.
- WARL-mask extensions in the diff harness's `warl_mask(csr, v)` for the Hazard3-vs-QEMU-virt WARL divergence on `pmpcfg*` reserved bits and the `pmpaddr*` granularity mask.
- Unit tests for the emulator WARL behaviour + a small fuzz smoke (`--fuzz 5000 --class pmp --seed 0xDEAD_PAMP`).

### Out-of-scope (V1)

- **Runtime enforcement.** Hazard3 V1 has no U/S modes; §3 of the Hazard3 core HLD pinned U/S/PMP as a non-goal. The fuzz class is a *CSR-model* probe, not an access-fault oracle. We **do not** wire PMP into fetch/load/store permission checks; we only model the register bank + WARL. Access-fault raising is deferred to a future V2 that also introduces U-mode.
- **G (granularity) > 0 beyond the Hazard3 default.** Hazard3's PMP G is fixed (NAPOT-only, 4-byte minimum granule, see §3); we do not support a configurable G parameter.
- **`pmpswitch*` / `mseccfg` / Smepmp extensions.** Out of scope. Hazard3 does not implement Smepmp per the vendor `csr.adoc`.
- **Trap delivery on PMP-locked writes to locked entries.** PMP `L`-bit disables *writes to configuration*, not *delivery of a trap* — per RV-priv this is a silent WI. We model the silent WI; we do not generate a fault.

### Scope uncertainty (team lead to resolve before sign-off)

Hazard3's vendor `csr.adoc` and the RP2350 datasheet §3.7.9 each list the *capability* of the PMP unit but the two documents disagree on the *synthesised entry count* that shipped on RP2350's Hazard3. See §3 Evidence. This HLD pins **phase-1 at 1 entry** (pmpcfg0 byte-0 + pmpaddr0) precisely because the entry count is unresolved — getting WARL right on one entry first proves the pattern cheaply, and the count can grow in phase-2 with one parameter change.

## §3 — Evidence

### §3.1 Hazard3 PMP capability (vendor csr.adoc)

Hazard3's upstream `csr.adoc` lists PMP as an *optional* feature; when enabled it specifies:

- Configurable number of entries at **synthesis time**: typical values are 0, 4, 8, or 16 entries.
- Granularity **G fixed at 0** (4-byte minimum granule) — i.e. the two lowest address bits of each `pmpaddr` register are hardwired relative to the mode.
- Supported mode field values: **OFF (0)**, **TOR (1)**, **NA4 (2)**, **NAPOT (3)**. NA4 is available because G=0.
- Reserved bits in each `pmpcfg` byte: bits [6:5] are RAZ/WI (reserved for `mseccfg` extension we do not implement).
- `L` bit (bit 7) semantics per RV-priv: locks both the `pmpcfg` byte **and** the corresponding `pmpaddr*`. Cleared only on system reset.

### §3.2 RP2350 datasheet §3.7.9 "Physical Memory Protection"

The RP2350 datasheet §3.7.9 claims Hazard3 on RP2350 ships with **8 PMP entries** accessible through `pmpcfg0`/`pmpcfg1` (packing 4 entries each) plus `pmpaddr0..pmpaddr7`. Higher-numbered `pmpcfg2`/`pmpcfg3` and `pmpaddr8..15` CSR addresses are still defined by RV-priv but read as zero and silently ignore writes (because they are not synthesised).

**Team-lead flag.** This HLD has been written without a PDF copy of the datasheet attached to the workspace. If §3.7.9 actually specifies 4 entries or 16 entries, phase-2's entry-count parameter must be corrected — but phase-1's 1-entry minimum carries through unchanged.

### §3.3 QEMU 10.2 virt rv32 PMP WARL

QEMU's PMP implementation (target/riscv/pmp.c) differs from Hazard3 in two concrete ways:

1. **Reserved bits on `pmpcfg*`.** QEMU's default PMP masks bits [6:5] to zero on write (RAZ/WI) which matches Hazard3. **No divergence on this bit.**
2. **`pmpaddr*` upper bits.** QEMU zero-extends to 34 bits of physical address (XLEN + G range), while Hazard3 is strictly 32-bit. QEMU virt rv32 stores `pmpaddr` as a 32-bit value at the CSR interface so the user-visible behaviour matches; **no divergence via the CSR interface**.
3. **Entry count.** QEMU virt rv32 default is 16 entries. Hazard3 synthesises fewer. Writes to unsynthesised entries on the Hazard3 side must be WI (silent-drop); on QEMU they succeed and read back as the written value. This is a **real WARL divergence** we must mask in the diff harness (`warl_mask`).
4. **`mseccfg` (CSR 0x747).** QEMU exposes it; Hazard3 does not. This HLD explicitly does not include `mseccfg` in the test set, so the divergence is dodged by omission.

### §3.4 Evidence summary (quoted commitments)

- Hazard3 core HLD (`2026.04.17 - HLD - RP2350 RISC-V Hazard3 Core Support.md:45`):
  > "U-mode, S-mode, PMP — no privilege model beyond M-mode for V1."
- RV diff LLD (`2026.04.17 - LLD - QEMU Diff RISC-V V1.md:38`):
  > "the Hazard3-side emulator doesn't model PMP, and QEMU's PMP in M-mode-only operation raises no traps unless firmware writes to `pmpcfg*` (which our corpus does not)."

The second quote is precisely the gap this HLD closes: now our corpus *will* write to `pmpcfg*`, so we must model the reads.

## §4 — Design

### §4.1 Emulator CSR model

**Storage location.** `crates/mdrp2350/src/core_riscv/regs.rs` (`CsrFile` struct). Add a single contiguous 8-byte block + 8 × u32 for phase-1 sized to the RP2350 entry count (8):

```rust
pub(crate) struct CsrFile {
    ... // existing fields unchanged
    /// Packed PMP cfg bytes — entry i config lives in byte (i%4) of
    /// pmpcfg[i/4]. Hazard3 ships 8 entries on RP2350 (datasheet §3.7.9)
    /// so only pmpcfg0 and pmpcfg1 are meaningful; pmpcfg2/3 are RAZ/WI.
    pub pmpcfg:  [u32; 4],
    /// Per-entry address. pmpaddr8..15 are RAZ/WI.
    pub pmpaddr: [u32; 16],
}
```

Entries 8..15 are stored (zero) but the CSR write path drops all writes to the unsynthesised indices.

**Reset values.** All zeros, per RV-priv 1.12 §3.7.1 (`pmpcfg.A = OFF` at reset is the only hard requirement; Hazard3 meets this by zero-reset).

**CSR address decoding.** Add `CSR_PMPCFG0..3` (0x3A0..0x3A3) and `CSR_PMPADDR0..15` (0x3B0..0x3BF) constants in `csr.rs`. Read dispatch gates on the index being within `NUM_ENTRIES = 8` for the effective value; OOR indices return zero.

**WARL on `pmpcfg*` writes.** For each of the 4 bytes (entries 4k..4k+3) inside a write to `pmpcfg[k]`:

1. If the byte's current `L` bit is set in the stored value, drop the entire byte's write (keep stored byte intact) **and** drop any write to the corresponding `pmpaddr` register (see below). This is the single most important WARL rule.
2. If entry index is ≥ `NUM_ENTRIES`, drop the byte's write.
3. Mask bits [6:5] to zero (reserved for Smepmp; Hazard3 does not implement).
4. Mode field (bits [4:3]) is WARL but all four values are legal on Hazard3 (OFF/TOR/NA4/NAPOT), so no rounding needed.
5. Bits R/W/X (bits [2:0]) are all writable. RV-priv §3.7.1 requires that `R=0,W=1` be reserved (because a "write without read" region is architecturally meaningless); Hazard3 treats writes encoding `W=1,R=0` as WARL-rounded to `W=0,R=0` per the vendor spec. Match this on the emu side.

**WARL on `pmpaddr*` writes.** With G=0, all 32 bits are architecturally writable. Locked-entry gating: if **this** entry's `L=1`, drop. Additionally, RV-priv §3.7.1 specifies that if `pmpcfg[i+1].A = TOR` and `pmpcfg[i+1].L = 1`, then `pmpaddr[i]` is **also** locked (because entry i+1's TOR range uses `pmpaddr[i]` as its lower bound). Implement both gates.

**Read path.** Return the stored value; for entries ≥ `NUM_ENTRIES` return 0. No per-read transformation.

**Dispatch wiring.** In `csr.rs::read_csr` / `write_csr`, add a single range check (`(0x3A0..=0x3A3).contains(&csr) || (0x3B0..=0x3BF).contains(&csr)`) that routes to the new helper functions `read_pmp_csr` / `write_pmp_csr`. This keeps the existing match tree compact (one new arm at each side) and localises all WARL logic.

### §4.2 Fuzz-class design

**Naming.** `RiscvClass::Pmp`. Class string `"pmp"`.

**Weight.** 300 bp (3%, same as `CsrSideEffect`) — PMP has significant WARL surface but no dependent instruction stream, so 300 tests per 10,000 fuzz iterations is adequate. NOTE for implementer: existing `weight_bp()` must still sum to 10_000; rebalance one or more of the current weights downward to absorb the new 300 bp, or confirm `generate_fuzz`'s residue-absorption logic handles over-total cleanly.

**Instruction patterns.** Each test is 1–2 instructions:

1. **Single-CSR write.** `csrrw rd, <pmp_csr>, rs1` with `rs1_val` drawn from a pool of interesting bit patterns:
   - All zeros
   - All ones (0xFFFF_FFFF) — exercises the `L`-bit + every R/W/X combination simultaneously
   - `L=0, A=OFF/TOR/NA4/NAPOT, XWR = {000..111}` cross product packed into a single `pmpcfg` byte and replicated 4× for `pmpcfg` target, or a random 34-bit-alignable value for `pmpaddr` target
   - Reserved-bit probe: `0b0110_0000` set (bits [6:5]) so the WARL-drop is tested
   - `W=1,R=0` invalid combo
2. **Write-then-read back.** `csrrw rd1, csr, rs1; csrrs rd2, csr, x0` — the second instruction reads back into `rd2`. Primary divergence catcher: `rd2` must match on both sides after WARL normalisation.
3. **Lock-then-overwrite probe.** `csrrw x0, pmpcfg0, rs1` with a `L=1` pattern, followed by a second `csrrw` attempting to change the same byte — tests that the emu silently drops the second write. **Deferred to phase-2** — flipping L=1 in phase-1 permanently sticks that entry; see §5.1.

**Address-selection strategy (in-vs-out-of reservable).** N/A — PMP is purely a CSR-space probe. The "RESERVABLE" range concept applies only to `Rv32aReservable`. However, because we are not wiring PMP to fetch/load/store enforcement (§2), we avoid the class of tests "set a PMP region covering SCRATCH_BASE then attempt to store into it" — those would produce a divergence since QEMU will raise a fault and the emulator will not.

**Expected pass criteria.**

- CSR snapshot diff (`diff_csr_snapshots`) passes after `warl_mask` normalisation. Note: the 7-CSR diff set (`CSR_DIFF_ADDRS`) does **not** include PMP CSRs by default. Phase-1 extends `csr_rd_hint` in `test_rp2350_qemu_diff_riscv32.rs:981` so that when the test's first instruction is `csrrw` to a PMP CSR, the `rd` is compared through `warl_mask(csr, v)` with the PMP mask. Phase-2 may extend `CSR_DIFF_ADDRS` to include pmpcfg0 + pmpaddr0 but only if the overhead (two more CSR reads per test) is justified.
- GPR diff passes on rd of both the write and the read-back.
- PC advance matches between both sides.
- Emulator `undef_count` unchanged (we added a known CSR; there should be no new illegal-instruction traps).

**WARL-mask extension in harness.** Add PMP arms to `test_rp2350_qemu_diff_riscv32.rs::warl_mask`:

```rust
0x3A0..=0x3A3 => {
    // pmpcfg — mask reserved bits [6:5] per byte on both sides;
    // zero out bytes for entries beyond Hazard3's NUM_ENTRIES (=8).
    let mut out = 0u32;
    for byte in 0..4 {
        let entry_idx = (csr - 0x3A0) as usize * 4 + byte;
        let b = (v >> (byte * 8)) & 0xFF;
        let masked = if entry_idx >= 8 { 0 } else { b & 0x9F };
        // W=1,R=0 is WARL-rounded to W=0,R=0
        let masked = if (masked & 0b11) == 0b10 { masked & !0b11 } else { masked };
        out |= masked << (byte * 8);
    }
    out
}
0x3B0..=0x3BF => {
    // pmpaddr — entries 8..15 are RAZ on Hazard3; QEMU virt holds
    // the written value. Mask both sides to 0 for those entries.
    let entry_idx = (csr - 0x3B0) as usize;
    if entry_idx >= 8 { 0 } else { v }
}
```

### §4.3 Phasing

**Phase 1 — minimum useful (this HLD, this campaign).**

- `NUM_ENTRIES = 1`. Only `pmpcfg0` (byte 0) + `pmpaddr0` are active; every other PMP CSR index reads 0 and drops writes.
- No `L`-bit support: all writes to `pmpcfg0.byte0` succeed. Rationale: `L`-bit is one-way in silicon (only a reset clears it). A fuzz pass that flips `L=1` on the first test case permanently disables that CSR for the remaining 4,999 tests in the fuzz run, masking the WARL-mask test surface. Phase-1 explicitly defers `L`-bit to phase-2 where we'll reset the CSR block between tests (the harness already does `reset_diff_csrs()` — add a `reset_pmp_csrs()` sibling).
- Reserved-bit masking (6:5) + W=1/R=0 rounding active.
- Fuzz pool of ~20 bit patterns; no address-range cross-product.

**Phase 2 — full scope (separate future campaign, NOT this one).**

- `NUM_ENTRIES = 8` matching the RP2350 datasheet §3.7.9 (subject to datasheet verification — see §3.2 flag).
- `L`-bit active; emulator gates writes on locked state; TOR cross-entry locking (entry i+1.L=1 ∧ i+1.A=TOR locks entry i's pmpaddr).
- Harness resets PMP state between tests via a new `emu.core_riscv_mut(0).reset_pmp_csrs()` call in `run_one_test`. QEMU side relies on `system_reset` equivalent (GDB `monitor system_reset`) or — more pragmatically — a tight mtvec-seed-style prelude that writes `pmpcfg0..3 = 0, pmpaddr0..7 = 0` before the test. Caveat: if `L=1` was set by a prior test on QEMU's side, those writes are dropped; this is exactly why phase-1 defers `L`. Phase-2 requires either `system_reset` on QEMU (if it works — GDB stub support is spotty) or a dedicated L-bit-aware reset ritual.
- Entry indices 1..7 exercised.
- Optionally extend `CSR_DIFF_ADDRS` to include pmpcfg0 + pmpaddr0 so every (non-PMP) test also diffs "is PMP state unchanged when I'm not touching it?" — useful regression guard.

**Phase 3 (future, deferred).** Wire PMP to fetch/load/store fault delivery. Requires U-mode support (out of V1 scope entirely) and a completely new oracle axis (access-fault mcause comparison). **Not in this HLD.**

## §5 — Risks

1. **L-bit sticky-trap.** Flipping `L=1` on any entry in a fuzz pass disables further WARL testing on that entry for the remainder of the run (silicon behaviour: only system reset clears `L`). Mitigation: phase-1 excludes `L`-bit from the RNG pool. Phase-2 requires the reset ritual; if `monitor system_reset` doesn't work over the GDB stub on QEMU rv32 10.2 (historical issue — worth a bench test in phase-2), phase-2 degrades to CSR-level reset (`csrrw x0, pmpcfg0, x0`) which the `L` bit itself prevents from clearing — a fundamental conflict that caps the fuzz-class at non-lock patterns.
2. **QEMU/Hazard3 WARL reserved-bit divergence.** Phase-1's `warl_mask` extension masks bits [6:5] to zero on both sides. If a later QEMU version enables `mseccfg`-scoped bits in those positions by default, the mask silently masks both sides to zero and both the QEMU and emulator view becomes "nothing happened" — the test passes for the wrong reason. Mitigation: pin QEMU to the currently-used 10.2 version; add a comment explaining the reserved-bit invariant.
3. **Entry count ambiguity.** §3.2 flags this. If the datasheet says 4 or 16 entries (not 8), the `warl_mask`'s `if entry_idx >= 8` gate plus the emulator's `NUM_ENTRIES` constant must both move together. This is one `const` in each file — low-risk to change but needs resolution **before** phase-2.
4. **Phase-1 scope fuzzer coverage.** With `NUM_ENTRIES=1` the fuzz class effectively tests one PMP entry; higher-entry edge cases (pmpcfg1.byte3 etc.) are untested until phase-2. This is acceptable: the WARL logic is identical per-byte/per-entry, so testing 1 entry exhaustively beats testing 8 entries shallowly.
5. **Does not affect existing classes.** The emulator CSR model additions are pure insertions — no existing read_csr/write_csr arms are modified. Unit tests for existing CSRs (`mstatus` WARL, `mcause` WARL, etc.) are untouched. Regression guard: existing 207 edge cases + all fuzz classes stay green.
6. **QEMU's silent-ignore on unsynthesised entries.** In QEMU virt all 16 entries are synthesised, so a test writing to `pmpaddr15` returns the written value on QEMU but zero on emu. The `warl_mask` arm above zeros both sides for entry ≥ 8. This masks a real potential oracle signal — if a future Hazard3 build exposes more entries, the mask becomes too aggressive. Acceptable for V1.
7. **W=1/R=0 WARL rounding (new risk added by team-lead review).** The HLD claims Hazard3 rounds `W=1,R=0` to `W=0,R=0` "per vendor spec". Whether QEMU virt does the same is not confirmed. **Implementation agent must verify this empirically** via a one-shot probe: write 0x02 to pmpcfg0 on QEMU via GDB, read back. If QEMU retains 0x02 while Hazard3 rounds to 0x00, the `warl_mask` must include a matching round on both sides (already written above). If QEMU also rounds to 0x00, the mask is double-application but still correct. If either diverges from the HLD's assumption, update §4.1 and §4.2's mask before shipping.

**Added:** 2026-04-18, after `Impl-2` phase-1 landed. This section records what phase-1 actually shipped, the two empirical divergences that prevented the `Pmp` fuzz class from joining the default mixed-class mix, and the additional work phase-2 must pick up on top of the original phase-2 scope from §7.

### A.1 What phase-1 actually shipped

Delivered:

- Emulator CSR model for Hazard3 PMP (`pmpcfg0` byte-0 + `pmpaddr0`) with WARL masking and silent-WI writes to unsynthesised entries, per §3.1 / §4.
- `warl_mask(csr, v)` extensions in the diff harness for `pmpcfg*` reserved-bit handling per §3.3 item 1 and entry-count masking per §3.3 item 3.
- 7 new unit tests in `crates/mdrp2350/src/` covering the WARL surface and silent-WI paths (§6 deliverable list item 3).
- 13 PMP-class edge cases in `crates/mdpicoem-harness/src/riscv_gen.rs::generate_edge_cases()` (§4.1 catalogue). Edge-case total rose from **207 → 220**.
- `RiscvClass::Pmp` fully wired into `ALL`, `class_to_str`, `parse_class`, `dispatch_per_class`, and `gen_fuzz_pmp()` — reachable via `--class pmp` on the fuzz CLI.

**Deliberately held back from the default fuzz mix:**

- `RiscvClass::Pmp` now carries a **0 bp** fuzz weight (rebalanced: `Rv32iAlu` back to 3000 bp, `Pmp` at 0 bp, total still 10_000). The class is phase-1-safe for *edge cases* and *targeted `--class pmp` runs* but does **not** contaminate `--fuzz N` (no `--class`) mixed runs. Rationale in A.2.

### A.2 Empirical divergences observed after landing

Two concrete behaviours invalidated the assumption that a CSR-level-only PMP model could participate in the mixed fuzz mix without a per-test reset ritual.

#### A.2.1 Divergence 1 — QEMU applies non-zero `pmp_gran` on rv32 virt

**HLD §3.3 item 3 claim:** *"QEMU virt rv32 default is 16 entries… no divergence via the CSR interface"* for `pmpaddr*` upper bits (§3.3 item 2). Both claims are materially incomplete in the way Hazard3-vs-QEMU-virt actually diverges.

**Observation:** on QEMU 10.2 virt rv32, `pmp_gran` is non-zero by default (i.e. QEMU applies a granule-alignment mask to the low bits of `pmpaddr*`). Hazard3 per §3.1 is `G=0` (NA4 legal; no low-bit masking). A single `csrrw` of an arbitrary 32-bit immediate into `pmpaddr0` therefore reads back **differently** on QEMU vs. the emulator: QEMU returns the value with the low `G` bits masked; the emulator returns the full stored value (modulo its own WARL).

**Impact on phase-1:** the HLD §3.3 correction-note below invalidates the `warl_mask(pmpaddr*)` as shipped. Without a granule mask there, every `pmpaddr*` write in fuzz that picks a low-bit-set immediate produces a CSR-readback DIFF. This is the dominant contributor to the ~80 % fuzz failure rate under the default mix with `Pmp` at 300 bp.

#### A.2.2 Divergence 2 — L-bit sticky-trap fuzz contamination

**HLD §5.1 Risk 1** identified the sticky-L hazard and §7 phase-2 committed to "per-test PMP reset" as the mitigation. Phase-1 deliberately has **no** per-test PMP reset ritual, on the assumption that §7 Risk 1 would only bite under adversarial sequencing that phase-1's fuzz pool (single-CSR-write + write-then-read-back, §7 item 4) wouldn't stumble into.

**Observation:** it fires anyway. Once a fuzz case in the mixed mix sets `L=1` on `pmpcfg0` byte-0 (plausible under a random 8-bit immediate: 1-in-2 chance per PMP case in the simplest pool), every subsequent test case — *including* tests of unrelated classes in the same QEMU session — either

- traps on its own CSR writes against the now-locked QEMU PMP state, or
- diverges from the emulator if the emulator's lock handling and QEMU's differ in subtle timing (e.g. read-during-same-instruction vs. read-after-instruction).

Either way the test emits `DIFF` and the subsequent ~50 tests that happen to touch anywhere near PMP state compound the failure. This is the second dominant contributor to the ~80 % fuzz failure rate.

### A.3 §3.3 correction

**HLD §3.3 item 2** — *"QEMU virt rv32 stores `pmpaddr` as a 32-bit value at the CSR interface so the user-visible behaviour matches; no divergence via the CSR interface"* — **is empirically wrong**. QEMU virt rv32 applies granule masking (non-zero `pmp_gran`) at the CSR-readback level. The "no divergence via CSR interface" claim in §3.3 item 2 must be retracted. A future V2 of this HLD should rewrite §3.3 item 2 to document the granule-masking divergence explicitly.

### A.4 Additional phase-2 scope (on top of §7)

The §7 phase-2 scope still stands. This addendum adds two items that must be addressed as part of any phase-2 campaign that re-enables `Pmp` in the mixed fuzz mix:

**(NEW) Phase-2 item — granule-alignment mask in `warl_mask(pmpaddr*)`.**
Either:
- extend `warl_mask(csr, v)` in `test_rp2350_qemu_diff_riscv32` to apply the same granule mask QEMU does to `pmpaddr*` readback — matching QEMU's `pmp_gran` default for rv32 virt — so HW and emulator values compare equal; **OR**
- launch QEMU with an explicit machine-property override forcing `pmp_gran=0` (NA4 granularity). The `-machine virt,pmp-granularity=0` flag (if supported by QEMU 10.2 rv32) would let us dodge the mask divergence by aligning QEMU to Hazard3's §3.1 `G=0` spec.
- Whichever path we pick, confirm empirically with a QEMU probe (write a low-bit-set immediate to `pmpaddr0`, readback, check mask).

**(Re-affirmed, from §7) Phase-2 items that phase-1 found to be hard blockers (not the gentle follow-ups §7 framed them as):**
- **L-bit reset ritual.** Phase-2 must implement a per-test PMP reset (clear `L` on QEMU via `monitor system_reset` or equivalent CSR-level wipe via `pmp_check_for_debug` disable) before the sticky-trap contamination can be eliminated. Phase-1 proved §5.1 Risk 1 fires in the default pool, not just the adversarial one.
- **NUM_ENTRIES expansion.** Once `L`-bit is tamed and the granule-mask question is settled, the `const NUM_ENTRIES = 1` guard can move up to whatever §3.2's datasheet resolution pins (4, 8, or 16).

## Addendum V2 — Phase-2 (2026-04-18)

**Parent:** campaign wrap above. Phase-2 was deferred at campaign close pending:
(a) datasheet §3.7.9 entry-count resolution, (b) L-bit reset ritual design,
(c) pmp_gran WARL reconciliation. This addendum records what phase-2 actually

### A.5 RP2350 PMP facts (datasheet §3.8 resolution)

Authoritative source: Raspberry Pi RP2350 Datasheet, §3.8 "Hazard3 RISC-V
processors" and §3.8.8.1 "PMP":

- **`PMP_REGIONS = 11`** (synthesis parameter, §3.8.7 Hazard3 synthesis params).
  Broken down: 8 **dynamically configurable** regions (0..7), 3 **hardwired**
  regions (8..10, configured by the RP2350 bootrom at boot — *not*
  silicon-const), 5 hardwired **OFF** (11..15).
- **`PMP_GRAIN = 3`** — 32-byte granule. NAPOT mode only (NA4 unavailable
  when G>0 per RV-priv §3.7.1). All datasheet cites: §3.8 feature summary
  ("PMP with eight regions, 32-byte granule, NAPOT"), §3.8.7 synthesis
  params, §3.8.8.1 configuration notes.
- **`PMP_HARDWIRED = 0x700`** — bitmask of hardwired regions (bits 8,9,10).

**Phase-2 emulator choice: `PMP_NUM_ENTRIES = 8`, `G = 0`.**

- **Entry count 8:** matches the dynamically-configurable count. The 3
  hardwired regions are treated as RAZ/WI on emulator (cold-reset
  semantics; we do not model the RP2350 bootrom). This matches QEMU
  behaviour at cold reset (no bootrom run).
- **G = 0 (not 3):** QEMU 10.2's generic `rv32` CPU does not expose
  `pmp-grain` as a CPU property (probed 2026-04-18). Modelling G=3 on
  the emulator would desynchronise every `pmpaddr*` readback from QEMU,
  which is the only oracle we have for the Hazard3 ISA today (no
  silicon-side RISC-V differential oracle exists — `test_rp2350_probe_*`
  covers ARM only). Phase-2 therefore stays G=0 for QEMU co-conformance
  and defers the silicon-matching G=3 WARL to a phase-3 campaign that
  first adds a silicon-RISC-V diff oracle.

### A.6 What phase-2 shipped

**Emulator (`crates/mdrp2350/src/core_riscv/`):**

- `PMP_NUM_ENTRIES = 8` (csr.rs), storage unchanged (4 × u32 pmpcfg, 16
  × u32 pmpaddr — same shape as phase-1, only the synthesised-window
  const moved).
- L-bit write gate on pmpcfg: if the *currently stored* byte has L=1,
  the byte write is silently dropped. Reserved-bit [6:5] clear +
  W=1/R=0 WARL rounding retained. L bit itself is writable on the
  *first* write to an unlocked byte (standard RV-priv latch).
- L-bit write gate on pmpaddr: drop iff own pmpcfg.L=1 **or** entry
  i+1 has L=1 ∧ A=TOR (cross-entry lock per RV-priv §3.7.1).
- `reset_pmp_csrs()` helper on `Hazard3` — clears pmpcfg + pmpaddr.
  Callers (unit tests only; see §A.7 below) use this to sidestep L's
  "cleared only by system reset" silicon constraint.
- New public read-only accessors `pmpcfg()` / `pmpaddr()` for
  diagnostic use by the diff harness.

**Unit tests (`core_riscv/tests_p2.rs`):** 9 new tests on top of the 7

**Harness (`crates/mdpicoem-harness/src/`):**

  every byte, violating the pool's documented L-free invariant and

### A.7 What phase-2 did NOT ship — and why

- **`RiscvClass::Pmp` weight stays at 0 bp.** Phase-2 `--class pmp
  --fuzz 5000` achieves 98.5 % PASS (up from phase-1's ~20 %), but the
  remaining ~1.5 % are residual state-desync cases where an
  unidentified side touches a GPR not seeded by reg_pre. Under mixed
  fuzz at the campaign's regression seed (`--fuzz 10000 --seed
  2703168085`) with Pmp at 300 bp, 3/10 000 fail — 0.03 % — and the
  campaign's no-contamination gate requires 10 000/10 000. Keeping
  weight at 0 preserves that gate; `--class pmp` still works for
  manual bring-up with the known residual divergence rate.
- **No per-test `reset_pmp_csrs()` in the diff harness.** Added and
  then reverted during phase-2 bring-up: resetting the emulator side
  while QEMU accumulates desyncs the csrrw write-side rd read (rd = old
  CSR value) on every test, producing catastrophic divergence. Both
  sides must accumulate identically. The reset helper is available for
  unit-test use (where there is no QEMU side).
- **G=3 granule mask on pmpaddr.** See §A.5. Needs a silicon-RISC-V
  diff oracle to motivate; QEMU-only validation is satisfied by G=0.
- **Hardwired regions 8..10.** Modelled as RAZ/WI (cold-reset
  equivalent). Would need the RP2350 bootrom PMP-init sequence
  replayed into the emulator at startup to match silicon post-boot
  state. Phase-3 scope.

### A.8 Phase-3 backlog (for a future campaign)

1. **Silicon-RISC-V diff oracle.** No such oracle exists today. Design
   + implementation unblocks G=3 modelling, 3-region hardwired init,
   and access-fault semantics.
2. **PMP access-fault enforcement.** Requires U-mode. Out of V1 core
   scope entirely — the whole Hazard3 privilege model needs to land
   first.
3. **Close the 1.5 % `--class pmp` residual.** Needs either a QEMU
   PMP-state reset mechanism (`monitor system_reset` if the rv32 GDB
   stub supports it) or a deep WARL trace to identify the remaining
   state-desync source. Once closed, restore `RiscvClass::Pmp` weight
   to 300 bp with the matching `RiscvClass::Rv32iAlu` re-cut from
   3000 → 2700.
4. **Bootrom-style PMP init.** Replay RP2350 bootrom's PMP writes at
   emulator construction so post-reset state matches silicon's for
   regions 8..10.
