## Summary of investigation

Overnight fuzz surfaced a suspicious bimodal signature on `uart0_rx_loopback`: HW reports `0x5A` (majority) or `0xAD` (minority) against a constant EMU value `0x42`. Agent 4's triage flagged it as "second state-leakage bug vs expected timing jitter".

**Finding (smoking gun):** `S_UART0_TX_SINGLE_BYTE` at `crates/mdpicoem-harness/src/silicon_scenarios.rs:855` pushes the literal byte `0x5A` to `UART0_UARTDR`. Silicon is not reset between scenarios inside an iteration; UART0 TX FIFO / shift register / RX FIFO retain state across the Fisher-Yates shuffle boundary. When `uart0_rx_loopback` follows `uart0_tx_single_byte` in the shuffle, the leaked `0x5A` appears in the RX observable.

The `0xAD` minority is likely a frame-boundary bit-slip in the same leaked state (paper decode pending; does not change the fix shape).

## Hypothesis rank

- **H1 (state-leakage — same family as PWM/PIO overnight findings): very strong.** Smoking gun at line 855.
- **H2 (emulator WLEN/framing gap): ruled out.** Neither `0x5A` nor `0xAD` is a bit-masked form of `0x42`.
- **H3 (bit-slip explaining 0xAD): likely mechanism** in composition with H1. No fix shape change.
- **H4 (silicon jitter — accept + document): unlikely.** Values are stable and `0x5A` is too precise a coincidence.

## Verdict

This is the same pattern as `pwm_wrap_irq` / `pio0_nop_loop` / `pio0_int_routing_split`. The fix shape is identical: prepend a `RESET_UART0` set-then-clear pulse to both `S_UART0_RX_LOOPBACK` and `S_UART0_TX_SINGLE_BYTE` setup tables (symmetric, bidirectional).
