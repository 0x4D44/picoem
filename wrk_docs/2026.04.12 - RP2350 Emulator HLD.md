## 1. Purpose

A cycle-accurate emulator of the RP2350/RP2354 microcontroller, written in Rust
for performance and safety. Designed as a **reusable library crate** (`mdrp2354`)
that can be consumed by downstream projects.

### Deployment Model

```
mdrp2354 (this repo)          — RP2354 emulator crate + CLI test harness
  └─► onerom-emu (separate repo) — OneROM firmware running on mdrp2354
        └─► mddosem (../mddosem) — DOS emulator, consumes OneROM for BIOS
```

This repo is a standalone RP2354 emulator. It knows nothing about OneROM or x86.
OneROM integration and mddosem BIOS boot are downstream concerns in their own
repos. The emulator's public API must be clean enough to support these use cases
without leaking downstream assumptions into the crate.

### Bootrom

The RP2350 bootrom is open source: https://github.com/raspberrypi/pico-bootrom-rp2350
Pre-built ELFs with debug info are available in releases. The bootrom is 32 kB and
contains the Arm M33 boot path, NS boot (USB/UART bootloader), and RISC-V boot
(with Armv8-M Baseline emulator). We can load the real bootrom binary directly.

## 2. Target Hardware Summary

| Feature               | RP2350 Specification                                    |
|-----------------------|---------------------------------------------------------|
| CPU cores             | 2x Cortex-M33 (Armv8-M Main) OR 2x Hazard3 (RV32IMAC) |
| Clock                 | 150 MHz (nominal), tested to 300 MHz overclocked        |
| SRAM                  | 520 kB across 10 banks (SRAM0-9)                        |
| ROM                   | 32 kB bootrom at 0x00000000                             |
| External flash        | Up to 16 MB QSPI via XIP (RP2354: 2 MB stacked)        |
| PIO                   | 3 blocks x 4 state machines = 12 total                  |
| DMA                   | 16 channels                                             |
| Bus                   | AHB5 crossbar, 6 upstream x 17 downstream ports         |
| Key peripherals       | 2x UART, 2x SPI, 2x I2C, PWM, ADC, USB 1.1, HSTX      |
| SIO                   | Spinlocks, FIFOs, doorbells, interpolators, TMDS enc.   |
| Coprocessors (M33)    | GPIO (CP0), DCP double-prec (CP4/5), RCP (CP7), FPU     |

### Scope for v1: Arm mode only

We emulate Arm Cortex-M33 cores only; Hazard3 RISC-V is out of scope for v1. The
architecture-switch mechanism (Section 3.9 of datasheet) can be stubbed.

### TrustZone: designed but not built in v1

The RP2350 has extensive Secure/Non-secure banking throughout: SIO, spinlocks,
FIFOs, PPB, bus filters (ACCESSCTRL). The architecture leaves seams for TrustZone
support:
- SAU struct and trait defined but returns "everything Secure" in v1
- Memory map includes Secure/Non-secure aliases (SIO_BASE vs SIO_NONSEC_BASE)
  but both map to the same backing state in v1
- ACCESSCTRL registers exist but default to "allow all"

This means the bus dispatch code has the right shape from day 1, and adding real
TrustZone is a matter of filling in the policy logic, not restructuring.

## 5. Timing Model

This is the critical design decision. We need cycle accuracy while running on a
pre-emptively scheduled Windows OS.

### 5.1. Internal Time: The Master Cycle Counter

A single `u64` master cycle counter is the sole source of truth for all timing.
Every component references this counter. There is no wallclock dependency in the
emulation logic itself.

```rust
/// The global emulation clock. All timing derives from this.
struct Clock {
    /// Monotonically increasing system clock cycle count.
    /// At 150 MHz, wraps after ~3,900 years. We'll be fine.
    cycles: u64,

    /// System clock frequency in Hz. Default 150_000_000.
    sys_clk_hz: u32,
}
```

### 5.2. Execution Model: Lockstep Round-Robin

Both cores and all PIO state machines advance in lockstep, driven by the master
cycle counter. The execution loop is:

```
loop {
    // 1. Advance master clock by 1
    clock.tick();

    // 2. Step each core (1 cycle of work)
    //    - Core may complete an instruction or be mid-multi-cycle op
    //    - Bus access may stall (arbitration contention, APB latency)
    core0.step(&mut bus);
    core1.step(&mut bus);

    // 3. Step PIO state machines (at their divided clock rate)
    for pio in &mut pios {
        pio.step(&mut bus);
    }

    // 4. Step DMA (if any channels active)
    dma.step(&mut bus);

    // 5. Step peripherals that need per-cycle attention
    //    (timers, UART shift registers, etc.)
    peripherals.step();
}
// After each quantum of N cycles, the Pacer (Section 5.3) spin-waits
// on rdtsc until the quantum's wallclock time has elapsed.
```

**Why lockstep, not run-ahead?** Cycle accuracy requires all components to observe
the same cycle counter. Run-ahead (letting one core race ahead) breaks this and
makes bus arbitration non-deterministic. Lockstep is simpler and correct.

**Performance implication:** At 150 MHz target and 5 GHz host, we have ~33 host
cycles per emulated cycle. The inner loop must complete in <33 host cycles on
average. This is tight but achievable if the hot path is lean.

### 5.3. Real-Time Pacing: Quantum-Based Execution with `rdtsc`

We do NOT run as fast as possible. Running flat-out distorts the absolute timing
of externally-observable events (GPIO transitions, PIO waveforms) even though
relative cycle counts are preserved. This is effectively overclocking with
non-uniform time distortion — a 1-cycle instruction and a 3-cycle instruction
both compress differently in wallclock time.

Instead, we pace to real-time using quantum-based execution:

```rust
/// Shared monitoring state. Atomic counters updated on the hot path,
/// safe to read from any thread without locking.
pub struct PacerStats {
    /// Total emulated cycles since start.
    pub emulated_cycles: AtomicU64,
    /// Host nanoseconds spent emulating (doing useful work).
    pub emulation_ns: AtomicU64,
    /// Host nanoseconds spent spinning (waiting for real-time).
    pub spin_ns: AtomicU64,
    /// Number of quanta where emulation couldn't keep up.
    pub behind_count: AtomicU64,
    /// Whether pacing is active.
    pub running: AtomicBool,
}

/// Point-in-time snapshot for monitoring. Derived metrics computed
/// on the read side to keep the hot path minimal.
pub struct PacerSnapshot { /* plain u64 copies + derived methods */ }

impl PacerSnapshot {
    pub fn utilization(&self) -> f64;   // emulation_ns / total_ns
    pub fn emulated_mhz(&self) -> f64;  // cycles / total_ns * 1000
    pub fn headroom(&self) -> f64;      // 1.0 - utilization
}

/// Real-time pacer. Manages quantum-based execution and spin-wait.
/// Separate from Emulator — the emulator stays pure simulation.
pub struct Pacer {
    stats: Arc<PacerStats>,
    quantum_cycles: u64,        // cycles per quantum (default 150 = 1us @ 150 MHz)
    quantum_tsc_ticks: u64,     // host rdtsc ticks per quantum
    quantum_start_tsc: u64,     // rdtsc at start of current quantum
    tsc_freq_hz: u64,           // calibrated TSC frequency
}
```

**Execution loop with pacing (caller owns the loop):**

```
// Caller (harness, onerom-emu, etc.) owns the run loop:
let mut emu = Emulator::new(Config::default());
let mut pacer = Pacer::new(150_000_000);
let stats = pacer.stats();  // Arc<PacerStats> for monitoring

// Hand stats to monitoring consumer (thread, GUI, etc.)
std::thread::spawn(move || monitor_loop(stats));

loop {
    pacer.begin_quantum();
    for _ in 0..pacer.quantum_cycles() {
        emu.step();
    }
    pacer.end_quantum();  // spin-wait, update stats
}
```

The Pacer does NOT own the Emulator — the caller wires them together. This
keeps the emulator as a pure simulation engine with no knowledge of real-time
concerns. `begin_quantum()` records the rdtsc start; `end_quantum()` measures
elapsed time, spin-waits if ahead of real-time, and updates atomic stats. The
caller can inject events (GPIO, breakpoints) between quanta.

**Why `rdtsc`, not `QueryPerformanceCounter`?**

| Mechanism | Resolution | Per-call cost | Verdict |
|-----------|-----------|---------------|---------|
| `Sleep(0/1)` | ~1-15ms | syscall | Useless |
| `QPC` | ~100ns (10 MHz typical) | ~20ns (syscall) | Can't resolve 6.67ns cycles |
| `rdtsc` | ~0.2ns on 5 GHz | ~1ns (user-mode) | **Can resolve single cycles** |

`rdtsc` on modern Intel/AMD with `constant_tsc` (invariant TSC, standard since
~2008) ticks at a fixed rate regardless of turbo/power state. At 5 GHz reference
clock, one RP2350 cycle = ~33 rdtsc ticks — well within measurement resolution.

**Quantum size is a configuration knob:**

| Quantum | Cycles | Wall time | Use case |
|---------|--------|-----------|----------|
| Fine | 15 | ~100ns | PIO waveform validation, precision testing |
| Default | 150 | ~1us | Normal operation, good fidelity |
| Coarse | 15,000 | ~100us | Bulk testing, profiling |
| Unpaced | ∞ | N/A | Benchmarking, differential testing |

Within a quantum, all cycles execute at host speed (time is compressed). At
quantum boundaries, time snaps to wallclock. At the default 1us quantum, the
sub-quantum distortion is invisible to any practical external observer.

**Graceful degradation:** If execution takes longer than the quantum (we can't
keep up at real-time), skip the spin-wait and log it. This is genuinely behind
real-time — a problem to investigate, not hide.

**Monitoring:** The `PacerStats` struct provides live telemetry via atomic
counters. The emulation loop updates these with fetch_add (~5 host cycles
each) — negligible overhead amortized across the quantum. Any thread can
read a consistent `PacerSnapshot` at any time.

The library provides the mechanism (`Arc<PacerStats>`) but not the policy —
the embedding application decides how to consume stats:
- Test harness: monitoring thread prints utilization/MHz every second
- GUI application: reads stats on frame tick for a debug overlay
- Headless: ignores stats entirely

The emulation loop never touches I/O. All logging happens on the monitoring
consumer's thread.

**Calibration at startup:** Read `rdtsc` twice bracketing a known `Sleep(100)`,
compute TSC frequency. Verify `constant_tsc` via `CPUID`. One-time cost.

**Thread affinity:** Pin the emulation thread to a specific core
(`SetThreadAffinityMask`) to avoid cross-core TSC synchronisation jitter and
keep the hot path in L1. The spin-wait burns this core at 100% — acceptable for
a real-time emulator.

### 5.4. Bus Cycle Accounting

The bus fabric is the bridge between instruction execution and memory. Access
latency depends on the target:

| Target            | Read Cycles | Write Cycles | Notes                        |
|-------------------|-------------|--------------|------------------------------|
| SRAM (AHB)        | 1           | 1            | Zero wait state              |
| ROM (AHB)         | 1           | N/A          | Read-only                    |
| SIO               | 1           | 1            | Zero wait state, core-local  |
| AHB peripherals   | 1-2         | 1-2          | Up to 1 wait state           |
| APB peripherals   | 3+          | 4+           | Bridge adds latency          |
| APB async (ADC..) | 4+          | 5+           | Extra stall for clock domain |
| XIP (cache hit)   | 1           | N/A          | Through 16kB 2-way cache     |
| XIP (cache miss)  | ~20-40      | N/A          | QSPI flash read latency      |

Bus contention: when two cores access the same bus port on the same cycle, the
higher-priority core proceeds and the other stalls for 1 cycle. DMA has its own
priority. The bus fabric tracks this per-cycle.

Atomic aliases (addr + 0x1000/2000/3000): native atomics are same-cost. Interposed
atomics (UART, SPI, I2C, SSI) cost 2 additional cycles.

## 6. Cortex-M33 Core Design

### 6.1. Pipeline Model

The Cortex-M33 has a 3-stage in-order pipeline. For emulation we don't model
individual pipeline stages — we model the *observable timing behaviour*:

- Most data-processing instructions: **1 cycle**
- MUL, MLA (32x32→32): **1 cycle**
- SDIV/UDIV: **2-12 cycles** (data-dependent, early termination)
- LDR (zero-wait target): **2 cycles** (addr calc + memory)
- STR (zero-wait target): **1 cycle** (write-buffered)
- LDM/STM: **1 + N cycles** (N = register count)
- Branch taken: **1 + pipeline refill** (~2-3 total)
- Branch not taken: **1 cycle**
- IT block: conditional execution, no branch penalty
- Exception entry: **~12 cycles** (register stacking)
- Exception return: **~12 cycles** (register unstacking)

**Source for cycle counts:** ARM doesn't publish a per-instruction table for M33
(unlike M3/M4). Our strategy:
1. Start with Cortex-M4 published timings (architecturally very similar pipeline)
2. Validate against real RP2354 hardware via DWT cycle counter (CYCCNT)
3. Use gdbdiff for automated differential testing
4. Adjust per-instruction where measured divergence exceeds tolerance

### 6.2. Thumb-2 Decoder Design

This is the hottest code in the emulator. Design for the L1 instruction cache.

**Encoding format:** All instructions are Thumb (16-bit) or Thumb-2 (32-bit).
No ARM (32-bit legacy) mode. Detection:

```rust
// Bits [15:11] of first halfword determine width
// 0b11101, 0b11110, 0b11111 → 32-bit instruction (fetch second halfword)
// Everything else → 16-bit instruction
fn is_wide(hw0: u16) -> bool {
    hw0 >= 0xE800
}
```

**Decoder structure:** A two-level decode using Rust `match`:

```rust
fn decode_execute(&mut self, bus: &mut Bus) -> u32 /* cycles */ {
    let hw0 = self.fetch16(bus);

    if is_wide(hw0) {
        let hw1 = self.fetch16(bus);
        self.execute_thumb32(hw0, hw1, bus)
    } else {
        self.execute_thumb16(hw0, bus)
    }
}
```

Inside `execute_thumb16` and `execute_thumb32`, use nested `match` on extracted
bit fields. Rust compiles `match` on integers into efficient jump tables or binary
search trees — this is equivalent to a large switch statement in C but with
exhaustiveness checking.

**Why not a lookup table?** A 64K-entry lookup table for 16-bit opcodes would be
64KB — it blows L1 data cache. The `match`-based decoder keeps the hot path in
L1 instruction cache where it belongs.

**Why not computed goto?** Rust doesn't have computed goto. But `match` on a
dense integer range compiles to a jump table anyway when the compiler determines
it's profitable. Trust the compiler + PGO.

### 6.3. Register File

```rust
#[repr(C)]  // Predictable layout for cache locality
struct Registers {
    r: [u32; 16],      // R0-R12, SP(R13), LR(R14), PC(R15)
    xpsr: u32,         // Combined APSR + IPSR + EPSR
    primask: u32,
    basepri: u32,
    faultmask: u32,
    control: u32,
    // Banked SP
    msp: u32,           // Main Stack Pointer
    psp: u32,           // Process Stack Pointer
    msp_ns: u32,        // Non-secure MSP (TrustZone)
    psp_ns: u32,        // Non-secure PSP
    // FPU
    s: [f32; 32],       // S0-S31
    fpscr: u32,         // FP status/control
}
```

Keep the entire struct under 256 bytes so it fits in 4 cache lines.

### 6.4. Instruction Cycle Accounting

Each `execute_*` function returns the number of cycles consumed. The core
tracks its local cycle debt:

```rust
struct CortexM33 {
    regs: Registers,
    /// Cycles remaining on current multi-cycle operation.
    /// When > 0, step() decrements instead of fetching.
    stall_cycles: u32,
    // ...
}

impl CortexM33 {
    fn step(&mut self, bus: &mut Bus) {
        if self.stall_cycles > 0 {
            self.stall_cycles -= 1;
            return;
        }
        let cycles = self.decode_execute(bus);
        // cycles includes bus latency from the fabric
        self.stall_cycles = cycles.saturating_sub(1);
    }
}
```

This means `step()` is called once per master clock cycle and either does real
work or counts down a stall. The bus fabric injects additional stall cycles when
it detects contention.

### 6.5. Fault Handling

Faults are part of the Cortex-M33 architecture, not error conditions in the
emulator. The real hardware uses faults for control flow — notably, the bootrom
probes for flash presence by attempting a read and catching the BusFault.

Fault types (all must be emulated):

| Fault | Vector | Trigger |
|-------|--------|---------|
| HardFault | 3 | Escalated fault, or fault during fault handler |
| MemManage | 4 | MPU violation, XN execute |
| BusFault | 5 | Access to unmapped address, bus error |
| UsageFault | 6 | Undefined instruction, unaligned access, div-by-zero |
| SecureFault | 7 | TrustZone violation (stub in v1) |

On fault:
1. Check if the fault is enabled (SHCSR register) — if not, escalate to HardFault
2. Stack the exception frame (R0-R3, R12, LR, PC, xPSR) — 8 words
3. Set LR to EXC_RETURN magic value
4. Load PC from vector table entry
5. Enter handler mode, update IPSR

This is the same exception entry mechanism as normal interrupts (Section 6.4 in
the core design, reused for faults). Faults just have fixed vector numbers and
priority rules.

**Required for Phase 3** (bootrom depends on BusFault for flash probing).

### 6.6. Coprocessor Port

The Cortex-M33 coprocessor port transfers up to 64 bits per cycle between the
processor and closely-coupled hardware. RP2350 defines four coprocessors:

| CP | Name | Function | Phase needed |
|----|------|----------|--------------|
| 0 | GPIOC | Fast GPIO read/write via SIO | Phase 3 (bootrom uses it) |
| 4,5 | DCP | Double-precision FP acceleration | Phase 3 (bootrom flash CRC) |
| 7 | RCP | Redundancy/canary assertions | Phase 3 (bootrom stack canaries) |
| 10,11 | FPU | Single-precision floating point | Phase 7 |

If a coprocessor instruction targets a CP that is not present or not enabled
(CPACR register), the core raises a UsageFault (NOCP). The bootrom executes RCP,
DCP, and GPIOC instructions during early init — so these must be at least stubbed
before the bootrom can run.

**Minimum stubs for Phase 3:**
- **RCP**: Accept salt write (MRC/MCR to CP7). Return dummy canary values.
  Don't assert NMI. Treat all encodings as valid (skip parity check).
- **DCP**: Accept double-precision operations (CDP/MCR/MRC to CP4/5). Return
  correct results using host f64 (similar to mddosem's FPU approach). The
  bootrom only uses DCP for SHA-256/CRC — a small subset.
- **GPIOC**: Forward MRC/MCR to SIO GPIO registers. Single-cycle.

## 7. PIO Emulation

### 7.1. PIO Architecture

3 PIO blocks, each containing:
- 4 state machines
- 32-instruction shared program memory (per block)
- Per-SM: 2 scratch registers (X, Y), input/output shift registers, clock divider
- TX and RX FIFOs (4 entries each, joinable to 8)

### 7.2. PIO Instruction Set (9 instructions)

| Instruction | Encoding    | Cycles | Description                         |
|-------------|-------------|--------|-------------------------------------|
| JMP         | 000_xxxxx   | 1      | Conditional jump                    |
| WAIT        | 001_xxxxx   | 1+     | Stall until condition (GPIO/IRQ)    |
| IN          | 010_xxxxx   | 1      | Shift N bits into ISR               |
| OUT         | 011_xxxxx   | 1      | Shift N bits out of OSR             |
| PUSH        | 100_0xxxx   | 1      | Push ISR to RX FIFO                 |
| PULL        | 100_1xxxx   | 1      | Pull TX FIFO to OSR                 |
| MOV         | 101_xxxxx   | 1      | Move between registers              |
| IRQ         | 110_xxxxx   | 1      | Set/clear/wait IRQ flag             |
| SET         | 111_xxxxx   | 1      | Write immediate to pins/regs        |

Every instruction takes exactly 1 PIO clock cycle. The PIO clock is derived
from the system clock via a 16.8 fractional divider per state machine.

Side-set and delay bits are encoded in the instruction word and add 0-31
additional delay cycles after the instruction.

### 7.3. PIO Timing

```rust
struct PioStateMachine {
    pc: u8,              // 0-31 program counter
    x: u32,             // Scratch X
    y: u32,             // Scratch Y
    isr: u32,           // Input shift register
    osr: u32,           // Output shift register
    isr_count: u8,      // Bits shifted into ISR
    osr_count: u8,      // Bits remaining in OSR
    clock_div: u32,     // 16.8 fixed-point divider
    clock_acc: u32,     // Fractional accumulator
    delay_count: u8,    // Post-instruction delay countdown
    stall: bool,        // WAIT/PULL/PUSH stall
    // ...
}
```

On each system clock cycle, the SM's fractional accumulator advances. When it
rolls over, the SM executes one PIO cycle (instruction or delay tick). This
gives exact sub-system-clock timing.

## 8. Memory Map

Rough decode on bits [31:28]:

| Bits [31:28] | Range                       | Target               |
|--------------|-----------------------------|-----------------------|
| 0x0          | 0x00000000 - 0x0000FFFF     | ROM (32 kB)           |
| 0x1          | 0x10000000 - 0x13FFFFFF     | XIP (flash, cached)   |
| 0x2          | 0x20000000 - 0x20081FFF     | SRAM (520 kB)         |
| 0x4          | 0x40000000 - 0x4013FFFF     | APB peripherals       |
| 0x5          | 0x50000000 - 0x501FFFFF     | AHB peripherals       |

## 9. Performance Strategy

### 9.1. Budget

At 150 MHz target on a 5 GHz host: **33.3 host cycles per emulated cycle.**

The inner loop (fetch → decode → execute → cycle account → advance clock) must
average under this. Breakdown target:

| Phase            | Host cycles budget |
|------------------|--------------------|
| Fetch (memory read) | 3-5             |
| Decode (match)      | 3-5             |
| Execute             | 5-10            |
| Bus accounting      | 2-3             |
| PIO step (amortised)| 2-3             |
| Overhead            | 5-10            |
| **Total**           | **~25-33**      |

Tight but feasible. mddosem's interpreter achieves similar ratios for x86.

### 9.2. Cache Discipline

- **CPU state struct < 256 bytes** → fits in 4 L1 cache lines.
- **Decode/execute functions**: single compilation unit, PGO-guided layout to keep
  hot paths on the same instruction cache pages.
- **Memory backing arrays** (SRAM, ROM): accessed via raw pointer + offset, no
  bounds checks on the hot path (unsafe block with documented safety invariant —
  address masking guarantees in-bounds).
- **Bus dispatch**: `match` on address bits [31:28], not trait objects. No vtable
  indirection on the hot path.

### 9.3. Profile-Guided Optimisation (PGO)

Build pipeline:
1. `cargo build --release` with `-Cprofile-generate=./pgo-data`
2. Run representative workload (OneROM boot, PIO exercise, interrupt-heavy code)
3. `cargo build --release` with `-Cprofile-use=./pgo-data`

PGO ensures:
- Hot decode branches are predicted correctly
- Hot functions are co-located in the same pages
- Inlining decisions reflect actual execution profiles

### 9.4. Compile-Time Options

See Section 13.4 for the full workspace Cargo.toml. Key points:

- `codegen-units = 1` on the `mdrp2354` core crate only (hot path)
- `lto = "fat"` at workspace level (cross-crate inlining in final binary)
- `opt-level = 3`, `panic = "abort"` (no unwind tables on hot path)

## 10. Testing Strategy (Oracles)

Tests are scaffolding — critical to producing the building, but not part of the
finished product. We build oracles first, then develop against them. The oracle
stack is layered: each layer covers what the one below cannot.

### 10.1. Oracle Stack (Build Order)

| Priority | Oracle | Validates | Cycle counts? | When |
|----------|--------|-----------|---------------|------|
| 1 | Hand-written unit tests | Basic correctness per instruction | Assumed from M4 TRM | Phase 1 day 1 |
| 2 | QEMU differential harness | Full Thumb-2 semantics | No | Phase 1 week 1 |
| 3 | probe-rs cycle counter | Per-instruction cycle timing | **Yes** (ground truth) | Phase 1 week 2 |
| 4 | Wokwi PIO differential | PIO instruction behaviour | PIO clocks only | Phase 6 |
| 5 | Piers' PIO harness | OneROM-specific PIO programs | PIO clocks only | Phase 6 |

We build oracles 1-3 before writing significant emulation code. The test
infrastructure is as important as the emulator and lives in the workspace as
standalone tools.

### 10.2. Layer 1: Hand-Written Unit Tests (Day 1)

For each instruction, write the expected result directly from the ARM Architecture
Reference Manual. No external dependencies. This is the fastest way to get a red
test to write code against.

```rust
#[test]
fn adds_r0_r1() {
    let mut core = CortexM33::new();
    core.set_reg(0, 5);
    core.set_reg(1, 3);
    let cycles = core.execute_one(0x1840); // ADDS R0, R0, R1
    assert_eq!(core.reg(0), 8);
    assert_eq!(core.flag_z(), false);
    assert_eq!(core.flag_n(), false);
    assert_eq!(core.flag_c(), false);
    assert_eq!(core.flag_v(), false);
    assert_eq!(cycles, 1);
}
```

Coverage targets:
- Every Thumb-1 (16-bit) instruction encoding: ~52 base opcodes
- Every Thumb-2 (32-bit) instruction encoding: ~150 base opcodes
- Flag-setting edge cases: zero, negative, carry, overflow, MAX/MIN boundaries
- Property-based tests (proptest): random register state → execute → compare
  against a reference implementation

Initial cycle counts come from the Cortex-M4 Technical Reference Manual (published
per-instruction table, architecturally similar 3-stage pipeline). These are our
best starting assumptions until Layer 3 provides ground truth.

### 10.3. Layer 2: QEMU Differential Harness (Week 1)

QEMU has a Cortex-M33 machine model (MPS2-AN505) with a GDB server. This validates
the full Thumb-2 ISA — including instructions Wokwi can't test (M0+ only supports
Thumb-1, which is roughly a third of our instruction set).

**Architecture:**

```
  ┌──────────────────────┐     ┌──────────────────────┐
  │    QEMU MPS2-AN505   │     │    mdrp2354 emulator  │
  │    (Cortex-M33)      │     │                       │
  │                      │     │                       │
  │    GDB server :3333  │     │    GDB server :3334   │
  └──────────┬───────────┘     └───────────┬───────────┘
             │                             │
             └──────────┬──────────────────┘
                        │
               ┌────────▼────────┐
               │  Diff harness   │
               │  (Rust binary)  │
               │                 │
               │  For each test: │
               │  1. Load binary │
               │  2. Single-step │
               │  3. Read regs   │
               │  4. Compare     │
               └─────────────────┘
```

**Test binary generation:** The harness generates bare-metal ELF binaries
programmatically — one instruction per test, with known register pre-conditions.
`arm-none-eabi-as` assembles each test; the harness loads it into both QEMU and
our emulator, single-steps via GDB RSP, and diffs register state.

```rust
// Pseudo-code for the diff harness
fn diff_test(instruction: &str, pre: &RegisterState) {
    let elf = assemble_test(instruction, pre);

    let qemu_post = run_in_qemu(&elf, pre);
    let emu_post = run_in_emulator(&elf, pre);

    assert_eq!(qemu_post.regs, emu_post.regs,
        "Register mismatch for {instruction}");
    assert_eq!(qemu_post.xpsr & FLAGS_MASK, emu_post.xpsr & FLAGS_MASK,
        "Flags mismatch for {instruction}");
}
```

QEMU validates **semantics** (correct results, correct flags) but NOT cycle
counts. That's Layer 3's job.

**Why not Wokwi for CPU testing?** Wokwi emulates Cortex-M0+ (Thumb-1 only, ~52
opcodes, 2-stage pipeline). Our Cortex-M33 has the full Thumb-2 extension (~200+
opcodes, 3-stage pipeline). Wokwi validates at most a third of our instructions,
and cycle counts differ even for the overlapping subset. QEMU with its M33 model
is strictly superior as a CPU oracle.

### 10.4. Layer 3: Real Hardware Cycle Validation (Week 2)

The only source of truth for cycle counts. ARM doesn't publish a per-instruction
cycle table for Cortex-M33 (unlike M3/M4). We build our own.

**Setup:**

```
[Dev PC] ──USB──► [Debug probe] ──SWD──► [RP2354 target]
                  (Picoprobe, J-Link, or CMSIS-DAP)
```

**probe-rs** (Rust crate, https://probe.rs/) talks SWD directly — no openocd
needed. Supports RP2350.

**On-target test binary:**

```rust
// Flashed to real RP2354
#[entry]
fn main() -> ! {
    // Enable DWT cycle counter
    let mut dcb = cortex_m::Peripherals::take().unwrap().DCB;
    let mut dwt = cortex_m::Peripherals::take().unwrap().DWT;
    dcb.enable_trace();
    DWT::unlock();
    dwt.enable_cycle_counter();

    loop {
        // Wait for host to write test parameters to known SRAM address
        let test = read_test_params(SRAM_MAILBOX);

        // Set up registers per test spec
        setup_registers(&test);

        // Measure
        DWT::reset_cycle_count();
        cortex_m::asm::isb();  // flush pipeline before measurement
        // --- instruction under test executes here ---
        // (injected via the test binary or via debug single-step)
        let cycles = DWT::cycle_count();

        // Write result back to mailbox
        write_result(SRAM_MAILBOX, cycles);
    }
}
```

**Host-side harness (using probe-rs):**

```rust
fn validate_cycle_count(probe: &mut Session, instr: u16, expected: u32) {
    // Write instruction to test slot in target SRAM
    probe.write_word_32(SRAM_MAILBOX, instr as u32)?;

    // Resume target, let it execute one test iteration
    probe.run()?;
    wait_for_halt(probe)?;

    // Read back measured cycle count
    let actual = probe.read_word_32(SRAM_RESULT)?;

    assert_eq!(actual, expected,
        "0x{instr:04x}: expected {expected} cycles, got {actual}");
}
```

This systematically sweeps every instruction encoding and builds a ground-truth
cycle count table specific to the RP2350's Cortex-M33 implementation. This table
replaces our initial M4-derived assumptions and becomes the definitive reference.

### 10.5. Layer 4: Wokwi PIO Differential (Phase 6)

Run identical PIO programs (UART TX, SPI, WS2812) in both Wokwi and our emulator.

## 11. Boot Sequence

At reset, the Cortex-M33 reads the vector table from address 0x00000000:

1. Processor loads initial SP from ROM word 0 (0x00000000) into MSP
2. Processor loads reset vector from ROM word 1 (0x00000004) into PC
3. Core 0 begins executing bootrom at the reset vector address
4. Bootrom initialises clocks, probes for flash (via BusFault), selects ARM/RISC-V
5. Core 1 enters sleep (WFE loop), waiting for vector table via FIFO
6. Bootrom loads second-stage bootloader from flash
7. Second-stage configures XIP, jumps to application

Note: the first bytes of ROM are the vector table (data), not code. The reset
vector (word 1) points to the bootrom's entry function.

For v1, we can:
- Include the real RP2350 bootrom binary (32 kB, publicly available in SDK)
- Let it run on the emulated cores
- This validates our emulation correctness at the deepest level

## 12. Public API Design

The core crate is a library that defines traits + core hardware. Downstream crates
implement those traits. The **binary** (or downstream consumer) is the composition
root that wires everything together.

### 12.1. Composition Root Pattern

The core crate (`mdrp2354`) does NOT depend on `mdrp2354-pio` or `mdrp2354-periph`.
Instead, it defines trait interfaces and accepts implementations via injection:

```rust
// In mdrp2354 (core crate) — lib.rs

/// Top-level emulator. Owns core hardware, accepts external peripherals.
pub struct Emulator {
    cores: [CortexM33; 2],
    bus: BusFabric,
    memory: Memory,       // ROM + SRAM + XIP backing
    sio: Sio,
    clock: Clock,
    // External components — injected, not owned by type
    pio: [Option<Box<dyn PioInterface>>; 3],
    peripherals: PeripheralMap,  // address → Box<dyn Peripheral>
}

/// Builder for wiring up the emulator.
pub struct EmulatorBuilder {
    config: Config,
    pio: [Option<Box<dyn PioInterface>>; 3],
    peripherals: Vec<(u32, Box<dyn Peripheral>)>,  // (base_addr, impl)
}

impl EmulatorBuilder {
    pub fn new(config: Config) -> Self;

    /// Register a PIO block (0, 1, or 2).
    pub fn with_pio(mut self, index: usize, pio: Box<dyn PioInterface>) -> Self;

    /// Register a peripheral at a base address.
    pub fn with_peripheral(mut self, base: u32, p: Box<dyn Peripheral>) -> Self;

    /// Build the emulator. Core hardware (CPU, bus, memory, SIO) is always
    /// present. PIO and peripherals are only active if registered.
    pub fn build(self) -> Emulator;
}
```

The binary (`main.rs`) is the composition root:

```rust
// In src/main.rs — wires everything together
fn main() {
    let uart0 = mdrp2354_periph::Uart::new(/* ... */);
    let clocks = mdrp2354_periph::Clocks::new(/* ... */);
    let pio0 = mdrp2354_pio::PioBlock::new(/* ... */);

    let emu = EmulatorBuilder::new(config)
        .with_pio(0, Box::new(pio0))
        .with_peripheral(0x40070000, Box::new(uart0))
        .with_peripheral(0x40010000, Box::new(clocks))
        .build();
}
```

This keeps the dependency graph clean: core defines interfaces, others implement
them, the binary assembles everything. Downstream consumers (e.g., onerom-emu)
do their own assembly with their own peripheral selection.

### 12.2. Core API Surface

```rust
impl Emulator {
    /// Load a binary image into memory at the given address.
    pub fn load_image(&mut self, addr: u32, data: &[u8]);

    /// Load the bootrom (32 kB at address 0x00000000).
    pub fn load_bootrom(&mut self, data: &[u8]);

    /// Load flash image (appears at XIP address 0x10000000).
    pub fn load_flash(&mut self, data: &[u8]);

    /// Load an ELF binary (extracts segments to their load addresses).
    pub fn load_elf(&mut self, elf_data: &[u8]);

    /// Step the entire system by one clock cycle.
    /// Returns the current cycle count.
    pub fn step(&mut self) -> u64;

    /// Run for N cycles. Returns actual cycles executed.
    pub fn run(&mut self, cycles: u64) -> u64;

    /// Run until a breakpoint, WFI, or cycle limit.
    pub fn run_until(&mut self, limit: u64) -> StopReason;

    /// Read/write GPIO pin state (for external bus modelling).
    pub fn gpio_read(&self, pin: u8) -> bool;
    pub fn gpio_write(&mut self, pin: u8, value: bool);
    pub fn gpio_read_all(&self) -> u64;  // all 48 pins
    pub fn gpio_write_mask(&mut self, mask: u64, values: u64);

    /// Access core state (for debugging / differential testing).
    pub fn core(&self, id: usize) -> &CortexM33;
    pub fn core_mut(&mut self, id: usize) -> &mut CortexM33;

    /// Direct memory access (bypasses bus timing).
    pub fn peek(&self, addr: u32) -> u32;
    pub fn poke(&mut self, addr: u32, value: u32);

    /// Current master cycle count.
    pub fn cycles(&self) -> u64;
}
```

### 12.3. GPIO as the Integration Boundary

Downstream consumers interact with the emulated chip through GPIO pins — the same
way real hardware does. The `gpio_read/write` methods are the integration seam.
This keeps the boundary identical to hardware and avoids leaking emulator internals.

For high-bandwidth downstream use (e.g., OneROM serving ROM data), a callback-based
GPIO notification API avoids polling:

```rust
pub fn set_gpio_callback(&mut self, cb: Box<dyn FnMut(u8, bool)>);
```

### 13.1. Why This Split

**The hot path is narrow.** The inner loop (fetch → decode → execute → bus access
→ cycle tick) touches only `core/`, `bus/`, `memory/`, `sio/`, and `clock/`.
These MUST be in the same crate so the compiler can:
- Inline across decode → memory access (no vtable, no cross-crate boundary)
- Apply PGO-guided function layout within one compilation unit
- Use `codegen-units = 1` effectively for the code that matters

**Everything else is cold by comparison:**
- PIO ticks once per N system clocks (clock divider). The main crate calls
  `pio.step()` once per system clock; if the divider says "not this cycle," it's
  a single branch-and-return. That cross-crate call is noise.
- Peripheral register reads happen orders of magnitude less often than instruction
  fetches. The APB bridge already adds 3-4 cycles of latency — one more function
  call across a crate boundary is invisible.
- Debug is completely off the hot path.

**Parallel agent benefit:** With 4 crates, agents can work on PIO instruction
semantics, peripheral register implementations, GDB protocol, and Thumb-2 decode
simultaneously with zero merge conflicts. The narrow interface contracts between
crates are stable early.

### 13.2. Cross-Crate Interface

The core crate defines traits that PIO and peripherals implement:

```rust
// In mdrp2354 (core crate)
pub trait Peripheral {
    fn read32(&mut self, offset: u32) -> u32;
    fn write32(&mut self, offset: u32, value: u32);
    /// Called once per system clock. Return true if interrupt asserted.
    fn step(&mut self) -> bool;
}

pub trait PioInterface {
    /// Advance by one system clock. Returns GPIO output changes if any.
    fn step(&mut self, gpio_in: u64) -> Option<GpioChange>;
}
```

These traits are NOT on the hot path — they're called through the bus fabric
dispatch, which is already behind an address-range `match`. The hot path
(instruction fetch from SRAM/ROM) never crosses a crate boundary.

### 13.3. Dependency Graph

```
                   mdrp2354 (core)
                   defines: Peripheral, PioInterface traits
                   owns: CPU cores, bus, memory, SIO, clock
                       ▲  ▲  ▲  ▲
                       │  │  │  │
          mdrp2354-pio─┘  │  │  └─mdrp2354-debug
       mdrp2354-periph────┘  └────mdrp2354-test-harness

                       ▼
               src/main.rs (binary)
               The composition root: depends on ALL crates,
               wires trait implementations into EmulatorBuilder
```

Core crate has zero dependencies on the others. It defines the trait interfaces
(`Peripheral`, `PioInterface`) and the `EmulatorBuilder` that accepts trait object
implementations. PIO and periph depend on core for shared types and implement its
traits. The binary is the composition root — it instantiates concrete types from
pio/periph crates and injects them into the `EmulatorBuilder` (see Section 12.1).

```toml
# workspace Cargo.toml
```

## 14. Risks and Open Questions

### 14.1. Cortex-M33 Cycle Counts

ARM doesn't publish per-instruction cycle tables for M33. We're starting from M4
timings and validating against hardware. Risk: some instructions may differ by
1-2 cycles between M4 and M33 in ways we don't catch until late.

**Mitigation:** Build automated cycle-count validation early. Run every instruction
encoding through the DWT CYCCNT on real hardware and diff against emulator.

### 14.2. PIO Accuracy

PIO timing is critical for OneROM (it's bit-banging ROM chip timing). If our PIO
clock divider accumulator doesn't match real silicon exactly, waveforms will drift.

**Mitigation:** Differential test PIO programs against Piers' harness and real
hardware. PIO is deterministic by design — if the accumulator logic is correct,
timing will be correct.

### 14.3. Performance Budget

33 host cycles per emulated cycle is tight. If we miss it, we fall behind
real-time and can't pace the OneROM ↔ mddosem integration correctly.

**Mitigation:** Benchmark early and often. Profile the inner loop from day 1.
If we're over budget, the first optimisation is skipping bus arbitration for
single-core operation (no contention possible).

### 14.4. Real-Time Pacing on Windows

`rdtsc` spin-wait for quantum-based pacing burns a host core at 100%. If the
user needs both the DOS emulator and the RP2354 emulator running real-time
simultaneously, that's at least 2 cores pinned.

**Mitigations:**
- When running as part of mddosem, synchronise on bus transactions instead of
  wallclock (no pacing needed — mddosem drives the clock).
- `rdtsc` requires `constant_tsc` CPU feature (standard since ~2008). Verify via
  CPUID at startup; fail with a clear error if absent — no QPC fallback.
- Quantum size is configurable: coarser quanta reduce spin overhead at the cost
  of sub-quantum timing fidelity.

### 14.5. I-Bus / D-Bus Pipeline Overlap

Each Cortex-M33 core has two AHB ports (instruction fetch + data access) that
operate in parallel. A `LDR` can overlap its memory read with the next
instruction's fetch, making the effective cost 1 cycle in many cases (no data
dependency). Our `step()` → return-cycles model doesn't capture this overlap.

**Mitigation:** Start conservative (no overlap — loads cost 2 cycles to
zero-wait-state targets). The DWT CYCCNT oracle (Layer 3 testing) will reveal
where we over-count. Refine per-instruction based on measured deltas.

### 14.6. DSP Extension Instruction Count

The RP2350's M33 has DSP extensions enabled, adding ~50 SIMD and saturating
arithmetic instructions (SMLAD, QADD, USAD8, SSAT, etc.) on top of base Thumb-2.
Total instruction count is ~200+ base opcodes, not ~150 as estimated for base
Thumb-2 alone. This affects Phase 1 scope but not architecture.

### 14.7. External Toolchain Dependencies

The test harnesses require external tools not managed by Cargo:

| Tool | Needed by | Purpose |
|------|-----------|---------|
| `arm-none-eabi-as` / `gcc` | QEMU diff harness | Assemble test binaries |
| `qemu-system-arm` | QEMU diff harness | Reference M33 emulation |
| USB debug probe + RP2354 board | Cycle sweep harness | Ground-truth cycle counts |
| `object` crate (Rust) | Core crate | ELF parsing for `load_elf()` |

These should be checked at test-harness build time with clear error messages.

### Phase 1: Core MVP
- Thumb-2 decoder + executor (16-bit instructions first, then 32-bit)
- Register file, basic xPSR handling
- Flat memory (SRAM + ROM, no bus fabric yet — single-cycle everywhere)
- Cycle counting per instruction
- Unit tests: per-instruction correctness + cycle count validation
- Differential tests against QEMU (instruction semantics)
- Milestone: **can execute simple Thumb-2 binaries in flat memory**

### Phase 2: Bus Fabric + Memory Map
- AHB5 bus fabric with cycle-accurate arbitration
- APB bridge with correct latency (3 read / 4 write)
- Full address map decode (ROM, SRAM, XIP, APB, AHB, SIO, PPB)
- Atomic access aliases (+0x1000/2000/3000)
- SRAM banking (striped SRAM0-7, non-striped SRAM8-9)
- Milestone: **bus timing matches datasheet, tests pass**

### Phase 3: Interrupts + Faults + Boot
- NVIC (nested vectored interrupt controller)
- Exception entry/return with correct cycle counts
- Fault handling: HardFault, BusFault, UsageFault, MemManage (bootrom needs BusFault for flash probing)
- SysTick timer
- Coprocessor port stubs: RCP (accept salt, dummy canaries), DCP (host f64 math), GPIOC (forward to SIO)
- Load real RP2350 bootrom binary
- Clock tree (enough to boot — XOSC, PLL_SYS, clock muxes)
- Reset controller (vector table load: SP from word 0, PC from word 1)
- Milestone: **bootrom runs and reaches "no flash" error path**

### Phase 4: Flash + Full Boot
- XIP cache (16 kB, 2-way, 2-bank write-back)
- QMI flash interface (enough for XIP reads)
- Load flash image, boot through bootrom into application code
- GDB RSP server for debugging
- Milestone: **boots a Pico SDK "blinky" from flash to main()**

### Phase 5: Dual Core + SIO
- Core 1 wake via inter-processor FIFO
- Hardware spinlocks
- Doorbells
- CPUID differentiation
- Integer divider, platform timer
- Milestone: **dual-core SDK examples run correctly**

### Phase 6: PIO
- PIO decoder + executor (9-instruction ISA)
- Fractional clock dividers
- TX/RX FIFOs, joining modes
- Autopush/autopull
- GPIO pin model (input/output, PIO function select)
- DMA integration (at least basic channel support)
- Differential tests against Piers' harness + real hardware
- Milestone: **PIO UART/SPI examples produce correct waveforms**

### Phase 7: Full Coprocessors + FPU
- Single-precision FPU (CP10/11) — full IEEE 754 single-precision
- GPIO coprocessor (CP0) — full instruction set (64-bit GPIO read/write)
- DCP (CP4/5) — full double-precision instruction set, cycle-accurate
- RCP (CP7) — full assertion/canary logic with random delays
- Lazy FP context save (LSPEN in FPCCR)
- Milestone: **floating-point SDK code runs correctly, coprocessors cycle-accurate**

Note: Phase 3 provides minimal coprocessor stubs (enough for bootrom). Phase 7
completes the implementations with full instruction coverage and cycle accuracy.

### Phase 8: Polish + Performance
- PGO build pipeline
- Comprehensive benchmarking
- Real-time pacing mode (rdtsc quantum-based, Section 5.3)
- Remaining peripheral stubs (UART, SPI, I2C — enough for SDK init)
- GPIO callback API for downstream consumers
- Milestone: **cycle-accurate, real-time capable, API-stable crate**

Phases 1-4 are the critical path to "something useful." Phases 5-8 are the path
to "downstream-ready." Downstream repos (OneROM emulator, mddosem integration)
begin work once Phase 6 is complete.
