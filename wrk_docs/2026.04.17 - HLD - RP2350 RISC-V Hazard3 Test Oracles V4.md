## 1. Goal

Verify the Hazard3 port on RP2354 to a level equivalent to the Cortex-M33 side: an ISA-level differential against QEMU (the `qemu_diff_m33` analogue) and a silicon differential against real RP2354 Hazard3 cores (the `probe_diff_rp2350` analogue). Two independent oracles because each catches bugs the other cannot.

**Plan D ceiling.** If Phase 1 discovers no viable silicon path (probe-rs target file lacks Hazard3, or no oracle path is feasible), this HLD's V1 verification ceiling leaves Hazard3 customs / Xh3Irq / MTIP/MSIP fan-out / WARL rounding / outside-reservable-region atomics at Unit-tested for V1 — roughly a third of the Hazard3 surface area by row count in the audit matrix. This is an accepted outcome, not a hidden failure mode.

## 2. Why two

| Oracle | Catches | Misses | Hardware? |
|---|---|---|---|
| **QEMU diff** (`qemu_diff_riscv32`) | RV32IMAC instruction semantics (including inside-reservable-region A-ext), base Zicsr CSRs, flag/`mstatus` shuffles, trap entry shape | Hazard3 custom CSRs (`meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` at `0xBE0..0xBE5`, `h3.misa` at `0xBF1`); Xh3Irq arbitration; outside-reservable-region atomics per RP2350 §2.1.6.2; `h3.block`/`h3.unblock`; cycle counts; WARL rounding where Hazard3 and QEMU's generic rv32 diverge | No |
| **Silicon diff** (`probe_diff_riscv_rp2350` + `silicon_cycle_oracle_riscv_rp2350`) | Everything QEMU misses: Hazard3 CSR semantics against real RTL, Xh3Irq, outside-reservable-region atomics, cycle accuracy (`mcycle` via mailbox — not debug-halt-readable), WARL rounding, level-sensitive `mip` timing | Nothing architecturally. Requires Pico probe + RP2354 in RV-select state. Not CI-runnable. | **Yes** |

Independence is at the implementation and test-corpus levels: QEMU is an independent implementation, silicon is the implementation being verified. Our emulator's Hazard3 decoder is the *thing under test* in both oracles by construction. The `riscv_gen.rs` fuzz generator is the only substantive shared harness code between the two; §3 names the property-test mitigation.

## 3. Non-goals

- No umbrella binary. Separate `cargo run -p mdpicoem-harness --bin <name>` per oracle.
- No feature flags, no cargo features, no env vars.
- No cross-arch test framework. `riscv_gen.rs` is Hazard3-only.
- No riscv-tests / riscv-arch-test / riscof / Spike dependency. Reconsider if Phase 2 fuzz under-samples.
- No SDK firmware support (core HLD Q4).
- No WARL-exhaustion oracle in V1.

**Shared-code hazard.** `riscv_gen.rs` is used by QEMU-diff and silicon-diff. Phase 2 LLD ships a property test against a hand-rolled reference encoder. The Hazard3 decoder is under test in both oracles — bugs surface as divergence; that is the whole point.

## 4. Phasing

Three phases, LLDs written just-in-time. Phase 2 is independent of Phase 1.

### Phase 1 — Probe-rs Hazard3 attach spike (≤1–2 days)

**Question.** Can `probe-rs 0.31` reach a Hazard3 core on RP2354, and at what capability level?

**Pre-spike precheck.** Inspect the probe-rs RP2350 target YAML (offline file inspection — typically `probe-rs/targets/RaspberryPi.yaml`) for a RISC-V core stanza. If absent, Phase 1 halts at **Plan D**: upstream probe-rs target-file work required.

**ARM-vs-RV mode detection.** After attach, `Core::architecture()` must return `Riscv`. **Plus a positive sanity probe**: read `mhartid` (CSR 0xF14) and verify it returns 0 or 1 (the two Hazard3 harts), not a generic unsupported-CSR response. `architecture()==Riscv` with a broken/incomplete probe-rs RV implementation is a plausible "green on paper, nonsense in practice" failure the sanity probe closes.

**Getting the RP2354 into RV mode.** Procedure lives in `RUNBOOK.md` (new section, added in Phase 1 PR): `CHIP_INFO` OTP fuses, POWMAN `CHIP_RESET.ARCH_SEL` soft-override, re-power sequence.

**Deliverable.** ~150 LoC throwaway `crates/mdpicoem-harness/src/bin/riscv_probe_spike.rs`. Deleted when Phase 3 LLD lands (`smoke_per_core_cyccnt_rp2350` precedent).

**Capability matrix** (5 probes):

| # | Capability | Gates |
|---|---|---|
| 1 | Attach exposes `RiscvCore` for both harts | Everything |
| 2 | Read/write GPRs | Pre- and post-state |
| 3 | Read/write CSRs via `read/write_core_reg` | Whether CSR-diff needs instruction-splice proxy |
| 4 | `set_hw_breakpoint` + `run` + `wait_for_core_halted` | HW breakpoint vs SW-breakpoint path |
| 5 | `core.step()` single-step semantics | Stepping vs mailbox |

The spike additionally records two empirical data points that do *not* gate path selection (because the cycle oracle is always mailbox-shaped and soak can fall back to quiescent-only): whether `mcycle` ticks during single-step, and whether halting with `mip[11]` asserted resumes cleanly without spurious traps.

**Phase 1 also spikes one operational question** on behalf of Phase 3: **can ARCHSEL be flipped via SWD between soak passes without physical access?** That is, is there a POWMAN sequence the host can drive over SWD (hold reset via CTRL_AP, write `CHIP_RESET.ARCH_SEL` via bootrom helper or direct bus, release reset) such that the next boot comes up in the selected arch? If yes, soak alternation can be unattended. If no, soak alternation requires manual reboot between ARM and RV passes — **not unattended overnight-capable for cross-arch soak**, though single-arch soak remains unattended. Phase 3 LLD picks the soak mode accordingly.

**Decision tree** (4 rows):

| Outcome | Capabilities | Path | Phase 3 cost |
|---|---|---|---|
| **Full** | All 5 pass | Path A — probe-rs direct for semantic oracle; mailbox for cycle oracle. | ~1 week semantic + ~3 days cycle |
| **Partial** | 1 + 2 pass; any of 3/4/5 fails (plus the halt-under-IRQ or mcycle-under-step fallback scenarios noted above) | Mix-and-match: Path A for what works, instruction-splice proxy for CSRs (if 3 fails), SW `ebreak` sentinels (if 4 fails), mailbox for scenarios that trip. Phase 3 LLD picks the exact mix after the spike reports. | +3–7 days |
| **Mailbox** | 1 + 2 pass; 3/4/5 all fail | Path C — firmware stub uploaded via SWD memory-write; host polls SRAM mailbox. Protocol reuses `silicon_cycle_oracle_rp2350`; stub is RV-native. | ~2 weeks + per-scenario firmware |
| **Plan D** | Even attach (1) or memory-write fails, or precheck found no RV stanza | Accept silicon gap. Hazard3 customs / Xh3Irq / outside-region atomics / cycle accuracy / WARL silicon-validation stay **Unit-tested only**. `tech_debt.md` entry with named triggers (below). | 0 |

**Mailbox requires attach (#1) + memory-write.** All three non-Plan-D outcomes depend on probe-rs being able to attach and issue SWD memory-writes; Plan D is the only outcome where even mailbox is unavailable.

**Plan D triggers** (named in the `tech_debt.md` entry; 90-day recurring review assigned to Arthur):
1. probe-rs ships a minor release with RP2350 RISC-V target-file support landed.
2. A second Pico probe + RP2354 board available for cross-arch parallel soak.
3. Upstream Raspberry Pi contributes a probe-rs target YAML stanza for RV.

**Phase 1 LLD** pins: probe-rs API call sequence, target-YAML path, RV-mode runbook pointer, ARCHSEL-via-SWD investigation result, PASS/FAIL matrix format. Written day-of.

### Phase 2 — QEMU differential oracle

Binary: `qemu_diff_riscv32`. GDB port: **3335**.

**QEMU invocation — pinned in LLD after empirical check.** First LLD step runs `qemu-system-riscv32 -cpu help` and `-cpu rv32,help` on the installed QEMU (`C:\Program Files\qemu\qemu-system-riscv32.exe`) and pins the invocation against what it accepts. Known-good elements: `-machine none -bios none -m 8M -nographic -icount shift=0,align=off,sleep=off -gdb tcp::3335 -S -kernel <bin>`. `QemuProcess` gains a `QemuProfile::RISCV32_RP2350` variant.

**CSR-diff mechanism — deferred to LLD post-empirical-check.** LLD first checks whether QEMU's RISC-V GDB stub exposes CSRs via `qXfer:features:read`. Outcomes:
1. Stub exposes the minimum CSR set directly → primary path.
2. Stub is GPR-only → instruction-splice proxy: prelude/epilogue `csrr`s into an SRAM scratchpad which the debugger reads.

**Proxy self-masking risk, explicitly acknowledged.** The proxy executes `csrr`/`csrw` on both sides for every test. A bug in our emulator's `csrr` for one of the diff-set CSRs that happens to agree with QEMU's `csrr` would be masked. Mitigation: (a) the Zicsr semantic subset is **excluded** from the proxy mechanism (diffed via trap/post-state side-effects instead — the Zicsr instructions themselves cannot be their own instrumentation); (b) the 7-CSR diff set is the final bounded case where silicon is the definitive oracle — Phase 3 LLD revalidates those specific CSRs against real Hazard3 RTL, closing the mask case. Read-side-effect CSRs (`meinext` clears `meifa` on read) are **never** in any diff path.

**Minimum CSR diff set:** `{mstatus, mcause, mepc, mip, mie, mtvec, mscratch}`. `mtval` excluded (Hazard3 hardwires 0; QEMU populates on faults).

**WARL rounding.** Hazard3 and QEMU round differently on at least `mstatus.MPP` and out-of-range `mcause` writes. Disposition is reactive: when fuzz hits a WARL-divergence, the LLD pins a per-field mask on the QEMU side (or skips the variant). No up-front enumeration — silicon is the authoritative WARL oracle (§6).

**Fuzz classes** (exact sample weights in LLD):
- RV32I ALU (register + immediate).
- RV32I memory (aligned load/store).
- RV32I misaligned load/store (exercises `mcause` 4/6 paths).
- RV32I branch/jump.
- RV32I upper (lui/auipc) + PC-relative pairs.
- RV32M.
- RV32A inside reservable region (addresses pre-primed to `0x2000_0000..0x2008_2000`).
- RV32C with Zcmp quadrant-2 encoding sweep (exhaustive over Zcmp-reachable bit patterns).
- Zicsr (minimum CSR set; read-side-effect CSRs excluded).
- Zifencei self-modifying probe.
- CSR-side-effect chains (`csrrw mstatus` → branch) exercising pipeline/hazard interaction.

Single-instruction focus mirrors `qemu_diff_m33` precedent. Multi-instruction sequence classes (branch-into-illegal, load-use hazards, atomic-then-branch) are deferred — if silicon reveals divergences that single-instruction fuzz didn't catch, add them in a follow-up.

**Unknown-opcode escalation.** In fuzz mode, our emulator's `warn!` for unknown-opcode escalates to test failure. QEMU's `mcause=2` is the expected reference.

**Phase 2 LLD** pins: QEMU invocation post-empirical-check, CSR-diff mechanism, fuzz generators, `riscv_gen.rs` property test against a hand-rolled reference encoder.

### Phase 3 — Silicon oracle (shape set by Phase 1)

Two binaries because `mcycle` has different constraints from register state:
- **`probe_diff_riscv_rp2350`** — semantic oracle. Path per Phase 1 outcome.
- **`silicon_cycle_oracle_riscv_rp2350`** — cycle oracle. **Always mailbox-shaped**, because `mcycle` is a CSR (not bus-mapped like DWT CYCCNT on ARM) and halts during debug per RISC-V debug §4.9.1.

**Cycle stub contract.** K-delta protocol from `silicon_cycle_oracle_rp2350` transfers; stub is RV-native:
- Prologue programs XOSC → PLL_SYS → clk_sys to the same pinned frequency the ARM cycle oracle uses. Default boot leaves clk_sys on ROSC (~6 MHz, ±jitter); cycle deltas against ROSC are below signal. **LLD commitment:** verify this CLOCKS sequence actually converges in RV mode before adopting (POWMAN's `CHIP_RESET.ARCH_SEL` path may leave different reset defaults in `CLK_*_CTRL.ENABLE` bits); if not, re-derive from datasheet §5.x.
- `csrrwi x0, mcountinhibit, 0` clears inhibit bits.
- Per iteration: JAL in, `csrrs t0, mcycle, x0` + `csrrs t1, mcycleh, x0`, run case, re-read, write delta to mailbox, JAL out.
- K-delta (K=101 vs K=201) cancels per-invocation framing.

**SW breakpoint path (Partial outcome where capability #4 fails):**
- `ebreak` (0x00100073) or `c.ebreak` (0x9002), aligned to preceding instruction granule.
- Issue `fence.i` after writing sentinel (real silicon needs prefetch flush).
- Enter test slot via JAL/JALR.

**Silicon-only test categories:**

| Category | Tests | Depends on |
|---|---|---|
| Hazard3 custom CSR window | `meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` against real RTL | core HLD P4 |
| Xh3Irq priority arbitration | Nested preempt, `meinext.update` auto-clear of `meifa`, IRQ-coincident-with-mret | core HLD P4 |
| Atomics outside reservable region | `amo*.w` → `mcause=7`; `lr.w`/`sc.w` → infinite loop (RP2350 §2.1.6.2) | core HLD P3 |
| `mip[3]`/`mip[7]` level-sensitive timing | SIO write → `mip` observable; IRQ during `csrrw mstatus`/`mie` race | core HLD P4 |
| Cycle accuracy | `mcycle` deltas per instruction / short sequence | Cycle oracle |
| `mcycle`/`mcycleh` wrap | 32→64 bit transition; `mcycleh` sampling discipline | Cycle oracle |
| Reservation granule | Empirical byte granularity of `sc.w` invalidation | core HLD P3 |
| WARL rounding | Hazard3-rounded value in each WARL field; Phase 3 LLD may expand beyond fuzz-hit fields if coverage gaps surface | core HLD P2 CSRs |
| CSR-proxy cross-check | Revalidate the 7-CSR QEMU-diff set against real Hazard3 values (closes the shared-bug mask case from §Phase 2) | Semantic oracle path |

**Concurrent probe use (core HLD Q7).** RP2354 ARCHSEL latches at reset. Cross-arch soak depends on the Phase 1 ARCHSEL-via-SWD investigation:
- If SWD-automated ARCHSEL flip works: `test_silicon` soak runs serialised alternating passes (ARM soak → reboot + re-arm + RV soak → reboot + re-arm + repeat) under host control. Unattended.
- If only manual reboot works: cross-arch soak is **not unattended**; single-arch soak is unattended on each board separately. Two-board parallel remains a rig upgrade.

**Phase 3 LLD** (after Phase 1) specifies: path selection from spike matrix, mailbox stub encoding, `test_silicon` orchestrator changes (per-case filter prefix `rv:`, watchdog tuning, probe-serial + ARCHSEL state tracking, soak-unattended-or-not decision), Plan D `tech_debt.md` entry if triggered.
