# LLD: Clock Tree — Boot Clock Fix

**Version:** 1.0.0
**Date:** 2026-04-13
**Scope:** Fix the emulator's boot clock speed so firmware runs at the
correct rate without PLL configuration.

**Revision history:**
- v0.1.0 — Full clock tree model (PLL, CLOCKS mux, dynamic Pacer).
  Reviewed by three agents. Verdict: over-scoped. Three critical design
  bugs (Pacer missing `overhead` field, u32 overflow in PLL math,
  division-by-zero on unconfigured PLL). No current firmware exercises
  the PLL path. Scaled back.
- v1.0.0 — Minimal fix based on bootrom evidence. This version.

## 1. Problem

The emulator hardcodes `sys_clk_hz = 150_000_000` at construction. The
actual RP2350 boots on ROSC (~6.5 MHz), and the CPU stays there unless
firmware configures the PLL and switches the CLOCKS mux. Our blinky
firmware does neither — it just toggles GPIO in a loop. On real hardware
the delay loop takes ~154ms (visible 3 Hz blink); on our emulator it
takes ~6.7ms (invisible).

## 2. Evidence: Bootrom Does Not Configure Clocks

Reviewed `roms/arm-bootrom.dis` for the flash boot path
(`___stepx_flash_boot` at 0x3dda). Findings:

- The bootrom **reads** CLK_REF_CTRL (offset 0x030 from CLOCKS base
  0x40010000) as a status check, but **does not write** any CLOCKS
  registers on the flash boot path.
- The bootrom **does not** enable XOSC or configure PLL_SYS for flash
  boot. (PLL_USB is configured only on the nsboot/USB boot path.)
- The CPU runs at **ROSC (~6.5 MHz)** through the entire bootrom and
  into user code for normal flash boot.

This means: for our blinky (and lcd_demo, and benchmark), the correct
boot clock is ROSC. No PLL or XOSC modelling is needed for these
firmwares.

## 3. What We're Changing

Two things:

### 3.1. Default sys_clk_hz → ROSC frequency

```rust
// lib.rs
const ROSC_FREQ_HZ: u32 = 6_500_000;

impl Default for Config {
    fn default() -> Self {
        Self { sys_clk_hz: ROSC_FREQ_HZ }
    }
}
```

And the matching default in `clock/mod.rs`:

```rust
pub fn new() -> Self {
    Self { cycles: 0, sys_clk_hz: 6_500_000 }
}
```

Callers that explicitly pass `Config { sys_clk_hz: 150_000_000, .. }`
are unaffected. Only `Config::default()` changes.

**Impact on existing tests:** 12 tests use `Config::default()`. None
depend on `sys_clk_hz` for cycle counting — it is purely informational
(feeds the Pacer for wall-clock pacing). `sys_clk_hz` is never read by
`step()`, `run()`, or any instruction execution logic. Verified by
tracing the field through `lib.rs`, `clock/mod.rs`, `bus/mod.rs`.

### 3.2. ROSC STATUS stub

The bootrom reads ROSC STATUS. Currently ROSC (0x400E8000) is not
handled in the bus dispatch — reads fall through to the HashMap and
return 0. Add a minimal stub:

```rust
// In bus read32 dispatch:
0x400E_8000 => self.rosc_read(offset),

// In peripherals.rs:
fn rosc_read(&self, offset: u32) -> u32 {
    match offset {
        0x018 => (1 << 31) | (1 << 12),  // STATUS: STABLE | ENABLED
        _ => 0,
    }
}

// In bus write32 dispatch:
0x400E_8000 => {}  // Accept writes, ignore
```

The bootrom also writes ROSC registers during some init paths; the
accept-and-ignore handler is sufficient.

## 4. What We're NOT Changing

- **No PLL model.** No firmware exercises PLL configuration today.
  Deferred until SDK firmware is loaded (see §7).
- **No CLOCKS mux resolution.** The existing stubs (accept writes,
  return stored values) are sufficient for flash boot.
- **No dynamic sys_clk_hz.** The Pacer is constructed once at the boot
  frequency. No `update_sys_clk_hz` method, no per-quantum polling.
- **No ClockTree struct.** The clock speed is a static constant, not a
  computed cache.
- **No Config rework.** `Config::sys_clk_hz` keeps its current
  semantics (initial clock frequency). Only the default changes.

## 5. Showcase App Impact

The `mdrp2354-app` sim thread uses `Config::default()`. After this
change, the Pacer starts at 6.5 MHz. Effects:

| Firmware | Before | After |
|----------|--------|-------|
| blinky | LED toggles every ~6.7ms (invisible) | LED toggles every ~154ms (visible 3 Hz blink) |
| lcd_demo | LCD refreshes at ~1 kHz | LCD refreshes at ~43 Hz (still smooth) |
| benchmark | Completes in ~67ms wall time | Completes in ~1.5s wall time |

The benchmark integration test has a 10s deadline — 1.5s is well within
budget. Cycle counts are unchanged (cycle counting is clock-independent).
REFERENCE_TABLE values remain valid.

The showcase app's `sim.rs` initialises the Pacer with
`Config::default().sys_clk_hz` (or reads it from the config). After this
change, it gets 6.5 MHz. No code changes needed in the app — the Config
change propagates automatically.

## 7. Tests

1. **Unit test: ROSC STATUS read.** `bus.read32(0x400E_8018)` returns
   `(1 << 31) | (1 << 12)`.

2. **Unit test: Config default.** `Config::default().sys_clk_hz ==
   6_500_000`.

3. **Existing tests: run `cargo test --release`.** All must pass. None
   depend on the default being 150 MHz (verified).

4. **Showcase app tests: `cargo test -p mdrp2354-app --release`.** All
   23 tests must pass. The benchmark test's 10s deadline accommodates
   the slower 6.5 MHz pacing (1.5s vs 67ms).

## 8. When to Build the Full Clock Tree

The trigger is concrete: **loading firmware that writes PLL/CLOCKS
registers and expects sys_clk_hz to change mid-execution.** Specifically:

- Running Pico SDK-compiled firmware where `runtime_init` configures
  PLL_SYS → 150 MHz.
- Running nsboot-path firmware that needs PLL_USB.

When that happens, revive v0.1.0 of this LLD, fix the three critical
bugs identified during review (Pacer overhead field, u64 in PLL math,
div-by-zero guard), and implement. The existing stubs already accept
PLL/CLOCKS writes silently, so the foundation is in place.

## 9. Known Issues (Pre-existing, Not Fixed Here)

1. **`clocks_write` does not handle atomic aliases.** The bus dispatch
   for CLOCKS writes (`bus/mod.rs:809`) does not pass the alias
   parameter (SET/CLR/XOR). Writes via the SET alias (0x40012000) do a
   raw overwrite instead of OR-ing bits. The bootrom uses SET alias for
   CLOCKS on some paths (literal at `arm-bootrom.dis:7435`). This does
   not affect the flash boot path (which doesn't write CLOCKS), but
   would need fixing for nsboot or SDK clock init. Filed as a known
   issue, not addressed here per multi-agent rules (pre-existing code
   not authored by us).

2. **XOSC/PLL stubs are always-stable/always-locked.** Fine for current
   use. Would need startup-delay modelling for high-fidelity PLL
   simulation.
