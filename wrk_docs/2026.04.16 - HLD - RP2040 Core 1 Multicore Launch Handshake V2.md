# HLD — RP2040 Core 1 Multicore Launch Handshake — V2

**Date:** 2026-04-16
**Crate scope:** `crates/mdrp2040` only (mdrp2350 is off-limits — concurrent agent).
**Driver:** PicoGUS v4.0.0 calls `multicore_launch_core1`. Current placeholder in `lib.rs:514 maybe_wake_core1` wakes core 1 at the reset vector on any non-zero `SIO_FIFO_WR` push; PicoGUS lands at the wrong entry, its I2S service loop never starts.

**V2 changes from V1:**
- State-machine armed iff `core1_halted` — parameter threaded through `Sio::fifo_wr`. Removes "runs unconditionally" compromise and its three downstream hazards (token drop, coincidental-IPC pollution, under-quantum race).
- Handshake pushes are **consumed** by the FSM; `val` is never put in `fifo_to_core1`. Removes the "drain at wake" side-effect.
- Wake path clears `event_flag[1]` and resets `CONTROL=0`, matching `direct_boot_from_flash` scope.
- T8 hand-rolled Thumb dropped; T9 pure-Rust scripted-sender test added.
- Protocol description (§1) corrected re: what the bootrom actually sends at seq=0.
- `Sio::reset()` wiring for handshake state added.
- Meta: §3.4 notes this HLD is necessary but not sufficient for PicoGUS audio (DMA + trace capture still blockers per tech_debt).

---

## 1. Protocol summary (oracle)

Transcribed from pico-sdk 2.1.1 `src/rp2_common/pico_multicore/multicore.c` lines 171–203 and pico-bootrom-rp2040 (tag b2) `bootrom/bootrom_rt0.S` lines 313–391. Copies saved under `wrk_scratch/multicore-research/`.

### Sender (`multicore_launch_core1_raw`)

```
cmd_sequence = { 0, 0, 1, (uint32_t)vector_table, (uint32_t)sp, (uint32_t)entry }
seq = 0
while seq < 6:
    cmd = cmd_sequence[seq]
    if cmd == 0:
        drain fifo_to_core0                ; multicore.c:192
        __sev()                            ; multicore.c:194
    push_blocking(fifo_to_core1, cmd)      ; multicore.c:196
    response = pop_blocking(fifo_to_core0) ; multicore.c:197 — WFE loop on VLD
    seq = (cmd == response) ? seq + 1 : 0  ; multicore.c:199
```

Sender pushes `entry` with Thumb bit set (sdk comment multicore.c:183).

### Receiver (`wait_for_vector` in mask ROM b2)

```
loop:
    drain fifo_to_core1                    ; handshake_loop, bootrom_rt0.S:341-343
    send(fifo_to_core0, 0)                 ; line 348-349: mov r0,#0; bl send_and_then
    r0 = recv_or_restart(fifo_to_core1)    ; bootrom_rt0.S:381-391; if 0, restart
    if r0 != 1: restart                    ; line 351-352
    send(fifo_to_core0, r0)                ; line 354: bl send_and_then (r0=1; echo)
    r0 = recv_or_restart(fifo_to_core1)    ; receive VTOR (0 => restart)
    str r0 -> M0PLUS_VTOR                  ; line 355
    send(fifo_to_core0, r0)                ; line 357: echo VTOR
    r0 = recv_or_restart(fifo_to_core1)    ; receive SP
    msr msp, r0                            ; line 359
    send(fifo_to_core0, r0)                ; line 360: echo SP
    r0 = recv_or_restart(fifo_to_core1)    ; receive entry
    r5 = &core1_launch                     ; line 361
    send(fifo_to_core0, r0)                ; line 363: echo entry
    core1_launch:
        clear SCR.SLEEPDEEP                ; line 366-368
        blx r0                             ; line 369
```

Key fact (corrected from V1): the receiver's first send is a **literal 0** (`mov r0, #0` at line 348), not an echo. Subsequent sends echo `r0` which at that point already holds the most recently received word. On the steady-state happy path this is observationally identical to "echo the received word" from the sender's perspective — see table below.

### Observed sender-side echo pattern (steady state)

| seq | sender push | receiver sends (what sender pops) |
|-----|-------------|-----------------------------------|
| 0   | 0           | 0 (literal, from mov r0,#0 path)  |
| 1   | 0           | 0 (from restart via received-0 branch) |
| 2   | 1           | 1 (echo of received word, which was 1) |
| 3   | vtor        | vtor (echo)                       |
| 4   | sp          | sp (echo)                         |
| 5   | entry       | entry (echo)                      |

Sender advances when `cmd == response`; table above satisfies that for every slot.

## 2. Shortcut design

Our core 1 is halted from reset and never runs the real bootrom. We synthesise the handshake response from the Sio FIFO write path, matching the `direct_boot_from_flash` posture (skip ROM, set up arch state directly).

### 2.1 State location and arming

A new field on `Sio` (`crates/mdrp2040/src/bus/sio.rs`):

```rust
#[derive(Default)]
struct MulticoreHandshake {
    seq: u8,                               // 0..=5, resets to 0 on mismatch
    vtor: u32,                             // captured at seq=3
    sp:   u32,                             // captured at seq=4
    pending_launch: Option<Core1Launch>,   // set at seq=5, consumed by Emulator::step
}

pub struct Core1Launch { pub vtor: u32, pub sp: u32, pub entry: u32 }
```

`Sio::reset()` clears `handshake: MulticoreHandshake::default()`.

**Arming rule:** the FSM is **armed iff core 1 is halted**. `Sio::fifo_wr` takes a new parameter `core1_halted: bool`, threaded from `Bus::sio_write32` which reads `bus.core1_halted` — a new `pub bool` field on `Bus` that `Emulator::step` refreshes once per quantum (before either core runs). Rationale:

- When core 1 is awake, `multicore_launch_core1` is a firmware bug on real silicon (sender hangs in `pop_blocking` forever because nobody runs `wait_for_vector`). The FSM must NOT advance, echo, or intercept — exactly mirroring silicon.
- When core 1 is halted, the FSM is the only mechanism that can push into `fifo_to_core0` (core 1 isn't running); so FSM is safe to arm.
- Gating at `fifo_wr` entry eliminates the "coincidental `0,0,1` IPC pollution" hazard.
- `Bus.core1_halted` is refreshed once per quantum, not once per instruction — fine because quantum boundaries are the only transition points (core 1 cannot unhalt mid-quantum from its own execution when halted).

### 2.2 Handshake does not push into fifo_to_core1

When the FSM is armed, `Sio::fifo_wr` **consumes** `val` entirely — does not push into `fifo_to_core1`. Rationale:

- Real bootrom pops each word between echoes (`recv_or_restart` between sends). Core 1 starts post-handshake with an empty RX. Our shortcut replicates this directly: don't push what would immediately be popped.
- Avoids the "drain at wake" side-effect from V1 §2.5. Simpler invariant: FSM-armed writes never touch `fifo_to_core1`.
- On sender's `push_blocking`: `RDY` bit reflects "has space in fifo_to_core1" — always true if we never push. Sender never blocks.
- If FSM is unarmed (core 1 awake), `fifo_wr` falls through to its existing behaviour: push into `fifo_to_core1`, signal `pending_fifo_event`. User IPC unaffected.

### 2.3 Transition table

```
on fifo_wr(val, core=0, core1_halted):
    if !core1_halted:
        // Unarmed path — existing behaviour. Do not touch FSM state.
        push val to fifo_to_core1; set pending_fifo_event = Some(1); return

    // Armed path
    let seq = handshake.seq
    match seq {
        0 => { echo 0;     handshake.seq = if val == 0 { 1 } else { 0 } }
        1 => { echo 0;     handshake.seq = if val == 0 { 2 } else { 0 } }
        2 => if val == 1 { echo 1;   handshake.seq = 3 }
             else        { echo 0;   handshake.seq = 0 }
        3 => if val == 0 { echo 0;   handshake.seq = 0 }
             else        { handshake.vtor = val; echo val; handshake.seq = 4 }
        4 => if val == 0 { echo 0;   handshake.seq = 0 }
             else        { handshake.sp   = val; echo val; handshake.seq = 5 }
        5 => if val == 0 { echo 0;   handshake.seq = 0 }
             else        { echo val;
                           handshake.pending_launch = Some(Core1Launch {
                               vtor:  handshake.vtor,
                               sp:    handshake.sp,
                               entry: val,
                           });
                           handshake.seq = 0 }
    }

    // "echo X" = push X to fifo_to_core0; set pending_fifo_event = Some(0)
```

`echo X` uses the existing `pending_fifo_event = Some(0)` mechanism — identical to how user-code-driven core-1 → core-0 pushes bubble into `event_flag[0]`. No side channel.

### 2.4 Echo timing

Echo is synchronous inside `fifo_wr`: by the time `fifo_wr` returns, `fifo_to_core0` has the echo and `VLD=1`.

- `Emulator::step` quantum default is 64 cycles (`DEFAULT_STEP_QUANTUM`, `lib.rs:59`). Core 0 runs up to ~64 instructions per quantum; push and pop are adjacent in the SDK sender (at most a few instructions apart). Within a single quantum, push → pop sees the echo on the first VLD poll.
- WFE on M0+ is **currently a NOP** (`execute.rs:839`). There is no sleep-on-VLD=0 path to worry about. If WFE is ever implemented, the existing `pending_fifo_event → event_flag[0]` bubble (which we re-use) will wake it.

So the echo-timing design is quantum-independent: works for `step_quantum=1` (per-instruction interleave) and `step_quantum=64` (batch), and is forward-compatible with future WFE plumbing.

### 2.5 Wake semantics — where the launch happens

`Emulator::step` after each core 0 step checks `self.bus.sio.handshake.pending_launch.take()`. When present AND core 1 is still halted:

```rust
if let Some(launch) = self.bus.sio.take_pending_launch() {
    // Invariant: FSM only arms when core 1 is halted, so this branch
    // should always find core 1 halted. Assert to surface logic bugs.
    debug_assert!(self.cores[1].is_halted());

    self.bus.ppb[1].vtor       = launch.vtor;
    self.cores[1].regs.msp     = launch.sp;
    self.cores[1].regs.r[13]   = launch.sp;
    self.cores[1].regs.set_pc(launch.entry & !1);  // Thumb bit strip
    self.cores[1].reset_control_for_launch();       // CONTROL = 0; PSP cleared
    self.bus.event_flag[1]     = false;             // no stale wake signal
    self.cores[1].wake();
}
```

- `entry & !1` matches the `direct_boot_from_flash` convention (`lib.rs:213`). A malformed entry (bit 0 clear) would HardFault on real silicon at `BLX`; our emulator silently strips. Documented as tech_debt; add a TODO entry. Not a blocker because the existing direct-boot path has the same behaviour.
- `reset_control_for_launch()` is a new helper on `CortexM0Plus` that sets CONTROL = 0, so r13 == MSP on the first instruction regardless of residual SPSEL from any prior launch. Keeps the MSP and r[13] assignments consistent.
- No other per-core state reset. SCR.SLEEPDEEP: real bootrom clears it at `bootrom_rt0.S:367-368`. Our existing `direct_boot_from_flash` does not touch SCR. Matching that scope to keep this HLD tight; add tech_debt entry for the SCR divergence (low risk — firmware running normally will not rely on SLEEPDEEP being clear on core 1 wake).
- `fifo_to_core1` is already empty (we never pushed anything during the handshake per §2.2).

The existing `maybe_wake_core1` function body is **replaced** by this block. Call sites at `lib.rs:290` and `lib.rs:301` stay; the function signature and the "called after each core step" discipline are unchanged.

### 2.6 What about the old `event_flag[1]` wake path?

Deleted. The only prior trigger was "core 0 pushed to FIFO while core 1 halted" — now handled entirely by `pending_launch`. `event_flag[1]` remains semantically "core 0 pushed something; wake core 1's WFE if it's sleeping" for the post-launch IPC case (user code on core 1 doing `__wfe` while core 0 pushes a message). That mechanism is unchanged.

## 3. Test plan

New file `crates/mdrp2040/tests/multicore.rs`. All tests gated on successful wake via `pending_launch` consumption in `Emulator::step`.

### 3.1 Unit tests — no firmware

**T1. `handshake_wakes_core1_at_entry`**
Halt core 1 (it is halted after `Emulator::new()`). For each of the 6 words in `{0, 0, 1, 0x2004_0000, 0x2001_0000, 0x2000_1001}`:
1. `emu.bus.write32(SIO_FIFO_WR, word)`
2. Read `emu.bus.read32(SIO_FIFO_ST) & VLD != 0` — assert true (echo in place).
3. Read `emu.bus.read32(SIO_FIFO_RD)` — assert equals `word`.

After the 6th iteration, call `emu.step()` once (so `Emulator::step` consumes `pending_launch`). Assert:
- `emu.cores[1].is_halted() == false`
- `emu.cores[1].regs.pc() == 0x2000_1000` (Thumb bit stripped)
- `emu.cores[1].regs.msp == 0x2001_0000`
- `emu.bus.ppb[1].vtor == 0x2004_0000`

Uses only `Bus::write32` / `Bus::read32` — no private-field access. Exposes no new public surface on `Sio`.

**T2. `restart_on_mismatch_at_seq2`**
Push `0, 0, 0x42`. Read echoes back (expect `0, 0, 0`). Then push the valid sequence `0, 0, 1, vtor, sp, entry`. Step. Assert wake succeeds, VTOR/SP/PC correct. Verifies the FSM restarts cleanly and a new attempt lands.

**T3. `restart_on_zero_at_seq3`**
Push `0, 0, 1, 0`. Read echoes (expect `0, 0, 1, 0`). Step. Assert core 1 still halted (no `pending_launch` was set).

**T4. `vtor_captured_independently_of_entry`**
After a valid handshake, `bus.ppb[1].vtor == launch.vtor` — not the pre-launch default. Covered implicitly by T1 but assert explicitly so regression is localised.

**T5. `second_launch_after_rehalt`**
Run T1 to completion. Manually `emu.cores[1].halt()` to simulate a mode-switch scenario. Run a second handshake with distinct `{vtor2, sp2, entry2}`. Assert second launch's PC/MSP/VTOR take effect. Guards `reset_control_for_launch` path.

**T6. `handshake_while_awake_is_pass_through`**
Call `emu.cores[1].wake()` directly (simulate core 1 running user code). Push `0, 0, 1, V, S, E` through `SIO_FIFO_WR`. Assertions:
- FSM did NOT advance: `emu.bus.sio.handshake_seq()` (new pub getter returns 0).
- No echoes in `fifo_to_core0`: read `SIO_FIFO_ST` — `VLD=0`.
- All 6 words are in `fifo_to_core1` (normal IPC push-through): verify by switching `active_core` and reading `SIO_FIFO_RD` 6 times, assert values `{0, 0, 1, V, S, E}`.
- Core 1 PC unchanged from pre-push value.

This pins the "pass-through when unarmed" contract.

**T7. `echo_visible_on_vld_before_next_instruction`**
After each `SIO_FIFO_WR` write during a valid handshake, read `SIO_FIFO_ST` (no intervening step). Bit 0 (VLD) must be 1. Pins the synchronous-echo contract that §2.4 depends on.

**T8. `fsm_state_resets_on_emulator_reset`**
Push `0, 0` (seq advances to 2). Call `emu.reset()`. Push the full valid sequence from scratch. Step. Assert wake succeeds. Guards `Sio::reset()` wiring per §2.1.

### 3.2 Scripted sender (pure Rust, no Thumb)

**T9. `scripted_sdk_sender_algorithm`**
Pure-Rust driver that mirrors `multicore_launch_core1_raw` (multicore.c:188-200) exactly:

```rust
let cmd_sequence = [0u32, 0, 1, VTOR, SP, ENTRY];
let mut seq = 0;
while seq < 6 {
    let cmd = cmd_sequence[seq];
    if cmd == 0 {
        // drain — read FIFO_RD while VLD
        while emu.bus.read32(FIFO_ST) & VLD != 0 {
            let _ = emu.bus.read32(FIFO_RD);
        }
    }
    // push-blocking: real sender polls RDY then writes. Our `fifo_wr` never
    // blocks in armed state (we don't push into fifo_to_core1), so just write.
    emu.bus.write32(FIFO_WR, cmd);
    // pop-blocking: poll VLD then read.
    while emu.bus.read32(FIFO_ST) & VLD == 0 {
        emu.step(); // in case future WFE-aware path needs step to drive echoes
    }
    let response = emu.bus.read32(FIFO_RD);
    seq = if cmd == response { seq + 1 } else { 0 };
}
emu.step(); // consume pending_launch
assert!(!emu.cores[1].is_halted());
assert_eq!(emu.cores[1].regs.pc(), ENTRY & !1);
```

Replaces V1's heavy T8 (hand-rolled Thumb image). Exercises the actual SDK algorithm end-to-end against our echo/restart/advance semantics, without asking the implementer to write an assembler.

## 5. Invariants and failure modes

- **Arming is the single protection against all misuse.** FSM only runs when core 1 is halted. Awake-core-1 handshake attempts pass through as raw FIFO writes — sender's `pop_blocking` hangs waiting for an echo that never comes. That's what real silicon does too (nothing echoes because no receiver is running). Matches observable silicon behaviour exactly. No silent drop, no panic — just silicon-faithful hang.
- **Restart always goes to seq=0, not seq=N-1.** Matches bootrom. Sender's own `seq = (cmd == response) ? seq + 1 : 0` resets its state too — both sides stay in sync via the same trigger.
- **Echo is synchronous and uses `pending_fifo_event`.** Forward-compatible with WFE-on-RP2040 if that ever lands.
- **No fifo_to_core1 pollution.** Unlike V1, handshake words never land in the RX FIFO core 1 will use post-wake. No drain needed at wake.
- **Thumb bit strip is asymmetric with silicon** for malformed entries. Tech_debt entry created.
- **SCR.SLEEPDEEP is not cleared on wake** (real bootrom does). Tech_debt entry created. Low risk — firmware that calls `multicore_launch_core1` expects to run from a clean state, and SCR on a freshly-reset core is already 0.
