**Date:** 2026-04-26
**Author:** Workstream 2 HLD agent (sonnet)

## 1. Problem statement

`Dma::route_irqs` (`crates/mdrp2350/src/dma.rs:729`) only fans out two of the four DMA IRQ lines. Residual C.2.1 added the storage-side fields `inte2`, `inte3`, `intf2`, `intf3` and made the read paths for `INTE2/INTF2/INTS2/INTE3/INTF3/INTS3` round-trip with the same `(intr | intf_n) & inte_n` predicate as IRQ0/IRQ1, but the controller never asserts NVIC lines `IRQ_DMA_IRQ_2` (12) or `IRQ_DMA_IRQ_3` (13).

**Silent-failure scenario.** Firmware that uses IRQ2 or IRQ3 — for example, partitioning channels across IRQ lines so high-rate ADC channels go to IRQ2 while a slow housekeeping channel goes to IRQ0 — sees this asymmetry:

- Polling `INTS2` works: it reads back `(intr | intf2) & inte2` and a write of 1 to a channel bit clears `intr`.
- Sleeping with `WFI` and waiting for the NVIC to wake the core never returns. `IRQ_DMA_IRQ_2` is never pended on `CoreAtomics`, so the wake-up event never appears.

The two observation paths disagree silently. No corpus scenario covers IRQ2/IRQ3 today (`tech_debt.md:184–189`), so there is no current test signal — the gap is provable only by the new unit tests this HLD adds.

## 3. Reference design — IRQ0/IRQ1 fan-out

The existing path is two textually-symmetric blocks inside `Dma::route_irqs`:

```rust
pub fn route_irqs(&self, atomics: &crate::threaded::CoreAtomics) {
    if (self.intr | self.intf0) & self.inte0 != 0 {
        atomics.assert_irq_shared(IRQ_DMA_IRQ_0);
    }
    if (self.intr | self.intf1) & self.inte1 != 0 {
        atomics.assert_irq_shared(IRQ_DMA_IRQ_1);
    }
}
```

Predicate identical to the corresponding `INTSn` register read at `:378–379`. `assert_irq_shared` ORs the bit into both cores' `irq_pending` words; this is shared-IRQ semantics (DMA IRQs are not core-local).

Single dispatch site: `Bus::tick_dma` at `bus/mod.rs:3133`, invoked by `Bus::tick_peripherals` at `bus/mod.rs:1153` once per per-step cadence (when DMA is not held in reset). All Serial-path test harnesses and Threaded-path CPU workers go through `Bus::tick_dma`.

## 4. Proposed design — IRQ2/IRQ3 fan-out

**Shape:** add two more `if` blocks, structurally identical to IRQ0/IRQ1, after the existing pair. Do **not** refactor into a loop. The duplication is exactly four lines, two repeats — well under the "three repeats" threshold for justifying an abstraction. A loop would force `INTE`/`INTF` storage into an array, which is a larger refactor than this fix should ever be.

**Imports.** Extend the existing `use crate::irq::{IRQ_DMA_IRQ_0, IRQ_DMA_IRQ_1};` at `dma.rs:42` to include `IRQ_DMA_IRQ_2, IRQ_DMA_IRQ_3`.

**Body.** After the IRQ1 block at `dma.rs:734–736`, append:

```rust
if (self.intr | self.intf2) & self.inte2 != 0 {
    atomics.assert_irq_shared(IRQ_DMA_IRQ_2);
}
if (self.intr | self.intf3) & self.inte3 != 0 {
    atomics.assert_irq_shared(IRQ_DMA_IRQ_3);
}
```

**Comment housekeeping.** Trim the "Not routed to NVIC IRQ_DMA_IRQ_2 / IRQ_DMA_IRQ_3 — tracked in `tech_debt.md`" notes at `dma.rs:272–275` and `dma.rs:380–383` so they no longer claim the gap. Keep the historical Residual C.2.1 framing; only delete the "tracked in tech_debt.md" sentences that are now stale.

**Threaded-runtime impact.** None. `Bus::tick_dma` is the single entry to `Dma::route_irqs`, and CPU workers on the threaded runtime drive `Bus::tick_dma` through the same code path the serial emulator does. The threaded coordinator's `tick_peripherals` (`threaded/emulator.rs:1113`) explicitly does **not** tick the DMA (`:1181`). Verified at survey rows `threaded/emulator.rs:1110–1190` and `threaded/peripherals.rs:525–589`.

## 7. Open questions / risks

**Q1. Do `INTSn` ack semantics need new per-line state on the new IRQ lines?**
No. NVIC pending bits live on `CoreAtomics::irq_pending`; DMA `INTR` lives on `Dma::intr`. `route_irqs` re-evaluates the predicate every call. When firmware writes 1 to a channel bit in `INTSn` (the existing W1C path at `dma.rs:456–463` clears `intr` for that channel), the next `route_irqs` call will see `(intr | intfN) & inteN == 0` and not re-pend. The NVIC bit, once latched, is cleared by the CPU's NVIC ICPR write — exactly the IRQ0/IRQ1 contract. No change to ack handling.

**Q2. Could a stuck `INTFn` continue to re-pend the NVIC every quantum?**
Yes — and that is the documented force-IRQ behaviour for IRQ0/IRQ1 too. `INTFn` is "force pending until cleared by software"; firmware that sets `INTF` is expected to clear it. The new lines inherit the existing semantics, not introduce new ones.

**Q3. NVIC line numbering — is 12/13 right?**
Confirmed at `crates/mdrp2350/src/irq.rs:53–59`. RP2350 uses contiguous lines 10..=13 for DMA IRQ0..3.

**Q4. Per-channel enable width.**
`INTEn` is 16 bits wide on RP2350 (one bit per channel; `NUM_CHANNELS = 16` per `dma.rs:44`). All four registers use the same `CHANNEL_MASK`. Predicate shape is identical for all four lines.

**Q5. Threaded vs Serial parity.**
Verified at survey: threaded coordinator does not tick the DMA (`threaded/emulator.rs:1181`), CPU workers go through `Bus::tick_dma` like serial. Single dispatch site.

**Q6. Does anything else read `inte2/inte3/intf2/intf3` and assume zero?**
Grep audited at survey (`inte2|inte3|intf2|intf3` matches inside `dma.rs` only). No other module touches these fields. Storage was added strictly for register round-trip.

**Q7. Should this fix also add a corpus scenario that uses IRQ2/IRQ3?**
No — explicitly out of scope. `tech_debt.md:196–198` says "land this alongside the first scenario that actually wires IRQ2/IRQ3." This HLD's contract is "remove the routing gap and prove with unit tests"; corpus integration is a separate change that can land independently when a firmware target needs it.
