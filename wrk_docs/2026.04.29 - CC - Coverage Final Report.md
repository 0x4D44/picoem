## 5. Why we did not reach 98 %

The remaining 498 in-scope misses concentrate in three buckets:

1. **Helper-function `if`-arm long tail.** `execute_fpu.rs` has 29 missed branches across 436 total — these are the individual `if n { *fpscr |= FPSCR_N }` style checks inside helpers like `fpscr_set_nzcv`. Covering them requires testing every {N,Z,C,V} ∈ {0,1}⁴ combination, but most VCMP test inputs only produce a small subset of the 16 possible flag patterns. A targeted "fpscr-set-flags-helper" unit test that calls the private helper directly would cover them in 8 tests, but the helper is module-private.

2. **`#[cfg(feature = "threading")]`-gated paths.** Both chip lib.rs files have ~10 conditional branches each that only compile when threading is on. Re-running the cov measurement with `--features mdrp2350/threading,mdrp2040/threading` did not unlock them either (those branches are inside `Emulator::run_quantum_threaded` and similar — they need a live ThreadedEmulator + a panic-injecting test, which exists in `tests/execution_model.rs` but is gated behind `--features testing`, which we did not run during the final cov measurement to avoid skewing the baseline).

3. **Specific bit-pattern instruction encodings.** `execute_thumb32.rs` has 29 missed branches across 422 total. Each is a specific encoding within a wider instruction class (e.g. SBFX with `widthm1 == 0`, USAT with `sat_imm == 31`). Covering them all is mechanical but tedious; some agents already added 45 tests to this file during Stage 2 and the count did not move because the new tests overlapped paths already exercised.

The Stage 4 + 5 agents made surgical attempts at these but the marginal gain per test dropped from ~0.6 branches/test in Stages 1-3 to ~0.1 branches/test in Stages 4-5. This is the classic diminishing-returns curve on coverage work.

## 7. What is provably unreachable (skip-with-annotation candidates)

A non-exhaustive list of branches that should be marked `#[cfg_attr(coverage_nightly, coverage(off))]` rather than chased:

- `core/coprocessor.rs:550` — `cp7_rcp _ => 1` catch-all: thumb32_coprocessor outer dispatch only forwards top-nibble 0xE/0xF, so reachable hw0 high bytes are constrained to {0xEE, 0xFE, 0xEC, 0xFC}. The `_` arm is structurally unreachable.
- `core_riscv/execute.rs:450` — `Op::Amo { Lr | Sc => unreachable!() }`: outer match already routed Lr/Sc to dedicated handlers.
- `core_riscv/csr.rs:330` — `_ => debug_assert!(false, "unsupported CSR")`: `read_csr` filters unsupported CSRs before `write_csr` is called, so the panic-arm is unreachable from public API.
- `dma.rs::apply_alias _ => value`: alias is a 2-bit field on the Bus, so values > 3 are unreachable from the public `Bus::write32` dispatch.
- `pll_write_into _ => val` in `bus/peripherals.rs`: alias derived as `(addr >> 12) & 3`, always 0..=3.
- All `# [test]`-only unreachable arms in `tests*.rs` files (the test infrastructure already excludes these from in-scope rollup).

Adding the annotations + a one-line source comment justifying each would remove ~50 branches from the denominator, lifting the in-scope figure to ~92.3 % without writing any new tests.

## 8. What was learned

- **Branch coverage agents need surgical instructions.** Pointing an agent at "raise execute_fpu.rs from 93.3 % to 96 %" without specific line numbers produces tests that pile onto already-covered paths. The Stage 5R re-run with explicit line numbers was 4× more efficient per test than Stages 2-4.
- **Tests inside the same file count as production branches.** Stage 4 added a `mod stage4_lib_residue` to `lib.rs` with `assert!`-heavy bodies; the total branch count didn't increase because llvm-cov treats `#[cfg(test)]` blocks as production. This is fine (the tests' assert-branches still count toward coverage), but it means tests added inline cannot regress the percentage by inflating the denominator.
- **The cov rebuild is the long pole.** Each `cargo +nightly llvm-cov` takes ~9 minutes (full LTO release rebuild). Stages should batch as many parallel agents as possible between rebuilds.
- **The 04-23 → 04-28 mutation-testing work delivered most of the visible gain.** Between commits `2c0a41d` and `42c7bc1` (≈ 5 days), in-scope branch coverage moved from 70.74 % to 89.07 % — that's a +18.33 pp jump, six times the +2.35 pp this session added. The mutation work was finishing *real* missing-test gaps; this session was sweeping the residue.

## 10. Recommendation

If a future session is asked to push further:

1. **Start with §7 — annotate provably-unreachable branches.** This is mechanical, low-risk, and immediately yields ~50 branches off the denominator (~+0.85 pp).
2. **Then tackle §6a — inline private-helper tests** inside `execute_fpu.rs`, `execute_thumb32.rs`, `exceptions.rs`. These are easy because the helper APIs are stable; just call them with each parameter combination. ~80 branches.
3. **Re-measure with `--features threading,testing` once.** The threaded panic-containment paths are real production code (`inject_panic_for_testing` is used by the integration tests under `tests/execution_model.rs`); the cov rollup currently misses them because the default cov run doesn't enable `testing`. Enabling it should reclaim ~60 branches without writing any new tests.

That sequence alone should land us at roughly **94-95 %** in-scope branch coverage in 2-3 hours. From there the diminishing-returns curve makes further gains expensive.
