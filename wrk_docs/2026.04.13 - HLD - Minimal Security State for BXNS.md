# HLD: Minimal Security State for BXNS

**Version:** 0.1.0 (DRAFT)  
**Date:** 2026-04-13  
**Scope:** Phase 4 prerequisite — just enough TrustZone to not crash on BXNS

## 1. Problem

The RP2350 bootrom starts in Secure state and launches user images into
Non-Secure via `enter_image_thunk`, which executes BXNS. Phase 4's milestone
("boots Pico SDK blinky from flash to main()") cannot be reached without this
instruction.

BXNS is not a standalone feature — it requires knowing which security state the
core is in and swapping banked registers on transition. But the full TrustZone
surface (SAU enforcement, SecureFault, SG, NSC regions, BLXNS + FNC_RETURN) is
large and unnecessary for Phase 4. We need the minimum viable slice.

## 2. What We're Adding

1. A `secure` flag on `CortexM33` — tracks Secure vs Non-Secure
2. BXNS instruction decode and execute
3. Register banking swap on S to NS transition

## 3. What We're NOT Adding

- SAU enforcement (keep "everything permitted")
- SecureFault
- SG (Secure Gateway) instruction
- BLXNS + FNC_RETURN (Secure-to-NS call with return)
- NS-aware exception entry/return (EXC_RETURN S/NS bit)
- MSR/MRS access control based on security state
- NS-aware memory access checks

These are all real TrustZone features. None are needed to boot a blinky.

## 4. Design

### 4.1. Core State

Add one field to `CortexM33`:

```rust
pub struct CortexM33 {
    // ... existing fields ...
    /// Security state. True = Secure, false = Non-Secure.
    /// Starts Secure at reset. Only BXNS can clear it (in this phase).
    pub(crate) secure: bool,
}
```

Initialised to `true` in `with_id()`. No configuration, no feature flags.

### 4.2. BXNS Decode

BXNS shares the T16 encoding space with BX. The only difference is bits [2:0]:

```
BX   Rm:  0100 0111 0 Rm(4) 000
BXNS Rm:  0100 0111 0 Rm(4) 100
BLX  Rm:  0100 0111 1 Rm(4) 000
```

Currently, `thumb16_special_data_bx()` ignores bits [2:0]. The change:

```rust
// In the BX/BLX arm (op == 0b11):
let rm = ((opcode >> 3) & 0xF) as usize;
let target = if rm == 15 { self.read_pc() } else { self.regs.r[rm] };
let link = opcode & (1 << 7) != 0;
let ns = opcode & 0x4 != 0;          // <-- new: bit 2

// ... existing BX/BLX logic (exception return, set PC, etc.) ...

if ns && !link && self.secure {       // <-- new: BXNS from Secure
    self.transition_to_nonsecure();
}
```

**Why `!link`?** Bit 7 = 1 with bit 2 = 1 would be BLXNS, which we are not
implementing. If we encounter it, we fall through to the existing BLX path
(wrong but safe — it's a branch, not a crash). This avoids a UsageFault on an
encoding that could theoretically appear in bootrom code we haven't traced.

**Why guard on `self.secure`?** BXNS from Non-Secure is architecturally
defined as plain BX. No state change.

### 4.3. Register Banking Swap

When the core transitions from Secure to Non-Secure, the "active" register
set changes. Our register file uses `msp`/`psp` for the active set and
`msp_ns`/`psp_ns` for the banked set. On transition, we swap them:

```rust
impl CortexM33 {
    /// Transition from Secure to Non-Secure state.
    /// Swaps all banked register pairs so the active set reflects NS state.
    pub(crate) fn transition_to_nonsecure(&mut self) {
        debug_assert!(self.secure);
        self.secure = false;

        // Flush R13 to the correct banked SP before swapping.
        self.regs.sync_sp_to_banked();

        // Swap all banked pairs. After this:
        //   msp = old msp_ns (NS stack the bootrom set up)
        //   msp_ns = old msp (Secure stack, preserved for later)
        std::mem::swap(&mut self.regs.msp, &mut self.regs.msp_ns);
        std::mem::swap(&mut self.regs.psp, &mut self.regs.psp_ns);
        std::mem::swap(&mut self.regs.msplim, &mut self.regs.msplim_ns);
        std::mem::swap(&mut self.regs.psplim, &mut self.regs.psplim_ns);
        std::mem::swap(&mut self.regs.primask, &mut self.regs.primask_ns);
        std::mem::swap(&mut self.regs.basepri, &mut self.regs.basepri_ns);
        std::mem::swap(&mut self.regs.faultmask, &mut self.regs.faultmask_ns);
        std::mem::swap(&mut self.regs.control, &mut self.regs.control_ns);

        // Load R13 from the now-active SP.
        self.regs.sync_sp_from_banked();
    }
}
```

**Why swap instead of having separate `_s` and `_ns` fields?** We already have
the `_ns` fields. Adding `_s` fields doubles the register surface and forces
every MSR/MRS/SP-access path to branch on `self.secure`. The swap keeps
existing code paths untouched — `self.regs.msp` always means "the active MSP",
regardless of security state.

**Trade-off:** After a swap, `msp_ns` holds the *Secure* MSP value, which is
semantically confusing. This is acceptable because (a) the only code that reads
`msp_ns` directly is the MSR/MRS handler for SYSm 0x88, which already means
"the other state's MSP" and (b) we can rename to `msp_other` in a future
cleanup if the confusion becomes a problem.

### 4.4. Ordering Within the BX Handler

The transition must happen *after* the PC update, not before. Sequence:

1. Read target address from Rm
2. Handle exception return (existing logic, unchanged)
3. Set PC to `target & !1` (existing logic, unchanged)
4. If BXNS and Secure: call `transition_to_nonsecure()`

The PC write in step 3 uses the pre-swap register file, which is correct —
the target address is in a Secure register (Rm), not an NS register.

### 4.5. What Happens After BXNS

The bootrom's flash boot path does this before BXNS:

1. `MSR MSP_NS, <user_initial_sp>` — writes `regs.msp_ns` (SYSm 0x88)
2. Loads user reset vector into a register
3. `BXNS Rm` — branches to user code

After our BXNS handler runs:
- `secure = false`
- `regs.msp` = the value the bootrom wrote to MSP_NS (user's initial SP)
- `regs.r[13]` = same (via `sync_sp_from_banked`)
- `regs.pc` = user's reset vector
- User code runs normally — all memory accesses permitted, MSR/MRS to
  standard SYSm codes (0x08 MSP, 0x09 PSP, etc.) hit the active (now NS)
  registers

No other code paths need to change for Phase 4.

## 5. Known Limitations

These are deliberate scope cuts, not bugs. Each has a natural home in a future
TrustZone phase if one is added to the roadmap.

| Limitation | Impact | When it matters |
|---|---|---|
| No NS to S transition | Can't return to Secure after BXNS | SG instruction, BLXNS, secure API calls |
| EXC_RETURN ignores S/NS bit | See note below | NS code taking interrupts that should return to S |
| MSR/MRS doesn't check security | NS code could write Secure registers | Malicious or buggy NS code (not blinky) |
| `_ns` naming misleading after swap | Readability | Code review, future maintenance |
| TT instruction assumes Secure | TTA/TTAT don't fault from NS; result bits always report full access | TrustZone-aware code using TT to query permissions |

**EXC_RETURN and exceptions from NS:** The hardcoded EXC_RETURN values
(`exceptions.rs:76-83`) don't encode the security bit, so exceptions taken in
NS generate an EXC_RETURN that claims "return to Secure." This is accidentally
harmless: `exit_exception()` never reads that bit — it just pops the frame and
restores SPSEL. The `secure` field is untouched through the entire
entry/return path, so the core stays in whatever state it was in. This works
for Phase 4 but is fragile — the moment EXC_RETURN is made spec-compliant,
NS exception return must also restore security state from the EXC_RETURN
encoding.

## 6. Tests

1. **BXNS from Secure:** Set up Secure state, write a target address to a
   register, execute BXNS. Verify: `secure == false`, PC updated, MSP/PSP
   swapped, R13 reflects new MSP.

2. **BXNS from Non-Secure:** Same but start with `secure = false`. Verify:
   behaves as plain BX, no state change, no register swap.

3. **MSP_NS setup + BXNS:** Write MSP_NS via MSR (SYSm 0x88), then BXNS.
   Verify R13 equals the value written to MSP_NS. This is the bootrom
   pattern.

4. **Bootrom integration:** The existing `bootrom_diagnostic_run` test should
   progress further once BXNS is implemented. Track which new trace addresses
   are reached.
