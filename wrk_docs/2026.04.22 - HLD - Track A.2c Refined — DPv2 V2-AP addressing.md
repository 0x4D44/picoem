## 1. Ground truth reset — what's known post Gate 1

### 1.1 Silicon behaviour on mdrp2354's RP2354

All three values below are reproduced across 3 runs and 3 reads-per-run, byte-identical each time (journal "2026-04-22 A.2a results" and "2026-04-22 A.2b Gate 1").

- **DPIDR (DPBANKSEL=0)** = `0x10212927` → version=2 (DPv2), designer=0x493 (Arm), part_no=0x02, revision=0x1, MINDP=true.
- **DPBANKSEL=1 write, then DP[0x0] read** = `0x10212927` (byte-identical to DPIDR — DPIDR1 not banked).
- **DPBANKSEL=2 write, then DP[0x0] read** = `0x10212927` (byte-identical — BASEPTR0 not banked).
- **AP IDR read (after patched arm upgrades cache to DPv3, writes `SELECT=0x2df0`)** = `0x00000000` → TYPE=JtagComAp → `ArmError::WrongApType`.

### 1.2 Inferences

- **RP2354 has no ADIv6 bank-1/2 DP register presence.** DPBANKSEL writes to 1 and 2 succeed (no abort), but DP offset 0x0 always returns DPIDR regardless. The `BASEPTR0.valid=true` decode in the A.2b probe was a false positive (bit 0 of DPIDR = revision LSB = 1).
- **RP2354's DP is a genuine DPv2, not a mis-reporting ADIv6.** The prior HLD's H1 fix shape (force `SelectCache::DPv3` in a vendor sequence after BASEPTR0.valid confirmation) would do the exact same thing the current Track A arm does — write DPv3-encoded SELECT to a DPv2 DP — and hit the same failure.
- **But the YAML declares V2-shaped APs** (`!v2 0x2000`, `!v2 0x4000`, `!v2 0x80000`) — these are real addresses on the silicon. The core 0 memory AP genuinely lives at 32-bit address `0x2000`.
- **probe-rs 0.31 couples DPv3⇔V2-AP enumeration as a code-side invariant** (`communication_interface.rs:284-289`): `access_ports` dispatches to V1 enumeration for DPv0/1/2 and V2 enumeration for DPv3. There is no path to "V2 APs on a DPv2 DP" in this version.

So the paradox that Track A.2c must resolve: how do you address a V2-shaped AP over a genuine DPv2 DP in probe-rs 0.31?

### 1.3 Residual puzzle — `probe_diff_rp2350 --fuzz 4000` PASS

Under H1 confirmed, the 4000/4000 PASS of `probe_diff_rp2350` is unexplained. The A.2 HLD flagged this (§2.1) and noted the same trace would show whether it reaches `MemoryAp::new` at V2 base `0x2000`. It is left as an open question (§9 Q3) — not load-bearing for the A.2c decision but must be answered before any Track-A-arm removal.

## 2. External research — how OpenOCD addresses V2-shaped APs on RP2350

### 2.1 Tcl config declaration (authoritative)

`tcl/target/rp2350.cfg` in raspberrypi/openocd@sdk-2.0.0 (verbatim):

```
dap create $_CHIPNAME.dap -chain-position $_CHIPNAME.swd -adiv6

target create $_CHIPNAME.dap.core0 cortex_m -dap $_CHIPNAME.dap -ap-num 0x2000 -coreid 0 -rtos hwthread
target create $_CHIPNAME.dap.core1 cortex_m -dap $_CHIPNAME.dap -ap-num 0x4000 -coreid 1 -rtos hwthread
```

Sources:
- <https://github.com/raspberrypi/openocd/blob/sdk-2.0.0/tcl/target/rp2350.cfg>

Meaning: OpenOCD declares the DAP as **ADIv6** in Tcl — an explicit user-config flag, not inferred from DPIDR. The ap-num is the full 32-bit AP base address (`0x2000`, `0x4000`).

### 2.2 How `adi_version` gets to 6 in `struct adiv5_dap`

In `src/target/arm_dap.c`, the Tcl `-adiv6` argument parses to `CFG_ADIV6` and sets `dap->dap.adi_version = 6`. There is no DPIDR-derived override — the flag is sticky from Tcl config.

Sources:
- <https://github.com/raspberrypi/openocd/blob/sdk-2.0.0/src/target/arm_dap.c> (search `CFG_ADIV6`, `"-adiv6"`).

### 2.3 SELECT encoding at AP-access time

In `src/target/adi_v5_swd.c` → `swd_queue_ap_bankselect`:

```c
if (is_adiv6(dap))
    sel = ap->ap_num | (reg & 0x00000FF0);
else
    sel = (ap->ap_num << 24) | (reg & ADIV5_DP_SELECT_APBANK);

uint64_t sel_diff = (sel ^ dap->select) & SELECT_AP_MASK;

bool set_select  = !dap->select_valid || (sel_diff & 0xffffffffull);
bool set_select1 = is_adiv6(dap) && dap->asize > 32
                   && (!dap->select1_valid || sel_diff & (0xffffffffull << 32));
```

Sources:
- <https://github.com/raspberrypi/openocd/blob/sdk-2.0.0/src/target/adi_v5_swd.c>

Crucially: **there is no DPIDR.version check at SELECT-write time.** For `ap_num = 0x2000` and `reg = 0xFC` (IDR), OpenOCD writes `sel = 0x2000 | 0x0F0 = 0x20F0` (plus DPBANKSEL bits at 3:0). SELECT1 is not written unless `asize > 32`.

### 2.4 Comparison to probe-rs 0.31 on the same access

probe-rs's patched arm writes (journal Gate 1 trace, decoded):
- `SELECT = 0x2df0` (DPv3 encoding: addr[31:4]=`0x2df`, dp_bank_sel[3:0]=`0`) for an AP `0x2000` + register `0xDFC` access — address `0x2dfc` shifted right by 4 = `0x2df`. Same encoding as OpenOCD would produce for the same register.
- `SELECT1 = 0` (no high-order bits needed; RP235x APs fit in 32 bits).

**These are the same wire bytes OpenOCD issues on a working RP2350.** If OpenOCD reports DPv3 on one RP2350 board and probe-rs reports DPv2 on mdrp2354's RP2354, and both are issuing the same ADIv6 SELECT encoding, then the difference is either:
- (a) the silicon is genuinely different (see §2.5); or
- (b) something outside SELECT is blocking the AP IDR read on mdrp2354's silicon.

### 2.5 DPIDR variation across RP2350 silicon

Public OpenOCD logs report DPIDR `0x4c013477` on "typical" RP2350 boards (CoreSight SoC-600, DPv3, designer=0x477/Arm — standard SoC-600).

mdrp2354's RP2354 reports DPIDR `0x10212927` (CoreSight SoC-400, DPv2, designer=0x493/Arm, part_no=0x02). This is an earlier-generation CoreSight IP. RP2354 is a 2026 A4-stepping variant of RP2350; the CoreSight IP may have been re-synthesised from a different source. Relevant background:

- <https://www.raspberrypi.com/news/rp2350-a4-rp2354-and-a-new-hacking-challenge/>
- <https://www.cnx-software.com/2025/07/29/raspberry-pi-rp2350-a4-stepping-fixes-e9-gpio-erratum-9-glitching-bugs-introduces-2mb-flash-variants/>
- <https://forums.raspberrypi.com/viewtopic.php?t=389218> (representative DPIDR = `0x4c013477` DPv3 on Pico 2).

This is evidence that **there is genuine silicon variation across RP2350-family steppings**, and the mdrp2354 RP2354 reports DPv2 honestly — not as a mis-report, but as the actual CoreSight generation of this silicon.

### 2.6 OpenOCD's behavior on a DPv2-reporting RP2350 DP

We could not find a public OpenOCD log that captures DPIDR = `0x10212927` on an RP2350. The closest hit (forums `viewtopic.php?p=2338595`) turned out to be an RP2040 misidentified as RP2350. OpenOCD's source gives no version-gated path, but we **cannot claim, with empirical certainty, that OpenOCD has been tested on the exact silicon mdrp2354 owns**. That is a Gate 3 open question (§9 Q1).

## 3. Root-cause hypothesis — refined

The prior HLD's H1, H1', H1'', H1''' framing, refined:

### 3.1 H1' (leading)

**Statement.** RP2354 accepts standard ADIv6 SELECT encoding (`sel = ap_num | (reg & 0xFF0)` at 32-bit DP offset 0x8) on a DPv2 DP. The SELECT/SELECT1 wire protocol is the same as on a DPv3 DP for AP addresses that fit in 32 bits. No proprietary SELECT extension is required.

**Why leading:** OpenOCD source shows no version-gated SELECT path and is known to work on RP2350 with ADIv6 AP-address-shaped writes. Probe-rs's patched arm writes the same bytes. If OpenOCD works on RP2350 silicon and probe-rs's wire bytes match OpenOCD's, the probe-rs failure is most likely **not** a SELECT-encoding mismatch but some sequence-level issue (power-up order, missing dormant wake, line reset state).

**What this predicts.** Fixing the probe-rs-internal DPv3⇔V2-AP coupling (so that `access_ports` can enumerate V2 APs on a DPv2 DP) and ensuring the SELECT write path uses `SelectV3` encoding even when DPIDR.version=2, should produce the same wire traffic OpenOCD does. If this produces a valid IDR read, H1' is confirmed. If IDR is still `0x0`, the bug is elsewhere (power/sequence) and we escalate to H1''' fallback.

**Confidence: medium-high, contingent on Gate 3 result (§9 Q1).**

### 3.2 H1''

**Statement.** RP2354 uses an RPi-proprietary SELECT extension on DPv2 that differs from standard ADIv6. The standard ADIv6 encoding OpenOCD uses would also fail on mdrp2354's silicon, but no one has publicly reported running OpenOCD against this specific stepping yet.

**Why not leading:** No evidence in OpenOCD source, Tcl config, or commit history suggests a proprietary SELECT shim for RP2350. The `-adiv6` flag is a standard ADIv6 activation, not a custom encoding. If such a shim existed, RP2354 would likely need its own Tcl config, which is not present in the repo (only `rp2350.cfg` + `rp2350-riscv.cfg`).

**Confidence: low.**

### 3.3 H1''' (fallback)

**Statement.** Something outside SELECT is blocking the AP IDR read on mdrp2354's silicon — e.g. a missed dormant-state wake, a missing POWER_REQ, a silent line-reset after the first DPIDR read, an overrun-detect misconfiguration. The fix is not SELECT-encoding but a sequence correction (and may be specific to the CoreSight SoC-400 + DPv2 silicon mdrp2354 has).

**Why considered:** The Gate 1 observation that DPBANKSEL=1 and 2 writes return byte-identical DPIDR is suspicious. On a well-behaved DPv2 with no bank 1/2, DPBANKSEL writes should succeed silently (no abort) and subsequent DP[0x0] reads should return DPIDR (which IS what we see) — so this is actually expected DPv2 behaviour. But the fact the AP IDR is `0x0` despite correct wire bytes suggests the AP itself isn't responding.

**Confidence: low-to-medium; this is the "residual bug" scenario after H1' is ruled in or out.**

### 3.4 Prior ranking

| Hyp | Prior | Rationale |
|---|---|---|
| H1' | **0.55** | OpenOCD works on RP2350 using standard ADIv6 encoding; probe-rs writes match. |
| H1''' | **0.30** | Gate 1 hints at sequence-level issues; silicon variation is real. |
| H1'' | **0.10** | No source-level evidence for a proprietary SELECT shim. |
| other | 0.05 | unknown residual. |

**Caveat: this ranking is contingent on at least one Gate 3 data point** (probe OpenOCD against mdrp2354's actual silicon, or probe-rs with decoupled adiv6 flag). Until then, honest uncertainty: we are picking Option A on the expected-value argument, not on proof.

## 4. Options

### Option A — Fork patch: decouple DPv3 ⇔ V2-AP enumeration in probe-rs 0.31

Teach probe-rs to address V2 APs over a DPv2 DP by following OpenOCD's model: declare ADIv6 addressing as a property of the **target**, not the **DP**.

**Shape.**
1. Add a new `DpState` field: `adi_version: AdiVersion` (enum `V5 | V6`), defaulted to V5 (preserves upstream behavior on non-ADIv6 targets).
2. Plumb the field via the `ArmDebugSequence::debug_port_start` or a new `probe_rs_target::Chip` field so the RP235x vendor sequence can declare `adi_version = V6`.
3. In `select_dp` (`communication_interface.rs:402`): initialise `current_select` to `SelectCache::DPv3(SelectV3(0), Select1(0))` if `adi_version == V6`, **independent of DPIDR.version**. Also set `debug_port_version` to the real DPIDR value for logging, but use `adi_version` for cache/enumeration routing.
4. In `access_ports` (line 284): enumerate V2 APs if `adi_version == V6`, regardless of `debug_port_version`.
5. In `select_ap_and_ap_bank` (line 454): the `(V2, DPv3)` arm already handles this; the Track A `(V2, DPv1)` recovery arm becomes unreachable under normal operation when `adi_version == V6` (because cache starts as DPv3 from step 3).

**Pros.** Matches OpenOCD's authoritative model. Wire traffic on AP access is the standard ADIv6 encoding, which OpenOCD uses and is known to work on RP2350. Single-commit shape.

**Cons.** Larger patch than Track A's single-arm fix. Touches `DpState`, `select_dp`, `access_ports`, plus target plumbing (~150–250 lines including docs/tests). Requires a target-schema decision (new YAML field vs. vendor-sequence-only plumbing).

**Risk.** If H1''' is correct, this doesn't fix anything — the wire is already correct under the patched arm; the bug is elsewhere. But this refactor is the prerequisite for any further diagnosis, so the work is not wasted.

**Effort:** 6–10 h (including test cycles).

### Option B — Vendor-sequence SELECT shim

Keep the probe-rs DPv3⇔V2-AP invariant as-is. In `vendor/raspberrypi/sequences/rp235x.rs`, override the DAP access path to intercept SELECT writes, decode the V2 AP address the caller wanted, and emit whatever wire bytes RP235x actually needs.

**Shape.** probe-rs 0.31 does not expose a `DapAccess` intercept hook in `ArmDebugSequence`. You would have to either:
- (a) wrap `interface: &mut dyn DapAccess` in a `Rp235xShim` before handing it off — not currently pluggable;
- (b) implement a new trait method on `ArmDebugSequence` that overrides SELECT programming — novel upstream surface.

Neither is a small change. This option is the tempting-but-hard one: it preserves the Track A entry point but requires inventing a transport shim abstraction. The architectural scope is comparable to Option A without Option A's benefit of matching OpenOCD's model.

**Pros.** Narrower blast radius per-commit (changes live under `vendor/raspberrypi/`).

**Cons.** Requires inventing a novel abstraction in probe-rs that doesn't exist today. Carries the same risk as A for the H1''' scenario. Does not match OpenOCD's model, so future debugging against OpenOCD as oracle is harder.

**Effort:** 10–20 h (abstraction design dominates).

### Option C — Use OpenOCD as the silicon oracle backend

Abandon probe-rs 0.31 for the oracles that need V2 AP access. Drive the silicon via OpenOCD's GDB-RSP interface (port 3333 by default) from the harness.

**Shape.**
- New harness crate `mdpicoem-openocd-backend` with a minimal GDB-RSP client (read/write register, read/write memory, reset, halt, step).
- Refactor `silicon_periph_diff_rp2350`, `probe_verify_rp2350`, etc. to switch between probe-rs and openocd-backend via a flag.
- Add an OpenOCD install/launch wrapper.
- Oracle harness starts OpenOCD as a child process, connects via RSP, runs the oracle, terminates OpenOCD.

**Pros.** OpenOCD demonstrably works on RP2350 (standard silicon). If H1''' is true, OpenOCD may still work where probe-rs doesn't — OpenOCD does a fuller sequence. Full RSP+OpenOCD would be a valuable backend to have regardless.

**Cons.** **Large architectural change.** The harness today is tightly coupled to probe-rs's `MemoryInterface` trait. GDB-RSP does not map 1:1 (e.g., no raw AP register read/write). Loses speed (RSP is slower than raw probe-rs). Adds a non-Rust runtime dependency. Does not help probe-rs users of our library. **Only helps the mdrp2354-internal oracle harness.**

**Effort:** 30–60 h minimum.

### Option D — Limit silicon-oracle scope to what works today

Accept that probe-rs 0.31 cannot reach the V2 APs on mdrp2354's RP2354 silicon. Do nothing on the probe-rs side beyond the Track A arm (which stays in place to prevent `unreachable!()`). Scope the silicon oracle surface to **only those oracles that work through the ISA path** (`probe_diff_rp2350 --fuzz 4000`, since it passes 4000/4000 under the current arm). Defer `probe_verify_rp2350`, `silicon_periph_diff_rp2350`, `silicon_dualcore_diff_rp2350`, `silicon_isr_diff_rp2350`, `bank_conflict_test_rp2350` until probe-rs upstream gains ADIv6-on-DPv2 support (no release target).

**Pros.** Zero engineering cost. Clean narrative for downstream users. Honest about the scope limitation.

**Cons.** Peripheral oracle remains unreachable on this silicon. Blocks the periph-diff workstream indefinitely. Does not contribute upstream.

**Effort:** 1 h (documentation + `tech_debt.md` entry + harness-side `--skip-v2-ap` guard).

## 5. Recommendation

**Option A.** Rationale:

- It's the only option that follows OpenOCD's authoritative model (`-adiv6` is a declared property of the target, not inferred from DPIDR).
- It's a bounded fork patch that stays inside `communication_interface.rs` + a small target-plumbing change + `rp235x.rs` vendor-sequence declaration.
- It gives us a prerequisite state where OpenOCD and probe-rs issue the same wire bytes — if that does not fix it, we have clean diagnostic ground on which to run Gate 3 (§9 Q1) and localise H1'''.
- It is the upstream-friendly answer: a "decouple ADIv6-AP-addressing from DPIDR.version" patch would close #3872 and #3257 cleanly and would be submitted as a follow-up to the current Track A upstream PR.
- Effort (6–10 h) is inside the original A.2 budget (2–6 h) doubled for the refactor overhead, and substantially less than the ~30 h Option C needs.

**Gate 3 — run before full commit.** Ship Option A behind a feature flag or in a scratch branch. Do a one-shot run of `probe_verify_rp2350` with Option A applied. If IDR reads succeed, H1' is confirmed — land the patch and remove the Track A arm. If IDR is still `0x0`, H1''' is in play — keep the patch (it's a required step for any further fix) and dispatch a diagnostic agent to compare wire captures between the mdrp-patched probe-rs and OpenOCD on the same silicon.

**Do NOT remove the Track A sentinel arm in the same commit.** The arm's removal is gated on Gate 3 + a clean `probe_diff_rp2350 --fuzz 4000` + `probe_verify_rp2350` pass with Option A alone. If Option A succeeds end-to-end, the arm becomes dead code and can be removed in a follow-up commit (see §6.3).

### 6.2 Track A sentinel arm disposition during A.2c

**Do not remove in the A.2c commit.** The sentinel arm is load-bearing for any code path where `SelectCache` has an `AdiVersion::V6` declaration that races the cache upgrade (e.g. a cold attach where the cache is queried before `debug_port_start` runs). Under Option A with `adi_version == V6` declared, the cache will be initialised as DPv3 from the first `DpState::new()` call, so the arm is a belt-and-braces dead-branch. Tag it:

```rust
// FIXME(A.2c): dead code under adi_version == V6 target declaration.
// Remove once Gate 3 (Option A end-to-end IDR read success) passes on hardware.
```

Removal lands in a follow-up commit after Gate 3 + 30-min soak.

## 7. Risks

### 7.1 What if OpenOCD's RPi fork has a closed-source transport layer we can't read?

The fork is open-source GPL-2.0 (`github.com/raspberrypi/openocd`). There is no closed-source transport. The Tcl config and C source are both visible. Risk realised: **none** — the research surfaced `-adiv6`, ap-num, and SELECT-programming source paths cleanly.

### 7.2 What if OpenOCD hasn't actually been tested on mdrp2354's silicon?

**This is the main residual risk.** Public OpenOCD logs on RP2350 show DPIDR = `0x4c013477` (DPv3/SoC-600). We could not find a public OpenOCD log for DPIDR = `0x10212927` (DPv2/SoC-400) — the silicon mdrp2354 has. If OpenOCD has never been tested on this CoreSight SoC-400-based RP2350 variant, the H1' premise ("OpenOCD works with ADIv6 encoding on this DP") is not empirically verified.

**Mitigation.** Gate 3 (§5, §6.3 step 4) is the direct empirical test: run Option A's implementation on the silicon. If IDR read succeeds, H1' holds regardless of whether OpenOCD has been run. If it fails, H1''' is in play — we still have the Option A refactor in place, making subsequent diagnosis easier.

**Belt-and-braces mitigation.** Optional pre-Gate-3 data collection: install OpenOCD on the mdrp2354 host, run `openocd -f interface/cmsis-dap.cfg -f target/rp2350.cfg` against the RP2354 board, observe whether OpenOCD successfully attaches and reads CPUID. If OpenOCD works, H1' is strongly supported. If OpenOCD ALSO fails, the silicon behaviour is genuinely different from standard RP2350 and we may need RPi-vendor engagement (Raspberry Pi forums, raspberrypi/openocd issue tracker). Estimated effort: 30 min install, 10 min test. Recommend doing this **before** dispatching the Option A implementation agent.

### 7.3 What if the answer requires hardware-level info from the datasheet we don't have?

The RP2350 datasheet (~800 pages) is publicly available at <https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf>. §3 covers the DAP and debug architecture. If H1''' is in play, the datasheet's §3.4 (Debug Interface) and §3.5 (Rescue Reset / RP-AP) may contain the missing sequence detail. Out of scope for this HLD to read the full §3; a lead-driven re-read is queued as a §9 Q2 open question for the H1''' contingency.

### 7.4 What if the refactor breaks non-RP235x targets?
