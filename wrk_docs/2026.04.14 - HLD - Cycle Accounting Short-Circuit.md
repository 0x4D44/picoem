# Cycle Accounting Short-Circuit

Version: 1.0.1
Date: 2026-04-14

## Problem

`decode_execute` in `crates/mdrp2350/src/core/decode.rs` wraps every
instruction in bus-bookkeeping calls:

```rust
bus.reset_extra_wait_states();   // line 33
let hw0 = bus.read16(pc);         // fetch
...                               // dispatch handler
cycles + bus.extra_wait_states()  // line 56 / 77
```

For the majority of instructions (ALU ops, branches, MOV, immediate
arithmetic, hints, barriers, data-processing, …) the dispatched handler
does not make a single call into `Bus::readXX` / `writeXX` and therefore
cannot change `extra_wait_states`. The reset/read pair is a per-instruction
overhead that serves no purpose for the common case.

At the measured baseline (`paced_bench_rp2350 --workload basic --unpaced`
→ 83.5 MHz, 36.80 host-cycles/emu-cycle), shaving any uncontended
bookkeeping from the hot path moves the budget toward the <33 target.

## Scope

This HLD defines a static `is_pure` classification of every decoded
Thumb op and the fast path that uses it in `decode_execute`. It depends
on Agent A's PC-keyed decoded-op cache: `is_pure` is a field on the cache
entry, set once at populate time.

## 1. `is_pure` classification rule

> An op is **pure** iff, for every well-formed invocation, its handler
> returns without changing `Bus::extra_wait_states` and without setting
> `self.pending_fault` / `bus.bus_fault`.

The second clause is required because synchronous fault delivery
(`deliver_fault` → `enter_exception`) performs up to eight `bus.write32`
calls for stack framing, each of which accumulates wait states. If a
"pure" op raised a fault, the fast path would skip the reset/read and
the stacker's accumulation would silently leak into the next
instruction's accounting.

Operationally, "doesn't touch the bus for wait-state purposes" ≡ "does
not call `bus.read8/16/32` or `bus.write8/16/32`, and does not cause
`enter_exception` / `deliver_fault` / `exit_exception` to be invoked."
Direct field access on the bus (`bus.sio.*`, `bus.ppb[core].*`,
`bus.rcp_*`, `bus.event_flag`, `bus.signal_sev`, `bus.set_burst_mode`)
does not go through the wait-state accumulator and is pure.

| `fpu_reg_transfer` (VMOV / VMRS / VMSR) | impure | Same lazy-flush gate on `fpu_execute` entry. |

CPACR-disabled coprocessor access raises `UsageFault`, so any coprocessor
slot that is not known to be enabled at cache-populate time must be
classified impure. A conservative "all coprocessor ops are impure"
classification is acceptable; the RCP and FPU rows above already force
that for CP4/5/7/10/11, and CP0 is used only after explicit CPACR
programming — classifying it impure costs nothing on the bootrom path
and removes a state-dependency risk.

**Simplification:** classify all coprocessor-dispatched ops (CP0, CP4/5,
CP7, CP10/11) as impure. This removes the CPACR-state dependency and
the FPU lazy-flush state dependency. The hot-path perf target is
integer code; coprocessor ops can stay on the slow path.

### Summary of the pure set

Pure ops are exactly:
- Pure-compute Thumb-16: shifts, ADDs, SUBs, MOVs, CMPs, data-processing
  (low reg), ADR, ADD SP, misc arithmetic/extend/REV/CPS/IT/hints/CBZ/CBNZ,
  B.cond (both directions), B (unconditional), B.W T3/T4.
- Pure-compute Thumb-32: data-processing (modified-imm, plain-imm,
  shifted-reg, register), multiply (short and long), BL, MSR, MRS,
  hints, barriers.

Everything else is impure: loads, stores, LDM/STM, PUSH/POP, LDR literal,
SVC, BX/BLX/MOV-to-PC (exc-return path), coprocessor, FPU, and undefined.

## 2. Where `is_pure` is set

At cache miss time, after Agent A's decoder resolves the instruction to
a concrete op variant, the populate path sets `is_pure` via a single
match on the variant discriminant or a per-variant const table. Either
form is acceptable; the encoding choice is Agent A's. The rule is
single-source-of-truth: the table / match must live next to the
`DecodedOp` enum so any new op variant forces a classification decision
(compiler exhaustiveness warnings are the ideal mechanism).

### Tricky groups worth calling out

- **Thumb-16 `0b01000`.** Bit 10 discriminates data-processing (pure)
  from special-data/BX (impure). The cache entry is per-decoded-op, so
  this only matters if Agent A's decoder has a single variant covering
  both — it should not. If Agent A splits on bit 10 at decode time,
  each resulting variant has a stable classification.
- **Thumb-16 misc (`opcode[15:12]=1011`).** The group fans out to many
  sub-ops. Agent A must decode the sub-op before recording `is_pure`,
  never classify the whole group.
- **B.W unconditional vs misc-control at `thumb32_branch_misc`.** Same
  consideration: decoder must resolve `hw1[14]` and `hw0[9:6]` to a
  specific op variant before stamping `is_pure`.

## 3. Fast path in `decode_execute`

Modified control flow, expressed against Agent A's cache interface:

```
fn decode_execute(&mut self, bus: &mut Bus) -> u32 {
    let pc = self.regs.pc();
    self.current_instr_addr = pc;
    let entry = cache.lookup_or_populate(pc, bus, &mut self.regs);

    // IT / condition handling (unchanged wrt. perf).
    let in_it = self.it_state & 0xF != 0;
    let cond_passed = in_it_or_always(self, in_it);

    if entry.is_pure {
        // Fast path: no bus bookkeeping. The fetch wait states for this
        // entry are pre-charged by the cache (see §9 request to Agent A).
        #[cfg(debug_assertions)]
        let ws_before = bus.extra_wait_states();
        self.regs.set_pc(pc.wrapping_add(entry.size));
        let cycles = if cond_passed {
            self.dispatch_pure(entry)   // no &mut Bus required
        } else { 1 };
        self.finish_pure(in_it, cond_passed, entry);
        #[cfg(debug_assertions)]
        debug_assert_eq!(bus.extra_wait_states(), ws_before,
            "pure op {:?} dirtied extra_wait_states at PC={:08X}",
            entry.op, pc);
        cycles
    } else {
        // Slow path: preserve existing semantics verbatim.
        bus.reset_extra_wait_states();
        self.regs.set_pc(pc.wrapping_add(entry.size));
        let cycles = if cond_passed {
            self.dispatch_impure(entry, bus)
        } else { 1 };
        self.finish_impure(in_it, cond_passed, entry);
        cycles + bus.extra_wait_states()
    }
}
```

Fields on `Bus` touched only by the slow path:
- `extra_wait_states` (r/w)
- `burst_mode` (written by STM/LDM/PUSH/POP handlers)
- `bus_fault`, `bus_fault_addr` (set by `readXX`/`writeXX` on failure)

None of these are touched by any pure handler.

### Why the fast path can skip `reset_extra_wait_states`

After a slow-path instruction, `extra_wait_states` holds whatever the
impure handler accumulated. That value was already added to the cycle
count and returned; it is stale residue as far as any subsequent reader
is concerned. The next instruction is either:

- **Slow path** — it calls `reset_extra_wait_states` at entry, wiping
  the residue.
- **Fast path** — it neither reads nor writes the accumulator.

So the accumulator is touched only by code that resets it first. The
pure path is a pure bystander. The debug-assert (§5) captures the
pre-dispatch value and compares against the post-dispatch value, so
residue from a previous slow-path op does not trigger a false fire.

## 4. Cycle-count correctness

For every handler in the pure set, we verified by inspection that the
function body contains no call to `bus.read8/16/32` or `bus.write8/16/32`
and does not set `self.pending_fault` / `bus.bus_fault`. The Thumb-16
handlers that take `&mut Bus` in their signature are all in the impure
set; ones without a `&mut Bus` parameter (a large majority) are trivially
pure. The same rule applies to Thumb-32 handlers.

Exceptions to "signature implies purity" — handlers that take `&mut Bus`
but are classified pure because they only access direct fields:
- `thumb16_misc` hints path (`bus.signal_sev`, `wfe` reads `bus.event_flag`).
- `thumb32_branch_misc` B.cond/B.uncond paths (bus arg unused by the
  taken/not-taken branch itself).

For these, the classification is per-sub-op at decode time, not per
handler. Agent A's cache entry stores the specific sub-op, not a
reference to the parent handler, so the `&mut Bus` signature is
irrelevant.

The invariant "pure handler leaves `bus.extra_wait_states` unchanged"
follows because:
1. The fast path does not do the fetch via `bus.read16(pc)` — it comes
   from the cache (§9 request), so no fetch-side wait states accrue
   during `decode_execute`.
2. The pure handler body makes no `bus.readXX` / `writeXX` call, so the
   accumulator's value at dispatch entry is preserved at dispatch exit.

If Agent A's cache implementation still routes fetches through
`bus.read16`, the fast path must additionally call
`bus.reset_extra_wait_states()` after the fetch (pre-charging the
fetch contribution into the cycle count separately) or preserve the
current reset-at-start / read-at-end pattern for fetch only. The
cleanest design is cache-owned fetch wait states. This is the request
in §9.

## 5. Misclassification guardrail

Delta-check assertion at the tail of the pure path:

```rust
#[cfg(debug_assertions)]
{
    let ws_before = /* captured before dispatch */;
    debug_assert_eq!(bus.extra_wait_states(), ws_before,
        "pure op {:?} dirtied extra_wait_states at PC={:08X}",
        entry.op, pc);
}
```

Release builds optimize this to nothing (both the capture and the
compare are gated on `cfg(debug_assertions)`). Unit tests and
`qemu_diff` / `probe_diff` harnesses run debug builds, so any
misclassification that slips in will fire this assert on the first
offending instruction, not silently under-count cycles for a million
executions.

Comparing against `ws_before` rather than `0` is necessary because an
earlier slow-path instruction may have left residue in the accumulator
(see §"Why the fast path can skip `reset_extra_wait_states`").

Severity: a pure-misclassified load would appear as a `1` or `2`-cycle
savings per access (wait states unaccounted), which would skew
`paced_bench` throughput but still PASS QEMU diff (QEMU doesn't model
SRAM bank wait states). The debug-assert is therefore the primary
oracle. Keep it.

**Addendum (v1.0.1) — fault-delivery exemption.** The HLD §1 rule that
pure handlers must not set `pending_fault` is strictly stricter than
correctness requires. A pure-classified handler that falls through to
its undefined-encoding fallback (`thumb16_undefined` / `thumb32_undefined`)
will raise a synchronous fault at dispatch exit, and `deliver_fault` →
`enter_exception` does accumulate wait states via its stacking writes.
However, `CortexM33::step` discards `decode_execute`'s cycle return when
a fault is delivered — the return value is overwritten by
`deliver_fault`'s own cycle count. So the pure path's "no wait-state
leakage" contract is preserved in practice even in this degenerate case.
The classification in `classify_is_pure` therefore does not need to
track fall-through-to-undefined paths as impure; doing so would be
correct but would cost coverage on well-formed encodings sharing the
same arm.

## 6. Interaction with exceptions and faults

Re-read of `CortexM33::step` (`core/mod.rs:92`) confirms:

```rust
let mut cycles = self.decode_execute(bus);
if bus.bus_fault() { ... deliver ... }
if !fault_handled {
    if let Some(fault) = self.pending_fault.take() { ... deliver_fault ... }
}
```

Fault delivery happens **after** `decode_execute` returns, unconditional
of which path (pure or impure) was taken. The pure path sets neither
`bus.bus_fault` nor `self.pending_fault` (by construction — that is
the definition of pure), so the `deliver_fault` branch is never reached
from a pure hit. Soundness preserved.

Should a misclassified pure op actually raise a fault, the assert from
§5 fires before the fault is delivered (since the handler exits cleanly
before `step` examines `pending_fault`). Both signals fire; neither is
lost.

## 7. Worked example — tight ADDS/B loop

```
loop:
  ADDS R0, R0, #1     ; thumb16 mov_imm group → thumb16_add_imm8 — pure
  B    loop           ; thumb16 branch        → thumb16_branch   — pure
```

Cache populated after the first miss; both entries carry
`is_pure = true`.

Subsequent iterations:

| Step | Path | Work |
|------|------|------|
| ADDS cache hit | Fast | No `reset_extra_wait_states`, no fetch via `bus.read16`, dispatch to `thumb16_add_imm8` (1 cycle), debug_assert, return 1. |
| B cache hit | Fast | Same — `thumb16_branch` writes PC, returns 1 (forward branch) or 6 (large backward). No bus touch. |

Contrast with `LDR R0, [PC, #4]` (literal pool):

| Step | Path | Work |
|------|------|------|
| LDR literal cache hit | Slow | `reset_extra_wait_states`, dispatch to `thumb16_ldr_literal` (calls `bus.read32`), 2 + `extra_wait_states` cycles. |

## 8. Risks and edge cases

**IT-block condition-passed-false.** When `cond_passed == false`, the
fast path skips `dispatch_pure` and charges 1 cycle. No handler runs.
`extra_wait_states` is unchanged (whatever residue it held remains);
the delta-assert in §5 still sees zero change. Correct.

Note: the **impure** path also short-circuits on `cond_passed == false`,
returning 1 cycle before dispatching. In that case `extra_wait_states`
equals whatever the fetch accumulated. Unchanged from today's behavior.
Not a correctness issue for the fast-path change.

**Burst mode residue.** `burst_mode` is set and cleared *within* each
impure multi-word handler (PUSH/POP/STM/LDM/VPUSH/VPOP/VLDM/VSTM) as a
bracketed pair. No impure handler exits with `burst_mode = true`. The
flag has no impact on any pure handler (it is only read inside
`sram_bank_wait`, which is only called from bus read/write methods
that no pure handler calls). No hysteresis.

**Cache entry staleness across a fault's re-entry.** If the PC of a
pure op is later remapped to a load (self-modifying code), the cache
entry would carry `is_pure = true` for a now-impure op. This is Agent
A's problem — cache invalidation on writes to the code region is
outside this HLD's scope.

**Wide-op composition.** A Thumb-32 instruction's `is_pure` is stamped
once on the full decoded op (hw0:hw1 together), never on hw0 alone.
The `is_wide(hw0)` check in the current decoder's partial decode must
not be exposed as a cache-entry type; Agent A should produce one cache
entry per full instruction. Called out only because it's an easy
regression — the Thumb-16 dispatch for `0b11101+` shouldn't accidentally
share a variant with the Thumb-32 path.

**State-dependent purity rejected.** FPU data-processing is *almost*
pure — it only becomes impure if FPCCR.LSPACT=1 on entry to the handler.
Making `is_pure` state-dependent would force a runtime check, defeating
the fast-path savings. Simpler: classify all FPU ops impure (§1).
Integer workloads see zero regression; FPU-heavy workloads retain
existing behavior.

paths.

## Requests to Agent A

Required on the cache entry:
1. **`is_pure: bool`** — as defined above, stamped at populate time.

Required on the cached-fetch design:
2. The fast path relies on the cache providing the opcode without
   calling `bus.read16(pc)`. If the cache must still route the fetch
   through the bus (for contention tracking), surface the fetch's
   wait-state contribution as a **`fetch_wait_states: u32`** field on
   the entry, pre-computed at populate time and charged per hit. This
   lets the pure path add `entry.fetch_wait_states` directly to its
   cycle return without touching `bus.extra_wait_states`. If the cache
   handles fetch tracking internally (adding to cycles before
   returning), no field is needed.

Not required (out of scope for this HLD):
3. `base_cycles` — not requested. The existing `execute_thumbXX` and
   per-handler cycle returns are already constants or small matches;
   inlining plus LLVM will fold them. Premature.

## What does NOT change

- **Slow path semantics.** Load/store, push/pop, coprocessor, FPU, SVC,
  undefined — all keep their current `reset / dispatch / extra_wait_states`
  flow verbatim.
- **Cycle-accuracy contract.** Pure ops on SRAM today accumulate zero
  wait states from their execute body; the only source is the fetch,
  which is Agent A's responsibility. The fast path reproduces the same
  cycle count.
- **Bus API.** No new public methods, no removed ones.
- **Fault delivery.** Unchanged.

## Expected impact

Per-instruction savings on the pure path:
- One virtual call to `reset_extra_wait_states` (write of a u32).
- One virtual call to `extra_wait_states` (read of a u32) + an add.

Conservatively ~2–4 host cycles per pure instruction. On `basic`
workload (overwhelmingly pure ALU + branches), this is ~5–10 % of the
current 36.8-cycles-per-emu-cycle budget. Combined with Agent A's
cache, it should push the budget under the 33 target.
