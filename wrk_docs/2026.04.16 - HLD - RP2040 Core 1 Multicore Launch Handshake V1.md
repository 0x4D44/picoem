# HLD — RP2040 Core 1 Multicore Launch Handshake

**Date:** 2026-04-16
**Crate scope:** `crates/mdrp2040` only (mdrp2350 is off-limits this sprint — concurrent agent).
**Driver:** PicoGUS v4.0.0 firmware calls `multicore_launch_core1`. Our current placeholder in `lib.rs:514 maybe_wake_core1` wakes core 1 at the reset vector on any non-zero `SIO_FIFO_WR` push; PicoGUS lands at the wrong entry and never starts its I2S service loop.

---

## 1. Protocol summary (oracle)

Transcribed from pico-sdk 2.1.1 `src/rp2_common/pico_multicore/multicore.c` lines 171–203 and pico-bootrom-rp2040 (tag b2) `bootrom/bootrom_rt0.S` lines 313–391. Copies saved under `wrk_scratch/multicore-research/` for re-verification.

### Sender (`multicore_launch_core1_raw`)

```
cmd_sequence = { 0, 0, 1, (uint32_t)vector_table, (uint32_t)sp, (uint32_t)entry }
seq = 0
while seq < 6:
    cmd = cmd_sequence[seq]
    if cmd == 0:
        drain fifo_to_core0         ; multicore_fifo_drain() on line 192
        __sev()                     ; line 194
    push_blocking(fifo_to_core1, cmd)  ; line 196 — push + SEV
    response = pop_blocking(fifo_to_core0) ; line 197 — WFE loop until VLD
    seq = (cmd == response) ? seq + 1 : 0   ; line 199
```

Sender pushes entry with Thumb bit set (sdk comment, line 183 — "don't forget to set the thumb bit").

### Receiver (`wait_for_vector` in ROM b2)

```
loop:
    drain fifo_to_core1                     ; handshake_loop, lines 339–343
    send(fifo_to_core0, 0)                  ; line 349
    r0 = recv_or_restart(fifo_to_core1)     ; receive_and_check_zero, lines 381–391
    if r0 != 1: restart                     ; cmp r0,#1 ; bne, lines 351–352
    send(fifo_to_core0, 1)                  ; line 354; echo received value
    r0 = recv_or_restart(fifo_to_core1)
    store r0 → M0PLUS_VTOR                  ; line 355
    send(fifo_to_core0, r0)                 ; line 357; echo VTOR
    r0 = recv_or_restart(fifo_to_core1)
    msr msp, r0                             ; line 359; set MSP
    send(fifo_to_core0, r0)                 ; line 360; echo SP
    r0 = recv_or_restart(fifo_to_core1)
    send(fifo_to_core0, r0)                 ; line 363; echo entry, r5=core1_launch
    blx r0                                  ; line 369
```

`recv_or_restart` = `wfe; poll VLD; read FIFO_RD; if r0 == 0 branch to handshake_loop`.

### Observed sender-side echo pattern (steady state)

| seq | sender push | receiver echo (what sender pops) |
|-----|-------------|-----------------------------------|
| 0   | 0           | 0                                 |
| 1   | 0           | 0                                 |
| 2   | 1           | 1                                 |
| 3   | vtor        | vtor                              |
| 4   | sp          | sp                                |
| 5   | entry       | entry                             |

Sender advances when `cmd == response`, so the echo is equivalent to "receiver echoes the word it just received" for every slot.

## 2. Shortcut design (what we implement)

Our core 1 is halted from reset — the real bootrom never runs. We synthesise the handshake response from the Sio FIFO write path, mirroring our existing `direct_boot_from_flash` posture (skip ROM, set up arch state directly).

### 2.1 State location

A new field on `Sio` (`crates/mdrp2040/src/bus/sio.rs`), next to `pending_fifo_event`:

```rust
struct MulticoreHandshake {
    seq: u8,                        // 0..=5, always resets to 0 on mismatch
    vtor: u32,                      // captured at seq=3
    sp:   u32,                      // captured at seq=4
    pending_launch: Option<Core1Launch>,  // armed at seq=5 completion, consumed by Emulator::step
}

struct Core1Launch { vtor: u32, sp: u32, entry: u32 }
```

Rationale:
- Sio owns the FIFO queues; the state machine is driven by FIFO writes.
- Echo generation is a push into `fifo_to_core0` — already a Sio primitive.
- The wake itself (setting PPB VTOR, setting core SP/PC, unhalting) needs `Emulator`-level access, so we surface a one-shot `pending_launch` token for `Emulator::step` to consume, matching the existing `maybe_wake_core1` consumption pattern.

### 2.2 When the state machine is "armed"

Armed iff `cores[1].is_halted() == true`. Check this inside `fifo_wr(val, core=0)` before advancing. If core 1 is awake, FIFO traffic is regular IPC — do not parse.

Concretely: `Sio::fifo_wr` doesn't know whether core 1 is halted (Sio has no handle on cores). Two options:
- (Chosen) Call `Bus::sio.fifo_wr` from a wrapper in `Bus` that also passes `core1_halted: bool`. Adjust signature to `fn fifo_wr(&mut self, val: u32, core: usize, core1_halted: bool)`.
- (Rejected) Stash the halt bit on Sio via Bus write — couples state.

The write-side dispatch already lives in `Bus::write32` which has `&mut self`; it can read `cores[1].is_halted()` via the emulator layer. Actually cores live on `Emulator`, not `Bus` — so the check must happen at `Emulator::step` level, not on every MMIO write.

**Revised**: `Sio::fifo_wr` always advances the state machine (it's cheap), but only while `seq > 0` OR the first word is seen in a "core-1-halted context". We gate consumption of `pending_launch` in `Emulator::step` on `cores[1].is_halted()`.

Actually simpler still: let the state machine run unconditionally; gate only the **launch side-effect**. If core 1 is already awake, `Emulator::step` ignores `pending_launch` and resets the state machine. The echo pushes are still made to `fifo_to_core0` — this is fine, because when core 1 is awake, user code is responsible for the FIFO protocol and can pop/ignore extras. Mirrors real silicon ambiguity (if `multicore_launch_core1_raw` is invoked while core 1 is running, nothing in hardware prevents the words from sitting in FIFOs).

**Final**: state machine runs unconditionally; the wake only happens when `pending_launch` is consumed by `Emulator` AND core 1 is halted. If core 1 is awake, the latched launch token is dropped silently.

### 2.3 Transition table (Sio::fifo_wr, core 0 push)

```
on fifo_wr(val, core=0):
    push `val` to fifo_to_core1 as usual      ; (*) see 2.5
    match seq:
        0:  echo 0 to fifo_to_core0; seq = if val == 0 { 1 } else { 0 }
        1:  echo 0 to fifo_to_core0; seq = if val == 0 { 2 } else { 0 }
        2:  if val == 1: echo 1; seq = 3
            else:        echo 0; seq = 0     ; bootrom-equivalent restart
        3:  if val == 0: echo 0; seq = 0
            else:        vtor = val; echo val; seq = 4
        4:  if val == 0: echo 0; seq = 0
            else:        sp = val; echo val; seq = 5
        5:  if val == 0: echo 0; seq = 0
            else:        entry = val; echo val;
                         pending_launch = Some({ vtor, sp, entry });
                         seq = 0
```

Every case ends with an echo push to `fifo_to_core0` and (if we choose to SEV) a wake of core 0's WFE — see 2.4. The echoes at seq 0/1/2 are **literal 0/0/1** on the happy path (same effect as real bootrom re-entering the drain-and-send-0 loop on every step).

Note the asymmetry at seq=0 vs seq=2-mismatch: at seq=0 we echo 0; at seq=2 we echo 0 AND reset. Real bootrom identical.

### 2.4 Echo timing and core 0 WFE wake

Echo is pushed synchronously inside `fifo_wr`. Under mdrp2040's current `step()` — one instruction per core, alternating — core 0's next instruction after the push-blocking MMIO store is the pop-blocking load. The echo is in `fifo_to_core0` by then, `VLD=1` is set, WFE is not hit on the happy path. No SEV needed. **Verified**: `crates/mdrp2040/src/lib.rs` step cadence is per-instruction, confirmed by `step_quantum` being unused (tech_debt.md).

If `step_quantum` is ever re-enabled (N instructions per core per step), the concern returns only if WFE is hit between push and pop. Current mdrp2040 WFE implementation (see `core/execute.rs`) uses `event_flag[core]` as the wake signal, which is set by `pending_fifo_event` flush in `Bus`. The existing pipeline already handles this — we piggy-back by ensuring echo push triggers the same event bubble for core 0. In practice, we set `pending_fifo_event = Some(0)` whenever we push an echo to `fifo_to_core0`, identical to how user-code-driven core-1 → core-0 pushes already behave.

### 2.5 Do we actually push `val` into fifo_to_core1?

Tension:
- If yes: fifo_to_core1 fills during handshake. When core 1 wakes at `entry`, its firmware doesn't expect 6 stale words in RX. Bug.
- If no: sender's `push_blocking` checks `RDY` (tx has space) — always true (we didn't push) — OK. But any test that inspects `fifo_to_core1` sees nothing. Confusing but correct-for-shortcut.

**Decision: drain fifo_to_core1 at wake time**, rather than skipping the push. Rationale:
- Preserves the "FIFO semantics first, launch semantics second" layering.
- Matches real hardware: the real receiver pops each word before the next push can be visible, so core 1 starts with empty RX.
- Easy to verify with a test: after launch, `fifo_to_core1` is empty.

Implementation: `Emulator::step` at wake point calls `bus.sio.drain_fifo_to_core1()` before setting core 1 PC.

### 2.6 Wake semantics — where the launch actually happens

In `Emulator::step`, after core 0 steps, check `bus.sio.pending_launch.take()`:

```rust
if let Some(launch) = self.bus.sio.pending_launch.take() {
    if self.cores[1].is_halted() {
        self.bus.ppb[1].vtor = launch.vtor;
        self.cores[1].regs.msp   = launch.sp;
        self.cores[1].regs.r[13] = launch.sp;
        self.cores[1].regs.set_pc(launch.entry & !1);  // strip Thumb bit
        self.bus.sio.drain_fifo_to_core1();
        self.cores[1].wake();
    }
    // else: core 1 already awake — drop token, machine will re-arm on next halt
}
```

This replaces the body of the existing `maybe_wake_core1`. The old `event_flag[1]`-triggered unconditional wake is **deleted**.

### 2.7 Deletion vs repurposing of current placeholder

Current `maybe_wake_core1` (lib.rs:514–526) is repurposed: same function name and call sites, but body replaced per 2.6. The `event_flag[1]` bubble for generic FIFO→WFE wake stays (user-code-driven IPC still needs it); we just stop piggy-backing the halt-breaking logic on it.

`bus.event_flag` remains for its original purpose: waking a WFE'd core when the other pushes into its RX.

## 3. Test plan

All tests live in `crates/mdrp2040/tests/multicore.rs` (new file, sibling to `firmware.rs`).

### 3.1 Unit-level, no firmware

**T1. `handshake_wakes_core1_at_entry`**
Construct emulator, halt core 1, directly poke `sio_hw->fifo_wr` equivalents by calling `emu.bus.write32(SIO_FIFO_WR, val)` six times in sequence `{0, 0, 1, 0x2004_0000, 0x2001_0000, 0x2000_1001}`. After each push, read `SIO_FIFO_RD` and assert the response equals the pushed value (echo). After the 6th pop, assert:
- `emu.cores[1].is_halted() == false`
- `emu.cores[1].regs.pc() == 0x2000_1000` (Thumb bit stripped)
- `emu.cores[1].regs.msp == 0x2001_0000`
- `emu.bus.ppb[1].vtor == 0x2004_0000`
- `emu.bus.sio.fifo_to_core1.is_empty()`

**T2. `restart_on_mismatch_at_seq2`**
Push `0, 0, 0x42`. Assert state machine resets to seq=0 (push `0, 0, 1, vtor, sp, entry` afterwards and verify wake still works).

**T3. `restart_on_zero_at_seq3`**
Push `0, 0, 1, 0`. Assert seq resets; core 1 stays halted.

**T4. `vtor_captured_before_entry`**
Interleave: after the 6th push, `emu.bus.ppb[1].vtor` must reflect the handshake VTOR, not the reset-time default.

**T5. `second_launch_after_halt`**
Complete a launch, then manually re-halt core 1, then run another handshake with different vtor/sp/entry. Assert second launch takes.

**T6. `handshake_while_awake_noops`**
Wake core 1 manually (`cores[1].wake()`), then run the 6-word sequence. Assert core 1's PC is NOT clobbered to the handshake entry — i.e., the launch token is dropped because core 1 wasn't halted when `Emulator::step` saw it.

**T7. `core0_sees_echo_on_vld`**
After each push in a valid handshake, immediately read `SIO_FIFO_ST`; `VLD` bit (bit 0) must be 1. Then read `SIO_FIFO_RD`; must equal the pushed value.

### 3.2 Integration-level, small synthesised SDK-style firmware

**T8. `sdk_style_sender_firmware`**
Write a minimal Thumb-2 firmware image that executes the real sender algorithm (drain-sev-push-pop-check-restart) with a target entry that writes a canary (`0xDEADBEEF`) to SRAM at a known address, then halts via `bkpt` or a branch-to-self. Load into SRAM via `load_image`, point core 0's reset vector at the sender, step the emulator until core 1 completes its canary write (or a step budget elapses). Assert:
- Canary word `0xDEADBEEF` landed at the expected SRAM address
- No stall: sender loop exited cleanly within N steps
- `cores[1].regs.pc()` has advanced past the entry address (core 1 genuinely executed)

This is the key test — it proves the shortcut is observationally equivalent to the real bootrom for any SDK-compliant sender.

### 3.3 Regression

- Existing `core1_stays_halted_until_fifo_wake` in `tests/firmware.rs` tests the placeholder behaviour (wake-on-any-push). **Rewrite** to: core 1 stays halted after a single push; only after the full 6-word handshake does it wake.
- Existing `halted_core0_does_not_freeze_core1` (tests.rs:1965) is unaffected.

### 3.4 End-to-end smoke (document only, not CI)

Run `picogus_diff_rp2040` per the prompt's acceptance block. Expose core 1 PC in the summary output. Acceptance = core 1 PC ≠ reset vector and zero stalls. Audio is separate.

## 5. Invariants and devil's-advocate notes (for Phase 5)

- **Race under `step_quantum > 1`**: Echo is pushed synchronously during `fifo_wr`, so by the next instruction core 0 sees VLD=1. No WFE needed on the happy path; irrelevant what quantum is.
- **Double-launch (firmware calls `multicore_launch_core1` twice while core 1 is running)**: Token dropped. State machine harmless. Matches "undefined but non-fatal" behaviour on real silicon.
- **Legitimate IPC that coincidentally starts `0, 0, 1, ...`**: Only dangerous if core 1 is halted at the time. In normal firmware flow, `multicore_launch_core1` is the only thing that launches core 1, and after it returns core 1 is awake. Subsequent IPC pushes happen with core 1 awake → state machine may advance internally but the launch token is dropped. Extra echoes in `fifo_to_core0` might confuse the user's IPC protocol — but this is an edge case with no real-world PicoGUS-style firmware hitting it. Document the limitation in tech_debt and move on.
- **Sender restart under partial mismatch**: If the sender's 3rd push is corrupted (seq=2, val=7), bootrom restarts; so do we. Sender's `cmd (1) != response (0)` → sender restarts to seq=0. Fresh handshake succeeds. Covered by T2.
