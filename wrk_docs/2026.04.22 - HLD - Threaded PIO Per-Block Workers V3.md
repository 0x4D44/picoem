# HLD — Threaded PIO Per-Block Workers (V3)

**Date:** 2026-04-22
**Scope:** `mdrp2350` `ThreadedEmulator` only (Windows x86_64 threaded runtime).
**Goal:** Split the single PIO worker thread into three per-block workers
(PIO0, PIO1, PIO2) so the emulator stops serialising what the hardware
runs in parallel, and make the threaded path **faster than serial** on
peripheral-heavy workloads.

**V3 changes vs V2:**
- **§1.1 math corrected.** The barrier is hit **once per quantum**, not
  twice (single-barrier rendezvous post Phase 4 Stage C; see
  `emulator.rs:662,732,838` and the module-level docstring at
  `emulator.rs:1-9`). Critical path is `max(phase_work) + barrier_tail`.
  Bands recomputed.
- **§2.3 `gpio_in_snapshot` dropped.** V2 admitted it solves a
  non-race — coord's only writer of `gpio_in` happens before coord's
  barrier, and the barrier's Release/Acquire pair makes the workers'
  next read see it. Dropping this removes an atomic, a publish call,
  and an accessor churn.
- **§2.4 accessor mechanism pinned.** `impl Deref<Target=T>` on
  `Aligned<T>` so the existing `self.pads[block].store(...)` pattern
  works unchanged.
- **§2.8 poisoning reassembly concrete type pinned.** `self.pio_blocks
  = None` on any panic path.
- **§7 gate tightened** with p99 criterion and a concrete
  proceed/reconsider matrix. Captures `contention` baseline in the
  same session.
- **§8 beat-serial floor added.** Success explicitly requires
  outperforming the serial emulator on OneROM.
- **§8 attribution formula corrected.** Identity is `max(phase_work) +
  barrier_tail`, not `max + coord + 2 × barrier_wait`.
- **§3 adds `paced_bench_rp2350 --runs N`** for statistics; previously
  assumed to exist.
- **§4 item 5 panic-injection mechanism specified** via a
  `debug_assert!` in `apply_pio_command` triggered by a mis-routed
  sentinel command.
- **§4 item 6 stress run** named as a `#[test] #[ignore]` in
  `emulator.rs` runnable via `cargo test -p mdrp2350 -- --ignored stress`.
- **§4 adds alignment layout regression test** (5 lines, catches
  future "let's remove padding" mistakes).
- **§4 tightens `contention` tolerance** to ±3 % mean / +5 % p99 and
  requires stdev reporting to establish noise floor.
- **§1.5 row B rejection** strengthened with code-clarity reasoning
  since no concrete future workload is available to cite.
- **§1 scope** honest about OneROM being the immediate case; drops
  the vague "general pattern" claim.

## 1. Motivation

On `paced_bench_rp2350 --workload onerom` at commit `990f1a7`,
2026-04-21:

| Config | Throughput | Notes |
|---|---|---|
| Serial | **42.1 MHz** | Single host core, no barrier |
| Threaded (current, 4 workers) | **37.5 MHz** | Slower than serial |

Per-worker `--timing` on the threaded path (sq=256):

| Worker | work_mean | wait_mean | wait% |
|---|---|---|---|
| core0 | 1.1 μs | 4.5 μs | 80.6 % |
| core1 | ~0 | 5.6 μs | 99.4 % (halted) |
| **pio** | **4.9 μs** | 0.7 μs | 12.6 % |
| coord | 0.12 μs | 5.5 μs | 97.8 % |

The threaded path is slower than serial on this shape because one
worker serialises all three PIO blocks while 3–5 other host cores
idle. The scope of this HLD is to fix that by making the thread
boundary match the hardware's PIO-block boundary — three independent
PIO blocks on silicon, three workers in the emulator.

**Scope honesty:** OneROM is currently the concrete peripheral-heavy
workload that exposes this bottleneck. The PicoGUS-lineage ISA-bridge
family (of which OneROM is the instance) typically exercises all three
PIO blocks simultaneously. If the roadmap ever lands a workload that
only uses one PIO block, the three-worker topology still runs it
correctly; idle workers park at the barrier within ~20 ns of spawn
(§6). This HLD is sized for "get OneROM right"; single-block-workload
optimisation would be a follow-up if ever measured to matter.

### 1.1 Expected throughput after split (corrected math)

**Per-quantum wall clock = max(all workers' phase_work) + barrier_tail.**

The barrier is hit **once per quantum** (single-barrier rendezvous
since Phase 4 Stage C; see emulator.rs:1-9 module docstring and
emulator.rs:662/732/838 call sites). "Barrier tail" is the time from
the last arriver's `count.fetch_add` returning `parties` to all
waiters being released — a few tens of nanoseconds of atomic store +
notify_all traffic, plus any spin budget burned by early arrivers
that doesn't overlap with the productive worker.

Per-SM `step_n` cost is ~4.9 ns/sysclk (post-2026-04-20 profiling).
For OneROM at sq=256: PIO1 ≈ 1.3 μs, PIO2 ≈ 2.5 μs, PIO0 ≈ 0 μs,
core0 ≈ 1.1 μs, core1 halted, coord ≈ 0.12 μs.

Per-quantum critical path ≈ `max(1.1, 0, 1.3, 2.5, 0.12) + barrier_tail`
≈ `2.5 + barrier_tail μs`.

**Bracketed by the §7 barrier microbench outcome:**

| Scenario | 6-way barrier (mean / p99) | Per-quantum wall | Throughput | vs threaded | vs serial |
|---|---|---|---|---|---|
| Optimistic | 450 ns / 1.2 μs | 2.95 μs | 87 MHz | **2.32 ×** | **2.07 ×** |
| Expected | 550 ns / 1.5 μs | 3.05 μs | 84 MHz | **2.24 ×** | **2.00 ×** |
| Conservative | 700 ns / 2.0 μs | 3.20 μs | 80 MHz | **2.13 ×** | **1.90 ×** |

Success floor (§8): **mean threaded OneROM ≥ 60 MHz** (1.6× threaded,
1.42× serial) — defended against model pessimism, measurement
variance, and unknown second-order effects like coord↔worker pad-line
bouncing (~60–120 ns per quantum, see §6) and one-off OS scheduling
jitter. The target band above is the *expected* outcome; 60 MHz is
the *must-achieve* bar below which we do not merge.

## 1.5 Alternatives considered and rejected

| # | Alternative | Cost | Rejection reason |
|---|---|---|---|
| A | Keep serial — declare threaded "not for peripheral workloads" | 0 lines | Abandons threading's premise; future dual-core-compute + peripheral workloads pay the serial tax |
| B | Fold PIO2 onto coord; keep 4 workers | ~20 lines | OneROM-specific heuristic (hard-coded "PIO2 is the hot block"); adds asymmetric temporal semantics across blocks (PIO2 has 0-quantum pad lag vs 1-quantum for PIO0/PIO1); hurts code clarity — three-block hardware maps cleanly to three workers, coord-with-a-PIO does not |
| C | Keep single PIO worker but `par_iter` the blocks internally | ~30 lines | Rayon spawn/join per quantum = μs-scale overhead; paying a nested parallelism primitive inside a barrier is strictly worse than a wider barrier |
| D | Amortise the quantum barrier across N quanta | ~50 lines | Breaks PLL-LOCK and master_cycle semantics (HLD V7 §3) — the Acquire/Release pair between coord's fetch_add and CPU PLL reads requires per-quantum synchronisation |
| E | Conditional split: 1 PIO worker when ≤ 1 block active, 3 when more | ~80 lines + feature flag | Runtime topology switching adds state machine + test matrix explosion; not warranted until measurement proves static 3-worker is too expensive for single-block workloads |

**Chosen:** full per-block split (3 PIO workers, always on). Reasoning:

1. **Matches hardware topology.** Three independent PIO blocks on
   silicon — the emulator mirrors that at the thread boundary.
2. **Symmetric.** Every block gets the same treatment; no per-block
   special cases in the worker body.
3. **Simpler than E.** One topology, no conditional paths.
4. **B's win is narrower than it looks** once §1.1's corrected math
   removes the phantom second barrier: B gives max(PIO1, PIO2+coord)
   ≈ max(1.3, 2.62) = 2.62 μs vs our 2.5 μs — a ~5 % throughput win
   for B's asymmetry. Not worth the topology-hard-codes-PIO2-is-hot
   debt.

## 2. Design delta

Go from 4 workers (core0, core1, pio, coord) to 6 (core0, core1, pio0,
pio1, pio2, coord). Nearly all state on `super::ThreadedPio` is
already per-block indexed (`sm_enabled: [AtomicU8; 3]`, `irq_flags`,
`dreq`, `pads`, TX/RX SPSC queues). Two concrete shared-state changes:

- The command queue becomes per-block.
- Per-block atomics written concurrently by three workers
  (`pads[3]`, `irq_flags[3]`, `sm_enabled[3]`, `dreq[3]`) are padded
  onto distinct cache lines.

### 2.1 Per-block PIO worker body

Replace `pio_worker_body(blocks: [PioBlock; 3], ...)` with
`pio_block_worker_body(block_idx: usize, block: PioBlock, ...)`. Each
worker owns one block. Loop body:

```rust
for _ in 0..n {
    for cmd in shared.pio.drain_commands(block_idx) {
        apply_pio_command(&mut block, &shared.pio, block_idx, cmd);
    }

    // `shared.gpio.read_in()` is already race-free: coord's only
    // writer is inside `update_gpio`, which happens before coord's
    // barrier.wait; workers' next read is after their own
    // barrier.wait returns, so the barrier's Release/Acquire pair
    // establishes happens-before coord-write → worker-read.
    let gpio_in = shared.gpio.read_in();

    if shared.pio.read_sm_enabled(block_idx) != 0 {
        block.step_n(step_q, gpio_in);
        shared.pio.write_irq_flags(block_idx, block.pending_irqs() as u8);
    }

    // UNCONDITIONAL — even a disabled block must publish its current
    // pad latch so coord's update_gpio sees a coherent snapshot.
    // Mirrors emulator.rs:724-726.
    shared.pio.write_pads(block_idx, block.pad_out, block.pad_oe);

    barrier.wait();
}
```

### 2.2 Per-block command queue

`ThreadedPio.commands: Mutex<Vec<PioCommand>>` becomes
`[Mutex<Vec<PioCommand>>; PIO_BLOCKS]`.
- `send_command(cmd)` routes by `cmd.block()` into
  `commands[cmd.block()]`.
- `drain_commands(block_idx) -> Vec<PioCommand>` drains one queue,
  preserving capacity via `mem::replace(&mut *guard, Vec::with_capacity(cap))`
  per pio.rs:246-250. `drain_preserves_capacity` test specialises to
  `block_idx = 0`; new `drain_preserves_capacity_per_block` exercises
  all three queues.
- `ThreadedPio::reset` loops all three mutex-guarded queues and clears
  each.

Add `PioCommand::block(&self) -> u8` (match over the four variants).

Add `debug_assert!(cmd.block() as usize == block_idx)` as the first
line of `apply_pio_command`. This is the panic-injection hook for
§4 item 5 — a test posts a command with a sentinel `block` value that
routes through `send_command` into queue N but is mis-constructed to
assert against block M, tripping the `debug_assert` inside worker M.

**Ordering contract:** intra-block FIFO preserved (each queue is its
own Mutex+Vec). Cross-block FIFO is not preserved at drain, but
quantum-boundary barrier serialises what any test or firmware
observes — commands posted before quantum N's start are drained by
all three workers at the top of quantum N. §4 item 3 keeps this
property visible.

### 2.3 False-sharing padding (upfront)

```rust
#[repr(align(64))]
struct Aligned<T>(T);

impl<T> std::ops::Deref for Aligned<T> {
    type Target = T;
    fn deref(&self) -> &T { &self.0 }
}

// In ThreadedPio:
pads:       [Aligned<AtomicU64>; PIO_BLOCKS],
irq_flags:  [Aligned<AtomicU8>;  PIO_BLOCKS],
sm_enabled: [Aligned<AtomicU8>;  PIO_BLOCKS],
dreq:       [Aligned<AtomicU8>;  PIO_BLOCKS],
```

`impl Deref` keeps existing accessor bodies (`self.pads[block].store(...)`)
unchanged — the Deref handles the `.0` indirection. 4 fields × 3
blocks × 64 B = 768 B padding per `ThreadedPio` instance. Memory
cost is noise; the three PIO workers each own one cache line per
field for writes, eliminating the textbook 3-writer false-sharing
pattern on a 24-byte (pads) or 3-byte (u8 atomics) array.

Coord reads all three `pads` sequentially in `update_gpio` — those
lines arrive in Shared state and bounce back to Exclusive when each
PIO worker writes the next quantum. ~60–120 ns per quantum of
coord↔worker invalidation traffic; accounted for in §1.1's
conservative band.

### 2.4 Barrier

`SpinBarrier::new(4)` → `SpinBarrier::new(6)` in emulator.rs:406.
§7 pre-implementation gate measures the 6-way cost before we
commit.

### 2.5 `thread_mask`

`[usize; 4]` → `[usize; 6]`. Default `[0, 1, 2, 3, 4, 5]`. Mapping:
`[core0, core1, pio0, pio1, pio2, coord]`. `with_thread_mask`
signature updates. Minimum-host-cores assertion in `from_emulator`
goes `>= 4` → `>= 6`. 4-core advisory `eprintln!` removed.

SMT caveat: dense mapping assumes logical cores 0..5 are on distinct
physical cores. Bench host has SMT disabled in BIOS; no action
needed for this HLD. Users on SMT hosts pass
`with_thread_mask([0, 2, 4, 6, 8, 10])`.

### 2.6 Timing

`RunTimings.pio` → `.pio0`, `.pio1`, `.pio2`. `RunTimings::summary()`
return `[WorkerSummary; 4]` → `[_; 6]`. `WorkerName` enum adds
`Pio0/Pio1/Pio2` (removes `Pio`). `name_idx` debug_asserts grow to 6.
`worker_name_labels_are_stable` and `run_timings_samples_reports_core0_count`
tests update.

### 2.7 Panic/poisoning reassembly

Each PIO worker returns `(PioBlock, PerWorkerTimings)` on Ok. On the
happy path (all three Ok), reconstruct `[PioBlock; 3]` into
`self.pio_blocks`. **On any PIO worker panic: `self.poisoned = true;
self.pio_blocks = None`** — all three returned `PioBlock` values are
dropped (even Ok ones from the non-panicking workers), matching the
existing poisoning contract (instance cannot be reused after any
worker panic). Panicked-worker message enumerates the specific block:
`pio1` rather than the V1 generic `pio`.

## 4. Test plan

1. **Unit tests `cargo test -p mdrp2350` pass.** The four renamed
   `ThreadedPio` tests plus five new ones.
2. **New per-block integration test.** SMs enabled on PIO1 (1 SM)
   and PIO2 (1 SM) with different INSTR_MEM; run N quanta; assert
   both `read_pads(1)` and `read_pads(2)` show expected state
   independently.
3. **Cross-block command ordering smoke.** From core0 in one burst:
   three `WriteCtrl` commands, one per block, enabling different SM
   counts. After `run_quanta(1)`, assert all three enable masks
   reflect the command.
4. **Idle-block pad-publish semantics.** Enable SM on PIO1 for
   several quanta (pads latch non-zero). Disable via
   `WriteCtrl{block:1, val:0}`. Run 10 more quanta. Assert
   `read_pads(1)` matches the latched value from before disable.
5. **Panic-in-pio1 naming + reassembly.** Post a command with a
   deliberate mis-routing sentinel that trips the `apply_pio_command`
   `debug_assert`. Join `run_quanta`. Assert: (a) panic message
   contains `pio1` specifically, not `pio`; (b) `emu.poisoned() ==
   true`; (c) `emu.pio_blocks.is_none()`. Parameterise over
   `{core0, core1, pio0, pio1, pio2, coord}` as a table-driven test
   if feasible; otherwise one pio1 case is the must-have, the others
   are nice-to-have.
6. **Stress run.** `#[test] #[ignore] fn stress_onerom_60s` in
   `crates/mdrp2350/src/threaded/emulator.rs` that runs
   ThreadedEmulator on the OneROM synthetic shape for 60 s or 10⁸
   quanta with `debug_assertions=on`. Invoked explicitly:
   `cargo test -p mdrp2350 -- --ignored stress_onerom`. No panic,
   no poison. Journal records elapsed wall time + quantum count.
7. **Throughput: OneROM win.** `paced_bench_rp2350 --threaded
   --workload onerom --runs 10` (no `--timing`). Report mean ±
   stdev + p50 + p99. **Mean ≥ 60 MHz absolute + ≥ 1.6× baseline
   threaded (= 60 MHz vs 37.5 MHz)**; both conditions must hold.
8. **Throughput: compute regression.** `paced_bench_rp2350 --threaded
   --workload contention --runs 10`. Mean within ±3 % baseline; p99
   within +5 % baseline. Report stdev — if stdev exceeds 2 % the
   ±3 % bound tightens only to within noise, and the reviewer
   judges whether a 3 % drift is within-noise or real. The stdev
   report is the noise-floor establishment the devil's advocate
   called for.
9. **Unaffected paths: serial + silicon oracles.** `cargo test -p
   mdrp2350` and `cargo test -p mdpicoem-harness` pass — serial path
   unchanged. No silicon-oracle delta expected (serial path
   untouched).
10. **OneROM serving oracle smoke.** `onerom_serving_oracle_rp2350`
    is serial-path only; run once to confirm no accidental fallout.
11. **Alignment layout regression guard.** `#[test]` in `pio.rs`:
    ```rust
    assert_eq!(align_of::<Aligned<AtomicU64>>(), 64);
    assert_eq!(size_of::<[Aligned<AtomicU8>; 3]>(), 192);
    ```
    Catches a future "let's drop the padding" mistake.

## 5. Out of scope

- **RP2040 threaded path.** Separate chip, not threaded yet.
- **PIO→NVIC IRQ routing.** Parity with today's serial `Bus`.
- **Real DMA modelling.** Emulator DMA is stubbed; `GlueDma` helper
  runs on driver thread. Consequence: in threaded mode PIO1 and
  PIO2 now step concurrently in the same quantum, whereas on
  silicon they are cycle-coupled through DMA. The pad-observable
  end state remains correct at quantum-boundary granularity; this
  skew is addressed when real DMA lands, not here. When DMA does
  land it will need to choose between adding a 7th worker (7-way
  barrier) or coord-hosting (eats coord's current 97.8 % wait
  headroom); that HLD will revisit the barrier-arity cost.
- **RISC-V (Hazard3) threading.** `from_emulator` already panics on
  RISC-V cores.
- **Per-SM split.** Would require per-SM pad merging inside
  `PioBlock`; not supported today, not needed for OneROM.
- **Silicon oracle deltas.** No serial-path changes → no silicon
  oracle impact.

## 6. Risks

- **6-way barrier cost.** Contention rises with party count. §7 gate
  measures it; recomputes the predicted throughput band based on the
  measured number before committing to implementation.
- **Non-PIO workload regression.** Compute workloads gain nothing
  from PIO parallelism but pay the arity tax. §4 item 8 caps
  tolerance at ±3 % mean / +5 % p99 with stdev reporting to
  establish the noise floor.
- **Idle-worker publish cost.** PIO0 idle in OneROM: worker runs
  `drain_commands(0)` (empty uncontended mutex ~20 ns),
  `write_pads(0, 0, 0)` (own cache line post-padding), barrier.wait.
  Total ~50 ns per quantum — accepted.
- **Coord ↔ worker `pads` line bouncing after padding.** Coord reads
  all three lines sequentially; workers each invalidate their line on
  the next quantum's write. ~60–120 ns per quantum of invalidation
  traffic — already in §1.1 conservative band, not a blocker.

## 7. Pre-implementation measurement gate

Before implementation starts, extend `threading_micro.rs` (Phase 0c
barrier microbench) to run at parties ∈ {2, 4, 6, 8}. Record mean /
p50 / p99 round-trip. **In the same bench session**, capture the
`contention` workload baseline at commit `990f1a7`:
`paced_bench_rp2350 --threaded --workload contention --runs 10`
→ mean / stdev / p50 / p99. This fixes the baseline for §4 item 8 and
removes merge-time ambiguity.

**Gate criteria (6-way barrier):**

| Outcome | Disposition |
|---|---|
| Mean ≤ 550 ns AND p99 ≤ 1.5 μs | **Proceed — optimistic band in play** |
| Mean ≤ 700 ns AND p99 ≤ 2.0 μs | **Proceed — expected band; target 60 MHz floor (§8)** |
| Mean ≤ 900 ns AND p99 ≤ 3.0 μs | **Proceed — conservative band; floor might be at risk, widen stdev tolerance by 50 %** |
| Anything worse | **Stop and reconsider** — options: raise `SPIN_BUDGET`, two-level barrier (local per-block-pair + global), or revisit whether the split is worth it |

Gate cost: ~15 min bench work; binary decision tree. No code change
to `ThreadedEmulator` required to run.

## 8. Success criteria

All measurements against baseline commit **`990f1a7`**, host = 20-core
bench with SMT disabled in BIOS, sq=256, `--timing OFF` during
throughput comparison (instrumentation adds ~1 % overhead).

Merge requires ALL of the following:

- `cargo test -p mdrp2350` and `cargo test -p mdpicoem-harness` pass.
- **OneROM:** `paced_bench_rp2350 --threaded --workload onerom
  --runs 10`. Mean ≥ **60 MHz** (absolute) AND mean ≥ **1.6× baseline
  threaded (37.5 MHz)**. Both conditions must hold.
- **Beat-serial floor:** the above 60 MHz figure already exceeds
  serial's 42.1 MHz by 42 %. Stated explicitly as a merge bar: if
  threaded OneROM does not outperform serial OneROM by at least 18 %
  (i.e. ≥ 50 MHz), the threading investment has not paid off for this
  workload and we regroup before merging.
- **Compute regression:** `paced_bench_rp2350 --threaded --workload
  contention --runs 10`. Mean within ±3 % baseline; p99 within +5 %
  baseline; stdev reported so reviewer can judge noise vs real drift.
- **Attribution check (loose):** one `--threaded --workload onerom
  --timing --runs 3` run. Sum the measured `max(pio0, pio1, pio2,
  core0, coord) phase_work_mean_ns + barrier_wait_min_ns` (the
  slowest worker's barrier wait, which is ~0 — it was the releaser;
  use the minimum across workers as a proxy for the barrier-release
  constant). Check that matches the `--timing OFF` mean wall-clock
  per-quantum throughput within ±10 %. If off by more, the timing
  instrumentation itself is skewing the measurement — report and
  journal, do not block merge.
- **Stress:** §4 item 6 passes (60 s / 10⁸ quanta, no panic, no
  poison, `debug_assertions=on`).
- **All other §4 items green.**

If any of the above fails, do not merge; regroup in a journal entry
with the failing numbers.
