# OneROM Full-System Oracle — Design

Version: 0.1.0 — DRAFT
Date: 2026-04-14
Parent: RP2350 Emulator HLD; direct follow-up to `2026.04.14 - HLD - OneROM PIO Differential.md`
Depends: PIO differential oracle complete; Phase 4 flash boot; Phase 7 coprocessors

## 1. Purpose

Run a real, unmodified OneROM firmware binary through our emulator
end-to-end: bootrom → second-stage → OneROM's `main()` → clock / GPIO
/ PIO / DMA init → serving loop. Then drive the same CS + address
pin stimulus the PIO oracle uses, observe the data byte on the
output pins, and confirm behaviour is plausible against an
independent reference.

This is Stage F from the PIO differential LLD, now scoped in its own
doc because it crosses multiple emulator subsystems and will surface
bugs well beyond the PIO engine.

### Why this matters

The PIO oracle (Stages A–E) validated our PIO engine against an
independent PIO implementation using **synthetic** driver code — no
Cortex-M33 involvement on either side. This Stage F exercises the
full stack: CPU, bus, XIP flash, clocks, coprocessors (during
bootrom), and DMA, with the PIO engine driven by firmware rather
than harness pokes.

Getting OneROM serving ROM data through our emulator proves the
Phase 1–7 stack actually holds together under a real workload.

### Non-goals

- Cycle-accurate comparison against Piers' `epio`. See §4 — the real
  OneROM PIO program almost certainly differs from Piers' sample
  `setup_onerom`, so the committed `onerom_2364.trace` may not apply.
- Full DMA emulation. Our emulator stubs DMA (writes silently no-op).
  The harness will glue the DMA chain externally; a real DMA
  peripheral remains future work.
- Testing every ROM configuration. One `.bin` (`test-sdrr-0`) is
  enough to prove the loop.
- CI integration. Local dev oracle.

## 2. Scope for this session

Four milestones, in strict order:

1. **F.1 — Boot without crash.** Load
   `onerom-fire-24-a-rp2350-test-sdrr-0.bin` into XIP flash, load
   the real RP2350 bootrom at `0x00000000`, run emulator. The CPU
   should boot through the bootrom, into OneROM's image, reach a
   settled state (main loop, WFE, or WFI). Diagnose any crash /
   fault / hang.
2. **F.2 — Detect PIO-ready sync point.** Identify cleanly when
   OneROM's init has finished and PIO SMs are enabled and serving.
3. **F.3 — Inspect PIO state, decide on oracle.** At the sync
   point, dump the loaded `instr_mem`, SM regs, and DMA config.
   Compare against `onerom_2364.trace`'s header block. If they
   match, reuse the committed trace. If not, pick a smoke-test
   criterion and document the divergence.
4. **F.4 — Drive stimulus + observe.** Assert CS low, drive an
   address, step N cycles, read the data byte off the output pins.
   Compare against the oracle decided in F.3.

Out of scope for this session: anything beyond F.4. No writing,
no bank switching, no multiple ROM configs, no image select pins.

## 3. Boot architecture

```
  t=0:  Emulator start
          │
          ▼
        Bootrom at 0x00000000 (roms/rp2350/bootrom-combined.bin)
          │  - reads IMAGE_DEF / vector table from flash
          │  - validates (via DCP SHA-256 / RCP canaries — Phase 7)
          │  - sets up second-stage load
          ▼
        XIP flash at 0x10000000 (onerom-*.bin)
          │  - first 256 B may be a second-stage bootloader stub
          │  - vector table at some offset, starting 0x20082000 (MSP)
          │  - reset vector points into flash
          ▼
        OneROM Reset_Handler → runtime init → main()
          │  - clock tree (XOSC, PLL_SYS; maybe overclock)
          │  - GPIO bank configure
          │  - PIO program upload (3 SMs in block 0)
          │  - DMA configure (2 channels, chained)
          │  - enable SMs → fire_serve_mode = FIRE_SERVE_PIO
          ▼
        Serving loop (CPU idles; PIO + DMA do the work)
```

## 4. The PIO-program-mismatch question

Piers' own comment on `test/onerom_programs.h`:
> "Set up a _sample_ One ROM serving algorithm. Note that the latest One
> ROM algorithm may be different to this."

And his `piorom.c` (600+ lines of comments + code) documents the real
algorithm: same **shape** (three SMs + chained DMA), but the specific
bytecode and configuration are generated at firmware build time from
apio macros with OneROM-specific tuning.

Therefore: **our committed `onerom_2364.trace` is almost certainly
not cycle-accurate for the real firmware.** We'll prove or disprove
this in F.3 by dumping the CPU-loaded `instr_mem` and comparing.

### Oracle strategy decision (made in F.3)

Branches:

- **Branch A — Bytecode matches.** Lucky case. Reuse
  `onerom_2364.trace` directly. Run F.4 as a strict cycle-by-cycle
  diff.
- **Branch B — Bytecode differs, architecture matches.** Most
  likely case. The committed trace is wrong but the timing envelope
  from `piorom.c` ("address valid to correct data byte: 11–14
  cycles") gives us a smoke-test oracle: data appears within 11–14
  cycles of CS assertion, value matches the SRAM content at the
  given address. Document this as the MVP oracle; cycle-accurate
  diff is a future enhancement.
- **Branch C — Architecture also differs.** Unlikely given
  `piorom.c` explicitly confirms the three-SM + two-DMA pattern,
  but if it happens we redesign the harness around whatever
  structure we observe.

For this LLD we assume **Branch B** is what we'll land on. Branch A
is a bonus.

## 5. Sync-point strategy (F.2)

Goal: detect deterministically when OneROM's init has finished and
PIO is ready to serve. Candidate signals, most reliable first:

| Signal | Pros | Cons |
|--------|------|------|
| PIO1.CTRL and PIO2.CTRL both have SMs enabled | Matches the real firmware's block layout exactly | Needs harness to poll two blocks, not one |
| `sdrr_runtime_info.rom_set_index` transitions from `0xFF` to a valid value | Corresponds to init-complete semantically | Requires knowing where the struct lives in RAM |
| Fixed cycle count (e.g. 50 000) | Trivial | Fragile: depends on bootrom + clock-tree timing |

**Choice:** poll PIO1.CTRL and PIO2.CTRL after each `emu.step()`.
Sync = `(PIO1.CTRL & 0xF) != 0 && (PIO2.CTRL & 0xF) != 0` — i.e. the
address reader and data writer blocks both have at least one SM
enabled. Cap the search at a generous cycle budget (e.g. 10 000 000)
to fail fast if boot never completes.

**Correction from v0.1 (which this supersedes):** The earlier draft
said "poll PIO0 block 0 for SM_ENABLE == 0b111". That applies only
to the synthetic `setup_onerom` sample in
`test/onerom_programs.h`, which consolidates three SMs on a single
block. The *real* firmware splits the algorithm across two blocks:
`sdrr/src/piodma/piorom.c:422-430`:

```c
#define BLOCK_ADDR    1   // PIO1 — SM0 = address reader
#define BLOCK_DATA    2   // PIO2 — SM0 = data writer, SM1 = CS handler
#define BLOCK_MONITOR 0   // PIO0 — unused in typical serving mode
```

Observed at sync on 2026-04-15: `PIO1.CTRL = 0x01`, `PIO2.CTRL =
0x03`, `PIO0.CTRL = 0` — matches Piers' design.

### Capturing the PIO state at sync

Immediately after sync is detected:

- Read `instr_mem[0..31]` via `read32(PIO0_BASE + 0x048 + i*4)` — the
  loaded bytecode.
- Read each SM's `CLKDIV / EXECCTRL / SHIFTCTRL / PINCTRL` — the
  configured registers.
- (For DMA, see §6.)

Compare to `onerom_2364.trace`'s header block. This is the
decision point for §4's oracle branch.

## 6. DMA intercept

Our emulator has **no DMA engine**. Writes to the DMA register range
(`0x50000000`) are silently accepted and produce nothing.

OneROM's init configures DMA0 + DMA1 as a chain, then the serving
loop depends on those channels running autonomously. Without
something emulating DMA, the PIO chain won't move data.

### Harness-side glue DMA (v2 of Stage D's pattern)

The harness watches DMA register writes during init. Specifically:

- `CHn_READ_ADDR` at `0x50000000 + 0x40*n + 0x00`
- `CHn_WRITE_ADDR` at `+0x04`
- `CHn_TRANS_COUNT` at `+0x08`
- `CHn_CTRL_TRIG` at `+0x0C` — writing this triggers the channel

When `CH0_CTRL_TRIG` is written with a valid config, the harness
captures the channel's read/write pointers and bit mode, and
activates its `GlueDma` state machine (same shape as Stage D's, but
now parameterised rather than hard-coded).

Open simplification: if OneROM's DMA config matches the parameters
our Stage D glue DMA hard-coded (`read_cycles=4`, `write_cycles=4`,
bit_mode=8, reading SM1→SM2 TX), we can **reuse that glue DMA
unchanged** and just enable it at the sync point. We'll know after
F.3.

### Bus-tap mechanism

Options:

- **Poll:** after each `emu.step()`, read the DMA registers via
  `read32` and compare to last-seen values. Cheap, doesn't need
  emulator changes.
- **Callback:** add a bus-write observer trait (bigger change).

**Choice:** polling. Fits the existing harness style.

## 7. Stimulus and observation (F.4)

After sync + glue DMA is running:

1. Cycle 0 (relative): drive CS (pin 8) low, address pins (9–20) to
   some fixed value (e.g. `0x000`).
2. Step 20 cycles.
3. Each cycle: `observe(&emu.bus.pio[0], input_drive, input_level)`
   → (our_drive, our_level). Log.
4. After 20 cycles: verify data byte appeared on pins 0–7 within
   the 11–14 cycle window documented in `piorom.c`, and that its
   value matches the SRAM content at the address we drove.

Expected output: pin 0–7 = SRAM[address] for a brief window while
CS is asserted.

"SRAM" here means whatever ROM image the OneROM build embedded for
the `test-sdrr-0` config. We'll figure out the expected byte
pattern from the `.bin` dump (search for the ROM table, look at
address 0).

## 9. Risks

- **Bootrom + OneROM image format.** RP2350 expects IMAGE_DEF
  blocks; OneROM's `.bin` may or may not include one. Our bootrom
  may not tolerate non-standard images. If it rejects OneROM's
  image, workaround: skip the bootrom and jump directly to
  OneROM's reset vector (dirty but unblocking).
- **Clock tree reprogramming.** OneROM configures PLL_SYS to some
  frequency (default 150 MHz; overclock variants up to 300 MHz).
  Phase 2 handles PLL but the specific frequency OneROM picks may
  exercise edge cases.
- **Coprocessors during bootrom.** Phase 7 closed out full
  coprocessor coverage. Any remaining bug here would fail during
  bootrom execution, before even reaching OneROM's code. Good
  canary — if bootrom completes, Phase 7 held up.
- **DMA register names / offsets.** We're guessing at DMA register
  layout from the RP2350 datasheet. First F.3 run may need to
  iterate on the intercept logic.
- **`sdrr_runtime_info` location.** The struct lives in a named
  section `.sdrr_runtime_info`. Finding it requires parsing the
  firmware's linker layout. Not needed for the PIO-CTRL sync but
  might be needed for deeper diagnostics.
- **OneROM hits a feature we don't implement.** Most likely
  candidates: SPI for SWD comms (unlikely in test config), USB
  (disabled in `fire-24-a`), TIMER (if OneROM polls a timer during
  init), FLASH ops beyond basic XIP reads (OneROM probably doesn't
  write flash).
- **Firmware uses a stdlib function our emulator's C-side stub
  can't satisfy.** OneROM runs bare-metal and doesn't depend on
  host stdlib. The bootrom uses internal copies. So this should be
  fine.

## 10. Open questions deferred to implementation

1. Which address range does OneROM expect DMA to read from? SRAM
   (`0x20000000`) or XIP (`0x10000000`)? The `.bin` embeds the ROM
   table; where does it end up at runtime? Answered at F.3.
2. Does OneROM's bootloader reprogram flash clock config (SSI/QMI)?
   Phase 4's flash boot handles basic XIP; if OneROM pokes SSI we
   may need stubs.
3. Does the `test-sdrr-0` config actually enable `FIRE_SERVE_PIO`?
   The runtime_info struct has `.fire_serve_mode` — if it's set to
   `FIRE_SERVE_CPU` for this variant, the PIO path never runs and
   we pick a different `.bin`.
4. Can the existing Stage D `GlueDma` state be reused verbatim, or
   does OneROM's DMA config differ enough to force a rewrite?
   Answered at F.3.
