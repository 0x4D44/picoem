# HLD: Optimize `condition_passed()`

**Version:** 1.0.0
**Date:** 2026-04-13
**Status:** PROPOSED

## Problem

Flamegraph profiling shows `Registers::condition_passed()` at 21% self-time -- the #2 hotspot after `step()` itself. It is a pure leaf function (no callees) called on every emulated cycle via `decode_execute()`.

## Current Implementation

```rust
// registers.rs:254 -- no #[inline(always)] attribute
pub fn condition_passed(&self, cond: u8) -> bool {
    match cond & 0xF {
        0x0 => self.flag_z(),                                     // EQ
        0x1 => !self.flag_z(),                                    // NE
        0x2 => self.flag_c(),                                     // CS/HS
        0x3 => !self.flag_c(),                                    // CC/LO
        0x4 => self.flag_n(),                                     // MI
        0x5 => !self.flag_n(),                                    // PL
        0x6 => self.flag_v(),                                     // VS
        0x7 => !self.flag_v(),                                    // VC
        0x8 => self.flag_c() && !self.flag_z(),                   // HI
        0x9 => !self.flag_c() || self.flag_z(),                   // LS
        0xA => self.flag_n() == self.flag_v(),                    // GE
        0xB => self.flag_n() != self.flag_v(),                    // LT
        0xC => !self.flag_z() && (self.flag_n() == self.flag_v()), // GT
        0xD => self.flag_z() || (self.flag_n() != self.flag_v()), // LE
        0xE => true,                                              // AL
        _ => true,                                                // unconditional
    }
}
```

## Call Sites (3 total)

| Location | Call pattern | Frequency |
|---|---|---|
| `decode.rs:45` | Every instruction via `decode_execute()` | Every cycle |
| `execute.rs:827` | Thumb-16 conditional branch `B.cond` | Per `B.cond` instruction |
| `execute_thumb32.rs:813` | Thumb-32 conditional branch `B.W T3` | Per `B.W cond` instruction |

The `decode_execute()` call site dominates. It calls `condition_passed(cond)` unconditionally for every instruction, even though `cond` is `0xE` (AL/always) outside IT blocks -- which is the overwhelming majority of instructions.

## Root Causes

Three compounding issues:

### 1. Missing `#[inline(always)]`

Every other flag accessor on `Registers` has `#[inline(always)]` (see `flag_n`, `flag_z`, `flag_c`, `flag_v`, `set_nz`, `set_nzcv`, etc. -- all annotated). `condition_passed` is the sole exception. Without the annotation, the compiler may or may not inline it, and with LTO disabled in the profiled build, it almost certainly does not. This means real call/return overhead on every single emulated cycle.

### 2. Called unconditionally for every instruction

In `decode_execute()`:

```rust
let in_it = self.it_state & 0xF != 0;
let cond = if in_it { (self.it_state >> 4) & 0xF } else { 0xE };
let cond_passed = self.regs.condition_passed(cond);  // called BEFORE checking is_wide
```

Outside an IT block, `cond` is always `0xE`, which means `condition_passed` does a match that falls through to `0xE => true`. This is pure overhead -- branching into a 16-arm match just to return `true`.

IT blocks are rare in typical ARM code (a few percent of instructions at most). The vast majority of cycles evaluate `condition_passed(0xE)` and get `true`.

### 3. Match-based dispatch is branch-heavy

The 16-arm match compiles to a jump table or branch chain. Each arm calls `flag_*()` accessors that are themselves bit extractions from `xpsr`. Even when inlined, this is at minimum: mask `cond`, index jump, extract flag bits, return. For `0xE` the jump is trivially `true`, but the jump-table dispatch and mask still happen.

## Proposed Optimization

Three changes, ordered by expected impact:

### Fix 1: Add `#[inline(always)]`

Annotate `condition_passed` the same as every other flag accessor:

```rust
#[inline(always)]
pub fn condition_passed(&self, cond: u8) -> bool {
```

This eliminates call/return overhead at all 3 call sites. Expected impact: significant on its own, since this is a pure leaf called ~80M times/sec.

### Fix 2: Early-out for `0xE` (AL) before the match

Guard the common case before entering the match:

```rust
#[inline(always)]
pub fn condition_passed(&self, cond: u8) -> bool {
    if cond >= 0xE { return true; }  // AL + unconditional -- ~95% of calls
    // ... match for the remaining 14 condition codes
}
```

This converts the hot path from "mask + jump table + return" to "compare + predicted-taken branch + return". Since `cond >= 0xE` covers both `0xE` (AL) and `0xF` (unconditional), it handles 100% of outside-IT-block calls and some inside-IT-block calls.

### Fix 3: Replace match with a lookup table

Replace the 16-arm match with a branchless lookup table indexed by condition code and the 4 flag bits:

```rust
/// Precomputed condition truth table: 16 conditions x 16 flag combinations = 256 bits = 32 bytes.
/// Index: (cond << 4) | (N << 3) | (Z << 2) | (C << 1) | V
static COND_TABLE: [u8; 32] = [ /* 32 bytes, each bit is one flag combo */ ];

#[inline(always)]
pub fn condition_passed(&self, cond: u8) -> bool {
    if cond >= 0xE { return true; }
    let flags = (self.xpsr >> 28) & 0xF;  // extract NZCV as 4-bit index
    let index = ((cond as u32) << 4) | flags;
    (COND_TABLE[(index >> 3) as usize] >> (index & 7)) & 1 != 0
}
```

This replaces all branching with: one compare (for early-out), one shift+mask (extract flags), one shift+mask (index the table), one byte load, one shift+mask (extract the bit). Fully branchless for the non-AL path.

The table is 32 bytes -- fits in a single cache line, will be permanently hot.

## Alternative Considered: Skip at call site

Instead of optimizing `condition_passed`, skip the call entirely when not in an IT block:

```rust
let cond_passed = if in_it {
    self.regs.condition_passed((self.it_state >> 4) & 0xF)
} else {
    true  // outside IT block, all instructions are unconditional
};
```

This is simpler but incorrect for `B.cond` instructions, which have their own condition code embedded in the opcode and are handled separately in `thumb16_cond_branch_svc` and `thumb32_b_w_cond`. Those call sites call `condition_passed` directly with the instruction-embedded condition code, so they bypass this path. Therefore this alternative is actually valid for the `decode_execute()` call site -- `B.cond` (Thumb-16) is dispatched via `thumb16_cond_branch_svc` which does its own condition check, and `B.W cond` (Thumb-32) is dispatched via `thumb32_b_w_cond` which also does its own condition check. The IT-block condition check in `decode_execute()` is only for non-branch instructions.

However, this approach duplicates the "am I conditional?" logic between the call site and the function, and doesn't help the two branch call sites. Fix 1+2 is better because it optimizes all three call sites with no call-site changes.

## Recommended Approach

Apply Fix 1 + Fix 2 first. Measure. Fix 3 (lookup table) only if the match is still measurable after inlining + early-out.

Rationale: Fix 1 is a one-line change that should be applied regardless. Fix 2 is two lines and eliminates ~95% of the work. Fix 3 adds complexity (a precomputed table that must be verified correct) and is only worthwhile if the remaining ~5% of calls through the match are still hot after Fix 1+2.

## Expected Impact

| Scenario | Estimated self-time recovery |
|---|---|
| Fix 1 alone (inline) | ~5-10% (eliminates call overhead) |
| Fix 1 + Fix 2 (inline + early-out) | ~15-20% (eliminates call overhead + match for 95% of calls) |
| Fix 1 + Fix 2 + Fix 3 (+ lookup table) | ~20-21% (eliminates remaining match branches) |

## Risks

- **None for Fix 1.** Pure annotation, no behavioral change.
- **None for Fix 2.** `cond >= 0xE` is equivalent to the existing `0xE => true, _ => true` arms. ARM architecture defines 0xF as unconditional (same as AL) for the condition_passed function.
- **Low for Fix 3.** The lookup table must be precomputed correctly. Verify with the existing differential fuzz harness against QEMU.
