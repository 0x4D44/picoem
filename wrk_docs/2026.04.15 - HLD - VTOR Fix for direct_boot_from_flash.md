# HLD — VTOR fix for direct_boot_from_flash

Date: 2026-04-15
Author: Agent (fix-A, Opus 4.6)

## 1. Exact code change

In `crates/mdrp2040/src/lib.rs` extend `direct_boot_from_flash` (lines 184–195) to also write VTOR on both per-core PPBs. PPB storage is plain `pub vtor: u32` (`bus/ppb.rs:39`); the write handler at `ppb.rs:160` is `self.vtor = val` with **no side-effects** — direct field assignment is equivalent.

```rust
let vtor_addr = bus::XIP_FLASH_BASE + vtor_offset; // 0x1000_0000 + offset
// ... existing SP/PC writes ...
self.bus.ppb[0].vtor = vtor_addr;
self.bus.ppb[1].vtor = vtor_addr;
self.cores[1].halt();
```

`XIP_FLASH_BASE` is already pub (`bus/mod.rs:66`).

## 2. Doc comment update

Append to the existing block (after "here is SP, here is PC"): replace that phrase with **"here is SP, here is PC, here is VTOR"** and add: *"On real silicon, `exit_from_boot2` writes all three before branching to the firmware's `_reset_handler`. Skipping the VTOR write causes pico-sdk's `runtime_init_install_ram_vector_table` to memcpy from bootrom base 0x00000000, producing a garbage RAM vtable and a downstream `hard_assert` in `irq_add_shared_handler`."*

## 3. API boundary decision

**Recommend (a): fold VTOR into `direct_boot_from_flash`.** Single atomic handoff matches `exit_from_boot2` semantics; no new API surface; impossible for callers to forget. Rule out (b) — separate `set_vtor` invites the same forget-bug we just hit. Rule out (c) — `reset()` zeroing VTOR is correct per ARMv6-M; teaching it to lie would break the genuine-bootrom path (`i2s_chime`).

- `cargo test -p mdrp2040 --test smoke` — all 6 must pass.
- `cargo test -p mdpicoem-harness chime_firmware_produces_nonzero_audio` — must still pass (same code path, non-SDK image, harmless VTOR write).
- **Skip** the optional SCB.VTOR round-trip firmware test — `exceptions.rs:110` already round-trips the field; orthogonal cost > confidence gain.


Acceptance: (a) firmware progresses past cycle 1.35 M (ideally to I2S audio in WAV), or (b) hits a different panic site — still a win, confirms VTOR was the blocker.

## 6. Risk analysis

- **Reset ordering** (`picogus_diff_rp2040.rs:827` → 844): `reset()` runs first, then `direct_boot_from_flash` — our VTOR write is the last word and is **not** defeated.
- **Bus aliasing**: `bus/mod.rs:676/858` only forwards high nibble `0xE` to PPB; the `0x0` window goes to bootrom (separate decoder). No `0x00000ED08` collision.
- **Direct field write vs `bus.write32`**: bypasses `active_core` indirection; equivalent for VTOR (no side-effects), and clearer.

## 7. Non-goals

Not fixing: bootrom QSPI detection; general VTOR refactoring; NVIC wiring; mdrp2350 (unaffected — different boot path).

## 8. Open questions

- Should we also seed `bus.ppb[*].vtor` inside `EmulatorBuilder::flash(...)` for symmetry? Probably no — keeps boot policy in one place.
- Worth promoting `vtor_addr` computation into a `pub const VTOR_FROM_OFFSET(offset)` helper, or inline-only? Recommend inline — single call site.
