# mdrp2354 — Phase 7 HLD: Coprocessors and FPU

Version: 0.2.0 — DRAFT (addresses V1 review)
Date: 2026-04-14

## 1. Purpose and downstream drivers

Phase 7 completes the Cortex-M33 coprocessor surface. Phase 3 shipped the
**minimum** stubs required for the RP2350 bootrom to run (accept RCP salt,
DCP scratch registers, GPIOC NOP). Phase 7 makes **code that actually
exercises these features** work.

### Concrete downstream drivers

Per the project HLD §1 (`2026.04.12 - RP2350 Emulator HLD.md:14-23`) the
deployment chain is OneROM → mddosem. We target Phase 7 at:

1. **OneROM itself**: needs working CP7 RCP canary checks (bootrom runs
   them); the current silent-accept stub hides real firmware bugs.
2. **A minimal float test firmware** we will add under
   `crates/mdrp2354-app/` (same pattern as the existing blinky/LCD firmware)
   that exercises the FPU subset OneROM's C runtime can emit from `-lm`.
3. **Pico SDK `pico_double` library**: because anything linked against
   `-ldouble` from the SDK lowers to CP4/5 DCP calls — this is the
   narrowest DCP consumer we can actually point to and must implement.
4. **Pico SDK `hardware_gpio` coproc macros** (`sio_hw->gpio_*` via CP0):
   OneROM itself is coproc-light but any firmware we compile with the
   SDK's default gpio helpers emits CP0 instructions.

What we are **NOT** building Phase 7 for: hypothetical third-party Pico
SDK applications we don't own. If something we're not testing ends up
needing it, we extend Phase 7 in a follow-up. No speculative
completeness.

| C | GPIOC (CP0) — ops actually emitted by Pico SDK, wired to SIO | `core/coprocessor.rs`, `sio/mod.rs` |
| D | DCP (CP4/5) — the instruction subset `pico_double` emits | `core/coprocessor.rs` |
| E | RCP (CP7) — assertion set actually called by pico-bootrom-rp2350 | `core/coprocessor.rs` |
| F | Testing: SoftFloat oracle, extended qemu_diff classes, probe-rs FPU diff | `mdrp2354-test-harness/` |

### Explicit non-goals

- **No QEMU-as-oracle dependence for FPU correctness.** QEMU FPv5 has
  documented divergences in NaN-payload propagation and denormal handling
  (see QEMU bug tracker refs cited in the Stage F section). We use QEMU
  *with a published skip list* as a smoke test; **SoftFloat** (Berkeley
  TestFloat via `softfloat-sys`) is the bit-exact primary oracle for
  FPU arithmetic and exception flags. Probe-rs is the confirmation
  oracle where silicon is available.
- **No random-delay simulation for RCP.** Deterministic emulation is
  strictly more useful to downstream consumers.
- **No double-precision FPU.** RP2350 M33 is FPv5-SP (single-precision
  only; the historical "-D16" suffix refers to *single-precision register
  count when viewed as double pairs* and does not imply double support).
  Double-precision math goes through DCP.
- **No TrustZone-correct EXC_RETURN S bit.** We carry forward Phase 3's
  convention of S=1 in EXC_RETURN (see
  `core/exceptions.rs:76` `FIXME(trustzone)`). Phase 7 only changes the
  FType bit [4]; the S bit stays 1 as a stub. Moving to NS-correct S=0
  is a TrustZone work item, not Phase 7.
- **No NS (Non-secure) lazy FP context save.** Follows from the
  TrustZone stub.
- **No VCVTA/N/P/M, no VRINTA/N/P/M.** These are specific-rounding-mode
  variants used by DSP code; none of our drivers need them. Defer to
  Phase 7.1 on first actual demand.
- **No feature flags, no migration shims, no backwards-compat for old
  stubs.** Replace in place.
- **Silicon errata not replicated.** If RP2350 has documented DCP/FPU
  off-by-ULP errata, the emulator follows the *specified* IEEE-754
  behavior. Divergence from silicon for these cases is explicitly
  accepted and listed in the README.
- **No RP2354B (48-pin) CP0 semantics.** We target 30-pin RP2354A only,
  matching the current SIO `gpio_out: u32` width at `sio/mod.rs:71-75`.

### Things we will NOT design for

- Configurable FPU behavior via env vars or Cargo features — FPSCR
  already gates FTZ/DN/rounding mode.
- A generalized "coprocessor framework." Four coprocessors, four dispatch
  helpers in `coprocessor.rs`, following the existing family-helper
  pattern (`cp7_mcr_mrc_family` / `cp7_mcrr_mrrc_family`).
- A new `core/dcp.rs` module. DCP state lives on `CortexM33` as plain
  fields; DCP dispatch lives in `coprocessor.rs` alongside its siblings.
- Defensive "log on unknown encoding" code. Match what the current stubs
  do (silent NOP on unrecognized encodings) — consistent, no per-step
  overhead, and the test matrix provides the signal.

## 4. Stage 0 — probe-rs harness bringup (prerequisite)

### Rationale

V1 proposed `fpu_probe_diff.rs` as a Stage A deliverable. The review
correctly identified this as circular: Stage A's oracle can't be
co-delivered with Stage A's code. probe-rs infrastructure is its own
scope and precedes any silicon-backed oracle.

### Deliverables

- `crates/mdrp2354-test-harness/src/probe_session.rs` — shared helper
  that opens a probe-rs Session, flashes a small target resident, sets
  up DWT cycle counting, and exposes `run_one(pre_state, instr_bytes) ->
  post_state` used by all future probe-rs binaries.
- `crates/mdrp2354-test-harness/src/bin/probe_smoke.rs` — smoke test:
  flash, run `NOP`, read registers back, confirm round-trip works.
- On-target resident firmware (flashed once, parameterized via SRAM
  mailbox). Same pattern as PIO probe harness from Phase 6.

### Exit criteria

- `cargo run -p mdrp2354-test-harness --bin probe_smoke` succeeds with
  probe + RP2354A connected, reporting correct DWT cycle counts for a
  known instruction sequence.
- **No emulator changes.** This stage is purely harness infrastructure.

### What Stage 0 unblocks

- Stage A silicon confirmation oracle (not primary oracle — SoftFloat
  is).
- Future FPU cycle-count validation.
- Future DCP status-register spot-check against silicon (§7.D).

### What Stage 0 is **not** a blocker for

- Stage A code landing. Stage A ships against SoftFloat as primary
  oracle. Silicon promotes Stage A from "green" to "cross-validated."
- Stages B, C, D, E. These have independent oracles.

## 5. Stage A — FPU correctness completion

### A.1 FPSCR exception flags

FPSCR bit layout, verified against Armv8-M ARM DDI0553 §D1.2.88:

| Bit | Name | Meaning | Status |
|-----|------|---------|--------|
| 31-28 | NZCV | Condition flags from VCMP | done |
| 27 | AHP | Alternative half-precision | add (lands with VCVTB/T) |
| 26 | DN | Default NaN | add |
| 25 | FZ | Flush-to-zero | add |
| 24-23 | RMODE | Rounding mode | done |
| 22 | Reserved (FZ16 in v8.1-M — RAZ/WI on M33) | | skip |
| 15-8 | Trap enables (IDE/IXE/UFE/OFE/DZE/IOE) | **RAZ/WI on M33** — no trapped FP exceptions | skip |
| 7 | IDC | Input denormal cumulative | **add** |
| 6-5 | Reserved | | skip |
| 4 | IXC | Inexact cumulative | **add** |
| 3 | UFC | Underflow cumulative | **add** |
| 2 | OFC | Overflow cumulative | **add** |
| 1 | DZC | Divide-by-zero cumulative | **add** |
| 0 | IOC | Invalid operation cumulative | **add** |

Cumulative sticky flags: set on trigger, cleared only by VMSR-to-FPSCR.
M33 has no trapped handling (all exceptions untrapped).

**FTZ interaction** (per DDI0553 §A2.7.3):

- If FZ=1 and an input is denormal: treat as ±0 (sign preserved), set
  **IDC**.
- If FZ=1 and the result is tininess-before-rounding: result = ±0, set
  **UFC** and **IXC** together.

**Default NaN** (DN=1): any NaN result → quiet NaN `0x7FC00000`.

**Implementation signature** — update in place, no wrapper struct:

```rust
// in core/execute_fpu.rs — matches existing fpscr_set_nzcv signature style
fn fp_add(fpscr: &mut u32, a: f32, b: f32) -> f32 { ... }
fn fp_mul(fpscr: &mut u32, a: f32, b: f32) -> f32 { ... }
// etc.
```

Helper functions share a small private module (inside `execute_fpu.rs`)
with utilities for: FTZ input, FTZ output, DN output, flag accumulation.

**IXC detection — correct approach per op**:

- ADD/SUB/MUL: `(result_as_f32) == (exact_f64 rounded to f32)` — safe
  because exact add/sub/mul of f32s is representable in f64.
- DIV: compute in f64, mul-add residual test using f64: `residual =
  (a as f64).mul_add(-(q as f64), (b as f64))` where `q = a / b`.
  `residual != 0.0` → IXC.
- SQRT: residual test `r*r − x` in f64.
- FMA (VFMA/VFNMA/etc.): use `f32::mul_add` (see A.3 caveat for MSVC).

### A.2 Armv8-M single-precision instructions to add

Based on current 23-type coverage and what our downstream code actually
calls:

**In scope for Phase 7:**
- **VSEL** — conditional select. Used by ARM GCC emitting branch-free
  conditional FP moves.
- **VMAXNM / VMINNM** — IEEE-754-2008 maxNum/minNum. Called from `fmaxf`
  / `fminf` in `-lm`.
- **VCVTB / VCVTT** (F16↔F32) — half-precision conversion. Current file
  has "F16 stub"; replace with real conversion. AHP flag lands here.

**Deferred to Phase 7.1 (no current driver):**
- VCVTA / VCVTN / VCVTP / VCVTM (specific-rounding convert-to-int)
- VRINTA / VRINTN / VRINTP / VRINTM (specific-rounding round-to-integral)

### A.3 Host-`f32` oracle caveats

The V1 claim "IEEE-754 single-precision is deterministic across x86/ARM"
is **only true with caveats**:

- `f32::mul_add` on Windows MSVC x86 without `+fma` target feature falls
  back to rounded-mul + rounded-add, which **is not bit-identical** to
  the fused result. **Mitigation:** the test harness requires a build
  configuration with `+fma` (add to `.cargo/config.toml` as target CPU
  feature); refuse to run if not set.
- **NaN payload propagation** for VMUL/VADD: x86 SSE vs ARM VFP differ
  on which input's payload survives when both are NaN. **Mitigation:**
  state in module comment that FPU NaN-payload bits are emulator-defined
  (match host semantics). Tests that care assert only the quiet-bit and
  DN-override, not payload.
- Subnormal *arithmetic* (not just FTZ): host CPUs may flush based on
  MXCSR/FPCR state. **Mitigation:** pin host MXCSR/FPCR to strict
  IEEE-754 at emulator startup; fail-loud if pin fails.

### A.4 Retro-validation of the existing 23 instructions

V1 added flags/instructions on top of the existing 23 but assumed the
23 are correct. Stage A.1 must retro-validate those first.

**Approach:** the SoftFloat oracle (§9) is available offline and
deterministic. Before extending, run the existing 23 instructions
against SoftFloat for every corner case in the generator (§9.2). Any
discrepancy becomes a known-divergence entry or a fix.

## 6. Stage B — Lazy FP context save

### B.1 Background (condensed)

Thread with `CONTROL.FPCA=1` enters exception → architecture stacks
additional 18 words of FP context. Lazy (`FPCCR.LSPEN=1`): reserve
space, defer write until first FP op in handler.

### B.2 New PPB state and invariants

Add to `crates/mdrp2354/src/bus/ppb.rs` (per-core, alongside `cpacr`):

```rust
/// FP Context Control Register. Cortex-M33, Armv8-M non-secure.
/// Bit layout per DDI0553 §D1.2.32:
///   bit 31: ASPEN   — RW, reset 1 (auto-preserve FP context)
///   bit 30: LSPEN   — RW, reset 1 (lazy state preservation)
///   bit 29: CLRONRET — RW, reset 0
///   bit 28: CLRONRETS — RW, reset 0 (TrustZone stub)
///   bit 27: LSPENS  — RW, reset 0 (TrustZone stub)
///   bit 26: TS      — RW, reset 0 (TrustZone stub)
///   bits 10-8: MMRDY/BFRDY/HFRDY — RW, status bits written during lazy flush fault
///   bit  7: SPLIMVIOL — RW, stack-limit violation during reserve
///   bit  6: UFRDY   — RW, usage-fault-ready
///   bit  3: S       — RW, reset 0 (TrustZone stub — report NS)
///   bit  2: MONRDY  — RW
///   bit  1: Reserved
///   bit  0: LSPACT  — RW, lazy state active
pub fpccr: u32,   // reset 0xC000_0000 (ASPEN|LSPEN)

/// FP Context Address Register. Holds frame address during lazy preservation.
/// Writes mask out bits [2:0] (forced 8-byte alignment per architecture).
pub fpcar: u32,   // reset 0

/// FP Default Status Control. FPSCR template at exception entry.
/// Only bits [26, 25, 24-23] (AHP/DN/FZ/RMODE) are architecturally defined.
pub fpdscr: u32,  // reset 0
```

Memory-mapped, confirmed:
- FPCCR at `0xE000_EF34`
- FPCAR at `0xE000_EF38`
- FPDSCR at `0xE000_EF3C`

**Documented invariants** (copy into source comments):

1. `CONTROL.FPCA == 1 ⇒ S0-S31 and FPSCR are live thread-mode state`.
2. `FPCCR.LSPACT == 1 ⇒ FPCAR points at a valid reserved FP frame
   slot; S0-S15 and FPSCR are the pre-exception thread values and
   have not yet been written to the frame`.
3. `EXC_RETURN bit [4] == 0 ⇒ the exception entry reserved 18 words
   above the basic frame`.
4. FPCCR.LSPACT is owned by exception-entry (sets) and by the lazy
   flush trigger in `fpu_execute` (clears) and by exception-return
   (clears on no-real-save path). No other writers.

### B.3 CONTROL.FPCA — single owner

To avoid the V1 collision risk, **centralize FPCA transitions**:

- **Write site #1:** `fpu_execute` — sets `FPCA=1` after CPACR check
  passes and after any lazy flush, before register writeback.
- **Write site #2:** `enter_exception` — reads FPCA into EXC_RETURN
  bit [4], then clears `FPCA=0`.
- **Write site #3:** `exit_exception` — restores FPCA from EXC_RETURN
  bit [4] (`FPCA = !EXC_RETURN[4]`).

**No other code writes FPCA.** The MSR-to-CONTROL path at
`execute_thumb32.rs:~943` masks out bit 2 when writing CONTROL (MSR
is not permitted to change FPCA per DDI0553 §B3.4.1).

### B.4 Exception entry

Existing `enter_exception` at `exceptions.rs:41` gets these changes:

1. **FType computation**: `let had_fp = (self.regs.control & 0x4) != 0;`
2. **EXC_RETURN base value selection** (carrying forward Phase 3 S=1 stub):
   - `0xFFFF_FFE1` = handler, MSP, FType=0 (FP frame present)
   - `0xFFFF_FFE9` = thread, MSP, FType=0
   - `0xFFFF_FFED` = thread, PSP, FType=0
   - `0xFFFF_FFF1 / F9 / FD` = same with FType=1 (no FP frame).
     Bit [4] flipped; all other fields (bits 7:5 = 111) unchanged from
     the current Phase 3 convention.
3. **Allocation**:
   - Basic frame: 32 bytes (unchanged).
   - If `had_fp`: additional 72 bytes (18 words = S0-S15 + FPSCR +
     1 reserved). Total 104 bytes + up to 4 bytes alignment padding.
4. **Stack-limit check**: before the allocation write, compare
   `frame_sp` against `regs.msplim` / `regs.psplim` as appropriate.
   If violated, set `FPCCR.SPLIMVIOL`, raise UsageFault; do not write
   the FP region.
5. **FP frame write**:
   - If `FPCCR.LSPEN=1` (default): set `FPCCR.LSPACT=1`, set `FPCAR
     = <FP region base>`, do **not** write S0-S15.
   - Else (LSPEN=0, eager): write S0-S15 + FPSCR (18 words). Cycle
     cost: M33 TRM gives ~17 cycles typical for eager FP stacking
     (not "+12" as V1 claimed) — bus-latency dependent.
   - Reset FPSCR from FPDSCR bits [26, 25, 24-23].
6. **Clear** `CONTROL.FPCA = 0`.

Cycle cost: +0 for lazy (bookkeeping only, ~2 cycles), +17 typical for
eager.

### B.5 Lazy flush trigger (`core/execute_fpu.rs`)

At the top of `fpu_execute`, **after** the CPACR access check:

```rust
fn fpu_execute(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
    // 1. CPACR access check — existing code (coprocessor.rs:10-15) already
    //    happens at thumb32_coprocessor() dispatch. If we arrive here, access
    //    is permitted.
    // 2. Lazy flush trigger if applicable.
    let core = bus.active_core();
    let ppb = &mut bus.ppb[core];
    if ppb.fpccr & 1 != 0 {  // LSPACT
        // Flush S0-S15 + FPSCR to FPCAR region.
        // Check MPU/bus faults on each write; set FPCCR.MMRDY/BFRDY on fault.
        self.flush_lazy_fp_context(ppb.fpcar);
        ppb.fpccr &= !1;  // clear LSPACT
    }
    self.regs.control |= 0x4;  // FPCA = 1
    // ... existing dispatch ...
}
```

Ordering rule: **CPACR check first** (at outer `thumb32_coprocessor`
dispatch, already present at `coprocessor.rs:10-15`). If CPACR denies,
raise NOCP UsageFault and do not flush. This matches DDI0553 §B.3.7.

Cost of the check when LSPACT=0 (>99% of calls): single `u32` read from
the same PPB struct already loaded for CPACR — no new cache miss.

Flush cost ~14-19 cycles depending on bus state (17 word-writes ~1 cycle
each + housekeeping).

### B.6 Exception return

If `EXC_RETURN` bit [4] is 0 (had FP frame):

- If `FPCCR.LSPACT == 1`: thread never touched FP during handler →
  just clear LSPACT, deallocate 18 words. S0-S15 retain pre-exception
  values (never written).
- Else: pop S0-S15 + FPSCR from the FP region.

Restore `CONTROL.FPCA = 1`.

**EXC_RETURN mismatch**: if EXC_RETURN[4]=0 but FPCCR.LSPACT=1 and
stack contents don't match expected frame, this is the "inconsistent
state" case — raise UsageFault (DDI0553 §B3.19). Add a test.

### B.7 FPU × sleep/WFI/WFE

Sleep states (WFI, WFE): sleeping core retains its FP state. LSPACT is
not cleared by sleep. Wake from sleep is transparent to FP state.
**Make this explicit in a comment on the sleep-handling site; no code
change.**

### B.8 FPU × Core 1

Per-core by construction: each `CortexM33` has its own `Registers`
(S0-S31, FPSCR, CONTROL), and PPB state is already per-core (`ppb[core]`
indexing). Phase 5 Core 1 wake path does not touch FP state. **Add one
integration test** that brings Core 1 up with FPCA=1 → interrupts →
returns, to confirm no cross-core contamination.

### B.9 Test strategy

Integration tests in `crates/mdrp2354/tests/lazy_fp.rs`:

1. **No-FP handler**: thread `VADD`, ISR doesn't use FP, returns. Assert:
   LSPACT=1 during handler, S0-S15 unchanged (observe via backdoor
   peek), post-return S0-S15 correct, **zero** bus writes to the FP
   region during the whole path.
2. **FP handler**: handler executes VADD. Assert LSPACT cleared,
   FP frame contents valid, thread's S0-S15 correct after return.
3. **Nested**: ISR takes a second interrupt. Each entry captures+clears
   FPCA independently; each return restores from its own EXC_RETURN[4].
4. **Eager mode**: `FPCCR.LSPEN=0`, verify FP frame written on entry
   (not deferred).
5. **Stack-limit during reserve**: set PSPLIM just below where the FP
   frame would land; verify UsageFault raised, FPCCR.SPLIMVIOL=1, no
   frame written.
6. **MPU fault during lazy flush**: configure MPU to deny FPCAR region,
   trigger flush, verify MemManage raised and FPCCR.MMRDY=1.
7. **EXC_RETURN[4]=0 mismatch**: construct a handler that returns with
   EXC_RETURN[4]=0 but no valid FP frame. Verify UsageFault.
8. **Phase 3/4/5 exception regression sweep**: replay every existing
   exception test with FPCA both 0 and 1. This is the main regression
   protection for Stage B changes.

## 7. Stage C — GPIO coprocessor (CP0)

### C.1 Scope (narrowed per review)

Target: every CP0 encoding emitted by Pico SDK `hardware_gpio.h`. We
enumerate by generating the list from the header in a one-off script,
not by hand. RP2354A (30-pin) only — pins 30-47 always read 0, writes
are masked.

Concretely enumerated from the SDK header (~20 distinct encoded
operations once OE and put-masked variants are counted, not the 12 in
V1). Full table goes into Stage C's implementing PR, not this doc.

### C.2 Dispatch structure (matching CP7 style)

Follow the existing family-helper pattern:

```rust

    if is_mrc_mcr {

fn cp0_mcr_mrc_family(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
```

No new module, no "one big match". Mirrors `cp7_mcr_mrc_family` at
`coprocessor.rs:67`.

- **Integration test with discrimination** (per review): firmware
  blinks via CP0; bus harness counts SIO MMIO accesses; assert MMIO
  access count == 0 for the CP0 path (proves CP0 is actually being
  used, not silently falling through).
- Mixed ordering test: alternate CP0 and MMIO writes to the same pin,
  verify last-writer-wins.
- CPACR-disabled path: UsageFault.

## 8. Stage D — DCP (CP4/5)

### D.1 Scope (narrowed)

Target: the DCP instruction subset emitted by Pico SDK
`rp2_common/pico_double/double_aeabi_dcp.S`. Enumerate them from the
SDK assembly file, not from the full RP2350 datasheet DCP chapter.

Concrete count (from walking the SDK file): arithmetic (`dadd`, `dsub`,
`dmul`, `ddiv`, `dsqrt`), compare (`dcmp_*`), convert (`i2d`, `u2d`,
`d2i`, `d2u`, `d2f`, `f2d`), transfer (`rfma/rfmb/wxma/wxmb` family). No
pipeline-internal ops (`wxup/rxup`), no accumulator ops — SDK doesn't
emit them. Final list committed in Stage D's PR.

### D.2 State — inline, not a new module

Replace `self.dcp_data: [u32; 2]` on `CortexM33` with two fields:

```rust
// on CortexM33
pub(crate) dcp_halves: [u32; 16],
pub(crate) dcp_status: u32,
```

No `core/dcp.rs`. No `struct Dcp`. DCP dispatch lives in `coprocessor.rs`
with a helper `dcp_cdp_family` paralleling `cp7_mcrr_mrrc_family`.

### D.3 Instructions

Implement as CDP + MCR/MRC dispatch inside `cp4_5_dcp`. Host `f64`
computes values. **Status register bits are a separate oracle target**:
per-op, we explicitly set sign/NaN/inf/zero bits after each computation.
Spec table goes into the implementing PR.

### D.4 Cycle counts

Inline in the dispatch match — one traversal, no separate table:

```rust
match op {
    DcpOp::Dadd => { /* compute */ ; /* set status */ ; 4 }
    DcpOp::Ddiv => { /* compute */ ; /* set status */ ; 18 }
    // ...
}
```

### D.5 Oracle (rebuilt)

V1's "host f64 matches by construction" was a tautology. Revised:

- **Primary oracle for arithmetic**: Berkeley TestFloat via
  `softfloat-sys`, round-to-nearest-even. Host f64 is the *target* of
  the emulator's computation; TestFloat is the *independent reference*.
- **Primary oracle for status register bits**: a hand-written spec
  table (one row per DCP op, documenting which status bits are set on
  which inputs). Test asserts against this table. This is the oracle —
  the only one, because no external reference exists for the DCP
  status register.
- **Spot-check oracle (Stage 0 once available)**: probe-rs runs a
  sampling of DCP ops on real silicon, confirms bit-identical result
  and status for the sampled set.

## 9. Stage E — RCP (CP7)

### E.1 Current state (keep)

`coprocessor.rs:56-118` already handles:
- `rcp_canary_status pc` (MRC Rt=15): N flag = salt valid
- `rcp_canary_get` (MRC Rt≠15): returns `salt ^ 0xDEADBEEF`
- `rcp_canary_check` (MCR): silent accept (**changes to check+NMI**)
- `rcp_salt_core0/1` (MCRR2): sets salt

### E.2 Additions and the NMI decision

The V1 MAJOR finding required picking NMI vs HardFault. Checked against
pico-bootrom-rp2350's `rcp.h` and the RP2350 datasheet §12.4:
**RCP assertion failures raise NMI (exception #2)** on the Cortex-M33.
The bootrom installs an NMI handler that locks up.

**Phase 7 behavior on mismatch**: set `pending_fault = NMI`, log `"RCP
assertion failed: <op> <args>"`. NMI fires regardless of PRIMASK;
HardFault does not — this matters for bootrom-style masked sections.

Full table (encodings enumerated from the SDK `rcp.h` in the
implementing PR):

| Instruction | Semantics | Mismatch action |
|-------------|-----------|-----------------|
| `rcp_canary_check` | Compare Rt against salt ^ 0xDEADBEEF | **NMI** |
| `rcp_iequal` | Compare two Rt values | NMI |
| `rcp_bvalid` | Validate Rt ∈ {0, 1} | NMI |
| `rcp_btrue` / `rcp_bfalse` | Assert Rt == 1 / Rt == 0 | NMI |
| `rcp_ifgte` / `rcp_iflte` | Unsigned comparison | NMI |
| `rcp_count_init` | Start a counter (Bus-side state) | side effect |
| `rcp_count_check` | Assert counter value | NMI |
| `rcp_panic` | Unconditional fault | NMI |
| `rcp_switch` | Redundancy compare + branch | NMI on mismatch |

### E.3 Impact on Phase 3/4 tests

Flipping `rcp_canary_check` from silent-accept to NMI-on-mismatch is
**behavior-changing** for Phase 3/4 boot paths. Before merging Stage E:

- Audit every existing test that reaches CP7 (grep for `rcp_` or
  `cp7_` in tests).
- Any test that currently relies on silent-accept against zero/stale
  salt must be updated to seed the salt first, or have the expected
  NMI added to its assertion.
- Bootrom tests: the real bootrom sets salt before running checks, so
  this should be a no-op if the bootrom boots correctly. Confirm
  empirically by running the Phase 3 boot test after E lands.

### E.4 What we skip (documented divergence)

- **Random delays** (0-127 cycle jitter): not replicated. Document in
  module comment.
- **Parity checks on instruction encoding**: real RCP validates parity
  on coproc encoding bits. We accept recognized encodings as valid.
  Unrecognized encodings → silent NOP, matching existing stub behavior
  (consistent with CP4/5 handling).

### E.5 Test strategy

Unit tests: for each assertion instruction, one pass-case and one
fail-case. Plus an encoding-level fuzz (random bit patterns into
`cp7_rcp`) asserting either correct dispatch or documented behavior
(silent NOP for unrecognized) — **never panic, never memory unsafety**.

### Performance budget check (HLD §9.1: 33 host cycles per emulated cycle)

Phase 7 adds to the hot path:

1. **Every FPU instruction**: `LSPACT` check (1 u32 read from the same
   PPB struct already loaded for CPACR — piggybacks on existing cache
   line, <1 host cycle), `FPCA |= 4` (1 cycle).
2. **Every exception entry**: +1 branch (had_fp), +1 bus read
   (FPCCR.LSPEN). Already load-bearing code; negligible.
3. **Every arithmetic FPU op with flag tracking**: flag computation
   costs ~3-5 host cycles (comparison + OR). This is the one
   non-trivial addition. Acceptable because FPU ops are 1-14 emulated
   cycles meaning 33-462 host cycles budget — 3-5 is lost in the noise.

**Benchmark gate**: after Stage A lands, run
`paced_bench --unpaced --workload fpu-heavy` and confirm we stay under
33 host cycles per emulated cycle. If we exceed, optimize or
renegotiate.

## 13. Risks

### 13.1 SoftFloat adoption
Soft-float crate introduces a native dependency (C sources for Berkeley
TestFloat). Mitigation: `softfloat-sys` is well-maintained,
cross-platform, and widely used. Acceptable.

### 13.2 probe-rs hardware availability (Stage 0)
If the probe stops working, Stages 0 and probe-rs confirmation in A/D
block. Mitigation: SoftFloat is the primary oracle; probe-rs is only
confirmation. Stages A/B/C/D/E can ship without probe-rs.

### 13.3 Lazy FP correctness edge cases
Nested exceptions, stack-limit faults during reserve, MPU faults during
lazy flush — all in §B.9 test matrix. If a Pico SDK application uncovers
a case we didn't test, we extend the matrix, not the architecture.

### 13.4 DCP instruction enumeration completeness
We target SDK-emitted ops. If application code hand-writes DCP asm
outside the SDK's helpers, we will silent-NOP unrecognized encodings
(matching the existing CP4/5 stub behavior). Acceptable divergence.

### 13.5 NaN payload divergence
Host FPU (x86 SSE vs ARM VFP) differs on NaN-payload propagation.
Mitigation: documented non-goal; tests assert quiet-bit + DN override
only, not payload bits.

### 13.6 MSVC `f32::mul_add` non-fused fallback
See §A.3. Mitigation: target feature requirement + startup check.

### 13.7 RCP behavior change breaking Phase 3/4 boot tests
See §E.3. Mitigation: audit tests, run bootrom boot test after Stage E
lands.

### 13.8 Benchmark regression
Phase 7 changes touch the hot path. See §12 benchmark gate.

## 14. Sequencing (DAG, not a list)

Per V1 review: "independently shippable" is partly fiction. The real
dependency graph:

```
 ┌────────────┐
 │  Stage 0   │ (probe-rs bringup — optional gate, see below)
 └─────┬──────┘
       │
       ↓
 ┌──────────────────────────────────────────────────────┐
 │  SoftFloat oracle lands (softfloat_diff harness)     │ ← blocks Stage A
 └──────────────┬───────────────────────────────────────┘
                │
                ↓
 ┌──────────────────┐      ┌──────────────────┐
 │  Stage A.2 (new  │      │  Stage C (CP0)   │
 │  FPU instrs)     │      │  ─────────────── │   ← independent of FPU
 └────────┬─────────┘      │  Stage E (RCP)   │
          │                └──────────────────┘
          ↓
 ┌──────────────────┐
 │  Stage A.1 (FPSCR │← retro-validates 23 existing +
 │   flags + retro)  │   validates A.2 additions
 └────────┬─────────┘
          │
          ↓
 ┌──────────────────┐      ┌──────────────────┐
 │  Stage B (lazy   │      │  Stage D (DCP)   │
 │  FP context)     │      │  ─────────────── │   ← uses SoftFloat oracle
 │  uses A complete │      │  independent of A/B
 └──────────────────┘      └──────────────────┘
```

- Stage 0 (probe-rs) is **not** a blocker for any other stage — all
  primary oracles are on-host. Stage 0 unlocks the confirmation oracle.
- SoftFloat landing (just the crate dep + wrapper + harness binary)
  blocks Stage A.
- Stages C and E are independent of FPU work — can land in any order
  relative to A.
- Stage B depends on Stage A being stable (otherwise bugs are ambiguous
  between "FPU semantics wrong" vs "lazy save wrong").
- Stage D depends on SoftFloat (for arithmetic oracle) but not on A or
  B — DCP is disjoint from FPU.

Each stage closes with its own commit; don't bundle. Each stage has
independent exit criteria and test gates.
