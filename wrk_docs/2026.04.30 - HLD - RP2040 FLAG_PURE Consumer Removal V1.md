# RP2040 `FLAG_PURE` Consumer Removal — V1

**Date:** 2026-04-30
**Author:** Claude
**Status:** draft for sign-off

## Summary

Delete the unused `is_pure` consumer-side scaffolding on
`mdrp2040`: the `DecodedOp::FLAG_PURE` bit, the `is_pure()` accessor,
the populate-time `classify_is_pure` invocation that writes the bit,
and one comment paragraph. Keep the four classifier functions
themselves, gated `#[cfg(test)]` so they remain available to the
existing `classifier_tests` decode-oracle module (and to the V2
mutation-testing triage work) but stop running in production.

## Why this is the design

The fast-path consumer was attempted and reverted with bench data:

> *"journal: iter 7 — is_pure fast-path within noise, REVERTED."*
> Commit `2621534`, 2026-04-26.
>
> `paced_bench_rp2040 basic --unpaced` 500M, 5 trials: **+0.06%**.
> `picogus_diff_rp2040 mode-5`, 9 trials: **+0.23% / -0.14 s
> paired-delta** — within noise, cycles bit-identical at
> 1,056,157,608.
>
> *"Reverted from src tree per CLAUDE.md 'smallest change that
> satisfies the request' — 197 lines for zero observable benefit is
> deadweight."*

The architectural reason: M0+ has no `extra_wait_states` accumulator
(`crates/mdrp2040/src/core/decode.rs:22-23`), so the M33 fast-path's
three-bus-call saving collapses to one store + one load. The
decode-cache port on its own already captured the decode-bound win
(+33% paced_bench / +3% OPL3, commit `42ee533`); whatever is left for
a purity-skip to claim is dwarfed by per-cycle slow-path overhead
(`tick_peripherals + tick_pio + update_gpio + drain_pending_irqs`).

What remains in tree today is the populate-side half of that
attempt: the classifier still runs every cache miss, the bit still
gets set in `DecodedOp.flags`, and nobody ever reads it. That is the
worst of both worlds — paying the classifier cost for no benefit. The
right cleanup is to pull the consumer-side scaffolding so the
classifier stops running in production while preserving its role as a
decode oracle for tests.

## Scope

### In scope (delete)

1. `crates/mdrp2040/src/bus/mod.rs:244` — `pub(crate) const FLAG_PURE`.
2. `crates/mdrp2040/src/bus/mod.rs:262-265` — `pub(crate) fn is_pure(&self)`.
3. `crates/mdrp2040/src/bus/mod.rs:235-237` — the three doc-comment
   lines on `DecodedOp.flags` describing `bit 1 — is_pure`.
4. `crates/mdrp2040/src/core/decode.rs:228` — the
   `let pure = classify_is_pure(hw0, hw1, wide);` call in
   `populate_decode_cache`.
5. `crates/mdrp2040/src/core/decode.rs:233-235` — the
   `if pure { flags |= DecodedOp::FLAG_PURE; }` block.

### In scope (gate)

6. `crates/mdrp2040/src/core/decode.rs:45-49` — rewrite the
   `classify_is_pure` doc-comment to reflect its new role (decode
   oracle for tests, no production consumer). Remove the "iter7
   fast-path" reference.
7. Add `#[cfg(test)]` to each of the four classifier functions:
   `classify_is_pure` (line 50), `classify_thumb16_pure` (line 58),
   `classify_thumb16_misc_pure` (line 88), `classify_thumb32_pure`
   (line 113).
8. `crates/mdrp2040/src/core/decode.rs:323-329` — the comment block
   in `classifier_tests` that explains "the `FLAG_PURE` field is
   populated at decode time but no production code on mdrp2040 reads
   `is_pure()` (commit `42ee533` deferred the consumer)" no longer
   matches reality post-change. Rewrite it to: "the classifier
   functions exist solely as decode oracles for these tests; the
   production decoder does not call them."

### Out of scope (do not touch)

- `crates/mdrp2350/` — M33 fast-path is benchmark-justified and
  stays as-is.
- The M0+ decode cache itself (commit `42ee533`) — the cache stays,
  only the unused purity-bit consumer is removed.
- M0+ test cases inside `classifier_tests` — every existing
  fingerprint and structural assertion stays; their visibility into
  the four classifier functions is preserved by the `#[cfg(test)]`
  gate.
- Mutation-testing V3 Stream A (commit `dabf3b3`,
  `wrk_journals/2026.04.30 - JRN - Mutation Testing V3 Execution.md`
  Stage 1) — 28 classifier test functions on M0+ landed as part of
  Stream A and are the active consumers of the four classifier
  functions. Stream A's coverage strategy (per-arm structural cases
  + FNV-1a fingerprints over the full input space) is named as the
  methodological template by the V3.1+V4 action plan
  (`wrk_docs/2026.05.01 - HLD - Mutation Testing V3.1 + V4 Action
  Plan V1.md` §inline pattern). Those tests stay; this design
  preserves their visibility into the classifier via the
  `#[cfg(test)]` gate.

## Why `#[cfg(test)]` on the classifier instead of full deletion

The four classifier functions are the test oracle for V3 Stream A.
Stream A landed 28 dedicated test functions on M0+ (commit `dabf3b3`,
~290 LOC at `crates/mdrp2040/src/core/decode.rs:312-660`) covering
per-arm structural cases plus full-input-space FNV-1a fingerprints —
the methodology the V3.1+V4 action plan now treats as the template
for further mutation-testing coverage. Deleting the classifier
functions would mean deleting Stream A, a measured-effective slice of
the V3 mutant-kill story (per the V3 execution journal's stage
table). That cost is unrelated to the consumer-removal question and
not worth paying here.

`#[cfg(test)]` correctly expresses the new reality: classifier exists
for tests only, vanishes from `--release` artefacts, leaves Stream A
intact. This is the smallest change that resolves the "populated but
unread" footgun without throwing away unrelated test infrastructure.

## Verification

1. `cargo build --release -p mdrp2040` — clean, warning-free. The
   `#[cfg(test)]` gate must compile away cleanly in release.
2. `cargo build -p mdrp2040` — clean, warning-free in debug too
   (tests compile in debug; the gated functions are visible to the
   test module).
3. `cargo test -p mdrp2040` — all classifier tests still pass. The
   FNV fingerprints and structural assertions are unchanged.
4. `cargo clippy -p mdrp2040 --all-targets -- -D warnings` —
   clean. In particular, no `dead_code` warnings on the classifier
   functions (the `#[cfg(test)]` gate removes them from the
   production build entirely).
5. `cargo test -p mdrp2040 --features threading` — dual_model parity
   unchanged (classifier wasn't on that path anyway).
6. Spot-check `cargo bench -p mdpicoem-harness --bin paced_bench_rp2040
   -- --workload basic --unpaced --cycles 100000000 --model serial`
   on one trial — should be within noise of pre-change. **Not a
   formal A/B**: the iter7 journal already shows the consumer is
   within noise; this run confirms the populate-side removal doesn't
   regress (which it shouldn't — fewer instructions per miss).

## Non-goals

- **No re-attempt of the iter7 consumer.** The bench data settles it
  for now. If a future workload exposes a different bottleneck that
  the bit could help with, that's a fresh design.
- **No symmetry restoration with M33.** The chips are architecturally
  parallel but their slow-path overheads differ; the bench evidence
  shows symmetry of *structure* doesn't imply symmetry of *win*. Tag
  this in the changed comments so the next reader doesn't refile the
  same item.
- **No CLAUDE.md amendment.** The `tech_debt.md` D5 entry can be
  closed out by the implementing commit message; no convention change
  needed.

## Commit shape

Single commit. Suggested subject:

```
mdrp2040: drop unused FLAG_PURE consumer; gate classifier as test-only
```

Body should reference both the iter7 revert (`2621534`) and the
sweep finding (D5 in
`wrk_docs/2026.04.29 - Codebase Tech-Debt Sweep Report.md`) so the
audit trail is one click each direction.

Diff size estimate: ~30 LOC removed (5 lines in `bus/mod.rs`, ~5
lines in `decode.rs` populate path), ~5 LOC added (`#[cfg(test)]`
attributes × 4, doc-comment updates). Net: ~25 LOC smaller.

## Risks

**One risk worth naming.** If a future agent re-runs the codebase
sweep and sees a `#[cfg(test)] fn classify_is_pure`, they may be
tempted to delete it as test-only dead code. Mitigation: the new
doc-comment on `classify_is_pure` should explicitly call out the V3
Stream A dependency by reference:

```rust
/// Decode-purity classifier — oracle for the `classifier_tests`
/// module below (V3 Stream A, commit `dabf3b3`; see
/// `wrk_journals/2026.04.30 - JRN - Mutation Testing V3
/// Execution.md` Stage 1). Not consumed by the production decoder;
/// kept for tests only after the iter7 fast-path attempt was
/// reverted (commit 2621534) — see
/// `wrk_docs/2026.04.30 - HLD - RP2040 FLAG_PURE Consumer Removal
/// V1.md` for context.
```

That's the only reader-rot risk; the rest of the change is mechanical.
