# 2026.04.17 — RP2350 Peripheral Coverage Audit

Scope: mdrp2350 crate, post-V5-Gap-Fill (`6919c19`). Triggered by the
question: *"have we actually implemented all the peripherals?"* The
short answer is **no** — and the longer answer is that "have we
implemented it" is the wrong question.

This document has two jobs:

1. §2–§4 — the MMIO coverage matrix the question literally asked for.
2. §5–§7 — the audit's blind spots, because the peripheral-enumeration
   frame misleads as much as it informs. Read this part before acting
   on §2–§4.

## §1 — Executive summary

- **37 bus-decoded addresses + 8 datasheet-enumerated-but-not-modelled
  peripherals** give a headline of 45 entries. Grades: **7 FULL** (SIO,
  WATCHDOG, BOOT_RAM, **DMA**, **PIO0/1/2**), **11 PARTIAL-BEHAVIOUR**,
  **6 PARTIAL-STORAGE**, **7 STUB**, **8 NOT MODELLED**. No rows
  remain OPEN QUESTION after direct code verification.
- **Correction (post-review)**: DMA and PIO0/1/2 were initially graded
  "effectively STUB" (surveyor) then OPEN QUESTION (synthesizer) based
  on a wrong surveyor annotation ("no FSM / no instruction execution").
  Direct code inspection: DMA is a full 1573-line behavioural model
  with 32 passing unit tests, wired via `Bus::tick_peripherals`. PIO
  lives in `mdpicoem-common` (3585 lines across `pio/{mod,sm,decode,
  fifo}.rs`) with a real `step_n(cycles, gpio_in)` driven from
  `Emulator::tick_peripherals` (lib.rs:377), gated by RESETS, with 24
  passing tests. Both regraded **FULL**. See §5.6 for post-mortem.
- **The grade that matters is "unverified on silicon".** Of the 11
  PARTIAL-BEHAVIOUR peripherals, most have zero cases in
  `silicon_periph_diff_rp2350`. Existence ≠ correctness. See §5.1.
- **Tier-1 firmware blockers** (will break typical pico-sdk programs):
  USB absent, XIP_CTRL absent, QMI stub, NVIC priority levels absent,
  HSTX absent. (DMA and PIO removed from this list after the §5.6
  correction — both are fully modelled.)
- **ARMv8-M core gaps** (separate from peripherals): no MPU, no SAU,
  no NVIC priority levels, FPCCR stub only, Secure/Non-Secure worlds
  collapsed. Plain single-world Cortex-M33 firmware works; TrustZone
  / MPU-using firmware does not. See §3.
- **This audit measured one axis: "does the code exist?"** It did not
  measure silicon-oracle coverage, inter-peripheral wiring, MMIO
  access-cycle accuracy, or 40+ NVIC fan-in lines. §5 lists what we
  didn't look at; §6 lists non-peripheral coverage dimensions
  (bootrom image, ISA buckets, VFPv5 completeness, DCP/RCP).
- **Recommended next move is not "implement more peripherals"** — it's
  to reframe the question around target firmware. See §7.

## §2 — Coverage matrix

Fidelity grades:

- **FULL** — behavioural model matching silicon for features implemented.
- **PARTIAL-BEHAVIOUR** — side effects beyond round-trip (FIFO flags,
  IRQ raising, clock-tree recompute).
- **PARTIAL-STORAGE** — register round-trip only, no semantic effect.
- **STUB** — hardcoded or zero reads, no storage or behaviour.
- **WARN-ONLY** — unmapped; HashMap fallthrough with warn-once.
- **NOT MODELLED** — no bus decode arm; access warns and returns 0.
- **OPEN QUESTION** — code volume suggests PARTIAL, but program-visible
  behaviour is absent and whether this is staged or missed is unclear.

## §3 — ARMv8-M core state

Separate from peripheral coverage, the CPU model itself has substantive
gaps against ARMv8-M Mainline:

- **MPU**: absent. Any region-based memory protection is silently
  ignored. RTOS protected-mode (Zephyr, FreeRTOS-MPU) won't work.
- **SAU**: absent. No Secure/Non-Secure address partitioning. SG /
  BLXNS / BXNS transitions cannot be faithfully modelled.
- **NVIC priority levels**: absent. Interrupts dispatch but don't order
  by priority. Nested preemption, BASEPRI, priority grouping degenerate
  to "first-pended wins".
- **FPCCR**: stub only. Lazy FP save (`LSPEN`/`LSPACT`) isn't fully
  driven by exception entry/exit beyond what lazy-save tests exercise.
- **Secure/Non-Secure world**: banked registers (MSP_S/MSP_NS, MSPLIM,
  CONTROL_NS, etc.) collapse to single copies.

**Firmware impact**: TrustZone-M partitioned firmware, MPU-using RTOSes,
and anything relying on priority-based preemption won't work correctly.
Plain single-world Cortex-M33 firmware with flat memory and
run-to-completion ISRs is fine.

## §4 — Firmware-visibility prioritisation

Caveat: this list assumes a pico-sdk-flavoured target. If the real
target includes RP2354 bring-up / bootrom work, several Tier-3 items
(OTP_CTRL, ACCESSCTRL, GLITCH_DETECTOR proper ARM path) move up. §5.2.

### Tier 1 — blocks non-trivial firmware

- **USB absent** — TinyUSB, pico-sdk USB stdio fail at init.
- **XIP_CTRL absent** — flash-XIP cache ops, stream DMA.
- **QMI stub** — flash erase/program via direct mode.
- **NVIC priority levels absent** — `irq_set_priority()` + nested IRQs.
- **HSTX absent** — PicoDVI-style video output.

### Tier 2 — blocks specific domains

- **ACCESSCTRL** + **SAU** — secure-boot, partitioned firmware.
- **MPU** — RTOS protected mode, stack-guard pages.
- **POWMAN COUNT/MATCH frozen** — RTC wall-clock, deep-sleep alarms.
- **IO_BANK0 storage-only** — peripherals don't route through muxing;
  SIO GPIO path works as separate fast path.
- **PADS_BANK0 storage-only** — no electrical effect.
- **IO_QSPI / PADS_QSPI absent** — flash pin muxing firmware.

### Tier 3 — cosmetic / eventually

- SYSINFO chip-id full fields, TBMAN, BUSCTRL, CORESIGHT_TRACE.
- GLITCH_DETECTOR ARM path (stuck at 0).
- SHA-256 DMA pipelining; TRNG entropy; OTP ECC.
- XOSC / ROSC / PLL startup latency.

## §5 — What this audit does NOT measure

The peripheral-existence frame hides most of what actually matters. Five
gaps in what we measured:

### 5.1 — Oracle coverage vs. implementation fidelity

A PARTIAL-BEHAVIOUR grade means "code exists with side effects". It does
**not** mean "verified against silicon". Of the 11 PARTIAL-BEHAVIOUR
peripherals, the `silicon_periph_diff_rp2350` catalogue covers only PIO,
PLL LOCK, and clock-tree reprogram. That leaves UART0/1, SPI0/1, I2C0/1,
ADC, PWM, TIMER0/1, TICKS, OTP_DATA, RESETS, PSM — **10 of 11** — as
written but unverified on silicon. A proper matrix would have an
oracle-coverage column per row.

### 5.2 — Target-firmware bias in visibility grading

Visibility was judged by "does pico-sdk / pico-examples touch this". If
the actual near-term target is RP2354 bring-up or bootrom work, the
ranking flips: ACCESSCTRL, OTP_CTRL, POWMAN, GLITCH_DETECTOR all become
HIGH. The audit has no standing answer to "what firmware are we
targeting *next*" and defaulted to a pico-sdk lens. That is an
assumption, not a finding.

### 5.3 — Inter-peripheral wiring is invisible

DMA↔UART/SPI/PIO/ADC via DREQ, PWM→DMA DREQ, TICKS→TIMER/WATCHDOG, and
CLOCKS→every baud/SMCLK divisor are all un-rowed. A working UART with a
dead DREQ grades the same as a working UART with a working DREQ. The
matrix silos peripherals; real firmware doesn't.

### 5.4 — Clock-domain propagation + reset-release re-init

PARTIAL-BEHAVIOUR CLOCKS does not imply every downstream peripheral
recomputes on CLK_PERI change. Reset-release ("toggle RESETS.SPI0 then
use SPI0") isn't graded. Both are plausible silent-divergence sources.

### 5.5 — MMIO access-cycle accounting + NVIC fan-in completeness

`silicon_cycle_oracle_rp2350` measures CPU instruction cost. It almost
certainly does not measure per-bus MMIO access cost (APB latency, PPB
single-cycle). Separately: there are 52 NVIC inputs on RP2350;
`silicon_isr_diff_rp2350` verifies ~1 (TIMER0) plus PendSV/SysTick.
That leaves ~49 IRQ lines as unverified plumbing.

### 5.6 — DMA and PIO misgrade post-mortem

An earlier pass of this audit graded DMA and PIO×3 as "effectively STUB"
(surveyor) then **OPEN QUESTION** (synthesizer). Arthur pushed back —
"I thought DMA was implemented, go check." On direct code inspection
both turned out to be **FULL**.

**DMA**:
- `crates/mdrp2350/src/dma.rs` is **1573 lines** of full behavioural model.
- 32 unit tests pass: mem→mem (byte/halfword/word), DREQ gating (UART0),
  DREQ timer pacing, chains, rings, INTR/INTS W1C, IRQ routing to
  DMA_IRQ0/1, abort, sniff warn-once, high-priority warn-once.
- `tick_dma()` wired into the per-cycle tick loop via
  `Bus::tick_peripherals` (bus/mod.rs:1077) from `Emulator::step`.
- Module doc explicitly lists the firmwares it drives: `hello_dma`,
  `dma_uart`, DMA chain tests.
- Caveat: `hello_dma_firmware_completes_transfer` integration test fails
  with "firmware must write marker 1 to counter cell after DMA completes
  (got 0)" — a specific firmware-level bug, not evidence DMA is absent.

**PIO**:
- PIO primitive lives in `crates/mdpicoem-common/src/pio/` (3585 lines
  across `mod.rs`, `sm.rs`, `decode.rs`, `fifo.rs`). Three-block-wrapper
  (`pio.rs` in mdrp2350) re-exports the common primitive.
- Real `PioBlock::step()` / `step_n()` and `StateMachine::execute_cycle()`
  / `execute_insn()` implement the full PIO ISA decoder and execute.
- `Emulator::tick_peripherals` (lib.rs:374–379) calls
  `pio.step_n(cycles, gpio_in)` on all three blocks every cycle, each
  gated by its RESET_PIO0/1/2 bit.
- IRQ routing via `route_pio_irqs()` (INT0_INTE / INT1_INTE to NVIC).
- 24 passing PIO tests in `pio_tests.rs`.

**How the error propagated.** The surveyor agent annotated DMA as
"stateless (no FSM progress)" and PIO as "no instruction execution" —
both flatly wrong. The synthesizer amplified them to "effectively STUB".
The devil's advocate correctly flagged the synthesizer overreach and
forced a downgrade to OPEN QUESTION, but the root cause (wrong surveyor
annotations) was never re-verified. Arthur's pushback caught it.

Both these peripherals have extensive HLD coverage and committed test
suites — the audit would have been correct if any agent had spent
30 seconds on `wc -l` + running the relevant test suite. Neither did.

**Lessons for future audits**:
1. Never accept a "stateless" or "no execution" annotation without
   reading the code directly. `wc -l` + test count is a 30-second
   sanity check that catches this class of error.
2. When an agent downgrades a peripheral's grade, require a code
   citation (line number of the missing FSM), not a summary phrase.
3. Run each peripheral's unit tests as part of the audit. The 32 DMA
   + 24 PIO passing tests would have short-circuited the whole
   misclassification.
4. Be suspicious of peripheral-by-peripheral grep done at arms' length
   by a subagent. Large modules (1000+ lines, rich test coverage) tend
   to be fully implemented — the grep is more likely to be looking in
   the wrong place than to be finding a real stub.

## §6 — Non-peripheral coverage dimensions the audit didn't grade

The audit was titled "peripheral coverage" and stayed in its lane. These
dimensions are equally "coverage" and were not graded:

- **Bootrom image (32 KB).** BOOT_RAM SRAM is FULL; the mask-ROM
  content, reset-vector execution, and `rom_func_lookup` are not graded.
- **Cortex-M33 ISA bucket coverage.** `qemu_diff_m33` fuzzes to
  catch bugs but we don't publish an instruction-class coverage figure.
  What fraction of `execute_thumb32.rs` opcodes has fuzz hit?
- **VFPv5 single-precision completeness.** Phase 7 work. Coverage vs.
  the VFPv5-SP instruction set is unreported.
- **DCP (CP4/5) and RCP (CP7).** RP2350-specific coprocessors. Present
  in `coprocessor.rs` per `CLAUDE.md`; coverage ungraded.
- **GDB RSP (`mdpicoem-debug`).** Stub. Gap or out of scope depends on
  Arthur's intent.
- **SIO cross-core stress.** Graded FULL based on single-threaded
  serial interleaving. Cross-core FIFO fairness, spinlock contention,
  doorbell ordering under the threaded-cores model (on the roadmap)
  will need re-validation.
- **ISR oracle ↔ peripheral IRQ cross-check.** Which of the 52 NVIC
  inputs has been observed raising from the right peripheral? A
  one-afternoon join; not done.
- **Hazard3 (RISC-V) track.** Scoped out here, but P1a–P4 have landed
  on `main`. This audit should footer a pointer to the RISC-V HLD —
  otherwise a reader concludes RP2350 == ARM only.

## §7 — Recommendations

In priority order:

1. **Reframe the question.** Instead of "what peripherals exist", ask:
   *"which of these 5 firmwares runs end-to-end, and which fails, how?"*
   Pick 5 representative images: blinky, TinyUSB CDC, PicoDVI demo,
   a FreeRTOS image, `pico-examples/pio/ws2812`. The gap map falls out
   for free — and it tells us what to build, not what exists.
2. **Add an oracle-coverage column** to every PARTIAL-BEHAVIOUR row in
   any future revision. Zero-case rows get flagged. Probably drops
   ~9 of 11 rows from "partial" to "written but unverified".
3. **Resolve the DMA / PIO open question explicitly.** Is the missing
   FSM staged or missed? If staged, point at the HLD that schedules it;
   if missed, promote it to a V6 Gap Fill line item.
4. **Decide on a success criterion before implementing more peripherals.**
   "DMA works" is not falsifiable; "pico-examples/dma/channel_irq runs
   to completion and prints expected UART output" is. Without this,
   Tier-1 prioritisation is vibes.
5. **Run `silicon_periph_diff_rp2350 --soak 8h` before publishing a V2
   of this audit.** Every new failure discovered is a row we would
   otherwise have graded green. Empirical beats static grep.
6. **Add the non-peripheral coverage dimensions to the project's
   tech_debt.md**, so they aren't silently excluded from future audits.
