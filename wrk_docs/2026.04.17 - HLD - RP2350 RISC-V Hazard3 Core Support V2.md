# RP2350 — RISC-V Hazard3 Core Support (V2)

**Date:** 2026-04-17
**Crate:** `crates/mdrp2350/`
**Supersedes:** V1 (this document).
**Companion audit:** `wrk_docs/2026.04.16 - HLD - RP2350 Feature Coverage Audit.md` §4.1 ("**Missing — RISC-V Hazard3 cores. Zero code.**")
**Review artefacts:** four-reviewer pass on V1 (architecture, ISA, test strategy, devil's advocate). V2 corrects four factual errors and tightens scope.

## 1. Goal

Run an RP2350 RISC-V firmware binary selected by an `EmulatorBuilder::arch(Arch::RiscV)` switch. First-cut target: a **bare-assembly `blinky-riscv.bin`** (no SDK, no libc, no B-extension use) that toggles a GPIO pin. V1 tried to promise "stock pico-sdk RISC-V blinky" — that was wrong (SDK emits Zba/Zbb/Zbs/Zcmp by default; see §4.5).

## 2. Background

RP2350 ships **two** complete dual-core complexes on the same die:

- **Arm path** — 2× Cortex-M33 (ARMv8-M Mainline, FPU, TrustZone). Implemented.
- **RISC-V path** — 2× **Hazard3** (Wren6991/Hazard3). Not implemented.

Hazard3 extensions actually present (Hazard3 csr.adoc + README):

- RV32I base, M, A, C. Zicsr, Zifencei.
- B-extension **parts**: Zba, Zbb, Zbs, Zbkb, Zbc. There is no RVA/RVB "B" profile on this core.
- Zcmp + Zcb (compressed push/pop, extra compressed loads/stores).
- Custom: `h3.bextm`, `h3.bextmi`, `h3.block`, `h3.unblock`, custom CSRs (including `h3.misa` at 0xBF1).

**Selection** is by OTP fuse + POWMAN at power-up. Only one complex runs at a time. The two paths share Bus, SIO, peripherals, clocks, DMA, PIO, memory map. The SIO side already exposes RISC-V observables as **storage only**: `RISCV_SOFTIRQ` (`sio/mod.rs:30`), `MTIME` / `MTIMECMP` (`sio/mod.rs:36-42`). Neither asserts an IRQ into the core today — that wiring is P4 work (§6), not a free lunch.

We do not run the bootrom (CLAUDE.md: `load_image` bypasses it). ARCHSEL / POWMAN handover stays unmodelled; chip-arch is an `EmulatorBuilder` choice.

## 3. Non-goals (explicit)

- **U-mode, PMP** — storage-only or absent. Matches M33 MPU/SAU enforcement-gap triage in the audit.
- **Hazard3 debug module.** Probe-rs RISC-V attach against RP2350 Hazard3 is unverified on the bench; silicon oracle is deferred to its own HLD (§6 P6).
- **Bootrom dispatch, ARCHSEL, POWMAN.** Not modelled.
- **Full B-extension (Zba/Zbb/Zbs/Zbkb/Zbc), Zcmp, Zcb.** Deferred. V1 MVP is **bare-asm rv32imac only**. See §4.5.
- **Custom Hazard3 instructions** `h3.bextm` / `h3.bextmi`. Deferred. `h3.block`/`h3.unblock` is a HINT-space encoding and falls out from the HINT-tolerant decode (§4.6); `h3.unblock` wake semantics deferred to P4 when IRQs land.
- **`fence`, `fence.i`** — no-op for V1 because we have no decoded-op cache on the RISC-V side. A **tripwire `debug_assert!`** in the future cache-add PR will force a revisit (§4.8).
- **A-extension reservation precision under threaded cores.** Serial-interleave only. Tripwire documented in §4.7.
- **Bootrom-host dependency for firmware builds.** `gen_blinky_riscv.py` emits raw bytes like the existing `gen_blinky.py`. No `riscv32-unknown-elf-gcc` required in the dev setup.
- **Performance counters** beyond `mcycle` / `minstret` (alias `Clock::cycles`).

These follow the audit's discipline: populate the **Verified** column for the RISC-V ISA core first, then come back.

## 4. Design

### 4.1 Cores — enum with explicit migration

```rust
// crates/mdrp2350/src/lib.rs
pub enum Cores {
    Arm([CortexM33; 2]),
    RiscV([Hazard3; 2]),
}

impl Cores {
    /// Panic-on-mismatch accessor for Arm-specific call sites.
    /// Programmer-error contract: only call on an emulator built with Arch::Arm.
    pub fn expect_arm(&self)         -> &[CortexM33; 2];
    pub fn expect_arm_mut(&mut self) -> &mut [CortexM33; 2];
    pub fn expect_riscv(&self)       -> &[Hazard3; 2];
    pub fn expect_riscv_mut(&mut self) -> &mut [Hazard3; 2];
    pub fn is_arm(&self)   -> bool;
    pub fn is_riscv(&self) -> bool;
}

pub struct Emulator {
    pub cores: Cores,     // was: [CortexM33; 2]
    pub bus: Bus,
    pub clock: Clock,
    pub step_quantum: u32,
}
```

**Public API of `Emulator`:**

```rust
// Unchanged signature, new semantics: panics on a RiscV emulator.
pub fn core(&self, id: usize) -> &CortexM33;
pub fn core_mut(&mut self, id: usize) -> &mut CortexM33;
// New, symmetric with the above.
pub fn core_riscv(&self, id: usize) -> &Hazard3;
pub fn core_riscv_mut(&mut self, id: usize) -> &mut Hazard3;
```

Panic on mismatch is a deliberate contract — the caller picked the arch at `build()` time; calling `.core(0)` on a RISC-V emulator is the same class of error as calling `.unwrap()` on a known-Some option. Documented panic, not silent wrong result.

**Migration shape for `emu.cores[i].regs.r[x]`-style call sites.** The dominant idiom today; ~119 sites across ~20 binaries (harness + TUI). Mechanical rewrite:

```
-    emu.cores[i].regs.r[x] = v;
+    emu.cores.expect_arm_mut()[i].regs.r[x] = v;
```

This is **not free** and **not subtle**. V1 understated it as "we just update those call sites." P1a (§6) is scoped explicitly to do this migration, on its own, before any Hazard3 code exists.

**`Emulator::wake_checks`** (`lib.rs:302-309`) reads `self.cores[i].wfe_waiting` directly — post-enum, it becomes an enum match with a `wake_if_ready` method on the private `CoreStep` trait. RISC-V implements this as "if parked on `wfi` and `mip & mie != 0`, resume" — the Arm analogue is "if parked on `wfe` and `bus.event_flag[core]`, resume."

**`Emulator::step`** dispatches once per quantum:

```rust
pub fn step(&mut self) -> u64 {
    self.bus.master_cycle = self.clock.cycles;
    let target = self.clock.cycles + self.step_quantum as u64;
    match &mut self.cores {
        Cores::Arm(cores)   => step_pair(cores, &mut self.bus, target),
        Cores::RiscV(cores) => step_pair(cores, &mut self.bus, target),
    }
    self.clock.advance(self.step_quantum as u64);
    self.tick_peripherals(self.step_quantum);
    self.tick_per_core_time_source();   // arch match — see §4.6
    self.wake_checks();
    self.clock.cycles
}
```

`step_pair` is generic over a `pub(crate) trait CoreStep` with a **closed method set** (no "future-proofing"):

```rust
pub(crate) trait CoreStep {
    fn step(&mut self, bus: &mut Bus);
    fn cycles(&self) -> u64;
    fn is_halted(&self) -> bool;
    fn is_parked(&self) -> bool;                  // Arm: wfe_waiting; RISC-V: wfi parked
    fn wake_if_ready(&mut self, bus: &mut Bus);   // arch-specific wake condition
    fn publish_cycles_to_ppb(&self, bus: &mut Bus) {} // Arm-only; default no-op
}
```

Not public. Two impls, two call sites. If a third arch ever appears, revisit.

**Performance claim** (corrected from V1): the `match` runs once per `step()` (every `step_quantum` cycles, default 64). Inner per-instruction dispatch is monomorphic over the concrete core type via `step_pair<C: CoreStep>`. The match cost is branch-predictor-friendly and not on the hot path, but V1's "inner loop is monomorphic" glossed over that the match runs 2.3 M times/sec at 150 MHz — fine, just not "free of enum dispatch."

### 4.2 Builder

```rust
EmulatorBuilder::new(Config::default())
    .arch(Arch::RiscV)
    .build();
```

Single knob. No env var, no cargo feature.

### 4.3 Reset

`Emulator::reset` becomes an outer arch match; the bus-side reset (RESETS, clocks, peripherals, SIO) is arch-agnostic and shared verbatim.

**Arm arm** — unchanged (`lib.rs:81-140`).

**RISC-V arm:**

- Both harts: all x0..x31 = 0.
- `pc` = reset vector **TBD, see §8 Open Q1** — Hazard3's reset PC is an RTL parameter (`RESET_VECTOR`). RP2350 ties cores to the bootrom alias, not `0x0000_0000`. V1's "PC = 0" claim is probably wrong; the datasheet must confirm before P1b ships.
- `mhartid` = core index (0 or 1) — **TBD, see §8 Open Q2**; confirm against datasheet (some multi-hart designs use `{0, 0x80000001}`, though 0/1 is the Hazard3 RTL default).
- `mstatus` = 0 (M-mode, MIE off, MPIE 0, MPP 00).
- `mtvec` = 0, firmware sets it.
- `mcountinhibit` = `0b11` (cy + ir inhibited — Hazard3 reset value).
- `meicontext.noirq` = 1 (Hazard3 reset value).
- `misa` = `0x4014_1105` (RV32IMAC: bits for I, M, A, C, plus MXL=01). `h3.misa` custom CSR returns windowed Hazard3 extension bitmap — storage for V1, semantics deferred.
- All other CSRs = 0.

Per-harness reset call sites (`emu.reset()` in ~20 binaries) are unaffected — the dispatch is internal to `Emulator::reset`.

### 4.4 Module layout

```
crates/mdrp2350/src/core_riscv/
    mod.rs        // Hazard3 struct, step(), reset(), CoreStep impl
    regs.rs       // x[0..32], pc, CSR file (mstatus/mie/mip/mcause/mepc/mtval/
                  //   mtvec/mscratch/mhartid/mvendorid/marchid/mimpid/
                  //   mcycle/minstret/mcountinhibit/misa + Hazard3 customs)
    decode.rs     // RV32I + M + A + C decode → Op enum
    execute.rs    // execute(Op, &mut Bus); bus.set_active_pc(pc) per instr
    csr.rs        // csrr{w,s,c}{,i} dispatch; illegal-CSR → mcause=2 trap
    trap.rs       // trap entry/return (mtvec direct+vectored modes, mret)
    irq.rs        // P4: meiea/meipa/meifa/meipra/meinext/meicontext windows
    atomics.rs    // lr.w, sc.w, amo*.w via Bus::reservation
```

The existing `core/` module (M33) is **untouched**. P1a touches harness call sites; P1b adds `core_riscv/`. No shared parent type, no public trait surface.

### 4.5 ISA scope — bare-asm rv32imac only for V1

| Feature | V1? | Notes |
|---|---|---|
| RV32I base | **Yes** | All loads/stores, ALU, branches, jal/jalr, lui/auipc, fence (no-op). |
| M | **Yes** | mul/mulh/div/rem per spec; div-by-zero per RISC-V spec. |
| A | **Yes** | lr.w, sc.w, amo*.w. See §4.7. |
| C | **Yes** | Required for any rv32imac toolchain output. |
| Zicsr | **Yes** | Table-driven CSR dispatch; unknown CSR → `mcause=2`. |
| Zifencei | **Yes** | No-op for V1; tripwire for future cache. |
| Zba/Zbb/Zbs/Zbkb/Zbc | **No** | **Follow-up phase**, not V1. |
| Zcmp (cm.push/pop/mva) | **No** | Follow-up. |
| Zcb (c.lbu, c.sb, c.zext.b, c.mul, …) | **No** | Follow-up. |
| `h3.bextm`, `h3.bextmi` | **No** | Follow-up. |
| `h3.block`, `h3.unblock` | Decode-tolerant | HINT-space; V1 treats as no-op (both cores). P4 wires `h3.unblock` to wake. |
| `misa` read | **Yes** | Standard bitmap. `h3.misa` = storage-only. |

**Firmware constraint:** V1 ships `roms/rp2350/blinky-riscv.bin` built by a new `gen_blinky_riscv.py` that emits **only rv32imac** bytes. No SDK, no libc, no Zba/Zbb/Zbs/Zcmp/Zcb — the SDK defaults emit these (pico-sdk RISC-V toolchain config uses `-march=rv32imac_zicsr_zifencei_zba_zbb_zbs_zbkb_zca_zcb_zcmp`), so **SDK firmware will not run on V1.** That is an explicit scope decision, not an oversight.

**Fail loudly on unknown opcodes.** Decode miss → `warn!("unimplemented RISC-V opcode", insn, pc)` + `mcause=2` trap. The audit's §7.2 pattern applied to ISA: no silent illegal-instruction faults that look like firmware corruption.

### 4.6 Interrupts

| Source | RISC-V plumbing | RP2350 side | Already exists? |
|---|---|---|---|
| `msip` (software) | `mip.MSIP` per hart | `SIO.RISCV_SOFTIRQ` storage at `sio/mod.rs:30,166` | Storage ✓; IRQ assert ✗ (P4 work) |
| `mtip` (timer) | `mip.MTIP` per hart | `SIO.MTIME`/`MTIMECMP` + `mtime_match_asserted` at `sio/mod.rs:36-42,405-445` | Storage + match flag ✓; IRQ assert ✗ (P4 work) |
| `meip` (external) | `mip.MEIP`, vectored via `meinext` | `bus.irq_pending[core]` (52 NVIC lines) | Transport ✓; CSR window ✗ (P4 work) |

**V1 was wrong** to call MTIME / RISCV_SOFTIRQ "already implemented." Storage is in place; **firing the interrupt is P4 work.** The per-core `bus.irq_pending` mask is genuinely arch-agnostic — peripherals already fan into it via `assert_irq_core` / `assert_irq_shared` — but the consumer on the RISC-V side (the Hazard3 external IRQ controller window at CSR addresses `0xBE0..0xBE5`: `meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext`) does not exist yet.

**`mtvec` modes.** Bit 0 selects direct (`pc = mtvec.BASE`) vs vectored (`pc = mtvec.BASE + 4*mcause`). Both must be implemented in P2 trap entry — the SDK sets vectored mode.

**NMI (V1 was wrong).** Hazard3's csr.adoc documents **no separate NMI mechanism** and no `mintthresh` CSR. Interrupt causes on Hazard3 are `{3, 7, 11}` standard + exceptions `0..11`. RP2350's "NMI-like" sources (watchdog, glitch detector, force-NMI) are routed through the **ordinary external IRQ controller** with high `meicontext.preempt` priority; they are not a separate non-maskable channel. V1's `Fault::Nmi` reuse was a bad mental model — Hazard3 traps go through its own `pending_trap` field, not the M33 `Fault` enum.

**PPB "inert" claim clarified.** Storage round-trip for M33 PPB reads/writes issued from RISC-V code is fine. One specific edge: `Bus::write*` to `0xE000_E100` (NVIC ISPR) deliberately mirrors into `bus.irq_pending` (`bus/mod.rs:2216`) — that's **correct** behaviour regardless of arch, since `irq_pending` is the arch-agnostic transport the RISC-V IRQ controller reads from. No guard needed; V1's "inert" wording just needed to say "inert storage, except the one intentional fan-out we want anyway."

**`bus.active_pc` per-instruction.** The RISC-V executor must call `bus.set_active_pc(pc)` before each instruction, same contract as `CortexM33::decode_execute`. MMIO trace lines (`bus/mod.rs:782`) require this for meaningful PC attribution. One-liner in the `execute.rs` dispatch loop.

**`wfi` support.** Hazard3 `wfi` parks the hart until `mip & mie != 0`. Implementation: a `wfi_parked: bool` flag on `Hazard3`, set by the `wfi` opcode, cleared by `wake_if_ready` when the wake condition fires. Mirrors the M33 `wfe_waiting`/`event_flag` plumbing through a different predicate. In the `CoreStep` trait as `is_parked`/`wake_if_ready`.

**`tick_per_core_time_source`.** Per-arch:

- Arm: walks `bus.ppb[core_id].systick_advance(cores[core_id].cycles())` as today.
- RISC-V: already ticked via `sio.tick_mtime_n(cycles)` in `tick_peripherals`; this function is a no-op for RISC-V. The `mip.MTIP` fan-out from `sio.mtime_match_asserted[core]` into `bus.irq_pending[core]` is the P4 wiring.

### 4.7 Atomics

Single-host-thread, serial-interleave (CLAUDE.md "Bank contention model").

**`Bus::reservation: [Option<u32>; 2]`** — per-core, stores the word-aligned address of the most recent `lr.w`.

Semantics:

- `lr.w rd, (rs1)`: the address **must be word-aligned and in SRAM** (`0x2000_0000..0x2008_0000`). Misaligned or outside SRAM → `mcause=5` (load address misaligned / fault). Records `rs1` into `reservation[active_core]`, returns the loaded word.
- Any `Bus::write8`/`write16`/`write32(addr, _)` clears **every** reservation where `reservation[c] == Some(addr & !3)`. Masking to word alignment is mandatory — sub-word stores invalidate the containing word's reservation per spec.
- `sc.w rd, rs2, (rs1)`: succeeds iff `reservation[active_core] == Some(rs1 & !3)` AND `rs1` is word-aligned; on success clears the reservation, performs the store, writes 0 to `rd`; on failure returns 1, memory untouched.
- `amo*.w`: read-modify-write within one bus call — atomic by construction (serial interleave).

**DMA writes** go through `Bus::write*` (`dma.rs:547`), so DMA invalidates reservations correctly at no extra cost.

**Tripwire.** The moment `wrk_docs/2026.04.14 - HLD - Threaded Dual-Core Emulation*.md` lands, `Bus::reservation` becomes a torn-read race. `tech_debt.md` entry to be added when P3 ships, pointing forward to the threaded-core HLD.

### 4.8 Decoded-op cache

Skip it for V1. `bus.decode_cache` stays M33-shaped.

**Tripwire.** When the RISC-V decode cache is added later, `fence.i` MUST flush it. Land this as a `debug_assert!(!RISC_V_CACHE_EXISTS, "fence.i is a no-op; wire invalidation first")` in the cache-add PR's `fence.i` execute path, forcing the reviewer to replace it deliberately.

### 4.9 Tests — `Bus::minimal()` for unit scaffolding

`core/mod.rs:262` uses `Bus::default()` inside `execute_one`, which heap-allocates a 192 KB decode cache every test. RISC-V adds ~100 new per-opcode tests; we'd rather not double that allocation. Introduce `pub(crate) fn Bus::minimal()` that returns a bus with an empty (zero-length) decode cache box, suitable for tests that never fetch through the cache. RISC-V tests use it exclusively; M33 test migration is opportunistic, not mandated.

## 6. Phasing

**P1a — Enum migration PR (no Hazard3 code).**
Introduce `Cores` enum with `Arm` arm only. Add `expect_arm*()`, `is_arm`/`is_riscv`. Migrate all `cores[i]` call sites across `crates/mdpicoem-harness/src/bin/` and `crates/mdrp2350app/` to `cores.expect_arm*()[i]`. `Emulator::core(id)` keeps its signature and its current behaviour (since only Arm exists). Define `CoreStep` trait; M33 impls it; `Emulator::step` uses `step_pair`. All existing tests, oracles, and harnesses pass unchanged. Dominant risk: conflicts with concurrent in-flight branches (CLAUDE.md multi-agent note) — merge promptly.

**P1b — Hazard3 skeleton.**
Add `RiscV` arm, add `core_riscv/` module with stub `Hazard3::step()` (advances PC by 4 via the decoded-op length, returns 1 cycle). Reset path. Builder `.arch(Arch::RiscV)`. Smoke: build a RISC-V emulator, step 100 times, observe cycles advance.

**P2 — RV32I + Zicsr + Zifencei + CSRs.**
Full base ISA, CSR table, trap entry/return, `mtvec` direct/vectored, `mret`, `ecall`/`ebreak`, illegal-instruction trap. Per-opcode unit tests. **No external oracle yet** — blocked until P2.5.

**P2.5 — `qemu_diff_riscv32` harness.**
See §7. Lands between P2 and P3 to provide a differential floor for ISA execution.

**P3 — M, A, C.**
Mul/div, atomics with `Bus::reservation`, compressed decoder. `qemu_diff_riscv32` run against each new class. Atomics get a dedicated fuzz generator.

**P4 — IRQ controller + time source wiring.**
Hazard3 IRQ controller CSR window reading from `bus.irq_pending`. `mtip` fan-out from `sio.mtime_match_asserted`. `msip` fan-out from `sio.riscv_softirq`. Trap dispatch at instruction boundary. **Interim oracle** is a hand-authored scenario suite (§7) — not external differential.

**P5 — App integration + smoke firmware.**
`mdrp2350app` gets an `--arch riscv` flag. `gen_blinky_riscv.py` (no toolchain dependency) emits `roms/rp2350/blinky-riscv.bin` with bare-asm rv32imac. Smoke test in `crates/mdrp2350/tests/firmware.rs` asserts GPIO toggles. **Developer smoke; not a validation claim** (§7).

**P6 — Silicon harness (separate HLD).**
Deferred pending probe-rs + RP2350 Hazard3 attach verification on the bench. This is the **single largest open risk** (§8) — without P6, the RISC-V IRQ controller and `mtip`/`msip` wiring ship as *Unit-tested* (audit terminology), not *Verified*. Not a blocker for P1–P5, but the audit column cannot be checked until P6 exists.

## 7. Testing strategy

Measured against the audit's four-tier bar (Verified / Unit-tested / Plumbed / Missing).

**Oracle choice: QEMU > Spike for a Windows host.** V1 recommended Spike. V2 switches to `qemu-system-riscv32 -cpu rv32 -M none -nographic` because:

- Existing `qemu_diff_m33` pattern is battle-tested, Windows-native, and operates on the same GDB-RSP single-step protocol we already know.
- Spike has no Windows binary; WSL2 pass-through forks the harness across two host environments and breaks parity with the probe-based oracles.
- QEMU has no Hazard3 model either — so both oracles share the **same gap** on vendor CSRs + IRQ controller. Given that gap is unavoidable without silicon, pick the oracle that's cheapest to operate.

**`qemu_diff_riscv32` harness (P2.5).** Mirrors `qemu_diff_m33` shape. Spawns QEMU on GDB port `3335`, single-steps both sides, diffs `x0..x31 + pc + mstatus + mcause + mepc + mtval + mip + mie`. `--fuzz N --seed S` mode. Register to CLAUDE.md Testing Topology as oracle #13.

**Coverage (audit-honest):**

- **P2 + P2.5** → RV32I / Zicsr / Zifencei reach **Verified** (QEMU differential).
- **P3 + qemu_diff_riscv32 class expansion** → M, C reach **Verified**. A (atomics) is QEMU-diffable for single-core semantics, but dual-core reservation-invalidation requires a custom property test (below) and so ships at **Unit-tested + property-tested**.
- **P4** → IRQ controller ships at **Unit-tested only** via a hand-authored scenario suite (below). QEMU `rv32` has no Hazard3 CSRs to diff against. Silicon oracle (P6) is the only route to **Verified**; it is deferred.
- **P5** → Developer smoke, explicitly not a validation claim.

**Atomics property test (P3).** Two-core interleaved random sequences of `lr.w` / `sc.w` / plain store against a small shared address pool, oracle = a hand-rolled reference reservation tracker. Catches the exact serial-interleave bugs §4.7 is exposed to. Not a QEMU diff.

**IRQ scenario suite (P4).** Hand-authored hex images that set up `meiea`/`meipa`/`meipra`, trigger an IRQ via a controlled `bus.assert_irq_core`, halt at `ebreak` in the handler, and assert observed `mcause` / `mepc` / `meinext` against hand-computed expectations. Same shape as `silicon_isr_scenarios.rs` but Unit-tested, not silicon.

**Cycle oracle (deferred).** The M33 path has `silicon_cycle_oracle_rp2350`; the RISC-V path will need `silicon_cycle_oracle_riscv_rp2350` eventually. Add as a tracked follow-up in P6 scoping, not V1.

## 8. Open questions / risks

**Q1 (blocks P1b).** **Exact RISC-V reset PC on RP2350.** Hazard3's reset PC is an RTL parameter; RP2350 ties it to the bootrom alias. Need a datasheet cite. Default until confirmed: `0x0000_0000` with a TODO and a silicon-probe verification as part of P6.

**Q2 (blocks P1b).** **`mhartid` assignment.** Hazard3 RTL default is `{0, 1}`. RP2350 datasheet should confirm. If the chip uses a non-standard value, update `Hazard3::reset`.

**Q3 (blocks P6).** **Probe-rs 0.31 + RP2350 Hazard3 attach.** Not verified on the bench. If it doesn't work, P6 needs a fallback plan (UART log capture + mailbox handshake, mirroring `silicon_cycle_oracle_rp2350`'s approach).

**Q4 (design choice now).** **Bare-asm V1 vs SDK support.** §4.5 pins V1 at bare-asm rv32imac. The SDK's toolchain defaults include Zba/Zbb/Zbs/Zcmp/Zcb. First firmware running the SDK is blocked until those extensions land — likely a P7. Decision: ship the narrower scope now, revisit after P5 passes.

**Q5.** **Cycle accuracy.** RISC-V V1 uses flat 1-cycle costs except mul/div (3) and loads (2). The M33 audit lists ~14 known cycle-model gaps; the RISC-V path inherits the same class of issue and will need its own cycle oracle. Tracked in `tech_debt.md`.

**Q6.** **`h3.misa` semantics.** Storage-only for V1. Firmware that probes it to detect extensions will read zeros and likely fall back to base ISA, which matches V1's scope anyway. If anything breaks on this, revisit.

**Q7.** **Threaded-core interaction.** `Bus::reservation` + single-host-thread assumption is tripwired in §4.7, not enforced. If the threaded-core HLD lands before this, the reservation model is wrong from day one of the merge.

## 9. What this HLD deliberately does NOT include

Per CLAUDE.md quality philosophy, and after V1 review:

- No migration plan for pre-existing harnesses beyond the mechanical sed. Dev sandbox.
- No backwards-compatibility shims.
- No feature flags. Chip-arch is a runtime-builder choice.
- No env vars.
- No bootrom / ARCHSEL / POWMAN.
- No abstraction layer beyond the closed `CoreStep` trait. Two arms is not an abstraction problem.
- No cross-cutting M33 refactor.
- No SDK firmware support in V1. The scope line is bare-asm rv32imac.
- No silicon oracle in V1. P6 is a separate HLD gated on bench verification.

If the design grows beyond this document, the growth is wrong.
