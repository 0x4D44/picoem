# Residual A.2.2 — UART0 RX loopback: silicon still BUSY after 25,000 sysclks

**Date:** 2026-04-17
**Parent HLD:** `wrk_docs/2026.04.17 - HLD - Stage A.2 Silicon Oracle Residuals Handoff.md` (Residual 3)
**Parent journal:** `wrk_journals/2026.04.16 - JRN - Silicon Oracle Fidelity Gaps Fix Wave.md` (Stage A) and `wrk_journals/2026.04.17 - JRN - Silicon Oracle Residuals Fix Wave.md`
**Silicon symptom:** `HW=0x18 EMU=0x80` at `0x4007_0018` (UARTFR), mask `0xFFFF_FFFF`, scenario `uart0_rx_loopback`. HW = `BUSY|RXFE` (TX in progress, RX empty); EMU = `TXFE` (drained, byte delivered into RX FIFO).

## 1. First-step analysis — baud-rate math (mandatory)

### Scenario writes

`D:\language\mdrp2354\crates\mdpicoem-harness\src\silicon_scenarios.rs:853` (`S_UART0_RX_LOOPBACK`):

```rust
(RESETS_RESET + ALIAS_CLR, RESETS_CLR_ALL),
(UART0_UARTIBRD, 81),                                  // integer divisor
(UART0_UARTFBRD, 24),                                  // fractional divisor
(UART0_UARTLCR_H, UARTLCR_H_FEN),                      // FEN=1, WLEN=00 (5-bit)
(UART0_UARTCR,  UARTCR_UARTEN | UARTCR_LBE | UARTCR_TXE | UARTCR_RXE),
(UART0_UARTDR,  0x42),                                  // push one byte
```

Scenario table entry (`silicon_scenarios.rs:1144`):

```rust
PeriphScenario {
    name: "uart0_rx_loopback",
    setup: S_UART0_RX_LOOPBACK,
    max_sysclks: 60_000,               // actual budget (CYCCNT-measured)
    observe: O_UART0_RX_LOOPBACK,      // UARTFR mask 0xFFFF_FFFF
    observe_pins: 0,
    custom_sled: None,
    min_sysclks: 25_000,               // warn-only floor (Stage A bump)
},
```

### PL011 baud formula (per RP2350 datasheet §12.1.3.3 / ARM PL011 TRM)

```
divisor = IBRD + FBRD/64 = 81 + 24/64 = 81.375
baud    = UARTCLK / (16 × divisor)
```

### Assumed 150 MHz UARTCLK (emulator default)

```
baud        = 150_000_000 / (16 × 81.375) ≈ 115,207 baud
bit-time    = 1 / 115,207 s ≈ 8.68 µs
byte-time   = 10 × bit-time ≈ 86.8 µs (1 start + 8 data + 1 stop, treating FEN/WLEN as 8N1 for the emulator model which assumes `× 10`; silicon's WLEN=00 = 5-bit would make this 7-bit frame = ~60.8 µs, shorter)
byte-time in sysclks @ 150 MHz = 86.8 µs × 150 MHz ≈ 13,020 sysclks
```

### Budget comparison

- `max_sysclks = 60_000` — the **actual budget** (the CYCCNT-measured sled duration fed into `Emulator::run`). `min_sysclks = 25_000` is a warn-only floor (`silicon_scenarios.rs:2275`), NOT a budget minimum.
- Byte-time at 150 MHz: 13,020 sysclks. 60,000 / 13,020 ≈ 4.6× — ample.
- Byte-time ratio is sys/peri-**invariant**: `byte_time_sysclks = sys_clk × 10 × 16 × divisor / peri_clk`. When `sys_clk == peri_clk` (the post-bootrom default where both follow clk_sys), the absolute frequency cancels: **13,020 sysclks for one byte, regardless of whether clk_sys is 150 MHz, 12 MHz (XOSC) or 6.5 MHz (ROSC).**

So at first glance the budget is more than sufficient. Yet silicon reports `BUSY|RXFE` at 60 k sysclks — TX has not completed after **4.6× byte-time**. The timeout is *not* the problem. Something is preventing the TX shift register from emptying on silicon.

### What *actually* differs between HW and EMU at t=0 of the sled

1. **Emulator**: `Bus::new()` seeds `ClockTree` to post-bootrom defaults (`sys_clk_hz = peri_clk_hz = 150_000_000`, `ref_clk_hz = XOSC`). `UartRegs::sysclks_per_byte` therefore returns ≈ 13,020 once IBRD/FBRD are programmed. The UART's `tick()` path (`crates/mdrp2350/src/peripherals/uart.rs:491`) runs unconditionally per quantum — it does **not** consult `CLK_PERI_CTRL.ENABLE`.
2. **Silicon post-`reset_and_halt`**: the bootrom has **not** run (`Core::reset_and_halt` holds the CPU in debug halt at the reset vector before any code executes — see the comment at `silicon_scenarios.rs:275` which explicitly documents "the bootrom left active (typically ROSC / XOSC post-reset_and_halt)"). All CLOCKS registers are at hardware reset. In particular, **`CLK_PERI_CTRL.ENABLE` (bit 11) is 0** at hardware reset per RP2350 datasheet §8.1.3. With the peripheral clock gate closed, **no UARTCLK reaches the PL011**, so the baud generator does not run, the TX shift register never advances, and `UARTFR.BUSY` remains latched with the byte still in flight.

That fully explains `HW = 0x18` (BUSY|RXFE) at 60 k sysclks: *silicon's UART never got a clock*.

EMU = 0x80 (TXFE + RX FIFO holding the loopback byte): the emulator happily drained at its seeded 150 MHz peri_clk and completed the loopback.

## 2. Hypothesis classification and verdict

Against the A.2 HLD's candidate list:

| Candidate | Match | Notes |
|---|---|---|
| (a) Scenario configures baud < 115200 → bump `min_sysclks` / fix divisors | No | Math is correct; budget is ample. |
| (b) Silicon `BUSY` latches longer than spec → model stretched BUSY in EMU | No | Silicon isn't "stretching" BUSY — it is physically unable to shift the byte without a clk_peri edge. |
| (c) LBE loopback multi-cycle silicon delay unmodelled | No | RX FIFO stays empty because TX never completed, not because the loopback path added latency. |
| **(d)** Emulator's `TXFE`-after-drain diverges from silicon's `BUSY`-during-TX — "emulator draining too fast or missing BUSY=1 window" | **Yes** | Concrete root cause: silicon's clk_peri is gated off (no bootrom to enable it); emulator ignores the `CLK_PERI_CTRL.ENABLE` gate entirely. |

### Verdict — scenario-local bug

**The emulator model is correct** for the case where clk_peri is enabled. The scenario omits the pico-SDK-equivalent step that real RP2350 firmware always does before touching UART: set `CLK_PERI_CTRL.ENABLE = 1`. The other UART scenario, `uart0_tx_single_byte`, gets away with omitting it only because it leaves `IBRD = FBRD = 0` and relies on "baud clock stopped" coincidentally producing the same observable (`TXFE` bit 7 = 0) on both sides. Once a real baud rate is programmed, the CLK_PERI gate matters on silicon.

Emulator-side gating of CLK_PERI.ENABLE is a legitimate fidelity gap (explicitly flagged by the existing warn-once at `crates/mdrp2350/src/bus/peripherals.rs:194` — "CLOCKS CLK_*_CTRL.ENABLE cleared; clock-gate behaviour not modelled"), but modelling it would have **wider blast radius** (ADC/SPI/I2C/PWM scenarios today implicitly assume clk_peri is always live) and is out of scope for the residuals wave. The simplest closed-form fix is scenario-side: set `CLK_PERI_CTRL.ENABLE = 1` before enabling the UART, matching what real firmware does.

### Why not fix the emulator instead?

Modelling `CLK_PERI_CTRL.ENABLE` in the emulator is tempting for fidelity — but:

1. It would break every scenario that skips the setup (e.g. `spi0_loopback_single_byte`, `i2c0_bus_scan_reserved_nack`, `uart0_tx_single_byte`) because each currently passes only because the emulator runs clk_peri regardless.
2. The emulator's `tick_peripherals` path does not plumb an ENABLE predicate into any of the peri peripherals today; we'd need a co-ordinated audit of `uart[0].tick`, `uart[1].tick`, `spi[0..].tick`, `i2c[0..].tick`, etc. plus the associated reset scenarios.
3. The fix wave's charter is "fix or tech-debt each residual" with scenario-local changes preferred. This closes cleanly in 1 line of scenario plus an optional scenario-local unit test mirror.

A broader "model CLK_PERI gating" audit is a worthwhile future task and should be filed as a tech_debt.md entry after this fix lands — but NOT as part of this residual.

## 3. Proposed fix

### 3a. Scenario edit (primary, required)

**File:** `D:\language\mdrp2354\crates\mdpicoem-harness\src\silicon_scenarios.rs`

1. **Add a constant for the `CLK_PERI_CTRL` address** near the other CLOCKS block constants (around L90, next to `CLOCKS_CLK_SYS_DIV`):

   ```rust
   /// CLOCKS CLK_PERI_CTRL — gate for the peripheral clock (UART / SPI /
   /// I2C). Silicon reset value: 0 (ENABLE=0, AUXSRC=0). Post-bootrom
   /// silicon stays ungated until `runtime_init_clocks` sets ENABLE=1.
   /// After `Core::reset_and_halt` the bootrom does NOT run, so scenarios
   /// that program a real UART baud must set ENABLE=1 themselves.
   pub const CLOCKS_CLK_PERI_CTRL: u32 = 0x4001_0048;
   /// ENABLE bit for CLK_*_CTRL (bit 11 on every gated channel).
   pub const CLK_CTRL_ENABLE: u32 = 1 << 11;
   ```

2. **Prepend the CLK_PERI enable write** to `S_UART0_RX_LOOPBACK` (L853). AUXSRC=0 (= clk_sys) is already the reset value, so we only need to set ENABLE:

   ```rust
   const S_UART0_RX_LOOPBACK: &[(u32, u32)] = &[
       (RESETS_RESET + ALIAS_CLR, RESETS_CLR_ALL),
       // Enable clk_peri gate (bootrom skipped by reset_and_halt — firmware
       // would normally do this in runtime_init_clocks). Without ENABLE=1
       // the UART shift register never advances on silicon and BUSY stays
       // latched. Emulator currently ignores the gate (TD-UART-CLK-PERI);
       // write is a no-op on EMU side.
       (CLOCKS_CLK_PERI_CTRL, CLK_CTRL_ENABLE),
       (UART0_UARTIBRD, 81),
       (UART0_UARTFBRD, 24),
       (UART0_UARTLCR_H, UARTLCR_H_FEN),
       (UART0_UARTCR, UARTCR_UARTEN | UARTCR_LBE | UARTCR_TXE | UARTCR_RXE),
       (UART0_UARTDR, 0x42),
   ];
   ```

3. **Update the scenario's `min_sysclks` rationale comment** (L1151-1155) to reflect that 13,020 sysclks of byte-time is now genuinely reached now that clk_peri is live. No change to the 25,000 value — it's still a sane warning floor.

### 3b. No emulator edits required

The emulator already produces `UARTFR = 0x80` after ≥13,020 sysclks with IBRD=81/FBRD=24/FEN/LBE/UARTEN/TXE/RXE (verified by `uart_loopback_uartfr_after_full_tx_is_0x80`, `crates/mdrp2350/src/peripherals/uart.rs:623`). The write to `CLK_PERI_CTRL = 0x800` lands in `Bus::clocks_write` and is silently dropped by the `match offset { ... _ => {} }` branch at `crates/mdrp2350/src/bus/peripherals.rs:205` — no warn is emitted because the write sets ENABLE rather than clearing it (`clears_enable` check at `peripherals.rs:189-193`). No EMU-side observable changes.

### 3c. tech_debt.md entry for the emulator-side gap

Add an entry noting:

- **Title:** "UART/SPI/I2C ignore `CLK_PERI_CTRL.ENABLE` — peripheral keeps running after firmware gates clk_peri"
- **Evidence:** this residual required a scenario-side workaround; silicon gates the UART's clk_peri input until firmware writes ENABLE=1, emulator runs it unconditionally.
- **Scope:** `tick` paths in `crates/mdrp2350/src/peripherals/{uart,spi,i2c}.rs` plus the ADC/PWM tick gate equivalents.
- **Cost of fixing:** coordinated audit of peri-clock consumers + every scenario that currently relies on implicit "clk_peri always live". Non-trivial — defer until a firmware scenario exercises dynamic clk_peri enable/disable.

This does NOT block closing A.2.2.

## 4. Test plan (TDD)

### 4a. Scenario-mirror unit test in `crates/mdrp2350/src/peripherals/uart.rs::tests`

Today's `uart_loopback_uartfr_after_full_tx_is_0x80` already captures the post-drain state. Add **one new test** that exercises the scenario's exact sequence end-to-end through the bus (verifies the added CLK_PERI write is a clean no-op on EMU):

```rust
/// End-to-end replica of the `uart0_rx_loopback` silicon scenario:
/// writes go through `Bus::write32` in the same order the scenario
/// applies them on silicon. Asserts EMU side produces UARTFR = 0x80
/// after one byte-time at 150 MHz. The CLK_PERI_CTRL write is a no-op
/// on EMU (TD-UART-CLK-PERI); this test locks in that invariant so a
/// future emulator that starts honouring CLK_PERI gating doesn't
/// silently break the scenario.
#[test]
fn scenario_uart0_rx_loopback_emu_end_to_end_matches_silicon_expected() {
    use crate::Bus;
    use crate::bus::RESET_UART0;
    const RESETS_BASE: u32 = 0x4002_0000;
    const RESETS_CLR: u32 = RESETS_BASE + 0x3000;
    const CLOCKS_CLK_PERI_CTRL: u32 = 0x4001_0048;
    const CLK_CTRL_ENABLE: u32 = 1 << 11;

    let mut bus = Bus::new();
    // Release UART0 (post-bootrom holds it in reset).
    bus.write32(RESETS_CLR, 1 << RESET_UART0);
    // Scenario setup sequence (matching silicon_scenarios.rs order).
    bus.write32(CLOCKS_CLK_PERI_CTRL, CLK_CTRL_ENABLE);
    bus.write32(UART0_BASE + UARTIBRD, 81);
    bus.write32(UART0_BASE + UARTFBRD, 24);
    bus.write32(UART0_BASE + UARTLCR_H, UARTLCR_H_FEN);
    bus.write32(UART0_BASE + UARTCR,
        UARTCR_UARTEN | UARTCR_LBE | (1 << 9) | UARTCR_TXE);
    bus.write32(UART0_BASE + UARTDR, 0x42);
    // Advance 60,000 sysclks (matching the scenario's max_sysclks).
    for _ in 0..60_000 {
        bus.tick_peripherals(1);
    }
    let fr = bus.read32(UART0_BASE + UARTFR);
    assert_eq!(
        fr, 0x0000_0080,
        "end-to-end EMU UARTFR must be 0x80 (TXFE + RX byte + CTS=0); got 0x{fr:08X}",
    );
}
```

**Today (pre-scenario-edit):** passes — the emulator happily drains regardless of CLK_PERI_CTRL, so this test already reaches 0x80. (The test's job is not to FAIL pre-fix; it's to pin down the emulator-side invariant so a later emulator refactor that correctly gates on CLK_PERI doesn't regress this scenario silently.)

**After scenario edit:** still passes — scenario now matches the test's setup exactly.

If `bus.tick_peripherals` is not `pub` at the needed visibility, substitute a minimal stand-in (`let mut emu = EmulatorBuilder::new(Config::default()).step_quantum(1).build(); emu.core_mut(0).halt(); emu.core_mut(1).halt(); ... emu.run(60_000);`). Same observable.
