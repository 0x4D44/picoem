## 3. The V3 hypothesis upgrade

V2.1 §9.3 left two competing hypotheses for the mdrp2350 classifier-cluster:

| # | Hypothesis | Evidence at end of V2.1 |
|---|---|---|
| 1 | Bucket 4 by call-site equivalence (consumer reads `is_pure()` only to gate a fast-path whose end-state is identical) | Strong — fast/slow path bodies in `decode.rs:302-402` produce identical `regs`/`xpsr` writes; the only divergence is `bus.extra_wait_states()` + `bank_penalty` accounting, which feeds `cycles` only. |
| 2 | Bucket 1/2 — real gap | Weak — would need cycle-only divergence to be observable, but QEMU doesn't report cycles. |

**V3 reading after the oracle code spelunking**: hypothesis 1 holds. The mdrp2350 fast/slow path split was designed to be observably-equivalent on register state — that's why `populate_decode_cache` and the slow-path body both call `bus.read16()` for the fetch and both end up at the same `execute_thumb*` handler. Mis-classifying a non-pure op as pure can cause cycle accounting to drift (the fast path doesn't `bus.add_extra_wait_states` for non-sequential fetches), but registers are identical.

**This recasts the 51 mdrp2350/decode.rs persistent survivors as Bucket 4 by oracle observability, not Bucket 1 or 2.** Closure: either (a) `#[mutants::skip]` the classifier helpers since the cycle path is the only escape and is unmeasured, OR (b) extend the oracle to compare cycles cross-tool (requires cycle counting in QEMU, which is hard, OR a silicon cycle oracle which we already have for RP2350 — `silicon_cycle_oracle_rp2350`).

The same logic applies to mdrp2040 classifier survivors (79 mutants, V2 triage §3.1) but with the additional "consumer is dead code" overlay: the mdrp2040 fast-path consumer hasn't shipped at all per `42ee533`. So the mdrp2040 cluster is doubly unobservable.

This re-reading shrinks the V3 hand-inspection budget significantly. Of the ~100 candidates triage HLD §5 sized for Bucket 1 + Bucket 2, the 51 mdrp2350/decode.rs entries collapse to confirmed Bucket 4. Remaining hand-inspection budget: ~50.

## 4. Plan — sequencing

The V3 work decomposes into three streams. Streams **A** and **B** are independent and can interleave; stream **C** depends on the others' outcomes.

### Stream A — Direct unit tests for classifiers (Action 2, mdrp2040 + mdrp2350)

Goal: convert classifier mutants from "unobservable via existing oracles" to "caught by direct unit test".

The classifiers are pure functions of opcode bits with no side effects. Thumb-16 has 65 536 inputs; Thumb-32 has 2³² but the relevant prefix space (`hw0 >> 11`) covers only ~16 distinct dispatch arms. Direct exhaustive enumeration is feasible.

**Test design:**

1. For each classifier function (`classify_thumb16_pure`, `classify_thumb16_misc_pure`, `classify_thumb32_pure`, plus mdrp2350's `classify_thumb32_branch_misc_pure` and `classify_thumb32_misc_control_pure` and `is_thumb16_flag_only`), compute the classifier output across the entire input space (16-bit for Thumb-16; for Thumb-32 use a representative `hw1 = 0` plus a handful of corner-case `hw1` values that exercise op-field bits).
2. Encode the expected result as a snapshot (`HashSet<u16>` of "pure" Thumb-16 opcodes, similar for Thumb-32 corner cases).
3. The test asserts the classifier matches the snapshot bit-for-bit. Any mutation that flips even one classification fails the test.

This is the equivalent of a **golden snapshot test** for the classifiers. Mutation kill rate should approach 100 % for the classifier mutants — every mutation alters at least one input → output mapping, and the test asserts every mapping.

**Files to add:**
- `crates/mdrp2040/src/core/decode_classifier_tests.rs` (new) — exhaustive snapshot tests for the four mdrp2040 classifier functions.
- `crates/mdrp2350/src/core/decode_classifier_tests.rs` (new) — same shape, six classifier functions.

Wire each into the parent crate's test module (existing `mod tests;` lives in `tests.rs` per crate). I'll inline-register a `#[cfg(test)] mod decode_classifier_tests;` next to the existing test wiring.

**Runtime budget**: 65 536 calls × ~1 ns each = sub-millisecond. No threat to CI runtime.

**Validation**: after landing, re-run `cargo mutants` scoped to `crates/mdrp2040/src/core/decode.rs` and `crates/mdrp2350/src/core/decode.rs`. Expect:
- mdrp2040 decode: 79 missed → ~0 missed (small residue from `decode_execute` body mutations not covered by classifier tests).
- mdrp2350 decode: 51 caught flips on the classifier helpers; the 12 `decode_execute` body mutants and 3 `populate_decode_cache` mutants stay surviving (different code path, not the classifier).

### Stream B — Triage softfloat IEEE-754 persistent survivors

Goal: distinguish Bucket 4 (semantic equivalence under the test corpus) from Bucket 2 (real oracle gap) for the ~30 IEEE-754-helper survivors.

**The two interesting headlines from V2.1 §9.4:**
1. `fp_div`: `/ → %` survives fuzz=2000.
2. `fp_sub`: `- → /` survives fuzz=2000.

These are *not* structurally Bucket 4 — the operations differ in the general case. Their persistence at 2000 iterations means either:
- (a) softfloat_diff doesn't generate inputs where `a / b` and `a % b` differ, OR `a - b` and `a / b` differ, OR
- (b) the mutation site is in an unreachable branch of `fp_div`/`fp_sub`.

**Method:**
1. Read the mutation patches for those two specific entries from `mutation/v2/mutants_catalog.json` to find the exact line + AST context.
2. Read the function body at that line.
3. If the `/` or `-` is on a flag/exponent path that is only reached for special values (NaN, ±0, infinity), the corpus distribution determines reachability. Check `softfloat_diff`'s test generators in `crates/mdpicoem-harness/src/lib.rs` (search for `softfloat_test_cases` / similar).
4. Verdict: Bucket 4 (unreachable code path) → annotate with `#[mutants::skip]` + comment, or Bucket 2 (corpus gap) → file a tech_debt entry and propose a corpus extension.

Apply the same pattern to the 20+ `| → ^` persistent survivors. V2.1 §9.4 calls those structurally Bucket 4 (disjoint bit-fields) — I'll spot-check 3-5 of them to confirm and then bucket the rest by pattern.

### Stream C — `#[mutants::skip]` annotations + tech_debt entries (Action 4)

Goal: clean the books so the next V3.1 sweep has lower noise and the bucket distribution reflects measured reality.

After Stream A, the mdrp2040 + mdrp2350 classifier helpers are caught by unit tests — no skip needed. After Stream B, confirmed-Bucket-4 IEEE-754 mutations get `#[mutants::skip]` with a one-liner per skip ("disjoint bit-field — `|` is `^`-equivalent").

**Skip targets (tentative, finalised after Stream B):**
- `vfp_sd`, `vfp_sn`, `vfp_sm`, `fpscr_set_nzcv`, `vfp_expand_imm_f32` in `execute_fpu.rs` — encoding helpers, only observable via `qemu_diff_m33 --classes fpu` (broken on QEMU 8.2 in this env, V2 triage Action 3). **Do NOT skip these** — the per-function routing already records them as `oracle_unavailable`, which is the right verdict. Skipping would lose the signal that the env fix is still owed.
- IEEE-754 confirmed bit-disjoint `| → ^` / `| → &` survivors (~22 mutants).
- mdrp2040 `execute_wide.rs` MSR/MRS unreachable register IDs (~16 mutants per V2 triage §3.2). Confirm individually before skipping.

For confirmed Bucket-2 oracle gaps (corpus extension owed), file a tech_debt entry under "Mutation testing residue — V3" and reference the specific mutants by name so a future sweep can validate the fix.

The `mutants` crate is added on first `#[mutants::skip]` use as a `[dev-dependencies]` entry in the affected crate's `Cargo.toml`. Standard Rust dev-dep — zero runtime impact, only consumed by `cargo mutants`.

## 5. Out of scope for V3

- **QEMU FPU class env fix** (V2 triage Action 3). Environment work, not a code change. Out of scope.
- **Mutation scope expansion** to bus / DMA / PIO / peripherals / exceptions. Deferred to V4.
- **CI integration**. The full V2 sweep is too slow for per-PR; `cargo mutants --in-diff` as a nightly job is V4.
- **Cycle-comparison cross-tool** for catching the mdrp2350 classifier cluster via the QEMU oracle. QEMU doesn't expose cycle counts and adding silicon cycle measurement to every mutant run is impractical. Hypothesis 1 (call-site equivalence) is the cheaper closure.
- **Bumping to a new V2 sweep**. The existing 801-mutant catalog is the V3 input; we're not regenerating it.
