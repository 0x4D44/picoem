# QEMU Differential Test Harness — Low-Level Design

Version: 0.2.0 — DRAFT
Date: 2026-04-13
Parent: HLD Section 10.3 (Oracle Layer 2)

## 1. Purpose

Validate Thumb-2 instruction semantics by executing identical instruction
sequences in both QEMU (Cortex-M33 model) and our mdrp2354 emulator, then
diffing register state. This is Oracle Layer 2 — it validates **correctness**
(right results, right flags) but NOT cycle counts (that's Layer 3, probe-rs).

**QEMU is not an infallible oracle.** It is a mature, well-tested Cortex-M33
implementation, but it has bugs and makes arbitrary choices for architecturally
UNPREDICTABLE results. When QEMU and our emulator disagree, we don't
automatically assume QEMU is right — we triage (see Section 14). The value of
QEMU is as a *second implementation* to catch bugs in ours, not as ground truth.

### What This Validates

- Every Thumb-16 and Thumb-32 instruction encoding produces correct results
- All flag updates (N, Z, C, V, Q, GE) match the ARM reference implementation
- Memory load/store operations read and write correct values
- Branch and link operations update PC and LR correctly
- Edge cases: overflow, underflow, carry chains, sign extension, saturation

### What This Does NOT Validate

- Cycle counts (QEMU doesn't model M33 pipeline timing)
- Bus arbitration or memory access timing
- Peripheral behaviour
- Exception entry/return timing (though exception semantics can be tested)

## 2. Architecture

```
 ┌───────────────────────┐       ┌───────────────────────┐
 │   QEMU MPS2-AN505     │       │   mdrp2354 emulator   │
 │   (Cortex-M33)        │       │   (in-process)        │
 │                        │       │                        │
 │   GDB server :1234    │       │   Direct Rust API      │
 └───────────┬────────────┘       └───────────┬────────────┘
             │ TCP                             │ fn call
             │                                 │
    ┌────────▼─────────────────────────────────▼────────┐
    │              qemu_diff binary                      │
    │                                                    │
    │  ┌──────────────┐    ┌──────────────────────────┐ │
    │  │ GdbClient    │    │ EmuRunner                 │ │
    │  │ (TCP → QEMU) │    │ (drives CortexM33 + Bus) │ │
    │  └──────┬───────┘    └──────────┬────────────────┘ │
    │         │                       │                   │
    │         └───────────┬───────────┘                   │
    │                     │                               │
    │              ┌──────▼──────┐                        │
    │              │ Comparator  │                        │
    │              │ diff regs,  │                        │
    │              │ flags, mem  │                        │
    │              └─────────────┘                        │
    └─────────────────────────────────────────────────────┘
```

**Key decision: no assembler toolchain at runtime.** Both QEMU and our emulator
are fed raw opcode bytes. QEMU gets them via GDB memory-write packets (`M`);
our emulator gets them via `execute_one()` / `execute_one_wide()`. This
eliminates the `arm-none-eabi-as` dependency from the test hot path.

## 3. QEMU Setup

### 3.1. Machine Model

QEMU machine: `mps2-an505` (ARM MPS2 with AN505 FPGA image, Cortex-M33, IoTKit
SSE). This is the primary Cortex-M33 target in QEMU, maintained by Peter Maydell.

### 3.2. Memory Map (QEMU MPS2-AN505)

| Region     | Address        | Size  | Notes                           |
|------------|----------------|-------|---------------------------------|
| ssram-0    | 0x00000000     | 4 MB  | Boot RAM (behind MPC)           |
| Secure alias | 0x10000000   | 4 MB  | Alias of ssram-0 (init-svtor)   |
| ssram-1    | 0x28000000     | 2 MB  |                                 |
| System RAM | 0x80000000     | 16 MB | Largest contiguous block        |

The vector table is at `0x10000000` (secure alias). QEMU reads SP from word 0
and reset vector from word 1 at this address on reset.

### 3.3. Launch Command

```bash
qemu-system-arm ^
    -machine mps2-an505 ^
    -cpu cortex-m33 ^
    -nographic ^
    -S ^
    -gdb tcp::3333
```

Notes:
- `-S` is essential: without it, QEMU starts executing from the vector table
  immediately and will fault on invalid memory before our harness connects.
- No `-kernel` flag needed. QEMU boots with ssram-0 zeroed; we write all test
  content via GDB memory packets before stepping.
- Port 3333 (not default 1234) to avoid conflicts with other GDB sessions.
- **Windows:** Uses `^` for line continuation. The harness constructs arguments
  programmatically via `std::process::Command`, so the shell syntax is
  irrelevant in practice — this example is for manual testing.

### 3.4. QEMU Lifecycle

The harness manages QEMU as a child process via `std::process::Command`:

```
1. Spawn QEMU process with args above
2. Retry TCP connect to localhost:3333 (up to 5 seconds, 100ms intervals)
3. Connect GDB client, perform handshake
4. Write minimal vector table once (SP + reset vector → TEST_SLOT)
5. Run all test cases (reusing the same QEMU instance)
6. Kill QEMU via Child::kill() + Child::wait() on completion or error
```

**One QEMU instance per test run, not per test case.** Spawning QEMU takes
~200ms; doing that per-instruction would dominate runtime. Instead, between
tests we reset state by writing registers and memory via GDB.

**Windows process management:** Use `std::process::Child::kill()` which calls
`TerminateProcess` on Windows. Always call `Child::wait()` after `kill()` to
avoid zombie processes. If the harness panics, use a `Drop` guard on the QEMU
handle to ensure cleanup:

```rust
struct QemuProcess {
    child: std::process::Child,
}

impl Drop for QemuProcess {
    fn drop(&mut self) {
        let _ = self.child.kill();
        let _ = self.child.wait();
    }
}
```

### 3.5. State Reset Between Tests

Between test cases, we must reset QEMU to a clean state:

1. Write all R0-R15 to known values via `P` packets
2. Write xPSR to a known value (T bit set, all flags cleared)
3. Write the test instruction(s) to the test slot address
4. Write BKPT after the test instruction(s) as safety net
5. Set PC to test slot address (with Thumb bit in GDB write)

We do NOT reset memory between tests (unnecessary — each test writes its own
instruction bytes). We DO zero the SRAM region used for load/store tests.

### 3.6. Test Slot Address

All test instructions are written to a fixed address in QEMU's SRAM:

```
TEST_SLOT    = 0x10000100   # Well past vector table
TEST_STACK   = 0x10040000   # SP for load/store tests (top of ssram-0 region)
TEST_SCRATCH = 0x10000200   # Scratch SRAM for load/store test data
```

The vector table (0x10000000-0x100000FF) is left alone after initial setup.
We write a minimal vector table once at startup (SP + reset vector pointing to
TEST_SLOT) so that if QEMU somehow resets, it lands in our test slot rather
than faulting.

## 4. GDB RSP Client

### 4.1. Module: `gdb_client.rs`

A minimal, purpose-built GDB RSP client. NOT a general-purpose GDB library —
only implements the 7 packets we need.

**TCP socket configuration (Windows):** Disable Nagle's algorithm
(`TcpStream::set_nodelay(true)`) to avoid 40ms+ delayed-ACK coalescing on
Windows localhost. This is critical for throughput — without it, each GDB
packet round-trip incurs Nagle delay.

```rust
pub struct GdbClient {
    stream: TcpStream,
    buf: Vec<u8>,               // Receive buffer
    reg_map: RegisterMap,       // Discovered via target XML at handshake
}

/// Register indices discovered from QEMU's target XML.
/// Not hardcoded — parsed from qXfer:features:read response.
pub struct RegisterMap {
    pub gpr: [u8; 16],      // R0-R15 GDB indices
    pub xpsr: u8,           // xPSR GDB index
    pub fpu_d: [u8; 16],    // D0-D15 GDB indices (optional)
    pub fpscr: u8,          // FPSCR GDB index (optional)
    pub has_fpu: bool,      // Whether FPU registers were found
}

impl GdbClient {
    /// Connect to QEMU GDB server. Retries for up to `timeout`.
    pub fn connect(addr: &str, timeout: Duration) -> Result<Self>;

    /// Send initial handshake: query halt reason, discover register map
    /// via qXfer:features:read, verify stopped.
    pub fn handshake(&mut self) -> Result<()>;

    /// Read one register by index. Returns 32-bit value.
    pub fn read_reg(&mut self, reg: u8) -> Result<u32>;

    /// Write one register by index.
    pub fn write_reg(&mut self, reg: u8, value: u32) -> Result<()>;

    /// Read all core registers (R0-R15 + xPSR). Returns 17-element array.
    /// Uses `g` packet (single round-trip).
    pub fn read_all_regs(&mut self) -> Result<[u32; 17]>;

    /// Write all core registers (R0-R15 + xPSR) in one packet.
    /// Uses `G` packet — single round-trip vs 17x `P` packets.
    /// This is the default for test setup, not an optimisation.
    pub fn write_all_regs(&mut self, regs: &[u32; 17]) -> Result<()>;

    /// Read memory. Returns bytes.
    pub fn read_mem(&mut self, addr: u32, len: usize) -> Result<Vec<u8>>;

    /// Write memory.
    pub fn write_mem(&mut self, addr: u32, data: &[u8]) -> Result<()>;

    /// Single-step one instruction. Returns stop reason.
    pub fn step(&mut self) -> Result<StopReply>;

    /// Kill the remote (for cleanup).
    pub fn kill(&mut self);
}
```

### 4.2. Packet Framing

```
Send: $payload#XX   (XX = sum(payload bytes) % 256, 2-digit hex)
Recv: +              (ACK)
Recv: $response#XX
Send: +              (ACK)
```

Implementation detail: after sending a packet, read bytes until we see `$`,
then read until `#XX`. Verify checksum. Send `+` to ACK.

### 4.3. Register Numbering (ARM Cortex-M GDB Target)

Register indices are **discovered at startup** by parsing QEMU's target XML
via `qXfer:features:read`. The typical layout for `mps2-an505` with M-profile:

| GDB Index | Register | Notes                         |
|-----------|----------|-------------------------------|
| 0-12      | R0-R12   | General purpose               |
| 13        | SP (R13) | Current stack pointer         |
| 14        | LR (R14) | Link register                 |
| 15        | PC (R15) | Program counter               |
| 25        | xPSR     | Combined status register      |

These are populated into `RegisterMap` during `handshake()`. **Do not hardcode
these values** — they can change between QEMU versions and depend on which XML
features the target reports.

**Constraint:** xPSR bits [8:0] (IPSR / exception number) are **read-only**
through QEMU's GDB interface. We cannot set the exception number via GDB. This
means we cannot diff exception-handler state through this harness — exception
testing requires a different approach (running code that triggers exceptions
and observing the outcome, rather than injecting exception state).

### 4.4. `P` Packet Value Encoding

Register values are encoded as **little-endian hex**:

```
P f=00010008   → Write PC (reg 15) = 0x08000100
P 0=05000000   → Write R0 = 0x00000005
```

Note: GDB's `P` packet uses target byte order (little-endian for ARM).

### 4.5. FPU Register Access

FPU registers are accessible via separate GDB register indices (beyond the
core registers). The exact numbering is discovered from QEMU's target XML
during `handshake()` and stored in `RegisterMap`. Typical layout:

- D0-D15: 64-bit double registers (indices vary by QEMU version)
- FPSCR: follows D15
- S0-S31 are synthesised from D0-D15 (S0 = low32(D0), S1 = high32(D0), etc.)

FPU diffing is Phase 7 scope. The harness supports it structurally
(`RegisterMap.has_fpu`) but skips FPU comparison until FPU instructions are
implemented.

## 5. Emulator Runner

### 5.1. Module: `emu_runner.rs`

Drives our mdrp2354 emulator for the same test case.

```rust
pub struct EmuRunner {
    core: CortexM33,
    bus: Bus,
}

impl EmuRunner {
    pub fn new() -> Self;

    /// Set all registers to match a TestCase's preconditions.
    pub fn setup(&mut self, tc: &TestCase);

    /// Execute the test instruction(s). Returns post-state.
    pub fn execute(&mut self, tc: &TestCase) -> RegisterState;

    /// Reset to clean state between tests.
    pub fn reset(&mut self);
}
```

### 5.2. Execution Strategy

For the emulator side, we use the direct execution API, NOT `step()`:

- **16-bit instruction**: `core.execute_one(opcode)`
- **32-bit instruction**: `core.execute_one_wide(hw0, hw1)`
- **Memory-accessing instructions**: `core.execute_one_with_bus(opcode, &mut bus)`

This tests the instruction semantics directly, without bus timing or stall
cycles muddying the comparison. We're diffing **what** the instruction does,
not **when** it completes.

### 5.3. Memory Setup for Load/Store Tests

For instructions that access memory (LDR, STR, LDM, STM, etc.), the emulator
runner sets up Bus memory to match what we wrote into QEMU via GDB:

```rust
fn setup_memory(&mut self, tc: &TestCase) {
    for &(addr, val) in &tc.memory_pre {
        self.bus.write8(addr, val);
    }
}
```

After execution, we also compare memory state at addresses specified in the
test case.

## 6. Test Case Model

### 6.1. `TestCase` Struct

```rust
/// A single differential test case.
pub struct TestCase {
    /// Human-readable name (e.g., "ADDS R0, R1, R2").
    pub name: String,

    /// Instruction encoding(s). 1 entry = 16-bit, 2 entries = 32-bit.
    pub opcodes: Vec<u16>,

    /// Register preconditions: (reg_index, value) pairs.
    /// Registers not listed default to 0 (R0-R12), TEST_STACK (SP),
    /// 0xFFFFFFFF (LR), TEST_SLOT (PC).
    pub reg_pre: Vec<(u8, u32)>,

    /// xPSR precondition (default: 0x01000000, T bit set only).
    pub xpsr_pre: u32,

    /// Memory preconditions: (address, byte_value) pairs.
    /// For load tests — pre-populate memory before execution.
    pub memory_pre: Vec<(u32, u8)>,

    /// Memory addresses to compare after execution.
    /// For store tests — verify memory was written correctly.
    pub memory_check: Vec<u32>,

    /// Which registers to compare (default: all R0-R12, SP, LR, PC, xPSR).
    /// Some tests may exclude registers that are legitimately different
    /// (e.g., PC after a branch differs by address space).
    pub compare_mask: CompareMask,
}

/// Controls which parts of state are compared.
pub struct CompareMask {
    /// Compare R0-R15 (bitmask, default: all set except PC — see below).
    pub regs: u16,
    /// xPSR flag bits to compare (bitmask). Default: N|Z|C|V|Q (0xF800_0000).
    /// Per-instruction masks exclude UNPREDICTABLE flag bits. For example,
    /// MUL's C and V flags are UNPREDICTABLE on M33 — QEMU produces
    /// arbitrary values for these, so we must mask them out.
    pub xpsr_mask: u32,
    /// Compare xPSR GE bits [19:16]. Default: true for DSP instructions.
    pub ge_bits: bool,
    /// Compare memory at check addresses. Default: true.
    pub memory: bool,
    /// If true, compare PC as relative delta (PC_post - PC_pre) rather
    /// than absolute value. Default: true (handles address space mismatch).
    pub pc_relative: bool,
}
```

### 6.2. Default Preconditions

| Register | Default Value  | Rationale                            |
|----------|----------------|--------------------------------------|
| R0-R12   | 0x00000000     | Clean slate                          |
| SP (R13) | TEST_STACK     | Valid stack pointer for push/pop     |
| LR (R14) | 0xFFFFFFFF     | Distinguishable sentinel             |
| PC (R15) | TEST_SLOT      | Points to test instruction           |
| xPSR     | 0x01000000     | T bit set (Thumb mode), flags clear  |

## 7. Test Generation

### 7.1. Capability Gating

The harness only generates tests for instruction classes the emulator actually
implements. This avoids thousands of guaranteed-failure noise tests.

```rust
/// Instruction classes the emulator currently implements.
/// Update this as new instruction groups are added to the decoder.
pub fn implemented_classes() -> &'static [InstrClass] {
    &[
        InstrClass::ShiftImm,        // LSL, LSR, ASR (immediate)
        InstrClass::AddSubReg,       // ADD, SUB (register, 3-bit imm)
        InstrClass::MovCmpImm8,      // MOV, CMP, ADD, SUB (8-bit imm)
        InstrClass::DataProcReg,     // AND, EOR, LSL, LSR, ADC, SBC, ROR, TST, RSB, CMP, CMN, ORR, MUL, BIC, MVN
        InstrClass::SpecialDataBx,   // MOV high, ADD high, BX, BLX
        InstrClass::LoadStoreReg,    // STR, LDR, STRB, LDRB, LDRSB, etc. (register offset)
        InstrClass::LoadStoreImm,    // STR, LDR, STRB, LDRB, STRH, LDRH (immediate offset)
        InstrClass::LoadStoreSp,     // STR, LDR (SP-relative)
        InstrClass::AdrAddSp,        // ADR, ADD Rd, SP, #imm
        InstrClass::Misc,            // ADD/SUB SP, SXTH, UXTB, REV, REV16
        InstrClass::PushPop,         // PUSH, POP
        InstrClass::StmLdm,          // STM, LDM
        InstrClass::BranchCond,      // B<cond>
        InstrClass::BranchUncond,    // B (unconditional)
        InstrClass::Bl,              // BL (32-bit)
    ]
}
```

`generate_all()` filters generators by this list. When a new instruction class
is implemented in the emulator, add it to `implemented_classes()` and the
corresponding test generator activates automatically.

### 7.2. Module: `test_gen.rs`

Generates `TestCase` instances for implemented instruction classes. Three
strategies:

#### Strategy 1: Exhaustive Encoding Sweep

For each instruction class, enumerate all valid encoding fields and generate
test cases. Example for ADDS (register):

```rust
fn gen_adds_reg() -> Vec<TestCase> {
    let mut tests = Vec::new();
    for rd in 0..8 {
        for rn in 0..8 {
            for rm in 0..8 {
                // ADDS Rd, Rn, Rm: 0001100_mmm_nnn_ddd
                let opcode = 0x1800 | (rm << 6) | (rn << 3) | rd;
                tests.push(TestCase {
                    name: format!("ADDS R{rd}, R{rn}, R{rm}"),
                    opcodes: vec![opcode],
                    reg_pre: vec![
                        (rn as u8, 0x1000_0000),
                        (rm as u8, 0x2000_0000),
                    ],
                    ..TestCase::default()
                });
            }
        }
    }
    // Add edge cases: overflow, zero, max values
    tests.extend(gen_adds_reg_edge_cases());
    tests
}
```

#### Strategy 2: Edge-Case Battery

For each instruction, generate tests targeting flag-setting boundaries:

| Edge Case           | Register Values                  | Tests             |
|---------------------|----------------------------------|--------------------|
| Zero result         | Rn = 0, Rm = 0                   | Z flag set         |
| Max positive + 1    | Rn = 0x7FFFFFFF, Rm = 1          | V flag (overflow)  |
| Unsigned overflow   | Rn = 0xFFFFFFFF, Rm = 1          | C flag (carry)     |
| Negative result     | Rn = 0x80000000, Rm = 0          | N flag set         |
| All ones            | Rn = 0xFFFFFFFF                   | Various            |
| Alternating bits    | 0xAAAAAAAA, 0x55555555            | Bit pattern edge   |

#### Strategy 3: Randomised (Property-Based)

For each instruction class, generate N random register states and compare
outcomes. This catches encoding errors the structured tests miss.

```rust
fn gen_random_adds(rng: &mut impl Rng, count: usize) -> Vec<TestCase> {
    (0..count).map(|_| {
        let rd = rng.gen_range(0..8);
        let rn = rng.gen_range(0..8);
        let rm = rng.gen_range(0..8);
        TestCase {
            name: format!("ADDS R{rd}, R{rn}, R{rm} (random)"),
            opcodes: vec![0x1800 | (rm << 6) | (rn << 3) | rd],
            reg_pre: vec![
                (rn as u8, rng.gen()),
                (rm as u8, rng.gen()),
            ],
            ..TestCase::default()
        }
    }).collect()
}
```

### 7.4. Instructions Excluded from Single-Step Diffing

Some instructions cannot be meaningfully tested via GDB single-step:

| Instruction | Problem | Approach |
|-------------|---------|----------|
| WFI         | QEMU halts waiting for interrupt; GDB step may hang | Skip, or pre-pend interrupt |
| WFE         | QEMU halts waiting for event; same issue | Skip |
| SEV         | Side effect only (sends event); no visible state change | Skip (vacuous pass) |
| SVC         | Triggers exception; QEMU enters handler | Test via multi-step sequence |
| BKPT        | Triggers debug halt; QEMU stops differently | Skip |
| UDF         | Undefined; QEMU faults, our emulator NOPs | Skip until exceptions implemented |
| DMB/DSB/ISB | NOP in both; vacuous pass | Include but document as low-value |
| IT          | Requires multi-instruction sequence | Defer to harness Phase 2 |

## 8. Comparator

### 8.1. Module: `comparator.rs`

```rust
/// Result of comparing QEMU and emulator state.
pub struct DiffResult {
    pub test_name: String,
    pub passed: bool,
    pub reg_diffs: Vec<RegDiff>,
    pub flag_diffs: Vec<FlagDiff>,
    pub memory_diffs: Vec<MemDiff>,
}

pub struct RegDiff {
    pub reg: u8,
    pub qemu_val: u32,
    pub emu_val: u32,
}

pub struct FlagDiff {
    pub flag: char,     // 'N', 'Z', 'C', 'V', 'Q'
    pub qemu: bool,
    pub emu: bool,
}

pub struct MemDiff {
    pub addr: u32,
    pub qemu_val: u8,
    pub emu_val: u8,
}
```

### 8.2. Comparison Logic

```rust
fn compare(
    tc: &TestCase,
    qemu: &RegisterState,
    emu: &RegisterState,
    qemu_mem: &[(u32, u8)],
    emu_mem: &[(u32, u8)],
) -> DiffResult {
    // 1. Compare R0-R12 (respecting compare_mask.regs bitmask)
    // 2. Compare SP, LR (if mask set) — absolute values
    // 3. Compare PC as relative delta (see 8.3)
    // 4. Compare xPSR via per-instruction mask (see 8.4)
    // 5. Compare GE bits if mask says so
    // 6. Compare memory at check addresses
    // 7. DO NOT compare IPSR (exception number) — not writable via QEMU GDB
}
```

### 8.3. PC Comparison — Resolved Approach

QEMU and our emulator use different address spaces (QEMU: ssram-0 at
0x00000000; ours: SRAM at 0x20000000). Absolute PC values will always differ.

**Decision: compare PC as a relative delta.**

```rust
let qemu_pc_delta = qemu.pc.wrapping_sub(QEMU_TEST_SLOT);
let emu_pc_delta  = emu.pc.wrapping_sub(EMU_TEST_SLOT);
if qemu_pc_delta != emu_pc_delta { /* flag mismatch */ }
```

This correctly handles:
- **Non-branching instructions:** both advance PC by instruction size → delta = 2 or 4
- **Relative branches:** both compute same offset from PC → same delta
- **BL:** LR is also a relative address; compare `LR - TEST_SLOT` similarly
- **BX (register):** Register value is absolute. If the register was set to
  `TEST_SLOT + offset`, both will branch to `SLOT + offset` → same delta.
  But if the register contains a fixed address (e.g., 0x08000100), the
  branch targets differ. **For BX/BLX register tests, set the target register
  relative to the test slot address** so the delta comparison works.
- **POP {PC}:** Same as BX — ensure the stacked value is slot-relative.

For absolute-address tests (rare — most branch targets are relative or
register-based), mark `pc_relative: false` in the compare mask and use
instruction-specific comparison logic.

### 8.4. UNPREDICTABLE Flag Masking

Some instructions have architecturally UNPREDICTABLE flag updates. QEMU
produces specific values for these, but they are arbitrary — not reference.
The comparator must mask them out.

| Instruction | UNPREDICTABLE flags | xpsr_mask to use         |
|-------------|---------------------|--------------------------|
| MUL         | C, V                | `0xC000_0000` (N, Z only) |
| MULS (Thumb)| C, V                | `0xC000_0000` (N, Z only) |
| Most ALU    | (none)              | `0xF800_0000` (all flags) |
| MOV (high)  | (no flag update)    | `0x0000_0000`            |
| ADD (high)  | (no flag update)    | `0x0000_0000`            |

Each test generator sets `compare_mask.xpsr_mask` appropriately.

### 8.5. Memory Comparison for Load/Store

Both QEMU and the emulator use the same address offsets for load/store tests.
Test cases specify memory addresses as offsets from a test scratch area:

- **QEMU:** `QEMU_TEST_SCRATCH + offset`
- **Emulator:** `EMU_TEST_SCRATCH + offset` (= `0x2000_0200`)

The comparator reads memory from both sides at the respective absolute
addresses and compares byte values.

## 9. Test Runner (`qemu_diff.rs`)

### 9.1. Binary: `crates/mdrp2354-test-harness/src/bin/qemu_diff.rs`

```rust
fn main() {
    // 1. Parse args (filter pattern, random seed, verbosity)
    let args = Args::parse();

    // 2. Spawn QEMU
    let mut qemu = QemuProcess::spawn(&args)?;

    // 3. Connect GDB client
    let mut gdb = GdbClient::connect("localhost:3333", Duration::from_secs(5))?;
    gdb.handshake()?;

    // 4. Initial QEMU setup (write vector table once)
    setup_qemu_initial(&mut gdb)?;

    // 5. Create emulator runner
    let mut emu = EmuRunner::new();

    // 6. Generate test cases
    let tests = test_gen::generate_all(&args);

    // 7. Run tests
    let mut results = Vec::new();
    for tc in &tests {
        let result = run_one_test(&mut gdb, &mut emu, tc);
        results.push(result);
    }

    // 8. Report
    report(&results, &args);

    // 9. Cleanup
    gdb.kill();
    qemu.kill();

    // 10. Exit with error code if any failures
    if results.iter().any(|r| !r.passed) {
        std::process::exit(1);
    }
}
```

### 9.2. Single Test Execution Flow

```rust
fn run_one_test(
    gdb: &mut GdbClient,
    emu: &mut EmuRunner,
    tc: &TestCase,
) -> DiffResult {
    // ── QEMU side ──────────────────────────────────────────────
    // 1. Write instruction bytes to TEST_SLOT
    let instr_bytes = opcodes_to_bytes(&tc.opcodes);
    gdb.write_mem(TEST_SLOT, &instr_bytes);

    // 2. Write BKPT after instruction
    gdb.write_mem(TEST_SLOT + instr_bytes.len() as u32, &[0x00, 0xBE]);

    // 3. Set up registers (defaults + overrides)
    setup_qemu_regs(gdb, tc);

    // 4. Set up memory preconditions
    for &(addr, val) in &tc.memory_pre {
        gdb.write_mem(addr, &[val]);
    }

    // 5. Single-step
    gdb.step();

    // 6. Read post-state
    let qemu_regs = gdb.read_all_regs();
    let qemu_mem: Vec<(u32, u8)> = tc.memory_check.iter()
        .map(|&addr| (addr, gdb.read_mem(addr, 1)[0]))
        .collect();

    // ── Emulator side ──────────────────────────────────────────
    // 7. Set up emulator state
    emu.setup(tc);

    // 8. Execute
    let emu_state = emu.execute(tc);

    // 9. Read emulator memory post-state
    let emu_mem: Vec<(u32, u8)> = tc.memory_check.iter()
        .map(|&addr| (addr, emu.bus.read8(addr)))
        .collect();

    // ── Compare ────────────────────────────────────────────────
    compare(tc, &qemu_regs, &emu_state, &qemu_mem, &emu_mem)
}
```

### 9.3. Error Handling and Robustness

- **QEMU crash:** If GDB connection drops, log the test that caused it,
  respawn QEMU, reconnect, continue from the next test.
- **QEMU timeout:** If single-step doesn't return within 5 seconds, treat
  as QEMU hang. Kill and respawn.
- **BKPT hit instead of step-stop:** This means the instruction branched
  into our BKPT. Log it — this is a valid test outcome to diff (it means
  the instruction behaved like a branch).

## 10. Performance Considerations

### 10.1. Expected Throughput

Per-test cost (using `G` packet for register setup, TCP_NODELAY enabled):
- GDB write instruction + BKPT: ~2 packets = ~0.2ms
- GDB write all registers (`G`): ~1 packet = ~0.3ms
- GDB set up memory preconditions: ~1-5 packets = ~0.5ms
- GDB single-step: ~1 packet + QEMU exec = ~0.5ms
- GDB read all registers (`g`): ~1 packet = ~0.2ms
- Emulator execution: ~0.001ms (negligible)
- **Total: ~1.7ms per test (best case), ~5ms (Windows with Nagle jitter)**

For 2,500 implemented tests: **~4-12 seconds.** Acceptable for CI.

**Windows caveat:** Even with `TCP_NODELAY`, Windows localhost sockets can
exhibit 1-2ms jitter per round-trip due to kernel scheduling. The estimates
above assume best-case; real-world may be 2-3x slower. Still under 30 seconds
for the full suite.

### 10.2. Optimisations (If Needed)

1. **Skip unchanged registers:** Track which registers changed from defaults,
   write only those via `P` packets instead of full `G`. Most tests set 2-3
   registers — saves ~0.2ms per test when most regs are at defaults.
2. **Parallel QEMU instances:** Run multiple QEMU instances on different ports,
   partition tests across them. Linear speedup.
3. **QEMU plugin API (v2):** For a future version, a QEMU TCG plugin that
   dumps register state via shared memory or pipe would eliminate TCP overhead
   entirely. ~100x faster than GDB RSP. Requires a C plugin compiled against
   QEMU headers — more complex build but worth it if test volume grows.
4. **Result caching:** Cache `(TestCase hash → QEMU RegisterState)` on disk.
   Skip QEMU for cached tests during development. Invalidate on QEMU version
   change (include QEMU version in cache key).

## 13. Resolved Design Decisions

These were open questions during drafting. Resolved during review.

| # | Question | Resolution | Section |
|---|----------|------------|---------|
| 1 | Address space mismatch | Compare PC/LR as relative deltas from test slot | 8.3 |
| 2 | IT block testing | Deferred to harness Phase 2; requires emulator IT support first | 7.4 |
| 3 | Exception testing | Out of scope for single-step harness; needs multi-step sequences | 7.4 |
| 4 | Caching QEMU results | Yes, with QEMU version in cache key. Build in v2 | 10.2 |
| 5 | FPU comparison | Bit-exact (IEEE 754, same rounding mode) | N/A |
| 6 | UNPREDICTABLE flags | Per-instruction xpsr_mask in CompareMask | 8.4 |
| 7 | WFI/WFE via GDB step | Skip these instructions | 7.4 |
| 8 | GDB register indices | Discover via target XML, not hardcode | 4.3 |

### Remaining Open Questions

1. **PC-reading instructions.** Instructions that encode R15 as a source
   register read `PC + 4` (Thumb convention). Does our `execute_one()` set
   `regs.r[15]` such that this works correctly, or only `read_pc()`? Need to
   audit the decoder for instructions that access R15 via `self.regs.r[15]`
   vs `self.read_pc()`. Generate specific test cases for PC-as-source.

2. **Multi-step test cases.** The current design is single-instruction.
   Some constructs (IT blocks, exception entry/return, LDM/STM interleaved
   with interrupts) need multi-step. Design a `steps: usize` field in
   TestCase for Phase 2 of the harness.

3. **QEMU bugs.** When we find a case where QEMU disagrees with the ARM
   ARM, what's the process? See Section 14 (Triage Protocol).

## 14. Triage Protocol

When QEMU and our emulator disagree on a test case:

### 14.1. Step 1: Verify the encoding

Confirm the opcode bytes are correct. Disassemble with `arm-none-eabi-objdump`
or manually decode against the ARM Architecture Reference Manual encoding
tables. Encoding bugs in the test generator produce misleading failures.

### 14.2. Step 2: Check for UNPREDICTABLE

Look up the instruction in the ARM ARM. If the result or specific flags are
marked UNPREDICTABLE, the disagreement is expected. Add the appropriate mask
to the test case and move on.

### 14.3. Step 3: Manual ARM ARM lookup

Read the pseudocode in the ARM Architecture Reference Manual for the specific
instruction variant. Trace through the pseudocode by hand with the test's
preconditions. Determine the correct result.

### 14.4. Step 4: Determine who's wrong

| Situation | Action |
|-----------|--------|
| Our emulator is wrong | Fix the emulator |
| QEMU is wrong | File QEMU bug, add test to skip list with comment |
| Both wrong | Fix ours, file QEMU bug |
| Ambiguous (ARM ARM unclear) | Test on real hardware (Layer 3) |

### 14.5. Skip list

Maintain a skip list of test cases where QEMU is known to be wrong:

```rust
/// Tests skipped due to known QEMU bugs.
/// Each entry: (test_name, qemu_bug_url, description)

    // Example: ("MUL R0, R1 (carry)", "https://...", "QEMU sets C flag on MUL")
];
```

This keeps the harness green while documenting known QEMU issues.

## 15. Implementation Phases

Build the harness incrementally, not all at once:

### Phase A: Minimal viable harness (implement first)

- `gdb_client.rs`: connect, handshake, `g`/`G`/`m`/`M`/`s`/`P` packets
- `qemu_process.rs`: spawn, kill, Drop guard
- `test_case.rs`: TestCase, CompareMask, RegisterState structs
- `comparator.rs`: register + flag diff with masking
- `emu_runner.rs`: drive CortexM33 for a TestCase
- `test_gen.rs`: ONE generator (e.g., `gen_add_sub_reg`) as proof of concept
- `bin/qemu_diff.rs`: orchestrator, text output
- **Goal: end-to-end diff working for one instruction class**

### Phase B: Full Thumb-16 coverage

- All Thumb-16 test generators (matching the 62 existing hand-written tests)
- Edge-case batteries for every implemented instruction
- Randomised tests (100 per instruction class)
- JSON output for CI
- **Goal: replaces/supplements hand-written tests for Thumb-16**

### Phase C: Thumb-32 coverage (as emulator grows)

- Add Thumb-32 generators as instruction classes are implemented
- Multi-step test cases for IT blocks (after emulator IT support)
- **Goal: grows with the emulator**

### Phase D: Advanced features (v2)

- QEMU result caching
- Parallel QEMU instances
- QEMU plugin API (eliminate GDB overhead)
- Exception-triggering test sequences
- FPU register diffing
