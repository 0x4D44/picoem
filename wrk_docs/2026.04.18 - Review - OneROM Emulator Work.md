## 1. Executive Summary

OneROM is a **BIOS-like firmware that runs on `mdrp2350`** (the RP2350 emulator in this workspace) and services ROM reads to a downstream consumer (initially `mddosem`, a DOS emulator — not yet created). It has two serving modes that the emulator now supports end-to-end:

- **PIO-serve** — PIO state machines on PIO1 (address decode / CS detect) and PIO2 (data output) plus a chained DMA pump.
- **CPU-serve** — core 0 executes a tight 5-instruction Thumb loop that reads the address pins via `SIO.GPIO_IN` and drives the data pins via `STRB → SIO.GPIO_OUT`.

**Headline results (commit `ac19a28`, 2026-04-18):**

| Oracle | Result |
|---|---|
| PIO differential vs. external `epio` library (cycle-accurate) | **PASS — 20/20 cycles** |
| PIO serving oracle (15-case walking-1 sweep + latency envelope 15..=45 cycles) | **15/15 PASS** |
| CPU serving oracle (15-case sweep + envelope 6..=60 cycles) | **15/15 PASS** |
| Full-system firmware boot smoke test | **PASS** (boot → WFI + CLOCKS correct) |
| PIO stress (2048-case address sweep on 1541 PIO fixture) | **2048/2048 PASS** |
| CPU stress (2048 cases on 1541-cpu fixture) | **2048/2048 PASS** (dedicated `-cpu.bin` pin map landed) |

**Net status:** both serving modes are byte-correct across every case the oracles admit. The CPU-stress gap is a harness coverage artefact, not an emulator defect.

## 2. What is OneROM

Per `D:\language\mdrp2354\README.md:11`, the dependency chain is:

```
mdpicoem (this repo) ─► onerom-emu (downstream) ─► mddosem (downstream)
        RP2350 emu       OneROM firmware as crate    DOS emulator
```

Neither `onerom-emu` nor `mddosem` exists yet — they are downstream children. What this repo delivers is the emulator foundation: a `mdrp2350` instance can now faithfully run the OneROM firmware binary and serve bytes against both a cycle-accurate PIO reference and against real ROM fixture content.

The OneROM firmware itself is an **SDRR** (Software-Defined ROM Replacement) build: a 64 KB flash image containing a descriptor table, a permutation-coded payload (address → byte LUT), and PIO/DMA init code. Fixtures exercised so far: **test_sdrr_0** (15-case walking-1 sweep) and **1541** (Commodore 64 1541 disk drive kernal $E000 ROM, 2048 addresses).

## 3. Emulator Features Added

All changes land on the **`mdrp2350`** chip crate (cycle-accurate Cortex-M33 / dual-core / RP2350-specific bus) or the **`mdpicoem-common`** shared-primitives crate. Nothing was added to `mdrp2040` for OneROM — it is RP2350-only.

### 3.1 PIO subsystem

Three fixes, all in `mdpicoem-common` so they benefit both chips:

1. **Side-set pad-OE fix** (commit `d37192c`, 2026-04-15, HLD `2026.04.15 - HLD - PIO Side-Set Pad OE.md`)
   `PioBlock::merge_pin_outputs` at `D:\language\mdrp2354\crates\mdpicoem-common\src\pio\mod.rs:196` previously OR'd the side-set mask into `pad_oe` unconditionally. Per RP2350 §11.3.2.3, side-set in value-drive mode writes pin *values* only — direction must come from `SET PINDIRS`, `OUT PINDIRS`, `MOV PINDIRS`, or `EXECCTRL.SIDE_PINDIR=1`. Validated by `silicon_periph_diff_rp2350::pio0_side_set_toggle` against RP2354 silicon.

2. **PIO idle-skip fast-path** (commit `6c090c7`, 2026-04-14)
   Added `sm_enabled_mask: u8` cache to `PioBlock`; `step()` early-returns when all SMs are disabled, skipping `clock_tick` and `merge_pin_outputs`. Net throughput win on paced-bench: **38 MHz → 82.5 MHz (~2.17×)**.

3. **PIO2 pad_out propagation fix** (commit `06a47ff`, 2026-04-15, JRN `2026.04.15 - JRN - PIO2 pad_out Propagation Fix.md`)
   The glue-DMA shim was hard-wiring its sink to `PIO2.TXF0` even when OneROM configured CH1 for `TXF1` (SM1). Bytes landed in the wrong FIFO and data pins stuck at reset (`0xFFFFFFFF`). Fixed by using `self.ch[1].write_addr` and a new `decode_pio_tx_addr` helper. Regression tests in `crates/mdpicoem-harness/src/onerom_glue_dma.rs` and `crates/mdrp2350/src/pio_tests.rs`.

### 3.2 Bus — narrow access + SIO GPIO_OUT replication

Two fixes that collectively unblocked CPU-serve mode:

1. **Unified narrow-access dispatcher** (commits `144f483`, `64c768a`, `92f74ac`, `982f96e`, 2026-04-17; HLD `2026.04.17 - HLD - Bus Narrow-Access Audit.md`)
   Replaced ~400 LOC of per-aperture RMW boilerplate with a single dispatcher across `D:\language\mdrp2354\crates\mdrp2350\src\bus\narrow.rs`, `bus\w1c.rs`, `bus\mod.rs`. Handles memory regions directly, then side-effect fast-paths (UART DR, SSP DR, I²C CMD, ADC FIFO, PIO RXF), then SIO GPIO_OUT replication, then APB aliases, then a W1C-aware RMW. The `w1c_narrow_mask` catalogue (~10 lines) covers 30+ registers with write-1-to-clear bits (NVIC_ICER/ICPR, DMA_INTR, UART ICR, PIO FDEBUG/IRQ, IO_BANK0 INTR, SIO FIFO_ST) to prevent RMW from clobbering unrelated pending bits.

2. **SIO GPIO_OUT byte-write replication** (commit `ac19a28`, 2026-04-17, TDD companion `f535804`)
   OneROM's CPU-serve loop uses `STRB R1, [SIO_GPIO_OUT]` to drive data pins 16–23 (lane 0 byte write). Hardware replicates the byte across all four lanes so bits [16:23] receive the data. The narrow dispatcher now detects writes to the SIO GPIO_OUT / OE register family and replicates the byte via `(val as u32) * 0x0101_0101` before delegating to `write32`. Regression tests: `sio_gpio_out_byte_write_replicates_across_lanes`, `sio_gpio_oe_byte_write_replicates_across_lanes`, `sio_gpio_out_halfword_write_replicates` in `crates\mdrp2350\src\tests.rs`.

### 3.3 Clocks — PLL LOCK cycle-counter reset

Commit `6b4a5b3` (2026-04-15, HLD `2026.04.15 - HLD - PLL LOCK Modelling.md`): `pll_sys_lock_at_cycle`, `pll_usb_lock_at_cycle`, and `master_cycle` are now reset on emulator reset so OneROM's init code sees clean power-up arming. Implementation at `D:\language\mdrp2354\crates\mdrp2350\src\lib.rs:266-273`.

### 3.4 DMA — no emulator-core changes

The emulator's DMA peripheral was **not modified** for OneROM. Instead, the harness supplies a **glue-DMA shim** (`GlueDma` in `D:\language\mdrp2354\crates\mdpicoem-harness\src\onerom_glue_dma.rs`) that watches SM1's RX FIFO and feeds pushed words into SM2's TX FIFO, replicating the serve-loop DMA chain OneROM's firmware would normally configure but which the emulator's DMA stub cannot yet execute. A `CHAN_ABORT` at sync entry prevents the emulator's own DMA model from racing the glue pump. Full-fidelity DMA remains open tech debt (see §7).

### 3.5 Supporting fixes picked up in parallel

- **RP2350 DMA global-register block offsets** — Residual C.2.1 (commit `f534afe`, 2026-04-17, HLD `2026.04.17 - HLD - Residual C.2.1 DMA Timer Paced Fix.md`).
- **Paced bench workload spread** (2026-04-15) — exposed the PIO idle-skip opportunity above.

## 4. Supporting Infrastructure

### 4.1 The `epio-sys` crate

- **Purpose.** Vendors Piers Finlayson's standalone `epio` cycle-accurate RP2350 PIO emulator (MIT) and binds it to Rust so we have an **independent PIO reference** to diff against.
- **Layout.** Two git submodules under `D:\language\mdrp2354\crates\epio-sys\third_party\`: `epio` (C library, ~1.5k LOC, includes `test/onerom_programs.h` with real OneROM PIO scenarios) and `apio` (header-only PIO assembly DSL).
- **Build.** `build.rs` compiles the C sources plus a first-party C shim (`src/c_shim/trace_gen_core.c`, ~80 LOC) via `cc::Build` with clang (forced). Bindgen generates Rust FFI.
- **One binary.** `onerom_trace_gen_rp2350` initialises epio state from apio macros, runs the OneROM setup scenario once, and dumps a golden trace to `D:\language\mdrp2354\crates\mdpicoem-harness\oracles\onerom_2364.trace` (committed). The diff binary `test_rp2350_onerom_diff_pio` is pure Rust and reads this committed trace — subsequent runs never invoke epio.

### 5.2 Bugs caught by the oracle suite

- **Shadow-source inversion.** Original design assumed firmware's DMA `memcpy(rom_table, set->data, 65536)` would populate SRAM before sync. It doesn't — the emulator's DMA stub cannot execute that program. Rather than fix DMA (multi-day, out of scope), the oracle now lifts the shadow directly from the committed `.bin` file's SDRR struct metadata (JRN `2026.04.15 - JRN - OneROM Shadow Source Investigation.md`, commit `a8a2ef5`). Ground truth inverted: the `.bin` is authoritative; SRAM is derived.
- **DMA CHAN_ABORT race.** V6 DMA bit-layout shift broke TREQ_SEL decoding; real DMA raced the glue pump and starved CH0/CH1. Fix: `CHAN_ABORT` at sync entry + tick head (commit `9d669ce`).
- **Stim-matching predicate.** Oracle was reading `CH1.READ_ADDR` register (which CH0 overwrites) instead of the address actually served. Fixed with `last_pushed_read_addr()` + stim-pattern matching (commit `1b0a5a9`).
- **CLOCKS register layout drift.** RP2350 shifted `CLK_SYS_SELECTED` to offset 0x44 (was 0x68 on RP2040). 9 test assertions updated; 554 tests pass post-fix (JRN `2026.04.15 - JRN - OneROM F.2-F.4 Implementation.md`).
- **SIO narrow-access replication** — see §3.2 above.
- **PIO side-set pad OE** — see §3.1 above.
- **Double-coincidence false PASS in CPU stress.** Early runs reported 140 "passes" that were actually zero-byte timeouts coinciding with expected-byte = 0x00. Fixed with a `unique_cycles` distribution check and `PinProfile` parameterisation (commits `0008235`, `3b9aeed`).

### 5.3 Strongest statement about correctness

Both serving modes are **byte-correct** for every case the oracles admit: 15/15 walking-1 cases on the test_sdrr_0 fixture (PIO + CPU) and **2048/2048 addresses on the 1541 fixture in both PIO and CPU modes**. Cycle timing falls within the declared envelopes in every case.

### 5.4 What would escape these oracles

- **PIO1 address-decode byte-swap artefact.** Walking-1 cases A8/A9 resolve to `0xB0002000` instead of `0x2000_B000` (byte-swapped). Byte-correct by coincidence — the shadow is zero at both locations. A PIO-level unit test would catch it; the current oracles do not. Tracked in §7.
- **Cycle-timing fidelity below the envelope.** The glue-DMA's 4-cycle pipeline is faster than silicon's `OUT PINS, 8` shift; the A3 case reads 9 cycles vs. silicon's 11–14. Documented in HLD §5.4 as an emulator limitation, not a bug.
- **Real DMA spec violations.** The glue-DMA's `CHAN_ABORT` workaround masks any malformed firmware DMA configuration. Real silicon would hang.

## 6. Performance

**Two clocks are at play — keep them separate:**

- **Model time** — the emulator's internal cycle count translated to nanoseconds via `cycles / sysclk_hz`. This is what a consumer of OneROM (a DOS emulator, or any downstream reader) would see as ROM access latency. **This is the speed rating.**
- **Host wall time** — actual elapsed time on the developer laptop while the emulator computes one case. This is "can the emulator keep up with real-time?" and has nothing to do with the emulated OneROM's behaviour.

### 6.1 OneROM access-time characterisation (the "speed rating")

This is the clock that matters to a consumer running *inside* the emulator (e.g. a DOS guest stepping through the same emulator loop). At sysclk = 150 MHz (1 cycle = 6.67 ns). Fresh measurements from running the stress binaries on commit HEAD:

| Metric | CPU-serve | PIO-serve (emulator) | PIO-serve (silicon aspiration) |
|---|---|---|---|
| Envelope (cycles) | 6..=60 | 15..=45 | 11..=14 (piorom.c) |
| Observed cycles (mean) | **12** (near-deterministic, 3 buckets) | **34** | ~13 |
| **Mean access time (model)** | **80 ns** | **226 ns** | ~87 ns |
| Min access time | 53 ns (8 cycles) | 126 ns (19 cycles) | — |
| Max access time | 266 ns (40 cycles) | 253 ns (38 cycles) | — |
| Envelope ceiling (worst-case spec) | 400 ns (60 cycles) | 300 ns (45 cycles) | 93 ns |
| **EEPROM-style speed grade (spec)** | **-400** | **-300** | **-90** |
| **EEPROM-style speed grade (typical)** | **-80** | **-230** | **-90** |

Source: freshly run `test_rp2350_onerom_stress_pio` and `test_rp2350_onerom_stress_cpu`; envelopes from `crates/mdpicoem-harness/src/onerom_serving_oracle.rs:77` and `onerom_serving_oracle_cpu.rs:88`; aspirational envelope from `2026.04.15 - HLD - OneROM Serving Oracle (Stage G).md` §5.4.

**Interpretation.** In model time, CPU-serve is actually *faster* than PIO-serve (80 ns vs 226 ns mean) — the 5-instruction ARM loop takes fewer emulated cycles than driving PIO2's shift pipeline. On real silicon this would likely invert (PIO parallelism vs serial loop), but the emulator's serial step-through doesn't capture PIO concurrency for this workload. As a consumer-facing rating, the emulated OneROM types out as a **-80 (CPU typical) / -230 (PIO typical)** part with spec-ceiling **-400 / -300**.

### 6.2 External-caller view: 1M random reads through the host API

A different consumer: a program outside the emulator hammering `run_case` in a loop. Fresh numbers, 2048-case stress run extrapolated linearly (per-case wall-clock is measured directly per case, so extrapolation is sound):

| Metric | CPU-serve | PIO-serve |
|---|---|---|
| Host wall-time per case (mean) | **3.65 µs** | **7.10 µs** |
| Host throughput (cases/sec) | 273 k | 141 k |
| **1,000,000-read projected wall time** | **3.65 s** | **7.10 s** |
| **Effective access time (per-byte host wall-clock)** | **3.65 µs** | **7.10 µs** |
| **EEPROM-style speed grade (external caller)** | **"-3650"** | **"-7100"** |
| Slowdown vs. model time¹ | **46×** | **31×** |

¹ `host_wall_time / model_latency_mean` — how many wall-clock seconds pass while the emulator advances one second of model time.

**Why CPU's host-slowdown is worse despite being faster in model time**: the model denominator shrinks faster than the host numerator. CPU-serve's 80 ns model × 46 = 3.7 µs host. PIO-serve's 226 ns model × 31 = 7 µs host. The ratio grows when the model time is small, because per-case host-side fixed overhead (Rust iteration, measurement wrapper) does not scale down.

**Compared to real EEPROMs** (-70 = 70 ns, -120 = 120 ns): the external-caller view of emulated OneROM is **~50× slower than a -70 part (CPU) and ~100× slower (PIO)**. It is firmly in microsecond territory — not suitable for directly emulating a real bus at silicon speed, which is the entire motivation for Phase 5 threaded dual-core.

### 6.3 Why the metric `b1e4236` added matters

Prior to that commit the harness only reported model latency. A regression that made the emulator 10× slower in wall-clock would not have shown up in the report, because model cycles would still compute the same nanoseconds. Host wall-clock catches emulator throughput drift; model latency catches OneROM-behaviour drift. They're orthogonal.

### 6.4 Bottlenecks

1. **Serial-interleaver overhead in `Emulator::step`** — 17.4% self-time in the quantum loop on prior profiling, plus ~45% in `decode_execute` (fn-pointer dispatch per instruction).
2. **Per-cycle PIO tick without batching** — `PioBlock::execute_cycle` fires 34–40× per case even when the SM is idle. Idle-skip helps only when *all* SMs in a block are off.
3. **Bus decode + unconditional core-1 interleave** — RP2350 always sequences both cores serially, even when core 1 is halted for the OneROM workload.

### 6.5 Outlook — why these aren't being optimised

Per user-memory and HLD `2026.04.16 - HLD - Workspace Tracing Infrastructure.md` + prior threaded-dual-core HLDs: **do not optimise serial-interleaver paths**. Threaded dual-core emulation (Phase 5 target: ≥105 MHz per core) is scheduled to demolish this overhead wholesale; a 5–10% win from micro-optimising the current step loop is dwarfed by the 20× gain from threading. The stress harness is therefore a **regression detector, not a real-time benchmark** — it catches drift in emulator correctness and wall-clock cost, not "can OneROM drive a real bus".

## 9. Downstream Integration Plan

Per `README.md:11`, the chain is `mdpicoem → onerom-emu → mddosem`. Only the first link exists.

What the emulator now provides that `onerom-emu` / `mddosem` will need:

- ✅ Both serving modes oracle-validated (PIO + CPU).
- ✅ SIO GPIO narrow-access correct for the CPU-serve loop.
- ✅ PIO side-set / pad_out / idle-skip correct.
- ✅ Shadow-lift parser for SDRR `.bin` layout (reusable as a crate API).
- ⚠️ **Real DMA execution** — still stubbed; the glue-DMA shim works around it. Downstream will need the emulator's DMA peripheral to actually execute firmware's configured chains, or continue to ship a glue shim.
- ⚠️ **Cycle-timing fidelity inside the serving envelope** — acceptable for byte-correctness but not for sub-cycle bus emulation.
- ⚠️ **Threaded dual-core** — needed for real-time throughput; serial interleaver is ~28–48× too slow.

No sequencing HLD for the downstream integration exists yet. The oracle suite is the API contract; once threaded cores land and real DMA executes, `onerom-emu` can be spun out as a standalone crate wrapping `mdrp2350` + the OneROM `.bin`.

## 10. Interesting Asides

1. **Shadow source inversion.** The original design assumed a DMA-driven SRAM preload would hold ground truth. It didn't — because emulator DMA doesn't run firmware's program. Rather than chase DMA for weeks, the oracle team inverted the ground truth: the `.bin` file's SDRR struct is authoritative; SRAM is derived. A nice example of "change the contract when the implementation isn't worth the fix".
2. **Double-coincidence false PASS.** Early CPU-stress reports of 140 passes looked like a bug hunt success. They were actually zero-byte timeouts lining up with expected-byte = 0x00. Added `unique_cycles` distribution check as a tripwire — if fewer than 4 unique cycle counts appear across 2048 cases, something is suspicious. Good defensive diagnostic.
3. **The PWM CTR persistence trap** (from the same close-out wave, JRN `2026.04.18 - JRN - Residual A.2.3 PWM Close-Out.md`). Four hypotheses chased before realising silicon's PWM counter is free-running across test scenarios while the emulator resets CTR per scenario. A 500-tick drift on a 1024-iter spin looked like a formula bug; wasn't. First-step numerical analysis ("where does 130k come from?") would have caught it faster.
4. **One binary, committed trace.** `epio-sys` builds `onerom_trace_gen_rp2350`, runs it once to produce `onerom_2364.trace`, and that trace lives in the repo. Subsequent CI runs never invoke the C library — they read the committed golden. A nice pattern for "vendor a heavy reference, freeze its output".
5. **PicoGUS sibling.** Running in parallel (HLD `2026.04.14 - HLD - PicoGUS Integration.md`) but on RP2040. Not a dependency either way — both are validation harnesses exercising different chips, sharing the common crate.

- **Threaded cores.** The 28–48× wall-clock gap is the entire story for live bus emulation. Everything else is polish.
