# 2026.04.21 — HLD — Track A Probe-rs Attach Fix

Status: Signed off by lead 2026-04-21
Depends on: probe-rs 0.31.0 (pinned at crates/mdpicoem-harness/Cargo.toml:13)
Supersedes: none (new track)
Related: wrk_docs/2026.04.17 - LLD - RISC-V Probe-rs Attach Spike V1.md

## 1. Executive summary

Today's (2026-04-21) RP2354 silicon oracle runs panic inside probe-rs 0.31 at
`communication_interface.rs:474` — an `unreachable!()` in `select_ap_and_ap_bank`
that fires whenever the RP235x YAML-declared V2 AP for core 0 (`ApV2Address(0x2000)`) is
accessed while probe-rs's cached `SelectCache` is still `DPv1`. This happens
when DPIDR.version is read as anything other than exactly `3` (DPv3) during
`select_dp`, leaving the cache unupgraded. The bug is confirmed present in the
latest upstream (master, probe-rs crate ≤ 0.31.0 on crates.io; GitHub issues
#3872 and #3257, both open, no fix merged).

Proposed fix: pin probe-rs via `[patch.crates-io]` to a small local fork that
replaces the `unreachable!()` with a deferred DPv3 cache upgrade on first V2 AP
access. This unblocks the full silicon oracle suite without a workspace-wide
API bump, and carries zero blast radius beyond `crates/mdpicoem-harness`.

## 3. Root cause analysis

### 3.1 The panic site

`probe-rs-0.31.0/src/architecture/arm/communication_interface.rs:454-477`:

```rust
fn select_ap_and_ap_bank(
    &mut self,
    ap: &FullyQualifiedApAddress,
    ap_register_address: u64,
) -> Result<(), ArmError> {
    let dp_state = self.select_dp(ap.dp())?;
    ...
    match (ap.ap(), &mut dp_state.current_select) {
        (ApAddress::V1(port), SelectCache::DPv1(s)) => { ... }
        (ApAddress::V2(base), SelectCache::DPv3(s, s1)) => { ... }
        _ => unreachable!(
            "Did not expect to be called with {ap:x?}. This is a bug, please report it."
        ),
    }
    ...
}
```

The `unreachable!()` covers three cross-product combinations:
- `(V1, DPv3)` — SelectCache mismatched an ADIv5 AP to an ADIv6 DP.
- `(V2, DPv1)` — the case hitting us today: an ADIv6 AP hitting a pre-DPv3 cache.
- (The fourth combination `(V2, DPv3)` is the supported path.)

### 3.2 Why the cache stays DPv1

`DpState::new()` (line 155-162) always initialises `current_select` as
`SelectCache::DPv1(SelectV1(0))`. It is only upgraded to `DPv3` on fresh DP
insertion, at line 402-404:

```rust
if idr.version == DebugPortVersion::DPv3 {
    state.current_select = SelectCache::DPv3(SelectV3(0), Select1(0));
}
```

The version is read from DPIDR bits [15:12]. On RP2354 ADIv6 hardware this
should report `0x3`. When it does not — e.g. stale pipelined read, SWD line
glitch during the first `raw_read_register` after the alert sequence, or probe
overrun — `idr.version` becomes `DPv1`/`DPv2`/`Unsupported(x)`, the cache stays
`SelectCache::DPv1`, and any subsequent V2 AP access panics.

### 3.3 Why core 0 (V2 AP 0x2000) is touched regardless

The RP235x target YAML (`targets/RP235x.yaml:11-16`) hardcodes:

```yaml
cores:
  - name: core0
    core_access_options: !Arm
      ap: !v2 0x2000
  - name: core1
    core_access_options: !Arm
      ap: !v2 0x4000
```

`CombinedCoreState::memory_ap` (`core/core_state.rs:245-263`) resolves this
into `FullyQualifiedApAddress::v2_with_dp(Default, ApV2Address::new(0x2000))`
**without** consulting DP version. During
`Session::attach_arm_debug_interface` → `core.enable_arm_debug` →
`debug_core_start` → `interface.memory_interface(core_ap)` →
`select_ap_and_ap_bank`, we hit the panic with the YAML-hardcoded V2 AP while
the cache is still `DPv1` from the half-failed DPIDR read.

For `silicon_periph_diff_rp2350` the trigger is even earlier: standalone attach
calls `session.core(0)?` and the `Rp235x::reset_system` sequence eventually
reads/writes core-0's V2 AP inside `debug_core_start` on line 77 of
`rp235x.rs`. Same panic.

### 3.4 Why the wildcard warning is a red herring (but informative)

The warning fires at `config/registry.rs:246-252`. `"rp2350"` matches `RP235x`
via the wildcard `x`-rule in `match_name_prefix`. The registry then sets
`targ.name = package.to_string()` (line 255), so the resolved `Target` is
identical regardless of whether we pass `"rp2350"` or `"RP235x"`. The warning
is cosmetic; switching the string changes **no behaviour** — same YAML, same
debug sequence, same V2 APs. It does not fix this panic. (Confirmed by reading
`src/config/registry.rs:170-257` end-to-end.)

### 3.5 Why `probe_diff_rp2350` escapes

`probe_diff_rp2350` attaches once and then issues only ISA-level reads/writes
through `Core` (`MemoryInterface::read_word_32`, `write_core_reg`,
`read_core_reg`, `reset_and_halt`). The initial DPIDR read happens to succeed
on most fresh-from-power-up attach attempts — once the DPv3 cache is set,
every subsequent transaction works. The 4000/4000 PASS today is evidence that
the panic is not 100% deterministic on the **first** DPIDR read; it becomes
100% reproducible on standalone `silicon_periph_diff_rp2350` because that
binary's `run_scenario_with_retry` path stresses `reset_and_halt` per scenario,
each of which invokes `Rp235x::reset_system` → `perform_reset` → fresh DP state
(via disconnect/reconnect inside the rescue-reset sequence).

## 4. Options considered

### Option A — Upgrade probe-rs to 0.32+

Status: **not viable today.**

crates.io has nothing newer than 0.31.0 (2026-01-17). Master still contains
the `unreachable!()`. Neither issue #3872 nor #3257 has a linked fix PR. We
would have to wait for upstream resolution, and issue #3257 has been open
since April 2025.

### Option B — Switch chip string from `"rp2350"` to `"RP235x"`

Status: **no effect.**

`registry.rs:246-255` normalises both to the same `Target`. The wildcard
warning goes away; the panic does not. Verified by reading the registry
lookup code. Zero value except cleaner logs. Can be done as a drive-by if
desired, but does not fix anything and should not be confused with a fix.

### Option C — `[patch.crates-io]` our own probe-rs fork (chosen)

Status: **viable, bounded blast radius.**

Add to workspace `Cargo.toml`:

```toml
[patch.crates-io]
probe-rs = { path = "third_party/probe-rs-0.31.0-mdrp-patched" }
probe-rs-target = { path = "third_party/probe-rs-target-0.31.0" }  # only if required by version pinning
```

Vendor `probe-rs-0.31.0` under `third_party/` (aligned with the existing
`third_party/` directory convention) and apply a single surgical patch to
`src/architecture/arm/communication_interface.rs::select_ap_and_ap_bank`:

```rust
(ApAddress::V2(base), cache @ SelectCache::DPv1(_)) => {
    // RP2354-on-0.31 workaround (mdrp2354 Track A fix):
    // The initial DPIDR read occasionally returns version != 3 on the
    // RP2354 ADIv6 DP (see upstream issues #3872 / #3257). When that
    // happens the cache stays DPv1 but the YAML-declared V2 APs are still
    // addressed, which would hit the unreachable!() panic. Upgrade the
    // cache on first V2-AP access as a recovery path; the target really is
    // ADIv6 if V2 APs are declared in the YAML.
    tracing::warn!(
        "ApV2 access on DPv1 cache; upgrading to DPv3 (mdrp-patched workaround)"
    );
    *cache = SelectCache::DPv3(SelectV3(0), Select1(0));
    // Re-enter by falling through to the DPv3 arm on the next loop iteration.
    let SelectCache::DPv3(s, s1) = cache else { unreachable!() };
    let address = base.0.unwrap_or(0) + ap_register_address;
    s.set_addr(((address >> 4) & 0xFFFF_FFFF) as u32);
    s1.set_addr((address >> 32) as u32);
}
```

(Implementation agent will adapt to the exact code structure; the semantic
is: upgrade cache in-place + continue with the V2 path.)

Trade-offs:
- Tiny patch, easy to review and rebase.
- Zero API surface change — harness code is untouched.
- Requires vendoring probe-rs source (~4 MB) into `third_party/`.
- We own maintenance until upstream fixes it; easy to upstream as a PR
  closing #3872 once verified on hardware.

### Option D — Pre-read DPIDR ourselves before `auto_attach`

Status: **infeasible.**

`ArmCommunicationInterface` is crate-private on `DpState`/`SelectCache`; we
cannot manipulate the cache from user code. This would require the same
fork.

### Option E — Use JTAG protocol instead of SWD

Status: **out of scope.**

Pico probes speak CMSIS-DAP/SWD. Would require different probe hardware.

### Option F — Drop probe-rs entirely and use openocd or libgdb-RSP

Status: **major rework.**

Rejected; too invasive for a targeted bug fix.

### Chosen: Option C.

## 5. Does this fix `probe_diff_rp2040`?

**No.** RP2040 uses V1 APs (ADIv5) only; see `targets/RP2040.yaml` and the
RP2040 debug sequence in `src/vendor/raspberrypi/sequences/rp2040.rs`. The
`unreachable!()` panic cannot fire on RP2040 paths. The "An ARM specific
error occurred." message from `probe_diff_rp2040` is a separate failure —
most likely a transient SWD error or a Multidrop RESCUE_DP handshake issue
from RP2040's own rescue-reset sequence. **Track A does not cover it.** A
separate investigation is needed; recommend opening a short follow-up HLD
("Track A.1 — probe_diff_rp2040 attach diagnosis") after Track A lands.

### 7.3 What PASS looks like

- The `WARN ... Matching rp2350 based on wildcard` line may still appear (unless we also flip to `"RP235x"` — optional cosmetic change).
- When the workaround fires, a `WARN ... ApV2 access on DPv1 cache; upgrading to DPv3` line appears at most once per session in `RUST_LOG=warn`. If it fires many times per session, the patch is masking a deeper issue and we escalate.

Recommend adding a line to `RUNBOOK.md` under a new "probe-rs patch notes"
section listing the patched fork path and the sentinel WARN line so anyone
bumping probe-rs knows to verify the patch still applies.

## 8. Risks & rollback

### 8.1 Risks

- **The cache upgrade masks a deeper DPIDR-read bug.** If DPIDR really is
  returning version 1/2 because the silicon DP is in some odd state, forcing
  DPv3 may produce incorrect SELECT register writes downstream. Mitigation:
  emit the WARN above; treat more-than-once-per-session firing as a bug.
- **Vendored fork drift.** If we later bump probe-rs (e.g. 0.32 lands), the
  patch may need re-porting. Mitigation: keep the patch small and comment it
  with the upstream issue number; track #3872 in `tech_debt.md`.
- **Cargo.lock churn.** Vendoring a crate with many transitive deps can
  change the lockfile. Mitigation: vendor only `probe-rs` itself; leave
  `probe-rs-target` as-is unless the patched source demands a matching pin
  (check during implementation).
- **`patch.crates-io` + local path may invalidate the `sccache`/build-cache
  hit ratio.** Mitigation: `cargo clean -p probe-rs` and rebuild once after
  the patch lands; subsequent builds are normal.

### 8.2 Rollback

- `git revert` the commit that adds `[patch.crates-io]` + `third_party/probe-rs-...`.
- Lockfile reverts automatically.
- No code changes in `crates/` need reverting because no API surface changed.
