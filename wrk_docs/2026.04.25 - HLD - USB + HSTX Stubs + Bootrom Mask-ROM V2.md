# 2026.04.25 — HLD — USB + HSTX Stubs + Bootrom Mask-ROM (V2)

Iterates V1 (`2026.04.24 - HLD - USB + HSTX Stubs + Bootrom Mask-ROM.md`)
on review feedback. Material changes flagged inline as **(R)**.

## Goal

Close three remaining RP2350 firmware-fidelity gaps so that pico-sdk
firmware touching USB init, HSTX config, or bootrom service functions
executes to steady state in the emulator without faulting.

1. **USB** — register-surface stub (no protocol).
2. **HSTX** — register-surface stub (no pixel stream).
3. **Bootrom mask-ROM** — `rom_func_lookup`-resolved calls run their
   documented semantics by executing the real RP2354 bootrom binary
   plus a small PC-hook for the few functions whose dependencies we
   don't emulate.

**(R) Workload value** is uneven across the three:

- Component 3 (bootrom) is high-value: any pico-sdk firmware that calls
  `flash_range_program`, `connect_internal_flash`, or `reboot` blocks on
  this. OneROM and any future RP2350 firmware that touches flash falls
  in scope. (Note: PicoGUS is RP2040 only, not an RP2350 driver here.)
- Components 1 and 2 (USB/HSTX) are pre-emptive insurance: no current
  RP2350 workload in-tree is blocked by them. They land cheaply because
  RESETS / IRQ / DREQ wiring already exists for both. The bar for them
  is lower — if either turns out non-trivial, defer it.

Success criterion per component is "firmware exercising this subsystem's
init runs without asserting or entering a fault loop," measured by the
firmware tests listed in each Oracle section.

## Explicit non-goals

- USB protocol emulation, host mode, device enumeration, CDC passthrough.
- HSTX pixel-stream observability, DVI/DPI capture.
- BOOTSEL UF2 drive emulation — `reboot` with BOOTSEL flag shuts the
  emulator down cleanly; UF2 ingest stays out of scope.
- Secure-boot verification through the bootrom path.
- RISC-V Hazard3 bootrom path, but **(R)** the design must not regress
  Hazard3 execution — see "Hazard3 isolation" in Component 3.

No feature flags. No environment variables. No migration / back-compat.
The two new peripherals and the bootrom hook land directly in
`mdrp2350`.

## Stage 0 — Survey (cheap, do first; no code lands until it completes)

Stage 0 is the design's branch point. Five facts must be confirmed, each
recorded in the implementation journal with the exact answer and evidence.

**(R) Fact 1 — bootrom binary layout.** `roms/rp2350/bootrom-combined.bin`
is exactly 32 KB. `mdpicoem-common::memory::ROM_SIZE` is also 32 KB.
Required:

- Hex-dump the file. Where does the Arm bootrom image start and end?
  `arm-bootrom.dis` shows Arm Thumb code at offset 0; is the back half
  Arm Secure-only, RISC-V, or padding?
- If real silicon expects more than 32 KB of bootrom space and our
  `ROM_SIZE` truncates it, hook resolution fails — the table walk lands
  on bytes we never loaded. Confirm whether the loaded 32 KB is the
  complete Arm image or only one half of a dual-arch concatenation.
- Pin a SHA256 of the file in `roms/rp2350/bootrom-combined.bin.sha256`
  (sibling file). `Emulator::load_bootrom` (or its caller) asserts on
  mismatch.

If the answer is "the loaded 32 KB is incomplete," **stop and re-scope
Component 3** — V2 of this HLD assumes a self-contained 32 KB Arm
bootrom. The fallback path (write a Stage 0 V3 update) is documented in
"Stage 0 failure modes" below.

**Fact 2 — bootrom executes through `rom_table_lookup`.** Pico-sdk's
table-walk entry point is `rom_table_lookup_entry_point`, not
`rom_func_lookup` (the latter is the wrapper). The well-known pointer
table sits at the top of bootrom (offset 0x14 holds the pointer to the
function table per `arm-bootrom.dis:53-93`). **(R)** Stage 0 must answer:

- Run a minimal RP2350 firmware that invokes `rom_table_lookup_entry_point`
  with a known 4-char code (e.g. `'FC'` = `flash_connect`). Does it
  return cleanly?
- The bootrom's table-walk uses `rcp_count_set` (RCP coprocessor canary)
  at bootrom address 0x4c. Verify our RCP semantics tolerate this — if
  RCP locks out NS or panics on unexpected counter state, *every* lookup
  faults.
- **(R) End-to-end smoke**: invoke `flash_range_program` of a tiny
  pattern through the bootrom and verify the flash backing-store
  actually changes. Catalogue-only ("which 4-char codes are called") is
  not enough — the bootrom drives QMI, OTP, TRNG, SHA256 along the way,
  and any of those can hang or fault even when the dispatch is clean.

**Fact 3 — pinned register maps.** From RP2350 datasheet §Appendix A:

- USB control: `USBCTRL_REGS_BASE = 0x5011_0000` (16 KB region).
- USB DPRAM: `USBCTRL_DPRAM_BASE = 0x5010_0000`, exactly 4096 bytes
  (`0x1000`). Structured: 0x000..0x180 = buffer-control + setup-packet
  area, 0x180..0xFFF = endpoint data buffers.
- HSTX control: `HSTX_CTRL_BASE` on **APB**, expected `0x400C_0000`.
  Confirm — APB-side decoding is different from AHB-side.
- HSTX FIFO: `HSTX_FIFO_BASE` on **AHB-Lite** at `0x5060_0000`,
  separate fabric.

**(R) The APB-vs-AHB split for HSTX is load-bearing.** Confusing the two
silently routes FIFO writes to APB and faults. Pin both bases by reading
the datasheet, not by guessing.

**(R) Fact 4 — current bus-fault semantics on the new regions.** The
`Bus::read32`/`write32` fall-through for region `0x5*` currently fires
`set_bus_fault` (`crates/mdrp2350/src/bus/mod.rs:2748`), so any access
to USB or HSTX MMIO today HardFaults. Adding stubs *changes* fault
semantics. Stage 0 grep:

```
grep -nr "0x501[0-9]_" crates/mdrp2350/src/tests.rs
grep -nr "bus_fault.*0x50" crates/mdrp2350/src/
grep -nr "bus_fault.*0x400[cC]" crates/mdrp2350/src/
```

Any test asserting a bus fault on these addresses is direct prior art
that the stub will break — list them, decide whether to delete or
rewrite. **Most likely outcome**: zero such tests. But the design must
have looked.

**(R) Fact 5 — RESETS_POST_BOOTROM state.** `RESETS_POST_BOOTROM` at
`bus/mod.rs:224` records which peripherals are held in reset *after*
emulator boot. Confirm USBCTRL is in that set on real silicon (it is on
RP2040). The new USB stub must initialise behind that gate — reads
should return 0 via the existing `is_held_in_reset_base` guard until
firmware writes a 1 to `RESETS_RESET_CLR.USBCTRL`. Same check for HSTX.

### Stage 0 failure modes

Each fact has a defined fallback if it fails:

- **Fact 1 fails** (bootrom truncated by ROM_SIZE): bump `ROM_SIZE` *or*
  scope Component 3 to "no bootrom service emulation, just stub
  `rom_table_lookup_entry_point` to return null for unknown codes."
- **Fact 2 fails** (bootrom faults inside its own code): catalogue which
  peripheral access faults. If it's QMI/OTP, fix the peripheral first
  (separate HLD); Component 3 blocks on it.
- **Fact 3 fails** (no public datasheet base): defer the affected stub.
- **Fact 4 fails** (existing tests assert the bus-fault behaviour):
  rewrite or delete them; record the choice in the journal.
- **Fact 5 fails** (USBCTRL not in `RESETS_POST_BOOTROM`): adjust the
  RESETS table — but this is also a real bug in current emulator
  fidelity, fix it independently.

Stage 0 outputs: one journal entry per fact, with answers. **No code
commits land in Components 1, 2, or 3 until Stage 0 is signed off.**

## Component 1 — USB stub

### Scope

- `USBCTRL_REGS_BASE` at `0x5011_0000` — control/status registers.
- `USBCTRL_DPRAM_BASE` at `0x5010_0000`, 4096 bytes plain RAM. **(R)**
  Stored as a `Box<[u8; 4096]>` field on the new `UsbCtrl` struct; not
  shared with the main `Memory`. Reset clears only buffer-control region
  (0x000..0x180), per silicon — the data-buffer region (0x180..0xFFF) is
  *not* cleared.
- All control register writes accepted (default last-write-wins).

**(R) W1C status registers** (writes-1-to-clear, not last-write-wins):
`SIE_STATUS` and any other "interrupt status" register where pico-sdk
writes 1 to acknowledge events. Implementation: writes mask out the
W1C bits, reads always return 0 for those bits in this stub. The list
of W1C bits (`VBUS_DETECTED`, `BUS_RESET`, `TRANS_COMPLETE`, etc.) is
pinned from RP2350 datasheet §12.6.5 in the module docblock.

- Static "no device": bits enumerated above all read 0.
- `BUFFER_STATUS = 0`. `INTS = 0`, `INTR = 0`.
- NVIC IRQ_USBCTRL_IRQ (line 14, `irq.rs:61`) never asserts. Pico-sdk
  device-mode init is safe with this; host-mode init *will* hang
  (declared in Risks).

### Bus integration **(R)**

The new module must wire five points, not "one match arm":

1. New base const + match arms in `Bus::read32` / `write32` for both
   `0x5010_*` (DPRAM) and `0x5011_*` (regs). Note these are AHB region
   `0x5*`, currently a bus-fault fall-through; the new arms must be
   added *before* that fall-through.
2. Entry in `reset_bit_for_base` (`bus/mod.rs:255`) for both bases →
   `RESET_USBCTRL` (already declared, line 214).
3. `usbctrl: UsbCtrl` field on `Bus`; construction in `Bus::new`.
4. Narrow-access policy: registers are word-only. DPRAM allows
   byte/halfword (real silicon does). Add to the bus carve-outs at
   `bus/mod.rs:1647-1706`.
5. RESETS_POST_BOOTROM table includes USBCTRL (Stage 0 Fact 5
   confirms).

### Function shape **(R)**

Per `peripherals/mod.rs:1-23` and `peripherals/uart.rs:339,373,491`:
inherent methods, no trait. Pinned signatures:

```rust
impl UsbCtrl {
    pub fn new() -> Self;
    pub fn reset(&mut self);
    pub fn read32(&mut self, offset: u32) -> u32;
    pub fn write32(&mut self, offset: u32, value: u32, alias: u32, irqs: &mut u64);
    pub fn read_dpram(&self, offset: u32, size: u8) -> u32; // narrow
    pub fn write_dpram(&mut self, offset: u32, value: u32, size: u8);
}
```

No `tick` — the stub never produces events. `irqs: &mut u64` is the
out-mask convention for IRQ assertion (UART pattern); USB stub never
sets a bit.

### Oracle

- **Unit tests** in the module:
  - pico-sdk USB init sequence (writes to `USB_MUXING`, `USB_PWR`,
    `MAIN_CTRL`, `SIE_CTRL`) followed by `SIE_STATUS` read returns
    `VBUS_DETECTED=0`. No bus fault.
  - W1C round-trip: write 1 to a W1C bit, read back — must return 0.
  - DPRAM word/byte/halfword writes round-trip in the data-buffer
    region; reset clears only buffer-control area.
  - IRQ_USBCTRL_IRQ stays low across full init.
- **No silicon scenario** unless a stub-drift bug surfaces later.
  Silicon scenarios are 30-100 lines (`silicon_scenarios.rs:106-130`)
  and probe time is precious; not worth it for "no device, no IRQ."

Estimate: ~150 lines including W1C handling, DPRAM, and tests.

## Component 2 — HSTX stub

### Scope

- Two MMIO regions (Stage 0 Fact 3):
  - `HSTX_CTRL_BASE` on APB — lane config, FIFO-status, enable bit.
  - `HSTX_FIFO_BASE` on AHB at `0x5060_0000` — write-only FIFO port.
- **(R)** Implementation pattern: follow `peripherals/inert.rs` —
  `HashMap<u32, u32>` for stored values plus a small `match offset` on
  reads to override status fields. Estimate ~80 lines, not 180.
- Control writes accepted, last-write-wins. FIFO writes silently
  consumed (no queue, no backpressure, stays empty).
- FIFO status: `FIFO_EMPTY=1`, `FIFO_FULL=0`, `FIFO_LEVEL=0` static.
  **(R)** Risk: firmware that polls `FIFO_LEVEL > 0` (self-test pattern)
  will hang. Documented in Risks; not currently observed in any in-tree
  RP2350 firmware.
- Stub does **not** consume `CLK_HSTX` despite the clock being modelled
  on the CLOCKS side. No timing coupling.
- Participates in RESETS (`RESET_HSTX = 3`, `bus/mod.rs:171`); same
  five-point bus integration as Component 1.

### Function shape

Same convention as Component 1 — inherent methods, no trait.

### Oracle

- Unit test: pico-sdk HSTX init sequence (lane map writes, `EXPAND_*`,
  `CTRL.EN=1`, then 1024 FIFO words). Asserts: no fault, FIFO status
  reports empty, no IRQ.
- No silicon scenario.

Estimate: ~80 lines.

## Component 3 — Bootrom mask-ROM

### Approach

**Default path**: execute the real RP2354 bootrom binary
(`roms/rp2350/bootrom-combined.bin`, SHA256-pinned per Stage 0 Fact 1)
from ROM memory. Firmware's `rom_table_lookup_entry_point` walks the
real `rom_func_table` and dispatches into real bootrom code.

Functions touching only-emulated peripherals (SHA256, TRNG, XIP_CTRL,
QMI, DMA, OTP) execute verbatim — the bootrom is the implementation.
**(R) Conditional on Stage 0 Fact 2 end-to-end smoke**: if the bootrom
hangs or faults inside QMI/OTP/TRNG/SHA256 paths, those peripherals
need fixing first; Component 3 blocks on them rather than proceeding.

**Single PC hook, inlined.** **(R) No `BootromHookTable` struct.** The
minimum hook set after Stage 3.1 is expected to be one entry: the
BOOTSEL flavour of `reboot` (4-char code from Stage 3.1; pico-sdk uses
`'RB'` with a flag value, not `'UB'`). Implementation:

```rust
// On `Emulator::load_bootrom`, resolve once:
self.bootrom_reboot_hook_pc = resolve_rom_func(bootrom, b"RB");

// In CortexM33::step (and step_no_atomics, and debug_step):
if pc == self.bootrom_reboot_hook_pc {
    self.shutdown_requested = true;
    return; // don't fetch
}
```

If Stage 3.1 reveals a second hook is needed, promote to a small const
slice. If the catalogue grows past five hooks **and** the underlying
reason is unsupported peripherals (not "the function reboots us"), STOP
— fix the peripheral instead. Hook proliferation is a wallpapering
tool.

### Stage 3.1 — Survey

Run available RP2350 firmware (OneROM family + any future
bootrom-using smoke tests) with a PC trace scoped to the ROM range.
For each call into ROM:

- Record the 4-char code (read from R0/R1 at `rom_table_lookup_entry_point`).
- Record whether the call returns cleanly, hangs, or faults.
- Catalogue grouped by category: "needs hook" (semantics depend on
  peripherals we don't have), "needs peripheral fix" (faults inside an
  emulated peripheral), "works" (no action).

Output: journal entry with the catalogue. Drives Stage 3.2 scope.

### Stage 3.2 — Inline hook

Land the single inline `if pc == self.bootrom_reboot_hook_pc` check at
the entry of all three step paths: `step`, `step_no_atomics`,
`debug_step` (`crates/mdrp2350/src/core/mod.rs:383, 460, 486`).

**(R) Hot-path cost gate**: before merge, run `paced_bench_rp2350`
before/after; throughput regression must be <1%. Recent
`ede95a1` (17% step_n speedup from gating diag counters) shows this
loop is cost-sensitive.

**(R) Hazard3 isolation**: the bootrom hook fires only when the
fetching core is the Cortex-M33. Hazard3's RV step path does not check
the hook table. (V2 deferral of RV is real — but the design must not
let an RV fetch into a hooked Arm PC silently execute Arm semantics.)

**(R) Soft-reboot / reload**: hook resolution recomputes on every
`Emulator::load_bootrom` call (`lib.rs:478` + downstream). If firmware
reboots and the host reloads bootrom bytes, the hook PC may shift; the
table is rebuilt.

**(R) Decode-cache invalidation**: hook handlers that *write to ROM or
flash* (none in the V2 hook set, but required for any future
`flash_range_program` hook — which we don't expect to need since real
bootrom does this) must call `bus.invalidate_decode_cache_*`. Not
applicable to the `reboot` hook.

**(R) Secure / Non-Secure**: the bootrom address is the same in both
worlds (no aliasing). Hook fires regardless of SAU state. If Stage 0
Fact 2 reveals NS firmware enters the bootrom through a different
path, address this in V3.

### Files

- `crates/mdrp2350/src/bootrom_hooks.rs` — NEW. Two functions:
  `resolve_rom_func(bootrom: &[u8], code: &[u8; 4]) -> Option<u32>` and
  the inline `Emulator::check_bootrom_hook(pc) -> bool`.
- One PC-equality check inserted in three step entry points.
- `Emulator::load_bootrom` adds a SHA256 assert + a
  `resolve_rom_func(b"RB")` call to populate the hook PC.

### Oracle

- **Unit test**: load bootrom, call `rom_table_lookup_entry_point('FC')`
  from a tiny ARM image, jump to returned PC, assert clean return and
  expected QMI/XIP_CTRL state. **(R)** This implicitly tests Stage 0
  Fact 2 — flag if the unit test is hard to write because Stage 0
  smoke didn't actually pass.
- **Integration test**: ARM firmware that calls `flash_range_program`
  with a 16-byte pattern at offset 0x1000 in flash. Verifies flash
  backing matches the pattern after the call returns.
- **`reboot` hook test**: ARM firmware that calls `reboot` with the
  BOOTSEL flag; emulator's `shutdown_requested` becomes true.

### Done condition

- All Stage 3.1 catalogue entries are in one of the three categories
  with a recorded resolution.
- Hot-path microbench within 1% of pre-hook throughput.
- The integration test (`flash_range_program`) and the `reboot` test
  pass.

If Stage 3.1 reveals a function in "needs peripheral fix" category, that
function does NOT block Component 3 closure — it spawns a new HLD for
the peripheral fix.

## Risks (consolidated)

- **(R) Stage 0 might reveal the bootrom binary is incomplete.** If the
  loaded 32 KB is half of a 64 KB image, every hook PC is wrong.
  Mitigation: Stage 0 explicit fact + fallback path.
- **(R) Bootrom faults inside QMI/OTP/TRNG/SHA256 under its own call
  patterns.** Our peripheral models pass register-level tests but might
  not survive the bootrom's exact polling sequences. Mitigation: Stage 0
  end-to-end smoke is mandatory before 3.2.
- **(R) RCP coprocessor state on bootrom entry** — `rcp_count_set` at
  bootrom 0x4c is on the table-walk hot path; if our RCP model rejects
  the state, every lookup faults. Mitigation: Stage 0 Fact 2 covers it.
- **Bootrom version drift** — pin SHA256 in `roms/rp2350/`; any refresh
  is an explicit commit.
- **Hot-path regression from hook check** — gated by paced_bench
  before/after; budget <1%.
- **Permanently-low USBCTRL IRQ** — safe for device-mode init only;
  host-mode init blocks on `BUS_RESET`. Document in module docblock.
- **HSTX FIFO_LEVEL=0 forever** — firmware that polls for `LEVEL > 0`
  hangs. Documented; no in-tree RP2350 firmware does this today.
- **(R) Adding USB/HSTX changes existing bus-fault semantics** — Stage 0
  Fact 4 grep catches any test that depends on the fault.

## Sequencing and versioning

Order, each a separate commit:

1. Stage 0 survey journal — five facts answered, no code.
2. **(R) Decision point**: based on Stage 0 outputs, confirm V2 design
   still applies. If a fact failed, revise before continuing.
3. Component 1 (USB stub) — `mdrp2350` minor bump.
4. Component 2 (HSTX stub) — `mdrp2350` minor bump.
5. Stage 3.1 bootrom call survey — journal only, no code.
6. Component 3 inline `reboot` hook + integration test — `mdrp2350`
   minor bump.
7. Additional hooks per Stage 3.1 catalogue, if any. Each one decided
   on against the "fix the peripheral instead" alternative.

No rollback. No coexistence.

## Appendix — V1 → V2 changes summary

- Stage 0 expanded from 3 facts to 5; each has a defined failure mode.
- Bus integration sub-section added per stub (5 wiring points each).
- Function-shape signatures pinned: inherent methods (no
  `Peripheral` trait — that name was wrong); explicit `(offset, value,
  alias, &mut u64 irqs)` shape.
- `BootromHookTable` struct removed; replaced by single inline PC check.
- Hot-path cost gated by paced_bench microbench, <1% budget.
- Hook fires from all three step entry points.
- Hazard3 isolation, soft-reboot reload, decode-cache invalidation,
  Secure/NS execution all addressed explicitly.
- USB DPRAM size pinned at exactly 4096 bytes; W1C semantics for
  `SIE_STATUS` called out.
- HSTX bases split APB/AHB; stub follows `inert.rs` HashMap pattern.
- Workload-value framing made explicit: bootrom is high-value,
  USB/HSTX are pre-emptive.
- Stage 3.2 done condition + stop condition pinned.
- `reset_to_usb_boot` example replaced with `reboot` (the actual RP2350
  4-char code per pico-sdk).
