# HLD — mdrp2040 MOV PC / ADD PC LSB fix (Phase 4)

Date: 2026-04-15
Journal: `wrk_journals/2026.04.15 - JRN - PicoGUS SDK Panic Debug.md`
Predecessors: Phase 1 VTOR write (22135ff), Phase 2 PPB mask/pattern (34d7d6a)

## 1. Problem

After the Phase 2 PPB fix, real PicoGUS v4.0.0 firmware now stalls at
cycle 43929 (was 42569). Phase 3 diagnosis pinned the cause in
mdrp2040: `MOV PC, Rm` and `ADD PC, Rm` raise `Fault::InvalidEpsr`
when the destination value has LSB=0. gcc's switch-statement jump
tables in `_vfprintf` load even-aligned label addresses from a literal
pool and branch via `mov pc, r3`, tripping the fault. Real silicon
handles it fine. mdrp2350's reference impl at
`crates/mdrp2350/src/core/execute.rs:361-388` is already correct.

## 2. Spec reference

ARMv6-M ARM DDI 0419E §A5.1.2 defines three separate PC-write
pseudocode functions:

- **`ALUWritePC(addr)`** — used by `MOV Rd, Rm` and `ADD Rdn, Rm`
  when `Rd == 15`. Defined as `BranchWritePC(addr)`, which simply
  calls `BranchTo(addr<31:1>:'0')` — the LSB is masked, never
  checked. No fault path.
- **`BXWritePC(addr)`** — used by `BX` / `BLX` / `BLX Rm`. Checks
  `addr<0>`; if it is 0 in Thumb state, UsageFault (INVSTATE) on
  M3/M4 or HardFault on M0+. Correctly faults on even LSB.
- **`LoadWritePC(addr)`** — used by `POP {PC}` / `LDR PC, ...`.
  Defined as `BXWritePC(addr)`. Also correctly faults on even LSB.

The overstrictness is confined to the two ALUWritePC callers. BX,
BLX, BLX Rm, and POP-to-PC are independent and already correct.

## 3. Fix (code)

`crates/mdrp2040/src/core/execute.rs`:

- **Lines 378-384 (ADD PC):** delete the `if result & 1 == 0 {
  set_pending_fault; return 1; }` branch. Keep
  `self.regs.set_pc(result & !1); return 3;`.
- **Lines 404-410 (MOV PC):** delete the `if val & 1 == 0 { ... }`
  branch. Keep `self.regs.set_pc(val & !1); return 3;`.

Post-fix mdrp2040 matches mdrp2350's special-data ADD/MOV paths.

## 4. Test plan

`crates/mdrp2040/src/tests.rs`:

- **Delete** `mov_pc_with_t0_raises_fault` (1784-1793) — codifies
  the wrong behaviour.
- **Add** `mov_pc_with_even_target_branches`: set `r0 = 0x2000_1000`
  (even), execute `0x4687` (MOV PC, r0), assert `cpu.regs.pc() ==
  0x2000_1000` and `!cpu.has_pending_fault()`.
- **Add** `add_pc_with_even_target_branches`: set `pc=base`, `r0 =
  0x1000` (even add), execute `0x4487` (ADD PC, r0), assert
  `cpu.regs.pc() == base + read_pc_offset + 0x1000` and no fault.
- **Keep** `blx_with_t0_target_raises_fault` (0x4790) and
  `pop_pc_with_t0_raises_fault` (0xBD00) — these paths still fault.

Then rerun `cargo test -p mdrp2040` (unit + firmware + smoke).

## 5. Risk analysis

- **BLX / BX / POP PC fault paths are independent** (execute.rs:433,
  445, 811). Unchanged.
- **mdrp2350 not touched.** Only mdrp2040.
- **No other callers of the deleted branches.** Grep across
  `crates/mdrp2040` for `0x4687`, `0x4478`, `0x44F7`, `0x4487`
  returned only the three existing fault tests; only 0x4687 is
  wired to MOV-PC, only 0x4487 to ADD-PC, none elsewhere.
- **ODD-target behaviour unchanged.** `set_pc(v & !1)` already
  masks LSB, so tests that use MOV/ADD PC with Thumb-tagged (odd)
  targets continue to observe identical post-state.
- **Fuzz oracle unaffected.** `qemu_diff_m0plus::is_m0plus_safe`
  filters all 32-bit wides but passes 16-bit high-register special
  data encodings; post-fix the two oracles will now agree on
  `0x4487 / 0x4687` with even Rm — previously they diverged silently
  because the filter randomly rarely picks this encoding with an
  even register seed.
