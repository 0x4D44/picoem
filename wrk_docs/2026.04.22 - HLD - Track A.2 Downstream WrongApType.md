## 1. Problem

After the Track A patch eliminated the `unreachable!()` panic at `communication_interface.rs:474` (now line 485 post-patch), two RP2354-silicon binaries regressed into a downstream ARM error:

| Binary | Pre-Track-A | Post-Track-A | Observable error |
|---|---|---|---|
| `probe_verify_rp2350` | PANIC `unreachable!` | `Arm(WrongApType)` | (#3872) |
| `silicon_periph_diff_rp2350` | PANIC `unreachable!` | "An ARM specific error occurred." | same root cause, wrapped |
| `probe_diff_rp2350 --fuzz 4000` | PASS 4000/4000 | **PASS 4000/4000** | unchanged — ISA path succeeds |
| `silicon_cycle_oracle_rp2350` | 5/9 PASS | 9/9 PASS | unchanged — Track B tolerance fix |

The sentinel WARN `"ApV2 access on DPv1 cache; upgrading to DPv3 (mdrp-patched workaround)"` fires **exactly once per session** when probe attaches. That confirms the patched pessimistic path IS taken, which means the *initial DPIDR read on RP2354 really does report `version != 3`*.

### 1.1 Exact error-raise site

`ArmError::WrongApType` has three possible origins in the 0.31 tree:
- `src/architecture/arm/mod.rs:114` — enum variant definition.
- `src/architecture/arm/ap/memory_ap/mod.rs:210` — **our site.**
- `src/vendor/nxp/sequences/mcx.rs:156` — NXP-specific, not relevant.

Relevant code (`memory_ap/mod.rs:200–213`):

```rust
impl MemoryAp {
    pub(crate) fn new<I: DapAccess>(
        interface: &mut I,
        address: &FullyQualifiedApAddress,
    ) -> Result<Self, ArmError> {
        let idr: IDR = interface.read_raw_ap_register(address, IDR::ADDRESS)?.try_into()?;
        tracing::debug!("reading IDR: {:x?}", idr);
        Ok(match idr.TYPE {
            ApType::JtagComAp => return Err(ArmError::WrongApType),   // <-- HERE
            $(ApType::$variant => <$type>::new(interface, address.clone())?.into(),)*
        })
    }
}
```

**IDR decoding** (`ap/registers.rs:405`): `TYPE = ApType::from_u8(value & 0x0F)`.

**`ApType::from_u8`** (`ap/mod.rs:353–365`, verified) only accepts `0x0..=0x8` with `0x3` absent. Any unknown value returns `None`, producing a `RegisterParseError` — **not** `WrongApType`. Only `TYPE == 0x0` (`JtagComAp`) maps to `WrongApType`.

**Consequence.** `WrongApType` fires iff the AP IDR read returns a value whose bottom 4 bits are `0x0`. The two candidate causes are:
- The AP really is a JTAG-COM-AP (not relevant on RP2350).
- The read returned a value with bottom nibble `0x0` (typically `0x0000_0000`) because we are addressing the wrong AP/bank altogether.

### 1.2 Full call stack to the error

`Session::auto_attach("rp2350", …)` → `Session::attach_arm_debug_interface` (`session.rs:187`) → per-core loop `CombinedCoreState::enable_arm_debug` (`core/core_state.rs:107`) → `ArmDebugSequence::debug_core_start` (`sequences.rs:739`) → `interface.memory_interface(core_ap)` with `core_ap = V2(ApV2Address(Some(0x2000)))` (`communication_interface.rs:260`) → `ap::v2::new_memory_interface` → `ADIMemoryInterface::new` (`adi_memory_interface.rs:39`) → `MemoryAp::new` (`ap/memory_ap/mod.rs:201`) → `interface.read_raw_ap_register(address, IDR::ADDRESS)` → `select_ap_and_ap_bank` (patched arm fires, cache upgraded DPv1→DPv3) → `raw_read_register(RegisterAddress::ApRegister(0xFC))` → returns value with low nibble `0x0` → `WrongApType`.

The first V2-AP access after attach is therefore the IDR probe of core 0's V2 AP at base `0x2000`.

## 2. Root-cause hypotheses

**Note (D1).** The prior HLD listed four hypotheses. H3 (cache-path ordering) has been **rejected by code inspection**. Verified: at `communication_interface.rs:461`, `previous_select` is captured as `DPv1` (the value pre-mutation); lines 485–495 perform `*cache = SelectCache::DPv3(...)` in place; the outer flush at line 502 compares against `previous_select` and therefore always fires after the patched arm (DPv3 != DPv1 by construction), writing both `SelectV3` and `Select1`. There is no ordering bug on the patched path. H3 is out.

**Note (D2).** H4 as previously framed ("the AP reports an unknown TYPE") is self-inconsistent with §1.1 — unknown TYPE produces `RegisterParseError`, not `WrongApType`. The only distinct-and-concrete reformulation is "RP2354 genuinely wires an AP class that reports `TYPE == 0x0` (a non-JTAG-COM-AP port masquerading with a JTAG-COM-AP low nibble)". This contradicts RP2350 datasheet §3.4.1 (APs declared AHB5 → TYPE `0x5`) and Cortex-M33 TRM's standard AP configuration. Very low prior; not pursued.

So we carry two live hypotheses:

### H1 — RP2354 DP genuinely reports DPv1/DPv2, not DPv3 ("hybrid DP")

**Premise.** The RP2040 DP is DPv2 (multidrop SWD) with ADIv5 V1 APs. The RP2350/2354 datasheet (§3.4) describes multidrop-SWD DP with ADIv6-style V2 APs — a hybrid that probe-rs 0.31 doesn't cleanly model. If DPIDR.version[15:12] on RP2354 is `0x2` (DPv2) — as the probe-rs target YAML does not declare — then Track A's cache-upgrade arm is *wrong* to force DPv3 addressing. We write `SelectV3(0x209)` to DP register SELECT at bank 0; on a DPv2 DP that decodes as `APSEL=0x00, APBANKSEL=0x9`. The subsequent AP register 0xFC read hits AP 0 bank 9 offset 0xC, which on RP2350 does not exist → hardware returns 0 or abort-error suppression → IDR reads as 0 → `WrongApType`.

**Evidence for.** Sentinel WARN fires exactly once per session; Track A HLD §8.1 flagged this risk explicitly; `debug_port_start` in `sequences.rs:636` sends `write SelectV1(0)` regardless, which would glitch a DPv2 target differently than DPv3.

**Evidence against (D5).** `probe_diff_rp2350 --fuzz 4000` passes 4000/4000. That binary runs `Session::auto_attach` and then `core.read_word_32` / `core.write_core_reg` in a tight loop across thousands of randomised instructions. If DPIDR permanently reported DPv2 (H1), every one of those calls would go through the same V2-AP-on-upgraded-DPv3-cache path and would fail identically with `WrongApType`. They don't. So either DPIDR does eventually report DPv3 on that binary (contradicting permanent-DPv2), or the address landed the patched arm writes happens to be benign for DPv2 SELECT decoding *for the specific AP addresses `probe_diff_rp2350` hits but not for the ones `probe_verify_rp2350` hits*. The second story is implausibly narrow — `probe_diff_rp2350` must also hit V2 AP `0x2000` for core access. This is material evidence against H1.

**Test.** `RUST_LOG=probe_rs=trace probe_verify_rp2350`; look for `"Debug Port version: "` at `communication_interface.rs:391`. DPv1 or DPv2 → H1 proved; DPv3 → H1 rejected.

**Fix shape if confirmed.** RP235x-specific `ArmDebugSequence::debug_port_setup` / `debug_port_start` override under `vendor/raspberrypi/sequences/rp235x.rs` that forces the dormant+alert+SWD-activation sequence and reads DPIDR1/BASEPTR0 directly to confirm ADIv6 despite DPIDR reporting DPv1/2.

### H2 — DP is DPv3 but the initial DPIDR read is transient garbage

**Premise.** ADIv6 requires entering SWD via the dormant-state wake + alert sequence. `debug_port_setup` (sequences.rs:515–624) only sends the dormant/alert sequence when `has_dormant = true`, which in the default-DP (non-multidrop) path starts as `false` and is only set to `true` after retry ≥1. On fresh attach, the first retry attempts the legacy SWJ-DP switch (0xE79E); some ADIv6 targets leave the DP in an indeterminate state where the first DPIDR read races and returns stale/zero, but the second read succeeds. By the time `MemoryAp::new` tries the AP IDR read, the line has recovered — but SELECT was programmed using the bad first-read's implied DPv1 semantics.

**Evidence for.** Sentinel firing exactly once per session is consistent with transient first-read + permanent steady-state. `debug_port_connect` (sequences.rs:984–1019) already retries DPIDR in a 1 s guarded loop, but only on `Err`, not on "wrong version". `probe_diff_rp2350 --fuzz 4000` passes because its `read_word_32` hits happen steady-state — once the DP is promoted to DPv3 and SELECT is correctly programmed post-first-failure, steady-state works. That's exactly H2's prediction.

**Test.** Compare first DPIDR read vs. subsequent ones in trace log. If first reads as DPv1/2 and a later read (e.g., after `abort_clear`) reports DPv3, H2 confirmed.

**Fix shape if confirmed.** Add a DPIDR re-read after `abort_clear` inside `select_dp` (`communication_interface.rs:390`), or treat `DPIDR.version < 3 || designer == 0` as "retry up to 3×" in the default `debug_port_start`. Strictly safer than doing nothing on any ADIv6 target.

### 2.1 Revised prior ranking (D5)

Given the `probe_diff_rp2350` 4000/4000 observation:

| Hyp | Prior (pre) | Prior (post-D5) | Rationale |
|---|---|---|---|
| H1 | 0.4 | **0.15** | Permanent-DPv2 would break `probe_diff_rp2350` too; it doesn't. |

**Expected A.2a outcome: H2 confirmed.** A.2b should plan against that while remaining honest that trace may overturn.

## 4. A.2b — Patch (sign-off AFTER A.2a)

This section specifies the shape of the patch *conditional on the A.2a ruling*. Lead does **not** sign off A.2b from this HLD alone; lead returns with a revised A.2b section once A.2a data is in.

### 4.1 Options

#### Option A — Bolt a second patch on top of Track A

Add a new fix on top of the existing Track A `(V2, DPv1)` arm. The arm stays in place; the new patch addresses the root cause (H1 or H2).

- **Pros:** smaller diff per-commit; Track A arm stays as a "defence" if new fix regresses.
- **Cons (D3):** two workarounds bolted together. If H1 confirmed, the Track A arm is **actively harmful** (forces DPv3 SELECT on a DPv2 target). If H2 confirmed, it's **dead code** once the retry fix lands. Neither state justifies "defence-in-depth".

#### Option A-prime (D4) — Replace the Track A arm with the confirmed-hypothesis fix in one edit

If H2: replace the `(V2, DPv1)` arm entirely. The root-cause fix lives in `select_dp` (retry DPIDR on wrong-version); with that in place, `select_ap_and_ap_bank` will never see a DPv1 cache at a V2 AP access, and the arm collapses back to its original `unreachable!()` shape — or, safer, a typed `ArmError::OutOfBounds` return for belt-and-braces.

If H1: replace the arm with a vendor-specific sequence override and remove the arm from the generic path. The arm was pragmatic pre-trace; post-trace it's either wrong (H1) or unreachable (H2).

- **Pros:** one well-designed workaround instead of two bolted together; diff tells a coherent story upstream; no dead code; no harmful-on-DPv2 hazard.
- **Cons:** slightly larger single diff; requires re-running Track A's regression suite from scratch (but that suite already exists and passes).

**Recommendation: Option A-prime.** This is the plan-of-record pending trace confirmation.

#### Option B — Harness-side catch and re-attach (fallback only)

Catch `Arm(WrongApType)` at the binary level, sleep 100 ms, drop the `Session`, re-attach. The orchestrator already does this between scenarios; we'd extend to initial attach.

- **Pros:** zero probe-rs changes; reversible.
- **Cons:** papers over the bug; doesn't help upstream; wastes SWD cycles; makes test_silicon slower; masks the bug on every cold attach.
- **Use only if Option A-prime's trace-driven fix blocks on data we can't collect.**

#### Option C — Straight revert of Track A

Rejected. Reinstates the `unreachable!()` panic; blocks all RP2354 oracles.

### 4.2 Patch shape by hypothesis

**If H2 (expected):**

Edit `communication_interface.rs` `select_dp` around line 390:

```rust
let mut idr: DebugPortId = self.read_dp_register::<DPIDR>(dp)?.into();
for attempt in 1..=3 {
    if idr.version == DebugPortVersion::DPv3 { break; }
    // ADIv6 targets occasionally report DPv1/DPv2 on the first DPIDR read
    // after dormant wake; retry briefly before committing to SELECT encoding.
    std::thread::sleep(std::time::Duration::from_millis(10));
    let reread: DebugPortId = self.read_dp_register::<DPIDR>(dp)?.into();
    tracing::debug!("DPIDR retry {attempt}: version={:?}", reread.version);
    idr = reread;
}
```

Then **remove** the `(V2, DPv1)` arm from `select_ap_and_ap_bank` (A-prime: one-edit replacement). The `unreachable!()` on that arm becomes a `debug_assert!` + typed `ArmError` return for safety, since the retry loop now prevents the condition. Sentinel WARN is deleted.

Total diff: ~25 lines (patch in) + ~15 lines (remove Track A arm) + ~5 lines of tests.

**If H1 (unexpected):**

Create `src/vendor/raspberrypi/sequences/rp235x.rs` with `ArmDebugSequence::debug_port_setup` / `debug_port_start` overrides:
- Always send the dormant+alert+SWD-activation sequence (copy from `sequences.rs:580–594` `has_dormant=true` branch).
- After `debug_port_connect`, read DPIDR1 / BASEPTR0. If BASEPTR0.valid = 1, treat as DPv3 regardless of DPIDR.version.
- Initialise `state.current_select = SelectCache::DPv3(SelectV3(0), Select1(0))` explicitly when BASEPTR0 valid.

Then **remove** the `(V2, DPv1)` arm (A-prime). The sequence override ensures the cache starts as DPv3 on this target, so the arm is unreachable; and on a DPv2 target, forcing DPv3 encoding through the arm was wrong, so it must be removed.

Total diff: ~80 lines (new sequence file + registration in `vendor/raspberrypi/mod.rs`) + ~15 lines (remove Track A arm).

## 6. Risks & mitigation

### 6.1 Risks

- **A.2a trace inconclusive.** Lead may need to re-capture with wider filters or on multiple boards. Mitigation: budget for a second 1 h A.2a iteration; if still ambiguous after that, ship H2's retry (strictly safer than nothing) and flag for a longer-horizon investigation.
- **H1 fix breaks other ADIv6 targets.** Mitigation: scope the new sequence file to `vendor/raspberrypi/sequences/rp235x.rs` — it's chip-name-gated.
- **H2 fix adds 30 ms to every fresh attach.** 3× retries × 10 ms. Acceptable for oracle harnesses; negligible on `probe_diff_rp2350`'s cold-start. Mitigation: only retry if first read returns non-DPv3 and target YAML declares V2 APs (target-aware).
- **Removing the Track A arm under A-prime risks regression if trace-reading was wrong.** Mitigation: the 8-item test plan above is mandatory before merge. If anything goes backward, revert commit 2 (arm removal) and land only commit 1 (root-cause fix) as Option-A (bolt-on, with FIXME).
- **Patched probe-rs drifts further from upstream.** Net-net A-prime *reduces* drift (one patch instead of two). Mitigation: upstream PR rebased against A.2b diff.
- **30-min soak not achievable during implementation session.** Mitigation: lead runs soak during overnight validation, as with Track A.

### 6.2 Rollback

- Each A.2b commit (§4.4) is a separate revert point.
- Reverting commit 2 (Track A arm removal) + commit 1 (root-cause fix) returns to current Track A state (sentinel fires, WrongApType returns). The `unreachable!()` panic does **not** come back because commit 2 only removed the arm; the `unreachable!` was already replaced by the arm in Track A. Revert of commit 1 alone = safely ship without removing Track A arm (effectively Option A bolt-on).
- Harness unchanged; nothing there to revert.
