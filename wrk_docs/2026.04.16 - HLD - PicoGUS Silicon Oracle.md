# HLD — PicoGUS Silicon Oracle (firmware-level differential)

Version: 1.0.0
Date: 2026-04-16
Author: Stream 2 (parallel PicoGUS audio-path investigation)

## 1. Purpose

Provide a **firmware-level** silicon-differential oracle that loads the pinned
PicoGUS v4.0.0 firmware on both live RP2040 silicon and our `mdrp2040`
emulator, drives both with the same ISA trace, halts at agreed
synchronisation points, and diffs **observables** (peripheral state, pin
activity, SRAM mailbox) rather than per-instruction register state.

The oracle is intended as:

1. **Post-fix validation** for the PWM `EN`/`CSR.EN` aliasing bug identified
   by Stream 1 — prove that after the fix, silicon and emulator observables
   match at every sample point across a known-good trace.
2. **A general integration oracle** that catches future bugs in the same
   shape as the PWM bug: peripheral quirks that don't surface in per-
   instruction ISA diffs but do cause the firmware's observable state to
   diverge over seconds of runtime.

It is **not** intended to be the fix-finding mechanism for the PWM bug
itself — Stream 1 already located that from source reading plus the
emulator's own bus trace.

## 2. Scope

### 2.1 What this oracle tests

- **Firmware-level end-state** across a bounded replay window: after N ms
  of ISA trace, are the DMA channels, PIO state machines, PWM slices,
  NVIC, and I2S pin stream in the same state on silicon as on the
  emulator?
- **Peripheral dispatch fidelity** under a real workload (PicoGUS v4.0.0
  GUS personality) rather than synthesised scenarios.
- **Cross-core coordination observables**: core-1-owned peripheral state
  (PWM IRQ path, PIO1 SM3 I2S feed) vs. core-0-owned state (ISA-tap
  PIO0 SM0, GUS register RMW, PSRAM PIO1 SM0).

### 2.2 What this oracle does NOT test

- **Per-instruction register state.** That is `probe_diff_rp2040`'s job —
  single-step a synthetic test case, diff R0–R15 + xPSR. Running a full
  firmware instruction-by-instruction over SWD is impractical (single-
  stepping ~30 MHz of emulated firmware at probe-rs's ~1 kHz step rate
  would take weeks).
- **Cycle-accurate timing** at instruction granularity. RP2040's
  Cortex-M0+ has no DWT CYCCNT (see risk R3 below), and the wall-clock
  behaviour of live silicon is not deterministic enough to validate
  emulator cycle counts at per-step granularity.
- **Bit-exact audio output.** DOSBox-X vs. PicoGUS firmware already
  differ on sample mixing; the existing `picogus_diff_rp2040` (with
  `I2sCapture` → WAV) is the subjective/spectrogram comparison path.
  This oracle compares the **I2S pin edge stream** (count + timing
  window), not the decoded PCM values.

## 3. Observables

All reads happen at a **synchronisation point** (§4.2). Silicon side is
read with probe-rs `read_word_32` / `read_8` while the core is halted;
emulator side is read via `Emulator::mmio_read32` / backing-store
accessors.

### 3.1 DMA channel state (all 12 channels)

Silicon: `read_word_32` on each channel's `CTRL_TRIG` (`DMA_BASE + N*0x40
+ 0x00c`), `READ_ADDR` (`+0x00`), `WRITE_ADDR` (`+0x04`), `TRANS_COUNT`
(`+0x08`), plus the global `INTS0` (`+0x40c`) and `INTS1` (`+0x41c`).

Emulator: same addresses through `Bus::read32`. No special APIs needed.

**Diff**: bit-exact on `CTRL_TRIG.EN` / `CTRL_TRIG.BUSY` /
`TRANS_COUNT`. `READ_ADDR` / `WRITE_ADDR` bit-exact at sync-point
granularity (both sides have halted the core, so the channel has no
in-flight update). `CHAN_ABORT` is write-only on silicon so we skip
it; `INTS0/1` bit-exact.

### 3.2 PIO block state (both blocks, all 4 SMs each)

Silicon: `CTRL` (`PIOx_BASE+0x000`), `FSTAT` (`+0x004`), `FDEBUG`
(`+0x008`), `FLEVEL` (`+0x00C`). Per-SM: `SMx_CLKDIV` (`+0x0C8 +
0x18*x`), `SMx_EXECCTRL` (`+0x0CC + 0x18*x`), `SMx_SHIFTCTRL`
(`+0x0D0 + 0x18*x`), `SMx_ADDR` (`+0x0D4 + 0x18*x`), `SMx_INSTR`
(`+0x0D8 + 0x18*x`), `SMx_PINCTRL` (`+0x0DC + 0x18*x`). FIFO contents
(`TXFx`, `RXFx`) via `FDEBUG` bit inspection rather than destructive
reads.

Emulator: all the above through `Bus::read32`. Our PIO model exposes
FIFO levels via `FSTAT`/`FLEVEL` the same way silicon does, and the
harness already imports `mdpicoem_common::pio::StateMachine` for
diagnostic access in `picogus_diff_rp2040`.

**Diff**: bit-exact on `FSTAT`, `FLEVEL` (FIFO levels), `SMx_ADDR`
(current program-counter in the PIO program). `SMx_INSTR` is reported
but compared advisorily — under some SM configurations reading it
latches a speculative instruction; treat mismatch as a warning, not a
hard fail. `FDEBUG` sticky bits compared with `|=` semantics (once set
either side, both sides must eventually see the bit).

### 3.3 PWM peripheral state

Silicon + emulator: per-slice `CSR[0..8]` (`PWM_BASE + 0x14*slice + 0x00`),
`DIV` (`+0x04`), `CTR` (`+0x08`), `CC` (`+0x0C`), `TOP` (`+0x10`).
Block-level: `EN` (`+0xA0`), `INTR` (`+0xA4`), `INTE` (`+0xA8`), `INTF`
(`+0xAC`), `INTS` (`+0xB0`).

**Critical for the current bug hunt (§1 item 1).** Post-fix,
`PWM.CSR[4].EN` must read back as 1, `EN[4]` must be synthesised to
match, `INTR[4]` must latch once the counter wraps, and `INTE[4]`
must be set by `audio_sample_handler`'s setup path — all identical on
silicon and emulator.

**Diff**: bit-exact on every field. `CTR` is advisory-compare at sync
points (both sides halted so it's stable, but the absolute phase
relative to the sync point depends on when setup writes landed —
reported with a note if drift exceeds ±1 cycle).

### 3.4 PSRAM content

This is the hardest observable to capture on silicon. Three options
considered; option C wins.

- **Option A — read back via SM0 program.** Pause the firmware, reuse
  the PSRAM PIO1 SM0 program to issue a fast read (`0x0B`) and capture
  the result via `RXF0`. **Rejected**: firmware owns SM0's program
  memory, instruction pointer, scratch X/Y. Hijacking it requires
  tearing down and re-initialising, which destroys the very state the
  oracle is trying to measure.

- **Option B — external logic analyser on PSRAM SPI pins.** **Rejected**:
  extra hardware we can't confirm we have (per brief's constraint).

- **Option C — firmware-cooperative readback through an injected
  helper.** At each sync point:
  1. Probe-rs halts all cores.
  2. Probe-rs writes a tiny helper stub (~128 B of Thumb) into a known-
     unused SRAM slot (`PSRAM_READBACK_STUB_BASE = 0x2003_E000`, 8 KB
     above `DUALCORE_CORE1_STACK` — well above anything PicoGUS
     firmware uses; datasheet RAM layout reserves this region for
     "downloaded code").
  3. Helper parameters (offset, length ≤ 256 B) are written into a
     mailbox at `PSRAM_READBACK_MAILBOX = 0x2003_E800`.
  4. Probe-rs reprograms core-0 PC to the helper, releases core 0,
     waits for the BKPT #1 at the helper's tail.
  5. Helper uses the live SM0 program and TX/RX FIFOs to issue a QPI
     fast-read of the requested window, copies bytes into the mailbox
     return area.
  6. Probe-rs halts core 0 at the BKPT, reads the mailbox return area
     over SWD, restores core-0 PC/regs/stack to the captured pre-
     helper values, resumes firmware.
  7. Emulator side: read the PSRAM backing store directly via the
     existing `Psram::read` API from `mdpicoem-devices`.

  **Risk**: the helper mutates SM0's X/Y scratch and possibly the
  TX/RX FIFO levels. We restore what we can (X/Y via `SMx_INSTR`
  execution of `OUT X,32 / OUT Y,32`), but residual FIFO level drift
  is a known soft-compare item — **PSRAM content diff is the
  authoritative signal; FIFO level after helper run is advisory.**

  Implementation of the helper is deferred to Phase 3 (§8.3). MVP
  (§8.1) does not diff PSRAM content — we accept this blind spot for
  the initial PWM fix validation, where PSRAM fill-in is upstream of
  the failure and known to be working.

### 3.5 I2S pin activity (GP16/17/18)

Two axes to compare: **edge count** (how many BCLK rising edges
elapsed between sync points) and **pin-drive polarity** at the sync
point.

Silicon capture mechanism: **reuse a spare PIO SM** (PIO0 SM2 or SM3
— unused by PicoGUS's ISA tap, verified from firmware source at
`isa_io.pio`) as a 3-pin edge-capture tap. The spare SM runs a 4-
instruction program (`IN PINS,3 / JMP X-- / IN PINS,3 / JMP 0`) that
autopushes 32 × 3-bit samples per autopush. Probe-rs reads `RXFx`
drain at each sync point, counts BCLK rising edges, and records the
LRCLK phase. No external hardware. No dedicated logic analyser.

This is **option (a)** from the brief — divert to a GPIO input on
the same board and count via another SM. Chosen over:

- **(b) External LA**: hardware we don't have and the brief forbids.
- **(c) Synthesise audio on a spare SM**: scope creep; we want edge
  activity, not PCM reconstruction (that's `picogus_diff_rp2040`'s job
  via `I2sCapture`).

Emulator-side equivalent: the existing `I2sCapture` module in
`mdpicoem-devices` already watches the same pin set. Extended to
expose `edges_since(last_mark) -> (bclk_edges, lrclk_phase, dout_level)`
as a snapshot for sync-point diffing. The PCM-decoding path stays
untouched.

**Diff**: BCLK edge count exact (tolerance ±1 to allow for sync-
point ordering jitter). LRCLK phase exact. DOUT level at sync point
advisory (silicon samples a single instant; skew possible — reported
but not a hard fail on its own).

### 3.6 NVIC state (per-core)

Silicon: `NVIC_ISER0` (`0xE000_E100`), `NVIC_ISPR0` (`0xE000_E200`),
`NVIC_IABR0` (not on M0+; skip), `NVIC_IPR0..7` (`0xE000_E400 + 4n`).
Read through core-0 AP then switch to core-1 AP and re-read — NVIC is
per-core on RP2040.

Emulator: already exposes per-core NVIC state through `Bus::nvic_pending`
/ `Bus::nvic_enabled` (our bus model tracks these per-core per
`mdrp2040/src/bus/mod.rs:300`). New public read accessors needed on
`Emulator` if not already present.

**Diff**: bit-exact on enable + pending. Active bit unavailable on
M0+ — skip. Priority bytes bit-exact.

**The PWM path is the most load-bearing NVIC diff for the current
bug**: pre-fix, emulator has `PWM_IRQ_WRAP` (NVIC[4]) never pending on
core 1, while silicon has it pending/active depending on the sync-
point instant. Post-fix, both sides match.

### 3.7 CYCCNT delta

**Not applicable.** Cortex-M0+ does not implement DWT CYCCNT (per
`probe_diff_rp2040` comment). Instead, use **SysTick** (`SYST_CVR`
read-sampled at each sync point) on both sides as a coarse cycle-
budget check, with the same soft-assertion discipline
`silicon_periph_diff_rp2040` uses (§4.2 of the RP2040 peripheral
coverage HLD).

Per-sync-point window: declare `min_sysclks` and `max_sysclks` per
trace position. Silicon's SysTick decrement is the reference.
Emulator's `Emulator::cycles()` delta is compared to the silicon
window with a ±5% tolerance (loose, because emulator and silicon
won't match exactly at firmware granularity without the per-
peripheral timing fidelity we haven't promised).

### 3.8 Firmware "I'm alive" mailbox

New addition: a **passive, probe-rs-only** mailbox. Picks a scratch
word in an SRAM region the firmware already uses but doesn't
semantically own — the last 4 bytes of the PicoGUS image's `.bss`
tail (resolved at firmware-load time from the firmware's metadata or
hard-coded per-release).

Alternative and preferred: the mailbox is **emulator-and-silicon-
only** and does not require firmware cooperation. We use the
**emulator's bus trace** on the emulator side (record the last few
MMIO addresses written to known firmware landmarks — spinlock
releases at `SIO+0x2A00..0x2A1C`, PIO TXF writes) and the **silicon
SRAM read of the same landmarks** on the silicon side. Liveness is
"core 0 released spinlock `gus_crit` at least once in the last
window" on both sides. No firmware patch needed.

**If** we later decide to cooperate with a firmware hook, that's a
Phase 3 extension; MVP does not require it.

## 4. Execution model

### 4.1 How to drive the same ISA trace into silicon

The emulator side already has ISA-trace replay — `picogus_diff_rp2040`
drives synthetic ISA bus cycles by poking RP2040 GPIOs (per
`picogus_diff_rp2040.rs:65-86`). The silicon side needs the same
waveform.

**Proposal**: a helper SM + host-driven write loop.

1. Host (probe-rs) halts core 0, reserves a ring buffer in an unused
   SRAM region (`ISA_REPLAY_RING = 0x2003_C000`, 16 KB) holding the
   next 4096 trace events as `(ns, port, data, kind)` tuples.
2. Host uploads a small Thumb driver (`isa_replay_driver`, ~256 B) to
   core-1 scratch and releases core 1 with PC = driver entry.
3. The driver reads events from the ring, busy-waits on a host-
   written `go_flag`, toggles IOW# / ADS# / AD0..9 pins in the exact
   waveform the firmware's PIO program expects, and increments a
   progress counter.
4. Host refills the ring as the driver consumes it, polling the
   progress counter between refills.

**Why core 1 drives**: PicoGUS's audio personality runs its main
synth loop on core 1 (`play_gus` at `gusplay.cpp:110` per Stream 1's
notes), but the audio personality **does not start the synth loop
until IOW# events configure the voices**. For the initial boot
window — and for every sync point where we halt all firmware
execution — core 1 is either idle (pre-first-write) or halted by us.
We hijack it for the trace driver during replay windows and restore
it at sync points.

**Risk — this is R1 below**: the brief flagged "ISA bus replay
fidelity over SWD is untested". We are specifying the mechanism; its
fidelity is a Phase 2 validation task.

**Alternative rejected — host bit-bangs ISA pins directly through
SWD writes to the SIO GPIO registers**. Too slow (SWD
`write_word_32` ~100 µs; PicoGUS expects IOW# pulses of 300 ns).

### 4.2 Synchronisation model

Replay runs in **bounded windows**. Each window is a list of trace
events to drive, terminating at a **sync point**. A sync point is a
trace-event index where both sides are halted for observable
comparison.

Sync points come from a `SyncPlan` CSV alongside the trace:

```
# picogus-sync v1
event_index,reason,min_sysclks,max_sysclks
500,first_pwm_csr_write,0,50000
1024,first_audio_sample_handler,40000,120000
8192,pwm_wrap_count_128,4000000,6000000
...
```

Generated once per trace+firmware combination by an
**off-line emulator-only run** (the emulator produces candidate sync
points at events where peripheral state transitions), then
**committed** to `fixtures/picogus-sync/<trace-stem>.sync`. Frozen
thereafter unless the trace or firmware changes.

At each sync point:
1. Silicon: halt all cores via probe-rs.
2. Silicon: read every observable from §3.
3. Emulator: `Emulator::run_until(target_event)` — step until the
   emulator has driven the same trace-event index. The emulator
   knows its own event index from the replayer.
4. Emulator: `Emulator::halt_all()`. Read every observable.
5. Diff; report first divergence per-category.
6. Release both sides; advance to the next window.

### 4.3 Real-time vs. instruction-paced

**Silicon is real-time**; **emulator is instruction-paced**. The
sync-point discipline resolves this:

- Silicon replay runs at live-firmware speed (~125 MHz sysclk, give
  or take the overclock). Each trace event's `ns` timestamp is
  converted to an absolute SysTick reload target.
- Emulator replay runs at `Emulator::cycles()` pace and consumes the
  same trace event at the same simulated-ns boundary.
- **Wait condition** at sync point: silicon waits for `SysTick` ≤
  `window_end_ns * sysclk_hz / 1e9`; emulator waits for
  `Emulator::cycles() ≥ window_end_cycles`.

**Jitter tolerance**: SysTick sample at sync point ± 1000 sysclks
(~8 µs) is within window. Outside window → FAIL with a
`window_sysclks` message, consistent with `silicon_periph_diff_rp2040`.

### 4.4 Sync point density

**Sparse is better.** Every sync point costs ~20 ms of wall-clock
per-side (probe-rs halt + read + release). A 10-second trace with
100k events and one sync point per 1000 events is ~100 sync points =
~4 s of oracle overhead on top of the 10 s trace replay. Acceptable.

**Density knobs:**
- `--sync-every <N>`: uniform density, N events per sync point.
  Default 1000.
- `SyncPlan` file: non-uniform, denser around peripheral state
  transitions (post-init, post-first-sample, post-first-DMA-wrap).
  Preferred.
- `--first-divergence-only`: stop at the first sync-point FAIL.
  Default on; `--all-sync-points` overrides for exhaustive diff
  runs.

### 4.5 How many sample points per run

MVP: **5 sync points** on a short boot trace (§8.1):
1. Pre-trace (boot complete, firmware idle).
2. First `0x343` ISA write landed.
3. First `PWM_IRQ_WRAP` pending.
4. First PIO1 SM3 TXF3 write.
5. +100 ms post-(4).

Phase 2: **~100 sync points** on the Doom E1M1 fixture
(`crates/mdpicoem-harness/fixtures/monkey_island_theme.trace` or a
shorter GUS-ready fixture).

Phase 3: **bounded long runs** with sync every 10 ms (1000 points
for a 10 s trace), driven by `test_silicon`-style orchestrator.

## 5. Divergence criterion

**First-divergence, per-category.** Matches the existing
`CaseOutcome` / `Verdict` convention in `silicon_oracle.rs`. A
sync point's verdict is `Fail` if **any** category diff is non-
empty; the `detail` field carries the **first** category's first
divergence in a deterministic order (DMA → PIO → PWM → NVIC → I2S-
edge → SysTick-window → PSRAM-content-if-Phase-3).

**Always-fail cases (hard diff):**
- DMA channel `EN` bit differs (one side armed, other not).
- PIO SM `CTRL.SM_ENABLE` differs (SM running on one side, not
  other).
- PWM slice `INTR[n]` bit latched on one side but not the other —
  this is literally the Stream 1 bug's signature.
- NVIC pending bit for `PWM_IRQ_WRAP` / `PIO0_IRQ_0` /
  `PIO1_IRQ_0` / `PIO1_IRQ_1` / `DMA_IRQ_0` / `UART0_IRQ` differs.
- I2S BCLK edge count delta > ±1.

**Soft-compare cases (tolerance):**
- `SYST_CVR` outside declared `[min_sysclks, max_sysclks]` window —
  FAIL with a `window` message (per §4.3).
- `PWM.CTR` phase drift ±1 sysclk — reported, not FAIL.
- PSRAM content (Phase 3 only): byte-exact; tolerance 0. If Phase 3
  can't suppress FIFO-level drift from the readback helper, drop
  PSRAM content to advisory.

**Tolerance defaults:**
- SysTick window: declared per-sync-point (default ±5% of median).
- I2S BCLK edge count: ±1.
- CTR phase: ±1.
- Everything else: 0.

## 6. HW + SW dependencies

### 6.1 Hardware

- **1× Pico debug probe** (`E46410955F3C5C27` per CLAUDE.md).
- **1× Pico V1 / RP2040 board** with the probe attached via SWD.
- **No external logic analyser required** (per §3.5 option (a)).
- **No PicoGUS PCB required** for the MVP. The oracle drives
  synthetic ISA waveforms; the firmware does not know it's not
  attached to a real PC ISA slot. Phase 3 *may* call for a real
  PicoGUS v2 board for PSRAM readback fidelity — but that's
  optional, and the helper-stub design (§3.4) means we don't need
  one for correctness.

### 6.2 Software

- **probe-rs 0.31** (already vendored).
- **The pinned PicoGUS firmware** — `third_party/picogus/picogus-
  v4.0.0.bin`, already present per the existing
  `picogus_diff_rp2040` setup.
- **The RP2040 bootrom** — `roms/rp2040/bootrom-rp2040-b2.bin`,
  already present per CLAUDE.md §Non-Obvious Conventions.
- **A frozen trace fixture** with a companion SyncPlan —
  `fixtures/picogus-stream2/<name>.trace` +
  `<name>.sync`. MVP ships one trace + SyncPlan; Phase 2 adds more.

### 6.3 CI gating

Same gate as every `probe_*` / `silicon_*` binary: **not run in CI**.
Annotated with a `#![cfg(feature = "silicon_oracle")]` gate if the
workspace grows one; today, the convention is simply "don't list it
in CI workflows," matching the existing oracles.

- **`Emulator::nvic_{pending,enabled,priority}_for_core(i)`** — if
  not already public, expose them.

## 8. Phasing

### 8.1 MVP — catch the PWM bug we have today

**Goal**: one sync-point run on a short (≤ 5 ms) trace fixture that
triggers the PWM IRQ setup + first wrap, with FAIL on pre-fix
emulator and PASS on post-fix emulator.

Scope:
- Observables: **DMA**, **PIO**, **PWM**, **NVIC**, **SysTick
  window**. Skip I2S edge count (one fewer fiddly bit) and skip
  PSRAM content (Phase 3).
- Sync points: the 5 listed in §4.5.
- Trace: a hand-crafted fixture — 4 or 5 ISA writes that mimic
  PicoGUS boot's first PWM setup. Short enough to replay reliably
  without the full trace driver infrastructure — pokes can be host-
  driven over SWD at 5 ms per event; that's fine for 5 events.
- ISA replay: host-driven SWD writes to GPIO registers, not the
  core-1 driver. **MVP trades ISA fidelity for simpler wiring.**
- Firmware: pinned v4.0.0 loaded via flash + bootrom.
- CLI: `picogus_silicon_diff_rp2040 --trace fixtures/picogus-
  stream2/pwm_smoke.trace --sync fixtures/picogus-stream2/pwm_smoke.sync`.

**Exit criterion**: FAIL with "PWM.INTR[4] HW=1 EMU=0" on pre-fix
`main`; PASS on the branch carrying the PWM fix.

**Est. effort**: ~300 LOC of new code + ~100 lines of trace+sync
fixtures.

### 8.2 Phase 2 — core-1 ISA replay driver + I2S edge capture

Wire up the core-1-hosted ISA replay driver (§4.1) for traces
longer than the host-SWD-bit-bang limit (~1000 events). Add the
PIO0 SM2 edge-capture tap for I2S (§3.5). Extend `I2sCapture` with
the snapshot accessor on the emulator side. Ship the Doom E1M1 /
Monkey Island fixture with a ~20-sync-point plan.

**Exit criterion**: full trace replay with I2S edge-count agreement
within ±1 at every sync point, on post-fix emulator.

### 8.3 Phase 3 — PSRAM content diff + long-running orchestration

Implement the PSRAM readback helper (§3.4 option C). Add `--soak
<duration>` orchestration à la `test_silicon`. Extend the SyncPlan
format with PSRAM-region-of-interest declarations so the readback
helper only pulls back the bytes we want to diff (saves SWD
roundtrips).

**Exit criterion**: long-run diff (1+ hour) on a loopable MIDI
fixture showing no divergence. Catches slow drift bugs the 10 s
replay would miss.

### 8.4 Phase 4 (stretch) — `test_silicon` integration

Wrap under the `test_silicon` orchestrator alongside `probe_diff_rp2040`
/ `silicon_periph_diff_rp2040` / `silicon_isr_diff_rp2040` so one
invocation on RP2040 silicon covers ISA, periph, ISR, and PicoGUS
oracles with shared probe session.

## 9. Risks / unknowns

**R1 — ISA bus replay fidelity over SWD is untested.**
The core-1 driver design (§4.1) is specified but not implemented.
The driving concern is timing accuracy: PicoGUS's ISA-tap PIO
program expects IOW# low pulses of ~300 ns (37 sysclks at 125 MHz);
a core-1 Thumb driver polling a ring buffer may introduce jitter
that desyncs the PIO's 10-bit-address / 8-bit-data capture phase.
**Mitigation**: MVP sidesteps entirely (host-driven for short
traces). Phase 2 validates fidelity by running a known-good trace
through both silicon-driven-by-core-1 and silicon-driven-by-core-0-
running-PicoGUS-source-replay (if we can generate the latter
locally) and diffing PIO0 SM0 autopush counts.

**R2 — silicon PSRAM can't be read back without firmware
cooperation.**
§3.4 option C lifts this to a helper-stub design, but the helper
itself is intrusive (hijacks core 0, mutates SM0 scratch). Residual
FIFO drift from helper execution will be a non-zero baseline that
may mask bona fide divergences. **Mitigation**: Phase 3 quantifies
the drift on a known-good post-fix run, sets the tolerance
accordingly. If tolerance must be > 1 byte, demote PSRAM-content
to advisory and rely on PSRAM-access-pattern (PIO1 SM0 autopush
count, FIFO level, `FDEBUG` sticky bits) as the primary PSRAM
oracle signal.

**R3 — M0+ has no DWT CYCCNT.**
Cycle-based comparisons at instruction granularity are
architecturally impossible. **Mitigation**: §3.7 switches to
SysTick windows with soft assertion. Accepts looser cycle matching
as the cost of working on M0+ silicon.

**R4 — firmware drift between silicon and emulator.**
PicoGUS v4.0.0's boot sequence includes a real-time-clock-dependent
initialisation (XOSC startup counter). Emulator may start the
firmware from an already-stable XOSC state; silicon goes through
the actual 64 ms startup delay. Sync point 1 ("boot complete,
firmware idle") must tolerate this. **Mitigation**: the first sync
point waits for `XOSC_STATUS.STABLE == 1` on both sides before
sampling observables, rather than a fixed wall-clock offset.

**R5 — bootrom divergence.**
Our emulator runs the vendored `bootrom-rp2040-b2.bin`. Silicon
runs the identical binary in masked ROM. Any bootrom-MMIO
interaction we don't model (GPIO for QSPI mux, WATCHDOG scratch
regs) will diverge during the pre-firmware window. **Mitigation**:
the MVP's first sync point is "post-boot2, firmware's `main()`
entered" — explicitly skipping the bootrom window. Pre-`main`
divergence is out of scope for this oracle.

**R6 — probe-rs session stability under long runs.**
`silicon_isr_diff_rp2040` and `silicon_periph_diff_rp2040` both
already include retry-once logic for transient probe errors. We
copy that pattern. **Mitigation**: same retry wrapper. Phase 3's
`--soak` mode adds per-case watchdog + reattach like `test_silicon`.

**R7 — core-1 driver conflicts with PicoGUS's core-1 use.**
PicoGUS runs its synth loop on core 1. The replay driver hijacks
core 1 during windows where we also want PicoGUS's synth active.
**Mitigation**: for MVP and Phase 2, the trace driver only runs
during ISA-write windows; between sync points, the driver halts and
core-1 PC is restored to PicoGUS's synth loop. For Phase 3 long-
run, we need a split-by-time-slice scheme or a dual-probe
orchestrator — deferred.

## 10. Open questions

- **Should the SyncPlan be CSV (human-authored) or JSON
  (programmatically-generated)?** CSV is simpler for MVP; JSON
  scales better for Phase 2+. Default to CSV; revisit if SyncPlan
  size exceeds ~1000 points.
- **Should the `SyncPlan` be checked into the repo alongside the
  trace, or regenerated per-run?** Checked in. Freezing removes a
  source of nondeterminism; `--regenerate-sync` is an explicit
  offline command.
- **Multi-core CPU register diff — cheap enough to include?**
  Reading R0–R15 + xPSR via probe-rs per sync point is ~50 ms.
  Interesting but out-of-scope for MVP. Phase 2 optional.
- **Does the oracle need to support UF2 firmware?** `.bin` via
  flash + bootrom is sufficient for v4.0.0. If future firmware
  ships UF2-only, adapt the loader then.

## 11. Success criteria

Oracle-level:
1. **MVP oracle FAILs on pre-fix emulator** with a clear
   "PWM.INTR[4] HW=1 EMU=0" message at the third sync point.
2. **MVP oracle PASSes on post-fix emulator** with no divergence
   across all 5 sync points.
3. **Phase 2 oracle PASSes** on post-fix emulator across the full
   committed trace.
4. Binary requires a probe + RP2040 board; exits cleanly with a
   non-zero exit code and a single fatal error line if the probe
   is missing (same shape as every other `probe_*` binary).
5. Documentation in `CLAUDE.md` §Testing Topology updated to
   include oracle #13.

Fix-validation-level (the thing the user cares about):
6. After the PWM fix lands, running MVP + Phase 2 against the
   pinned firmware produces zero unexpected FAILs. Any FAIL
   surfaced by the oracle is demonstrably a real divergence, not
   an oracle artefact.
