# OneROM PIO Differential — Design

Version: 0.2.0 — DRAFT
Date: 2026-04-14
Parent: RP2350 Emulator HLD §10.1 (Oracle 5 — deferred in Phase 6)
Depends: Phase 6 complete (`mdpicoem-common::pio`)

## 1. Purpose

Close the fifth PIO oracle from the master HLD by running real-world OneROM
PIO programs through both Piers Finlayson's `epio` (a standalone
cycle-accurate RP2350 PIO emulator, MIT-licensed) and our own
`mdpicoem-common::pio`, comparing observable pin behaviour. `epio` is
explicitly designed as a reference implementation, has its own comprehensive
test suite, and already contains OneROM-specific programs in
`test/onerom_programs.h`.

This closes the "Piers' harness differential" deferred item from the Phase 6
LLD V3 §7.1 and the Phase 6 Implementation journal open-items list.

### What this oracle catches

The existing four oracles validate:

| Oracle | Validates |
|--------|-----------|
| Unit tests (`pio_tests.rs`, `tests.rs`) | Our own semantics, self-consistent |
| `qemu_diff_m33` | Cortex-M33 ISA vs. QEMU M33 |
| `probe_diff_rp2350` / `probe_verify_rp2350` | CPU + bus behaviour vs. real RP2354 silicon |
| Phase 6 waveform tests | Our PIO integration — self-consistent only |

What none of them catch: whether our PIO **engine** agrees with an
independent third-party RP2350 PIO implementation on the pin sequence
produced by a given program under a given input-pin stimulus. This oracle
fills that gap.

### Non-goals for this work

- Running the full OneROM firmware `.bin` through our Cortex-M33. Deferred
  to the "Next Session" row in §11.
- Clock-divider accuracy. `epio` ignores `CLKDIV`; all differential
  scenarios run at `clkdiv=1,frac=0`.
- Side-set pin behaviour. `epio` doesn't model it (delays are fine);
  scenarios must avoid side-set.
- MOV ↔ RX FIFO. Unsupported in `epio`; scenarios must avoid it.
- `>4`-word FIFO joining. `epio` is fixed at 4; scenarios must avoid
  joining.
- CI integration. Local dev oracle only.
- Integration into `cargo test`. The diff binary is invoked explicitly via
  `cargo run --bin onerom_pio_diff_rp2350`.

## 2. Scope for this session

Three deliverables, nothing more:

1. **`crates/epio-sys/`** — new workspace crate. Vendors `epio` + `apio`
   as git submodules, compiles `epio/src/*.c` + one small first-party C
   shim via `cc::Build` (forced to clang), generates Rust bindings for
   `epio.h` via `bindgen`. Ships one binary: `onerom_trace_gen_rp2350`.
2. **`onerom_trace_gen_rp2350`** binary. Links against the C shim, runs
   the OneROM 2364 scenario, writes a text trace to
   `crates/mdpicoem-harness/oracles/onerom_2364.trace`. Run on demand;
   not part of `cargo build` or `cargo test` at workspace root.
3. **`onerom_pio_diff_rp2350`** binary under
   `crates/mdpicoem-harness/src/bin/`. **Pure Rust, zero C
   dependencies.** Reads the committed trace file, reconstructs the
   program from the trace's header block, loads it into a fresh
   `PioBlock`, replays the same stimulus, diffs cycle-by-cycle. Reports
   first divergence with full context.

Whatever divergences surface, we triage (Stage E). If none surface, we
widen the test corpus in a follow-up.

                            body: one row per cycle)

  REGULAR USE  (cargo run -p mdpicoem-harness --bin onerom_pio_diff_rp2350)
  ─────────────────────────────────────────────────────────────

Key property: the diff binary and `mdpicoem-harness` as a whole have

## 5. Vendoring

`epio` and `apio` are added as git submodules under
`crates/epio-sys/third_party/`. Submodule SHAs are pinned in
`.gitmodules` and travel with the repo.

```
git submodule add https://github.com/piersfinlayson/epio.git \
    crates/epio-sys/third_party/epio
git submodule add https://github.com/piersfinlayson/apio.git \
    crates/epio-sys/third_party/apio
```

First-time setup is documented in `crates/epio-sys/README.md`:
`git submodule update --init --recursive`. Not mentioned in top-level
`CLAUDE.md` — this is an opt-in subcomponent that most workspace users
never touch.

### Why we vendor apio even though we only use epio

`epio.h` transitively `#include`s `<apio.h>` — epio and apio are
co-designed. Skipping apio breaks the `cc::Build` include path and
bindgen's clang invocation. `apio` has **no `src/` directory** (confirmed
from its git tree); it is header-only, so vendoring costs us nothing at
compile time beyond an `-I` flag.

## 6. `epio-sys` crate

### 6.1. `build.rs`

```text
1. Verify third_party/epio/src and third_party/apio/include exist.
   Error with a "run git submodule update --init" hint if not.

2. Collect sources:
     let epio_srcs = glob("third_party/epio/src/*.c")        // compiled
     let shim_srcs = ["src/c_shim/trace_gen_core.c"]         // compiled

3. cc::Build::new()
       .compiler("clang")                     // explicit; no MSVC fallback
       .include("third_party/epio/include")
       .include("third_party/apio/include")
       .include("src/c_shim")
       .define("APIO_EMULATION", "1")
       .flag_if_supported("-Wno-unused-parameter")
       .flag_if_supported("-Wno-unused-function")
       .files(epio_srcs.chain(shim_srcs))
       .compile("trace_gen");                 // produces libtrace_gen.a

4. bindgen::Builder::default()
       .header("wrapper.h")                   // #include <epio.h>
       .clang_arg("-Ithird_party/epio/include")
       .clang_arg("-Ithird_party/apio/include")
       .clang_arg("-DAPIO_EMULATION=1")
       .allowlist_function("epio_.*")
       .allowlist_type("epio_.*")
       .blocklist_function("APIO_.*")         // apio function-like macros
       .generate()
       .write_to_file($OUT_DIR/bindings.rs);

5. Also emit bindings for the C shim entry points (trace_gen_core.h),
   via a second bindgen::Builder pass with
   .header("src/c_shim/trace_gen_core.h").
```

Single supported compiler on every host: **clang**. No MSVC detection, no
MinGW fallback. Fail loudly if clang isn't found — the error message
points at `C:\Program Files\LLVM\bin\clang.exe` and `apt install clang`.

Two inputs we don't need to worry about:

- **`-fshort-enums`.** `epio/Makefile` passes this flag. We grepped
  `include/epio.h` — it contains zero `typedef enum`. The one `enum` case
  inside the library is a type we never see across the FFI boundary, so
  there's no ABI mismatch to worry about. Skip the flag.
- **Native C enum ABI.** Nothing exported through `epio.h` uses a C enum
  — bindgen produces pure function + struct bindings.

### 6.2. `wrapper.h`

```c
#include <epio.h>
```

One line. That is the entire bindgen input.

### 6.3. `src/lib.rs`

```rust
#![allow(non_upper_case_globals, non_camel_case_types, non_snake_case)]

// epio public API bindings
include!(concat!(env!("OUT_DIR"), "/epio_bindings.rs"));

// C shim entry points (trace_gen_core.h bindings)

```

No hand-written safe wrappers. Callers (our one binary, inside this
crate) work directly with the bindgen types. A safe layer would be more
code than its only caller.

### 6.4. C shim — `src/c_shim/trace_gen_core.{h,c}`

The shim is a thin bridge between Rust and the `apio` + `epio` world.
It exists because:

- `apio` is macro-based. apio state lives in C globals populated by
  macro expansion. It cannot be driven from Rust.
- `setup_onerom()` is built entirely from apio macros. It lives in C
  whether we like it or not.
- `epio_from_apio()` is the only way to transfer apio's pre-init
  instruction list (used by OneROM's `APIO_SM_EXEC_INSTR(PULL BLOCK)` +
  `APIO_SM_EXEC_INSTR(MOV X, OSR)` init) into epio state. Direct
  `epio_set_instr` + `epio_set_sm_reg` calls would skip that replay.

Exported functions (C side):

```c
// trace_gen_core.h

#include <stdint.h>

typedef struct trace_gen_ctx trace_gen_ctx;

// Build apio state from setup_onerom, then call epio_from_apio,
// then epio_dma_setup_read_pio_chain. Returns opaque context.
trace_gen_ctx *trace_gen_init(void);

// Returns the number of u16 instructions loaded into the given PIO block
// and copies them into the caller-provided buffer (up to buf_len).
uint32_t trace_gen_dump_instr_mem(trace_gen_ctx *ctx, uint8_t block,
                                  uint16_t *buf, uint32_t buf_len);

// Fill a caller-provided struct with the SM registers for the given
// (block, sm) pair.
void trace_gen_dump_sm_reg(trace_gen_ctx *ctx, uint8_t block, uint8_t sm,
                           uint32_t *clkdiv, uint32_t *execctrl,
                           uint32_t *shiftctrl, uint32_t *pinctrl);

// Drive the input pins, step one cycle, then read back pin state.
// out_drive / out_level refer to epio_read_driven_pins / epio_read_pin_states
// truncated to the low 32 bits.
void trace_gen_step(trace_gen_ctx *ctx,
                    uint32_t input_drive, uint32_t input_level,
                    uint32_t *out_drive, uint32_t *out_level);

void trace_gen_free(trace_gen_ctx *ctx);
```

C side implementation (`trace_gen_core.c`) is ~60 lines plus the
verbatim copy of `setup_onerom` from `epio/test/onerom_programs.h` with:

- `#include "test.h"` removed (cmocka contamination)
- The `void **state` parameter retained but unused (no behavioural change)

`setup_onerom.h` in our crate is a straight copy of
`onerom_programs.h` with just that one edit.

## 7. Trace format

Line-oriented text, tab-separated. Two sections separated by a blank
line: **header block** (metadata + program), then **body** (one data
row per PIO cycle).

```
# onerom_2364 differential trace
# version: 2
# generator_sha: <git submodule HEAD of third_party/epio, short>
# scenario: onerom_2364_single_byte
# cycles: 20
# pin_width: 32
#
# Program section (one record per loaded SM, in block/sm order):
#   instr <block> <sm> <count>  <hex16>,<hex16>,...
#   reg   <block> <sm> <clkdiv_hex>  <execctrl_hex>  <shiftctrl_hex>  <pinctrl_hex>
#
instr 0 0 7  0x6080,0x4001,0x0041,0x60a0,0x4001,0x0085,0xa042
reg   0 0 0x00010000 0x00000000 0x40000000 0x58400008
instr 0 1 3  0xa242,0x0062,0x4010
reg   0 1 0x00010000 0x00000000 0x00c40000 0x00400800
instr 0 2 1  0x6008
reg   0 2 0x00010000 0x00000000 0x000c0000 0x40000000
#
# Body rows — columns: cycle, input_drive, input_level, out_drive, out_level
#
0	0x00000100	0x00000000	0x00000000	0x00000000
1	0x00000100	0x00000000	0x00000000	0x00000000
...
12	0x00000100	0x00000000	0x000000FF	0x00000000
```

Design points:

- **All masks are 32-bit hex.** Our PIO's `step` takes `gpio_in: u32`
  and reports `pad_out`/`pad_oe` as `u32`. `epio`'s u64 results are
  truncated to the low 32 bits at the C shim boundary.
- **The program is in the trace.** This replaces the "lift bytecode to
  Rust constants" plan from v0.1. The diff binary loads from the trace
  header — no separate program source, no separate hash check, no drift
  possible between the program the trace was generated against and the
  program the diff binary tries to run.
- **Determinism check.** The trace generator runs the scenario twice
  internally and aborts with a clear error if the two runs produce
  different rows. This guarantees that any row committed to the repo
  is repeatable.

The example bytecode values above are illustrative, not ground truth —
the real values fall out of the `setup_onerom` + `epio_get_instr` path
at generation time.

## 8. Glue DMA (diff binary only)

OneROM's PIO programs expect a chained DMA pair: one channel reads an
address word from SM1's RX FIFO and writes it to SM2's TX FIFO (acting
as the data-byte output SM's input). `epio` implements this via
`epio_dma_setup_read_pio_chain()` — the trace generator uses that
directly, one function call. No glue DMA on the generator side.

Our `mdpicoem-common::pio` has no DMA at all. The **diff binary** adds
a ~30-line Rust mini-DMA **inside** its replay loop, sharing no code
with anything else in the workspace:

```rust
fn tick_glue_dma(pio: &mut PioBlock) {
    // Replicates epio_dma_setup_read_pio_chain(..., src_sm=1, dst_sm=2, ...)
    if let Some(word) = pio.sm[1].rx_fifo.pop() {
        pio.sm[2].tx_fifo.push(word);
    }
}
```

Called once per `pio.step(gpio_in)`, immediately after. Not a step
toward real DMA in `mdrp2350` — real DMA remains out of scope and lives
in future `mdrp2350-periph` work.

## 9. Known `epio` limitations and how we handle each

| Limitation | Our PIO | Resolution |
|-----------|---------|------------|
| Ignores `CLKDIV` | Fractional divider implemented | Run at `clkdiv=1,frac=0` on both sides (enforced by `setup_onerom`) |
| No side-set pins (delays OK) | Implemented | `setup_onerom` doesn't use side-set |
| MOV to/from RX FIFO not supported | Implemented | `setup_onerom` doesn't use it (spot-checked) |
| Fixed 4-word FIFOs (no joining) | Joining implemented | Default 4-word config; no joining in scenario |
| No GPIO input flip-flop delay | **Also absent** (known Phase 6 gap — stores `INPUT_SYNC_BYPASS` but doesn't model synchronizer) | Both sides treat inputs as instant. **Matches**. |
| Limited DMA | No DMA | Glue DMA (§8) on our side only |
| Force-execute via `APIO_SM_EXEC_INSTR` only reachable through `epio_from_apio()` | `force_execute` works, but Phase 6 tech-debt item notes it "passes gpio_in=0" — a known bug we may trip | If the diff binary flags a divergence at the init-time forced instructions, fix the `gpio_in=0` bug in `sm.rs` |

## 10. 2364 MVP scenario

The scenario is Piers' `setup_onerom` verbatim from
`epio/test/onerom_programs.h`, which loads three SMs into PIO block 0:

- **SM0 — CS handler.** WRAP loop reading CS pin; toggles PINDIRS on
  edge. Controls the data-bus drive enable.
- **SM1 — Address reader.** `IN PINS 16` with autopush; pre-loaded with
  a ROM base address via init-time `APIO_TXF` + forced `PULL BLOCK` +
  forced `MOV X, OSR`. Emits `(base + address) * N` into RX FIFO on
  each address-pin sample.
- **SM2 — Data byte out.** `OUT PINS 8` with autopull; consumes TX
  FIFO into the data pins.

Inter-SM data flow: SM1's RX FIFO → (epio DMA chain / our glue DMA) →
SM2's TX FIFO → data pins.

Test stimulus (a single read transaction):

1. Cycles 0–2: CS high (pin 8 driven high). Address pins = 0. Data
   pins should stay undriven.
2. Cycle 3: CS driven low, address = 0x0000.
3. Cycles 3–N: step; data pins should become driven (`out_drive` lower
   byte all 1s). The `out_level` value reflects the byte returned by
   `setup_onerom`'s configured SRAM at address `base + 0` — which we
   read back and commit as ground truth in the trace, not assert on a
   priori.
4. Cycle N+8: CS high again; data pins should become undriven.

Cycle budget: ~20 cycles. Piers' own `test_onerom_program` uses
`epio_wait_tx_fifo(..., count=13)` as its main wait; we use a fixed
20-cycle window so the trace has a stable length.

Pass criterion: every body row of the diff binary's runtime output
matches the committed `onerom_2364.trace` byte-for-byte.

Explicitly out-of-scope for the MVP:

- Bank switching
- Multiple ROMs in a set
- X1/X2 pin overrides
- Any ROM type other than 2364

All follow-ups once the MVP loop is green.

## 12. Risks

- **bindgen on `epio.h`.** Header has zero native enums (confirmed by
  grep). Transitive includes pull in `apio.h` function-like macros;
  we `blocklist_function("APIO_.*")` and bindgen ignores macros anyway.
  Fallback if a macro expansion confuses clang: write a minimal
  `wrapper.h` that manually declares the subset of `epio.h` functions
  we call. About 20 prototypes.
- **`cc::Build` compiler selection.** Cargo's `cc` crate defaults to
  MSVC on Windows. We force clang with
  `.compiler("clang")` — documented in `cc` 1.x. If clang-on-Windows
  produces an unsupported flag error, drop the flag. `epio` uses plain
  C11 with no GCC extensions beyond `__attribute__((visibility))` (the
  `EPIO_EXPORT` macro) which clang understands natively.
- **Trace non-determinism.** The in-process determinism check in the
  generator catches the obvious case (same process, two runs). A
  cross-process check — run twice in separate `cargo run` invocations
  and diff the files — is done manually once before the first commit
  and not automated.
- **`setup_onerom` drift.** Vendored `epio` is pinned to a submodule
  SHA. The committed trace is tied to that SHA. Bumping the submodule
  requires regenerating the trace — a deliberate act, flagged in any
  PR touching `.gitmodules`.
- **OneROM `gpio_in=0` force-execute bug.** Phase 6 tech debt notes
  that `force_execute` in our PIO passes `gpio_in=0` instead of the
  live input mask. `setup_onerom` only uses force-execute for `PULL
  BLOCK` + `MOV X, OSR`, neither of which touches pin state, so this
  specific bug may not bite. If it does, fix in
  `crates/mdpicoem-common/src/pio/sm.rs::force_execute`.

## 13. Open questions

1. **Which `epio` submodule SHA?** Pin to `epio` HEAD at LLD approval
   time; document in `.gitmodules`. Bumping is a deliberate act.
2. **ROM image source.** `setup_onerom` uses `epio`'s internal SRAM
   (`epio_sram_set`) as the backing store; the test expects the ROM
   base address to be pre-populated. For the MVP we pre-populate with
   a deterministic pattern (`sram[i] = (i & 0xFF) as u8`) — not a real
   game ROM — so expected bytes are predictable. Done inside the C
   shim, before `trace_gen_init` returns.
3. **Multi-stimulus traces.** Single stimulus per trace file for the
   MVP. If the corpus grows, revisit — at that point a binary format
   may make more sense than text.
4. **Deleting `epio-sys` from `workspace.default-members` — Cargo
   ergonomics.** Expected behaviour: `cargo build` at repo root skips
   `epio-sys`, `cargo build -p epio-sys` builds it explicitly. Verify
   on the first Stage-A attempt; revisit if Cargo surprises us.
