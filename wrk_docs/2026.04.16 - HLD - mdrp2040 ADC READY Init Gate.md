# HLD — mdrp2040 ADC `CS.READY` Init Gate (Phase A of PicoGUS Bring-up)

Date: 2026-04-16
Phase: A (first blocker in the PicoGUS end-to-end effort tracked in
`wrk_journals/2026.04.16 - JRN - PicoGUS End-to-End Bring-up.md`)
Crate: `mdrp2040`
Author: Design agent (Opus 4.6 1M)
Supersedes: nothing (net-new peripheral behaviour fix).

## 1. Purpose

Real PicoGUS v4.0.0 firmware parks forever in pico-sdk's `adc_init()`
wait-for-READY loop at SRAM PC `0x20012ba6` because our emulator's ADC
model never raises `CS.READY` on a bare `EN`-only write. The SDK
canonical init — `hw_set_bits(&adc_hw->cs, ADC_CS_EN_BITS); while
(!(adc_hw->cs & ADC_CS_READY));` — exercises a power-up path the Phase 3
test corpus (which always issued `EN|START_*` together) did not cover.
Phase A plugs that hole as the single blocker standing between the
emulator and the next phase of PicoGUS bring-up.

## 2. Root cause

Citations are `C:\language\mdrp2354\crates\mdrp2040\src\peripherals\adc.rs:<line>`.

- `AdcRegs::new` (line 158–174) zeroes `cs`, so `CS.READY = 0` at reset.
- `AdcRegs::reset` (line 176–179) delegates to `new`, same state.
- `CS_WRITE_MASK` (line 87–93) deliberately excludes `CS_READY`, and
  `write32` for `CS` (line 378–386) preserves only the existing
  `CS_READY | CS_ERR` bits — firmware cannot write `READY` directly.
  **This invariant must be preserved** by any fix.
- The **only** place `CS_READY` is set today is inside
  `complete_conversion` at line 268, reached only when
  `conversion_remaining` counts down to zero.
- `conversion_remaining` is armed only by `maybe_start` (line 308–321),
  which requires both `CS_EN` **and** one of
  `CS_START_ONCE | CS_START_MANY`.
- On real silicon the ADC macro asserts `READY` after its analog block
  completes a ~200 µs power-up stabilisation once `EN` transitions
  low→high — independent of any pending conversion (RP2040 datasheet
  §4.9.5 / §4.9.6: "READY: 1 if the ADC is ready to start a new
  conversion" — in reset the bit is `0`).

### Why Phase 3 missed it

`crates/mdrp2040/src/peripherals/adc.rs:580–594`
(`start_once_completes_sets_ready_and_result`) and the FIFO /
START_MANY tests all write `CS = CS_EN | CS_START_ONCE | AINSEL` or
`CS_EN | CS_START_MANY` in a single store. With a START bit set,
`maybe_start` arms a conversion immediately and `complete_conversion`
latches `READY` on completion. The SDK's "write `EN`, then poll
`READY` **before** writing any `START`" sequence never got exercised.

### Secondary: fast-path gating

After an `EN`-only write, `is_idle()` (line 189–194) returns `true`
(no conversion pending, no FIFO entries, `INTR == 0`, no `START_*`
bits). `Bus::all_peripherals_idle()` (`bus/mod.rs:1443`) folds that
into the fast-path gate consulted by `Emulator::step`
(`lib.rs:330`). So on the emulator today, `Adc::tick` may not even be
called while firmware spins. Any option that relies on `tick()` to
flip `READY` must either open the fast path (gate on "EN set but
READY clear") or accept that the tick-path fix only works when some
other peripheral is keeping the slow path open — which is not
guaranteed in `adc_init()` (pico-sdk resets all blocks via RESETS,
then programs ADC before anything else that would keep the bus busy).

## 3. Design options

Three options considered; all preserve the `CS_WRITE_MASK` invariant
that firmware writes to bit 8 of `CS` are dropped on the floor.

### Option A — Synchronous latch in `write32(CS)` on EN 0→1

In `write32(CS)` (line 378–386), after the normal merge, detect an
`EN` low→high transition. If the post-merge value has `EN=1` and no
conversion is currently in flight (`conversion_remaining.is_none()`),
set `CS_READY` in the stored `cs` **synchronously**, inside the same
write.

- **Pros**: Single write-site change, ~5 lines. No bus/tick plumbing
  touched. Firmware's next poll of `CS` observes `READY=1` on the
  very next load, matching the SDK's assumption that a handful of
  poll iterations suffice. Works whether the slow path is open or
  not — no dependence on `tick_peripherals`. Easy to reason about.
- **Cons**: Zero-delay model — on real silicon there is a ~200 µs
  `clk_adc`-scaled stabilisation window. Our other peripherals
  (UART, SPI, PLL_LOCK) tend to emulate similar macro delays; this
  one departs from that pattern. That said, the pattern isn't
  uniform (DIV is pure storage; TIMER lazy-polls) and PicoGUS does
  not time the ready window.
- **Impact on Phase 3 tests**: `start_once_completes_sets_ready_and_result`
  arms a conversion in the same write, which means `maybe_start`
  runs after our new `READY=1` latch and clears `READY` for the
  conversion window (line 319). The test asserts `READY=1` after
  `tick(400)` so it still passes. `cs_write_cannot_set_ready_directly`
  writes `CS_READY` with `EN=0` → no latch (EN not low→high) →
  `READY` stays 0. Still passes. `is_idle_true_after_completion_and_drain`
  clears EN with BITCLR; the pre-write EN state was 1 so no 0→1
  transition → no latch. Still passes.
- **Impact on other SDK paths**: `adc_select_input` writes
  `AINSEL` via `hw_write_masked` while `EN=1` — no 0→1 edge, no
  latch change. `adc_run(true)` sets `START_MANY` while `EN=1` — no
  edge. `adc_fifo_setup` / `adc_set_clkdiv` do not touch `EN`.

### Option B — Latch in `tick()` when enabled and idle

Add to `tick` (line 447): when entering with `is_enabled() &&
conversion_remaining.is_none() && (cs & CS_READY) == 0`, set
`CS_READY` on the first tick.

- **Pros**: Keeps all READY-setting on the peripheral-driven side
  (intuitive mental model: "tick resolves state"). Handles the
  `EN` being set via the BITSET alias path without any additional
  conditional — the next tick does the right thing regardless of
  how EN arrived.
- **Cons**: **`all_peripherals_idle()` returns true after the
  `EN`-only write** (see §2 "Secondary"), so the fast path opens
  and `tick_peripherals` isn't called. The fix would silently
  depend on another peripheral (TIMER alarm, UART shifting) holding
  the slow path. PicoGUS `adc_init()` runs extremely early in main
  — no guarantee another peripheral is busy. To make Option B
  work we'd need to change `AdcRegs::is_idle` to return `false`
  while `EN=1 && READY=0`, which is a second change and closes the
  fast path for a potentially large firmware window (the spin-wait
  itself). The fast-path gate exists for a reason; widening it is
  a perf regression we don't want to chase.
- **Impact on Phase 3 tests**: same as Option A for the conversion
  tests. Would additionally require amending `is_idle`, which
  shifts `is_idle_true_after_completion_and_drain` behaviour
  depending on whether the end state still has EN set.

### Option C — Realistic `clk_adc` power-up countdown

On `EN` 0→1, start a power-up countdown in `clk_adc` ticks (say
`READY_POWERUP_ADC_TICKS = 2048` ≈ ~43 µs, tunable). Clear `READY`
if it was set. Advance the countdown inside `tick`; when it hits 0,
set `READY`. Track the countdown with a new `ready_delay:
Option<u32>` field next to `conversion_remaining`.

- **Pros**: Closest to real silicon. Gives us a principled place to
  park any future `READY` transition (e.g. clearing on EN=1→0 when
  we decide what silicon does there).
- **Cons**: Same fast-path problem as Option B, plus a new `Option<u32>`
  field, plus a magic number with no clear silicon oracle available
  to us today (§4.9.6 gives the 96-`clk_adc` conversion latency but
  no documented `READY` power-up figure — SDK just polls). PicoGUS
  does not time this interval, so the "accuracy" is unverifiable.
  More moving parts, more test surface, zero user-visible gain.
- **Impact on Phase 3 tests**: `start_once_completes_sets_ready_and_result`
  writes `EN|START_ONCE` in a single store. The new power-up
  countdown starts on the same write, runs concurrently with the
  96-tick conversion countdown. Current tick budget (400 sys_clk)
  ≈ 153 adc sub-ticks — well inside a 2048-tick power-up window.
  **The test would start failing** because `READY` would no longer
  be set at the end of the 400-cycle window. We'd have to retune
  every existing ADC test. Not worth it.

## 4. Recommendation

**Option A**. Smallest change, preserves the
`CS_WRITE_MASK`-excludes-READY invariant (firmware still cannot set
`READY` via a write — the peripheral sets it based on observing the
`EN` low→high transition), does not require any change to fast-path
gating, does not perturb existing Phase 3 tests, and fixes the exact
observed PicoGUS blocker. Option C's extra fidelity has no oracle we
can check and would break our own unit tests; Option B requires
widening the slow-path gate for dubious benefit.

The concrete change is inside `AdcRegs::write32` for the `CS` arm
(line 378–386 today):

```rust
CS => {
    let old_cs = self.cs;
    let mut stored = self.cs;
    apply_alias_rmw(&mut stored, value, alias);
    self.cs = (stored & CS_WRITE_MASK) | (self.cs & (CS_READY | CS_ERR));
    // Power-up latch: silicon asserts READY after EN 0->1 once the
    // analog block stabilises (~200 µs). We model that as a zero-
    // delay transition so the pico-sdk `adc_init()` poll loop exits
    // on its first re-read. maybe_start() below will then clear
    // READY again if the same write armed a conversion — that keeps
    // the existing Phase 3 behaviour intact.
    if (old_cs & CS_EN) == 0
        && (self.cs & CS_EN) != 0
        && self.conversion_remaining.is_none()
    {
        self.cs |= CS_READY;
    }
    self.maybe_start();
}
```

The `CS_READY` invariant is preserved by the *ordering*: the write
first funnels through `CS_WRITE_MASK` (which doesn't include
`CS_READY`), so a firmware write of `CS_READY` alone with `EN=0`
still produces `cs = 0`, and the `old_cs.EN == 0 && new.EN == 1` edge
test then won't fire. The existing
`cs_write_cannot_set_ready_directly` regression continues to hold.

## 5. Interaction with `EN` 1→0

Datasheet §4.9.6 describes `READY` as an instantaneous "ADC is ready
to start a new conversion" flag, and §4.9.5 says that clearing `EN`
powers the ADC down. On real silicon the ADC cannot be ready while
powered down, so `READY` should follow `EN` back to zero.

**Decision**: on an `EN` 1→0 transition, clear `CS_READY`. This is a
second edge case in the same `write32(CS)` arm — we add it alongside
the 0→1 latch. Rationale: cheap to implement, matches silicon's "ADC
off → not ready" semantics, and avoids a stale `READY=1` surviving a
power-cycle that firmware later polls. No existing test writes `EN`
back to 0 and then reads `READY`, so there's no regression risk. The
SDK's `adc_init()` never clears `EN`, so PicoGUS is not sensitive to
this path either way — but correctness is correctness.

## 6. Interaction with mid-conversion `EN` clear

If firmware clears `EN` while `conversion_remaining.is_some()`, we:

1. Drop `conversion_remaining` to `None` (abort the in-flight
   conversion — the analog block is powering down).
2. Clear `CS_READY` (§5).
3. Leave `last_sample` / FIFO contents untouched — firmware can still
   drain whatever was already committed.
4. Do **not** clear `CS_START_ONCE` / `CS_START_MANY` — firmware's
   stored request is round-trip; on the next `EN` 0→1 those bits (if
   still set) rearm via `maybe_start`.

This is the behavioural choice. Real silicon here is under-documented
and not exercised by PicoGUS. Deviations would surface as a future
probe_diff_rp2040 case if we care; for Phase A this keeps the model
internally consistent.

## 7. Test plan (TDD order)

Tests live in the existing `#[cfg(test)] mod tests` at the tail of

### 7a. Unit tests (new)

1. **`en_alone_sets_ready`** — fresh `AdcRegs`; write `CS = CS_EN`;
   assert `cs & CS_READY == CS_READY` immediately after the write
   (synchronous latch, Option A semantics). Regression guard for
   the exact PicoGUS blocker.

2. **`en_then_sdk_style_poll_exits`** — fresh `AdcRegs`; write `CS =
   CS_EN`; read `CS`, confirm `READY=1`. This mirrors pico-sdk
   `adc_init`'s `while (!(adc_hw->cs & ADC_CS_READY))` loop exit
   condition. No `tick` call required with Option A — the test
   documents that property.

3. **`conversion_in_flight_clears_ready_then_restores`** — write
   `CS = CS_EN` (READY latches). Assert `READY=1`. Then write `CS
   |= CS_START_ONCE` via BITSET alias. Assert `READY=0` right after
   (maybe_start clears it). `tick(400, …)`. Assert `READY=1`
   (complete_conversion sets it again). This explicitly locks
   down the three-state transition: powered-up → converting →
   complete.

4. **`en_cleared_clears_ready`** — write `CS = CS_EN`; assert
   `READY=1`. Write `CS &= ~CS_EN` (via BITCLR alias of `CS_EN`).
   Assert `READY=0`. Covers §5.

5. **`en_cleared_midconversion_cancels`** — write `CS = CS_EN |
   CS_START_ONCE` (conversion armed, READY cleared by
   maybe_start). Without ticking, write BITCLR `CS_EN`. Assert
   `conversion_remaining == None` and `READY=0`. Covers §6.

6. **`bitset_en_alias_path_sets_ready`** — write `CS = 0` (EN=0);
   then write `CS = CS_EN` via BITSET alias. Assert `READY=1`.
   Confirms the edge detection works through the alias RMW.

### 7b. Unit tests (regressions — must still pass)

   Writing `CS_READY` with EN=0 produces `cs=0` (READY excluded by

8. **`start_once_completes_sets_ready_and_result`** (line 580) —

### 7c. Integration test (new, `crates/mdrp2040/tests/firmware.rs`)

11. **`adc_init_sdk_pattern_exits_ready_poll`** — hand-assembled
    Thumb stub that mirrors `adc_init()`. Success detection uses
    option **(b)** — a `B .` self-branch sentinel at a known address
    — matching the existing `gpio_blink_program_drives_pin0_high`
    idiom (`crates/mdrp2040/tests/firmware.rs:12,29,41–60`). That
    test hand-assembles Thumb, terminates with `B .` (`0xE7FE`,
    branch to PC-2), steps a fixed count, and asserts final state
    via direct bus reads. Reused here verbatim. `BKPT` is rejected:
    on ARMv6-M it escalates to HardFault, and with no vector table
    at VTOR=0 the stacked frame reads garbage and re-faults, giving
    unpredictable final PC. The `B .` sentinel is cleanly
    distinguishable from the inner poll loop because the inner
    loop's back-branch target differs from the exit sentinel's
    address — asserting `PC == exit_sentinel_addr` rules out
    "still spinning on the poll".

    Exact stub (loaded at `0x2000_0000`):

    ```text
    ; r0 = ADC_BASE (loaded from literal pool)
    ; r1 = CS_EN = 0x1
    ; r2 = CS_READY mask = 0x100
    ; 0x2000_0000: 4B04        LDR  r3, [PC, #16]   ; r3 = ADC_BASE
    ; 0x2000_0002: 2101        MOVS r1, #1          ; r1 = CS_EN
    ; 0x2000_0004: 2280        MOVS r2, #0x80
    ; 0x2000_0006: 0052        LSLS r2, r2, #1      ; r2 = 0x100 (CS_READY)
    ; 0x2000_0008: 6019        STR  r1, [r3, #0]    ; adc_hw->cs = EN
    ; poll: (0x2000_000A)
    ; 0x2000_000A: 681C        LDR  r4, [r3, #0]    ; r4 = adc_hw->cs
    ; 0x2000_000C: 4214        TST  r4, r2          ; r4 & CS_READY
    ; 0x2000_000E: D0FC        BEQ  poll            ; back to 0x2000_000A
    ; exit: (0x2000_0010)
    ; 0x2000_0010: E7FE        B    .              ; self-loop sentinel
    ; 0x2000_0012: BF00        NOP                  ; align literal pool
    ; 0x2000_0014: 0000 404C   .word 0x4004_C000    ; ADC_BASE
    ```

    Test harness: pre-clear RESETS bit 0 for ADC (the default `Bus`
    holds ADC in reset — see `bus/mod.rs:2135`) via
    `emu.bus.write32(RESETS_BASE + CLR_ALIAS, 1 << 0)`; set core-0
    PC to `0x2000_0000`, SP to `0x2002_0000`, xPSR Thumb bit (same
    shape as `gpio_blink_program_drives_pin0_high`). Step 64
    instructions. Assert `emu.cores[0].regs.pc() == 0x2000_0010`
    (the `B .` sentinel address) — this rules out both "still in
    poll loop at `0x2000_000A`" and "faulted into 0x0000_0000".
    Proves the fix works through the full bus path — the same path
    PicoGUS exercises.

    This is the test Phase 3 never wrote and which the PicoGUS
    blocker retroactively motivates.
