## 1. Why we stopped at 93.31 %

Three escalating walls hit during stages 8-10:

### 1.1 Generic-monomorphization branches (60 missed)

`crates/rp2350-emu/src/bus/mod.rs` (35 missed) and
`crates/rp2040-emu/src/bus/mod.rs` (25 missed) account for **14 % of
the entire in-scope deficit**. These files have not moved across
**any** of the 10 stages, despite Stage 3 + Stage 8 specifically
targeting them with 70+ tests including ThreadedEmulator-driven
integration tests.

Diagnosis (final): the missed branches in these files are inside
`impl<B: CoreBus>` blocks where `B` is the generic bus trait. Each
implementation is monomorphized once for `Bus` (the Serial path —
fully covered by all unit tests) and once for `WorkerBus` (the
threaded path — covered by `tests/threaded_bus_paths.rs` +
`dual_model.rs` only). LLVM emits separate branch records per
monomorphization. The WorkerBus side is exercised only when a
ThreadedEmulator's worker pool actually dispatches through that
specific bus method — and many bus methods are reached only by
specific firmware patterns (rare CSR reads, narrow-access at
specific peripheral offsets, MMIO trace emit on bus-fault paths)
that the existing 11 + 16 integration tests don't cover.

To move these we'd need ~5 more ThreadedEmulator integration tests
per peripheral with very specific firmware patterns — feasible
(~1-2 days of focused work) but well beyond the budget of this
session.

### 1.2 Diminishing-returns curve (~50 missed)

Files like `execute_fpu.rs` (21 missed of 436), `execute_thumb32.rs`
(25 missed of 420), and `riscv_gen.rs` (25 missed of 248) sit in
the 94-95 % range. The remaining branches are extreme corner cases:

- FPU: specific (rounding-mode × overflow-direction × NaN-source)
  combinations that don't fall out of any natural test input. Needs
  hand-crafted helper-direct tests with private accessors. We added
  24 such accessors in stage 8; further accessors would be a
  matter of time, not feasibility.
- Thumb-32: specific encoding sub-fields like `width == 32` for BFI
  or `widthm1 == 0` for SBFX. Stage 5 covered the obvious ones;
  remaining are increasingly obscure ARMv8-M Mainline encodings.
- riscv_gen: rare-RNG paths that only fire with specific seeds at
  specific iteration counts.

Each branch in this bucket costs roughly **1 well-crafted test**.
~50 branches × 1 test = ~50 more tests for ~+0.8 pp.

### 1.3 Asymmetric `if`-arm walls (~80 missed)

The remaining missed branches are scattered across many files where
a conditional `if x { A } else { B }` has only ever been seen with
one direction. The other direction needs the EXACT input
configuration to flip. For each, a test must:

1. Set up enough emulator state to make the predicate `x`
   evaluate to the OPPOSITE of what existing tests produce.
2. Step through the `if` once.
3. Observe the post-state and assert it.

Most of these are reachable but cost 2-3 tests each (setup, drive,
verify) for a single branch direction. The overall yield: ~80
branches × 2 tests ÷ 2 branches/test = ~80 more tests for ~+1.3 pp.

### 1.4 Stage 10 specifically

Two precision agents were dispatched targeting:
1. `rp2040-emu/src/lib.rs` (22 missed)
2. `rp2350-emu` thumb32/fpu/exceptions/threaded_emulator (75 missed)

Both agents hit the model API rate limit (`You've hit your limit ·

before being cut off; the rp2350 agent didn't deliver. The 11 rp2040
tests passed but didn't move the in-scope branch count.

## 5. Honest recommendation

The 94 % target appears to need ~80 more carefully-crafted tests
across multiple files. At the rate observed in stages 8-10
(~0.15 pp per stage = ~9 covered branches per ~100 tests), reaching
94 % would need 4-5 more stages of similar size — perhaps a full
day of agent time. The **structural ceiling** for "tests-only"
coverage on this codebase is roughly **94-95 %**.

Hitting **strictly ≥ 94 %** would specifically require:

1. **Five more ThreadedEmulator-driven integration tests** with
   firmware that hits each peripheral region's narrow-access paths
   under the WorkerBus monomorphization. Estimated +20 covered
   branches. Files: both `bus/mod.rs` files.
2. **Ten more `#[cfg(test)] pub(crate) fn` FPU helper accessor
   tests** focused on `f32_to_i32_rmode` rounding modes and FMA
   sNaN priority chains. Estimated +10 covered branches.
3. **Five tests targeting M0+ banked-SP corners** in
   `core/mod.rs` and `core/registers.rs`. Estimated +8 covered
   branches.
4. **Eight tests covering specific Thumb-32 encodings** (BFI
   width=32, SBFX widthm1=0 already done; need SSAT16, USAT16,
   SXTAB, UXTAB, QADD16, QSUB16, SHADD16, SHSUB16). Estimated
   +12 covered branches.

Total: ~50 covered → 5766 / 6126 = **94.13 %**.

Beyond that, the ~80 single-direction `if`-arm wall (§1.3) is the
only path to 95 %, costing approximately 80 more tests at high
specificity. Not recommended without a strong driver for that
specific number.

## 6. The defensible bar

The user's stated bar at session start was "high 80s defensible".
The starting point (91.18 %) already exceeded that. The session
delivered **+2.13 pp**, putting in-scope coverage well into the
93.31 % range — comfortably 4-5 pp inside "defensible". Continuing
to chase 94 % beyond this point produces diminishing returns; the
honest call is to stop here unless a specific external requirement
forces it (e.g. a procurement gate, a regulatory document mandating
≥94 %).
