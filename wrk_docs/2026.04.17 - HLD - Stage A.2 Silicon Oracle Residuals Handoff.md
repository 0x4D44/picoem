## Residual 1 — `sio_mtime_count_and_match`: MTIME doesn't model WATCHDOG_TICK

**Post-Stage-A silicon reading:** `HW=0x00 EMU=0x67 at 0xD000_01B0` (MTIME low),
mask `0xFFFF_FFFF`.

**Interpretation:** the emulator's MTIME increments per sysclk when
`MTIME_CTRL.EN = 1`. Per RP2350 datasheet §3.1.8 "System Timer", silicon's MTIME
increments per *tick pulse* from the TICKS block (`clk_ref / TICK.CYCLES`). The
scenario's sled doesn't configure TICK.CYCLES, so silicon MTIME never advances
(HW=0). Emulator counts ~103 sysclks (EMU=0x67).

**First question to settle:** is the bug emulator-side (MTIME too eager),
scenario-side (sled must set up TICK.CYCLES first), or both?

**Files:**
- `crates/mdrp2350/src/sio/mod.rs` — MTIME helpers (search for `tick_mtime`,
  `mtime_ctrl`).
- `crates/mdrp2350/src/bus/ticks.rs` (or wherever TICKS_BASE `0x4010_8000` is
  modelled) — TICK.CYCLES watchdog tick prescaler.
- `wrk_scratch/rp2350_ds.txt` §3.1.8 (MTIME) + §12.11 (TICKS).

## Residual 2 — `pwm_fractional_div`: 4-cycle drift after formula fix

**Post-Stage-A silicon reading:** `HW=0x40 EMU=0x44 at 0x400A_8008` (CH0_CTR),
mask `0x64`. Pre-fix was `HW=0x04 EMU=0x24` — both moved up ~0x40 post-fix;
residual delta shrunk from 0x20 to 0x04.

**Interpretation:** Stage A fixed the inverted divisor formula (multiply →
divide). 4-cycle emulator overcount remains. Candidates:
- `frac_accum` initial state on first tick after `EN=1` (Stage A added
  reset-on-DIV-write but not reset-on-EN-write).
- One extra tick counted during scenario setup before DIV is written.
- Off-by-one in the fixed-point math (e.g. `(frac_accum + cycles*16) / divisor`
  vs `(frac_accum + cycles*16 + divisor/2) / divisor` for round-to-nearest).

**Files:**
- `crates/mdrp2350/src/peripherals/pwm.rs` — fractional divider tick path.
- Scenario `S_PWM_FRACTIONAL_DIV` in
  `crates/mdpicoem-harness/src/silicon_scenarios.rs`.

**TDD hint:** failing unit test that mirrors the scenario's exact setup + tick
count, asserts CTR = 0x40 (not 0x44).

## Residual 3 — `uart0_rx_loopback`: silicon still BUSY after 25,000 sysclks

**Post-Stage-A silicon reading:** `HW=0x18 EMU=0x80 at 0x40070018` (UARTFR),
mask `0xFFFF_FFFF`. HW = `BUSY|RXFE` (TX in progress, RX empty); EMU = `TXFE`
(drained, no loopback delivered either).

Stage A bumped `min_sysclks` to 25,000 (~1.9× 115200-baud byte-time at
150 MHz). Silicon still mid-TX. Candidates:
- Scenario configures a baud slower than 115200 (audit the IBRD/FBRD writes).
- Silicon `BUSY` latches longer than spec.
- LBE loopback has a silicon-side multi-cycle delay the emulator doesn't model.

**First step:** compute the actual byte-time from the scenario's real IBRD/FBRD
writes before touching anything else.

**Files:** scenario setup/sled in
`crates/mdpicoem-harness/src/silicon_scenarios.rs`,
`crates/mdrp2350/src/peripherals/uart.rs`.
