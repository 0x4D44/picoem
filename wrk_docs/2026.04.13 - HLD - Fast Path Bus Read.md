# Fast Path Bus Read

Version: 1.0.0
Date: 2026-04-13

## Problem

Flamegraph shows the bus fetch path at 20% of total emulator time:

| Function | Self | Inclusive |
|----------|------|-----------|
| `Bus::read16()` | 6% | 20% |
| `Bus::check_contention()` | 8% | 8% |
| `Memory::bank_for_address()` | 3% | 3% |
| `sram_bank_wait()` | 2% | 2% |

Every instruction fetch follows this call chain:

```
decode_execute
  -> bus.read16(pc)
       -> Self::read_latency(region)    // already #[inline(always)]
       -> self.check_contention(addr)   // #[inline(always)] but calls...
            -> Self::downstream_port()  // NOT inlined -- separate function
                 -> Memory::bank_for_address()  // NOT inlined
       -> self.memory.sram_read16()     // NOT inlined
       -> sram_bank_wait()              // NOT inlined, free function
```

For the overwhelmingly common case -- single core executing from SRAM with
no contention -- the work is: shift `addr >> 28` to get `0x2`, return
`(1, 0)` latency, call `check_contention` which calls `downstream_port`
which calls `bank_for_address` to compute a port number then compares it
against `core0_port` (which is `None` because contention checking is
inactive), record the port as `core0_port`, strip alias bits, read two
bytes from a `Vec<u8>`, and call `sram_bank_wait` to check if this is
bank 2 or 6.

The work is correct. The problem is that it spans 5 non-inlined function
calls (6 if you count `sram_read16` in `Memory`). LLVM cannot inline
across this many boundaries when the functions are in different impl blocks
and some are `pub`. The call/return overhead and the inability to fold
constants across call boundaries is why 8% of total time is in
`check_contention` alone -- a function whose hot path is: read one bool
(`contention_check_active`), see it's false, write one `Option<u8>`, return 0.

## Root cause

The following functions lack `#[inline(always)]`:

**`Bus` methods (in `crates/mdrp2354/src/bus/mod.rs`):**
- `read16()` (line 534) -- the main entry point, ~75 lines
- `read32()` (line 699) -- same pattern, ~68 lines
- `write16()` (line 610) -- same pattern
- `write32()` (line 768) -- same pattern
- `read8()` (line 377) -- same pattern
- `write8()` (line 446) -- same pattern
- `downstream_port()` (line 188) -- called from `check_contention`
- `sram_bank_wait()` (line 852) -- free function, called from all SRAM paths

**`Memory` methods (in `crates/mdrp2354/src/memory/mod.rs`):**
- `sram_read16()` (line 63)
- `sram_read32()` (line 72)
- `sram_read8()` (line 59)
- `sram_write16()` (line 93)
- `sram_write32()` (line 102)
- `sram_write8()` (line 86)
- `rom_read16()` (line 34)
- `rom_read32()` (line 43)
- `xip_read16()` (line 123)
- `xip_read32()` (line 132)
- `bank_for_address()` (line 156)

Three functions already have `#[inline(always)]`: `check_contention`,
`read_latency`, `write_latency`. These are the smallest helpers. The
larger callers and callees around them are not annotated.

## Proposed change

Add `#[inline(always)]` annotations. Nothing else.

### Phase 1: Bus hot path (highest impact, lowest risk)

Add `#[inline(always)]` to:

1. `Bus::downstream_port()` -- called every bus access via `check_contention`.
   Currently a `match addr >> 28` with an inner call to `bank_for_address`.
   Once inlined into `check_contention`, LLVM can see the whole contention
   path as a single basic block when `contention_check_active` is false:
   compute port, store it in `core0_port`, return 0.

2. `sram_bank_wait()` -- called from every SRAM read and write. A small
   function (15 lines) with two branches. Inlining lets LLVM fold the
   `burst_mode` check with the caller's context.

3. `Memory::bank_for_address()` -- called from `downstream_port`. Small
   (15 lines), pure arithmetic on the address. Once both are inlined into
   `check_contention`, the entire contention-check + bank-wait path
   collapses into arithmetic on `addr` with no function calls.

### Phase 2: Memory accessors (moderate impact, zero risk)

Add `#[inline(always)]` to all `Memory` read/write methods:
`sram_read8/16/32`, `sram_write8/16/32`, `rom_read8/16/32`,
`xip_read8/16/32`.

These are trivial (bounds check + byte extraction from a `Vec<u8>`).
They are called from `Bus::read16/32` etc. which are already large
functions, so LLVM's inlining cost model may decline to inline them
without the annotation. Forcing it eliminates the call/return overhead
and lets LLVM combine the bounds check with the caller's region dispatch.

### Phase 3: Bus entry points (optional, measure first)

Add `#[inline(always)]` to `Bus::read16()`, `read32()`, `write16()`,
`write32()`, `read8()`, `write8()`.

These are large functions (60-80 lines each) with complex match
dispatches. Inlining them into `decode_execute` could let LLVM
specialize the fetch path (the PC is always in SRAM or ROM, never in a
peripheral register). However, inlining 6 large functions into every call
site risks code bloat and instruction cache pressure.

**Recommendation:** implement phases 1 and 2 first, measure, and only
add phase 3 if the flamegraph still shows significant overhead in the
bus entry points themselves (the 6% self time in `read16`).

## What does NOT change

- **Cycle-accurate timing is preserved.** Every code path still executes
  the same sequence of operations: `read_latency`, `check_contention`
  (including `downstream_port` and `bank_for_address`), the actual memory
  read, and `sram_bank_wait`. The same `extra_wait_states` are accumulated.
  `#[inline(always)]` only affects code generation, not semantics.

- **Bus structure and API.** No fields added, no method signatures changed,
  no methods moved or reorganized. All existing callers compile unchanged.

- **Contention model.** `check_contention`, `downstream_port`,
  `bank_for_address`, and `sram_bank_wait` keep their current logic.
  The optimization is that LLVM can now see through the call chain and
  eliminate overhead, not that we skip any work.

- **Burst mode.** `sram_bank_wait` still checks `burst` and returns 0.
  When inlined, the `self.burst_mode` load can be hoisted or folded but
  the result is identical.

## Expected impact

The 8% self time in `check_contention` is almost entirely call/return
overhead for a function whose hot path (when `contention_check_active` is
false) is: compute port (2 shifts, 1 match), write an `Option<u8>`, return
0. When inlined with `downstream_port` and `bank_for_address`, LLVM should
reduce this to a handful of instructions directly in the caller's body.

Conservative estimate: 10-15% total emulator speedup from phases 1+2
(recovering most of the 20% inclusive time, minus the irreducible work of
the address dispatch and memory read).

## Impact on existing tests

None. `#[inline(always)]` is a codegen directive. All existing tests
exercise the same bus paths and will produce identical results.

## Risks

**Code size.** Inlining `downstream_port` (17 lines) and
`bank_for_address` (15 lines) into every `check_contention` call site
adds ~50 instructions per bus access method (6 methods). Total: ~300
extra instructions. At 4 bytes each, ~1.2 KB. Negligible vs. icache.

**Phase 3 code bloat.** Inlining the 60-80 line `read16`/`read32` etc.
into every call site in `decode_execute`, `execute_thumb16`, and
`execute_thumb32` could add 5-10 KB of code. This should be measured
before committing to. If icache pressure increases, it may offset the
gains from eliminating call overhead.

**Compile time.** More inlining means more work for LLVM's optimizer.
Unlikely to be noticeable for a crate of this size.
