# 2026.04.25 — HLD — USB + HSTX Stubs + Bootrom Mask-ROM (V4)

Iterates V3 (`2026.04.25 - HLD - USB + HSTX Stubs + Bootrom Mask-ROM V3.md`)
on a third review pass. Material changes flagged inline as **(R4)**.

## Goal

Close three remaining RP2350 firmware-fidelity gaps so that pico-sdk
firmware touching USB init, HSTX config, or bootrom service functions
executes to steady state in the emulator without faulting.

1. **USB** — register-surface stub (no protocol).
2. **HSTX** — register-surface stub (no pixel stream).
3. **Bootrom mask-ROM** — `rom_table_lookup_entry_point`-resolved calls
   run their documented semantics by executing the real RP2354 bootrom
   binary plus a small PC-hook for the few functions whose dependencies
   we don't emulate.

**Workload value** is uneven across the three:

- Component 3 (bootrom) is high-value: any pico-sdk firmware that calls
  `flash_range_program`, `connect_internal_flash`, or `reboot` blocks
  on this. OneROM and any future RP2350 firmware that touches flash
  fall in scope. (Note: PicoGUS is RP2040 only, not an RP2350 driver.)
- Components 1 and 2 (USB/HSTX) are pre-emptive insurance: no current
  RP2350 workload in-tree is blocked by them. **Defer threshold**: if
  Stage 0 discovery reveals either component would take >50% above the
  line estimate (USB ≥375 lines, HSTX ≥120 lines), defer it to its
  own future HLD when a real workload requests it. This is the
  explicit YAGNI escape hatch.

Success criterion per component is "firmware exercising this subsystem's
init runs without asserting or entering a fault loop," measured by the
firmware tests listed in each Oracle section.

## Explicit non-goals

- USB protocol emulation, host mode, device enumeration, CDC passthrough.
- HSTX pixel-stream observability, DVI/DPI capture.
- BOOTSEL UF2 drive emulation — `reboot` with BOOTSEL flag shuts the
  emulator down cleanly; UF2 ingest stays out of scope.
- Secure-boot verification through the bootrom path.
- RISC-V Hazard3 bootrom path. The design must not regress Hazard3
  execution — see "Hazard3 isolation" in Component 3.

No feature flags. No environment variables. No migration / back-compat.
The two new peripherals and the bootrom hook land directly in
`mdrp2350`.

## Stage 0 — Survey (cheap, do first; no code lands until it completes)

Stage 0 is the design's branch point. Five facts must be confirmed,
each recorded in the implementation journal with the exact answer and
evidence.

**Sign-off enforcement.** Stage 0 sign-off is a **commit-message
trailer convention**, not CI. Every commit landing Component 1, 2, or 3
code must include:

```
Stage-0-journal: wrk_journals/2026.MM.DD - JRN - V4 Stage 0 Survey.md
```

Reviewers (human or agent) reject Component-1/2/3 commits without the
trailer. Soft norm, visible at review time. **Acknowledged limitation**:

### Fact 1 — bootrom binary layout

`roms/rp2350/bootrom-combined.bin` is exactly 32 KB.
`mdpicoem-common::memory::ROM_SIZE` is also 32 KB. Required:

- Hex-dump the file. Where does the Arm bootrom image start and end?
  `arm-bootrom.dis` shows Arm Thumb code at offset 0; is the back half
  Arm Secure-only, RISC-V (Hazard3 boot path), or padding?
- If real silicon expects more than 32 KB of bootrom space, hook
  resolution lands on bytes we never loaded.

**(R4) Fallback caveat.** If Fact 1 reveals truncation, the fix is
NOT a one-line constant bump:

- `mdpicoem-common::memory::load_rom` clamps to the *const* `ROM_SIZE`
  (`crates/mdpicoem-common/src/memory.rs:60` — `data.len().min(ROM_SIZE)`).
- `crates/mdrp2350/src/bus/mod.rs:546` constructs `Memory::new()`
  which hard-codes the const.
- The threaded subtree adds further `SharedMemory::new()` call sites.

The fallback is a multi-file refactor (common + mdrp2350 bus + threaded
subtree) and a constant change in a crate shared with mdrp2040. **Stage
0 confirms the refactor is tractable before committing to it** — a
half-day spike with a per-chip ROM_SIZE goes in the journal as part of
Fact 1's answer.

### Fact 2 — bootrom executes through `rom_table_lookup`

Pico-sdk's table-walk entry point is `rom_table_lookup_entry_point`.
Stage 0 must answer:

- Run a minimal RP2350 firmware that invokes
  `rom_table_lookup_entry_point` with a known 4-char code. Does it
  return cleanly?
- The bootrom's table-walk uses `rcp_count_set` (RCP coprocessor
  canary) at bootrom address 0x4c (`arm-bootrom.dis:90`). Verify our
  RCP semantics tolerate this.
- **End-to-end smoke**: invoke `flash_range_program` of a tiny pattern
  through the bootrom and verify the flash backing-store actually
  changes. Catalogue-only is not enough — the bootrom drives QMI, OTP,
  TRNG, SHA256 along the way, and any of those can hang or fault even
  when dispatch is clean.

**Integration-test pre-condition**: the `flash_range_program` smoke
must pre-erase the target region (`flash_range_erase` first) or start
from an all-`0xFF` flash image. Real silicon flash requires
erase-before-program at sector granularity.

### Fact 3 — pinned register maps

From RP2350 datasheet §Appendix A:

- USB control: `USBCTRL_REGS_BASE = 0x5011_0000` (16 KB region).
- USB DPRAM: `USBCTRL_DPRAM_BASE = 0x5010_0000`, exactly 4096 bytes
  (`0x1000`). Structured: 0x000..0x180 = buffer-control + setup-packet
  area, 0x180..0xFFF = endpoint data buffers.
- HSTX control: `HSTX_CTRL_BASE` on **APB** — value **TBD via
  datasheet §Appendix A**. Likely answer is `0x400C_C000`; confirm
  before Component 2 lands.
- HSTX FIFO: `HSTX_FIFO_BASE` on **AHB-Lite** at `0x5060_0000`,
  separate fabric.

The APB-vs-AHB split for HSTX is load-bearing.

### Fact 4 — current bus-fault semantics on the new regions

The `Bus::read32`/`write32` fall-through for region `0x5*` does NOT
bus-fault — `bus/mod.rs:2722-2725` routes unmodelled accesses through
`warn_unmodelled_mmio` + `peripheral_regs` HashMap, returning 0.
Adding stubs converts a warn-once HashMap noop into defined behaviour.
The risk is that **tests reading from `0x501x_*` / `0x506x_*` /
`0x400C_x*` and asserting they return 0** will see real stub state
instead. Stage 0 grep:

```
grep -nr "0x501[01]_" crates/mdrp2350/src/tests.rs
grep -nr "0x5060_"   crates/mdrp2350/src/tests.rs
grep -nr "0x400[cC]_" crates/mdrp2350/src/tests.rs
grep -nr "0x501[01]_" crates/mdrp2350/src/threaded/
grep -nr "0x5060_"   crates/mdrp2350/src/threaded/
grep -nr "0x400[cC]_" crates/mdrp2350/src/threaded/
```

(Threaded subtree includes round-trip tests at `0x5060_0000` —
`crates/mdrp2350/src/threaded/bus.rs:2082, 2122, 2363` — that
Component 2 will need to reckon with.)

Any test that reads these regions and asserts `== 0` is direct prior
art that the stub will break — list them, decide whether to delete or
rewrite.

### Fact 5 — RESETS_POST_BOOTROM state and W1C bit list

`RESETS_POST_BOOTROM` at `bus/mod.rs:224` records which peripherals
are held in reset *after* emulator boot. Confirm USBCTRL is in that
set on real silicon.

**(R4) W1C bit list source priority.** Datasheet §12.6.5 (USB
SIE_STATUS register description) is **primary**; pico-sdk
`hardware/regs/usb.h` is **corroborating** (the regs headers pin bit
position but not always W1C semantics — those are in datasheet
register descriptions). Journal entry: paste the W1C bit positions
verbatim with both citations.

### Stage 0 failure modes

Each fact has a defined fallback if it fails:

- **Fact 1 fails**: bump RP2350-specific ROM_SIZE; Stage 0 confirms

- **Fact 2 fails**: catalogue which peripheral access faults. If it's

- **Fact 3 fails** (no public datasheet base): defer the affected stub.
- **Fact 4 fails** (existing tests assert `== 0` on these regions):

- **Fact 5 fails** (USBCTRL not in `RESETS_POST_BOOTROM`): adjust the

Stage 0 outputs: one journal entry per fact, with answers. **No code
commits land in Components 1, 2, or 3 until Stage 0 is signed off**.

## Component 1 — USB stub

### Scope

- `USBCTRL_REGS_BASE` at `0x5011_0000` — control/status registers.
- `USBCTRL_DPRAM_BASE` at `0x5010_0000`, 4096 bytes plain RAM. Stored
  as a `Box<[u8; 4096]>` field on the new `UsbCtrl` struct; not shared
  with the main `Memory`. Reset behaviour is a **stub policy**, not a
  silicon claim — we clear `0x000..0x180` on reset to satisfy
  pico-sdk's expected read-back; the data region is left as last
  written, since real silicon DPRAM contents are unspecified
  post-reset.
- All control register writes accepted (default last-write-wins).

**W1C status registers**: writes mask out W1C bits, reads always
return 0 for those bits. Exact list per Stage 0 Fact 5, pinned in
docblock.

- Static "no device": `VBUS_DETECTED`, `BUS_RESET`, `TRANS_COMPLETE`,
  `CONNECTED`, `SUSPENDED`, `RESUME` all read 0.
- `BUFFER_STATUS = 0`. `INTS = 0`, `INTR = 0`.
- NVIC IRQ_USBCTRL_IRQ (line 14) never asserts. Pico-sdk device-mode
  init is safe; host-mode init blocks on `BUS_RESET` (declared in
  Risks).

### Bus integration

The new module wires five points:

1. New base const + match arms in `Bus::read32` / `write32` for both
   `0x5010_*` (DPRAM) and `0x5011_*` (regs). The new arms replace the
   `warn_unmodelled_mmio` + HashMap fall-through at
   `bus/mod.rs:2722-2725` for these specific bases.
2. Entry in `reset_bit_for_base` (`bus/mod.rs:255`) for both bases.
3. `usbctrl: UsbCtrl` field on `Bus`; construction in `Bus::new`.
4. Narrow-access policy: registers word-only; DPRAM byte/halfword.
   Add to bus carve-outs at `bus/mod.rs:1647-1706`.
5. `RESETS_POST_BOOTROM` table includes USBCTRL.

### Function shape

Per `peripherals/mod.rs:1-23` and `peripherals/uart.rs:339,373,491`:
inherent methods, no trait. Pinned signatures:

```rust
impl UsbCtrl {
    pub fn new() -> Self;
    pub fn reset(&mut self);
    pub fn read32(&mut self, offset: u32) -> u32;
    pub fn write32(&mut self, offset: u32, value: u32, alias: u32, irqs: &mut u64);
    pub fn read_dpram(&self, offset: u32, size: u8) -> u32;
    pub fn write_dpram(&mut self, offset: u32, value: u32, size: u8);
}
```

No `tick`. `irqs: &mut u64` is the out-mask convention (UART pattern);
USB stub never sets a bit.

### Oracle

- pico-sdk USB init sequence + `SIE_STATUS` read returns
  `VBUS_DETECTED=0`. No bus fault.
- W1C round-trip: write 1, read back returns 0.
- DPRAM word/byte/halfword writes round-trip; reset clears only
  buffer-control region.
- IRQ_USBCTRL_IRQ stays low across full init.

Estimate: ~200-250 lines. Defer if discovery shows >375.

## Component 2 — HSTX stub

### Scope

- Two MMIO regions per Stage 0 Fact 3 (APB CTRL, AHB FIFO).
- Implementation pattern: `peripherals/inert.rs` — `HashMap<u32, u32>`
  + small `match offset` for status overrides.
- Control writes accepted, last-write-wins. FIFO writes silently
  consumed.
- FIFO status: `FIFO_EMPTY=1`, `FIFO_FULL=0`, `FIFO_LEVEL=0` static.
  Risk: firmware polling `FIFO_LEVEL > 0` hangs. No in-tree RP2350
  firmware does this.
- Stub does not consume `CLK_HSTX`.
- Same five-point bus integration as Component 1 (`RESET_HSTX = 3`).

### Function shape

Inherent methods, same convention as Component 1.

### Oracle

- pico-sdk HSTX init sequence (lane map writes, `EXPAND_*`,
  `CTRL.EN=1`, then 1024 FIFO words). No fault, status reports empty,
  no IRQ.

Estimate: ~80 lines. Defer if discovery shows >120.

## Component 3 — Bootrom mask-ROM

### Approach

**Default path**: execute the real RP2354 bootrom binary
(`roms/rp2350/bootrom-combined.bin`) from ROM memory. Firmware's
`rom_table_lookup_entry_point` walks the real `rom_func_table` and
dispatches into real bootrom code.

Functions touching only-emulated peripherals (SHA256, TRNG, XIP_CTRL,
QMI, DMA, OTP) execute verbatim. Conditional on Stage 0 Fact 2
end-to-end smoke: if the bootrom hangs or faults inside those paths,
those peripherals need fixing first; Component 3 blocks on them.

**Single PC hook, inlined.** No `BootromHookTable` struct. Minimum hook
set after Stage 3.1 is expected to be one entry: the BOOTSEL flavour
of `reboot` (4-char code expected `'RB'`; Stage 3.1 confirms).

### **(R4) Hook PC field ownership and Secure/Non-Secure aliasing**

**Where the fields live.** Two `Option<u32>` fields on each
`CortexM33`, not on `Emulator`. Reason: in threaded mode,
`crates/mdrp2350/src/threaded/emulator.rs:766` moves `CortexM33` by
value into the worker thread; an `Emulator` field would be unreachable
from the per-step hook check.

```rust
pub struct CortexM33 {
    // ...
    pub bootrom_reboot_hook_pc_s: Option<u32>,   // Secure alias
    pub bootrom_reboot_hook_pc_ns: Option<u32>,  // Non-Secure (= S + 0x8000)
}
```

`Emulator::load_bootrom` resolves both PCs and writes them into each
`CortexM33` it owns by mutable borrow. In threaded mode, the workers
have already taken ownership of their `CortexM33` by value at spawn; a
soft-reboot reload mid-run goes through the existing
`Emulator::load_bootrom` path which the threaded scheduler already
serialises against worker quanta — the runtime joins workers, updates
each `CortexM33`, then respawns.

**Why two PCs.** RP2350 IDAU treats `0x0000_8000..0x0000_FFFF` as the
Non-Secure ROM alias of `0x0000_0000..0x0000_7FFF`
(`crates/mdrp2350/src/core/exceptions.rs:837`). NS firmware fetches
the bootrom at `+0x8000`. A bare `pc == hook_pc_s` equality check
silently misses NS callers. Storing two PCs is cleaner than a
mask-and-compare.

### **(R4) Hook check placement**

`crates/mdrp2350/src/core/mod.rs:417-422` shows `step()` flow:
WFE/halt checks → `take_irq_pending` → `try_take_any_pending_exception`
→ `decode_execute`. The hook check goes **immediately before
`decode_execute` (line 422)**.

Pseudo-code:

```rust
if Some(self.pc) == self.bootrom_reboot_hook_pc_s
    || Some(self.pc) == self.bootrom_reboot_hook_pc_ns {
    self.shutdown_requested = true;
    return Ok(StepOutcome::Halted);
}
self.decode_execute(...)
```

The check fires from **two** entry points — `step` (just before line
422) and `step_no_atomics` (just before line 499; the same shape
repeats there). `debug_step` at line 460 delegates to `step` and does
not need a separate insertion.

### Hot-path cost gate

Before Component 3 merge:

- `paced_bench_rp2350 --runs 5 --seconds 60` on `pre` (merge baseline)
  and `post` (hook-armed branch).
- The binary already does 1 warmup run + N measured runs and emits p50
  per run (`crates/mdpicoem-harness/src/bin/paced_bench_rp2350.rs:1127-1135`).
- Compare p50 across the 5 measured runs.
- Budget: `p50(post) / p50(pre) < 1.005` (≤0.5% regression).

**Acknowledged limitation**: the V3 review correctly observed that 0.5%
is inside `paced_bench`'s typical run-to-run jitter. Median-of-5 with
one warmup reduces but doesn't eliminate noise. If the gate fires
ambiguously, run with `--seconds 180` and re-evaluate; if still
ambiguous, the hook check is below the noise floor and the gate is a
no-op (fine).

### Hazard3 isolation

The hook check fires only from `CortexM33::step` paths. Hazard3's
`core_riscv` step path does not check hook PCs. A Hazard3 fetch into
the bootrom address range will execute Arm bootrom bytes as RV
instructions and fault — accepted as a documented limitation, not a
regression. Filed as Risk.

### Soft-reboot / reload

Hook resolution recomputes on every `Emulator::load_bootrom` call
(`lib.rs:478`). If firmware reboots and the host reloads bootrom
bytes, the hook PCs are rebuilt across each `CortexM33`. **Note**: a
future serialize/restore path that skips `load_bootrom` and rehydrates
ROM bytes directly into `Memory` would leave hook PCs stale. No such
path exists today; if added, that HLD must call into
`resolve_rom_func` explicitly.

### Stage 3.2 — Inline hook + integration-test firmware

**(R4) Component 3 owns creation of integration-test firmware.** No
firmware in `roms/rp2350/` currently calls `flash_range_program` or
`connect_internal_flash`. Stage 3.2 must produce a small firmware
binary (`roms/rp2350/gen_bootrom_flash_smoke.py` + `.bin`) whose entry
sequence is: pre-erase a sector → call `flash_range_program` with a
16-byte pattern → BKPT. Backing-store flash bytes are inspected post-run.

Implementation files for the hook itself:

- `crates/mdrp2350/src/bootrom_hooks.rs` — NEW. Two functions:
  `resolve_rom_func(bootrom: &[u8], code: &[u8; 4]) -> Option<u32>`
  and `resolve_bootrom_hooks(bootrom: &[u8]) -> (Option<u32>, Option<u32>)`
  returning the (S, NS) PC pair.
- One PC-equality check inserted at `core/mod.rs:422` (in `step`) and
  the corresponding point in `step_no_atomics` (around line 499).
- `Emulator::load_bootrom` calls `resolve_bootrom_hooks`, writes the
  pair to each owned `CortexM33`.

### **(R4) SHA256 pin on the bootrom binary**

Pin lives at the **`mdrp2350` crate**, not at the harness or the
emulator's `load_bootrom`. Reason: 21 existing unit tests pass
synthetic ROMs through `Emulator::load_bootrom`; an unconditional
assert there breaks them. And `mdpicoem-harness` is not reachable from
`mdrp2350app` (`crates/mdrp2350app/src/main.rs:34`,
`crates/mdrp2350app/src/sim.rs:28`), which also loads the silicon
bootrom — so a harness-resident helper is the wrong layer.

Concrete shape:

- `roms/rp2350/bootrom-combined.bin.sha256` — sibling file holding
  the hex digest of the pinned silicon bootrom.
- `mdrp2350::load_pinned_silicon_bootrom() -> std::io::Result<Vec<u8>>`
  — public function on the `mdrp2350` crate. Reads
  `roms/rp2350/bootrom-combined.bin`, computes SHA256, asserts equality
  with the `.sha256` sibling, returns the bytes. Callers
  (`mdrp2350app`, harness oracles, OneROM runners) use this helper
  rather than open-coding the file load.
- Synthetic-ROM unit tests in `mdrp2350` continue calling
  `Emulator::load_bootrom` directly with hand-crafted bytes — no
  assert in their path.

Producer of the `.sha256` file: a one-line `sha256sum
roms/rp2350/bootrom-combined.bin > roms/rp2350/bootrom-combined.bin.sha256`,
run when the bootrom binary is intentionally refreshed.

### Decision criterion for hooks 2..N

Each new hook beyond `reboot` requires a journal entry stating:

1. The 4-char code and what the function does.
2. The smallest peripheral diff that would obviate the hook —
   specifically, name the registers/bits in the affected peripheral
   that don't behave correctly today.
3. Why that diff is being deferred.

A hook commit without all three is reverted on review.
**Acknowledged limitation**: this is a confessional check (the agent
writing the hook also writes the journal entry); falsification would
require a second-agent or human sign-off, which V4 does not impose.
The criterion is meant to make the alternative *visible* at decision
time, not to enforce a particular choice.

### Oracle

- **Unit test**: load bootrom, call `rom_table_lookup_entry_point('FC')`
  from a tiny ARM image, jump to returned PC, assert clean return and
  expected QMI/XIP_CTRL state.
- **Integration test**: ARM firmware (Stage 3.2 deliverable) that
  calls `flash_range_program` with a 16-byte pattern at a pre-erased
  flash offset. Verifies flash backing matches post-call.
- **`reboot` hook test**: ARM firmware that calls `reboot` with the
  BOOTSEL flag; emulator's `shutdown_requested` becomes true.

### Done condition

- All Stage 3.1 catalogue entries are in one of the three categories
  with a recorded resolution.
- Hot-path microbench within budget per protocol above.
- Integration-test firmware exists in `roms/rp2350/` and the test
  passes.
- `reboot` hook test passes.

If Stage 3.1 reveals a "needs peripheral fix" function, that function
does NOT block Component 3 closure — it spawns a new HLD for the
peripheral fix. Component 3 closes with a list of outstanding
peripheral-fix HLDs in the journal.

## Risks (consolidated)

- **Stage 0 might reveal the bootrom binary is incomplete.** Mitigation:
  Stage 0 Fact 1 + ROM_SIZE bump fallback (acknowledging it's a
  multi-site refactor).
- **Bootrom faults inside QMI/OTP/TRNG/SHA256 under its own call
  patterns.** Mitigation: Stage 0 Fact 2 end-to-end smoke before 3.2.
- **RCP coprocessor state on bootrom entry**. Mitigation: Stage 0
  Fact 2.
- **Bootrom version drift** — pin SHA256; refresh is an explicit commit
  pair (binary + .sha256).
- **Hot-path regression from hook check** — gated by paced_bench
  protocol; honestly acknowledged that ≤0.5% may be inside noise.
- **Permanently-low USBCTRL IRQ** — safe for device-mode init only;
  host-mode init blocks. Documented in module docblock.
- **HSTX FIFO_LEVEL=0 forever** — firmware polling for `LEVEL > 0`
  hangs. Documented; no in-tree RP2350 firmware does this.
- **Hazard3 fetching Arm hook PC** — Hazard3 will execute Arm bootrom
  bytes as RV instructions and fault. Documented as a limitation of
  the V4-deferred RV bootrom path; not a regression.
- **Adding USB/HSTX stubs replaces a warn-once HashMap noop with
  defined behaviour.** Tests reading these regions and asserting
  `== 0` will see real stub state. Stage 0 Fact 4 grep catches them.

## Appendix — V3 → V4 changes summary

- **(R4) Hook PC fields moved from `Emulator` to `CortexM33`**: V3
  said "snapshot at quantum boundary" which doesn't exist; V4
  acknowledges the threaded plumbing reality (`CortexM33` is moved by
  value into worker threads at spawn) and pins the field location on
  `CortexM33` itself, populated by `Emulator::load_bootrom` via
  mutable borrow before workers are spawned.
- **(R4) SHA256 helper home moved from `mdpicoem-harness` to
  `mdrp2350`**: `mdrp2350app` cannot depend on `mdpicoem-harness`,
  but it does depend on `mdrp2350`; the helper as
  `mdrp2350::load_pinned_silicon_bootrom` reaches all callers.
- **(R4) Paced_bench protocol restated to match existing tooling**:
  `paced_bench_rp2350 --runs 5 --seconds 60` (the binary already does
  1 warmup + N measured + p50 emit). Replaces V3's "30s warm-up + 60s
  measurement window" which didn't map onto existing flags.
- **(R4) Hook check sites trimmed**: `step:422` and
  `step_no_atomics:499` only. `debug_step` delegates to `step` and
  does not need a separate insertion (V3 wrongly listed it as a third
  site).
- **(R4) Stage 0 Fact 5 W1C source priority reversed**: datasheet
  primary, pico-sdk corroborating (V3 had the order inverted).
- **(R4) Stage 0 Fact 1 fallback caveat added**: bumping ROM_SIZE is
  a multi-file refactor (common + mdrp2350 bus + threaded). Stage 0
  confirms the refactor is tractable as part of Fact 1's answer
  before assuming the fallback is cheap.
- **(R4) Component 3 explicitly owns integration-test firmware
  creation**: no `flash_range_program`-calling firmware exists today
  in `roms/rp2350/`; Stage 3.2 ships `gen_bootrom_flash_smoke.py` +
  `.bin` alongside the hook.
- **(R4) Hot-path cost gate honestly acknowledges noise floor**:
