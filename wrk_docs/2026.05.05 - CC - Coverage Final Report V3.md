### Stage 7 — Annotation pass (reverted)

Attempted `#[cfg_attr(coverage_nightly, coverage(off))]` on 5
provably-unreachable arms. **Reverted** — the `#[coverage]`
attribute is rejected by rustc on match arms (rust-lang/rust#84605
documents this; the attribute is allowed only on functions, modules,
and impl blocks).

Wrapping each unreachable arm in a helper function for ~5 branches
of denominator reduction wasn't worth the production-code churn.
The 5 candidate arms remain in scope as uncovered branches (out of
6 112 total).

## 5. Why the gain was +1.64 pp (not +6 pp)

The plan projected 91.18 % → 95 % (+3.8 pp). We delivered +1.64 pp.
Three factors:

1. **Generic monomorphization branches.** The `Bus` type is generic
   over `B: CoreBus`. Every method that takes `&mut B` produces TWO
   instrumented branch records — one for the Serial `Bus`
   monomorphization (covered by all existing tests) and one for the
   threaded `WorkerBus` monomorphization (covered only by tests that
   explicitly construct a `ThreadedEmulator`). About 100 missed
   branches in `bus/mod.rs`, `threaded/bus.rs`, and execute_thumb32
   are this shape; covering them requires test paths that build a
   `ThreadedEmulator`, run a quantum that touches the relevant
   peripheral, and observe the bus path through the threaded
   monomorphization. Several Stage 1 + 4 tests do this; not enough
   to close the gap.
2. **`mod tests` branches inflate the denominator.** Tests added
   inside production files (e.g. `picoem-common/src/pio/mod.rs`)
   contain `assert_eq!`, `if cfg!(...)`, and `match` arms whose
   FALSE-side never fires when the test passes. These add to the
   in-scope branch count without adding to coverage. The session
   added +80 such branches from 531 tests; this is fine (the asserts
   are valuable), but it cancels some of the gain.
3. **Already-covered FALSE-arms.** Many "missed" branches are
   single-direction edges of `if`-statements where the OTHER
   direction is already covered by the existing test suite. Adding
   tests that take the same direction again doesn't help; tests must
   take the *other* direction. Stage 3 (bus/mod.rs) and Stage 5
   (execute_fpu.rs) hit this pattern hardest — many of the agents'
   tests were duplicates from a coverage standpoint.

These structural reasons mean further stages targeting the same
files would have hit the same wall. The remaining 439 misses
concentrate in:

- **Generic-monomorphization paths** (~120 branches): `bus/mod.rs`,
  `threaded/bus.rs`, `execute_thumb32.rs`. Need threaded-runtime
  driver tests.
- **Builder error arms** (~30 branches): `rp2040/lib.rs`,
  `rp2350/lib.rs`. Need direct error-injection tests.
- **FPU sNaN / denormal paths** (~30 branches): `execute_fpu.rs`.
  Need exhaustive helper-direct tests with private accessors.
- **Single-direction `if`-arms** (~150 branches): scattered. Hard to
  identify without per-line analysis; many are likely
  fundamentally-unreachable from the public API.
- **Tests-only branches** (~80 branches): `assert!` failure arms in
  `mod tests` blocks. Can't be covered without the test failing.

## 6. Workspace headline (45.61 %)

The workspace TOTAL went from 63.22 % → 45.61 %. **This is not a
regression.** The drop comes entirely from running cov with
`--features threading,testing` — those features expose ~4 000
additional branch records in the threaded runtime + panic-injection
APIs, almost all of which are out-of-scope (in harness binaries that
need silicon, or in TUI apps that aren't unit-testable).

The IN-SCOPE percentage is the metric of record. Workspace headline
is structurally bound by hardware-only binaries and is not a primary
KPI per the baseline document § 5.

to extract uncovered branch line numbers from the cov JSON).

## 8. Recommendation

If a future session is asked to push further:

1. **Don't attack `bus/mod.rs` directly with more narrow-access
   tests.** The remaining 35 misses are nearly all
   monomorphization-pair branches; the only way to move them is
   threaded-runtime drivers that exercise each peripheral via
   `WorkerBus`. Plan for ~5 fully-fledged ThreadedEmulator tests per
   peripheral, not 30 narrow-access drives.
2. **Annotation pass via wrapper functions.** The 5 provably-
   unreachable match arms can be lifted into `#[inline] fn
   unreachable_*() { ... }` helpers and annotated `#[coverage(off)]`
   on the function. ~10 branches off denominator (~+0.16 pp). Low
   risk if reviewed.
3. **execute_fpu.rs private-helper sweep.** ~30 missed branches in
   `fpscr_set_nzcv` / `fpu_compute_op` family helpers. Add
   `#[cfg(test)] pub(crate) fn` accessors with explicit `(N, Z, C, V)
   x sNaN x ±Inf` parameter sweeps. ~30 covered; +0.5 pp.
4. **rp2040/rp2350 lib.rs builder error arms.** ~20 branches each;
   need direct `EmulatorBuilder::build` tests with deliberately-
   unsupported configs. ~30 covered; +0.5 pp.

Total realistic future budget: **~80 branches** to ~94.0 %. Hitting
strictly **≥ 95 %** would need an additional pass over generic
monomorphization paths in `bus/mod.rs` (8-10 ThreadedEmulator tests
that drive every peripheral) — feasible but high-effort, ~1 day of
agent work.
