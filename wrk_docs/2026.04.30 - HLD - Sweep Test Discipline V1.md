## 2. Phase 4.1 plan — PPB-bypass tests

### 2.1 The trigger

Both tests are gated by the existing `debug_assert!` at
`crates/mdrp2350/src/bus/mod.rs:2915-2921`:

```rust
debug_assert!(
    addr >> 28 != 0xE
        || Self::is_boot_ram(addr)
        || Self::is_coresight_trace(addr),
    "PPB/coresight-aperture-bypass: address 0x{:08X} reached \
     Bus::write32 — use CortexM33::bus_write32 wrapper",
    addr
);
```

That guard exists because `Ppb` lives on the per-core `CortexM33::ppb`
(`crates/mdrp2350/src/core/mod.rs:288`), not on `Bus`. Bare `Bus::write32`
for region 0xE outside boot-RAM / coresight-trace falls through to the
unmapped arm at `bus/mod.rs:3114-3116`, which raises a bus fault — useless
for tests that need NVIC ISER, NVIC ISPR, or VTOR seeded.

### 2.2 The replacement API

`Emulator::mmio_write32` at `crates/mdrp2350/src/lib.rs:1336-1365`:

```rust
pub fn mmio_write32(&mut self, addr: u32, value: u32) {
    self.assert_not_placeholder();
    self.bus.master_cycle = self.clock.cycles;
    if addr >> 28 == 0xE && !Bus::is_boot_ram(addr) {
        self.core_mut(0).ppb.write32(addr, value);
        // ... NVIC_ISPR/ICPR mirror back to bus.atomics.irq_pending[0] ...
    } else {
        self.bus.write32(addr, value, 0);
    }
}
```

The PPB branch routes onto core 0's `Ppb`, exactly the path
`CortexM33::bus_write32` would take during `step()`. NVIC_ISPR/ICPR writes
also mirror back into `bus.atomics.irq_pending[0]` so the Serial step path's
short-circuit dispatch sees the latched IRQ — this is the wiring both tests
were written to exercise. `Emulator::mmio_read32` at `lib.rs:1377` is the
symmetric reader.

### 2.3 Inventory of test-line changes

Only the writes/reads that hit region 0xE need to change. SRAM, POWMAN,
RESETS writes stay as `emu.bus.write32` (correct today, no debug_assert
applies).

#### `tests.rs:10519` — `powman_match_pends_nvic_line_45`

| Line | Today | After |
|---|---|---|
| 10553-10554 | `emu.bus.write32(0xE000_E104, …, 0)` | `emu.mmio_write32(0xE000_E104, …)` |
| 10561 | `emu.bus.read32(0xE000_E204, 0)` | `emu.mmio_read32(0xE000_E204)` |

Plus: drop `#[ignore = …]` at `:10520`.

#### `tests.rs:10569` — `powman_match_enters_emulator_handler`

| Line | Today | After |
|---|---|---|
| 10605 | `emu.bus.write32(0xE000_ED08, VT_BASE, 0)` | `emu.mmio_write32(0xE000_ED08, VT_BASE)` |
| 10606 | `emu.bus.write32(0xE002_ED08, VT_BASE, 0)` | `emu.mmio_write32(0xE002_ED08, VT_BASE)` |
| 10636-10637 | `emu.bus.write32(0xE000_E104, …, 0)` | `emu.mmio_write32(0xE000_E104, …)` |

Plus: drop `#[ignore = …]` at `:10570`.

Five call-site rewrites total. The non-PPB writes (RESETS, POWMAN, vector
table SRAM, handler bytes) stay unchanged.

### 2.4 Why this is the right shape

The action plan and the source report's R2 entry both mandate this: the
protection (the debug_assert) is correct; the tests were the bug. There is
no need for a new API. `Emulator::mmio_write32` was added in Phase 0b.1
Commit B for exactly this kind of harness setup — its doc comment
(`lib.rs:1328-1335`) explicitly cites "configuring SIO GPIO_OE/_OUT,
releasing RESETS bits, etc., without hand-rolling the bus machinery" as the
target use case.

## 3. Phase 4.2 design — `Bus::seed_hfsr_for_test`

### 3.1 The problem

`crates/mdrp2350/src/tests_narrow.rs:799-813` is the only ignored test in
the narrow-audit suite that does NOT block on Stage 2/3/4 production work.
Its ignore reason calls out the missing seeder:

> No public bus API seeds HFSR; it is only set via the fault-escalation
> path. Without a seed, a byte-write test trivially passes (storage is
> zero, RMW is a no-op) without actually exercising the W1C preservation
> contract.

But the test as currently written compounds two issues:

1. `bus.write32(SCB_HFSR, 0x0000_0F0F, 0)` trips the `Bus::write32`
   PPB-bypass debug_assert at `bus/mod.rs:2915` and would also raise a bus
   fault (region 0xE, not boot-RAM, not coresight) at the `_ =>` arm at
   `bus/mod.rs:3114`.
2. Even if seeded, `bus.read32(SCB_HFSR, 0)` raises a bus fault for the
   same reason at `bus/mod.rs:2900`.

`Ppb::hfsr` (`crates/mdrp2350/src/bus/ppb.rs:64`) lives on the `CortexM33`
core, not on `Bus`. The narrow-audit test only constructs a bare `Bus` (no
`CortexM33`). So the seeder cannot just delegate to `Ppb::hfsr`.

### 3.2 Sub-section 4.2.a — feature gating

The action plan says "behind the existing `testing` feature." Verified:

- `crates/mdrp2350/Cargo.toml:59` defines `testing = []` with the comment
  "NOT in `default` on purpose — integration tests that need the injector
  declare `required-features = ["testing"]`. Callers outside of the test
  tree should never enable this." (lines 50-58).
- The default feature set at `:36` is `default = []` — `testing` is opt-in.
- Existing precedent: `Emulator::inject_panic_for_testing` at
  `lib.rs:1048-1066` uses `#[cfg(all(feature = "testing", …))]`.

The seeder will use **`#[cfg(any(test, feature = "testing"))]`**. Rationale:

- `cfg(test)` covers the in-crate `tests_narrow.rs` consumer with no
  Cargo-level plumbing change (it already compiles under `cargo test
  -p mdrp2350`).
- `feature = "testing"` makes the helper available to future out-of-crate
  integration tests that opt in via `required-features = ["testing"]`,
  matching the inject-panic precedent.
- Neither path enables the seeder in a release library build — the
  workspace `release_max_level_info` discipline plus the `cfg` gate together
  guarantee zero runtime cost and zero public surface in `cargo build
  --release` for downstream consumers.

What stops it leaking: same as the panic injector. Production builds run
`cargo build --release` without `--features testing`; in that
configuration `cfg(test)` is false and `feature = "testing"` is false, so
the function does not exist in the compiled crate.

### 3.3 Sub-section 4.2.b — API surface

Single function, lives on `Bus`. Signature:

```rust
#[cfg(any(test, feature = "testing"))]
pub fn seed_hfsr_for_test(&mut self, value: u32) {
    // body — see §3.4.
}
```

**Where it lives:** `crates/mdrp2350/src/bus/mod.rs`, in the same `impl
Bus` block as `clear_bus_fault` (around `:1218`). NOT in
`bus/ppb.rs` — `Bus` does not own a `Ppb`, so the helper cannot delegate
into one.

**Doc comment template** (cap at ~10 lines, mirrors the
`inject_panic_for_testing` style):

```rust
/// Test-only: seed the SCB HFSR storage observable by `Bus::read32(SCB_HFSR)`.
///
/// HFSR is set in production exclusively via the fault-escalation path on
/// `CortexM33::ppb`. This helper exists so the narrow-access audit suite
/// (`tests_narrow.rs::s65_scb_hfsr_byte_write_clears_only_target_lane`)
/// can seed HFSR without an Emulator/CortexM33 in scope. The seed is
/// written into `Bus::peripheral_regs[SCB_HFSR]`; subsequent `Bus::read32`
/// of `SCB_HFSR` consults that map (see `bus/mod.rs` — read path patch).
///
/// Feature-gated via `cfg(any(test, feature = "testing"))`. Never reachable
/// in a release library build.
```

### 3.4 Sub-section 4.2.c — implementation sketch

**State touched.** `Bus::peripheral_regs: HashMap<u32, u32>` at
`bus/mod.rs:303` is the existing catch-all for inert APB stub addresses.
HFSR is normally a PPB register on `Ppb`, but for the narrow-audit test the
contract is only "no bus fault on a byte write to SCB_HFSR" — there is no
runtime read-path consumer in production.

Three code touches:

1. **Define the seeder** in the `impl Bus` block:
   ```rust
   #[cfg(any(test, feature = "testing"))]
   pub fn seed_hfsr_for_test(&mut self, value: u32) {
       self.peripheral_regs.insert(SCB_HFSR_ADDR, value);
   }
   ```
   `SCB_HFSR_ADDR = 0xE000_ED2C` (matches `tests_narrow.rs:42`).

2. **Patch `Bus::read32` PPB fall-through** under the same cfg so reads
   from `SCB_HFSR` consult `peripheral_regs` before the fault arm. The
   minimal patch is at `bus/mod.rs:2900` (the `_ =>` arm of the region 0xE
   match for read32):
   ```rust
   _ => {
       #[cfg(any(test, feature = "testing"))]
       if addr == SCB_HFSR_ADDR {
           if let Some(v) = self.peripheral_regs.get(&addr) {
               return *v; // no fault — test-only path
           }
       }
       self.atomics.set_bus_fault(core as usize, addr);
       0
   }
   ```
   This is the **only** production-touched dispatch. It is a one-address
   intercept under a test-only cfg, so production binaries are byte-identical.

3. **Do NOT patch `Bus::write32` PPB-bypass debug_assert** — the test does
   not need to write SCB_HFSR through `Bus::write32`; the seeder side-steps
   `write32` entirely. Leave the existing guard at `bus/mod.rs:2915-2921`
   exactly as is. (This is what protects the Phase 4.1 tests from
   regressing.)

The narrow `Bus::write8` path is unaffected — narrow PPB writes today fall
into `peripheral_regs` (no debug_assert on `write8` for region 0xE; see
`bus/mod.rs:1620-1624` — that debug_assert is SIO-only). A `bus.write8(SCB_HFSR
+ 1, 0x00, 0)` lands in the catch-all at `:2010-2020` which does the
RMW against `peripheral_regs`. That is the production behaviour the test
currently asserts is non-faulting.

### 3.5 Sub-section 4.2.d — how the un-ignored test will use it

Re-shape `s65_scb_hfsr_byte_write_clears_only_target_lane` at
`tests_narrow.rs:799-813`:

```rust
#[test]
fn s65_scb_hfsr_byte_write_clears_only_target_lane() {
    let mut bus = Bus::new();
    clear_bf(&mut bus);
    bus.seed_hfsr_for_test(0x0000_0F0F);
    bus.write8(SCB_HFSR + 1, 0x00, 0);
    assert!(!bus.bus_fault(0), "HFSR byte write must not fault");
    // Future Stage 2/3/4 work: also assert lane preservation through
    // Ppb-routed narrow access. Today the narrow write lands in the
    // peripheral_regs catch-all, so we only pin the no-fault contract.
}
```

Drop the `#[ignore = …]` attribute, drop the two `bus.read32(SCB_HFSR, 0)`
calls (they were dead — results discarded — and would fault with the
existing `Bus::read32` for region 0xE), keep the `assert!(!bus.bus_fault(0))`.

The 21 sibling narrow-audit tests at `:311-1243` stay `#[ignore]`d — they
need the larger Stage 2/3/4 production rewire (already tracked under T1 of
the source report). This HLD does not touch them.

## 4. Phase 4.3 — SAFETY comments on threaded-affinity FFI

### 4.1 Inventory

Both files contain a single `pin_to_host_core(host_core: usize)` function
with five `unsafe` blocks each. The two functions are byte-identical (a
known duplicate covered by Du2 of the source report; the unification is
Phase 5.1 of the action plan, NOT this workstream). For Phase 4.3 we add
matched SAFETY comments to each occurrence so that when the dedup happens
later, the comments come along for free.

Verified via `grep -rn "unsafe " crates/mdrp2350/src/threaded/
crates/mdrp2040/src/threaded/`: exactly five `unsafe` blocks per chip, all
inside `pin_to_host_core`. No sibling `unsafe` blocks elsewhere in the
threaded subtree on either chip.

| ID | File:line | Call | Group |
|---|---|---|---|
| W1 | `crates/mdrp2350/src/threaded/emulator.rs:776` | `GetCurrentThread()` | Win32 |
| W2 | `crates/mdrp2350/src/threaded/emulator.rs:778` | `SetThreadAffinityMask(h, mask)` | Win32 |
| L1 | `crates/mdrp2350/src/threaded/emulator.rs:786` | `std::mem::zeroed()` for `cpu_set_t` | Linux init |
| L2 | `crates/mdrp2350/src/threaded/emulator.rs:787-790` | `libc::CPU_ZERO` + `libc::CPU_SET` | Linux init |
| L3 | `crates/mdrp2350/src/threaded/emulator.rs:791-797` | `libc::pthread_setaffinity_np(...)` | Linux apply |
| W1' | `crates/mdrp2040/src/threaded/emulator.rs:561` | `GetCurrentThread()` | Win32 |
| W2' | `crates/mdrp2040/src/threaded/emulator.rs:563` | `SetThreadAffinityMask(h, mask)` | Win32 |
| L1' | `crates/mdrp2040/src/threaded/emulator.rs:571` | `std::mem::zeroed()` for `cpu_set_t` | Linux init |
| L2' | `crates/mdrp2040/src/threaded/emulator.rs:572-575` | `libc::CPU_ZERO` + `libc::CPU_SET` | Linux init |
| L3' | `crates/mdrp2040/src/threaded/emulator.rs:576-582` | `libc::pthread_setaffinity_np(...)` | Linux apply |

### 4.2 SAFETY justifications (one per group, applied identically to RP2350 + RP2040)

Style follows `crates/mdpicoem-harness/src/gdb_client.rs:235-240` — terse,
preconditions stated, what the call does named explicitly.

**W1 — `GetCurrentThread`:**
```rust
// SAFETY: GetCurrentThread is a documented Win32 entry point that
// takes no arguments and returns a pseudo-handle to the current thread.
// It cannot fail and never touches user memory.
let h = unsafe { GetCurrentThread() };
```

**W2 — `SetThreadAffinityMask`:**
```rust
// SAFETY: `h` is the pseudo-handle just returned by GetCurrentThread,
// so it is valid for the lifetime of this call. `mask` is a single-bit
// processor-mask `usize` and the bit width was checked against
// `usize::BITS` in the assert at the top of this function — bit positions
// outside the host's processor count produce a documented zero return,
// which the post-call `assert!(prev != 0)` catches.
let prev = unsafe { SetThreadAffinityMask(h, mask) };
```

**L1 — `std::mem::zeroed::<cpu_set_t>`:**
```rust
// SAFETY: cpu_set_t is a POD struct (a fixed-size array of unsigned
// long bitmaps under glibc); the all-zero bit pattern is the documented
// "empty CPU set" representation, equivalent to a CPU_ZERO call.
let mut set: libc::cpu_set_t = unsafe { std::mem::zeroed() };
```

**L2 — `libc::CPU_ZERO` + `libc::CPU_SET`:**
```rust
// SAFETY: `set` is a stack-local `cpu_set_t` whose lifetime spans both
// macros. CPU_ZERO clears every bitmap word; CPU_SET writes the bit at
// `host_core`, whose bound vs. the cpu_set_t bit width is enforced by
// the assert at the top of this function.
unsafe {
    libc::CPU_ZERO(&mut set);
    libc::CPU_SET(host_core, &mut set);
}
```

**L3 — `libc::pthread_setaffinity_np`:**
```rust
// SAFETY: `pthread_self()` returns the calling thread's pthread_t,
// which is documented to be valid until the thread exits. `&set`
// points to a stack-local cpu_set_t initialised on the lines above
// and not freed until this block returns. `size_of::<cpu_set_t>()` is
// the documented length parameter. Errors surface via the int return
// value, captured into `rc` and asserted non-zero immediately after.
let rc = unsafe {
    libc::pthread_setaffinity_np(
        libc::pthread_self(),
        std::mem::size_of::<libc::cpu_set_t>(),
        &set,
    )
};
```

The same five comments are applied verbatim to the RP2040 sibling. Total
edit: ten `// SAFETY:` blocks added; zero behaviour change.

## 6. Risks and open questions

### 6.1 Does the un-ignored `s65_scb_hfsr_byte_write_clears_only_target_lane`
test actually pass with the seeder shape proposed?

**Best read of the source: yes.** The test's only assertion is
`!bus.bus_fault(0)`. After the re-shape (drop the bus.read32/write32 calls,
add `seed_hfsr_for_test`), the only operation that touches the bus fault
state is `bus.write8(SCB_HFSR + 1, 0x00, 0)`. That goes through `Bus::write8`
at `bus/mod.rs:1614-1612`. The PPB region 0xE write8 path lacks a
debug_assert (only DIV/INTERP / SIO is guarded) and lands in the
`peripheral_regs` catch-all at `:2010-2020`. RMW against the catch-all does
not raise a bus fault. So the assertion holds.

**Risk:** I have read the dispatch but not exhaustively traced every path
the catch-all takes for a region 0xE address. If the catch-all has its own
"raise bus fault for unknown PPB addresses" guard I missed, the test will
FAIL on un-ignore even with the seeder. **Mitigation:** in Phase B
implementation, run the test before and after the re-shape. If it fails
post-re-shape, the helper is the wrong shape (need to also patch the
write8 fall-through under the same cfg) — surface back here, do not paper
over the failure.

### 6.2 The `testing` feature is off by default

Confirmed at `crates/mdrp2350/Cargo.toml:36` (`default = []`) and `:59`
(`testing = []`). Running `cargo test -p mdrp2350` (no `--features`) still
enables `cfg(test)`, which is the primary gate — the seeder is reachable
and the test runs without further plumbing. The `feature = "testing"` arm
of `cfg(any(test, feature = "testing"))` is redundant for the in-crate
unit-test consumer; it is included for forward compatibility with
out-of-crate integration tests that may want to seed HFSR. Equivalent
defensible alternative: use just `#[cfg(test)]`. The action plan said "the
existing `testing` feature"; I went with the union because it costs nothing
and gives external consumers the same affordance the panic injector has.
**Open question for Phase B:** Arthur — `cfg(test)` only, or
`cfg(any(test, feature = "testing"))`? My preference is the union (matches
existing `inject_panic_for_testing` precedent in `Emulator`).

### 6.3 Phase 4.1 SRAM writes via `emu.bus.write32` stay unchanged

The two un-ignored tests do many non-PPB `emu.bus.write32` calls (RESETS,
POWMAN, SRAM vector table). Those are NOT bound by the PPB debug_assert and
work today. Leaving them as `emu.bus.write32` keeps the diff minimal and
matches the action plan's guidance that the protection is correct and only
the *PPB* call sites need to change. **Risk:** none — production flows
already write SRAM/POWMAN through `Bus::write32`. **Mitigation:** the
verification in §5 covers this — if a non-PPB `emu.bus.write32` somehow
broke between commits, the broader test suite catches it.

### 6.4 The narrow `Bus::write8` for SCB_HFSR may someday gain a PPB
debug_assert (Stage 2/3/4 work)

If the narrow-audit Stage 2 work eventually adds a PPB-bypass debug_assert
to `Bus::write8` symmetric with the existing one on `write32`, the
re-shaped test will trip it. **Mitigation:** That work is owned by a
different workstream and is currently `#[ignore]`d behind the T1 tracker
entry. When Stage 2 lands, the implementer will need to re-evaluate this
test (along with the 21 siblings) — that is in-scope for Stage 2, not for
this Phase 4 cleanup.

### 6.5 SAFETY-comment churn vs. Phase 5.1 dedup

Phase 5.1 of the action plan dedups `pin_to_host_core` into
`mdpicoem-common::threaded`. After Phase 5.1 the ten SAFETY blocks become
five (one canonical copy). Adding the comments now and dedup-ing later is
strictly cheaper than dedup-ing then back-filling, because the dedup PR
diff stays mechanical (move + delete) instead of mixing comment authorship.
**Risk:** minimal — five lines of comments duplicated for one PR cycle.

- Does not dedup `pin_to_host_core` (Phase 5.1, separate workstream).
