# Threaded Dual-Core Emulation

Version: 2.0.0
Date: 2026-04-14

## Problem

Dual-core paced throughput on a 3 GHz host: **73.8 MHz per core** (49%
of 150 MHz target). Single-core is 143.8 MHz (96%). The 2x gap comes
from sequentially executing both cores in one host thread.

## Target (honest)

**Realistic ceiling from threading alone: ~120–130 MHz per core** (80–87%
of 150 MHz). This is a **2x improvement** on current 73.8 MHz, bringing
us close to but not at real-time.

Hitting 150 MHz per core requires additional interpreter work — decode
cache, threaded-dispatch, or targeted JIT of hot inner loops. That is
a **follow-up**, not part of this HLD.

Why not 150 MHz per core? Current single-core runs at 143 MHz = 21 host
cycles per emulated cycle. Threading puts one emulated core per host
thread but adds atomic-load overhead, barrier overhead, cache coherence
traffic, and memory-fence translation cost. Realistic per-core throughput
with those overheads is ~120–130 MHz, not 143.

**This HLD is validated by Phase 0 workload validation (below) before
substantial engineering begins.** If real firmware has core 1 mostly
WFI-idle, threading gains are near-zero and we should shelve this and do
decode cache instead.

## Non-goals

- No per-cycle bus contention in threaded mode (documented trade-off).
- No hybrid mode — pure single-threaded OR pure threaded per invocation.
- No dynamic thread count — two emulated cores means two worker threads.
- No env vars, no feature flags. Selected by calling a different method.

## Phase 0: Workload validation + prerequisite refactors

Before designing the threaded execution path, two things must happen:

### 0a. Measure a real workload

Run the existing bootrom + representative OneROM firmware under single-
threaded `paced_bench`. Instrument to count:
- Cycles spent in core 0 decode/execute
- Cycles spent in core 1 decode/execute
- Cycles spent in core 1 WFI (no decode/execute work)
- Cycles spent in bus contention stalls
- Peripheral register access frequency (vs. SRAM)

**Decision point:** if core 1 is >80% idle (typical for asymmetric
firmware), threading gains are below 20%. Shelve threaded mode, spend
engineering on decode cache instead. Continue to Phase 1 only if core 1
is >20% active.

### 0b. Prerequisite refactors

These are single-threaded-correct improvements that are also required
for threading. Land them first, independently:

1. **Move PPB to `CortexM33`.** PPB (NVIC, SCB, MPU, SAU, SysTick) is
   per-core in hardware. Currently lives on `Bus::ppb: [Ppb; 2]`,
   accessed via `bus.active_core()` — a shared mutable flag that does
   not survive threading. Refactor so each `CortexM33` owns its PPB.
   Bus no longer has `active_core()`.

2. **Implement proper LDREX/STREX.** Currently stubs
   (`execute_thumb32.rs:709-738`). Add per-core exclusive monitor state:
   `exclusive_address: Option<u32>`. LDREX sets it; STREX checks it
   and clears. Any write to that address (from same core OR the other
   core, which requires cross-core snoop in threaded mode) invalidates
   it. Without this, software spinlocks break.

3. **Atomicize cross-core fields on `CortexM33`.** `halted`, `wfe_waiting`,
   `event_flag` (currently plain bool) must become `AtomicBool`. These
   are read/written across cores (SEV, WFE, core-1-launch).

4. **RCP salt shared state.** `rcp_salt: u32` and `rcp_salt_valid: bool`
   on CortexM33 are ostensibly per-core coprocessor state, but the
   hardware has cross-core visibility rules. Audit against datasheet;
   if cross-core visible, atomicize.

Each refactor is its own commit, its own test pass. Total: ~1–2 weeks.
After this, the single-threaded emulator is still cycle-accurate, but
has removed the shared mutable state that would have made threading
unsound.

## Phase 1: Separate threaded execution path

### API: two types, one conversion

```rust
/// Single-threaded, cycle-accurate. Reference for validation.
pub struct Emulator { /* existing */ }

impl Emulator {
    pub fn run(&mut self, cycles: u64) -> u64 { /* existing */ }

    /// Consume self, return a threaded emulator with the same state.
    pub fn into_threaded(self) -> ThreadedEmulator { ... }
}

/// Threaded. Quantum-synchronized, not cycle-accurate per cycle
/// (still real-time accurate at quantum boundaries).
pub struct ThreadedEmulator { /* see below */ }

impl ThreadedEmulator {
    /// Run until `stop` is signaled or duration elapses.
    /// Pacer drives real-time.
    pub fn run(
        &mut self,
        pacer: &mut Pacer,
        duration: Duration,
        stop: Arc<StopSignal>,
    );

    /// Convert back to single-threaded (state preserved).
    pub fn into_emulator(self) -> Emulator { ... }
}
```

The conversion moves state; no unsafe, no field-splitting dance. The
two types have different field layouts — shared things wrapped in
`Arc`, core-local things owned directly.

### Thread topology: 2 threads, coordinator folded into worker-0

Three threads (2 workers + dedicated coordinator) wastes a host core
on spin-waiting. Fold the coordinator into worker-0:

```
  ┌────────────────────────────┐  ┌────────────────────────────┐
  │ Worker 0 (pinned to core X)│  │ Worker 1 (pinned to core Y)│
  │                            │  │                            │
  │ for 0..Q:                  │  │ for 0..Q:                  │
  │   core0.step(mem, …)       │  │   core1.step(mem, …)       │
  │ barrier.wait()             │  │ barrier.wait()             │
  │                            │  │                            │
  │ pacer.spin_wait()          │  │                            │
  │ handle_cross_core_events() │  │                            │
  │ barrier.wait()             │  │ barrier.wait()             │
  └────────────────────────────┘  └────────────────────────────┘
```

Worker 0 does pacing + cross-core event handling between quanta.
Worker 1 just waits. Two host cores used, not three.

### Custom spin-barrier (not `std::sync::Barrier`)

`std::sync::Barrier` uses Mutex+Condvar internally; measured cost on
Windows is 3–10 µs per crossing. At Q=150 (1 µs quantum), that's
100–1000% overhead. Replace with:

```rust
pub struct SpinBarrier {
    generation: AtomicU32,   // incremented each crossing
    count:      AtomicU32,   // number of threads arrived in current gen
}

impl SpinBarrier {
    pub fn wait(&self) {
        let my_gen = self.generation.load(Acquire);
        let n = self.count.fetch_add(1, AcqRel) + 1;
        if n == 2 {
            self.count.store(0, Relaxed);
            self.generation.store(my_gen.wrapping_add(1), Release);
        } else {
            while self.generation.load(Acquire) == my_gen {
                std::hint::spin_loop();
            }
        }
    }
}
```

Target crossing cost: <100 ns. Burns one host cycle per iteration
while waiting — fine, both cores are pinned at HIGH priority and the
other worker will complete its quantum in <1 µs.

### Shared memory: AtomicU32 backing

`AtomicU8` for each SRAM byte breaks Armv8-M single-copy atomicity:
two independent byte loads for a u32 can tear mid-write from another
core. Armv8-M guarantees aligned u16/u32 are single atomic
transactions — firmware (including Rust `core::sync::atomic`, pico-sdk
spinlocks, bootrom handshakes) universally depends on this.

Back SRAM with `[AtomicU32]`:

```rust
pub struct SharedMemory {
    sram:  Box<[AtomicU32]>,         // 130K entries × 4B = 520 KB
    rom:   Box<[u8]>,                // read-only, no atomics needed
    xip:   Box<[AtomicU32]>,         // if writable via QMI, else plain
}

impl SharedMemory {
    /// Aligned u32 read — single atomic op (on x86: plain mov).
    pub fn read32(&self, addr: u32) -> u32 {
        self.sram[(addr >> 2) as usize].load(Relaxed)
    }

    /// Aligned u16 read — word load + byte extract (still atomic).
    pub fn read16(&self, addr: u32) -> u16 {
        let word = self.sram[(addr >> 2) as usize].load(Relaxed);
        let shift = (addr & 2) * 8;
        (word >> shift) as u16
    }

    /// u8 read — word load + byte extract.
    pub fn read8(&self, addr: u32) -> u8 {
        let word = self.sram[(addr >> 2) as usize].load(Relaxed);
        let shift = (addr & 3) * 8;
        (word >> shift) as u8
    }

    /// Aligned u32 write — single atomic op.
    pub fn write32(&self, addr: u32, val: u32) {
        self.sram[(addr >> 2) as usize].store(val, Relaxed);
    }

    /// u8/u16 writes use compare_exchange_weak loops (RMW).
    pub fn write8(&self, addr: u32, val: u8) {
        let word_idx = (addr >> 2) as usize;
        let shift = (addr & 3) * 8;
        let mask = 0xFFu32 << shift;
        let new_byte = (val as u32) << shift;
        let mut current = self.sram[word_idx].load(Relaxed);
        loop {
            let desired = (current & !mask) | new_byte;
            match self.sram[word_idx].compare_exchange_weak(
                current, desired, Relaxed, Relaxed
            ) {
                Ok(_) => return,
                Err(actual) => current = actual,
            }
        }
    }
}
```

Cost note: u32 aligned access is 1 atomic op (free on x86). u16/u8
reads are 1 atomic load + bit extraction (~2-3 cycles). u16/u8 writes
use CAS loops (~10-20 cycles on contention, ~5 cycles uncontended).
Instruction fetches are u16/u32 aligned, so stay on the fast path.

### Exclusive monitor (cross-core aware)

Each `CortexM33` holds `exclusive_address: Option<u32>`. On STREX,
check the address matches. A write to that address from *any* core
clears both cores' monitors:

```rust
pub struct SharedMemory {
    ...
    /// Per-core exclusive-monitor addresses. Cleared on any write
    /// that overlaps a core's exclusive range.
    exclusive: [AtomicU32; 2],  // 0 = not held, else = tagged address
}

// On any write:
//   for each core_id: if self.exclusive[core_id].load == addr_tag:
//     clear it via compare_exchange
```

Overhead: one atomic load per write, one branch. For uncontended
common case (no STREX active), the load sees 0 and we continue.

### SIO: threaded-only redesign

Keep existing single-threaded `Sio` (VecDeque FIFOs, plain u32 regs).
Build new `ThreadedSio` for threaded mode only:

```rust
pub struct ThreadedSio {
    fifo_01: SpscRing<u32, 8>,     // core 0 → core 1, 8 deep
    fifo_10: SpscRing<u32, 8>,     // core 1 → core 0, 8 deep
    spinlocks: [AtomicU32; 32],    // 32 hardware spinlocks
    // ...
}
```

**Hand-roll a 100-LOC SPSC ring** rather than pulling in crossbeam.
The SIO FIFOs are strict single-producer/single-consumer with fixed
depth and u32 payload. No allocator, no cfg-if, no scopeguard. Simpler
to audit for correctness, no supply chain surface.

The Rust `core::sync::atomic` model provides enough guarantees. The
ring is ~80 lines including sticky WOF/ROE flag semantics that match
hardware.

### Peripherals: sharded locks

One global `Mutex<Peripherals>` creates head-of-line blocking. Bootrom
workloads may hit 20–50% peripheral access (PLL lock polling, QMI,
RESETS). Shard by block:

```rust
pub struct Peripherals {
    apb:      Mutex<ApbPeripherals>,      // UART, SPI, I2C, etc.
    ahb:      Mutex<AhbPeripherals>,      // DMA, interp, etc.
    clocks:   Mutex<ClocksPll>,           // PLL, clock tree
    qmi:      Mutex<QmiRegs>,             // flash control
    resets:   Mutex<ResetsState>,         // reset controller
}
```

Cores usually touch different blocks; when they do touch the same
block, contention is brief (nanoseconds). If profiling shows hot
contention on one block, split further.

### Bus split (more granular than "memory + peripherals")

```rust
// Shared, concurrently accessible
pub struct SharedMemory { ... }     // SRAM, ROM, XIP (atomic)
pub struct ThreadedSio { ... }      // lock-free FIFOs + atomics
pub struct Peripherals { ... }      // sharded mutexes

// Per-core, owned by each worker
pub struct CortexM33 { ppb, exclusive_address, ... }

// ThreadedEmulator holds Arc<T> for each shared thing,
// passes them into each worker at spawn.
```

### StopSignal

```rust
pub struct StopSignal(AtomicBool);
impl StopSignal {
    pub fn new() -> Arc<Self> { Arc::new(Self(AtomicBool::new(false))) }
    pub fn stop(&self) { self.0.store(true, Release); }
    pub fn is_stopped(&self) -> bool { self.0.load(Acquire) }
}
```

Workers check `stop.is_stopped()` at each barrier crossing. Coordinator
also checks it when deciding whether to spin-wait. Caller can trigger
from another thread (Ctrl-C handler, breakpoint hit).

### Memory fence translation

Single-threaded mode: DMB/DSB/ISB remain no-ops (1-cycle count).

Threaded mode: translate to host fences. In `ThreadedEmulator`'s
execute path:
- `DMB` → `std::sync::atomic::fence(Ordering::AcqRel)`
- `DSB` → same (stronger semantics in guest ISA but host can't express)
- `ISB` → `fence(Ordering::SeqCst)` + potentially flush decode cache
  (once we add one). For now, AcqRel.

**Relaxed ordering + explicit fences matches the guest architecture**:
Armv8-M is a weakly-ordered memory model. Firmware that doesn't use
DMB/DSB has ordering bugs on real silicon too. We emulate that
faithfully.

## Implementation phases

Each phase: reviewable commit, all tests pass, binary still runs.

- **Phase 0a** — Measure OneROM workload. Decide go/no-go.
- **Phase 0b** — Prerequisite refactors (PPB, exclusive monitor,
  atomize cross-core fields). Weeks 1–2.
- **Phase 1** — `SharedMemory` type. Single-threaded Bus wraps
  `Arc<SharedMemory>`. Existing tests pass. Week 3.
- **Phase 2** — `ThreadedSio` + hand-rolled SPSC ring. Unit tests.
  Week 3.
- **Phase 3** — `ThreadedEmulator` minimal viable: spawn, barrier,
  no Pacer yet, fixed-cycle run. Integration test: run dual-core
  SIO ping-pong firmware, assert outcome. Week 4.
- **Phase 4** — Pacer + StopSignal integration. `paced_bench --threaded`
  runs. Week 4.
- **Phase 5** — Benchmark, profile, tune quantum size. Compare to
  single-threaded for same firmware. Week 5.

Total: ~5 weeks. Each phase bails cleanly if blocking issue found.

## Validation strategy

1. **Existing single-threaded tests keep passing.** The threaded mode
   is additive; lockstep path is untouched.

2. **Thread-safety audit.** Use Rust's type system as the primary
   oracle — if `SharedMemory: Send + Sync`, the compiler enforces it.
   Review any `unsafe` blocks by hand.

3. **Loom tests for SIO ring + barrier.** Write `loom::model` tests
   for the SPSC queue and SpinBarrier. Catches ordering bugs that
   show up under weak memory models.

4. **Dual-run differential test.** Run same firmware under `Emulator`
   and `ThreadedEmulator`. Assert state at every SIO sync point
   matches (not cycle counts — those will drift).

5. **Manual benchmark.** `paced_bench --dual-core --threaded` must
   show ≥120 MHz per core to declare success. ≥140 MHz per core is
   the aspiration.

## What this does NOT do

- **No JIT.** Interpreter + threads gives ~2x. JIT would give another
  3-5x on top. Follow-up project if needed.
- **No decode cache.** Related to JIT; could give 30-50% on its own.
  Follow-up.
- **No cycle-accurate dual-core.** Per-cycle bus contention not
  modeled in threaded mode. Single-threaded retains full accuracy
  for validation runs.
- **No graceful crash recovery.** Worker panic → process abort,
  same as single-threaded.
- **No runtime mode switch.** Caller chooses once via `into_threaded()`.

## Risks

1. **Phase 0a might say "don't do it"** — if OneROM firmware is
   core-1-idle-heavy, threading buys nothing. Accept this as a valid
   outcome; shelve and do decode cache instead.
2. **CAS loops on byte writes** — if firmware is write-heavy, the
   u8/u16 write path is slower than u32 write. Measure. If it
   matters, provide a u32-only fast path for hot loops.
3. **Cache coherence traffic** — when both cores write adjacent
   cache lines, MESI invalidations add latency. False sharing risk
   on `ThreadedSio` fields (pad to cache line).
4. **Loom coverage gap** — Loom tests the synchronization primitives;
   it doesn't test that we correctly classified every
   access as shared vs per-core. Thread Sanitizer on Linux (WSL2)
   catches those.

## Dependencies added

- None. We deliberately hand-roll the SPSC ring to avoid crossbeam's
  transitive deps (cfg-if, scopeguard, allocator polyfill). If the
  hand-roll turns out to be subtly broken after Loom testing, revisit.
