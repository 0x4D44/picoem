**Author:** HLD agent

## 1. Goal

Eliminate an undefined-behaviour shift in the four ARMv8-M Thumb-32 bit-field instructions (BFC, BFI, SBFX, UBFX) on the M33 emulator (`crates/mdrp2350/src/core/execute_thumb32.rs`). The current implementation computes the field mask as `1u32 << width` where `width` may legally be 32; in Rust this is UB and panics in debug builds. Re-enable the previously-skipped residue test `bfc_full_width_clears_word` with a real assertion, and add positive coverage for the same boundary on the other three instructions, so the V2 mutation sweep can run without `--skip` flags.

## 3. Root cause

Three call sites all compute a low-`n`-bit mask via `(1u32 << width) - 1`:

```rust
// execute_thumb32.rs:340 — SBFX
let val = (self.regs.r[rn] >> lsb) & ((1u32 << width) - 1);

// execute_thumb32.rs:349 — BFI / BFC
let mask = ((1u32 << width) - 1) << lsb;

// execute_thumb32.rs:389 — UBFX
self.regs.r[rd] = (self.regs.r[rn] >> lsb) & ((1u32 << width) - 1);
```

In all three places `width ∈ 1..=32`. When `width == 32`:
- `1u32 << 32` is **undefined behaviour** in Rust (the shift exceeds the type's bit-width).
- Debug builds: panics with `attempt to shift left with overflow` (LLVM's `shl_with_overflow` intrinsic check).
- Release builds: implementation-defined; on x86_64 the hardware silently masks the shift amount mod 32, so `1u32 << 32 == 1u32 << 0 == 1`, which then computes mask=0. Both extraction (SBFX/UBFX) and mask construction (BFI/BFC) produce **architecturally wrong** results — UBFX returns 0 instead of `rn`, BFC clears nothing, BFI inserts nothing. Silently wrong on real hardware-equivalent firmware.

Encoding ranges that hit `width == 32`:
- **SBFX / UBFX**: `widthm1 = 0x1F`, i.e. `hw1[4:0] == 31`. Architecturally legal — ARMv8-M ARM admits the encoding (extracts the whole 32-bit word).
- **BFC**: `lsb == 0` and `msb == 31`, i.e. `hw1[4:0] == 31` and `imm3:imm2 == 0` with Rn==15. Architecturally legal — clears the entire destination word.
- **BFI**: same `lsb==0, msb==31` with `Rn != 15`. Architecturally legal — replaces the entire destination word with Rn.

## 4. Design

### 4.1 Options considered

**Option 1 — special-case `width == 32`:**
```rust
let mask = if width == 32 { u32::MAX } else { (1u32 << width) - 1 };
```
Branches on the narrow case; introduces an extra control-flow edge per call.

**Option 2 — compute via `u64`:**
```rust
let mask = ((1u64 << width) - 1) as u32;
```
Well-defined for all `width ∈ 1..=32` because `u64`'s bit-width is 64, so shifting by up to 32 stays in-range. The upper 32 bits of the `u64` are then truncated by `as u32`. At `width=32` this yields `0x1_0000_0000 - 1 = 0xFFFF_FFFF`, which is exactly the architectural mask. Branchless; same number of operations on x86_64 (a 64-bit shl + sub + truncating mov).

### 4.2 Choice: **Option 2 (u64 widening)**.

Reasons:
- **Branchless.** No extra control flow on the hot Thumb-32 path. The current sites are 1-cycle instructions per the M33 measurement; keep them tight.
- **Localised.** The fix is a one-token change at each call site (`1u32` → `1u64`, then `as u32`), no helper introduction needed for three sites. Three duplicates is borderline for extracting a helper, but the duplication is one expression, not a block, and a helper would obscure rather than clarify.
- **Defensive against future encoding decoder changes.** If a future change broadens `width`'s range (e.g. a buggy decoder yielding `width = 33`), Option 2 still produces a defined value (`0` for width=64 specifically, but anything ≤ 63 stays defined), whereas Option 1's `else` branch would be UB again.
- **Consistent with the rest of the file.** USAT at `:367–371` already uses `i64` precisely to dodge the same kind of edge.

### 4.3 Helper vs inline

Three sites, identical mask-construction idiom. **No helper.** Rationale matches the IRQ2/IRQ3 fan-out HLD's "duplication is exactly N lines, well under the abstraction threshold" reasoning. A helper would have to be named (`width_mask` is the natural choice) but would only save 6 characters per site and force readers to navigate to a definition for what is now obviously a one-line idiom.

If a future fourth site appears (or a peripheral sub-system needs the same mask construction), revisit. Not now.

### 4.4 Resulting code (sketch)

```rust
// SBFX (line 340)
let val = (self.regs.r[rn] >> lsb) & (((1u64 << width) - 1) as u32);

// BFI / BFC (line 349)
let mask = (((1u64 << width) - 1) as u32) << lsb;

// UBFX (line 389)
self.regs.r[rd] = (self.regs.r[rn] >> lsb) & (((1u64 << width) - 1) as u32);
```

`sign_extend` at `:341` is unchanged: it already handles `bits=32` correctly via the no-op shifts. After the fix at line 340, `val` for SBFX width=32 is `rn >> 0 & 0xFFFF_FFFF = rn`, and `sign_extend(rn, 32) = rn` — the architecturally correct identity for "sign-extend the whole 32-bit word".

### 4.5 BFI sub-case — does the existing `(rn << lsb) & mask` still work?

For BFI width=32 (lsb=0, msb=31, Rn ≠ 15) the post-fix code computes:
```
mask = 0xFFFF_FFFF
rd = (rd & !mask) | ((rn << 0) & mask)
   = (rd & 0)     | (rn & 0xFFFF_FFFF)
   = rn
```
Exactly the architectural "replace the whole word" semantics. No further branching needed.

## 5. Test plan

All tests live in `crates/mdrp2350/src/tests.rs` `mod stage2_thumb32_residue` (immediately around the existing `bfc_full_width_clears_word`). The hw0/hw1 encodings follow the patterns already used in that module — match the existing style (Rust closures, `c.execute_one_wide`).

### 5.1 Re-enable the existing skipped test

`bfc_full_width_clears_word` (`tests.rs:24587`) currently ends with `let _ = c.reg(0);` and a comment about the unspecified width=32 behaviour. Replace with:
```rust
assert_eq!(c.reg(0), 0, "BFC width=32 must clear the entire destination word");
```
and delete the "implementation behaviour at width=32 is unspecified" paragraph — that's no longer true.

### 5.2 New positive tests at width=32

Three new tests, parallel to the existing narrower-width tests:

1. **`bfi_full_width_replaces_word`** — BFI with lsb=0, msb=31, Rn != 15.
   - Pre: R0 = 0xDEAD_BEEF, R1 = 0x1234_5678.
   - Encode `enc_t32_bfi(rd=0, rn=1, lsb=0, width=32)` style: hw0=0xF361 (Rn=1), hw1=31.
   - Assert `c.reg(0) == 0x1234_5678`.

2. **`sbfx_full_width_passthrough_negative`** — SBFX with lsb=0, width=32, sign bit set.
   - Pre: R1 = 0x8000_0000.
   - hw0 = 0xF200 | (0b10100u16 << 4) | 1 = 0xF541, hw1 = 31.
   - Assert `c.reg(0) == 0x8000_0000` (sign-extension of a 32-bit field is identity).

3. **`ubfx_full_width_passthrough`** — UBFX with lsb=0, width=32.
   - Pre: R1 = 0xCAFE_BABE.
   - hw0 = 0xF200 | (0b11100u16 << 4) | 1 = 0xF7C1, hw1 = 31.
   - Assert `c.reg(0) == 0xCAFE_BABE`.

### 5.3 Regression — existing narrower tests

The following must remain green (no behaviour change at widths < 32):
- `bfc_byte_field_in_middle` (BFC width=8)
- `ubfx_high_field` (UBFX width=24)
- `sbfx_low_byte_negative` (SBFX width=8)
- All bitfield cases in `gen_t32_dp_plain_imm` (`crates/mdpicoem-harness/src/thumb32_gen.rs:4535–4660`) when `qemu_diff_m33` is run against QEMU.

Mathematically, the u64-widened expression at width ∈ 1..=31 is bit-identical to the original `1u32 << width` expression — the upper bits truncated by `as u32` are zero in that range. Confirmed by the type coercion: `((1u64 << w) - 1) as u32 == (1u32 << w) - 1` whenever the latter is well-defined.

### 5.4 QEMU diff oracle coverage gap (follow-up, not in this work-package)

`gen_t32_dp_plain_imm` covers BFI/BFC/SBFX/UBFX at widths 1, 4, 8, 16 only. There is no random fuzz generator for this instruction class today. **Width=32 is not in the QEMU corpus.**

This means once the unit-test fix lands, the QEMU oracle will not independently re-validate the width=32 boundary — only the new unit tests will. That is acceptable for this work-package: the unit tests are deterministic and the architectural behaviour is fully specified. A follow-up to extend `gen_t32_dp_plain_imm` with explicit width=32 cases (one per instruction, four cases) is logged here but **not in scope**. If that follow-up is wanted, it lives in `crates/mdpicoem-harness/src/thumb32_gen.rs::gen_t32_dp_plain_imm` and is mechanical (4 new closures matching the existing pattern, lsb=0, width=32).

- **Refactoring the SSAT/USAT or other adjacent bit-field paths.** Those compute `1i32 << (sat_bit - 1)` and `1i64 << sat_bit` already; no UB there at the architecturally-legal sat_bit ranges. Don't touch them.
