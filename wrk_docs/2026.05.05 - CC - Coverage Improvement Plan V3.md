# Coverage Improvement Plan V3 — 2026-05-05

Companion to `2026.05.05 - CC - Coverage Baseline V3.md`.
Baseline: **91.18 % branch in-scope** (5 500 / 6 032).
Predecessor: `2026.04.28 - CC - Coverage Improvement Plan V2.md`.

## Targets

| Tier | Branch goal | Branches to cover | Notes |
|------|------------:|------------------:|-------|
| **Primary** | **≥ 95.0 %** | +230 | Defensible upper bound for "covered everything reasonably reachable" |
| Stretch    | ≥ 96.0 %     | +291 | Consistent with §9 of the 04-29 final report |
| Aspirational | ≥ 98.0 %   | +412 | Almost certainly not achievable; long-tail single-branch arms in `execute_fpu`/`execute_thumb32`/`exceptions` |

The user's stated bar is "high 80s" defensible. The current 91.18 %
exceeds that already, but we have headroom to push to 95 % with
focused stages, which is what this plan executes.

## Operating rules (from V2, retained)

- **Agent-per-file (or tightly-related-pair).** Each agent gets a
  single file or a same-subsystem pair, the missed-branch number,
  the cargo command, and explicit line numbers from the
  `target/cov-full.json` detail file.
- **Run agents in parallel within a stage.** One stage = one
  parallel batch of 4–6 file-level agents → one re-measure → one
  commit. Do not re-measure between files within a stage.
- **Commit per stage.** Stage commit message format:
  `tests: stage <N> — <area> coverage (<before%> → <after%> branch)`.
- **Tests must be real.** No `assert!(true)` padding; no
  `#[ignore]`-but-counted tests. If a branch is provably unreachable,
  request `#[cfg_attr(coverage_nightly, coverage(off))]` with a
  one-line source comment justifying it.
- **No production-code reshape disguised as testing.** If a branch
  needs a tested code path but is sealed under a private boundary,
  prefer adding a `#[cfg(test)]` accessor or moving the test inline
  rather than weakening the production API.
- **Match the existing test style.** Most chips already have
  `tests.rs` and `pio_tests.rs` files; new tests go there.
  Cross-cutting integration tests go under `crates/<crate>/tests/`.

## Standard coverage command (every stage)

```bash
cargo +nightly llvm-cov --workspace --exclude epio-sys \
    --branch --json --output-path target/cov-full.json
COV_JSON=target/cov-full.json python3 scripts/cov_analyze.py \
    | tee target/cov-rollup.txt
```

`scripts/cov_analyze.py` is the JSON-walking helper that prints
workspace + in-scope + per-crate totals plus the top-30 missed-branch
files. It was updated 2026-05-05 to handle the post-restructure
crate paths and to read `$COV_JSON`.

to ensure we're measuring everything that *can* be measured at default

## Stage 1 — Threaded runtime + I²C state machine

The four files with the lowest in-scope branch coverage of any
non-trivial size:

| File | Missed | Total | Now | Target | Notes |
|------|------:|------:|----:|-------:|-------|
| `rp2040-emu/src/threaded/emulator.rs`           | 24 | 64 | 62.50 % | ≥ 92 % | Builder error arms, worker spin-up/spin-down, halt-on-shutdown, panic injection (with `testing`) |
| `rp2350-emu/src/threaded/emulator.rs`           | 24 | 90 | 73.33 % | ≥ 92 % | M33 builder error arms, RISC-V parallel core start/stop, FPU lazy-save mailbox |
| `rp2350-emu/src/peripherals/i2c.rs`             | 20 | 52 | 61.54 % | ≥ 92 % | DW_apb_i2c arbitration-lost path, GEN_CALL handling, raw-data direct-push (no slave model) |
| `picoem-common/src/threaded/barrier.rs`         |  5 | 28 | 82.14 % | ≥ 95 % | Watchdog-fire path, poison-after-fire, deadlock-recovery |

**Goal: +60 branches → 5 560 / 6 032 = 92.18 %.**

Technique notes:
- For the threaded `emulator.rs` builder errors, drive
  `EmulatorBuilder` with a deliberately-unsupported config
  (e.g. `Threaded` on a non-x86_64 platform — gated `#[cfg(...)]`),
  or directly assert against the `ConfigError` enum members where the
  builder catches them.
- For panic-injection branches, use `inject_panic_for_testing` from the
  `testing` feature; the `tests/execution_model.rs` integration test
  already does this and shows what a working scenario looks like.
- For `i2c.rs`, drive the DW_apb_i2c register interface through `Bus`
  with the master-mode register sequence; the missed branches are
  inside the IC_DATA_CMD restart/stop encoding and the
  `IC_RAW_INTR_STAT` mask updates.
- For `barrier.rs`, use a 2-thread `loom`-style test that triggers the
  watchdog by holding a thread past `DEFAULT_DEADLINE`.

Commit: `tests: stage 1 — threaded runtime + i2c (91.18 % → ~92.2 %
branch)`.

| File | Missed | Total | Now | Target |

| `rp2040-emu/src/dma.rs`                        |  3 |  72 | 95.83 % | ≥ 97 % |

Technique notes:
- For `bus/mod.rs` (both chips), focus on the reserved-region
  narrow-access fault paths. The Stage 3 of plan V2 covered the
  wide-access variants; the narrow `read8`/`read16`/`write8`/`write16`

- For `bus/sio.rs` and `bus/ppb.rs`, the missing branches are
  spinlock contention edges and ICSR pendsv-set-clr corners; both

## Stage timing

Each stage:
- Agents work in parallel (4-6 per stage).
- Estimated 30-60 min agent time per stage.
- Re-measure: 12 min cargo llvm-cov rebuild + 1 min rollup.
- Commit: 1 min.

Realistic per-stage wall-clock: 45-90 min.
Total budget across 6 stages + Stage 0: **~6-9 hours active work**.

## Exit criteria

After each stage, re-run:

```bash
cargo +nightly llvm-cov --workspace --exclude epio-sys \
    --branch --json --output-path target/cov-full.json
COV_JSON=target/cov-full.json python3 scripts/cov_analyze.py \
    | tee target/cov-rollup.txt
```

Stop conditions (hit any one):
1. **In-scope branch coverage ≥ 95 %** (primary target, after Stage 4).
2. **In-scope branch coverage ≥ 96 %** (stretch target, after Stage 6).
3. Two consecutive stages adding < 0.3 pp each — diminishing-returns
   point, escalate to Arthur.
4. Any stage introduces a test failure that can't be fixed within the
   stage — escalate.

## What we are explicitly NOT chasing

- **Workspace headline > 65 %** — bound by hardware-only binaries.
  Document, don't chase.
- **TUI panel coverage** — interactive only, not unit-testable in
  process.
- **Harness binary coverage** — same.
- **`epio-sys`** — vendored submodule, requires clang.
- **Test-runner branches in `tests*.rs`** — mostly assertion
  failure paths that *should* be uncovered.

## Risks

1. **`tests/execution_model.rs` requires `testing` feature.** Stage 1
   needs `--features testing` for some panic-injection branches. The
   default cov run does NOT enable this. If we add it, the cov number
   moves on its own (some `inject_panic_for_testing` branches were
   counted as uncovered before; with the feature on, they get
   exercised). The 04-29 report tried this and saw no movement; if
   that's still true, we'll need explicit unit tests rather than
   relying on the integration test.
2. **Branches inside `assert_eq!` in test files.** llvm-cov counts
   the `false` arm of every `assert!` macro as a branch. Some of the
   "missed" branches in non-`tests*.rs` files come from `assert!` in
   `#[test]` blocks inside library modules. These are good — the
   tests pass. The in-scope filter excludes `tests*.rs` for this
   reason; if a library module has `mod tests` inside it, those
   branches stay in scope.
3. **Agent cost-per-test ratio drops late in the curve.** The 04-29
   report saw 0.1 branch/test in late stages vs 0.6 branch/test in
   early stages. Allow for stages 5-6 to underdeliver vs the target.
