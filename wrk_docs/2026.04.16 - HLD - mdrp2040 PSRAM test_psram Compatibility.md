# HLD: mdrp2040 PSRAM test_psram Compatibility

**Date:** 2026-04-16
**Status:** Design review
**Author:** Phase D design agent
**Blocks:** PicoGUS end-to-end audio bring-up (firmware parks in `err_blink` at SRAM `0x2000_160C`)

## 1. Purpose

PicoGUS v4.0.0 firmware calls `test_psram(&psram_spi, 97)` on core 0 during
early init. This function writes a 1 MB test pattern into PSRAM via
`psram_write32` (32-bit SPI write, opcode `0x02`), then reads it back at 8-bit,
16-bit, and 32-bit widths via `psram_read8/16/32` (fast-read, opcode `0x0B`).
Any mismatch returns 1 (failure). The firmware retries once with
`fudge=!fudge`; both fail, and `err_blink()` parks the CPU forever. Everything
downstream -- settings, GUS reset, `multicore_launch_core1(&play_gus)`, audio
synthesis -- is unreachable.

The root cause is **not in `psram.rs`**. The existing pin-level PSRAM model is
protocol-correct for the SPI commands `test_psram` issues. All 16 existing unit
tests pass, including PIO-driven round-trip tests. The bug is in the bus fabric:
**byte-width DMA writes to PIO TXF registers are silently dropped**, so the PIO
state machine never receives any data and stalls on autopull, producing zero SPI
activity.

## 2. Protocol Characterisation

### 2.1 Upstream `test_psram` (rp2040-psram SHA `7786c93e`)

Source: `psram_spi.c` function `test_psram(psram_spi_inst_t*, int increment)`.

**Write phase (1 MB):**
```c
for (uint32_t addr = 0; addr < (1024 * 1024); addr += 4) {
    uint32_t value = (((addr+3) & 0xFF) << 24) | (((addr+2) & 0xFF) << 16) |
                     (((addr+1) & 0xFF) << 8)  | (addr & 0xFF);
    psram_write32(psram_spi, addr, value);
}
```

Each `psram_write32` builds:
```
write32_command[] = { 64, 0, 0x02, addr>>16, addr>>8, addr, val&0xFF, val>>8, val>>16, val>>24 };
```
10 bytes, DMA'd byte-at-a-time (`DMA_SIZE_8`) into PIO1 TXF0 (`0x5030_0010`).

**Read-back phase (three passes):**
- 8-bit: `psram_read8` sends `read8_command[] = {40, 8, 0x0B, addr_hi, addr_mid, addr_lo, 0x00}` (7 bytes DMA write to TXF0), then DMA reads 1 byte from RXF0.
- 16-bit: `psram_read16` sends same 7-byte command with `read_bits=16`, DMA reads 2 bytes from RXF0.
- 32-bit: `psram_read32` sends same 7-byte command with `read_bits=32`, DMA reads 4 bytes from RXF0.

All three use `pio_spi_write_read_dma_blocking` which:
1. `dma_channel_transfer_from_buffer_now(write_dma, src, src_len)` -- DMA_SIZE_8 writes to TXF0.
2. `dma_channel_transfer_to_buffer_now(read_dma, dst, dst_len)` -- DMA_SIZE_8 reads from RXF0.
3. Waits for both DMA channels to complete.

**SPI commands used:** `0x02` (Write) and `0x0B` (Fast Read) only.
No QPI commands (`0x38`, `0xEB`, `0x35`, etc.) are issued -- confirmed by
tracing through `psram_write32`/`psram_read8`/`psram_read16`/`psram_read32`.
The `qspi_psram` PIO program is NOT loaded; only `spi_psram_fudge` or
`spi_psram` (both single-bit SPI) are used.

### 2.2 PIO Program (`psram_spi.pio`, `spi_psram_fudge` variant)

10 instructions, `.side_set 2` (bit 1 = SCK on GPIO2, bit 0 = CS on GPIO1):

```
[0] out x, 8       side 0b01   ; x = write-bit count. CS=1 (deasserted), SCK=0
[1] out y, 8       side 0b01   ; y = read-bit count.  CS=1, SCK=0
[2] jmp x--, [3]   side 0b01   ; pre-decrement x.     CS=1, SCK=0
[3] out pins, 1    side 0b00   ; MOSI = OSR MSB.      CS=0 (asserted), SCK=0
[4] jmp x--, [3]   side 0b10   ; raise SCK.           CS=0, SCK=1
[5] jmp !y, [0]    side 0b00   ; write-only? back to begin. CS=0, SCK=0
[6] nop            side 0b10   ; fudge: extra SCK cycle. CS=0, SCK=1
[7] jmp [9]        side 0b00   ; CS=0, SCK=0
[8] in pins, 1     side 0b00   ; read MISO. CS=0, SCK=0 (falling-edge sample >83MHz)
[9] jmp y--, [8]   side 0b10   ; raise SCK. CS=0, SCK=1
```

PIO SM0 config (`pio_spi_psram_cs_init`):
- OUT_BASE = MOSI (GPIO3), OUT_COUNT = 1.
- IN_BASE = MISO (GPIO0).
- SIDESET_BASE = CS (GPIO1), SIDESET_COUNT = 2 (CS + SCK).
- Shift direction = left (MSB-first) for both OUT and IN.
- Autopull enabled, pull threshold = 8.
- Autopush enabled, push threshold = 8.

Data flow for a `write32_command` (10 bytes):
1. Bytes `[64, 0, 0x02, ...]` are DMA'd one at a time into TXF0.
2. PIO autopulls each FIFO word into OSR.
3. `out x, 8` / `out y, 8` extract the write-count (64) and read-count (0).
4. `out pins, 1` shifts one MOSI bit per SCK cycle, 64 times total.
5. Since y=0, `jmp !y, begin` returns to idle; CS goes high on next `out x`.

Data flow for a `read8_command` (7 bytes write, 1 byte read):
1. 7 bytes DMA'd to TXF0 (40 write bits, 8 read bits, 0x0B cmd, 3 addr, 1 dummy).
2. PIO shifts out 40 MOSI bits: cmd + addr + dummy.
3. Since y=8 != 0, PIO enters read loop: 8x `in pins, 1` (samples MISO).
4. After 8 bits, autopush fires: ISR pushed to RX FIFO.
5. DMA reads 1 byte from RXF0 into the destination buffer.

### 2.3 ARM AHB-Lite Byte Replication

On Cortex-M0+ (and all ARM AHB-Lite masters), a byte-width write (`HSIZE=0`)
places the byte value on **all four lanes** of HWDATA:
`HWDATA = byte | (byte << 8) | (byte << 16) | (byte << 24)`.
This is standard ARM bus behaviour (ARM IHI 0033C, AHB-Lite spec, §3.2).

The PIO hardware latches the full 32-bit HWDATA on any write to TXF, regardless
of HSIZE. So a byte write of `0x40` to TXF pushes `0x40404040` into the FIFO.
With shift-left, `out x, 8` extracts bits [31:24] = `0x40`. Correct.

This is WHY the rp2040-psram library can use `io_rw_8` casts and DMA_SIZE_8 to
write individual bytes to TXF and have the PIO program see the right values.

## 3. Existing Model Gap

### 3.1 Primary Bug: `Bus::write8` drops PIO byte writes

**File:** `crates/mdrp2040/src/bus/mod.rs`, lines 1078-1085:
```rust
0x4 | 0x5 => {
    let canonical = addr & !0x3000;
    let base = canonical & 0xFFFF_F000;
    if base == PIO0_BASE || base == PIO1_BASE {
        // PIO is 32-bit access only (matches mdrp2350) -- byte
        // writes would trigger spurious RXF pops via the RMW
        // read. Silently ignore.
        return;
    }
```

This early return was added to prevent the generic RMW path from triggering
spurious RXF pops (since the RMW read of a word-aligned PIO register that
includes an RXF offset would consume a FIFO entry). The intent was correct for
*most* PIO registers, but it **also silently drops writes to TXF0-TXF3**.

TXF registers are write-only with FIFO-push side effects. They do NOT need RMW
protection -- they need *direct-push* handling, identical to how UART_DR and
SPI_DR are dispatched through `peripheral_has_narrow_register` /
`narrow_peripheral_write8`.

**Impact:** Every byte-width DMA write to TXF0 is a no-op. The PIO SM's TX
FIFO stays empty. Autopull stalls the SM immediately at the first `out x, 8`
instruction. No SCK/CS/MOSI transitions ever occur. The PSRAM model never sees
any SPI activity. `test_psram` reads back zeros (or whatever was in the buffer
before), mismatches, returns 1.

### 3.2 Secondary Bug: `Bus::read8` from RXF pops-and-truncates

**File:** `crates/mdrp2040/src/bus/mod.rs`, lines 924-932:
```rust
0x4 | 0x5 => {
    ...
    let word = self.peripheral_read32(addr & !3);
    word.to_le_bytes()[(addr & 3) as usize]
}
```

A byte-width read from RXF0 (`0x5030_0020`) calls `peripheral_read32(0x5030_0020)`,
which pops a 32-bit word from the RX FIFO, then returns only the LSB. On real
hardware, a byte read from RXF pops the 32-bit FIFO word and places byte lane 0
on HRDATA[7:0]. Our code does the same thing functionally -- the pop is correct,
and `to_le_bytes()[0]` returns the LSB.

However, the ARM AHB byte-read response replicates the byte across all lanes of
HRDATA (so the CPU sees `byte | byte<<8 | byte<<16 | byte<<24`). For single-byte
DMA reads this doesn't matter -- DMA_SIZE_8 only looks at bits [7:0].

The *real* problem is that the PIO program uses shift-left for IN, and autopush
at threshold 8. The ISR accumulates 8 bits from `in pins, 1` into bits [7:0]
(shift-left: new data goes to LSB). On autopush, the full 32-bit ISR
(`0x000000XX`) is pushed to the RX FIFO. A byte read of lane 0 from the 32-bit
FIFO word correctly returns `XX`. So this path is actually fine for the 8-bit
case.

For 16-bit and 32-bit reads (`psram_read16`/`psram_read32`), the firmware
issues `pio_spi_write_read_dma_blocking` with `DMA_SIZE_8` and `dst_len=2` or
`dst_len=4`. The DMA does 2 or 4 separate byte-width reads from RXF0. Each
read pops a full 32-bit word from the FIFO and returns the LSB. So for a 32-bit
PSRAM read, 4 separate PIO FIFO pushes (each containing one byte of data in the
LSB) are consumed by 4 byte-width DMA reads. Each DMA read correctly deposits
one byte into the destination buffer. This works.

**Conclusion:** The read path is NOT buggy for this specific protocol. Each PIO
autopush at threshold 8 produces one 32-bit FIFO entry with the byte in bits
[7:0]; each DMA byte-read pops that entry and returns byte 0. The byte ordering
in the destination buffer matches what the firmware expects.

### 3.3 Non-issue: PSRAM model (`psram.rs`)

The pin-level PSRAM model is **correct** for the SPI command subset
`test_psram` uses:
- `0x02` Write with 3-byte big-endian address and streaming data: handled.
- `0x0B` Fast Read with 3-byte address, 8 dummy cycles (1 byte), streaming
  data out on MISO: handled.
- `0x66` / `0x99` Reset Enable / Reset sequence: handled.
- No QPI commands are issued.
- Address width: 24-bit (3 bytes big-endian) -- matches.
- Bit ordering: MSB-first -- matches.
- Dummy cycle count: 8 (one byte) -- matches.

All 16 existing PSRAM unit tests confirm protocol correctness in isolation.

## 4. Evidence

### 4.1 Code-level trace (no instrumentation needed)

The bug is in the bus dispatch logic, not in the PSRAM model or PIO execution
engine. The evidence is purely structural:

1. `psram_spi_init_clkdiv` configures DMA write channel with `DMA_SIZE_8` and
   write address `&spi.pio->txf[spi.sm]` = `0x5030_0010` (PIO1 TXF0).

2. Every `psram_write*` and `psram_read*` function ultimately calls either
   `pio_spi_write_dma_blocking` or `pio_spi_write_read_dma_blocking`, which
   triggers the DMA write channel.

3. The DMA engine (`crates/mdrp2040/src/dma.rs`, line 526) performs
   `bus.write8(write_addr, value as u8)` for DMA_SIZE_8 transfers.

4. `Bus::write8` (`crates/mdrp2040/src/bus/mod.rs`, line 1081) checks
   `if base == PIO0_BASE || base == PIO1_BASE { return; }` -- **silently
   drops the write**.

5. PIO1 SM0's TX FIFO never receives any data.

6. SM0 stalls on the first `out x, 8` (autopull from empty FIFO).

7. No SCK/CS/MOSI transitions occur.

8. `psram.tick()` never observes a CS-low + SCK-rising-edge sequence.

9. PSRAM buffer is never written to; reads return zero.

10. `test_psram` compares expected pattern against zero; returns 1 (failure).

### 4.2 Counterfactual: existing tests pass because they don't use DMA

- **Unit tests** (`psram.rs::tests`): call `psram.tick()` directly with
  hand-crafted pin bitmasks. No bus involved.
- **Bus integration tests** (`psram.rs::bus_integration`): poke SIO GPIO_OUT
  registers (32-bit writes to SIO_BASE, which is region 0xD, not 0x4/0x5) and
  call `emu.update_gpio()`. No PIO, no DMA.
- **PIO integration tests** (`psram.rs::pio_integration`): use a hand-installed
  SCK-toggler PIO program with SIO-driven CS/MOSI (again, 32-bit SIO writes).
  The PIO program here is a trivial `SET PINS` oscillator that doesn't consume
  TXF data -- it generates a fixed SCK waveform while the test drives MOSI from
  SIO. No DMA.

None of these tests exercise the DMA -> TXF0 -> PIO SM -> pin -> PSRAM -> pin
-> PIO SM -> RXF0 -> DMA path that the real firmware uses.

## 5. Options Considered

### F1: Fix PIO Narrow-Write Dispatch in `Bus::write8`

Add PIO TXF0-TXF3 as narrow-write registers, bypassing the blanket PIO-drop
guard. On a byte write to TXF, replicate the byte to all four lanes (ARM AHB
byte replication) and push the resulting 32-bit word into the TX FIFO. On a byte
read from RXF, the existing generic path (pop word, return LSB) is already
correct.

**Scope:** Modify `Bus::write8` (and optionally `Bus::write16`) in
`crates/mdrp2040/src/bus/mod.rs` to add PIO TXF/RXF to the narrow-register
dispatch. ~30 lines changed in bus/mod.rs. Add a unit test that exercises the
DMA -> TXF0 -> PIO -> PSRAM -> RXF0 -> DMA round-trip. ~60 lines test code.

**Estimate:** ~90 LOC changed/added. 2-3 hours including test.

**Risk:** Low. The change is confined to one dispatch branch in `write8`. Existing
bus tests are unaffected (they use 32-bit PIO writes). The blanket PIO-drop guard
for *non-TXF* registers remains in place, preserving the RMW-pop protection for
RXF and other side-effect registers.

**Verdict:** Fixes the root cause. Verifiable via unit test before firmware re-run.

### F2: PIO-FIFO-Level Loopback (bypass pin-level simulation)

Intercept TXF0 writes and RXF0 reads at the bus level, parse the QSPI byte
protocol directly, and loopback through a PSRAM model without involving the PIO
execution engine or pin-level PSRAM.tick().

**Estimate:** ~200 LOC new code. 4-6 hours. Risk of duplicating protocol state
machine already in psram.rs.

**Verdict:** Overly complex. The pin-level PSRAM model already works; the PIO
engine already works; only the bus byte-write dispatch is broken. F2 builds
around the bug instead of fixing it.

### F3: Firmware Patch (NOP the BL to err_blink)

Patch flash `0x1000_A414`: change `f7ff f9f4` (BL err_blink) to `bf00 bf00`
(NOP NOP). Firmware continues past the PSRAM failure.

**Estimate:** ~10 LOC patch script. 30 minutes.

**Risk:** High. PSRAM is used by the GUS voice synth on core 1. Without a
functioning PSRAM model, `play_gus` reads garbage from PSRAM and produces
incorrect audio output. Every downstream debug session would need to account for
"PSRAM reads return zero" as a confound. Also fragile: any firmware version
change invalidates the patch offset.

**Verdict:** Papering over the root cause. Unblocks firmware past `err_blink`
but breaks the audio path that is the entire point of PicoGUS bring-up.

## 6. Recommendation

**F1: Fix PIO Narrow-Write Dispatch.**

Justification:
- Smallest change (~30 LOC in production code).
- Fixes the root cause.
- All existing tests remain green.
- New unit test provides regression coverage.
- The PSRAM model + PIO engine are already correct; only the bus glue is wrong.
- Unblocks both `test_psram` and the downstream audio path (GUS voice synth
  reads from PSRAM via the same DMA+PIO mechanism).

## 7. Test Plan

### 7.1 New Unit Test: DMA-to-PIO-to-PSRAM Round-Trip

Add a test to `crates/mdrp2040/src/peripherals/psram.rs` (or a new test module
in `crates/mdrp2040/src/tests.rs`) that reproduces the exact `test_psram` byte
sequence for one write+read cycle:

1. Build an `Emulator` with the real `spi_psram_fudge` PIO program loaded into
   PIO1 SM0 (matching firmware's PINCTRL, SHIFTCTRL, EXECCTRL, CLKDIV).
2. Configure DMA channel 0: DMA_SIZE_8, read-increment, write to TXF0.
3. Configure DMA channel 1: DMA_SIZE_8, write-increment, read from RXF0.
4. Load `write32_command[] = {64, 0, 0x02, 0, 0, 0, 0xDE, 0xAD, 0xBE, 0xEF}`
   into SRAM; trigger DMA channel 0.
5. Run the emulator for enough cycles to complete the DMA transfer and PIO
   execution.
6. Verify PSRAM buffer at address 0x000000 contains `[0xDE, 0xAD, 0xBE, 0xEF]`.
7. Load `read8_command[] = {40, 8, 0x0B, 0, 0, 0, 0}` into SRAM; trigger both
   DMA channels (write + read).
8. Run the emulator for enough cycles.
9. Verify the DMA read destination byte equals `0xDE`.

**This test must fail against current code** (write8 to TXF0 is dropped) **and
pass after the fix.**

### 7.2 Existing Tests: Regression

All existing tests must remain green:
- `cargo test -p mdrp2040` (includes all 16 PSRAM tests, instruction tests,
  PIO tests, firmware smoke tests).
- `cargo test -p mdpicoem-common` (PIO SM engine tests).

### 7.3 Firmware Validation

After the fix, run:
```bash
cargo run -p mdpicoem-harness --release --bin picogus_probe_pc -- \
    third_party/picogus/picogus-v4.0.0.bin --cycles 200000000
```

**Expected:** PC advances past flash `0x1000_A414` (the `err_blink` call site)

- PIO1 SM0 running (not stalled on autopull).

## 10. Implementation Notes

### 10.1 Byte Replication for TXF Writes

The fix must replicate the written byte across all four lanes before pushing to
the TX FIFO, matching ARM AHB-Lite byte-write behaviour:

```rust
// In Bus::write8, PIO TXF dispatch:
let replicated = (val as u32) * 0x01010101; // byte on all 4 lanes
self.pio[idx].sm[sm].tx_fifo.push(replicated);
```

This ensures the PIO program's `out x, 8` with shift-left extracts the correct
byte from bits [31:24].

### 10.2 TXF Offset Detection

PIO TXF0-3 are at offsets `0x010`, `0x014`, `0x018`, `0x01C` within the PIO
register block. RXF0-3 are at `0x020`-`0x02C`. The dispatch must distinguish
TXF (push on write) from RXF (pop on read) from other PIO registers (keep the
blanket-drop guard).

```rust
let pio_offset = canonical & 0x0000_0FFF;
match pio_offset {
    0x010..=0x01C => {
        // TXF write: replicate byte and push to TX FIFO
        let sm_idx = ((pio_offset - 0x010) / 4) as usize;
        let replicated = (val as u32) * 0x01010101;
        let pio_idx = if base == PIO0_BASE { 0 } else { 1 };
        self.pio[pio_idx].sm[sm_idx].tx_fifo.push(replicated);
    }
    _ => {
        // All other PIO registers: keep the blanket-drop guard
        return;
    }
}
```

### 10.3 RXF Read Path (No Change Needed)

The existing `read8` path for PIO RXF is correct for this protocol:
1. `peripheral_read32(addr & !3)` pops a 32-bit word from the RX FIFO.
2. `to_le_bytes()[0]` returns byte 0 (the LSB).
3. The PIO autopush puts the 8-bit ISR value in bits [7:0] (shift-left, threshold 8).
4. So byte 0 of the LE representation is the data byte. Correct.

No change to `read8` is needed for `test_psram` compatibility.

### 10.4 Halfword (16-bit) Writes to TXF

For completeness and future-proofing, `Bus::write16` should also handle PIO TXF
writes. ARM AHB halfword writes replicate the halfword across both 16-bit lanes:
`HWDATA = half | (half << 16)`. The current `write16` likely has the same
blanket-drop issue for PIO. Check and fix in the same commit if so.

## 11. Out of Scope

- **Multicore launch handshake** (`maybe_wake_core1`): concurrent team owns this.
  The fix here unblocks firmware reaching `multicore_launch_core1`, but the
  handshake itself is a separate concern.
- **DMA modelling accuracy**: the DMA engine already transfers bytes correctly;
  the bug is bus-side, not DMA-side.
- **Full QPI protocol**: `test_psram` uses single-SPI only. QPI would require
  `out pins, 4` / `in pins, 4` and the `qspi_psram` PIO program. Not needed.
- **PSRAM model enhancements**: the pin-level model is correct for the command
  subset in use. No changes to `psram.rs` protocol handling.
- **mdrp2350 PIO narrow writes**: mdrp2350 has no PIO-driven external device
  that uses DMA byte writes to TXF. Not in scope.

## 11. Acceptance Criteria

1. **Unit tests green:** `cargo test -p mdrp2040` passes, including the new
   DMA+PIO+PSRAM integration test.
2. **New test fails on current code:** The DMA+PIO+PSRAM test must fail before

3. **Firmware advances past `err_blink`:** `picogus_probe_pc` against real

   `0x1001_A6DC` (or its SRAM copy) within 200M cycles.
4. **Existing tests unaffected:** All PSRAM, PIO, instruction, and firmware
