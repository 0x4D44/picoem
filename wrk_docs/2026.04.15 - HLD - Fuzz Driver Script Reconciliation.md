**Status:** **Signed off** by team lead, 2026-04-15. Agent C authored the draft; §10 captures the lead's review and the decisions that close out the risks/open questions flagged in §9. Implementation may proceed against this HLD as-is.

## 1. Goal & non-goals

**Goal.** Reconcile the three bash fuzz drivers under `d:\language\mdrp2354\fuzz-runs\` so each independently survives the failure modes observed during the 2026-04-14 overnight campaign (see `wrk_journals\2026.04.14 - JRN - Overnight QEMU Fuzz Campaign.md`). Specifically: transient Windows exe-locks (Defender / AV) and mid-run deletion of `fuzz-runs/deadline`.

**Non-goals.**
- No new abstractions; no shared bash library; no pipeline framework.
- No changes to the Rust oracle binaries (Agent A) or Windows runbook (Agent B).
- No new hardening beyond what the campaign actually demanded.

## 3. Proposed target state

One row per driver × hardening. "Hardenings to consider" numbering matches the task brief.

| # | Hardening | run-m33.sh | run-m0plus.sh | run-probe.sh |
|---|---|---|---|---|
| 1 | PID-qualified `.exe` copy + `trap rm EXIT` | already present | already present | already present |
| 2 | Deadline read-once + fallback | **add** (mirror run-probe.sh lines 11–14) | **add** (mirror run-probe.sh lines 11–14) | already present |
| 3 | Pre-batch scrub of zombie QEMU on oracle port | **skip** (duplicates Agent A) | **skip** (duplicates Agent A) | **skip** (no QEMU) |
| 4 | Guarded `cp -f` with explicit error on missing source | **add** | **add** | **add** |
| 5 | `set -Eeuo pipefail` at top | **skip** | **skip** | **skip** |
| 6 | Timestamp every log line | **skip** | **skip** | **skip** |
| 7 | Shared bash helper (`_common.sh`) | **skip** (see §5) | **skip** (see §5) | **skip** (see §5) |

**Decisions in prose.**

- **(#2) Add.** This is the required carry-over from the campaign. Each script captures `DEADLINE` at start, falls back to `now + 28800` (8 h) if the file is empty or missing, and loops on the variable. The loop survives any mid-run deletion of the file. Log a single line at start recording the effective deadline for post-mortem.

- **(#3) Skip.** Agent A is fixing zombie-QEMU cleanup in the Rust oracle itself (spawn a child process guard that kills the QEMU child on any exit path). Duplicating it in bash has two costs: (a) it hides a Rust-side regression if Agent A's fix silently breaks, and (b) port cleanup on Windows from bash needs `netstat -ano | awk | taskkill` — exactly the fragile tool chain the campaign spent an hour failing at (see journal 00:05–00:15). The bash scripts are a worse place to own this invariant. Single owner (Rust oracle) wins.

  *Counter-argument:* belt-and-braces could save a campaign night if Agent A's fix has a gap. Rejected because the fragility of Windows port cleanup from bash makes the brace more dangerous than the belt — the kill pipeline can itself hang and wedge the runner (see 00:15 journal entry). Let the Rust fix own it; revisit only if it proves inadequate.

- **(#4) Add.** Currently `cp -f target/release/<driver>.exe "$BIN"` fails silently if the source is missing (e.g. the binary wasn't built). The next line invokes `"$BIN"`, which also fails, and the runner logs a cryptic batch-end with `rc=127` indistinguishable from a Defender exe-lock. Replace with: check `cp` exit status; on failure, write `driver binary missing: target/release/<driver>.exe` to the log and exit non-zero. Cheap and diagnostic.

- **(#5) Skip.** `set -Eeuo pipefail` would catch some failure modes earlier but changes the failure *shape* for the batch loop: a transient non-zero `rc` from the oracle (the whole campaign depends on survival across these!) would abort the entire driver. The campaign journal shows that rc=127 / rc=1 / rc=2 happened repeatedly and were expected to be tolerated. Keeping the current permissive behaviour is deliberate, not accidental.

  *Counter-argument:* `pipefail` + an explicit `|| true` on the oracle line gives early-warning for script-setup bugs while still tolerating oracle exits. Plausible. Rejected because the script is 25 lines and the scope for script-setup bugs is tiny; the cost (another branch to think about when touching it) exceeds the benefit. Revisit if scripts grow.

- **(#6) Skip.** Each batch already logs start and end timestamps; per-iteration oracle output gets its own timestamps from inside the oracle. Per-line log prefixing would double log size for low marginal signal (we can correlate from batch markers). Not worth it.

- **(#7) Skip — see §5.**

## 4. keep-deadline.sh disposition

**Delete once §3 #2 lands on all three scripts.**

Rationale: the watchdog exists solely to paper over per-iteration `cat "$DEADLINE_FILE"`. Once every driver reads the deadline once at start, the file can be deleted mid-run with no effect. The watchdog then has zero function and is pure confusion — an agent reading `fuzz-runs/` six months from now will wonder why it exists.

Order of operations (for the implementation PR):
1. Land §3 #2 and #4 in `run-m33.sh` and `run-m0plus.sh` (run-probe.sh already has #2; add #4).
2. `git rm fuzz-runs/keep-deadline.sh` in the same commit or immediately after.
3. Update any doc references (grep for `keep-deadline` — there's one mention in the journal entry 2026-04-14 23:49 which is historical and can stay).

## 5. Shared-helper decision

**Reject. Each script stays independent.**

The three drivers are ~25 lines each, differ in oracle name, log path, batch size, and `--fuzz` count — i.e. the parts that matter. The parts that would move to a helper (PID-qualified copy, deadline-read-once, guarded cp) are ~8 lines of boilerplate. Factoring them into `fuzz-runs/_common.sh` buys:

- a new file to maintain,
- a new sourcing layer to debug (path resolution from the bash-driver cwd),
- a new failure mode (helper broken → all three drivers broken simultaneously mid-campaign),

in exchange for removing ~16 duplicated lines. Per Arthur's CLAUDE.md "premature abstractions don't just waste effort — they actively resist the correct design when it arrives": these scripts haven't earned an abstraction yet. Three copies of eight lines is the right shape for a ~30-line driver family. Revisit if we add a fourth driver with the same pattern.

## 7. Testing

Run each on a throwaway deadline:

1. **Happy path.** `echo $(( $(date +%s) + 60 )) > fuzz-runs/deadline`, run each driver with `--fuzz 50` (temporarily edit-swapped in) or equivalent short batch. Confirm it runs N batches, logs deadline-reached, exits rc=0.
2. **Deadline file deletion mid-run.** Start driver with a 120 s deadline. After 30 s: `rm fuzz-runs/deadline`. Confirm the driver keeps looping to the 120 s captured deadline. (This is the 2026-04-14 23:49 failure replayed — run-probe.sh should already pass this today.)
3. **Missing deadline file at start.** `rm fuzz-runs/deadline` before launch. Confirm driver logs fallback deadline (`now + 28 800`), runs until either the fallback or manual kill.
4. **Missing oracle binary.** Rename `target/release/qemu_diff_m33.exe` temporarily. Confirm driver logs a clear "driver binary missing" message and exits non-zero without running a batch.
5. **Concurrent cargo build.** Start driver. `cargo build --release --bin qemu_diff_m33` in parallel. Confirm the build completes (doesn't hit Windows exe-lock) and the driver's in-flight batch completes using the pre-copied PID-qualified exe. (This is the structural guarantee of hardening #1 — already present today, re-verify after edits.)

No automated CI here; these are manual bench checks before a real overnight run.

## 9. Risks

- **Deadline-read-once hides a stale deadline file.** If Arthur edits `fuzz-runs/deadline` mid-run to extend / shorten the window (journal 2026-04-14 §Driver design mentions this as an intentional capability: *"I can stretch or shorten the window by editing one file"*), the edit **will not take effect** — each running driver pinned its deadline at launch. Workaround: Arthur kills and relaunches the driver after editing. This is a behaviour change worth flagging.
- **Guarded `cp -f` rejection blocks a race-condition launch.** If the oracle is being rebuilt at the exact moment of launch, `cp -f` sees a partial file or a lock and the driver exits. Currently the silent `cp` failure gives the same net result (an unrunnable `$BIN`) but with a cryptic rc=127 for the first batch; the guarded version just fails louder and sooner. Net: strict improvement; risk is zero unless a human reads the change wrong.
- **`set -Eeuo pipefail` deliberately not adopted** — rc-tolerant batch loop is a feature, not an accident. If a future author adds `pipefail` thinking it's an obvious hardening, the campaign is silently more fragile (one transient oracle crash aborts the whole night). Call this out in commit message.
- **Deleting `keep-deadline.sh` while an M0+ hot loop is still running from 2026-04-14** — the keeper was launched with `keeper PID=103712` that night and may still be alive. Delete the file only after confirming no bash process is sourcing or re-exec'ing it. `ps -W | grep keep-deadline` should be clean first.
- **Agent A's zombie-QEMU fix has a gap we didn't catch.** Because we're explicitly not adding a bash-side port scrub (§3 #3), any Rust-side regression in Agent A's cleanup path would resurface the M0+ hot-loop scenario. Mitigation: the per-batch rc=127 cluster is cheap to notice (hotloop completes 10 batches/minute in ~0 s each) and the runner auto-recovers when QEMU stops accumulating. Not a campaign-killer; a morning-after observation.

### Decisions on risks and residual questions

1. **Deadline-edit-mid-run capability — accept the loss.** §9's first
   risk flags that pinning deadline at launch removes the "edit one
   file to stretch or shorten the window" capability from 2026-04-14
   §Driver design. Accept the behaviour change. The capability was a
   convenience; the safety fix (survive mid-run deletion) matters more.
   Arthur can relaunch the driver if he needs to extend a window.
   **Required:** call this out in the commit message so future
   archaeologists understand the tradeoff.
2. **No SIGHUP re-read hack.** Do not add a signal-handler re-read
   of the deadline file to "keep" the edit-mid-run capability. That's
   incidental complexity for a marginal feature; the simplicity of
   read-once wins.
3. **Bash-side zombie scrub — skip, confirmed.** Agent A's Job Object
   + `ExitCode` refactor + `ctrlc` handler covers the failure modes
   the campaign saw. Belt-and-braces via bash would duplicate
   ownership of the same invariant across two languages — rejected.
4. **`set -Eeuo pipefail` — stays out.** Agent C's argument is
   correct: the rc-tolerant batch loop is a feature of how the
   campaign survives oracle crashes, not an accident.
5. **Per-line log timestamps — stays out.** Oracle-side progress
   lines already carry their own timing; batch markers bracket the
   rest. Not worth the log bloat.

### Clarifications for implementation

- **Remove `DEADLINE_FILE` variable entirely.** §6's note that
  "`DEADLINE_FILE` becomes unused but can stay for clarity" — no,
  delete it outright. Dead code is noise. The scripts should read
  `fuzz-runs/deadline` directly in the read-once block (mirroring
  `run-probe.sh` which does exactly this) and not declare a constant
  that's referenced only in the read-once line. Clean diff.
- **Guarded `cp -f` — use `cp -f ... && chmod +x` pattern.** Check
  `cp` exit status via `|| { echo "..."; exit 1; }` rather than
  `set -e`. Keeps the rc-tolerant batch loop intact while failing
  loudly on the specific setup error the hardening targets.
- **`keep-deadline.sh` deletion — verify first.** Per §9's fourth
  risk bullet: before `git rm`, run `ps -W | grep keep-deadline` to
  confirm no instance from 2026-04-14 is still running. If one is,
  kill it via the Agent B runbook (i.e. `kill -9 <POSIX_PID>` from
  the PPID walk) *before* deleting the file on disk. That's an
  operator step, not a script step — call it out in the PR
  description.
- **Diff-equivalence acceptance check.** §8's final acceptance item
  `diff <(sed -n '1,20p' ...) <(...)` — extend from 1–20 to 1–25
  to catch the full preamble including the guarded-cp block. Keep
  the test; tighten the range.
- **Commit structure.** One logical commit: "fuzz-runs: reconcile
  run-m33/m0plus deadline-read-once; delete keep-deadline.sh". No
  need to split by file.
