**Date:** 2026-04-17
**Author:** Claude Opus 4.7 (implementer HLD-writer)
**Parent:** `wrk_docs/2026.04.17 - HLD - Stage A.2 Silicon Oracle Residuals Handoff.md` (Residual 2)
**Grandparent:** `wrk_journals/2026.04.16 - JRN - Silicon Oracle Fidelity Gaps Fix Wave.md`
**Ancestor of the bug:** commit `5eac6a1` — "mdrp2350: PWM fractional divider formula + frac_accum reset" (Stage A formula fix; keeper work, not in scope to re-litigate).
**Status:** DRAFT for supervisor review — no code written.

## TL;DR

The parent A.2 HLD proposed three fixes in the emulator's fractional-divider tick path (`frac_accum` reset on EN-write, fixed-point rounding off-by-one, extra tick in setup). Section 1 below shows — with exact CYCCNT-derived math — that **none of those candidates is the real divergence**. The emulator's `PwmRegs::tick` is correct for the declared scenario window; the divergence is a *scenario-design* defect: silicon PWM ticks through setup and readback because the probe can't gate it, while emulator PWM only ticks during the `actual_sysclks` window because setup MMIO writes cost zero virtual cycles. Stage A's reading moved silicon from `HW=0x04` to `HW=0x40` to (today) `HW=0x64` without any emulator regression; the HW side is unstable precisely because the measurement window is unbounded on silicon. Proposed fix: turn `pwm_fractional_div` into a **custom sled** that self-gates (writes `CSR_EN=1` as the sled's first instruction, `CSR_EN=0` as the last before `BKPT`), making both sides measure an identical PWM-enabled window with a small constant overhead. Emulator code does not change. Blast radius is confined to the one scenario; Stage A's unit tests and the sibling `pwm_wrap_irq` scenario are unaffected.

## Section 1 — Re-measurement analysis (MANDATORY)

`crates/mdpicoem-harness/src/silicon_scenarios.rs:1281-1288` (catalogue entry).

const S_PWM_FRACTIONAL_DIV: &[(u32, u32)] = &[

    (PWM_SLICE0_DIV, 0x0020),                    // [3] INT=2, FRAC=0 -> raw divisor = 32 (8.4 = 2.0)

PeriphScenario {

### 1.2 Sysclk configuration

No PLL / CLOCKS writes appear in the setup; `release_common_resets` releases PLL_SYS so the default post-bootrom sysclk (≈150 MHz from PLL_SYS) is in effect. sysclk is irrelevant to the divider math, which is all sysclk-referenced — but it matters indirectly for DAP-write inter-write latency (µs of wall-clock between setup writes translates to many PWM ticks).

### 1.3 Default countdown sled produced by `assemble_sled(max_sysclks=200)`

File: `crates/mdpicoem-harness/src/silicon_scenarios.rs:2002-2024`.

```
  movw r0, #N          ; N = ceil(200/4) = 50  (1 cyc)
loop:
  subs r0, #1          ; 1 cyc
  bne  loop            ; 2 cyc taken (M33 pipeline flush), 1 cyc final fall-through
  bkpt #0              ; halts, CYCCNT frozen
```

Cycles per loop iteration on M33 (approx): 1 (subs) + 2 (bne taken) = 3. For 49 taken + 1 not-taken iterations: `49 × 3 + 2 (final subs + bne-not-taken) + 1 (movw) = 150` sysclks. Real silicon adds 1–2 cycles of pipeline and flash-prefetch variance; the scenario runner captures the true count via DWT CYCCNT and feeds that as `actual_sysclks` to `emu.run()` — both sides see the **same** window size.

For the math below I'll use `actual_sysclks = 152` (worst-case realistic sled cost); the argument holds for 148–156, and any drift in this band alone cannot produce the 0x20 divergence we observe.

### 1.4 Expected CTR after the measurement window

Emulator's tick formula, file `crates/mdrp2350/src/peripherals/pwm.rs:366-378`:

```
divisor = 32             (raw 8.4 encoding of 2.0)
per step_quantum=1 tick: total = frac_accum + 1 * 16
                         advance = total / 32
                         frac_accum = total % 32
```

Expanding 152 × tick(1):

| tick | total | advance | accum |
|------|-------|---------|-------|
|   1  |   16  |    0    |  16   |
|   2  |   32  |    1    |   0   |
|   3  |   16  |    0    |  16   |
|   4  |   32  |    1    |   0   |
| ...  | ...   |   ...   |  ...  |
| 152  |   32  |    1    |   0   |

Total advances = 76.   Raw CTR = **76 = 0x4C**.

The reported `EMU=0x44` is the **masked** reading: `0x4C & 0x64 = 0x44`. Confirmed: 76 masked by 0x64 = bit-wise AND of `0100_1100 & 0110_0100 = 0100_0100 = 0x44`. **So the emulator raw CTR is exactly 76, which is `actual_sysclks / 2` rounded down — precisely what the fractional-divider formula should produce.** The emulator side is self-consistent with the measurement window.

(For a different `actual_sysclks` value the raw EMU CTR would shift, but the fact that `EMU=0x44` masked has stayed constant across A.2 readings suggests actual_sysclks has been stable ≈ 148–155.)

### 1.5 The "mask" is not really a mask

The observe-tuple `(PWM_SLICE0_CTR, 100)` is documented by the author's comment as the expected value (100 = "200 sysclks / 2 = 100"), but the runner (`crates/mdpicoem-harness/src/silicon_scenarios.rs:2292-2294`) treats the second field as a **mask** and compares `hw & mask` vs `emu & mask` for equality. The mask value 100 = 0x64 = `0b0110_0100` is not a contiguous bit-range, so it selects bits 2, 5, and 6 arbitrarily. This is a secondary scenario-authoring defect: even if silicon CTR lands far from 100, the diff can still "PASS" by coincidence when the selected-bit pattern happens to match. The fix in §3 also replaces 0x64 with `0xFFFF` (full 16-bit CTR) so the comparison is a genuine equality.

### 1.6 The HW side math — and why HW raw CTR is free-running

The raw HW reading is **not** pinned down by the scenario. Between DAP write [4] (`CSR_EN=1`) and the probe-side `core.read_word_32(PWM_SLICE0_CTR)`, silicon PWM ticks continuously:

1. Write [4] via DAP: CSR_EN=1 → slice 0 starts counting from that moment. Per datasheet Table 1137 the `EN` register "aliases the CSR_EN bits for all channels … there is only one physical EN register bit, which can be accessed through here or CHx_CSR". So HW needs only write [4] to start; write [5] is a no-op alias. The emulator models them as two separate storage bits (file `pwm.rs:146-162, 353-394`) and requires both ANDed to tick — a second divergence from the datasheet, but not the cause of this residual because by the end of setup both are 1 on both sides.
2. DAP inter-write latency: typical probe-rs DAP word writes land at roughly 1–10 µs each depending on link speed. At 150 MHz sysclk that's 150 – 1500 sysclks between write [4] and write [5], plus further setup-finish → sled-start latency (memory-write of sled bytes, CYCCNT reset, PC/SP/LR writes, `core.run()` request). Conservatively, **multiple thousands of sysclks** elapse between CSR_EN=1 being latched and the CYCCNT window opening.
3. Sled runs for ~152 sysclks; CYCCNT delta = `actual_sysclks` is read.
4. `gate_peripheral_hw(name)` (file `silicon_scenarios.rs:2086-2097`) has branches for PIO / PLL only — **no PWM branch**. Slice 0 keeps ticking through the gate step.
5. The runner then calls `core.read_word_32(PWM_SLICE0_CTR)`. Another 1–10 µs of DAP read latency — more ticks.
6. Even the post-BKPT "halted core" does not gate PWM: the datasheet documents `DBGPAUSE` for TIMER and MTIME, but §12.5 (PWM) makes no mention of a debug-halt gate. Verified in the datasheet extract `wrk_scratch/rp2350_ds.txt` §12.5.2 — no `DBGPAUSE` wording anywhere in the PWM section.

**HW raw CTR = (setup ticks + 152 sled ticks + readback delay) / 2, modulo 65536.** With unbounded setup and readback latencies, the raw HW value is not even stable across runs — the probe's USB scheduling jitter lands it at different 16-bit counter positions each time. Any match under `& 0x64` is chance alignment.

The progression of reported HW values tells the same story:

| Date | Stage A pre-fix | Stage A post-fix (A.2 HLD) | Today (A.2 diagnostic) |
|------|-----------------|------|------|
| HW raw (masked 0x64) | 0x04 | 0x40 | 0x64 |

No emulator change lies between column 2 and column 3 (commit log confirms PWM unchanged since `5eac6a1`), yet HW drifted. The drift is **host-side DAP timing noise surfaced through an over-broad measurement window**, not a silicon change.

### 1.7 Verdict

The new `HW=0x64` reading is **not** a silicon regression or self-correction, and the new `delta=0x20` is **not** informative of any emulator bug. It is the inevitable consequence of:

- **Silicon measurement window = open-ended** (setup + sled + readback), and
- **Emulator measurement window = `actual_sysclks` only** (setup is zero virtual cycles; core halted after `emu.run()`).

The A.2 HLD's candidate list (accumulator reset on EN-write, rounding off-by-one, extra setup tick) **does not apply**. Verified:

- `frac_accum` reset on EN-write — not needed. The `Config::default()` + `EmulatorBuilder::new` path gives a fresh `PwmRegs` with `frac_accum=0` per scenario; no stale state carries in.
- Rounding — the emulator's `(accum + cycles*16) / divisor` lands exactly on silicon's intended arithmetic for DIV=0x0020 (trivial case — divisor is a power-of-2 multiple of 16).
- Extra tick in setup — verified by walking the 152-cycle trace in §1.4. No extra ticks.

**Additional data would help only if we were still trying to prove the emulator is correct**; we now have that proof from the formula itself. The remaining fix is entirely scenario-authoring.

## Section 2 — Root cause

Two defects in `S_PWM_FRACTIONAL_DIV` (both in `crates/mdpicoem-harness/src/silicon_scenarios.rs:947-957`):

1. **Measurement window asymmetry.** The `custom_sled: None` default path runs a purely timing-burning sled (countdown loop → BKPT). Silicon PWM starts ticking at write [4] (`CSR_EN=1`) via DAP, long before the sled starts, and continues through `gate_peripheral_hw` and CTR readback. The emulator PWM starts ticking only when `emu.run(actual_sysclks)` begins, because setup MMIO writes cost zero virtual cycles. Window mismatch ≥ an order of magnitude.
2. **Incorrect "mask" in observe tuple.** The author wrote `(PWM_SLICE0_CTR, 100)` intending "expected value = 100", but the runner treats the second field as a mask. 100 = 0x64 = `0b0110_0100` is a non-contiguous mask that can PASS by coincidence even when raw values differ substantially.

Defect #1 is the residual's true cause. Defect #2 is a latent observation-fidelity problem that would otherwise silently weaken the scenario's guarantee once #1 is fixed.

Out of scope but noted for Arthur: the emulator's split storage of `slice.csr & CSR_EN` vs `self.en` (file `pwm.rs:146-162`) does not match the datasheet's "one physical bit" model. Both bits are 1 at end of setup, so it is not the cause of this residual; it would affect scenarios that write `EN` without `CSR_EN` (or vice versa). This is minor technical debt, tracked in §6 below, not changed by this HLD.

## Section 3 — Proposed fix

All edits are in `crates/mdpicoem-harness/src/silicon_scenarios.rs`. Emulator source is untouched.

### 3.1 Custom sled that self-gates the PWM window

Add a `SLED_PWM_FRACTIONAL_DIV_HW` Thumb halfword array roughly modelled on `SLED_TICKS_TIMER0_RETARGET_HW` (file `silicon_scenarios.rs:503-515`). Shape:

```
  ; r3 = PWM_BASE (0x400A_8000)
  movw r3, #0x8000
  movt r3, #0x400A
  ; CSR_EN = 1 for slice 0 — start ticking HERE
  movs r0, #1
  str  r0, [r3, #0x00]      ; CH0_CSR = 1
  ; busy-spin ~N sysclks; choose N so that N/2 lands in a non-trivial CTR range
  movw r1, #N
loop:
  subs r1, #1
  bne  loop
  ; CSR_EN = 0 — freeze the counter
  movs r0, #0
  str  r0, [r3, #0x00]      ; CH0_CSR = 0  (also clears global EN[0] — they alias)
  bkpt #0
```

Design notes:

- **Why write CSR_EN inside the sled rather than let the `setup` table do it.** If we leave the enable in `setup`, DAP inter-write latency between enable and sled-start is unbounded. By moving the enable into the sled's first instruction, the EMU side also sees CSR_EN flip at a well-defined virtual cycle (the sled instruction executes under `emu.step()`, so PWM tick calls begin on the next cycle).
- **Why clear CSR_EN before BKPT.** Freezes the counter at a deterministic cycle on both silicon and EMU. Readback timing no longer affects CTR. Also: one physical bit for CSR_EN and EN (datasheet Table 1137) means `str 0, [r3, #0x00]` clears the global enable too — both the per-slice CSR_EN bit and the EN[0] bit drop atomically.
- **Sized for a precise, deterministic mask.** Pick N so the spin-loop's cycle count (1 × movs + 1 × str + loop + str + bkpt, plus movw/movt at 1 cyc each) yields an exact expected `CTR = (actual_sysclks_between_enable_and_disable) / 2`. Since both HW and EMU execute the same Thumb-16 encoding and both run the sled until BKPT, `actual_sysclks` measured by CYCCNT is the same on both sides, and the setup-before-enable and readback-after-disable windows no longer bleed into CTR. Small remaining bias is from the two `str` instructions themselves (typically 1 + buffered write cycle on AHB) — still bilaterally identical.
- Keep `max_sysclks` at 200 for the budget sanity upper-bound; the custom-sled path uses its own termination (PC reaches BKPT) and `actual_sysclks` is whatever DWT CYCCNT actually measures.

Add a **per-cycle** companion that mirrors the oracle runtime's `step_quantum=1` dispatch:

```rust
#[test]
fn fractional_div_integer_2_per_cycle_dispatch_matches_bulk() {
    let mut p = new_pwm();
    let mut irqs = 0u64;
    p.write32(SLICE_TOP, 0xFFFF, 0, &mut irqs);
    p.write32(SLICE_DIV, 0x0020, 0, &mut irqs);
    p.write32(SLICE_CSR, CSR_EN, 0, &mut irqs);
    p.write32(EN, 1, 0, &mut irqs);
    // Mirror the silicon oracle's step_quantum=1 dispatch: 152 calls
    // of tick(1, ...) — the CYCCNT-typical sled cost.
    for _ in 0..152 {
        p.tick(1, &default_tree(), &mut irqs);
    }
    assert_eq!(
        p.slices[0].ctr, 76,
        "152 sysclks / divisor 2.0 = 76 advances under per-cycle dispatch"
    );
    assert_eq!(p.slices[0].frac_accum, 0);
}
```

This test **passes on the current emulator** (no pre-fix FAIL mode). Its role is to *encode* the exact per-cycle behaviour so the formula and step-quantum=1 interaction cannot silently drift in the future.

## Section 6 — Blast radius + rollback

### 6.1 Scenarios potentially affected

- **`pwm_wrap_irq`** (file `silicon_scenarios.rs:934-941`, catalogue entry line 1190) — unchanged by this fix. Its observable is threshold-like (INTR bit-0 latched = 1) and tolerates setup-window drift. No change in behaviour.
- **PWM DREQ-enable warn-once plumbing** (`pwm.rs:180-203, 677-700`) — out of scope. Stays as is.
- **`hello_pwm` integration test** (file `crates/mdrp2350/tests/hello_pwm.rs`) — firmware-level PWM smoke. Unaffected; does not reach silicon.
- **`paced_bench_rp2350`**, other harness binaries — no PWM dependency.

### 6.2 Pico SDK usage

The SDK widely calls the PWM via `hardware/pwm.h` functions that ultimately write `CHn_CSR`, `CHn_DIV`, `CHn_TOP`, and `EN` in the order our scenario does. Any firmware that uses `pwm_set_enabled(slice, true)` is writing the one physical EN/CSR_EN bit — it would run correctly under our emulator because `PwmRegs::tick` ANDs `globally_enabled && locally_enabled`, and the SDK always ends up setting both views. No firmware behaviour change.

**The one real firmware-visible emulator-vs-silicon divergence** is the "two physical bits" model (§2 aside / §6.3). That's technical debt, not this residual's scope.

### 6.3 Remaining tech debt spotted during this residual

- `PwmRegs::en` and `slice.csr & CSR_EN` are independent storage in the emulator, whereas the datasheet defines them as one physical bit aliased two ways (Table 1137). Firmware that writes `EN[0]=1` without setting `CSR_EN` in the same write (or vice versa) behaves differently in the emulator vs silicon. Recommend a follow-up: unify them as a single storage (e.g. keep `self.en` as the source of truth, return its bit when reading `CHn_CSR[0]`). Not part of this residual's edit; suggest tracking in `tech_debt.md` if Arthur agrees.

### 6.4 Rollback

`git revert` on the single commit that lands the §3 changes restores the pre-fix scenario. No emulator rollback needed because no emulator code changes. The Stage A keeper fix (`5eac6a1`) is untouched.

## Appendix A — Math references

### A.1 Sled cycle accounting (approximate)

M33 Thumb-16 typical non-pipelined cycle counts:

| Opcode | Cycles |
|--------|--------|
| movs rX, #imm | 1 |
| str rX, [rY, #imm] | 1 (with 1-cyc buffered AHB write) |
| subs rX, #imm | 1 |
| bne short (taken) | 2 (pipeline flush) |
| bne short (not taken) | 1 |
| movw rX, #imm | 1 |
| movt rX, #imm | 1 |
| bkpt | 1 (halt) |

Default countdown sled at `max_sysclks=200`:
`1 (movw) + 49 × (1 subs + 2 bne-taken) + 1 subs + 1 bne-nt = 1 + 147 + 2 = 150 cyc`.

Custom sled from §3.1 (prefix + spin-N + suffix):
`2 (movw+movt r3) + 1 (movs) + 1 (str) + 2 (movw r1 ×1-2) + N × 3 cyc spin-loop body + 1 (movs) + 1 (str) + 1 (bkpt)`.

The spin count `N` is picked so that the total PWM-enabled window (str-to-str) divides cleanly by the divisor 32 and lands on a mid-range non-zero CTR, so both a formula bug and a setup-window drift would show up. Exact N encoded at implementation time.

### A.2 Masked-reading arithmetic

`76 & 0x64`: `0b0100_1100 & 0b0110_0100 = 0b0100_0100 = 0x44` — confirms §1.4.

`100 & 0x64`: `0b0110_0100 & 0b0110_0100 = 0b0110_0100 = 0x64` — confirms §1.5 (HW side reading 0x64 is consistent with, but not uniquely evidence of, a raw CTR of 100).
