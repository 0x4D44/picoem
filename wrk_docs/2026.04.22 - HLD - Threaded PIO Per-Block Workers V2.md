# HLD — Threaded PIO Per-Block Workers (V2)

**Date:** 2026-04-22
**Scope:** `mdrp2350` `ThreadedEmulator` only (Windows x86_64 threaded runtime).
**Goal:** Split the single PIO worker thread into three per-block workers
(PIO0, PIO1, PIO2) so the emulator stops serialising what the hardware
runs in parallel, and make the threaded path competitive with serial on
peripheral-heavy workloads.

**V2 changes vs V1:** §1 reframed to serial-baseline; §1.5 alternatives
enumerated and rejected; §2.1 pseudocode fixed (idle-block pad publish
unconditional, cross-block ordering justification corrected); §2.2 spells
out drain + reset + poisoning contract; §3 file list expanded; §4 test
plan specifies stress run, cross-block concurrent test, specific unit-test
names; §6 false-sharing padding moved from contingency to V2 design; §7
adds a pre-implementation measurement gate; §8 tightens success criteria.

## 1. Motivation

On `paced_bench_rp2350 --workload onerom` (OneROM-shape: PIO0 idle, PIO1
× 1 SM, PIO2 × 2 SMs) at commit `990f1a7`, 2026-04-21:

| Config | Throughput | Notes |
|---|---|---|
| Serial | **42.1 MHz** | Single host core, no barrier |
| Threaded (current, 4 workers) | **37.5 MHz** | Slower than serial |

Per-worker `--timing` on the threaded path (sq=256):

| Worker | work_mean | wait_mean | wait% |
|---|---|---|---|
| core0 | 1.1 μs | 4.5 μs | 80.6 % |
| core1 | ~0 | 5.6 μs | 99.4 % (halted) |
| **pio** | **4.9 μs** | 0.7 μs | 12.6 % |
| coord | 0.12 μs | 5.5 μs | 97.8 % |

**The threaded path is slower than serial on this shape**, because one
worker serialises all three PIO blocks while 3–5 other host cores idle.
The scope of this HLD is to fix that — make threaded compete with serial
on peripheral-heavy shapes, and do so with a topology that matches the
hardware (3 independent PIO blocks) for the sake of future workloads.
We are not optimising for OneROM alone; OneROM is the sharpest current
instance of a general pattern.

### 1.1 Expected throughput after split (honest math)

Per-SM `step_n` cost is ~4.9 ns/sysclk (post-2026-04-20 profiling).
For OneROM at sq=256 sysclk: PIO1 ≈ 1.3 μs, PIO2 ≈ 2.5 μs, PIO0 ≈ 0 μs.

Per-quantum wall clock after the split ≈
`max(core0, pio0, pio1, pio2) + coord + 2 × barrier_wait`
≈ `max(1.1, 0, 1.3, 2.5) + 0.12 + 2 × 0.5 μs`
≈ `2.5 + 0.12 + 1.0 ≈ 3.6 μs per quantum`

At 256 sysclk / 3.6 μs → **~71 MHz**. Bracketed:
- **Optimistic (~80 MHz, 2.13× threaded, 1.9× serial):** barrier
  contention stays close to today's 4-way numbers; V7 §5 phase overlap
  hides coord behind next-quantum worker work.
- **Conservative (~60 MHz, 1.6× threaded, 1.4× serial):** 6-way barrier
  adds 150–300 ns, false sharing on `pads`/`irq_flags` costs 50–100 ns,
  non-PIO workloads pay the barrier-arity tax for no gain.

Success target: **≥ 1.6× threaded (≥ 60 MHz on OneROM)**, with an
aspirational stretch of ≥ 1.8× if the pre-implementation barrier
microbench (§7) comes in below 600 ns 6-way mean.

## 1.5 Alternatives considered and rejected

Enumerated here because the devil's-advocate view during V1 review
surfaced several cheaper options. Each is real; none is the right fit
for this change. Summary first, reasoning follows.

| # | Alternative | Cost | Rejection reason |
|---|---|---|---|
| A | Keep serial — declare threaded "not for peripheral workloads" | 0 lines | Abandons threading's one-chip-per-host-core premise; future dual-core-compute workloads pay the serial tax |
| B | Fold PIO2 onto coord; keep 4 workers | ~20 lines | Asymmetric (PIO2 has 0-quantum pad lag vs PIO1's 1-quantum); OneROM-specific — any shape where PIO1 is hot re-opens the same problem |
| C | Keep single PIO worker but `par_iter` the blocks internally | ~30 lines | Rayon spawn/join per quantum = µs-scale overhead; we already pay the barrier once, paying rayon barriers 3× inside it is strictly worse |
| D | Amortise the quantum barrier across N quanta | ~50 lines | Breaks PLL-LOCK and master_cycle semantics (HLD V7 §3) — the Acquire/Release pair between coord's fetch_add and CPU PLL reads requires per-quantum synchronisation |
| E | Conditional split: use 1 PIO worker when ≤ 1 block active, 3 when more | ~80 lines + feature flag | Runtime topology switching adds state machine + test matrix explosion; not warranted until measurement proves static 3-worker is too expensive for single-block workloads |

**Chosen:** full per-block split (3 PIO workers, always on). Reasoning:

1. **Matches hardware topology.** Three PIO blocks are independent on
   silicon. The emulator should reflect that at the thread boundary so
   future workloads that exercise all three are free.
2. **Symmetric.** Every block gets the same treatment regardless of
   which one is currently "hot". Alternative B hard-codes PIO2-is-hot.
3. **Simpler than E.** One topology, no conditional paths, no feature
   flag. Idle-worker overhead measured in §6; if it ever matters for a
   single-block workload, E becomes a follow-up (not this HLD).
4. **Arithmetic is good enough.** §1.1's 1.6–2.1× band exceeds
   alternative B's predicted ≈1.8× by a slim margin, but per-block
   symmetry is worth the slim margin.

## 2. Design delta

Go from 4 workers (core0, core1, pio, coord) to 6 (core0, core1, pio0,
pio1, pio2, coord). Nearly all state on `super::ThreadedPio` is already
per-block indexed (`sm_enabled: [AtomicU8; 3]`, `irq_flags`, `dreq`,
`pads`, TX/RX SPSC queues). The three concrete shared-state changes:

- The command queue becomes per-block.
- Per-block atomics that three workers write concurrently
  (`pads[3]`, `irq_flags[3]`) are padded onto distinct cache lines.
- The `gpio_in` snapshot used by PIO workers is coord-published once
  per quantum into a dedicated atomic, consumed by all three PIO
  workers without skew.

### 2.1 Per-block PIO worker body

Replace `pio_worker_body(blocks: [PioBlock; 3], ...)` with
`pio_block_worker_body(block_idx: usize, block: PioBlock, ...)`. Each
worker owns one block. Loop body:

```rust
for _ in 0..n {
    for cmd in shared.pio.drain_commands(block_idx) {
        apply_pio_command(&mut block, &shared.pio, cmd);
    }

    // Coord publishes gpio_in_snapshot during its phase-2; all 3 PIO
    // workers load the same value for this quantum. One AtomicU32 load.
    let gpio_in = shared.gpio.read_in_snapshot();

    if shared.pio.read_sm_enabled(block_idx) != 0 {
        block.step_n(step_q, gpio_in);
        shared.pio.write_irq_flags(block_idx, block.pending_irqs() as u8);
    }

    // UNCONDITIONAL — even a disabled block must publish its current
    // pad latch so coord's update_gpio sees a coherent snapshot. Mirrors
    // current pio_worker_body emulator.rs:724-726.
    shared.pio.write_pads(block_idx, block.pad_out, block.pad_oe);

    barrier.wait();
}
```

Three correctness notes (added in V2 in response to review):

1. `write_pads` is unconditional regardless of enable mask. V1's
   pseudocode put it inside the enable gate, which would silently drop
   pad state for blocks that latched non-zero pads and then had all
   SMs disabled.
2. `gpio_in` is read from a coord-published snapshot atomic, not from
   the live `shared.gpio.gpio_in`. Coord writes the snapshot during its
   phase-2 (§2.3 below), so all three PIO workers observe the same value
   for quantum N. (They would anyway, given coord only writes once per
   quantum, but making the dedicated snapshot explicit eliminates a
   subtle cross-quantum race if coord ever grows a mid-phase write.)
3. The barrier-wait is the last action. No work happens between
   `barrier.wait()` return and the next iteration's `drain_commands`.

### 2.2 Per-block command queue

`ThreadedPio.commands: Mutex<Vec<PioCommand>>` becomes `[Mutex<Vec<PioCommand>>; PIO_BLOCKS]`.
- `send_command(cmd)` routes by `cmd.block()` into `commands[cmd.block()]`.
- `drain_commands(block_idx) -> Vec<PioCommand>` drains one queue,
  **preserving capacity** via the existing `mem::replace(&mut *guard, Vec::with_capacity(cap))`
  pattern at `pio.rs:246-250` — the `drain_preserves_capacity` test
  carries over unchanged, just specialised to `block_idx = 0`.
- `ThreadedPio::reset` loops over all three mutex-guarded queues and
  clears each; unit test confirms all three are empty post-reset.

Add a `PioCommand::block(&self) -> u8` inherent method (single match
over the four variants) for routing.

**Ordering contract (corrected from V1):** Today's single-queue
implementation preserves FIFO order of commands from a single CPU
thread across blocks — the Mutex plus Vec enforce strict insertion
order. With per-block queues, **intra-block** FIFO is preserved (each
queue is its own Mutex+Vec), but **cross-block** FIFO among the three
queues is not preserved at the point of drain. In practice this does
not matter because:

- The coordinator's single-barrier-per-quantum rendezvous at quantum N
  ensures all three workers have drained and applied every command
  that was posted before quantum N's start. Commands posted during
  quantum N land in queues that all three workers drain at the top of
  quantum N+1 — still ordered at quantum boundaries, which is the
  only granularity any current test or firmware observes.
- A grep across `crates/mdrp2350/src/threaded/**` and the harness
  confirms no test depends on cross-block command ordering within a
  single quantum. (§4 adds an explicit cross-block test to keep this
  property visible.)

### 2.3 `gpio_in` snapshot atomic

Add `AtomicU32 gpio_in_snapshot` to `AtomicGpio` (alongside the
existing `gpio_in`). Coord's phase-2 (after `update_gpio` merges SIO +
PIO pads) writes the final merged value into `gpio_in_snapshot` with
Release; PIO workers read it with Acquire in `read_in_snapshot()`. One
extra 4-byte atomic store per coord quantum — cost negligible. This
eliminates any hypothetical skew and makes the
"all-PIO-workers-see-same-gpio_in" contract explicit in the type.

### 2.4 False-sharing padding (upfront, not contingent)

Wrap each per-block atomic in a cache-line-aligned newtype:

```rust
#[repr(align(64))]
struct Aligned<T>(T);

// In ThreadedPio:
pads:       [Aligned<AtomicU64>; PIO_BLOCKS],
irq_flags:  [Aligned<AtomicU8>;  PIO_BLOCKS],
sm_enabled: [Aligned<AtomicU8>;  PIO_BLOCKS],
dreq:       [Aligned<AtomicU8>;  PIO_BLOCKS],
```

Memory cost: 4 fields × 3 blocks × 64 B ≈ 768 B of padding per
`ThreadedPio` instance. The three PIO workers write their own index
every quantum (pads and irq_flags unconditionally; sm_enabled on
control-write commands only). Without padding, every write bounces
the line between workers. With padding, each block's atomics live on
their own line, writes stay on the writer's core. This is textbook
false sharing — pre-committing to the padding avoids a measurable
regression at merge.

`ThreadedPio` accessors (`write_pads`, `read_pads`, etc.) are
transparently updated to dereference through the newtype. No change
to call sites.

### 2.5 Barrier

`SpinBarrier::new(4)` → `SpinBarrier::new(6)` in emulator.rs:406. The
primitive handles arbitrary party counts. Pre-implementation gate (§7)
confirms the cost.

### 2.6 `thread_mask`

`[usize; 4]` → `[usize; 6]`. Default `[0, 1, 2, 3, 4, 5]`. Mapping:
`[core0, core1, pio0, pio1, pio2, coord]`. `with_thread_mask` signature
updates. Minimum-host-cores assertion in `from_emulator` goes from
`>= 4` to `>= 6`. Existing 4-core `eprintln!` advisory removed.

SMT caveat: the dense default mapping assumes logical cores 0..5 are on
distinct physical cores. On SMT hosts where that doesn't hold, callers
pass an explicit `with_thread_mask([0, 2, 4, 6, 8, 10])` or similar.
Not a V2 scope item — the 20-core test host has SMT disabled at the
BIOS on the bench, and `paced_bench_rp2350` already allows an override.

### 2.7 Timing

`RunTimings.pio` (single `PerWorkerTimings`) → `.pio0`, `.pio1`, `.pio2`.
`RunTimings::summary()` return type `[WorkerSummary; 4]` → `[_; 6]`.
`WorkerName` enum adds `Pio0/Pio1/Pio2` (removing `Pio`), and the
`worker_name_labels_are_stable` test updates. The `run_timings_samples_reports_core0_count`
test constructs a literal `RunTimings { pio: ..., ... }` and moves to
the three pio fields.

### 2.8 Panic/poisoning reassembly

`run_quanta` today collects a single `[PioBlock; 3]` back from the PIO
worker on the Ok path. With three workers each owning one `PioBlock`,
the return-path reassembly is:

- Each worker returns `(PioBlock, PerWorkerTimings)` on Ok.
- On the happy path (all three workers Ok), reconstruct the
  `[PioBlock; 3]` array from the three individual returns.
- On any PIO worker panic, set `poisoned = true` and drop whatever
  blocks returned Ok. This matches the existing poisoning contract
  (the instance cannot be reused after any worker panics). The
  panicked-worker message enumerates the specific pio block:
  `panic in pio1` rather than the V1 generic `panic in pio`.

## 4. Test plan

1. **Unit tests `cargo test -p mdrp2350` pass.** The four renamed
   `ThreadedPio` tests (§3 row 1) and four new ones go with the per-block
   API; everything else should compile-and-pass unchanged.
2. **New per-block integration test.** Seed `ThreadedEmulator` with SMs
   enabled on PIO1 (1 SM) and PIO2 (1 SM), different INSTR_MEM each,
   run N quanta, assert `read_pads(1)` and `read_pads(2)` show the
   expected steady state independently. Catches cross-block
   mis-routing in commands or pad publishing.
3. **Cross-block command ordering smoke.** From core0, in one burst:
   `WriteCtrl{block:0}`, `WriteCtrl{block:1}`, `WriteCtrl{block:2}`,
   each enabling different SM counts. After one `run_quanta(1)`, assert
   all three blocks' enable masks reflect the command. Keeps the §2.2
   ordering contract visible in tests.
4. **Idle-block pad-publish semantics.** Enable SM on PIO1 for a few
   quanta so its pads latch to a non-zero state. Disable the SM
   (`WriteCtrl{block:1, val: 0}`). Run 10 more quanta. Assert
   `read_pads(1)` matches the latched value from before disable
   (blocks do not spontaneously zero pads when disabled) — mirrors
   hardware and current serial semantics.
5. **Panic-in-pio1 naming.** Fault-inject a panic from the pio1 worker
   (e.g. corrupt a command's `block` to a sentinel the worker asserts
   on). Join `run_quanta`, assert the panic message contains `pio1`
   specifically (not `pio`), and that `poisoned == true`.
6. **Stress run.** `paced_bench_rp2350 --threaded --workload onerom`
   with `debug_assertions=on` for ≥ 60 s (≥ 10⁸ quanta at the target
   throughput). No panics, no poisoned runs. Treat as gate before
   merge. Document wall time + quantum count in the journal.
7. **Throughput: OneROM win.** `paced_bench_rp2350 --threaded --workload
   onerom` with `--timing OFF` (see §8 for the criterion formula), ≥ 10
   runs, mean ≥ 1.6× baseline (baseline = commit `990f1a7` threaded
   OneROM MHz). Stretch target 1.8× if §7 microbench gates pass.
8. **Throughput: compute regression check.** `paced_bench_rp2350
   --threaded --workload contention` (the daily-driver), ≥ 10 runs.
   Mean within ±5 %, p99 within +8 % of baseline. If p99 regresses
   further, investigate before merging.
9. **Unaffected paths: serial + silicon oracles.** `cargo test -p mdpicoem-harness`
   and a smoke run of `silicon_periph_diff_rp2350` (if available locally)
   confirm the serial code path is byte-identical. Included here only
   to confirm no accidental fallout in shared PIO code.
10. **OneROM serving oracle smoke.** Serial-path only today
    (`onerom_serving_oracle_rp2350` does not use `ThreadedEmulator`).
    Run once to confirm it still passes post-change — it should, since
    the serial path is untouched.

## 5. Out of scope

- **RP2040 threaded path.** Separate chip, not threaded yet. Separate
  HLD when that lands.
- **PIO→NVIC IRQ routing.** Parity with today's single-threaded `Bus`,
  which also does not route PIO IRQs.
- **Real DMA modelling.** Emulator DMA is stubbed; `GlueDma` helper
  runs on the driver thread. **Consequence for this HLD:** in
  threaded mode PIO1 and PIO2 now step concurrently in the same
  quantum, whereas on silicon they are cycle-coupled through DMA. The
  pad-observable end state remains correct at quantum-boundary
  granularity (no current oracle tests sub-quantum timing on the
  threaded path), but this skew grows once real DMA lands — addressed
  there, not here.
- **RISC-V (Hazard3) threading.** `ThreadedEmulator::from_emulator`
  already panics on RISC-V cores; no change.
- **Per-SM split.** Splitting a single block across SM-level workers
  would require per-SM pad merging inside `PioBlock`; not supported
  today, not needed for OneROM (≤ 2 SMs per hot block).
- **Silicon oracle deltas.** Silicon oracles
  (`silicon_periph_diff_rp2350`, `silicon_cycle_oracle_rp2350`,
  `silicon_isr_diff_rp2350`, `silicon_dualcore_diff_rp2350`) run against
  the serial emulator. This change does not affect the serial path; no
  silicon-oracle delta expected.

## 6. Risks

- **6-way barrier cost.** `SpinBarrier` has `count`/`generation`
  atomics in one cache line — contention rises with party count.
  Hybrid spin+park avoids continuous invalidation for idle waiters.
  Mitigation: §7 measurement gate; if the 6-way mean exceeds 700 ns,
  either defer the split or investigate a hierarchical barrier
  (`[per-block-pair + global]`) before landing.
- **Non-PIO workload regression.** Compute-heavy workloads
  (`contention`, dual-core CPU-only benchmarks) gain nothing from PIO
  parallelism but still pay the barrier-arity cost and the false-sharing
  cost. §4 item 8 caps tolerance at ±5 % mean / +8 % p99; a regression
  outside that gates the merge.
- **Idle-worker publish cost.** PIO0 in OneROM is always idle. Its
  worker still runs `drain_commands(0)` (empty mutex lock, ~20 ns
  uncontended), `write_pads(0, 0, 0)`, and `barrier.wait()`. The
  cache-line padding (§2.4) isolates the pad store from the two active
  blocks; the mutex lock cost stays. Total ~50 ns per quantum for an
  always-idle block — acceptable.

## 7. Pre-implementation measurement gate

Before starting the implementation, extend `threading_micro.rs` (the
Phase 0c barrier microbench) to run at parties ∈ {2, 4, 6, 8} and
record mean / p50 / p99 round-trip. The V1 design rested on
"barrier scales fine to 6" as an assertion; gating on measurement
closes that gap cheaply (10 minutes of bench work, no code change to
the ThreadedEmulator).

**Gate criterion:** 6-way mean ≤ 700 ns round-trip under the current
hybrid spin-then-park implementation. If that holds, proceed to
implementation at §1.1's optimistic end (~80 MHz OneROM). If
600 < mean ≤ 700, proceed at the conservative end (~60 MHz target). If
mean > 700 ns, stop and reconsider: either increase `SPIN_BUDGET`,
move to a two-level barrier, or revisit whether the split is worth it
for this workload.

## 8. Success criteria (tightened)

All measurements against baseline commit **`990f1a7`** with the same
host (20-core, SMT disabled on bench), same sq=256, `--timing OFF`
during throughput comparison (timing instrumentation adds ~1 % overhead
per Phase 0c; throughput numbers must come from a timing-disabled run
to be comparable).

- All `cargo test -p mdrp2350` and `cargo test -p mdpicoem-harness`
  pass.
- **OneROM:** `paced_bench_rp2350 --threaded --workload onerom`, ≥ 10
  runs, reported as **mean ± stdev + p50 + p99**. Mean ≥ 1.6× baseline
  threaded mean. Stretch: ≥ 1.8× if §7 gate passes at optimistic end.
- **Compute regression:** `paced_bench_rp2350 --threaded --workload
  contention`, ≥ 10 runs. Mean within ±5 % baseline; p99 within +8 %
  baseline.
- **Timing-on attribution check:** one separate
  `--threaded --workload onerom --timing` run showing
  `max(pio0, pio1, pio2) + coord + 2 × barrier_wait_mean` matches
  measured wall-clock per-quantum throughput within ±15 %. Closes
  the critical-path-model-vs-reality loop; journal captures the
  reconciliation.
- **Stress:** §4 item 6 passes (60 s or 10⁸ quanta without panic or
  poison, `debug_assertions=on`).
- **No cross-block test surprises:** §4 items 2–5 all green.

If any of the above fails, do not merge; regroup in a journal entry
with the failing numbers.
