# PicoGUS Integration — Design

Version: 1.0.0
Date: 2026-04-14

## Purpose

Run real PicoGUS firmware inside `mdrp2040` end-to-end, driven by
DOSBox-X's MIDI output over a GUS-write trace, with the resulting I2S
stream captured to a WAV file. Validates our RP2040 + PIO stack on a
demanding real-world workload that exercises dual-core coordination,
PIO at both ISA and I2S bit rates, SPI PSRAM, and flash XIP — all in
a single integration binary.

### Why now

- `mdrp2040` is feature-complete for ARMv6-M + core RP2040 peripherals.
- The OneROM PIO differential work (in flight) is closing the last
  integration gap in the PIO engine — PicoGUS will stress the same
  code from a totally different angle.
- PicoGUS is open source (`github.com/polpo/picogus`), well-documented,
  and its firmware is exactly the class of workload this emulator is
  ultimately for: a real product built on the RP2040's unusual
  capabilities.

## Scope

**In scope (this HLD covers all six stages):**

1. XIP flash model for `mdrp2040` (firmware boot prerequisite).
2. External SPI PSRAM model (GUS sample RAM).
3. DOSBox-X GUS-write tap + trace format.
4. Trace replayer + GPIO injection in a new harness binary.
5. I2S output capture → WAV.
6. End-to-end MIDI demo using a known file.

**Deferred (future HLDs):**

- Real-time playback via `cpal`. Blocked on ongoing `mdrp2040` perf
  work. Offline-first is cleaner regardless: produces a diffable
  artefact.
- Live IPC bridge (DOSBox-X talking to our emulator in real time,
  routing reads). Needed to run DOS games whose control flow depends
  on GUS status reads. Not needed for static MIDI playback.
- Sample-for-sample oracle against DOSBox-X's internal GUS synth. Both
  sides emulate the same original hardware but differ subtly;
  qualitative match (spectrogram + ear) is the success bar here.
- CI integration. Local dev oracle only — requires DOSBox-X build +
  PicoGUS firmware.

## Architecture

```
    DOSBox-X (patched)
        │
        ├── internal GUS plays MIDI          ──► reference.wav
        │
        └── GUS port-write tap               ──► isa_writes.trace
                                                    │
                                                    ▼
                                             picogus_diff_rp2040  (single Rust binary)
                                             ┌──────────────────────────────────────┐
                                             │  trace replayer                      │
                                             │      │                               │
                                             │      ▼                               │
                                             │  mdrp2040 GPIO inputs                │
                                             │      │                               │
                                             │  ┌───┴──── PicoGUS firmware ──────┐  │
                                             │  │  Core 0: ISA decode            │  │
                                             │  │  Core 1: voice synth + mixer   │  │
                                             │  │  PIO 0: ISA interface          │  │
                                             │  │  PIO 1: I2S output             │  │
                                             │  │  PIO 2: SPI PSRAM              │  │
                                             │  └───┬──────────┬─────────────────┘  │
                                             │      │          │                    │
                                             │  psram model   i2s capture  ──► output.wav
                                             └──────────────────────────────────────┘
```

Single process. The trace file is the only cross-process artefact. The
replayer, emulator, PSRAM model, and I2S capture all live in one
harness binary.

## Stages

### Stage 1 — XIP flash in `mdrp2040`

Firmware boot prerequisite. Today `mdrp2040` has no onboard flash
(per `CLAUDE.md`); `load_image` drops straight into SRAM. PicoGUS is a
standard Pico SDK app: bootrom → boot2 in flash → main image in flash.

Changes:

- **`crates/mdpicoem-common/src/memory.rs`** — extend `Memory` to carry
  a flash buffer alongside ROM/SRAM. Add a `with_flash(rom, sram, flash)`
  constructor. Existing `with_sizes(rom, sram)` keeps working for users
  who don't need flash.
- **`crates/mdrp2040/src/memory.rs`** — wire the flash buffer through.
  Size: 2 MB (matches stock Pico flash).
- **`crates/mdrp2040/src/bus/`** — route reads in `0x10000000..0x10200000`
  (and its XIP aliases at `0x11000000`, `0x12000000`, `0x13000000`) to
  the flash buffer. Writes in that range are ignored (real flash
  requires erase-program via `XIP_SSI`; not needed for firmware
  execution).
- **`crates/mdrp2040/src/lib.rs`** — add `EmulatorBuilder::flash(bytes)`
  and `Emulator::load_flash(bytes)`. Accepts raw `.bin` at flash offset
  0. UF2 parsing stays in the harness/app layer.
- **No XIP cache, no fetch-timing model.** Flash reads are single-cycle
  for now. PicoGUS's cycle-sensitive ISA response code runs from SRAM
  (copied by boot2 at startup), so XIP fetch timing isn't what this
  integration tests.

**Acceptance:** `cargo run -p mdrp2040app -- --flash roms/rp2040/blinky.bin`
boots a flash-linked blinky. GPIO25 toggles. Existing `--image` path
continues to work for SRAM-only firmware.

### Stage 2 — External SPI PSRAM model

PicoGUS v2 hardware carries an 8 MB SPI PSRAM for GUS sample storage,
accessed via a PIO-driven SPI interface on dedicated GPIOs. Firmware
writes samples there when DOS loads patches; reads them per-voice
during synthesis.

Changes:

- **`crates/mdrp2040/src/peripherals/` (new directory), `psram.rs`** —
  byte-addressable 8 MB buffer + SPI protocol state machine. Pins:
  CS, SCK, SIO[3:0] (QSPI-capable). Decodes the minimal command set
  PicoGUS actually uses: `0x02` page program, `0x0B` fast read,
  `0x38` enter QPI, `0x66`/`0x99` reset. Tracks CS transitions as
  frame boundaries.
- **`crates/mdrp2040/src/bus/`** — hook the PSRAM device into the
  GPIO pin layer. PIO output on PSRAM pins clocks bits into the
  device; the device drives bits back on the input side.
- Pin assignment hardcoded to match PicoGUS v2 — this is not a
  generic PSRAM peripheral. No env var, no feature flag.

**Scoping note:** the firmware source is open; before coding, read
`picogus/firmware/src/psram.c` (or equivalent) and implement exactly
the command subset it uses. Do not pre-emptively implement the full
APS6404L datasheet.

**Acceptance:** unit test in `psram.rs` — drive a known byte pattern
out via a scripted PIO program, read it back via another PIO program,
expect a match. No PicoGUS firmware involvement at this stage.

### Stage 3 — DOSBox-X tap + trace format

Patch DOSBox-X to log every GUS port I/O with a timestamp. Produces a
plain-text trace file.

**Trace format** (CSV, one line per event, first line is a header):

```
# picogus-tap v1
ns,port,value,kind
0,0x243,0x00,write8
1234567,0x240,0xff,write8
1234890,0x246,0x20,write16
```

`kind` is one of `write8 | write16 | read8 | read16`. Reads are logged
for diagnostics but the replayer ignores them (see "Risks" below).
Text CSV over binary: one-line `fprintf` in the DOSBox-X patch,
trivially greppable, no encoding bugs. A 10-second MIDI produces
~100K records ≈ 3 MB — fine.

**Patch:** hook `GUS_WriteHandler` / `GUS_ReadHandler` in DOSBox-X's
`src/hardware/gus.cpp`. Single-file diff. Vendored as
`third_party/dosbox-x-picogus-tap.patch`. Building the tapped DOSBox-X
is a documented one-off; not part of `cargo build`.

**Acceptance:** running DOSBox-X with a fixed MIDI for 10 s produces
a trace file whose record count and timespan look sane (spot check).

### Stage 4 — Trace replayer + ISA injection

New binary: **`crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs`**.

Loop:

1. Read the next event from the trace.
2. Step the emulator until its cycle counter ≥ the event's target
   cycle (`event_ns * system_clock_hz / 1_000_000_000`).
3. Poke GPIOs to drive a synthetic ISA bus cycle — idealised square
   waveform: assert address + IOW#, hold for ~300 ns of emulated
   time, deassert, idle.
4. Repeat until trace exhausted.

No separate "ISA bus model." The emulator's existing GPIO state is
what PicoGUS's PIO program samples; generating plausible pin waveforms
is enough — we're not re-implementing the ISA bus, we're driving the
pins the firmware expects to see.

CLI:

```
picogus_diff_rp2040 \
    --flash third_party/picogus/picogus-vX.Y.Z.bin \
    --trace traces/doom_e1m1.trace \
    --out  output.wav \
    --duration 10s
```

**Acceptance:** replay the full 10 s trace through the emulator with
firmware booted; firmware's ISA handler stays live (no hangs, no bus
fault, spinlock contention counts sane on a debug dump).

### Stage 5 — I2S capture → WAV

Watch the PIO 1 I2S output pins (BCLK, LRCLK, DOUT). Decode the stream
to stereo PCM frames. Write a WAV file.

- **`crates/mdpicoem-harness/src/i2s_capture.rs`** (new module in the
  harness crate) — I2S decoder: consumes timestamped pin-state samples
  from the emulator's GPIO bus, emits 16-bit stereo frames. Handles
  standard I2S framing (LRCLK edge selects channel, data MSB-first,
  one-cycle delay after the frame edge).
- Output written to the path given via `--out`; default
  `crates/mdpicoem-harness/oracles/picogus_<trace_stem>.wav`.

**Acceptance:** unit test in `i2s_capture.rs` — drive a scripted pin
waveform encoding a known sine burst, run through the decoder, expect
reconstructed PCM to round-trip.

### Stage 6 — End-to-end MIDI demo

**Target MIDI:** a CC-licensed GUS demo MIDI, or a public-domain MIDI
from a game known to drive the GUS reliably. Licensing check required
before committing the file under `traces/` — see Open Questions. The
demo value depends on the MIDI being recognisable; "Canon in D" works
as a fallback if no game MIDI clears.

Flow:

1. Run patched DOSBox-X with the target MIDI. Collect:
   - `reference.wav` (DOSBox-X's audio output).
   - `isa_writes.trace` (GUS port-write tap).
2. Run `picogus_diff_rp2040` → `output.wav`.
3. Compare `output.wav` and `reference.wav` by ear + spectrogram.
   Success = recognisably the same music.

**Acceptance:** subjective ear-test match on a 10-second opening
segment. Spectrograms side-by-side should show the same dominant
frequency bands at the same times, modulo phase and mixing detail.

**Stage 6 delivery status (2026-04-14):** the Rust-side pipeline is
complete and exits cleanly under the demo script. What lands with
this HLD stage is the runbook (`third_party/picogus-demo-runbook.md`),
the demo driver (`scripts/picogus_demo.sh`), the pinned PicoGUS
v4.0.0 firmware metadata (`third_party/picogus/VERSION` +
`README.md`, with the firmware itself fetched on demand by the
script), and a smoke-tested end-to-end plumbing pass against the
existing CSV fixture. **The subjective ear-test acceptance is
external** — it requires Arthur to build patched DOSBox-X (Stage 3
patch is in place), run it against
`doom2_map01_running_from_evil.mid` to capture both the ISA trace
and reference WAV, and then compare. A secondary blocker discovered
during Stage 6 smoke: our `mdrp2040` ships a synthetic 8-byte
bootrom stub that cannot run a real Pico SDK firmware past boot2;
until the real RP2040 bootrom is vendored (tracked as Phase 8 in
`tech_debt.md`), `picogus_diff_rp2040 --flash picogus-v4.0.0.bin`
will stall immediately and produce a 44-byte empty WAV. The demo
driver and runbook call this out explicitly so Arthur isn't surprised.

## What does NOT change

- `mdpicoem-common::Memory` gains an optional flash field, but the
  existing `with_sizes(rom, sram)` constructor still works — no
  breaking change to `mdrp2350` callers.
- `mdrp2350` is unaffected. PicoGUS is RP2040-only.
- `qemu_diff_m0plus`, existing unit tests, and app binaries keep
  working. This work adds new code paths; it does not rewrite existing
  ones.
- No env vars. No feature flags. No conditional compilation. All
  configuration is CLI args on the harness binary or hardcoded
  constants for pin mapping (PicoGUS v2 hardware is fixed).
- The PSRAM and I2S models are not peripherals in the general-purpose
  sense — they are PicoGUS-specific integrations that live with the
  harness + `mdrp2040`. No abstraction layer is introduced for
  "arbitrary external devices." If a second demo ever needs a
  different external device, we extract a trait then; not before.

## Risks

**DOS program control flow depends on GUS reads.**
Our replayer feeds writes only. If the DOS MIDI player branches on
reads of GUS voice-status registers, the trace diverges from what the
program would actually do when driven live. Most stock MIDI players
do minimal status polling (set up voices, fire them, sleep on a
timer). Mitigation: pick a MIDI from a game with a well-behaved GUS
driver. If a chosen MIDI fails to replay, try another before reaching
for the live-bridge design. Live bridge is deferred, not ruled out.

**DOSBox-X GUS is not PicoGUS firmware.**
Both emulate the same original hardware, both differ from it subtly.
Mitigation: the success criterion is qualitative match, not
sample-for-sample. A sample-accurate oracle is a much larger problem
(we'd need real PicoGUS hardware for that, which we don't have).

**PSRAM protocol mismatch.**
PicoGUS uses a specific APS6404L command subset. Modelling the wrong
subset → firmware hangs or reads back garbage samples. Mitigation:
read firmware source before implementing; implement exactly the
subset it uses; add a unit test with captured PSRAM traffic before
integrating with firmware.

**Performance.**
A 10 s MIDI at 125 MHz emulated is ~1.25 billion cycles. At current
`paced_bench_rp2040` throughput (~80 MHz after the PIO Idle Skip
work lands), that's ~15 s of wall-clock per 10 s of audio. Fine for
an offline demo. If slower than 4× real-time, budget for a shorter
capture window rather than optimise.

**Firmware version drift.**
PicoGUS is actively developed. Mitigation: pin a specific release
(`third_party/picogus/picogus-vX.Y.Z.bin`, vendored), record the
release tag in a README, treat firmware upgrade as an explicit
revalidation task.

## Success criteria

End-of-work definition:

1. `cargo test -p mdrp2040 -p mdpicoem-common -p mdpicoem-harness`
   green, including the new flash, PSRAM, and I2S decoder tests.
2. `cargo run -p mdpicoem-harness --release --bin picogus_diff_rp2040
    -- --flash <firmware> --trace <midi>.trace --out output.wav`
    produces a non-silent WAV on the committed demo trace.
3. Listening to `output.wav` and DOSBox-X's `reference.wav`
   side-by-side: same music, recognisably.
4. Existing oracles unregressed: `qemu_diff_m0plus --fuzz 1000`
   clean, `paced_bench_rp2040` within 5% of pre-change baseline.

## Open questions

- **Demo MIDI licensing.** Which file? Options: a public-domain
  classical MIDI (safe, boring), a CC-licensed demoscene MIDI (good
  showcase, need to verify licence), a game MIDI (best recognition,
  licensing risk). Arthur to pick before Stage 6.
- **PSRAM mode.** Does PicoGUS firmware run the PSRAM in serial SPI
  or QPI? Answer is in the firmware source; determines how much of
  the QPI command set we need to model. Read before Stage 2.
- **Trace timestamps.** Wall-clock ns from DOSBox-X is simple but
  couples the replay to the exact MIDI tempo at capture time. An
  alternative is "cycles since DOS boot" which is deterministic in
  DOSBox-X's simulated time. Stick with ns unless it bites us.
- **Multi-MIDI regression.** Out of scope for this HLD — one demo is
  enough. Worth revisiting once Stage 6 works: if the pipeline is
  solid, a regression corpus of 3–5 MIDIs becomes cheap and catches
  firmware upgrade breakage.
