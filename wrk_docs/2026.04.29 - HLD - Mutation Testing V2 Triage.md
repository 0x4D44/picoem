## 2. Methodology

### Runner

`scripts/v2_mutation_runner.py` (~250 LOC). Per-mutant pipeline:
1. Look up mutant by name in `mutation/v2/mutants_catalog.json`
   (full catalog from `cargo mutants --list --json --diff`).
2. Compute byte offsets `[start_col-1, end_col-1)` from the JSON span;
   splice the source file with `replacement` from the JSON.
3. `cargo build --release -p mdpicoem-harness --bin <oracle>` with
   per-worker `--config` overrides (LTO off + `codegen-units=16` on
   chip libs and workspace) so steady-state rebuild is ~20 s vs the
   default profile's ~60 s.
4. Run the oracle with `--fuzz 100` plus per-oracle CLI quirks
   (`qemu_diff_m33 --classes base`, `softfloat_diff --mode all`).
5. Revert the source file (always; `try`/`finally`).
6. Append a JSON record to `mutation/v2/results.jsonl`.

### Parallelism

`scripts/v2_mutation_run_parallel.sh` (~150 LOC). Sharding is
**oracle-grouped**, not round-robin, because two `qemu_diff_m33`
workers would race on GDB port 3333 (`QemuProfile` hardcodes ports):
- W0: M33 oracle (mdrp2350/decode.rs + execute.rs + execute_thumb32.rs,
  447 mutants, port 3333).
- W1: M0+ oracle (all mdrp2040 files, 182 mutants, port 3334).
- W2: softfloat (mdrp2350/execute_fpu.rs, 166 mutants, no port).

Each worker runs in its own `git worktree` under `/tmp/v2_workspaces/wN`
with an isolated `target/`. After completion,
`v2_mutation_run_parallel.sh merge` concatenates and de-dups the
per-worker `results.<i>.jsonl` into the canonical
`mutation/v2/results.jsonl`.

### Oracle routing

| File                                 | Oracle             | CLI flags          |
|---                                   |---                 |---                 |
| `mdrp2350/core/execute_thumb32.rs`   | `qemu_diff_m33`    | `--classes base`   |
| `mdrp2350/core/execute_fpu.rs`       | `softfloat_diff`   | `--mode all`       |
| `mdrp2350/core/execute.rs`           | `qemu_diff_m33`    | `--classes base`   |
| `mdrp2350/core/decode.rs`            | `qemu_diff_m33`    | `--classes base`   |
| `mdrp2040/core/execute.rs`           | `qemu_diff_m0plus` | (none)             |
| `mdrp2040/core/execute_wide.rs`      | `qemu_diff_m0plus` | (none)             |
| `mdrp2040/core/decode.rs`            | `qemu_diff_m0plus` | (none)             |

### Known limitations baked into the V2.0 numbers

1. **`qemu_diff_m33 --classes fpu` is broken on QEMU 8.2/mps2-an505
   in this env** (FPU cases all return EAGAIN on the GDB pipe and
   never terminate). Pinned `--classes base` for V2.0. Encoding
   helpers in `execute_fpu.rs` (`vfp_sd`, `vfp_sn`, `vfp_sm`,
   `fpscr_set_nzcv`) are only observable when actual VFP instructions
   run — they appear `oracle_survived` even when the mutation is
   semantically meaningful (see §3.5).
2. **`--fuzz 100` first-pass** may statistically miss rarely-
   triggered paths. The deep-pass at `--fuzz 2000` (recommended; not
   yet run for V2.0) confirms first-pass survivors.
3. **Two cargo-mutants baseline-blocking residue tests** were skipped
   via `-- --skip <name>` (`bfc_full_width_clears_word`,
   `coresight_trace_halfword_read_dispatches_through_byte_path`).
   Mutants only catchable by those tests appear `missed` in the
   V2 sweep but are unrelated to the V2 oracle replay outcome
   (the runner runs oracles, not unit tests).

## 3. Per-file analysis

### 3.1 `mdrp2040/core/decode.rs` — 79 survived / 79 total — Bucket 4 dead-code cluster

Function breakdown:

| Survived | Function                  |
|---:      |---                        |
|   37     | `classify_thumb32_pure`   |
|   25     | `classify_thumb16_pure`   |
|   13     | `classify_thumb16_misc_pure` |
|    3     | `classify_is_pure`        |
|    1     | `CortexM0Plus::decode_execute` |

V1 reported 0 survivors here (110 mutants on the V1 codebase; classifier
hadn't been added yet). V2 reports **all 79 missed mutants survive
the M0+ oracle**.

Cause: the classifier writes `FLAG_PURE` into `DecodedOp.flags` at
`crates/mdrp2040/src/core/decode.rs:234`, the `is_pure()` accessor reads
it at `crates/mdrp2040/src/bus/mod.rs:264`, but **no production code on
mdrp2040 calls `.is_pure()`**. (Production grep:
`grep -rnE "\.is_pure|is_pure\(\)" crates/mdrp2040/` returns zero call
sites — the deferred fast-path consumer hasn't shipped yet, per commit
`42ee533` "is_pure fast-path... deferred for a follow-up iteration".)

The mutations are **Bucket 4 by current observability**. They become
Bucket 3 when the deferred consumer lands (it reads `is_pure()` to
skip Bus side-effects on pure decodes; wrong classification will
diverge the QEMU end-state diff).

**Recommended actions (V3)**:
1. Add direct unit tests for the classifier functions, mirroring the
   mdrp2350 test pattern in `crates/mdrp2350/src/tests.rs`. The
   classifiers are pure functions of opcode bits — exhaustive
   enumeration is feasible (16-bit Thumb-16 = 65 k cases, trivial).
2. OR `#[cfg(feature = "fast_path")]`-gate the classifier until the
   consumer lands, so the default build doesn't carry observability
   gaps.
3. OR `#[mutants::skip]` annotations as a low-cost noise reducer.

### 3.2 `mdrp2040/core/execute_wide.rs` — 24 survived / 24 total — small-corpus oracle gap

Function breakdown:

| Survived | Function                      |
|---:      |---                            |
|   9      | `CortexM0Plus::thumb32_msr`   |
|   9      | `CortexM0Plus::thumb32_mrs`   |
|   5      | `CortexM0Plus::thumb32_bl`    |
|   1      | `CortexM0Plus::thumb32_misc_control` |

V1 reported 21 survivors here (23 in V2); same shape. Today's
`9c9ea6e` "harness: relax qemu_diff_m0plus filter for M0+ Thumb-32
subset" admitted Thumb-32 cases through the oracle's `is_m0plus_safe`
filter — but only 10 cases (BL + MRS/MSR for PRIMASK/CONTROL +
DSB/DMB/ISB), out of a 410-case total corpus. With `--fuzz 100`,
each mutant gets ~100 random tests against this 10-case Thumb-32
subset; mutations on rarely-fuzzed bit-fields can statistically slip
through.

**The MSR/MRS mutants on register-IDs that aren't PRIMASK/CONTROL
(8/9/14/20) are Bucket 4** — those encodings are filtered out by
`is_m0plus_safe` precisely because the M0+ ISA reserves them, so the
oracle never exercises them. V1 triage HLD §3.6 anticipated this.

**The 5 BL survivors are likely first-pass statistical misses** —
BL has only one M0+ encoding, so any wrong bit-field assembly should
be caught by ANY BL test, but the mutation may be on a rarely-
exercised bit (e.g. `S` bit in the second halfword). Deep-pass at
`--fuzz 2000` should drop these to oracle_caught.

**Recommended actions (V3)**:
- Run V2 deep-pass on the BL cluster to confirm.
- For MSR/MRS: extend `qemu_diff_m0plus`'s special-register table
  generator to cover all 5 ARMv6-M-architectural register IDs (16
  PRIMASK, 17 BASEPRI rejected, 19 FAULTMASK rejected, 20 CONTROL,
  10 SP) so the oracle exercises the full match space, OR
  `#[mutants::skip]` the unreachable IDs.

### 3.3 `mdrp2350/core/decode.rs` — 51 survived / 58 total

Function breakdown:

| Survived | Function                       |
|---:      |---                             |
|  12      | `CortexM33::decode_execute`    |
|  11      | `classify_thumb16_misc_pure`   |
|  10      | `classify_thumb16_pure`        |
|   8      | `classify_thumb32_pure`        |
|   5      | `is_thumb16_flag_only`         |
|   3      | `CortexM33::populate_decode_cache` |
|   2      | `classify_thumb32_branch_misc_pure` |

Mixed cluster:
- **decode_execute (12)** — match-arm deletions on the dispatch
  table. Mutants like "delete match arm 0b1111" survive because
  fuzz=100 may not generate the encoding the deleted arm matches
  (unreachable in the corpus distribution). Deep-pass at fuzz=2000
  should catch most. Some genuine Bucket 4 (duplicate encoding paths
  routed elsewhere).
- **classifier functions (29)** — same shape as mdrp2040 §3.1, but
  mdrp2350's classifier *is* used in production (consumer at
  `mdrp2350/src/core/decode.rs:284`), AND has unit-test coverage in
  `mdrp2350/src/tests.rs`. So why are these surviving? Hypothesis:
  the unit tests assert specific encodings, but the survivors mutate
  bit-shift and bit-mask helpers that map specific encodings to
  same outputs as the original (Bucket 4 for the actual call set).
  Worth deep-passing to confirm.
- **is_thumb16_flag_only (5)** — pure inline classifier, similar
  shape to the others.

V1 triage HLD §3.5 estimated ~50 Bucket 3 / ~8 Bucket 4 here. V2's
51 survivors haven't been individually classified yet — deep-pass
plus unit-test gap analysis is V3's job.

|   3      | `vfp_expand_imm_f32`              |

|  ≤2 each | other (vfp_sd, vfp_sm, vfp_sn, fpu_minnum, fpu_maxnum, …) |

Big surprise: V1 triage HLD §3.2 explicitly verified that
`softfloat_diff` covers `f32_to_f16_bits`, `f16_bits_to_f32`,
`fp_add/sub/div/fma/mul`, `fpu_unary` via the `HalfDir`/`run_vcvt_half`
path plus the IEEE-754 helpers. V2 measurement says 30 + 7 + 7 + 5 +
6 + 4 + 7 + 11 = 77 of those "covered" mutations *survive* at
fuzz=100. Three explanations are plausible, in increasing severity:

1. **First-pass statistical miss**: `softfloat_diff` only generates
   ~6800 fuzz cases per run; rare IEEE-754 corner-cases (specific
   subnormal patterns, signaling-NaN payloads, rounding-mode-specific
   tininess detection) might land outside the fuzz distribution at
   fuzz=100. Deep-pass at fuzz=2000 would multiply attempts ×20.
2. **Equivalent-mutant drift**: V1's heuristic placed many of these
   in Bucket 3 "would be caught"; the V2 measurement says they
   survive because the mutations are equivalent under the actual
   IEEE-754 helper inputs softfloat_diff generates (a Bucket 4
   reclassification).
3. **Real coverage gap**: softfloat_diff's edge-case tables don't
   exhaustively cover the architectural surface, and rare paths
   (e.g. specific RMode × subnormal × FTZ combinations) aren't
   exercised. Bucket 2.

Distinguishing 1 from 2/3 needs deep-pass. Distinguishing 2 from 3
needs hand-inspection of each survivor against the softfloat_diff
test plan. Both are V3 tasks.

The vfp_sd/sn/sm/fpscr_set_nzcv encoding helpers (≤2 each, ~10
total) are confirmed Bucket 4 by current oracle routing —
softfloat_diff doesn't run actual VFP instructions, so encoding
mutations don't observably propagate.

## 4. Cross-cutting findings

1. **V1 hypothesis was too optimistic by ~50 percentage points.**
   V1 said 87 % Bucket 3; V2 measures 37 % oracle-caught. **The
   divergence is real, not a tooling artefact** — but most of the
   gap is in three categories that V1 framing didn't separate:
   - **Pre-staged dead code**: 79 mdrp2040 classifier mutants (the
     consumer is deferred per commit `42ee533`).
   - **Oracle routing gap**: the encoding-helper subset of
     execute_fpu.rs (~10 mutants) is observable only via
     `qemu_diff_m33 --classes fpu` (broken on QEMU 8.2 in this env).
   - **First-pass statistical**: many survivors at `--fuzz 100`
     would likely be caught at `--fuzz 2000` deep-pass, especially
     the match-arm-deletion patterns on dispatch tables.

   Subtracting 79 + 10 = 89 known Bucket-4 from the 506 survivors
   gives 417 "needs deep-pass". If deep-pass catches even half (per
   the statistical-miss hypothesis), V2.1's adjusted bucket
   distribution becomes much closer to V1's heuristic.

2. **V1 verifications of "harness corpus already covers this" don't
   always survive contact with measurement**. V1 triage HLD §3.1
   declared the SIMD parallel-add/sub cluster oracle-covered after
   reading `thumb32_gen.rs:6435-6482`; V2 measurement says 19 of
   those mutations slip through `--fuzz 100`. V1 §3.2 made the same
   call for FP16 conversion via softfloat_diff; V2 says 37 of those
   slip through. **This was V1 triage HLD §8's exact concern**:
   "V2's deliverable should be exactly that: the runner, plus a
   triage-style follow-up document categorising the survivor list
   one more time, this time with per-mutant oracle-catch ground
   truth instead of cell-level inference." Confirmed.

3. **Match-arm deletes are systematically under-tested at low fuzz
   budgets.** The dispatch-table mutants (delete match arm 0b...)
   only fail when the deleted encoding actually gets dispatched.
   `--fuzz 100` × ~168 ALU classes for M33 = ~16,800 tests; for a
   specific 5-bit op-field encoding with uniform fuzz distribution,
   that's ~525 hits per encoding — should be plenty. So if a
   match-arm-delete survives, either:
   - The corpus generator doesn't hit that encoding (real Bucket 4
     reachability gap), or
   - The dispatched fallback handler returns the same observable
     result on the test inputs (semantic Bucket 4).
   Hand-inspection is the only definitive resolver.

4. **The oracle-routed differential model is correct in shape, but
   has gaps where the same source file has multiple observability
   contracts.** `execute_fpu.rs` mixes IEEE-754 helpers
   (softfloat-observable) with VFP-instruction encoding helpers
   (only QEMU-instr-observable). Routing the whole file to one
   oracle is a coarse approximation. V3 should consider per-function
   oracle routing in the runner (a function → oracle map, populated
   from inspection of the file's API surface).

## 5. Bucket distribution — measured (post deep-pass)

This is the V2.1 bucket distribution. It supersedes both V1 triage HLD
§2 and V2.0 §5.

| Bucket | Description                              | V1 est. | V2.1 measured |
|---:    |---                                       |---:     |---:           |
| 3      | Caught by oracle, missed by unit tests   | ~617    | **331**       |
| 4      | Equivalent / unreachable / dead-code     | ~85     | **~370** (79 mdrp2040 dead-code + ~30 encoding helpers + ~260 deep-pass-persistent) |
| 2      | Real oracle gap                          | ~5      | **~50** (estimate; subset of the 51 mdrp2350/decode.rs classifier survivors and 24 M0+ Thumb-32 wide-encoding survivors that hand-inspection would re-classify here) |
| 1      | Real test gap                            | ~0      | **~50** (estimate; the residual after subtracting 4 + 2 candidates) |
| **Total** |                                       | **707** | **801**       |

The Bucket 4 number jumps from V1's 85 estimate to ~370 because:
- 79 mdrp2040 classifier mutants are pre-staged dead code in *the
  current source state* (not in V1's source).
- ~10 vfp encoding helpers depend on `qemu_diff_m33 --classes fpu`
  which is broken on QEMU 8.2 in this env (see §3.6 / §1 limitations).
- ~260 deep-pass-persistent survivors at fuzz=500/2000 are strong
  Bucket 4 candidates by call-site equivalence — they breach the
  source semantically but the production-observable end state is
  unchanged. Pattern dominant: `| → ^` on disjoint bit-fields,
  `match arm delete` on never-reached encodings, equivalent-output
  IEEE-754 corner cases.

Bucket 1 + Bucket 2 are still hypothesis until each non-dead-code
survivor is hand-inspected. Methodologically, V2.1 narrowed the
"needs human triage" set from 506 down to ~75 candidates (~10 %)
— that's the productive deliverable. **V3's job** is to convert
those ~75 hypotheses into measured Bucket 1 vs Bucket 2 splits and
file the corresponding test gaps and oracle gaps.

V1's qualitative thrust ("residual survivors are dominated by
oracle gap, not test gap") still holds — once dead-code and
encoding-helper artefacts are subtracted, the remaining survivors
are mostly call-site-equivalent Bucket 4, with a small Bucket 2
tail and an even smaller Bucket 1 tail.

## 6. Proposed actions

Numbered for reference. Sized as half-day to one-day units unless noted.

1. **Deep-pass the 506 first-pass survivors at `--fuzz 2000`**.
   Sized: ~5 h wall-clock with 3-way parallel (M33 worker bottleneck:
   245 survivors × 70 s ≈ 4.8 h; M0+ 139 × 60 s ≈ 2.3 h; softfloat
   122 × 5 s ≈ 10 min). Single-line invocation:
   `./scripts/v2_mutation_run.sh deep-pass`. Sequential; would need
   the parallel launcher extended to support `--retry-survivors` mode.
   **Highest-value V2.1 action** — converts the 417 "first-pass
   statistical miss" candidates into measured Bucket 3 vs. Bucket 4.

2. **Add direct unit tests for the mdrp2040 decode classifier** to
   close the §3.1 cluster. The functions are pure; exhaustive
   enumeration of 16-bit Thumb-16 + the mdrp2040 Thumb-32 prefix
   subset is ≤ 100 k cases, under 1 s of test time. ~half-day.

| Pattern                     | Count |
|---                          |---:   |

the test inputs hit edge cases where modulo or division yields the

high-bits set), OR softfloat_diff's IEEE-754 corpus doesn't generate
the operands that would expose the divergence. Worth direct

### 10.4 Why Action 4 closes without `#[mutants::skip]`

The action plan tentatively listed three skip targets; on closer
reading, none is the right call:

1. **vfp_sd / vfp_sn / vfp_sm / fpscr_set_nzcv / vfp_expand_imm_f32**.
   Some mutations are structurally equivalent (disjoint bit-fields),
   but other mutations on the same functions ARE non-equivalent
   (e.g. `>> with <<`, `& with |` would extract different bits) and
   ARE observable through `qemu_diff_m33 --classes fpu`. The
   per-function routing already routes them to FPU class with
   `requires: "fpu_class"`, which classifies as `oracle_unavailable`
   under V3's runner. Adding `#[mutants::skip]` would silence the
   signal that the QEMU env fix is owed and would lose specificity
   on the non-equivalent mutations.
2. **mdrp2040 + mdrp2350 classifier helpers (post Stream A)**. After
   Stream A's exhaustive unit tests, every non-equivalent mutation
   is caught. Remaining MISSED mutants are structurally equivalent
   by default-arm fall-through. Skipping silences true negatives.
3. **MSR/MRS unreachable register IDs in `execute_wide.rs`**. Same
   argument as (1) — the per-function routing handles oracle
   visibility; whole-function skips lose specificity.

**The right closure for Action 4 is the combination of per-function
routing (already in place) plus the QEMU FPU class env fix
(Action 3, deferred — env problem not code).** Once both are in
place, the residual `oracle_survived` set is structurally bounded by
cargo-mutants methodology limitations only.
