## 1. What V2 is

V1 produced a survivor list of 707 mutants and classified them into four
buckets via *heuristic* per-(file, function, pattern) inspection. The V1
HLD §8 + V1 triage HLD §8 explicitly flagged that this was hypothesis,
not measurement: ~87 % were *plausibly* Bucket 3 (caught by oracle, not
by unit tests). Two clusters (SIMD parallel-add/sub and FP16 conversion)
were initially flagged as Bucket 2 (real oracle gap) and then verified
on inspection of `thumb32_gen.rs` / `softfloat_diff.rs` to actually be
Bucket 3 — the surfaces *are* oracle-covered, the survivors *would* be
oracle-caught, `cargo-mutants` just doesn't run the oracles.

**V2 converts heuristic to measurement.** For each missed mutant we apply
its patch, run the matching differential oracle (qemu_diff_m33 /
qemu_diff_m0plus / softfloat_diff) for a bounded fuzz window, and record
whether the oracle catches it. The output is a per-mutant ground truth:

- `oracle_caught` ⇒ Bucket 3 confirmed (oracle catches; tests don't).
- `oracle_survived` ⇒ either Bucket 4 (equivalent / unreachable) or
  Bucket 2 (real oracle gap) — the latter must be sub-classified by
  code inspection, since the runner can't introspect why the oracle
  missed it.

The V1 hypothesis: ~617 oracle_caught (~87 %) and ~90 oracle_survived
(~13 %, of which ~85 are Bucket 4 and ~5 Bucket 2). V2's job is to test
that.

### 3.1 mdrp2040/decode.rs — pre-staged dead-code cluster (Bucket 4 confirmed)

V1 reported 0 survivors in this file (110 mutants). V2 reports **79
oracle_survived out of 79 missed**. The delta is the
`classify_is_pure` / `classify_thumb16_pure` /
`classify_thumb16_misc_pure` / `classify_thumb32_pure` cluster added in
commit `42ee533` ("mdrp2040: port RP2350 decode cache (per-core,
region-invalidated)"). The commit message explicitly states:

> is_pure fast-path (skip Bus side-effects when decode is pure)
> deferred for a follow-up iteration.

Source-graph trace:
- `classify_is_pure` writes `FLAG_PURE` into `DecodedOp.flags` at
  `crates/mdrp2040/src/core/decode.rs:234`.
- `DecodedOp::is_pure()` reads the flag at
  `crates/mdrp2040/src/bus/mod.rs:264`.
- `grep -rnE "\.is_pure|is_pure\(\)" crates/mdrp2040/` returns **zero
  call sites** in production code. The mdrp2350 sibling has one
  consumer at `crates/mdrp2350/src/core/decode.rs:284` plus assertion
  suites in `crates/mdrp2350/src/tests.rs` (lines 9016, 9243, 9285,
  11851, 11866, 11882, 11893, 11906, 11907).

Verdict: **all 79 mdrp2040 classifier mutants are Bucket 4 by current
observability**. The classifier output isn't observed by anything; no
oracle can catch the mutations. The same mutations would land in
Bucket 3 the day the deferred fast-path consumer ships (it reads
`is_pure()` to skip bus-side-effect handling, so wrong classification
will diverge the QEMU end-state diff).

Recommended actions (V3):
1. **Direct unit tests for the classifier functions** — match the
   mdrp2350 test pattern. The classifier is a pure function of opcode
   bits; exhaustive 16-bit enumeration is feasible (65k cases).
2. OR **gate the classifier with `#[cfg(feature = "fast_path")]`**
   until the consumer lands. Avoids carrying observability gaps in
   the default build.
3. OR **`#[mutants::skip]`** annotations until consumer lands. Lowest-
   cost noise reduction; doesn't fix the underlying gap, just
   declares it.

This finding is the headline V2 result so far: V1's heuristic put
`mdrp2040/decode.rs` at 0 survivors and called it "well-tested";
V2 measurement shows 100 % of *new* mutants survive *because the
classifier is unobserved code*. The methodology pivot is what V2 was
built for.

## 4. Cross-cutting findings

(filled in after V2 run completes — V1 hypothesis vs measurement, any
new clusters, surprises.)

Two findings already locked:

1. **Pre-staged dead code is a coverage trap.** V1's heuristic
   classification is correct for the source state at the time it ran;
   it can't predict that a future commit will add classifier code
   without test coverage. V2's per-mutant oracle replay catches it
   immediately.
2. **Oracle-routing is observability-dependent.** A mutation in
   `vfp_sd` (FPU encoding helper) was caught by `softfloat_diff` only
   when the mutation broke the IEEE-754 helper output. Mutations in
   the encoding lookup itself (`(vd << 1) & d` style) were not caught
   because softfloat_diff doesn't run actual VFP instructions. This
   is a known gap of the V2 routing: encoding helpers in
   `execute_fpu.rs` are observable to QEMU FPU class (broken on QEMU
   8.2 in this env) or to silicon FPU oracles, but not to
   softfloat_diff.

## 6. Methodology — runner design

`scripts/v2_mutation_runner.py` (~250 LOC). Per-mutant pipeline:

1. Look up the mutant by name in `mutation/v2/mutants_catalog.json`
   (the full catalog produced by `cargo mutants --list --json --diff`,
   4480 entries).
2. Compute byte offsets `[start_col-1, end_col-1)` from the JSON span;
   splice the source file with `replacement` from the JSON.
3. `cargo build --release -p mdpicoem-harness --bin <oracle>` — uses
   incremental compilation; each mutation triggers a rebuild of the
   chip lib + relink of the harness binary (~18 s).
4. Run the oracle with bounded `--fuzz N`. Per-oracle CLI quirks:
   - `qemu_diff_m33`: `--classes base` (FPU class is broken on QEMU 8.2).
   - `softfloat_diff`: `--mode all` (FPU + DCP coprocessors).
   - `qemu_diff_m0plus`: no extra flag.
5. Revert the source file (always; `try`/`finally`).
6. Record JSON record to `mutation/v2/results.jsonl`.

### Oracle routing

| File                                 | Oracle             | Notes                          |
|---                                   |---                 |---                             |
| `mdrp2350/core/execute_thumb32.rs`   | `qemu_diff_m33`    | base classes, no FPU           |
| `mdrp2350/core/execute_fpu.rs`       | `softfloat_diff`   | FPU IEEE-754 helpers; gap on encoding helpers (vfp_sd etc.) |
| `mdrp2350/core/execute.rs`           | `qemu_diff_m33`    | base classes                   |
| `mdrp2350/core/decode.rs`            | `qemu_diff_m33`    | base classes                   |
| `mdrp2040/core/execute.rs`           | `qemu_diff_m0plus` |                                 |
| `mdrp2040/core/execute_wide.rs`      | `qemu_diff_m0plus` | M0+ Thumb-32 subset filter relaxed (today's work) |
| `mdrp2040/core/decode.rs`            | `qemu_diff_m0plus` |                                 |

### Known limitations

1. **QEMU 8.2 cortex-m33 FPU class broken in this env**. All FPU cases
   fail with EAGAIN on the GDB pipe. Pinned `--classes base`. Encoding
   helpers in `execute_fpu.rs` (`vfp_sd`, `vfp_sn`, `vfp_sm`,
   `fpscr_set_nzcv`) only get exercised when actual VFP instructions
   run; they will appear `oracle_survived` even when the mutation is
   semantically meaningful. **Not a Bucket-2 oracle gap in steady state**
   — a V2.1 with QEMU 10.2 (CI) FPU class restored should catch them.

2. **Single-shot fuzz budget**. First-pass `--fuzz 200` per mutant.
   Mutants that "look caught" via early-exit failure (e.g. a generic
   ADD test fails on every iteration) terminate quickly; mutants on
   rarely-triggered paths might be missed in 200 iterations. The
   `--retry-survivors --fuzz 2000` deep-pass mode confirms first-pass
   survivors aren't statistical misses.

3. **Per-mutant cargo rebuild**. Cannot avoid: cargo notices the source
   change and recompiles the chip lib + relinks the harness binary.
   ~18 s/mutant baked-in cost. Sequential 707 missed × 37 s/mutant =
   ~7.3 h wall-clock. Acceptable for an overnight run on the same host
   that processed V1 in 13 h.

4. **Cancellation**. Python `try/finally` reverts on SIGINT, but a
   SIGKILL would leave the source tree mutated. `git checkout` of the
   affected files restores cleanly. For CI safety this would warrant
   a process supervisor.

## 7. What V2 deliberately is NOT doing

- No CI integration (still a measurement exercise).
- No automated `#[mutants::skip]` annotation insertion. The V1 triage
  HLD §5 Action 2 proposed annotating Bucket-4 helpers; that remains
  pending and is unaffected by V2.
- No expansion of mutation scope beyond the seven files listed in V1
  (decode/execute on M33 + M0+ + execute_fpu on M33). V3 considers
  expanding to `exceptions.rs`, `coprocessor.rs`, etc. — out of scope
  for V2.
- No second-stage oracle for genuine Bucket-2 candidates. V2 reports
  `oracle_survived` and stops; further classification is human triage.
