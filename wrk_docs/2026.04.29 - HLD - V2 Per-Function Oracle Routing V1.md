## 1. Goal

Replace V2's coarse per-file oracle routing (`crates/mdrp2350/src/core/execute_fpu.rs → softfloat_diff` for every mutant) with **per-function** routing inside the runner, scoped initially to `execute_fpu.rs`. The IEEE-754 helpers (`fp_add`, `fp_sub`, `fp_mul`, `fp_div`, `fp_fma`, `fp_sqrt`, `fpu_unary`, the f16/f32 conversions, the rounding-mode helpers) are observable through `softfloat_diff` because the binary calls them with `f32` operands directly. The VFP-encoding helpers (`vfp_sd`, `vfp_sn`, `vfp_sm`, `fpscr_set_nzcv`, `vfp_expand_imm_f32`) are observable only when actual VFP instructions execute — they need `qemu_diff_m33 --classes fpu` (or a silicon FPU oracle). Routing the whole file to `softfloat_diff` puts ~10 encoding-helper mutants in `oracle_survived` purely because the wrong oracle ran, not because the mutation is equivalent (V2 triage HLD §3.6, §4 driver 2; JRN §Stage 5 case 6).

This HLD specifies the wiring. Activation of the QEMU FPU class is a separate problem (V2 triage HLD §6 Action 3, gated on QEMU 10.2 / fixed env). The wiring is independently valuable: it ships today, and **the moment the FPU class is healthy, the table activates the right route automatically**.

## 3. Proposed design

### 3.1 Where the routing table lives

**Recommend: a separate JSON sidecar at `scripts/v2_oracle_routing.json`**, loaded once at runner startup. Justification:

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| **(a)** Inline Python dict in `v2_mutation_runner.py` | Trivial; no extra file. | Editing routing requires editing the runner; review scope conflates "runner logic" with "routing data"; harder to diff routing-only changes. | Reject. |
| **(b)** JSON sidecar `scripts/v2_oracle_routing.json` | Pure data. Reviewable diff. Loaded with `json.load`. Same toolchain as `mutants_catalog.json`. Schema-validated easily. | One extra file to track. | **Pick.** |
| **(c)** YAML sidecar | Comments + nicer multi-line. | Adds a `pyyaml` dep that the runner currently doesn't carry. | Reject — payoff doesn't justify the dep. |
| **(d)** TOML sidecar | Stdlib `tomllib` in Python 3.11+ . | Awkward for nested arrays of route specs. | Reject. |

The sidecar is checked in (under `scripts/`), small (≤200 lines), and human-editable. The runner picks it up by default; `--routing <path>` on the CLI overrides it for ad-hoc experiments.


Field reference:

- `version` — integer, currently `1`. Future bumps allow schema migration.
- `default_oracles_by_file` — replaces today's `ORACLE_FOR_FILE`. Each entry is now a **list of routes** (one or more oracles), so the schema is uniform with `by_function`. For files we don't override per-function (everything except `execute_fpu.rs` initially), this is still a single-element list.
- `by_function[<file>][<fn>]` — per-function override. **Match key is the catalog's `function.function_name` field**, including `Type::method` qualification (e.g. `CortexM33::fpu_unary`). Glob/regex deliberately not supported in V1 — keep matches exact.
- `requires` — optional capability gate. The runner records which capabilities are healthy (see §3.4) and skips routes whose required capability is unavailable.
- `args` — passed verbatim after `--fuzz N` on the oracle command line. Today's `--classes base` / `--mode all` move from hardcoded into the table.

### 3.3 Function-name extraction

**Recommend: read the catalog's `function.function_name` field** (cargo-mutants exposes it natively). Falls back to a per-route resolver only for the 16 module-scope mutants that have no `function` field.

| Approach | Pros | Cons | Verdict |
|---|---|---|---|
| **(a)** Parse the source file at the mutant's line; walk back for `fn`/`impl` | Works without depending on catalog format. | Reinvents what cargo-mutants already gives us. Tricky for nested `impl`s, traits, macros; needs a parser. | Reject. |
| **(b)** Use the catalog's `function.function_name` field | **Verified populated for 4464/4480 (99.6 %) in-scope mutants** by direct inspection of `mutation/v2/mutants_catalog.json`. Method names appear as `Type::method` (e.g. `CortexM33::fpu_unary`), matching the source convention. Zero new tooling. | 16 module-scope mutants have no `function` (top-level `const` shifts, free helpers at module level). | **Pick.** |
| **(c)** Static `file:line_range → function_name` map precomputed | Catches the 16 module-scope cases too. | Adds a precompute step + a third file to maintain; brittle to source churn. | Reject — module-scope mutants fall back to file-default routing, which is what the current per-file code already does correctly. |

**Resolver pseudocode**:

```python
def resolve_routes(mutant: dict, routing: dict, capabilities: set[str]) -> list[Route]:
    file_rel = mutant["file"].replace("\\", "/")
    fn = (mutant.get("function") or {}).get("function_name")
    by_fn = routing["by_function"].get(file_rel, {})
    if fn and fn in by_fn:
        candidates = by_fn[fn]
    else:
        candidates = routing["default_oracles_by_file"].get(file_rel, [])
    return [r for r in candidates if r.get("requires") in (None, *capabilities)]
```

The 16 module-scope mutants land in the `else` branch and route via `default_oracles_by_file` — identical behaviour to today's per-file routing. No regression.

### 3.4 Multi-oracle handling

When a function has multiple routes (e.g. `CortexM33::fpu_v8m_dp` → both `softfloat_diff` AND `qemu_diff_m33 --classes fpu`), the runner runs them **sequentially** and aggregates as **"caught if ANY oracle catches"**.

| Choice | Rationale |
|---|---|
| **Sequential, not parallel** | The existing parallel launcher (§stage 6b of the JRN) shards by oracle to avoid GDB-port-3333 races; running two oracles per mutant inside one worker would re-introduce that race. Sequential keeps the worker single-port-bound and the parallel launcher unchanged. |
| **Caught-if-ANY** | A mutation is real if any oracle catches it. The differential semantics across oracles are independent (softfloat_diff observes IEEE-754; qemu_diff_m33 fpu observes encoding); the union is the correct combination. Equivalent to `OR` over per-oracle classifications. |
| **Short-circuit on first catch** | Save wall-clock — once one oracle reports caught, subsequent routes can skip. Recorded in result's `routes` array as `"skipped": true`. |
| **No partial-credit** | A mutant where softfloat catches but qemu-fpu would have missed is still "caught" — single bit of truth per mutant. Per-route detail kept in `routes` for triage. |

### 3.5 Backward compatibility

When a file has no `by_function` entry (every file other than `execute_fpu.rs` initially), the runner uses `default_oracles_by_file` — which in turn must mirror today's `ORACLE_FOR_FILE` exactly. **Identity at the per-file level is the regression test.** If `default_oracles_by_file` is missing from the routing JSON entirely (sidecar absent, `--routing /dev/null`, parse error), the runner falls back to the in-code `ORACLE_FOR_FILE` constant — preserving today's behaviour byte-identically.

The runner accepts a CLI `--routing <path>` (default `scripts/v2_oracle_routing.json`); `--no-routing` disables sidecar loading and forces fall-back. This lets the parallel launcher keep working unchanged while the sidecar is being authored / iterated.

### 3.6 Result schema extension

The current `Result` dataclass (one record per mutant, single oracle) becomes:

```python
@dataclass
class RouteResult:
    oracle: str
    args: list[str]
    classification: str   # oracle_caught / oracle_survived / oracle_unavailable
                           #   build_failed / skipped / error
    fuzz_count: int
    wall_seconds: float
    exit_code: Optional[int]
    notes: str

@dataclass
class Result:
    name: str
    file: str
    function: Optional[str]   # NEW — function.function_name from catalog
    classification: str       # AGGREGATE: oracle_caught / oracle_survived /
                              #            oracle_unavailable / build_failed / error
    routes: list[RouteResult] # NEW — one entry per oracle that ran (or was skipped)
    wall_seconds: float       # total across all routes
    # Legacy back-compat fields (kept so old consumers don't break):
    oracle: str               # = routes[0].oracle (for single-route compat)
    fuzz_count: int           # = routes[0].fuzz_count
    exit_code: Optional[int]  # = routes[0].exit_code
    notes: str                # = routes[0].notes
```

**Additive change.** Existing JSONL records (without `function` / `routes`) still parse: `function` defaults to `None`, `routes` to `[]`. Existing summary scripts (`scripts/v2_mutation_summary.py`) keep working because they read `classification` / `oracle` / `file`, none of which changed. New consumers that want per-route detail read `routes`.

### 3.7 Aggregate classification rules

Given a list of `RouteResult`, the aggregate `classification` is:

| Rule | Aggregate |
|---|---|
| Any route is `oracle_caught` | `oracle_caught` |
| All routes are `oracle_survived` | `oracle_survived` |
| All routes are `oracle_unavailable` | `oracle_unavailable` |
| Any route is `build_failed` | `build_failed` |
| Mixed `oracle_unavailable` + `oracle_survived` | `oracle_survived` (we measured at least once; the gap is on the unavailable route) |
| Anything else (errors, partial dropouts) | `error` |

The mixed `unavailable + survived` rule is the subtle one. Example: `CortexM33::fpu_v8m_dp` routes to softfloat (works) AND fpu (unavailable). softfloat returns survived. We **don't** want to report `oracle_unavailable` because we did get a real measurement; we **do** want `routes[1]` to record `oracle_unavailable` so triage can re-process when the fpu class returns. Reporting `oracle_survived` at the aggregate level preserves V2's existing bucket-counting semantics.

## 5. Gating the QEMU FPU class

### 5.1 Detection (smoke probe at startup)

When the runner starts, if any route in the loaded table has `requires: "fpu_class"`, the runner runs a **single 5-second smoke probe**:

```bash
qemu_diff_m33 --classes fpu --fuzz 1
```

with a 5-second wall-clock cap. Pass criteria: process exits within the cap **and** the exit code is 0 or 1 (oracle ran and either passed or caught a non-existent diff). Fail criteria: timeout, EAGAIN on stderr, or non-{0,1} exit code (typically the tooling/env error path).

On pass, `capabilities` includes `"fpu_class"`. On fail, the runner logs:

```
[12:34:56] FPU-class smoke probe failed (timeout=5s, env=QEMU 8.2). 'requires: fpu_class' routes will record 'oracle_unavailable'.
```

and continues. The 5-second budget is tight enough that an unhealthy env doesn't stall the run; loose enough that one slow QEMU spawn doesn't false-fail.

The smoke probe runs once per runner invocation, not per mutant. Result cached in the runner process for the lifetime of that worker.

### 5.2 Behaviour: `oracle_unavailable`

A new outcome `oracle_unavailable` joins the existing six (`oracle_caught`, `oracle_survived`, `build_failed`, `skip_no_oracle`, `error`, `timeout`). Records produced when:

- A route's `requires` capability is missing from the runner's healthy set, AND
- It's the **only** route for that mutant (otherwise the route is recorded as unavailable inside `routes` but the aggregate uses the available routes' verdicts per §3.7).

This is the key V2-numbers fix: a mutant in `vfp_sd` no longer counts as Bucket 4 `oracle_survived` when the only oracle that could observe it (`qemu_diff_m33 --classes fpu`) wasn't run. It counts as `oracle_unavailable`, which the V2 triage HLD can subtract cleanly from the Bucket 4 total.

### 5.3 Operator override

Two new CLI flags:

- `--allow-fpu` — force `"fpu_class"` into capabilities even if the smoke probe failed. Useful if the operator knows the env is fine (e.g. they fixed it manually) and wants to override a stale cache or a flaky probe.
- `--no-fpu` — force `"fpu_class"` OUT of capabilities even if the smoke probe passed. Useful if the operator suspects flakiness and wants to compare runs.

Default: capability set populated by the smoke probe. Flags are mutually exclusive; specifying both is a CLI error.

## 6. Test plan

### 6.1 Unit tests (Python)

A new `scripts/test_v2_routing.py` (pytest-shaped, importable as a module). Test surface:

1. **Function-name extraction**:
   - Catalog entry with `function.function_name = "fp_add"` resolves to `"fp_add"`.
   - Catalog entry with `function.function_name = "CortexM33::fpu_unary"` resolves verbatim.
   - Catalog entry with no `function` field falls back to `None` and routes via `default_oracles_by_file`.
2. **Route resolution**:
   - In-table function returns the per-function route list.
   - Out-of-table function returns the file-default list.
   - Out-of-table file returns `[]` (preserves today's `skip_no_oracle` behaviour).
3. **Capability gating**:
   - Route with `requires: "fpu_class"` and `capabilities = {"fpu_class"}` survives filtering.
   - Same route with empty capabilities is dropped.
   - Mixed list (one gated, one ungated) keeps the ungated.
4. **Aggregation**:
   - 1 caught + 1 survived → `oracle_caught`.
   - 2 survived → `oracle_survived`.
   - 1 survived + 1 unavailable → `oracle_survived` (the §3.7 mixed rule).
   - 2 unavailable → `oracle_unavailable`.
   - 1 caught + 1 unavailable → `oracle_caught`.
5. **Backward compat**:
   - Routing sidecar absent → uses the in-code `ORACLE_FOR_FILE`. Each (file, expected oracle) pair from today's table re-resolves to the same oracle.
   - Routing sidecar present but `by_function` empty → behaviour identical to per-file routing.

All run in isolation against synthetic catalog dicts; no cargo / no source tree.

## 7. Out of scope

- **No mutation-scope expansion** to bus / peripherals / DMA / PIO / exceptions (V3 territory).
- **No QEMU FPU class fix** — separate problem; V2 triage HLD §6 Action 3. This HLD's wiring lights up the moment that fix lands.
- **No softfloat_diff changes** — the oracle's coverage is what it is; we route mutants to it, we don't expand it.
- **No curated FPU corpora** — the QEMU FPU class corpus is what `thumb32_gen.rs` already emits.
- **No per-function routing for files OTHER than `execute_fpu.rs`**. The other six in-scope files (`execute_thumb32.rs`, `execute.rs` ×2, `decode.rs` ×2, `execute_wide.rs`) keep per-file routing. Adding entries for them is additive in the same schema and a follow-up if/when V3 surfaces a similar split.
- **No glob/regex match keys** in the function table. Exact match only. Glob is a future-V2.x option if the table grows past ~50 entries.
- **No retroactive re-classification** of the existing 506 first-pass survivors — see §8. The V2 triage doc owns that re-tabulation; this HLD owns the wiring.

## 10. Open questions for supervisor

1. **Sidecar location.** Is `scripts/v2_oracle_routing.json` the right home, or do you prefer it under `mutation/v2/` (which is gitignored — would need an exclusion) or under `wrk_docs/`?
2. **Aggregation rule for mixed `unavailable + survived`.** §3.7 picks `oracle_survived` (we did measure once; the gap is just on the unavailable route). The other defensible choice is `oracle_unavailable_partial` as a new outcome — more accurate in the presence of routing gaps, but adds a 7th classification that consumers (`v2_mutation_summary.py`, the V2 triage HLD bucket-counter) would need to learn.
3. **`function` field reliability.** I verified 99.6 % coverage on the current catalog. Is it worth adding a source-walk-back fallback for the 16 module-scope mutants, or is "module-scope routes via file default" (today's behaviour) acceptable forever?
4. **Smoke probe wall-clock budget.** I picked 5 s. The journal records "30 cases skipped over 90 s" on the broken QEMU 8.2 path — 5 s seems safe for a single-case probe but I'd like confirmation we don't have a host where 5 s is too tight even when the FPU class is healthy.
5. **Operator override semantics.** Should `--allow-fpu` cap retry attempts or impose a longer timeout when the FPU class is forced on? Today, an unhealthy `--allow-fpu` run will time out per-mutant (180 s default) and pile up `error` results. That's loud failure, which is arguably correct — but you may want a per-mutant FPU-route timeout cap.
6. **Should the routing table be loaded by `v2_mutation_run_parallel.sh` too, or only by the Python runner?** The current launcher passes through `--cargo-arg` flags but doesn't read the routing JSON. If a worker shards by oracle (W0 = m33, W1 = m0plus, W2 = softfloat), per-function routing in `execute_fpu.rs` may now route some mutants to W0 (the m33 worker) — does the launcher need to re-shard? My current expectation: no, because the parallel launcher hands a list of mutant names to one Python instance per worker, and the Python instance internally decides which oracle to spawn. A `vfp_sd` mutant arriving at the W2 (softfloat) worker via the file-shard rule will internally spawn `qemu_diff_m33`, which would race against W0's port 3333. **This is a real conflict** — see notes for option (a) keep file-sharding in the launcher and have the runner skip routes whose oracle doesn't match the worker's "owned" oracle (cleanest but introduces a `--owned-oracle <name>` runner flag); option (b) re-shard inside the launcher per-function. Want your take before Stage A starts.
