# RP2350 — RISC-V Hazard3 Test Oracles (V2)

**Date:** 2026-04-17
**Crate:** `crates/mdpicoem-harness/`
**Supersedes:** V1.
**Companion:** `wrk_docs/2026.04.17 - HLD - RP2350 RISC-V Hazard3 Core Support V6.md` (Hazard3 core HLD).

**V1 → V2 changes:** compliance suite switched from riscv-arch-test/riscof/Spike to `riscv-tests` (self-checking, no signature infrastructure); Phase 1 decision tree expanded with Outcomes D/E/Plan-D and ARM-vs-RV mode detection gate; cycle oracle split from semantic oracle on silicon because `mcycle` is CSR-only and halt-stops-counter; QEMU atomics split by reservable-region (inside diff'd, outside silicon-only); `mtval` and read-side-effect CSRs removed from diff set; WARL rounding disposition made explicit; fuzz-class weight table cut (LLD detail); "Verified" tier for Phase 2 renamed *Spec-conformant*; Plan D explicit for total-silicon-infeasible outcome; Phase 2A CSR-diff mechanism deferred to LLD after empirical check of QEMU's GDB `qXfer:features:read`.

## 1. Goal

Deliver verification for the Hazard3 port on RP2354 equivalent in rigour to what the Cortex-M33 side has today: an ISA-level differential against a reference simulator (QEMU analogue of `qemu_diff_m33`), a lightweight spec-conformance suite reading the standard Berkeley RISC-V tests, and a silicon differential against real RP2354 Hazard3 cores (the `probe_diff_rp2350` analogue).

Three independent oracles, because each catches different bugs and their test corpora do not overlap meaningfully.

## 2. Why three

| Oracle | Catches | Misses | Hardware? |
|---|---|---|---|
| **QEMU diff** (`qemu_diff_riscv32`) | RV32IMAC instruction semantics (including inside-reservable-region A-ext), base Zicsr CSRs, flag/`mstatus` shuffles, trap entry shape | Hazard3 custom CSRs (`meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` at `0xBE0..0xBE5`, `h3.misa` at `0xBF1`); Xh3Irq priority arbitration; outside-reservable-region atomics per RP2350 §2.1.6.2; `h3.block`/`h3.unblock`; cycle counts; WARL fields where Hazard3 rounds differently from QEMU | No |
| **Spec-conformance suite** (`riscv_tests`) | Spec-literal RV32I/M/A/C semantics from the Berkeley `riscv-tests` corpus: each test is self-checking (writes PASS/FAIL code to `tohost` + `ebreak`), so no signature infrastructure and no external reference simulator. Different test *authors* from QEMU — different bugs in each. | Same Hazard3-custom gaps as QEMU; single-hart only; no WARL exhaustion (that's riscv-arch-test territory, explicitly deferred) | No |
| **Silicon diff** (`probe_diff_riscv_rp2350` + `silicon_cycle_oracle_riscv_rp2350`) | Everything the others miss: Hazard3 CSR semantics against real RTL, Xh3Irq, outside-reservable-region atomics, cycle accuracy (`mcycle` via mailbox — not debug-halt-readable), WARL rounding, level-sensitive `mip` races | Nothing architecturally. Requires a Pico probe + RP2354 board in RV-select state, not CI. | **Yes** |

**Honest independence.** The three oracles are independent *where it matters*: three different test corpora authored by three different groups. They are **not** fully decorrelated at the implementation layer — all three load ELFs the same way, all three use the emulator's Hazard3 decoder, and QEMU-diff plus silicon-diff share the `riscv_gen.rs` fuzz generator. §3 lists the shared-code contamination hazards and §4 Phase 2A pins the property-test mitigations.

**"Spec-conformant" vs "Verified".** After Phases 2A + 2B ship, the ISA subsystems are **Spec-conformant** — they agree with two independent test corpora and QEMU. *Verified* (in the core HLD §7 audit terminology) requires the silicon oracle: nothing rules out a bug that silently agrees across all CI-reachable reference models. Only the hardware closes that loop.

## 3. Non-goals

- **No umbrella binary.** Each oracle is a separate `cargo run -p mdpicoem-harness --bin <name>`, matching the existing per-oracle topology.
- **No cross-arch test framework.** Thumb and RISC-V encodings, register sets, and trap models are different enough that one generic harness costs more than two focused ones. `thumb32_gen.rs` is M33-only; `riscv_gen.rs` is Hazard3-only.
- **No feature flags, no cargo features, no env vars** (per CLAUDE.md). Oracles run when invoked.
- **No riscof / Spike / riscv-arch-test runtime dependency.** V1 considered this; V2 dropped it in favour of `riscv-tests` (self-checking, no Python tooling, no Spike, no signature regeneration procedure).
- **No SDK firmware support.** Core HLD Q4 already deferred; these oracles validate the V1 ISA scope only.
- **No WARL-exhaustion oracle in V1.** `riscv-arch-test` style WARL-rounding corner cases are a follow-up; silicon catches the ones that matter for the RP2354 WARL set.

**Shared-code contamination hazards** (explicitly acknowledged, not hand-waved):
- The `riscv_gen.rs` fuzz generator is used by QEMU-diff and silicon-diff. Property tests against a hand-rolled reference encoder in Phase 2A LLD.
- The ELF loader is shared by `riscv_tests` and silicon-diff Path C firmware upload. Covered by the loader's unit tests plus a smoke test that loads a known-good ELF and verifies each byte.
- The emulator's Hazard3 decoder is under test in all three oracles by construction — that's the point; a bug there must be caught by divergence, not coverage.

## 4. Phasing

Three phases, one LLD each, written just-in-time. Phase 1 is an information-gathering spike; its outcome reshapes Phase 3. Writing Phase 3's LLD before Phase 1 completes is the M8-ring-road failure mode.

### Phase 1 — Probe-rs Hazard3 attach spike (≤1–2 days)

**Question:** can `probe-rs 0.31` reach a Hazard3 core on RP2354 at all, and at what capability level?

**Pre-spike precheck** (≤30 min, gates the whole spike):

1. `probe-rs chip info rp2350` — does the installed probe-rs target definition enumerate Hazard3 cores, or only the Cortex-M33 pair? If RV cores absent from the target file, **Phase 1 halts** and the decision tree short-circuits to Outcome 0 below (upstream probe-rs work required).
2. `probe-rs list` — confirm the Pico probe attached to the RP2354 board.
3. **ARM-vs-RV mode detection mechanism.** The spike must positively identify it is talking to a Hazard3 core, not an M33. Two independent checks, both required:
   - probe-rs `Core::architecture()` returns `Riscv` (not `Arm`).
   - Sentinel read: attempt `csrr x10, h3.misa` (CSR 0xBF1, Hazard3-only). On Hazard3 returns 0 cleanly. On an M33 the encoding is Thumb garbage; the observed PC/fault signature is distinct.

Both checks **must pass** before any test runs. If the board is booted into Arm mode (ARCHSEL OTP not programmed / POWMAN boot override not set), the spike exits with a loud "not in RV mode" message pointing to the OTP procedure (see next paragraph).

**Getting the RP2354 into RV mode.** RP2350 §5.10 POWMAN has a `CHIP_RESET.ARCH_SEL` soft-override path, and the OTP `CHIP_INFO` block carries the persistent fuse bits. A one-page procedure (`wrk_docs/RP2354_RV_mode_procedure.md`, delivered with Phase 1 LLD) documents both the soft-override-via-SWD path and the OTP-fuse procedure. Without this doc, the spike is unrunnable on a stock Pico 2; with it, the failure mode is loud-and-early, not silent.

**Deliverable.** ~200 LoC throwaway binary `crates/mdpicoem-harness/src/bin/riscv_probe_spike.rs` that runs the capability matrix. Not committed long-term; deleted when Phase 3 LLD lands (following the `smoke_per_core_cyccnt_rp2350` pattern).

**Capability matrix the spike measures** (expanded from V1's six to eleven):

| # | Capability | Why it matters |
|---|---|---|
| 1 | `Session::auto_attach("rp2350", …)` exposes a `RiscvCore` | Gates everything else |
| 2 | `core.halt()` succeeds on hart 0 | Path A/B baseline |
| 3 | `core.halt()` succeeds on hart 1 | Dual-core path A/B viability |
| 4 | `core.read_core_reg(RegisterId(...))` for x1..x31 + PC | GPR readback |
| 5 | `core.read_core_reg` works for **CSRs** (mstatus, mcause, mepc, mie, mip, mtvec) — or only for GPRs | Determines whether CSR-diff needs GPR-proxy |
| 6 | `core.write_core_reg` works for GPRs | Pre-state priming |
| 7 | `core.write_core_reg` works for CSRs | Pre-state priming for mstatus/mie/mtvec; without it, pre-state requires instruction-splice |
| 8 | `core.set_hw_breakpoint(addr)` | Path A vs B discriminator |
| 9 | `core.step()` single-step semantics | Path A vs C discriminator |
| 10 | `mcycle` reads deterministic under single-step (or: is the counter halted by debug entry per RISC-V debug §4.9.1?) | Whether Path A/B cycle oracle is viable |
| 11 | Halt-under-interrupt-pressure behaviour (halt with `mip[11]` asserted, read state, resume, no spurious traps) | Soak-mode viability; attach-when-quiescent-only is a major Path-A limitation |

**Decision tree** (pre-registered, expanded from V1):

| Spike outcome | Path | Phase 3 cost | Notes |
|---|---|---|---|

| **Outcome B.** As A but #8 (HW breakpoint) fails | **Path B — SW breakpoints via instruction-splice.** Harness writes `ebreak` (0x00100073) / `c.ebreak` (0x9002) as data at the end of each test slot. | +3 days over Path A | Requires explicit alignment + `fence.i` + prefetch-flush contract (see below). |
| **Outcome C.** As A but #5 AND/OR #7 fails (CSRs not accessible via `read_core_reg`/`write_core_reg`) | **Path A' — probe-rs + instruction-splice CSR-proxy.** Each test slot gets a small epilogue of `csrr`/`csrw` instructions into a scratch SRAM region; probe-rs reads scratch. | +2 days over Path A | The GPR-proxy idea from V1, promoted to deliberate design once the spike confirms it's needed. **Excludes `meinext` and any other read-side-effect CSRs** — those go to Path C. |

**Plan D is not a hidden outcome.** Making it explicit in the decision tree means §6 audit table has a defensible bottom-row even if silicon is unreachable.

**Phase 1 LLD** (`YYYY.MM.DD - LLD - RISC-V Probe-rs Attach Spike.md`) pins the exact probe-rs API calls, the sentinel read encoding, the RV-mode procedure doc, and the PASS/FAIL matrix format. Written day-of.

### Phase 2 — QEMU diff + spec-conformance suite (parallel, CI-only)

Phase 2A and 2B are independent and can proceed as soon as core HLD P2 lands. **Phase 2 does not depend on Phase 1.**

#### 2A — `qemu_diff_riscv32`

Binary name: `qemu_diff_riscv32`. GDB port: **3335** (3333 = M33, 3334 = M0+).

**QEMU invocation — pinned in the LLD after empirical check.** The V1 draft invocation (`-cpu rv32,a=true,m=true,c=true,zicsr=true,zifencei=true`) uses `-cpu` property syntax that may not be valid on the installed QEMU. The first LLD step runs `qemu-system-riscv32 -cpu help` and `qemu-system-riscv32 -cpu rv32,help` on the `C:\Program Files\qemu\qemu-system-riscv32.exe` binary and pins the invocation against what QEMU actually accepts. Known-good elements:
- `-machine none -bios none` (no peripheral aliases, no OpenSBI).
- `-m 8M -nographic`.
- `-icount shift=0,align=off,sleep=off` (deterministic stepping).
- `-gdb tcp::3335 -S -kernel <bin>`.

`QemuProcess` adds a `QemuProfile::RISCV32_RP2350` variant and a spawn wrapper that dispatches to `qemu-system-riscv32` when the profile's `cpu` field begins with `rv32`. No gdb_client restructure.

**CSR-diff mechanism — deferred to LLD pending QEMU GDB-stub empirical check.** V1 designed a GPR-proxy prelude/epilogue as the primary path; V2 defers this choice. The LLD first checks whether QEMU's RISC-V GDB stub exposes the minimum CSR set via `qXfer:features:read` (documented as supported in upstream since ~7.0). Outcomes:
1. **Stub exposes CSRs via `qXfer`** → direct CSR read. Primary path.
2. **Stub exposes some CSRs but not all** → mixed: `qXfer` for what works, instruction-splice proxy for the rest.
3. **Stub is GPR-only** → full instruction-splice proxy (falls out of scope for `csrr`/`csrrw` semantic *tests* because the proxy uses the DUT's own `csrr` — would mask decoder bugs on those specific instructions; those tests diff via trap/post-state side-effects instead).

**Minimum CSR diff set** (V1 had 8; V2 drops `mtval`):
`{mstatus, mcause, mepc, mip, mie, mtvec, mscratch}`.

- `mtval` dropped: Hazard3 hardwires `mtval=0` (core HLD §4.3); QEMU's generic rv32 writes fault/illegal-insn addresses; every trap test would diff spuriously. Either mask it on QEMU side or exclude — V2 chooses exclude, simpler.
- Read-side-effect CSRs (`meinext` reading clears `meifa` per Hazard3 csr.adoc) are **not** in any diff path — included Phase-3-only. Reading them in the epilogue would itself corrupt state.

**WARL rounding disposition.** Hazard3 rounds `mstatus.MPP` writes to `0b11`, drops out-of-range `mcause` bits, etc. (core HLD §4.5). QEMU's generic rv32 rounds differently. The LLD enumerates the affected WARL fields and specifies a per-field disposition: either mask the QEMU post-state to Hazard3 semantics before compare, or skip the fuzz variant that hits the affected pattern. Not "the encoder filters them out" — concrete table.

**Fuzz classes.** Mirror `qemu_diff_m33`'s class structure. Class list:

- RV32I ALU (register + immediate forms).
- RV32I memory (load / store, aligned).
- RV32I misaligned load/store (exercises `mcause` 4/6 paths per core HLD §4.5).
- RV32I branch / jump.
- RV32I upper (lui / auipc) + PC-relative pairs (auipc/jalr, auipc/addi).
- RV32M.
- RV32A **inside reservable region** (lr.w/sc.w/amo\*.w with addresses pre-primed to `0x2000_0000..0x2008_2000`). Outside-region is silicon-only per §4.7 of the core HLD.
- RV32C (with dedicated Zcmp quadrant-2 encoding sweep per core HLD §4.5 V6).
- Zicsr (against the minimum CSR set, excluding read-side-effect CSRs).
- Zifencei self-modifying probe (small; the no-op implementation and the future decoded-op cache tripwire both need this to not silently drift).
- CSR-side-effect chains (`csrrw mstatus` then branch — exercises pipeline/hazard interaction).

Exact per-class sample weights live in the LLD, not the HLD.

**Unknown-opcode escalation:** in fuzz mode, our emulator's `warn!` for unknown-opcode escalates to test failure. QEMU's illegal-instruction trap (`mcause=2`) is the expected reference; a mismatch signals a decoder bug on our side.

**Phase 2A LLD** pins the QEMU invocation post-empirical-check, the CSR-diff mechanism post-empirical-check, the WARL-field disposition table, fuzz generators, and a property test for the `riscv_gen.rs` encoder against a hand-rolled reference.

#### 2B — `riscv_tests` (spec-conformance suite)

**Corpus:** Berkeley [`riscv-software-src/riscv-tests`](https://github.com/riscv-software-src/riscv-tests). Self-checking: each test sets up state, executes, and either writes success (`tohost = 1`) or a failure code and `ebreak`s. No signature infrastructure. No Spike. No riscof.

**Vendoring.** `third_party/riscv-tests/` as a git submodule pinned at a specific upstream SHA. Only the pre-compiled ELFs for the relevant subset are used; the build tooling stays out of the runtime. Targeted subset:
- `rv32ui-p-*` (user ISA-I, machine-mode, physical memory) — ~35 tests.
- `rv32um-p-*` — ~8 tests.
- `rv32ua-p-*` — ~10 tests (inside-reservable addresses by default).
- `rv32uc-p-*` — ~3 tests.
- `rv32mi-p-*` (machine ISA) — ~11 tests: CSR basics, illegal-insn, misaligned-access, wfi, mtvec.

**Toolchain pinning.** The submodule includes a `riscv-tests/env` and a Makefile that requires `riscv64-unknown-elf-gcc`. Because we only use the pre-built ELFs the submodule ships (no runtime build), **toolchain version doesn't matter for running**. For *rebuilding* (e.g. local ELF changes), a pinned Docker image in `scripts/riscv-tests-rebuild.dockerfile` gives a reproducible environment. Matches the simplicity bar — Docker is not a runtime dependency.

**Runner: `riscv_tests`.**

```
for each ELF in third_party/riscv-tests/isa/rv32u{i,m,a,c}-p-*, rv32mi-p-*:
    load ELF into emulator's SRAM (respecting linker symbol layout)
    set pc = ELF entry point
    run with cycle cap (e.g. 100k cycles) until:
        tohost_write detected (success / fail code)
        ebreak hit (shouldn't happen in well-formed tests; distinct outcome)
        cycle cap reached (HUNG)
        bus fault (FAULTED)
    report PASS / FAIL(code) / HUNG / FAULTED per ELF
```

CLI: `--filter <glob>`, `--list`, `--verbose`. No fuzz (conformance, not randomised).

**Why `riscv-tests` over `riscv-arch-test`:**
- Self-checking → no Spike dependency, no signature regeneration, no staleness risk.
- Shipped pre-built → no build-time toolchain dependency for running.
- Smaller corpus (~65 tests vs ~400) → faster CI, easier failure triage.
- Idiomatic first step — every RISC-V implementation under the sun uses it.
- WARL-exhaustion is the only real loss vs riscv-arch-test, and WARL matters for RP2354 in ways silicon (Phase 3) catches authoritatively. Re-visit arch-test in a follow-up phase if silicon is unreachable (Plan D) and WARL coverage becomes the only remaining gap.

**Phase 2B LLD** pins: submodule SHA, the ELF subset allowlist, the `tohost` memory-map convention (address is from the ELF linker script — `begin_signature`/`tohost` symbols), cycle-cap values per test class, the four outcome codes.

### Phase 3 — Silicon oracles (shape set by Phase 1)

**Split into semantic oracle and cycle oracle.** V1 treated them as one; V2 separates because `mcycle` has fundamentally different constraints from register state:

- `mcycle` is a CSR, not a bus-mapped register. Probe-rs `read_core_reg` may or may not reach it (Phase 1 capability #5).
- `mcycle` halts while the hart is in debug halt (RISC-V debug §4.9.1 `countstop_debug` default behaviour). So even if readable under single-step, the delta doesn't reflect executing-at-native-speed cost.
- Therefore the cycle oracle **always needs a self-running stub that reads `mcycle` itself and writes to a mailbox** — the ARM-side `silicon_cycle_oracle_rp2350` K-delta protocol transfers, but the *stub* is RV-native (JAL/JALR framing, `csrrs t0, mcycle, x0` into mailbox, `csrrs t0, mcycleh, x0` for the upper half, `csrrwi x0, mcountinhibit, 0` in the prologue).

Binaries:
- `probe_diff_riscv_rp2350` — semantic oracle. Path A/B/A'/D/E per Phase 1 outcome.
- `silicon_cycle_oracle_riscv_rp2350` — cycle oracle. Always mailbox-shaped; the K-delta protocol from `silicon_cycle_oracle_rp2350` transfers directly.

**Path B details (SW breakpoints).** If Path B applies, the contract for each test slot:
1. Align sentinel (`ebreak` 0x00100073 or `c.ebreak` 0x9002) to an instruction granule boundary; pick the variant matching the preceding instruction's length.
2. Emit `fence.i` after writing the sentinel — even though our emulator makes `fence.i` a no-op (core HLD §4.5), real silicon requires it to flush the prefetch queue before executing the newly-written bytes.
3. Enter the test slot via JAL/JALR so the prefetch sees the slot from its head, not mid-flight.

**`mcountinhibit` priming.** Regardless of path, silicon boot leaves `mcountinhibit.CY = 1`. Semantic oracle tests don't care; cycle oracle's stub clears `mcountinhibit` in its prologue (single `csrrwi x0, mcountinhibit, 0`). No path requires probe-rs to write `mcountinhibit` directly — the stub owns it.

**Silicon-only test categories** (expanded from V1):

| Category | What it tests | Depends on |
|---|---|---|
| Hazard3 custom CSR window | `meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` semantics against real RTL | core HLD P4 complete |
| Xh3Irq priority arbitration | Nested preempt, `meinext.update` auto-clear of `meifa`, IRQ-coincident-with-mret (core HLD §4.6) | core HLD P4 |
| Atomics outside reservable region | `amo*.w` → `mcause=7`; `lr.w`/`sc.w` → infinite loop (RP2350 §2.1.6.2) | core HLD P3 |
| `mip[3]`/`mip[7]` level-sensitive timing | MSIP/MTIP from SIO register write to `mip` observable, and IRQ asserted during `csrrw mstatus`/`csrrw mie` race | core HLD P4 |
| Cycle accuracy | Per-instruction and short-sequence `mcycle` deltas; K-delta vs emulator | Cycle oracle working |
| `mcycle`/`mcycleh` wrap | 32→64 bit transition; `mcycleh` sampling discipline | Cycle oracle working |
| Reservation granule | Empirical: what byte granularity does `sc.w` actually clear? RP2350 datasheet says word; silicon may differ. | core HLD P3 |
| `fence.i` cross-core | Core 0 writes instruction; does core 1's prefetch see it with/without `fence.i`? | Dual-hart Path A or C |
| WARL rounding | Per-field enumeration from Phase 2A LLD; validate QEMU's mask-to-Hazard3 decisions against real silicon | Phase 2A shipped |

**Concurrent probe use (Q7 promoted to constraint).** RP2354's ARCHSEL latches at reset. A single probe cannot toggle between ARM and RV modes within a soak pass — the chip must be re-booted into the chosen mode and the OTP / POWMAN state determines which one. Consequence:
- `test_silicon` soak mode runs **serialised alternating passes**: ARM soak, reboot chip into RV mode, RV soak, reboot back. Cadence is per-duration-chunk; a full-rotation soak is the baseline.
- True-parallel requires two boards (one ARM-mode Pico 2, one RV-mode Pico 2) with two probes — doable when the rig exists, not required for V1.

**Phase 3 LLD** (written **after** Phase 1 concludes) nails down: exact path selection from the spike matrix, the mailbox stub encoder, the `test_silicon` orchestrator wiring (per-case filter prefix `rv:`, watchdog tuning for RV step latency, probe-serial selection), the Plan D documentation entry if triggered.

## 7. Open questions / risks

**Q1 — Phase 1 exact outcomes.** Resolved at spike conclusion.

**Q2 — QEMU Hazard3 alignment.** Generic `rv32` model matches ISA semantics but not Hazard3-custom CSR addresses or WARL rounding. Covered by CSR-diff-set exclusions (§4 Phase 2A) and WARL disposition table (LLD).

**Q3 — `riscv-tests` corpus freshness.** Submodule pinned at SHA. Upgrade is a manual `git submodule update` + re-run the conformance suite; a failing test on upgrade is the oracle's job to surface. No signature regeneration means no staleness risk class — this is the main reason V2 dropped riscv-arch-test.

**Q4 — Reference implementation bugs.** QEMU has bugs; `riscv-tests` has bugs. Expected failure modes: (a) we catch a real emulator bug and fix it; (b) we agree with one oracle and diverge from the other, needing triage against the spec; (c) rarely, both oracles agree on something the spec doesn't say — silicon (Phase 3) closes this final loop, which is the whole point of a three-oracle design.

**Q5 — Phase 3 LLD timing.** LLD written *after* Phase 1 concludes.

**Q6 — Cycle-accuracy divergence budget.** Analogue of the ARM-side bank-contention / backward-branch penalty. Cycle gaps discovered by the cycle oracle land in `tech_debt.md`, not as Phase 3 blockers.

**Q7 — Concurrent silicon use (promoted from curiosity to constraint).** ARCHSEL-latches-at-reset means soak is serialised alternating passes. Two-board parallel is a rig upgrade, not a Phase 3 requirement.

**Q8 — ARM-vs-RV mode detection in the spike.** Two-check requirement (probe-rs `architecture()` + sentinel CSR read) pinned in §4 Phase 1. Without this, the failure mode is "spike runs against M33 and reports nonsense". With it, mismatched-mode exits loudly.

**Q9 — Shared-code contamination.** Property-tested encoder (§3) is the mitigation. The ELF loader has shared-code exposure between `riscv_tests` and Path C firmware upload; a byte-level smoke test in the loader's unit tests addresses it.

## 8. Deliberate exclusions

Trimmed from V1's 9 bullets to what's load-bearing:

- No riscof / Spike / riscv-arch-test runtime dependency (V2 replaces V1's vendored-ELF+signature plan with `riscv-tests`).
- No cycle-accuracy from QEMU (QEMU isn't a cycle-accurate reference for Hazard3 — Phase 3 cycle oracle is the only answer).
- No WARL-exhaustion oracle in V1 (defer to follow-up, or catch via silicon).
- No umbrella / cross-arch harness; two separate QEMU diffs, two separate silicon diffs.

If the design grows beyond this document, the growth is wrong.
