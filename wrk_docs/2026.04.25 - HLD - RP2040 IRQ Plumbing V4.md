## 1. Purpose

Make `silicon_isr_diff_rp2040` PASS on the EMU side for both V1
scenarios:

- `isr_m0_timer_cold` — TIMER ALARM0 → NVIC IRQ #0 → handler.
- `isr_m0_tail_chain_pendsv_systick` — SysTick underflow + ICSR
  PENDSVSET → tail-chained PendSV + SysTick handlers.

Exit criterion is "two scenarios green on EMU; FAIL surface
shrinks to genuine HW divergences when the probe attaches."

## 2. Current state — what's already there

V7 §5.2/§5.5 plumbing has landed in `crates/mdrp2040/src/`:

- `Bus::irq_pending: u32` — peripheral-asserted level/pulse bitmap
  (26 IRQ lines, `crates/mdrp2040/src/irq.rs`).
- `Bus::tick_peripherals` (`bus/mod.rs:1692`) — per-cycle slow-path
  tick that folds TIMER alarms, UART/SPI/I2C/ADC/PWM level IRQs
  into `irq_pending`.
- `Emulator::drain_pending_irqs_to_cores` (`lib.rs:678`) — drains
  `irq_pending` into both cores' `Nvic::set_pending`.
- `CortexM0Plus::maybe_dispatch_external_irq` (`core/mod.rs:280`,
  called from `step` at `:229`) — pre-instruction poll for IRQs ≥
  16; honours PRIMASK; "no preemption" rule.
- `Bus::nvic_mmio_read32`/`write32` (`bus/mod.rs:1387-1457`) —
  ISER/ICER/ISPR/ICPR/IPR per-core via `Bus::active_core()`.
- `Bus::ppb` is `[Ppb; 2]` (per-core); each holds VTOR, ICSR
  W1S/W1C bits, SHPR2/3 storage. ICSR `PENDSVSET`/`PENDSTSET`
  latch correctly on write (`bus/ppb.rs:153-164`).
- TIMER ALARM emission end-to-end works; INTE checked at
  fire-time (`peripherals/timer.rs:182`), so the oracle's
  ALARM0-then-INTE-then-ISER write order is safe.

## 3. Gap analysis

| # | Gap | Today | Effect on oracle |
|---|---|---|---|
| 1 | SysTick (`SYST_CSR/RVR/CVR/CALIB` at `0xE000_E010..0x1F`) | Not decoded; PPB falls through with `_ => 0` / `_ => {}` (`bus/ppb.rs`) | Tail-chain scenario's SysTick MMIO writes are no-ops → no underflow → `ICSR.PENDSTSET` never asserted by HW |
| 2 | ICSR `PENDSVSET` / `PENDSTSET` dispatch | Bits latch in `Ppb::icsr` but neither `core/mod.rs::step` nor `core/exceptions.rs::exit_exception` polls them; only `maybe_dispatch_external_irq` runs (IRQs ≥ 16 only) | PendSV / SysTick handlers never dispatch; tail-chain back-edge missing |
| 3 | Threaded `WorkerBus` NVIC MMIO interception | `WorkerBus::ppb_read32`/`write32` (`threaded/bus.rs:769-775`) routes ALL of region 0xE directly to per-core `Ppb::read32`/`write32` — no NVIC decode | In threaded mode (the default), `str` to `NVIC_ISER0` is silently dropped → IRQ #0 never enabled |

Closing 1, 2, 3 satisfies the oracle.

## 4. M33 → M0+ delta

The proven shape lives in `crates/mdrp2350/src/`. M0+ trim:

- **No Secure / Non-Secure split.** Single ICSR / NVIC / SysTick
  alias. Oracle uses `VTOR_ADDR = 0xE000_ED08` (singular).
- **No FAULTMASK, no BASEPRI.** Priority masking is just PRIMASK.
- **4 priority levels**, top 2 bits significant. SHPR3 already
  models this; NVIC IPR already masks to `PRIORITY_MASK = 0xC0`
  (`core/nvic.rs:52`).
- **No DWT CYCCNT.** Oracle treats CYCCNT as unobserved on M0+.
- **17-entry vector table** (oracle places TIMER_IRQ_0 at
  vector[16]). VTOR-driven walk reads `mem[vtor + 4*exc_num]`.
- **Configurable exceptions are SVCall (#11), PendSV (#14),
  SysTick (#15).** Same priority arbitration as M33.
- **No ICI continuation on multi-register transfers.** Async
  dispatch fires at instruction boundaries only (existing
  `maybe_dispatch_external_irq` already does this; the new
  `try_take_any_pending_exception` inherits the call site).
- **`Bus::irq_pending` is a single shared `u32` on M0+**;
  mdrp2350 carries a per-core `irq_pending: [u32; 2]` with a
  "dual-clear invariant" (`crates/mdrp2350/src/core/exceptions.rs:
  608-622`). M0+ keeps the single shared mask — the V1 oracle
  scenarios don't drive cross-core asymmetric delivery.

What we explicitly do **not** copy from M33: SAU, MPU, CPACR,
FPCCR/FPCAR, lazy-FP, NMI ICSR.NMIPENDSET dispatch, dual-clear
invariant.

### 5.2 Component B — SysTick model

Five registers at `0xE000_E010..0xE000_E01F`:

| Offset | Name | Purpose |
|---|---|---|
| 0x10 | `SYST_CSR` | ENABLE (bit 0), TICKINT (1), CLKSOURCE (2), COUNTFLAG (16, RC) |
| 0x14 | `SYST_RVR` | 24-bit reload value (writes truncated to `[23:0]`; reads return 24 bits) |
| 0x18 | `SYST_CVR` | 24-bit current value (any write zeroes `cvr` *and* clears `csr.COUNTFLAG`; reads return current decremented value) |
| 0x1C | `SYST_CALIB` | RAZ stub — `0` |

**Where it lives.** New module `crates/mdrp2040/src/bus/systick.rs`
plus `pub(crate) systicks: [SysTick; 2]` on `Bus`. Threaded:
`pub(crate) systicks: [SysTick; 2]` on `WorkerBus` (matches the
existing `[Ppb; 2]` / `[Nvic; 2]` per-core arrays).

```rust
pub struct SysTick {
    pub csr: u32,    // ENABLE | TICKINT | CLKSOURCE | COUNTFLAG (RC)
    pub rvr: u32,    // 24-bit
    pub cvr: u32,    // 24-bit
}

impl SysTick {
    pub fn new() -> Self { Self { csr: 0, rvr: 0, cvr: 0 } }
    pub fn read32(&mut self, addr: u32) -> u32 { /* see below */ }
    pub fn write32(&mut self, addr: u32, val: u32) { /* see below */ }
    pub fn is_enabled(&self) -> bool { self.csr & 1 != 0 }

    /// Tick once per master cycle. Returns `true` iff this tick
    /// generated a SysTick exception (caller sets ICSR.PENDSTSET on
    /// the active-core PPB).
    ///
    /// Per ARMv6-M ARM §B3.3.1: when the counter reaches 0, on the
    /// *next* clock cycle the value is reloaded from RVR; if
    /// TICKINT is set, that reload-tick asserts the SysTick
    /// exception. Period is therefore RVR+1 cycles (with CVR=0
    /// after firmware's clearing write, the very first tick fires).
    pub fn tick(&mut self) -> bool {
        if !self.is_enabled() { return false; }
        if self.cvr == 0 {
            self.cvr = self.rvr & 0x00FF_FFFF;
            self.csr |= 1 << 16;            // COUNTFLAG
            return self.csr & 2 != 0;       // TICKINT
        }
        self.cvr -= 1;
        false
    }
}
```

**MMIO write semantics:**
- `RVR`: `self.rvr = val & 0x00FF_FFFF`.
- `CVR`: any write `val` stores `0`; also clear `csr.COUNTFLAG`.
- `CSR`: store `val & 0x7` (only ENABLE/TICKINT/CLKSOURCE
  writable); leave `COUNTFLAG` untouched on write.

**MMIO read semantics:**
- `CSR`: read returns `csr`, then clears `csr.COUNTFLAG` (read-clear).
- `RVR` / `CVR` / `CALIB`: plain reads (CALIB=0).

**CLKSOURCE.** RP2040 silicon: `CLKSOURCE=0` selects the watchdog-
tick generator (1 µs nominal); `CLKSOURCE=1` selects the processor
clock. Oracle's `SYST_CSR_ENABLE_TICKINT_CORE = 0b111` (ENABLE |
TICKINT | CLKSOURCE) — processor clock. **V1 ticks SysTick once
per master cycle when `csr.ENABLE`, regardless of CLKSOURCE.** This
is exact for `CLKSOURCE=1`; `CLKSOURCE=0` is approximated. RVR=4
underflows in the same handful of cycles either way for the V1
scenarios. See §9.1.

**Where it ticks.** Once per master cycle inside the slow-path
inner loop of `Emulator::step` (`lib.rs:652-664`), after
`tick_peripherals` and before `drain_pending_irqs_to_cores`:

```rust
if self.bus.systicks[self.bus.active_core()].tick() {
    self.bus.ppb[self.bus.active_core()].icsr |= 1 << 26;
}
```

**Precondition.** SysTick is ticked for the active core only.
This is correct when at most one core is unhalted (the V1 oracle
case — core 1 halted), OR when both cores' SysTicks are
programmed identically. A future scenario with both cores running
and asymmetric SysTick programming would tick the secondary
core's SysTick at half-rate and is not in scope; track in §9.2.

The fast-path gate at `lib.rs:641-651` is **not modified**.
SysTick-enabled workloads stay on the slow path because they
typically also have peripheral activity. If `paced_bench_rp2040`
later shows ≥3% regression with SysTick enabled, add a gate then.

**Threaded path.** `WorkerBus` gets the same `[SysTick; 2]` field
and `systick_mmio_*` methods. The threaded worker's per-cycle tick
loop (`threaded/peripherals.rs`) ticks `systicks[self.core_id]`
adjacent to `tick_peripherals` and ORs the result into the
worker's `ppb[self.core_id].icsr`.

### 5.3 Component C — `try_take_any_pending_exception`

Replace `maybe_dispatch_external_irq` (`core/mod.rs:280`) with a
single helper that arbitrates **all** pending exceptions
(PendSV, SysTick, external IRQ) under one priority comparison. The
helper is a near-line-for-line port of mdrp2350's
`try_take_any_pending_exception` (`crates/mdrp2350/src/core/
exceptions.rs:564`), trimmed for ARMv6-M and rewritten against the
M0+ `CoreBus` API (`bus.ppb(idx)` / `bus.ppb_mut(idx)` / `bus.nvic
(idx)` / `bus.nvic_mut(idx)`). **No new `CoreBus` methods are
needed.**

```rust
fn try_take_any_pending_exception<B: CoreBus>(&mut self, bus: &mut B) -> u32 {
    if self.regs.primask & 1 != 0 { return 0; }

    let core = self.core_id as usize;
    let icsr = bus.ppb(core).icsr;
    let pendsv = icsr & (1 << 28) != 0;
    let pendst = icsr & (1 << 26) != 0;

    let mut best: Option<(u8, u16)> = None;  // (prio, exc_num)

    if pendsv {
        best = Some((bus.ppb(core).exception_priority(14) as u8, 14));
    }
    if pendst {
        let p = bus.ppb(core).exception_priority(15) as u8;
        best = match best {
            None => Some((p, 15)),
            Some((bp, be)) if p < bp || (p == bp && 15 < be) => Some((p, 15)),
            other => other,
        };
    }

    // Highest-priority pending+enabled external IRQ. Reuse the
    // existing scan logic (currently inline at core/mod.rs:307-321);
    // factor out as `Nvic::highest_priority_pending(&self) ->
    // Option<(u8, u8)>` returning `(irq, priority)` or None — folds
    // the priority lookup the caller would otherwise repeat.
    if let Some((irq, p)) = bus.nvic(core).highest_priority_pending() {
        let exc = 16u16 + irq as u16;
        best = match best {
            None => Some((p, exc)),
            Some((bp, be)) if p < bp || (p == bp && exc < be) => Some((p, exc)),
            other => other,
        };
    }

    let Some((_, candidate)) = best else { return 0; };
    if !self.can_dispatch_now(bus) { return 0; }

    match candidate {
        14 => bus.ppb_mut(core).icsr &= !(1 << 28),
        15 => bus.ppb_mut(core).icsr &= !(1 << 26),
        e  => bus.nvic_mut(core).clear_pending((e - 16) as u8),
    }
    self.enter_exception(candidate, bus)
}

/// V1 dispatch gate: `true` iff no exception is currently active.
///
/// This is **stricter** than ARMv6-M ARM §B1.5.4, which permits a
/// higher-priority exception to preempt a lower-priority handler.
/// V1 follows the existing `maybe_dispatch_external_irq` behaviour
/// because the V1 oracle scenarios don't exercise preemption (all
/// dispatches enter from thread mode). Tracked in §9.2 as
/// follow-up.
fn can_dispatch_now<B: CoreBus>(&self, bus: &B) -> bool {
    !bus.ppb(self.core_id as usize).any_active()
}
```

**New addition to `Nvic`.** Hoist the priority-scan loop currently
inline at `core/mod.rs:307-321` into a `Nvic::highest_priority_
pending(&self) -> Option<(u8, u8)>` method, returning `(irq,
priority)` for the IRQ with the lowest priority value among
`pending & enabled`, tie-breaking by lower IRQ number (matching
today's behaviour). The dispatcher calls it once and destructures
both fields, instead of inlining the scan and re-reading
`priority[irq]`. Pure refactor: the
existing tests for `maybe_dispatch_external_irq`'s scan continue
to assert correctness via the new dispatcher.

**Call site.** Replace the `maybe_dispatch_external_irq` call at
`core/mod.rs:229` with `try_take_any_pending_exception`. Same
position (top of `step`, before fetch), same return-type contract
(cycles consumed on dispatch, 0 otherwise). Delete the old helper.
Existing IRQ-only tests for `maybe_dispatch_external_irq` migrate
verbatim by call-site rename — the IRQ-only branch of the new
helper is byte-equivalent. Preserve test names with a `#[test]`
rename only.

**Tail-chain at exception return.** `core/exceptions.rs::
exit_exception` (`:173-260`) gets a single new block immediately
before the final return at `:261`, *after* the active-flag clear at
`:253` (so `can_dispatch_now` correctly sees no handler active for
tail-chain):

```rust
fn exit_exception(...) -> u32 {
    // ... existing unstack + active-flag clear + register restore ...

    // Tail-chain poll: if any exception is still pending and
    // dispatchable now that we've exited handler mode, take it
    // without unwinding back to thread mode.
    let chained = self.try_take_any_pending_exception(bus);
    cycles_so_far + chained   // chained is 0 if no tail-chain
}
```

The poll runs *after* SP unstack (so the next exception entry
stacks fresh thread-mode state) and *after* the active-flag clear
(so `can_dispatch_now` permits dispatch). This matches the M33
sequence at `crates/mdrp2350/src/core/exceptions.rs` exit path.

### 6.2 EMU-side integration test for the oracle scenarios

Refactor `crates/mdpicoem-harness/src/isr_scenarios_rp2040.rs::
run_one_scenario` (line 777). Today the EMU half is a contiguous
block (`:846-895`). Extract:

1. `pub fn setup_emulator_image(&mut Emulator, &IsrScenario)` —
   image upload, init regs, scenario preamble, core priming,
   CYCCNT-mailbox state. No probe-rs.
2. `pub fn run_emu_scenario(&mut Emulator, &IsrScenario) ->
   EmuOutcome` — runs the EMU forward and returns observable
   readouts plus a status flag. **Does not run for the full
   `max_millis` budget when success is observable.**

   ```rust
   pub enum EmuOutcome {
       /// Run completed; observables collected. Caller diffs
       /// against expected per-scenario asserts.
       Completed(Vec<u32>),
       /// CPU entered HardFault during the run — a distinct
       /// failure class so a misdispatch surfaces clearly.
       HardFault { pc: u32, ipsr: u8 },
       /// Cycle budget exhausted with no observable progress.
       Timeout,
   }
   ```

   The runner:
   - Picks a primary success observable per scenario (oracle
     already does this at `:812-816` — `CTR_TIMER_ADDR` for cold
     timer, `CTR_PENDSV_ADDR` for tail-chain).
   - Steps in chunks of `cycles_per_ms / 4` (~1.6k cycles at ROSC
     ~6.5 MHz). After each chunk: if the primary observable
     reached its expected non-zero value, do one extra chunk
     (so the tail-chain scenario has a window to fire the
     second exception), then break and return `Completed`.
   - HardFault detection: between chunks, check
     `emu.core(0).is_in_hardfault()` — a thin one-line wrapper
     to be added during step Final on `CortexM0Plus`:
     ```rust
     pub fn is_in_hardfault(&self) -> bool {
         (self.regs.xpsr & 0x1FF) == 3   // IPSR == HardFault exc #
     }
     ```
     On true, return `HardFault { pc: regs.pc(), ipsr: (xpsr &
     0x1FF) as u8 }`. (Inlining `(xpsr & 0x1FF) == 3` in the
     runner without the wrapper is also acceptable; the wrapper
     is preferred for naming clarity at no cost.)
   - If the cycle budget exhausts with no progress, return
     `Timeout`.

3. New file `crates/mdpicoem-harness/tests/isr_scenarios_rp2040
   _emu.rs` — invokes the helpers per scenario, matches on the

### 6.3 Regression budget

`paced_bench_rp2040 --workload basic` shows no measurable
regression vs the pre-change baseline. Apply the same noise-floor
escape clause as V5 Component 3: if cv ≥ 0.5%, the gate is a
no-op as long as the post-change p50 sits within ±5% of pre-change
p50.

### 6.4 Threaded-runtime coverage

Two layers:

1. **Direct unit test of the new mechanism** — `nvic_iser_through
   _workerbus_enables_in_per_worker_nvic` and `nvic_ispr_through_
   workerbus_pends_dispatchable_irq` (§5.1) cover per-core NVIC
   MMIO routing in `WorkerBus`. These are load-bearing because
   the existing dual-model parity tests don't exercise NVIC MMIO
   writes.

2. **End-to-end via existing parity** — `crates/mdrp2040/tests/
   dual_model.rs:444` (SIO FIFO IRQ parity) continues to pass,
   confirming the threaded barrier IRQ-drain mechanism is
   unchanged. (This test does *not* exercise the new NVIC MMIO
   path, hence layer 1.)

V1 does not add a new dual-model parity case for the ISR
scenarios — the §6.2 integration test runs `step_quantum=1`
serial mode, and adding a threaded variant would require
re-implementing the EMU-side runner against the `ThreadedEmu
lator` API for marginal new coverage.

## 7. Out of scope (V7 phasing)

- UART / SPI / I2C / ADC / PWM IRQ wiring — already plumbed via
  `tick_peripherals`; no V1 scenario covers them. V7 Phases 2–3.
- DMA IRQ_0 / IRQ_1 routing through `Bus::irq_pending`. V7 Phase 4.
- PIO IRQ routing. V7 Phase 1 mentions it but no oracle scenario
  exercises it.
- DWT CYCCNT modelling on M0+.
- Lazy-scheduled SysTick.
- Preemption of an active handler by a higher-priority pending
  exception. The tail-chain scenario does *not* require it
  (SysTick re-pending mid-PendSV-handler sits until handler
  returns, then dispatches via the post-`exit_exception` poll).
  Tracked in §9.2.
- M33-style per-core `irq_pending: [u32; 2]` with dual-clear.
- Symmetric multi-core SysTick. V1 ticks active-core only; see
  precondition in §5.2.

## 9. Risks and open questions

**9.1 SysTick CLKSOURCE simplification.** V1 ticks once per master
cycle for both `CLKSOURCE=0` and `CLKSOURCE=1`. Oracle uses
`CLKSOURCE=1` so this is exact. A future scenario relying on the
1-µs external tick will see a faster countdown on EMU than silicon
— file a `tech_debt.md` entry then.

**9.2 No-preemption rule and asymmetric multi-core SysTick.**
V1 follows the existing `maybe_dispatch_external_irq` behaviour
("never preempt any active handler"), and ticks SysTick on the
active core only. V1 oracle doesn't exercise either case; track
both in `tech_debt.md` after V1 lands so a future scenario doesn't
silently rely on the deferred behaviour.

**9.3 Scenario divergences not covered by V1.** When the silicon
session attaches and runs the oracle for real, the silicon side
may reveal observable differences (stacked LR encoding, IPSR low
bits, exact CYCCNT-mailbox value) that V1 doesn't cover. Treat
any new FAIL surfaced by silicon as a follow-up ticket, not a V1
regression.

**9.4 `step_quantum` boundary effects.** Oracle uses
`step_quantum=1`. The `dual_model.rs:444` parity test uses default
quantum (64); that test does not touch NVIC MMIO so the difference
doesn't expose anything. A future scenario combining
`step_quantum > 1` + threaded + NVIC MMIO writes may surface a
quantum-boundary IRQ-drain race; deferred until a concrete
reproducer.

**9.5 Image-base alignment.** Add a `const _: () = assert!(ISR_
IMAGE_BASE & 0x7F == 0);` at module scope in `crates/mdpicoem-
harness/src/lib.rs` next to the existing `ISR_IMAGE_BASE`
constant (currently `0x2000_2000` per `lib.rs:241`, which already
satisfies the assertion). Compile-time assert; no feature gate.
Independent of SysTick — lands as a one-line addition during the
"Final" step in §8.

**9.6 NVIC bits 26..31 — current behaviour and silicon parity.**
The existing emulator (`bus/mod.rs:1422-1439`) latches all 32 bits
of ISER/ICER/ISPR/ICPR — `n.enabled |= val` and `n.pending |= val`
have no mask, so a write of `0xFFFF_FFFF` to ISER0 latches all 32
enable bits. Only IPR (`:1448`) gates by `if irq < 32`, which on
M0+ is a no-op since the array is 32 wide anyway. The latched
high bits are **unobservable in normal operation** because no
peripheral source ever asserts those IRQs and no exception
vector slot exists for them — so they cannot dispatch through
the new `try_take_any_pending_exception`. V1 keeps this
behaviour. If `probe_diff_rp2040` later proves silicon RAZ/WI's
bits 26..31, the fix is a one-line `& 0x03FF_FFFF` mask in
`nvic_mmio_write32` (and the threaded sibling). Documented here
so a future probe-diff failure can be triaged quickly.

**9.7 Bootrom non-interaction.** RP2040 has no mask-ROM call
surface today (V5 Component 3's hook is RP2350-only). A
misdispatched IRQ landing on the test image's default-handler
slot (`bkpt #1` at offset `0x048`) halts the emulator on a
distinct halt reason — observable from `is_in_hardfault()` /
core debug state and reported via `EmuOutcome::HardFault` per
§6.2. No bootrom-hook interaction is possible.
