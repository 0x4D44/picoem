# Phase 4: Flash + Full Boot — Low-Level Design

Version: 0.2.1
Date: 2026-04-13
Parent: HLD Section 15, Phase 4
Depends: Phase 3 complete + TrustZone NS support (in progress)

## 1. Purpose

Load a Pico SDK application binary into flash. The bootrom discovers the
image via XIP reads, validates it (including software SHA-256), and jumps to
the application's entry point. The application reaches `main()`.

### Milestone

Integration test: load bootrom + Pico SDK blinky binary → bootrom finds valid
picobin image → SHA-256 validates → application reaches `main()` → GPIO 25 set.

### What exists today

| Component | Status | Gap for Phase 4 |
|-----------|--------|-----------------|
| Flash storage | `load_flash()` → `Vec<u8>` at 0x10000000 | Works as-is |
| XIP reads | Direct vec read, 1-cycle | Works as-is (no cache needed) |
| XIP SRAM | 16KB at 0x1C000000 | Works (bootrom populates it during secure phase) |
| QMI stub | Returns TXEMPTY+RXEMPTY | Needs register backing store |
| SIO | Returns 0 for all reads, ignores writes | **Needs GPIO registers** |
| IO_BANK0 / PADS | Not stubbed (HashMap fallback) | Need basic stubs |
| CLOCKS | Hardcoded `*_SELECTED=1` | Need dynamic source tracking |
| Bootrom | Runs full secure path → bxns | Needs TrustZone NS support |
| Flash images | Not tested | Need real Pico SDK binary |

### Key discovery from review: SHA-256 is software, not DCP

The bootrom validates flash images using software SHA-256 (`sb_sha256_init`/
`update`/`finish` at ROM addresses 0x454E/0x444C/0x44C6). This is pure
Thumb-2 code — our emulator executes it naturally. No DCP/coprocessor stub
is needed for hash validation.

**Consequence:** Flash images MUST contain valid SHA-256 hash blocks. The
bootrom will reject images with incorrect hashes. We need real Pico SDK-
compiled binaries, not hand-crafted test images.

### No boot2 on RP2350

The RP2040 had a 256-byte "boot2" second-stage bootloader at flash offset 0.
The RP2350 does NOT use boot2. It uses picobin IMAGE_DEF blocks directly.
The bootrom reads the picobin block at 0x10000000, validates, and jumps to
the image entry point. No intermediate bootloader stage.

## 2. Design

### 2.1. XIP reads — no changes needed

The bootrom's flash scan reads via XIP at 0x10000000+. Our existing path
(`memory.xip_read32(offset)` when `flash_loaded == true`) serves this
correctly. The bootrom configures QMI timing/mode registers before reading
XIP, but since our XIP path bypasses QMI entirely, those configurations
have no effect. This is by design — we model the result (correct data at
correct address) not the mechanism (QSPI bus transactions).

**Explicitly not implementing:** XIP cache, QMI-mediated reads, flash timing.
These are Phase 8 performance optimizations.

### 2.2. QMI register expansion

The bootrom writes many QMI registers during flash initialization. Our stub
must accept these writes without blocking. Add a register backing store.

```rust
pub struct Bus {
    // ... existing fields ...
    qmi_regs: [u32; 28],  // QMI register space: offsets 0x000-0x06C (through ATRANS7)
}
```

Register dispatch in `bus/peripherals.rs`:

```rust
pub(crate) fn qmi_read(&self, offset: u32) -> u32 {
    match offset {
        // DIRECT_CSR: always report ready
        0x000 => self.qmi_regs[0] | (1 << 16) | (1 << 17), // TXEMPTY + RXEMPTY
        // All others: return stored value
        _ if (offset >> 2) < 28 => self.qmi_regs[(offset >> 2) as usize],
        _ => 0,
    }
}

pub(crate) fn qmi_write(&mut self, offset: u32, val: u32) {
    if (offset >> 2) < 28 {
        self.qmi_regs[(offset >> 2) as usize] = val;
    }
}
```

Note: address 0x400D1000 is the XOR atomic alias of QMI base (0x400D0000),
not a separate chipselect register. The bus's existing alias stripping
(`addr & !0x3000`) handles it — no separate dispatch needed.

### 2.3. SIO GPIO registers

The SIO block at 0xD0000000 currently returns 0 for all reads and ignores all
writes. The Pico SDK's `gpio_put(25, 1)` writes to SIO GPIO_OUT. We need
minimal register backing.

New: `sio/mod.rs` expansion (or inline in bus dispatch):

```rust
pub struct Sio {
    pub spinlocks: [u32; 32],
    pub gpio_out: u32,      // 0x010: GPIO output value
    pub gpio_oe: u32,       // 0x024: GPIO output enable
    pub gpio_in: u32,       // 0x004: GPIO input (always 0, no external pins)
}
```

SIO register dispatch (bus region 0xD):

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x000 | CPUID | Return `core_id` (0 or 1) |
| 0x004 | GPIO_IN | Return 0 (no pins) |
| 0x010 | GPIO_OUT | Read/write gpio_out |
| 0x014 | GPIO_OUT_SET | Write: gpio_out |= val |
| 0x018 | GPIO_OUT_CLR | Write: gpio_out &= !val |
| 0x01C | GPIO_OUT_XOR | Write: gpio_out ^= val |
| 0x024 | GPIO_OE | Read/write gpio_oe |
| 0x028 | GPIO_OE_SET | Write: gpio_oe |= val |
| 0x02C | GPIO_OE_CLR | Write: gpio_oe &= !val |
| 0x030 | GPIO_OE_XOR | Write: gpio_oe ^= val |

The milestone test checks `sio.gpio_out & (1 << 25) != 0` after blinky runs.

### 2.4. CLOCKS stub expansion

The Pico SDK's `runtime_init` switches CLK_SYS source by writing
CLK_SYS_CTRL, then polling CLK_SYS_SELECTED for the new source bit. Our
hardcoded `0x1` return breaks this.

Fix: track the written CTRL value and reflect the selected source in the
SELECTED register.

```rust
pub(crate) fn clocks_read(&self, offset: u32) -> u32 {
    match offset {
        0x030 => self.clk_ref_ctrl,
        // CLK_REF_SELECTED: bit position = source from CTRL[1:0]
        0x038 => 1 << (self.clk_ref_ctrl & 0x3),
        0x060 => self.clk_sys_ctrl,
        // CLK_SYS_SELECTED: bit position = source from CTRL[0] (0=ref, 1=aux)
        0x068 => 1 << (self.clk_sys_ctrl & 0x1),
        _ => 0,
    }
}
```

Add `clk_ref_ctrl: u32` and `clk_sys_ctrl: u32` to Bus.

### 2.5. IO_BANK0 and PADS_BANK0 stubs

The Pico SDK's `gpio_init(25)` writes function select to IO_BANK0 at
0x40028000 and pad configuration to PADS_BANK0 at 0x4001C000. The existing
HashMap fallback handles writes (stores them) but reads return 0.

For Phase 4: the HashMap fallback is sufficient for IO_BANK0 and PADS. The
SDK writes config and moves on — it doesn't read back to verify for GPIO
init. If we later find it does, add explicit stubs then.

No changes needed — existing HashMap handles it.

### 2.6. Picobin image format

The bootrom scans flash at 0x10000000 for a picobin IMAGE_DEF block. The
magic value is `0xffffded3`. The picobin format is documented in the Pico
SDK (`pico-sdk/src/rp2_common/boot_picobin_headers/`).

For Phase 4, we load a real Pico SDK-compiled binary. The SDK toolchain
produces correctly-formatted picobin images with valid SHA-256 hashes. We
do NOT need to construct picobin headers manually.

### 2.7. Pre-validation: XIP SRAM content

After the secure boot phase (`bxns` at 0x7EA4), the bootrom has copied NS
code into XIP SRAM at 0x1C000000. Before proceeding with Phase 4 testing,
verify this content is valid:

```rust
// After bxns, check XIP SRAM contains executable code
let word0 = emu.bus.xip_sram_read32(0x1C00_0000);
assert!(word0 != 0, "XIP SRAM should be populated by secure bootrom");
```

If XIP SRAM is empty after the secure phase, the NS transition is broken
and Phase 4 cannot proceed (TrustZone blocker).

## 3. Staging

Two implementation stages. Investigation is a prereq, not a stage.

### Prereqs (can start now, before TrustZone)

1. Obtain a Pico SDK blinky binary compiled for RP2350. Either:
   - Compile from SDK source (`cmake` + `arm-none-eabi-gcc`)
   - Download a pre-built example from Pico examples repo
2. Verify the binary contains a valid picobin header at offset 0
3. Verify XIP SRAM content after bootrom secure phase

### Stage A: Peripheral expansion

- QMI register backing store (`qmi_regs: [u32; 24]`) with read/write dispatch
- SIO GPIO registers (gpio_out, gpio_oe, gpio_in, CPUID, set/clr/xor aliases)
- CLOCKS dynamic source tracking (clk_ref_ctrl, clk_sys_ctrl → *_SELECTED)
- Tests: QMI register round-trip, SIO GPIO write/read, CLOCKS source switch

### Stage B: Flash boot integration (requires TrustZone NS)

- Load bootrom + blinky binary
- Run full boot: secure init → NS → flash scan → SHA-256 → app launch
- Assert: GPIO 25 is set after blinky runs
- Debug any missing stubs iteratively (same approach as Phase 3)

## 5. Known Limitations

- **No XIP cache.** Direct flash reads. Phase 8.
- **No flash write/erase.** Read-only. Phase 6+.
- **No GDB RSP server.** Deferred.
- **QMI is a register store.** Accepts config writes but doesn't simulate QSPI.
- **SIO is minimal.** Only GPIO and CPUID. No divider, interpolator, FIFO.
- **IO_BANK0 via HashMap only.** No function-select enforcement.

## 6. Risk Assessment

**Low risk (changed from V1):** SHA-256 validation is software, not DCP. Our
emulator runs the SHA-256 code natively. As long as the flash image has valid
hashes (which SDK-compiled binaries do), validation will pass.

**Medium risk:** The application's `runtime_init` may touch peripherals we
haven't stubbed (TICKS at 0x40108000, WATCHDOG at 0x400D8000, ROSC at
0x40060000). These will be caught by the iterative debug approach used in
Phase 3. Each missing peripheral is ~10 lines of stub.

**Blocked on:** TrustZone NS support (another agent). Everything after `bxns`
requires NS execution.
