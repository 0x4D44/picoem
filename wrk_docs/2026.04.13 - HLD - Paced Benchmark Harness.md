# Paced Benchmark Harness

Version: 2.0.0
Date: 2026-04-13

## Problem

We have a Pacer but nobody has run it with a real workload. We don't know if
the emulator can sustain 150 MHz real-time.

## Solution

A new binary `paced_bench` in the test harness crate. It creates an Emulator,
loads a workload, runs it paced, and prints live stats to the terminal. One
file, ~80 lines.

Two prerequisite fixes in the emulator crate (discovered during design review):

1. **`CortexM33::halt()` uses `stall_cycles = u32::MAX`** — a time bomb that
   wakes the core after ~28.6 seconds at 150 MHz. Fix: add a proper `halted`
   flag to the core.
2. **`PacerStats::set_running()` is `pub(crate)`** — external crates (like the
   test harness) can't call it. Fix: make it `pub` (it's caller-managed by
   design, not an internal mutation method).

## Prerequisite 1: Fix CortexM33 halt

The current `halt()` sets `stall_cycles = u32::MAX`, which counts down on every
`step()`. After u32::MAX cycles (~28.6s at 150 MHz), the core wakes with
undefined register state and starts executing garbage. The stall_cycles field is
the wrong abstraction for "this core is powered off" — it's meant for
multi-cycle instructions.

**Fix:** Add a `halted: bool` field to `CortexM33`.

```rust
pub struct CortexM33 {
    // ... existing fields ...
    /// Core is halted — will not execute until explicitly woken.
    halted: bool,
}
```

**Changes to `step()`:**

```rust
pub fn step(&mut self, bus: &mut Bus) {
    if self.halted {
        return;  // Halted cores do nothing, indefinitely
    }
    if self.stall_cycles > 0 {
        self.stall_cycles -= 1;
        return;
    }
    // ... existing decode/execute/fault logic ...
}
```

**Changes to `halt()` and new `wake()`:**

```rust
pub fn halt(&mut self) {
    self.halted = true;
    self.stall_cycles = 0;  // Clear any pending stall — clean slate on wake
}

pub fn wake(&mut self) {
    self.halted = false;
}

pub fn is_halted(&self) -> bool {
    self.halted
}
```

**Initialisation:** `with_id()` sets `halted: false`. `Emulator::reset()` calls
`self.cores[1].halt()` (unchanged call site, new semantics).

**Test impact:** One test (`tests.rs:4735`) asserts
`assert_eq!(emu.cores[1].stall_cycles(), u32::MAX)` to verify halt. Update it
to `assert!(emu.cores[1].is_halted())`.

## Prerequisite 2: Fix set_running visibility

In `pacer.rs`, change `set_running` from `pub(crate)` to `pub` and remove the
`#[allow(dead_code)]` attribute. It is part of the monitoring API — callers
set it to signal lifecycle to monitoring consumers.

## How the benchmark works

```
main thread                    monitor thread
───────────                    ──────────────
create Emulator
create Pacer(150 MHz)
set up core 0 manually         receive Arc<PacerStats>
halt core 1
stats.set_running(true) ─────►
start timer ──────┐
                  │
loop {            │            loop {
  begin_quantum() │              sleep 1s
  emu.run(150)    │              read snapshot
  end_quantum()   │              print stats line
}                 │              if !is_running: break
                  │            }
after N seconds ──┘
stats.set_running(false)
join monitor thread
print summary
```

**Core 0 setup** (no bootrom needed — manual initialisation):

```rust
let mut emu = Emulator::new(Config::default());

// Write a tight loop into SRAM
emu.poke(0x20000000, 0x1C40_2001);  // MOVS R0, #0 | ADDS R0, R0, #1
emu.poke(0x20000004, 0x0000_E7FD);  // B .-4 (back to ADDS)

// Set up core 0 to run from SRAM
emu.core_mut(0).regs.set_pc(0x20000000);
emu.core_mut(0).regs.xpsr = 1 << 24;          // Thumb bit
emu.core_mut(0).regs.msp = 0x20080000;         // SP at top of SRAM
emu.core_mut(0).regs.r[13] = 0x20080000;

// Core 1: halted (now properly — boolean flag, not stall countdown)
emu.core_mut(1).halt();
```

**Workload:** A 2-instruction loop in SRAM (ADDS + B). This is the purest
throughput test: sustained instruction execution in zero-wait-state SRAM, no
peripheral access, no bus contention. It answers "can the interpreter keep up?"
before we add complexity.

## Output

Live stats printed every second:

```
mdrp2354 paced benchmark — target 150 MHz, quantum 150 cycles
TSC calibrated: 4987 MHz

  time   emu_cycles    emu_MHz   util%   headroom%   behind
     1   150000000      150.0    12.3%      87.7%        0
     2   300000000      150.0    12.1%      87.9%        0
     3   450000000      150.0    12.2%      87.8%        0
  ...
```

At exit, print summary:

```
--- summary ---
Duration:       5.0 s
Total cycles:   750000000
Avg MHz:        150.0
Avg util:       12.2%
Behind count:   0
Verdict:        REAL-TIME OK (87.8% headroom)
```

The "verdict" is simple: if behind_count is 0 and utilization < 100%, we can
do real-time. The utilization number tells us how much budget remains for
peripherals, bus contention, and core 1.

## CLI

```bash
# Default: 5 seconds
cargo run -p mdrp2354-test-harness --release --bin paced_bench

# Custom duration
cargo run -p mdrp2354-test-harness --release --bin paced_bench -- --seconds 30

# Custom quantum size
cargo run -p mdrp2354-test-harness --release --bin paced_bench -- --quantum 15
```

Three args, all optional: `--seconds N`, `--quantum N`, `--clock-mhz N`
(default 5, 150, 150).

## What this does NOT do

- No bootrom or flash loading (pure SRAM loop)
- No profiling (flamegraph, perf) — just the Pacer's own stats
- No thread affinity — add later if numbers look noisy
- No CSV/JSON export — terminal output is enough to answer the question
