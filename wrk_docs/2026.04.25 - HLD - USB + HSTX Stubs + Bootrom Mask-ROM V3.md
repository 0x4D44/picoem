# 2026.04.25 — HLD — USB + HSTX Stubs + Bootrom Mask-ROM (V3)

Iterates V2 (`2026.04.25 - HLD - USB + HSTX Stubs + Bootrom Mask-ROM V2.md`)
on a second review pass. Material changes flagged inline as **(R3)**.

## Goal

Close three remaining RP2350 firmware-fidelity gaps so that pico-sdk
firmware touching USB init, HSTX config, or bootrom service functions
executes to steady state in the emulator without faulting.

1. **USB** — register-surface stub (no protocol).
2. **HSTX** — register-surface stub (no pixel stream).
3. **Bootrom mask-ROM** — `rom_table_lookup_entry_point`-resolved calls
   run their documented semantics by executing the real RP2354 bootrom
   binary plus a small PC-hook for the few functions whose dependencies
   we don't emulate.

**Workload value** is uneven across the three:

- Component 3 (bootrom) is high-value: any pico-sdk firmware that calls
  `flash_range_program`, `connect_internal_flash`, or `reboot` blocks
  on this. OneROM and any future RP2350 firmware that touches flash
  fall in scope. (Note: PicoGUS is RP2040 only, not an RP2350 driver.)
- Components 1 and 2 (USB/HSTX) are pre-emptive insurance: no current
  RP2350 workload in-tree is blocked by them. **(R3) Defer threshold**:
  if Stage 0 discovery reveals either component would take >50% above
  the line estimate (USB ≥375 lines, HSTX ≥120 lines), defer it to its
  own future HLD when a real workload requests it. This is the explicit
  YAGNI escape hatch.

Success criterion per component is "firmware exercising this subsystem's
init runs without asserting or entering a fault loop," measured by the
firmware tests listed in each Oracle section.

## Explicit non-goals

- USB protocol emulation, host mode, device enumeration, CDC passthrough.
- HSTX pixel-stream observability, DVI/DPI capture.
- BOOTSEL UF2 drive emulation — `reboot` with BOOTSEL flag shuts the
  emulator down cleanly; UF2 ingest stays out of scope.
- Secure-boot verification through the bootrom path.
- RISC-V Hazard3 bootrom path. The design must not regress Hazard3
  execution — see "Hazard3 isolation" in Component 3.

No feature flags. No environment variables. No migration / back-compat.
The two new peripherals and the bootrom hook land directly in
`mdrp2350`.

## Stage 0 — Survey (cheap, do first; no code lands until it completes)

Stage 0 is the design's branch point. Five facts must be confirmed,
each recorded in the implementation journal with the exact answer and
evidence.

**(R3) Sign-off enforcement.** Stage 0 sign-off is a **commit-message
trailer convention**, not CI. Every commit landing Component 1, 2, or 3
code must include:

```
Stage-0-journal: wrk_journals/2026.MM.DD - JRN - V3 Stage 0 Survey.md
```

Reviewers (human or agent) reject Component-1/2/3 commits without the
trailer. Soft norm, but visible at review time.

### Fact 1 — bootrom binary layout

`roms/rp2350/bootrom-combined.bin` is exactly 32 KB.
`mdpicoem-common::memory::ROM_SIZE` is also 32 KB. Required:

- Hex-dump the file. Where does the Arm bootrom image start and end?
  `arm-bootrom.dis` shows Arm Thumb code at offset 0; is the back half
  Arm Secure-only, RISC-V (Hazard3 boot path), or padding?
- If real silicon expects more than 32 KB of bootrom space, hook
  resolution lands on bytes we never loaded. Confirm whether the loaded
  32 KB is the complete Arm image or only one half of a dual-arch
  concatenation.

**(R3) Pinned fallback (no enumeration):** if Fact 1 reveals the
loaded 32 KB is incomplete, bump RP2350's ROM_SIZE via
`Memory::with_sizes(rom, sram)` (already per-chip; see
`mdpicoem-common::memory`). Do **not** downscope Component 3 — bootrom
truncation is itself a fidelity bug worth fixing on its own merits.
Update the journal with the new ROM_SIZE value and the bytes added.

### Fact 2 — bootrom executes through `rom_table_lookup`

Pico-sdk's table-walk entry point is `rom_table_lookup_entry_point`
(the well-known pointer table sits at the top of bootrom). Stage 0
must answer:

- Run a minimal RP2350 firmware that invokes
  `rom_table_lookup_entry_point` with a known 4-char code. Does it
  return cleanly?
- The bootrom's table-walk uses `rcp_count_set` (RCP coprocessor
  canary) at bootrom address 0x4c (`arm-bootrom.dis:90`). Verify our
  RCP semantics tolerate this.
- **End-to-end smoke**: invoke `flash_range_program` of a tiny pattern
  through the bootrom and verify the flash backing-store actually
  changes. Catalogue-only is not enough — the bootrom drives QMI, OTP,
  TRNG, SHA256 along the way, and any of those can hang or fault even
  when dispatch is clean.

**(R3) Integration-test pre-condition**: the `flash_range_program`
smoke must pre-erase the target region (`flash_range_erase` first) or
start from an all-`0xFF` flash image. Real silicon flash requires
erase-before-program at sector granularity; a write-without-erase test
will diverge from real bootrom behaviour for reasons unrelated to our
emulator.

### Fact 3 — pinned register maps

From RP2350 datasheet §Appendix A:

- USB control: `USBCTRL_REGS_BASE = 0x5011_0000` (16 KB region).
- USB DPRAM: `USBCTRL_DPRAM_BASE = 0x5010_0000`, exactly 4096 bytes
  (`0x1000`). Structured: 0x000..0x180 = buffer-control + setup-packet
  area, 0x180..0xFFF = endpoint data buffers.
- HSTX control: `HSTX_CTRL_BASE` on **APB** — value **TBD via
  datasheet §Appendix A**. **(R3) Do not pre-commit a literal here**;
  V2 had `0x400C_0000` which is TICKS/WATCHDOG territory. Likely
  answer is `0x400C_C000`; confirm before Component 2 lands.
- HSTX FIFO: `HSTX_FIFO_BASE` on **AHB-Lite** at `0x5060_0000`,
  separate fabric.

The APB-vs-AHB split for HSTX is load-bearing. Confusing the two
silently routes FIFO writes to APB and faults.

### Fact 4 — current bus-fault semantics on the new regions

**(R3) Corrected rationale.** The `Bus::read32`/`write32` fall-through
for region `0x5*` does NOT bus-fault — `bus/mod.rs:2722-2725` routes
unmodelled accesses through `warn_unmodelled_mmio` +
`peripheral_regs` HashMap, returning 0. Adding stubs converts a
warn-once HashMap noop into defined behaviour. The risk is not that
firmware tests assert HardFault; the risk is that **tests reading from
`0x501x_*` / `0x506x_*` / `0x400C_x*` and asserting they return 0**
will see real stub state instead. Stage 0 grep:

```
grep -nr "0x501[01]_" crates/mdrp2350/src/tests.rs
grep -nr "0x5060_" crates/mdrp2350/src/tests.rs
grep -nr "0x400[cC]_" crates/mdrp2350/src/tests.rs
grep -nr "0x501[01]_" crates/mdrp2350/src/threaded/
grep -nr "0x5060_" crates/mdrp2350/src/threaded/
```

(Threaded subtree included — V2 review noted threaded/bus.rs has a
"legacy AHB unmapped" round-trip test at `0x5060_0000` near line 2086.)

Any test that reads these regions and asserts `== 0` is direct prior
art that the stub will break — list them, decide whether to delete or
rewrite. Most likely outcome: zero tests in scope. But the design must
have looked.

### Fact 5 — RESETS_POST_BOOTROM state and W1C bit list

`RESETS_POST_BOOTROM` at `bus/mod.rs:224` records which peripherals are
held in reset *after* emulator boot. Confirm USBCTRL is in that set on
real silicon. The new USB stub must initialise behind that gate —
reads should return 0 via the existing `is_held_in_reset_base` guard
until firmware writes a 1 to `RESETS_RESET_CLR.USBCTRL`. Same for HSTX.

**(R3) W1C bit list verification.** Component 1 declares W1C semantics
for `SIE_STATUS` bits. Stage 0 must record the exact source:

- Source-of-truth: pico-sdk `hardware/regs/usb.h` (or RP2350 datasheet
  §12.6.5).
- Journal entry: paste the W1C bit positions verbatim with file path
  and line numbers.
- Component 1's docblock cites this journal entry.

### Stage 0 failure modes

Each fact has a defined fallback if it fails:

- **Fact 1 fails** (bootrom truncated by ROM_SIZE): bump
  RP2350-specific ROM_SIZE via `Memory::with_sizes`. Component 3
  proceeds with the larger ROM.
- **Fact 2 fails** (bootrom faults inside its own code): catalogue
  which peripheral access faults. If it's QMI/OTP/TRNG/SHA256, fix the
  peripheral first (separate HLD); Component 3 blocks on it.
- **Fact 3 fails** (no public datasheet base): defer the affected
  stub.
- **Fact 4 fails** (existing tests assert `== 0` on these regions):
  rewrite or delete them; record the choice in the journal.
- **Fact 5 fails** (USBCTRL not in `RESETS_POST_BOOTROM`): adjust the
  RESETS table — fixing this is also a real bug in current emulator
  fidelity, fix it independently.

Stage 0 outputs: one journal entry per fact, with answers. **No code
commits land in Components 1, 2, or 3 until Stage 0 is signed off** (per
trailer convention above).

## Component 1 — USB stub

### Scope

- `USBCTRL_REGS_BASE` at `0x5011_0000` — control/status registers.
- `USBCTRL_DPRAM_BASE` at `0x5010_0000`, 4096 bytes plain RAM. Stored
  as a `Box<[u8; 4096]>` field on the new `UsbCtrl` struct; not shared
  with the main `Memory`. **(R3) Reset behaviour**: this is a stub
  policy, not a silicon claim — we clear `0x000..0x180` (buffer-control
  region) on reset to satisfy pico-sdk's expected read-back; the data
  region (`0x180..0xFFF`) is left as last written, since real silicon
  DPRAM contents are unspecified post-reset.
- All control register writes accepted (default last-write-wins).

**W1C status registers** (writes-1-to-clear, not last-write-wins):
`SIE_STATUS` and any other "interrupt status" register where pico-sdk
writes 1 to acknowledge events. Implementation: writes mask out the
W1C bits, reads always return 0 for those bits in this stub. **(R3)
The exact W1C bit list is per Stage 0 Fact 5** — pinned in the
docblock with cite.

- Static "no device": `VBUS_DETECTED`, `BUS_RESET`, `TRANS_COMPLETE`,
  `CONNECTED`, `SUSPENDED`, `RESUME` all read 0.
- `BUFFER_STATUS = 0`. `INTS = 0`, `INTR = 0`.
- NVIC IRQ_USBCTRL_IRQ (line 14, `irq.rs:61`) never asserts. Pico-sdk
  device-mode init is safe with this; host-mode init *will* hang
  (declared in Risks).

### Bus integration

The new module must wire five points, not "one match arm":

1. New base const + match arms in `Bus::read32` / `write32` for both
   `0x5010_*` (DPRAM) and `0x5011_*` (regs). The new arms replace the
   `warn_unmodelled_mmio` + HashMap fall-through at
   `bus/mod.rs:2722-2725` for these specific bases.
2. Entry in `reset_bit_for_base` (`bus/mod.rs:255`) for both bases →
   `RESET_USBCTRL` (already declared, line 214).
3. `usbctrl: UsbCtrl` field on `Bus`; construction in `Bus::new`.
4. Narrow-access policy: registers are word-only. DPRAM allows
   byte/halfword (real silicon does). Add to the bus carve-outs at
   `bus/mod.rs:1647-1706`.
5. RESETS_POST_BOOTROM table includes USBCTRL (Stage 0 Fact 5
   confirms).

### Function shape

Per `peripherals/mod.rs:1-23` and `peripherals/uart.rs:339,373,491`:
inherent methods, no trait. Pinned signatures:

```rust
impl UsbCtrl {
    pub fn new() -> Self;
    pub fn reset(&mut self);
    pub fn read32(&mut self, offset: u32) -> u32;
    pub fn write32(&mut self, offset: u32, value: u32, alias: u32, irqs: &mut u64);
    pub fn read_dpram(&self, offset: u32, size: u8) -> u32;
    pub fn write_dpram(&mut self, offset: u32, value: u32, size: u8);
}
```

No `tick` — the stub never produces events. `irqs: &mut u64` is the
out-mask convention for IRQ assertion (UART pattern); USB stub never
sets a bit.

### Oracle

- **Unit tests** in the module:
  - pico-sdk USB init sequence (writes to `USB_MUXING`, `USB_PWR`,
    `MAIN_CTRL`, `SIE_CTRL`) followed by `SIE_STATUS` read returns
    `VBUS_DETECTED=0`. No bus fault.
  - W1C round-trip: write 1 to a W1C bit, read back — must return 0.
  - DPRAM word/byte/halfword writes round-trip in the data-buffer
    region; reset clears only buffer-control area (per stub policy
    above).
  - IRQ_USBCTRL_IRQ stays low across full init.
- No silicon scenario unless a stub-drift bug surfaces later.

**(R3) Estimate revised**: ~200-250 lines including W1C handling,
DPRAM, and tests. (V2 said 150; CA review pointed out that even with
inert.rs-style HashMap base, the W1C plus DPRAM byte/halfword carve-out
adds shape. If discovery shows >375 lines, defer per the threshold in
"Workload value" above.)

## Component 2 — HSTX stub

### Scope

- Two MMIO regions (Stage 0 Fact 3):
  - `HSTX_CTRL_BASE` on APB — lane config, FIFO-status, enable bit.
  - `HSTX_FIFO_BASE` on AHB at `0x5060_0000` — write-only FIFO port.
- Implementation pattern: follow `peripherals/inert.rs` —
  `HashMap<u32, u32>` for stored values plus a small `match offset` on
  reads to override status fields.
- Control writes accepted, last-write-wins. FIFO writes silently
  consumed (no queue, no backpressure, stays empty).
- FIFO status: `FIFO_EMPTY=1`, `FIFO_FULL=0`, `FIFO_LEVEL=0` static.
  Risk: firmware that polls `FIFO_LEVEL > 0` (self-test pattern) will
  hang. Documented in Risks; no in-tree RP2350 firmware does this.
- Stub does **not** consume `CLK_HSTX` despite the clock being modelled
  on the CLOCKS side. No timing coupling.
- Participates in RESETS (`RESET_HSTX = 3`, `bus/mod.rs:171`); same
  five-point bus integration as Component 1.

### Function shape

Same convention as Component 1 — inherent methods, no trait.

### Oracle

- Unit test: pico-sdk HSTX init sequence (lane map writes, `EXPAND_*`,
  `CTRL.EN=1`, then 1024 FIFO words). Asserts: no fault, FIFO status
  reports empty, no IRQ.
- No silicon scenario.

Estimate: ~80 lines. Defer-threshold ~120 lines per "Workload value."

## Component 3 — Bootrom mask-ROM

### Approach

**Default path**: execute the real RP2354 bootrom binary
(`roms/rp2350/bootrom-combined.bin`) from ROM memory. Firmware's
`rom_table_lookup_entry_point` walks the real `rom_func_table` and
dispatches into real bootrom code.

Functions touching only-emulated peripherals (SHA256, TRNG, XIP_CTRL,
QMI, DMA, OTP) execute verbatim — the bootrom is the implementation.
Conditional on Stage 0 Fact 2 end-to-end smoke: if the bootrom hangs
or faults inside QMI/OTP/TRNG/SHA256 paths, those peripherals need
fixing first; Component 3 blocks on them.

**Single PC hook, inlined.** No `BootromHookTable` struct. The minimum
hook set after Stage 3.1 is expected to be one entry: the BOOTSEL
flavour of `reboot` (4-char code expected `'RB'`; **(R3) Stage 3.1
confirms** — V2 asserted this as fact, but pico-sdk source is the
authoritative reference).

### **(R3) Hook PC field ownership and Secure/Non-Secure aliasing**

**Where the field lives.** Two `u32` fields on `Emulator`:

```rust
pub struct Emulator {
    // ...
    bootrom_reboot_hook_pc_s: Option<u32>,   // Secure alias
    bootrom_reboot_hook_pc_ns: Option<u32>,  // Non-Secure alias (= S + 0x8000)
}
```

`Emulator::load_bootrom` resolves both. The threaded runtime exposes
them to worker cores by snapshot at quantum boundary — workers do not
see in-flight changes mid-quantum. Soft-reboot (a reload of bootrom
mid-run) goes through the existing `Emulator::load_bootrom` path,
which the threaded scheduler already serialises against worker
quanta.

**Why two PCs.** RP2350 IDAU treats `0x0000_8000..0x0000_FFFF` as the
Non-Secure ROM alias of `0x0000_0000..0x0000_7FFF` (cf.
`crates/mdrp2350/src/core/exceptions.rs:837`). NS firmware fetches the
bootrom at `+0x8000`. A bare `pc == hook_pc_s` equality check silently
misses NS callers. Storing two PCs is cleaner than a mask-and-compare
(which would also match non-bootrom addresses sharing the low 15 bits).

### **(R3) Hook check placement**

`crates/mdrp2350/src/core/mod.rs:383-422` shows `step()` flow:
WFE/halt checks → `take_irq_pending` → `try_take_any_pending_exception`
→ `decode_execute`. The hook check goes **immediately before
`decode_execute`**, NOT at step entry. Placing it at step entry would
swallow pending exception entries on the cycle before fetch.

Pseudo-code at the point of insertion:

```rust
// crates/mdrp2350/src/core/mod.rs — both step() and step_no_atomics()
// at the line just before `self.decode_execute(...)`:
if Some(self.pc) == self.emulator_hooks.reboot_pc_s
    || Some(self.pc) == self.emulator_hooks.reboot_pc_ns {
    self.emulator_hooks.shutdown_requested = true;
    return Ok(StepOutcome::Halted);
}
```

The check fires from all three step entry points: `step` (line 383),
`step_no_atomics` (line 486), `debug_step` (line 460). The
`emulator_hooks` snapshot is propagated to each `CortexM33` at
construction and refreshed by `Emulator::load_bootrom`.

### **(R3) Hot-path cost gate**

Before Component 3 merge, run `paced_bench_rp2350` with this protocol:

- 5 runs each of `pre` and `post` (the merge baseline and the
  hook-armed branch).
- 30-second warm-up per run, then a 60-second measurement window.
- Compare median throughput.
- Budget: `median(post) / median(pre) < 1.005` (i.e. ≤0.5%
  regression).

The 1% V2 budget was meaningless without specifying jitter handling;
the overnight fuzz journal (`wrk_journals/2026.04.20`) shows
single-digit-percent run-to-run jitter. Median-over-5 with warm-up
should distinguish a real branch cost from noise.

### **(R3) Hazard3 isolation**

The hook check fires only from `CortexM33::step` paths. Hazard3's
`core_riscv` step path does not check hook PCs. A Hazard3 fetch into
the bootrom address range will execute Arm bootrom bytes as RV
instructions and fault — this is acceptable as a documented
limitation, not a regression (Hazard3 has its own bootrom path that
this HLD defers). Filed as Risk.

### Soft-reboot / reload

Hook resolution recomputes on every `Emulator::load_bootrom` call
(`lib.rs:478`). If firmware reboots and the host reloads bootrom
bytes, the hook PCs are rebuilt. **Note**: a future serialize/restore
path that skips `load_bootrom` and rehydrates ROM bytes directly into
`Memory` would leave hook PCs stale. No such path exists today; if one
is added, that HLD must call into `resolve_rom_func` explicitly.

### Stage 3.1 — Survey

Run available RP2350 firmware (OneROM family + any future
bootrom-using smoke tests) with a PC trace scoped to the ROM range.
For each call into ROM:

- Record the 4-char code (read from R0/R1 at
  `rom_table_lookup_entry_point`).
- Record whether the call returns cleanly, hangs, or faults.
- Catalogue grouped by category: "needs hook" (semantics depend on
  peripherals we don't have), "needs peripheral fix" (faults inside an
  emulated peripheral), "works" (no action).

Output: journal entry with the catalogue. Drives Stage 3.2 scope.

### Stage 3.2 — Inline hook

Land the hook check at the placement defined above. Implementation
files:

- `crates/mdrp2350/src/bootrom_hooks.rs` — NEW. Two functions:
  `resolve_rom_func(bootrom: &[u8], code: &[u8; 4]) -> Option<u32>`
  and the `Emulator::resolve_bootrom_hooks(...)` that populates both
  S and NS PCs.
- One PC-equality check inserted in three step entry points (file:line
  pinned above).
- `Emulator::load_bootrom` adds a call to `resolve_bootrom_hooks`.

### **(R3) SHA256 pin on the bootrom binary**

Pin lives at the **harness/app layer**, not in `Emulator::load_bootrom`.
Reason: 21 existing unit tests pass synthetic ROMs through
`load_bootrom`; an unconditional assert breaks all of them.

Concrete shape:

- `roms/rp2350/bootrom-combined.bin.sha256` — sibling file, holds the
  hex digest of the pinned silicon bootrom binary.
- `mdpicoem-harness::load_pinned_bootrom() -> Vec<u8>` — helper that
  reads `bootrom-combined.bin`, computes SHA256, asserts equality with
  the `.sha256` file, returns the bytes. Callers
  (`probe_diff_rp2350`, `silicon_*` oracles, OneROM runners) use this
  helper.
- Synthetic-ROM unit tests in `mdrp2350` continue calling
  `Emulator::load_bootrom` directly with hand-crafted bytes — no
  assert in their path.

Producer of the `.sha256` file: a one-line `sha256sum
roms/rp2350/bootrom-combined.bin > roms/rp2350/bootrom-combined.bin.sha256`
command, run when the bootrom binary is intentionally refreshed. This
is a manual step; if it grows to >1 binary, write a script.

### **(R3) Decision criterion for hooks 2..N**

Each new hook beyond `reboot` requires a journal entry stating:

1. The 4-char code and what the function does.
2. Why a hook is preferable to fixing the underlying peripheral —
   specifically, the smallest peripheral change that would let the
   real bootrom function run, and why we're not doing that.

A hook commit without (1) and (2) is reverted on review. The five-hook
ceiling is unchanged; the criterion is what fills the budget honestly.

### Oracle

- **Unit test**: load bootrom, call `rom_table_lookup_entry_point('FC')`
  from a tiny ARM image, jump to returned PC, assert clean return and
  expected QMI/XIP_CTRL state. (Implicitly tests Stage 0 Fact 2.)
- **Integration test**: ARM firmware that calls `flash_range_program`
  with a 16-byte pattern at a pre-erased flash offset. Verifies flash
  backing matches the pattern after the call returns.
- **`reboot` hook test**: ARM firmware that calls `reboot` with the
  BOOTSEL flag; emulator's `shutdown_requested` becomes true.

### Done condition

- All Stage 3.1 catalogue entries are in one of the three categories
  with a recorded resolution.
- Hot-path microbench within budget per the protocol above.
- The integration test (`flash_range_program`) and the `reboot` test
  pass.

If Stage 3.1 reveals a function in "needs peripheral fix" category,
that function does NOT block Component 3 closure — it spawns a new HLD
for the peripheral fix. Component 3 closes with a list of outstanding
peripheral-fix HLDs in the journal.

## Risks (consolidated)

- **Stage 0 might reveal the bootrom binary is incomplete.** If the
  loaded 32 KB is half of a 64 KB image, every hook PC is wrong.
  Mitigation: Stage 0 Fact 1 + pinned ROM_SIZE bump fallback.
- **Bootrom faults inside QMI/OTP/TRNG/SHA256 under its own call
  patterns.** Our peripheral models pass register-level tests but
  might not survive the bootrom's exact polling sequences. Mitigation:
  Stage 0 Fact 2 end-to-end smoke is mandatory before 3.2.
- **RCP coprocessor state on bootrom entry** — `rcp_count_set` at
  bootrom 0x4c is on the table-walk hot path; if our RCP model rejects
  the state, every lookup faults. Mitigation: Stage 0 Fact 2.
- **Bootrom version drift** — pin SHA256 in `roms/rp2350/`; any
  refresh is an explicit commit pair (binary + .sha256).
- **Hot-path regression from hook check** — gated by paced_bench
  protocol (5 runs, median, ≤0.5%).
- **Permanently-low USBCTRL IRQ** — safe for device-mode init only;
  host-mode init blocks on `BUS_RESET`. Documented in module docblock.
- **HSTX FIFO_LEVEL=0 forever** — firmware that polls for `LEVEL > 0`
  hangs. Documented; no in-tree RP2350 firmware does this today.
- **(R3) Hazard3 fetching Arm hook PC** — Hazard3 will execute Arm
  bootrom bytes as RV instructions and fault. Documented as a
  limitation of the V3-deferred RV bootrom path; not a regression.
- **(R3) Adding USB/HSTX stubs replaces a warn-once HashMap noop with
  defined behaviour.** Tests reading these regions and asserting `==
  0` will see real stub state. Stage 0 Fact 4 grep catches them.
