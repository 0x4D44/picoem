# HLD: Paced Bench Workload Spread

**Date:** 2026-04-15
**Status:** Draft v1.1.0
**Scope:** `crates/mdpicoem-harness/src/bin/paced_bench_rp2040.rs` and
`paced_bench_rp2350.rs`

## Context

`paced_bench_rp2040` and `paced_bench_rp2350` today each measure a
single cheap workload: a two-instruction ALU loop in striped SRAM.
For RP2040 the headline numbers from the recent quantum work
(210.9 MHz unpaced, 119.7 MHz paced at the 125 MHz target) come from
this workload, single-core, with peripherals quiescent.

That is the floor of the cost envelope, not the middle:

- **Peripherals are idle.** No PIO program runs, so the per-quantum
  `PioBlock::execute_cycle` short-circuits. No SIO traffic (FIFO,
  divider, interpolators). No GPIO toggling. No interrupts.
- **No bank contention.** One core, one striped bank. When RP2040
  `--dual-core` is used today, core 1 is deliberately placed in SRAM5
  scratch to *avoid* contention with core 0's striped accesses.
- **No dispatch diversity.** One ADD and one B every loop. The decoded-
  op cache on RP2350 (and any future cache on RP2040) sees 100% hit on
  two PCs.

Real firmware running close to the target clock will typically have
both cores active, at least one PIO SM executing, and occasional
same-bank access patterns. A regression in any of those axes is
invisible to the current bench.

## Goal

Extend each bench with a small set of named workloads that span the
cost envelope from floor to realistic worst case, so a single
`paced_bench_*` invocation per chip can reveal regressions on any of
the axes above.

## Non-goals

- **No workload DSL or config file.** Workloads are hard-coded
  in the benchmark binary, one match arm each.
- **No representative firmware images.** Those belong to full-system
  oracles (`onerom_full_system_rp2350`, `picogus_diff_rp2040`); the
  bench stays synthetic and deterministic.
- **No regression-gate thresholds.** The bench reports numbers; any
  pass/fail gate lives in a future HLD.
- **No attempt to cover every peripheral.** PIO + SIO covers the two
  hot paths that currently tick every quantum. DMA, timers, etc. are
  not yet wired to the quantum tick path and adding them is out of
  scope.

## Workloads

Four workloads on RP2040, five on RP2350 (inherits `fpu-heavy`).
Each is a single fixed configuration — no orthogonal flags stack on
top. `--dual-core` is **removed**; core count is a property of the
workload.

### `basic` — ALU floor (1 core)

Current workload, unchanged. Core 0 in striped SRAM bank 0 running
`MOVS / ADDS / B .-2`. No peripheral activity, no contention. This
is the baseline against which every other workload is compared.

### `peripheral` — peripherals active (1 core)

Core 0 in striped SRAM running an ALU+store loop **plus**:

- **PIO0 SM0 running** a two-instruction wrap loop:
  `set pins, 1 / set pins, 0` (`.wrap`). Keeps
  `PioBlock::execute_cycle` on the hot path — no idle-skip. CLKDIV = 1
  (one SM cycle per sys_clk cycle).
- **Core 0 inner loop toggles GPIO** via SIO `GPIO_OUT_XOR` writes.
  Exercises the SIO register path on every iteration.

Core 0 loop shape (hand-coded halfwords, literal pool for the SIO
address):

```
    LDR  R2, [PC, #lit_off]   ; SIO_GPIO_OUT_XOR address (once)
    MOVS R1, #1               ; pin mask (once)
loop:
    ADDS R0, R0, #1           ; ALU
    STR  R1, [R2]             ; SIO GPIO toggle
    B    loop
```

Three instructions per iteration: ALU, SIO store, branch. Keeps real
compute in the loop (unlike a pure STR+B) so the signal isolates
peripheral-path cost on top of ALU work, not replacement of it.

Isolates per-quantum peripheral-tick cost. Expected to drop from
`basic` because `PioBlock::execute_cycle` now does real work each
call and every GPIO toggle hits SIO.

### `contention` — bank contention (2 cores)

Both cores run the ALU loop in **striped SRAM bank 0**. RP2040
striped SRAM is word-interleaved across banks 0-3, so addresses
chosen to all land in bank 0 must be a multiple of 16 bytes apart:
core 0 at `0x2000_0000`, core 1 at `0x2000_0040` (16 words = 64
bytes apart; both are bank 0). Stacks live in **scratch SRAM5** on
RP2040 (or non-striped banks 8-9 on RP2350), keeping push/pop
traffic out of the fetch-contention signal. Core 1 is woken
directly.

Isolates dual-core cost with contention active: when both cores'
fetches hit the same bank on the same cycle, core 1's access pays
+1 cycle. Because a 3-instruction loop (`ADDS / B`, 6 bytes) spans
two words in two different banks, contention fires on roughly half
the cycles, not every cycle.

**Throughput interpretation (important).** The +1 contention cycle
is a counter increment on the emulator's cycle count; host compute
for that cycle is near-zero (both cores still execute their next
instruction on the following step). So `contention` will report
**higher MHz than a non-contended 2-core baseline would** — virtual
stall cycles inflate the numerator of cycles/sec without consuming
host time. This is correct behaviour, not a bug. Expected ordering
on unpaced MHz: `basic` highest (single-core throughput);
`contention` below `basic` (dual-core host compute roughly doubles
per master cycle) but above what a pure 2× scaling from `basic`
would predict.

The user-facing regression signal is the **paced verdict**, not raw
MHz.

**Chip asymmetry.** Bank contention is modelled *only* on the RP2040
in the production hot path. `crates/mdrp2040/src/lib.rs::step`
interleaves core 0 and core 1 per-instruction with
`contention_check_active` wired up (+1 cycle on same-port access).
`crates/mdrp2350/src/lib.rs::step` runs the two cores **sequentially**
— core 0 drains its quantum first, then core 1 drains its own — with
no cross-core contention hooks in the production path (the
`Bus::arbitrate_pair` primitive exists but is called only from unit
tests). Consequently, on RP2350 the `contention` workload measures
**dual-core compute cost only**, with no bank-contention accounting;
the MHz drops to ~0.5× `basic` because the host pays for twice the
instruction stream with no virtual stall cycles to inflate the
numerator. The workload name is kept for CLI symmetry with RP2040,
and to give a dual-core-compute baseline that future contention
hooks can be measured against. See "Out of scope" for the follow-up
work needed to bring RP2350 to parity.

### `stress` — composite realistic worst case (2 cores)

Combines `peripheral` and `contention`; stacks in scratch. PIO0
SM0 runs the wrap loop. Per-core layout on RP2040 (chosen so core 1's
fetches collide with core 0's hot path):

- **Core 0** at `0x2000_0000` runs the `peripheral` loop shape
  (`ADDS / STR [SIO_GPIO_OUT_XOR] / B`). Three-halfword loop. The
  hot path lives in word 1 (bank 1 — `ADDS@0x4`, `STR@0x6`) and
  word 2 (bank 2 — `B@0x8`); the prologue (word 0) and the SIO
  literal (word 3) run once each.
- **Core 1** at `0x2000_0044` runs the `basic` ALU loop shape
  (`MOVS / ADDS / B`). Two-halfword loop. Placed at word 17
  (bank 1 — `ADDS@0x46`) / word 18 (bank 2 — `B@0x48`) so core 1's
  steady-state fetches land on core 0's banks 1 and 2, triggering
  the `+1` contention cycle on overlapping fetches.

Why asymmetric: we want SIO traffic to fire (only one core needs to
drive it) while both cores contend on the fetch bank. Making both
cores toggle GPIO would serialise on the SIO path and hide the
contention signal.

This is the "both cores active and peripherals singing" case from
the motivation. It is not a pure-axis measurement — a regression
here could be contention, peripheral, or the interaction — but it
is the one number that reflects how close to the cliff we are for
realistic firmware.

**Chip asymmetry (same note as `contention`).** On RP2040 the
`stress` workload really exercises same-bank fetch contention in
addition to dual-core + peripheral cost. On RP2350, with cores
serialised per quantum and no production-path contention model, the
bank placement of core 1 has no timing effect — `stress` on RP2350
measures dual-core compute + peripheral cost only (the RP2350 bench
leaves core 1 at `0x2000_0040` for simplicity; the specific offset
doesn't matter there). Kept named `stress` for CLI symmetry; will
become a true composite once the RP2350 per-instruction interleave
+ contention hooks land.

### `fpu-heavy` (RP2350 only)

Existing workload, unchanged. VFP single-precision inner loop on
core 0.

## CLI

Single change: `--workload` accepts the expanded set; `--dual-core`
is removed.

```
--workload {basic,peripheral,contention,stress}                  # rp2040
--workload {basic,peripheral,contention,stress,fpu-heavy}        # rp2350
```

Default remains `basic` so bare invocations preserve the existing
headline number. `--seconds`, `--cycles`, `--quantum`, `--clock-mhz`,
`--core`, `--unpaced` are unchanged and orthogonal.

RP2040 rejects `fpu-heavy` with a clear error (no FPU on M0+).

## Implementation sketch

Each bench binary gains:

1. An enum `enum Workload { Basic, Peripheral, Contention, Stress, FpuHeavy }`
   parsed from `--workload`.
2. A `fn setup(emu: &mut Emulator, workload: Workload)` that pokes the
   right instructions, configures PIO/SIO registers, and wakes core 1
   if the workload is dual-core. One match, one arm per workload.
3. The existing pacing loop is unchanged.

PIO and SIO setup use the same MMIO path firmware would take. The
`Emulator` API needs one small addition on each crate:

```rust
// crates/mdrp2040/src/lib.rs  (and mdrp2350 equivalent)
pub fn mmio_write32(&mut self, addr: u32, value: u32);
pub fn mmio_read32(&mut self, addr: u32) -> u32;
```

These delegate to the bus and charge zero emulator cycles (called
outside `run()`). **Rustdoc on `mmio_read32` must warn that some
MMIO reads have side effects** (FIFO pop, divider CSR clears,
sticky-flag clears). Setup code should be write-heavy; reads are
for confirmation only, chosen carefully.

No feature flags, no env vars.

**PIO bring-up is non-trivial.** A functional SM0 on PIO0 requires
~30–50 lines of MMIO writes per bench binary: de-assert
`RESETS.PIO0`, write `INSTR_MEM0..N`, configure
`SM0_{EXECCTRL, SHIFTCTRL, PINCTRL, CLKDIV}`, set
`IO_BANK0_GPIO<n>_CTRL.FUNCSEL = PIO0`, configure
`PADS_BANK0_GPIO<n>` for output, then set `CTRL.SM_ENABLE` bit 0.
The RP2350 path is analogous with minor register-layout differences.
Factor the setup into `setup_pio0_sm0_wrap(emu)` and
`setup_gpio_output(emu, pin, funcsel)` helpers so the workload arms
stay readable.

The `contention` and `stress` workloads set up core 1 by direct
`core_mut(1)` register manipulation + `core.wake()`, same pattern as
today's `--dual-core` (which is otherwise removed).

## Verification

Per-chip, after implementation:

1. **`cargo test -p mdrp2040`** and **`cargo test -p mdrp2350`** —
   zero regressions (sanity for the `mmio_write32`/`mmio_read32`
   addition).
2. **`cargo build --release -p mdpicoem-harness`** — warnings-clean.
3. **Sanity: `basic` number unchanged from pre-change baseline.** The
   existing workload must produce the same MHz it did before the
   refactor (within run-to-run noise ~1%). RP2040 `basic` unpaced
   should land near the post-quantum headline (~210 MHz).
4. **Measure each workload unpaced and paced**, record in the journal.
   Expected spread pattern (for diagnosis, not a strict gate):
   - **Unpaced MHz.** `basic` is the highest. `peripheral` lands
     below `basic` (per-quantum peripheral tick overhead). `contention`
     and `stress` are dual-core so compute-cost doubles per master
     cycle — they will report meaningfully lower MHz than `basic`,
     though higher than a naive 2× scaling because virtual stall
     cycles don't consume host time (see `contention` section).
   - **Paced verdict.** This is the primary user-facing signal.
     `basic` should remain at least MARGINAL at 125 MHz (RP2040) /
     150 MHz (RP2350). `stress` verdict is the Arthur's-hunch test:
     if `stress` is CANNOT SUSTAIN and the others aren't, the
     composite-worst-case story is validated.
5. **No unit-test coverage for workload setup functions** — they're
   bench-binary plumbing, validated by observation of the bench output.
   The small `mmio_write32`/`mmio_read32` additions on each emulator
   crate are inherently covered by the bench exercising them.

## Open questions

- **PIO clock divider.** CLKDIV=1 keeps the SM maximally busy; a
  realistic firmware might run the SM at 10–50 MHz off a 125 MHz
  sys_clk (CLKDIV=2.5–12). Pick CLKDIV=1 for worst-case peripheral
  load; revisit if the signal is too pessimistic.
- **GPIO toggle granularity in `peripheral`.** One toggle per
  iteration vs. every N iterations changes the SIO hit rate. Start
  with one-per-iteration; adjust if the workload is dominated by
  SIO and obscures peripheral-tick cost.

## Out of scope / future

- **`isr` workload.** A periodic-SysTick workload that exercises the
  exception-entry/exit path. Decided against folding into `stress`:
  at realistic SysTick rates (~1 kHz on a 125 MHz core) the amortised
  overhead is ~0.03% and doesn't move the needle; at pathological
  rates the signal becomes "ISR-dominated workload" which deserves
  its own name. Tracked in `tech_debt.md` ("Exception entry/exit not
  differentially validated") as step 1 of a three-stage plan that
  culminates in a dedicated `qemu_diff_isr_*` differential fuzzer.
- **`peripheral-dual`** (dual-core + peripheral, no contention):
  useful fifth axis but the four-workload set already shows the
  envelope.
- **Per-instruction interleave + contention hooks on mdrp2350.**
  `mdrp2350::Emulator::step` runs cores sequentially (core 0 drains
  its quantum, then core 1 drains its own) so `contention`/`stress`
  on RP2350 currently measure dual-core compute cost only — no bank
  contention. The RP2040 emulator has a per-instruction interleave
  with `contention_check_active` wired through the bus; mirroring
  that on RP2350 is a follow-up in its own right and is explicitly
  out of scope for this HLD. Tracked separately.
- SIO FIFO ping-pong between cores as its own workload (`fifo-pong`).
- DMA workload once DMA is wired to the quantum tick path.
- Regression-gate thresholds (e.g. "fail CI if `stress` < 80 MHz").
- Machine-readable output (JSON) for trend tracking.
