# 2026.04.17 — HLD — OneROM Stress Harness

## Purpose

Sweep every address in a real OneROM ROM image on the emulator, validate the
byte served against the flash-lifted shadow, and report a latency histogram
in nanoseconds. Answers "is our emulated OneROM still byte-correct at full
coverage, and how fast is it?"

## Non-goals

- **No arbitrary ROM injection.** Uses existing pre-baked fixtures shipped by
  OneROM. Adding a new ROM still means running `sdrr-gen` externally or
  swapping in a committed fixture.
- **No silicon-calibrated timing.** Same caveat as the existing oracles —
  `silicon_cycle_oracle_rp2350` is the eventual venue for that. This tool
  reports emulator-bounded timing; its value is regression detection and
  a relative "ROM speed class" read.
- **No progress pacing / streaming UI.** Run to completion, print at the
  end. Sweeps take ~10–30 s.
- **No CSV / JSON export.** Stdout is the report. If an outlier analysis
  workflow emerges later, add it then.
- **No CLI flags for mode, fixture, or sample count.** Two binaries, one
  fixed fixture each, full sweep each. Simpler than a flag matrix.

## Scope

Two new binaries, one shared library module, no env vars, no features.

### What's built

1. `crates/mdpicoem-harness/src/onerom_stress.rs` — library module:
   - `generate_sweep_cases() -> Vec<Case>` — every `addr_bits` in
     `0x1800..=0x1FFF` (the A11=A12=1 invariant range, 2048 cases) paired
     with its expected byte.
   - `Histogram { count, pass, fail, min_ns, max_ns, mean_ns, p50, p95, p99 }`
     pure-function aggregator over a slice of per-case latencies.
   - `format_report(&Histogram, &[Fail]) -> String` — plain-text dump.
2. `crates/mdpicoem-harness/src/bin/onerom_stress_pio_rp2350.rs` — driver
   for PIO-mode stress. Hardcoded path
   `crates/mdpicoem-harness/fixtures/onerom-fire-24-a-rp2350-1541.bin`, ROM
   set 0 (1541 $E000 kernal 901229-06AA). Uses
   `crate::onerom_serving_oracle::run_case` in a loop.
3. `crates/mdpicoem-harness/src/bin/onerom_stress_cpu_rp2350.rs` — CPU-mode
   counterpart. Same fixture, metadata-patched to CPU at load time (reuse
   the existing patcher logic or ship a second pre-patched fixture — see
   "Open questions" below). Uses the CPU oracle's run_case.

### What's shared from existing code

| Concern | Source | Reused as-is? |
|---|---|---|
| Shadow lift from flash | `onerom_serving_oracle::lift_shadow_from_flash_pub` | ✅ |
| Stimulus pin composition | `onerom_serving_oracle::stimulus_level_pub` | ✅ |
| Per-case sim + observation (PIO) | `onerom_serving_oracle::run_case` | ✅ |
| Per-case sim + observation (CPU) | `onerom_serving_oracle_cpu::run_case` | ✅ |
| Case struct + verdict enum | `onerom_serving_oracle::{Case, Verdict}` | ✅ |
| cycles→ns at `sys_clk_hz` | existing oracle binary report formatter | extracted into `onerom_stress` |

The stress tool is effectively "the existing oracle, looped over 2048
cases instead of 15, with a histogram at the end."

## Output format

One screenful, no surprises:

```
OneROM Stress — 1541 $E000 kernal (901229-06AA), PIO mode
sys_clk_hz: 150 MHz
fixture: crates/mdpicoem-harness/fixtures/onerom-fire-24-a-rp2350-1541.bin
rom_set: 0

cases    : 2048
pass     : 2048
fail     :    0

latency (ns):
  min    :   60
  p50    :  213
  mean   :  215
  p95    :  280
  p99    :  293
  max    :  320

ROM speed class: standard (mean 215 ns)
```

If there are fails, append up to the first 20 in a flat table:

```
first failures (20 of 47):
  addr=0x1837 expected=0xC3 observed=0x00 cycles=—  verdict=WrongByte
  addr=0x1A40 expected=—    observed=—    cycles=—  verdict=NoResolve
  ...
```

Exit code: 0 if all pass; 1 otherwise. Matches the serving-oracle binary
convention.

## Data flow

```
 fixture.bin
     │
     ▼
 lift_shadow_from_flash_pub   ──►  Vec<u8; 64KiB>
     │
     ▼
 generate_sweep_cases(shadow, 0x1800..=0x1FFF) ──►  Vec<Case>
     │
     ▼
 for case in cases {
     run_case(&mut emu, &glue_or_cpu_state, case) ──► CaseResult
 }
     │
     ▼
 Histogram::from(&results)          ──► summary
 format_report(summary, &fails)     ──► stdout
```

Single boot, single sync, single emulator instance — just 2048 `run_case`
invocations.

## Fixture handling

Two options; picking (a) for simplicity.

**(a)** Ship a second pre-patched fixture for CPU mode
(`onerom-fire-24-a-rp2350-1541-cpu.bin`), produced once via
`wrk_scratch/patch_fixture_cpu_mode.py`. Commit it. Stress binaries pick
the right variant by hardcoded path. No runtime patching.

**(b)** Patch in memory at load time. Reuses
`patch_fixture_cpu_mode.py`'s logic (port to Rust). More moving parts;
no benefit for this tool since the patch is pre-computable.

Going with (a) — same commit strategy as the existing CPU-mode fixture.

## Testability

Two small pure-function tests in `onerom_stress.rs`:

1. `histogram_of_empty_is_zeroed` — sanity.
2. `histogram_percentiles_match_hand_computation` — feed
   `[60, 100, 150, 200, 250, 300, 320]`, assert p50 / p95 / p99 land on the
   right bucket. No emulator needed.
3. `generate_sweep_cases_covers_full_range` — assert
   `len == 2048`, endpoints hit `0x1800` and `0x1FFF`.

The run_case logic is already unit-tested in the oracle crates. The stress
binary itself is an integration test — run it against the 1541 fixture,
expect all-pass.

## What's deliberately excluded

- **Multi-rom_set sweep in one run.** If needed, run the binary with a
  different hardcoded `rom_set_index` (change the constant and recompile).
  Adding a loop + per-set histogram doubles output complexity for
  marginal benefit on day one.
- **Per-bank / image-select sweeping.** Same reasoning. The fixture's ROM
  sets are the bank axis; this tool sweeps one bank at a time.
- **Shared binary with `--mode pio|cpu` flag.** Two binaries mirror the
  existing `onerom_serving_oracle_rp2350` / `_cpu_rp2350` pattern. One
  flag would save ~30 lines of boilerplate; not worth it.
- **Outlier CSV.** Inline "first 20 fails" is enough to start an
  investigation.
- **Runtime-configurable envelope.** Envelope is not used here — we're
  reporting raw latency distribution, not pass/fail against a window.
  Byte correctness is the only PASS/FAIL axis.

## Open questions

- **Rom_set selection.** Defaulting to index 0 for 1541 (the 901229-06AA
  kernal). Arthur: is that the right canonical target, or would a
  different set tell us more?
- **Failure threshold for early exit.** Should the binary bail after the
  first N fails, or run to completion and print them all? Going with
  "always run to completion" — a histogram over partial data is misleading.
- **CS / image-select invariant for the 1541 fixture.** Current oracle
  assumes `A11=A12=1` (the `test-sdrr-0` layout). For `1541.json` this
  may or may not be identical; HLD author hasn't verified yet. If it
  differs, the sweep range + stimulus_level permutation need a per-fixture
  override. Cheapest: read the fixture's pin config from flash metadata.
  Most expensive: fixture-specific binaries. Defer to implementation time.

## Risks surfaced during pressure-test

1. **CPU-mode sync PC range is firmware-specific.** `is_synced_cpu` hardcodes
   `0x1000_0926..=0x1000_0930` — the serve loop PCs for the `test-sdrr-0`
   build. The 1541 firmware was built with a different ROM config; its
   serve loop could live at different addresses. **Mitigation:** run
   `onerom_cpu_probe` against the 1541 fixture before writing the CPU
   stress binary. If the PC range differs, make `is_synced_cpu` take the
   range as a parameter (it's small, cheap, explicit).
2. **CPU fixture patcher offset assumption.** The patcher writes a new
   `onerom_firmware_overrides_t` at file offset `0xc328` — an unused
   `0xff`-run in `test-sdrr-0`. Not validated for 1541.bin. **Mitigation:**
   have the patcher validate "16 consecutive 0xff bytes at candidate
   offset" before writing, and search for a different free slot if the
   default one is occupied.
3. **PIO-mode residue buildup at 2048-case scale.** The 15-case sweep has
   a short-fixed-drain pattern that was *empirically* tuned on 15
   iterations. At 2048 iterations, latency could drift upward
   (sawtooth) if residue accumulates across cases. **Mitigation:**
   inspect the per-case cycle distribution after the first run. If
   latency increases with case index, the drain between cases is
   insufficient.
4. **Per-case report noise.** The existing oracle prints a per-case
   `[ i/15]` line. Don't do that at 2048 — suppress per-case output,
   print the summary only.

## Implementation order

1. Verify the 1541 fixture's A11/A12 invariant matches the `test-sdrr-0`
   assumption. If not, decide whether to parse the config from flash or
   hardcode a second invariant.
2. Write `onerom_stress.rs` with the 3 unit tests. TDD — histogram + sweep
   generator first.
3. Write `onerom_stress_pio_rp2350.rs`. Wire the existing PIO `run_case`
   through the sweep. Run on the 1541 fixture.
4. Inspect first run. If all-pass, commit. If fails, triage — stress runs
   often surface edge cases that the 15-case sweep missed.
5. Repeat (3)(4) for CPU mode after producing / committing
   `onerom-fire-24-a-rp2350-1541-cpu.bin` via the patcher.
6. Commit binaries + library + pre-patched CPU fixture.

Rough effort: half a day if the 1541 fixture behaves; another half if it
surfaces a PIO / CPU emulator gap that needs to be chased.
