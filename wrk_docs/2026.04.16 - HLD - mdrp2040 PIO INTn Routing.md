# HLD: mdrp2040 PIO INTn Routing

Date: 2026-04-16

## Problem

PicoGUS firmware never processes ISA bus events that the harness fires
into the emulator. Result: PSRAM stays empty, GUS synth reads zeros,
audio output is silent (12,344 frames × 0 samples).

Root cause: PicoGUS's ISA handler is wired to `PIO0_IRQ_0` via the
`INT0_INTE` register with `RXNEMPTY_SM0` enabled — "wake me when the
ISA RX FIFO has data." The `tick_pio_and_route_irqs_single` function
in `mdrp2040::Emulator` (lib.rs:409) over-routes only the 8-bit
`irq_flags` register set by the PIO `irq` instruction. It does not
model `INT0_INTE` / `INT1_INTE`, and crucially does not propagate
FIFO status conditions (RXNEMPTY, TXNFULL) to the NVIC. Autopush
fills the RX FIFO, the firmware is never woken, ISA events sit
unprocessed.

Documented in `tech_debt.md` line 234 ("PIO INTn_INTE routing not
modelled").

## Solution

Port the existing fix from mdrp2350 (commit `8bb7614`). The shared
`mdpicoem-common::PioBlock` already has all the required plumbing:

- `int0_inte`, `int1_inte`, `int0_intf`, `int1_intf` fields
- `raw_intr()` — 12-bit status: IRQ flags + RXNEMPTY + TXNFULL
- `int0_ints()` / `int1_ints()` — `(raw_intr() & inte) | intf`
- MMIO read/write dispatch for offsets `0x128`-`0x140`
  (INTR / INT0_INTE / INT0_INTF / INT0_INTS / INT1_INTE / INT1_INTF
  / INT1_INTS)

The bus already dispatches PIO MMIO to `pio[i].read32`/`write32`
(bus/mod.rs:679-744), so the new register surface is reachable via
firmware writes without any bus changes.

The only change needed: replace the over-route in
`tick_pio_and_route_irqs_single` with the per-line routing pattern
mdrp2350 already uses.

## Change

### Before (mdrp2040/src/lib.rs:409-428)

```rust
fn tick_pio_and_route_irqs_single(&mut self) {
    let gpio_in = self.bus.gpio_in;
    self.bus.pio[0].step_n(1, gpio_in);
    self.bus.pio[1].step_n(1, gpio_in);
    let any0 = (self.bus.pio[0].pending_irqs() & 0xF) != 0;
    let any1 = (self.bus.pio[1].pending_irqs() & 0xF) != 0;
    let mut nvic_bits = 0u32;
    if any0 {
        nvic_bits |= 0b11 << 7;  // PIO0_IRQ_0 + PIO0_IRQ_1
    }
    if any1 {
        nvic_bits |= 0b11 << 9;  // PIO1_IRQ_0 + PIO1_IRQ_1
    }
    self.bus.irq_pending |= nvic_bits;
}
```

### After

```rust
fn tick_pio_and_route_irqs_single(&mut self) {
    let gpio_in = self.bus.gpio_in;
    self.bus.pio[0].step_n(1, gpio_in);
    self.bus.pio[1].step_n(1, gpio_in);
    self.route_pio_irqs();
}

/// Route PIO IRQ flags + FIFO status to the NVIC via
/// INT0_INTE / INT1_INTE masks. A flag reaches NVIC line N iff
/// `(INTR & INTn_INTE) | INTn_INTF != 0`.
///
/// RP2040 PIO IRQ assignments (datasheet §2.20.7):
///   PIO0_IRQ_0 = NVIC #7,  PIO0_IRQ_1 = NVIC #8
///   PIO1_IRQ_0 = NVIC #9,  PIO1_IRQ_1 = NVIC #10
fn route_pio_irqs(&mut self) {
    for (i, base) in [7u32, 9u32].iter().enumerate() {
        let ints0 = self.bus.pio[i].int0_ints();
        let ints1 = self.bus.pio[i].int1_ints();
        if ints0 != 0 {
            self.bus.irq_pending |= 1 << base;
        }
        if ints1 != 0 {
            self.bus.irq_pending |= 1 << (base + 1);
        }
    }
}
```

The IRQ-line numbers `7..10` on RP2040 differ from RP2350's
`IRQ_PIO0_IRQ_0` constant — RP2040 uses bare bit indices in
`bus.irq_pending`, RP2350 uses a named const + `assert_irq_shared`.
Otherwise the routing logic is identical.

## What this unblocks

1. PicoGUS ISA handler will run when PIO0 RX FIFO has data
2. Firmware processes ISA events, routes GUS DRAM writes to PSRAM
3. PSRAM model receives waveform data
4. Synth reads non-zero waveform from PSRAM
5. I2S output carries actual audio samples
6. WAV capture contains real PCM, not silence

## What this does NOT change

- The `tick_pio` (bulk path) IRQ routing. The fast path is taken
  when all PIO is idle, which means no FIFO state changes can
  happen — the over-route check is moot. We could harmonize for
  consistency but it's not required for PicoGUS audio.
- mdrp2350 — already has the fix.
- `tech_debt.md` — entry stays for the bulk-path inconsistency
  noted above. The blocking issue (PicoGUS audio) is resolved.

## Tests

Add one unit test in `mdrp2040/src/tests.rs` mirroring the mdrp2350
`pio0_int_routing_split` scenario:

- Configure PIO0 SM0 to autopush data
- Set `INT0_INTE` to enable RXNEMPTY_SM0 only
- Set `INT1_INTE` to enable IRQ flag 0 only
- Push data via SM0 autopush
- Verify NVIC bit 7 (PIO0_IRQ_0) is set, NVIC bit 8 (PIO0_IRQ_1) is NOT
- Trigger PIO `irq 0` instruction
- Verify NVIC bit 8 (PIO0_IRQ_1) is now also set

Existing test `pio_high_irq_flags_do_not_route_to_nvic` (tests.rs:2583)
stays — it still validates that bits 4-7 of `irq_flags` don't escape.
