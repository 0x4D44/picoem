Version: 1.2.0

## 1. Sweep summary

`cargo-mutants` 27.0.0 against the seven decode/execute files listed in the
V1 HLD (6170 LOC total). Wall-clock 13h 17m, single worker, warm `target/`.

| Outcome      | Count | %     |
|---           |---    |---    |
| Caught       | 3626  | 82.6  |
| Missed       | 707   | 16.1  |
| Timeout      | 53    | 1.2   |
| Unviable     | 3     | 0.07  |
| Baseline OK  | 1     | 0.02  |
| **Total**    | 4390  | 100.0 |

**Headline hypothesis.** Bucket 3 (caught by differential oracle, missed by
in-tree unit tests) appears to dominate the survivor list at every file. The
methodology looks like it is working as the V1 HLD predicted: 82 % of mutants
are caught by `cargo test` alone, the residual 16 % are concentrated in the
exact code paths the QEMU / silicon oracles were built to validate. This
classification is heuristic — by inspection of (file, function, pattern)
cells, not per-mutant oracle replay. The V2 second-pass runner is what would
convert hypothesis into measurement. The two clusters initially flagged as
Bucket 2 (real oracle gap) — `parallel_unsigned_16`/`parallel_signed_16` SIMD
lanes and `f32_to_f16_bits` FP16 conversion — turn out on inspection of the
existing harness corpus to be already covered (see §3.1, §3.2 verifications),
so the residual Bucket 2 budget is small (~5 survivors). There is no Bucket
1 (real test gap) cluster of significant size — the unit tests are doing
what they were designed to do.

This is the expected V1 outcome. The "follow-up" branch from the V1 HLD that
this points at is the second-pass oracle runner, sized as a half-day script.
With the SIMD and F16 oracles verified already-covered, the second-pass
runner is now the *only* mechanism that distinguishes "real gap" from
"oracle catches but cargo-mutants doesn't run it" — a sharper motivation
than V1's framing gave.

## 3. Per-file analysis

### 3.1 `mdrp2350/core/execute_thumb32.rs` — 324 survivors

By function (top 10):

| Survivors | Function                              | Notes                                  |
|---:       |---                                    |---                                     |
|  66       | `parallel_unsigned_16`                | UADD16/USUB16/UASX/USAX + Q/H variants |
|  31       | `barrel_shift`                        | imm/reg shift with carry-out           |
|  31       | `thumb32_long_multiply`               | UMULL/SMULL/UMLAL/SMLAL/UMAAL          |
|  26       | `thumb32_dp_register`                 | rotated extension forms                |
|  25       | `thumb32_dp_shifted_reg`              | DP with shifted Rm                     |
|  23       | `thumb32_dp_plain_imm`                | ADDW/SUBW/MOVW/MOVT                    |
|  19       | `thumb32_msr`                         | MSR APSR/IPSR/EPSR/Special             |
|  17       | `parallel_signed_16`                  | SADD16/SSUB16 + Q/H variants           |
|  15       | `thumb32_bl`                          | branch-link target assembly            |
|  14       | `thumb32_multiply`                    | MUL/MLA/MLS variants                   |

Patterns are dominated by `| ↔ ^` (51), `>> ↔ <<` (41), and `& ↔ |/^` (53).
These are the literal bit-field assembly patterns of Thumb-32 decode
(`(rd & 0xF) << 8 | imm8`).

Sample lines:

```
execute_thumb32.rs:18:34 — replace | with ^ in thumb_expand_imm_c
execute_thumb32.rs:64:38 — replace >> with << in barrel_shift
execute_thumb32.rs:1746:9 — replace parallel_unsigned_16 -> u32 with 1
  (replace return value with literal `1`)
```

**Verdict.** The non-SIMD bulk (`barrel_shift`, `thumb32_dp_*`,
`thumb32_long_multiply`, `thumb32_multiply`, `thumb32_bl`) is Bucket 3:
mutations break the result of normal data-processing instructions, which
QEMU diff catches densely. `cargo-mutants` doesn't run the QEMU oracle, so
they survive.

The SIMD cluster (`parallel_unsigned_16` 66 + `parallel_signed_16` 17 +
`parallel_unsigned_8` 4 + `parallel_signed_8` 3 = 90 survivors total) was
initially read as a Bucket 2 oracle gap. **Verification (`thumb32_gen.rs:6435-6482`)
shows it is in fact Bucket 3:** the parallel-add/subtract generator
randomises across all six modifier values (signed=0b000, Q=0b001, H=0b010,
unsigned=0b100, UQ=0b101, UH=0b110) and all six operation values
(ADD8/ADD16/ASX/SUB8/SUB16/SAX where ISA-legal), with `xpsr_mask` set to
`MASK_ALL_FLAGS_GE` for the plain signed/unsigned variants that update GE.
The saturating, halving, and exchange lanes are exercised by QEMU diff;
they survive `cargo-mutants` only because that tool doesn't run the QEMU
oracle. No generator extension is needed.

`thumb32_msr` (19) is partly Bucket 2: the special-register switch on the
M0+ side (PRIMASK/CONTROL only) is also lightly tested on the M33 side, and
match-arm deletions for unreachable register IDs are likely Bucket 4.
That is the residual Bucket 2 in this file (~5 survivors).

**Proposed actions.**
- (Bucket 3 follow-up) Run the second-pass oracle runner (V1 HLD §Follow-up)
  over `barrel_shift`, `thumb32_long_multiply`, `thumb32_dp_*`, and the
  full SIMD parallel cluster to convert the Bucket-3 hypothesis into
  measured ground truth. With the generator already covering UQ/UH/ASX/SAX
  + GE flags, the runner should report these as oracle-caught.

### 3.2 `mdrp2350/core/execute_fpu.rs` — 167 survivors

By function (top 10):

| Survivors | Function                  | Notes                                      |
|---:       |---                        |---                                         |
|  44       | `f32_to_f16_bits`         | FP16 conversion (VCVT.F16.F32)             |
|  13       | `fpu_unary`               | VABS/VNEG/VSQRT dispatch                   |
|  12       | `fp_fma`                  | VFMA/VFMS/VFNMA/VFNMS                      |
|   8       | `f16_bits_to_f32`         | FP16 unpack (VCVT.F32.F16)                 |
|   7       | `fp_div`                  | VDIV                                       |
|   7       | `f32_to_u32_rmode`        | VCVT.U32.F32 with rounding                 |
|   6       | `fp_sub`, `fp_add`        | scalar VADD/VSUB                           |
|   6       | `canonicalize_nan_fma`    | NaN propagation for fused-MAC              |
|   5       | `underflowed`             | tininess-before-rounding helper            |
|   4       | `ftz_output`              | flush-to-zero result lane                  |

Plus the small register-extraction helpers `vfp_sd` / `vfp_sn` / `vfp_sm` /
`fpscr_set_nzcv` (7 survivors total — Bucket 4, see below).

Patterns: `| ↔ ^` (55) dominates because the file is full of FPSCR flag
assembly (`FPSCR_N | FPSCR_Z | FPSCR_C | FPSCR_V`). `&& ↔ ||` (12) and
`< ↔ <=` / `< ↔ ==` (15) sit in the IEEE corner-case logic.

Sample lines:

```
execute_fpu.rs:53:25 — replace | with ^ in fpscr_set_nzcv
execute_fpu.rs:130:24 — replace || with && in ftz_output
execute_fpu.rs:1466:* — many in f32_to_f16_bits
execute_fpu.rs:26:15 — replace | with ^ in vfp_sd
```

**Verdict.** Three sub-clusters with different bucket assignments.

1. **`vfp_sd` / `vfp_sn` / `vfp_sm` / `fpscr_set_nzcv` `| ↔ ^` (7 mutants):
   Bucket 4 equivalent.** These compose disjoint bit-fields:
   `(vd << 1) | d` where `d ∈ {0, 1}` and `vd << 1` always has LSB 0;
   FPSCR flag bits are also disjoint. `|` and `^` produce identical results
   on disjoint bit sets. Cannot be caught by any oracle. Candidates for
   `#[mutants::skip]`.
2. **`f32_to_f16_bits` (44) and `f16_bits_to_f32` (8): Bucket 3 (oracle
   already covers this).** Initial inspection suggested an oracle gap.
   **Verification (`softfloat_diff.rs:551-741`) shows the half-precision
   converter is fully covered**: a dedicated `HalfDir`/`run_vcvt_half`
   path runs both `VCVTB.F32.F16` and `VCVTB.F16.F32` against the
   `ieee754_ref` reference, sweeping all five FPSCR modes, edge-case
   tables (`half_edge_cases_f16` / `half_edge_cases_f32` covering ±0,
   ±inf, SNaN/QNaN, ±subnormals, smallest/largest normal, ±1.0,
   overflow/underflow boundaries), and a fuzz path (`random_f16_bits`)
   under `--fuzz N`. These survivors are Bucket 3, not Bucket 2 — the
   mutations would be caught if `cargo-mutants` ran `softfloat_diff`,
   but it doesn't.
3. **`fp_add` / `fp_sub` / `fp_div` / `fp_fma` / `fpu_unary` / `underflowed` /
   `ftz_input` / `ftz_output` (~50 mutants): Bucket 3.** These are the
   IEEE-754 hot path.  `softfloat_diff` is the oracle of record; the
   mutations break the result, the oracle would catch them, the unit tests
   don't run the oracle.

**Proposed actions.**
- (Bucket 4) Annotate `vfp_sd` / `vfp_sn` / `vfp_sm` / `fpscr_set_nzcv` with
  `#[mutants::skip]` plus a one-line comment ("disjoint bit-fields, `|`
  equivalent to `^`"). Closes 7 survivors. (Do not commit until explicitly
  asked — this HLD only proposes.)
- (Bucket 3 follow-up) The full `f32_to_f16_bits` / `f16_bits_to_f32` /
  `fp_add` / `fp_sub` / `fp_div` / `fp_fma` / `fpu_unary` cluster (~110
  survivors) is the highest-value input for the V2 second-pass runner —
  `softfloat_diff` is verified to cover the corresponding architectural
  surface, so the runner should report nearly all of them as oracle-caught.

### 3.3 `mdrp2040/core/execute.rs` — 75 survivors

By function (top 5): all in `thumb16_*` instruction implementations.
Patterns: `>> ↔ <<` (~25), `!= ↔ ==` (~12), `& ↔ |` (~10).

Sample lines:

```
execute.rs:25:26 — replace > with >= in add_with_carry
execute.rs:64:46 — replace & with | in thumb16_lsl_imm
execute.rs:139:13 — delete match arm 0b10 in thumb16_add_sub
execute.rs:248:53 — replace & with ^ in thumb16_data_processing
```

**Verdict.** Bucket 3 throughout. Every survivor breaks an ARMv6-M
instruction's semantics: shift amounts, register-decode bit fields, flag
updates in `add_with_carry`. The M0+ silicon oracle (`probe_diff_rp2040`)
is the explicit catch for these — `qemu_diff_m0plus` masks them out
because it runs against `cortex-m0` which has UNDEFs on parts of the M0+
ISA. There are no Bucket 1 candidates: any test that exercises the
mutation would already be in `mdrp2040/src/tests.rs`, and the survival rate
across functions is uniform — no single function stands out as
under-tested.

**Proposed actions.**
- None required for V1. Confirm Bucket-3 hypothesis with the second-pass
  oracle runner against `probe_diff_rp2040` once that follow-up lands.

### 3.5 `mdrp2350/core/decode.rs` — 58 survivors

By function: split between `is_thumb16_flag_only`, `classify_thumb16_pure`,
`classify_thumb16_misc_pure`, and several `delete match arm` mutations on
group-dispatch tables.

Sample lines:

```
decode.rs:21:28 — replace << with >> in is_thumb16_flag_only
decode.rs:74:9 — delete match arm 0b01001 in classify_thumb16_pure
decode.rs:128:15 — replace match guard `op & 0x5 == 0x1` with true in classify_thumb16_misc_pure
```

**Verdict.** Bucket 3 with a Bucket 4 tail. Deleting a match arm in
`classify_thumb16_pure` re-routes the encoding to a neighbouring group
(or the catch-all UNDEFINED) — when the encoding is exercised by either
the unit tests or the QEMU corpus, the diff fails. The match-guard
mutations on rare encodings (e.g. `op & 0x5 == 0x1` covering misc-control
sub-groups CPS / SETEND / nops) are partly Bucket 4 because some
guard-mutation outputs are equivalent on the encodings the corpus actually
generates. Ratio is hard to call without per-mutant patching; estimate
~50 Bucket 3 / ~8 Bucket 4.

**Proposed actions.**
- None required for V1. The mdrp2040 sibling has 0 survivors despite a
  smaller decoder, which suggests the M33 decode path's larger surface
  area (Thumb-32 encoding bits on top of Thumb-16) is the variable, not
  test density.

## 4. Cross-cutting findings

1. **Bucket 3 likely dominates the survivor list (hypothesis).** Across all
   six non-empty files, the dominant signal *appears to be* "this mutation
   breaks an instruction's architectural semantics, which the differential
   oracle would observe, but `cargo-mutants` doesn't run the differential
   oracle". This is the methodology behaving as designed *if* the
   classification holds. We have not measured it per-mutant; that is V2's
   job. Two clusters initially flagged as Bucket 2 dissolved on
   verification of the harness corpus (§3.1 SIMD, §3.2 F16) — a reminder
   that pattern-level inference can over-count oracle gaps. The same
   risk applies inversely: some "obviously oracle-caught" mutants in
   Bucket 3 may turn out not to be exercised by the existing fuzz
   distribution.
2. **No remaining Bucket 2 clusters of significant size.** The SIMD
   parallel-add/sub-16 cluster (~85 survivors) and F16↔F32 conversion
   cluster (~52 survivors) are already covered by `thumb32_gen.rs` and
   `softfloat_diff.rs` respectively (verified, see §3.1 / §3.2). Residual
   Bucket 2 is small (~5 survivors, partly `thumb32_msr` reg-id paths).
3. **Helpers that compose disjoint bit-fields are universally Bucket 4.**
   The pattern `(hi << k) | lo` where `hi << k` is disjoint from `lo` is
   immune to `| ↔ ^` mutation. That accounts for the bulk of the residual
   "unreachable" tail. Most live in `vfp_*` / FPSCR / decode-bit-field
   helpers.
4. **No Bucket 1 cluster.** The unit-test density established in the
   pre-V1 coverage push (98 % line coverage on these files) is genuinely
   the right shape: where survivors exist, oracle gaps and bit-field
   equivalences explain them. This is a positive validation of the recent
   coverage work — it was not vacuous.
5. **`mdrp2040/decode.rs` 0 survivors validates the methodology
   end-to-end.** A small, well-scoped decoder that is exercised by both
   unit tests and oracles produces no surviving mutants. That this
   actually happened on at least one in-scope file is the strongest
   single piece of evidence that the rest of the survivors are real
   coverage signal, not tooling artefact.
6. **53 timeouts are mixed pathology, not pure infinite loops.** The
   cluster spans `thumb16_lsl/lsr`, `thumb32_bl`, and the
   `thumb32_dp_register` arithmetic block. Shift/mask mutations
   (`<<` ↔ `>>`, `&` ↔ `^`/`|`) inside tight executor loops do produce
   non-terminating runs, but the cluster also includes panic-class
   mutations — e.g. `execute_thumb32.rs:1637:59 replace - with /` in
   `thumb32_dp_register`, where the original subtraction can yield zero
   and the mutated divisor panics on `i32::div`. The test runner would
   normally observe such a panic as a Catch, but `cargo-mutants`'
   per-mutant timeout fires first, so the result is recorded as a
   timeout rather than caught. Either way the harness can't distinguish
   the buckets here, so the 53 stay in §1's outcome table and out of
   §2's bucket distribution; the `timeout_multiplier=5` in
   `.cargo/mutants.toml` absorbs the wall-clock noise.

## 5. Proposed actions

Numbered list. Sized for half-day units unless noted. V1 stops at
proposing — implementation is separate work.

1. **Build the second-pass oracle runner.** Take `missed.txt`, apply each
   patch in turn, run `qemu_diff_m33 --fuzz 5000` (and `_m0plus`,
   `softfloat_diff`, optionally `probe_diff_*` opportunistically) per
   mutant, report whether the oracle catches it. Report-only — do not
   gate anything. This converts our Bucket 3 estimate into a hard
   number. Sized ~half-day per V1 HLD §Follow-up. With the verified
   already-covered SIMD and F16 oracles (§3.1, §3.2), this runner is
   the *only* mechanism that can distinguish "real gap" from "oracle
   catches but cargo-mutants doesn't run it". That is a sharper reason
   for V2 than the V1 HLD framing.
2. **Annotate Bucket 4 helpers with `#[mutants::skip]`.** `vfp_sd`,
   `vfp_sn`, `vfp_sm`, `fpscr_set_nzcv`, plus identified disjoint-bit-field
   helpers in `decode.rs`. Each gets a one-line comment explaining the
   equivalence (e.g. "disjoint bit-fields: `|` equivalent to `^`"). Adds
   the `mutants = "0.0.3"` dev-dep on first use per V1 HLD §Configuration.
   Sized ~1 hour. Closes ~7 survivors mechanically; reduces noise on
   future runs.

That is two concrete actions. The previously proposed SIMD-generator
extension and FP-corpus F16 extension are removed: verification (§3.1,
§3.2) showed the harness already covers those surfaces, so the work
would be duplicate. Neither action needs to be done now; this HLD
records the proposal.

## 6. What we deliberately are NOT doing

- **No new unit tests.** Bucket 1 is empty; nothing to address.
- **No `#[mutants::skip]` annotations in this commit.** Per the V1 HLD,
  triage stops at "list and propose". Action 2 above is queued but not
  applied.
- **No new mutation-test infrastructure.** No CI integration, no custom
  mutation operators, no per-crate mutation budgets. V1 was a measurement
  exercise.
- **No expansion of mutation scope.** `exceptions.rs`, `coprocessor.rs`,
  bus, peripherals, DMA, PIO, harness — all still out of scope. Decision
  on V2 scope expansion deferred (see §8).
- **No fix to `mutants.out/lock.json` cleanup.** Cosmetic; documented in
  the journal as future work.

## 8. V2 scope recommendation

Per V1 HLD §Follow-up, three branches were possible. V1 results *appear*
to land in the **Bucket 3-dominated** branch — but that classification
is hypothesis, not measurement:

> Survivor list is dominated by bucket 3 (oracle catches, tests don't).
> Build a small "second-pass" runner: take `missed.txt`, apply each patch
> in turn, run `qemu_diff_m33 --fuzz 5000` (or `_m0plus`), and report
> whether the oracle caught it. Sized as a half-day script.

Recommendation: **execute that branch as V2**. The second-pass runner is
the single piece of infrastructure that converts the 707-survivor list
from "hypothesised bucket distribution" into "measured bucket
distribution". The motivation is now sharper than the V1 HLD framing:
verification of the harness corpus during this triage (§3.1 SIMD, §3.2
F16) already dissolved two of the three originally proposed Bucket 2
clusters — the surfaces are oracle-covered, the survivors are oracle-
catchable, but cargo-mutants doesn't run the oracle. Only a per-mutant
runner can distinguish that case from a real gap. Without V2, every
"this looks like Bucket 2 to me" reading remains exposed to the same
classification error as the SIMD/F16 misreads we just corrected.

V2's deliverable should be exactly that: the runner, plus a triage-style
follow-up document categorising the survivor list one more time, this
time with per-mutant oracle-catch ground truth instead of cell-level
inference. Estimated wall-clock for the runner itself is ~half-day; the
mutation×oracle compute is overnight class on the same machine the V1
sweep used.

If V2 confirms Bucket 3 saturation, the question of whether to extend
mutation scope to `exceptions.rs`, `coprocessor.rs`, and the bus /
peripheral code becomes a V3 conversation. That decision is not on
today's table.
