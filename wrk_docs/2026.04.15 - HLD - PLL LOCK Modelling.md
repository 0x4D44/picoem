# PLL LOCK Modelling

Version: 0.1.0
Date: 2026-04-15

## 1. Problem

Both chip crates unconditionally force CS[31] (LOCK) to 1 on every PLL
register read, regardless of whether the PLL is enabled, powered, or
has had time to settle. This was dialled in as a deliberate "firmware
poll short-circuit" in the early clock-tree model
(`wrk_docs/2026.04.14 - LLD - Clock Tree Model V2.md` §9 risk 2:
"PLL PWR ignored but LOCK reported"). While no oracle could observe it,
this was a fine simplification. The new silicon peripheral oracle
exposes the divergence directly.

### Code locations

- `d:\language\mdrp2354\crates\mdrp2350\src\bus\peripherals.rs:21` —
  `pll_read_from` does `regs[0] | (1 << 31)` on the CS register. Shared
  between PLL_SYS and PLL_USB (`pll_sys_read` at line 213,
  `pll_usb_read` at line 222).
- `d:\language\mdrp2354\crates\mdrp2040\src\bus\clocks.rs:263` —
  `pll_read(regs, offset)` does `regs[0] | (1 << 31)`. Dispatched from
  `bus/mod.rs:426-427` for PLL_SYS_BASE / PLL_USB_BASE.

### Oracle reproducer

`crates/mdpicoem-harness/src/silicon_scenarios.rs:216-226`
(`S_PLL_SYS_LOCK_TIMING` + `O_PLL_SYS_LOCK_TIMING`, scenario name
`pll_sys_lock_timing`). The setup sequence is:

```
RESETS_RESET CLR PLL_SYS         # release reset
PLL_SYS_BASE + CS  = 1           # REFDIV=1
PLL_SYS_BASE + FBDIV_INT = 100
PLL_SYS_BASE + PRIM = (2<<16) | (2<<12)   # POSTDIV1=2, POSTDIV2=2
PLL_SYS_BASE + PWR = 0           # everything powered up (PD, DSMPD, POSTDIVPD, VCOPD all cleared)
```

Then the runner spins a `max_sysclks = 1500` countdown sled on the core
(`silicon_periph_diff_rp2350.rs:251-353`), measures the actual sysclk
count via CYCCNT (`read_cyccnt`, line 146), gates the PLL by
re-asserting `RESETS_RESET` bit, and finally reads
`PLL_SYS_BASE + CS & (1 << 31)` on both sides.

### Observed silicon result

`wrk_journals/2026.04.15 - JRN - Silicon Peripheral and Cycle Oracles Implementation.md:70`:

```
pll_sys_lock_timing  1133 sysclks  FAIL  HW LOCK=0, EMU LOCK=1 → emulator forces CS[31]=1
```

At 1133 measured sysclks the hardware PLL is still not locked. With the
emulator booting at ROSC ~6.5 MHz, 1133 sysclks is roughly 174 µs of
wall-clock — but crucially the run starts from **the moment PWR clears**,
not from power-on. The lock delay is therefore at least on the order of
the whole sled window this scenario uses (~1133 sysclks). The emulator
reports LOCK=1 from the first read forward, regardless of PWR state or
time elapsed. This HLD designs the fix.

### Scope discipline

Bug surface: the CS[31] read value only. This HLD is explicitly **not**
a rewrite of the PLL model — FBDIV/REFDIV/POSTDIV math already produces
correct frequencies (`crates/mdpicoem-common/src/clocks.rs:53-65`). We
don't touch `pll_output_hz`, we don't touch `recompute_clock_tree`, we
don't add VCO frequency modelling, and we don't unify the two chips'
PLL storage. §11 lists what's out of scope explicitly.

### Register layout (same for PLL_SYS and PLL_USB, both chips)

| Offset | Register | Writable bits | LOCK-relevant semantics |
|---|---|---|---|
| 0x000 | CS | `[5:0] REFDIV`, `[8] BYPASS` | `[31] LOCK` is RO status. REFDIV=0 is illegal — hardware clamps `.max(1)` in our math (common/clocks.rs:58). BYPASS=1 routes the reference clock straight through, sidestepping the VCO entirely. |
| 0x004 | PWR | `[0] PD`, `[2] DSMPD`, `[3] POSTDIVPD`, `[5] VCOPD` | All four are active-high power-down. Any one of `PD`, `VCOPD` being set stops the VCO; `POSTDIVPD` stops the post-divider. Reset value `0x0000_002D` has PD, DSMPD, POSTDIVPD, VCOPD all set (fully powered down). |
| 0x008 | FBDIV_INT | `[11:0] FBDIV` | Feedback divider. FBDIV=0 is the "not configured" sentinel; `pll_output_hz` returns 0 when FBDIV=0 (common/clocks.rs:54-56). |
| 0x00C | PRIM | `[18:16] POSTDIV1`, `[14:12] POSTDIV2` | Both post-dividers. Reset value `0x0007_7000` (POSTDIV1=7, POSTDIV2=7). |

### LOCK semantics

The RP2350 / RP2040 datasheets (Raspberry Pi Ltd, not vendored here)
describe CS.LOCK as an asynchronous status bit driven by an on-die
lock-detect counter. The counter starts only when the VCO is powered
and running (i.e. `PWR.PD`, `PWR.VCOPD` both clear) and has a stable
reference (XOSC stable and REFDIV set). The counter waits for N
consecutive cycles of phase agreement between reference and feedback,
then asserts LOCK. Any write that changes FBDIV, REFDIV, or re-asserts
`PWR.VCOPD` de-asserts LOCK until the counter re-completes.

Concretely, for the reset value `PWR=0x2D`:
- `PWR.PD=1` ⇒ the entire PLL is off ⇒ LOCK must read 0.
- `PWR.VCOPD=1` (even with PD=0) ⇒ VCO is off ⇒ LOCK must read 0.
- `PWR=0` (everything powered up) ⇒ LOCK asserts after the lock-detect
  counter expires (order of tens of microseconds; on our oracle sled
  at 6.5 MHz = ~1µs per 6.5 sysclks, ~1133 sysclks ≈ 174µs and silicon
  still reports LOCK=0).

Because our emulator runs at ROSC nominal (6.5 MHz) during this
scenario, the **sysclk-count** for lock delay is relatively small —
a handful of sysclks would track real lock time in µs, but the oracle
gives us 1133 and LOCK is still 0, so the hardware lock-delay
expressed in sysclks of the boot clock is greater than 1133 and
less-than-or-equal-to whatever value causes a PASS at larger
`max_sysclks`. We don't know that upper bound from today's run.

### Behaviour I am inferring, not quoting

Items I could not trace to a vendored spec; flagged for sign-off (§9):

- Whether the lock-detect counter resets on each FBDIV/REFDIV write or
  only on a power-cycle. The conservative assumption is: any write to
  CS (REFDIV), FBDIV_INT, or a PWR write that sets then clears VCOPD
  re-arms the counter.
- Whether `BYPASS=1` forces LOCK=1 (because the output just passes the
  reference through, with no VCO to lock) or LOCK=0 (because the VCO
  isn't running). The conservative assumption: BYPASS does not itself
  assert LOCK.
- The exact sysclk count for lock-detect to complete. The oracle tells
  us it's >1133 at ROSC/6.5 MHz, nothing more.

### `0xFFFF_FFFF` reset value — there isn't one

The tech-debt entry (`tech_debt.md:131`) references a `0xFFFF_FFFF`
reset. That's a confusing cross-reference — neither PLL CS nor PWR
resets to `0xFFFF_FFFF`. The reset values we honour today are
`PLL_RESET = [0x0000_0001, 0x0000_002D, 0, 0x0007_7000]`
(`mdrp2040/src/bus/clocks.rs:249`, mirrored in `mdrp2350/src/bus/mod.rs:227-228`).
Treat the tech-debt line as "whatever the reset value is, it's the
honest one" and move on.

## 3. Design options

Three modelling strategies, cheapest to most faithful. Each is expressed
against the current code, with concrete field additions and hook
points.

### Option A — "LOCK when locked-enable conditions hold"

Read semantics on CS:

```rust
// in common/src/clocks.rs (new helper) or inline in each chip
fn pll_is_locked(regs: &[u32; 4]) -> bool {
    let pwr = regs[1];
    let fbdiv = regs[2] & 0xFFF;
    let pd_or_vcopd_set = (pwr & 0x01) != 0 || (pwr & 0x20) != 0;
    fbdiv != 0 && !pd_or_vcopd_set
}
```

Then `pll_read`/`pll_read_from` becomes:

```rust
Some(0) => if pll_is_locked(regs) { regs[0] | (1 << 31) } else { regs[0] & !(1 << 31) }
```

**Pros**
- No new state. No new bus field. Purely a read-side derivation.
- Fixes every existing unit test that matters
  (`test_pll_cs_read_forces_lock_bit` already starts from a default
  Bus where `PWR = 0x2D` and `FBDIV = 0` — both the `pd_set` and
  `fbdiv == 0` arms trip, so LOCK reads 0; that test would need its
  assertion updated, which is the correct outcome).
- Trivial to reason about: LOCK mirrors "PLL is trying to run". No time
  component whatsoever.

**Cons**
- No lock-delay modelling. The oracle at 1500 sysclks observes HW
  LOCK=0; under Option A the emulator would flip to LOCK=1 the cycle
  after the `PWR = 0` write, so at the oracle's readback point
  emulator reads LOCK=1, silicon reads LOCK=0. **This option does not
  pass the existing `pll_sys_lock_timing` scenario.**
- The oracle's `max_sysclks = 1500` was chosen to be shorter than real
  silicon's lock delay so that `HW LOCK = 0` is the load-bearing
  observation. Option A cannot satisfy that shape.

**Verdict**
Rejected as "fixes the PWR=0x2D reset path but fails the oracle". Kept
in the HLD because it's the natural starting sketch — every other
option layers something on top of this predicate.

### Option B — "Cycle-counted lock-delay after power-up"

Carry a `pll_lock_at_cycle: Option<u64>` per PLL, populated when a
write transitions the PLL from "not powered + not configured" to
"powered + configured", set to `current_cycle + LOCK_DELAY_SYSCLKS`.
Each read computes LOCK against the current master cycle.

Bus state additions (`crates/mdrp2350/src/bus/mod.rs` + mirror on mdrp2040):

```rust
pub(crate) pll_sys_lock_at_cycle: Option<u64>,  // None = not locked / powered down
pub(crate) pll_usb_lock_at_cycle: Option<u64>,
```

Read path (CS offset):

```rust
// Need current cycle count. Bus doesn't own Clock today — see §6 for
// the plumbing options.
let current = bus.current_master_cycle();
let locked = pll_is_locked_base(regs) && match regs_lock_at {
    Some(arm) => current >= arm,
    None => false,
};
```

Write path (after `pll_write_into`, before `recompute_clock_tree`):

```rust
let now = bus.current_master_cycle();
if pll_is_locked_base(new_regs) && !pll_is_locked_base(old_regs_before_write) {
    // PLL just came out of power-down with a live FBDIV.
    bus.pll_*_lock_at_cycle = Some(now + LOCK_DELAY_SYSCLKS);
} else if !pll_is_locked_base(new_regs) {
    bus.pll_*_lock_at_cycle = None;
} else if fbdiv_or_refdiv_changed(old_regs, new_regs) {
    // Config change while powered ⇒ re-arm.
    bus.pll_*_lock_at_cycle = Some(now + LOCK_DELAY_SYSCLKS);
}
// Writes to PRIM (POSTDIV1/POSTDIV2) do NOT de-assert LOCK on real
// silicon — those are post-VCO.
```

**Pros**
- Faithful to silicon at the resolution the oracle can observe. The
  count can be tuned to match HW under any sled size the oracle
  chooses.
- Natural place to thread VCO bypass / REFDIV illegal-value semantics
  if they need deeper modelling later.

**Cons**
- Requires Bus to know the master cycle count, which today lives on
  `Emulator::clock` (`crates/mdrp2350/src/lib.rs:60`, aggregated
  outside Bus). Three remedies available (§6), all workable, but all
  add plumbing we don't have today.
- Needs a concrete `LOCK_DELAY_SYSCLKS`. The oracle only tells us
  "> 1133 at 6.5 MHz boot clock". To pick a value that makes the
  oracle PASS, we either (a) pick `LOCK_DELAY_SYSCLKS >= 1500` so
  emulator LOCK stays 0 through the readback, or (b) pick a value
  tuned to some calibration run. (a) is what the oracle actually
  needs.
- Edge cases add real branches:
  - PWR writes that re-assert VCOPD after lock → clear `lock_at_cycle`.
  - FBDIV changes without re-power → re-arm counter per silicon.
  - PRIM changes → no effect on lock.
  - Alias-aware writes (XOR/SET/CLR) interact because the computed new
    register value is what determines the transition, not the RHS.
    `pll_write_into` must expose the before/after pair.

### Option C — "Two-stage: not-locked → locked after first enable + N"

A simplified version of B: one-shot latch. The **first** time after
reset that `pll_is_locked_base(regs)` transitions true, record
`lock_at = current + N`. After that point, LOCK stays 1 for all reads
where `current >= lock_at`. Further PWR / FBDIV writes don't rearm.

**Pros**
- Data footprint: one `Option<u64>` per PLL, same as Option B.
- Handles the oracle scenario correctly (one power-up event, one
  settling delay, one readback).
- Simpler predicate on writes — a single "first true → arm" transition,
  no mid-run rearm logic.

**Cons**
- Diverges from silicon on reconfiguration. If firmware does
  "configure → observe LOCK → change FBDIV → poll LOCK again", Option
  C reports LOCK=1 continuously (because we don't rearm), but silicon
  drops LOCK=0 during the reconfiguration. Any future oracle scenario
  that reconfigures PLL mid-run will expose this.
- In practice neither bootrom nor any current firmware under test does
  mid-run reconfiguration (per the bootrom disassembly survey — no
  `ldr` to `0x4005_0000` in a polling shape, and the OneROM full-
  system test bypasses the bootrom anyway). So the divergence only
  hurts a scenario we don't have yet.

### Option B vs C at a glance

| Criterion | B | C |
|---|---|---|
| Handles current oracle | Yes | Yes |
| Handles a "change FBDIV mid-run" scenario | Yes | No (always-locked after first lock) |
| Plumbing (Bus ↔ master cycle) | Same | Same |
| Code complexity | ~25 LoC delta per chip | ~10 LoC delta per chip |
| Risk of getting transition logic wrong | Medium (multiple rearm conditions) | Low (one latch) |

## 4. Recommendation — Option C with one guard rail

Go with **Option C** — one-shot latch — plus an explicit "rearm on
PWR write that re-asserts VCOPD/PD" to avoid the obvious bug where
firmware can "turn off the PLL" and our emulator still reads LOCK=1.

### Rationale

The testing oracle shape drives this. The silicon oracle is an
end-state diff after a fixed sysclk window (`silicon_periph_diff_rp2350.rs:251-352`).
It's not a tight cycle-counted check. We only need:

1. At `current >= max_sysclks` (1500 in the scenario), LOCK reads 0 iff
   silicon reports LOCK=0 at that point.
2. Further scenarios that power up PLL for long enough should report
   LOCK=1.

Option C satisfies both with a single `Option<u64>` per PLL and no
mid-run rearm logic. Option B is strictly more faithful, but the
fidelity gap it closes (mid-run reconfiguration) is invisible to every
test we have today and every firmware we plan to run this quarter
(blinky, OneROM, PicoGUS — none reconfigure PLL after boot-up).

The CLAUDE.md "simple, clean, maintainable solutions over clever or
complex ones" + "don't predict the future" pressure both favour C.
If a future oracle exposes the reconfig gap, lifting C to B is
mechanical: replace the one-shot latch with a rearm-on-write check.

### Concrete read semantics

```rust
// Shared helper — mdpicoem-common/src/clocks.rs
pub fn pll_is_locked_base(regs: &[u32; 4]) -> bool {
    let pwr = regs[1];
    let fbdiv = regs[2] & 0xFFF;
    let pd = (pwr & 0x01) != 0;
    let vcopd = (pwr & 0x20) != 0;
    fbdiv != 0 && !pd && !vcopd
}
```

CS[31] on read is then:

```rust
let locked_base = pll_is_locked_base(regs);
let locked_time = match lock_at_cycle {
    Some(arm) => current_cycle >= arm,
    None => false,
};
if locked_base && locked_time { regs[0] | (1 << 31) } else { regs[0] & !(1 << 31) }
```

### Concrete write semantics

After `pll_write_into` updates the backing regs:

```rust
let now_locked_base = pll_is_locked_base(new_regs);

if !now_locked_base {
    // Any write that lands in "not powered / not configured" state
    // clears the arm. Covers PWR re-assert of PD/VCOPD and
    // FBDIV → 0.
    lock_at_cycle = None;
} else if lock_at_cycle.is_none() {
    // Transitioned into "could be running" from "powered down /
    // unconfigured". Arm the counter.
    lock_at_cycle = Some(current_cycle + LOCK_DELAY_SYSCLKS);
}
// else: already armed (or already past arm time); leave it alone —
// the one-shot latch.
```

The `else: leave it alone` branch is what makes this Option C rather
than Option B. A PLL that's powered up and running continues to read
LOCK=1 even if firmware writes back-to-back PWR/FBDIV values — which
is the load-bearing simplification versus B.

### Edge case table

| Edge case | Option C behaviour | Silicon behaviour | Diverges? |
|---|---|---|---|
| `PWR = 0x2D` at reset | `lock_at_cycle = None` ⇒ LOCK=0 | LOCK=0 | No |
| `PWR = 0`, wait N, read CS | arms at write, LOCK=1 when `current >= arm` | arms counter, LOCK=1 after | No (by construction) |
| `PWR = 0`, read CS immediately | `current < arm` ⇒ LOCK=0 | counter in flight ⇒ LOCK=0 | No |
| `PWR = 0x2D` re-asserted after lock | `lock_at_cycle = None` ⇒ LOCK=0 next read | LOCK drops | No |
| `FBDIV = 0` after lock | base predicate false ⇒ LOCK=0 | LOCK drops | No |
| FBDIV change while powered | C keeps old arm (LOCK stays 1) | Silicon drops then re-locks | **Yes** — accepted gap |
| `BYPASS = 1` | base predicate unchanged (doesn't inspect BYPASS) | Unclear from datasheet we have | Flagged for §9 |
| `REFDIV = 0` | `.max(1)` in `pll_output_hz`; base predicate doesn't inspect REFDIV | Undefined behaviour on silicon | N/A — out of scope |
| Alias writes (XOR/SET/CLR) | Transition check runs on final `new_regs` post-alias-apply, same path as normal | Same | No |

### Choosing `LOCK_DELAY_SYSCLKS`

The oracle's `max_sysclks = 1500` window, with observed
`actual_sysclks = 1133` and silicon LOCK=0, implies the silicon lock
delay at boot clock is `>1133 sysclks`. Recommend `LOCK_DELAY_SYSCLKS = 2000`:

- Comfortably above 1133 so the current oracle PASSes with
  `HW LOCK=0, EMU LOCK=0`.
- Far below typical wall-clock multi-microsecond windows we'd expect
  firmware to actually poll LOCK over.
- A constant — no per-chip tuning, no registry. If a later oracle
  scenario with `max_sysclks > 2000` shows EMU reporting LOCK=1 before
  silicon, bump the constant. Cheap iteration.

Document the constant as a tunable in `common/clocks.rs` so both chips
share one source of truth:

```rust
/// PLL lock-detect delay, in sysclks. Tuned to be strictly greater than
/// what `silicon_periph_diff_rp2350 pll_sys_lock_timing` observes on
/// real RP2354 silicon (1133 sysclks at ROSC boot clock). Not a fit to
/// the datasheet's LOCK_DETECT_COUNTER field — that would require a
/// richer PWR-cycle model. See HLD `2026.04.15 - HLD - PLL LOCK Modelling.md`.
pub const PLL_LOCK_DELAY_SYSCLKS: u64 = 2_000;
```

## 5. Cross-chip strategy

The two chips today already share `pll_output_hz` and `ClockTree` via
`mdpicoem-common::clocks` (`crates/mdpicoem-common/src/clocks.rs:53`).
They differ in:

- mdrp2040 has `PllRegs = [u32; 4]`, `pll_read`, `pll_write` as
  free functions in `crates/mdrp2040/src/bus/clocks.rs:245-286`.
- mdrp2350 has the same shape but as free functions in
  `crates/mdrp2350/src/bus/peripherals.rs:6-41` (`pll_reg_index`,
  `pll_read_from`, `pll_write_into`), one tier down in naming but
  identical math.
- Bus storage is `pll_sys_regs: [u32; 4]` on both, with identical
  reset values (`PLL_RESET = [0x0000_0001, 0x0000_002D, 0, 0x0007_7000]`).

### Recommendation: put the lock predicate + the delay constant in `mdpicoem-common`, keep the per-chip plumbing local

Add to `crates/mdpicoem-common/src/clocks.rs`:

```rust
pub const PLL_LOCK_DELAY_SYSCLKS: u64 = 2_000;

pub fn pll_is_locked_base(regs: &[u32; 4]) -> bool {
    let pwr = regs[1];
    let fbdiv = regs[2] & 0xFFF;
    let pd = (pwr & 0x01) != 0;
    let vcopd = (pwr & 0x20) != 0;
    fbdiv != 0 && !pd && !vcopd
}

pub fn pll_cs_read_with_lock(regs: &[u32; 4], lock_at: Option<u64>, now: u64) -> u32 {
    let locked = pll_is_locked_base(regs) && matches!(lock_at, Some(arm) if now >= arm);
    if locked { regs[0] | (1 << 31) } else { regs[0] & !(1 << 31) }
}
```

Each chip crate then:

1. Adds `pll_sys_lock_at_cycle: Option<u64>` and
   `pll_usb_lock_at_cycle: Option<u64>` fields to its `Bus`
   (`crates/mdrp2350/src/bus/mod.rs:146-150`, mirror on mdrp2040 at
   `crates/mdrp2040/src/bus/mod.rs:118-121`).
2. Keeps its existing `pll_read*` / `pll_write*` functions — they
   still live next to the existing register-image helpers.
3. Calls `pll_cs_read_with_lock(regs, lock_at, current_cycle)` from
   the CS arm of each reader.
4. Updates the transition logic in the chip's write path.

### Why not move the whole PLL model into common

Temptation: lift `PllRegs`, `pll_read`, `pll_write` out of each chip
and into common. Reject for this HLD:

- The two crates' functions have slightly different signatures and
  names today (`pll_read_from` vs `pll_read`) for reasons this HLD
  doesn't need to unravel.
- Restructuring the read/write split is a separate refactor — likely
  worth doing alone, but coupling it to a bug fix bloats the diff and
  mixes "fix a real bug" with "tidy the surface area".
- The **only** cross-chip symmetry that the lock-modelling logic
  needs is (a) the predicate and (b) the delay constant. Those are
  pure functions of the register image, not dependent on the storage
  layout or read/write dispatch style. Common is the right home for
  those two items only.

### Trade-off

**Pro**: the predicate itself is one function, reviewed once.
**Con**: the chip-specific files each add a few lines of transition
handling. That's fine — it's where the chip-specific `Bus.cycles()`
access happens anyway.

## 6. Current-cycle plumbing

Bus does not own the master cycle today. The master clock lives on
`Emulator::clock` (`crates/mdrp2350/src/lib.rs:60`, mirrored in
`crates/mdrp2040/src/lib.rs:63`). Three plumbing options; pick one:

### Option P1 — pass `current_cycle` on each MMIO write

Change PLL reader/writer signatures to take a cycle count:

```rust
pub(crate) fn pll_sys_read(&self, offset: u32, now: u64) -> u32 { ... }
pub(crate) fn pll_sys_write(&mut self, offset: u32, val: u32, alias: u32, now: u64) { ... }
```

Caller (one layer up, in the `read32`/`write32` match on peripheral
base) has to pipe `now` in. Today that top-level dispatch doesn't know
the cycle count either — it only flows in via `Emulator::step` →
`self.cores[i].step(&mut self.bus)`.

**Pro**: no new Bus state.
**Con**: touches ~4-8 call sites per chip for a small payload.

### Option P2 — stash the cycle count on Bus before each step

In `Emulator::step` and `Emulator::run`, before routing work to the
Bus, write `bus.current_cycle = self.clock.cycles`. Bus gains one
u64 field; readers / writers consult `self.current_cycle`.

**Pro**: zero signature churn. Matches the existing shape of
`bus.ppb[core_id].update_latest_cycles(self.cores[core_id].cycles)`
(`mdrp2350/src/lib.rs:167`).
**Con**: the field can go stale between steps if anyone reads PLL
state outside of the step path. Two readers matter: the
`silicon_periph_diff_rp2350` harness (uses `emu.mmio_read32`
post-run, `mdrp2350/src/lib.rs:320`) and interactive TUI readouts.
Both read from a quiescent state where the last `step()` left
`current_cycle` accurate.

### Option P3 — Bus carries its own cycle counter, incremented when Emulator advances clock

Bus gains a `master_cycle: u64` that `Emulator::step` increments in
lockstep with `self.clock`. Readers consult `bus.master_cycle`.

**Pro**: self-contained; no "stash before use" dance.
**Con**: two cycle counters that must stay in sync. One more thing
to maintain.

### Recommendation: **P2** — stash on Bus before step

Easiest to implement, lowest diff, and the staleness window is bounded
by "the Emulator is outside a step call" — which is exactly when
`emu.mmio_read32` gets called by the harness, and the value from the
last step is correct for that context.

```rust
// crates/mdrp2350/src/bus/mod.rs, new field:
pub(crate) master_cycle: u64,

// crates/mdrp2350/src/lib.rs, in step(), first thing:
self.bus.master_cycle = self.clock.cycles;
// before each core's inner loop.
```

Updated identically in mdrp2040's `step()` around the inner loop.

## 7. Validation plan

The silicon oracle (`silicon_periph_diff_rp2350`) needs real hardware
and isn't in CI. Fast iteration must come from unit tests.

### Unit tests to add (mdrp2350 side: `crates/mdrp2350/src/tests.rs`)

All tests use `Bus::new()` + direct `bus.write32` / `bus.read32`; the
master cycle is seeded via `bus.master_cycle = N` between calls (new
field is `pub(crate)` within the crate — tests are in the crate).

1. `test_pll_cs_read_lock_zero_at_reset` — fresh `Bus::new()`, read CS
   at `master_cycle=0`. Expect `read & (1 << 31) == 0`. Supersedes
   `test_pll_cs_read_forces_lock_bit` at line 6763 (that test's
   assertion inverts).

2. `test_pll_cs_lock_zero_before_arm` — write `PWR=0`, read CS at
   `master_cycle = 100`. Expect LOCK=0.

3. `test_pll_cs_lock_one_after_arm` — write `PWR=0` at `master_cycle=0`,
   read at `master_cycle = PLL_LOCK_DELAY_SYSCLKS + 1`. Expect LOCK=1.

4. `test_pll_cs_lock_zero_with_pd_set` — `PWR = 0x01` (PD only, others
   clear), `FBDIV = 100`, `master_cycle = 10_000`. Expect LOCK=0 — PD
   gate wins regardless of time.

5. `test_pll_cs_lock_zero_with_vcopd_set` — `PWR = 0x20` (VCOPD only),
   `FBDIV = 100`. Expect LOCK=0.

6. `test_pll_cs_lock_zero_with_fbdiv_zero` — `PWR = 0`, `FBDIV = 0`.
   Expect LOCK=0 (unconfigured).

7. `test_pll_cs_lock_rearm_after_powerdown` — `PWR = 0`, advance past
   `LOCK_DELAY`, assert LOCK=1; then `PWR = 0x21` (re-assert PD+VCOPD),
   assert LOCK=0 on next read. (Confirms the non-latch path.)

8. `test_pll_cs_bypass_does_not_force_lock` — `PWR = 0`, `FBDIV = 100`,
   `BYPASS = 1` (via CS write), read before `LOCK_DELAY`. Expect
   LOCK=0 (recommendation 9.2 — unless Arthur sign-off flips this).

9. `test_pll_cs_read_preserves_refdiv` — write `CS = 0x05` (REFDIV=5),
   read CS at `master_cycle = 10_000` when locked. Expect
   `read & 0x3F == 5` — confirms we don't clobber REFDIV while
   mucking with bit 31.

10. `test_pll_cs_alias_writes_trigger_arm` — write `CS` via SET alias
    (`+0x2000`) to change REFDIV; write `PWR` via CLR alias
    (`+0x3000`) to clear power-down. Verify arm transition fires at
    the PWR CLR, not the CS SET.

11. `test_pll_prim_write_does_not_rearm` — after lock is established,
    write PRIM (different POSTDIV values). LOCK must stay 1 on the
    next read. (Guards against over-eager rearm.)

12. `test_pll_usb_independent_of_pll_sys` — arm PLL_SYS lock, verify
    PLL_USB CS reads LOCK=0 (separate backing + separate arm state).

### Silicon oracle outcome (after fix)

With `LOCK_DELAY_SYSCLKS = 2000`:

- `pll_sys_lock_timing` runs with `max_sysclks = 1500`,
  `actual_sysclks ≈ 1133` (stable CYCCNT result).
- Post-fix emulator: `PWR=0` write happens at roughly `now ≈ a few
  sysclks into the sled` (MMIO writes during setup cost a small
  handful of cycles). `lock_at_cycle ≈ few + 2000 = ~2005`.
- Readback at `now = 1133 + epsilon` (gate + readback overhead): still
  `< lock_at_cycle`, so LOCK=0 — matching HW.

The scenario's `actual_sysclks` adjustment is **not needed**. The
oracle already measures actual cycles via CYCCNT; we just need the
emulator to produce the same LOCK value at that cycle count.

If a later scenario wants to test "long enough to lock", add
`pll_sys_lock_timing_long` with `max_sysclks = 5000` and assert
LOCK=1 on both sides — that's a new scenario, not a change to the
existing one.

## 8. Risk and rollback

### Tests that touch PLL state

- `crates/mdrp2350/src/tests.rs:6685-6785` — Clock Tree V2 Phase B
  tests. Most configure PLL and read `sys_clk_hz()` / `pll_sys_regs`
  directly, not CS[31]. One test explicitly asserts CS[31]=1
  (`test_pll_cs_read_forces_lock_bit` at 6763). Update its
  assertion — exactly the kind of "this test was locking in the bug"
  that we want to flip.
- `crates/mdrp2040/src/bus/clocks.rs:387-391` —
  `pll_forces_lock_bit_on_read`. Invert.
- `crates/mdpicoem-harness/src/silicon_scenarios.rs:260-265` —
  `pll_sys_lock_timing` scenario. No code change; expected result
  flips from FAIL to PASS.

### Tests that assume LOCK=1 implicitly

A systematic grep (`Grep "CS\.LOCK|forces LOCK|1 << 31"` across
`crates/`) finds only the sites listed above. The bootrom disassembly
(`roms/rp2350/arm-bootrom.dis`) has no `while !(read & (1 << 31))` /
`ldr r, [r, #0]; lsls r, #1; bpl` shape against the PLL bases I
could see. No firmware smoke test reads PLL CS.

### Firmware smoke / full-system tests

- `crates/mdpicoem-harness/src/bin/onerom_full_system_rp2350.rs` —
  boots OneROM firmware. OneROM bypasses the bootrom (line 124-140),
  jumps straight to its image. Its clock setup may poll
  PLL.LOCK — I cannot confirm from code without disassembling the
  `.bin`. If it does, modelling sets `LOCK_DELAY_SYSCLKS` sysclks
  of busy-wait in the emulator until lock arrives. At 150 MHz target
  sys_clk, 2000 sysclks = ~13 µs; OneROM would observe that delay
  and continue. **This is the correct behaviour** — real silicon has
  this delay; the emulator previously short-circuited it.
- `crates/mdrp2040app/` smoke test — boots blinky. blinky doesn't
  configure PLL (stays on ROSC); no change.
- `crates/mdrp2040/tests/firmware.rs` — boot paths, no direct PLL
  polling.

### Rollback

Single revert commit reverts both chip-crate changes and the common
addition. The `silicon_periph_diff_rp2350 pll_sys_lock_timing`
scenario goes back to FAIL. No data loss, no downstream impact —
revert is safe.

### Risk ranking

| Risk | Severity | Mitigation |
|---|---|---|
| OneROM boot stalls waiting for LOCK | Low | Delay is 2000 sysclks = microseconds; firmware polls have bounded timeouts |
| A unit test elsewhere asserts LOCK=1 implicitly | Low | Grep + test-suite run pre-merge; no matches found in survey |
| `master_cycle` staleness between step calls | Low | Stash-before-step in §6 P2 guarantees it's current at every Bus entry point |
| `LOCK_DELAY_SYSCLKS = 2000` is too short / too long | Low | Tunable constant; oracle catches drift immediately |

## 9. Out of scope

This HLD deliberately does not cover:

- **VCO frequency modelling.** `pll_output_hz` already computes VCO
  frequency correctly in `common/clocks.rs:53`; LOCK status doesn't
  depend on VCO frequency being in the datasheet's valid range
  (400 MHz–1600 MHz). Running the PLL out of spec would report LOCK=1
  under both the current bug and Option C; that's a silicon-only
  concern.
- **`LOCK_DETECT_COUNTER` field on some chips.** The RP2350 datasheet
  may expose the lock-detect counter's target as a writable field
  (per Raspberry Pi engineering docs referenced in tech forums, not
  verifiable here). Modelling it requires reading that field on
  every lock-arm calculation. Not touching until a scenario needs it.
- **BYPASS semantics.** §2 flags BYPASS=1 as ambiguous from our
  sources. Option C treats BYPASS as orthogonal to LOCK. If Arthur
  confirms BYPASS=1 forces LOCK=1 on silicon (the "bypass = always
  locked" interpretation), one-line predicate change: add
  `|| (regs[0] & (1 << 8)) != 0` to `pll_is_locked_base`.
- **REFDIV=0 handling.** The write currently stores the value; the
  math clamps `.max(1)` on read. Silicon behaviour is undefined. Not
  changing.
- **Other forced-to-1 status bits.** `xosc_read` CS STATUS
  (`peripherals.rs:179`), `rosc_read` STATUS
  (`peripherals.rs:138`), QMI `DIRECT_CSR` TXEMPTY/RXEMPTY
  (`peripherals.rs:235`) — same shape as the PLL bug. Out of scope
  for this fix; separate tech-debt items (and separate oracle
  scenarios if/when someone writes them).
- **Unifying `PllRegs` storage + read/write helpers in common.**
  Noted in §5; deferred to a follow-up refactor.
- **Modelling PLL lock re-arming on FBDIV/REFDIV change mid-run.**
  This is the Option B → C simplification delta. Listed for §8 as
  a known fidelity gap; not closed here.
