# DMA Pacing Within Step Quantum

Version: 0.1.0
Date: 2026-05-06

## 1. Problem

`crates/picoem-harness/src/onerom_glue_dma.rs` and a fork of the same file in
the mddosem project are 100-line two-channel DMA reimplementations that the
OneROM serving loop and the mddosem ROM-emulator firmware both depend on.
Both abort the real DMA peripheral (CH0/CH1) every cycle and pump the data
path themselves. Two copies of the same workaround means a fix in one will
silently rot in the other; a third consumer (PicoGUS-style ISA bridges, USB
PHY shims) would make it three.

The header comment in `onerom_glue_dma.rs` claims rp2350-emu's DMA "is too
stubbed to execute that chain faithfully." That comment is **stale**. The
DMA peripheral has the V6 CTRL bit-field map, the full DREQ matrix wired
through `Bus::collect_dreqs()` (`crates/rp2350-emu/src/bus/mod.rs:3217`),
PIO MMIO read-pop / write-push semantics
(`crates/picoem-common/src/pio/mod.rs:600` / `:669`), channel arming,
chaining, ring buffers, abort, IRQ routing, and `dma_chain_trigger` +
`dma_timer_paced` silicon coverage. The newer comment inside `GlueDma::tick`
acknowledges this directly: *"the real DMA now decodes the firmware's
TREQ_SEL = DREQ_PIO1_RX0 correctly and would race the pump for RX words
otherwise."*

So GlueDma isn't filling a behavioural gap. It's filling a **throughput**
gap. With one upstream fix, both copies of GlueDma can be deleted.

## 2. Root cause

`crates/rp2350-emu/src/dma.rs:612-619` documents `Dma::tick` as *"Advance
DMA by one system clock. Issues at most one transfer across all channels."*
That contract is intact and correct. The bug is at the **caller**.

`crates/rp2350-emu/src/bus/mod.rs:1196-1199`:

```rust
// DMA ticks after peripherals produce DREQ (HLD V5 §5.6).
if !self.is_held_in_reset_bit(RESET_DMA) {
    self.tick_dma();
}
```

`tick_peripherals(sys_clks)` advances every other peripheral by `sys_clks`
cycles in one batch (UART baud, SPI clkdiv, ADC accumulator, PIO program
steps via `pio.step_n_with_pins`). DMA is the one peripheral that gets
ticked exactly once regardless of `sys_clks`. With `step_quantum=64`,
peripherals reflect 64 cycles of progress and DMA reflects 1 cycle of
progress — an effective 1/64× DMA throughput cliff.

The OneROM serving loop programs CH0 with `TREQ_SEL = DREQ_PIO1_RX0` and
CH1 with a chain into a PIO TX FIFO. Per quantum, PIO can fill its 4-deep
RX FIFO; DMA drains exactly one entry; the FIFO sits at 3 entries.
The address-source PIO program back-pressures and the firmware stalls.
GlueDma works around the cliff by doing its own per-cycle pump from the
harness and aborting the real engine.

`step_quantum=1` masks the bug — `tick_peripherals` is invoked once per
sysclk so DMA gets one tick per sysclk by accident. This is why
`dma_chain_trigger` and `dma_timer_paced` pass: the silicon-oracle harness
pins `step_quantum=1` (`silicon_scenarios.rs:2971`). The bug is invisible
at quantum 1 and only surfaces when callers raise the quantum for
performance.

## 3. Fix

Loop the existing `tick_dma()` call inside `Bus::tick_peripherals` once
per advanced sysclk:

```rust
if !self.is_held_in_reset_bit(RESET_DMA) {
    for _ in 0..sys_clks {
        self.tick_dma();
    }
}
```

That is the entire production-path change. Three lines.

### Why this is correct

- **DMA timer accumulators (TIMER0–3).** The X/Y rate accumulator advance
  at the head of `Dma::tick` runs once per iteration. Looping advances
  them once per sysclk, matching real silicon's per-sysclk ticking. The
  existing `dma_timer_paced` scenario continues to pass (in fact gets
  more accurate; it currently advances accumulators once per quantum,
  which only happens to match because the oracle pins quantum=1).
- **DREQ snapshot freshness.** Each iteration calls
  `bus.collect_dreqs()`, so DMA writes that mutate peripheral state
  inside the loop (e.g. CH1 writing to PIO2 TXF1 fills SM1's TX FIFO and
  may de-assert `tx_dreq` on the next iteration) feed back into the next
  cycle's arbitration. This is the desired behaviour and preserves the
  HLD V5 §5.6 "snapshot then arbitrate" contract — the snapshot just
  refreshes once per sysclk inside the quantum.
- **Arbitration.** Fixed-priority lowest-index-wins is unchanged.
- **IRQ routing.** `Dma::route_irqs` runs at the end of each iteration;
  re-asserting an already-asserted shared IRQ line is idempotent.
- **Unit-test compatibility.** `Dma::tick` and `Bus::tick_dma` keep their
  single-transfer-per-call contract. The 16 dma.rs unit tests that drive
  `tick_dma()` step-by-step are unaffected.

### What this is *not*

This fix does **not** change the §5.6 ordering contract beyond the
inner-loop refresh just noted. Other peripherals still tick first for
the full quantum and only then does DMA loop. Peripheral state machines
and DMA are not interleaved at sub-cycle granularity — a `tx_dreq` that
should re-assert mid-cycle on real silicon (because a PIO program just
executed a `pull` and freed a TX FIFO slot) is not modelled at
sub-quantum resolution. PIO RX/TX FIFO depth (4 entries; 8 with FJOIN)
absorbs the imprecision for the workloads in scope. If a future workload
exposes a sub-quantum interleave divergence, that is a separate HLD.

### Cost

Each DMA-armed sysclk pays one `bus.collect_dreqs()` call (~30 trivial
method dispatches across PIO/SPI/UART/I2C/ADC dreq getters) plus a
16-entry busy scan that terminates at the first ready-and-busy channel.
Workloads with no armed channel exit the inner scan after at most 16 cheap
checks per cycle. For `step_quantum=64` with no DMA active, that's
~64×30 method calls per quantum — a handful of nanoseconds per quantum.
Acceptable. If `paced_bench_rp2350` shows regression, add an `is_idle()`
early-exit at the head of `Dma::tick`; expected hit is noise.

### Scope: Serial only

This fix applies to the Serial execution model only. The Threaded
coordinator runs its own `tick_peripherals`
(`crates/rp2350-emu/src/threaded/emulator.rs:1091`) which **does not
tick DMA at all** — `crates/rp2350-emu/src/threaded/emulator.rs:1159`
documents this as *"Peripherals::dma intentionally deferred to Phase 5
(HLD V7 §2.2)."* Threaded DMA is a deeper deferred work item, not a
per-quantum throughput cliff like Serial. OneROM and mddosem use Serial,
so the Serial-only fix unblocks both consumers. Threaded DMA is out of
scope for this HLD; tracked under HLD V7 §2.2.

`Bus::tick_peripherals` is `pub(crate)` so the §4.1 unit tests inside
the `dma.rs` `mod tests` can call it directly. The §4.2 integration
test cannot — it lives in `tests/` and goes through the public
`Emulator::run` API instead, which is fine because Serial `Emulator::run`
is built on `tick_peripherals` (see `lib.rs:843-848`).

### Watchdog tick frequency unchanged

`Bus::tick_peripherals` ends with a `self.watchdog.tick()` call
(`bus/mod.rs:1205`) outside the `if !held(RESET_DMA)` block — once per
quantum, not per sysclk. The fix does not move this. Watchdog
LOAD-down-to-zero behaviour stays as documented in HLD V5 §7.D.3
("granularity matches the paced step-quantum tick loop closely enough
for the LOAD=100 / fire-within-130-cycles test bound"). Do not move
`watchdog.tick()` into the per-cycle loop in passing.

## 4. Validation

Five layers, each catching a distinct failure mode. §4.1 unit tests
pin per-cycle semantics; §4.2's quantum-invariance integration test
gates the fix as a whole-system property; §4.3 silicon scenarios pin
PIO-DMA wiring at quantum=1; §4.4's OneROM smoke confirms cleanup
leaves real workloads working; §4.5 catches performance regressions
on no-DMA workloads.

### Argument for sufficiency

The silicon oracle harness pins `step_quantum=1` (`silicon_scenarios.rs:2971`),
so silicon scenarios alone can't gate a fix that's invisible at quantum=1.
The transitive argument used here:

- **Silicon at quantum=1** ↔ **emulator at quantum=1**: the existing oracle
  guarantees this, and §4.3 extends the wiring coverage to the PIO-DMA
  paths the new fix is meant to support.
- **Emulator at quantum=1** ↔ **emulator at quantum=N**: §4.2's
  parametric integration test gates this for each workload class.
- ⇒ **Silicon at quantum=1** ≈ **emulator at quantum=N** by composition.

This is what makes the silicon attachment load-bearing: it pins one end
of the chain while the integration test pins the other.

### 4.1 Unit tests in `crates/rp2350-emu/src/dma.rs`

Each test below targets a specific failure mode of the multi-cycle loop
that no existing test reaches. Tests 1–4 *must* fail with the change
reverted; 5–6 are guards that protect existing semantics.

**1. FORCE pacing throughput.** N transfers in N cycles. Catches
"DMA still ticked once per quantum" — the most basic regression.

```rust
#[test]
fn tick_peripherals_drains_one_transfer_per_sysclk_force() {
    let mut bus = Bus::new();
    release_dma(&mut bus);

    let src: u32 = 0x2000_0100;
    let dst: u32 = 0x2000_0300;
    for i in 0..64u32 {
        bus.write32(src + i * 4, 0xCAFE_0000 + i, 0);
    }

    bus.write32(DMA_BASE, src, 0);
    bus.write32(DMA_BASE + 0x04, dst, 0);
    bus.write32(DMA_BASE + 0x08, 64, 0);
    let ctrl = make_ctrl(true, 2, true, true, 63, 0, 0, false);
    bus.write32(DMA_BASE + 0x0C, ctrl, 0);

    bus.tick_peripherals(64);

    for i in 0..64u32 {
        assert_eq!(bus.read32(dst + i * 4, 0), 0xCAFE_0000 + i, "word {i}");
    }
    assert_eq!(bus.read32(DMA_BASE + 0x0C, 0) & CTRL_BUSY, 0);
}
```

**2. Timer pacing rate accuracy.** `TIMER0` X=1, Y=10 produces ~10
transfers per 100 cycles. Catches accumulator-state caching bugs (e.g.
"someone hoisted timer advance outside the loop and now it advances
once per quantum"). Without the fix this completes 1 transfer in 100
cycles, not 10.

```rust
#[test]
fn tick_peripherals_advances_dma_timer_per_sysclk() {
    let mut bus = Bus::new();
    release_dma(&mut bus);

    bus.write32(DMA_BASE + 0x440, (1 << 16) | 10, 0); // TIMER0: X=1 Y=10

    let src: u32 = 0x2000_0100;
    let dst: u32 = 0x2000_0300;
    for i in 0..16u32 {
        bus.write32(src + i * 4, 0x1000 + i, 0);
    }
    bus.write32(DMA_BASE, src, 0);
    bus.write32(DMA_BASE + 0x04, dst, 0);
    bus.write32(DMA_BASE + 0x08, 16, 0);
    let ctrl = make_ctrl(true, 2, true, true, 59, 0, 0, false); // TREQ_SEL = TIMER0
    bus.write32(DMA_BASE + 0x0C, ctrl, 0);

    bus.tick_peripherals(100);

    // 100 sysclks at 1/10 rate ⇒ 10 transfers fired. 6 remaining.
    let intr = bus.read32(DMA_BASE + REG_INTR, 0);
    assert_eq!(intr & 1, 0, "channel must still be in flight");
    let busy = bus.read32(DMA_BASE + 0x0C, 0) & CTRL_BUSY;
    assert_ne!(busy, 0);
    for i in 0..10u32 {
        assert_eq!(bus.read32(dst + i * 4, 0), 0x1000 + i, "word {i}");
    }
    assert_eq!(bus.read32(dst + 10 * 4, 0), 0, "word 10 must be untouched");
}
```

**3. PIO RX pacing — DREQ feedback inside the loop.** Pre-fill PIO0
SM0 RX FIFO with 4 words via the test-only `push_rx`, arm CH0 with
TREQ_SEL=DREQ_PIO0_RX0 and TRANS_COUNT=16, run `tick_peripherals(64)`.
Expect exactly 4 transfers (FIFO is empty after the 4th and SM0 is
disabled so doesn't refill); BUSY remains. Catches `collect_dreqs`
caching outside the loop — without per-cycle re-snapshot DMA would
either drain past empty (reading zeros) or stop on cycle 1.

**4. Chain trigger fires mid-quantum.** CH0 TRANS_COUNT=4, CHAIN_TO=1;
CH1 pre-programmed via AL1 (no trigger), TRANS_COUNT=4. Run
`tick_peripherals(8)` once. Expect both channels complete, both INTR
bits set, both destination buffers populated. Catches "chain only fires
on the next quantum boundary."

**5. `sys_clks=0` does nothing.** Guards against a `0..n` ⇒ `0..=n`
typo that would shift behaviour by one cycle.

**6. DMA in reset is silent.** RESETS_RESET bit 2 set + armed channel
+ `tick_peripherals(64)` ⇒ no transfers, BUSY unchanged. Guards the
`is_held_in_reset_bit` gate.

### 4.2 Quantum-invariance integration test

`crates/rp2350-emu/tests/dma_quantum_invariance.rs`. Same shape as the
existing `dual_model.rs`. Asserts that for each workload class, the
end-state after running a fixed number of total sysclks is independent
of `step_quantum`. This is the strongest gate — it catches any bug
that produces a quantum-dependent result, regardless of mechanism.

```rust
const QUANTA: &[u32] = &[1, 4, 16, 64, 256];
const TOTAL_CYCLES: u64 = 768; // 3 × max(QUANTA) — divides every quantum

#[derive(Debug, PartialEq, Eq)]
struct Snapshot {
    sram_window: Vec<u8>,           // 0x2000_0000..0x2000_1000 — covers all
                                    //   workload src/dst regions
    intr: u32, inte0: u32, inte1: u32, ints0: u32, ints1: u32,
    chans: [(bool, u32, u32, u32, u32); 16], // (busy, trans_count,
                                             //  read_addr, write_addr, ctrl)
    pio_rx_levels: [[u8; 4]; 3],    // per (block, sm) RX FIFO occupancy
    pio_tx_levels: [[u8; 4]; 3],    // per (block, sm) TX FIFO occupancy
}

fn run_workload(quantum: u32, setup: fn(&mut Emulator)) -> Snapshot {
    let mut emu = EmulatorBuilder::new(Config::default())
        .step_quantum(quantum)
        .build()
        .unwrap();                   // Serial — fix only applies to Serial
    emu.core_mut(0).halt();
    emu.core_mut(1).halt();
    setup(&mut emu);
    emu.run(TOTAL_CYCLES).expect("Serial run is infallible");
    Snapshot::capture(&emu)
}

#[test]
fn dma_end_state_invariant_across_step_quantum() {
    let workloads: &[(&str, fn(&mut Emulator))] = &[
        ("force_64",       setup_force_64_words),       // FORCE pacing,
                                                        //   64 transfers
        ("timer_x1_y10",   setup_timer_paced),          // TIMER0 1/10,
                                                        //   ~76 transfers
                                                        //   in 768 cycles
        ("pio_rx_drain",   setup_pio_rx_paced),         // pre-filled
                                                        //   PIO0 RX,
                                                        //   stalls when
                                                        //   empty
        ("chain",          setup_chain_4_then_4),       // CH0 → CH1
                                                        //   chain
        ("two_armed",      setup_two_channels_armed),   // CH0 + CH2,
                                                        //   different
                                                        //   pacing
    ];
    for (name, setup) in workloads {
        let reference = run_workload(1, *setup);
        for &q in &QUANTA[1..] {
            let result = run_workload(q, *setup);
            assert_eq!(
                result, reference,
                "workload '{}' diverged at quantum={}", name, q
            );
        }
    }
}
```

**Cycle-count alignment.** `TOTAL_CYCLES = 768` is `3 × 256`, which
divides every quantum in `QUANTA`. This avoids `emu.run`'s round-up
behaviour producing different actual master-cycle counts per quantum
(`lib.rs:843-848` runs while `clock.cycles < target`, so partial
quanta short the run). Without alignment, a 100-cycle target at
quantum=64 runs for 64 cycles (one quantum stops above target) but
quantum=1 runs exactly 100 — different master-cycle counts means
different end-states even with a correct fix. The `3×` multiplier is
to give workloads room to complete or settle into a steady stall
state.

**Snapshot contents.** Compared by `PartialEq`. Five workloads × four
non-reference quanta = 20 invariance assertions per run. `chans` covers
every channel (most idle, all-zero); `pio_*_levels` covers PIO state
that DMA writes/reads can mutate. Other peripheral state (UART, SPI,
etc.) is zero in these workloads and excluded for diff legibility.

**Workload setup notes.** All five `setup_*` functions program DMA via
`bus.write32(DMA_BASE + …)` directly — no firmware running on the
cores (cores halted at start). For `pio_rx_drain`, the SM is left
disabled so it doesn't refill; pre-fill via `bus.pio[0].push_rx(0, …)`
(test-hook, in scope under `#[cfg(test)]`).

### 4.3 Silicon scenarios (regression coverage at quantum=1)

Add two to `crates/picoem-harness/src/silicon_scenarios.rs`. Each
exercises a wiring path that the existing `dma_chain_trigger` and
`dma_timer_paced` don't reach. Both run at quantum=1 and serve as
ground-truth pins for §4.2's transitive argument. The OneROM-shape
chain idiom is left to §4.4 — see the closing note in this section
for why.

#### 4.3.1 `dma_pio_rx_paced`

DMA CH0 paced on `DREQ_PIO0_RX0`, draining a PIO0 SM0 RX FIFO into
SRAM. Covers: `DREQ_PIO_RXn` assertion + the DMA-side MMIO read
against PIO RXFn that pops a word.

PIO0 SM0 program (3 instructions, autopush enabled in shiftctrl):

```pio
.wrap_target
    set x, 4         ; constant payload — small set immediate, repeats
    in  x, 32        ; shifts X into ISR
    push noblock     ; auto-push variant via SHIFTCTRL.AUTOPUSH=1
.wrap
```

(Final encoding chosen to match what the existing `pll_sys_lock_timing`
+ `dma_chain_trigger` sled-builders use for raw `u16` PIO instruction
words. The choice of constant doesn't matter — the observable is "8
identical words landed in SRAM at consecutive addresses and DMA INTR
bit 0 is set." A counter program is one extra instruction if a
varying payload is wanted later.)

Setup writes:

- Reset clear `RESET_PIO0`.
- Write the 3-instruction program to PIO0 INSTR_MEM[0..3].
- Configure PIO0 SM0: `SHIFTCTRL.AUTOPUSH=1`, `IN_BASE=...` arbitrary,
  default clkdiv (sysclk/1).
- Enable PIO0 SM0 via `CTRL.SM_ENABLE`.
- Program DMA CH0: `READ_ADDR = PIO0_BASE + 0x020` (RXF0, no incr),
  `WRITE_ADDR = sram_dst` (incr), `TRANS_COUNT = 8`,
  `CTRL = EN | DATA_SIZE=word | INCR_WRITE | TREQ_SEL=4 | CHAIN_TO=self`.
- The CTRL_TRIG write arms and triggers CH0; sled busy-polls
  `CHn_CTRL_TRIG.BUSY` until clear, then BKPT.

Observables (diffed against silicon):

- The 8-word destination buffer at `sram_dst`.
- `DMA.INTR` bit 0 set.
- `DMA.CHn_CTRL_TRIG.BUSY` cleared.

`min_sysclks` and `max_sysclks` are calibrated by running once on
silicon and reading `actual_sysclks` from the oracle output. Pick
`min ≈ 0.5×` and `max ≈ 4×` of measured. Calibration belongs in the
implementation PR, not in this HLD.

#### 4.3.2 `dma_pio_tx_paced`

Mirror of 4.3.1, opposite direction. DMA CH0 paced on
`DREQ_PIO0_TX0`, sourcing 8 words from SRAM and pushing them to PIO0
SM0 TX FIFO. PIO0 SM0 runs an `OUT pins, 32` / `pull` program that
consumes the FIFO so DREQ stays alive. Covers the `tx_dreq` getter
+ the DMA-side MMIO write against PIO TXFn that pushes a word.

Observables: PIO0 TX FIFO empty after the run, `DMA.INTR` bit 0
set, the SM's `TXSTALL` bit not set (it consumed everything), and a
GPIO pin sample showing the last pushed word's LSB on the OUT base
pin.

**Why no isolated chain scenario.** The OneROM idiom (CH0 paced on
PIO RX writing CH1.READ_ADDR while CH1 fires on PIO TX) is exactly
what `onerom_full_system_rp2350` exercises — the OneROM firmware
solves the synchronisation problem (initial address values, both
channels armed before either fires, etc.) that an isolated test would
have to redo from scratch. Two further wrinkles: writing
`CH1.AL3_READ_ADDR_TRIG` repeatedly does *not* re-arm CH1 once
`trans_count` reaches 0 (`dma.rs:531-535` calls `trigger_channel`,
which gates on `trans_count > 0`); and the OneROM idiom relies on a
large CH1.TRANS_COUNT pre-armed at start, with CH0 just updating
`CH1.READ_ADDR` without triggering — a setup whose initial-cycle race
between CH1's first fire and CH0's first read_addr write makes for a
fragile test outside the firmware's real synchronisation. The full
chain is gated by §4.4 instead.

### 4.4 End-to-end smoke (post-cleanup)

After §5 deletes `onerom_glue_dma.rs` and rewires the OneROM
binaries, run `onerom_full_system_rp2350` against the attached probe.
Expected: the firmware boots and serves bytes through the real DMA
peripheral, with no harness-side pump. This is the integration check
that ties the unit / quantum-invariance / silicon-wiring pieces back
to a concrete user, and it is the de facto chain-idiom test (see
§4.3 closing note for why no isolated chain scenario lives in §4.3).

### 4.5 Performance sanity check

After the fix lands, run `paced_bench_rp2350` with a CPU-only
workload (no DMA armed) at `--step-quantum 64`. Expected: no
measurable regression vs pre-fix, since `Dma::tick` early-returns
when no channel is busy after at most a 16-entry scan + one
`collect_dreqs` per cycle. If a regression shows, add an
`if self.is_idle() { return; }` short-circuit at the head of
`Dma::tick` (after the timer-accumulator advance, since timer state
must still tick). This is a one-line follow-up, not a blocker.

## 5. Cleanup

After §4.1, §4.2, §4.3 pass:

1. Delete `crates/picoem-harness/src/onerom_glue_dma.rs`.
2. Remove its `pub mod onerom_glue_dma;` line in
   `crates/picoem-harness/src/lib.rs`.
3. Update binaries that previously instantiated `GlueDma` to drive the
   real DMA peripheral instead. Search-and-remove targets are
   `GlueDma::new()`, `prime_after_sync`, `glue.tick(&mut bus)`, and the
   per-cycle CH0/CH1 abort calls those binaries issue to keep the
   stand-in pump uncontested. Identified consumers (from a quick grep):
   `onerom_full_system_rp2350`, `onerom_serving_oracle_rp2350`,
   `onerom_serving_oracle_cpu_rp2350`, `picogus_diff_rp2040` (uses the
   shape but on rp2040; out of scope here — see §6 last bullet).

mddosem's GlueDma deletion lives outside this repo and is the consumer's
responsibility once picoem ships this change.

## 6. Out of scope

- **Sub-quantum interleaving of peripherals and DMA.** §3 documents this
  as preserved-as-is.
- **CRC sniff, byte-swap, HIGH_PRIORITY, DMA_IRQ_2/3, read/write-error
  IRQs.** Listed as V1 gaps in the master HLD; remain V1 gaps.
- **`Bus::collect_dreqs()` caching / incremental update.** Possible perf
  optimisation. Not needed today.
- **Per-cycle interleaving of `Bus::tick_peripherals` itself** (UART,
  SPI, etc., currently batched per quantum). Out of scope; the fix
  loops only DMA.
- **`FJOIN_RX` 8-deep PIO FIFO modelling.** New scenario uses default
  4-deep configuration.
- **rp2040-emu equivalent.** The mddosem firmware targets RP2350; the
  rp2040-emu bus has the same per-quantum DMA call shape but no current
  consumer is hitting the cliff. PicoGUS uses a different shape (the
  diff harness builds its own ISA replayer, not a GlueDma). If a real
  rp2040-emu consumer surfaces the cliff later, mirror this change there
  in a follow-up.
- **Threaded DMA.** The Threaded coordinator's `tick_peripherals` does
  not tick DMA at all (`threaded/emulator.rs:1159` —
  *"Peripherals::dma intentionally deferred to Phase 5 (HLD V7 §2.2)"*).
  This is a deeper deferred work item, not the per-quantum throughput
  cliff this HLD fixes. OneROM and mddosem use Serial. Threaded DMA
  remains as previously scheduled; this HLD does not advance it.
- **`AL3_READ_ADDR_TRIG` re-arm semantics.** In the current emulator,
  writing `CH_AL3_READ_ADDR_TRIG` calls `trigger_channel` which gates
  on `trans_count > 0` — so a completed channel is not re-armed by
  another AL3 write. Real silicon may behave differently; the OneROM
  firmware does not rely on AL3-trigger re-arming (it sets a large
  `TRANS_COUNT` once and uses non-triggering `CH_READ_ADDR` writes from
  CH0). Out of scope here; flag for a separate HLD if a future workload
  hits it.

## 7. Implementation order

1. **Add the §4.1 unit tests first, against the unchanged code.**
   Tests 1–4 must FAIL on current main; 5–6 must PASS. This proves
   the tests gate what they claim to.
2. Apply the §3 three-line change. Tests 1–4 flip to PASS; 5–6 stay
   PASS.
3. Add the §4.2 quantum-invariance integration test. Should pass on
   the fixed code for all five workloads × four non-reference quanta.
4. Add the two §4.3 silicon scenarios (`dma_pio_rx_paced`,
   `dma_pio_tx_paced`). Calibrate `min/max_sysclks` from one silicon
   run each.
5. §4.5 perf sanity: `paced_bench_rp2350` no-DMA workload at
   `--step-quantum 64`. Expect no regression; if regression appears,
   add the `is_idle()` early-exit and re-run.
6. Run `onerom_full_system_rp2350` and other GlueDma consumers with
   the fix in place but GlueDma still wired up. Expect zero
   behavioural regression — this is the smoke that the fix doesn't
   break the workaround it's meant to replace.
7. Apply §5 cleanup. Delete GlueDma and its consumers' wiring.
8. Re-run the consumers from step 6 (§4.4). Expect parity — they now
   drive the real DMA peripheral end-to-end. This is the gate that
   the chain idiom works without the harness-side stand-in.
