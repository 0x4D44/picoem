## 1. Problem

### 1.1 Observed error text

```
fatal: An ARM specific error occurred.
```

From `probe_diff_rp2040.rs:60`, via `eprintln!("fatal: {e}")` in `main()`. No further context. The `{e}` formatter drops the `source()` chain, so the underlying `ArmError` variant is invisible.

### 1.2 Call site

`crates/mdpicoem-harness/src/bin/probe_diff_rp2040.rs:414–420`:

```rust
let mut session = match args.probe.as_ref() {
    None => Session::auto_attach("rp2040", SessionConfig::default())?,
    Some(selector) => {
        let probe = Lister::new().open(selector.clone())?;
        probe.attach("rp2040", Permissions::default())?
    }
};
```

Fails at attach, before `core.reset_and_halt` on line 426. `core(0)` is not reached.

### 1.3 Where the ArmError variant originates

String `"An ARM specific error occurred."` is the `Display` text of `Error::Arm(#[source] ArmError)` (`third_party/probe-rs-0.31.0-mdrp-patched/src/error.rs:14–15`). `#[source]` (not `#[from]`) means the inner `ArmError` is only on the `source()` chain and is NOT included in `{}` formatting — hence the bare outer message.

`Error::Arm(_)` is produced by `impl From<ArmError> for Error` at `error.rs:85–94`.

### 1.4 Crucial upstream fact — fork already enforces the firmware denylist

Verified 2026-04-22 via `gh`:
- **probe-rs#2696** — CLOSED 2025-05-19, stateReason COMPLETED. Root cause attributed to old Raspberry Pi debugprobe firmware in comments.
- **probe-rs#2950** — CLOSED 2025-06-22 by **PR#3252 "Reject old RPi debugprobes"** (MERGED). PR body: "Closes #2950 as the 2.22 firmware seems to work just fine."
- **probe-rs#1849** — CLOSED 2024-11-22, stateReason COMPLETED.
- **probe-rs PR#3578** — OPEN, empty body, titled "Fix 3257"; touches `select_ap_and_ap_bank` call site (Track A.2 territory, not A.1).

PR#3252 added a denylist in `cmsisdap/tools.rs` that rejects any probe with VID:PID `2e8a:000c` and `device_version < 0x0220` (firmware 2.2.0). **This patch is already in our fork** at `third_party/probe-rs-0.31.0-mdrp-patched/src/probe/cmsisdap/tools.rs:325–349`, called from both the v2 (`:290`) and v1/HID (`:458`) open paths.

**Implication.** Because the denylist is already active in our build, the observed "An ARM specific error occurred." cannot be caused by pre-2.2.0 firmware: such a probe would fail earlier with `CmsisDapError::ProbeFirmwareOutdated("2.2.0")`, producing an error whose Display text names the firmware version. Ours does not — so our probe is already ≥ 2.2.0, and the remaining possibilities are:

- **C1 — firmware variant escaped the denylist.** The denylist is a single < 0x0220 check; some 2.2.x / 2.x variant could have a latent bug not caught.
- **C2 — genuinely fresh bug.** Not filed upstream; our silicon, our host, our exact firmware combination exposes a path upstream hasn't seen yet.
- **C3 — upstream regression.** Bug landed in probe-rs between when the original firmware-rejection PR merged (2025-06-22) and our fork point (0.31.0), or in our own patched code.
- **C4 — transient hardware / timing.** Unrelated to firmware or software; USB re-enumeration flake, power-rail glitch, static state in a prior session.
- **C5 — harness plumbing drift.** Something about how `probe_diff_rp2040` constructs the attach call differs from the probe-rs CLI `info --chip RP2040` path.

**D9 is therefore half-correct** — stale-issues framing is the wrong diagnostic because those issues are closed, but it's NOT the case that "upgrade to 2.x" is the universal fix: our rig must already be at 2.2.0+. Phase 0a will confirm the firmware version anyway (nearly free), but the decision logic differs from the first-draft HLD.

## 2. Hypothesis space (trimmed)

Since the firmware is almost certainly ≥ 2.2.0, the hypothesis space narrows to an ArmError-variant-first question:

- **H1 — `DebugPort(NoAcknowledge)` on TARGETSEL / DPIDR.** Consistent with C1/C2; multidrop handshake still fragile for some 2.2.x variant.
- **H2 — `Other("Target ID and DLPIDR do not match...")`.** The explicit guard at `src/architecture/arm/sequences/mod.rs:1056–1065`; consistent with C1/C2 and with a probe that's been touched since last cold boot.
- **H3 — `Timeout`.** Power-up wait for `CDBGPWRUPACK`/`CSYSPWRUPACK` never completes; C4 flavoured.
- **H4 — `Probe(Cmsisdap(ProbeFirmwareOutdated("2.2.0")))`.** Only possible if our host actually DOES have pre-2.2.0 firmware; the outer Display text would contain the firmware-version message rather than the bare "ARM specific error" text, so this is unlikely — but Phase 0a rules it out deterministically in one command.
- **H5 — transient flake recoverable by simple retry.** C4; 1 in 3 attach attempts fails.
- **H6 — harness-only drift.** C5; `Session::auto_attach("rp2040", ..)` vs probe-rs CLI `info --chip RP2040 --probe ...` take subtly different code paths, and ours hits a hole theirs doesn't.

**Rejected:**
- Pre-2.2.0 firmware as the primary root cause (§1.4 above).
- Chip-registry lookup issues (previous HLD §2 H6; same rationale — lowercase lookup is fine).
- Stale-BP issues blocking attach (FPB clear happens post-attach).

## 3. Phase 0a — Probe firmware fingerprint (BLOCKING, ~10 min)

**Goal:** get a definitive reading of the probe's `bcdDevice` / firmware version and confirm whether it's the one we think it is.

**Rationale:** the denylist already gates on < 0x0220, so if the probe presents at all, firmware is ≥ 2.2.0. But we want to know the *exact* version for three reasons:

1. Sanity-check that the denylist is actually being exercised (if we're somehow on a pre-2.2.0 probe we'd expect `ProbeFirmwareOutdated` long before any attach begins — getting further than that is itself signal).
2. Make the firmware fingerprint part of the triage record so Phase 1 conclusions are reproducible.
3. If a newer firmware exists upstream (e.g. 2.3.x) and ours is 2.2.0 flat, the cheapest fix is "upgrade to latest debugprobe firmware" before proceeding to any code change.

**Three methods the impl agent can use — pick whichever works first:**

**Method 1 — PowerShell (zero-install, Windows-native):**

```powershell
Get-PnpDevice -PresentOnly |
    Where-Object { $_.InstanceId -like "*VID_2E8A&PID_000C*" } |
    ForEach-Object {
        $hw = (Get-PnpDeviceProperty -InstanceId $_.InstanceId -KeyName 'DEVPKEY_Device_HardwareIds').Data
        [PSCustomObject]@{
            FriendlyName = $_.FriendlyName
            InstanceId   = $_.InstanceId
            HardwareIds  = $hw -join ' ; '
        }
    } | Format-List
```

The `InstanceId` / `HardwareIds` strings contain `REV_0222` (or similar) — that's the `bcdDevice` in hex, 4 digits, so `0222` = 2.22, `0220` = 2.2.0, `0100` = 1.0, etc.

**Method 2 — probe-rs CLI (if the fork binary has been built):**


`probe-rs list` prints the probe's `bcdDevice` via the nusb `device_version()` it already calls in the denylist path.

## 4. Phase 0b — Diagnostic fidelity (BLOCKING, ~15 min, lands first)

*Addresses D11.*

**Goal:** land a standalone one-line commit that replaces `eprintln!("fatal: {e}")` in `probe_diff_rp2040.rs:60` with a source-chain walker, so Phase 1 can read the real `ArmError` variant from a single binary re-run — no probe-rs CLI dance required.

**Scope:** exactly one file, three-ish lines of change. No test changes, no HLD references.

**Proposed change (impl agent writes real code):**

```rust
// probe_diff_rp2040.rs:59–62 (before)
if let Err(e) = run() {
    eprintln!("fatal: {e}");
    std::process::exit(2);
}

// after
if let Err(e) = run() {
    eprintln!("fatal: {e}");
    let mut source = std::error::Error::source(&*e);
    while let Some(s) = source {
        eprintln!("  caused by: {s}");
        source = s.source();
    }
    std::process::exit(2);
}
```

Alternative: `eprintln!("fatal: {e:#}")`. Impl agent verifies which of the two actually prints the ArmError variant (probe-rs 0.31 uses `thiserror` / `docsplay`; `:#` may or may not walk the source chain depending on which derive macro the outer `Error` enum uses). A 2-minute check with `dbg!(&e)` during development is sufficient.

**Commit message style:** `probe_diff_rp2040: print error source chain on fatal exit`.

**PR plan:** land as a single commit *before* Phase 1. No tests required — this is a diagnostic-only change in a binary entry point, and the existing `#[cfg(test)]` suite in the binary does not exercise `main()` at all (per D16; see §8).

**Exit criterion:** re-running `probe_diff_rp2040 --probe 2e8a:000c:E46410955F3C5C27` prints at least one `caused by:` line identifying the concrete `ArmError` variant.

## 6. Options (revised)

### Option F — Bounded retry around `auto_attach` (re-evaluated)

*Addresses D12.*

Not "cosmetic" if the triage matrix puts us in row 6 (flaky attach, no other discriminator). If firmware is known-good per Phase 0a and the bug is intermittent, a 3× retry with a 250–500 ms backoff around the attach call IS a correct fix — transient-state masking is a legitimate layer. The devils-advocate's D12 point stands: dismissing this as "masking" is a category error when the underlying failure is a hardware-level race that probe-rs code cannot fix.

**Shape:**

```rust
// Pseudocode; impl agent writes real code.
fn attach_with_retry(
    selector: Option<&DebugProbeSelector>,
    chip: &str,
    max_attempts: usize,
) -> Result<Session, probe_rs::Error> {
    let mut last_err = None;
    for attempt in 0..max_attempts {
        if attempt > 0 {
            std::thread::sleep(Duration::from_millis(300));
        }
        let result = match selector {
            None => Session::auto_attach(chip, SessionConfig::default()),
            Some(sel) => Lister::new().open(sel.clone())
                .map_err(probe_rs::Error::from)
                .and_then(|p| p.attach(chip, Permissions::default())),
        };
        match result {
            Ok(s) => return Ok(s),
            Err(e) => last_err = Some(e),
        }
    }
    Err(last_err.expect("at least one attempt"))
}
```

- **Delta:** ~15 lines in `probe_diff_rp2040.rs`.
- **Blast radius:** one binary.
- **Pro:** tiny; defensible against C4/H5 specifically; no fork divergence.
- **Pro:** if Phase 0b shows the ArmError variant is deterministic (same text on every retry), Option F will *not* mask it — the retry exhausts and surfaces the same error. The diagnostic-fidelity commit still wins. No downside.
- **Con:** does nothing for C1/C2/C3 (genuine deterministic bugs).
- **When to pick:** Triage matrix row "flaky (1/3 or 2/3 pass)".

### Option A — `attach_under_reset`

Alternate attach semantic. Reframed per devils-advocate: **this is not a workaround for a known bug**, it's a different attach method that happens to be defensible for this binary regardless of whether the underlying attach has a bug or not (we want a deterministic post-reset chip state for ISA differential tests).

**Shape:**

```rust
let mut session = match args.probe.as_ref() {
    None => {
        // No `auto_attach` equivalent of `attach_under_reset`; route via Lister.
        let probe = Lister::new()
            .list_all()
            .into_iter()
            .next()
            .ok_or("no probes found")?;
        let probe = probe.open()?;
        probe.attach_under_reset("rp2040", Permissions::default())?
    }
    Some(selector) => {
        let probe = Lister::new().open(selector.clone())?;
        probe.attach_under_reset("rp2040", Permissions::default())?
    }
};
```

- **Delta:** ~15 lines in `probe_diff_rp2040.rs`.
- **Blast radius:** one binary.
- **Pro:** semantic fit with the binary's intent (differential tests over known-clean state).
- **Pro:** no fork divergence.
- **Con:** requires RESET line wiring on the carrier board. Pico V1 exposes RUN on a solder pad; impl agent confirms during Phase 2.
- **When to pick:** Triage matrix row "`probe-rs reset --connect-under-reset` succeeds" (rows 4 or 5).

### Option B — Probe-rs vendored patch (sub-shape decided at triage time)

*Addresses D13 (acknowledge PR#3578), D14 (pick sub-shape now).*

**Open upstream context.** PR#3578 ("Fix 3257") is open, empty body, improves the panic message at `select_ap_and_ap_bank` — a Track A.2 site, not an A.1 site. If Option B goes ahead, the patch lands in `vendor/raspberrypi/sequences/rp2040.rs` or `architecture/arm/sequences/mod.rs`, which does not collide with PR#3578. We do NOT promise to submit an upstream PR for A.1 unless we have a reproducer on a probe+host combination other than our own — upstream closed #2696 and #2950, so without fresh evidence we'd be submitting noise.

**Sub-shape selection from §5.3 triage — decided here, not "re-HLD later":**

- **B1 — Override `Rp2040::debug_port_setup` with a hardened multidrop handshake.** Add the override to `third_party/probe-rs-0.31.0-mdrp-patched/src/vendor/raspberrypi/sequences/rp2040.rs` (currently only `reset_system` is overridden). The hardened version does a stricter SWD line-reset → dormant wake → TARGETSEL → DPIDR with explicit retries and a longer guard on the DLPIDR check at `sequences.rs:1056–1065`. **Pick when:** H1 or H2 confirmed with `DebugPort(NoAcknowledge)` or `Other("Target ID and DLPIDR do not match")`.
- **B2 — Tune `RESET_RECOVERY_TIMEOUT` / `NUM_RETRIES`.** In `src/architecture/arm/sequences/mod.rs:547,979-980`, bump the constants for multidrop specifically — conditionalise on `DpAddress::Multidrop(_)`. Smallest possible patch. **Pick when:** H3 confirmed (`Timeout` on power-up ACK).
- **B3 — Pre-attach Rescue DP reset.** Explicitly poke `RESCUE_DP` (0xf1002927) before the first `debug_port_setup` runs. Larger patch, mimics OpenOCD's `reset halt` path. **Pick when:** cold-boot succeeds but warm-run fails with a DP-state variant (C4 + H1).

- **Delta:** 20–50 lines in the patched fork.
- **Blast radius:** probe-rs fork; transparent to all harness consumers via `[patch.crates-io]`.
- **Pro:** fixes the real bug, not just our binary.
- **Con:** carries fork surface area. If upstream ships a fix in a future release, we rebase.
- **When to pick:** Triage matrix rows 1, 2, 3 (concrete DP-layer variants, `probe-rs info` also fails).

## 7. Recommendation

**Sequential, not gated sign-off:**

1. **Phase 0a (§3)** — run the firmware fingerprint. If the probe is at 0x0220 flat, upgrade the firmware to latest Raspberry Pi `debugprobe` release and re-test. If green, **end A.1**. If > 0x0220 or upgrade doesn't help, continue.
2. **Phase 0b (§4)** — land the source-chain diagnostic fix as a standalone commit. This is a prerequisite for Phase 1.
3. **Phase 1 (§5)** — re-run the binary to capture the real `ArmError` variant; run the CLI cross-check; fill in the triage matrix row.
4. **Phase 2** — implement exactly one of Option F (flaky), Option A (under-reset works), or Option B sub-shape (probe-rs bug). Options are NOT stacked; pick one.
5. **Phase 3** — hardware verification per §8, journal, close.

**Primary expectation — what's most likely to happen.** Given that the fork's denylist has already filtered old firmware and upstream closed #2696/#2950 as fixed, the most probable outcomes are (a) firmware upgrade fixes it at Phase 0a, (b) Option F (retry) if flaky, or (c) Option A if under-reset consistently works. Option B would be the least likely — it implies a genuinely fresh bug, which is possible but unusual given upstream's attention to this probe.

## 9. Test plan / acceptance criteria

*Addresses D15 (hard numeric floor) and D16 (silicon is the only oracle).*

### 9.1 Phase 0a acceptance

- Probe firmware `bcdDevice` value is recorded in the journal (4 hex digits).
- If < 0x0220 observed: escalate; A.1 is moot.
- If = 0x0220: firmware upgraded to latest Raspberry Pi `debugprobe` release; re-test below.
- If > 0x0220: continue to Phase 0b.

### 9.2 Phase 0b acceptance

Re-running the binary prints at least one `caused by:` line with a concrete `ArmError` variant (e.g. `DebugPort(...)`, `Timeout`, `Other(...)`). If the new code path is exercised and no source is printed, the fix is wrong — investigate before proceeding.

### 9.3 Phase 1 acceptance

One row of the §5.3 triage matrix is marked; the chosen Option (F, A, or B) is identified. Journal captures the raw `caused by:` text plus the CLI command outputs.

### 9.4 Phase 2 (silicon) acceptance

**PASS criterion (hard floor):**

1. `cargo run -p mdpicoem-harness --release --bin probe_diff_rp2040 -- --probe 2e8a:000c:E46410955F3C5C27` attaches without error.
2. Summary line reports **`Passed: N, Failed: 0, Skipped: 0, Undef: 0`** with **`N ≥ 100`**.

**That's the floor.** If attach succeeds but N < 100 — either because filter gaps convert most cases to `UndefOnSilicon`, or because most tests FAIL — A.1 is NOT complete. Investigate the filter / semantic gap within A.1's scope before landing. The point of this binary is to serve as an ISA differential oracle; an attach that produces no usable oracle output is a no-op.

**Acceptable caveats (journal, don't block):**
- A small number of FAILs (single-digit) that are obviously filter-gap or emulator divergences unrelated to the attach path — journal them for future triage, they don't block landing.
- Skips = 0 is required — a `[SKIP]` means a probe-rs error during an individual case, which is exactly the symptom we're trying to fix, so any Skip > 0 is a regression.

### 9.5 Regression

`cargo run -p mdpicoem-harness --release --bin probe_diff_rp2350 -- --fuzz 10 --probe 2e8a:000c:E46410955F614129` — must remain green. (Not changed in scope here; Option A/F changes touch only `probe_diff_rp2040`. Option B changes to the probe-rs fork apply to RP2040-specific code paths or constants; re-run this to confirm no spillover.)

### 9.6 Host-test caveat (D16)

`cargo test -p mdpicoem-harness --lib --release` remains in CI but provides NO evidence about silicon attach health. The existing 20 `#[cfg(test)]` tests inside `probe_diff_rp2040.rs` are filter / classifier / arg-parse coverage; they don't exercise `main()`, `run()`, or any probe-rs call. A passing test run is necessary (no regressions in filter logic) but emphatically not sufficient. The only oracle for attach is `§9.4`.

## 10. Risk register (trimmed)

1. **R1 — Phase 0a firmware probe output is uninformative.** PowerShell method doesn't print bcdDevice on every Windows version. Fallback: `probe-rs list` via the fork binary, or the tiny Rust smoke. Three methods = enough redundancy.
2. **R2 — Option A requires RESET wiring.** Pico V1 exposes RUN on a solder pad; if the test carrier doesn't connect it, `attach_under_reset` falls through to `attach` silently (session.rs:216–221). Impl agent checks the first run's trace for `reset_hardware_assert` being actually hit; if not, escalate.
3. **R3 — Option A changes chip state between tests.** Each test case already sets PC/SP/xPSR from scratch; the `classify_post_step_pc` bootrom classifier assumes VTOR=0 which reset-assert preserves. Document in the commit message; verify first silicon run.
4. **R4 — Option F exhausts retries and surfaces the same error.** Not a risk — that's correct behaviour. Phase 0b ensures the error is still readable.
5. **R5 — Phase 0b output doesn't include an ArmError variant name because `thiserror`/`docsplay` nests differ.** `{:#}` and the manual source walker handle different derive flavours; impl agent tries the manual walker first (unconditionally correct).
6. **R6 — Intermittent.** If the bug is flaky AND Phase 0a firmware is known good, Option F is the answer. If Phase 1 can't reproduce the failure even once, journal the state and close A.1 as "could not reproduce under controlled conditions" — don't blind-fix.
7. **R7 — Fork build of `probe-rs` CLI isn't current.** If the CLI cross-check in §5.2 uses a stale `probe-rs.exe`, results may mislead. Impl agent confirms `cargo build --release -p probe-rs --manifest-path third_party/...` is recent before trusting the CLI outputs.
