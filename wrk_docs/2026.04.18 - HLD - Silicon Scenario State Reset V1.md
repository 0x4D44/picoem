## TL;DR

Three silicon periph scenarios surfaced FAIL across the 2026-04-18 overnight soak (`pwm_wrap_irq`, `pio0_nop_loop`, `pio0_int_routing_split`). A companion HLD-4 investigation confirmed that `uart0_rx_loopback` has the **same** root cause (HW value `0x5A` is literally the payload of `S_UART0_TX_SINGLE_BYTE` — smoking gun). Root cause is structural, not emulator drift: the orchestrator's `core.reset_and_halt` fires once per **iteration**, never between **scenarios**. Fisher-Yates shuffling inside an iteration therefore lets each scenario inherit the peripheral state the prior scenario left on silicon. The emulator gets a fresh `EmulatorBuilder::new(...)` per scenario and is correct. The A.2.3 fix for `pwm_fractional_div` already used the recommended pattern — **explicit per-peripheral state reset in the scenario setup table** — and that pattern generalises trivially. We recommend **Option A (per-scenario explicit reset in the setup table), generalised via a tiny helper-const pattern for latent scenarios**; Option B (orchestrator-level per-scenario reset) is rejected because it would destroy the soak's genuine cross-scenario leakage signal. No emulator code changes.

## 1. Goal

Make every affected silicon periph scenario reproducible under Fisher-Yates soak-shuffle by asserting explicit peripheral-state reset in its `setup` table, matching the parent A.2.3 fix pattern, without disabling the orchestrator's intentional cross-iteration leakage detection.

## 2. Evidence

### 2.1 The four confirmed failure signatures

From the overnight fuzz log (`fuzz-runs/overnight-2026.04.18/rp2354-silicon.log`, seed `5831149830256`):

| Scenario | MMIO | HW | EMU | Notes |
|---|---|---|---|---|
| `pwm_wrap_irq` | `0x400A_80F4` (PWM INTR bit 0) | `0x0` | `0x1` | ~63% FAIL |
| `pio0_nop_loop` | `PIO0.SM0_ADDR` | `0x2` | `0x0` | ~100% FAIL |
| `pio0_int_routing_split` | `PIO0.IRQ0_INTS` bit 8 | `0x0` | `0x100` | ~100% FAIL |
| `uart0_rx_loopback` | `UART0.UARTDR` (`0x4007_0000`) | `0x5A`/`0xAD` | `0x42` | ~100% FAIL (bimodal) |

### 2.2 Shared root cause — per-peripheral state leakage

- **Orchestrator** (`test_rp2350_silicon.rs:1011-1020`): single `reset_and_halt` per iteration, explicitly documented as "deliberately does NOT reset between oracles within one iteration". Even within an oracle, `silicon_scenarios::run_scenario` (line 2335) only resets on `first_scenario=true`, i.e. the first case in the shuffled list.
- **Scenario runner** (`silicon_scenarios.rs:2335-2386`): for every subsequent scenario, `first_scenario=false` → no reset → only `release_common_resets` (line 2198) runs, which clears `RESET_PIO0|RESET_PIO1|RESET_PLL_SYS` if currently held. It never pulses them through a reset-then-release cycle and never touches PWM, UART, or TIMER reset bits.
- **Emulator side** (same function, line 2382): `let mut emu = EmulatorBuilder::new(Config::default()).step_quantum(1).build();` — fresh instance per scenario. PWM `CTR`=0, PIO `instr_mem[]`=0, SM state zeroed, UART FIFOs empty, `irq_flags=0`.

Per-peripheral leaked state:

- **PWM** (`pwm_wrap_irq`): `CHn_CSR.EN`==`EN[n]` is one physical bit on silicon. Setup writes `CSR=EN_BIT` *before* `TOP=100`, so DAP latency between the two ticks the counter at the prior scenario's `TOP` with `CTR` carried over.
- **PIO** (`pio0_nop_loop`): prior PIO scenario left `instr_mem[0..32]` populated. Setup writes only `instr_mem[0] = JMP 0`; slots `[1..32]` retain prior-scenario bytes.
- **PIO** (`pio0_int_routing_split`): prior scenario's `sm.pc` is non-zero, so SM0 resumes at a stale PC that runs prior-scenario opcodes, never reaching slot 0's `IRQ SET 0`.
- **UART0** (`uart0_rx_loopback`): `S_UART0_TX_SINGLE_BYTE` at `silicon_scenarios.rs:855` pushes literal `0x5A` to `UART0_UARTDR`. No scenario asserts `RESET_UART0` — TX FIFO / shift register / RX FIFO retain the `0x5A` byte when `uart0_rx_loopback` follows in the shuffle. The `0xAD` minority is a frame-boundary bit-slip in the leaked state (paper decode pending; does not change the fix shape).

### 2.3 Why the A.2.3 close-out is the right precedent

The A.2.3 residual was structurally identical: `pwm_fractional_div` showed HW=0xFE82 vs EMU=0x004C, closed by discovering that silicon's PWM CTR persisted across scenarios. The accepted fix was a three-line addition to `S_PWM_FRACTIONAL_DIV` — explicit `EN[0]=1`, `CSR=0`, `CTR=0` writes — that reduced the observable state to "known zero" before the sled armed the measurement. No emulator change. Same pattern applies to the four novel failures.

## 3. Design options

### Option A — Per-scenario explicit reset in the setup table (RECOMMENDED)

Each affected scenario's `const S_*: &[(u32, u32)]` array prepends writes that force its owned peripheral into a known state. Concretely:

- **PWM scenarios**: write `PWM_EN_OFFSET=0`, `CHn_CSR=0`, `CHn_CTR=0`, `PWM_INTR=0xF` before real configuration.
- **PIO scenarios**: pulse `RESETS_RESET + ALIAS_SET = RESET_PIO0` → `ALIAS_CLR = RESET_PIO0`. Wipes `instr_mem[]`, all SM registers, FIFOs, `irq_flags`.
- **UART scenarios**: pulse `RESETS_RESET + ALIAS_SET = RESET_UART0` → `ALIAS_CLR = RESET_UART0`. Wipes TX FIFO, RX FIFO, shift registers, CR.

**Pros:** Tiny, local, mirrors the accepted A.2.3 pattern. Emulator side unaffected. Zero orchestrator churn. Soak still exposes cross-scenario leakage for scenarios that didn't add explicit resets.

**Cons:** Doesn't prevent a future scenario from repeating the bug. Every author must remember the idiom.

### Option B — Orchestrator-level per-scenario reset hook

REJECTED. Would silence the soak loop's designed-in cross-scenario leakage signal. Also adds ~25% per-iteration cost (`reset_and_halt` × 30 scenarios × 500ms each).

### Option C — Scenario-API refactor: declare owned peripherals

DEFERRED. Overkill for 4 confirmed + 4 latent scenarios. Consider when ≥10 scenarios would benefit.

## 4. Minimal safe design — the exact changes

All edits in `crates/mdpicoem-harness/src/silicon_scenarios.rs`. No emulator source touched. No orchestrator touched.

### 4.1 Add shared-reset helper constants (near `RESETS_CLR_ALL`, ~line 1601)

```rust
/// Canonical per-slice PWM clean-state prefix for scenario setups.
const PREFIX_PWM_SLICE0_CLEAN: &[(u32, u32)] = &[
    (PWM_EN_OFFSET, 0),         // gate all slices off
    (PWM_SLICE0_CSR, 0),        // clear per-slice enable
    (PWM_SLICE0_CTR, 0),        // zero counter
    (PWM_INTR_OFFSET, 0xF),     // W1C-clear any latched wrap IRQs (4 slices)
];

/// Canonical PIO0 hard-reset pulse for scenario setups.
const PREFIX_PIO0_HARD_RESET: &[(u32, u32)] = &[
    (RESETS_RESET + ALIAS_SET, RESET_PIO0),
    (RESETS_RESET + ALIAS_CLR, RESET_PIO0),
];

/// Canonical UART0 hard-reset pulse.
const PREFIX_UART0_HARD_RESET: &[(u32, u32)] = &[
    (RESETS_RESET + ALIAS_SET, RESET_UART0),
    (RESETS_RESET + ALIAS_CLR, RESET_UART0),
];
```

These constants serve as documentation anchors. Inline the tuples into each `S_*` array (Rust const-slice concat requires macro; inline duplication is acceptable for ≤8 usages).

### 4.2 Fix `S_PWM_WRAP_IRQ` — inline `PREFIX_PWM_SLICE0_CLEAN` + reorder TOP-before-CSR_EN.

### 4.3 Fix `S_PIO0_NOP_LOOP` — prepend `PREFIX_PIO0_HARD_RESET`.

### 4.4 Fix `S_PIO0_INT_ROUTING_SPLIT` — prepend `PREFIX_PIO0_HARD_RESET` (replace the existing single-line `RESETS_CLR` release with the set-then-clear pulse pair).

### 4.5 Fix `S_UART0_RX_LOOPBACK` and `S_UART0_TX_SINGLE_BYTE` (folded-in from HLD-4) — prepend `PREFIX_UART0_HARD_RESET`.

Apply to both for symmetry (bidirectional cleanliness): whichever scenario lands first in the shuffle leaves a clean UART0 for the next.

## 6. Risks and mitigations

- **Soak-iteration time impact**: < 0.2% per iter. Acceptable.
- **Resets that miss subtle state**: PIO/UART/PWM full-peripheral RESETS wipe all architecturally-visible state. Confirmed adequate by RP2350 datasheet and existing `pio0_reset_gating_placeholder` mechanic.
- **Watchdog trigger**: No risk. 50 ms per-write timeout × 4 prefix writes × 30 scenarios = 6 s worst case; actual < 50 µs each.
- **Scenario semantic drift**: All four scenarios become strictly easier to satisfy (known-clean start); no false-positive risk.
- **A.2.2 UART fix regression**: `UARTFR` observable is fully green in the overnight log (zero divergences). The `RESET_UART0` pulse precedes the existing CLK_PERI / LCR_H / CR sequence, preserving A.2.2's logic. Verify by re-running `scenario_uart0_rx_loopback_emu_end_to_end_matches_silicon_expected` unit test post-fix.
