# Differential Harness Coverage Expansion

Version: 1.1.0
Date: 2026-04-13

## Review findings (post-draft)

After drafting v1.0, I re-checked assumptions against the actual code and found
four issues. All are addressed in the revised sections below.

1. **`run_one_emu` creates a fresh `CortexM33` on every call** (lib.rs:4164) and
   executes via `execute_one()` / `execute_one_wide()`, which bypass
   `decode_execute()` entirely (mod.rs:193-229). They don't check `it_state`,
   don't do conditional execution, don't call `advance_it_state()`. So the v1.0
   design's "call run_one_emu twice with `steps: u8`" approach is broken on two
   counts: fresh core loses state, and the execution path doesn't honour IT
   anyway. **Fix:** IT tests use a new `run_one_emu_multistep()` path that
   writes instructions into the bus and calls `core.step()` (which routes
   through `decode_execute`).

2. **FPU GDB register numbers are unverified and likely wrong.** The v1.0 guess
   (S0 at index 26, FPSCR at 58) assumed a standard ARM VFP layout. But the
   existing harness comment (lib.rs:80) says "Indices 16-24 are legacy FPA
   (return E14 on QEMU 10.2). xPSR is at index 25" — the FPA slots exist but
   are empty. QEMU's Cortex-M33 GDB stub may place FPU registers at 26-41
   (D-register layout) or 26-57 (S-register layout), or the harness's basic
   `p`/`P` packets may not cover them at all without parsing `target.xml`.

3. **probe-rs 0.31 FPU register support is unverified.** The existing probe
   code only uses `RegisterId(0..=16)`. I can find no evidence that probe-rs
   0.31 exposes S0-S31 via `RegisterId`.

   **Fix for both 2 and 3:** don't use debugger-native FPU register access at
   all. Use prelude/epilogue instruction sequences (VLDR/VSTR/VMRS/VMSR) that
   move FPU state through memory, which both debuggers can already read and
   write. This costs extra single-steps per FPU test but eliminates two whole
   classes of compatibility risk. Details in section A.

4. **CPACR must be written explicitly on real hardware.** The emulator defaults
   `cpacr = 0x00F0_0000` (FPU enabled), but the RP2354 after `reset_and_halt`
   has CPACR = 0 (FPU disabled — executing any VFP instruction would raise
   UsageFault). **Fix:** write CPACR = 0x00F0_0000 during probe session setup,
   alongside `enable_cyccnt()`. QEMU may also need this — verify during smoke
   test.

## Problem

The differential test harness (`probe_diff` and `qemu_diff`) covers Thumb-16 and
most Thumb-32 integer instructions with both targeted and fuzz modes. But four
areas have zero or inadequate coverage:

| Gap | Current State | Risk |
|-----|---------------|------|
| **FPU** | Unit tests only, no differential testing | QEMU FPv5 has known quirks (rounding, NaN, denormals). Real silicon is the only trustworthy oracle. |
| **IT blocks** | Not tested at all in the harness | Condition evaluation, flag suppression, ITSTATE advancement — all untested against hardware. |
| **Long multiply / DSP** | Hand-crafted only, no fuzz | 64-bit multiply-accumulate carry propagation, GE flags, saturation — prime fuzz targets. |
| **POP {PC}** | Excluded everywhere (address-space-dependent) | `probe_diff` shares the address space — no reason to exclude it there. |

The FPU gap is the most dangerous because floating-point corner cases are where
emulators most commonly diverge from silicon.

## Scope

All changes are in `mdrp2354-test-harness` (the test harness crate). No changes
to the emulator crate.

Four independent additions to the harness, all following the existing pattern:
add encoding helpers, add a test generator, wire into `generate_all()` and/or
`generate_fuzz()`.

## A. FPU Differential Testing

### Approach

FPU tests need three things the integer tests don't: writing FPU registers before
execution, reading them after, and comparing float results. The existing
`TestCase` / `RunState` / comparison functions are integer-only. Extend them.

### TestCase changes

Add optional FPU fields:

```rust
pub struct TestCase {
    // ... existing fields ...

    /// FPU register preconditions: (Sn index 0-31, bit-pattern as u32).
    /// Values are raw bit patterns (f32::to_bits), not interpreted as floats,
    /// because test setup must handle NaN/Inf/denormal without Rust's float
    /// semantics getting in the way.
    pub fpu_pre: Vec<(u8, u32)>,

    /// FPU registers to read back after execution (list of Sn indices).
    pub fpu_check: Vec<u8>,

    /// FPSCR precondition (0 = default). Set non-zero for rounding mode tests.
    pub fpscr_pre: u32,

    /// FPSCR mask for comparison. 0 = don't compare FPSCR.
    /// 0xF000_0000 = compare N/Z/C/V only (VCMP tests).
    pub fpscr_mask: u32,
}
```

All new fields default to empty/zero, so every existing test is unaffected.

### RunState changes

Add FPU post-state:

```rust
pub struct RunState {
    // ... existing fields ...

    /// FPU register values at checked indices (bit patterns, same order as
    /// TestCase::fpu_check).
    pub fpu: Vec<u32>,

    /// FPSCR after execution.
    pub fpscr: u32,
}
```

### Emulator side (`run_one_emu`)

Before execution:
- Write `tc.fpscr_pre` to `cpu.regs.fpscr`.
- For each `(sn, bits)` in `tc.fpu_pre`: write `f32::from_bits(bits)` to
  `cpu.regs.s[sn]`.

After execution:
- Read `cpu.regs.s[sn].to_bits()` for each sn in `tc.fpu_check`.
- Read `cpu.regs.fpscr`.

This is straightforward — the emulator stores FPU state in `Registers`.

### FPU register access — unified approach via memory

Rather than debating GDB register numbers vs probe-rs `RegisterId` values
(both unverified and both likely to differ across QEMU versions and probe-rs
versions), use the one mechanism guaranteed to work on both sides:
**architecture-defined instruction sequences that move FPU state through
memory**.

**Pre-execution (write S registers and FPSCR):**

Before the test instruction, insert a prelude that loads FPU state from
scratch memory:
```
VLDR S0, [R12, #0]      ; hw0=0xED9C, hw1=0x0A00
VLDR S1, [R12, #4]
...
VLDR S31, [R12, #124]
VMSR FPSCR, R11         ; hw0=0xEEE1, hw1=0xBA10
```

This means **the test slot holds a multi-instruction prelude**, not just the
one instruction under test. R12 is set to point at a prelude-scratch area
(separate from `EMU_TEST_SCRATCH`), R11 holds the FPSCR precondition value.
We single-step through the prelude, then through the test instruction.

That's heavy. Lighter alternative:

**Only write the S registers the test actually uses.** `tc.fpu_pre` lists
exactly which S registers need setup. For a typical VADD S0, S1, S2, that's
3 VLDRs (6 halfwords + 6 steps) before the one instruction under test.

For post-execution (read S registers and FPSCR):
```
VSTR S0, [R12, #0]
VSTR S1, [R12, #4]
...
VMRS R11, FPSCR
STR R11, [R12, #128]
```

Step through the epilogue, then read the scratch area via normal memory
reads (`gdb.read_mem` on QEMU, `core.read_8` on probe).

**This avoids the FPU register access problem entirely.** Both QEMU and
probe-rs can read and write arbitrary memory — that's the only debugger
primitive we need.

**Trade-off:** Each FPU test is ~10-20 instructions instead of 1. At
probe-rs single-step rates (~5-10ms per step), a 100k-fuzz run on FPU goes
from ~15 minutes to ~2-3 hours. For QEMU it's still under a minute.
Acceptable — FPU bugs are rare enough that a long nightly run is fine.

### Prelude / epilogue plumbing

Add fields to `TestCase`:

```rust
pub struct TestCase {
    // ... existing fields ...

    /// FPU register preconditions: (Sn, bit pattern).
    pub fpu_pre: Vec<(u8, u32)>,

    /// FPU registers to read back after execution.
    pub fpu_check: Vec<u8>,

    /// FPSCR precondition (raw 32-bit value).
    pub fpscr_pre: u32,

    /// FPSCR compare mask (0 = don't compare FPSCR).
    pub fpscr_mask: u32,
}
```

In the runners, when `fpu_pre` or `fpu_check` is non-empty:

1. Write prelude VLDRs into the bus starting at `TEST_SLOT`.
2. Populate the FPU-prelude scratch area with the precondition bit patterns.
3. Write the test instruction(s) immediately after the prelude.
4. Write epilogue VSTRs after the test instruction.
5. Step N+1+M times (N prelude, 1 test, M epilogue).
6. Read the FPU-epilogue scratch area to recover the post-state.

The multi-step path from section B (`step` on the emulator side, repeated
`s` on QEMU and probe) is reused — FPU tests are a superset of IT tests in
terms of harness machinery. **Build B first; A builds on top of it.**

### CPACR setup — required on both sides

The emulator defaults `cpacr = 0x00F0_0000` in PPB init (ppb.rs:42) so FPU
access works out of the box. Real RP2354 hardware after `reset_and_halt` has
CPACR = 0, which would make any VFP instruction raise `UsageFault`.

**Fix:** In `probe_diff::run()`, write CPACR after `enable_cyccnt()`:
```rust
core.write_word_32(0xE000_ED88, 0x00F0_0000)?;  // CPACR: CP10/11 full access
```

For QEMU: verify during the smoke test whether the MPS2-AN505 default CPACR
allows VFP. If not, apply the same write via `gdb.write_mem()` during setup.

### Smoke test (do this first, before any generator work)

Before building out `gen_t32_fpu()` or `generate_fuzz_fpu()`, write a
**single hand-crafted FPU test end-to-end** and make sure it passes on both
QEMU and probe_diff:

1. Prelude: `VLDR S0, [R12, #0]; VLDR S1, [R12, #4]` with known values.
2. Test: `VADD S2, S0, S1`.
3. Epilogue: `VSTR S2, [R12, #8]`.
4. Verify scratch[8..12] = expected sum on both sides.

This validates: CPACR is set, the bus path for instruction fetch works for
FPU opcodes, VLDR/VSTR work at the hardware level, and the prelude/epilogue
single-step sequence doesn't trip on exceptions. If this one test works,
the rest is just generator plumbing. If it doesn't work, we find out before
investing in generators.

### Comparison

Add `compare_fpu()` (called from both `compare()` and `compare_probe()`):

```rust
fn compare_fpu(tc: &TestCase, a: &RunState, b: &RunState) -> Result<(), String> {
    let mut diffs = Vec::new();

    // FPU register comparison (bit-exact)
    for (i, &sn) in tc.fpu_check.iter().enumerate() {
        if a.fpu[i] != b.fpu[i] {
            diffs.push(format!("S{sn}: {:#010x} vs {:#010x}", a.fpu[i], b.fpu[i]));
        }
    }

    // FPSCR comparison (masked)
    if tc.fpscr_mask != 0 {
        let a_masked = a.fpscr & tc.fpscr_mask;
        let b_masked = b.fpscr & tc.fpscr_mask;
        if a_masked != b_masked {
            diffs.push(format!(
                "FPSCR: {:#010x} vs {:#010x} (mask={:#010x})",
                a.fpscr, b.fpscr, tc.fpscr_mask
            ));
        }
    }

    if diffs.is_empty() { Ok(()) } else { Err(diffs.join(", ")) }
}
```

FPU results are compared as bit patterns, not as floats. This catches NaN
sign bit differences, -0 vs +0, and quiet-vs-signalling NaN — all of which
`==` on f32 would miss.

### Test generators

Move the existing encoding helpers from `tests.rs` into `thumb32_gen.rs`
(they're currently private to the unit test module). Then add:

**Targeted: `gen_t32_fpu()`** — ~60 hand-crafted tests covering:

- Arithmetic: VADD, VSUB, VMUL, VNMUL, VDIV (normal values, zeros, large, small)
- Multiply-accumulate: VMLA, VMLS, VNMLA, VNMLS, VFMA, VFMS, VFNMA, VFNMS
- Unary: VMOV, VABS, VNEG, VSQRT
- Compare: VCMP (equal, less, greater, NaN, negative zero, ±inf)
- Convert: VCVT.F32.S32, VCVT.F32.U32, VCVT.S32.F32, VCVT.U32.F32, VCVTR
- Transfer: VMOV arm↔fpu, VMRS, VMSR
- Load/store: VLDR, VSTR (positive and negative offsets)
- Special values: ±0, ±Inf, NaN, denormals, MAX_FLOAT, MIN_POSITIVE

**Fuzz: `generate_fuzz_fpu()`** — random FPU tests, structured as:

```
count tests per class:
  - Arithmetic (random op from {VADD,VSUB,VMUL,VDIV}, random Sn/Sm/Sd,
    random bit patterns for operands)
  - Multiply-accumulate (random op, random registers, random bits)
  - Unary (random op, random register, random bits)
  - Convert (random direction, random bits — biased toward edge cases:
    10% NaN, 10% Inf, 10% denormal, 10% zero, 60% normal)
  - Compare (random operand pairs, check FPSCR flags)
```

Random bit patterns are key — they naturally hit denormals, NaN encodings,
and other corner cases that hand-crafted tests miss.

Wire `gen_t32_fpu()` into `generate_all()` and `generate_fuzz_fpu()` into
`generate_fuzz()` as a third category alongside ALU and memory.

### VLDR/VSTR in fuzz

FPU load/store tests are memory tests (need `needs_bus = true`). The fuzz
generator for VLDR/VSTR follows the same pattern as integer load/store fuzz:
random base register, random aligned offset within scratch, random data.
Put these in `generate_fuzz_fpu_mem()` and add to the memory fuzz list.

## B. IT Block Test Generation

### Approach (revised)

An IT block is 2-5 instructions: the IT instruction itself, then 1-4
conditional instructions. Testing IT + 1 body instruction is sufficient: it
validates condition evaluation, execute-vs-skip, flag suppression, the
flag-only exception (CMP/TST/CMN), and one ITSTATE advance. Longer blocks
just re-exercise the same shift-register logic already covered in unit
tests.

### Why `run_one_emu` can't just be called twice

The v1.0 approach ("add a `steps` field, loop the runner") doesn't work:

- `run_one_emu` creates a **fresh** `CortexM33::new()` on every call
  (lib.rs:4164). Any IT state set by the first call is discarded.
- `execute_one()` / `execute_one_wide()` bypass `decode_execute()`
  (mod.rs:193-229). They call `execute_thumb16` / `execute_thumb32` directly,
  so even on a preserved core they wouldn't check `it_state`, wouldn't skip
  conditionally, and wouldn't call `advance_it_state()`.

The IT instruction itself *does* set `it_state` (via `thumb16_misc` at
execute.rs:724) regardless of which path we're on. So step 1 works. But step
2 — the body instruction — has to go through `decode_execute()` to honour
the newly-set `it_state`. That means:

- Keep the same `CortexM33` instance across both steps.
- Fetch the body instruction from the bus (not pass it as a parameter).
- Use `core.step()`, which routes through `decode_execute()` (mod.rs:65-103).

### Solution: new runner `run_one_emu_multistep`

Add a sibling function to `run_one_emu` with a different execution path:

```rust
pub fn run_one_emu_multistep(tc: &TestCase, shared_bus: &mut Bus) -> RunState {
    let mut core = CortexM33::new();

    // Standard register/memory setup (same as run_one_emu).
    // ... R0-R12=0, SP, LR, PC=EMU_TEST_SLOT, xpsr_pre, reg_pre, mem_pre ...

    // Write BOTH instructions into the bus at the test slot.
    // The core will fetch them via decode_execute().
    write_u16(shared_bus, EMU_TEST_SLOT, tc.opcode);
    let body_offset = 2u32;
    match (tc.opcode2.unwrap(), tc.hw1_2) {
        (op2, None) => write_u16(shared_bus, EMU_TEST_SLOT + body_offset, op2),
        (op2, Some(hw1)) => {
            write_u16(shared_bus, EMU_TEST_SLOT + body_offset, op2);
            write_u16(shared_bus, EMU_TEST_SLOT + body_offset + 2, hw1);
        }
    }

    // Step through IT instruction, then body. step_to_completion drains stall
    // cycles the way unit tests do (tests.rs:2972-2978).
    let c1 = step_to_completion(&mut core, shared_bus);
    let c2 = step_to_completion(&mut core, shared_bus);

    // Collect post-state (same as run_one_emu).
    // cycles = c1 + c2
}

fn step_to_completion(core: &mut CortexM33, bus: &mut Bus) -> u32 {
    // Drain any residual stall cycles from previous instruction.
    while core.stall_cycles() > 0 { core.step(bus); }
    // Execute one new instruction. step() returns void but sets stall_cycles
    // = cycles - 1; we need the actual cycle count, so track it another way.
    let before = core.stall_cycles();  // 0
    core.step(bus);
    // After step, stall_cycles() is (cycles - 1). So cycles = stall + 1.
    core.stall_cycles() + 1 - before
}
```

**Note on cycle counting:** `step()` is void and stores `cycles - 1` in
`stall_cycles`. For IT tests, exact cycle count comparison is less critical
than semantic correctness, so tracking cycles precisely can be skipped for
IT tests (leave `RunState::cycles = 0`). Skip cycle comparison for IT tests
in `probe_diff`.

### TestCase fields

```rust
pub struct TestCase {
    // ... existing fields ...

    /// Second instruction (placed at test_slot + 2). Set for IT-block tests.
    /// When present, runners use the multi-step execution path.
    pub opcode2: Option<u16>,

    /// Second halfword of opcode2 (for Thumb-32 body inside IT block).
    pub hw1_2: Option<u16>,
}
```

Runners dispatch on `opcode2.is_some()`:
- `run_one_emu` — existing path (single instruction).
- `run_one_emu_multistep` — new path (IT + body via `step()`).

Same dispatch in `run_qemu_side` and `run_one_probe`: write both instructions
to the test slot, step **twice**. QEMU and real silicon handle ITSTATE
natively, so stepping twice Just Works on those sides — the complication is
only on the emulator side.

### Encoding

The IT instruction is Thumb-16: `0xBF<firstcond><mask>`.

```rust
fn enc_it(firstcond: u16, mask: u16) -> u16 {
    0xBF00 | (firstcond << 4) | (mask & 0xF)
}
```

For single-instruction IT blocks, mask = `0b1000` (just the T bit).

### Targeted: `gen_it_block()`

~50 tests covering the important axes:

- **Condition taken vs skipped**: For each of EQ, NE, CS, CC, MI, PL, VS, VC,
  HI, LS, GE, LT, GT, LE: set xPSR flags so condition passes, then set flags
  so it fails. Body = `MOVS R0, #42` (observable effect: R0 changes or doesn't).

- **Flag suppression**: IT EQ + `ADDS R0, R1, R2` with condition true. Verify
  flags are preserved (not updated by ADDS). Then IT EQ + `CMP R0, R1` with
  condition true. Verify flags ARE updated (CMP is flag-only).

- **Thumb-32 body**: IT EQ + `ADD.W R0, R1, R2` to verify 32-bit instructions
  work inside IT blocks.

### Fuzz: `generate_fuzz_it()`

```
For each of count tests:
  - Random condition (0-13)
  - Random xPSR flags (50% chance condition passes)
  - Random body instruction chosen from:
    - MOVS Rd, #imm8 (flag-updating, should be suppressed)
    - ADDS Rd, Rn, Rm (flag-updating, should be suppressed)
    - MOV Rd, Rm (high register, no flags)
    - CMP Rn, Rm (flag-only, NOT suppressed)
  - Random register values
```

Wire into `generate_fuzz()` ALU list (IT tests don't need memory).

## D. Hardware-Only POP {PC} and Branch Fuzz

### Problem

`POP {PC}` and `LDM {…, PC}` load an absolute address into PC. In the QEMU
harness, QEMU and the emulator use different address spaces, so the loaded PC
value is wrong on one side. The QEMU harness excludes these.

`probe_diff` uses the same address space (both sides are in RP2354 SRAM at
`0x2000_xxxx`). There's no reason to exclude PC-loading instructions there.

### Approach

Add a `probe_only: bool` field to `TestCase`. Tests marked `probe_only` are
included in `generate_all()` and `generate_fuzz()` but skipped by `qemu_diff`.

```rust
pub struct TestCase {
    // ... existing fields ...

    /// Skip this test in QEMU mode (address-space-dependent result).
    pub probe_only: bool,
}
```

`qemu_diff` filters: `tests.retain(|tc| !tc.probe_only)`.
`probe_diff` runs everything.

### Targeted: add to `gen_push_pop()` and `gen_stm_ldm()`

Restore the ~18 tests that were removed (listed in `tech_debt.md`):

- **POP {PC}**: Push a known return address to scratch memory via `mem_pre`,
  set SP to point at it, POP {PC}. The PC comparison in `compare_probe()` is
  absolute — this just works.

- **ADR Rd, #imm**: Writes `PC + imm` to Rd. With same address space, the
  result matches. Mark `probe_only`.

- **ADD Rd, SP, #imm**: Same — result is an absolute address, matches on
  hardware.

### Fuzz: add POP {PC} to `generate_fuzz_mem()`

In the existing POP fuzz section, currently `pc=false` always. Change to:

```rust
let pc = rng.coin(0.3);  // 30% chance of POP {PC}
let opcode = enc_pop(reglist8, pc);
// ... if pc, set up memory with a valid target address ...
// ... mark probe_only = pc ...
```

For POP {PC}, the loaded value must have bit 0 set (Thumb bit) and point to a
valid SRAM address. Use `EMU_TEST_SLOT + 4` (address just after the test
instruction) as the return target — it's where execution would go anyway, so
the PC delta is predictable.

Same approach for LDM with PC in the register list.

## Implementation Order

C and D are independent. B is a prerequisite for A (A reuses B's multi-step
runner plumbing). Order:

1. **C (long multiply / DSP fuzz)** — Pure additions to existing fuzz
   generators. No structural changes. ~200 lines. Start here; ship it; move on.

2. **D (POP {PC} / probe-only)** — Add `probe_only: bool` to `TestCase`,
   filter in `qemu_diff`, restore the ~18 excluded tests, add POP {PC} to
   POP fuzz. ~80 lines. Still no multi-step machinery needed.

3. **B (IT blocks)** — The first change that needs multi-step execution.
   Adds `opcode2` / `hw1_2` to TestCase, adds `run_one_emu_multistep`, teaches
   `run_qemu_side` and `run_one_probe` to step twice when `opcode2.is_some()`.
   ~300 lines. This is the risky structural change — land it on its own and
   verify the existing tests still pass before touching A.

4. **A (FPU)** — Reuses B's multi-step path (FPU tests are N-step, not 2-step,
   but the mechanism is the same). Adds FPU fields to TestCase/RunState, the
   prelude/epilogue builder, CPACR setup, `compare_fpu`, `gen_t32_fpu`, and
