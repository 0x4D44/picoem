### Why this shape

- **Root has 14 files.** Down from 28. All are conventional OSS hygiene
  files or workspace config.
- **`docs/` is the one place a contributor looks** for design docs,
  journals, runbooks, tech debt, and the article. Today these are split
  across 5 directories (`docs/`, `wrk_docs/`, `wrk_journals/`, `notes/`,
  + `RUNBOOK.md` + `tech_debt.md` at root).
- **`docs/design/` is sub-grouped by topic** instead of flat-by-date.
  240 flat files is unnavigable; 12 topic folders × ~5 files each is.
- **`tools/` consolidates `scripts/` and `fuzz-runs/`.** Two
  similarly-purposed dirs collapse into one with sub-domains.
- **`third_party/dosbox-x/` is consistent** with the shape of
  `third_party/picogus/` and `third_party/probe-rs-...` — every vendor
  gets its own subdir + README.

### What this does NOT change

- **`crates/` layout.** All 8 workspace crates keep their current names
  and paths. `Cargo.toml` only changes if `.cargo/mutants*.toml` paths
  shift inside `.cargo/`.
- **`roms/` layout.** Already cleanly partitioned by chip; the generator
  Python files live alongside the binaries they produce, which is right.
- **`CLAUDE.md` location.** Root, per agent convention.
- **Commit history.** All moves done with `git mv`; no `git filter-repo`
  or rewriting history. Public history starts from whatever commit Arthur
  pushes.

## 4. The doc-curation question (largest single piece of work)

`wrk_docs/` is 240 files; collapsing into topic folders and pulling
the latest version of each topic is ~3–4 hours of mechanical work.
Three concrete approaches, in order of effort:

### Option A — light touch (60 min)

1. Bulk rename `wrk_docs/` → `docs/design/`.
2. Bulk rename `wrk_journals/` → `docs/journals/`.
3. Move `RUNBOOK.md`, `tech_debt.md`, `notes/`, the article, the OSS
   release HLD into `docs/`.
4. Move `fuzz-runs/` + `scripts/` into `tools/`.
5. Update the ~40 cross-references.
6. Leave the 122 versioned drafts in place (still flat-by-date).

Result: cleaner top-level, but `docs/design/` is still 240 flat files.

### Option B — recommended (3–4 hours)

Everything in A, plus:

7. Sort `docs/design/*.md` into 12 topic folders (phase-2-bus,
   phase-3-interrupts, ..., picogus, onerom, mutation-testing, riscv,
   threading).
8. For each topic, pick the highest `V<N>` per (topic, date) tuple
   as the canonical file; rename it to drop the version suffix.
9. Move all earlier drafts into `docs/design/archive/<topic>/`.
10. Write a one-page `docs/design/README.md` index that lists the
    topic folders and the supersedence chain ("for the threading
    runtime, start at `threading/dual-execution-model.md`; the
    `archive/` folder has Phase 0–4 LLD iterations").

Result: someone landing in `docs/design/` can find the load-bearing
HLD for any subsystem in one folder hop. Archive is preserved for
citation chains in tech_debt.md and journals.

### Option C — aggressive (1 day, irreversible)

Everything in B, plus:

11. Hard-delete the `archive/` folder and any draft beyond the
    canonical version. ~80 fewer files.
12. Delete the OSS pre-release notes (`notes/oss-*.md`,
    `wrk_docs/2026.04.26 - HLD - Open Source Release V1.md`) once
    publication is done.

Result: smallest repo. Loses the design-evolution audit trail and
~20 cross-references in `tech_debt.md` that point at older drafts.

**My recommendation is B.** Public readers benefit from a curated
`docs/design/` tree; the historical drafts are real evidence of how
the design evolved (especially the threading and PIO iterations) and
the cost of keeping them in `archive/` is one folder.

## 5. Sequencing

Independent of which doc-curation option Arthur picks, this is the
order I'd execute, broken into commits a reviewer can read:

1. **Detritus sweep** (no commit, just `rm`) — reclaim 12 GB locally.
2. **`.cargo/mutants/` sub-folder + cleanup** — small, isolates the
   `Cargo.toml` config field rename if any.
3. **`tools/` consolidation** — `git mv fuzz-runs/* tools/fuzz/`,
   `git mv scripts/* tools/<subdir>/`. Update README.md, CLAUDE.md,
   tech_debt.md refs.
4. **`third_party/dosbox-x/` regrouping** — per-vendor subdir.
5. **`docs/` consolidation** (option A baseline) — move RUNBOOK.md,
   tech_debt.md, notes/, article, OSS-release HLD into `docs/`.
   `git mv wrk_docs docs/design`, `git mv wrk_journals docs/journals`.
   Bulk rewrite of cross-references.
6. **(if option B/C)** Topic folders + draft archiving inside
   `docs/design/`. One commit per topic folder so a reviewer can verify
   the supersedence chain folder by folder.
7. **`.gitignore` audit** — drop entries that no longer match anything
   (e.g. `mutation/` if we never use that workdir again).
8. **README polish** — re-read the README + CONTRIBUTING + RUNBOOK with
   the new paths, sweep for any link that broke.

Each step is one commit, each commit is independently revertable, none
of them require touching git history.

## 6. Risks and call-outs

- **External backlinks.** If anything outside this repo (e.g. an
  upstream probe-rs issue thread, the article on a blog) links to a
  current `wrk_docs/...` URL on github.com, that link breaks once we
  push the rename. The only known external link target today is the
  probe-rs PR (Track A.2c, A.2d) — which is a draft, not yet upstreamed.
- **Cargo lints / mutants config.** `[workspace.lints.clippy]` and the
  three `mutants*.toml` files reference no in-repo paths, so moving them
  inside `.cargo/mutants/` is purely a `--config-file` discovery
  question. If `cargo mutants` looks in `.cargo/mutants.toml` only,
  we'd need to keep `default.toml` at the original name OR pass
  `--config <path>` from the runner script. **Action**: verify before
  committing the `.cargo/mutants/` move.
- **`docs/probe_serials.md` is rig-specific.** It documents Arthur's
  particular probe serials. CONTRIBUTING.md already calls this out as
  "specific to the maintainer's hardware". Worth a sentence at the top
  of the file itself for public readers.
- **OSS audit notes (`notes/oss-*.md`) are dated.** They're a snapshot
  from 2026-04-26. If we move them to `docs/release/`, they need a "as
  of <date>; subsequent commits may have added new files" line so a
  reader doesn't treat them as the current state.
