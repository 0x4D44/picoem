# Silicon Peripheral and Cycle Oracles

Version: 1.1.0
Date: 2026-04-15
Scope: mdrp2350 only (RP2354 is the hardware we have)

## Changelog

- **1.1.0 (2026-04-15)** — stress-test pass. Drop pre-computed
  `run_sysclks`; use CYCCNT-measured actual cycles instead.
  `PeriphScenario` uses absolute MMIO addresses (no `pio_block` field).
  Cycle-oracle stub fixed to use callee-saved registers across `blx`.
  K=101 vs K=201 (two hot runs) replaces K=1 vs K=101. Emulator-side
  tick path clarified (`run()` with halted cores already ticks
  peripherals). Assumption (1) re-characterised: question is readback
  atomicity, not whether PIO runs at all.

## Problem

Today's oracles validate the ISA only. The tech-debt list spells out what's
left uncovered:

- PIO-RESETS gating, PIO register-level behaviour (Phase 5.A)
- PLL LOCK timing, SIO divider 8-cycle latency, SIO divider dirty-clear rule
- PUSH-2 minimum cost (HW=4 vs formula=3), backward-branch pipeline penalty,
  additional bank-contention patterns
- Halt-step CYCCNT cannot see pipeline overlap or back-to-back forwarding

Two oracles close these gaps, using the RP2354 already sitting on the bench.

## Goals

1. **Peripheral oracle** — diff mdrp2350 peripheral register/FIFO/pin state
   against live RP2354 silicon. PIO first (widest surface, highest risk), same
   pattern reusable for SIO-DIV, CLOCKS, RESETS-gated anything.
2. **Cycle oracle** — measure true instruction-sequence cycle cost on silicon
   at native speed (no halt-step overhead), diff against our model. Resolves
   the Phase-2 cycle-timing debt entries.

Both are small, self-contained, use existing infrastructure.

## Non-goals

- No RP2040 silicon oracle (no board).
- No external stimulus peripherals (I2C/SPI/UART/ADC) — they need wiring or a
  stub device; defer until a downstream consumer actually needs them.
- No cycle-by-cycle PIO single-step over SWD. PIO doesn't halt when the core
  halts; trying to gate it one sysclk at a time over probe-rs is both slow
  and fragile. End-state diff of self-terminating programs is enough to catch
  the bugs we actually have.
- No trace-capture mode feeding the existing `onerom_pio_diff_rp2350` format.
  Nice-to-have, not in this pass.

## Reused infrastructure

| Piece | Source |
|---|---|
| probe-rs attach / reset-halt / DWT enable / NOP baseline | `probe_diff_rp2350.rs` |
| Shared SRAM layout (`EMU_TEST_SLOT`, `EMU_TEST_SCRATCH`, `SCRATCH_SIZE`) | `mdpicoem-harness/src/lib.rs:113-125` |
| Emulator PIO stepping | `PioBlock::step` / `step_n` (`mdpicoem-common/src/pio/mod.rs:102,125`) |
| Emulator PIO MMIO | `PioBlock::read32` / `write32` (`mdpicoem-common/src/pio/mod.rs:237,281`) |

No new crates. No new features. No env vars. No feature flags.

## Oracle 1 — `silicon_periph_diff_rp2350`

### Shape

One binary under `crates/mdpicoem-harness/src/bin/`. Attaches to the RP2354,
runs a catalogue of **peripheral scenarios**. Each scenario:

1. Resets the peripheral (write RESETS).
2. Programs it via a fixed sequence of MMIO writes.
3. Runs it for a known number of sysclks until it reaches a deterministic
   terminal state.
4. Reads back a fixed set of observable registers/memory.
5. Replays the identical MMIO sequence and sysclk count on the emulator.
6. Diffs the two state vectors. First divergence wins.

### Scenario type

```rust
pub struct PeriphScenario {
    pub name: &'static str,
    /// MMIO writes (absolute address, value), applied in order. Uses
    /// absolute addresses (0x5020_0000 for PIO0, 0x4002_C000 for PLL_SYS,
    /// 0xD000_0000 for SIO, etc.) so PIO and bare-MMIO scenarios share one
    /// shape. Host writes via probe-rs; emulator writes via `bus.write32`.
    pub setup: &'static [(u32, u32)],
    /// Upper bound on sysclks the core runs inside the NOP sled. The
    /// actual cycle count is read from CYCCNT after BKPT halts and fed to
    /// the emulator's `run()` so the two sides advance by the same amount.
    pub max_sysclks: u32,
    /// Observables: (absolute address, mask). Mask=0xFFFF_FFFF = full word.
    pub observe: &'static [(u32, u32)],
    /// GPIO pins to sample drive+level after the run.
    pub observe_pins: u32,
}
```

A catalogue starts small and grows:

- `pio_nop_loop` — single SM running `jmp 0`, verifies ADDR advances, no pin
  activity.
- `pio_fixed_cycles` — `set x, 31 / jmp x-- here / stall:` — verifies
  terminal ADDR = stall, X=0, clkdiv phase.
- `pio_side_set_toggle` — SM toggling a pin via side-set — verifies pad_oe,
  pad_out, final GPIO level, FDEBUG side-set counter.
- `pio_tx_drain` — preload TXF with N words, SM pulls each, pushes to RX —
  verifies FLEVEL, FSTAT.EMPTY/FULL.
- `pio_out_pins` — SM emits a known bit pattern via OUT PINS — verifies
  pad_oe/pad_out at terminal state.
- `pio_irq_set_wait` — SM0 sets IRQ, SM1 waits on IRQ, terminal IRQ bits.
- `pio_reset_gating` — assert PIO RESETS mid-run, verify SM frozen (directly
  tests the Phase 5.A debt item).

Plus non-PIO:

- `pll_sys_lock_timing` — write PLL_SYS FBDIV/REFDIV/CS.ENABLE, step N
  sysclks, read CS.LOCK. Resolves `tech_debt.md` "PLL LOCK always 1".
- `sio_div_latency` — write DIV_UDIVIDEND/DIVISOR, step 1..10 sysclks,
  read DIV_CSR.READY each step. Resolves "SIO divider 8-cycle latency".
- `sio_div_dirty_clear` — write+read QUOTIENT vs REMAINDER, verify dirty
  clears per-read. Resolves "2-read dirty clear heuristic".

### Cycle synchronisation

The flow, with no pre-calibrated cycle counts anywhere:

```
1. core halted → host applies peripheral setup via probe-rs
2. host writes a countdown-loop sled sized for `max_sysclks`, followed by
   BKPT, into SILICON_RUN_SLED
3. host zeroes CYCCNT, sets PC = SILICON_RUN_SLED | 1, resumes core
4. core runs the sled, executes BKPT, halts
5. host's first action on halt: write SM_ENABLE=0 (or the relevant
   peripheral gate) to freeze the peripheral. This guarantees the
   subsequent readback is atomic w.r.t. peripheral state (see
   Assumption 1 below).
6. host reads CYCCNT → `actual_sysclks`
7. host reads observables via probe-rs
8. emulator side: apply same setup via bus.write32, call
   emu.run(actual_sysclks), read observables via bus.read32
9. diff
```

The sled is a small countdown loop written to `SILICON_RUN_SLED`
(`EMU_TEST_SLOT + 0x1000`, 4 KB below the ISA oracle's slot):

```
movs r0, #N        ; N = max_sysclks / 4 (rounded up)
subs r0, #1
bne  -4
bkpt
```

Per-iteration cost is constant, so the host can pick N for any
`max_sysclks` target without further calibration. CYCCNT captures the
truth — no NOP-baseline arithmetic, no halt-overhead subtraction. The
NOP-baseline logic in `probe_diff_rp2350` stays in its binary and isn't
reused here.

**Emulator side**: `Emulator::step()` with both cores halted already does
the right thing — the core `while` loops skip cheaply, then
`clock.advance`, `tick_peripherals` (PIO + SIO mtime), `tick_systick`, and
`wake_checks` all run unconditionally (`mdrp2350/src/lib.rs:143-172`). So
`emu.run(actual_sysclks)` with halted cores ticks peripherals by exactly
that many sysclks. Build the emulator with `step_quantum=1` so PIO sees
single-sysclk granularity rather than quantum-sized chunks. No new Bus or
PioBlock API needed.

**Critical simplification**: scenarios live entirely inside one PIO block
(or one peripheral). No cross-peripheral orchestration in v1. The catalog
is data, not code.

### State snapshot

For PIO, per scenario, read via probe-rs and emulator's `read32`:

- `CTRL`, `FSTAT`, `FDEBUG`, `FLEVEL`, `IRQ`
- Per enabled SM: `SMx_CLKDIV`, `SMx_EXECCTRL`, `SMx_SHIFTCTRL`,
  `SMx_ADDR`, `SMx_INSTR`, `SMx_PINCTRL`
- TX/RX FIFOs: drain via successive `TXFx`/`RXFx` reads until
  `FSTAT.EMPTY/FULL` says stop (captures contents without popping state
  the program needs).

Internal X/Y/OSR/ISR are **not directly observable**. A scenario that wants
to diff them must itself push that state to a FIFO (`MOV ISR, X` → `PUSH`)
or to pins (`MOV PINS, X`). This is a deliberate constraint, not a gap —
silicon debugging of PIO works the same way.

GPIO drive/level: read `PADS_BANK0` / `GPIO_IN` / `GPIO_OUT` / `GPIO_OE`
for the observed pin mask.

## Oracle 2 — `silicon_cycle_oracle_rp2350`

### Shape

One binary, one measurement stub, one diff step.

The measurement stub is a small Thumb routine living in SRAM. It reads a
mailbox, runs the code at the specified pointer *K* times, measures CYCCNT
before and after, writes the delta back. The host (the binary, running on
the PC via probe-rs) writes mailbox, pokes go, polls done, reads result.

No flash. No cargo target for an embedded crate. The stub is ~30 Thumb
halfwords, hand-assembled as a `const [u16; N]` — auditable in one sitting,
same pattern as the test-slot instruction writes in `probe_diff_rp2350`.

### Mailbox protocol

Layout in SRAM (addresses derived from existing `EMU_TEST_*` constants):

```
0x2004_0100  CYCLE_MAILBOX_GO        u32  host writes 1, stub clears
0x2004_0104  CYCLE_MAILBOX_DONE      u32  stub writes 1
0x2004_0108  CYCLE_MAILBOX_SEQ_PTR   u32  host: address of sequence to run
0x2004_010C  CYCLE_MAILBOX_ITER      u32  host: K (iteration count)
0x2004_0110  CYCLE_MAILBOX_CYCLES    u32  stub: raw CYCCNT delta
0x2004_0114  CYCLE_MAILBOX_RESERVED  u32  0 (future use)
```

These sit in a fresh region above `EMU_TEST_STACK` (stack is 0x2004_0000);
add `pub const CYCLE_MAILBOX_BASE: u32 = 0x2004_0100;` to `lib.rs`.

### Stub loop

The loop state (seq_ptr, K counter, DWT_CYCCNT pointer, mailbox base)
must survive each `blx`. Per AAPCS, r0–r3 and r12 are caller-saved, so
the called sequence is free to clobber them — using r0–r3 for state
across a `blx` is wrong. Callee-saved regs (r4–r11) must hold anything
that lives across a call.

```
stub_entry:
  push {r4-r7, lr}         ; save callee-saved + return
  ldr  r5, =MAILBOX_BASE   ; r5 = mailbox (preserved across blx)

poll:
  ldr  r0, [r5, #0]        ; GO
  cbz  r0, poll            ; spin until host writes 1
  movs r0, #0
  str  r0, [r5, #0]        ; clear GO

  ldr  r6, [r5, #8]        ; r6 = seq_ptr (preserved, LSB=1 for Thumb)
  ldr  r7, [r5, #12]       ; r7 = K counter (preserved)
  ldr  r4, =DWT_CYCCNT     ; r4 = DWT_CYCCNT ptr (preserved)

  movs r0, #0
  str  r0, [r4]            ; CYCCNT = 0

loop:
  blx  r6                  ; call test sequence — clobbers r0-r3, r12, LR
  subs r7, #1
  bne  loop

  ldr  r0, [r4]            ; read CYCCNT
  str  r0, [r5, #16]       ; CYCLES mailbox

  movs r0, #1
  str  r0, [r5, #4]        ; DONE = 1
  b    poll                ; next round
```

~60 bytes. The `push {r4-r7, lr}` on entry is the callee-saved frame for
whoever called into the stub (the host, via resume-from-PC). r5–r7 and r4
hold all loop state across the `blx`, so the sequence can safely trash
r0–r3, r12, and LR.

The sequence the host hands in (`seq_ptr`) ends in `bx lr`, so it's a
normal function call. The host must write `seq_ptr | 1` into the mailbox
so the `blx` enters Thumb mode, and prime xPSR.T=1 on the stub itself
when setting PC (same as the ISA oracle's setup).

The host writes the instruction bytes into a scratch region
(`EMU_TEST_SLOT` works, or a dedicated `CYCLE_SEQ_SLOT` if we want to keep
it separate from the ISA oracle's slot).

### Why two hot runs, not one cold and one hot

Measuring one execution and subtracting "empty" baseline blends BLX/return
overhead with pipeline effects and hides the back-to-back forwarding
we're trying to see. The K-delta trick, using two steady-state runs:

- Run with K=101 → m₁ = setup + overhead + 101 × seq_cost + warm_residual
- Run with K=201 → m₂ = setup + overhead + 201 × seq_cost + warm_residual
- Per-iter cost = (m₂ − m₁) / 100

Picking both K values well past the cold start (K=1 vs K=101 would mix
one cold-ish iteration into m₁) isolates the steady-state per-iteration
cost exactly — any first-call cache/predictor transient is in
`warm_residual` on both sides and cancels in the subtraction. Each test
case is measured twice; wall-clock per case is microseconds.

### Test cases

The catalog lives beside the peripheral scenarios as
`mdpicoem-harness::cycle_cases` — a `&'static [CycleCase]`:

```rust
pub struct CycleCase {
    pub name: &'static str,
    /// Instruction halfwords, terminated implicitly by `bx lr` appended
    /// by the runner.
    pub seq: &'static [u16],
    /// Expected per-iteration cycles (emulator's current answer).
    pub expected_emu: u32,
}
```

Initial catalog — every one of these is a tech-debt entry:

- `push_2_min_cost` — `push {r0, r1}; pop {r0, r1}` → HW=4+? vs EMU=3+?
- `backward_branch_large` — forward 1024 bytes then backward 1024 — catch
  pipeline flush on large backward jumps
- `backward_branch_small` — the positive control (same span < 256 bytes)
- `bank_contention_fetch_data_same` — `ldr r0, [r1]` with r1 pre-set so
  data and fetch hit the same SRAM bank (extends `bank_conflict_test`
  but now as a diff, not just a measurement)
- `muls_1_cycle` — confirms the M0+-inherited assumption on M33 (it's
  different, but recording the measurement is the point)
- `ldm_8_reg` — `ldm r0, {r1-r8}` — verify `1 + N` holds for LDM/STM
- `back_to_back_alu` — `adds r0, r1; adds r0, r1; ...` (8×) — exposes
  back-to-back forwarding the halt-step oracle can't see

Each case reports: HW per-iter, EMU per-iter, delta, PASS/FAIL against a
configurable tolerance (default 0 cycles, but `--tolerance 1` available for
the noisier cases until we understand them).

## Shared nice-to-have — not in v1

Both binaries independently do: `Session::auto_attach`, `reset_and_halt`,
`enable_cyccnt`, parse `--filter`. If a third silicon binary appears,
factor those into `mdpicoem-harness::silicon_probe` at that point. Not
before — two call sites isn't enough for an abstraction to pay for itself.

## Assumptions (worth verifying early)

1. **Readback atomicity w.r.t. peripheral state after BKPT halt.** PIO
   runs on its own clock, independent of the core. The real question is:
   once BKPT halts the core, does PIO freeze instantly, or keep ticking
   while probe-rs drains the readback? If it keeps ticking, observed
   state is non-deterministic (race between probe-rs transfer time and
   PIO clock).

   **Mitigation**: the runner's first action after halt is to write the
   peripheral's gate register (`PIO.CTRL.SM_ENABLE=0` for PIO,
   `PLL.CS.ENABLE=0` for PLL, etc.) via probe-rs. This stops the
   peripheral before anything else is read. Any cycles accrued during
   the probe-rs write latency are bounded (µs) and deterministic enough
   for end-state diffs — the scenario catalogue should design for a
   terminal *stall* state (tx_empty, irq_wait, or a counter that's
   already zero) where a few extra sysclks don't change observable
   state. A 20-line smoke binary verifies this empirically before we
   commit to the full catalog: set up a PIO counter, halt, gate, read,
   delay, gate+read again — both reads should match.

2. **DWT CYCCNT is reliable in a free-running loop.** Already verified
   by existing `bank_conflict_test` and `probe_diff --cycles`.
3. **SRAM-resident stub is safe against core-1 activity.** Core 1 is
   halted from reset in both oracles — same as `probe_diff_rp2350`.

If the mitigation in (1) proves insufficient (probe-rs gate write is too
slow), fall back to "self-terminating PIO programs only" — scenarios
whose PIO code reaches a stall state before the core BKPTs, so readback
sees the same value regardless of extra ticks. That's a narrower catalog
but still catches most real bugs.

## What this does NOT do

- No RP2040 variants. Mirroring to `silicon_periph_diff_rp2040` and
  `silicon_cycle_oracle_rp2040` is a one-line chip-id change plus a
  board — add when the lab rig gains an RP2040.
- No hardware I2C/SPI/UART/ADC/USB oracles. External stimulus is out of
  scope for v1.
- No cycle-by-cycle PIO state capture. Only end-state.
- No trace capture feeding `onerom_pio_diff_rp2350`. The two oracles stay
  independent.
- No CI integration. Both binaries need silicon on USB; they run locally,
  same as `probe_diff_rp2350`.
- No JSON/CSV output. Terminal text is enough to drive the next tech-debt
  fix.
- No perf goal. These oracles are correctness tools. Runtime of a few
  seconds per full catalog is fine.

## Acceptance

- `silicon_periph_diff_rp2350` runs the initial PIO catalog plus the three
  non-PIO scenarios (PLL LOCK, SIO-DIV latency, SIO-DIV dirty-clear) and
  reports PASS/FAIL per scenario, with a first-divergence dump on FAIL.
- `silicon_cycle_oracle_rp2350` runs the initial cycle catalog and reports
  per-case HW/EMU/delta, with a summary line for overall PASS/FAIL.
- Running either with `--filter never_matches` is a no-op that exits 0.
- Each FAIL points at a specific tech-debt item or exposes a new one; the
  existing tech-debt entries can be closed or updated based on measured
  HW numbers.

## Order of operations

1. Verify assumption (1) with a 20-line smoke binary: one PIO SM running
   `jmp 0` with CLKDIV=1, halt via BKPT, immediately write SM_ENABLE=0
   via probe-rs, read ADDR — then delay 10 ms and read ADDR again. Both
   reads must match for the mitigation to hold. Delete the smoke binary
   after.
2. Ship `silicon_cycle_oracle_rp2350` first. Smaller surface, smaller
   catalog, directly retires four tech-debt items on first run.
3. Ship `silicon_periph_diff_rp2350` with the minimal PIO catalog
   (`pio_nop_loop`, `pio_fixed_cycles`, `pio_side_set_toggle`). Add the
   rest as each scenario catches or confirms the absence of a bug.
4. When the non-PIO scenarios are working, close the corresponding
   tech-debt entries with measured numbers.
