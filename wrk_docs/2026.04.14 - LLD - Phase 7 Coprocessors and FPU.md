# mdrp2354 — Phase 7 LLD: Coprocessors and FPU

Version: 0.1.0 — DRAFT
Date: 2026-04-14

## 1. Purpose

Phase 7 completes the Cortex-M33 coprocessor surface. Phase 3 shipped the
**minimum** stubs required for the RP2350 bootrom to run (accept RCP salt, DCP
scratch registers, GPIOC NOP). Phase 7 makes **application code** work:

- Single-precision FPU instructions return IEEE-754-correct results with
  correct FPSCR exception flags.
- Lazy FP context save on exception entry (so interrupt latency isn't bloated
  by always stacking 16 FP registers).
- GPIOC (CP0) performs real 1-cycle GPIO reads/writes against the SIO GPIO
  state — the Pico SDK's fast-GPIO path.
- DCP (CP4/5) executes double-precision arithmetic using host `f64`.
- RCP (CP7) implements the full canary/redundancy check surface used by
  hardened application code (not just bootrom salt).

Downstream consumer that unblocks work: any Pico-SDK application using
`float`/`double`, or using `hardware_gpio` coproc macros. OneROM itself is
likely GPIO-coproc-light, but mdrp2354 is a library crate — applications we
don't own will exercise these paths.

### In scope

| C | GPIOC (CP0) full instruction set, wired to SIO GPIO | `core/coprocessor.rs`, `sio/gpio.rs` |
| D | DCP (CP4/5) full double-precision instructions via host `f64` | `core/coprocessor.rs` (new `core/dcp.rs`) |
| E | RCP (CP7) full assertion set (canary check, iequal, bvalid, count_*) | `core/coprocessor.rs` |
| F | Testing: FPU probe-rs generator, DCP host-f64 oracle, unit tests | `mdrp2354-test-harness/` |

### Explicit non-goals

- **No QEMU differential for FPU.** QEMU's FPv5 has known divergences in
  rounding, NaN payloads, and denormal handling. We use probe-rs (real
  silicon) as the FPU oracle. Trying to chase QEMU would burn time on
  QEMU-vs-silicon differences that don't matter to us.
- **No random-delay simulation for RCP.** The real RCP injects 0-127 cycles
  of random delay on some instructions as a side-channel countermeasure.
  Deterministic emulation is strictly more useful to downstream consumers;
  we mark this explicitly as a diverge-from-silicon (documented in the
  emulator README, not a bug).
- **No double-precision FPU.** RP2350 M33 is FPv5-SP-D16: single-precision
  only. Double-precision math goes through DCP (by design).
- **No feature flags, no migration shims.** Replace stubs in-place.
- **No NS (Non-secure) lazy FP context save.** TrustZone is stubbed in v1
  (HLD §2). Lazy FP respects only Secure state for now.

### Things we will NOT design for

- Configurable FPU behavior via env vars or features — FPSCR already gates
  FTZ/DN/rounding mode, which is all the configurability the architecture
  defines. No emulator-level knobs.
- Backwards-compat shims for the old CP0/CP4/CP5 stubs. Replace them.
- A generalized "coprocessor framework." Four coprocessors, four modules.
  Don't abstract prematurely.

## 4. Stage A — FPU correctness completion

### A.1 Add FPSCR exception flags

FPSCR bit layout (ARMv8-M ref manual §A2.7):

| Bit | Name | Meaning |
|-----|------|---------|
| 31-28 | NZCV | Condition flags from VCMP | done |
| 27 | AHP | Alternative half-precision | add |
| 26 | DN | Default NaN | add |
| 25 | FZ | Flush-to-zero | add |
| 24-22 | RMODE | Rounding mode | done |
| 7 | IDC | Input denormal cumulative | **add** |
| 4 | IXC | Inexact cumulative | **add** |
| 3 | UFC | Underflow cumulative | **add** |
| 2 | OFC | Overflow cumulative | **add** |
| 1 | DZC | Divide-by-zero cumulative | **add** |
| 0 | IOC | Invalid operation cumulative | **add** |

These are **cumulative sticky** flags. Once set, they stay set until VMSR
clears them. Every arithmetic instruction that could raise one must OR its
status into FPSCR.

**Implementation**: wrap the existing host-`f32` operations in a helper that
maps the result's IEEE-754 status to FPSCR bits.

```rust
// in core/execute_fpu.rs
struct FpOp { result: f32, flags: u32 }

fn fp_add(a: f32, b: f32, fpscr: u32) -> FpOp {
    // Detect IOC: any NaN input
    // Detect DZC: (±inf + ∓inf) — N/A for add, but for div
    // Detect OFC: result is ±inf and neither input was
    // Detect UFC: result rounded to zero (or to smallest denormal under FTZ)
    // Detect IXC: rounding occurred (compare exact f64 vs f32 result)
    // Apply FTZ if FPSCR.FZ: denormal inputs → ±0, denormal outputs → ±0
    // Apply DN if FPSCR.DN: NaN output → default quiet NaN 0x7FC0_0000
    ...
}
```

The host-`f32` approach is fine because IEEE-754 single-precision is
deterministic across x86/ARM. What's not automatic is FTZ/DN behavior —
those we wrap explicitly.

Keep it one file, no new module. Helpers live as free functions in
`execute_fpu.rs` above the instruction dispatchers.

### A.2 Missing Armv8-M single-precision instructions

Scan against the FPv5-SP-D16 instruction list and add what's missing. Based
on the current 23-type list, the gaps are:

- **VSEL** — conditional select (Armv8-M addition, not in FPv4)
- **VMAXNM / VMINNM** — IEEE-754-2008 maxNum/minNum (NaN-aware)
- **VCVTA / VCVTN / VCVTP / VCVTM** — convert-to-int with specific rounding
- **VRINTA / VRINTN / VRINTP / VRINTM** — round-to-integral with specific
  rounding (we have `VRINTR/X/Z` only)
- **VCVTB / VCVTT** (F16↔F32) — half-precision conversion
  (current file says "F16 stub")

Each is a ~20-line addition in the decode match. Full list of encodings in
ARMv8-M ARM §C4.3. No new architecture.

### A.3 Oracle: probe-rs FPU generator

The only trustworthy oracle. Add one harness binary:

```
crates/mdrp2354-test-harness/src/bin/fpu_probe_diff.rs
```

Sweeps a curated set of inputs (see §10) for each FPU instruction, runs
each on real RP2354 silicon via probe-rs, compares against emulator.

Generator: lives in `mdrp2354-test-harness/src/fpu_gen.rs`. For each
instruction, yields `(encoding, pre_state)` tuples with inputs from:

- Standard corners: ±0, ±1, ±∞, qNaN, sNaN, ±FLT_MIN, ±FLT_MAX, ±smallest-denormal
- Random floats (PRNG seeded from a CLI arg for reproducibility)
- Arithmetic edge cases: overflow boundary, underflow boundary, exact
  rounding cases

**Out of scope for Stage A oracle**: VMLA/VFMA variants that use internal
extended precision. These we validate by construction (host `f32::mul_add`
uses the same IEEE-754 fused semantics).

## 5. Stage B — Lazy FP context save

### B.1 Background

Armv8-M exception entry normally stacks 8 words (basic frame). If the
thread was using the FPU (`CONTROL.FPCA == 1`), the processor additionally
stacks 18 words of FP context (S0-S15 + FPSCR + reserved). That's a ~22-cycle
interrupt latency cost even if the handler never touches the FPU.

Lazy stacking (`FPCCR.LSPEN == 1`, default): on entry, just **reserve** the
18 words of space and set `FPCCR.LSPACT = 1`. Actual save is deferred until
the first FP instruction in the handler, which traps, flushes S0-S15 +
FPSCR to the reserved frame, and clears LSPACT.

Most interrupts don't touch the FPU, so the deferred flush never happens.
Pico SDK relies on this for interrupt latency.

### B.2 New PPB registers

Add to `crates/mdrp2354/src/bus/ppb.rs` (alongside `cpacr`):

```rust
pub fpccr: u32,   // FP Context Control Register, reset 0xC000_0000
                  //   bit 31: ASPEN (auto-preserve) — RAO for simplicity
                  //   bit 30: LSPEN (lazy state preservation) — reset 1
                  //   bit 0:  LSPACT (lazy state active)
pub fpcar: u32,   // FP Context Address Register (reserved frame location)
pub fpdscr: u32,  // FP Default Status Control — FPSCR template for NS handlers
                  //   bits 26:22 (DN, FZ, RMODE) used on exception entry
```

Memory-mapped at E000_EF34 (FPCCR), E000_EF38 (FPCAR), E000_EF3C (FPDSCR)
— add to the existing PPB dispatch table.

### B.3 CONTROL.FPCA bit

`CONTROL` is already in the register file. Bit 2 is FPCA. It:

- Is set by the first FPU instruction executed in a context (add to the
  entry prologue of `fpu_execute` — once per step, cheap)
- Is cleared by exception entry after the FP frame is reserved
- Is restored from EXC_RETURN bit [4] on exception return

### B.4 Exception entry changes (`core/exceptions.rs`)

Replace the hardcoded `0xFFFF_FFF1`/`FFD`/`FF9` EXC_RETURN values with:

```rust
// Current: LR bit [4] always set (no FP frame).
// New: LR bit [4] = !FPCA   (clear if FP frame present)

let had_fp = self.regs.control & 0x4 != 0;
let base = if self.regs.in_handler_mode() { 0xFFFF_FFE1 }
           else if use_psp { 0xFFFF_FFED }
           else { 0xFFFF_FFE9 };
// bits [3:0] = 0b1001/1101/0001; bit [4] = had_fp ? 0 : 1
self.regs.r[14] = base | (if had_fp { 0 } else { 0x10 });
```

If `had_fp`:

1. Allocate **18 more words** above the basic frame (total 32 + 72 = 104
   bytes, or 108 with alignment padding).
2. If `FPCCR.LSPEN == 1`: just reserve the space, set `FPCCR.LSPACT = 1`
   and `FPCAR = frame address of FP region`. Don't touch S0-S15. Done.
3. Else (LSPEN == 0, eager): write S0-S15 + FPSCR + reserved to the FP
   region now.

Clear `CONTROL.FPCA`. Update return-address cost: +12 cycles for eager
save, 0 additional for lazy (just bookkeeping).

### B.5 Lazy flush trigger (`core/execute_fpu.rs`)

At the top of `fpu_execute`:

```rust
fn fpu_execute(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
    let core = bus.active_core();
    let fpccr = bus.ppb[core].fpccr;
    if fpccr & 1 != 0 {  // LSPACT
        self.flush_lazy_fp_context(bus);
        // clears LSPACT, writes S0-S15 + FPSCR to FPCAR frame
    }
    self.regs.control |= 0x4;  // FPCA
    // ... existing dispatch ...
}
```

`flush_lazy_fp_context` uses `FPCAR` to know where to write. ~12 cycles
(16 word-writes + housekeeping).

### B.6 Exception return changes

If `EXC_RETURN` bit [4] is clear (had FP frame):

- If `FPCCR.LSPACT == 1`: thread never touched FP during handler, no real
  save happened. Just clear LSPACT, deallocate 18 words.
- Else: pop S0-S15 + FPSCR from the FP region.

Restore `CONTROL.FPCA = 1` (had_fp was 1 on entry, so it's 1 on return).

### B.7 Test strategy

Integration test in `crates/mdrp2354/tests/lazy_fp.rs`:

1. **No-FP handler**: thread does `VADD`, takes an interrupt whose handler
   doesn't use FP, returns. Assert: `FPCCR.LSPACT` was 1 during handler,
   S0-S15 retained their values, zero cycles spent on FP save.
2. **FP handler**: same thread, handler does `VADD`. Assert: LSPACT
   cleared, FP frame contents valid, thread's S0-S15 preserved across.
3. **Nested**: ISR takes a second interrupt — second entry sees fresh
   FPCA state.
4. **Eager mode**: set `FPCCR.LSPEN = 0`, verify FP frame written on entry.

## 6. Stage C — GPIO coprocessor (CP0)

### C.1 Instruction set

Pico SDK hardware_gpio.h macros decode to ~15 CP0 encodings. Reference:
RP2350 datasheet §3.6.6, and `hardware/gpio.h` in pico-sdk.

The important operations, using ARM coproc encoding notation:

| SDK name | Encoding | Op |
|----------|----------|-----|
| gpioc_bit_out_get(pin) | MRC CP0, 0, Rd, CRn=pin_hi, CRm=pin_lo, op2=0 | Return 1 bit |
| gpioc_bit_out_put(pin, v) | MCR CP0, 0, Rt, ... op2=4 | Set 1 bit |
| gpioc_bit_set(pin) | MCR CP0, 0, -, ... op2=5 | Atomic set |
| gpioc_bit_clr(pin) | MCR CP0, 0, -, ... op2=6 | Atomic clear |
| gpioc_bit_xor(pin) | MCR CP0, 0, Rt, ... op2=7 | Atomic XOR |
| gpioc_hi_out_get() | MRC CP0, 4, Rd, CRn=0, CRm=0 | Read GPIO[47:32] |
| gpioc_lo_out_get() | MRC CP0, 0, Rd, CRn=0, CRm=0 | Read GPIO[31:0] |
| gpioc_hi_out_put(v) | MCR CP0, 4, Rt, ... | Write GPIO[47:32] |
| gpioc_lo_out_put(v) | MCR CP0, 0, Rt, ... | Write GPIO[31:0] |
| gpioc_hi_oe_*(mask) | similar, CRn=1 | Output enable bank |
| gpioc_lo_oe_*(mask) | similar, CRn=1 | Output enable bank |
| gpioc_hi_in_get(), lo_in_get() | MRC variants | Read input bank |

Decode in `cp0_gpioc` via match on `(opc1, CRn, CRm, opc2)`. One big match,
routes to SIO GPIO operations.

### C.2 Wiring to SIO

The SIO block (`crates/mdrp2354/src/sio/gpio.rs` — per our module layout)
already holds GPIO out/oe/in state as `u64` (48 pins). Expose
fast-path methods:

```rust
impl Sio {
    pub(crate) fn gpio_bit_out(&self, pin: u8) -> bool;
    pub(crate) fn gpio_bit_set(&mut self, pin: u8);
    pub(crate) fn gpio_bit_clr(&mut self, pin: u8);
    pub(crate) fn gpio_bit_xor(&mut self, pin: u8);
    pub(crate) fn gpio_bit_put(&mut self, pin: u8, v: bool);
    pub(crate) fn gpio_lo_out(&self) -> u32;
    pub(crate) fn gpio_hi_out(&self) -> u32;
    pub(crate) fn gpio_lo_in(&self) -> u32;
    pub(crate) fn gpio_hi_in(&self) -> u32;
    // ... and OE variants
}
```

These are the same operations as writing to the SIO GPIO MMIO registers,
minus the bus round-trip. CP0 dispatches straight to them.

Cycle cost: 1 (the whole point of CP0 is that it's single-cycle).

### C.3 Test strategy

Unit tests in `core/coprocessor.rs` `#[cfg(test)]`:

- Encode each CP0 macro, execute, assert SIO state matches a direct
  MMIO-path write.
- Bit operations: set/clr/xor/put round-trip correctness.
- Bulk operations: lo/hi out/in/oe read-what-you-wrote.
- CPACR-disabled path: assert UsageFault.

Integration test: a firmware blob that toggles GPIO via CP0 and verifies
it's observed externally (we can reuse the blinky test harness from
Phase 4).

## 7. Stage D — DCP (CP4/5)

### D.1 Architecture

The DCP is a custom double-precision coprocessor: 8 double-precision
values held as 16 × 32-bit half-registers, plus a status register. Custom
CDP instructions operate on the register file; MCR/MRC transfer between
ARM Rt and half-registers.

Reference: RP2350 datasheet §3.6.7. Pico SDK wrapper:
`pico-sdk/src/rp2_common/pico_double/double_aeabi_dcp.S`.

### D.2 State

New module `crates/mdrp2354/src/core/dcp.rs`:

```rust
pub(crate) struct Dcp {
    /// 8 double values, each represented as two u32 halves.
    /// Matches the half-register addressing used by MCR/MRC.
    pub halves: [u32; 16],
    /// Status register (sign, NaN, inf, zero flags).
    pub status: u32,
}
```

Replace `self.dcp_data: [u32; 2]` on `CortexM33` with `self.dcp: Dcp`.

### D.3 Instructions

Implement as CDP dispatch, opcode-indexed match. The core operations,
grouped:

- **Arithmetic**: `dcp_dadd`, `dcp_dsub`, `dcp_dmul`, `dcp_ddiv`,
  `dcp_dsqrt`. Read operand pairs, execute in host `f64`, write back.
- **Compare**: `dcp_dcmp_*` → status register bits.
- **Convert**: `dcp_i2d`, `dcp_u2d`, `dcp_d2i`, `dcp_d2u`, `dcp_d2f`,
  `dcp_f2d`. Host-`f64` conversions.
- **Transfer**: `dcp_rfma/rfmb/wxma/wxmb` etc. — MCR/MRC variants that
  already work as-is (just extend to more registers).
- **Divide-by-zero behaviors**: produce ±∞ or NaN per IEEE-754.

All CDP ops accept a CRd/CRn/CRm triple — treat as half-register indices
(0-15), read operands as adjacent pairs, same for results.

### D.4 Cycle counts

From datasheet §3.6.7 table: ~2-28 cycles depending on operation.
Implement as a lookup (small match) keyed by opcode. Don't overthink
micro-timing — the real DCP's exact cycle counts are operation + input
dependent; we use the datasheet's "typical" column.

### D.5 Oracle

Host-`f64` *is* the oracle. The DCP's specification is "do IEEE-754
double-precision." We compute in host `f64`; results match by
construction. Tests are:

- Unit tests: known value pairs → expected results.
- Property tests (proptest): generate random f64 pairs, run through DCP
  dispatch path, compare against naive host `f64` op. These must match
  exactly because it's the same code path reached two ways.

No QEMU, no probe-rs needed for DCP arithmetic.

## 8. Stage E — RCP (CP7)

### E.1 Current state (keep)

`coprocessor.rs:56-118` already handles:

- `rcp_canary_status pc` (MRC with Rt=15): N flag = salt valid
- `rcp_canary_get` (MRC Rt≠15): returns `salt ^ 0xDEADBEEF`
- `rcp_canary_check` (MCR): accepted silently
- `rcp_salt_core0/1` (MCRR2): sets salt

### E.2 Additions

Extend the MCR / CDP dispatch to cover the full SDK surface:

| Instruction | Semantics | Mismatch action |
|-------------|-----------|-----------------|
| `rcp_canary_check` | Compare Rt against salt ^ 0xDEADBEEF | HardFault |
| `rcp_iequal` | Compare two Rt values | HardFault |
| `rcp_bvalid` | Validate Rt ∈ {0, 1} | HardFault |
| `rcp_btrue` / `rcp_bfalse` | Assert Rt == 1 / Rt == 0 | HardFault |
| `rcp_ifgte` / `rcp_iflte` | Assert unsigned comparison | HardFault |
| `rcp_count_init` | Start a counter | side effect |
| `rcp_count_check` | Assert counter value | HardFault |
| `rcp_panic` | Unconditional fault | HardFault |

On assertion failure the real RCP raises NMI and the bootrom's NMI
handler loops. Emulator behavior: set `pending_fault = HardFault`, log
`"RCP assertion failed: <which>"` for diagnosability.

Encoding mapping per pico-sdk `rcp.h`. The majority are CDP with `opc1`
distinguishing them.

### E.3 What we skip (documented divergence)

- **Random delays**: real RCP inserts 0-127 pseudo-random cycles on some
  ops. We don't. Document in module-level comment: *"This emulator's RCP
  is deterministic. Real hardware varies cycle count by ±127."*
- **Parity checks on instruction encoding**: real RCP validates a parity
  bit in the instruction encoding. We accept any encoding we recognize.

Neither affects functional correctness of hardened SDK code.

### E.4 Test strategy

Unit tests: for each assertion instruction, one test that passes and one
that triggers HardFault. Unit-test level is sufficient — RCP semantics
are trivially enumerable.

## 12. Risks

### 12.1 FPU oracle dependency

Blocker if hardware access is unavailable. Mitigation: Stage A exception
flags are the highest-value subset; land instruction additions first
(low risk — no regression potential since we're adding, not modifying),
defer the flag sweep to when silicon is available.

### 12.2 Lazy FP correctness is subtle

Armv8-M lazy stacking has edge cases around nested exceptions, BASEPRI
masking, and TrustZone transitions. We skip TrustZone entirely (HLD §2).
For nested: the standard says each level sees independent FPCA/LSPACT
state via the saved EXC_RETURN — follow the spec.

Mitigation: integration tests cover nesting explicitly (§B.7 #3). If a
real Pico SDK application exposes a bug we don't catch in the integration
test, that's a known risk.

### 12.3 DCP instruction set completeness

We're reading off the datasheet + pico-sdk. If an application uses a DCP
instruction we didn't enumerate, it'll hit the "not a recognized CP4/5
encoding" path and silently NOP. That's a silent-wrong-answer bug.

Mitigation: log warning on unrecognized CDP encoding (don't fault — the
real hardware does the same, instruction isn't strictly reserved). Easier
to diagnose than a silent NOP.

### 12.4 RCP HardFault-on-mismatch might surprise us

Real RCP raises NMI, not HardFault. Difference matters: NMI can fire
when faults are masked; HardFault can't. For bootrom-style code that
masks everything during sensitive sequences, this matters.

Mitigation: check which vector the RP2350 bootrom actually uses for RCP
traps and match it. Likely NMI. Easy to switch.

## 14. Sequencing

Propose this order, each independently shippable:

1. **Stage C (GPIOC)** — simplest, clearest win, unblocks any Pico SDK
   app using fast GPIO. ~1 day.
2. **Stage E (RCP extensions)** — small, enumerable, self-contained.
3. **Stage A.2 (Armv8-M FPU additions)** — risk-free additions.
4. **Stage D (DCP)** — medium-complexity, needs new module.
5. **Stage B (Lazy FP)** — touches exception path, save for after A.2 is
   solid so any regression is obviously in B.
6. **Stage A.1 (FPU exception flags)** — requires probe-rs; may land last
   or in parallel with B.

Each stage closes with its own commit; don't bundle.
