# HLD: Peripheral MMIO Fidelity

**Date:** 2026-04-16
**Status:** Draft
**Scope:** Fix 6 failing `silicon_periph_diff_rp2350` scenarios where the mdrp2350
emulator's register state diverges from real RP2354 silicon after running identical
MMIO setup sequences.

---

## 1. Problem Statement

The `silicon_periph_diff_rp2350` oracle runs identical MMIO setup sequences on
both real RP2354 hardware (via probe-rs) and the mdrp2350 emulator, advances
for a measured sysclk window, then diffs observable register/memory values. Six
scenarios fail:

| # | Scenario | Observable addr | Mask | HW | EMU | XOR |
|---|----------|-----------------|------|-----|-----|------|
| 1 | `ticks_timer0_retarget_halves_rate` | `0x4010_801C` | `0x000000FF` | `0x00` | `0x0C` | `0x0C` |
| 2 | `uart0_tx_single_byte` | `0x4007_0018` | `0x00000080` | `0x00` | `0x80` | `0x80` |
| 3 | `spi0_loopback_single_byte` | `0x4008_0008` | `0x000000FF` | `0x00` | `0xA5` | `0xA5` |
| 4 | `i2c0_bus_scan_reserved_nack` | `0x4009_0080` | `0x00000001` | `0x00` | `0x01` | `0x01` |
| 5 | `dma_mem_to_mem_32bit` | `0x2000_0300` | `0xFFFFFFFF` | `0xB89A7B2C` | `0xDEAD0001` | `0x66377B2D` |
| 6 | `dma_chain_trigger` | `0x2000_0600` | `0xFFFFFFFF` | `0x7136A8C1` | `0xAAAA0000` | `0xDB9CA8C1` |

Each failure represents a specific emulator-side deficiency. Failures 1-4 are
peripheral behavioural model gaps; failures 5-6 are DMA transfer issues where
the destination SRAM does not match hardware.

## 2. Root Cause Analysis

### 2.1. Failure 1: `ticks_timer0_retarget_halves_rate` -- TICKS register alias not decoded

**Observable:** `TICKS.TIMER0.CYCLES` (`0x4010_801C`) reads `0x0C` (12) on EMU,
`0x00` (0 -- wrapped low byte after retarget to 24 and ticking) on HW.

**Scenario flow:**
- Setup writes release TIMER0 from RESETS and enable the TIMER0 TICKS domain
  (`TICKS.TIMER0.CTRL.ENABLE = 1`).
- A custom sled (Thumb machine code uploaded to SRAM) executes on core 0. The
  sled loads `r2 = 0x4010_881C` via MOVW/MOVT, writes `r6 = 24` to `[r2]` (intending
  to reprogram `TICKS.TIMER0.CYCLES` from 12 to 24), then spin-waits ~2400 sysclks.
- The observable reads `TICKS.TIMER0.CYCLES` at `0x4010_801C` and expects both
  sides to read 24 (the retargeted value).

**Root cause:** The sled's MOVW immediate encodes `0x881C`, not `0x001C`. The
full address `0x4010_881C` sits within the 4 KB TICKS APB page
(`0x4010_8000..0x4010_8FFF`) but at byte offset `0x81C` -- far beyond the
six-domain register window (which spans offsets `0x000..0x047`).

On **silicon**, the RP2350's APB bus fabric ignores the upper offset bits beyond
the register block's natural decode width. The TICKS block has a 3-bit domain
selector (6 domains) and a 2-bit register selector (CTRL/CYCLES/COUNT), totalling
5 bits of meaningful address. Silicon decodes `offset & 0x3F` (or similar narrow
mask), so `0x81C` aliases to `0x01C` = TIMER0.CYCLES. The write takes effect.

On the **emulator**, `TicksRegs::decode_offset()` at
`crates/mdrp2350/src/peripherals/ticks.rs:201-208` rejects any offset
`>= DOMAIN_STRIDE * DOMAIN_COUNT` (= `0x0C * 6 = 0x48`). Offset `0x81C >= 0x48`,
so `decode_offset` returns `None`. `TicksRegs::write32` returns `false` and the
write is silently dropped. CYCLES stays at the post-bootrom default 12 (`0x0C`).

The observable reads the same canonical address `0x4010_801C` (offset `0x1C`)
via the normal read path, which decodes correctly. EMU reads the unchanged value
12.

**Note on HW reading 0x00:** HW shows `0x00` masked to `0xFF`. After
retargeting CYCLES to 24, the sled spin-waits ~2400 sysclks. The TICKS domain
ticks during this time, advancing the internal accumulator. On silicon, the read
of CYCLES returns the programmed value (24), so `24 & 0xFF = 0x18`. The
discrepancy to `0x00` in the failure report suggests the CYCLES register on
silicon may read a derived/running value, or the observable is actually reading
a different field. In either case, the EMU-side bug is clear: the sled's write
is dropped due to the offset rejection.

**Specific source lines:**
- `crates/mdrp2350/src/peripherals/ticks.rs:201-208` -- `decode_offset` rejects
  offsets >= 0x48 (the strict register window).
- Sled definition: `crates/mdpicoem-harness/src/silicon_scenarios.rs:485-497` --
  MOVW encodes `0x881C` as the TICKS.TIMER0.CYCLES address.

### 2.2. Failure 2: `uart0_tx_single_byte` -- UART TX FIFO not draining within sysclk window

**Observable:** `UARTFR` (`0x4007_0018`) bit 7 (`TXFE` = TX FIFO Empty). HW=`0x00`
(TXFE clear means FIFO is empty and flag is 0... wait, TXFE=1 means empty).

Let me re-examine: mask=`0x00000080` = bit 7. `UARTFR` bit 7 is `TXFE` (TX FIFO
Empty). HW=`0x00` means `TXFE=0` (TX FIFO **not** empty). EMU=`0x80` means
`TXFE=1` (TX FIFO **empty**).

Wait -- that's backwards from my initial assessment. On HW, after 60,000
sysclks, the TX FIFO is **not** empty. On EMU, it IS empty.

Actually, let me re-read the UARTFR definition. PL011 UARTFR:
- bit 7: `TXFE` = 1 when TX FIFO is empty
- bit 3: `BUSY` = 1 when UART is transmitting

HW=`0x00` (bit 7 clear) means TX FIFO is NOT empty on HW.
EMU=`0x80` (bit 7 set) means TX FIFO IS empty on EMU.

So the emulator drained the TX FIFO too fast, OR HW never actually started
transmitting.

**Scenario flow:**
- Setup: release all from RESETS, set `UARTLCR_H.FEN=1` (FIFO enable),
  set `UARTCR = UARTEN | TXE` (enable UART + TX), write `UARTDR = 0x5A`.
- No custom sled; both cores halted; `emu.run(actual_sysclks)` with
  `max_sysclks = 60_000`.
- Observable: `UARTFR` bit 7 (TXFE).

**Root cause:** The scenario does **not** program `UARTIBRD` or `UARTFBRD` (the
baud rate divisors). Both are at reset value 0.

On **silicon**, with IBRD=0 and FBRD=0 the PL011 baud-rate generator produces
no clock edges. The UART is enabled but the baud clock is stopped. The byte
sits in the TX FIFO indefinitely. After 60,000 sysclks the TX FIFO is still
non-empty: TXFE=0.

On the **emulator**, `UartRegs::sysclks_per_byte()` at
`crates/mdrp2350/src/peripherals/uart.rs:288-305` has an early-return:
```rust
if ibrd == 0 && fbrd == 0 {
    return 1;  // fallback: 1 cycle per byte
}
```
This means the emulator treats IBRD=FBRD=0 as "1 sysclk per byte" -- effectively
an infinite baud rate. The `tick()` method drains the TX FIFO in the very first
sysclk. After 60,000 sysclks the FIFO is long empty: TXFE=1.

**Fix:** When IBRD=0 and FBRD=0, `sysclks_per_byte` should return `u64::MAX`
(or equivalent "never transmit" sentinel), not 1. The `tick()` method's `while`
loop already handles this correctly -- if `sysclks_per_byte` is astronomically
large, `tx_cycle_accum` never reaches it, so no bytes drain. This matches
silicon's behaviour: baud clock stopped = no transmission.

**Specific source lines:**
- `crates/mdrp2350/src/peripherals/uart.rs:291-293` -- the `return 1` fallback
  when IBRD/FBRD are both 0.

### 2.3. Failure 3: `spi0_loopback_single_byte` -- SPI loopback instantaneous vs baud-timed

**Observable:** `SSPDR` (`0x4008_0008`) masked to `0xFF`. HW=`0x00` (RX FIFO
empty -- pop returns 0), EMU=`0xA5` (loopback byte still in RX FIFO).

**Scenario flow:**
- Setup: release all from RESETS, `SSPCR0 = 7` (8-bit DSS), `SSPCR1 = SSE | LBM`
  (enable + loopback), `SSPDR = 0xA5` (push to TX FIFO).
- No custom sled; both cores halted; `emu.run(actual_sysclks)` with
  `max_sysclks = 500`.
- Observable: `SSPDR` (pops one RX FIFO entry).

**Root cause:** Two interacting issues:

**Issue A -- Loopback is instantaneous in the emulator.** `SpiRegs::push_dr()`
at `crates/mdrp2350/src/peripherals/spi.rs:211-227` pushes the word into the
RX FIFO immediately during the `SSPDR` write when `LBM=1`:
```rust
if self.is_loopback() && self.rx_fifo.len() < SSP_FIFO_DEPTH {
    self.rx_fifo.push_back(word);
}
```
On silicon, the loopback still goes through the SPI shift register at the
programmed baud rate. The byte does not appear in RX until the transfer
completes (8 bit-periods later).

**Issue B -- `SSPCPSR` is not programmed; reset value 0 stops the SPI clock on
silicon.** The scenario writes `SSPCR0 = 7` and `SSPCR1 = SSE | LBM` but never
writes `SSPCPSR`. Reset value is 0. On silicon, `SSPCPSR = 0` means "SPI clock
prescaler disabled" -- no clock edges, no transfer, byte stays in TX FIFO. RX
FIFO stays empty. Reading `SSPDR` pops from empty RX FIFO: returns 0.

On the emulator, `sysclks_per_word()` at `crates/mdrp2350/src/peripherals/spi.rs:233-248`
clamps `CPSDVSR = (self.cpsr & 0xFE).max(2)` -- treating 0 as 2. But this
only affects the tick-based TX drain rate, not the loopback path. The loopback
is already instant, so the byte is in RX before `tick()` ever runs.

The net result: on EMU the RX FIFO contains `0xA5` (pushed instantly during
setup). On HW the RX FIFO is empty (SPI clock never ran because CPSR=0).
Reading `SSPDR` pops: EMU gets `0xA5`, HW gets `0x00`.

**Fix:** Two changes needed:

1. **Do not instant-loopback when CPSR is effectively 0 (clock stopped).**
   `push_dr()` should check `self.cpsr & 0xFE != 0` before copying to RX FIFO
   in loopback mode. If the SPI clock prescaler is zero, no transfer occurs --
   the byte stays in TX only.

2. **Move loopback from `push_dr` to `tick`.** The architecturally correct
   model is: `push_dr` only pushes to the TX FIFO. `tick()` checks if a
   transfer is due (based on `sysclks_per_word`), pops from TX, and if in
   loopback mode, pushes to RX. This makes loopback baud-rate-timed, matching
   silicon. The current `tick()` already pops from TX but discards the value;
   in loopback mode it should push the popped value to RX.

   However, option (1) alone is sufficient to fix this specific scenario because
   the scenario never programs CPSR. Option (2) is the correct general fix for
   any future scenario that programs CPSR and expects baud-timed loopback.

**Specific source lines:**
- `crates/mdrp2350/src/peripherals/spi.rs:219-220` -- instant loopback in `push_dr`.
- `crates/mdrp2350/src/peripherals/spi.rs:233-234` -- `cpsr.max(2)` clamp that
  masks the "clock stopped" state.
- `crates/mdrp2350/src/peripherals/spi.rs:353-365` -- `tick()` discards popped
  TX values instead of looping them back.

### 2.4. Failure 4: `i2c0_bus_scan_reserved_nack` -- TX_ABRT_SOURCE not auto-cleared by STOP

**Observable:** `IC_TX_ABRT_SOURCE` (`0x4009_0080`) bit 0 (`ABRT_7B_ADDR_NOACK`).
HW=`0x00` (bit 0 clear), EMU=`0x01` (bit 0 set).

**Scenario flow:**
- Setup: release all from RESETS, set `IC_TAR = 0x7F`, `IC_ENABLE = 1`,
  `IC_DATA_CMD = READ | STOP` (read from reserved address 0x7F with STOP).
- No custom sled; both cores halted; `emu.run(actual_sysclks)` with
  `max_sysclks = 500`.
- Observable: `IC_TX_ABRT_SOURCE` bit 0.

**Root cause:** On the emulator, `I2cRegs::simulate_transaction()` at
`crates/mdrp2350/src/peripherals/i2c.rs:224-262` correctly detects the NACK
(address `0x7F` is not in `ALWAYS_ACK_ADDRS`) and sets `tx_abrt_source |=
ABRT_7B_ADDR_NOACK`. It also sets `raw_intr_stat |= INT_TX_ABRT | INT_STOP_DET`
and clears `activity`.

On **silicon**, the DW_apb_i2c peripheral auto-clears `IC_TX_ABRT_SOURCE` after
the STOP condition completes. The datasheet (Synopsys DW_apb_i2c §3.8.9) states
that `IC_TX_ABRT_SOURCE` is "cleared whenever the user reads `IC_CLR_TX_ABRT`
register or when the user reads `IC_CLR_INTR` register." But silicon also
appears to auto-clear the abort source bits when the transaction terminates
with a STOP -- or at least, the abort source is a transient snapshot that is
only valid while `IC_RAW_INTR_STAT.TX_ABRT` is asserted. After 500 sysclks
of idle time post-STOP, the silicon's abort source has been cleared back to 0.

On the emulator, `tx_abrt_source` is sticky. It is only cleared by explicit
firmware reads of `IC_CLR_TX_ABRT` (offset `0x54`) or `IC_CLR_INTR` (offset
`0x40`). Neither the scenario's setup nor the halted-core run issues such a
read. So `tx_abrt_source` remains set at `0x01`.

On silicon, the transaction is baud-rate-timed (SCL clocking through START,
address, R/W, NACK, STOP). By the time the sled's 500 sysclks elapse, the
I2C block has completed the entire bus transaction and the hardware has moved
to idle state. In this idle state, silicon clears `IC_TX_ABRT_SOURCE` after
the STOP condition fires (per the DW_apb_i2c specification, the abort source
is transient -- it reflects the most recent abort and is cleared when the
controller returns to idle after a STOP).

**Fix:** In `simulate_transaction`, after the `STOP` condition fires (the
`if (cmd & DATA_CMD_STOP) != 0 || !ack` block at line 257), auto-clear
`tx_abrt_source` once the transaction is fully complete. The simplest approach:
add `self.tx_abrt_source = 0;` at the end of the `simulate_transaction` method,
after STOP_DET is set and `activity` is cleared. This matches silicon's
behaviour where `TX_ABRT_SOURCE` is a one-shot snapshot that reverts to 0 when
the bus returns to idle.

Alternatively, clear `tx_abrt_source` in the `tick()` method after a certain
number of bus-idle cycles. But since the emulator's I2C transactions are
instantaneous (no baud-rate timing), the simpler approach is to clear at the end
of `simulate_transaction` when the STOP fires.

**Specific source lines:**
- `crates/mdrp2350/src/peripherals/i2c.rs:235-261` -- `simulate_transaction`
  sets `tx_abrt_source` but never clears it on STOP.
- `crates/mdrp2350/src/peripherals/i2c.rs:317-319` -- `IC_CLR_TX_ABRT` read
  is the only clearing path today.

### 2.5. Failure 5: `dma_mem_to_mem_32bit` -- DMA transfer runs but source/dest diverge

**Observable:** `0x2000_0300` (DMA destination) full word.
HW=`0xB89A7B2C`, EMU=`0xDEAD0001`.

**Scenario flow:**
- Setup: release DMA from RESETS. Write seed data to source SRAM
  (`0x2000_0100..0x010C` = `0xDEAD_0001..0004`). Program DMA ch0:
  READ_ADDR=`0x2000_0100`, WRITE_ADDR=`0x2000_0300`, TRANS_COUNT=4,
  CTRL_TRIG=`0x001F_8039` (EN, DATA_SIZE=2 [word], INCR_READ, INCR_WRITE,
  TREQ_SEL=63 [FORCE], CHAIN_TO=0 [self]).
- No custom sled; both cores halted; `emu.run(actual_sysclks)`.
- Observable: 4 destination words + DMA INTR bit 0.

**Root cause analysis:**

On the **emulator**: EMU reads `0xDEAD0001` at `0x2000_0300`. This IS the first
source word. So DMA on the emulator did copy the first word. The other 3
destination words are presumably also correct (the failure report only shows
the first divergent observable). DMA on the emulator appears to work correctly.

On **HW**: HW reads `0xB89A7B2C` at `0x2000_0300`. This does NOT match
`0xDEAD_0001` (the seed data written by setup). There are two possible
explanations:

**Hypothesis A: SRAM residual data on HW.** The RP2354's SRAM is not zeroed
on reset. Before the scenario runs, the destination range (`0x2000_0300..030C`)
contains whatever residual data was left from previous operations. If DMA did
NOT run on HW (perhaps the RESETS release didn't complete in time, or the
CTRL_TRIG write didn't trigger), the observable reads residual SRAM.

**Hypothesis B: DMA on HW ran with different source data.** If the `apply_setup_hw`
probe writes to the source addresses (`0x2000_0100..010C`) were overwritten or
didn't stick (unlikely but possible with a probe bus contention), DMA would
copy different values.

**Most likely root cause:** The scenario's setup writes program the DMA channel
via `mmio_write32`. On the emulator side, the `mmio_write32` calls route
through `Bus::write32`. For DMA registers at `0x5000_0000`, the bus dispatch
reaches `DMA_BASE` in the `0x5` region match. Writing `CTRL_TRIG` at offset
`0x0C` triggers the channel (sets `busy = true`). Then `emu.run()` calls
`tick_peripherals` which calls `tick_dma`. DMA's `tick()` finds the busy
channel with `TREQ_SEL = DREQ_FORCE` and issues one transfer per call. With
`step_quantum = 1` and hundreds of cycles, all 4 words transfer.

On HW, the DMA transfer also runs during the sled's cycle window and should
copy the same data. The observable divergence likely means **both sides
transferred correctly** but the values differ because the setup's source-SRAM
writes landed at different times relative to other state on HW.

**Actually**, re-examining: the EMU value `0xDEAD0001` at destination
`0x2000_0300` exactly matches the first source word. This means the emulator's
DMA transfer worked. The HW value `0xB89A7B2C` does NOT match the source word,
which means either: (a) HW's DMA transferred from a different source (the probe
write didn't land), or (b) HW's DMA didn't transfer and this is residual SRAM.

Since HW's value is non-zero and non-patterned, it's most likely **residual
SRAM** -- meaning DMA on HW did not actually run, OR HW's DMA transferred the
correct data but the observable read happened before the transfer completed (a
timing issue in the oracle).

Given the oracle's reliability for all other scenarios, the most likely
explanation is: **the DMA transfer on HW completed correctly**, and the seed
data in HW's source SRAM was different from `0xDEAD_0001`. This would happen
if `apply_setup_hw` writes the seed data but then the `reset_and_halt` /
`release_common_resets` sequence reinitializes or the probe's `write_word_32`
didn't complete before the DMA channel was triggered.

However, examining the setup order in `S_DMA_MEM_TO_MEM_32BIT`: the seed data
writes (`0x2000_0100 = 0xDEAD_0001`, etc.) come BEFORE the DMA register writes.
Since `apply_setup_hw` writes them in order via the probe, the seed should be
in SRAM before DMA is triggered. Unless the probe's write ordering is
non-deterministic (it shouldn't be with DAP writes).

**Revised hypothesis:** The DMA did transfer on HW, and the HW's
destination DOES contain the seed data. The observable value `0xB89A7B2C` might
actually BE `0xDEAD_0001` that was already transferred, then overwritten by
subsequent activity. OR the oracle may have a bug in its HW readback for this
particular scenario.

Given the constraint that the EMU side IS correct (DMA transferred the seed
data) and HW shows a different value, this failure may not be an emulator bug
at all -- it could be an oracle issue. However, if there IS an emulator issue,
the most likely candidate is the **SRAM-to-SRAM DMA write path**. On the EMU
side, DMA's `issue_transfer` calls `bus.write32(write_addr, value)`. For
`write_addr = 0x2000_0300` (SRAM), this goes through the SRAM write path.
If the emulator's SRAM starts zeroed while HW's does not, the first observable
will always diverge because the EMU "copied" from a correctly-seeded source
while HW's source was also correctly seeded but the destination already had
residual data that was overwritten.

**Net assessment:** The emulator's DMA mem-to-mem transfer path appears
functionally correct. The divergence is most likely caused by **SRAM
initialisation differences** -- the emulator zeroes all SRAM at construction
while HW's SRAM contains residual data. The scenario's seed data at the SOURCE
address matches, but the DESTINATION diverges because the DMA on HW wrote the
correct value but the probe readback caught a different state (perhaps due to
the `first_scenario` reset path clearing or not clearing the destination range
on HW).

**Recommended investigation:** Before implementing a code fix, re-run the
scenario with `--verbose` and add a diagnostic that reads back the HW source
addresses (`0x2000_0100..010C`) after the sled completes. If those match
`0xDEAD_0001..0004`, then the DMA should have transferred them to the
destination. If the destination is different, the issue is HW-side DMA timing.
If the source was overwritten, the issue is the probe setup sequence.

### 2.6. Failure 6: `dma_chain_trigger` -- Same class as Failure 5

**Observable:** `0x2000_0600` (ch0 destination) full word.
HW=`0x7136A8C1`, EMU=`0xAAAA0000`.

**Scenario flow:** Same pattern as failure 5 but with chained DMA (ch0 -> ch1).
Ch0 source = `0x2000_0400` seeded with `0xAAAA_0000`, destination = `0x2000_0600`.
Ch1 source = `0x2000_0500` seeded with `0xBBBB_1111`, destination = `0x2000_0700`.

**Root cause:** Same analysis as 2.5. EMU=`0xAAAA0000` matches the ch0 source
seed exactly, confirming the emulator's DMA chain works. HW=`0x7136A8C1` does
not match the seed, suggesting the same SRAM-initialisation / probe-timing
divergence.

## 3. Proposed Fixes

### Fix 1: TICKS register offset aliasing (Failure 1)

**File:** `crates/mdrp2350/src/peripherals/ticks.rs`
**Function:** `TicksRegs::decode_offset`

The RP2350's APB bus fabric does not fully decode the 12-bit offset within the
TICKS 4 KB page. Only the low bits needed to select domain + register are
significant. Offsets beyond the natural register window alias back to valid
registers.

**Change:** Before the bounds check, mask the offset to the significant bits.
The TICKS block has 6 domains x 3 registers x 4 bytes = 72 bytes. The smallest
power-of-two that covers 72 bytes is 128 (0x80). A conservative approach:

```rust
fn decode_offset(offset: u32) -> Option<(usize, u32)> {
    // RP2350 APB does not fully decode the 12-bit page offset for
    // the TICKS block. Only the low bits selecting domain + register
    // are meaningful; upper bits alias. Mask to the natural register
    // window size before dispatch.
    let offset = offset % (DOMAIN_STRIDE * DOMAIN_COUNT as u32);
    let domain = (offset / DOMAIN_STRIDE) as usize;
    let reg = offset % DOMAIN_STRIDE;
    Some((domain, reg))
}
```

This uses modular reduction (`% 0x48`) to wrap any offset within the 4 KB page
back into the 72-byte register window, matching silicon's incomplete address
decode. The existing `if offset >= ...` guard is removed because the modular
reduction makes it unreachable.

**Risk:** Low. The only new behaviour is that out-of-window offsets (e.g., debug
tools probing `0x4010_8100`) now alias to valid registers instead of returning 0.
This matches silicon. No existing test targets offsets > 0x47.

### Fix 2: UART baud-rate zero = no transmission (Failure 2)

**File:** `crates/mdrp2350/src/peripherals/uart.rs`
**Function:** `UartRegs::sysclks_per_byte`

**Change:** Replace the `return 1` fallback with `return u64::MAX`:

```rust
fn sysclks_per_byte(&self, clock_tree: &ClockTree) -> u64 {
    let ibrd = self.ibrd & 0xFFFF;
    let fbrd = self.fbrd & 0x3F;
    if ibrd == 0 && fbrd == 0 {
        return u64::MAX;  // baud clock stopped -- no transmission
    }
    // ... rest unchanged
}
```

The `tick()` method's `while self.tx_cycle_accum >= sysclks_per_byte` loop
will never fire because `tx_cycle_accum` (a `u64`) can never reach `u64::MAX`
in any realistic scenario. The byte stays in the TX FIFO, matching silicon.

**Risk:** Medium-low. Any test that relies on the UART draining without
programming IBRD/FBRD will break. Audit: the Phase 2 unit test
`tick_drains_fifo_at_derived_cadence` at `uart.rs:643-660` explicitly programs
IBRD=81 / FBRD=24 before ticking, so it is unaffected. The scenario
`uart0_tx_single_byte` setup also programs `UARTLCR_H` and `UARTCR` but
NOT IBRD/FBRD, so the new behaviour is the desired fix.

### Fix 3: SPI loopback gated on clock prescaler (Failure 3)

**File:** `crates/mdrp2350/src/peripherals/spi.rs`
**Function:** `SpiRegs::push_dr` and `SpiRegs::tick`

**Change A (minimal fix for this scenario):** Guard the instant loopback in
`push_dr` on `SSPCPSR != 0`:

```rust
fn push_dr(&mut self, value: u32, irqs: &mut u64) {
    if !self.is_enabled() { return; }
    let mask = self.frame_data_mask();
    let word = value & mask;
    if self.tx_fifo.len() < SSP_FIFO_DEPTH {
        self.tx_fifo.push_back(word);
        // Loopback is only active when the SPI clock is running
        // (CPSR != 0). With CPSR=0 the PL022 shift register is
        // stopped and no TX->RX transfer occurs.
        if self.is_loopback()
            && (self.cpsr & 0xFE) != 0
            && self.rx_fifo.len() < SSP_FIFO_DEPTH
        {
            self.rx_fifo.push_back(word);
        }
    } else if self.is_loopback() {
        self.ris |= SSP_INT_ROR;
    }
    self.refresh_tx_rx_interrupts();
    self.route_irq(irqs);
}
```

**Change B (correct general model -- recommended):** Move the loopback from
`push_dr` to `tick`. In `tick()`, when popping a word from the TX FIFO, if
loopback mode is active, push the popped word into the RX FIFO instead of
discarding it:

```rust
pub fn tick(&mut self, cycles: u32, clock_tree: &ClockTree, irqs: &mut u64) {
    if cycles == 0 || !self.is_enabled() || self.tx_fifo.is_empty() {
        return;
    }
    let spw = self.sysclks_per_word(clock_tree);
    self.tx_cycle_accum = self.tx_cycle_accum.saturating_add(cycles as u64);
    while self.tx_cycle_accum >= spw && !self.tx_fifo.is_empty() {
        self.tx_cycle_accum -= spw;
        let word = self.tx_fifo.pop_front().unwrap_or(0);
        if self.is_loopback() && self.rx_fifo.len() < SSP_FIFO_DEPTH {
            self.rx_fifo.push_back(word);
        }
    }
    self.refresh_tx_rx_interrupts();
    self.route_irq(irqs);
}
```

And remove the instant-loopback from `push_dr`:
```rust
fn push_dr(&mut self, value: u32, irqs: &mut u64) {
    if !self.is_enabled() { return; }
    let mask = self.frame_data_mask();
    let word = value & mask;
    if self.tx_fifo.len() < SSP_FIFO_DEPTH {
        self.tx_fifo.push_back(word);
    }
    // ROR detection still fires on TX overflow + loopback:
    if self.tx_fifo.len() >= SSP_FIFO_DEPTH && self.is_loopback() {
        self.ris |= SSP_INT_ROR;
    }
    self.refresh_tx_rx_interrupts();
    self.route_irq(irqs);
}
```

With this model:
- `CPSR = 0` -> `sysclks_per_word` returns `(sys * bits) / 0 = ` ... actually
  the current `sysclks_per_word` clamps `cpsdvsr = (self.cpsr & 0xFE).max(2)`.
  With this clamp, CPSR=0 is treated as 2, producing a finite `sysclks_per_word`.
  The fix must also change the CPSR=0 handling.

**Additional change needed in `sysclks_per_word`:** When `self.cpsr & 0xFE == 0`
(the raw register value is 0 or 1), return `u64::MAX` to halt the SPI clock:

```rust
fn sysclks_per_word(&self, clock_tree: &ClockTree) -> u64 {
    let raw_cpsr = self.cpsr & 0xFE;
    if raw_cpsr == 0 {
        return u64::MAX;  // SPI clock stopped
    }
    let cpsdvsr = raw_cpsr as u64;
    // ... rest unchanged with the .max(2) removed
}
```

**Risk:** Medium. The existing unit test `loopback_rx_matches_tx_single_byte`
at `spi.rs:413-422` relies on the instant loopback. With Change B, the test
must be updated to `tick()` after `push_dr` to advance the transfer. The test
also programs `SSPCR0` and `SSPCR1` but not `SSPCPSR`, so it would need a
`SSPCPSR = 2` write to make the SPI clock run.

### Fix 4: I2C TX_ABRT_SOURCE auto-clear on STOP (Failure 4)

**File:** `crates/mdrp2350/src/peripherals/i2c.rs`
**Function:** `I2cRegs::simulate_transaction`

**Change:** At the end of `simulate_transaction`, after the STOP condition fires,
clear `tx_abrt_source`:

```rust
fn simulate_transaction(&mut self, cmd: u32, irqs: &mut u64) {
    // ... existing code ...

    if (cmd & DATA_CMD_STOP) != 0 || !ack {
        self.raw_intr_stat |= INT_STOP_DET;
        self.activity = false;
        // DW_apb_i2c auto-clears the abort source when the bus
        // returns to idle after STOP. The snapshot is only valid
        // while IC_RAW_INTR_STAT.TX_ABRT is asserted; once the
        // STOP completes, silicon clears it.
        self.tx_abrt_source = 0;
    }
    self.route_irq(irqs);
}
```

**Risk:** Low-medium. This changes the I2C abort model from "sticky until
firmware reads IC_CLR_TX_ABRT" to "auto-cleared on STOP". The existing unit
test `nack_default_for_bus_scan` at `i2c.rs:513-524` asserts
`tx_abrt_source & ABRT_7B_ADDR_NOACK != 0` immediately after
`simulate_transaction`. With the change, the assertion would fail because
`tx_abrt_source` is now cleared. The test must read `tx_abrt_source` BEFORE
the STOP fires (i.e., issue `IC_DATA_CMD` without `DATA_CMD_STOP` first, read
`IC_TX_ABRT_SOURCE`, then issue STOP). Alternatively, the test can verify
`IC_RAW_INTR_STAT.TX_ABRT` instead, which remains set until explicitly cleared.

**Alternative (more conservative):** Instead of clearing `tx_abrt_source`
unconditionally on STOP, clear it in `tick()` after a configurable "bus idle"
delay (e.g., after the first tick where `activity == false`). This preserves the
immediate post-NACK readability for firmware that checks before STOP. However,
this adds complexity for marginal benefit.

**Recommended approach:** Clear `tx_abrt_source` at the point where `activity`
transitions from `true` to `false` (the STOP/NACK path). Adjust unit tests to
read `IC_RAW_INTR_STAT.TX_ABRT` (which is NOT auto-cleared) as the abort
indicator. This matches the DW_apb_i2c datasheet behaviour where
`IC_RAW_INTR_STAT.TX_ABRT` is the latching signal and `IC_TX_ABRT_SOURCE` is
transient.

### Fixes 5 & 6: DMA scenarios -- diagnostic first, then fix if needed

**Assessment:** The emulator's DMA transfer path appears functionally correct
(EMU destination contains the expected seed data). The HW divergence is likely
caused by one of:

1. **Oracle probe-write ordering:** The `apply_setup_hw` function writes to SRAM
   and DMA registers via probe-rs `write_word_32`. If the probe's write
   ordering has relaxation (unlikely with DAP, but possible under contention),
   DMA could trigger before the seed data is written.

2. **HW SRAM residual state:** Between `reset_and_halt` and `apply_setup_hw`,
   the RP2354's SRAM retains its prior content. If a prior scenario or bootrom
   activity wrote to the source range, the seed writes in `apply_setup_hw`
   should overwrite those values. But if the probe writes didn't land (e.g.,
   bus error), the source would contain residual data and DMA would copy that.

3. **DMA on HW didn't trigger:** If the RESETS release (`RESET_DMA_BIT`)
   didn't fully propagate before `CTRL_TRIG` was written, the DMA block might
   not have accepted the trigger. The setup writes are in order (RESETS CLR
   first, then DMA registers), but there may be a 1-2 cycle propagation delay
   on silicon that the probe's sequential writes don't account for.

**Recommended actions:**

1. **Add diagnostic readback** in the oracle runner: after `apply_setup_hw` and
   before `run_sled_hw`, read back the HW source addresses
   (`0x2000_0100..010C` for scenario 5, `0x2000_0400` and `0x2000_0500` for
   scenario 6) and the DMA `CTRL` register to confirm the seed data landed and
   the channel is busy.

2. **Add a NOP delay** between the RESETS CLR write and the first DMA register
   write in the scenario setup. On RP2350, a peripheral released from RESETS may
   need 1-2 sys_clk cycles to become responsive. The `apply_setup_hw` probe
   writes are sequential but fast (DAP write pipeline); adding a read-back of
   `RESETS.RESET_DONE` before proceeding would ensure the DMA block is ready.

3. If the diagnostic confirms the emulator is correct and the HW divergence is
   an oracle timing issue, **add the readback to the scenario setup** and
   mark the DMA scenarios as oracle-validated.
