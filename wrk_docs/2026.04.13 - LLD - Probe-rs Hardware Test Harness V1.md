# Probe-rs Hardware Test Harness — Low-Level Design

Version: 1.1.0
Date: 2026-04-13
Parent: HLD Sections 10.4 (Oracle Layer 3), 10.6 (Unit Tests)

## 1. Purpose

Validate Thumb instruction semantics AND cycle counts against real RP2354
silicon via SWD, using probe-rs. This is Oracle Layer 3 — the only source
of ground truth for per-instruction cycle timing on Cortex-M33.

### What This Validates (Beyond QEMU)

- **Cycle counts.** ARM doesn't publish per-instruction tables for M33.
  We build our own from real silicon.
- **Silicon-validated semantics.** Third independent oracle (after hand-written
  tests and QEMU). If the RP2354 and QEMU agree, we're very confident.
- **Pipeline effects.** Branch penalties, load latency, multi-cycle ops.

### Two Modes

**Mode 1: Halt-step** (Phase A, no firmware)
- Halt core via SWD, write instruction to SRAM, set registers, single-step,
  read registers back. Pure probe-rs, no firmware flashed.
- Validates: instruction semantics, flags, register results, memory effects.
- Also measures: isolated instruction cycle count via DWT CYCCNT.
- Limitation: CYCCNT includes pipeline refill from debug halt/resume, so
  counts may be +1-2 vs real execution. Good enough for most instructions.

**Mode 2: Firmware mailbox** (Phase B, when pipeline accuracy matters)
- Flash a small test binary that measures CYCCNT around the instruction
  in a tight loop, eliminating debug overhead.
- Validates: exact cycle counts, pipeline overlap effects.
- Only needed if Mode 1 CYCCNT diverges from expected counts.

**This LLD covers Mode 1 only.** Mode 2 is a future extension.

## 3. Architecture

```
 ┌───────────────────────────┐     ┌───────────────────────┐
 │  RP2354 target (OneROM)   │     │  mdrp2354 emulator    │
 │  halted via SWD           │     │  (in-process)         │
 └─────────────┬─────────────┘     └───────────┬───────────┘
               │ SWD (probe-rs)                │ fn call
               └───────────┬───────────────────┘
                    ┌──────▼──────┐
                    │ probe_diff  │
                    │ binary      │
                    └─────────────┘
```

No GDB, no TCP, no packet framing. probe-rs is a Rust crate that talks SWD
directly. The binary uses probe-rs API calls where the QEMU harness uses
GDB RSP packets. Everything else — TestCase model, generators, comparison
logic, emulator runner — is reused from the existing harness.

## 4. probe-rs Interface

### 4.1. Setup

```rust
use probe_rs::{Session, SessionConfig, MemoryInterface, RegisterId};

let mut session = Session::auto_attach("rp2350", SessionConfig::default())?;
let mut core = session.core(0)?;  // Core 0

// Halt
core.reset_and_halt(Duration::from_millis(100))?;
```

Target name: `"rp2350"` (covers RP2350/RP2354).

### 4.2. Register Access

```rust
use probe_rs::architecture::arm::core::registers::cortex_m::{PC, SP, XPSR};

// Read/write named registers
core.write_core_reg(PC, 0x2000_0100u32)?;
let xpsr: u32 = core.read_core_reg(XPSR)?;

// Read/write R0-R12 by index
core.write_core_reg(RegisterId(0), 0xDEAD_BEEFu32)?;
let r0: u32 = core.read_core_reg(RegisterId(0))?;
```

### 4.3. Memory Access

```rust
// Write instruction bytes to SRAM
core.write_8(0x2000_0100, &instruction_bytes)?;

// Read/write 32-bit words
core.write_word_32(0x2000_0200, 0x1234_5678)?;
let val = core.read_word_32(0x2000_0200)?;

// Bulk read
let mut buf = [0u8; 256];
core.read_8(0x2000_0200, &mut buf)?;
```

### 4.4. Single-Step

```rust
core.step()?;  // Execute one instruction, re-halt
```

### 4.5. DWT Cycle Counter

```rust
const DEMCR: u64 = 0xE000_EDFC;
const DWT_CYCCNT: u64 = 0xE000_1004;
const DWT_CTRL: u64 = 0xE000_1000;

// Enable (once at startup)
let demcr = core.read_word_32(DEMCR)?;
core.write_word_32(DEMCR, demcr | (1 << 24))?;  // TRCENA
let ctrl = core.read_word_32(DWT_CTRL)?;
core.write_word_32(DWT_CTRL, ctrl | 1)?;          // CYCCNTENA

// Per-test: reset, step, read
core.write_word_32(DWT_CYCCNT, 0)?;               // Reset counter
core.step()?;                                       // Execute instruction
let cycles = core.read_word_32(DWT_CYCCNT)?;       // Read count
```

CYCCNT does not increment while the core is halted. It increments during
the single-step execution, then stops when the core re-halts. The count
includes pipeline refill overhead (~1-2 cycles), which is consistent and
can be calibrated out.

## 5. Address Space

Unlike the QEMU harness, **the target and emulator use the same address
space.** The RP2354's SRAM is at 0x20000000 — exactly where our emulator
maps it. This eliminates the entire address-translation complexity:

- Same TEST_SLOT, TEST_STACK, TEST_SCRATCH addresses on both sides
- Register values are identical — no addr_regs translation needed
- PC, SP, LR compared as absolute values
- Memory compared at absolute addresses

```rust
const TEST_SLOT:    u32 = 0x2000_0100;
const TEST_STACK:   u32 = 0x2004_0000;
const TEST_SCRATCH: u32 = 0x2000_0200;
```

These are the EMU_ constants from the existing harness. The QEMU_ constants
are not used.

**SRAM is accessible without bootrom initialization.** After `reset_and_halt()`,
the core is halted before the bootrom's first instruction. On RP2350/RP2354,
SRAM is always-on and bus-accessible from power-on — no clock gating, no
peripheral initialization required. Contents are indeterminate but readable
and writable. The harness writes everything it needs before stepping.

## 6. Test Execution Flow

### 6.1. Per-Test (Semantic Diff)

```rust
fn run_one_probe(
    core: &mut Core,
    tc: &TestCase,
) -> Result<RunState, probe_rs::Error> {
    // 1. Write instruction + BKPT to test slot
    let mut code = tc.opcode.to_le_bytes().to_vec();
    code.extend_from_slice(&0xBE00u16.to_le_bytes());  // BKPT
    core.write_8(TEST_SLOT as u64, &code)?;

    // 2. Set registers (defaults, then overrides)
    for i in 0..=12u32 {
        core.write_core_reg(RegisterId(i as u16), 0u32)?;
    }
    core.write_core_reg(SP, TEST_STACK)?;
    core.write_core_reg(RegisterId(14), 0xFFFF_FFFFu32)?;  // LR
    core.write_core_reg(PC, TEST_SLOT)?;
    core.write_core_reg(XPSR, tc.xpsr_pre)?;
    for &(reg, val) in &tc.reg_pre {
        // No address translation needed — same address space
        core.write_core_reg(RegisterId(reg as u16), val)?;
    }

    // 3. Memory setup (zero scratch + write preconditions)
    if tc.needs_bus {
        core.write_8(TEST_SCRATCH as u64, &[0u8; 256])?;
        for &(offset, val) in &tc.mem_pre {
            core.write_8((TEST_SCRATCH + offset) as u64, &[val])?;
        }
    }

    // 4. Single-step
    core.step()?;

    // 5. Read post-state
    let mut regs = [0u32; 16];
    for i in 0..16u32 {
        regs[i as usize] = core.read_core_reg(RegisterId(i as u16))?;
    }
    let xpsr: u32 = core.read_core_reg(XPSR)?;
    let mut mem = Vec::new();
    for &offset in &tc.mem_check {
        let mut byte = [0u8; 1];
        core.read_8((TEST_SCRATCH + offset) as u64, &mut byte)?;
        mem.push(byte[0]);
    }

    Ok(RunState { regs, xpsr, mem })
}
```

### 6.2. Per-Test (Cycle Count)

Same as above, but also:

```rust
// Before step: reset CYCCNT
core.write_word_32(DWT_CYCCNT, 0)?;

// After step: read CYCCNT
```

### 6.3. Comparison

Since both sides use the same address space, comparison is simpler than
the QEMU harness. Use absolute values for everything:

```rust
fn compare_probe(
    tc: &TestCase,
    hw: &RunState,
    emu: &RunState,
) -> Result<(), String> {
    let mut diffs = Vec::new();

    // All registers compared as absolute values (same address space)
    for i in 0..=12 {
        if hw.regs[i] != emu.regs[i] {
            diffs.push(format!("R{i}: HW={:#010x} EMU={:#010x}",
                hw.regs[i], emu.regs[i]));
        }
    }

    // SP, LR, PC — absolute
    if hw.regs[13] != emu.regs[13] {
        diffs.push(format!("SP: HW={:#010x} EMU={:#010x}",
            hw.regs[13], emu.regs[13]));
    }
    if hw.regs[14] != emu.regs[14] {
        diffs.push(format!("LR: HW={:#010x} EMU={:#010x}",
            hw.regs[14], emu.regs[14]));
    }
    if hw.regs[15] != emu.regs[15] {
        diffs.push(format!("PC: HW={:#010x} EMU={:#010x}",
            hw.regs[15], emu.regs[15]));
    }

    // Flags — include T bit (bit 24) for probe comparison.
    // Unlike QEMU (which strips EPSR.T), real hardware reports it.
    // Both sides should always have T=1 in Thumb mode.
    let probe_mask = tc.xpsr_mask | 0x0100_0000; // add T bit
    let hw_flags = hw.xpsr & probe_mask;
    let emu_flags = emu.xpsr & probe_mask;
    if hw_flags != emu_flags {
        diffs.push(format!("xPSR: HW={:#010x} EMU={:#010x}",
            hw.xpsr, emu.xpsr));
    }

    // Memory
    for (idx, &offset) in tc.mem_check.iter().enumerate() {
        if hw.mem[idx] != emu.mem[idx] {
            diffs.push(format!("MEM[+{offset:#x}]: HW={:#04x} EMU={:#04x}",
                hw.mem[idx], emu.mem[idx]));
        }
    }

    if diffs.is_empty() { Ok(()) } else { Err(diffs.join(", ")) }
}
```

No addr_regs skipping, no PC/SP delta computation, no QEMU/EMU base
translation. Everything is absolute because the address spaces match.

## 7. Emulator Side

Identical to the QEMU harness, but using EMU_ addresses (which are the
same as the probe addresses). Reuse `run_one_emu()` from lib.rs directly.

The only difference: for cycle count comparison, we also capture the return
value of `execute_one()` / `execute_one_with_bus()`, which is the emulator's
predicted cycle count.

## 8. Cycle Count Calibration

The single-step CYCCNT measurement includes debug overhead (pipeline refill
on halt/resume). To calibrate:

1. **Measure multiple known-cost instructions** at startup (100 times each):
   - NOP (0xBF00) — 1 cycle
   - ADDS R0, R0, #1 (0x3001) — 1 cycle
   - MULS R0, R1 (0x4348) — 1 cycle on M33
   Each should show the same overhead delta. If `NOP_raw - ADDS_raw != 0`,
   the overhead is instruction-dependent and simple calibration won't work.
2. **Compute baseline:** `baseline = NOP_median - 1` (subtract NOP's known
   1-cycle cost).
3. **Net cycles = measured - baseline** for each test instruction.

If the three calibration instructions show different overheads, the debug
halt/resume cost is instruction-class-dependent. In that case, fall back to
firmware mode (Phase B) for accurate cycle counting. Halt-step semantic
diffing is still valid regardless.

Verify baseline consistency by checking that the standard deviation across
100 NOP measurements is 0. Any jitter means CYCCNT is unreliable in
halt-step mode.

## 9. Test Runner

### 9.1. Binary: `crates/mdrp2354-test-harness/src/bin/probe_diff.rs`

```
Usage:
  probe_diff                      Run targeted edge-case tests
  probe_diff --fuzz N             Random fuzz tests (N per class)
  probe_diff --fuzz N --seed S    Reproducible fuzz
  probe_diff --cycles             Also compare cycle counts
  probe_diff --cycles-only        Only measure cycle counts (skip semantic diff)
```

```rust
fn main() -> Result<()> {
    // 1. Attach to target via probe-rs
    let mut session = Session::auto_attach("rp2350", SessionConfig::default())?;
    let mut core = session.core(0)?;

    // 2. Reset and halt
    core.reset_and_halt(Duration::from_millis(100))?;

    // 3. Enable DWT cycle counter
    enable_dwt(&mut core)?;

    // 4. Calibrate cycle counter (measure NOP baseline)
    let baseline = calibrate_cycles(&mut core)?;
    println!("DWT baseline: {baseline} cycles (debug overhead)");

    // 5. Generate tests
    let tests = generate_all();  // or generate_fuzz()
    let mut shared_bus = Bus::new();
    let mut pass = 0;
    let mut fail = 0;
    let mut cycle_mismatches = 0;

    // 6. Run each test
    for tc in &tests {
        // Hardware side
        let hw_state = run_one_probe(&mut core, tc)?;

        // Emulator side (reuse existing function)
        let emu_state = run_one_emu(tc, &mut shared_bus);

        // Semantic comparison
        match compare_probe(tc, &hw_state, &emu_state) {
            Ok(()) => pass += 1,
            Err(diff) => {
                fail += 1;
                eprintln!("[FAIL] {}: {}", tc.name, diff);
            }
        }

        // Cycle comparison (if enabled)
        if args.cycles {
            let hw_cycles = hw_state.cycles - baseline + 1;
            let emu_cycles = emu_state.cycles;
            if hw_cycles != emu_cycles {
                cycle_mismatches += 1;
                eprintln!("[CYCLE] {}: HW={} EMU={}",
                    tc.name, hw_cycles, emu_cycles);
            }
        }
    }

    // 7. Report
    println!("{pass}/{} passed", pass + fail);
    if args.cycles {
        println!("{cycle_mismatches} cycle count mismatches");
    }
    Ok(())
}
```

### 9.2. Performance

SWD is slower than QEMU GDB (physical wire vs localhost TCP):
- Register write: ~0.5ms per register via SWD
- 17 register writes (R0-R12 + SP + LR + PC + xPSR): ~8.5ms
- Memory write (256 byte zero + preconditions): ~2ms
- DWT reset + step: ~1.5ms
- 16 register reads + xPSR + CYCCNT: ~9ms
- Memory reads (mem_check): ~1ms
- **Total: ~20-25ms per test**

For 382 targeted tests: ~10 seconds. Acceptable.
For fuzz 1000/class: ~5 minutes. Acceptable.
For overnight fuzz: `--fuzz 25000` (~325k tests) = ~2.5 hours.

## 10. RunState Extension

Add `cycles: u32` field to `RunState` in lib.rs:

```rust
pub struct RunState {
    pub regs: [u32; 16],
    pub xpsr: u32,
    pub mem: Vec<u8>,
    pub cycles: u32,  // DWT CYCCNT (0 if not measured)
}
```

The QEMU harness sets this to 0 (QEMU doesn't report cycles). The probe
harness populates it from CYCCNT. The emulator runner populates it from
the return value of `execute_one()`.

## 12. What Changes in lib.rs

Minimal changes to support the probe harness:

1. **Add `cycles: u32` to `RunState`** (default 0)
2. **Update `run_one_emu` to return cycles** from execute_one's return value
3. **Add `compare_probe()` function** — simpler than `compare()`, absolute
   values only, no address translation
4. **Make TEST_SLOT / TEST_STACK / TEST_SCRATCH public** (the EMU_ versions,
   which are now also the hardware addresses)

The existing `compare()` function, generators, and QEMU binary are untouched.

## 13. Excluded from Phase A

- Firmware mailbox mode (Phase B — only if halt-step CYCCNT is unreliable)
- Multi-instruction program execution (Phase B — needs firmware)
- Thumb-32 tests (waiting for emulator implementation)
- Core 1 testing (single core is sufficient for instruction validation)
- Peripheral interaction testing (out of scope for instruction oracle)

## 14. Open Questions

1. **CYCCNT baseline consistency.** Is the debug halt/resume overhead
   constant? If it varies by +/-1 cycle, single-instruction cycle counts
   will have that jitter. The calibration step (Section 8) will reveal this.

2. **xPSR T bit from real hardware.** Unlike QEMU (which omits EPSR.T),
   real hardware should report the T bit in xPSR reads via SWD. Need to
   verify and adjust the xpsr_mask if needed.

3. **Secure vs Non-Secure.** The RP2354 boots in Secure mode. DWT and SRAM
   are accessible. If the target has firmware that configures TrustZone,
   we may need to account for that. For bare-metal halt-step, this is not
   an issue.
