# 2026-04-26 — HLD — RP2040 Slow-Path Chunked Peripheral Advance — V2

> **V2 changelog vs V1**: SysTick design replaced with per-core cycle accounting (V1 silently inherited a latent dual-core bug); perf-gain estimate lowered to 10–25% (Iter 1's instrumentation overhead caveat); q=4 evidence framed as no-longer-load-bearing for the chunked path; validation set tightened to full `cargo test`; caller count corrected to 2; version bump corrected to patch; `bus.master_cycle` audit added to sequencing; minor placement clarifications on `update_gpio`. Reviewer team: correctness, implementation, devil's advocate.

## 1. Goal

Reduce per-cycle slow-path overhead on `mdrp2040`'s `step_serial` by ticking peripherals once per quantum instead of N times. Targeted at the PicoGUS OPL3 workload, currently ~36–55× slower than real-time.

Expected gain (paired with the q=4 default landed earlier today): **10–25% wall reduction** on `picogus_diff_rp2040 --firmware-mode 5`. The 25–35% headline that earlier journal entries cited was derived from Iter 1's instrumented bench, which the journal itself flags as polluted by `Instant::now()` overhead (~30 ns/call) inflating sub-100ns attributions. **Treat ≥10% as success**; do not gate the change on hitting the upper bound.

## 2. Background — current slow path

`crates/mdrp2040/src/lib.rs:639` `Emulator::step_serial`:

```rust
for _ in 0..consumed {
    self.bus.master_cycle = self.bus.master_cycle.wrapping_add(1);
    self.bus.tick_peripherals();        // 8 peripherals × tick(1, …)
    if self.bus.systicks[active].tick() { … }
    self.tick_pio_and_route_irqs_single();   // pio.step_n(1) × 2
    self.update_gpio();
    self.drain_pending_irqs_to_cores();
}
```

None of the per-cycle work is *structurally* per-cycle: every peripheral already accepts a `cycles: u32` argument and uses accumulator state. The slow path is calling them N times with `1` because of an interleave the original design didn't justify — the per-cycle interleave was inherited from the bank-contention model, formally retired (CLAUDE.md "Bank contention model").

## 3. Reference — `mdrp2350`

`mdrp2350` already implements the target shape. `crates/mdrp2350/src/lib.rs:649` `Emulator::step_serial` ticks peripherals once per quantum via `tick_peripherals(self.step_quantum)`; `crates/mdrp2350/src/lib.rs:1010` and `crates/mdrp2350/src/bus/mod.rs:1077` define the chunked entry points.

**The mirror is structural, not semantic.** RP2350 runs at default `step_quantum=1024`, has different peripherals (TICKS, POWMAN, dual-ISA Cortex-M33+RV32), and exercises different workloads. RP2040-specific quirks must be validated separately:

- **Dual-core SysTick** — RP2350's ARM path uses `arm[core_id].ppb.systick_advance(cycles)` per core, advancing each core's SysTick by *that core's* cycle count. RP2040 must do the same; V1's "tick `active_core()`'s SysTick N times" preserved a latent bug (see §5.2 below).
- **PSRAM PIO timing** — RP2040's PSRAM model exercises PIO step_n at `clkdiv=2`. Iter 4's bulk-skip experiment showed this clkdiv-sensitive; same code path lives in `step_n` regardless of how often it's called.
- **OPL3 ISA-waveform sampling** — already characterised by today's quantum sweep: q=4 audio-clean, q=64 silent. The chunked refactor preserves q=4 as default; a fresh sweep must re-validate.

## 4. Open questions — investigation results

### 4.1 IRQ delivery semantics under chunked tick (Arthur Q1)

PicoGUS firmware **is interrupt-driven** for ISA-bus capture: `RXNEMPTY_SM0` on PIO0 INT0_INTE asserts NVIC line 7 (`PIO0_IRQ_0`) when an autopushed ISA event lands in PIO0 SM0's RX FIFO. Source: `crates/mdrp2040/src/lib.rs:787`.

Trace data places ~1800 ISA events across 2.5 s sim → ~720 events/s, ~1.7 ms between events. The IRQ-delivery delay this refactor introduces is bounded by `step_quantum-1` cycles (3 cycles at q=4, ~24 ns wall at 125 MHz emulated). Three orders of magnitude below the inter-event interval.

**The q=4 measurement landed earlier today is NOT load-bearing evidence for this refactor.** That measurement was taken on the per-cycle slow path with N=4 ticks/quantum scattered through the inner loop. The chunked path has ONE tick at end-of-quantum, with peripheral state changes batched. These are different timing models, even at the same `step_quantum` value. **Cake-gate on the chunked path is the load-bearing validation** (§6.3). If cake-gate fails post-refactor, debug by reducing default quantum, not by re-citing the per-cycle q=4 result.

### 4.2 `silicon_periph_diff_rp2040` status (Arthur Q2)

Per CLAUDE.md ("`silicon_periph_diff_rp2040` ships ahead of silicon hookup"), the oracle is HLD-checkpoint compliance, not a regression gate. **No constraint on this design.**

### 4.3 `mdrp2350` parity (Arthur Q3)

Pattern proven, threaded runtime depends on it, 945+ tests cover it. The RP2350-vs-RP2040 differences listed in §3 are real; the chunked-tick *mechanism* itself is well-understood.

## 5. Design

### 5.1 Scope of change

**In scope:**
- Refactor `Emulator::step_serial` slow branch in `crates/mdrp2040/src/lib.rs` to tick peripherals once with the consumed cycle count, mirroring RP2350.
- Update `Bus::tick_peripherals` signature to take `cycles: u32`. All inner peripheral `tick(n, …)` already accept a cycle count.
- Replace `tick_pio_and_route_irqs_single()` with `tick_pio_and_route_irqs(cycles: u32)`. PIO `step_n(cycles, gpio_in)` already does the right thing.
- Add `Emulator::tick_systick(c0_cycles: u32, c1_cycles: u32)` — advances each core's SysTick by ITS core's cycle count. Fixes a latent dual-core SysTick bug in the existing code (see §5.2).
- DMA: keep `Bus::tick_dma()` once-per-quantum at the tail of `Bus::tick_peripherals`. Mirrors RP2350.
- Move `update_gpio()` from per-cycle (current slow loop) to per-quantum (after `tick_pio_and_route_irqs`). Mirrors RP2350.
- Remove the slow-path `for _ in 0..consumed` loop entirely. Single straight-line tick at quantum end.

**Out of scope:**
- Fast-path gate at `lib.rs:718` stays as-is.
- Threaded runtime untouched (its peripheral path is already once-per-quantum; verified — `crates/mdrp2040/src/threaded/peripherals.rs` has no callers of the changed `Bus::tick_peripherals` signature).
- No changes to peripheral internals beyond the bus-level wrapper.
- No feature flag, no env var, no `--legacy-tick` fallback. CLAUDE.md is explicit: "We do not need to support the old code." If cake-gate fails, revert via git.

### 5.2 SysTick — per-core cycle accounting (V2 design correction)

**The latent bug in current code**: `crates/mdrp2040/src/lib.rs:742-745` reads:

```rust
let active = self.bus.active_core();
if self.bus.systicks[active].tick() { … }
```

`active` is whatever core was set last by `set_active_core` during the inner-iteration's core dispatch. When both cores run in an iteration, dispatch order is `set_active_core(0); core0.step(); … set_active_core(1); core1.step(); …` — so `active=1` at the SysTick line. **Result: when both cores run, only SysTick[1] advances per cycle. SysTick[0] never advances.** This is wrong against ARMv6-M semantics where each core's SysTick is per-core.

V1's chunked design preserved this bug by sampling `active_core()` once at quantum end. V2 fixes it.

**V2 design**: track per-core cycles consumed in the inner loop, advance each core's SysTick by its own count.

```rust
// Inside step_serial inner loop, accumulate:
core0_cycles_total += c0;
core1_cycles_total += c1;

// After inner loop, in slow branch:
self.tick_systick(core0_cycles_total as u32, core1_cycles_total as u32);
```

```rust
fn tick_systick(&mut self, c0: u32, c1: u32) {
    for _ in 0..c0 {
        if self.bus.systicks[0].tick() {
            self.bus.ppb[0].icsr |= 1 << 26;
        }
    }
    for _ in 0..c1 {
        if self.bus.systicks[1].tick() {
            self.bus.ppb[1].icsr |= 1 << 26;
        }
    }
}
```

The double per-cycle loop is bounded by `step_quantum` (default 4, max ~64). Per-cycle SysTick decrement is ~3 ns; total ≤300 ns/quantum even at q=64. Closed-form `SysTick::advance_n(n) -> u32` is a future optimisation when the loop shows hot in profiling, not worth the math complexity up front.

**Note**: this is a *correctness improvement* over current code. Existing tests that depend on "core 0's SysTick never advances when core 1 is running" — if any exist — are encoding the latent bug and must be loosened, not ported.

### 5.3 New `step_serial` shape

```rust
fn step_serial(&mut self) -> u64 {
    self.bus.master_cycle = self.clock.cycles;
    let start = self.clock.cycles;
    let target = start.wrapping_add(self.step_quantum as u64);

    let mut c0_total: u64 = 0;
    let mut c1_total: u64 = 0;

    while self.clock.cycles < target
        && (!self.cores[0].is_halted() || !self.cores[1].is_halted())
    {
        let c0 = if !self.cores[0].is_halted() {
            self.bus.set_active_core(0);
            let c = self.cores[0].step(&mut self.bus) as u64;
            Self::drain_cache_invalidations(&mut self.bus, &mut self.cores);
            self.maybe_wake_core1(0);
            c
        } else { 0 };

        let c1 = if !self.cores[1].is_halted() {
            self.bus.set_active_core(1);
            self.bus.begin_core1_step();
            let c = self.cores[1].step(&mut self.bus) as u64;
            Self::drain_cache_invalidations(&mut self.bus, &mut self.cores);
            self.bus.end_core1_step();
            self.maybe_wake_core1(1);
            c
        } else {
            self.bus.end_core1_step();
            0
        };

        if c0 == 0 && c1 == 0 { break; }
        c0_total = c0_total.wrapping_add(c0);
        c1_total = c1_total.wrapping_add(c1);
        self.clock.cycles = self.clock.cycles.wrapping_add(c0.max(c1));
    }
    let consumed = self.clock.cycles.wrapping_sub(start);

    // Fast-path branch unchanged.
    let pio_idle    = self.bus.pio_all_idle();
    let peri_idle   = self.bus.all_peripherals_idle();
    let dma_idle    = self.bus.dma.is_idle();
    let any_irq     = self.bus.irq_pending != 0;
    let systick_idle = !self.bus.systicks[self.bus.active_core()].is_enabled();
    if pio_idle && peri_idle && dma_idle && systick_idle && !any_irq {
        self.tick_pio(consumed as u32);
        self.bus.advance_lazy_scheduled(consumed);
        self.drain_pending_irqs_to_cores();
        self.update_gpio();
    } else {
        // Slow branch — chunked, single straight-line tick.
        self.bus.master_cycle = self.bus.master_cycle.wrapping_add(consumed);
        self.bus.tick_peripherals(consumed as u32);
        self.tick_systick(c0_total as u32, c1_total as u32);
        self.tick_pio_and_route_irqs(consumed as u32);
        self.update_gpio();
        self.drain_pending_irqs_to_cores();
    }
    self.wake_checks();
    consumed
}
```

`update_gpio` moves from inside the inner loop (today) to once at quantum end (above), matching RP2350's `step_serial` (which has no `update_gpio` in the per-cycle path at all — it's purely a quantum-boundary refresh).

### 5.4 IRQ delivery semantics — explicit behaviour change

| Path | Today | After this refactor |
|---|---|---|
| Peripheral asserts IRQ at intra-quantum cycle k | `bus.irq_pending |= bit` at k; `drain_pending_irqs_to_cores` runs at end-of-cycle k; CPU sees pending IRQ at cycle k+1 | `bus.irq_pending |= bit` accumulates during chunked tick; `drain_pending_irqs_to_cores` runs once at end-of-quantum; CPU sees pending IRQ at start of next quantum |

Net delivery delay grows from ≤1 cycle to ≤`step_quantum-1` cycles. **At default q=4 this is ≤3 cycles.** Documented in source via doc-comments referencing this HLD.

This is identical to RP2350's behaviour; the threaded runtime already lives with this.

## 6. Validation

### 6.1 Full unit + integration test suite

`cargo test -p mdrp2040 --release` (924 unit + 47 integration). **Every test must pass — green is mandatory before this refactor merges.** Tests that pin exact cycle-of-IRQ-arrival within a quantum will see IRQ delivery shift; the assertions need to loosen to "IRQ pending within the next quantum boundary" (same accommodation `mdrp2350` already lives with). If any test FAILS that we don't understand, the refactor blocks until the failure is reasoned about — not silenced.

The dual-core SysTick correctness improvement (§5.2) means existing tests that asserted "SysTick[0] doesn't advance under dual-core load" — if any — were encoding the latent bug. They are wrong and need updating. Audit before refactor: grep for `systicks[0]` assertions in `crates/mdrp2040/src/tests.rs` and `crates/mdrp2040/src/bus/systick.rs`.

### 6.2 Threaded parity

`cargo test -p mdrp2040 --release --features threading --test dual_model`. Serial and Threaded paths must produce the same end state. Threaded already runs once-per-quantum; this refactor brings Serial into agreement, so dual_model parity becomes *easier* to maintain.

### 6.3 PicoGUS audio cake-gate (load-bearing)

Replay Monkey Island AdLib trace at default `--step-quantum 4`. Required:
- Peak ≥ −20 dBFS
- ≥ 4 musical-band peaks (60–5000 Hz)
- Top-5 FFT peaks within 1 dB of pre-refactor q=4 baseline (peaks `324, 384, 648, 162, 809 Hz` per today's measurement)

Bench script: `wrk_scratch/bench_quantum_sweep.sh` + `wrk_scratch/analyze_quantum_wavs.py`. Run pre-refactor for the baseline snapshot, run post-refactor to compare.

### 6.4 Quantum sweep re-measurement

Re-run the sweep at q=1/4/16/64. Acceptance:
- Confirm q=4 wall reduces by ≥10% beyond today's 80.95 s baseline (success).
- Confirm cycles delta stays within ±0.2% of pre-refactor at q=4.
- Note any audio change at q=16 or q=64 — chunked tick may unlock previously-unsafe quanta (because per-cycle ISA-pin sample alignment was the root cause of q=64 silence, not peripheral overhead). New safe-quantum upper bound, if any, gets reported back.

## 7. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| TIMER alarm fires inside a quantum but chunked poll misses it | Low | `master_cycle` updated *before* `tick_peripherals(N)`; `Timer::poll_alarms` uses `>=` match. Same machinery RP2350 already uses. |
| DMA throughput cap (one transfer per quantum) starves I2S | Low | OPL3 needs ~88 K transfers/s; q=4 ceiling is 31 M transfers/s. Cake-gate catches it if wrong. |
| A test pins exact IRQ-delivery cycle | Medium | Loosen assertion to "within next quantum boundary"; same RP2350 accommodation. Listed up-front so it doesn't surprise. |
| Per-cycle observation diagnostics under-count by quantum factor | Medium-low | Diagnostic counters (`pio0_sm0_pc_advances`, etc.) are relative-magnitude, consumed post-run by `picogus_diff_rp2040` summary. Per-quantum granularity is fine; doc-comment notes it. |
| Firmware polls `SIO_GPIO_IN` during a quantum, sees stale state | Low | PicoGUS doesn't appear to do GPIO polling in OPL3 mode; cake-gate is silent on this. If a future workload regresses on this, the fix is reducing quantum, not reverting the refactor. |
| Per-cycle perf gain estimate (Iter 1's 27.4% + 31.7%) inflated by `Instant::now()` overhead | Already accepted | §1 lowered estimate to 10–25%. Iter 2's 3% was the floor reality on a different attribution premise. Measure post-refactor. |
| Q=64 still breaks audio post-refactor | Acceptable | Q=64 unlock is bonus; q=4 staying clean is the goal. |
| Cake-gate passes but a peripheral-state regression escapes it | Medium-low | Mitigated by §6.1 (full test suite green). Cake-gate is one oracle of several; not the only gate. |

## 8. Pre-refactor audits (mandatory before §9 begins)

1. **`bus.master_cycle` mid-tick reads**: grep all peripheral tick handlers for `master_cycle` reads. If any peripheral reads `bus.master_cycle` during its `tick(n, …)`, that's a hidden dependency on per-cycle freshness. Today, `master_cycle` advances per inner-cycle iteration before `tick_peripherals`. After: it advances once per quantum *before* the chunked tick. Per-tick reads will see one stale value all the way through, possibly breaking accumulator logic.
   - Files to grep: `crates/mdrp2040/src/peripherals/{adc,i2c,pwm,spi,uart,timer,psram,watchdog_tick}.rs`, `crates/mdrp2040/src/bus/systick.rs`, `crates/mdrp2040/src/dma.rs`.
   - Pattern: `master_cycle` in any `fn tick`.
   - Action if hits: refactor the affected peripheral to take `master_cycle` as a `tick` parameter, or update `master_cycle` mid-quantum where needed.
2. **Tests asserting `systicks[0]` static under dual-core**: grep `crates/mdrp2040/src/tests.rs` for `systicks[0]`. Any test that asserts SysTick[0] never advanced when both cores ran is encoding the latent bug; flag for adjustment.
3. **Caller count for changed signatures** (verified: 2 sites for `Bus::tick_peripherals` — `crates/mdrp2040/src/lib.rs:674` slow-path + `crates/mdrp2040/src/tests.rs:4818` ADC test fixture).
