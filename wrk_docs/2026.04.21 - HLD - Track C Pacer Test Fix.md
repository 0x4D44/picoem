# HLD — Track C: Pacer Test Fix

**Date:** 2026-04-21
**Author:** edmund@epkconsulting.co.uk
**Scope:** Fix `pacer::tests::test_pacer_behind_detection` flake in release mode. ~30 min work.

## 1. Problem

`cargo test --release -p mdpicoem-common pacer::tests::test_pacer_behind_detection` fails:

```
thread 'pacer::tests::test_pacer_behind_detection' panicked at
crates\mdpicoem-common\src\pacer.rs:613:9:
should detect being behind real-time
```

Test is present since Phase 2 extraction (`d158246`) — not a regression, just never validated in release mode.

## 2. Root Cause (Confirmed)

File: `crates/mdpicoem-common/src/pacer.rs:597-614`.

The test constructs a `Pacer::new(u32::MAX)` to shrink `quantum_tsc_ticks` toward zero, then runs a "burn loop" of `dummy = dummy.wrapping_add(i)` over `0..10_000` between `begin_quantum`/`end_quantum` and expects `behind_count > 0`.

- `Pacer::new` path (`pacer.rs:284`) gives `nominal = tsc_freq_hz * 150 / u32::MAX`. On a ~3 GHz TSC that's ~105 ticks; after the `nominal/4` overhead clamp (`pacer.rs:238`), `quantum_tsc_ticks` is ~78 ticks.
- The "behind" branch (`pacer.rs:400-404`) fires when `emulation_tsc >= quantum_tsc_ticks`.
- In release mode LLVM recognises `Σ i for i in 0..10_000` as a closed-form arithmetic series and eliminates the loop entirely. `std::hint::black_box(dummy)` only forces the *final value* to be observable — it does not force the loop's iterations to execute.
- Net result: between `begin_quantum` and `end_quantum`, the only work remaining is the two `rdtscp` calls. Their combined tick cost sits close to the ~78-tick threshold, so the test is flaky (and on fast hosts / small TSC overhead, reliably fails).

The sister test `test_pacer_begin_end_quantum` (`pacer.rs:581`) uses the same pattern but only asserts `emulation_ns > 0`, which remains true from the `rdtscp` overhead alone — it has the same latent bug but its assertion doesn't catch it. No other burn-loop tests exist in the workspace (grep for `black_box(dummy)` / `wrapping_add(i)` returns only these two sites).

## 3. Options

| # | Approach | Pros | Cons |
|---|---|---|---|
| a | `black_box` each iteration: `dummy = std::hint::black_box(dummy.wrapping_add(i));` | Minimal diff; no new deps; no wall-clock sleep; fast. | Still relies on host to be "slow enough" — but 10k black-boxed adds is ~30 µs even on fast x86, comfortably above the ~25 ns threshold. |
| b | `std::thread::sleep(Duration::from_micros(50))` | Deterministic wall-clock wait; zero CPU work. | `thread::sleep` on Windows has ~1 ms granularity — may oversleep and slow the test suite. Intent (burn time) becomes implicit. |
| c | `Instant::now()` busy-wait until N µs elapsed | Sub-ms granularity; deterministic. | More code than (a); mildly wastes CPU; still a hand-rolled loop. |

## 4. Chosen Approach

**Option (a)** — `black_box` inside the loop body.

Rationale: smallest possible change, consistent with existing idiom elsewhere in the codebase, no dependency on OS scheduler granularity, and the safety margin is ~1000× (tens of µs of real work vs. a ~25 ns threshold). Apply the same change to `test_pacer_begin_end_quantum` pre-emptively to stop the latent-bug twin from biting later.

## 5. Change Summary

One file: `crates/mdpicoem-common/src/pacer.rs`.

- **`test_pacer_behind_detection`** (lines 605-609): replace
  ```rust
  let mut dummy = 0u64;
  for i in 0..10_000 {
      dummy = dummy.wrapping_add(i);
  }
  std::hint::black_box(dummy);
  ```
  with
  ```rust
  let mut dummy = 0u64;
  for i in 0..10_000 {
      dummy = std::hint::black_box(dummy.wrapping_add(i));
  }
  std::hint::black_box(dummy);
  ```

- **`test_pacer_begin_end_quantum`** (lines 585-589): identical treatment for the `0..1000` loop.

Estimated effort: **~15 minutes** edit + **~15 minutes** test runs. No API changes, no doc changes, no other crates touched.
