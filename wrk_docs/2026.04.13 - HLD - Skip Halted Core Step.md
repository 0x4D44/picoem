# Skip Halted Core Step

Version: 1.0.0
Date: 2026-04-13

## Problem

Flamegraph of `Emulator::step()` shows 31% SELF time in `CortexM33::step()`.
Roughly half of that (~15% of total) is core 1's halted check: every cycle,
`step()` is called unconditionally on both cores, and core 1 immediately checks
`self.wfe_waiting` then `self.halted` and returns. At 80M+ cycles/sec the
function-call overhead (push frame, branch, pop frame) is significant.

The contention tracking calls (`clear_contention_state` /
`begin_contention_check`) are similarly wasted when core 1 is not stepping --
they set and clear a flag that nobody reads.

## Proposed change

Move the halted check from inside `CortexM33::step()` up into
`Emulator::step()`, so the function call is never made in the first place.
Also skip the contention tracking setup when core 1 will not step.

### Before (`crates/mdrp2354/src/lib.rs`, `Emulator::step()`)

```rust
pub fn step(&mut self) -> u64 {
    self.clock.tick();
    self.bus.clear_contention_state();
    self.cores[0].step(&mut self.bus);
    self.bus.begin_contention_check();
    self.cores[1].step(&mut self.bus);

    // WFE/SEV wake check
    for i in 0..2 {
        if self.cores[i].wfe_waiting && self.bus.event_flag[i] {
            self.bus.event_flag[i] = false;
            self.cores[i].wfe_waiting = false;
        }
    }

    self.bus.sio.tick_mtime();
    self.clock.cycles
}
```

### After

```rust
pub fn step(&mut self) -> u64 {
    self.clock.tick();

    if self.cores[1].is_halted() {
        // Core 1 halted: skip contention tracking entirely, step core 0 only
        self.cores[0].step(&mut self.bus);
    } else {
        // Both cores active: full contention-tracked dual-core step
        self.bus.clear_contention_state();
        self.cores[0].step(&mut self.bus);
        self.bus.begin_contention_check();
        self.cores[1].step(&mut self.bus);
    }

    // WFE/SEV wake check
    for i in 0..2 {
        if self.cores[i].wfe_waiting && self.bus.event_flag[i] {
            self.bus.event_flag[i] = false;
            self.cores[i].wfe_waiting = false;
        }
    }

    self.bus.sio.tick_mtime();
    self.clock.cycles
}
```

The branch prediction cost of the `is_halted()` check is negligible: once
core 1 enters the halted state it stays there for millions of cycles, so the
branch is perfectly predicted in the steady state.

### Why not also gate on core 0?

Core 0 is always running in normal operation. The RP2350 bootrom launches
core 0 immediately on reset; core 1 starts halted and only wakes when core 0
explicitly writes to the SIO FIFO to launch it. Adding a halted gate for
core 0 adds a branch that is never taken in practice and complicates the code
for no measurable gain.

## What does NOT change

- `CortexM33::step()` still checks `self.halted` internally. This is a
  defense-in-depth guard; removing it would save one branch but risks
  executing a halted core if a future caller bypasses `Emulator::step()`.
- The WFE/SEV wake check still runs for both cores unconditionally. A halted
  core cannot be WFE-waiting (halt clears all pending state), so the check
  short-circuits on the first condition. Not worth special-casing.
- `CortexM33::halt()`, `wake()`, and `is_halted()` are unchanged.
- Contention tracking logic in `Bus` is unchanged.
- No new fields, no new methods, no API changes.

## Impact on existing tests

None. All existing tests exercise either:

1. Single-core execution via `execute_one()` / `execute_one_wide()`, which
   bypass `Emulator::step()` entirely.
2. Full emulation via `Emulator::step()` / `Emulator::run()`, where core 1
   starts halted by default -- these will now take the fast path and produce
   identical results.
3. Dual-core tests that explicitly wake core 1 -- these will take the full
   contention path, identical to today.

No test changes required.

## Risks

**Can a halted core need to step?** No. `halt()` clears `stall_cycles` and
`pending_fault`, and `step()` returns immediately on `self.halted`. There is
no internal state that accumulates while halted. The only way to resume is an
explicit `wake()` call, which is a public API invoked from outside the step
loop (currently not called from within `Emulator::step()` or any bus/SIO
handler).

**Could we miss a wake event?** No. `wake()` sets `self.halted = false`. The
next `Emulator::step()` call will see `is_halted() == false` and take the
full dual-core path. There is no race: the emulator is single-threaded and
`step()` is not reentrant.

**Contention state left dirty?** When core 1 is halted we skip
`clear_contention_state()`. This means `core0_port` and
`contention_check_active` retain their values from the previous tick. This is
safe because the contention state is only read during core 1's step, which we
also skip. When core 1 wakes, the next tick takes the else branch and calls
`clear_contention_state()` before either core steps.
