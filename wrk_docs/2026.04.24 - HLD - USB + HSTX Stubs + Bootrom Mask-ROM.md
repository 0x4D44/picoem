# 2026.04.24 — HLD — USB + HSTX Stubs + Bootrom Mask-ROM

## Goal

Close three remaining RP2350 firmware-fidelity gaps so that pico-sdk firmware
touching USB init, HSTX config, or bootrom service functions executes to
steady state in the emulator without faulting.

1. **USB** — register-surface stub (no protocol).
2. **HSTX** — register-surface stub (no pixel stream).
3. **Bootrom mask-ROM** — `rom_func_lookup`-resolved calls run their
   documented semantics.

Success criterion per component is "firmware runs past this subsystem's
init without asserting or entering a fault loop," measured by firmware
smoke tests listed in the Oracle section of each component.

## Explicit non-goals

- **USB protocol emulation**, host mode, device enumeration, CDC passthrough.
  Those are separate HLDs if ever justified by a concrete workload.
- **HSTX pixel-stream observability** — no rendered output, no DVI/DPI
  capture. A 3 Gb/s pin stream runs at silicon speed; emulating it slower
  is pointless (see conversation 2026.04.24).
- **BOOTSEL UF2 drive** — `reset_to_usb_boot` shuts the emulator down
  cleanly; drag-and-drop UF2 ingest stays out of scope.
- **Secure-boot verification** through the bootrom path. Whatever the
  current Secure-world state is, this HLD doesn't extend or regress it.
- **RISC-V bootrom path** — Hazard3 side is conceptually the same design
  but deferred until a workload forces it.

No feature flags. No environment variables. No migration or
back-compat. The two new peripherals and the bootrom-hook table land
directly in `mdrp2350`.

## Stage 0 — Survey (cheap, do first)

Three facts are load-bearing for the design below. Confirm each by
inspection before writing code; record findings in the implementation
journal.

1. **What does `Emulator::load_bootrom` actually do today?** Does it
   install `roms/rp2350/bootrom-combined.bin` at `0x0000_0000`? Does a
   firmware `rom_func_lookup` currently reach real bootrom code, or
   fault on unimplemented addresses?
2. **What bootrom service functions does real workload firmware actually
   call?** Run OneROM + PicoGUS firmware under a PC trace scoped to the
   ROM range, log the 4-char code at each `rom_func_lookup`. Output: a
   prioritised catalogue of functions the emulator must support.
3. **Pinned register maps**: USB (`USBCTRL_REGS_BASE = 0x5011_0000`,
   DPRAM at `0x5010_0000`) and HSTX (`HSTX_CTRL_BASE` + `HSTX_FIFO_BASE`
   — read from RP2350 datasheet §Appendix A, not guessed). Paste exact
   offsets into the component docblocks.

Stage 0 output is a single journal entry. If Stage 0 reveals the bootrom
already dispatches cleanly through `rom_func_lookup` for the observed
workload, Component 3 collapses to "add PC hooks for the two or three
functions that don't work" — not the full catalogue.

## Component 1 — USB stub

### Scope

- Two MMIO regions:
  - `USBCTRL_REGS_BASE = 0x5011_0000` — control/status registers.
  - `USBCTRL_DPRAM_BASE = 0x5010_0000`, 4 KB — dual-port RAM for
    endpoint buffers. Plain RAM backing.
- All control register writes accepted, last-write-wins stored.
- Reads return stored value, except a small set of status registers that
  statically report "no device, no activity":
  - `SIE_STATUS`: `CONNECTED=0`, `SUSPENDED=0`, `RESUME=0`,
    `VBUS_DETECTED=0`, `BUS_RESET=0`, `TRANS_COMPLETE=0`.
  - `BUFFER_STATUS = 0`.
  - `INTS = 0`, `INTR = 0`. NVIC IRQ line for USBCTRL never asserts.
- Participates in RESETS (`RESET_USBCTRL = 28`, already defined in
  `bus/mod.rs:214`): on reset-asserted, register state returns to reset
  values; DPRAM is *not* cleared (silicon behaviour — confirm in Stage 0).

### File

`crates/mdrp2350/src/peripherals/usb.rs`. Register map constants at top,
`UsbCtrl` struct with `read32` / `write32` / `reset` / `tick` following
the existing `Peripheral` trait shape (mirror `uart.rs` idioms).

### Oracle

- **Unit tests** alongside the module:
  - pico-sdk `usb_hw_init()` sequence runs: writes to `USB_MUXING`,
    `USB_PWR`, `MAIN_CTRL`, `SIE_CTRL`, then a `SIE_STATUS` read. Assert
    no fault, `SIE_STATUS` reports `VBUS_DETECTED=0`.
  - DPRAM write-then-read at several offsets round-trips.
  - IRQ line stays low across the full init sequence.
- **Silicon oracle (stretch)**: scenario `usb_init_no_device` in
  `silicon_periph_diff_rp2350` — identical MMIO sequence against an
  RP2354 board with nothing on the USB port; diff register surface at
  end of window. Only worth adding if a later bug suggests stub drift.

Estimate: ~250 lines including docblock, tests, and the register-name
constants.

## Component 2 — HSTX stub

### Scope

- Two MMIO regions (confirm bases in Stage 0):
  - `HSTX_CTRL_BASE` — lane config, FIFO-status register, enable bit.
  - `HSTX_FIFO_BASE` — write-only FIFO port.
- Control register writes accepted, last-write-wins stored.
- FIFO writes silently consumed (no queue; no backpressure; stays empty).
- `CSR`/FIFO status reads report `FIFO_EMPTY=1`, `FIFO_FULL=0`,
  `FIFO_LEVEL=0`. Whatever "expected word count" register exists stays
  at zero.
- Participates in RESETS (`RESET_HSTX = 3`, already defined in
  `bus/mod.rs:171`).

### File

`crates/mdrp2350/src/peripherals/hstx.rs`. Same shape as `usb.rs`.

### Oracle

- **Unit tests**:
  - pico-sdk HSTX init sequence (clock setup already happens in
    `CLK_HSTX_CTRL`; this test starts from there): write lane map to
    `BIT0..BIT7`, `EXPAND_SHIFT`, `EXPAND_TMDS`, then set
    `CTRL.EN=1`. Write 1024 words to the FIFO. Assert no fault, FIFO
    status still reports empty.

No silicon oracle proposed — HSTX register-surface matching with no
active DVI output is low-information; save probe time.

Estimate: ~180 lines.

## Component 3 — Bootrom mask-ROM

### Approach

**Default path**: run the real RP2354 bootrom binary
(`roms/rp2350/bootrom-combined.bin`, already in-tree) from ROM memory.
Firmware's `rom_func_lookup` walks the real `rom_func_table` and
dispatches into real bootrom code. Functions that only touch peripherals
we already emulate (SHA256, TRNG, XIP_CTRL/QMI, DMA, OTP) just work —
the bootrom *is* the implementation, we don't duplicate it.

**PC hooks** for functions that depend on peripherals we don't support
(e.g. USB BOOTSEL mass-storage). A small table keyed by entry-point PC
intercepts before fetch, runs a Rust semantic, writes the return value
to `R0`, and returns to `LR`. This is the minimum mechanism that avoids
hand-rolling every function.

Rationale: hand-rolling every bootrom service function duplicates
proprietary behaviour we can already execute verbatim. The hook
mechanism is the smallest thing that handles the hard cases without
forking the full function catalogue.

### Stage 3.1 — Bootrom dispatch survey

Output of Stage 0 fact #2 drives this. For the observed call catalogue,
classify each function:

- **Runs in real bootrom today** — no work needed beyond confirming via
  firmware smoke.
- **Reaches bootrom but faults partway** — identify which peripheral
  access faults; either fix that peripheral or add a PC hook.
- **Never reaches — `rom_func_lookup` itself is broken** — fix at the
  table-walk level before anything downstream.

### Stage 3.2 — PC hook table

`crates/mdrp2350/src/bootrom_hooks.rs`:

```rust
pub struct BootromHookTable { ... }

impl BootromHookTable {
    pub fn resolve(bootrom: &[u8]) -> Self { ... }
    pub fn dispatch(&self, pc: u32, regs: &mut CoreRegs) -> Option<()> { ... }
}
```

Resolution happens once, at `Emulator::load_bootrom` completion: walk
the real `rom_func_table` in the loaded bootrom binary, match 4-char
codes against a static list, record (code → entry-point PC → Rust
handler).

Dispatch happens on the fetch path in `CortexM33::step`: one
table-lookup per instruction. Empty table → zero-cost. Non-empty table →
one hash/linear probe on PCs (expected ≤5 entries; linear probe is
fine).

Minimum handler set (revise after Stage 3.1 survey):

- `reboot` / `reset_to_usb_boot` — set `Emulator::shutdown_requested =
  true`; caller never returns from firmware's viewpoint (silicon
  reboots).
- Possibly: secure-boot-only functions if Stage 3.1 shows firmware hits
  them.

### Files

- `crates/mdrp2350/src/bootrom_hooks.rs` — table + dispatch.
- One-line call site in `Emulator::step` (or `CortexM33::step`) before
  fetch.

### Oracle

- **Unit test**: emulator with real bootrom loaded; firmware calls
  `rom_func_lookup('FC')` (`flash_connect`), jumps to returned pointer,
  runs to completion. Assert expected XIP_CTRL/QMI register state at end
  and no fault.
- **Integration**: a minimal firmware exercising
  `flash_range_program` + `flash_range_erase` with a small data pattern;
  verify flash backing-store state matches the documented semantics.
- **Silicon oracle stretch** — per-hook scenarios in
  `silicon_periph_diff_rp2350`: same function call on silicon and
  emulator, diff observables (register surface, flash contents where
  applicable). Worth doing once Stage 3.1 catalogue is fixed.

## Risks and things to watch

- **Stage 0 might invalidate the "run real bootrom" assumption.** If the
  bootrom doesn't execute cleanly today, Component 3 is larger than
  described — potentially a function-by-function hand-roll. Stage 0 is
  explicitly the branch point; re-scope before starting 3.2 if the
  survey is bad.
- **Bootrom version drift.** Pin `bootrom-combined.bin` to a recorded
  SHA256; any refresh is an explicit commit. Mechanism can be as simple
  as an assert in `load_bootrom`.
- **Hook table growth.** If Stage 3.1 reveals >10 functions need
  hooking, the "use real bootrom" idea has lost its leverage and the
  alternative (hand-roll each function) deserves a second look. Revisit
  the HLD at that point.
- **IRQ line for USBCTRL**: permanently-low is only safe if real
  firmware doesn't *require* the USB IRQ as part of init (e.g. waiting
  on `BUS_RESET` to assert). Confirm in Stage 0 fact #2 survey.

## Sequencing and versioning

Land in this order, each a separate commit:

1. Stage 0 survey journal.
2. Component 1 (USB stub) — `mdrp2350` minor bump.
3. Component 2 (HSTX stub) — `mdrp2350` minor bump.
4. Stage 3.1 bootrom survey — journal only, no code.
5. Stage 3.2 PC hooks + `reset_to_usb_boot` handler — `mdrp2350` minor
   bump.
6. Additional bootrom hooks one per commit as Stage 3.1 survey dictates.

No rollback, no migration, no coexistence with an older code path.
