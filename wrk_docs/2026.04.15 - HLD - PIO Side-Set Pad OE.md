# PIO Side-Set Pad OE

Version: 0.1.0
Date: 2026-04-15

## Problem

`PioBlock::merge_pin_outputs` in
`crates/mdpicoem-common/src/pio/mod.rs` forces the side-set pins to be
output-enabled whenever `EXECCTRL.SIDE_PINDIR=0` (value-drive mode),
regardless of whether firmware ever programmed those pin directions.
The offending line is `crates/mdpicoem-common/src/pio/mod.rs:196`:

```rust
let side_pindir = (sm.execctrl >> 29) & 1 != 0;
if side_pindir {
    // Side-set controls pin directions
    oe = (oe & !positioned_mask) | (sm.sideset_dirs & positioned_mask);
} else {
    // Side-set controls pin values (normal mode)
    out = (out & !positioned_mask) | (sm.sideset_pins & positioned_mask);
    oe |= positioned_mask; // side-set pins are always output-enabled  ← WRONG
}
```

Per RP2350 §11.3.2.3, side-set with `SIDE_PINDIR=0` drives pin
**values** only; pin directions must come from `SET PINDIRS`, `OUT
PINDIRS`, or `SIDE_PINDIR=1`. The current line silently asserts OE=1
for any side-set pin, which means firmware that relies on tri-state
side-set signals (bidirectional buses, open-drain wiring) will
diverge from silicon.

The bug affects **both chips**: `crates/mdrp2350` and `crates/mdrp2040`
both depend on `mdpicoem-common` and share the same
`PioBlock::merge_pin_outputs` code path.

### The silicon oracle's view

Scenario `pio0_side_set_toggle` in
`crates/mdpicoem-harness/src/silicon_scenarios.rs:125` programs SM0
with `PINCTRL.SIDESET_COUNT=1`, `PINCTRL.SIDESET_BASE=0`,
`EXECCTRL=0` (both `SIDE_EN=0` and `SIDE_PINDIR=0`), loads `JMP 0, side
1` at instruction slot 0, routes GPIO0 through PIO0 via IO_BANK0 /
PADS_BANK0, and enables SM0 for roughly 100 sysclks. Never at any
point is `SET PINDIRS` executed.

- **Silicon:** `pad_oe` for GPIO0 stays clear (pin remains an input).
  The level read back via SIO `GPIO_IN` (bit 0) is **0** — the pad is
  tri-stated, and with no external drive the PADS pull chain resolves
  to logic 0.
- **Emulator (today):** the side-set branch ORs the positioned mask
  into `pad_oe`. During the run, `update_gpio`
  (`crates/mdrp2350/src/lib.rs:234`) observes `pad_oe=1 pad_out=1` on
  bit 0 and sets `bus.gpio_in` bit 0 to **1**. A subsequent read of
  `SIO_GPIO_IN` returns 1.

The harness gate — `emu.mmio_write32(PIO0_BASE + PIO_CTRL_OFF, 0)` at
`crates/mdpicoem-harness/src/bin/silicon_periph_diff_rp2350.rs:182`
— disables all SMs and re-runs `merge_pin_outputs`, which takes the
`sm_enabled_mask == 0` branch (`crates/mdpicoem-common/src/pio/mod.rs:160-164`)
and zeroes both `pad_out` and `pad_oe`. But `bus.gpio_in` is not
refreshed by `write_ctrl`; it still holds the stale value from the
last `tick_peripherals` call inside `emu.run`. So the `DBG_PADOE`
readback at `PIO0 + 0x040` agrees (both 0), but the `SIO_GPIO_IN`
readback diverges. Exactly the behaviour documented in the scenario
comment at `silicon_scenarios.rs:144-167`.

The divergence fires as a GPIO-side line in the scenario summary:
> `GPIO mask=0x00000001: HW oe=0x00000000 level=0x00000000, EMU oe=0x00000000 level=0x00000001`

## Datasheet reality

RP2350 §11.3.2.3 ("Side-set") in paraphrase, corroborated by the
comment at `silicon_scenarios.rs:146-151` and the tech-debt entry at
`tech_debt.md:189-214`:

1. **Value-drive mode (`EXECCTRL.SIDE_PINDIR = 0`, the default).**
   Side-set writes to the **pin-value** latch for the side-set pin
   range. The PIO state machine does **not** assert output-enable as a
   side effect. If firmware wants the pin driven, it must have
   separately set the pin direction via one of:
   - `SET PINDIRS, <mask>` (SET-base-aligned, up to `SET_COUNT` bits;
     handler `exec_set` destination 4 at
     `crates/mdpicoem-common/src/pio/sm.rs:786-791`).
   - `OUT PINDIRS, <count>` (OUT-base-aligned, up to `OUT_COUNT` bits;
     handler `exec_out` destination 4 at
     `crates/mdpicoem-common/src/pio/sm.rs:606-612`).
   - `MOV PINDIRS, <src>` (OUT-base-aligned; handler `exec_mov`
     destination 3 at `crates/mdpicoem-common/src/pio/sm.rs:732-737`).
   - Prior SDK helper `pio_sm_set_consecutive_pindirs` (seen in
     `target/picogus_refs/isa_io.pio:60-67`) or
     `pio_sm_set_pindirs_with_mask` — both ultimately emit SET PINDIRS
     instructions via force-execute.

2. **Direction-drive mode (`EXECCTRL.SIDE_PINDIR = 1`).** Side-set
   writes the **pin-direction** latch instead of the value latch. This
   is the path `merge_pin_outputs` line 192 takes, and it already
   correctly merges `sm.sideset_dirs` into `oe` without assuming any
   default. This mode is rarely used — a side-set "pulse" pattern that
   flips direction rather than value.

3. **Relationship between the in-PIO PINDIR mirror and SIO
   `GPIO_OE`.** The PIO block owns its own `pad_oe` (exposed at
   `DBG_PADOE`, `PIO + 0x040`). The merge across PIO / SIO happens at
   `update_gpio` in `crates/mdrp2350/src/lib.rs:234`: `pio.pad_oe`
   wins wherever it has a bit set (PIO overrides SIO for the pins it
   drives), and the merged value lands in `bus.gpio_in` as the "pin is
   driven" indicator. The SIO `GPIO_OE` register at `0xD000_0030` is
   the **SIO-side** direction latch; it is unrelated to the PIO
   direction latch except via the downstream merge. A pin that is PIO-
   controlled (`IO_BANK0_GPIOn_CTRL.FUNCSEL=6`) takes its direction
   from the PIO block, never from SIO `GPIO_OE`.

So what we are missing today is: on the value-drive path, we should
carry across whatever direction `SET PINDIRS` / `OUT PINDIRS` / `MOV
PINDIRS` already established for those pins, rather than synthesising
`OE=1` from the side-set mask.

### Where PINDIRS lands today

Both `SET PINDIRS` and `OUT PINDIRS` route through
`StateMachine::write_pin_field` (`crates/mdpicoem-common/src/pio/sm.rs:323-336`)
into the **block-shared** `shared_pin_dirs` latch owned by
`PioBlock`. `merge_pin_outputs` copies `shared_pin_dirs` straight into
`oe` at `mod.rs:166` before any side-set masking:

```rust
let mut out: u32 = self.shared_pin_values;
let mut oe: u32 = self.shared_pin_dirs;
```

So a `SET PINDIRS, 1` (with `SET_BASE=1`, `SET_COUNT=1`) sets bit 1 of
`shared_pin_dirs`, which flows into `oe` as bit 1, which is exactly
the right answer. The whole architecture is already in place to
support the correct behaviour — the buggy `oe |= positioned_mask` in
the value-drive branch is a single extra line layered on top.

Note that `shared_pin_dirs` is block-scoped, not per-SM. Two SMs in
the same PIO block writing `SET PINDIRS` to overlapping pin ranges
will overwrite each other, which matches silicon (all four SMs feed
one shared pad-direction bus inside the PIO block).

## Design options

### Option A — "Drop the OR"

Delete the offending line:

```rust
} else {
    // Side-set controls pin values (normal mode)
    out = (out & !positioned_mask) | (sm.sideset_pins & positioned_mask);
    // (no `oe |= positioned_mask` — direction is whatever SET/OUT/MOV
    // PINDIRS established via `shared_pin_dirs`)
}
```

**Cost.** One line deleted. The `oe` starts as `self.shared_pin_dirs`
from `mod.rs:166`; no other code path synthesises OE bits for
side-set pins in value-drive mode, so dropping the OR makes the
emulator behave like silicon for every encoding of side-set.

**Pros.**
- Minimum delta, matches Arthur's "smallest change" preference from
  CLAUDE.md.
- No per-SM state added; no new field to keep in sync across reset,
  restart, and force-execute.
- `SIDE_PINDIR=1` path is unchanged — no regression risk on the mode
  that was already correct.
- "Side-set in the same instruction as SET PINDIRS" is already
  handled correctly by the sequencing: `apply_sideset` runs before
  `execute_insn` (`sm.rs:205-214`), so within a single
  `execute_cycle` the SET PINDIRS write to `shared_pin_dirs` happens
  after the side-set writes to `sideset_pins`. On the next
  `merge_pin_outputs` call (after the step loop), `oe =
  shared_pin_dirs` picks up the SET PINDIRS bits, and the side-set
  branch leaves `oe` alone.
- "Multiple SMs sharing pins": `shared_pin_dirs` is already
  block-shared; neither SM needs to track OE separately. Matches
  silicon.
- "`EXECCTRL.SIDE_EN`" (optional-side-set): when the opcode's MSB
  bit of the delay/sideset field is 0, the decoder emits
  `decoded.sideset = None` (see `decode.rs`); `apply_sideset` does
  nothing (`sm.rs:298`), so `sideset_pins` is untouched. In
  `merge_pin_outputs`, `actual_ss_pins = ss_count - 1` (for SIDE_EN=1
  with SIDESET_COUNT=1, that is 0), so `actual_ss_pins > 0` is false
  and the side-set branch is skipped entirely. Option A's delta is
  inert in this configuration — no behaviour change.
- "`PINCTRL.SIDESET_COUNT=0`": the `if actual_ss_pins > 0` guard at
  `mod.rs:180` already skips the whole branch. Option A's delta is
  inert.
- "Pad-merge-on-SM-disable" (the `pio0_side_set_toggle` relies on
  `pad_oe` being cleared when `PIO_CTRL=0` disables all SMs): the
  early-return at `mod.rs:160-164` zeroes both `pad_out` and
  `pad_oe` when `sm_enabled_mask == 0`, untouched by either option.

**Cons.**
- Silently assumes nothing else upstream expected the old behaviour.
  `test_pio_spi_clk_mosi` (`crates/mdrp2350/src/pio_tests.rs:337-443`)
  is one such place — its comment at line 380-384 explicitly states:
  > "Side-set pins get their OE set automatically by
  > merge_pin_outputs when sideset_count > 0. So we only need to
  > force-enable pin 0 direction."
  This test will fail because `clk_trace[i] = emu.gpio_read(1)` walks
  `bus.gpio_in`, and with `pad_oe` bit 1 unset, `update_gpio` treats
  the pin as undriven. The test must be updated to explicitly program
  PINDIRS for pin 1. This is a test bug exposing the emulator bug;
  the test was encoding the bug as spec.

- Test-only: no per-SM "OE established by PINDIRS" tracking, so if
  a future path emerges where we want to know "was this pin's
  direction set via PINDIRS or by side-set", Option A can't answer.
  No such path exists today.

### Option B — "Per-SM PINDIR shadow"

Add `pindirs: u32` to `StateMachine` (zero at reset). Every `SET
PINDIRS` / `OUT PINDIRS` / `MOV PINDIRS` / side-set-with-`SIDE_PINDIR=1`
execution updates the shadow in addition to (or instead of)
`shared_pin_dirs`. `merge_pin_outputs` then ORs each enabled SM's
shadow:

```rust
fn merge_pin_outputs(&mut self) {
    if self.sm_enabled_mask == 0 {
        self.pad_out = 0;
        self.pad_oe = 0;
        return;
    }
    let mut out: u32 = self.shared_pin_values;
    let mut oe: u32 = 0;  // no longer seeded from shared_pin_dirs
    for sm in &self.sm {
        if !sm.enabled {
            continue;
        }
        oe |= sm.pindirs;   // NEW — per-SM OE contribution
        // side-set value-drive overlay: value only
        // ...
    }
    self.pad_out = out;
    self.pad_oe = oe;
}
```

**Cost.** One `u32` per SM (16 bytes total across three PIO blocks ×
four SMs ≈ 48 bytes). Every PINDIRS-touching handler writes both the
shared latch and the per-SM shadow. `PioBlock::reset` and
`StateMachine::reset` clear the shadow.

**Pros.**
- More architecturally honest: the shadow matches the "each SM
  maintains its own in-PIO PINDIR mirror" model in the datasheet
  (§11.3.2.3 notes the PIO block's internal pin-direction tracking).
- If a future scenario needs to attribute an OE bit to a specific SM
  (e.g. a future oracle that diffs per-SM state), the shadow is
  ready.
- Removes the need for `shared_pin_dirs` to be block-shared; the
  block can compute its aggregate OE from the SM shadows.

**Cons.**
- More code. Four handlers need updating (SET PINDIRS, OUT PINDIRS,
  MOV PINDIRS, side-set with `SIDE_PINDIR=1`), plus reset plumbing,
  plus the merge changes.
- The `SIDE_PINDIR=1` branch would need to write both
  `sm.sideset_dirs` AND `sm.pindirs`, or `merge_pin_outputs` would
  need to OR both fields — a design decision with tradeoffs.
- `shared_pin_dirs` becomes vestigial if the shadow fully subsumes
  it. Leaving both in place is confusing; removing `shared_pin_dirs`
  is a larger refactor that touches `sm.rs`'s PINDIRS write path.
- "Side-set in the same instruction as SET PINDIRS": within one
  `execute_cycle`, `apply_sideset` updates `sideset_pins` /
  `sideset_dirs`, then `execute_insn` dispatches SET PINDIRS which
  updates `pindirs` (and `shared_pin_dirs`). The merge sees both
  contributions. Correct.
- "Multiple SMs sharing pins": each SM's `pindirs` contributes; the
  OR in the merge handles overlap. Silicon behaviour is that all
  SMs share one pin-direction bus, so the OR-merge matches.
- "`EXECCTRL.SIDE_EN`" / "`PINCTRL.SIDESET_COUNT=0`": same analysis
  as Option A — those paths are skipped at higher guards; the
  shadow is unaffected.
- "Pad-merge-on-SM-disable": the `sm_enabled_mask == 0` early-return
  zeros `pad_oe` regardless of what is in the shadows. Same as
  Option A.
- Test migration cost is the same: `test_pio_spi_clk_mosi` still
  needs an explicit PINDIRS programming because the side-set on
  pin 1 no longer synthesises OE.

## Recommendation

**Option A**: delete `oe |= positioned_mask` at
`crates/mdpicoem-common/src/pio/mod.rs:196`.

Rationale, weighing CLAUDE.md's "smallest change" and "don't predict
the future" principles against test-coverage debt:

1. Option A is correct today. The existing `shared_pin_dirs` latch
   already encodes every way firmware can program pin directions
   (SET/OUT/MOV PINDIRS all route through it). The merge picks up
   `shared_pin_dirs` unconditionally at `mod.rs:166`. Dropping the
   single OR line makes emulator behaviour match silicon for every
   scenario I can construct.

2. Option B's extra expressiveness (per-SM attribution of OE bits)
   has no current consumer. The tech-debt entry notes
   ("`silicon_periph_diff_rp2350::pio0_side_set_toggle`", PicoGUS's
   firmware, potential bidirectional-bus scenarios) all validate by
   observing the aggregate `pad_oe` / SIO `GPIO_IN`, never per-SM
   attribution. Building the shadow on speculation violates
   CLAUDE.md's "premature abstractions resist the correct design
   when it arrives" rule.

3. The `SIDE_PINDIR=1` path already demonstrates the correct pattern:
   its `sideset_dirs` field is per-SM and *that* contribution is OR'd
   into `oe` at `mod.rs:192`. The value-drive branch does not need
   to mirror this structure — the value-drive mode's whole defining
   property is that it does not contribute to direction.

4. The test-coverage debt is localised: exactly one test
   (`test_pio_spi_clk_mosi`) has to be updated to add an explicit
   `SET PINDIRS, 3` instead of `SET PINDIRS, 1`, bringing it in
   line with silicon. One test comment needs revision. No other
   test touches the buggy path as a load-bearing spec.

If a future scenario appears where per-SM PINDIR attribution
matters (e.g. a differential oracle comparing each SM's contribution
to the direction bus), Option B is a clean extension: add the
shadow, wire it into merge, leave the existing `shared_pin_dirs`
flow untouched. The fix ordering is: ship Option A now, reach for
Option B only if a concrete consumer materialises.

All tests live in
`crates/mdpicoem-common/src/pio/mod.rs`'s `#[cfg(test)] mod tests`
block (test module starts around `mod.rs:501`; the `pad_oe` family
lives near the `PIO Idle Skip` fast-path probes at lines 1490-1542).
Style to match: the existing `idle_block_step_is_noop` /
`disable_clears_pin_outputs` tests both pre-enable SM0, poke
`shared_pin_values` / `shared_pin_dirs` / instruction memory

and assert on `pio.pad_oe` / `pio.pad_out`.

### T1 — `side_set_value_drive_does_not_force_oe` (the tech-debt
### reproducer)

Mirrors `tech_debt.md:205-208`:

```rust
#[test]
fn side_set_value_drive_does_not_force_oe() {
    let mut pio = PioBlock::new();
    // PINCTRL: SIDESET_COUNT=1, SIDESET_BASE=0
    pio.sm[0].pinctrl = 1u32 << 29;
    // EXECCTRL: SIDE_EN=0, SIDE_PINDIR=0 (value-drive)
    pio.sm[0].execctrl = 0;
    // JMP 0, side 1 (side-set bit in [12]=1, delay 0, JMP addr=0)
    pio.instr_mem[0] = 0x1000;
    pio.set_sm_enabled(0, true);
    pio.sm[0].clkdiv_int = 1;
    pio.sm[0].clkdiv_frac = 0;

    pio.step(0);

    // Side-set drove the VALUE on pin 0 …
    assert_ne!(pio.pad_out & 1, 0,
        "side-set pin 0 value should be driven high");
    // … but DID NOT force the direction.
    assert_eq!(pio.pad_oe & 1, 0,
        "side-set value-drive must not set pad_oe without PINDIRS");
}
```

Fires today; passes after the fix.

### T3 — `set_pindirs_drives_oe_without_side_set`

Confirms the non-side-set path that Option A relies on still works.
Uses force-execute to issue SET PINDIRS without needing a program

fn set_pindirs_drives_oe_without_side_set() {
    let mut pio = PioBlock::new();

Passes today; must continue to pass.

### T4 — `side_set_after_pindirs_keeps_oe`

Composite scenario that proves the correct behaviour for the
bidirectional-bus / open-drain pattern: firmware explicitly sets
direction via PINDIRS, then uses side-set to toggle values. The
PINDIRS-established OE must persist across the side-set.

```rust
#[test]
fn side_set_after_pindirs_keeps_oe() {
    let mut pio = PioBlock::new();
    // PINCTRL: SIDESET_COUNT=1, SIDESET_BASE=0,
    //          SET_COUNT=1, SET_BASE=0
    pio.sm[0].pinctrl = (1u32 << 29) | (1u32 << 26);
    // EXECCTRL: SIDE_EN=0, SIDE_PINDIR=0
    pio.sm[0].execctrl = 0;
    // Program:
    //   addr 0: SET PINDIRS, 1  (enable pin 0 as output)
    //   addr 1: NOP, side 1     (MOV Y, Y with side=1 — drives pin 0 high)
    pio.instr_mem[0] = 0xE081;  // SET PINDIRS, 1
    pio.instr_mem[1] = 0xB042 | (1 << 12); // MOV Y,Y + side=1
    pio.set_sm_enabled(0, true);
    pio.sm[0].clkdiv_int = 1;
    pio.sm[0].clkdiv_frac = 0;

    pio.step(0);  // SET PINDIRS, 1 → shared_pin_dirs bit 0 = 1
    assert_ne!(pio.pad_oe & 1, 0,
        "OE established by SET PINDIRS on tick 1");

    pio.step(0);  // NOP side 1 → sideset_pins bit 0 = 1; oe stays set
    assert_ne!(pio.pad_oe & 1, 0,
        "OE from PINDIRS must persist across side-set value write");
    assert_ne!(pio.pad_out & 1, 0,
        "side-set drove the value high on tick 2");
}
```

Fires today if the MOV Y,Y encoding plus the merge's OR leaves the
PINDIRS bit set (it happens to, because the OR is additive), so
this test likely passes before the fix too — but it pins down the
*intended* behaviour: Option A must preserve PINDIRS-established OE
across side-set value writes. After the fix, this test continues to
pass because `oe` starts from `shared_pin_dirs` (which has bit 0)
and the side-set branch's value-only write doesn't touch `oe`.

## Cross-chip blast radius

`mdpicoem-common` is shared; every test that exercises
`PioBlock::merge_pin_outputs` in either chip is in scope.

### RP2350 (`crates/mdrp2350/src`)

Unit tests that assert on `pad_oe` or on `bus.gpio_in` derived from
`pad_oe`:

- `crates/mdrp2350/src/pio_tests.rs:111-141` — the GPIO-merge tests
  (`test_gpio_merge_pio_overrides_sio`, `test_gpio_merge_independent_pins`).
  These poke `pad_oe` directly; they do not exercise the side-set
  path. Unaffected.
- `crates/mdrp2350/src/pio_tests.rs:337-443` —
  `test_pio_spi_clk_mosi`. **Breaks under Option A.** The test
  configures SIDESET_COUNT=1, SIDESET_BASE=1, SIDE_PINDIR=0, and then
  force-executes `SET PINDIRS, 1` with `SET_COUNT=1, SET_BASE=0`. The
  comment at line 380-384 explicitly encodes the bug as spec: "Side-
  set pins get their OE set automatically by merge_pin_outputs when
  sideset_count > 0. So we only need to force-enable pin 0
  direction."
  - **Fix:** change SET_COUNT to 2 (`pinctrl |= 2u32 << 26`) and
    the force-executed instruction to `SET PINDIRS, 3` (drive both
    MOSI at pin 0 and CLK at pin 1). The opcode for `SET PINDIRS, 3`
    is `0xE083` (dest=100, data=00011). Delete the misleading
    comment, replace with one noting that silicon requires PINDIRS
    for the side-set pin.
  - This test is the *only* file that encodes the bug as spec in
    either chip's test tree.
- `crates/mdrp2350/src/tests.rs:7297-7340` — pokes `pad_oe` directly
  on `emu.bus.pio[0]`; no side-set involvement. Unaffected.
- The four `idle_block_step_is_noop` / `disable_clears_pin_outputs` /
  `test_sideset_on_stall` / `test_sideset_persists_during_delay` tests
  in `pio/mod.rs` assert on `sideset_pins` (the per-SM latch), not on
  `pad_oe`. Unaffected.

## Risk + rollback

### Risks

1. **`test_pio_spi_clk_mosi` regression.** Mitigated by updating the
   test as described above. This is a must-fix, not optional.
2. **A silent dependency on the buggy behaviour in downstream firmware
   images** (OneROM, PicoGUS, blinky ROMs in `roms/`). Verified: none
   of these exercise side-set in value-drive mode without an
   accompanying PINDIRS programming. See the harness scenarios
   section.
3. **Test coverage gap on PINDIRS interaction with `MOV PINDIRS`.**
   Currently there is no test that force-executes a `MOV PINDIRS`
   and checks `pad_oe`. T4 covers SET PINDIRS; consider adding a T5
   for `MOV PINDIRS` if Arthur wants fuller coverage. Not blocking.
4. **Forward regression risk from future changes to
   `merge_pin_outputs`.** The fix makes the function's contract
   cleaner (value-drive does not contribute to direction); T1 + T2
   + T3 + T4 are the regression probes.

### Rollback

The fix is one line deleted and one test updated. Rollback is a
`git revert` of that commit; the behaviour reverts to pre-fix, all
four new tests fail, `pio0_side_set_toggle` silicon oracle fails.
No migration concerns; no data-shape changes; no API surface
affected.

## Out of scope

Explicitly **not** covered by this HLD:

- **The adjacent "PIO not gated on RESETS bit" tech-debt item**
  (`tech_debt.md:180-187`). That is a separate bug with separate
  reproducer and separate risk profile.
- **OUT PINDIRS cycle accuracy.** Today, OUT PINDIRS takes one PIO
  tick like any other OUT; the datasheet permits up to `OUT_COUNT`
  bits to be written per tick. No known discrepancy, and none
  surfaced by the silicon peripheral oracle.
- **MOV PINDIRS semantics.** The `exec_mov` destination 3 handler
  (`sm.rs:732-737`) is RP2350-specific and writes
  `shared_pin_dirs`. Its correctness is orthogonal to this fix;
  adding a T5 to verify `MOV PINDIRS → pad_oe` is noted above but
  deferred.
- **Per-SM attribution of `pad_oe` bits.** Option B provides this;
  Option A doesn't. If a future oracle needs it, see Option B's
  pros for the migration path.
- **`DBG_PADOE` mid-run observation without an SM-disable gate.**
  The silicon oracle gates via `PIO_CTRL=0` before reading
  `DBG_PADOE`, so the early-return path zeros `pad_oe` and
  `DBG_PADOE` reads 0 on both sides. If a future oracle wants to
  observe `DBG_PADOE` *during* the run without gating, the HLD
  does not cover that read path (`update_gpio` is only called at
  quantum end, not on `DBG_PADOE` reads — which is fine because
  `DBG_PADOE` directly returns `pad_oe` without going through
  `update_gpio`).
- **Side-set on the `SIDE_EN=1` delay-encoded form where the
  opcode's delay/sideset field MSB is the enable bit.** Option A
  leaves this path unchanged because the decoder short-circuits
  `decoded.sideset = None` when the enable bit is 0. The `SIDE_EN=1,
  ss_count=1` case (which yields `actual_ss_pins=0`) is handled by
  the `actual_ss_pins > 0` guard at `mod.rs:180`. No code change
  needed.
- **CI integration of `silicon_periph_diff_rp2350`.** The oracle is
  hardware-gated (requires a Pico probe + RP2354). CI runs
  `cargo test -p mdpicoem-common` and `cargo test -p mdrp2350`,
  which cover T1-T4. The silicon re-run is a post-commit manual
  step against the lab rig.
