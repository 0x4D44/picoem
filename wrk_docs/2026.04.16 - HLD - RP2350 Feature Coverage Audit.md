# RP2350 Emulator — Feature Coverage Audit vs. Datasheet

**Date:** 2026-04-16
**Scope:** `crates/mdrp2350/` and its harness (`crates/mdpicoem-harness/`). Compares the emulator against the RP2350 datasheet and the Cortex-M33 / ARMv8-M Mainline architecture reference.
**Companion journal:** `wrk_journals/2026.04.16 - JRN - RP2350 Feature Coverage Deep Dive.md`.
**Methodology:** five-agent audit (CPU, bus, peripherals, security, devil's-advocate) plus spot-verification of load-bearing claims by the author. Findings that did not survive source-code verification were cut before publication.

## 1. Why this document exists

The mdrp2350 project has gained surface area fast — seven LLD phases, multiple silicon oracles, active peripheral-fidelity work. That surface area has made "does the RP2350 emulator support feature X?" harder to answer cheaply. This audit separates four concepts that the existing HLDs tend to blur:

| Term | Meaning |
|---|---|
| **Verified** | Silicon or QEMU differential oracle runs at least one scenario that exercises the feature end-to-end and passes. |
| **Unit-tested** | Rust `#[test]` exists; no external oracle has ever seen the feature. |
| **Plumbed / stubbed** | Register reads/writes round-trip, but the underlying side effects are absent. |
| **Missing** | No register decode, no file, zero code. |

Everything downstream (gap list, recommendations) is organised by these four categories.

## 2. Executive summary

- The emulator is a **competent Cortex-M33 Secure-world instruction simulator** with broad peripheral register-plumbing. For firmware that stays in the Secure world, does not use TrustZone isolation, does not touch the RP2350-only peripherals in §4.4, and does not depend on signed-boot behaviour — it will run.
- **Peripheral counts match the RP2350 datasheet exactly**: 3 PIO blocks, 16 DMA channels, 2 TIMERs (0 and 1), 12 PWM slices, 48 GPIOs. That is a real architectural advance over the RP2040 port.
- **Oracle coverage is broad but shallow.** Fifty silicon scenarios across four oracles gate the entire claim of "RP2350-accurate". Section 6 prosecutes this.
- **Three classes of feature are load-bearing in the datasheet and absent or advisory in the emulator**:
  1. The **RISC-V Hazard3 alternative cores** — zero implementation. The dual-ISA selector (ARCHSEL, via POWMAN) is not modelled.
  2. **Security enforcement** — SAU/IDAU/MPU/ACCESSCTRL are plumbed (or in MPU's case TT-only) but never gate a memory access. NSC, BLXNS/FNC_RETURN, SecureFault, NSACR are absent.
  3. **Boot ROM execution** — `load_bootrom` drops a canned image at `0x0`. Signed-image verification, boot2 chaining, XIP setup, and ARCHSEL are not simulated.
- **Interpolators are dead storage.** `sio/mod.rs:45` is `interp: [[u32; 32]; 2]`; the write path stores the word verbatim with zero CTRL/BLEND/CLAMP/SHIFT behaviour. Firmware that actually uses interpolators will compute nonsense and pass every existing test.
- Cycle accuracy is real where it has been measured — `silicon_cycle_oracle_rp2350` passes on the cases it covers — but the cases it covers are `tech_debt.md`-level primitives, not workloads.

## 4. Coverage by subsystem

### 4.1 CPU / ISA (Cortex-M33, ARMv8-M Mainline)

**Verified (QEMU + silicon):**
- Complete Thumb-16 base ISA (data processing, PUSH/POP/LDM/STM, branches, CBZ/CBNZ, IT blocks, ADR).
- Thumb-32 subset actually exercised by `qemu_diff_m33` generators: branches/misc (DSB/DMB/ISB, MSR/MRS, SVC, BKPT, SG, CPS, CPSID/CPSIE), LDM/STM wide, LDRD/STRD, long multiply, BL/BLX, wide B, some data-processing modified-immediate forms.
- VFPv5 single-precision FPU incl. FPSCR exception flags, FZ/DN handling, half↔single conversion, VLDR/VSTR, lazy FP context save (FPCCR LSPACT/CLRONRET/TS/LSPEN). Verified via QEMU and `silicon_isr_diff_rp2350`'s lazy/eager FP scenarios.
- Exception entry/return (8-word basic + 18-word FP frame), EXC_RETURN magic, stack-limit checks (MSPLIM/PSPLIM), tail-chaining, PRIMASK/BASEPRI/FAULTMASK masking, HardFault escalation, lockup. BASEPRI correctly byte-stored and `0xE0`-masked at priority compare (`exceptions.rs:515`) — architecturally correct for the 3 implemented priority bits.
- DWT CYCCNT per core (load-bearing for the silicon cycle oracle).
- BXNS + SG + banked Secure/Non-Secure register pairs for MSP/PSP/MSPLIM/PSPLIM/PRIMASK/BASEPRI/FAULTMASK/CONTROL; state-swap on transition (`core/mod.rs:178-180`).
- IDAU region mapper returning S/NS plus exempt flag (`core/exceptions.rs:816-848`) — the result is consumed only by TT, not by memory-access paths.
- Coprocessor dispatch + CPACR gate for CP0 (SIO), CP4/5 (DCP), CP7 (RCP), CP10/11 (FPU).

**Unit-tested only (no oracle):**
- Thumb-32 classes whose QEMU generators are commented out: `gen_t32_multiply_divide`, `gen_t32_dp_mod_imm`, `gen_t32_load_store_single`. Implementations exist in `execute_thumb32.rs`; fuzz never hits them.
- DCP (CP4/5) CDP arithmetic operations and RCP (CP7) assertion ops. Neither coprocessor appears in any silicon or QEMU scenario — their entire behaviour rests on Rust unit tests.
- FPU fixed-point conversions (VCVT.FX variants).
- TT / TTA / TTT / TTAT decoding.

**Stubbed / partial:**
- **MPU (PMSAv8):** 16 regions banked S/NS are register-addressable and queryable via TT, but `bus::read*`/`write*` never consult MPU state. No privilege, no XN enforcement, no fault on violation.
- **SAU:** 8 regions are storage-only. SAU region matching does not gate memory access. All accesses are treated as the current CPU security state.
- **Exception return S/NS bit** in EXC_RETURN is hardcoded (`exceptions.rs:76-83`). Return from an NS-invoked exception does not restore the security state.
- **Cycle costs** are per-instruction flat numbers. `tech_debt.md:29-89` enumerates ~14 known systematic deltas vs. silicon (load-use latency not modelled, backward-branch pipeline flush, SRAM bank contention, PUSH floor-cost off-by-one, etc.). The 9 cycle-oracle cases intentionally test primitives that model *does* predict; the known-bad patterns are not in the oracle.

**Missing:**
- **RISC-V Hazard3 cores.** Zero code. No ARCHSEL register, no POWMAN-gated boot-arch selection, no Hazard3 decoder, no RISC-V CSRs (mtime/mtimecmp are modelled only from the M33 SIO side), no PMP. This is **half the RP2350 CPU story**.
- `SecureFault` (exception #7) — not in the Fault enum (`core/mod.rs:16-30`).
- `BLXNS` (S→NS call) and `FNC_RETURN`.
- `NSC` (Non-Secure Callable) attribute on SAU regions.
- `NSACR`, `CPPWR`, `CPACR_NS` — no Secure-side coprocessor gating.
- `ETM`, `ITM` stimulus ports, `TPIU`, `PMU` (beyond CYCCNT).

### 4.2 Bus, memory, clocks

**Verified (silicon):**
- Address map decode for ROM, XIP main, SRAM (striped + scratch), APB, PPB, BOOTRAM alias, XIP SRAM cache window. Unmapped apertures → sticky `bus_fault` → HardFault.
- SRAM: 10 banks × 4 KB, striped 0–7 + scratch X/Y (`memory.rs:23-33`).
- RESETS 29-bit field with instant done-bit handshake over 12 modelled peripherals.
- Clock tree: XOSC, ROSC, PLL_SYS, PLL_USB, CLK_REF/CLK_SYS/CLK_PERI/CLK_USB/CLK_ADC/CLK_HSTX selectors, glitchless mux `SELECTED` handshake, PLL LOCK cycle-based timeout (`bus/clocks.rs`).
- Integer clock dividers (fractional parts stored inert).
- TICKS 1 µs fanout to TIMER0, TIMER1, RISCV MTIME, WATCHDOG (plus GPIO/PWM/CLOCKS counter domains).
- PPB: SCB, NVIC (52 external IRQs + SysTick + DWT CYCCNT), SCS — covered by `silicon_isr_diff` and `silicon_cycle_oracle`.
- QMI register bank + 16 KB XIP cache window mapping via `M0_RFMT`.

**Unit-tested / partial:**
- PLL lock *timing* (cycle-based lock-at) — modelled; not cross-checked against silicon lock times.
- SysTick autoreload + COUNTFLAG — correct per spec; no cross-core smoke test.
- MPU / SAU storage — §4.1 covers the enforcement gap.

**Stubbed:**
- APB arbitration collapsed to a flat read=3 / write=4 cycle latency (`bus/mod.rs:1154-1176`).
- Per-peripheral clock-gate enable bits in CLOCKS stored but not used to gate peripheral accesses.
- QMI direct-mode commands, cache invalidate, XIP streaming DREQs.
- BUSCTRL (BUS_PRIORITY) — not decoded.
- `HSTX` reset bit reserved; peripheral itself missing.
- UART1 / SPI1 / I2C1 / PIO1-2 RESET bits named; peripheral structs exist for PIO but not for the second UART/SPI/I2C instance.

**Missing:**
- **ACCESSCTRL** — not decoded at all. The RP2350 per-peripheral CPU-role / security-state access filter is absent. Firmware configuring ACCESSCTRL writes into the `HashMap<u32, u32>` fallthrough.
- **EPPB** (Extended PPB) — not on the address map.
- **PSRAM** aperture — QMI PSRAM window not modelled (blocks the PicoGUS-on-mdrp2040 equivalent that has been diagnosed in the journal).
- **Bank contention on RP2350** — deliberately omitted per `wrk_journals/2026.04.15 - JRN - Contention Modelling Declined.md`. Policy, not bug; flagged here for completeness.
- **Pacer wall-clock accounting** — `#[cfg(target_arch = "x86_64")]`-gated. Non-x86 hosts lose this.

### 4.4 Security, boot, RISC-V

**Verified:**
- `BXNS`, `SG`, banked register pairs for S/NS, IDAU region mapper (consumed by TT only), CPACR coprocessor gating, `DWT CYCCNT`.

**Unit-tested only:**
- MSR/MRS to banked SYSm (`0x88` = MSP_NS, `0x89` = PSP_NS, etc.).
- `TT` / `TTA` with SAU disabled — returns IDAU attribution only.

**Stubbed / advisory:**
- SAU regions are storage-only (no enforcement).
- MPU is TT-queryable but **never gates a bus access**. No XN enforcement, no privilege checks.
- AIRCR.BFHFNMINS, VTOR, CONTROL.SPSEL/NPRIV — register-level correct, not exhaustively tested against nested-preemption edges.
- `load_bootrom` loads a binary at `0x0` but does not execute bootrom. Post-boot state is hand-seeded (`lib.rs` reset path seeds RESETS + clock tree + SP/PC from vector table).

**Missing:**
- **RISC-V Hazard3**: zero code. Not scoped in V1 per `wrk_docs/2026.04.12 RP2350 Emulator HLD.md` §4, but the emulator's name does not qualify that. See §7.
- Signed-boot chain, dual-image A/B, rollback protection, OTP secure-boot fuse + public-key hash storage.
- SecureFault (#7), BLXNS, FNC_RETURN, NSC attribute.
- NSACR, CPPWR, CPACR_NS.
- ACCESSCTRL (covered from the bus side in §4.2 but the policy consequences are security).
- GLITCH_DETECTOR.
- Debug authentication (SBAC / REAUTH), SWD-side debug is external (`probe-rs`).

## 5. Pattern: "plumbed" ≠ "enforced"

SAU, MPU, ACCESSCTRL, per-peripheral clock-gate enables, BUSCTRL.BUS_PRIORITY, interpolator CTRL registers, DMA CRC sniffer, DMA byte-swap, DMA HIGH_PRIORITY: all storage-without-effect. **Firmware that uses these for correctness succeeds on our emulator and may fail on silicon — or vice versa.** This is a systematically worse failure mode than missing features, because missing features produce obvious symptoms (bus faults, wrong addresses), whereas plumbed-but-inert features produce silent wrong answers that escape any test that does not specifically measure the side effect.

This is the number-one concrete vulnerability in the current emulator.

## 6. Devil's-advocate findings (verified)

The devil's-advocate lens ran after the four research agents, with their outputs as input evidence. Its findings were then spot-checked by the author. Findings that survived:

1. **"Silicon-verified" is broad, not deep.** Fifty cases total across four oracles (§3). PIO scenarios exercise a handful of operating modes out of 4 SMs × 32 instruction slots × multiple configurations per block. TIMER has alarm-fire + clear. UART has TX + loopback. This is *sanity coverage*, not *behavioural coverage*. Any claim of the form "we are silicon-accurate for X" should be read as "we have 1–3 scenarios that pass for X."
2. **Cycle accuracy is structurally narrower than it looks.** The 9 cycle-oracle cases include constructs (`single_adds`, `back_to_back_alu`, `ldm_8_reg`) where the emulator's flat-cost model is correct by construction. The ~14 known systematic deltas catalogued in `tech_debt.md` (load-use, bank contention, backward-branch flush, PUSH floor) are **specifically not tested by the oracle**. The oracle therefore cannot fail on them. "Cycle-accurate" in marketing contexts should be tightened to "cycle-exact on steady-state ALU and branch sequences without bus contention."
3. **Interpolators verified as dead storage.** `sio/mod.rs:45`, `:148`. Three unit tests (`interp_register_round_trip`, `interp_per_core_isolation`, `interp_all_registers`) check only that `write(x); read() == x`. None exercise CTRL-driven result computation. Any pico-sdk firmware using interpolators for blending, clamping, or iterative DSP will produce wrong outputs, and the current oracles will not catch it.
4. **Boot ROM is not bootrom.** `load_bootrom` + the hand-seeded reset state in `lib.rs` is an emulation shortcut that is valid only for firmware that does not depend on ROM-side state. Real firmware that inspects USB BOOTSEL, performs signed-image verification, or reads OTP fuses is outside our envelope, and that is invisible from outside the crate.
5. **Boldest claim we should retract:** the *existence* of `crates/mdrp2350` implies RP2350 coverage, but it omits the RISC-V half of the dual-ISA story. Most stakeholders reading "mdrp2350 emulator" will assume Hazard3 is at least *started*. It is not.

Findings that did **not** survive verification (and are therefore withdrawn):

- **BASEPRI width claim.** The devil's advocate asserted BASEPRI stores 8 bits without the 3-bit mask on compare. Source says otherwise: `execute_thumb32.rs:932` masks on write, `exceptions.rs:515-517` masks to `0xE0` before priority compare. Architecturally correct. Withdrawn.

## 7. What we should do differently

Short and prioritised. These are strategy-level — the peripheral-fidelity HLDs already have the per-feature tactics.

1. **Rename or qualify.** `mdrp2350` is accurate for the Cortex-M33 path; it is misleading for the full chip. Either document front-and-centre ("Arm-only; Hazard3 RISC-V out of scope") or carve out a `mdrp2350-m33` / future `mdrp2350-hazard3` split. A one-paragraph caveat in `lib.rs`'s crate-level doc comment is a cheap first step.
2. **Fail-loud on inert registers, not silent.** Accesses to `ACCESSCTRL`, `OTP`, `GLITCH_DETECTOR`, `POWMAN`, `PSM`, `HSTX`, `TRNG`, `SHA256`, `TBMAN`, `CORESIGHT_TRACE` should trace-emit a `warn!` with address + PC the first time each is touched, not silently hit the HashMap fallthrough. This converts the "plumbed but inert" silent failure mode into a diagnosable one.
3. **Interpolator: model it, or mark it loud.** Firmware uses interpolators heavily in real workloads. Either implement CTRL-driven semantics (lane select, blend, shift, signed-saturation, pop-on-read) or raise a `warn!` when the CTRL registers are written.
4. **Oracles should test known-bad patterns, not only known-good ones.** Each item in `tech_debt.md`'s cycle-delta list should have a cycle-oracle case that currently *fails* with a recorded delta. That way a fix is easy to confirm and a regression is easy to catch. This inverts the current structure where `tech_debt.md` is a parallel document the oracle cannot observe.
5. **Bootrom stub note.** Add a one-line caveat to `load_bootrom` and to the workspace README: "Real silicon runs a signed bootrom that selects architecture (Arm/RISC-V), verifies images, and programs QSPI. This emulator skips that and begins execution at the reset vector of the provided image."
6. **Decide on RISC-V formally.** Either (a) declare permanent out-of-scope and state that the emulator is `mdrp2350-arm`, or (b) open a Phase-8 HLD for a minimal Hazard3 path that can execute a `blinky-riscv.elf` targeting RP2350's RISC-V mode. Silence is the worst option because it lets "RP2350 emulator" be over-interpreted.
7. **Per-peripheral verification depth metric.** For each verified peripheral, emit a coverage number: scenarios × registers exercised ÷ total register count. Treat anything under 20% as "sanity-only". This makes §4.3's partial-verified category self-documenting.

## 8. Risks the audit may still miss

- **Coverage-of-coverage.** We audited the emulator against the datasheet. We did not audit whether the *scenarios* test what they claim to test. A scenario named `pio0_side_set_toggle` could in principle exercise only a trivial subset; the `name` field is not enforced against the test body.
- **Undiscovered silent-wrong features.** Anywhere a register is stored and read back, firmware could be relying on side effects we haven't noticed. The interpolator example was found by an agent reading the struct definition. A systematic grep for `pub fn read.*=.*self\.` that returns only stored fields would turn up a list.
- **Dynamic-firmware blind spots.** All verification firmware is hand-written or SDK-example. We have not run any adversarial firmware (random-MMIO-walk, firmware that programs ACCESSCTRL, firmware that executes from XIP SRAM, etc.).
