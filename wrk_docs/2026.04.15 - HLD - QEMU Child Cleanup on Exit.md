# HLD — QEMU Child Cleanup on Exit

**Status:** **Signed off** by team lead, 2026-04-15. Agent A authored the draft; §10 captures the lead's review and the decisions that close out §9's open questions. Implementation may proceed against this HLD as-is.

## 1. Goal & non-goals

### Goal
Guarantee that the `qemu-system-arm` child spawned by `qemu_diff_m33` /
`qemu_diff_m0plus` is terminated on *every* exit path the parent can take,
so that bash-loop fuzz drivers never inherit a zombie QEMU holding GDB
port 3333/3334.

### Exit paths covered (commit)
1. Normal `main` return (Ok path).
2. `main` returns `Err` (propagated via the `?` chain).
3. Panic (workspace currently sets `panic = "abort"` in release — this
   **skips** Drop; addressed below).
4. `std::process::exit(1)` / `exit(2)` from the `fatal:` print-and-exit
   path and the fuzz-failure summary path (six call-sites; see §3).
5. User-typed Ctrl-C in the terminal hosting the oracle.
6. External `taskkill /F` / `TerminateProcess` of the oracle parent from
   another process (the overnight-run failure mode).

### Non-goals (concede)
- `kill -9 <oracle_parent_pid>` on **Linux**. SIGKILL is uncatchable by
  design; no userspace cleanup can run. On Linux we would additionally
  want `prctl(PR_SET_PDEATHSIG, SIGKILL)` in the *child* so the kernel
  reaps the child on parent death, but the harness is overwhelmingly
  Windows today, so this is tracked as §8 rollback-plus, not blocker.
- macOS. Not a current host.
- Cleanup of zombies **already present** at launch from a prior crashed
  run. That is Agent C's bash-side pre-batch port scrub territory.
- Double-booking the GDB port (multi-instance policy). Out of scope.

## 2. Current behaviour (verified)

### What fires today
`impl Drop for QemuProcess` at
`crates\mdpicoem-harness\src\gdb_client.rs:157–162` calls
`self.child.kill()` and `self.child.wait()`. This runs on:
- Normal return from `main` (the `_qemu` / `qemu` binding goes out of scope).
- Any `?`-propagated error that unwinds back to `main`.
- Panic **only** when `panic = "unwind"` — which is **not** our current
  profile.

### What doesn't
- **Panic-abort.** `Cargo.toml:22-25` sets `panic = "abort"` on the
  release profile. A panic in the hot path — for example, a malformed
  GDB reply tripping one of the `unwrap()`s in `gdb_client.rs` — skips
  Drop entirely. The workspace keeps `panic = "abort"` for code-size /
  codegen benefits on the emulator crates; flipping it globally would
  affect every release binary and is a bigger decision than this HLD.
- **`std::process::exit(_)`.** Six call-sites do not unwind:
  `qemu_diff_m33.rs:35` (fatal), `:187` (targeted-suite failure),
  `:281` (fuzz summary failure), and the symmetric trio in
  `qemu_diff_m0plus.rs:42`, `:164`, `:234`. All six skip Drop.
- **Windows Ctrl-C.** The default console handler calls `ExitProcess`,
  which also skips Drop.
- **External `TerminateProcess`.** Defender briefly locking the `.exe`
  before launch reported as `rc=127`; external `taskkill /F` from a
  sibling agent; WMI-initiated kill; all of these bypass userspace
  entirely.

### What got us overnight
Path (4)/(6) was the actual failure chain from the 2026-04-14 campaign
(see journal, 23:39 entry and onwards): Defender-triggered abnormal exit
of the oracle → zombie QEMU on 3334 → bash loop re-launches oracle →
new oracle connects to the zombie → 10060 timeout → oracle dies →
loop. By 00:01 three zombies were bound to 3334, every Windows cleanup
tool (taskkill, Stop-Process, `kill -9 <WINPID>`) hung, and M0+
contributed nothing material for the next 7 hours.

## 3. Alternatives considered

### A. Ctrl-C handler + refactor main to ExitCode
Add the `ctrlc` crate and replace all `std::process::exit(_)` with
`return ExitCode::from(N)` out of `fn main() -> ExitCode`. Ctrl-C
handler drops the `QemuProcess`; the rest of the exit paths unwind.
Covers paths (1)–(5). Does **not** cover (6) — external
`TerminateProcess` still bypasses userspace. Cheapest to land; leaves
the actual overnight failure mode wide open.

### B. Windows Job Object (kernel-enforced parent→child lifetime)
Create a Job Object at parent startup with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`,
assign the spawned QEMU to it. When the parent handle to the Job closes —
**for any reason, including `TerminateProcess` from outside** — the
kernel tears down every process in the Job. This is the only mechanism
that covers path (6). Needs a handful of `windows-sys` calls
(`CreateJobObjectW`, `SetInformationJobObject`,
`AssignProcessToJobObject`). Cost: one new dep (already in the tree
transitively; adding a direct dep is cheap), ~40 lines of unsafe code,
gated on `#[cfg(windows)]`.

### C. Bash-side pre-batch port scrub
Before launching each batch, the driver script probes 3333/3334 with
`netstat -ano` and kills anything bound. Belt-and-braces, catches
zombies from prior crashes, and makes the bash loop self-healing.
Excellent defence in depth but **does not belong in this HLD** — it's
Agent C's territory. Noted here so the team lead can confirm the two
HLDs stack: Job Object prevents zombies from being created, bash scrub
cleans up any that slip through (e.g. parent killed via `kill -9` on
Linux, which Job Objects don't help with).

### D. Do nothing; rely entirely on bash scrub
Zero Rust changes, hand the whole problem to Agent C. Lowest code
churn, but leaves the Rust binaries permanently fragile: any future
harness consumer outside the bash drivers (ad-hoc run, CI, IDE green
button) has no protection. The Rust binaries should be well-behaved
citizens on their own.

## 4. Chosen approach

**Combine B (Job Object on Windows) with a light version of A for the
in-process paths.** Concretely:

1. **Windows Job Object** assigned to the spawned QEMU at the end of
   `QemuProcess::spawn_with`. The parent holds the Job handle in the
   `QemuProcess` struct. When the Job handle closes — Drop, panic-unwind,
   **or the parent process dies abnormally** — the kernel kills every
   process in the Job. This is the one mechanism that covers the actual
   overnight failure (Defender-induced abnormal exit of the parent).
2. **`fn main() -> ExitCode`** refactor for both binaries; replace
   `std::process::exit(_)` with `return ExitCode::from(_)`. Ensures
   normal and error-path termination unwind through `QemuProcess`'s
   Drop, so Drop still does the cooperative `child.kill()` for logging /
   fast path (and so the Linux case has at least this much).
3. **Ctrl-C handler** via `ctrlc::set_handler` in both binaries. The
   handler flips an `AtomicBool` and lets the main loop notice and exit
   via its normal `return ExitCode::from(130)` path. *Does not* call
   `process::exit` directly — that would re-skip Drop.
4. **Panic-abort retained.** We don't change the workspace profile. The
   Job Object catches panic-abort the same way it catches
   `TerminateProcess`: the parent dies, the Job handle closes, the kernel
   kills QEMU. No behavioural regression from keeping abort.

Rationale: the overnight failure was path (6), which only B covers. A
alone is insufficient. The in-process refactor is cheap and makes
Drop-based cleanup the primary path under normal operation with the Job
Object as the safety net. Total new direct dep surface: `windows-sys`
(already transitively present) + `ctrlc` (new).

### Shapes

```rust
// gdb_client.rs — additions sketched, not full code
#[cfg(windows)]
struct JobHandle(windows_sys::Win32::Foundation::HANDLE);
#[cfg(windows)]
impl Drop for JobHandle {
    fn drop(&mut self) {
        // CloseHandle — releasing the last handle to a
        // JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE Job kills every process in it.
        unsafe { windows_sys::Win32::Foundation::CloseHandle(self.0); }
    }
}

pub struct QemuProcess {
    child: Child,
    profile: QemuProfile,
    #[cfg(windows)]
    _job: Option<JobHandle>,   // underscore: existence matters, not direct use
}
```

`spawn_with` post-spawn sequence (Windows):
1. `CreateJobObjectW(NULL, NULL)` → job handle.
2. `SetInformationJobObject(job, JobObjectExtendedLimitInformation, &LimitFlags { LimitFlags: JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, .. })`.
3. `AssignProcessToJobObject(job, OpenProcess(PROCESS_SET_QUOTA | PROCESS_TERMINATE, FALSE, child.id()))`.
4. Store the job handle in the struct; `CloseHandle` runs on Drop.

On non-Windows the struct field is absent and the whole code path is
`#[cfg(windows)]`-gated. Drop semantics unchanged on Linux.

### Ctrl-C handler pattern

```rust
// in each binary main
static SHUTDOWN: AtomicBool = AtomicBool::new(false);
let _ = ctrlc::set_handler(|| SHUTDOWN.store(true, Ordering::SeqCst));

// run() checks SHUTDOWN at loop boundaries (between fuzz tests) and
// returns Err("interrupted") or a sentinel ExitCode::from(130).
```

The handler only flips a flag — it never calls `process::exit`. The
main loop polls the flag between tests (existing `done % 1000 == 0`
cadence is a natural checkpoint). On observed flag, `run()` returns
cleanly, Drop fires on `QemuProcess`, Job closes, QEMU dies — same path
as a normal exit.

### Exit-site refactor (all six)

Before:
```rust
if fail > 0 { std::process::exit(1); }
Ok(())
```

After:
```rust
if fail > 0 { return Ok(ExitCode::from(1)); }
Ok(ExitCode::SUCCESS)
```

And in `main`:
```rust
fn main() -> ExitCode {
    match run() {
        Ok(code) => code,
        Err(e) => { eprintln!("fatal: {e}"); ExitCode::from(2) }
    }
}
```

`run()`'s signature changes from `Result<(), Box<dyn Error>>` to
`Result<ExitCode, Box<dyn Error>>`. The change is mechanical.

## 6. Testing

Three layers.

### L1 — Drop/unwind path (unit test)
Test `QemuProcess::spawn_with` → grab `child.id()` → drop the
`QemuProcess`. Assert (via `ps` / `OpenProcess` on Windows) that the
PID is gone within, say, 500 ms. Doesn't touch QEMU specifically; any
long-lived child program works. Covers paths (1)/(2)/(3-with-unwind).

### L2 — Job Object enforcement (integration test, Windows-only)
New test binary under `crates\mdpicoem-harness\tests\` (or as a
`#[cfg(all(test, windows))]` test in a new module):

1. Spawn a stand-in child via `QemuProcess`-like glue (could be
   `timeout /t 60 >NUL` — pick any quiet long-running .exe).
2. Record the child PID.
3. **Kill the test process's own parent** — actually impossible from
   within; instead fork a helper: launch a small Rust binary that
   does the spawn, prints the child PID to stdout, then exits via
   `TerminateProcess` on its own handle (or `ExitProcess(1)`, skipping
   Drop). The test harness reads the PID from stdout.
4. Assert the child PID disappears within 1 s after the helper exits.

This is the critical test — it's the only one that directly
demonstrates the failure mode from the overnight campaign is fixed.

### L3 — Socket leak regression (integration, Windows-only)
Launch `qemu_diff_m33 --fuzz 1` in a helper, kill it externally via
`TerminateProcess`, then immediately attempt to `TcpListener::bind` on
`127.0.0.1:3333`. If the bind succeeds, the port is free → no zombie.
Repeat for `qemu_diff_m0plus` on 3334. Should run as a smoke test in
CI on Windows hosts; skip on Linux.

### What we can't easily unit-test
- Linux `kill -9` of the parent — by design no userspace runs; we
  concede and document.
- Ctrl-C specifically (as opposed to the `AtomicBool` it sets). The
  `ctrlc` crate has its own tests; we trust them. Manual verification
  once during implementation is enough.

## 7. Acceptance criteria

After merge, the following must hold on a Windows 11 host:

1. `qemu_diff_m33 --fuzz 1` under a failing seed exits with rc=1, and
   `netstat -ano | grep :3333` shows no listener owned by any
   `qemu-system-arm.exe`.
2. Ctrl-C during a `--fuzz 100000` run exits with rc=130 within 2 s and
   leaves 3333 free.
3. From a sibling shell, `taskkill /F /PID <oracle_pid>` while
   `qemu_diff_m33 --fuzz 100000` is running. Within 2 s, 3333 is free
   and no `qemu-system-arm.exe` owned by the dead oracle's session
   remains. **This is the overnight-regression test.**
4. Same three checks with `qemu_diff_m0plus` on 3334.
5. `cargo build --workspace --release` clean with no new warnings.
6. `cargo test -p mdpicoem-harness` passes, including the new L1/L2/L3
   tests (L2/L3 gated `#[cfg(windows)]`).

On a Linux host, (1) and (2) must still hold. (3) will not — documented
as a known gap, pending a follow-up that adds
`prctl(PR_SET_PDEATHSIG, SIGKILL)` in the child's pre-exec hook.

## 8. Risks & rollback

### Risk: Job Object on nested-job hosts (WSL, Docker, CI)
Prior to Windows 8, a process could only be in one Job at a time. Since
Windows 8 nested Jobs are supported and the kill-on-close behaviour
propagates through the nest. Windows 11 is fine. Docker Desktop on
Windows runs Linux containers; the Rust harness isn't run inside those.
WSL is Linux userspace; the `#[cfg(windows)]` guard skips the Job path
entirely there. CI runners (GitHub Actions `windows-latest`) are
Windows Server 2022 — Job Object support verified by `windows-sys`
tests. Low risk.

### Risk: `windows-sys` feature bloat
The three Win32 namespaces we need (`Win32_System_JobObjects`,
`Win32_System_Threading`, `Win32_Foundation`) are small and already
pulled in transitively via probe-rs. Direct dep adds zero build time.

### Risk: `ctrlc` crate behaviour
`ctrlc` is small (3.4k stars, widely used), pure-Rust, single-function
API. Alternative would be hand-rolling `SetConsoleCtrlHandler` on
Windows + `signal-hook` on Linux; not worth it. If `ctrlc` is
unacceptable to Arthur, drop it and accept that Ctrl-C on Windows
skips Drop but the Job Object still catches QEMU.

### Risk: Drop ordering with other resources
`QemuProcess` is the only resource of note in the two binaries. The
`GdbClient` holds a `TcpStream` which closes on its own Drop; that
fires before `QemuProcess`'s Drop (reverse declaration order). Closing
the GDB socket before killing QEMU is the correct order (QEMU logs a
clean disconnect instead of a broken pipe).

### Rollback plan
If the Job Object path turns out to break in an environment we care
about:
1. Revert the `gdb_client.rs` job-handle additions — one commit, one
   struct field, gated on `#[cfg(windows)]`.
2. Keep the `ExitCode` refactor and `ctrlc` handler — those are
   independently useful and cover paths (1)–(5) even without Jobs.
3. Fall back to defence in depth via Agent C's bash-side port scrub for
   the external-kill case.

Worst case: we regress to the pre-change state on path (6) only, which
is exactly the overnight behaviour. No new failure mode introduced by
the rollback.

### Risk: Agent C's bash scrub conflict
If both this HLD and Agent C's bash scrub land, pre-batch scrub sees no
zombies to clean (because this HLD prevented them being created). No
conflict; Agent C's HLD becomes a defence-in-depth layer for the
conceded cases (Linux `kill -9`, legacy Windows hosts without nested
Jobs). The two HLDs stack cleanly.

### Decisions on §9 open questions

1. **`ctrlc` crate — accepted.** Standard kit, ~200 LOC pure-Rust, wide
   adoption. Hand-rolled `SetConsoleCtrlHandler` + `signal-hook` would
   save one dep but burn implementation time we'd rather spend on the
   Job Object work. Add `ctrlc = "3"` as a regular direct dep.
2. **Job Object scope — `QemuProcess` only.** All current and planned
   QEMU spawns flow through `QemuProcess::spawn_with`; wrapping at that
   seam transparently covers every future consumer. No separate audit
   needed. Silicon/probe runners do not spawn QEMU — out of scope.
3. **L2 helper-binary test pattern — accepted.** The helper-process
   dance is the only way to deterministically exercise "parent dies
   without Drop running"; `ExitProcess` on self is clean and doesn't
   require synthesising an external `TerminateProcess`. Land both L2
   *and* L3 — they test different guarantees (Job kernel enforcement
   vs socket-level observable state).

### Clarifications for implementation

- **Field declaration order in `QemuProcess`.** Rust drops struct
  fields in source-declaration order *after* the explicit `Drop::drop`
  returns. Declare the new `_job: Option<JobHandle>` field **last** in
  the struct so it drops after `child: Child`. Result: the existing
  `Drop::drop` calls `self.child.kill()`+`wait()` cooperatively first,
  then fields drop in order (child → job handle), and QEMU is already
  gone by the time the Job handle closes. In the abnormal-exit case
  (panic-abort, external `TerminateProcess`, `rc=127`), the explicit
  Drop never runs — the Job handle closes as part of kernel cleanup,
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` fires, QEMU dies. Both paths
  converge on a dead QEMU with no race.
- **Keep `child.kill()` in `Drop`.** The Job Object is the safety net;
  the explicit kill in Drop remains the cooperative fast path so QEMU
  gets a `TerminateProcess` immediately on normal drop rather than
  waiting on Job-handle close semantics. Do not remove it during the
  refactor.
- **Ctrl-C polling cadence.** Poll `SHUTDOWN` at the existing
  `done % 1000 == 0` heartbeat *and* inside `run_with_recovery` before
  each iteration — <1 s latency to user Ctrl-C under fuzz load. Don't
  poll per-GDB-packet; that would add overhead to the hot path.
- **`windows-sys` version — pin to the workspace's transitively-used
  major.** Run `cargo tree -p mdpicoem-harness` before adding the
  direct dep to pick the version already in the tree; avoid pulling
  a second copy. Features needed: `Win32_System_JobObjects`,
  `Win32_System_Threading`, `Win32_Foundation`.
- **Drop-order sanity unit test.** Add a tiny `#[test]` that
  constructs a `QemuProcess` with a no-op child (e.g. `timeout` /
  `ping -n 60 127.0.0.1`), drops it, and asserts the child PID is
  gone within 500 ms. Catches accidental field-reorder regressions.
