# 2026.04.29 — Testing Audit and Risk Review

**Authors:** Claude Opus 4.7 agent team (4 reviewers + devil's advocate)
**Scope:** Whole-workspace testing review for `mdpicoem` post-Phase-7 / post-restructure
**Date:** 2026-04-29

---

## Executive summary

The testing apparatus is **layered, principled, and aesthetically impressive**, with a real differential-oracle pyramid (unit → firmware-integration → QEMU/spike → silicon) and one consumer-shaped quality target (PicoGUS / "does Monkey Island sound right"). It is also showing signs of **diminishing returns and inverted priorities**: oracle theatre on cold paths (single-cycle PendSV deltas), under-attention on hot user-facing paths (PSRAM+Threaded incompatibility, RP2040 NVIC plumbing that ships ahead of its oracle), a "fuzz 100k" headline that covers ~10 hand-curated T32 cases on M0+, and a 91 → 98 % coverage push consuming agent-cycles that produced "+11,528 lines, overwhelmingly test code; zero production-code logic changes" on 2026-04-29 alone.

The most valuable critique below is the **devil's advocate** §6: the ratio of meta-work to material has flipped, and the cheapest oracle (QEMU) is the one with the most known caveats while the most expensive oracle (silicon) runs the least. Read that section before the recommendations.

## 2. Architecture review

### 2.1 Oracle quality
- **`qemu_diff_m0plus` Thumb-32 filter** was rewritten on 2026-04-29 to admit BL/MRS/MSR/DSB/DMB/ISB. **It has never been run end-to-end** — QEMU isn't installed on the WSL host (Stage D blocked, per the day's journal). The implementation is committed; the differential signal it claims to produce has never been observed.
- The relaxed filter wasn't paired with a corpus generator: `run_fuzz` still uses M33-only T32 buckets that the M0+ filter rejects. The "100 000-iteration" run actually exercises **10 hand-curated T32 cases**, the same 10, repeated. (See §6 critique 4.)
- Tech-debt deletion (Stage E) was correctly *not* performed — the oracle isn't validated yet.

### 2.2 Robustness — masking is principled, not papering
`crates/mdpicoem-harness/src/lib.rs:378–386` defines a small fixed mask palette (`MASK_ALL_FLAGS`, `MASK_NZ_ONLY`, `MASK_NO_FLAGS`, `MASK_ALL_FLAGS_GE`, `MASK_Q_ONLY`). Per-`TestCase` declaration, ~30 sites. **Not a skip-list, not a per-seed allowlist** — an architectural-class bitmask. Healthy. The M0+ filter (`is_m0plus_safe:338-341`) rejects masks outside `{0, ALL, NZ}` rather than silently passing through, so it can't accidentally hide M33-only flag diffs.

The fragility is the `silicon_isr_diff_rp2350` 6-cycle "EMU overcounts" delta (`tech_debt.md:652+`) — logged but unowned, and the test goes green on state match. That's a **non-actionable known divergence**.

### 2.3 Layering — sound, with one inversion
Pyramid is healthy: in-crate ISA tests → firmware-smoke `tests/hello_*.rs` (boot real `roms/rp2350/*.bin`, assert observable side-effects) → QEMU/spike → silicon. The **inversion**: `silicon_isr_diff_rp2040` is a silicon-tier oracle for behaviour with no unit-tier coverage. Testing from the top of the pyramid because the bottom isn't built.

### 2.4 Reproducibility
- QEMU/RISC-V oracles preserve seeds and print exact reproduce commands. Excellent.
- Silicon oracles **cannot** be reproduced byte-for-byte (PLL lock jitter, ROSC, real interrupts).
- `test_silicon --soak --seed N` does Fisher-Yates on case order; iteration order is reproducible, per-case state isn't.
- Probe attach errors auto-retry, which papers over deterministic failures as flakes. **No "this case failed N consecutive times" gate.**

### 2.5 Threaded runtime tests
`dual_model.rs` enforces the HLD V1 §7.1 contract: end-state equality only, never per-instruction interleave. Tests are honest about it (`pio_sm_state_coherent_after_concurrent_step` and `cross_core_irq_routes_on_fifo_push` carry explicit `TODO("stage-4")` markers). Mid-quantum partial state is **untestable by construction** (placeholder pattern, ~1287 call-sites to migrate). Watchdog timeout attribution is broken (`tech_debt.md:31-36`, `which` hardcoded). Panic containment is solid (`tests/execution_model.rs:85`).

### 2.6 Performance regression detection — the weakest dimension
`paced_bench_rp2350.rs:1098–1117` hardcodes a `<33 host-cycles/emu-cycle` budget for `basic`/`fpu-heavy` only; other workloads emit informational numbers. **No `bench-results/`, no baseline file, no CI history.** Humans eyeball journal entries. For a perf-sensitive emulator this is the weakest dimension; small regressions absolutely will go unnoticed.

## 3. Risk register — where bugs lurk

Top 8, prioritized by Likelihood × Impact:

### 3.1 Cortex-M33 Thumb-32 executor — opaque coverage of FPU/parallel/saturating classes
`crates/mdrp2350/src/core/execute_thumb32.rs` is **2,105 LoC across 11 functions** (~190 LoC/fn — giant match arms). The QEMU oracle has only three classes (`base_alu`, `base_mem`, `fpu`); rare families (`SMUAD`, `SMLAD`, `SMUSD`, `USAD8`, `SMMUL`, parallel-add, bitfield, saturating, divide) get fuzzed in proportion to encoder calls — single calls each vs. dozens of `dp_mod_imm` permutations. Highest-density "looks right, wrong flag" surface in the codebase. **L: High × I: High.**

### 3.2 FPU/VFPv5 — denormal/NaN/AHP, `f32_to_iN_rmode` rounding
FPSCR.AHP not honoured (`tech_debt.md:1603-1616`, TODOs at `execute_fpu.rs:1414, :1465`). `f32_to_i32_rmode` uses Rust's `round_ties_even`/`floor`/etc. directly — these don't precisely match ARM's "Invalid Operation when result doesn't fit" saturation behaviour for ±Inf/NaN. NaN canonicalisation chains in `fp_add`/`fp_mul`/`fp_msc` (lines 482–540) have a documented priority (`SNaN > QNaN > default`); no oracle has been confirmed to walk an SNaN×QNaN×denormal cross-product. `softfloat_diff` exists but isn't wired into `qemu_diff_m33`. **L: High × I: Med.**

### 3.3 Exception entry/exit — TrustZone S-bit FIXME, banked-SP discipline
`tech_debt.md:615-639` is unambiguous: "Exception entry/exit not differentially validated." The FIXME at `crates/mdrp2350/src/core/exceptions.rs:197` confirms NS exceptions claim Secure return — every NS-side handler is wrong today. The recently-fixed banked-SP staleness bug (CLAUDE.md #10) implies `sync_sp_to_banked`/`sync_sp_from_banked` aren't enforced by the type system; by-convention only. RP2040 sibling has **zero passing oracle** — `silicon_isr_diff_rp2040` will FAIL until plumbing lands. **L: High × I: High.**

### 3.4 DMA — IRQ_QUIET interaction, IRQ2/IRQ3 storage-only
`crates/mdrp2350/src/dma.rs` is 1,852 LoC / 60 functions. `CHAIN_TO != self` guard (`:712`) is correct, but a CHAIN-A→B-with-CHAIN-B→A pair would re-enter `tick` with no loop guard. **IRQ2/IRQ3 are storage-only** (`:447, :871`) — firmware using INTE2/INTE3 silently never gets IRQs. Silicon-tested via two scenarios (`dma_chain_trigger`, `dma_timer_paced`). **L: Med × I: High.**

### 3.5 Internal PIO simulator — not differentially tested against `epio-sys`
`crates/mdpicoem-common/src/pio/sm.rs` (2,383 LoC) + `mod.rs` (3,297 LoC). `onerom_pio_diff_rp2350` is a **trace-replay test** (reads a static `onerom_2364.trace`), not differential. Header explicitly says "Zero C dependencies — the trace file is the only interface to epio." So the only PIO scenario ever differentially validated against the C reference is the OneROM ROM-emulator program. No fuzzed pin patterns, no random-program PIO fuzz, no side-set/wrap/autopull cross-product. **5,680 LoC vs 41 unit tests across both chips. Biggest LoC-to-test ratio in the workspace.** **L: Med × I: High.**

### 3.6 Threaded runtime — barrier deadline misattribution + dead spin-path watchdog
`tech_debt.md:1-46` lists four open issues. `WATCHDOG_STRIDE=1024 > SPIN_BUDGET=512` — spin-path watchdog never triggers (dead code). `BarrierTimeout.which` hardcoded to `WorkerName::Coord`. Watchdog deadline is a flat 5 s ignoring the HLD's quantum-scaled formula — a low-clock-rate config misfires before completing one quantum. Coordinator only ticks TIMER (`:131-150`) — UART/SPI/I2C/ADC/PWM/DMA quietly diverge in Threaded mode. PSRAM not modelled (`:107-128`). **L: Med × I: High.**

### 3.7 Bus / clock tree
`crates/mdrp2350/src/bus/clocks.rs` is **11 lines** — a stub forwarding to `mdpicoem-common`. mdrp2040 has its own 792-LoC version. `pll_sys_freq_hz` (`common/clocks.rs:79`) gates `fbdiv == 0` correctly but doesn't visibly check `postdiv1`/`postdiv2` for zero. No "two cores mutating CLOCKS simultaneously" stress; in Threaded both cores might write `CLK_SYS_CTRL` in the same quantum. **L: Med × I: Med.**

### 3.8 Test-only feature flag drift
`testing` feature widens API surface (`inject_panic_for_testing`, `PioCommand::TestPanic`). CI compiles two ABI variants. Risk pattern: someone adds `#[cfg(feature = "testing")]` early-return on a hot path → tests pass, production fails. Low likelihood today (only 4 sites), but the surface only grows. **L: Low × I: Med.**

**Honourable mentions.** Hazard3 is by ratio the **best-tested core path** in the workspace (5,545 LoC tests for 4,617 LoC implementation), so don't worry there. PicoGUS is Serial-only by hard requirement; a future Threaded variant would silently get zero-MISO output. The vendored `probe-rs-0.31.0-mdrp-patched/` fork is a single-maintainer dependency that risks breaking on every probe-rs bump.

## 4. Devil's advocate dissent

> The other reviewers are listing what's missing inside a frame the team has chosen. Step out of the frame.

### 4.1 The oracles are not as independent as the topology slide suggests
The cheap oracle (`qemu_diff_m0plus`) pins to QEMU 10.2's `cortex-m0` because `cortex-m0plus` doesn't exist (`tech_debt.md:552`). It does not compare cycle counts. For M33 the team *suspects* QEMU's NVIC/SCB is "less mature" (`tech_debt.md:640`). The cheap oracle is two-thirds of an oracle on the wrong CPU, and you already suspect it can't witness the things that matter most.

The expensive oracle (real RP2354 silicon) catches the most bugs, runs the least often, requires hardware no CI machine has, and depends on a vendored `probe-rs` fork carrying a patch upstream hasn't merged in a year. **The oracle of record is now a single-maintainer fork.**

`silicon_isr_diff_rp2040` ships with every scenario documented to FAIL. **An oracle whose negative results are routinely ignored is not an oracle; it is decoration.**

### 4.2 Cycle accuracy is craft pride, not a requirement
`silicon_cycle_oracle_rp2350`, `silicon_dualcore_diff_rp2350`, K=101/K=201 K-delta protocols, per-core CYCCNT smoke binaries, bank-contention silicon characterisation, "EMU+3 residual cycle delta" triage on `isr_pendsv_cold` (`tech_debt.md:658`).

Then `tech_debt.md:582` quietly admits: **`MULS=1` cycle on RP2040 is a hardcoded number with no silicon calibration**, consumed as ground truth by the TUI. The RP2040 bank-contention model is "deprecated-in-place" because the wall-clock perf gap is 10×.

**Who consumes single-cycle accuracy?** No harness, app, or external user does. The PicoGUS oracle ("does Monkey Island sound right") is the only consumer-shaped quality target in the workspace. The cycle oracles measure themselves and report deltas to no downstream system that will fail.

### 4.3 The threaded runtime's correctness is *defined* as "equals serial"
"Oracles validate Serial. QEMU diff, probe diff, silicon cycle/periph/isr/dualcore — all run Serial." This is a circular safety net. Threaded is correct iff it equals Serial. Therefore threaded **cannot ever surface a real concurrency bug** that doesn't manifest in serial — because that bug would be marked as a threaded-side regression and "fixed" back to serial parity. The actual hazards (memory ordering, lost wakeups, racy mid-quantum publication) are exactly the ones serial cannot exhibit. PSRAM-MISO at `tech_debt.md:91` is the canary: harnesses must build with `Serial`. The mitigation for known threaded incorrectness is *avoid the threaded path*. Where else is this true and not yet noticed?

### 4.4 "100k iterations" is rounding error
M33 Thumb-32 is 2³² encodings. `--fuzz 100000` covers ~0.0001 % of the space, before register/memory state. After the M0+ filter relaxation, the corpus is **"410 total, 400 Thumb-16, 10 Thumb-32"** — the celebrated `--fuzz 100000` run hits **10 hand-curated T32 cases, the same 10, repeated**. The 91.42 % branch coverage measures the residue of a known-shape corpus, not the unknown.

### 4.5 The test suite is becoming the building, not the scaffolding
The 2026-04-29 final report adds **+11,528 lines, overwhelmingly test code; zero production-code logic changes**. 720 tests, 8 stages, three deferred plans for stages 6a-6f, all to chase a self-assigned coverage goal not requested by any user. The Mutation Testing V1 work runs supervisor + 3-agent loop per stage for two config files and a sweep run. **The ratio of meta-work to material has flipped. This is process performing competence.**

### 4.6 What a real RP2354 user would trip over
Not a wrong cycle delta on PendSV. They would write firmware with `__wfe()` and discover the M0+ wake path was wired three days ago, or hit a silently-FAIL'd ISR scenario on RP2040 because the IRQ plumbing landed but the oracle still reports red, or build with PSRAM+threading because the docs don't shout the incompatibility hard enough. **None of these end-user hazards are caught by the cycle oracles, the coverage push, or the mutation sweep.** They are caught by the journals — by humans reading prose.

## 5. Recommendations (prioritized)

The combined picture suggests cutting low-yield work and reallocating to user-facing quality. Order matters: do (1) and (2) before chasing more coverage points.

### Stop / shrink
1. **Halt the 91 → 98 % coverage push** until §3 hot risks (Thumb-32 encoder weighting, FPU NaN/AHP cross-product, exception entry/exit oracle) are addressed. Coverage residue is the wrong currency right now.
2. **Don't extend per-stage triple-agent supervisor loops** to small-scope work (config files, single-paragraph HLD revisions). The DA-on-every-stage cadence is theatre on routine work.

### Fix / land
3. **RP2040 NVIC + `tick_peripherals` + pending-exception dispatch** so `silicon_isr_diff_rp2040` stops being decoration. This is the most material gap — Phase-1 exit criterion is currently fictional.
4. **Validate the relaxed M0+ T32 filter** (Stage D of today's journal): get QEMU installed and run the oracle end-to-end. Either it works, or it doesn't — until then the journal claim is unbacked.
5. **Build a real M0+ T32 corpus generator** (target: 1k+ encodings across BL/MRS/MSR/barrier with diverse register state) so `--fuzz 100k` actually fuzzes. The current 10-case curated set is unit-test-grade.

### Add
6. **Wire `softfloat_diff` into `qemu_diff_m33`** (or an FPU-specific differential) with NaN×denormal×AHP cross-product cases. FPU is Risk #2 and unverified at the bit level.
7. **PIO differential against `epio-sys` at runtime**, not via static trace replay. `epio-sys` is already in the workspace; build a thin shim and fuzz random PIO programs across both. This is the largest unverified subsystem by LoC.
8. **Performance baseline DB**: `bench-results/<bin>/<workload>/baseline.json` checked into the repo, with a `paced_bench_*` mode that compares against baseline and exits non-zero on regression > X %. Otherwise perf regressions land silently.
9. **A "real-firmware sound right" oracle for non-PicoGUS targets.** PicoGUS proved the model works. Adopt it for at least one RP2350 user-facing target (LCD demo? blinky timing?) — a consumer-shaped pass/fail beats a thousand cycle deltas.

### Watch
10. **`probe-rs` fork drift**: schedule a quarterly upstream-rebase or budget for the maintenance cost of permanent divergence. Currently the silicon-oracle line of defence depends on it.
11. **Threaded runtime concurrency oracles**: the parity-with-serial check by construction cannot find the bugs the threaded mode exists to enable. Consider deterministic-schedule fuzzing (preempt at every memory op via something like loom) for the SpscQueue / SpinBarrier hot loops, even if only as a one-off audit.

### Question (open)
12. **What is the real customer for cycle accuracy?** If the answer is "no external consumer; internal craft goal", be honest about it and re-budget. The cycle oracle apparatus is excellent engineering; the question is whether it's the highest-value use of further engineering.

## 6. Tensions and open questions

The agents disagreed in two places worth flagging rather than smoothing over:

- The architecture reviewer scored masking discipline as **principled and not papering over bugs**. The devil's advocate scored the silicon-ISR 6-cycle drift and the whole oracle topology as **routine ignored negatives**. Both are right at different scales: the per-mask palette is sound; the per-oracle "log delta and move on" pattern at the ISR level is not. Resolve by either owning the 6-cycle drift (file an issue, fix or document why it's irreducible) or removing the assertion.
- The coverage agent flagged the RP2040 NVIC gap as the most critical. The risk auditor put Thumb-32 / FPU / exceptions ahead. Both should be done; (3.3 RP2040 exceptions) and (5.3 NVIC plumbing) are the **same gap** seen from the test side and the production side. Land them together.

What we may still be missing:
- An actual customer / consumer of the emulator's outputs other than the team itself. Without that, "quality" floats free.
- Any evidence that the threaded runtime's bugs (which by §4.3 cannot be caught by the parity tests) have shown up in practice — or any evidence they haven't.
- A retro on whether the per-stage DA cadence actually changed outcomes vs. a single end-of-work review. If it didn't, that's process to retire.

1. **"The relaxed M0+ T32 filter has never been run end-to-end" — false by mid-day.**

2. **"Fuzz 100k is rounding error" — true literally, misleading in context.**
   The fixed-corpus number is small, but the workspace has **multi-day campaign infrastructure** I underweighted:
   - **Overnight 04-25 / 04-26:** ~12.3M QEMU M33 cases, ~11M projected M0+ cases, **0 emulator divergences** (`wrk_journals/2026.04.25 - JRN - Overnight Fuzz Supervisor.md`).

3. **"Tests are becoming the building" — partial overreach.**
   The +11,528-line residue-test push *was* coverage-for-coverage — that critique stands. But the V2 mutation runner is exactly the kind of work the user's quality philosophy endorses ("Testing oracles encode 'what correct looks like' in a form machines can check at scale. They are the critical multiplier"). It produced a **falsifying measurement** about oracle quality that the residue tests could never have. Lumping the two together was unfair to V2.

**This is the most important finding of the day:** the team's own published oracle-coverage claims (V1 triage HLD §3.1–§3.2) declared SIMD parallel-add/sub *and* FP16 conversion oracle-covered after reading the harness sources. Subjected to mutation, **19 SIMD parallel mutants and 37 FP16 mutants survived**. The team has been systematically over-confident about what its corpus reaches. This is the V1 → V2 hypothesis falsification, on paper.

**Two genuine production bugs surfaced by the V2 baseline run** and are *not* yet fixed:
- `crates/mdrp2350/src/core/execute_thumb32.rs:349` — BFC width=32 does `1u32 << 32`, UB in Rust. Test `bfc_full_width_clears_word` was skipped to unblock the cargo-mutants baseline.
- `crates/mdrp2350/src/bus/mod.rs:2123` — coresight PPB read16 panics with "use bus_read16 wrapper" when the test exercises that exact path. Test `coresight_trace_halfword_read_dispatches_through_byte_path` was skipped.
Both are real Bucket-1 finds (test catches a production bug, the bug isn't fixed). Currently in `tech_debt.md` § "Residue-test failures discovered by V2 mutation sweep". **Fixing these should be ahead of any further coverage-chasing.**

**The oracle-routing artefact is measured.** Routing `execute_fpu.rs` to `softfloat_diff` is structurally insufficient: softfloat exercises IEEE-754 helpers directly with `f32` operands, never running actual VFP instructions, so the encoding-helper mutations (`vfp_sd`, `vfp_sn`, `vfp_sm`, `fpscr_set_nzcv`) cannot observably propagate. Real fix would be `qemu_diff_m33 --classes fpu`, **but that's broken on the host's QEMU 8.2** (all FPU cases EAGAIN on the GDB pipe).
