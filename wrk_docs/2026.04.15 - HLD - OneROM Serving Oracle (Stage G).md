# OneROM Serving Oracle — Stage G Design

Version: 0.2.0 — DRAFT (folded in review findings: SRAM-base shadow,
bounds verdicts, push-anchored stability, CS seed, sys_clk_hz guard,
trace-driven verdict tests, explicit emulator-bounded ns caveat).
Date: 2026-04-15
Parent: `2026.04.14 - HLD - OneROM Full-System Oracle.md` (Stage F)
Depends: Stage F.4 complete (glue DMA pumps, stable byte observed)

## 1. Purpose

Close Stage F's three known gaps in one pass:

1. **Byte correctness.** Stage F accepts any stable byte on D0..D7 as
   a "smoke PASS". The observed 0xFF is ambiguous — could be served
   ROM payload, could be PIO2 reset state, could be pull-up
   convention. Make this unambiguous.
2. **Address sweep.** Stage F drives a single address (0x000). An
   address-bit-swap bug in PIO1's assembly or CH0 forwarding would
   pass today.
3. **Access timing.** Stage F tells us a byte is stable "somewhere
   in rel_cycles 8..30". It does not tell us CS-to-valid-data
   latency, does not convert to nanoseconds, and cannot answer
   "what speed ROM is this — 80 ns, 120 ns, 150 ns?"

One new harness binary, one new harness module. No emulator-crate
changes. No changes to `onerom_full_system_rp2350` (which stays as
the narrative boot-diagnostic binary).

### Non-goals

- **PIO1 address-assembly correctness.** That's the PIO differential
  oracle's job (`onerom_pio_diff_rp2350`). Stage G treats whatever
  PIO1 pushes to RX0 as authoritative and validates the rest of the
  pipeline against it. See §4 for why this is fine and what it
  misses.
- **Cycle-accurate comparison to silicon.** We compare emulator
  measurements to the 11-14 cycle envelope documented in Piers'
  `piorom.c`, not to live RP2354. Cross-checking against silicon
  belongs in a future silicon-oracle pass.
- **Multiple ROM configs, bank switching, write ops.** One fixture
  (`test-sdrr-0`), serving mode only, same as Stage F.
- **CI integration.** Local dev oracle, like Stage F.

## 2. Scope

Three milestones, in strict order. A single binary
`onerom_serving_oracle_rp2350` runs all three and prints one report.

| Stage | Deliverable | Done when |
|-------|-------------|-----------|
| G.1 | Byte oracle | For the address-0 case, the byte observed on D0..D7 matches `bus.read8(ch1.read_addr)` captured at the first CH1 push |
| G.2 | Address sweep | ~14 address stimuli (walking 1s across A0..A10 + a small pattern set) each produce a byte matching their resolved SRAM content |
| G.3 | Timing envelope | Per-case `cycles_cs_low_to_stable_byte` recorded, converted to ns via `bus.sys_clk_hz()`, min/max/mean reported, pass criterion = all cases within the 11-14 cycle envelope from `piorom.c` |

Out of scope: fault injection, concurrent reads, clock-sweep, live
silicon comparison.

## 3. The oracle

### 3.1 SRAM shadow at sync

OneROM's `Reset_Handler` memcopies the embedded ROM table from flash
to SRAM before enabling PIO (journal note, 2026-04-15). At sync
time, SRAM holds the ROM payload. The firmware programs CH1 with
`READ_ADDR = 0x20000000` (SRAM base) as the initial source; CH0
then overwrites that per-request with a full 32-bit address that
PIO1 assembled.

The oracle: **snapshot the SRAM region that spans the ROM table at
sync, use it as the ground truth for subsequent address stimuli.**

The shadow is anchored at SRAM base, not at CH1.READ_ADDR — that
register is a moving target (CH0 overwrites it on every forward).
SRAM base is fixed by the architecture (`0x20000000`) and matches
the initial DMA programming we observed in Stage F.

Concretely:

```
const SHADOW_BASE: u32 = 0x2000_0000;
const SHADOW_SIZE: usize = 0x2000;   // 8 KB — one 2364-class ROM

at sync (once):
  rom_shadow = [bus.read8(SHADOW_BASE + i) for i in 0..SHADOW_SIZE]

for each address-stimulus N in the sweep:
  drive pins:  CS1 low, A-bus = N, CS2/CS3 high
  record ch1_pushes_before = glue.ch1_pushes()
  step until glue.ch1_pushes() > ch1_pushes_before  → that's push_cycle
  resolved_addr = bus.read32(DMA_BASE + 0x40 + 0x00)  (CH1.READ_ADDR)
  if resolved_addr not in [SHADOW_BASE, SHADOW_BASE + SHADOW_SIZE):
      verdict = ResolvedAddrOutOfRange { addr: resolved_addr }
      continue
  expected = rom_shadow[resolved_addr - SHADOW_BASE]
  step further until (first_stable_cycle > push_cycle) AND
                    D0..D7 stable for MIN_STABLE_CYCLES with pad_oe == 0xFF
  observed = data byte on D0..D7
  verdict  = (expected == observed) ? Pass : WrongByte
```

Note the `first_stable_cycle > push_cycle` guard: without it, if two
consecutive cases resolve to the same byte value, the stability
check would pass at rel_cycle=0 (holding the prior case's byte) and
we'd record a bogus zero-latency PASS. Anchoring stability to
*after* the push event rules this out.

### 3.2 Why the SRAM shadow, not the `.bin`?

Two options were considered. The shadow wins on simplicity:

| Option | Pros | Cons |
|--------|------|------|
| **SRAM shadow at sync** | One emulator call; captures whatever the Reset_Handler actually produced, including any overclock/variant-specific remapping | If SRAM gets corrupted mid-test, the shadow is still consulted against the corrupt state (but this is a serving-loop bug we'd catch by sheer chance through byte mismatches) |
| Parse `.bin` for the embedded ROM image | Independent of any emulator preload bug | Requires knowing `sdrr_info_t` layout, section offsets, relocation; brittle to firmware rebuilds |

The shadow does not validate *preload correctness* (whether the
firmware correctly memcpy'd the ROM table). That's implicitly
validated by boot-to-sync reaching a healthy state at all, and by
the byte sweep producing non-trivial variation (not all the same
value).

### 3.3 What this oracle catches vs misses

**Catches:**
- Wrong byte on D0..D7 (PIO2 OUT bugs, pad-drive mask bugs, bit ordering).
- Byte stuck at reset value (0xFF when it shouldn't be).
- Latency outside the 11-14 cycle envelope (timing regression).
- CH1 reading from the wrong address (if CH1.READ_ADDR drifts
  while pin stimulus is stable).
- Different address stimuli producing the same observed byte
  (indicator that PIO1 is ignoring the pin stimulus).

**Does not catch:**
- PIO1 assembling the wrong address word for the given pin
  stimulus. Because the shadow is indexed by `CH1.READ_ADDR`
  (whatever PIO1 produced), a PIO1 assembly bug that consistently
  maps pin bits X to SRAM byte Y would still "match" the shadow at
  Y. That's covered by `onerom_pio_diff_rp2350` against a reference
  PIO implementation.

This split is deliberate: Stage G is the *serving-pipeline* oracle
(end-to-end byte flow + timing); the PIO differential is the *PIO
code correctness* oracle. Each catches a different class of bugs.

## 4. Address sweep

### 4.1 Pin-map collision constraint

Per Stage F's CAUTION block in `onerom_full_system_rp2350.rs`:

- CS3 = GPIO 15 = A11
- CS2 = GPIO 12 = A12

To keep CS2/CS3 *deasserted* (high) during reads, we must drive
A11=1 and A12=1 for every stimulus. Consequence: addresses have the
form `0x1800 | low11` where `low11 ∈ [0, 0x7FF]`.

This limits the sweep to 2048 addresses within the 4096-byte
address space the decoder exposes with A11=A12=1. That's fine for
the MVP — we're sampling for bit-level coverage, not exhausting.

### 4.2 Case set

**Walking-1s across A0..A10** (11 cases) — catches single-bit
address-decode bugs:

```
0x1800, 0x1801, 0x1802, 0x1804, 0x1808, 0x1810, 0x1820,
0x1840, 0x1880, 0x1900, 0x1A00, 0x1C00
```

(That's 12 cases: the baseline `0x1800` + one per bit of A0..A10.)

**Pattern set** (4 cases) — catches wider-range bugs:

```
0x1AAA   // alternating bits
0x1D55   // complementary alternating
0x1FFF   // all low 11 bits set
0x1800   // (already in walking set; omit)
```

Total: 15 distinct addresses. Runtime budget at ~20 cycles per case
+ sync boot (~7 100 cycles): well under 100 000 cycles. Milliseconds
on the emulator.

### 4.3 Per-case state machine

```
one-shot:         init → idle
per case (×N):    idle → cs_assert → wait_push → wait_stable
                       → record → cs_release → idle
```

| Transition | Condition | Emits |
|------------|-----------|-------|
| init → idle | drive CS1 high + CS2/CS3 high + address=0 for `SEED_CYCLES` (Stage F ended with CS1 LOW; we need a clean high-to-low edge for case 1) | — |
| idle → cs_assert | apply new pin stimulus (CS1 low, A-bus = case.addr_bits), snapshot `ch1_pushes_before` | `cs_low_cycle` |
| cs_assert → wait_push | next `tick` | — |
| wait_push → wait_stable | `glue.ch1_pushes() > ch1_pushes_before` | `push_cycle`, latch `resolved_addr = CH1.READ_ADDR` |
| wait_stable → record | `current_cycle > push_cycle` AND D0..D7 stable for `MIN_STABLE_CYCLES` AND PIO2 pad_oe == 0xFF | `observed_byte`, `stable_cycle` |
| record → cs_release | n/a | `latency_cycles = stable_cycle - cs_low_cycle` |
| cs_release → idle | CS1 high for ≥ `GAP_CYCLES` to let the pipeline settle | — |

Budgets:
- `SEED_CYCLES = 4`
- `GAP_CYCLES = 3`
- `PER_CASE_TIMEOUT = 60 cycles` (envelope is 11–14; 60 gives ~4× slack)

Timeout verdicts:
- Timed out in `wait_push` → `Verdict::NoResolve`
- Timed out in `wait_stable` → `Verdict::NoStableByte`
- `resolved_addr` outside `[SHADOW_BASE, SHADOW_BASE + SHADOW_SIZE)` at the `wait_push → wait_stable` transition → `Verdict::ResolvedAddrOutOfRange { addr }`

### 4.4 Why ch1_pushes delta is load-bearing

Two reasons, not one:

1. **Resolve detection.** `CH1.READ_ADDR` is a persistent bus
   register — it holds its last value. Two consecutive cases that
   happen to resolve to the same SRAM address (possible with
   mapping bugs or degenerate stimuli) would leave it unchanged,
   and a naive "addr != prior_addr" check would hang. `ch1_pushes`
   increments on every successful push regardless of address.

2. **Stable-byte anchoring.** If prior-case's byte equals this
   case's expected byte, D0..D7 is already "stable at the right
   value" the moment CS goes low — we'd report a fictional
   zero-latency PASS. Requiring `first_stable_cycle > push_cycle`
   anchors stability to *after* the new byte has been pushed,
   which makes the latency measurement meaningful and catches the
   "stuck at prior byte" bug.

## 5. Timing measurement

### 5.1 Latency definition

```
latency_cycles = stable_cycle - cs_low_cycle
```

where `cs_low_cycle` is the cycle at which we applied the stimulus
(`emu.bus.gpio_external_in` bit for CS1 cleared), and `stable_cycle`
is the first cycle in a run of `MIN_STABLE_CYCLES=3` where
`pio2_pad_oe == 0xFF` AND `data_byte == prior_data_byte`.

`MIN_STABLE_CYCLES=3` matches Stage F's evaluator.

### 5.2 Conversion to nanoseconds

```
sys_hz = emu.bus.sys_clk_hz()
if sys_hz == 0 {
    // OneROM didn't settle the PLL by sync (shouldn't happen;
    // guard against div-by-zero rather than crash).
    warn in report; latency_ns = None.
} else {
    latency_ns = (latency_cycles as u64) * 1_000_000_000 / (sys_hz as u64)
}
```

Sampled once post-sync. The report must print `sys_clk_hz`
prominently in its header — it's the conversion factor and any
"80 ns vs 120 ns" interpretation hinges on it.

### 5.3 Pass criterion

Per-case: `11 ≤ latency_cycles ≤ 14` (envelope from `piorom.c`).

Summary: `all cases passed` + the `latency_ns` min/max/mean. Mean
against a ROM-speed table emitted in the output:

```
ROM speed classes (JEDEC-ish for classic 2364 / 27C256-era parts):
    ≤  55 ns  → "fast" (2764-15 / 27256-15 class)
    ≤  70 ns  → "standard fast"
    ≤ 100 ns  → "standard"
    ≤ 120 ns  → "slow standard" (2364 classic)
    ≤ 150 ns  → "slow"
    >  150 ns → "very slow"
```

(These are labels for the report, not pass/fail criteria. The
pass/fail is the cycle envelope.)

### 5.4 What the ns number actually measures (caveat)

The latency we report is **emulator-bounded**, not silicon-calibrated.
Specifically:

- Our glue DMA hardcodes a 4+4 cycle read+write pipeline. Silicon's
  RP2354 DMA has its own pipeline depth, arbitration latency, and
  SRAM-port contention behaviour — any of which could differ by a
  few cycles. Our number is "what the emulator's DMA model says",
  not "what silicon would deliver".
- PIO1's `in`/`push` timing and PIO2's `pull`/`out` timing are
  bytecode-dependent; our engine matches the PIO diff oracle on the
  synthetic `setup_onerom` program but has not been cycle-calibrated
  against real PIO on silicon.

This is explicit in the printed report so the reader knows what
they're looking at:

```
  Latency measured against the emulator's glue DMA + PIO model
  (4+4 cycle DMA latency; PIO timing per mdpicoem-common::pio).
  Silicon-calibrated timing is a future pass via the silicon oracle
  rig (see silicon_cycle_oracle_rp2350).
```

### 6.1 `onerom_serving_oracle.rs` public surface

```rust
pub const ADDR_A11_A12_HIGH: u16 = 0x1800;
pub const SHADOW_BASE: u32 = 0x2000_0000;  // SRAM base on RP2350
pub const SHADOW_SIZE: usize = 0x2000;     // 8 KB — one 2364-class ROM
pub const ENVELOPE_CYCLES: std::ops::RangeInclusive<u32> = 11..=14;

/// One address case for the sweep.
#[derive(Clone, Copy, Debug)]
pub struct Case {
    pub label: &'static str,  // e.g. "walk1 A5"
    pub addr_bits: u16,       // value to drive on A0..A12 (must have A11=A12=1)
}

/// Default case set — walking-1s over A0..A10 plus patterns. See §4.2.
/// Construction enforces `addr_bits & 0x1800 == 0x1800`.
pub const DEFAULT_CASES: &[Case] = &[ /* 15 entries */ ];

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Verdict {
    Pass,
    WrongByte { expected: u8, observed: u8 },
    NoResolve,                                // wait_push timed out
    NoStableByte,                             // wait_stable timed out
    ResolvedAddrOutOfRange { addr: u32 },     // CH1.READ_ADDR outside shadow
    LatencyOutOfEnvelope { cycles: u32 },
}

#[derive(Clone, Copy, Debug)]
pub struct CaseResult {
    pub case: Case,
    pub resolved_addr: Option<u32>,
    pub expected_byte: Option<u8>,
    pub observed_byte: Option<u8>,
    pub latency_cycles: Option<u32>,
    pub verdict: Verdict,
}

/// Oracle state. Lives for the duration of the run; owns the SRAM
/// shadow and the accumulating results.
pub struct ServingOracle {
    rom_shadow: Box<[u8; SHADOW_SIZE]>,
    results: Vec<CaseResult>,
}

impl ServingOracle {
    /// Called once at sync — copies `SRAM[SHADOW_BASE..+SHADOW_SIZE]`
    /// into the shadow buffer.
    pub fn new_at_sync(bus: &mut Bus) -> Self;

    /// Drive one case, stepping the emulator + glue DMA as needed.
    /// Appends to `self.results` and returns a reference to the new
    /// entry.
    pub fn run_case(
        &mut self,
        emu: &mut Emulator,
        glue: &mut GlueDma,
        case: Case,
    ) -> &CaseResult;

    pub fn results(&self) -> &[CaseResult];

    /// Formatted summary (per-case table + aggregate stats + the
    /// sys_clk_hz header + the caveat from §5.4). `sys_clk_hz == 0`
    /// emits a warning and omits ns columns.
    pub fn format_report(&self, sys_clk_hz: u32) -> String;
}

/// Trace-driven verdict evaluator — the state machine in §4.3 as a
/// pure function. Takes a synthetic `&[Observation]` sequence and
/// the shadow, returns a `CaseResult`. Used by unit tests so
/// verdict logic can be exercised without spinning an emulator.
pub(crate) fn evaluate_case_trace(
    case: Case,
    shadow: &[u8; SHADOW_SIZE],
    trace: &[Observation],
) -> CaseResult;

#[derive(Clone, Copy, Debug)]
pub(crate) struct Observation {
    pub cycle: u64,
    pub ch1_pushes: u32,
    pub resolved_addr: u32,   // snapshot of bus.read32(CH1.READ_ADDR)
    pub data_byte: u8,
    pub pio2_pad_oe_data: u8, // (pio[2].pad_oe >> 16) & 0xFF
}
```

### 6.2 `bin/onerom_serving_oracle_rp2350.rs` flow

```
1. Load bootrom + flash, bypass bootrom (same as Stage F binary).
2. Step until `onerom_sync::is_synced(&mut bus)` → record sync_cycle.
3. Capture snapshot via `onerom_sync::capture_snapshot` (for the report header).
4. `glue_dma.prime_after_sync(&mut bus)`.
5. Tick once to let the glue DMA observe pre-armed CTRL_TRIGs.
6. Read CH1.READ_ADDR → `rom_base`. Build `ServingOracle::new_at_sync`.
7. For each case in DEFAULT_CASES: oracle.run_case(&mut emu, &mut glue, case).
8. Print:
     - Sync header (cycle, PIO CTRL values)
     - Oracle branch decision (reuse Stage F's decide_oracle_branch)
     - Per-case table: label, pin_addr, resolved_addr, expected, observed, cycles, ns, verdict
     - Summary: pass/fail count, min/max/mean latency (cycles + ns), ROM-speed class
9. Exit code: 0 if all cases pass, 1 otherwise.
```

Total new LOC estimate: ~450 lines (module) + ~250 lines (binary).

## 7. What stays hard-coded (deliberately)

No feature flags, no env vars, no CLI args. Rationale: this is a
local dev oracle for one fixture. Adding knobs before we have a
second fixture is speculative abstraction — exactly the M8 Glasgow
on-ramp CLAUDE.md warns against.

Hard-coded in the binary:
- `BOOTROM_PATH`, `FLASH_PATH` (same constants as Stage F binary).
- `DEFAULT_CASES` from `onerom_serving_oracle.rs`.
- `SHADOW_SIZE`, envelope bounds (11..=14).

If we later add a second fixture, we split either the constants or
the whole binary. We'll know then what the right factoring is.

## 8. Testing

### 8.1 Unit tests in `onerom_serving_oracle.rs`

Five tests. The shadow-capture test uses the real emulator; the
verdict tests are trace-driven (see `evaluate_case_trace` in §6.1) —
no mocks, no feature flags, just a pure function over a synthetic
observation sequence.

1. `rom_shadow_captures_sram_at_build_time` — pre-populate SRAM at
   `SHADOW_BASE..SHADOW_BASE+SHADOW_SIZE` with a walking pattern,
   call `ServingOracle::new_at_sync(bus)`, confirm the shadow
   mirrors SRAM exactly.

2. `verdict_pass_when_byte_matches_shadow_after_push` — synthesize a
   trace where `ch1_pushes` increments at cycle 5, `resolved_addr =
   SHADOW_BASE + 0x10`, shadow at that offset is `0x42`, and
   `data_byte` stabilises at `0x42` with `pio2_pad_oe_data == 0xFF`
   for ≥ 3 cycles starting at cycle 12 (latency = 12). Expect
   `Verdict::Pass` with `latency_cycles == 12`.

3. `verdict_wrong_byte_when_observed_mismatches_shadow` — same
   shape as (2) but `data_byte` stabilises at `0x00` while shadow
   says `0x42`. Expect `Verdict::WrongByte { expected: 0x42,
   observed: 0x00 }`.

4. `verdict_rejects_prior_case_residue` — shadow says expected =
   `0xAA`; trace shows `data_byte == 0xAA` from cycle 0 onward (the
   residue), `ch1_pushes` increments at cycle 5, and `data_byte`
   *remains* `0xAA` throughout. The `first_stable_cycle >
   push_cycle` rule must anchor the measurement after cycle 5 →
   latency ≈ `stable_cycle - cs_low_cycle` computed correctly, not
   from cycle 0. Proves (3) of the HLD's correctness claims.

5. `verdict_resolved_addr_out_of_range` — `resolved_addr = 0x2100_0000`
   (outside `[SHADOW_BASE, SHADOW_BASE + SHADOW_SIZE)`). Expect
   `Verdict::ResolvedAddrOutOfRange { addr: 0x2100_0000 }`.

`latency_outside_envelope_fails` is deliberately left to the live
run — envelope adherence is what the real firmware produces, not
something we synthesize.

### 8.2 Manual run acceptance

Once G.1/G.2/G.3 are wired:

```bash
cargo run -p mdpicoem-harness --release --bin onerom_serving_oracle_rp2350
```

## 9. Risks and unknowns

1. **PIO1 trigger model unknown (edge vs level on CS).** Stage F
   observed 2 pushes in ~40 cycles with static stimulus, which
   suggests PIO1 samples periodically rather than pure CS-edge
   triggered. The state machine in §4.3 pulses CS via the `init`
   seed and `cs_release → idle` transition, which works for either
   trigger model. If `NoResolve` verdicts dominate in the real
   run, the fix is likely widening `PER_CASE_TIMEOUT` rather than
   rethinking the stimulus shape — PIO1's sampling cadence may
   simply be slower than 60 cycles across address transitions.

2. **Address sweep might starve the pipeline.** Switching stimulus
   every ~20 cycles may not give PIO1 enough time to observe the
   new address and push it. Mitigation: `PER_CASE_TIMEOUT = 60` is
   generous; if we still see starvation, add a tunable `SETTLE_CYCLES`
   before the `cs_assert` step.

3. **A11/A12 pin-map collision could bite here too.** The sweep
   requires `A11=A12=1`. Case construction in §6.1 enforces this
   (`debug_assert!(case.addr_bits & 0x1800 == 0x1800)`); a future
   fixture without the collision would let us drop this constraint.

4. **`sys_clk_hz` might be 0 at sync.** Shouldn't happen — the
   Stage F journal shows a settled frequency — but guard the ns
   division anyway (see §5.2); the report states "ns unavailable"
   if we hit this.

5. **Shadow boundary with ROM size.** `SHADOW_SIZE = 8 KB` covers
   a 2364-class ROM. If a future fixture serves a larger ROM
   (27C256 class at 32 KB), the shadow needs widening. For
   `test-sdrr-0` (the sole fixture we're targeting), 8 KB is
   correct.

6. **First-case CS seed assumes Stage F's CS1-low ending.** The
   `init → idle` transition drives CS1 *high* for `SEED_CYCLES`
   because the binary-level flow after sync already has CS1 low
   (inherited from the Stage F binary's external-input mask). If
   that convention ever changes, the seed step needs to match the
   actual post-sync pin state.

7. **The report's ns numbers are emulator-bounded.** See §5.4.
   Not a risk per se, but a claim-scope limit the reader must not
   misinterpret.

## 10. Open questions deferred to implementation

1. Should the binary also print a `DMA CH_n armed` event log like
   Stage F does? **Default: no.** Stage F's log is useful for
   diagnosing boot; here we want a clean per-case table. Add a
   `--verbose` flag only if we need it during bring-up — and
   remove it once stable.

2. How do we handle a case that times out? **Default:** record
   `Verdict::NoResolve` or `Verdict::NoStableByte`, continue to
   the next case, fail the whole run at the end. Don't abort on
   first failure — the report is more useful with all cases' data.

3. Should the ROM-speed class be emitted per-case or just in the
   summary? **Default: summary only.** Per-case classes are noise.
