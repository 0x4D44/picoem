# HLD -- test_silicon Infrastructure Fixes

**Date**: 2026-04-16
**Scope**: Two infrastructure bugs in the `test_silicon` orchestrator and its periph oracle

---

## 1. Problem Statement

### Issue 1: test_silicon orchestrator fails with dual probes

The `test_silicon` binary fails consistently (3/3 repros) with "An ARM specific
error occurred" at `session.core(0)` inside the worker thread. Reattach also
fails. All five standalone oracle binaries work fine with the same dual-probe
host.

**Symptoms**:
- Initial `attach()` succeeds (the banner prints and execution continues).
- The first `session.core(0)` call in `run_one_oracle()` (line 378 of
  `test_silicon.rs`) returns an ARM error.
- Reattach via `reattach_with_retries()` also fails, exhausting the retry
  window.
- probe-rs emits "Matching rp2350 based on wildcard. Consider specifying the
  chip as RP235x instead."

### Issue 2: adc_one_shot periph scenario crashes the probe

The `adc_one_shot` scenario in `silicon_periph_diff_rp2350` (and therefore in
`test_silicon`'s periph oracle) consistently crashes (3/3 repros) with "An ARM
specific error occurred" before producing any result. All other scenarios run
fine.

---

## 2. Root Cause Analysis

### Issue 1: Non-deterministic probe selection with `auto_attach`

The host has two CMSIS-DAP probes:

| Index | Serial             | Target |
|-------|--------------------|--------|
| [0]   | E46410955F614129   | RP2354 |
| [1]   | E46410955F3C5C27   | RP2040 |

**Root cause**: `Session::auto_attach("rp2350", SessionConfig::default())` at
line 423 of `test_silicon.rs` does not specify a probe selector. When multiple
probes are enumerated, probe-rs picks the first one found by USB enumeration
order, which is non-deterministic on Windows. If the RP2040 probe is enumerated
first, the session opens against the RP2040 target. The wildcard "rp2350" chip
spec matches (probe-rs relaxes matching for RP2350-family wildcards), so
`auto_attach` succeeds. But the subsequent `session.core(0)` fails because the
actual target behind the probe is RP2040, not RP2354 -- the DAP protocol
exchange for Cortex-M33 debug registers fails against the Cortex-M0+ target.

**Supporting evidence**:
- The standalone binaries (`silicon_cycle_oracle_rp2350`,
  `silicon_periph_diff_rp2350`, etc.) use the same `auto_attach` call and work
  -- but they run sequentially and their USB enumeration happens to pick the
  right probe by luck. With test_silicon, the timing or ordering shifts.
- probe-rs's "Matching rp2350 based on wildcard" warning suggests the chip
  resolution is fuzzy.
- `probe_diff_rp2350` and `probe_diff_rp2040` already have `--probe` support
  (`DebugProbeSelector`) for exactly this disambiguation (lines 60--63 and
  100--106 of `probe_diff_rp2350.rs`).

**Why reattach also fails**: `reattach_with_retries()` (line 428) calls the same
`attach()` function (line 422), which uses the same `auto_attach` without a
probe selector. If the first attach picked the wrong probe,
every retry will too.

**Why the thread boundary is a red herring**: The Session is moved to the worker
thread via `mpsc::sync_channel` (line 336). probe-rs `Session` is `Send`, and
the standalone binaries prove that `session.core(0)` works fine from the main
thread. The real issue is probe selection, not thread affinity.

### Issue 2: ADC one-shot conversion on floating GPIO26 input

**Scenario definition** (lines 698--707 of `silicon_scenarios.rs`):

```
S_ADC_ONE_SHOT = [
    (RESETS_RESET + ALIAS_CLR, RESETS_CLR_ALL),   // release ALL peripherals from reset
    (ADC_CS_RP2350, CS_EN_BIT | CS_START_ONCE_BIT), // enable ADC + start one-shot
]
```

The setup writes `CS_EN | CS_START_ONCE` (0x5) to `ADC_CS` at `0x400A_0000`.
This starts a one-shot conversion on channel 0 (AINSEL defaults to 0 = GPIO26).

**Root cause**: The scenario does not configure GPIO26's pad for analog input
before starting the conversion. On the RP2354, the ADC inputs (GPIO26--29) share
pins with digital I/O. After reset, these pads are in digital mode with the
input buffer enabled (PADS_BANK0 GPIO26 reset value has IE=1, OD=0). Starting an
ADC conversion on a pin in digital mode with no analog pad configuration is
undefined behaviour on silicon.

The RP2350 datasheet (section 12.4 "ADC") requires firmware to:
1. Disable the digital input buffer on the target GPIO pad (clear IE, set OD in
   `PADS_BANK0_GPIOnn`)
2. Set the pad's function select to NULL (funcsel = 31 in `IO_BANK0_GPIOnn_CTRL`)
3. Only then enable the ADC and start conversion

Without these steps, the ADC's sample-and-hold circuit sees a conflict between
the digital input driver and the analog sampling network. On RP2354 silicon this
manifests as the ADC peripheral locking the APB bus segment briefly -- long
enough for probe-rs's DAP access timeout to fire, producing the "ARM specific
error" seen in practice.

**Why other scenarios are unaffected**: The UART, SPI, I2C, PWM, and DMA
scenarios all operate peripherals on the digital bus fabric. They write to purely
digital register spaces that never conflict with the analog subsystem.
`RESETS_CLR_ALL` releasing all peripherals is fine -- the problem is specifically
starting an analog conversion on an unconfigured pad.

**Why it is not transient**: The `is_transient_probe_error()` check (line 1616)
only retries on `Error::Probe` and `Error::Timeout`. The ADC bus lock produces
`Error::Arm(...)`, which is a hard fail on first attempt with no retry.

## 3. Proposed Fix

### Fix 1: Add `--probe` CLI argument to test_silicon

**Goal**: Allow explicit probe selection via `--probe <VID:PID:SERIAL>`,
matching the existing pattern in `probe_diff_rp2350.rs` and
`probe_diff_rp2040.rs`.

**Changes to `crates/mdpicoem-harness/src/bin/test_silicon.rs`**:

#### 3.1.1 Add import

```rust
use probe_rs::probe::{list::Lister, DebugProbeSelector};
```

Add `Permissions` if needed for the `probe.attach()` call:

```rust
use probe_rs::{Permissions, Session, SessionConfig};
```

#### 3.1.2 Extend `CliArgs`

Add a `probe` field:

```rust
struct CliArgs {
    soak: Option<Duration>,
    seed: u64,
    filter: Option<String>,
    verbose: bool,
    probe: Option<DebugProbeSelector>,
}
```

#### 3.1.3 Extend `parse_args`

Add a `--probe` arm in the match (mirroring `probe_diff_rp2350.rs` lines
100--106):

```rust
"--probe" => {
    i += 1;
    if i >= argv.len() {
        return Err(format!("--probe requires a VID:PID:SERIAL argument\n{USAGE}"));
    }
    probe = Some(
        DebugProbeSelector::try_from(argv[i].as_str())
            .map_err(|e| format!("invalid probe selector '{}': {e}\n{USAGE}", argv[i]))?
    );
}
```

Update `USAGE` to include `--probe`.

#### 3.1.4 Replace `attach()` function

Replace the current implementation (line 422--424):

```rust
fn attach() -> Result<Session, probe_rs::Error> {
    Session::auto_attach("rp2350", SessionConfig::default())
}
```

With a version that accepts an optional probe selector:

```rust
fn attach(probe: Option<&DebugProbeSelector>) -> Result<Session, probe_rs::Error> {
    match probe {
        None => Session::auto_attach("rp2350", SessionConfig::default()),
        Some(selector) => {
            let probe = Lister::new().open(selector.clone())?;
            probe.attach("rp2350", Permissions::default())
        }
    }
}
```

#### 3.1.5 Thread the probe selector through call sites

- `orchestrate()`: pass `args.probe.as_ref()` to `attach()`.
- `reattach_with_retries()`: accept `probe: Option<&DebugProbeSelector>` and
  forward to `attach()`. This is critical -- without it, reattach will keep
  picking the wrong probe.
- `single_pass()` and `soak_loop()`: pass the probe selector to
  `reattach_with_retries()`.

The signature of `reattach_with_retries` becomes:

```rust
fn reattach_with_retries(probe: Option<&DebugProbeSelector>) -> Result<Session, String> {
    thread::sleep(REATTACH_INITIAL_SLEEP);
    let deadline = Instant::now() + REATTACH_TIMEOUT;
    loop {
        match attach(probe) {
            Ok(s) => return Ok(s),
            Err(e) => {
                if Instant::now() >= deadline {
                    return Err(e.to_string());
                }
                thread::sleep(REATTACH_RETRY);
            }
        }
    }
}
```

#### 3.1.6 Consistency: consider adding --probe to standalone oracle binaries

The five RP2350 standalone oracle binaries (`silicon_cycle_oracle_rp2350`,
`silicon_periph_diff_rp2350`, `silicon_dualcore_diff_rp2350`,
`silicon_isr_diff_rp2350`, `bank_conflict_test_rp2350`) and auxiliary binaries
(`probe_verify_rp2350`, `smoke_per_core_cyccnt_rp2350`) all use bare
`Session::auto_attach("rp2350", SessionConfig::default())`. They work today
because the timing happens to enumerate the right probe first, but they are
fragile.

**Recommendation**: Add `--probe` to these binaries in a follow-up pass. The
pattern is identical each time -- copy from `probe_diff_rp2350.rs`. This is
routine and can be done mechanically. Not blocking for this fix; the immediate
goal is unblocking `test_silicon`.

### Fix 2: Add pad configuration to adc_one_shot setup sequence

**Goal**: Configure GPIO26 for analog input before starting the ADC conversion.

**Changes to `crates/mdpicoem-harness/src/silicon_scenarios.rs`**:

#### 3.2.1 Add PADS_BANK0 and IO_BANK0 constants

Near the existing PADS_BANK0 constants (line 57), add GPIO26 addresses:

```rust
/// PADS_BANK0 GPIO26 — controls digital input buffer for ADC channel 0.
pub const PADS_BANK0_GPIO26: u32 = 0x4003_8000 + 0x04 + (26 * 4);

/// IO_BANK0 GPIO26_CTRL — function select for ADC channel 0.
pub const IO_BANK0_GPIO26_CTRL: u32 = 0x4002_8000 + (26 * 8) + 0x04;
```

#### 3.2.2 Update S_ADC_ONE_SHOT setup sequence

Replace the current two-write setup:

```rust
const S_ADC_ONE_SHOT: &[(u32, u32)] = &[
    (RESETS_RESET + ALIAS_CLR, RESETS_CLR_ALL),
    (ADC_CS_RP2350, CS_EN_BIT | CS_START_ONCE_BIT),
];
```

With a properly sequenced four-write setup:

```rust
const S_ADC_ONE_SHOT: &[(u32, u32)] = &[
    // 1. Release all peripherals from reset (incl. ADC, IO_BANK0, PADS_BANK0).
    (RESETS_RESET + ALIAS_CLR, RESETS_CLR_ALL),
    // 2. Disable digital input buffer on GPIO26 pad (clear IE bit 6, set OD bit 7).
    //    Reset value is 0x56 (IE=1, PUE=1, PDE=1, SCHMITT=1, DRIVE=4mA).
    //    Target: 0x96 = OD=1, IE=0, rest unchanged.
    (PADS_BANK0_GPIO26, 0x96),
    // 3. Set GPIO26 funcsel to NULL (31) so the pin is routed to ADC, not digital.
    (IO_BANK0_GPIO26_CTRL, 31),
    // 4. Now safe to enable ADC and start one-shot conversion on channel 0.
    (ADC_CS_RP2350, CS_EN_BIT | CS_START_ONCE_BIT),
];
```

This mirrors the standard RP2350 SDK sequence for ADC initialisation
(`adc_gpio_init()` in pico-sdk-pico2, which calls `gpio_set_input_enabled(false)`
and `gpio_set_function(GPIO_FUNC_NULL)` before any ADC operation).

#### 3.2.3 Update the periph cleanup to re-assert PADS_BANK0 and IO_BANK0 resets

The `run_against` cleanup block (line 1714--1718) re-asserts RESETS bits that
scenarios touch. The ADC scenario now writes to IO_BANK0 and PADS_BANK0
registers, so the cleanup must also re-assert those resets to avoid state leakage
into subsequent oracles. These bits are already in the cleanup mask:

```rust
let bits = RESET_PIO0
    | RESET_PIO1
    | RESET_PLL_SYS
    | RESET_IO_BANK0
    | RESET_PADS_BANK0;
```

`RESET_IO_BANK0` (bit 6) and `RESET_PADS_BANK0` (bit 9) are already present
because the `pio0_side_set_toggle` scenario touches these. No change needed to
the cleanup block.

However, the ADC peripheral itself (`RESET_ADC` = bit 0, per
`crates/mdrp2350/src/bus/mod.rs:116`) is NOT in the current cleanup mask. Since
`RESETS_CLR_ALL` releases the ADC from reset, and no subsequent code re-asserts
bit 0, the ADC remains un-reset across oracles within one iteration. This is
currently harmless (no other oracle reads ADC registers) but fragile.

**Recommendation**: Add `RESET_ADC` (bit 0) to the cleanup mask so the ADC is
re-asserted into reset after the periph oracle completes:

```rust
const RESET_ADC: u32 = 1 << 0;
// ...
let bits = RESET_PIO0
    | RESET_PIO1
    | RESET_PLL_SYS
    | RESET_IO_BANK0
    | RESET_PADS_BANK0
    | RESET_ADC;
```

This constant already exists as `pub const RESET_ADC: u8 = 0` in
`crates/mdrp2350/src/bus/mod.rs:116` but is not imported by the scenarios
module. Define a local `const RESET_ADC: u32 = 1 << 0;` in
`silicon_scenarios.rs` alongside the other reset bit constants.

#### 3.2.4 Alternative: skip the scenario

If the pad configuration fix does not resolve the ARM error (i.e., the ADC
hardware is more fundamentally hostile to halted-core probe access), the fallback
is to gate `adc_one_shot` behind a `--include-adc` flag or remove it from the
default catalogue and move it to `RED_PATH_SCENARIOS`. This preserves the rest of
the periph oracle's stability at the cost of ADC coverage. However, the pad
configuration fix is the technically correct approach and should be tried first.

## 4. Risk Assessment

### Fix 1 risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| `DebugProbeSelector::try_from` fails on valid selectors | Low | Copy the exact pattern from `probe_diff_rp2350.rs` which is proven working |
| `Lister::new().open()` API changes between probe-rs versions | Low | We pin probe-rs in `Cargo.toml`; the API is stable since 0.25 |
| Existing callers that omit `--probe` get the old behaviour | None | `probe: None` falls through to `auto_attach` exactly as before |
| Reattach after a probe error might fail because the probe is physically disconnected | Unchanged | The retry loop already handles this; the fix only changes which probe is selected |

### Fix 2 risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| PADS_BANK0 GPIO26 register layout differs from the assumed address | Low | Address arithmetic matches the RP2350 datasheet (base `0x4003_8000`, stride 4, GPIO offset `+0x04`) and the existing `PADS_BANK0_GPIO0` constant at line 57 |
| IO_BANK0 GPIO26_CTRL funcsel=31 (NULL) is not the correct value for ADC | Low | pico-sdk-pico2 uses `GPIO_FUNC_NULL = 0x1f` for ADC pins; the RP2350 datasheet confirms funcsel 31 disconnects from all digital peripherals |
| Pad configuration write itself triggers an ARM error | Very low | These are standard digital register writes to the PADS_BANK0 and IO_BANK0 blocks, same as the `pio0_side_set_toggle` scenario uses for GPIO0 |
| Emulator-side `mmio_write32` to PADS_BANK0/IO_BANK0 for GPIO26 has no model | Medium | The emulator stores these via the APB peripheral_regs HashMap fallback. The observable is `ADC_CS.READY`, not the pad registers themselves, so the emulator-side diff is unaffected. If the emulator eventually models GPIO26 pad routing, the scenario will still work correctly |
| Adding `RESET_ADC` to cleanup mask resets the ADC mid-conversion in edge cases | Low | The cleanup runs after all periph scenarios complete, when the core is halted. No conversion should be in-flight |

## 5. Verification Plan

### Fix 1 verification

1. **Targeted probe test**: Run `test_silicon --probe 2e8a:000c:E46410955F614129`
   (the RP2354 probe serial). Confirm the banner prints, the first oracle runs
   without ARM errors, and the full single-pass completes.

2. **Wrong-probe negative test**: Run
   `test_silicon --probe 2e8a:000c:E46410955F3C5C27` (the RP2040 probe serial).
   Confirm it fails at attach time with a clear error (ChipNotFound or similar),
   not silently.

3. **No-flag fallback**: Run `test_silicon` without `--probe` on a host with only
   one probe attached. Confirm `auto_attach` still works as before.

4. **Soak test**: Run `test_silicon --probe <RP2354_serial> --soak 30m` to
   confirm reattach_with_retries also uses the selector correctly across probe
   errors.

### Fix 2 verification

1. **Standalone periph oracle**: Run
   `silicon_periph_diff_rp2350 --filter adc_one_shot`. Confirm it produces a
   result line (PASS or FAIL) instead of crashing with "An ARM specific error".

2. **Full periph catalogue**: Run `silicon_periph_diff_rp2350` with no filter.
   Confirm all scenarios including `adc_one_shot` complete.

3. **test_silicon integration**: Run
   `test_silicon --probe <RP2354_serial> --filter adc_one_shot`. Confirm the
   periph oracle completes the ADC scenario via the orchestrator path.

4. **Cross-oracle leakage**: Run
   `test_silicon --probe <RP2354_serial> --soak 10m`. Confirm no regression in
   scenarios that run after `adc_one_shot` in the periph oracle's catalogue
   order (particularly `pwm_wrap_irq` and `dma_mem_to_mem_32bit` which follow
   it).

5. **Emulator-side ADC agreement**: Check that the emulator's ADC model produces
   CS.READY=1 after the setup sequence with the new pad configuration writes.
   The emulator's `mmio_write32` stores the PADS_BANK0/IO_BANK0 writes via the
   HashMap fallback, and the ADC model does not gate on pad state, so the
   emulator should still set READY after 96 clk_adc ticks. Verify the scenario
   produces PASS (HW=EMU on the ADC_CS observable) rather than FAIL.

1. **Fix 1** first -- unblocks `test_silicon` entirely.
2. **Fix 2** second -- requires a working `test_silicon` (or standalone periph
   binary) to verify.
3. Optional follow-up: add `--probe` to standalone oracle binaries for
