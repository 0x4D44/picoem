# Phase 5: Dual Core + SIO — Low-Level Design

Version: 0.2.0
Date: 2026-04-13
Parent: HLD Section 15, Phase 5
Depends: Phase 4 complete (bootrom + flash boot working)

## 1. Purpose

Enable both Cortex-M33 cores to run simultaneously. Core 1 boots the real
bootrom (same reset vector as Core 0), enters the bootrom's FIFO-polling wait
loop, and can be launched by Core 0 via the standard Pico SDK
`multicore_launch_core1` protocol. Implement the remaining SIO block features:
inter-processor FIFO, hardware spinlocks, integer divider, doorbells, and
platform timer.

### Milestone

Integration test: load bootrom + dual-core test binary → bootrom boots both
cores → Core 0 sends FIFO launch sequence → Core 1 wakes from WFE → both
cores execute independently → each core sets a distinct GPIO pin → verify
both pins in SIO GPIO_OUT and Core 1's PC is in application code (not
bootrom wait loop).

### What exists today

| Component | Status | Gap for Phase 5 |
|-----------|--------|-----------------|

| CPUID (0x000) | Returns `active_core()` | ✓ Works as-is (forward core_id parameter after refactor) |
| GPIO (SIO low) | Inline in Bus dispatch | Move to Sio struct |
| GPIO_HI_OUT / HI_OE | Silently ignored | Add to Known Limitations |
| FIFO | Not implemented | Two 8-entry queues + status register |
| Spinlocks | `[u32; 32]` in Sio, unused | Replace with `u32` bitmask + atomic test-and-set |
| SPINLOCK_ST | Not implemented | Trivially the bitmask value |
| Integer divider | Not implemented | Per-core state, immediate computation |
| Doorbells | Not implemented | Per-core pending bits (4 per core) |
| Platform timer | Not implemented | 64-bit MTIME + per-core compare |
| Interpolators | Not implemented | Register backing store only |
| WFE hint | Dispatched but NOP (thumb32) / undecoded (thumb16) | Real stall-wait semantics |

## 2. Design

### 2.1. SIO struct refactor

Move GPIO state from Bus into Sio. Make Sio handle region-0xD 32-bit register
dispatch via `read32(offset, core_id)` and `write32(offset, val, core_id)`.
Move `Sio` from `Emulator` into `Bus` (currently Emulator owns both — the
Emulator `sio` field is constructed but never used; it goes away entirely).

Bus delegates to Sio following the PPB pattern. One exception: `GPIO_HI_IN`
at offset 0x008 needs access to `flash_loaded` (a Bus field), so Bus handles
that offset directly before delegating the rest to `self.sio`. The LFSR state
(`gpio_hi_noise_state`) stays on Bus with `read_gpio_hi_in()`.

```rust
// Bus::read32 for region 0xD:
0xD => {
    let reg_offset = addr & 0xFFF;
    if reg_offset == 0x008 {
        self.read_gpio_hi_in()  // stays on Bus; needs flash_loaded
    } else {
        let core = self.active_core();
        self.sio.read32(reg_offset, core)
    }
}
```

**Address masking:** change all SIO dispatch sites from `addr & 0x0FFF_FFFF`
to `addr & 0xFFF`. This strips both the region selector and the NS alias bit
(0xD4000000), mapping both Secure and Non-Secure aliases to the same register.
All RP2350 SIO registers live within the first 0x200 bytes, so 12-bit masking
is sufficient. (Note: this collapses all 4 KB-aligned aliases in region 0xD
to the same register set — acceptable since the RP2350 SIO has no other
registers in region 0xD.)

**Sub-word SIO access:** Bus retains its 8-bit/16-bit SIO dispatch paths
(`read8`, `read16`). After the refactor, they call `self.sio.read32(offset &
!3, core)` and extract the relevant byte/halfword from the returned 32-bit
value. `write8` and `write16` continue to silently ignore SIO writes
(current behavior — the bootrom and SDK use word-aligned SIO writes).

**Helper method decomposition:** `Sio::read32` / `Sio::write32` delegate to
per-subsystem helpers: `fifo_read`, `fifo_write`, `spinlock_read`,
`spinlock_write`, `divider_read`, `divider_write`, `doorbell_read`,
`doorbell_write`, `mtime_read`, `mtime_write`, `interp_read`, `interp_write`.
Keeps the top-level dispatch readable.

**External access changes:** `emu.bus.gpio_out` → `emu.bus.sio.gpio_out`.
Tests at `crates/mdrp2354/src/tests.rs` need 4 line updates. Other crates
(test-harness, debug, periph, pio) have been grepped — no GPIO/SIO references.

### 2.2. Inter-processor FIFO

Two 8-entry circular buffers, one per direction. Core 0's FIFO_WR pushes to
Core 1's receive queue; Core 1's FIFO_WR pushes to Core 0's receive queue.

```rust
struct Fifo {
    buf: [u32; 8],
    head: u8,
    tail: u8,
    count: u8,
}

// In Sio:
fifo_to_core1: Fifo,  // Core 0 writes here; Core 1 reads here
fifo_to_core0: Fifo,  // Core 1 writes here; Core 0 reads here
fifo_wof: [bool; 2],  // sticky write-overflow flag, per-core (set when THIS core's write hit a full queue)
fifo_roe: [bool; 2],  // sticky read-underflow flag, per-core (set when THIS core's read hit an empty queue)
```

| Offset | Register | Read | Write |
|--------|----------|------|-------|
| 0x050 | FIFO_ST | Status bits (see below) | Writing any value clears WOF and ROE for this core |
| 0x054 | FIFO_WR | — | Push to the OTHER core's RX queue |
| 0x058 | FIFO_RD | Pop from THIS core's RX queue | — |

**FIFO_ST bits (for calling core):**
- Bit 0 (VLD): this core's RX queue has data (`count > 0`)
- Bit 1 (RDY): the other core's RX queue has space (`count < 8`)
- Bit 2 (WOF): write overflow (sticky)
- Bit 3 (ROE): read underflow (sticky)

**FIFO_RD when empty**: returns 0, sets ROE for the reading core.
**FIFO_WR when full**: data is dropped, sets WOF for the writing core.

**Event signaling:** on a successful `FIFO_WR` (non-overflow), set
`bus.event_flag[other_core] = true`. This matches RP2350 hardware behavior
and provides a safety net for any code that relies on FIFO-triggered wake
rather than explicit SEV.

### 2.3. Hardware spinlocks

32 shared locks. Use a single `u32` bitmask (one bit per lock) — this both
minimizes storage and makes the SPINLOCK_ST register trivially
implementable.

```rust
spinlock_bits: u32,  // bit N = SPINLOCK<N> claimed
```

| Offset | Register | Read | Write |
|--------|----------|------|-------|
| 0x100 + 4*N | SPINLOCK<N> (0..32) | If `bit N == 0`: set bit N, return `1 << N`. If already set: return 0. | Clear bit N (ignore value). |
| 0x05C | SPINLOCK_ST | `spinlock_bits` | — |

The read returns `1 << N` on successful claim (matches RP2350 hardware — the
SDK and any user code that uses the return bitmask value will work correctly).
A write of any value releases the lock. No ownership tracking.

**Fairness note:** since Core 0 steps before Core 1 in each emulator tick,
Core 0 wins all contested claims. This is a valid arbitration model (real
hardware leaves arbitration implementation-defined) and cannot deadlock.
Pathological livelock is theoretically possible but not exhibited by the
bootrom or SDK code. Accepted as a known modelling choice.

### 2.4. Integer divider

Per-core hardware divider. Result is computed immediately when the divisor
is written. CSR.READY is always 1.

```rust
struct Divider {
    dividend: u32,
    divisor: u32,
    quotient: u32,
    remainder: u32,
    signed: bool,
    dirty: bool,
}
// In Sio:
divider: [Divider; 2],
```

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x060 | DIV_UDIVIDEND | Write: store + mark unsigned. Read: return dividend. |
| 0x064 | DIV_UDIVISOR | Write: store, compute unsigned quotient/remainder, mark READY. Read: return divisor. |
| 0x068 | DIV_SDIVIDEND | Write: store + mark signed. Read: return dividend. |
| 0x06C | DIV_SDIVISOR | Write: store, compute signed quotient/remainder, mark READY. Read: return divisor. |
| 0x070 | DIV_QUOTIENT | Read: quotient. Write: set directly (marks DIRTY). |
| 0x074 | DIV_REMAINDER | Read: remainder. Write: set directly (marks DIRTY). |
| 0x078 | DIV_CSR | Bit 0 READY (always 1). Bit 1 DIRTY (set after any div register write). |

**Division by zero** (RP2350 semantics):
- Unsigned: quotient = 0xFFFFFFFF, remainder = dividend
- Signed: quotient = (dividend < 0) ? 1 : -1, remainder = dividend

**Why immediate computation works:** On real hardware, the divider takes 8
cycles and reading the result early auto-stalls the bus. The SDK does NOT
insert explicit delays — it relies on this auto-stall. Our immediate-result
model works because the result is always "already done" by the time the SDK
reads it, so the auto-stall path is never taken. The cycle count is off by
up to 8 per division; this is acceptable for Phase 5 and a Phase 8 polish
target.

### 2.5. Doorbells

4 doorbell bits per core (not 8 — RP2350 has DOORBELL_{SET,CLR}{4:0}).
Writing DOORBELL_OUT_SET sets bits on the other core; reading DOORBELL_IN_SET
shows this core's pending bits.

```rust
doorbell_pending: [u8; 2],  // lower 4 bits valid; upper 4 ignored
```

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x180 | DOORBELL_OUT_SET | Write: `doorbell_pending[1 - core] \|= val & 0xF` |
| 0x184 | DOORBELL_OUT_CLR | Write: `doorbell_pending[1 - core] &= !(val & 0xF)` |
| 0x188 | DOORBELL_IN_SET | Read: `doorbell_pending[core]` |
| 0x18C | DOORBELL_IN_CLR | Write: `doorbell_pending[core] &= !(val & 0xF)` |

**IRQ delivery:** when `doorbell_pending[core]` transitions 0 → nonzero,
set the SIO_IRQ_BELL<core> pending bit in `bus.ppb[core]`. The exact IRQ
number will be looked up from the RP2350 datasheet during implementation
and a constant added in `bus/mod.rs`. If the dual-core test binary doesn't
exercise doorbell IRQs, IRQ delivery can be deferred without blocking the
milestone.

### 2.6. Platform timer (MTIME)

64-bit counter accessible via SIO. Per-core 64-bit compare values.

```rust
mtime: u64,
mtime_ctrl: u32,
mtimecmp: [u64; 2],  // per-core compare
```

| Offset | Register | Behavior |
|--------|----------|----------|
| 0x1A0 | MTIME_CTRL | Bit 0: enable |
| 0x1A8 | MTIME (low) | Read/write low 32 bits |
| 0x1AC | MTIMEH (high) | Read/write high 32 bits |
| 0x1B0 | MTIMECMP0 (low) | Core 0 compare, low 32 |
| 0x1B4 | MTIMECMP0H (high) | Core 0 compare, high 32 |
| 0x1B8 | MTIMECMP1 (low) | Core 1 compare, low 32 |
| 0x1BC | MTIMECMP1H (high) | Core 1 compare, high 32 |

Offsets differ from V1 — corrected against RP2350 layout. Verify against
the datasheet during implementation if any mismatches appear.

Increment logic in `Emulator::step()` after both cores step:
```rust
if self.bus.sio.mtime_ctrl & 1 != 0 {
    self.bus.sio.mtime = self.bus.sio.mtime.wrapping_add(1);
}
```

Timer interrupt: when `mtime >= mtimecmp[core]`, set SIO_IRQ_MTIMECMP<core>
pending on that core's NVIC. IRQ numbers TBD during implementation.

**Prescaler note:** MTIME increments once per system clock cycle in our
model. The RP2350 TICKS peripheral handles 1-MHz prescaling at a higher
level; for Phase 5 we assume the tick rate configuration lives outside SIO
(not modeled), matching the bootrom's expectations.

### 2.7. Interpolator stubs

Two interpolators per core (INTERP0 at 0x080–0x0BC, INTERP1 at 0x0C0–0x0FC),
16 words each. Phase 5 provides a register backing store only — no
computation logic.

```rust
// 2 cores × 32 words (16 per interpolator × 2 interpolators)
interp: [[u32; 32]; 2],  // [core][reg] where reg = (offset - 0x080) >> 2
```

V1 had a typo (`[[u32; 16]; 2]`) that undercounted by a factor of 2; fixed
to 32 per core.

### 2.8. WFE/SEV semantics

The bootrom's Core 1 wait loop uses WFE. The SDK's `multicore_launch_core1`
sends SEV to wake Core 1. Hints must actually stall/wake rather than NOP.

**State**:
- `Bus`: `pub event_flag: [bool; 2]` (per-core ARM event register)
- `CortexM33`: `pub(crate) wfe_waiting: bool`

**WFE instruction**:
1. If `bus.event_flag[self.core_id]` is set → clear it, return 1 cycle
2. Else → `self.wfe_waiting = true`, return 1 cycle

**SEV instruction**: set `bus.event_flag[0] = true; bus.event_flag[1] = true`.
(SEV is broadcast to all cores including the issuer, per ARM ARM.)

**FIFO_WR auxiliary event**: on a successful FIFO write, also set
`bus.event_flag[other_core] = true` (see §2.2).

**Core step gate**: add `if self.wfe_waiting { return; }` as the FIRST check
in `CortexM33::step()`, before the existing `halted` and `stall_cycles`
checks. A WFE-sleeping core is frozen — it does not decrement, fetch, or
touch the bus.

**Emulator wake check**: after both cores step in `Emulator::step()`:
```rust
for i in 0..2 {
    if self.cores[i].wfe_waiting && self.bus.event_flag[i] {
        self.bus.event_flag[i] = false;
        self.cores[i].wfe_waiting = false;
    }
}
```
This gives 1-cycle wake latency — realistic for real hardware.

### 2.9. Hint instruction dispatch

Current state:
- **Thumb-16** (`execute.rs` line 720–735): hint opcodes group under
  `thumb16_misc` but the code does not decode the hint subcode — all
  hints return 1 cycle as NOP. The function has access to `bus`.
- **Thumb-32** (`execute_thumb32.rs` line 845–857): `thumb32_misc_control`
  decodes the hint subcode (`0x00=NOP, 0x01=YIELD, 0x02=WFE, 0x03=WFI,
  0x04=SEV`) but every arm returns 1 as NOP. The function does NOT take
  `bus` — it is called from `thumb32_branch_misc` (line 794) which takes
  `_bus: &mut Bus` but discards it.

**Required changes:**

1. `thumb32_branch_misc`: rename `_bus` → `bus`, pass it to
   `thumb32_misc_control`.
2. `thumb32_misc_control`: add `bus: &mut Bus` parameter.
3. `thumb32_misc_control` hint arms: replace the NOP returns with:
   ```rust
   0x02 => self.wfe(bus),     // WFE.W
   0x03 => 1,                 // WFI.W — still NOP
   0x04 => { bus.signal_sev(); 1 },  // SEV.W
   ```
4. `thumb16_misc` hint branch (execute.rs line 730–733): decode the hint
   subcode from the opcode:
   ```rust
   let hint_op = (opcode >> 4) & 0xF;
   match hint_op {
       0x0 | 0x1 => 1,              // NOP, YIELD
       0x2 => self.wfe(bus),        // WFE
       0x3 => 1,                    // WFI — NOP
       0x4 => { bus.signal_sev(); 1 },  // SEV
       _ => 1,                      // Reserved
   }
   ```
5. New methods on `CortexM33`: `fn wfe(&mut self, bus: &mut Bus) -> u32`.
   New method on `Bus`: `fn signal_sev(&mut self)`.

### 2.10. Core 1 boot sequence

Change `Emulator::reset()` to give both cores the same initial state:

```rust
pub fn reset(&mut self) {
    let initial_sp = self.bus.memory.rom_read32(0);
    let reset_vector = self.bus.memory.rom_read32(4);
    for id in 0..2 {
        self.cores[id] = CortexM33::with_id(id as u8);
        self.cores[id].regs.msp = initial_sp;
        self.cores[id].regs.r[13] = initial_sp;
        self.cores[id].regs.set_pc(reset_vector & !1);
        self.cores[id].regs.xpsr = 1 << 24;
    }
    self.bus.clear_bus_fault();
    self.bus.ppb = [Default::default(), Default::default()];
    self.bus.event_flag = [false; 2];  // NEW
    self.bus.resets_state = 0x1FFF_FFFF;
    self.clock = Clock { cycles: 0, sys_clk_hz: self.clock.sys_clk_hz };
}
```

Both cores start at the reset vector. The bootrom reads CPUID (SIO 0x000) to
differentiate — Core 1 branches to `core1_boot_path` at 0x1c6 and enters the
WFE + FIFO poll loop at `wait_for_vector` / `wait_for_rcp_salt` (0x1c4).

**Pico SDK launch protocol** (SDK side, for reference — not emulator code):
1. Core 0 drains its RX FIFO.
2. Core 0 sends the sequence `{0, 0, 1, vtor, sp, entry}` one word at a
   time. After each word, Core 0 calls `__sev()` to wake Core 1, waits
   for Core 1 to echo the value back via FIFO, and verifies the echo.
   A mismatched echo restarts the sequence from index 0.
3. Core 1 receives each word via WFE/FIFO_RD, echoes it back via FIFO_WR.
4. On the final word, Core 1 sets VTOR (PPB 0xE000ED08), SP, and branches
   to `entry`.

The LLD does not implement this protocol — the real bootrom on Core 1 and
the real SDK on Core 0 do. Our responsibility is making FIFO, WFE, and SEV
work correctly enough that the protocol succeeds.

### 2.11. RCP coprocessor MRC2 decoding — BLOCKER for Core 1 boot

**This is the single highest-risk item in Phase 5.**

Core 1's bootrom path uses `rcp_canary_status pc, nodelay` at address 0x1d2
(encoding `0xFE30 F710`). This is an ARMv8.1-M MRC2 instruction with Rt=15,
which writes condition flags (NZCV) into APSR. The subsequent `bpl.n`
branches on those flags.

Current CP7 handler (`core/coprocessor.rs` line 58):
```rust
let is_mrc_mcr = (hw0 >> 12) & 0xF == 0xE && hw1 & (1 << 4) != 0;
```

For `hw0 = 0xFE30`, `(hw0 >> 12) & 0xF = 0xF`, NOT 0xE. The MRC2/MCR2
encodings use the `0xF` prefix. The current handler silently falls through
for MRC2, returning 1 cycle without touching any state — so
`rcp_canary_status pc` acts as a no-op, and the following `bpl.n` branches
on stale flags from the preceding instruction.

Core 0 happens to reach its `rcp_canary_status` sites (0x38b8, 0x3990) with
flags that coincidentally take the "good" path through the bootrom. Core 1's
execution path is different, and the flag coincidence may not hold.

**Required fix in Stage B (before Core 1 integration test):**

1. Extend the MRC/MCR detection in `cp4_5_dcp` and `cp7_rcp` to also accept
   MRC2/MCR2 encoding: `((hw0 >> 12) & 0xF == 0xE || (hw0 >> 12) & 0xF == 0xF) && hw1 & (1 << 4) != 0`.
2. Add a `rcp_canary_status` handler: when MRC2 targets CP7 with Rt=15,
   write a known-good flag pattern (N=0, Z=1, C=1, V=0) into APSR. Per
   bootrom source, "OK canary" should produce `bpl` taken (N=0) and `bvc`
   taken (V=0). Verify this against the real bootrom binary during
   implementation.
3. Add a `rcp_salt_core<N>` handler: when MCR2 targets CP7 with the
   opcode that sets the other core's salt, store it in the other core's
   `rcp_salt` field via a cross-core bus path (new method
   `bus.set_cross_core_rcp_salt(other_core, value)`).

This work goes into Stage B alongside WFE/SEV. It is an implementation
prerequisite for Core 1 boot — without it, Core 1 will likely hang or
fault in `core1_boot_path`.

## 4. Staging

### Stage A: SIO refactor + FIFO + spinlocks (pure data path)

Establish the SIO module. No Core 1 boot yet — all existing tests must pass.
Two commits:

1. **A1 — Refactor** — Move `Sio` from `Emulator` to `Bus`. Move GPIO fields
   (`gpio_out`, `gpio_oe`, `gpio_in`) from Bus to Sio. Leave
   `gpio_hi_noise_state` + `read_gpio_hi_in()` on Bus. Add `Sio::read32` /
   `Sio::write32` with dispatch to per-subsystem helpers. Update sub-word
   paths (`read8`, `read16`) in Bus to extract from `self.sio.read32()`.
   Fix all 4+ address-mask sites (`addr & 0x0FFF_FFFF` → `addr & 0xFFF`).
   Update tests.rs 4 lines (`emu.bus.gpio_out` → `emu.bus.sio.gpio_out`).
   Remove `pub sio: Sio` from `Emulator`. Zero behavior change — all 476+
   existing tests must pass.

2. **A2 — FIFO + spinlocks** — Add `Fifo` struct and two instances. Wire
   FIFO_ST / FIFO_WR / FIFO_RD via `fifo_read` / `fifo_write` helpers (do
   NOT wire event signaling yet — that comes with WFE/SEV in B1). Add
   `spinlock_bits: u32` + SPINLOCK_ST dispatch (0x05C) and
   SPINLOCK<N> dispatch (0x100–0x17C). Unit tests: FIFO push/pop,
   overflow/underflow flags, spinlock claim/release/contention, SPINLOCK_ST
   bitmask reflects state.

### Stage B: WFE/SEV + Core 1 boot + RCP MRC2 + divider

High-risk stage — Core 1 actually executes code. Three commits:

1. **B1 — WFE/SEV plumbing** — Add `event_flag: [bool; 2]` to Bus with
   `signal_sev()` method. Add `wfe_waiting: pub(crate) bool` to CortexM33
   with new step-gate check and `wfe(bus)` method. Change Thumb-32
   `thumb32_branch_misc` to pass `bus` (not `_bus`) and
   `thumb32_misc_control` to accept `bus`. Update hint dispatch in both
   `execute.rs` line 730 and `execute_thumb32.rs` line 848. Wire FIFO_WR
   event signaling (see §2.2). Add wake check in `Emulator::step()`.
   Clear `event_flag` in `reset()`. Unit tests for: WFE when event pending
   (no sleep), WFE when no event (sleep), SEV wakes sleeping core, FIFO_WR
   wakes receiving core.

2. **B2 — RCP MRC2 + Core 1 boot** — Fix `cp7_rcp` to accept MRC2/MCR2
   encoding (`(hw0 >> 12) & 0xF == 0xE || 0xF`). Add `rcp_canary_status`
   handler that writes known-good NZCV to APSR when Rt=15. Add cross-core
   salt propagation (`bus.set_cross_core_rcp_salt`). Change
   `Emulator::reset()` to boot both cores from the reset vector (remove
   `cores[1].halt()`). Run bootrom for ~10k cycles and assert:
   - `cores[1].is_wfe_waiting() == true`
   - `cores[1].regs.ipsr() == 0` (no exception)
   - `cores[1].regs.pc` is inside `core1_boot_path` (address range 0x1c0–0x200).

3. **B3 — Divider** — Add `Divider` struct, per-core `divider: [Divider; 2]`
   in Sio. Dispatch 0x060–0x078. Immediate computation with correct
   RP2350 divide-by-zero semantics. Unit tests: UDIV positive, UDIV by
   zero, SDIV positive/negative, SDIV by zero, QUOTIENT/REMAINDER
   direct writes mark DIRTY.

### Stage C: Doorbells + platform timer + interpolator stubs + integration

Leaf features and final validation. Four commits:

1. **C1 — Doorbells** — `doorbell_pending: [u8; 2]` (4 bits per core).
   Dispatch 0x180–0x18C. Unit tests for SET/CLR/IN semantics.

2. **C2 — MTIME** — 64-bit counter + per-core compare. Increment in
   `Emulator::step()` when enabled. Unit tests.

3. **C3 — Interpolator stubs** — `interp: [[u32; 32]; 2]` backing store at
   0x080–0x0FC. No computation. Unit tests for register round-trip.

4. **C4 — Integration test** — Dual-core test binary. See §5. Asserts both
   GPIO pins set and Core 1 PC is in application code (not bootrom wait
   loop).

    vtor, sp, entry1}` via `FIFO_WR`, calling SEV between words, verifying
    echoes via `FIFO_RD`.
  - After Core 1 is launched, set GPIO 25.
  - Halt (infinite loop).
- Core 1 entry (after launch):
  - Set GPIO 0.
  - Halt (infinite loop).

This bypasses some SDK complexity but exercises the exact FIFO handshake
protocol the bootrom's `core1_boot_path` implements. Core 1's bootrom-side
protocol code is what runs from reset to launch — `gen_dualcore.py` only
generates Core 0's launching code and Core 1's post-launch code.

**Assertions:**
- After N cycles (budget: 100k), `bus.sio.gpio_out & (1 << 25) != 0`.
- `bus.sio.gpio_out & 1 != 0`.
- `cores[1].regs.pc >= 0x1000_0000` (Core 1 is running app code, not bootrom).
- `cores[1].is_wfe_waiting() == false`.

**Fallback plan:** if hand-assembling the launch protocol proves too
complex, install the Pico SDK toolchain and build an official multicore
example. Document either path in the implementation journal.

## 7. Known Limitations

- **No divider latency.** Results are immediate. Cycle count off by up to 8 per division. Phase 8.
- **No interpolator computation.** Register store only. Phase 7.
- **GPIO_HI_OUT / GPIO_HI_OE registers.** Writes accepted and silently dropped; reads return 0. Upper-GPIO modeling deferred until needed.
- **Doorbell/MTIME IRQ delivery.** Register state works; IRQ number constants and NVIC wiring TBD during implementation once datasheet numbers are confirmed. If test binary doesn't need IRQ, defer.
- **MTIME prescaler.** MTIME increments once per system clock. No prescaler; TICKS peripheral not modeled.
- **WFI treated as NOP.** Bootrom uses WFE (not WFI). SDK apps that sleep via WFI will busy-burn cycles but not hang.
- **Zero-latency FIFO.** A write by Core 0 is visible to Core 1 in the same emulator tick. Real hardware has 1-cycle bus latency. SDK code uses WFE/SEV synchronization, so this doesn't affect protocol correctness. Relevant only for pathological polling loops.
- **Spinlock fairness.** Core 0 always wins contested claims (it steps first). No deadlock possible; livelock theoretically possible but not observed.
- **No TrustZone differentiation.** Secure and Non-Secure SIO aliases map to the same state (per HLD v1 design).
- **CP0 GPIOC coprocessor.** Remains a pure stub (returns 0, ignores writes). Not regressed by this phase but also not fixed. Bootrom uses memory-mapped SIO, not CP0 GPIOC.
- **NSACR writes.** Pre-existing: silently ignored. Not known to affect bootrom/SDK.

## 8. Risk Assessment

**Highest risk:** §2.11 RCP MRC2 decoding for Core 1 boot. Core 1 hits
`rcp_canary_status pc` at address 0x1d2 and `bpl.n` branches on the flags.
The current CP7 handler silently no-ops on MRC2 encoding because it only
accepts MCR/MRC (hw0[15:12] == 0xE). Mitigation: fix in Stage B2 before
attempting Core 1 integration test. Trace Core 1's bootrom path with the
existing bootrom tracer to confirm the flag states required. If the
known-good flag pattern fails, iterate — same approach as Phase 3/4
bootrom debugging.

**Medium risk:** Thumb-32 hint handler signature change. `thumb32_misc_control`
doesn't currently accept `bus`. Trivial change but touches a hot path.
Mitigation: refactor is mechanical; verify all callers.

**Medium risk:** Test binary source. Hand-assembling the multicore launch
protocol in `gen_dualcore.py` is non-trivial (~50–80 lines of Thumb
assembly). Mitigation: §5 provides a fallback (install Pico SDK). If
neither works, demo Core 1 launch via a minimal hand-crafted FIFO write
sequence from the test harness (not from Core 0 application code).

**Low risk:** SIO refactor. ~20 line moves in `bus/mod.rs`, 4 test line
updates. PPB delegation pattern is proven. Existing tests catch regressions
immediately.

**Low risk:** FIFO, spinlocks, divider, doorbells, MTIME, interpolator stubs.
Independent, self-contained, well-defined semantics.

**Low risk:** Sub-word SIO access after refactor. Bootrom and SDK use
word-aligned SIO accesses. Sub-word reads delegate through `sio.read32`
and extract. Sub-word writes continue to silently ignore (pre-existing).

**Pre-existing risk (not introduced by Phase 5):** `active_core()` on Bus
uses a boolean hack (`contention_check_active`). Phase 5's post-step wake
check runs with `contention_check_active = true` left over from Core 1's
step, but the wake check only touches `event_flag` and `wfe_waiting` — it
never queries `active_core()`. Document the assumption; fix-up is out of
scope.
