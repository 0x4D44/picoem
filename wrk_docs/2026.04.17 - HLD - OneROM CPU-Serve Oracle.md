# OneROM CPU-Serve Oracle — Design

**Date:** 2026-04-17
**Parent:** `2026.04.15 - HLD - OneROM Serving Oracle (Stage G).md` (PIO oracle)
**Scope:** one emulator-crate bus fix + one harness module + one harness
binary. The bus fix is a prerequisite; without it the oracle cannot
produce a PASS verdict.

## 1. Purpose

Close out the second of OneROM's two serving modes. The PIO-mode oracle
is green (15/15 PASS on `1b0a5a9`) but relies on two harness
substitutions the firmware would normally drive: `populate_sram_from_shadow`
(preload DMA replacement) and `GlueDma` (serve-loop DMA replacement).

CPU-serve mode has neither dependency. The `-cpu` fixture's
`Reset_Handler` copies the ROM payload into SRAM via a CPU `memcpy`
(confirmed by `onerom_cpu_probe`: 64512 non-zero bytes at shadow base,
expected values at walking-1 offsets), and the serve loop is five Thumb
instructions at `0x1000_0926..=0x1000_0930` that read pins, look up a
byte from SRAM, and drive it back via SIO — no PIO, no DMA.

**Result:** a green CPU-serve oracle is the first end-to-end proof that
our emulator runs OneROM firmware unassisted.

### Non-goals

- Silicon-calibrated timing. Envelope is emulator-bounded, same caveat
  as the PIO oracle's HLD §5.4.
- Multi-fixture, multi-ROM-set, bank-switching. One fixture
  (`test-sdrr-0-cpu`), one `rom_set_index`.
- Threaded dual-core. CPU-serve is single-core; core 1 is halted.
- CI integration. Local dev oracle.

## 3. Prerequisite: `Bus::write8` SIO-aperture fix (emulator crate)

### 3.1 Evidence

`onerom_cpu_probe` includes a direct write8 self-check:

```
before write8: SIO_GPIO_OUT = 0x00000000
after  write8: SIO_GPIO_OUT = 0x00000000  (expected 0x000000A5)
after  write32 0xA5: SIO_GPIO_OUT = 0x000000A5
```

`bus.write8` into the SIO aperture (`0xD000_0000..`) is silently
dropped. `write32` at the same register works.

The probe's in-firmware address sweep confirms the downstream symptom:
under stimulus, core 0 computes the correct byte in R1 (`R1=0x02` for
A1, `0x04` for A2, `0x08` for A3 — matching `shadow[0x9040/0x9020/0x9010]`)
but `byte_out` observed on `SIO_GPIO_OUT[16..23]` stays `0x00` for every
case. The CPU serve loop's defining instruction is
`STRB R1, [R5, #0]` at `0x1000_0926` (R5 = `SIO_GPIO_OUT`); that STRB
vanishes on its way to the bus.

Without this fix, every oracle case would observe `0x00` regardless of
expected byte. Cases whose expected byte is also `0x00` would coincidentally
PASS; all others would FAIL as `WrongByte { expected: N, observed: 0x00 }`.
The oracle cannot distinguish "emulator is correct" from "emulator drops
byte writes".

### 3.2 Fix

In `crates/mdrp2350/src/bus/mod.rs`, `Bus::write8` dispatches to a
per-region arm. The SIO arm (region `0xD`) currently either falls
through to the peripheral-register `HashMap` (which is word-granular)
or early-returns without writing. Add explicit byte-lane handling:

- Compute `base = addr & !0x3`, `lane = (addr & 0x3) * 8`.
- Read the existing 32-bit register value at `base`.
- Merge: `new = (old & !(0xFFu32 << lane)) | ((val as u32) << lane)`.
- Write back through the same code path a 32-bit `write32(base, new)`
  would take, so register-specific side effects (SET/CLR/XOR aliases,
  GPIO masks, …) fire correctly.

Applies uniformly to the SIO register family: `GPIO_OUT`,
`GPIO_OUT_SET`/`CLR`/`XOR`, `GPIO_OE`, `GPIO_OE_SET`/`CLR`/`XOR`, plus
the `_HI` aliases for pins 32..47. No other SIO register needs byte
access for OneROM but doing the whole family keeps the semantics
uniform and avoids a rat's nest of region sub-dispatch.

### 3.3 Test (TDD)

Before the fix, write a unit test in `crates/mdrp2350/src/bus/mod.rs`
or `tests.rs` that fails:

```rust
#[test]
fn write8_sio_gpio_out_targets_single_lane() {
    let mut bus = Bus::new();
    bus.write32(SIO_GPIO_OUT, 0x0000_0000);
    bus.write8(SIO_GPIO_OUT + 2, 0xA5); // lane 2 → bits 16..23
    assert_eq!(bus.read32(SIO_GPIO_OUT), 0x00A5_0000);
    bus.write8(SIO_GPIO_OUT + 0, 0x11);
    assert_eq!(bus.read32(SIO_GPIO_OUT), 0x00A5_0011);
    bus.write8(SIO_GPIO_OUT + 3, 0xFF);
    assert_eq!(bus.read32(SIO_GPIO_OUT), 0xFFA5_0011);
}
```

And a sibling test for `SIO_GPIO_OE`. That's enough to pin the lane
algebra. The SET/CLR/XOR aliases get their own regression if needed.

### 3.4 Scope guard

This is narrow. It does **not** widen to:
- `read8` from SIO (no evidence it's broken; add a test if needed).
- Non-SIO regions (untouched by OneROM's CPU-serve path).
- Sub-word reordering of atomic alias semantics (SET/CLR/XOR already
  route through `write32` after the merge, so they inherit correctness).

## 5. Design

The PIO oracle catalogue (`DEFAULT_CASES`, `Case`, pin maps,
`ADDR_A11_A12_HIGH`, `SHADOW_BASE`, `SHADOW_SIZE`, `stimulus_level`,
`lift_shadow_from_flash`) is reused verbatim.

**Time units.** Verified against `mdrp2350/src/lib.rs:264-313`:
`step_quantum = 1` means one master cycle per `step()`, so one
`emu.run(1)` tick equals one emulated cycle. All cycle counts in this
oracle (floor, timeout, envelope, MIN_STABLE_CYCLES) are emulator
cycles, not instructions.

### 5.1 Sync detection — PC range

CPU-serve firmware settles into a 5-instruction loop at
`0x1000_0926..=0x1000_0930`. Verified by `onerom_cpu_probe`: 5000-
instruction PC histogram shows 100% of observed PCs fall in this range
and distribute 28/14/14/14/28% across the five loop PCs.

```rust
pub fn is_synced_cpu(emu: &Emulator) -> bool {
    (CPU_SERVE_LOOP_PC_LO..=CPU_SERVE_LOOP_PC_HI).contains(&emu.core(0).regs.pc())
}
```

Takes `&Emulator` (not `&mut Bus`) because the PC is in the core's
register file. Single caller; signature difference from the PIO
oracle's `is_synced` is fine.

### 5.2 Shadow source — flash parser, not live SRAM

In CPU-serve mode the firmware populates SRAM itself, so live SRAM
would also be correct. We still lift from flash via
`lift_shadow_from_flash` because:

- The parser is tested and is the authoritative ground truth by design.
- Lifting from SRAM adds a second sync condition (firmware copy loop
  complete).
- Both oracles report against the same shadow source → symmetric.

The oracle does **not** call `populate_sram_from_shadow` — firmware
already did it.

### 5.3 Stimulus and observation

Same pin maps as the PIO oracle (`ADDR_PINS`, `GPIO_CS1/2/3`). The
oracle pokes `gpio_external_in`/`gpio_external_mask` directly. Data
pins 16..23 are CPU-driven so the external-input mask excludes them.

Observation per tick:

- Data byte: `(emu.bus.gpio_in >> 16) & 0xFF`.
- OEN: `(emu.bus.read32(SIO_GPIO_OE_ADDR) >> 16) & 0xFF`. `oe_data != 0xFF`
  means partial drive → reset stable-run accumulator.

### 5.4 Stability detector (the only non-trivial design choice)

The detector answers "when has the CPU served a fresh byte in response
to the stimulus?" without being fooled by:

- **Stale residue.** The CPU may still be driving the previous case's
  byte while it samples new pins and issues a fresh STRB.
- **Expected-byte-is-0x00.** If the prior steady byte is 0x00 and the
  new expected byte is also 0x00, no transition is observable.

Three gates:

1. **Fresh-arrival floor (`MIN_FRESH_ARRIVAL_CYCLE_CPU`).** Reject
   stable runs whose first tick is below this floor. The drafted value
   is 6. The probe's hot-PC distribution indicates one loop iteration
   takes ~5-6 emulator cycles; with M33 multi-cycle LDR/STR the
   steady-state STRB-to-STRB gap is closer to 8-10 cycles.
   **Start at 10** on first run; tune down if genuine cases need
   latency below that.
2. **Transition latch (`byte_changed_since_stim`).** Stability may
   anchor iff the byte with OEN=0xFF has differed from the
   initially-captured byte at least once since stimulus apply.
3. **Zero-byte trust timeout (`ZERO_BYTE_TRUST_TIMEOUT_CPU = 40`).**
   If neither transition fires nor timeout elapses, no anchoring.
   40 cycles comfortably exceeds `MIN_FRESH_ARRIVAL_CYCLE_CPU +
   MIN_STABLE_CYCLES` so legitimate expected-zero cases resolve.

The detector is a pure state machine (`observe_tick`) with existing
unit-test coverage for (a) premature-zero-lock rejection, (b)
transition lock, (c) zero-trust timeout, (d) partial-OEN reset. If
`MIN_FRESH_ARRIVAL_CYCLE_CPU` moves from 6 → 10, the "locks on
non-zero after transition" test's expected tick shifts with it — a
trivial edit.

### 5.5 Envelope

`CPU_ENVELOPE_CYCLES: 20..=200` in the draft — a guess. Treat as
provisional:

1. First clean run measures the observed window.
2. Set envelope to `measured_min - 5 ..= measured_max + 20`.
3. Document in HLD changelog + `tech_debt.md` silicon-calibration note.

Envelope misses are reclassified as `LatencyOutOfEnvelope`, not FAIL.

### 5.6 CPU-fixture shadow regression test

Add a unit test analogous to the PIO oracle's
`walking_1s_distinctness_from_real_fixture`:

- Load the CPU fixture bytes.
- Call `lift_shadow_from_flash(&bytes, rom_set_index=0)`.
- Assert the walking-1 canonical offsets produce distinct bytes:
  `shadow[0x9080] != shadow[0x9040] != shadow[0x9020] != shadow[0x9010]`.

This pins that the CPU fixture's SDRR struct layout matches the parser's
expectations. Without it, a silently-failing parse (returning zeros)
would not FAIL the oracle on expected-zero cases and would silently
false-green on matching zero-byte shadows.

## 6. Binary wiring

`onerom_serving_oracle_cpu_rp2350`:

1. Load bootrom + CPU fixture.
2. Build emulator with `step_quantum=1`.
3. Bypass bootrom: `SP`, `PC` ← flash[0..8] (OneROM isn't an IMAGE_DEF).
4. Halt core 1.
5. Step until `is_synced_cpu` — fail after `BOOT_CYCLE_CAP` cycles.
6. Sanity check: PIO1.CTRL == PIO2.CTRL == 0. Warn if non-zero
   (fixture-type tripwire).
7. Construct oracle (`new_at_sync` → lift shadow from flash).
8. Print shadow-uniqueness tripwire (same as PIO oracle).
9. Sweep all `CPU_DEFAULT_CASES`, print per-case line.
10. Print full report (`format_report(sys_clk_hz)`).
11. Exit 0 iff all cases are `Pass`, else 1.

No env vars. Bootrom and fixture paths as `const`s.

## 7. Success criteria

Done when:

- **Bus fix:** new `Bus::write8` SIO lane test passes; full
  `cargo test -p mdrp2350` green.
- **Harness build:** `cargo build --release -p mdpicoem-harness`
  compiles cleanly.
- **Harness tests:** `cargo test -p mdpicoem-harness --lib` green,
  including the new CPU-fixture shadow regression test.
- **Oracle:** `cargo run -p mdpicoem-harness --release --bin
  onerom_serving_oracle_cpu_rp2350` boots, reaches sync, prints the
  per-case table + report, and either reports 15/15 PASS or diagnoses
  every failing case against a concrete structural reason (envelope
  too tight, gate tuning, fixture quirk).

Stretch goal: 15/15 PASS after one round of envelope tightening. Because
no firmware behaviour is substituted by the harness, any byte-level
failure is a real bug in either the emulator, the fixture, or the
oracle's observation semantics. That is the point.

## 9. Open questions (resolve at implementation time)

Empirical tunings, not design decisions:

1. **Envelope range.** Set from first clean-run observation.
2. **`MIN_FRESH_ARRIVAL_CYCLE_CPU` final value.** Start at 10; measure
   whether genuine PASS cases sit above it. Update detector unit tests
   to match the chosen value.
3. **Transient cycles 0..MIN_FRESH.** Verify on first run that the
   prior case's trailing STRB does not leak past the floor. If it
   does, raise the floor rather than adding a second gate.

No design changes needed for any of these; they require a working run
to measure.
