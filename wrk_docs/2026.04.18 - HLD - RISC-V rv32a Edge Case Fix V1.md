## Goal

Make the unit test `riscv_gen::tests::edge_cases_rv32a` PASS on `main` without weakening the reservable-window invariant, the minimum-scope way.

## Evidence / reproduction

```

Fails at `crates/mdpicoem-harness/src/riscv_gen.rs:2334`:

```

The failing block:

```rust
// riscv_gen.rs:2328-2340
fn edge_cases_rv32a() {
    let cs = gen_rv32a_reservable_edge_cases();
    check_class(&cs, RiscvClass::Rv32aReservable, false);
    for tc in &cs {
        for reg in &tc.addr_regs {
            let v = tc.reg_pre.iter().find(|(r, _)| r == reg).map(|(_, v)| *v).unwrap();
            assert!(
                (RESERVABLE_LO..RESERVABLE_HI).contains(&v),
                "atomic address out of reservable window: 0x{v:08X}"
            );
        }
    }
}
```

Constants in the same file (`riscv_gen.rs:125, 136-137`):

```
SCRATCH_BASE   = 0x8000_0400   // QEMU virt-DRAM alias of 0x2000_0400
RESERVABLE_LO  = 0x2000_0000
RESERVABLE_HI  = 0x2008_2000
```

`gen_rv32a_reservable_edge_cases` (`riscv_gen.rs:796-861`) seeds every AMO `rs1` with `SCRATCH_BASE` and appends `rs1` to `addr_regs`. Raw `0x8000_0400` is outside `[RESERVABLE_LO, RESERVABLE_HI)` — the assert fires for every case.

## Root-cause analysis

### Hypothesis 1 (accepted) — assertion missed the alias relocation
Commit `d9a66a7` moved the test-visible scratchpad from `0x2000_0300` to `0x8000_0400` because QEMU virt's `VIRT_FLASH` occupies `0x2000_0000` and silently drops CPU-side `sw`. The runtime code path handles this: `mdrp2350/src/bus/mod.rs:132-138` defines `canon_oracle_addr`, which maps `0x8xxx_xxxx -> 0x2xxx_xxxx` at bus entry; `mdrp2350/src/core_riscv/execute.rs:28-35` calls it inside `in_reservable` before comparing against `RESERVABLE_LO/HI`, so atomics at `0x8000_0400` are legitimately reservable at run time. **The unit-test assertion, authored earlier in `049cab1`, compares the raw u32 and never canonicalises** — so it flags addresses that are runtime-valid. Supporting evidence:
- `git log -S SCRATCH_BASE` shows `049cab1` (assertion born at `0x2000_0300`) predates `d9a66a7` (scratchpad relocation).
- The journal (`2026.04.18 - JRN - Follow-ups Campaign.md:13`) lists this exact failure as a pre-existing "not in scope" carry-over.
- The actual QEMU-diff and emulator runs of the same generator PASS, because `canon_oracle_addr` canonicalises before the reservable-window check on both sides.

### Hypothesis 2 (ruled out) — the generator is seeding the wrong base
Would imply mem/atomic tests fail at run time too. They don't: `gen_rv32a_reservable_edge_cases` → `check_class` succeeds (decode is valid), and the same scratchpad works in `gen_rv32i_mem_edge_cases`, `gen_rv32c_edge_cases`, etc. `SCRATCH_BASE = 0x8000_0400` is correct by design.

### Hypothesis 3 (ruled out) — reservable window is wrong
`RESERVABLE_LO/HI` in the harness match the emulator's copy in `core_riscv/execute.rs:24-25` exactly and match RP2350 datasheet §2.1.6.2 (528 KB SRAM). Not the bug.

**Ranking:** H1 is the only hypothesis consistent with the evidence.

## Proposed fix (minimum change)

Make the test's assertion canonicalise addresses the same way the runtime does, in `crates/mdpicoem-harness/src/riscv_gen.rs` inside the `edge_cases_rv32a` test body:

```rust
// Mirror mdrp2350::bus::canon_oracle_addr so the 0x8xxx_xxxx alias
// resolves to its SRAM image before the window check — matches the
// runtime's in_reservable() semantics.
let canon = |a: u32| if (a >> 28) == 0x8 { (a & 0x0FFF_FFFF) | 0x2000_0000 } else { a };
let v_canon = canon(v);
assert!(
    (RESERVABLE_LO..RESERVABLE_HI).contains(&v_canon),
    "atomic address out of reservable window: raw=0x{v:08X} canon=0x{v_canon:08X}"
);
```

**Why this shape:**
- Localised to the test — no production code change.
- Preserves the real invariant the test is meant to guarantee (no generator accidentally seeds atomics outside reservable SRAM).
- Uses the same alias rule the runtime uses; no new constants or magic numbers.

A slightly cleaner long-term form is to lift the lambda to a `pub(crate) fn` in the harness or re-export `mdrp2350::bus::canon_oracle_addr`. Out of scope for a minimum fix; flag as optional follow-up.

### Alternatives explicitly considered

| Option | Change | Blast radius | Why rejected / accepted |
|---|---|---|---|
| **A. Canonicalise in the assert** (proposed) | Test-only, ~3 lines | None outside the test | Smallest, keeps invariant meaning |
| B. Move `SCRATCH_BASE` back to `0x2000_0300` | Generator constant | **Regresses Stage-6 fix from `d9a66a7`.** QEMU virt drops `sw` to `0x2000_0000`; all mem/atomic QEMU-diff coverage breaks. | Rejected — would re-open the issue `d9a66a7` fixed |
| C. Add a `0x8000_0000..0x8008_2000` alias to `RESERVABLE_LO/HI` (widen bounds) | Test-visible constants | High — these constants are `pub`; consumers outside the test (`RESERVABLE_*` are referenced from the fuzz generator and the journals document them as the authoritative window). Would diverge from the emulator's own copy in `execute.rs:24-25`. | Rejected — duplicates semantics already in `canon_oracle_addr` |
| D. Relax assertion to `!= 0` or delete it | Test-only | Loses a real safety net — a future generator change could silently seed an atomic at `0x1000_0000` or a peripheral address, and mcause=7 divergence would show up as a mysterious QEMU-diff regression. | Rejected — keep the invariant |
| E. Extend reservable window in the emulator | `execute.rs:24-25` plus any datasheet-bound call sites | Changes CPU behaviour: AMO outside `[0x2000_0000, 0x2008_2000)` would no longer trap mcause=7 on the alias. Real Hazard3 traps on the 0x8 alias; the only reason our bus canonicalises is to plaster over QEMU's VIRT_FLASH. Changing the window would make the emulator more permissive than silicon. | Rejected — violates datasheet §2.1.6.2 |

## Risks / blast radius

- **Scope:** one test body, a handful of lines. No `pub` surface area touched.
- **Invariant preservation:** the canonicalised check is strictly equivalent to the old one for any address in `[0x2000_0000, 0x2008_2000)`, and correctly accepts the `[0x8000_0000, 0x8008_2000)` alias that runtime code already accepts. Addresses that would have failed the old check but are *not* the virt alias (e.g. `0x4000_0000` peripheral range) still fail, as intended.
- **No production code touched** — `canon_oracle_addr` in `crates/mdrp2350/src/bus/mod.rs`, `in_reservable` in `crates/mdrp2350/src/core_riscv/execute.rs`, and `gen_rv32a_reservable_edge_cases` in `crates/mdpicoem-harness/src/riscv_gen.rs:796-861` all remain untouched.
- **Tests to re-run:**
  - `cargo test -p mdpicoem-harness --release --lib riscv_gen` (full module: `edge_cases_rv32a` plus the other ten `edge_cases_*` siblings that must stay green).
  - `cargo test -p mdpicoem-harness --release --lib` (entire harness library tests).
  - `cargo test -p mdrp2350 --release --lib core_riscv` — sanity that no emulator behaviour slipped.
  - Optional: `cargo run -p mdpicoem-harness --release --bin test_rp2350_qemu_diff_riscv32 -- --class rv32a` if a QEMU environment is available — already passing at HEAD; should remain passing.
