# 14 Days of Building a Cycle-Accurate RP2350 Emulator

*A retrospective on `mdpicoem` — a Rust workspace that grew from an empty repo to a dual-chip, dual-architecture, silicon-validated emulator in two weeks of supervised AI-agent work.*

**Written:** 2026-04-26
**Author:** Arthur (Martin Davidson)
**Repo:** `0x4D44/mdpicoem`

---

## What it is, in 60 seconds

`mdpicoem` is a cycle-accurate emulator for the Raspberry Pi RP2350 / RP2354 (dual Cortex-M33 + a parallel RISC-V Hazard3 core + 12-state-machine PIO) and its older sibling RP2040 (dual Cortex-M0+ + PIO). Both chips live in one Rust workspace as independent library crates that share a small `mdpicoem-common` core (memory, clock tree, pacer, PIO primitives, threading primitives) and `mdpicoem-devices` (off-chip PSRAM/LCD/I²S).

The emulator boots the real RP2350 bootrom through to the secure→non-secure transition. It runs ARMv8-M Mainline (Cortex-M33) with FPU, DCP, RCP, lazy FP context save, TrustZone scaffolding, and the full peripheral suite (TIMER0/1, POWMAN, UART × 2, SPI × 2, I²C × 2, PWM, ADC, WATCHDOG, OTP, TRNG, SHA-256, IO_BANK0, PADS_BANK0, CoreSight, 16-channel DMA). The RP2040 runs ARMv6-M with the same peripheral coverage less the M33-specific bits. A parallel RISC-V Hazard3 core (RV32IMAC + Zicsr + Zifencei + Xh3Irq) shares the same bus on the M33 path.

Validation is layered:

- **Differential fuzzing** against QEMU on each ISA (Cortex-M33, Cortex-M0, RV32IMC).
- **Real-silicon oracles** over SWD via probe-rs, against an actual RP2354 (Pico 2) board and a Pico V1: ISA differential, cycle-accurate K-delta cycle catalogue, end-state peripheral diff, ISR / lazy-FP, dual-core bank-contention, plus an orchestrator (`test_silicon`) that runs them all under one probe session with a 60 s watchdog.
- **PicoGUS replay** — a real GUS firmware running on the emulated RP2040, fed an ISA-trace captured from a patched DOSBox-X, with stereo I²S sampled to WAV.
- **Coverage** at 91 % in-scope branch.

That landed in **14 days**, 538 commits, ~189 kLOC of Rust, 152 session journals, 210 HLDs/LLDs. One human, supervising teams of AI agents.

This article is the honest retrospective. What worked, what didn't, what I'd do differently if I rebuilt it from scratch tomorrow.

## The setup: how I actually worked

I am one engineer with a strong background in emulation and reasonable hardware experience. I had two debug probes on my desk (one wired to an RP2354 Pico 2, one to an RP2040 Pico V1) and a Windows machine running Claude Code with the 1M-context Opus model.

Every session followed the same shape:

1. **HLD first, code second.** For anything non-trivial I wrote (or had an agent draft) a high-level design under `wrk_docs/` with a dated, versioned filename: `2026.04.15 - HLD - Silicon Peripheral and Cycle Oracles V3.md`. The HLD got reviewed by 3–5 specialist agents in parallel (concurrency, performance, architecture, devil's advocate) before any implementation.
2. **Implementer agents land code in stages.** A fresh agent reads the latest HLD, writes a stage's code in an isolated worktree, runs the tests, summarises in &lt; 500 words.
3. **Code-reviewer + apply-feedback + devil's-advocate.** Three more agents critique the diff, the implementer applies the fixes, and a devil's-advocate looks for things the reviewer missed (it caught real bugs three times — see the M0+ CPS bit-swap, the Cortex-M33 banked-SP staleness in exception handlers, the MEIP infinite-loop hazard in the Hazard3 IRQ controller).
4. **Atomic commit, journal entry.** The supervisor (me, or a supervisor agent in a long-running session) writes a short journal under `wrk_journals/` documenting decisions, surprises, and the next step.

I never read raw agent output into my own context if I could avoid it. Agents reported in bounded summaries; long build/test logs stayed in the agent's context; my journal was the persistent state.

The result is heavily auditable. Every decision has a paper trail: the HLD that justified it, the review that pressure-tested it, the journal that records the result. That paper trail is what made it possible to keep the project coherent across 538 commits in 14 days, with at peak ~30 agents in flight at once.

It's also what made it survivable. When I made a wrong call (and there were several — the threaded-perf goose chase, the WorkerBus-monomorphization-hypothesis-that-wasn't, the agent dispatched against uncommitted HLDs), I could go back, find the moment, and recover rather than re-derive.

## How it was tested

This is the section I find hardest to write without sounding like I'm bragging. So let me just put the numbers down and explain what each layer is actually for.

The testing topology has five tiers, each catching a different class of bug:

### Tier 1 — unit tests (~4,700 across the workspace)

Per-crate `#[test]` count at the close of week 3:

| Crate | Tests |
|---|---|
| `mdrp2350` (M33 + Hazard3 emulator core) | 2,856 |
| `mdrp2040` (M0+ emulator core) | 967 |
| `mdpicoem-harness` (test-harness library) | 568 |
| `mdpicoem-common` (shared primitives) | 236 |
| `mdpicoem-devices` (off-chip device models) | 35 |
| Apps and stubs | ~32 |
| **Total** | **~4,694** |

Most of those are instruction-semantics tests, decode-edge cases, exception mechanics, clock-tree config, peripheral register behaviour. The ratio of test code to production code is roughly 1.4:1 (the largest single file in the workspace is `crates/mdrp2350/src/tests.rs` at 22,240 lines). They run in `cargo test --release` in about 90 seconds.

Roughly **1,600 of those tests** were written in a single day during the coverage push on Apr 23 — three concurrent agents grinding through every uncovered branch in the executor, decoder, FPU, PIO, and threaded-runtime paths. ~22,600 lines of test code added; zero production-code changes (one TSC-timing tolerance widened — that's it).

### Tier 2 — QEMU differential fuzzing (one oracle per ISA)

Three separate QEMU-backed differential harnesses run as independent binaries:

- **`qemu_diff_m33`** — spawns QEMU's Cortex-M33 on GDB port 3333, runs the same instruction in both QEMU and `mdrp2350`, diffs R0–R15 + xPSR with masking for architecturally-unpredictable flag fields. Throughput in solo mode: **~660 tests/s**, ~500/s when running parallel with the M0+ oracle. An 8-hour overnight session does **~14 million instruction trials** on this oracle alone.
- **`qemu_diff_m0plus`** — same idea against QEMU's `cortex-m0` (QEMU 10.2 has no `cortex-m0plus` model; M0+ is a strict ISA superset for the subset the oracle covers). ~250 tests/s solo, ~400/s parallel. ~11M trials per 8h session.
- **`qemu_diff_riscv32`** — RV32IMC differential against QEMU virt rv32. Surfaced one genuinely interesting bug: QEMU's `-machine virt` maps `VIRT_FLASH` at `0x2000_0000` (the address I'd originally used to match the RP2350 SRAM base). CFI flash silently drops CPU `sw` instructions that don't do the unlock dance, while still accepting GDB `M`-packet writes from the debugger — so every "csrrw silently no-ops" observation was actually `csrrw` working fine and the subsequent register spill being dropped into the flash bit bucket. Moved everything to `0x8000_0000` (virt DRAM) via a `canon_oracle_addr` test-mode alias. Took two days to diagnose.

A single fuzz session of `--fuzz 100000 --seed <S>` on either chip is the day-to-day "did I just regress something" gate. A `--fuzz 1000000` session is the deep regression check. Failures are deterministic: the harness prints the seed, you reproduce, you fix, you re-run the same seed.

### Tier 3 — softfloat differential (3.6M iterations on FPU + DCP)

Phase 7 (FPU and coprocessors) is the only place I built a dedicated reference oracle in pure Rust rather than leaning on QEMU. Six FPSCR exception flags (IOC/DZC/OFC/UFC/IXC/IDC) plus FTZ/DN modes are narrow enough to encode in ~414 lines without a softfloat-sys C dependency. The harness runs **~3.6 million differential iterations** across the FPU instruction set and DCP (CP4/5) operations under all four FPSCR mode permutations. Zero discrepancies found in the 23 existing arithmetic ops — they were correct, just missing flag updates, which the differential immediately surfaced.

The small amount of effort to build the oracle paid for itself within hours.

### Tier 4 — real-silicon oracles (the only honest tier)

This is the layer that catches the bugs unit tests and QEMU don't. There are five oracles, all running over SWD via probe-rs against the actual RP2354 (Pico 2) and RP2040 (Pico V1) boards on my desk:

| Oracle | What it does | Catalogue size |
|---|---|---|
| `probe_diff_rp2350` | M33 ISA differential against live silicon, register-state diff | runs against any seed (fuzz mode) |
| `probe_diff_rp2040` | M0+ ISA differential, same shape (silicon is the only oracle for the M0+ Thumb-32 subset that QEMU's `cortex-m0` model rejects) | fuzz mode |
| `silicon_cycle_oracle_rp2350` | True instruction-sequence cycle cost via K-delta protocol (each case run twice at K=101 and K=201; the delta cancels per-invocation framing) | **10 cases** |
| `silicon_periph_diff_rp2350` | End-state diff of peripheral register state, FIFOs, pin state under a CYCCNT-measured sysclk window | **32 scenarios** (PIO, PLL, clock-tree, DMA, UART, SPI, I²C, ADC, PWM, POWMAN, WATCHDOG, OTP, TRNG, SHA-256, IO_BANK0) |
| `silicon_isr_diff_rp2350` | ARMv8-M exception entry, lazy FP context save, tail-chained ISRs, external IRQ priority preempt | **9 scenarios** (cold PendSV, lazy FP save, eager FP save, PendSV+SysTick tail-chain, TIMER0 cold, masked-pending, priority-preempt) |
| `silicon_dualcore_diff_rp2350` | Cross-core contention oracle — bank thrash, spinlock churn, FIFO transfer with antagonist running on core 1 | scenario set |
| `silicon_periph_diff_rp2040` / `silicon_isr_diff_rp2040` | RP2040 siblings of the above | smaller catalogues |

All of these get wrapped under the **`test_silicon` orchestrator**, which runs them all under one shared probe session with a 60 s per-case watchdog and probe drop-and-reattach on transient errors. `test_silicon --soak <duration>` shuffles every oracle's case order Fisher-Yates per iteration, prints failures immediately + hourly heartbeat, and survives multi-day unattended runs.

The orchestrator is what made overnight silicon fuzzing actually viable. Without it, a single transient probe error would terminate the run.

The real-silicon oracles are where the project's most important bugs were caught:

- **PLL LOCK always-1** (CS[31] forced unconditionally instead of polling-then-locking after ~1133 sysclks) — only visible because `silicon_periph_diff_rp2350`'s `pll_sys_lock_timing` scenario diffed register state under a 1133-sysclk window.
- **PIO side-set `pad_oe` leak** — the emulator drove `pad_oe` regardless of `PINDIRS`; RP2350 §11.3.2.3 says side-set drives values onto pads but `PINDIRS` solely owns `pad_oe`. The `pio0_side_set_toggle` scenario flagged a pin-state divergence at sysclk 83.
- The Hazard3 RV32 csrrw goose chase mentioned above.

Without the silicon tier, both PLL and PIO bugs would have shipped to V1.

### Tier 5 — overnight unattended fuzz campaigns (~72 hours of fuzz cumulative)

Once the harness infrastructure was solid, I started running overnight campaigns:

| Date | Duration | Oracles | Notes |
|---|---|---|---|
| 2026-04-13 night | 8 h | QEMU M33 + bug-fix wave | First overnight; surfaced 3 emulator bugs |
| 2026-04-14 night | 8 h | QEMU M33 + M0+ + RP2354 silicon ISA diff | Three oracles in parallel |
| 2026-04-15 night | 8 h | QEMU + silicon | Operational debt cleanup |
| 2026-04-16 night | ~14 h | RP2040 probe soak | First sustained RP2040 silicon run |
| 2026-04-18 night | 8 h | Silicon orchestrator first soak | Tested `test_silicon --soak` UX |
| 2026-04-19 night | 8 h | Silicon (regression-gate replay) | 4,659 silicon iters + 420 k RP2040 ISA tests |
| 2026-04-20 night | 8 h | Silicon (day-over-day stability) | Same residual signature as 04-19 — clean |
| 2026-04-24 night | 8 h | QEMU + silicon | Concurrent with active dev |
| 2026-04-25 night | 8 h | QEMU M33 + M0+ + silicon (4 oracles) | 4-driver campaign, deepest run of the project |

Cumulative across those nine sessions, the fuzz tally is roughly:

- **M33 QEMU differential:** ~100 million instruction trials.
- **M0+ QEMU differential:** ~80 million instruction trials.
- **RV32 QEMU differential:** smaller, came later in the project. ~5 M.
- **Silicon ISA differential** (`probe_diff_*`): ~250 k iterations cumulative, against a live silicon DUT.
- **Silicon orchestrator** (`test_silicon --soak`): ~5 k full catalogue passes, each running cycle + periph + ISR + dual-core oracles end-to-end.

That doesn't include the 3.6 M FPU differential, the per-PR smoke runs (every change ran `--fuzz 100000` minimum on the affected oracle before commit), or the ~4,700 unit tests on every push.

Each overnight session was supervised the same way: I went to sleep, an agent driver loop ran the oracles in batches with random seeds per batch, monitor tools fired notifications on `[FAIL]` / `panicked` lines, and a triage agent waited to investigate any failure. By morning I had a journal entry summarising what ran, what found, and what's now in `tech_debt.md`.

The overnight runs are how the residual cycle deltas in `tech_debt.md` got their honest 1 % confidence labels. You can't get that from a one-shot test. You only get it after the same residual signature reproduces deterministically across two consecutive overnight soaks — the journal of 2026-04-20 gleefully calls itself a "day-over-day stability replay" because the previous night's residual list reproduced exactly.

### What this cost

I'm a one-person project. The fuzz machine ran on my desktop while I slept. The probes were under a desk lamp. I wasn't paying for cloud CI cycles or test-fleet infrastructure.

Roughly:

- **Wall-clock fuzz hours:** ~72 of overnight + ~10–15 of daytime per-PR + sporadic. Call it **~90 hours** total.
- **Engineering hours building the test infrastructure:** roughly 30 hours across the project (the QEMU harness, the probe-rs harness, the silicon scenario catalogues, the `test_silicon` orchestrator, the fuzz drivers, the triage tooling). Maybe 10 % of total project effort.
- **Bugs caught:** at least 9 real emulator bugs that I can clearly attribute to a specific oracle finding — the inherited CPS bit-swap, the M0+ banked-SP staleness, the SG instruction missing, the PLL LOCK, the PIO pad_oe leak, three FPU flag-update gaps, the RV32 csrrw oracle blind. Probably more I'm forgetting.

The ratio that matters: **9-ish caught bugs per 30 hours of test-infrastructure investment**, plus enormous confidence in everything that *didn't* fail. The unit tests prove the code does what I think it does; the differential oracles prove what I think is correct actually is.

That last sentence is the whole point of differential testing and I'm going to put it in bigger letters because I keep forgetting:

> **A test that you wrote yourself only proves the code does what you thought when you wrote it.**
> **A differential oracle proves the code does what something else thinks is correct.**

Real silicon is the highest-authority "something else" you can have.

## Week 1: empty repo to dual-chip emulator (Apr 12–15)

### Sunday Apr 12 — the master HLD

`wrk_docs/2026.04.12 - RP2350 Emulator HLD.md` was the only artefact of day zero. It set the seven-phase shape that the next ten days would follow:

| Phase | Scope |
|---|---|
| 1 | Thumb-2 ISA decode + execute (M33) |
| 2 | AHB5 bus fabric, SRAM banking, atomic aliases |
| 3 | NVIC, exceptions, faults, secure boot |
| 4 | Flash boot end-to-end |
| 5 | Dual-core SIO (FIFO, spinlocks, divider, MTIME, doorbells, WFE/SEV) |
| 6 | PIO (3 blocks × 4 state machines) |
| 7 | FPU + coprocessors (DCP CP4/5, RCP CP7) |

The HLD identified TrustZone as scope ("designed but not built in v1"), declared Hazard3 RISC-V out of scope, and called the pacer a "critical design decision" because the host is a pre-emptively scheduled Windows OS. The cycle counter would be a single `u64` master, monotonically driven, with all timing derived from it. That decision held the whole way through; I'd make it again.

### Monday Apr 13 — the seven-phase sprint

Phases 1–5 landed on a single day. 99 commits. The shape was:

- **Phase 1 (Thumb-2)** — full Thumb-16 + Thumb-32 decode+execute, 11 sub-stages culminating in 100 % instruction coverage including DSP and FPU encodings. The QEMU Cortex-M33 differential harness (`qemu_diff_m33`) was already running by mid-morning, fuzzing against a real QEMU reference. By evening we had an early bootrom run reach PC=`0x7EA4` — the secure→non-secure transition, deep into the real `pico-bootrom-rp2350` code path.
- **Phase 2 (Bus Fabric)** — AHB5 address decode, 10-bank SRAM map, APB bridge latency (3 R / 4 W cycles), 2-master arbitration, atomic-access aliases (XOR/SET/CLR via `+0x1000/0x2000/0x3000`). A devil's-advocate review at this stage punted bus-bank contention modelling to Phase 5; in the end we never built it for RP2350, and that turned out to be the right call (see "what I'd do differently").
- **Phase 3 (Interrupts/Faults/Boot)** — PPB, NVIC, SCB, SAU stubs, MPU stubs, exception entry/exit, fault delivery, the `TT` (test target) instruction. The bootrom actually executes 12 distinct boot steps inside the emulator — clock setup, QMI init, RCP canary ops, SAU verification via TT — before doing the `bxns` to non-secure code.
- **Phase 4 (Flash Boot)** — the SG (secure gateway) instruction was missing; without it the nsboot callback was decoded as LDRD and silently corrupted registers. With SG, blinky boots from a flashed image and toggles GPIO 25 in 58,969 cycles.
- **Phase 5 (Dual-core SIO)** — Core 1 launches via the FIFO handshake. The blocker was the RCP handler: the bootrom's Core 1 path uses `rcp_canary_status pc` (MRC2 encoding `0xFE30`) and `rcp_salt_coreN` (MCRR2 encodings `0xFC4x`), and the existing handler only matched the `0xEE` MCR T1 prefix. Splitting the handler into MCR/MCR2 and MCRR/MCRR2 families with proper `(opc1, CRm)` discrimination unblocked Core 1.

Two findings from Phase 5 stuck with me:
> *"The bootrom echoes ALL values (including zeros). Core 0 must drain each echo to prevent FIFO backpressure. Without this, Core 1 remains stuck in receive_and_check_zero."*

> *"Bus contention is asymmetric. Core 0's progress is unaffected by Core 1's concurrent bootrom execution — contention stalls only Core 1."*

Both are the kind of detail you only learn by running the actual silicon's bootrom against your model and watching where it diverges.

### Tuesday Apr 14 — workspace restructure mid-flight

By Monday evening the codebase had outgrown its single-crate shape. I wanted RP2040 as a peer, not as a feature flag, and I wanted PIO + memory + clock primitives in one shared place. The restructure happened mid-flight in 7 phases:

1. Capture `paced_bench` baseline (32.9 MHz emulated).
2. Rename `mdrp2354 → mdrp2350`, drop stub crates, fix MSRV inheritance.
3. Extract `mdpicoem-common` (memory, clock, pacer, PLL math, FIFO, divider, PIO).
4. Stub `mdrp2040` — and immediately surface that `Memory::new()` had hardcoded RP2350 sizes, requiring a `with_sizes(rom, sram)` constructor.
5. Build the RP2040 M0+ core. The devil's-advocate review on this stage caught a **CPS bit-swap bug that had been silently inherited from the RP2350 codebase**: ARMv6-M says bit 1 = I-flag, the code was checking bit 0. The test was passing because it encoded `CPSIE f` (bit 0 = F) and the assertion happened to work for the wrong reason. Bug fixed retroactively in both chips.
6. Build the RP2040 bus + peripherals. The same review caught **banked SP staleness in exception entry/exit** — `enter_exception` / `exit_exception` were reading `msp`/`psp` directly, but a handler doing `SUB SP, #N` updates `r[13]` without syncing back to the banked field. Every SDK handler with stack locals would have silently corrupted state. Fixed with explicit `sync_sp_to_banked` / `sync_sp_from_banked` calls.
7. Split the test harness, build a `qemu_diff_m0plus` binary against QEMU's `cortex-m0` model. Discovery: `mdpicoem_harness::compare` had hardcoded M33 address bases, so 100 % of M0+ fuzz tests were false-failing until the `CompareBases` struct landed.

At the end of Tuesday: 1088 tests, paced-bench within 0.3 % of baseline.

The same day a second team finished **Phase 7 — FPU and coprocessors**: VFPv5 single-precision, FPSCR exception flags, FTZ/DN modes, lazy FP context save (the most invasive change, with a subtle `LSPACT` leak that needed a `UsageFault.INVPC` integrity check on `FType=1 + LSPACT=1` mismatch on exception exit), full DCP and RCP coprocessor dispatch. **3.6 million differential fuzz iterations** against a hand-rolled IEEE-754 reference oracle, four FPSCR modes, no discrepancies.

I deliberately chose the hand-rolled oracle (~414 LOC) over `softfloat-sys`. The C dependency is fragile on MSVC and the scope was narrow — six FPSCR flags, enumerable. This was the right call: the oracle is in pure Rust, compiles instantly, and has been stable since.

A third team in parallel ran the **Threaded Dual-Core HLD review loop**. V1 was written, then critiqued by four agents (concurrency/correctness, performance, architecture, devil's advocate) and revised to V2, V3, V4, V5 over the next 48 hours. By Friday it was signed off, but the implementation didn't begin in earnest — that was a deliberate decision to land the serial path first, validate it against silicon, and only then introduce a threading model that could trade against it.

### Wednesday Apr 15 — first real silicon, first real emulator bugs

The two silicon oracles came up against the actual RP2354 board:

- **`silicon_cycle_oracle_rp2350`** measures true instruction-sequence cycle cost via a measurement stub plus a mailbox handshake. Each case runs twice at K=101 and K=201 iterations; the K-delta cancels per-invocation framing (BLX/BX, stub entry) to isolate steady-state cost.
- **`silicon_periph_diff_rp2350`** runs identical MMIO setups under a CYCCNT-measured sysclk window on both silicon and a `step_quantum=1` emulator, then diffs a scenario-declared set of registers, FIFOs, and pin states.

The first peripheral oracle run produced exactly the kind of result you want from an oracle: **two real emulator bugs surfaced immediately**:

1. **PLL LOCK always 1** — the emulator forced `CS[31]=1` unconditionally; silicon takes ~1133 sysclks to actually lock. Same bug existed in the RP2040 model; both have been logged in `tech_debt.md`.
2. **PIO side-set `pad_oe` leak** — the emulator drove `pad_oe` regardless of `PINDIRS`; RP2350 §11.3.2.3 says side-set drives values onto pads but `PINDIRS` (set via SET/OUT/MOV PINDIRS) solely owns `pad_oe`. Fixed (commit `5eac6a1` and follow-up).

Both bugs would have been almost impossible to find without real silicon. Synthetic tests can't tell you that the state you've designed is wrong.

End of Week 1: dual-chip framework, both ISAs running through the bootrom, FPU validated, two real bugs caught by silicon, threading HLD signed off. 261 commits.

## Week 2: RISC-V, real silicon at scale, and the perf mystery (Apr 16–21)

### The Hazard3 RISC-V port

The original master HLD said RISC-V was out of scope. Three days in, I changed my mind. The RP2350 ships with two pairs of cores (M33 × 2 and Hazard3 RV32IMAC × 2) — the architecture switch is firmware-selectable. Skipping RISC-V meant skipping half the chip, and the work to share the bus turned out to be smaller than expected.

The decision was: **single Cores enum + dual-dispatch, not separate emulators**. Both ISAs share `Bus`, `SIO`, peripherals, clocks, DMA, PIO, the memory map. Justification:

- Memory hierarchy (OTP, flash, SRAM offsets) must agree.
- Clock sync is trivial via single `Clock` struct.
- Silicon-oracle consistency is guaranteed — same hardware produces one set of cycle counts.

The cost is ~1–2 dispatch branches in hot paths. Acceptable.

P1a–P5 of the Hazard3 port landed in a single Thursday. The team was 8 implementer agents, 10 reviewers, 5 apply-feedback rounds. Final state: 1160 mdrp2350 lib tests + a smoke firmware binary booting on the RV32 path.

### The Coverage Gap Fill

In parallel, the RP2350 Peripheral Coverage HLD went from V1 to V10 over four days as we kept finding peripherals that needed real semantics, not just register storage. The final HLD is monumental: 6 stages, 45+ new registers, the interpolator's nine CTRL bits (SHIFT, MASK, SIGNED, CROSS_INPUT, CROSS_RESULT, ADD_RAW, FORCE_MSB, BLEND, CLAMP) with W1C `OVERF` semantics, real WATCHDOG with reset plumbing, OTP 16 KB fuse storage, TRNG, SHA-256 via the `sha2` crate.

Three datasheet errors surfaced *during implementation*, not during HLD review:

- SPI1 base is `0x4008_4000`, not the `0x4000` stride the HLD guessed.
- I²C1 is `0x4009_4000`, same.
- WATCHDOG_BASE is `0x400D_8000`, not `0x4005_8000` (which clashed with `PLL_USB`).

Hardware address spaces are notoriously error-prone; future projects need a "datasheet verification spreadsheet" front-loaded into the HLD.

### The PicoGUS side-quest

Halfway through the week I started a parallel thread: get a real **PicoGUS** firmware (a Pico-based emulation of the Gravis Ultrasound) playing real audio inside the emulated RP2040, fed an ISA-bus trace captured from a patched DOSBox-X running Monkey Island.

This was supposed to be a small integration smoke test. It became a multi-day debug saga across PSRAM dispatch, PWM clock alignment, I²S framing, OPL3 register-write capture, ISA write-drop rates, and the FFR sample-rate pipeline. The audio output progressed through:

1. **Silence** — diagnosed via a tracing-instrumented I²S sink as "the firmware never actually pushed sample data; the trace is dropping 81 % of writes in deciles 0–50 %."
2. **Noise** — frame width fixed, sample rate wrong.
3. **Silence again** — different cause, different layer.
4. **Audible melody at the wrong pitch** — eventually +3 octaves off, but recognisable as the Monkey Island theme.

I shipped it in that state. The pitch error is documented; correcting it would mean re-deriving the FFR scaling against silicon timing. Whether anyone cares enough to chase it is a future-Arthur problem.

The honest learning here: PicoGUS was a feature creep. It was fun, it stress-tested the emulator under a real workload, and the diagnostic infrastructure (tracing on PIO TXF writes, on I²S LRCLK edges, on BCLK at 1.5 MHz) is reusable. But it ate four to five days of engineering attention I could have spent on coverage or RP2040 IRQ work, and the end state isn't shippable as a demo.

If I were doing this again, the rule would be: integration demos against real workloads are valuable but only if you commit a hard time budget. PicoGUS budget should have been "two days, then either it sounds right or we accept silence and move on."

### The threaded-perf mystery

This is the most embarrassing and most useful episode of the project. I include it in full because it's the kind of thing a postmortem usually elides.

The threaded execution model was supposed to deliver dual-core scaling — two host threads, each running one emulated core, barrier-synchronised at quantum boundaries. The first measurement showed 25 MHz emulated throughput on a workload that the serial single-thread runtime was hitting at 232 MHz. **Threading was nine times slower than serial.**

The samply profile said 60 % of aggregate worker time was in barrier spin. Plausible cause: barrier overhead per quantum dominates. So I (well, an agent under my supervision) shipped three speculative fixes over a day:

1. Hybrid spin+park barrier (spin for ~2.5 µs, then `Condvar::wait` to let idle cores actually sleep).
2. Worker body hoist (read `is_halted` once per quantum instead of per instruction).
3. `step_no_atomics` fast path skipping three atomic loads per instruction.

All three are architecturally sound. **None of them moved the needle.** Still 25 MHz.

Two more days of profiler-led speculation. Then a different agent did something basic: stripped out the entire benchmark wrapper. Ran the executor directly, no `Pacer`, no monitor thread, no stats tracking — just executor + workload. Result:

| Runtime | sq=64 | sq=256 | sq=1024 | sq=4096 |
|---|---|---|---|---|
| serial | — | — | — | 232 MHz |
| threaded | 97 | 216 | **307** | 251 |

Threading at quantum=1024 was *winning*. The 25 MHz cap was the benchmark harness, not the executor.

Drilled into `paced_bench_rp2350`. Found a one-line bug at `threaded/emulator.rs:584`:

```rust
let mut target: u64 = 0;                    // BUG
for _ in 0..n {
    target = target.wrapping_add(step_q as u64);
    while ... && core.cycles() < target { core.step(...) }
    barrier.wait();
}
```

`target` is local, zeroed on every call to `run_quanta`. But `core.cycles()` is persistent. After call 1 (150 M cycles of real work), call 2 entered with `core.cycles() = 150_003_713` and `target = 0`. First iteration set `target = 4096`. Inner-loop predicate `150_003_713 < 4096` is false. So the loop skipped. Every quantum after the first call did **zero work**, just barrier-synced and returned.

One-line fix:

```rust
let mut target: u64 = core.cycles();
```

After fix: 250 MHz on the basic workload at sq=256, 450 MHz on fpu-heavy at sq=4096. The original speculative fixes from days 3–4 stayed in — they were correct, and they still help on small quantum sizes. They just didn't touch the actual problem.

The lesson is stark: **strip your instrumentation before you debug performance**. The samply trace was honest about what it was measuring (barrier spin), but barrier spin was a *consequence* of the bug — workers had no work to do, so they spent all their time waiting. The profiler was telling the truth and I was reading it wrong for three days.

### The probe-rs upstream patch

Late in the week, the silicon oracle suite stopped working: probe-rs 0.31 was hitting an `unreachable!()` panic in `select_ap_and_ap_bank` whenever the RP2354's V2-AP (core 0 at `ApV2Address(0x2000)`) was accessed while the SelectCache was still DPv1. This happens whenever the initial DPIDR read returns a stale/glitched value, leaving the cache unupgraded.

It's a known upstream bug — GitHub issues `probe-rs/probe-rs#3872` and `#3257`, both open since April 2025, no fix merged.

The right move was: vendor a patched fork now, submit upstream in parallel.

The patch is 23 lines. It adds a `(V2, DPv1)` arm to the cache-state match that does an in-place DPv3 cache upgrade on first V2 AP access, with a one-shot WARN sentinel so we'd know if it ever fired more than once per session (which would mean we're masking a deeper DP bug). Wired via `[patch.crates-io]` in the workspace `Cargo.toml`.

Result: silicon oracle suite unblocked. The sentinel fires exactly once per session, as expected. The WARN is logged in `tech_debt.md` along with the upstream issue number; the moment probe-rs ships a release with the upstream fix, we drop the fork and the patch.

The PR draft is at `wrk_docs/2026.04.21 - DRAFT - probe-rs PR body.md`, ready to submit.

## Week 3: dual execution model, coverage push, OSS prep (Apr 22–26)

### The dual execution model

The big architectural decision of week 3, and one I genuinely went back and forth on, was: **does Threaded replace Serial, or sit alongside it?**

The naive answer is "Threaded should always win." It doesn't. Measured crossover on real workloads:

- **OneROM CPU-mode (a real production workload):** Serial wins at ~22 MHz, Threaded ~18 MHz.
- **Synthetic FPU-heavy at large quantum:** Threaded wins, by a lot (450 MHz vs 256 MHz).
- **Anything peripheral-heavy or short-quantum:** Serial wins.

The HLD V1 (`2026.04.24 - HLD - Dual Serial and Threaded Execution Models V1.md`) made the call explicit:

> *"We do not pick a winner model. Workload-dependent. We do not delete the serial path. Ever. We do not change the default model. Default stays Serial."*

The implementation: a runtime selector on the builder, not a compile-time feature flag. Both models expose the same public API. Threaded returns `Err(NotSupportedInThreadedMode)` on `step()` (single-stepping doesn't make sense in a barrier-synchronised model). All oracles — QEMU diff, probe diff, silicon diff — run Serial. Serial is the oracle-validated reference; Threaded is opt-in for crossover workloads.

This decision feels obvious in retrospect. It wasn't, going in. The pull to "make the new thing the default" is strong. Resisting it kept Serial as a clean, oracle-validated reference path that we can always trust, and made Threaded a tool you reach for when you've measured that you need it.

### The coverage push to 91 % (not 98 %)

I budgeted a day to take in-scope branch coverage from 70.74 % to 98 %. Sixteen stages, ~30 agents in flight, ~1,600 new test functions, ~22,600 lines of test code, **zero changes to production code** (one TSC-timing tolerance widened — that's it).

We landed at 91.19 %, not 98 %.

Three categories of blocker:

1. **Architectural ceilings (~80 branches).** Things you genuinely can't cover: I²C ACK arms gated by an empty-set `ALWAYS_ACK_ADDRS` constant, `debug_assert!` tautologies (`shift >= 32` on a 5-bit field), WFI/WFE-wait false arms requiring live firmware to execute the exact instruction.
2. **Reachable but unwritten (~396 branches).** SSAT/USAT saturation variants, FPU edge-flag combinations, NVIC priority-level edges. Each needs a focused test. ~10–15 hours of work.
3. **Rate limits.** Three concurrent agents hit the platform's request limit simultaneously. Stage 8 ended partial.

The other lesson: **measure your assumption before you build for it.** I'd hypothesised that a chunk of the residual gap was a `cargo llvm-cov --branch` monomorphization artefact — that paths generic over `B: CoreBus` recorded separate branches for `Bus` vs `WorkerBus` instantiations. An agent built 99 WorkerBus-only smoke tests against this hypothesis. Coverage moved by **6 branches**. The monomorphization-aggregation hypothesis was wrong; `--branch` aggregates across instantiations and reports source-level control flow. Three agent-hours, gone.

It would have taken 20 minutes to read the `cargo-llvm-cov` source first.

### The tech-debt sweep

The final day, I ran a 4-agent parallel audit of the whole codebase, then a devil's-advocate review that downgraded or rejected most of their findings (three of four agents over-flagged phased `#[allow(dead_code)]` placeholders as debt). The net residual debt — the stuff that's actually load-bearing — clusters into five real items:

1. Documentation rot in `CLAUDE.md` (three lines about a `Peripheral` trait that was deleted weeks ago).

## What I'd do differently

In rough order of how much pain it caused:

### 1. Strip instrumentation before debugging perf

Three days lost on the threaded-perf goose chase because the benchmark wrapper was masking the executor. The real bug was one line. The fix took five minutes once the benchmark wrapper came off. Future rule: when measuring, run the most stripped-down configuration that still represents the workload, *before* trusting the profile.

### 2. Commit HLDs before dispatching agents

Twice — once in the oracle-fix-team week-2 wave, once in the dual-execution-model rollout — I dispatched implementation agents into worktrees against HLDs that were still uncommitted. Worktrees only see committed state. The agents flailed; I had to recall and re-dispatch. Future rule: HLD signed off → commit → dispatch. No exceptions.

### 3. Front-load datasheet-address verification

Three peripheral base addresses (SPI1, I²C1, WATCHDOG) were wrong in the HLD because I'd inferred them from "stride." Real silicon caught all three during implementation, but each one cost ~30 minutes of debug. A one-page spreadsheet — base address, alias range, register-by-register offset, datasheet section reference — would have caught these in the HLD review.

### 4. Hard time-budget integration demos

PicoGUS was supposed to be a smoke test and became a multi-day saga ending in Monkey Island playing 3 octaves too high. Future rule: integration demos are valuable, but they get a 2-day budget and a hard "does it work or not" gate. If you can't decide at the gate, accept silence and document why.

### 5. Test the assumption before you build against it

The WorkerBus-monomorphization-coverage hypothesis cost three agent-hours and 99 useless tests. Twenty minutes of reading the `cargo-llvm-cov` source would have killed it. Future rule: when a hypothesis would change the size of your work by more than ~10×, validate it cheaply before scaling up.

### 6. `pub(crate)` from day one

The `Emulator` struct exposes `pub cores`, `pub bus`, `pub clock` for legacy reasons — direct field access was the path of least resistance early on. The threaded execution model needs to redirect those fields to placeholders after `promote_to_threaded`, and we have a debug-only `bus_is_placeholder` guard, but it only catches typed-API callers. Raw `.bus.` / `.cores[` / `.clock.` access bypasses the guard silently. Migrating ~1,287 call sites to typed accessors is a major project; doing it from day one would have been a 30-minute decision. Future rule: default to `pub(crate)`, expose only what callers need.

### 7. Resist HLD-version sprawl

Some HLDs went to V10. The latest is canonical, but a directory full of V1–V10 makes new contributors second-guess which to read. `CLAUDE.md` does explicitly say "prefer later-dated versions," but a `wrk_docs/archive/` for superseded versions would be cleaner. Future rule: V3+ moves predecessors to `archive/`.

### 8. Don't over-trust the devil's-advocate when the agent is rate-limited

Three of four tech-debt-audit agents over-flagged phased `#[allow(dead_code)]` as debt because they couldn't read every HLD into context. The DA caught it. But the DA was the only thing standing between me and a multi-day "fix" of code that wasn't broken. Future rule: tech-debt audits get a DA pass *before* the action plan is written, not after.

### 9. Don't re-litigate "won't-do" items

The bus-bank-contention-modelling decision (deferred Phase 2, declined Phase 5, declined again in week 3) keeps coming back. The reasoning is solid every time — virtual contention cycles don't consume host compute, the threaded model bypasses the interleave path, the perf gap against silicon dwarfs the accuracy gain by an order of magnitude — but I keep having to write it down. Future rule: a "won't-do" decision gets its own dated journal entry in `wrk_journals/` so the next agent can find it instead of re-deriving.

## Closing thought

The thing this project demonstrated to me, over and over, is that the bottleneck in modern software engineering is not typing speed and not even reasoning capacity. It's *coordination overhead* — keeping decisions, designs, and work-in-progress legible across many parallel actors over many days.

The HLD-first, journal-tracked, devil's-advocate-reviewed pattern works because it externalises the coordination state. When I'm working with one agent it feels like overhead. When I'm running ten in parallel, it's the only thing that keeps the project coherent.

The other thing it demonstrated is that real silicon is the only honest oracle. QEMU is a great differential against ISA correctness but it doesn't model RP2354 peripherals, and unit tests can only catch the bugs you thought to write. Two of the most embarrassing bugs in the codebase — the PLL LOCK always-1, the PIO side-set `pad_oe` leak — were invisible until the first silicon oracle run. Both would have shipped to V1 without the probe in the loop.

If you're building an emulator, get hardware on your desk early. If you're working with AI agents at scale, write more HLDs than feels comfortable. And strip your instrumentation before you debug performance.
