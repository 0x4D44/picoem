# Residual C.2.1 — DMA timer-paced fix

**Date:** 2026-04-17
**Parent HLD:** `wrk_docs/2026.04.17 - HLD - Stage C.2 DMA Silicon Stall Investigation Handoff.md`
**Parent journal:** `wrk_journals/2026.04.17 - JRN - Silicon Oracle Residuals Fix Wave.md`
**Silicon symptom:** `BKPT timeout: PC=0x2000_115A SP=0x2004_0000 LR=0xFFFFFFFF` for scenario `dma_timer_paced`.
**Key context update since parent HLD:** 2 of 3 C.2 DMA scenarios now PASS on silicon without any fix (`dma_mem_to_mem_32bit`, `dma_chain_trigger`). Only `dma_timer_paced` remains. This partly falsifies the parent HLD's bootrom-init hypothesis and strongly biases the investigation toward a scenario-local cause.

**Failure-PC decode:** `SILICON_RUN_SLED = 0x2000_1100`, so `PC = 0x2000_115A` is at byte offset `0x5A = 90`. From the sled table at `crates/mdpicoem-harness/src/silicon_scenarios.rs:1828`, halfword index `[45]` sits at byte 90 — that is the `ldr r2, [r1, #0x0C]` read of `CH0_CTRL_TRIG` inside the BUSY-poll loop. So silicon hangs exactly the same way the parent HLD described for the other two scenarios, but only for timer-paced: DMA accepted the trigger, `BUSY=1` latched, BUSY never clears, the CPU loops forever reading CTRL_TRIG until `BKPT_TIMEOUT` (5 s) fires.

---

## 1. Scope narrow-down: the 3 DMA scenarios side-by-side

All three scenarios share the same reset-and-halt path, the same RESETS setup (`RESETS_RESET + ALIAS_CLR, RESET_DMA_BIT`), the same sled-authoring patterns (MOVW/MOVT/STR/LDR/TST/BNE/BKPT), the same RP2350 CTRL bit positions from `a7266bf`, and the same BUSY-poll loop structure. Sled-by-sled deltas that would be visible to silicon:

| Aspect | dma_mem_to_mem_32bit | dma_chain_trigger | **dma_timer_paced** |
|---|---|---|---|
| CTRL value (ch0) | `0x007E_0059` | `0x007E_2059` | `0x0076_0059` |
| CTRL.TREQ_SEL | `63` (FORCE) | `63` (FORCE) | **`59` (TIMER0)** |
| CTRL.CHAIN_TO | `0` (self=no chain) | `1` (→ ch1) | `0` (self=no chain) |
| Channels used | ch0 only | ch0 + ch1 | ch0 only |
| Extra register writes before CTRL_TRIG | READ_ADDR, WRITE_ADDR, TRANS_COUNT | both channels' READ/WRITE/COUNT + ch1 AL1_CTRL | READ_ADDR, WRITE_ADDR, TRANS_COUNT, **DMA_TIMER0 (= `DMA_BASE + 0x420`)** |
| Channel count | 4 words × 4 bytes | 1 word per channel | 4 words × 4 bytes |
| TRANS_COUNT ch0 | 4 | 1 | 4 |
| Status on silicon | **PASS** | **PASS** | **FAIL** (BUSY never clears) |
| Status on emulator (unit test) | PASS | PASS | PASS |

Deltas that localise to the timer-paced scenario and would plausibly cause BUSY to never clear:
- **`TREQ_SEL = 59` (DREQ_TIMER0)** instead of `63` (FORCE). FORCE bypasses the DREQ matrix entirely, so as long as EN=1 and TRANS_COUNT>0 the channel fires on every tick. TREQ_SEL=59 gates transfers on DREQ_TIMER0, which must be asserted by the DMA's internal pacing timer 0. If that timer is never programmed, or is programmed to 0/0 (both reset), DREQ_TIMER0 never fires and the channel stalls indefinitely — BUSY stays set, busy-poll spins forever. **This is exactly the observed symptom.**
- **The sled writes DMA_TIMER0 at `DMA_BASE + 0x420`** (sled halfwords [18..25]). If the silicon register at `0x5000_0420` is not DMA_TIMER0, the write hits some other register (or reserved space), TIMER0 stays at its reset value of `0x0000_0000` (X=0, Y=0), and no DREQ is ever produced.

The other two scenarios use `TREQ_SEL=63` and never program a pacing timer, so neither can catch this bug. This is consistent with exactly the one scenario failing.

The deltas localise cleanly. The scenario-local framing stands.

## 2. Root-cause hypothesis: wrong DMA_TIMER0 register offset

**The sled (and the emulator) use `DMA_BASE + 0x420` for DMA_TIMER0, but the RP2350 datasheet says DMA_TIMER0 is at `DMA_BASE + 0x440`.**

### 2.1 Datasheet evidence (RP2350 §12.6.6)

From the datasheet extract at `wrk_scratch/rp2350_ds.txt`:

- Line 75327–75341 (authoritative heading):
  > **DMA: TIMER0, TIMER1, TIMER2, TIMER3 Registers**
  > **Offsets: 0x440, 0x444, 0x448, 0x44c**
  > Pacing (X/Y) fractional timer. … X = dividend (bits 31:16), Y = divisor (bits 15:0).

- Line 74378–74400 (global DMA register table; the "Info" column in this PDF extraction is shifted, but the offset/name columns are authoritative):
  ```
  0x400  INTR                  Interrupt Status (raw)
  0x404  INTE0                 Interrupt Enables for IRQ 0
  0x408  INTF0                 Force Interrupts (IRQ 0)
  0x40c  INTS0                 Interrupt Status (IRQ 0)
  0x414  INTE1                 Interrupt Enables for IRQ 1
  0x418  INTF1                 Force Interrupts (IRQ 1)
  0x41c  INTS1                 Interrupt Status (IRQ 1)
  0x424  INTE2                 Interrupt Enables for IRQ 2
  0x428  INTF2                 Force Interrupts (IRQ 2)
  0x42c  INTS2                 Interrupt Status (IRQ 2)
  0x434  INTE3                 Interrupt Enables for IRQ 3
  0x438  INTF3                 Force Interrupts (IRQ 3)
  0x43c  INTS3                 Interrupt Status (IRQ 3)
  0x440  TIMER0                Pacing timer (generate periodic TREQs)
  0x444  TIMER1                Pacing timer (generate periodic TREQs)
  0x448  TIMER2                Pacing timer (generate periodic TREQs)
  0x44c  TIMER3                Pacing timer (generate periodic TREQs)
  0x450  MULTI_CHAN_TRIGGER    Trigger one or more channels simultaneously
  0x454  SNIFF_CTRL            Sniffer Control
  0x458  SNIFF_DATA            Data accumulator for sniff hardware
  0x460  FIFO_LEVELS           Debug RAF, WAF, TDF levels
  0x464  CHAN_ABORT            Abort an in-progress transfer sequence
  0x468  N_CHANNELS            The number of channels this DMA instance is equipped with
  ```

- Compare to RP2040 datasheet §2.5.7: TIMER0..3 at `0x420..0x42c`, MULTI_CHAN_TRIGGER `0x430`, SNIFF_CTRL `0x434`, SNIFF_DATA `0x438`, FIFO_LEVELS `0x440`, CHAN_ABORT `0x444`, N_CHANNELS `0x448`. **Identical to what the emulator uses today.**

Structural explanation: RP2350 adds two IRQ groups (INTE2/INTF2/INTS2 at `0x424..0x42c` and INTE3/INTF3/INTS3 at `0x434..0x43c`). These are new MMIO that didn't exist on RP2040. Every register from `0x420` onward shifts up by `0x20` bytes relative to RP2040.

### 2.2 Emulator current state (confirming the bug)

File `crates/mdrp2350/src/dma.rs:79–88`:
```rust
const REG_TIMER0: u32 = 0x420;
const REG_TIMER1: u32 = 0x424;
const REG_TIMER2: u32 = 0x428;
const REG_TIMER3: u32 = 0x42C;
const REG_MULTI_CHAN_TRIGGER: u32 = 0x430;
const REG_SNIFF_CTRL: u32 = 0x434;
const REG_SNIFF_DATA: u32 = 0x438;
const REG_FIFO_LEVELS: u32 = 0x440;
const REG_CHAN_ABORT: u32 = 0x444;
const REG_N_CHANNELS: u32 = 0x448;
```

Every one of these is at the RP2040 offset. Nothing for INTE2/INTF2/INTS2/INTE3/INTF3/INTS3 exists. `0x424..0x42c` / `0x434..0x43c` currently decode to DMA storage in the emulator (TIMER1, TIMER2, TIMER3, SNIFF_CTRL, SNIFF_DATA) instead of to IRQ registers. This means:

- **On the emulator:** sled writes `DMA_TIMER0 = 0x5000_0420` → hits the emulator's TIMER0 cell → DREQ_TIMER0 fires at rate 1/10 → channel drains → BUSY clears → scenario passes in the Rust unit test.
- **On silicon:** sled writes `0x5000_0420` → hits reserved/padding between INTS1 and INTE2 (a harmless write, likely RAZ/WI) → TIMER0 at `0x5000_0440` stays at reset `0x0000_0000` → DREQ_TIMER0 never asserts → BUSY never clears → busy-poll timeout.

### 2.3 Rejection of the parent HLD's alternative hypotheses

Relative to the parent HLD's four candidates:
- **(a) TIMERx register layout or offset wrong in the sled.** Confirmed, refined: it's not a layout issue inside the register, it's the *base offset of the whole global-register block* being shifted between RP2040 and RP2350. Both the sled and the emulator have the RP2040 offset.
- **(b) TREQ_SEL value wrong (V5 vs V6 decoding).** Rejected. Commit `a7266bf` moved TREQ_SEL to bits `[22:17]` and the sled uses `0x0076_0059` which correctly encodes TREQ_SEL=59 at those bits. The decoding path is exercised by the existing `dma_timer_paced_transfer` unit test in `crates/mdrp2350/src/dma.rs:1338`, which passes. Commit `9d669ce` is orthogonal (it's about PIO1 glue-DMA, not about the pacing-timer path).
- **(c) Emulator doesn't model timer-paced DREQ at all.** Rejected. `Dma::tick` at `crates/mdrp2350/src/dma.rs:564–606` clearly services `DREQ_TIMER0..3` via `timer_dreq_asserted[]` and the `timer_accum` X/Y divider.
- **(d) Emulator models DREQ with wrong timing.** Rejected — the unit test proves tick-by-tick correctness.
- **(e) Silicon's timer-paced DMA is gated by additional setup the sled doesn't perform.** Partially right (the "additional setup" is simply writing to the correct register), but not in the bootrom-init sense the parent HLD proposed.

Parent HLD's bootrom-init hypothesis (Path 1) is clearly falsified by the two sibling scenarios now passing through the same `reset_and_halt` path — that end of the space is closed without further investigation.

## 3. Empirical confirmation plan

I consider this one high-confidence enough that the Rust implementation should go direct to silicon verify, but here is a minimal, cheap silicon probe we can run first to preempt surprise:

### 3.1 Pre-fix readback (optional, but recommended if probe access is cheap)

Run the current `dma_timer_paced` scenario once with the emulator **and silicon** instrumented to dump these four 32-bit words at BKPT (via `observe` tuple extension — no sled change, just extra observe reads):

- `0x5000_0420` — sled-written "TIMER0" address. On emulator: `0x0001_000A`. On silicon: expected `0x0000_0000` (reserved padding or RAZ/WI).
- `0x5000_0440` — authoritative RP2350 TIMER0 address. On emulator: unmapped, likely `0x0000_0000`. On silicon: expected `0x0000_0000` (pristine reset).
- `DMA_BASE + 0x40C` (INTS0) — reads as the channel-0 raw intr bit, confirms DMA's channel 0 is still latched busy on silicon.
- `DMA_BASE + 0x468` (RP2350 N_CHANNELS). On emulator today: reads back zero from unmapped space. On silicon: `16`.

If we see silicon `0x5000_0440 == 0` and silicon `0x5000_0420 == 0`, the hypothesis is fully confirmed. The fourth address also neatly confirms the whole block is shifted.

This probe can run as a one-shot custom sled added to `silicon_scenarios.rs` with a new scenario name `dma_timer_paced_diagnostic`. Not merged — we delete it after confirmation, same pattern as `smoke_per_core_cyccnt_rp2350`.

### 3.2 If the pre-fix readback surprises us

If `0x5000_0440` reads non-zero on silicon, or `0x5000_0420` reads the value we just wrote, the hypothesis is partially wrong and the HLD needs to widen scope — escalate back to the supervisor before coding.

**Recommendation:** skip the probe and go straight to the fix unless Arthur prefers extra empirical confidence. The datasheet quote in §2.1 is unambiguous; RP2040 → RP2350 shifted-block behaviour is a known pattern (the `a7266bf` CTRL-field-shift fix did the same thing at the bit-field level for CTRL).

## 4. Proposed fix

Two files. No bit-layout change; purely offset constants and one sled MOVW immediate update.

### 4.1 `crates/mdrp2350/src/dma.rs` — register map offsets

Lines 79–88 — shift the whole global-register block to RP2350 offsets, and add the four new IRQ registers the RP2350 block has:

```rust
// Global registers (RP2350 datasheet §12.6.6, rev. 2026-04-17 fix).
// RP2350 adds IRQ2/IRQ3 groups vs RP2040, shifting everything from
// 0x420 onward up by 0x20 bytes.  Pre-fix these constants matched the
// RP2040 layout which is why `dma_timer_paced` ran green on the emulator
// while failing on silicon (see Residual C.2.1 HLD).
const REG_INTR:  u32 = 0x400;
const REG_INTE0: u32 = 0x404;
const REG_INTF0: u32 = 0x408;
const REG_INTS0: u32 = 0x40C;
// 0x410 reserved
const REG_INTE1: u32 = 0x414;
const REG_INTF1: u32 = 0x418;
const REG_INTS1: u32 = 0x41C;
// 0x420 reserved (padding where RP2040 used to put TIMER0)
const REG_INTE2: u32 = 0x424;
const REG_INTF2: u32 = 0x428;
const REG_INTS2: u32 = 0x42C;
// 0x430 reserved
const REG_INTE3: u32 = 0x434;
const REG_INTF3: u32 = 0x438;
const REG_INTS3: u32 = 0x43C;
const REG_TIMER0: u32 = 0x440;
const REG_TIMER1: u32 = 0x444;
const REG_TIMER2: u32 = 0x448;
const REG_TIMER3: u32 = 0x44C;
const REG_MULTI_CHAN_TRIGGER: u32 = 0x450;
const REG_SNIFF_CTRL: u32 = 0x454;
const REG_SNIFF_DATA: u32 = 0x458;
// 0x45C reserved
const REG_FIFO_LEVELS: u32 = 0x460;
const REG_CHAN_ABORT: u32 = 0x464;
const REG_N_CHANNELS: u32 = 0x468;
```

Scope of new IRQ2/IRQ3 modelling: **storage-only** for this residual. The existing `Dma` struct has `inte0/intf0/inte1/intf1` fields (plural of INTE for IRQ0/IRQ1). Extending to IRQ2/IRQ3 means:
- Add `inte2/intf2/inte3/intf3: u32` fields to the `Dma` struct.
- Read dispatch: `REG_INTE2 => self.inte2`, `REG_INTS2 => (self.intr | self.intf2) & self.inte2`, etc.
- Write dispatch: plain `apply_alias` assignments.
- `route_irqs`: extend to route `(intr | intf2) & inte2` to `IRQ_DMA_IRQ_2` and `intf3` pair to `IRQ_DMA_IRQ_3`.

Alternative: keep IRQ2/IRQ3 unmodelled and just return 0 on read / swallow writes, add a warn-once on first use, and reserve full modelling for when some scenario actually wires IRQ2/IRQ3 into anything. This is what `HIGH_PRIORITY` / `BSWAP` / `SNIFF_EN` do today. That's cleaner for this residual, which is about timer pacing, not about IRQ routing.

**Proposal: go with the lighter option.** Just storage + return-0 for IRQ2/IRQ3 reads, like existing unmodelled bits. Saves ~30 lines of code and doesn't expand the blast radius. IRQ2/IRQ3 routing becomes a follow-up tech_debt entry.

Lines 1350, 407–410 in the same file — reference `REG_TIMER0..3` via the constants, so changing the constants threads through the read/write dispatch automatically. Spot-check: `self.timer_dreq_asserted[i]` consumers at L572/L578/L580/L595 use indices `0..4`, independent of the register offset. No changes needed there.

Line 1350 — the existing unit test at `dma_timer_paced_transfer` writes `DMA_BASE + REG_TIMER0`, which via the updated constant now hits `0x5000_0440`. The test still passes because it uses the named constant, not a literal.

### 4.2 `crates/mdpicoem-harness/src/silicon_scenarios.rs` — sled + public constant

- L1787 (public pub const): `pub const DMA_TIMER0: u32 = DMA_BASE + 0x420;` → `DMA_BASE + 0x440`. Update the doc comment at L1786 to cite RP2350 §12.6.6.
- L1850–1851 sled halfwords [18..19]: `movw r2, #0x0420 hw0/hw1`. Currently `0xF240, 0x4220` (imm4=0,i=0,imm3=4,imm8=0x20). Change to `0xF240, 0x4440` (imm4=0,i=0,imm3=4,imm8=0x40). Verification: `MOVW T3` encoding of `#0x0440` = `imm4=0,i=0,imm3=4,imm8=0x40`; hw0 = `0xF240 | (0<<10) | 0 = 0xF240`, hw1 = `(4<<12) | (2<<8) | 0x40 = 0x4240`. Wait — that's `0x4240`, not `0x4440`. Let me redo: Rd=2, so `(Rd<<8) = 0x0200`. hw1 = `(imm3<<12) | (Rd<<8) | imm8 = (4<<12) | 0x0200 | 0x40 = 0x4240`. **Correct new hw1 = `0x4240`.** Same structure as L1851's current `0x4220` which was `(4<<12) | (2<<8) | 0x20`, just with imm8=0x40 instead of 0x20. The HLD-writer slipped; the implementation agent must re-derive from the encoding tables.
- L1811 comment "DMA_TIMER0 = 0x5000_0420 — cannot reach with a simple [r1,#imm5*4]" → "DMA_TIMER0 = 0x5000_0440 — cannot reach with a simple [r1,#imm5*4] (0x440/4=272 > imm5_max=31)".
- L1820 comment "0x0420={imm4=0,i=0,imm3=4,imm8=0x20}" → "0x0440={imm4=0,i=0,imm3=4,imm8=0x40}".
- L1849 comment "---- write DMA_TIMER0 = 0x0001_000A (r2 = 0x5000_0420) ----" → `r2 = 0x5000_0440`.

No change to CTRL values, no change to any other register address, no change to the bit-position layout from `a7266bf`.

### 4.3 Not fixing: non-paced-timer side effects

The emulator's shifted register block also means `INTE2/INTF2/INTS2/INTE3/INTF3/INTS3` reads would, today, silently land in TIMER1/2/3/SNIFF_CTRL/SNIFF_DATA storage. No V1 corpus scenario uses IRQ2 or IRQ3 (all the DMA tests route via IRQ0), and this residual's acceptance gate doesn't require fixing it. The right thing is to log a `tech_debt.md` entry documenting the IRQ2/3 gap and move on.

**Out-of-scope cleanup deferred to tech_debt.md:**
- DMA IRQ2/IRQ3 routing (inte2/intf2/ints2, inte3/intf3/ints3) is now storage-only.
- Emulator could be extended to return zero / warn-once on read.

### 4.4 ROMs / firmware check

Neither `roms/rp2350/hello_dma.bin` (uses FORCE) nor `roms/rp2350/gen_hello_dma.py` touch DMA_TIMER. No regeneration needed.

## 7. Blast radius + rollback

### 7.1 Sibling DMA scenarios (`dma_mem_to_mem_32bit`, `dma_chain_trigger`)

Neither scenario writes to any register in the `0x420..0x44c` range. Both use `TREQ_SEL=63 (FORCE)` which bypasses the DREQ matrix. Verified by regexing sled halfwords for absolute addresses in `0x5000_042X..0x5000_044X`: only `dma_timer_paced` does it. **No regression risk.**

### 7.2 `ctrl_field_positions_rp2350_not_rp2040` (from `a7266bf`)

This residual does **not** modify any CTRL bit-position constant. The pinned test asserts `make_ctrl(.., 63, 0, 0, false) == 0x007E_0059` and `bits[22:17] == TREQ_SEL`. Unaffected — the CTRL layout lives in separate constants (`CTRL_TREQ_SEL_SHIFT`, etc.).

### 7.3 `mdrp2040` DMA code

RP2040's DMA does have TIMER0..3 at `0x420..0x42C` — that's the real RP2040 layout. **No changes to `mdrp2040` — that crate keeps its existing (correct-for-RP2040) offsets.** This residual is strictly an RP2350 register-map correction.

### 7.4 Inert-register warn paths

`crates/mdrp2350/src/dma.rs` has warn-once latches for SNIFF_CTRL.EN (L421) and SNIFF_DATA (L428). These are keyed on `REG_SNIFF_CTRL` and `REG_SNIFF_DATA` constants, so the shift just moves the dispatch targets; they keep firing on the same semantic writes. No behaviour change.

### 7.5 `paced_bench_rp2350` / `full_test_rp2350` / other DMA-touching harnesses

None of them configure DMA pacing timers; confirmed by searching for `TIMER0|0x420|0x440` across `crates/mdpicoem-harness/src/bin/`. **No regression risk.**

### 7.6 OneROM glue-DMA path

`crates/mdpicoem-harness/src/onerom_glue_dma.rs` does not touch DMA_TIMER (confirmed by Grep). Commit `9d669ce`'s CHAN_ABORT fix is on `REG_CHAN_ABORT`, which under the fix shifts from `0x444` to `0x464`. The glue file uses the named constant from `dma.rs`, so it threads automatically. Sanity-run `onerom_serving_oracle` after the fix.

### 7.7 Rollback

`git revert` the residual's single atomic commit. Recovers the RP2040 offsets — silicon dma_timer_paced returns to BKPT timeout, but `dma_mem_to_mem_32bit` and `dma_chain_trigger` remain PASS (no rollback of their sleds). No hardware state is touched.
