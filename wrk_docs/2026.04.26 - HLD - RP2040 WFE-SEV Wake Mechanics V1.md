# HLD — RP2040 WFE/SEV Wake Mechanics V1

**Date:** 2026-04-26
**Author:** Workstream 1 HLD agent (sonnet)
**Supervisor sign-off:** 2026-04-26 (see journal `2026.04.26 - JRN - Triple Workstream WFE-DMAirq-ProbeHardening.md`).

## 1. Problem statement

`crates/mdrp2040/src/core/execute.rs:836-841` decodes `WFE` (`0xBF20`), `WFI` (`0xBF30`), and `SEV` (`0xBF40`) as 1-cycle no-ops. The bus already carries a `Bus::event_flag: [bool; 2]` field and a working `signal_sev()` helper, but nothing in the M0+ decode path consumes or sets either, and `Emulator::wake_checks` at `crates/mdrp2040/src/lib.rs:993-998` unconditionally clears `event_flag[0]` at every quantum-end — so any latched SEV is wiped before firmware can observe it.

**Concrete failing-firmware sketch** (Pico SDK style):

```c
// Core 0 producer
multicore_fifo_push_blocking(0xCAFE);   // FIFO_WR; SDK then __sev()
__sev();

// Core 1 consumer — currently busy-loops at 100% utilisation
while (!multicore_fifo_rvalid()) {
    __wfe();                // decoded as 1-cycle NOP today
}
uint32_t v = sio_hw->fifo_rd;
```

On real silicon, `__wfe()` on the consumer core suspends until the producer's FIFO_WR (which sets the receiver's event register inside the SIO block) or its `__sev()` lifts it. Today the emulator burns thousands of synthetic cycles in the busy loop, distorting both throughput numbers and any timing-sensitive downstream (e.g. `paced_bench_rp2040` MHz panel). The threaded runtime *has* the wake plumbing wired (`crates/mdrp2040/src/threaded/emulator.rs:592-597, 633-635`) but the decoder never sets `wfe_waiting`, so the threaded path silently hits the same bug.

**Flagged surprises:**

1. The mdrp2040 threaded coordinator has the wake mechanism fully wired *as if* the decoder already drove it. The serial path is the one without coordinator-side support. So this work is mostly: (a) decode + cycle counting in execute.rs, (b) a lightweight `wfe_waiting` flag, and (c) wake-check + step-skip on the serial path. The threaded coordinator changes are minimal.

2. mdrp2040's `Bus::wake_checks` does the **exact opposite** of what its mdrp2350 counterpart does — it actively **clears** `event_flag[0]`, which would erase any wake even if WFE worked. This is the line that has to flip.

3. `CortexM0Plus` has no Arc to `CoreAtomics`. The serial path needs to reach `event_flag` through the `CoreBus` trait. The threaded path's `WorkerBus` reaches it through `self.shared.atomics`. The trait needs a small extension that both impls satisfy.

## 3. Reference design (mdrp2350)

The mdrp2350 design centres on a **single shared `Arc<CoreAtomics>`** co-owned by `Bus` and both `CortexM33` instances:

- **State location**: `CoreAtomics { halted: [AtomicBool; 2], wfe_waiting: [AtomicBool; 2], event_flag: [AtomicBool; 2], … }`. Same `Arc` is used in serial and threaded paths.

- **Decode hooks** (`crates/mdrp2350/src/core/execute.rs:736-756` plus `core/mod.rs:757-765`):
  - **WFE** (`0xBF20`): calls `self.wfe(bus)`, which atomically swaps `event_flag[core]` to false. If swap returned true → wake immediately and continue; otherwise `set_wfe_waiting(core)`.
  - **WFI** (`0xBF30`): peeks `irq_pending_load(core)` and tests it against the per-core PPB's `any_pending_enabled`. If pending and enabled → NOP through; otherwise `set_halted(core)`. **WFI reuses the `halted` flag.**
  - **SEV** (`0xBF40`): `self.atomics.sev_both()` — Release-stores `true` to `event_flag[0]` and `event_flag[1]` in turn. Self-wake of the issuing core is achieved by the receiving-side `event_flag_consume` swap on the next WFE.

- **Wake events (V1 cut, exhaustive):**
  - SEV from sibling core (or this core's own SEV — sets local register too).
  - WFI wakes on pending+enabled IRQ at `wake_checks` time.
  - **FIFO-rx event**: on RP2350, `Sio::fifo_wr` sets `pending_fifo_event = Some(other)`. `Bus::write32` drains this immediately into `atomics.set_event_flag(other)`. Datasheet: RP2040 §2.3.1.4.1 ("Inter-processor FIFOs") — "When a CPU writes to its TX FIFO, an event is signalled to the other CPU. This event will release the other CPU from a WFE."

- **Step-loop skip** (`crates/mdrp2350/src/lib.rs:1339-1342`): `while !is_halted() && !is_wfe_waiting() && cycles < target { … }`. When a core is WFE-blocked, *zero* cycles are charged to it during that quantum. The clock still advances on the back of the running core (`c0.max(c1)`).

- **Quantum-end wake**: `Emulator::wake_checks` (`crates/mdrp2350/src/lib.rs:1076-1115`) is the single-point wake decision after each quantum: WFE wake = `is_wfe_waiting(i) && event_flag_consume(i)` then `clear_wfe_waiting(i)`. WFI wake mirrors the same shape on `halted`+`any_pending_enabled`.

- **Cycle accounting**: 1 master cycle for the WFE/WFI/SEV instruction itself. While *blocked*, the core charges no further cycles.

## 4. Proposed design (mdrp2040)

### 4.1 State changes

**Serial path:**
- Add `wfe_waiting: [bool; 2]` to `Bus` next to the existing `event_flag: [bool; 2]` (`crates/mdrp2040/src/bus/mod.rs:334-335`). Reset to `[false; 2]` in `Bus::new()` and `Emulator::reset()` parallel to the existing `event_flag` reset (`lib.rs:411`).
- **Do not** add a per-core field on `CortexM0Plus`. The Bus is the source of truth; this matches how mdrp2040 already keeps `event_flag` Bus-owned.

**Threaded path:**
- No new state — `CoreAtomics::wfe_waiting` already exists.
- The Serial → Threaded promotion at `threaded/emulator.rs:170-183` already lifts `event_flag[c]` into atomics; extend it to also lift `bus.wfe_waiting[c]`.

### 4.2 Decode/execute changes

In `crates/mdrp2040/src/core/execute.rs:834-842`, replace the three placeholder match arms:

- **WFE (`0x2`)**: call a new inherent helper `self.wfe(bus)` (in `core/mod.rs`) that:
  1. Reads `bus.event_flag(core)`. If true → consume (set false) and return 1 cycle without sleeping.
  2. Else → `bus.set_wfe_waiting(core, true)`; return 1 cycle.
- **WFI (`0x3`)**: read `bus.nvic(core).pending_and_enabled()`. If non-zero → return 1 cycle as a NOP. Else → call existing `self.halt()`; return 1 cycle. **WFI ignores PRIMASK for the wake decision** — verified against ARMv6-M ARM B1.5.18.
- **SEV (`0x4`)**: call `bus.signal_sev()`; return 1 cycle.

The `CoreBus` trait needs four new methods (added to `core/bus_trait.rs`):
- `fn event_flag(&self, core: usize) -> bool;`
- `fn consume_event_flag(&mut self, core: usize) -> bool;`
- `fn set_wfe_waiting(&mut self, core: usize, val: bool);`
- `fn signal_sev(&mut self);`

The `impl CoreBus for Bus` (serial) implements these against the `bool` fields directly; the `impl CoreBus for WorkerBus` (`threaded/bus.rs:1036`) forwards to `self.shared.atomics.event_flag_consume / set_wfe_waiting / sev_both`.

### 4.3 Step-loop changes (Serial)

In `Emulator::step_serial` at `lib.rs:595-625`, change the per-iteration core-eligibility predicate from `!self.cores[c].is_halted()` to `!self.cores[c].is_halted() && !self.bus.wfe_waiting[c]`. Skipped cores contribute zero cycles and the existing `if c0 == 0 && c1 == 0 { break; }` correctly terminates the inner loop.

### 4.4 `wake_checks` re-shape (Serial)

Replace the current body at `lib.rs:993-998`:

```text
for core in 0..2 {
    // WFE wake
    if self.bus.wfe_waiting[core] && self.bus.event_flag[core] {
        self.bus.event_flag[core] = false;       // consume
        self.bus.wfe_waiting[core] = false;      // un-park
    }
    // WFI wake (existing halt semantics — covers BKPT-halt too,
    // matching mdrp2350's flag-reuse choice)
    if self.cores[core].is_halted()
        && self.bus.nvics[core].pending_and_enabled() != 0
    {
        self.cores[core].wake();
    }
}
// (Crucially: no longer unconditionally clears event_flag[0].)
```

The unconditional clear at the current line 995 is **deleted**. Any latched event with no waiter survives until the next WFE consumes it — that's the architectural latch behaviour required by the SEV-before-WFE idiom.

The launch-token consumer's `event_flag[1] = false` at `lib.rs:1065` is preserved verbatim — that's an intentional clean-launch reset, not the bug.

### 4.5 Threaded runtime changes

The worker body (`threaded/emulator.rs:566-647`) is already correct. Changes needed:

1. **Promotion handoff** at `threaded/emulator.rs:170-183`: after the existing `event_flag[c]` carry, add a parallel `if bus.wfe_waiting[c] { atomics.set_wfe_waiting(c); }`.
2. **Decode-side dispatch in threaded mode**: the same WFE/WFI/SEV decode arms now route through the `CoreBus` trait, so `WorkerBus`'s impl is automatically used.
3. **Coordinator awareness**: existing `core_worker_body` already handles SEV-from-peer wake (lines 592-597 and 633-635). No additional barrier needed.

### 4.6 SEV semantics

- Broadcasts to **both** cores via `Bus::signal_sev` (Serial) / `CoreAtomics::sev_both` (Threaded).
- Self-wake-on-issue is automatic: the issuing core's own `event_flag` is set, so its next WFE consumes the latch and falls through.
- Latch behaviour: once set, `event_flag[c]` persists until consumed by a WFE on core `c`. Multiple SEVs collapse to one bit.
- A SEV issued while the receiver is *not* in WFE simply latches; the next WFE on that core sees it and falls through (one-shot wake).

### 4.7 WFI semantics

- Wake-decision uses `Nvic::pending_and_enabled() != 0` for the calling core — no PRIMASK gating on the wake decision (ARMv6-M ARM B1.5.18).
- We **reuse `CortexM0Plus::halted`** for WFI sleep — mirroring the mdrp2350 choice. The conflation with debug/BKPT halt is acceptable because both wake on pending+enabled IRQ.

### 4.8 FIFO-rx event wake

Already wired upstream:

- Serial: `Bus::sio_write32` drains `Sio::pending_fifo_event` into `event_flag[receiver]` at `bus/mod.rs:1546-1548`.
- Threaded: `WorkerBus::write32` calls `atomics.set_event_flag(other)` at `threaded/bus.rs:406`.

**No new FIFO code is required**; the change is purely that the receiver's WFE will now actually park (and thus actually wake on this signal) instead of trivially falling through. The doorbell mechanism (RP2350-only) is out of scope.

### 4.9 Wake-source enumeration (V1)

Per "don't predict the future":

- SEV from any core (sets `event_flag` on both).
- FIFO_WR from peer (sets `event_flag` on receiver via `pending_fifo_event` drain).
- WFI: any pending+enabled NVIC IRQ.

Out of scope: debug halt / external event signal — not modelled. A generic "wake_source" enum is **explicitly rejected** for V1.

### 4.10 Cycle accounting

- WFE / WFI / SEV: 1 master cycle each on the issuing core. Matches mdrp2350.
- WFE-/WFI-blocked core: 0 cycles per quantum tick.

## 6. Cycle / pacer impact

The hot path adds:
- Per-instruction WFE/WFI/SEV decode: identical cost.
- Per-quantum top-of-loop: one extra `bus.wfe_waiting[c]` boolean read.
- `wake_checks` re-shape: 2 boolean reads + 2 conditional stores per core. Predicted neutral, possibly faster.

**Measurement gate**: run `paced_bench_rp2040` pre/post and compare p50 throughput. **Budget: ±2% p50 deviation**. If p50 regresses by >2%, the WFE-waiting predicate is moved into the existing `is_halted` short-circuit.

The blocked-core case is in fact a **pacer improvement**, not a regression.

## 8. Open questions / risks (supervisor decisions recorded)

1. **PRIMASK + WFE corner case.** Design treats WFE wake-on-event as PRIMASK-independent (matching silicon). **Resolution: approved as designed.**

2. **Shared `halted` flag for both BKPT-halt and WFI-sleep.** Mirrors the mdrp2350 design wart. **Resolution: approved. Match mdrp2350 precedent. If a future test scenario needs to distinguish BKPT-halt from WFI-halt, split the flag in a follow-up — but no current test does, so don't predict the future.**

3. **Master-clock advance when both cores are WFE-blocked.** Today's `step_serial` halts the clock when both cores are at 0 cycles. On real silicon a TIMER alarm could fire and assert IRQ that wakes a WFI'd core. **Resolution: defer in V1, matching mdrp2350 precedent. Add a tech_debt entry capturing the risk for both chips. The firmware-deadlock scenario (timer + WFI) is not in the current test corpus; the gap is theoretical, not blocking.**

4. **Inline Thumb-2 blob vs firmware project for `dual_model.rs::wfe_sev_handshake_parity`.** **Resolution: inline blob.** Faster to land, no new build dep, the test is small (a handful of `__sev`/`__wfe` words). Comment with disassembly above the blob is mandatory.

5. **`wfe_waiting` field placement on `Bus` (not on `CortexM0Plus`).** **Resolution: approved as designed.** Bus-owned matches existing `event_flag` placement; promotion handoff lifts into atomics, so no leak.

6. **Doorbells / external events.** Out of scope for V1.
