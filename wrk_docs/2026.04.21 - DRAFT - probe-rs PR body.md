## Title

arm/communication_interface: recover V2 AP access on DPv1 cache instead of panicking (fixes #3872, #3257)

## Body

### Summary

`ArmCommunicationInterface::select_ap_and_ap_bank` currently panics via
`unreachable!()` whenever an ADIv6 V2 AP is accessed while the DP state
cache is still `SelectCache::DPv1`. This can happen in practice when the
initial DPIDR read returns a version field that is not exactly `3`
(e.g. a transient SWD read, a reset-halt retry, or a first-attach race),
because `DpState::new()` always starts the cache at `DPv1` and only
upgrades it on a successful `idr.version == DebugPortVersion::DPv3` read
in `select_dp`.

Two open issues report this symptom from different vendors:

- #3872 — RP2354 (Raspberry Pi RP235x, `ApV2Address(Some(2000))`)
- #3257 — nRF9151

Both ship `v2` APs in their target YAML, so `memory_ap` resolution
addresses the AP via a V2 fully-qualified address during
`Session::attach_arm_debug_interface` → `core.enable_arm_debug` →
`debug_core_start` → `interface.memory_interface(core_ap)`, and the
cache-mismatch path is hit.

### Change

Replace the `unreachable!()` for the `(ApAddress::V2, SelectCache::DPv1)`
cross-product with an in-place cache upgrade to `DPv3` followed by the
normal V2 AP write. The outer `previous_select != dp_state.current_select`
branch then flushes the new `SELECT` / `SELECT1` registers on this same
call, so the caller sees no functional difference from a freshly-booted
DPv3 session.

A single `tracing::warn!` records the recovery so it is visible in
`RUST_LOG=warn` output. Downstreams that see this line firing more
than once per session can treat it as a signal that a deeper DP state
bug is being masked.

The other three cross-product combinations (`(V1, DPv1)` = existing
supported path; `(V2, DPv3)` = existing supported path; `(V1, DPv3)` =
genuinely illegal AP/DP mismatch) are unchanged.

### Testing

Tested on Raspberry Pi RP2354 (Pico 2) via a CMSIS-DAP probe, running
the downstream test suite from the reporter of #3872:

- `probe_verify_rp2350` — previously panicked on attach; now completes.
- `silicon_periph_diff_rp2350`, `silicon_isr_diff_rp2350`,
  `silicon_dualcore_diff_rp2350`, `bank_conflict_test_rp2350` — all
  previously panicked on attach; all now run the full scenario
  catalogue.
- `probe_diff_rp2350 --fuzz 4000` — regression check for the ISA-level
  path that happened to dodge the panic pre-patch; unchanged PASS
  4000/4000.

The sentinel WARN fired 0–1 times per session across these runs, as
expected for a transient first-read recovery.

### Backwards compatibility

No public API changes. No existing passing code path is altered
(`(V1, DPv1)` and `(V2, DPv3)` arms are untouched). Only the panic-arm
pattern narrows to cover the two remaining impossible combinations
`(V1, DPv3)` and the implicit fourth cell.

Closes #3872.
Related: #3257.
