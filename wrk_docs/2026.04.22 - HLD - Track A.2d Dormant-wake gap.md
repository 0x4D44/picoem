## 1. Problem statement

A.2c Option A landed cleanly: probe-rs now carries an `AdiVersion` target property (`src/architecture/arm/mod.rs:195-207`), the `Rp235x` vendor sequence declares `AdiVersion::V6` (`src/vendor/raspberrypi/sequences/rp235x.rs:114-116`), and the SELECT cache / AP enumeration path uses it in place of DPIDR-derived version detection. 2614 unit tests pass; `probe_diff_rp2350 --fuzz 4000` 4000/4000 PASS; `probe_diff_rp2040` 127/127 PASS. No regressions.

**Gate 3 result: RED.** From the impl agent's log (journal 2026-04-22 "A.2c Option A — Gate 3 RED"):

- `RP235x debug sequence constructed; declaring ADIv6 for V2-AP addressing` — override fires.
- `Target declared ADIv6 addressing (vendor sequence override); SELECT cache initialised as DPv3 regardless of DPIDR.version` — path live.
- `Debug Port version: DPv2 MinDP: Implemented (target adi_version: ADIv6)` — **probe-rs still reads DPIDR = `0x10212927`.**
- `Error: Arm(WrongApType)` — AP IDR read still fails.

OpenOCD 0.12.0 with `-adiv6` reads DPIDR = `0x4c013477` (DPv3 / SoC-600) on the **same probe, same silicon, same session** (`wrk_debug/openocd-rp2354-attach2.stderr.log:18`). That is a read-path divergence, not silicon variation. The A.2c refactor decoupled SELECT encoding from DPIDR.version, but it left in place the upstream `ArmDebugSequence::debug_port_setup` — and that default never sends the dormant-to-SWD wake sequence unless the generic SWDv1 attempt fails twice. On RP2354 the generic SWDv1 attempt *succeeds* (DPIDR reads as `0x10212927`, which is a legal DPv2 value), so the retry-gated dormant fallback never fires. The DP is left in its power-on-reset identity rather than transitioned to its ADIv6 identity, and subsequent AP IDR reads at V2 addresses return `0x0`.

## 2. Research summary — what OpenOCD does that probe-rs doesn't

### 2.1 The OpenOCD SWD sequences (authoritative wire bytes)

From [openocd-org/openocd `src/jtag/swd.h`](https://github.com/openocd-org/openocd/blob/master/src/jtag/swd.h):

- **Line reset** — 64 bits, SWDIO high × ≥50 + trailing low: `ff ff ff ff ff ff ff 00`.
- **JTAG-to-SWD** — 136 bits: `ff ff ff ff ff ff ff 9e e7 ff ff ff ff ff ff ff 00`. The magic 16 bits are `0x9EE7` (= `0xE79E` in bit-reversed/LE transmit order). Comment: "compatibility switch, may be intercepted by a pre-ADIv5 DP."
- **JTAG-to-Dormant** — 40 bits: `ff 75 77 77 67`.
- **Dormant-to-SWD** — **224 bits** total:
  - `0xff` — 8 cycles SWDIO high to abort any in-progress selection alert.
  - `92 f3 09 62 95 2d 85 86 e9 af dd e3 a2 0e bc 19` — **128-bit JEDEC selection alert sequence** (ARM IHI 0074C §B4.3.3).
  - `a0 f1 ff` — 4 cycles low + **SWD activation code `0x1A`** (8 bits) + 16 cycles high (line-reset prefix).
  - `ff ff ff ff ff ff ff 00` — **line reset** (50 high + 2 low).

Per IHI 0074C comment in OpenOCD: *"DPv3 (ADIv6 only): line reset sets DP_SELECT_DPBANK to zero"* — and *"read of DP_DPIDR takes the connection out of reset"*.

### 2.2 OpenOCD's selection logic in `swd_connect_single`

From [openocd-org/openocd `src/target/adi_v5_swd.c`](https://github.com/openocd-org/openocd/blob/master/src/target/adi_v5_swd.c) (retry loop around lines 516-579):

```c
do {
  if (dap->switch_through_dormant) {
    swd_send_sequence(dap, JTAG_TO_DORMANT);
    swd_send_sequence(dap, DORMANT_TO_SWD);
  } else {
    swd_send_sequence(dap, JTAG_TO_SWD);
  }
  // ... read DP_DPIDR ...
  dap->switch_through_dormant = !dap->switch_through_dormant;  // TOGGLE
} while (timeval_ms() < timeout);
```

Key properties:

1. **`switch_through_dormant` is toggled every iteration**, not only on failure. If the first iteration uses JTAG_TO_SWD and gets a "wrong" DPIDR, the second uses DORMANT_TO_SWD.
2. The RPi fork has the same structure plus an SWD-to-dormant branch. The toggle on retry is unchanged.
3. On the `-adiv6` RP2350 config, OpenOCD reads DPIDR = `0x4c013477` on the first attempt (see the session log `wrk_debug/openocd-rp2354-attach2.stderr.log:18`), which means **either** OpenOCD's default `switch_through_dormant` value is `true` on ADIv6 targets, **or** the JTAG-to-SWD sequence alone is sufficient to wake this silicon into its ADIv6 identity. The existing probe-rs JTAG-to-SWD path (`0xE79E`, `sequences.rs:607`) also succeeds at getting a DPIDR, but that DPIDR is `0x10212927` rather than `0x4c013477` — so the difference must be in the sequence that preceded it.

### 2.3 The probe-rs sequence that corresponds

Located at `third_party/probe-rs-0.31.0-mdrp-patched/src/architecture/arm/sequences.rs:529-638`:

- `let mut has_dormant = matches!(dp, DpAddress::Multidrop(_));` — starts `false` for non-multidrop.
- Retry loop, up to 5 attempts. Each attempt:
  - `swd_line_reset(interface, 0)` — 51 bits high.
  - If `active_protocol() == Swd`:
    - If `has_dormant`: SWD→Dormant (31-bit `0x33BBBBBA`), then `alert_sequence()` (8 FFs + 128-bit JEDEC in two u64 halves), then 12 bits = 4 low + SWD activation `0x1A`.
    - Else: JTAG→SWD via 16 bits `0xE79E`.
  - `debug_port_connect` — another `swd_line_reset`, then `raw_read_register(DPIDR)`.
  - If that succeeds → break.
  - After the first retry (`if retry >= 1 { has_dormant = true; }`) — flip dormant on.

**The bug (in a sentence):** on RP2354 the initial `debug_port_connect` returns `Ok(0x10212927)`, so the loop breaks before `has_dormant` ever flips. The dormant-to-SWD activation sequence is never sent on the wire. The DP remains in its power-on/JTAG-compat identity (DPv2), not its ADIv6 identity (DPv3). When probe-rs later writes SELECT with V2-AP addressing, the DP routes to the wrong internal register and returns 0.

This retry-gated dormant is probe-rs#2914 (merged 2024-11-18, "arm: Fall back on SWDv2 wake from dormant on SWDv1 failure"), by seanmlyons22 — see [probe-rs#2914](https://github.com/probe-rs/probe-rs/pull/2914). It is present in 0.31.0 / our fork. The design assumes a failed DPIDR read is the signal to switch to dormant. It doesn't handle "DPIDR succeeds but returns the wrong value."

### 2.4 Wire-level diff between the two tools on this silicon

| step | OpenOCD `-adiv6` on RP2354 | probe-rs today on RP2354 | needs to be |
|---|---|---|---|
| 1 | 8 cycles SWDIO high (abort alert) | 51 cycles line reset | (OpenOCD's is implicit in Dormant-to-SWD prefix; fine either way) |
| 2 | **128-bit JEDEC selection alert** | JTAG-to-SWD `0xE79E` only | 128-bit alert — **missing** |
| 3 | **4 low + SWD activation `0x1A`** | (none) | activation 0x1A — **missing** |
| 4 | line reset (50+ high) | line reset (51 high) | present |
| 5 | DPIDR read | DPIDR read | present |

Steps 2 and 3 are what move the DP from "legacy SWD / DPv2" to "ADIv6 / DPv3" identity on this silicon. This is exactly what ARM IHI 0074C §B4.3.3 calls the "dormant to SWD" transition.

## 3. Hypothesis — pin it to a specific missing step

**H_A (leading, confidence 0.80): the missing sequence steps are (2) + (3) as a unit.** The 128-bit JEDEC alert and the `0x1A` activation code must be sent together for the DP to transition. RP2354 silicon is CoreSight SoC-600 internally, reports DPv2 in its default/compat identity, and reports DPv3 + exposes V2-APs only after receiving the alert+activation pair. This matches OpenOCD's behaviour exactly.

**H_B (alternative, confidence 0.10): only (3) is missing.** The `0x1A` activation code alone is what flips the identity, and probe-rs's existing `JTAG-to-SWD 0xE79E` already primes the DP into an alert-accepting state. *Unlikely* because per IHI 0074C the activation code is only meaningful *after* the JEDEC alert — sending it without the alert is a no-op.

**H_C (alternative, confidence 0.05): only (2) is missing.** *Unlikely* — the alert alone with no activation code leaves the DP in dormant state, and the next transfer would fault.

**H_D (residual, confidence 0.05): something else entirely** — e.g. POWER_REQ ordering, overrun-detect state, a probe-level CMSIS-DAP quirk. *Unlikely* because the sequence in (2.1) is the textbook ARM-spec'd difference between a legacy DP read and an ADIv6 DP read, and it's exactly what OpenOCD does.

**Prediction under H_A.** If we make `Rp235x::debug_port_setup` unconditionally send the dormant-to-SWD sequence (SWD→dormant + alert + activation `0x1A`) before the first DPIDR read, probe-rs should read DPIDR = `0x4c013477` and the subsequent AP IDR at `0x2000` should return `0x34770008` (matching OpenOCD's log).

## 4. Fix shape

Two candidate shapes. Both rely on the fact that `ArmDebugSequence::adi_version()` already exists (added in A.2c, `sequences.rs:458-460`) and `Rp235x` already returns `AdiVersion::V6`.

### 4.1 Fix shape A — Rp235x override, unconditional dormant on first attempt

Add `fn debug_port_setup` to `Rp235x` in `src/vendor/raspberrypi/sequences/rp235x.rs`. The method reuses the upstream retry structure but starts with `has_dormant = true`, so the first iteration sends the alert+activation sequence OpenOCD sends.

Pseudocode (not production code — the implementation agent writes the real thing):

```
fn debug_port_setup(&self, interface, dp) -> Result<(), ArmError> {
    tracing::debug!("Rp235x::debug_port_setup (ADIv6 dormant-wake path)");

    // Always start with dormant-to-SWD, matching OpenOCD `-adiv6` behaviour.
    // RP2354 needs the 128-bit JEDEC alert + SWD activation (0x1A) to
    // transition from its DPv2 power-on identity to its ADIv6 identity.
    // See HLD A.2d §2 for wire-level rationale.
    let mut has_dormant = true;

    // ... inline the upstream retry-loop body with SWD-protocol branch only
    // (Rp235x never uses JTAG), keeping alert_sequence() in scope ...
}
```

The `alert_sequence` helper is module-private to `sequences.rs`, so the vendor override either (i) duplicates it locally (~12 lines) or (ii) promotes it to `pub(crate)`. Option (ii) is cleaner; one-line visibility change.

### 4.2 Fix shape B — generic default, gated on `adi_version() == V6`

Modify the default `debug_port_setup` in `sequences.rs:529-638` to initialise `has_dormant` from `self.adi_version()`:

```
let mut has_dormant = matches!(dp, DpAddress::Multidrop(_))
    || self.adi_version() == AdiVersion::V6;
```

One-line change. Every other ADIv6 target in probe-rs (upstream and future) benefits.

### 4.3 Why *either* shape should work

The existing SWD-branch dormant code (`sequences.rs:594-603`) is **already correct** wire-level: it emits SWD-to-Dormant (31-bit `0x33BBBBBA`, which is the widely-deployed equivalent of the 16-bit `0xE3BC` in IHI 0074 — both settle the DP into dormant), then `alert_sequence` (8 bits `0xFF` + 64-bit `0x86852D956209F392` + 64-bit `0x19BC0EA2E3DDAFE9` = 128 bits JEDEC alert), then 12 bits = 4 low + 8-bit activation `0x1A`. That exactly matches OpenOCD's Dormant-to-SWD minus the final line reset (which probe-rs does a few lines later in `debug_port_connect` via `swd_line_reset(interface, 3)`). The code is already there; it's just not being *reached*.

## 5. Options

### Option I — Vendor override in `rp235x.rs` (fix shape A)

**Blast radius:** RP2350/RP2354 only.
**Delta:** ~35 lines in `rp235x.rs` (override body + module imports), plus a one-line visibility change in `sequences.rs` to promote `alert_sequence` to `pub(crate)`, OR a ~12-line copy of `alert_sequence` into `rp235x.rs`.
**Upstreamable?** Yes, alongside A.2c Option A, as "RP235x: send dormant-to-SWD on attach (matches OpenOCD `-adiv6`)."
**Regressions risk:** minimal. RP2040 vendor sequence unaffected — it doesn't override `debug_port_setup` (see `rp2040.rs`) and `adi_version()` defaults to V5.

### Option II — Generic default, gated on `adi_version() == V6`

**Blast radius:** every target that ever declares `AdiVersion::V6`. Today that's only Rp235x; tomorrow it could be nRF54L15, STM32N6, etc.
**Delta:** ~1 line in `sequences.rs:541`.
**Upstreamable?** Yes, and arguably the cleaner patch for upstream since A.2c's `adi_version` trait method was introduced precisely to be a target-property gate. OpenOCD's `-adiv6` flag has the same universal semantics.
**Regressions risk:** all V6 targets now send a dormant wake on every attach attempt. On a target that was working without it, the dormant sequence should be a no-op (the 128-bit alert + 0x1A activation is benign on an already-ADIv6 DP — it just cycles the DP through dormant and back, and the subsequent DPIDR read still returns the same value). But "should be a no-op" is not "is a no-op" — there's a non-zero risk that some already-working V6 target mis-behaves.

### Non-options (rejected)

- **Unconditional dormant on every target.** Would affect all non-ADIv6 targets too. The existing upstream PR #2914 author chose the retry-gated fallback precisely because "some targets don't like a spurious dormant wake." Rejected.
- **Re-read DPIDR after dormant.** Doesn't help — we need the dormant *before* the first DPIDR read, not after.
- **Flush DP state with abort.** Doesn't help — the DP's identity is fixed by which wake sequence it receives, not by sticky flags.

---

## 6. Recommendation

**Option I (vendor override).** Rationale:

1. **Known-safe scope.** RP2350/RP2354 is the only V6 target we ship today. Any regression risk is confined to the silicon we test on hardware anyway.
2. **Pattern-matched to existing vendor practice.** `vendor/microchip/sequences/atsam.rs` and other vendor files override `debug_port_setup` today. This is the documented way to add target-specific sequence steps.
3. **Defers the upstreamability call.** If Option I works, we can upstream it as-is (fix shape A) *or* refactor to fix shape B (upstream default, RP235x override removed) in a follow-up PR. The reverse — shipping fix shape B and being forced to retract it because a third-party V6 target regresses — is much costlier.
4. **Option II is 1 line vs. Option I's ~35 lines.** The difference is not material; we already maintain ~150 lines of A.2c refactor. The scope argument dominates.

If Option I fails Gate 4, we escalate to Option II (flip the default and see if blast radius materialises). If Option II also fails, the hypothesis is wrong and we diverge into H_D (residual) — see §9.

## 9. Risks

### 9.1 RP2040 regression

**Risk:** the dormant sequence on a DPv2/DPv1 target is malformed and the DP faults.

**Mitigation:** Option I confines the change to `Rp235x`; `rp2040.rs` doesn't override `debug_port_setup`. RP2040 path is byte-for-byte identical to pre-patch. Verified by Gate 4a. **Residual risk: near zero.**

### 9.2 Hypothesis wrong — DPIDR still reads `0x10212927`

**Risk:** sending the 128-bit alert + 0x1A activation doesn't actually change the DP identity on this silicon. Perhaps the RPi CoreSight-600 implementation does something else at wake time (a vendor-specific sequence, a POWER_REQ, a specific TARGETSEL-like encoding).

**Mitigation:**
1. Gate 4 is fast to run (5 min wall clock end-to-end).
2. If RED, capture USB-level CMSIS-DAP frames from both OpenOCD and probe-rs attaching to the same silicon within minutes of each other — diff the frames byte-for-byte. Tooling: Wireshark with USBPcap on Windows, or a CMSIS-DAP request logger (our fork already logs at TRACE). This is A.2e scope, not A.2d.
3. Fallback options already in A.2c §4 (Option C OpenOCD-backed oracle, Option D narrow silicon scope).

### 9.3 Intermittent flakes from dormant sequence (timing-sensitive)

**Risk:** The 128-bit alert + activation is a long wire burst (224 bits at 5 MHz ≈ 45 µs). CMSIS-DAP v2 packet boundaries or USB buffering could split the burst and the DP might see it as two separate sequences → ambiguous state.

**Mitigation:** probe-rs's existing `swj_sequence` at `cmsisdap/mod.rs:1168` already packs the u64 bits into `to_le_bytes()` and sends in one CMSIS-DAP `DAP_SWJ_Sequence` request. The alert sequence is split into 2×64 bits already (see `alert_sequence` at `sequences.rs:543-556`) but each half is sent as a single CMSIS-DAP request; the DP spec doesn't require strict back-to-back timing (the DP tracks the alert via a shift register, not a timer). **Residual risk: low.** If realised, Gate 4 will show flake — mitigation is a `swj_clock` call to pin the clock before the burst.

### 9.4 Test harness assumes current (broken) behaviour

**Risk:** Downstream harness code has worked around `WrongApType` in some tests, and after the fix those workarounds become bugs.

**Mitigation:** Gate 4c runs the full silicon suite. Any regressions are real and must be addressed. Budget: +1 h for follow-on triage if needed.

### 9.5 Option I is not upstreamable

**Risk:** upstream probe-rs would reject a RPi-specific `debug_port_setup` override in favour of the Option II pattern.

**Mitigation:** this is an *upstream* risk, not a fork risk. Our fork ships Option I. Upstream PR (if we choose to submit) can be Option II — the diff is small enough to do both. Non-blocking for Gate 4.

## 10. Open questions

### Q1 — Does the SWD-to-Dormant sequence need to come first on a fresh DP?

The existing probe-rs dormant path does `SWD-to-Dormant (0x33BBBBBA, 31 bits)` before `alert_sequence`. On a fresh probe attach, the DP is not necessarily in SWD mode — it might be in JTAG or unknown. OpenOCD sends `JTAG_TO_DORMANT` unconditionally (40 bits `ff 75 77 77 67`) rather than `SWD_TO_DORMANT`. The `0x33BBBBBA` is widely deployed and per the ARM spec commentary can safely transition *any* state to dormant, but "widely deployed" is weaker than "matches OpenOCD exactly." **Decision for impl agent:** start with probe-rs's existing `0x33BBBBBA` (it's in the body being copied); if Gate 4 fails yellow on this axis, try the OpenOCD `JTAG_TO_DORMANT` 40-bit sequence first. This is a one-line tweak to try if the first attempt yellows.

### Q2 — After Gate 4 green, should we also remove the retry-gated `has_dormant = true; if retry >= 1` in the default path?

No — that code still serves upstream non-V6 targets per probe-rs#2914. Leave it alone. Track A.2d's scope is RP235x only.

### Q3 — Does OpenOCD's success on the first DPIDR read imply `switch_through_dormant` defaults to `true` on ADIv6?

We couldn't confirm from source inspection where `switch_through_dormant` is initialised on an ADIv6 DAP. Likely candidates: `dap_create` in `tcl.c` when `-adiv6` is passed, or `dap_dp_init` when DPIDR.version == 3. Not load-bearing for A.2d — we're asserting the dormant wake unconditionally on Rp235x, which covers both paths.

### Q4 — What about RP2354 A2/B stepping silicon that might already report DPv3 on first read?

If such silicon exists, the dormant wake is a no-op (already ADIv6) — no harm. Gate 4 will confirm on our A0 silicon. Out-of-scope hardware is out-of-scope.

### Q5 — Do we also need to issue POWER_REQ before the first AP read?

`debug_port_start` at `sequences.rs:645-...` does power-up already (`Ctrl` write with `CSYSPWRUPREQ | CDBGPWRUPREQ`). That is independent of the dormant wake. No change needed.
