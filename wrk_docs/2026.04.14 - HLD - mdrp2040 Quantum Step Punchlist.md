## A. Halted core 0 freezes core 1

### Problem

`Emulator::step()` (`crates/mdrp2040/src/lib.rs:195`):

```rust
while self.clock.cycles < target && !self.cores[0].is_halted() {
```

If core 0 is halted at quantum start but core 1 is awake, the loop
never enters; `consumed = 0`, `run()` breaks, core 1 never steps.

### Bank-contention analysis (before picking a fix)

The main HLD says per-instruction interleaving is *required* for bank
contention. Verified against source:

- `core0_bank_touched: u8` (`crates/mdrp2040/src/bus/mod.rs:153`) is a
  bitmap; `note_sram_access` (`:342-357`) OR-accumulates with `|=` on
  any `active_core == 0` SRAM access — **accumulated, not overwritten**.
- `begin_core1_step()` (`:208`) sets `contention_check_active = true`
  but **does not reset the bank map**.
- `end_core1_step()` (`:216`) clears `contention_check_active` **and
  wipes `core0_bank_touched = 0`** — the map lives for exactly one
  core-0 → core-1 pair.
- Core 1 SRAM accesses with `contention_check_active && bit != 0` get
  +1 cycle.

Per-iteration sequence today: *core 0 touches bank(s) → core 1 contends
against exactly those bank(s) → wipe*. Correct per-pair contention.

**mdrp2350 does not have a live contention model.** `arbitrate_pair` /
`arbitrate_stall` (`crates/mdrp2350/src/bus/mod.rs:329-350`) are a
standalone API exercised only by `tests.rs:5317-5382`, **never called
from `read32`/`write32`** (verified by grep). mdrp2350's serial drain
is safe precisely because nothing is live to break. No end-to-end
cross-core contention test exists on either chip.

**What a full serial drain would do on mdrp2040:** core 0 would OR-
accumulate every bank it touches across the whole quantum into
`core0_bank_touched`; then core 1 would drain against the *union*,
so every core-1 SRAM access contends if core 0 ever touched that
bank anywhere in the quantum. At quantum 64 with core 0 sweeping all
four striped banks once, every subsequent core-1 SRAM access would
false-positive +1. v1.0.0 of this HLD got this wrong.

**Conclusion:** the main HLD's interleaving requirement is correct;
a full per-core serial drain silently breaks bank-contention timing.

### Option 1 — Targeted fix (CHOSEN)

Keep per-instruction interleaving; relax only the loop guard and arm
both cores independently.

```rust
pub fn step(&mut self) -> u64 {
    debug_assert!(self.step_quantum > 0, "step_quantum must be >= 1");
    let start = self.clock.cycles;
    let target = start.wrapping_add(self.step_quantum as u64);

    while self.clock.cycles < target
        && (!self.cores[0].is_halted() || !self.cores[1].is_halted())
    {
        let c0 = if !self.cores[0].is_halted() {
            self.bus.set_active_core(0);
            let c = self.cores[0].step(&mut self.bus) as u64;
            self.maybe_wake_core1(0);
            c
        } else { 0 };

        let c1 = if !self.cores[1].is_halted() {
            self.bus.set_active_core(1);
            self.bus.begin_core1_step();
            let c = self.cores[1].step(&mut self.bus) as u64;
            self.bus.end_core1_step();
            self.maybe_wake_core1(1);
            c
        } else {
            self.bus.end_core1_step();
            0
        };

        if c0 == 0 && c1 == 0 { break; }
        self.clock.cycles = self.clock.cycles.wrapping_add(c0.max(c1));
    }

    let consumed = self.clock.cycles.wrapping_sub(start);
    self.tick_pio(consumed as u32);
    self.update_gpio();
    self.wake_checks();
    consumed
}
```

Master clock advances by `max(c0, c1)` — both cores share one clock on
real silicon. When only one core runs, max collapses to that core's
cycles (identical to the old asymmetric path when core 1 was halted).

### Option 2 — Full per-core serial drain (REJECTED)

Adopt mdrp2350's `for core_id in 0..2` pattern. Simpler control flow,
one shape across both chips. **Rejected**: silently degrades bank-
contention correctness (union instead of per-pair, see analysis
above). No existing test catches it, so the regression would land
silently and only surface under firmware workloads. Would force
amending the main HLD and adding cross-core contention tests first.

### Recommendation: Option 1

A three-line guard relaxation plus independent arm of the two step
calls; preserves the main HLD's interleaving contract; preserves
bank-contention per-pair semantics; fixes the bug. Disproportionate
to consider Option 2 given the main HLD is unamended.

### What does NOT change

- `maybe_wake_core1`, FIFO/SIO/PIO semantics.
- Default `step_quantum = 64`.
- Per-pair bank-contention: core 0 touches → core 1 contends against
  *those exact* touches → wipe.
- Quantum-end peripheral tick.

### Risks

- **`max(c0, c1)` vs old `c0`.** When both cores run, master clock
  steps by the longer. `run()` only inspects `consumed == 0`, so
  invisible there; `paced_bench_rp2040` tallies actual consumed
  cycles (commit `6fedd39`).
- **Asymmetric iteration costs** (e.g. c0=4 BL, c1=1 NOP) give core 1
  three "free" cycles of peripheral-time. Unchanged from current
  code, which already advances master clock by `c0` regardless of
  `c1`. Not introduced here.

### Test

One regression test in `crates/mdrp2040/src/tests.rs` under
`mod emulator_step`, fails under current bug, passes after fix:

```rust
#[test]
fn halted_core0_does_not_freeze_core1() {
    let mut emu = EmulatorBuilder::new(Config::default()).step_quantum(4).build();
    let prog = 0x2000_1000u32;
    for i in 0..8u32 {
        emu.bus.write16(prog + i * 2, 0xBF00); // NOP
    }
    emu.cores[1].wake();
    emu.cores[1].regs.set_pc(prog);
    emu.cores[1].regs.msp = 0x2002_0000;
    emu.cores[1].regs.r[13] = emu.cores[1].regs.msp;
    emu.cores[0].halt();

    let pc_before = emu.cores[1].regs.pc();
    let consumed = emu.step();
    assert!(consumed > 0, "step() must advance when core 1 is runnable");
    assert!(emu.cores[1].regs.pc() > pc_before, "core 1 PC must advance");
}
```

## B. Quantum-contract tests

### Problem

The main HLD relies on four `step()` contracts. None are pinned down in
tests; future changes can silently regress semantics.

### Proposed change

New `mod quantum_contract` at the bottom of
`crates/mdrp2040/src/tests.rs`. Four tests, one per contract.

**PIO observable for contract #3.** `StateMachine::pc` is `pub(crate)`,
not `pub fn pc()`; `tests.rs` is in-crate and can read the field, but
coupling tests to an internal field is weak. Use `PioBlock::pad_out`
instead: it is `pub` and is the accepted idiom in `pio_tests.rs`
(lines 96, 150, 163, 174, 185, 469, 483). A 2-instruction SM0 program
— `SET PINS, 1` then `SET PINS, 0` with auto-wrap — makes `pad_out & 1`
equal `1` on odd PIO cycles and `0` on even. Reference = N × quantum 1;
subject = 1 × quantum N. If `tick_pio` fires twice per step the subject
diverges.

Four tests (sketched; `seed_nop_program` shared helper):

1. **`step_quantum_1_advances_by_one_instruction`** — builder with
   `step_quantum(1)`, NOP seeded, assert `step() == 1` and `pc += 2`.
2. **`step_quantum_n_advances_within_bounds`** — `step_quantum(N=16)`,
   NOP seeded, assert `N <= c < N + MAX_INSTR_COST` where
   `MAX_INSTR_COST = 4` (BL on M0+).
3. **`step_return_equals_clock_delta`** — `step_quantum(8)`, assert
   `c == emu.cycles() - before`.
4. **`peripherals_tick_once_per_step`** — two emulators, one
   `step_quantum(1)` reference looped N times, one `step_quantum(N=8)`
   subject stepped once; both seeded with identical 2-instruction
   SM0 toggle program; assert
   `subject.bus.pio[0].pad_out & 1 == reference.bus.pio[0].pad_out & 1`.

### What does NOT change

No production code.

### Risks

- **Contract #2 fragile vs future WFE.** When WFE lands, a core may
  suspend mid-quantum and `consumed < quantum` becomes legitimate.
  Tracked in `tech_debt.md` ("RP2040 WFE/SEV").

## D. Test-builder helper

### Problem

12 sites repeat `EmulatorBuilder::new(Config::default()).step_quantum(1)
.build()`: 5 in `pio_tests.rs` (210, 296, 337, 437, 448), 5 in
`tests.rs` (1807, 1834, 1866, 1895, 1919), 2 in `tests/firmware.rs`
(44, 96). The new `halted_core0_does_not_freeze_core1` uses
`step_quantum(4)`, so it is not a site — v1.0.0 miscounted.

### Option X — Minimal in-crate helper

`#[cfg(test)] pub(crate) fn single_cycle_emu()` in
`crates/mdrp2040/src/lib.rs`, reachable from both `src/tests.rs` and
`src/pio_tests.rs` (10 sites). `tests/firmware.rs` is a separate
compilation unit and can't reach `pub(crate)`, so it keeps a single
local copy (2 sites). Net: 2 copies covering 12 sites, saves ~10
lines across two files.

### Option Y — No factoring (CHOSEN)

Skip §D. The code-reviewer called it a nit, not a blocker. At 12 sites
the builder call is localised, declarative, and immediately greppable;
a `single_cycle_emu()` indirection hides the quantum-1 semantics from
the reader at each call site — the tests are specifically saying *I
want quantum 1 here, not the default*, and the builder says so inline.

### Recommendation: Option Y

Duplication is a pattern here, not accidental. If a future test adds
clock-frequency or peripheral-config variants and boilerplate grows,
revisit with Option X.

### What does NOT change

Everything. §D drops out of the changeset.

## C. Deferred — Pacer MHz undercount

`crates/mdrp2040app/src/sim.rs:52` passes `qc = pacer.quantum_cycles()
= 150` to `emu.run(qc)`. `run()` overshoots by up to `step_quantum - 1
= 63` cycles, but `Pacer` reports MHz from cycles *asked for*, not
cycles *consumed*. Systematic undercount of up to ~42% on the first
quantum (63/150) amortising toward ~22% on longer runs. Fix requires a
`Pacer` API extension — deferred.

### Proposed tech_debt.md entry

Add under "Phase 5.A Simplifications (RP2040 bus)":

> ### RP2040 pacer MHz panel undercounts consumed cycles
>
> `crates/mdrp2040app/src/sim.rs` calls `emu.run(pacer.quantum_cycles())`
> and `Pacer` reports MHz from cycles *asked for*. `run()` overshoots by
> up to `step_quantum - 1` cycles (quantum-step landed in
> `wrk_docs/2026.04.14 - HLD - mdrp2040 Quantum Step.md` v1.2.0), so the
> app's MHz panel systematically undercounts by up to ~22% at default
> settings — surfaced during the punchlist review (see
> `wrk_docs/2026.04.14 - HLD - mdrp2040 Quantum Step Punchlist.md`).
> Fix requires a `Pacer` API extension to feed consumed cycles back
> (replace `begin_quantum`/`end_quantum` with a form that takes the
> actual cycle count from `emu.run`'s return). Low priority — firmware
> runs correctly; only the displayed MHz figure is wrong.
