# 2026-04-26 — HLD — RP2040 Slow-Path Chunked Peripheral Advance

## 1. Goal

Reduce per-cycle slow-path overhead on `mdrp2040`'s `step_serial` by ticking peripherals once per quantum instead of N times. Targeted at the PicoGUS OPL3 workload, which spends ~200 ns of host work per emulated master cycle in the slow-path inner loop.

Expected gain (paired with the q=4 default landed earlier today): another 25–35% wall reduction on `picogus_diff_rp2040 --firmware-mode 5`, taking the cumulative win since baseline to roughly 35–45%.

## 2. Background — current slow path

`crates/mdrp2040/src/lib.rs:639` `Emulator::step_serial`:

```rust
for _ in 0..consumed {
    self.bus.master_cycle = self.bus.master_cycle.wrapping_add(1);
    self.bus.tick_peripherals();        // 8 peripherals × tick(1, …)
    if self.bus.systicks[active].tick() { … }
    self.tick_pio_and_route_irqs_single();   // pio.step_n(1) × 2
    self.update_gpio();
    self.drain_pending_irqs_to_cores();
}
```

Iter 1's instrumented bench attributed ~31% of slow-path wall to `tick_pio_irqs` and ~27% to `tick_peripherals`, with the remainder split across `update_gpio`, `drain_pending_irqs`, and `systick`. None of the per-cycle work is structurally per-cycle: most peripherals already accept a `cycles: u32` argument and use accumulator state. The slow path is calling them N times with `1` because of an interleave the original design didn't justify.

The per-cycle interleave was inherited from the bank-contention model, which has been formally retired (CLAUDE.md "Bank contention model"). With contention dead-in-place, there is no design reason to keep the per-cycle peripheral tick.

## 3. Reference — `mdrp2350`

`mdrp2350` already implements the target shape. `crates/mdrp2350/src/lib.rs:649` `Emulator::step_serial`:

```rust
match &mut self.cores {
    Cores::Arm(cs)   => step_pair_arm(cs,   &mut self.bus, target),
    Cores::RiscV(cs) => step_pair_riscv(cs, &mut self.bus, target),
}
self.clock.advance(self.step_quantum as u64);
self.tick_peripherals(self.step_quantum);   // ONCE
self.tick_systick();
self.wake_checks();
```

`Emulator::tick_peripherals(cycles)` at `crates/mdrp2350/src/lib.rs:1010` calls `pio[i].step_n(cycles, gpio_in)` once per block, then delegates to `Bus::tick_peripherals(sys_clks)` at `crates/mdrp2350/src/bus/mod.rs:1077` which advances every modelled peripheral with the cycle count and ticks DMA exactly once.

This refactor mirrors that pattern in `mdrp2040`, adapted for the RP2040 differences (no TICKS, no POWMAN, no RISC-V; different IRQ count; PIO0/1 only).

## 4. Open questions — investigation results

### 4.1 Sub-quantum IRQ delay tolerance (Arthur Q1)

PicoGUS firmware **is interrupt-driven** for ISA-bus capture: `RXNEMPTY_SM0` on PIO0 INT0_INTE asserts NVIC line 7 (`PIO0_IRQ_0`) when an autopushed ISA event lands in PIO0 SM0's RX FIFO. Source: `crates/mdrp2040/src/lib.rs:787` `tick_pio_and_route_irqs_single` doc comment.

Audit of the trace data places ~1800 ISA events across 2.5 s sim, i.e. ~720 events/s. This is modest — the ISR has 1.7 ms between events on average, far longer than the up-to-quantum delay we'd introduce.

The q=4 measurement landed earlier today is the load-bearing evidence: the per-cycle slow path delivers IRQs to the CPU on the *next* cycle (≤1 cycle delay), while the chunked path delivers at end-of-quantum (≤N-1 cycle delay). Going from "≤1" to "≤3" cycles at q=4 is well below the 37-cycle ISA write window the original `step_quantum=1` guard was protecting. **Risk: low.** Cake-gate validates regardless.

### 4.2 `silicon_periph_diff_rp2040` status (Arthur Q2)

Per CLAUDE.md ("`silicon_periph_diff_rp2040` ships ahead of silicon hookup … scenarios will FAIL on the EMU side until `Bus::irq_pending` + `tick_peripherals` + pending-exception dispatch land in `CortexM0Plus::step`"). The oracle exists for HLD-checkpoint compliance but is not currently a regression gate. **No constraint on this design.**

### 4.3 `mdrp2350` parity (Arthur Q3)

Already exists, fully tested, in production. The 945+ test suite covers the chunked path; the threaded runtime depends on it. **The pattern is proven.** This refactor brings RP2040 into structural alignment.

## 5. Design

### 5.1 Scope of change

**In scope:**
- Refactor `Emulator::step_serial` in `crates/mdrp2040/src/lib.rs` to mirror RP2350: cores tick first per-cycle internally, then peripherals tick once with the quantum cycle count.
- Add `Bus::tick_peripherals(cycles: u32)` (rename existing `tick_peripherals()` → take a count). All inner peripheral `tick(n, …)` signatures already accept `cycles`; just propagate.
- Add `tick_systick(cycles)` that advances both cores' SysTick by `cycles` instead of one cycle.
- Replace `tick_pio_and_route_irqs_single()` with `tick_pio_and_route_irqs(cycles)`. Calls `pio[block].step_n(cycles, gpio_in)` once per block (already exists).
- DMA: keep `Bus::tick_dma()` once-per-quantum at the tail of `Bus::tick_peripherals`. Mirrors RP2350. Validation: cake-gate.
- Remove the slow-path `for _ in 0..consumed` loop entirely. Single straight-line tick at quantum end.

**Out of scope:**
- The fast-path gate at `lib.rs:718` stays as-is. It still gates on the fast/slow choice for fully-idle quanta; only the slow branch is being changed.
- The threaded runtime (`crates/mdrp2040/src/threaded/`) is not touched — its peripheral path already runs once per quantum.
- No changes to peripheral internals. `tick(cycles, …)` already exists on every peripheral that needs it.
- No new feature flags. No fallback to the per-cycle path. No backwards-compat shim.

### 5.2 New / modified function signatures

```rust

impl Bus {
    pub fn tick_peripherals(&mut self, sys_clks: u32) {

        self.i2c1 .tick(sys_clks, …);
        self.adc  .tick(sys_clks, …);
        self.pwm  .tick(sys_clks, …);
```

```rust
// crates/mdrp2040/src/lib.rs
//
// Was: tick_pio_and_route_irqs_single() — calls step_n(1) × 2
impl Emulator {
    fn tick_pio_and_route_irqs(&mut self, cycles: u32) {
        let gpio_in = self.bus.gpio_in;
        self.pio_tick_count = self.pio_tick_count.wrapping_add(cycles as u64);
        // diagnostic: pio0_sm0_max_pc / pc_advances unchanged in shape,
        //             observed once per quantum instead of once per cycle.
        if gpio_in & (1u32 << 4) == 0 {
            self.pio_tick_iow_low_count =
                self.pio_tick_iow_low_count.wrapping_add(cycles as u64);
        }
        self.bus.pio[0].step_n(cycles, gpio_in);
        self.bus.pio[1].step_n(cycles, gpio_in);
        // PC observation done once at quantum end — same shape, different
        // resolution. Acceptable: PicoGUS sees ~720 PIO events/s, well
        // below quantum frequency.
        let sm0_pc = self.bus.pio[0].sm[0].pc();
        if sm0_pc > self.pio0_sm0_max_pc { self.pio0_sm0_max_pc = sm0_pc; }
        if sm0_pc != self.pio0_sm0_last_pc {
            self.pio0_sm0_pc_advances =
                self.pio0_sm0_pc_advances.wrapping_add(1);
            self.pio0_sm0_last_pc = sm0_pc;
        }
        for (block, line0_bit) in [(0usize, 7u32), (1usize, 9u32)] {
            if self.bus.pio[block].int0_ints_rp2040() != 0 {
                self.bus.irq_pending |= 1u32 << line0_bit;
            }
            if self.bus.pio[block].int1_ints_rp2040() != 0 {
                self.bus.irq_pending |= 1u32 << (line0_bit + 1);
            }
        }
    }

    fn tick_systick(&mut self, cycles: u32) {
        let active = self.bus.active_core();
        for _ in 0..cycles {
            if self.bus.systicks[active].tick() {
                self.bus.ppb[active].icsr |= 1 << 26;
            }
        }
    }
}
```

`tick_systick` keeps the per-cycle loop because `SysTick::tick()` decrements a 24-bit counter and reloads on underflow — a chunked variant would need `advance_n` semantics that the SysTick struct does not currently expose. The loop is cheap (one branch + one decrement per iteration in the common non-firing case) and is bounded by `step_quantum` (default 4). If profiling shows this remains hot post-refactor, add `SysTick::advance_n(cycles) -> u32` returning the number of underflows; not worth the code surface up front.

### 5.3 New `step_serial` shape

```rust
fn step_serial(&mut self) -> u64 {
    self.bus.master_cycle = self.clock.cycles;
    let start = self.clock.cycles;
    let target = start.wrapping_add(self.step_quantum as u64);

    // Cores tick per-cycle internally (instruction completion is
    // multi-cycle and faults are cycle-precise). Same loop body as
    // today, minus the embedded peripheral tick.
    while self.clock.cycles < target
        && (!self.cores[0].is_halted() || !self.cores[1].is_halted())
    {
        let c0 = if !self.cores[0].is_halted() { /* … unchanged … */ };
        let c1 = if !self.cores[1].is_halted() { /* … unchanged … */ };
        if c0 == 0 && c1 == 0 { break; }
        self.clock.cycles = self.clock.cycles.wrapping_add(c0.max(c1));
    }
    let consumed = self.clock.cycles.wrapping_sub(start);

    // Fast-path branch unchanged.
    let pio_idle    = self.bus.pio_all_idle();
    let peri_idle   = self.bus.all_peripherals_idle();
    let dma_idle    = self.bus.dma.is_idle();
    let any_irq     = self.bus.irq_pending != 0;
    let systick_idle = !self.bus.systicks[self.bus.active_core()].is_enabled();
    if pio_idle && peri_idle && dma_idle && systick_idle && !any_irq {
        self.tick_pio(consumed as u32);
        self.bus.advance_lazy_scheduled(consumed);
        self.drain_pending_irqs_to_cores();
        self.update_gpio();
    } else {
        // Slow branch — chunked.
        self.bus.master_cycle = self.bus.master_cycle.wrapping_add(consumed);
        self.bus.tick_peripherals(consumed as u32);
        self.tick_systick(consumed as u32);
        self.tick_pio_and_route_irqs(consumed as u32);
        self.update_gpio();
        self.drain_pending_irqs_to_cores();
    }
    self.wake_checks();
    consumed
}
```

The slow branch goes from O(N) function-call frames to O(1). At quantum=4, that's 5 calls instead of 20. At quantum=64 (post-this-change, if Arthur revisits the quantum sweep), 5 calls instead of 320.

### 5.4 IRQ delivery semantics

Today: peripheral asserts IRQ at cycle `k` of an N-cycle quantum → `bus.irq_pending` set at cycle `k` → `drain_pending_irqs_to_cores` at end-of-cycle `k` routes to NVIC → CPU sees pending IRQ at cycle `k+1`.

After: peripheral asserts IRQ during the chunked tick at quantum end → `bus.irq_pending` set at cycle `N` → `drain_pending_irqs_to_cores` at end-of-quantum routes to NVIC → CPU sees pending IRQ at start of next quantum.

**Net effect**: IRQ delivery delay grows from `O(1)` to `O(N)` cycles. At the default q=4, that's up to a 3-cycle additional delay. Validated by the q=4 measurement landed earlier today, which already tolerates this magnitude of timing slip without audible regression.

**This is the intentional behaviour change.** Documented at `tick_peripherals` and `step_serial` in the source via doc-comments referencing this HLD.

## 6. Validation

### 6.1 Existing test suite

`cargo test -p mdrp2040 --release` (924 unit + 47 integration). Must remain green. Tests that arm a peripheral and assert IRQ-after-N-cycles will see IRQ delivery shift by up to `step_quantum-1` cycles; any test that pins exact cycle-of-IRQ-arrival is genuinely overspecified for the chunked design and will need its assertion loosened to "IRQ pending within the next quantum" — same accommodation `mdrp2350` already lives with.

### 6.2 Threaded parity

`cargo test -p mdrp2040 --release --features threading --test dual_model`. Serial and Threaded paths must produce the same end state. Threaded already runs once-per-quantum; this refactor brings Serial into agreement, so dual_model parity becomes *easier* to maintain, not harder.

### 6.3 PicoGUS audio cake-gate

Replay Monkey Island AdLib trace at default `--step-quantum 4`. Required:
- Peak ≥ −20 dBFS
- ≥ 4 musical-band peaks (60–5000 Hz)
- Top-5 FFT peaks within 1 dB of pre-refactor baseline

If those clear, also run the q=16 and q=64 sweeps from earlier today and report. If chunked tick lifts the q=64 silence (because per-cycle ISA-pin sample alignment was the q=64 break, not the peripheral overhead), record the new safe-quantum upper bound.

### 6.4 Quantum sweep re-measurement

Re-run `wrk_scratch/bench_quantum_sweep.sh` post-refactor:
- Confirm q=4 wall reduces by 25–35% beyond today's 80.95 s baseline.
- Confirm cycles delta within ±0.2% of pre-refactor (peripheral state-update count is identical when batched correctly — this catches a class of bugs where an off-by-one in chunked tick produces a different cycle path-length from the firmware).

## 7. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| TIMER alarm fires inside a quantum but the chunked poll misses it | Low | `Timer::poll_alarms` already takes the latest `master_cycle`; we update `master_cycle` *before* calling `tick_peripherals(N)`. Covered by `phase1_tests::tick_peripherals_alarm_match_raises_irq_via_assert_shared` (mirrored on RP2350; need to verify equivalent exists on RP2040). |
| DMA throughput cap (one transfer per quantum) starves I2S | Low | OPL3 needs ~88 K transfers/s; at q=4 we get 31 M transfers/s ceiling. Cake-gate catches this if it's wrong. |
| Per-cycle observation diagnostics (`pio0_sm0_pc_advances`) under-count | Medium-low | Diagnostic-only counters; downstream consumers (perf journal, paced_bench) treat them as relative ranking, not absolute. Documented in the doc-comment. |
| A test pins exact IRQ-delivery cycle | Medium | Loosen the assertion; same fix `mdrp2350` already lives with. Listed up-front so it doesn't surprise. |
| Q=64 still breaks audio post-refactor | Medium | Acceptable — q=64 is not a goal of this refactor. Validated outcome is "q=4 stays clean and is faster"; q=64 unlock is bonus. |

## 8. Non-goals

- **No fallback to the per-cycle path.** CLAUDE.md is explicit: "We do not need to support the old code." Once the chunked path lands, the per-cycle slow path is gone. The Bus's `tick_peripherals(1)` is callable from tests if a test genuinely needs cycle-by-cycle granularity.
- **No environment variable, no `--legacy-tick` flag.** The default behaviour is the chunked behaviour. Period.
- **No reorganisation of the peripheral module structure.** Each peripheral's `tick(cycles, …)` already exists; we just call them with the real cycle count instead of `1`.
- **No introduction of `tick_n` as a separate method.** The existing `tick(cycles, …)` IS the chunked method. Renaming is churn.
- **No changes to fast-path gate logic.** That's a separate optimisation; coupling it to this change risks confounding the cake-gate validation.
- **Not addressing threading wire-in for `picogus_diff_rp2040` (move #3).** That's a follow-up dependent on this landing first.

## 9. Sequencing

1. Refactor `Bus::tick_peripherals` to take `cycles: u32`. Build, fix any in-tree callers (~10 sites grep-able). Run `cargo test -p mdrp2040`.
2. Refactor `Emulator::tick_pio_and_route_irqs_single` → `tick_pio_and_route_irqs(cycles)`. Single caller (`step_serial`).
3. Add `Emulator::tick_systick(cycles)` (loop today, optimise to `advance_n` later if needed).
4. Refactor `step_serial` slow branch to single-pass chunked tick.
5. Run unit tests; relax any over-specified IRQ-cycle assertions; re-confirm threaded parity.
6. Run quantum sweep; record results in `wrk_journals/2026.04.26 - JRN - RP2040 OPL3 Perf Optimization.md`.
7. Bump `mdrp2040` Cargo.toml minor (slow-path semantics change is a behaviour change for downstream).

Estimated scope: ~250 lines of source change across `lib.rs` + `bus/mod.rs`, ~50 lines of test adjustment. Single focused commit.
