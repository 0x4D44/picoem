## 1. Goal

Reduce per-cycle slow-path overhead on `mdrp2040`'s `step_serial` by ticking peripherals once per quantum instead of N times. Targeted at the PicoGUS OPL3 workload, currently ~36–55× slower than real-time.

**Success bar**: ≥10% wall reduction on `picogus_diff_rp2040 --firmware-mode 5` at default q=4, paired with a clean audio cake-gate. If the measured gain is below 10%, **revert via git** and reopen the design — do not commit a marginal-or-negative change. The 25–35% range earlier journal entries cited was derived from Iter 1's instrumented bench, which the journal itself flags as polluted by `Instant::now()` overhead (~30 ns/call) inflating sub-100ns attributions; treat that as an upper bound for hope, not a planning number.

## 2. Background — current slow path

`crates/mdrp2040/src/lib.rs:730-749` `Emulator::step_serial`:

```rust
for _ in 0..consumed {
    self.bus.master_cycle = self.bus.master_cycle.wrapping_add(1);
    self.bus.tick_peripherals();          // 8 peripherals × tick(1, …)
    let active = self.bus.active_core();
    if self.bus.systicks[active].tick() { … }
    self.tick_pio_and_route_irqs_single();   // pio.step_n(1) × 2
    self.update_gpio();
    self.drain_pending_irqs_to_cores();
}
```

None of the per-cycle work is *structurally* per-cycle: every peripheral already accepts a `cycles: u32` argument and uses accumulator state. The slow path is calling them N times with `1` because of an interleave the original design didn't justify — the per-cycle interleave was inherited from the bank-contention model, formally retired (CLAUDE.md "Bank contention model").

## 3. Reference — `mdrp2350`

`mdrp2350` already implements the target shape. `crates/mdrp2350/src/lib.rs:649` `Emulator::step_serial` ticks peripherals once per quantum via `tick_peripherals(self.step_quantum)`; `crates/mdrp2350/src/lib.rs:1010` and `crates/mdrp2350/src/bus/mod.rs:1077` define the chunked entry points.

**The mirror is structural, not semantic.** RP2350 runs at default `step_quantum=1024`, has different peripherals (TICKS, POWMAN, dual-ISA Cortex-M33+RV32), and exercises different workloads. RP2040-specific quirks must be validated separately:

- **Dual-core SysTick** — RP2350's ARM path uses `arm[core_id].ppb.systick_advance(cycles)` per core. RP2040 must do the same; V1's "tick `active_core()`'s SysTick N times" preserved a latent bug (see §5.2 below).
- **PSRAM PIO timing** — RP2040's PSRAM model exercises PIO step_n at `clkdiv=2`. Iter 4's bulk-skip experiment showed this clkdiv-sensitive; same code path lives in `step_n` regardless of how often it's called.
- **OPL3 ISA-waveform sampling** — already characterised by today's quantum sweep: q=4 audio-clean, q=64 silent. The chunked refactor preserves q=4 as default; a fresh sweep must re-validate.

## 4. Open questions — investigation results

### 4.1 IRQ delivery semantics under chunked tick (Arthur Q1)

PicoGUS firmware is interrupt-driven for ISA-bus capture: `RXNEMPTY_SM0` on PIO0 INT0_INTE asserts NVIC line 7 (`PIO0_IRQ_0`) when an autopushed ISA event lands in PIO0 SM0's RX FIFO. Source: `crates/mdrp2040/src/lib.rs:787`.

Trace data: ~1800 ISA events across 2.5 s sim → ~720 events/s, ~1.7 ms between events. The IRQ-delivery delay this refactor introduces is bounded by `step_quantum-1` cycles (3 cycles at q=4, ~24 ns wall at 125 MHz emulated). Three orders of magnitude below the inter-event interval.

**The q=4 measurement landed earlier today is NOT load-bearing evidence for this refactor.** That measurement was taken on the per-cycle slow path with N=4 ticks/quantum scattered through the inner loop. The chunked path has ONE tick at end-of-quantum, with peripheral state changes batched. These are different timing models. **Cake-gate on the chunked path is the load-bearing validation** (§6.3). If cake-gate fails post-refactor, debug by reducing default quantum, not by re-citing the per-cycle q=4 result.

### 4.2 `silicon_periph_diff_rp2040` status (Arthur Q2)

Per CLAUDE.md ("`silicon_periph_diff_rp2040` ships ahead of silicon hookup"), the oracle is HLD-checkpoint compliance, not a regression gate. **No constraint on this design.**

### 4.3 `mdrp2350` parity (Arthur Q3)

Pattern proven, threaded runtime depends on it, 945+ tests cover it. The RP2350-vs-RP2040 differences listed in §3 are real; the chunked-tick *mechanism* itself is well-understood.

## 5. Design

### 5.1 Scope of change

**In scope:**
- Refactor `Emulator::step_serial` slow branch in `crates/mdrp2040/src/lib.rs` to tick peripherals once with the consumed cycle count, mirroring RP2350.
- Update `Bus::tick_peripherals` signature to take `cycles: u32`. All inner peripheral `tick(n, …)` already accept a cycle count.
- Replace `tick_pio_and_route_irqs_single()` with `tick_pio_and_route_irqs(cycles: u32)`. PIO `step_n(cycles, gpio_in)` already does the right thing.
- Add `Emulator::tick_systick(c0_cycles: u32, c1_cycles: u32)` per §5.2.
- DMA: keep `Bus::tick_dma()` once-per-quantum at the tail of `Bus::tick_peripherals`. Mirrors RP2350.
- Move `update_gpio()` from per-cycle (current slow loop) to per-quantum (after `tick_pio_and_route_irqs`). Mirrors RP2350.
- Remove the slow-path `for _ in 0..consumed` loop entirely. Single straight-line tick at quantum end.

**Out of scope:**
- Fast-path gate at `lib.rs:718` stays as-is.
- Threaded runtime untouched (its peripheral path is already once-per-quantum; verified — `crates/mdrp2040/src/threaded/peripherals.rs` has no callers of the changed `Bus::tick_peripherals` signature).
- No changes to peripheral internals beyond the bus-level wrapper.
- No feature flag, no env var, no `--legacy-tick` fallback. CLAUDE.md is explicit: "We do not need to support the old code." If cake-gate fails, revert via git.

### 5.2 SysTick — per-core cycle accounting (V2 design correction)

#### 5.2.1 The bug in current code (cited)

`crates/mdrp2040/src/lib.rs:730-749`:

```rust
730  for _ in 0..consumed {
…
742      let active = self.bus.active_core();
743      if self.bus.systicks[active].tick() {
744          self.bus.ppb[active].icsr |= 1 << 26;
745      }
…
749  }
```

`active_core` is a simple `usize` field on `Bus` (`crates/mdrp2040/src/bus/mod.rs:426`); `set_active_core(c)` (`bus/mod.rs:542`) just stores the argument. The inner-loop dispatch above this snippet calls `set_active_core(0)` before core 0's step, then `set_active_core(1)` before core 1's step. **When both cores run, `active_core() == 1` at line 742.** Result: when both cores run, `systicks[0]` is *never* advanced by this loop. SysTick[0] only ticks when core 1 is halted.

This contradicts ARMv6-M semantics: each core's SysTick is per-core hardware, decrementing on cycles its core consumes. SysTick[0] should advance whenever core 0 advances, regardless of what core 1 is doing.

V1's chunked design preserved this bug by sampling `active_core()` once at quantum end. **V2/V3 fix it.**

#### 5.2.2 The "decouple from this refactor" tie-break

Devil's advocate Round 2 argued: land the chunked refactor first preserving the bug, then fix SysTick separately for clean bisection.

**This is not feasible.** Once we batch peripheral advance, the SysTick path inside `tick_peripherals` (or peer to it) needs a cycle-count argument. We have to decide *now* what each SysTick advances by. Three options:

1. **Preserve the bug**: pass a single `cycles` to "the active core's SysTick" → carries the latent dual-core bug forward, requires a second commit to fix.
2. **Pass the active core's cycles to one SysTick, zero to the other** → equivalent to (1), more code.
3. **Per-core accounting** → fix the bug in passing.

Option 3 is no more code than (2) and removes the bug. The bisection concern is real but mitigated by the §8 pre-refactor audit (positive dual-core SysTick test must pass *both* before and after the refactor). The audit gives us an independent regression detector that doesn't rely on the cake-gate.

#### 5.2.3 Design

The cores' inner-loop `step()` returns the cycles each core actually consumed (M0+ instructions take 1–4 cycles depending on opcode — `MULS=1`, `LDR=2`, `BL=4`, `LDM N=1+N`; see `crates/mdrp2040/src/core/execute.rs`). `c0` and `c1` differ in the common case; they happen to be equal only when both cores are running same-cycle-cost instructions in lockstep. The clock advances by `c0.max(c1)` (`lib.rs:687`); each core's individual cycle count is what its SysTick should advance by.

```rust
// Inside step_serial inner loop, accumulate per-core:
c0_total = c0_total.wrapping_add(c0);
c1_total = c1_total.wrapping_add(c1);

// After inner loop, in slow branch:
self.tick_systick(c0_total as u32, c1_total as u32);
```

```rust
fn tick_systick(&mut self, c0: u32, c1: u32) {
    for _ in 0..c0 {
        if self.bus.systicks[0].tick() {
            self.bus.ppb[0].icsr |= 1 << 26;
        }
    }
    for _ in 0..c1 {
        if self.bus.systicks[1].tick() {
            self.bus.ppb[1].icsr |= 1 << 26;
        }
    }
}
```

#### 5.2.4 Loop-bound analysis

At default q=4, the loop runs at most `c0_total + c1_total ≤ 2 × step_quantum = 8` iterations (each core consumes at most `step_quantum` cycles in a quantum). At q=64, ≤128 iterations. SysTick `.tick()` is one branch + one decrement (~3 ns); 8 iterations ≈ 24 ns/quantum at q=4, 128 iterations ≈ 400 ns/quantum at q=64.

At q=4 (the operational target): 24 ns is well under the slow-path floor we're attacking (~200 ns/cycle × 4 = 800 ns/quantum); SysTick is 3% of slow-path budget. Not a concern.

At q=64 (a hypothetical larger quantum if chunking unlocks it): 400 ns/quantum SysTick against a vastly-reduced slow-path floor would matter. **At that point**, the optimisation is `SysTick::advance_n(n) -> u32` returning the number of underflows in closed-form. Not worth the code surface up front; flag as a future TODO if and when q≥16 becomes default.

### 5.3 New `step_serial` shape

```rust
fn step_serial(&mut self) -> u64 {
    self.bus.master_cycle = self.clock.cycles;
    let start = self.clock.cycles;
    let target = start.wrapping_add(self.step_quantum as u64);

    let mut c0_total: u64 = 0;
    let mut c1_total: u64 = 0;

    while self.clock.cycles < target
        && (!self.cores[0].is_halted() || !self.cores[1].is_halted())
    {
        let c0 = if !self.cores[0].is_halted() {
            self.bus.set_active_core(0);
            let c = self.cores[0].step(&mut self.bus) as u64;
            Self::drain_cache_invalidations(&mut self.bus, &mut self.cores);
            self.maybe_wake_core1(0);
            c
        } else { 0 };

        let c1 = if !self.cores[1].is_halted() {
            self.bus.set_active_core(1);
            self.bus.begin_core1_step();
            let c = self.cores[1].step(&mut self.bus) as u64;
            Self::drain_cache_invalidations(&mut self.bus, &mut self.cores);
            self.bus.end_core1_step();
            self.maybe_wake_core1(1);
            c
        } else {
            self.bus.end_core1_step();
            0
        };

        if c0 == 0 && c1 == 0 { break; }
        c0_total = c0_total.wrapping_add(c0);
        c1_total = c1_total.wrapping_add(c1);
        self.clock.cycles = self.clock.cycles.wrapping_add(c0.max(c1));
    }
    let consumed = self.clock.cycles.wrapping_sub(start);

    // Fast-path branch unchanged.
    let pio_idle    = self.bus.pio_all_idle();
    let peri_idle   = self.bus.all_peripherals_idle();
    let dma_idle    = self.bus.dma.is_idle();
    let any_irq     = self.bus.irq_pending != 0;
    let systick_idle = !self.bus.systicks[self.bus.active_core()].is_enabled();
    if pio_idle && peri_idle && dma_idle && systick_idle && !any_irq {
        self.tick_pio(consumed as u32);
        self.bus.advance_lazy_scheduled(consumed);
        self.drain_pending_irqs_to_cores();
        self.update_gpio();
    } else {
        // Slow branch — chunked, single straight-line tick.
        self.bus.master_cycle = self.bus.master_cycle.wrapping_add(consumed);
        self.bus.tick_peripherals(consumed as u32);
        self.tick_systick(c0_total as u32, c1_total as u32);
        self.tick_pio_and_route_irqs(consumed as u32);
        self.update_gpio();
        self.drain_pending_irqs_to_cores();
    }
    self.wake_checks();
    consumed
}
```

`update_gpio` moves from inside the inner loop (today) to once at quantum end (above), matching RP2350's `step_serial` (which has no `update_gpio` in the per-cycle path at all).

### 5.4 IRQ delivery semantics — explicit behaviour change

| Path | Today | After this refactor |
|---|---|---|
| Peripheral asserts IRQ at intra-quantum cycle k | `bus.irq_pending |= bit` at k; drain runs at end-of-cycle k; CPU sees pending IRQ at cycle k+1 | `bus.irq_pending |= bit` accumulates during chunked tick; drain runs once at end-of-quantum; CPU sees pending IRQ at start of next quantum |

Net delivery delay grows from ≤1 cycle to ≤`step_quantum-1` cycles. **At default q=4 this is ≤3 cycles.** Identical to RP2350; the threaded runtime already lives with this.

## 7. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| TIMER alarm fires inside a quantum but chunked poll misses it | Low | `master_cycle` updated *before* `tick_peripherals(N)`; `Timer::poll_alarms` uses `>=` match. Same machinery RP2350 already uses. |
| DMA throughput cap (one transfer per quantum) starves I2S | Low | OPL3 needs ~88 K transfers/s; q=4 ceiling is 31 M transfers/s. Cake-gate catches it if wrong. |
| A test pins exact IRQ-delivery cycle | Medium | Loosen assertion to "within next quantum boundary"; same RP2350 accommodation. |
| Per-cycle observation diagnostics under-count by quantum factor | Medium-low | Diagnostic counters are relative-magnitude; per-quantum granularity is fine; doc-comment notes it. |
| Firmware polls `SIO_GPIO_IN` during a quantum, sees stale state | Low | PicoGUS doesn't poll GPIO in OPL3 mode; cake-gate is silent on this. If a future workload regresses, fix is reducing quantum. |
| Per-cycle perf gain estimate inflated by `Instant::now()` overhead | Already accepted | §1 commits to "measure post-refactor; revert if <10%". |
| Q=64 still breaks audio post-refactor | Acceptable | Q=64 unlock is bonus; q=4 staying clean is the goal. |
| Cake-gate passes but a peripheral-state regression escapes it | Medium-low | Mitigated by §6.1 (full test suite green). Cake-gate is one oracle of several; not the only gate. |
| SysTick decouple-from-refactor argument (devil's advocate Round 2) | Tie-broken | §5.2.2 explains why it's not feasible. Pre-refactor positive dual-core SysTick test (§8.4) gives independent regression detection without coupling-to-cake-gate. |

## 8. Pre-refactor audits (mandatory before §9 begins)

### 8.1 `bus.master_cycle` mid-tick reads

Grep all peripheral tick handlers for `master_cycle` reads. If any peripheral reads `bus.master_cycle` during its `tick(n, …)`, that's a hidden dependency on per-cycle freshness. After this refactor, `master_cycle` advances once per quantum *before* the chunked tick, so per-tick reads will see one stale value all the way through, possibly breaking accumulator logic.

- Files to grep: `crates/mdrp2040/src/peripherals/{adc,i2c,pwm,spi,uart,timer,psram,watchdog_tick}.rs`, `crates/mdrp2040/src/bus/systick.rs`, `crates/mdrp2040/src/dma.rs`.
- Pattern: `master_cycle` inside any `fn tick`.
- Action if hits: refactor to take `master_cycle` as a tick parameter, OR update `master_cycle` mid-quantum where needed.

Round 2 implementation review confirmed zero hits today; re-run before kicking off implementation in case anything has landed since.

### 8.2 Tests asserting `systicks[0]` static under dual-core

Grep `crates/mdrp2040/src/tests.rs` and `crates/mdrp2040/src/bus/systick.rs` for `systicks[0]`. Any test that asserts SysTick[0] never advanced when both cores ran is encoding the latent bug; update the assertion to "advances by core 0's cycle count" before the refactor.

### 8.4 Positive dual-core SysTick test (V3 addition per devil's advocate §13)

**Write a test before the refactor lands**, in `crates/mdrp2040/src/tests.rs` mod `systick_dual_core_tests`:

```rust
#[test]
fn both_cores_systick_advance_when_both_running() {
    // Arm SysTick on BOTH cores with RVR=0 (period 1, fire every cycle).
    // Run a quantum where both cores execute non-halted instructions.
    // Assert: BOTH systicks fired (PENDSTSET set on both cores' ICSR).
}
```

This is the regression detector decoupled from the cake-gate. Today, the test will FAIL on current code (the latent bug). After this refactor, it MUST PASS. Land the test in the same commit as the SysTick fix; the test is the proof both that the bug existed and that we fixed it.

**If the test passes on `main` unexpectedly** (i.e. the bug claim in §5.2.1 is wrong because some other code path advances `systicks[0]` that this HLD missed), the §5.2 design pivots:

- Drop the per-core accounting in §5.2.3 entirely.
- `tick_systick(consumed: u32)` advances ONLY `systicks[active_core()]` by `consumed` cycles — preserving today's `active_core()` semantic exactly. No dual-core fix in this commit.
- Update the §8.4 test in this same commit to assert the *current* (pre-refactor) behaviour of whichever path was advancing SysTick[0] — so it remains a green regression detector for the chunked refactor without claiming anything about the original bug.
- The "is this a real bug?" investigation moves to a separate issue/HLD; the refactor lands without entangling it.

This pivot is cheap (smaller diff than V3's design) and unblocks the perf work even if the bug-existence claim turns out to be wrong.

## 10. Non-goals

- No fallback to the per-cycle path. Revert via git if cake-gate fails.
- No environment variable, no `--legacy-tick` flag.
- No reorganisation of peripheral module structure.
- No introduction of `tick_n` as a separate method name. `tick(cycles, …)` IS the chunked method.
- No changes to fast-path gate logic.
- No threading wire-in for `picogus_diff_rp2040` (move #3 — separate follow-up after this lands).
- No closed-form `SysTick::advance_n` math optimisation (future work, only if q≥16 becomes default).
