# Fn-Pointer Dispatch in DecodedOp

Version: 1.1.0
Date: 2026-04-15
Status: **REJECTED — see §11 Post-mortem.**

Revision history:
- 1.0.0 (initial) — struct/layout, uniform signature, miss/hit path sketch.
- 1.0.1 — §2.4 rewritten to mirror the real nested Thumb-32 dispatch tree
  (op1/op2/op) and the Thumb-16 sub-arms that v1.0.0 collapsed
  (`0b01000` splits on bit 10; `0b01010|0b01011`;
  `0b10110|0b10111`; `0b11010|0b11011`). §5 sentinel differentiated
  (narrow vs wide fault-fetch). New §5a mandates a two-commit split.
  §6 impact estimate tempered for `lto="fat"` release profile. §7 scope
  narrowed to top-level dispatched handlers (internal helpers keep their
  signatures). §8 gains a pre-flight disassembly step.
- 1.1.0 — Implementation rejected at the §8 measurement gate. New §11
  Post-mortem documents the A/B numbers, the failure mode, and the
  lesson. Stage A signature refactor retained (harmless); Stage B
  reverted at commits `dd16ce3` (revert of `d2c76ed`) and `9cc8965`
  (revert of `8f4d2c1`). The classifier-style oracle idea
  (`fn_addr_eq` against an expected handler table) survives in spirit
  as a follow-up if we ever build a static dispatch table outside the
  hot path.

## 1. Problem

Profile from journal `2026.04.15 - JRN - Hot-Path Perf Profile (post
decode-cache + short-circuit)`:

| Self-time | Function |
|---:|---|
| 45.4 % | `CortexM33::decode_execute` |
| 32.0 % | `CortexM33::execute_thumb16` |
| 17.4 % | `Emulator::step` (serial-world; skip) |

The 32 % in `execute_thumb16` is almost entirely the 5-bit `opcode >> 11`
dispatch match and the enclosing `execute_thumb16(hw0, bus)` call frame
(register saves, stack prologue/epilogue). Every cache hit runs this match
even though the resulting handler is a pure function of `(hw0, hw1, is_wide)`
— it was determined at populate time and could be remembered.

Same argument for `execute_thumb32` on wide instructions; the basic
workload has none, but real firmware mixes narrow and wide and the symmetry
keeps the design tidy.

## 2. Design

Stamp a function pointer on each `DecodedOp` at populate time. On hit,
call it directly. `execute_thumb16` / `execute_thumb32` stay — `execute_one*`
test helpers (`crates/mdrp2350/src/core/mod.rs:237`) use them — but are no
longer on the cache hit path.

### 2.1 Struct layout

```rust
pub(crate) type Handler = fn(&mut CortexM33, u16, u16, &mut Bus) -> u32;

#[derive(Clone, Copy, Debug)]
pub(crate) struct DecodedOp {
    pub handler:    Handler,  //  8 B  offset 0
    pub tag:        u32,      //  4 B  offset 8
    pub hw0:        u16,      //  2 B  offset 12
    pub hw1:        u16,      //  2 B  offset 14
    pub fetch_wait: u8,       //  1 B  offset 16
    pub flags:      u8,       //  1 B  offset 17
    // 6 B tail pad (8-byte alignment from `handler`)
}
// Total: 24 B.
```

`handler` first: the hit path reads it almost immediately after the tag
compare, so keep it in the same cache line as `tag`. The tail pad is
unavoidable given the 8-byte alignment of `Handler`.

Cache footprint: 16384 × 24 = 384 KB (up from 192 KB). Still small next
to `Bus`'s existing 520 KB SRAM + peripheral state. The cost is memory
not hit rate — 2.67 entries per 64-byte line vs. today's 5.33, but every
hit touches exactly one entry.

### 2.2 Uniform handler signature

`fn(&mut CortexM33, hw0: u16, hw1: u16, &mut Bus) -> u32`

Every top-level dispatched handler is rewritten to this signature. Narrow
handlers take `hw1` and ignore it (`_hw1: u16`). Handlers that don't
currently touch the bus take `_bus: &mut Bus`. Existing bodies unchanged.

Scope is narrower than "every function named `thumb16_*` / `thumb32_*`" —
see §7 for the full list. Internal helpers called from inside top-level
handlers (e.g. `thumb32_b_w_cond`, `thumb32_msr`, `thumb32_ls_single_access`,
or any private helper that isn't on a top-level dispatch arm) keep their
existing signatures; they are not in the dispatch path.

Rationale: a uniform signature is the simplest way to store fn pointers in
a fixed-layout `DecodedOp`. The alternative (two signature types, tagged
dispatch, or unsafe transmute based on `is_wide`) adds complexity for no
runtime benefit — LLVM elides dead parameters at the leaf.

### 2.3 Miss path — populate

`populate_decode_cache` gains a step: after `classify_is_pure`, call
`classify_handler(hw0, hw1, wide)` and write the result into
`DecodedOp::handler`.

```rust
let handler = classify_handler(hw0, hw1, wide);
// (existing flags computation unchanged)
let entry = DecodedOp { handler, tag: pc, hw0, hw1, fetch_wait, flags };
bus.decode_cache[slot] = entry;
```

### 2.4 `classify_handler`

Bitwise-identical decision tree to the live `execute_thumb16` /
`execute_thumb32` dispatchers (`crates/mdrp2350/src/core/decode.rs:429`
and `:485`). `classify_handler` returns a function item; the live
dispatcher calls the same item. Identity of classification is a
correctness requirement, not a stylistic one — any divergence is a bug
detectable by `dispatch_equiv` (§4).

**Thumb-16 tree.** Primary key is `hw0 >> 11` (bits 15:11). Several arms
have sub-keys that `classify_handler` MUST reproduce:

- `0b01000` — split on bit 10:
  - bit 10 = 0 → `thumb16_data_processing`
  - bit 10 = 1 → `thumb16_special_data_bx`
- `0b01010 | 0b01011` — both → `thumb16_load_store_reg`
- `0b10110 | 0b10111` — both → `thumb16_misc`
- `0b11010 | 0b11011` — both → `thumb16_cond_branch_svc`

All other bits-15:11 arms map 1-to-1 to a single handler (`thumb16_lsl_imm`
for `0b00000`, …, `thumb16_branch` for `0b11100`). Default → `thumb16_undefined`.

**Thumb-32 tree.** Matches the nested structure at
`core/decode.rs:485`. Extract:

```
op1 = (hw0 >> 11) & 0x3
op2 = (hw0 >>  4) & 0x7F
op  = (hw1 >> 15) & 0x1
```

Dispatch:

```rust
pub(crate) fn classify_handler(hw0: u16, hw1: u16, is_wide: bool) -> Handler {
    if !is_wide {
        return match hw0 >> 11 {
            0b00000 => CortexM33::thumb16_lsl_imm,
            0b00001 => CortexM33::thumb16_lsr_imm,
            0b00010 => CortexM33::thumb16_asr_imm,
            0b00011 => CortexM33::thumb16_add_sub,
            0b00100 => CortexM33::thumb16_mov_imm,
            0b00101 => CortexM33::thumb16_cmp_imm,
            0b00110 => CortexM33::thumb16_add_imm8,
            0b00111 => CortexM33::thumb16_sub_imm8,
            0b01000 => if hw0 & (1 << 10) == 0 {
                CortexM33::thumb16_data_processing
            } else {
                CortexM33::thumb16_special_data_bx
            },
            0b01001           => CortexM33::thumb16_ldr_literal,
            0b01010 | 0b01011 => CortexM33::thumb16_load_store_reg,
            0b01100           => CortexM33::thumb16_str_imm,
            0b01101           => CortexM33::thumb16_ldr_imm,
            0b01110           => CortexM33::thumb16_strb_imm,
            0b01111           => CortexM33::thumb16_ldrb_imm,
            0b10000           => CortexM33::thumb16_strh_imm,
            0b10001           => CortexM33::thumb16_ldrh_imm,
            0b10010           => CortexM33::thumb16_str_sp,
            0b10011           => CortexM33::thumb16_ldr_sp,
            0b10100           => CortexM33::thumb16_adr,
            0b10101           => CortexM33::thumb16_add_sp_imm,
            0b10110 | 0b10111 => CortexM33::thumb16_misc,
            0b11000           => CortexM33::thumb16_stm,
            0b11001           => CortexM33::thumb16_ldm,
            0b11010 | 0b11011 => CortexM33::thumb16_cond_branch_svc,
            0b11100           => CortexM33::thumb16_branch,
            _                 => CortexM33::thumb16_undefined,
        };
    }

    let op1 = (hw0 >> 11) & 0x3;
    let op2 = ((hw0 >> 4) & 0x7F) as u32;
    let op  = (hw1 >> 15) & 0x1;

    match op1 {
        0b01 => match op2 >> 5 {
            0b00 => if op2 & 0x04 == 0 {
                CortexM33::thumb32_ldm_stm
            } else {
                CortexM33::thumb32_load_store_dual
            },
            0b01 => CortexM33::thumb32_dp_shifted_reg,
            _    => CortexM33::thumb32_coprocessor,
        },
        0b10 => if op == 0 {
            if op2 & 0x20 == 0 {
                CortexM33::thumb32_dp_modified_imm
            } else {
                CortexM33::thumb32_dp_plain_imm
            }
        } else {
            CortexM33::thumb32_branch_misc
        },
        0b11 => if op2 & 0x40 != 0 {
            CortexM33::thumb32_coprocessor
        } else if op2 & 0x20 == 0 {
            CortexM33::thumb32_load_store_single
        } else if op2 & 0x10 == 0 {
            CortexM33::thumb32_dp_register
        } else if op2 & 0x08 == 0 {
            CortexM33::thumb32_multiply
        } else {
            CortexM33::thumb32_long_multiply
        },
        _ => CortexM33::thumb32_undefined,
    }
}
```

Lives in `core/decode.rs` next to `classify_is_pure`. The classifier must
be grep-linked to the live dispatcher: add a doc-comment at the top of
both `execute_thumb16` and `execute_thumb32` that names `classify_handler`
as the mirror, and vice versa. `dispatch_equiv` (§4) backstops the review:
every top-level match arm has a representative test.

### 2.5 Hit path — `decode_execute`

Replace the two `is_wide`-branched `self.execute_thumb16(hw0, bus)` /
`self.execute_thumb32(hw0, hw1, bus)` calls with one indirect call:

```rust
let cycles = if cond_passed {
    (entry.handler)(self, hw0, hw1, bus)
} else {
    1
};
```

Both the pure-fast-path and impure-slow-path arms of `decode_execute`
converge on this single call. `is_wide` is still consulted for the PC
increment (`+2` vs. `+4`) and, on the impure path, nowhere else; the top-
level dispatch branch is gone.

### 2.6 `execute_thumb16` / `execute_thumb32` after the change

They become one-line wrappers:

```rust
pub(crate) fn execute_thumb16(&mut self, hw0: u16, bus: &mut Bus) -> u32 {
    (classify_handler(hw0, 0, false))(self, hw0, 0, bus)
}
pub(crate) fn execute_thumb32(&mut self, hw0: u16, hw1: u16, bus: &mut Bus) -> u32 {
    (classify_handler(hw0, hw1, true))(self, hw0, hw1, bus)
}
```

The test-only `execute_one` helpers keep calling them unchanged. The big
match moves out of the body into `classify_handler`.

## 3. What does NOT change

- `is_pure` classification (`classify_is_pure`) and the fast-path / slow-
  path split. Fn-pointer dispatch is orthogonal to wait-state bookkeeping.
- Cache topology (16384 direct-mapped slots, PC-keyed, tag = full PC).
- Invalidation hooks on SRAM / XIP-SRAM writes, flash loads, bootrom loads.
- Fetch-wait preservation (`entry.fetch_wait as u32` added on hit).
- IT-block state machine, flag-only suppression, condition handling.
- Fault delivery. `thumb16_undefined` / `thumb32_undefined` set
  `pending_fault`; `CortexM33::step` picks this up after `decode_execute`
  returns, as today.
- Handler bodies — only the signature extends to accept `hw1` and `&mut Bus`
  where currently absent.
- `execute_one` / `execute_one_with_bus` / `execute_one_wide*` test
  entry points.

## 4. Correctness

For any `(hw0, hw1, is_wide)` with no bus fault on fetch, `classify_handler`
returns the fn item that `execute_thumb16(hw0, bus)` or
`execute_thumb32(hw0, hw1, bus)` would currently select and call. Because
the function body of each handler is unchanged, the cycle count and state
transition are identical.

Differential test (`crates/mdrp2350/src/tests.rs`, new `mod dispatch_equiv`):
for each top-level match arm of `execute_thumb16` (including every sub-arm
listed in §2.4) and `execute_thumb32`, pick one representative opcode, and
assert that running it through `decode_execute` (cache path) and through
`execute_one` (direct-dispatch path) produces identical `(regs, xpsr,
cycles)`. One test per arm, ~45 total.

## 5. Risks and edge cases

- **Classification drift.** A new Thumb-16 / Thumb-32 variant added to
  `execute_thumb16` / `execute_thumb32` without a matching arm in
  `classify_handler` silently dispatches to `thumb16_undefined` /
  `thumb32_undefined` — a wrong answer that fakes "unknown opcode"
  behaviour. Mitigation: mirror-comment at the top of each dispatcher
  and classifier; `dispatch_equiv` tests catch any mapping miss for
  every arm that has a representative.
- **Handlers that don't currently take `&mut Bus` or `hw1`.** Adding the
  parameters is a mechanical edit; LLVM drops unused args at the leaf.
  Tests stay green because call sites inside `execute_thumb16` /
  `execute_thumb32` pass the same `bus` / a zero `hw1` that the bodies
  already ignore.
- **`classify_handler` on a fault-fetch.** If `bus.read16(pc)` faults on
  populate, `populate_decode_cache` returns early with `tag = u32::MAX`
  and a minimal entry. The proposed change must stamp *some* valid
  `handler` on those sentinels. Use the width-matched undefined handler:
  - Narrow fault-fetch (first halfword read faulted) → `thumb16_undefined`
    (the returned entry has `FLAG_WIDE = 0`).
  - Wide fault-fetch (second halfword read faulted) → `thumb32_undefined`
    (entry has `FLAG_WIDE = 1`).
  Strictly safer than today's behaviour: today's `decode_execute`
  dispatches on junk `hw0` bits after a faulted fetch and may run a
  handler's arithmetic before `step` sees `pending_fault`; the undefined
  sentinel cleanly sets `pending_fault` instead. Both undefined handlers
  must accept the uniform signature (ignoring all four inputs is fine).
- **Indirect call cost vs. current jump table.** LLVM currently lowers the
  5-bit match in `execute_thumb16` to a single indirect jump — same raw
  cost as an indirect call. The win is elsewhere: the `execute_thumb16`
  call frame (register saves + stack prologue, visible in the disassembly
  at `0xcb70` under `profiling`), and the `if is_wide` branch in
  `decode_execute`. Release + `lto = "fat"` may already inline some of
  this; see §6.

## 5a. Implementation split

Two commits, not one. As a single patch the diff is ~2000 lines across
two dozen files and review is unmanageable.

1. **Commit A — uniform handler signature.** Extend every top-level
   `thumb16_*` / `thumb32_*` handler (see §7 for the precise list) to
   `fn(&mut CortexM33, u16, u16, &mut Bus) -> u32`. `execute_thumb16` /
   `execute_thumb32` call them with the new arity. Bodies, cycle counts,
   and test behaviour unchanged. `cargo test -p mdrp2350` must be green
   before the commit lands. No performance effect (LLVM elides dead
   args). This is the de-risked step: reviewable as "does every
   dispatched handler have the right signature now?".
2. **Commit B — `handler` field + `classify_handler` + indirect dispatch.**
   Adds the `Handler` type alias, `handler: Handler` to `DecodedOp`,
   `classify_handler`, the populate-time stamp (with width-matched
   sentinels on fault-fetch), the single-call-site dispatch in
   `decode_execute`, the one-line wrapper bodies for `execute_thumb16` /
   `execute_thumb32`, and the `dispatch_equiv` test module.
   Measurement gate (§8) lives on this commit. Reviewable as "does
   `classify_handler` mirror the live dispatchers and does dispatch go
   through it?".

## 6. Expected impact

The 2026.04.15 profile was taken under a dedicated `profiling` profile
(`lto = false`, `debug = 2`). The measurement gate uses `release` with
`lto = "fat"`, which may already inline parts of the `execute_thumb16`
call frame — so the absolute saving against the 30.75 h/e baseline can
be smaller than the profile's 32 % self-time suggests.

Savings on the pure hit path that should survive `lto = "fat"`:

- `execute_thumb16` call frame — if LTO has not already inlined it in
  release (check the disassembly before and after; see §8 pre-flight).
  Observed at `0xcb70` under `profiling`.
- The top-level `is_wide` branch in `decode_execute` collapses into
  the single indirect call.
- The Thumb-16 / Thumb-32 top-level jump tables are still executed
  once per opcode, but only at miss time, not on every hit.

Estimate range (against the 30.75 h/e / 99.9 MHz baseline):

- **Pessimistic** (LTO already inlined most of the frame): 2–4 host
  cycles / instr saved → ~27–29 h/e, ~105–111 MHz on `--workload basic`.
- **Realistic**: 4–7 host cycles / instr → ~24–27 h/e, ~111–125 MHz.
- **Optimistic** (frame was not inlined): 7–10 host cycles / instr →
  ~21–24 h/e, ~125–140 MHz.

The measurement gate (§8) is the oracle. Any reduction below 30.75 h/e
is a pass; we do not gate on hitting a specific number. If the measured
saving is under the pessimistic range, this is a miss and we revert or
iterate — do not land a negative-win change.

## 8. Measurement gate

Pre-flight (before Commit B lands):
- Capture `llvm-objdump -d --start-address=...` of `decode_execute` and
  the post-inlining neighbourhood under `--profile=release` (what the
  measurement uses), not `profiling`. Note whether the `execute_thumb16`
  frame is already inlined. This sets the §6 expectation.

Gate:
1. `cargo test -p mdrp2350` — zero regressions.
2. `cargo run -p mdpicoem-harness --release --bin qemu_diff_m33 -- --fuzz 10000` — clean.
3. `cargo run -p mdpicoem-harness --release --bin paced_bench_rp2350 -- --unpaced --seconds 5 --workload basic` — h/e strictly lower than 30.75.

Record the numbers in the implementation journal. If (3) regresses or
does not improve, revert Commit B and re-plan.

## 9. Alternatives considered

- **u16 handler index + static table.** Cache entry stays 12 B. One extra
  L1 load per hit vs. direct fn pointer. Rejected because the 192 KB
  saving is irrelevant and the extra load compounds with every hit.
- **Split Thumb-16 / Thumb-32 handler signatures, store `*const ()` and
  transmute on `is_wide`.** Saves the dead `hw1` parameter on Thumb-16
  handlers. Rejected because the uniform signature is the simpler contract
  and LLVM already elides dead args.
- **Basic-block linking (next-op hint on `DecodedOp`).** Separate design.
  Fn-pointer dispatch is the prerequisite — linked entries still need
  per-entry dispatch. Address in a follow-up HLD if the measurement
  gate confirms a win.

## 10. What we are explicitly NOT doing

- No feature flag / env-var gate. The old and new paths do not coexist.
- No compatibility shim for callers that expected the old `execute_thumb16`
  signature. All call sites are in-crate; they get updated.
- No re-design of handler bodies; this HLD is dispatch-only.

## 11. Post-mortem (added in v1.1.0)

The change shipped, was measured, and was reverted. The full
implementation journal lives at `wrk_journals/2026.04.15 - JRN -
Fn-Pointer Dispatch Implementation.md`. This section captures the
numbers and the lesson so future contributors don't re-run the same
experiment.

### What we built

Two atomic commits per §5a:

- **Stage A** (`12ce8c1`) — uniform handler signature refactor. 28
  Thumb-16 + 11 Thumb-32 top-level handlers gained the
  `(&mut CortexM33, u16, u16, &mut Bus) -> u32` shape. Bodies
  unchanged. Zero behavioural change. **Retained — harmless cleanup.**
- **Stage B** (`8f4d2c1` + `d2c76ed` test fix) — `Handler` type alias,
  `DecodedOp::handler` field (struct grows 12 → 24 B),
  `classify_handler` mirroring the live dispatcher trees,
  populate-time stamp, single indirect call in `decode_execute`,
  collapsed wrappers, plus the `raise_usage_fault` helper carry-over.
  **Reverted** at `dd16ce3` and `9cc8965`.

Stage B's `dispatch_equiv` test module — initially tautological in
the first commit (`8f4d2c1`), corrected in the test fix (`d2c76ed`)
— exercised `std::ptr::fn_addr_eq` against hard-coded expected
handlers. The validation pass (corrupt the classifier, observe
exactly the right tests fail, revert, observe pass) demonstrated
the oracle was real, not tautological. **The test idea is sound and
worth porting separately.**

### Measurement gate

The §8 `paced_bench_rp2350 --unpaced --seconds 5 --workload basic`
gate ran on the post-Stage-B HEAD and on a worktree pinned to Stage A
(`12ce8c1`), each built in its own `target` directory under release
+ `lto = "fat"`. Five consecutive runs each, on the same Windows host,
no other heavy load.

| Configuration               | h/e (avg) | MHz (avg) | Verdict |
|-----------------------------|----------:|----------:|--------:|
| Stage A only (pre-Stage-B)  | **28.84** | **105.5** | OK |
| HEAD post-Stage-B           | **36.76** | **83.6**  | **OVER 30.75** |
| Δ owned by Stage B          | **+7.92** | **−21.9** | regression |

Stage A actually *outperforms* the HLD §6 baseline (30.28 h/e from
journal `2026.04.14 - JRN - Hot-Path Perf (Decode Cache + Cycle
Accounting)`) — likely because LTO has more freedom to inline after
the signature refactor. Stage B then erases that win and adds a
further ~7 h/e.

A 27 % regression in host-cycles-per-emulated-cycle is the
opposite direction to the §6 prediction (which estimated 2–10 host
cycles **saved** per instruction). Per §6 ("If the measured saving is
under the pessimistic range, this is a miss and we revert or iterate
— do not land a negative-win change") and §8 ("If (3) regresses or
does not improve, revert Commit B and re-plan"), Stage B was reverted.

### Why it failed (the lesson)

The pre-flight disassembly step from §8 already hinted at it. Under
release + `lto = "fat"`, the `mdrp2350app.exe` binary contains **no
discoverable `decode_execute` / `execute_thumb16` / `execute_thumb32`
symbol**. LTO had inlined the entire Thumb-16 / Thumb-32 dispatch
tree directly into `CortexM33::step`. The "call frame" §6 wanted to
remove **did not exist in the binary**. The 32 % `execute_thumb16`
self-time the profile saw was an artefact of the `profiling` profile
(`lto = false`), not a real cost in the shipped release build.

Stage B replaced free, fully-inlined `match` arms with a forced
indirect call through a cache-loaded `fn` pointer. A function pointer
is, by definition, an **inlining barrier** — LLVM cannot prove which
handler will run, so every opcode now pays a real call setup +
return cost. On top of that, doubling the decode-cache footprint
(192 KB → 384 KB) increased L1d pressure on the very structure the
hot path reads twice per instruction (tag + handler).

Both effects compound. Roughly:

- Pre-Stage-B: opcode → cache hit → tag compare → inlined handler
  body → flag update. ~10 host cycles/instr after the cache hit.
- Post-Stage-B: opcode → cache hit → tag compare → load fn pointer →
  indirect call → handler frame setup → handler body → return →
  flag update. ~18 host cycles/instr after the cache hit.

The +8 h/e delta is consistent with one extra forced call frame per
instruction, dominated by ~3 cycles of frame setup and ~3 cycles of
return + a BTB miss penalty when the fn pointer is cold.

### What the profile actually meant

Re-reading the journal `2026.04.15 - JRN - Hot-Path Perf Profile`:
the 32 % `execute_thumb16` self-time was correct for the `profiling`
profile, where `lto = false` and the function frame existed at
`0xcb70`. Under `release` + `lto = "fat"`, that frame is collapsed
into `CortexM33::step` and the 32 % is distributed across every
opcode body, not concentrated in one symbol. The profile told us
"these instructions cost 32 % of runtime"; we mis-read it as "the
function `execute_thumb16` costs 32 % of runtime". A profile under
the same profile flags as the deployment build would have shown the
real story.

**Lesson 1:** Profile under the build profile that prod uses, not a
debug-friendly variant. The §8 pre-flight step (added in v1.0.1)
exists to catch exactly this — but the implementer ran it AFTER
landing Stage B rather than BEFORE designing it. Move the disassembly
check earlier in the design process: "before you propose to remove a
function frame, prove it exists in the build profile that ships."

**Lesson 2:** A function pointer is an inlining barrier. Any "make
dispatch faster by caching the handler" idea must account for this.
If the existing dispatch is already fully inlined by LTO, the only
way to win is to provide LTO with *more* inlining opportunities
(e.g. specialising `decode_execute` per opcode at miss time —
basic-block linking), not to introduce a barrier.

**Lesson 3:** The 30.28 h/e baseline was already at the §6
pessimistic end of the win range — there was no room to spare. The
HLD's "optimistic" / "realistic" / "pessimistic" range should have
prompted us to ask: **what if the win is zero or negative?** The
answer was in the design all along — a fn pointer cannot be inlined,
and the existing dispatch was already inlined, so the floor is
"add per-call cost without saving anything" — a guaranteed
regression. We did not connect those dots before writing the code.

### What survives

- **Stage A** (commit `12ce8c1`) is on `main` and stays. It cleaned
  up handler signatures and is mechanically harmless.
- **`dispatch_equiv` test idea** — the `std::ptr::fn_addr_eq`-against-
  expected-handler oracle is genuinely useful and would catch
  classification drift in the live dispatcher too (the handler the
  *match arm* calls vs the handler the test author expects). A
  follow-up task could port this against `execute_thumb16` /
  `execute_thumb32` using a static expected-handler table without
  touching the hot path. Tracking as a separate idea in
  `tech_debt.md`.
- **The disassembly pre-flight step** in §8 — keep this in any
  future perf HLD that proposes to remove a function frame.

### What to try next (if anything)

The 17.4 % `Emulator::step` self-time the profile noticed is a
serial-interleaver path scheduled for demolition once cores run on
their own threads — out of scope per the journal's threading
constraint. The 45.4 % `decode_execute` self-time is now the
optimisation target, but the analysis above suggests it's already
near the LTO floor. **Possible directions, in rough order of
likely-yield:**

1. **Threaded cores.** Removes the 17.4 % serial-interleaver
   overhead AND the 4-cycle bank-contention check. Single biggest
   pending win. Already on the roadmap; no perf HLD needed —
   unrelated work.
2. **Basic-block linking with specialised dispatch.** Each cache
   entry stores a pointer to a code blob produced at miss time
   that runs the handler inline (no fn-pointer barrier). This is
   what JITs do; it's a much bigger lift and demands a generated-
   code lifetime story. If we go this way, the test infrastructure
   from the failed Stage B is reusable.
3. **Decode-cache footprint shrink.** If we ever return to a
   similar idea, keep the cache entry ≤ 16 B so it stays at the
   current 5.33 entries / cache line and L1d pressure doesn't get
   worse. Stage B's 24 B layout was a self-inflicted wound.

None are queued. Reverting Stage B closes this line of investigation
until something on the above list becomes worth designing.
