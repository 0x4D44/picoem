V1 does not ship that; V1 only *measures* whether RV attach is reachable via existing APIs. Upshot: the spike's most likely outcome is **Plan D** (target YAML gap) — that is not a bug, that is the honest measurement this phase is designed to produce.

## 3. Probe-rs 0.31 API call sequence

Mirrors `probe_diff_rp2350.rs` with the RISC-V register set from `architecture/riscv/registers.rs`:

```rust
// Attach (identical to probe_diff_rp2350)
let mut session = match args.probe.as_ref() {
    None => Session::auto_attach("rp2350", SessionConfig::default())?,
    Some(sel) => Lister::new().open(sel.clone())?
        .attach("rp2350", Permissions::default())?,
};

// Enumerate cores
let list = session.list_cores(); // Vec<(usize, CoreType)>

// Per-hart attach + halt + probe
for (hart_id, core_type) in &list {
    let mut core = session.core(*hart_id)?;
    core.halt(Duration::from_millis(500))?;
    let arch = core.architecture();      // Architecture::Arm | Riscv | Xtensa
    // Sentinel mhartid read — see §4
    // GPR / CSR probes — see §5
}
```

**RISC-V RegisterId layout** (from `probe-rs-0.31.0/src/architecture/riscv/registers.rs`):

- `x0..x31` = `RegisterId(0x1000)..RegisterId(0x101F)`
- `PC` = `RegisterId(0x7b1)` — this is the standard architectural `dpc` CSR address per RISC-V External Debug Spec §4.8.1 (`dpc` = Debug PC). probe-rs uses it directly as the PC pseudo-ID; it is not a probe-rs internal invention.
- For `read_core_reg`, *any* `RegisterId(n)` dispatches through `read_csr(n)` on the RISC-V backend, so arbitrary CSR numbers (e.g. `mhartid` = `RegisterId(0xF14)`) are addressable directly.

The ARM backend uses completely different IDs (DCRSR numbering), so the spike must branch on `core.architecture()` before issuing any RV-specific read.

## 4. Sentinel probe: `mhartid` readback

CSR `mhartid` = 0xF14. The spike reads it two ways and cross-checks:

1. `core.read_core_reg(RegisterId(0xF14))` — if probe-rs's RV backend is wired, this succeeds.
2. Fallback (diagnostic only, not used for PASS): the raw RV32 encoding `csrrs x10, mhartid, x0` = **`0xF1402573`**, little-endian bytes **`73 25 40 F1`**. V1 does *not* splice this into memory and execute it — that would need #4 (hw breakpoint) to have passed first, chicken-and-egg. Recorded in the LLD for Phase 3 reference.

**PASS criterion for the mode sanity probe:** `core.architecture() == Architecture::Riscv` AND `mhartid ∈ {0, 1}`. Anything else (`architecture() == Arm`, CSR read errors, values ≥ 2) is FAIL and the reason is printed verbatim.

## 5. Capability matrix (5 + 2 + 1)

Each row prints one `PASS`/`FAIL`/`SKIP` line with a ≤ 1-line reason. `SKIP` is used when a prior-row failure invalidates the test (e.g. row 2 can't run if row 1 failed).

| # | Capability | Test | Maps to HLD |
|---|---|---|---|
| 1 | Attach exposes RV core for both harts | `session.list_cores()` returns 2 entries; for each, `core.architecture() == Riscv` | §4 cap #1 |
| 2 | Read/write GPRs | Write 0xDEADBEEF to `RegisterId(0x100A)` (x10/a0), read back, diff | §4 cap #2 |
| 3 | Read/write CSRs | Read `mscratch` (0x340), write inverted, read back, restore | §4 cap #3 |
| 4 | HW breakpoint + run + wait_for_halted | Plant 4 × `c.nop` + `c.ebreak` at `EMU_TEST_SLOT`, set a hardware breakpoint at `EMU_TEST_SLOT + 6` (between the last `c.nop` and the `c.ebreak`), seed SP/PC, `run()`, `wait_for_core_halted(2s)`, **clear the breakpoint before returning** (so Row 5 can re-seed PC to the same address without re-tripping it). PASS only if `set_hw_breakpoint` succeeded *and* the core halted; if HW BP allocation failed and the core only halted on the `c.ebreak` sentinel tail, the row is FAIL ("HLD §4 cap #4 requires HW BP unit — Path B / Partial"). | §4 cap #4 |
| 5 | `core.step()` single-step | After Row 4, re-seed PC to `EMU_TEST_SLOT`, step once, confirm PC advanced by **exactly 2** (c.nop is a 16-bit compressed instruction). A Δ of 4 is FAIL with reason "probe-rs may not decode RV32C compressed instructions correctly" — a latent RV32C decode bug in probe-rs must not pass silently. | §4 cap #5 |
| E1 | `mcycle` advances during step | Read `mcycle` (CSR 0xB00), step 10 × nop, re-read, expect monotone increase | empirical (not gating) |
| E2 | Halt with `mip[11]` asserted resumes cleanly | Inject pending MEIP via `mip` write, halt, re-run, step, observe no trap entry | empirical (not gating) |
| A | ARCHSEL-via-SWD sub-question | See §6 | Phase 3 soak unattended/attended |

Rows E1 and E2 are **best-effort**; failures record the observation but do not alter the decision-tree outcome.

## 6. ARCHSEL-via-SWD investigation

**Question (HLD §4).** Can the host flip POWMAN `CHIP_RESET.ARCH_SEL` over SWD between soak passes such that next boot comes up in the selected arch, without physical power-cycle?

**Attempt 1 — direct bus write.** POWMAN base in the emulator is assumed `0x4010_0000` with ARCHSEL at offset `0x20` (per `crates/mdrp2350/src/peripherals/powman.rs` §module doc — datasheet §12 not verified in tree). Real silicon base/offset **must** be looked up in RP2350 datasheet §5.10 before the spike attempts a write. If the datasheet pin is not done pre-run, the spike prints `ARCHSEL-SWD: SKIPPED (datasheet offset unverified)` and exits that row as INDETERMINATE — not FAIL.

**Attempt 2 — reset sequence.** Even if the write lands, ARCHSEL only takes effect on next reset per RP2350 §2.2. The spike:

1. Writes the datasheet-verified POWMAN ARCHSEL register to select the *other* arch (RV → ARM or vice-versa).
2. Issues `core.reset()` (probe-rs abstracts this through `session.target().reset_and_halt()`; the RV target YAML gap means probe-rs ARM sequence runs).
3. Re-attaches and re-reads `core.architecture()`.
4. If `architecture()` switched, PASS. If not, FAIL with "POWMAN write ineffective across reset over SWD".

**Honest limit.** If probe-rs cannot route a reset sequence cleanly (because the ARM target YAML is wrong for the current boot arch after the flip), the test prints UNSUPPORTED. Arthur observes power LED + console to confirm the physical reset did happen.

The Phase 3 soak mode depends on this outcome:

- PASS → cross-arch soak is unattended (orchestrator alternates ARM/RV passes under host control).
- FAIL / UNSUPPORTED → cross-arch soak is manual-reboot-only; single-arch soak remains unattended.

### Row A split (Critical-1 from the review)

Row A originally unconditionally SKIPed. V1 splits it:

- **A1 (always runs):** read-only probe of `POWMAN_BASE + CHIP_RESET_OFFSET`. PASS on successful read (prints current value); FAIL on probe-rs error. Never writes. Exercises the "can the host see CHIP_RESET over SWD?" sub-question independent of whether a write+reset flip works.
- **A2 (gated by `--attempt-archsel-flip`):** the write + reset + re-attach flip. Even with the flag set, stays SKIP until the POWMAN CHIP_RESET offset is pinned from RP2350 datasheet §5.10 in `RUNBOOK.md` (the source constant `POWMAN_OFFSET_PINNED` flips when that happens). Until then, writing based on the emulator's educated-guess offset could scribble into an unrelated POWMAN register on silicon.

## 8. Honest gaps the spike cannot answer

- **Dual-hart behaviour if only one hart enumerates.** If `list_cores()` returns 1 entry instead of 2, the spike flags it but cannot distinguish "probe-rs RV backend lacks multi-hart routing" from "RP2354 RV RTL only exposes hart 0 to DM".
- **Atomics outside reservable region timing.** Not probed at all — pure Phase 3 silicon concern.
- **`mip[3]`/`mip[7]` level-sensitive timing.** Requires firmware stub; deferred.
- **WARL rounding on each CSR field.** The spike tests *round-trippability* of `mscratch` only (all-bits-writable), not the WARL CSRs.
- **CSR proxy self-masking.** Out of scope for spike — closed by Phase 3 LLD §CSR-proxy cross-check.
- **Whether `auto_attach("rp2350")` silently ignores RV silicon.** See §2: likely yes. Spike reports Architecture::Arm → Plan D in that case.

### Failure modes

How the spike behaves when the environment itself is broken, so the operator can triage:

- **No probe attached / no target powered.** `Session::auto_attach` (or `probe.attach` with `--probe`) returns `Err`. The spike catches it, records Row 1 as FAIL with the probe-rs error string, cascades SKIP through rows 1b / 2 / 3 / 4 / 5 / E1 / E2 / A1, still runs A2 (which has no session dep), prints the matrix, maps to **Plan D**, and exits **0**. No probe = valid data, not a fatal error.
- **Bad `--probe VID:PID:SERIAL`.** CLI parse returns `Err` from `DebugProbeSelector::try_from`, `main()` exits **2** with the error on stderr. This is the only exit-2 path in V1.
- **Probe selector resolves but `Lister::open` fails** (e.g. serial matches no attached probe). Handled in the attach block like "no probe": Row 1 FAIL, cascade SKIP, Plan D, exit 0.
- **Row 4 hang.** `wait_for_core_halted(2s)` bounds the wait, so Row 4 can't wedge the spike. If it returns `Err` (timeout or DM fault), Row 4 is FAIL and rows 5 / E1 / E2 SKIP.
- **Row E1 hang.** Bounded by `E1_STEP_BUDGET` (5 s wall-clock) across the 10 single-step iterations. If the budget expires, Row E1 is FAIL with the iteration index that tripped the bound. E2 still runs.
- **Row E2 pending-MEIP escape.** If clearing `mstatus.MIE` doesn't actually suppress the trap and the stepped PC lands in `mtvec` instead of `EMU_TEST_SLOT + 2`, the row is SKIP with "step trapped — mstatus.MIE handling unclear", not a false PASS.
- **Row 5 delta=0 from a stale breakpoint.** Fixed by clearing the HW BP at the end of Row 4 regardless of outcome (see §5 row 4). If Row 5 still shows Δ=0 it means `step()` genuinely didn't advance.
- **Generalised step timeout.** No global timeout wraps the whole spike — if probe-rs itself blocks forever inside a non-timeout-bounded call (outside the rows listed above), kill with Ctrl-C. This is acceptable for an interactive bring-up tool; hardening is out of scope until Phase 3.
