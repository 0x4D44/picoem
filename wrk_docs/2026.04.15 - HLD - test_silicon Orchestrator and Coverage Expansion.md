# test_silicon Orchestrator and Coverage Expansion

Version: 1.1.1
Date: 2026-04-15
Scope: mdrp2350 only (RP2354 is the hardware on the bench)

## Changelog

- **1.1.1 (2026-04-15)** — Stage 2 devil's-advocate pass on the
  implementation flagged that the bank-conflict K-delta recast
  proposed in 1.1.0 silently deletes the +1 bank-contention cycle
  signal (already documented as masked in K-delta mode at
  `tech_debt.md:545-554`). Reverted: bank-conflict stays on
  halt-step + per-run NOP-baseline calibration, with a small
  tolerance to absorb debug-overhead variation. Cleanup table also
  expanded to call out IO_BANK0/PADS_BANK0 as RESETS bits the
  catalogue currently deasserts (gap surfaced by review).
- **1.1.0 (2026-04-15)** — devil's-advocate pass. Added probe-session
  resilience (reattach-on-error, per-iteration watchdog, give-up
  threshold) for week-long soak runs. Promoted `bank_conflict_test`
  refactor from "cheap extension" to its own design call (K-delta
  recasting required to drop the halt-step debug overhead). Added an
  explicit cross-oracle state-cleanup contract (each oracle's
  `run_against` restores VTOR/RESETS/etc. on exit). Concretised the
  ISR oracle's `image` layout convention (vector slots, code start
  offset, MSP source). Soak mode now defaults to quiet output
  (failures + hourly heartbeat) with `--verbose` opt-in. Minor flags
  added on clock-reprogram cycle semantics, M33 secure-state CPACR
  addressing, dependency policy, and CLAUDE.md update step.

## Problem

The two silicon oracles shipped on 2026-04-15 (`silicon_cycle_oracle_rp2350`,
`silicon_periph_diff_rp2350`) plus `bank_conflict_test_rp2350` already find
real bugs — the cycle oracle's first run flagged 8 of 9 cases with non-zero
HW−EMU deltas (`tech_debt.md:481`). Each is its own binary with its own
`Session::auto_attach`, its own arg parser, its own pass/fail accounting.
Two consequences:

1. **The hardware sits idle most of the time.** Arthur runs a binary, reads
   the diff, fixes the bug, runs it again — minutes of silicon time per day.
   The probe is attached to an RP2354 that could be running tests for hours.
2. **Coverage gaps remain.** `tech_debt.md:295` ("Exception entry/exit not
   differentially validated") explicitly flags `probe_diff_rp2350`-class
   silicon oracles as the higher-yield path for M33 ISR work. Dual-core
   contention beyond the single-core bank-conflict test, lazy FP context
   save, and clock reprogramming under load are all unit-test-only today.

This HLD covers two changes:

- A `test_silicon` orchestrator that wraps existing oracles plus two new
  ones, sharing one probe session, with an unattended **soak mode** for
  multi-day runs.
- Two new oracle modules (`silicon_isr_diff_rp2350`,
  `silicon_dualcore_diff_rp2350`) plus clock-reprogram scenarios in the
  existing peripheral oracle. These cover the four "small + medium"
  coverage items.

## Goals

1. **One orchestrator binary** that runs all hardware-gated mdrp2350
   oracles in sequence under one probe session. Single-pass mode for
   day-to-day CI-style use; soak mode for unattended overnight/multi-day
   runs that randomise case order across iterations.
2. **`silicon_isr_diff_rp2350`** — exception entry/exit + lazy FP save
   end-state oracle. Closes `tech_debt.md:295`.
3. **`silicon_dualcore_diff_rp2350`** — dual-core contention catalogue
   (cross-core bank thrash, spinlock churn, FIFO transfer). Extends
   `bank_conflict_test_rp2350`'s single-core bank-contention model with
   the cross-core dimension the emulator implements but never diffs.
4. **Clock-reprogram scenarios** added to `silicon_periph_diff_rp2350`
   (PLL_SYS FBDIV switch mid-workload, CLOCKS divider switch with PIO
   running). Requires one new field on `PeriphScenario`.

## Non-goals

- No new RP2040 silicon oracles. Lab rig only carries an RP2354 board.
- No `probe_diff_rp2350` integration into the orchestrator in v1. It has
  its own `--fuzz` mode and its own SRAM scratch layout; bringing it
  under the orchestrator is a v2 follow-on once the orchestrator pattern
  is proven on the simpler oracles.
- No DMA oracle. The emulator does not model the DMA engine
  (`grep -r dma crates/mdrp2350/src/bus` → 0 hits); building a silicon
  oracle against a missing implementation is a category error. DMA is a
  separate "implement DMA, then oracle it" project, not in scope here.
- No external stimulus harness (USB/UART/SPI/I2C). Out of scope for v1
  for the same reasons as the existing oracles.
- No CI integration. Both orchestrator and new oracles need silicon on
  USB; they run locally only.
- No JSON/CSV output. Plain text plus exit code is enough; a developer
  can `tee` to a file when they want a log of the soak run.
- No env vars. No feature flags. No backwards-compatibility shims for
  the old oracle binary entry points (they're refactored in place).

## Component 1 — `test_silicon` orchestrator

### Shape

One new binary, `crates/mdpicoem-harness/src/bin/test_silicon.rs`. Attaches
to the RP2354 once, calls each oracle's library entry point with the
shared `Core`, accumulates a unified `Report`. With `--soak <duration>`,
loops the same set of oracles with shuffled case order, accumulating a
running tally and logging failures with the seed that produced them.

### Library-API extraction (prerequisite refactor)

Each existing oracle's `main` body becomes a public function on the
oracle's catalog module. The `bin/<oracle>.rs` files shrink to thin
wrappers that own only the standalone-binary niceties (CLI parsing,
`Session::auto_attach`, exit-code translation).

| Oracle | New entry point |
|---|---|
| `silicon_cycle_oracle_rp2350` | `cycle_cases::run_against(&mut Core, &CycleArgs) -> CycleReport` |
| `silicon_periph_diff_rp2350` | `silicon_scenarios::run_against(&mut Core, &PeriphArgs) -> PeriphReport` |
| `bank_conflict_test_rp2350` | `bank_conflict_cases::run_against(&mut Core, &BankArgs) -> BankReport` |

`bank_conflict_test_rp2350` today measures via halt-step single-step,
which embeds a fixed ~5-cycle debug overhead in every reading. Bringing
it under the orchestrator's diff model needs a comparison protocol.
**Stay with halt-step**: it is the only modality that exposes the
+1 cycle SRAM bank-contention signal we built this oracle for.
`tech_debt.md:545-554` already documents that K-delta sequence-in-loop
measurements MASK the contention (`bank_contention_fetch_data_same`
and `bank_contention_fetch_data_diff` measure identically on HW=9 and
EMU=11) — so a K-delta recast would silently delete the very coverage
this oracle exists for. Use halt-step + a configurable tolerance
(default 1 to absorb debug-overhead variation across instructions /
bus paths; 0 for the strict cases). The library API is still
`run_against(&mut Core, &BankArgs) -> Result<Vec<CaseOutcome>, _>`,
the runner is just shaped around halt-step + emu.step() instead of
the K-delta stub. Diff = `(HW_observed - debug_overhead) - emu_cycles`,
with `debug_overhead` calibrated per-run from a NOP baseline (same
trick the existing `bank_conflict_test_rp2350` uses today).

The shared report types live in a new module `silicon_oracle.rs`:

```rust
pub struct CaseOutcome {
    pub oracle: &'static str,    // "cycle", "periph", "bank", "isr", "dualcore"
    pub case: &'static str,
    pub verdict: Verdict,        // Pass | Fail
    pub detail: String,          // first divergence; empty on pass
    pub elapsed_ms: u32,
}

pub struct OracleReport {
    pub outcomes: Vec<CaseOutcome>,
}
```

Each oracle's `*_Report` is just a `Vec<CaseOutcome>`. The orchestrator
concatenates them. No leaky abstractions — each oracle still owns its own
case type, runner, and diff logic; only the *outcome* shape is shared.

### Soak mode

```bash
test_silicon                          # single pass, exit 1 on any FAIL
test_silicon --soak 1h                # run for 1 hour, summary at end
test_silicon --soak 24h               # overnight
test_silicon --soak 7d --seed 42      # week-long, reproducible base seed
test_silicon --filter pio             # single pass restricted to PIO cases
test_silicon --soak 8h --verbose      # full per-case output (default: quiet)
```

Per soak iteration:

1. `iter_seed = base_seed.wrapping_add(iter_index)`
2. `StdRng::seed_from_u64(iter_seed)` shuffles each oracle's selected
   case slice (Fisher-Yates over `Vec<&'static T>` — original `&'static`
   catalogue arrays are untouched).
3. Each oracle's `run_against` is called with the shuffled selection.
4. `CaseOutcome` rows are appended to the running report. On FAIL,
   one line is printed immediately (`oracle, case, iter_seed, detail`)
   so a soak run that finds a bug at hour 17 leaves a breadcrumb in
   `tee`d output — no waiting until the end.
5. Iteration continues until the wall-clock deadline.

### Output policy

- **Single-pass mode** (no `--soak`): full per-case PASS/FAIL table
  per oracle, plus an overall summary. Same shape the standalone
  binaries produce today.
- **Soak mode default**: quiet. Print the start banner, each FAIL line
  immediately as it happens, and a one-line heartbeat per hour
  (`[+02:00:00] iter=7218 pass=72180 fail=3`). Final summary at end.
  This keeps a `tee`d week-long log readable.
- **`--verbose` in soak mode**: full per-case output every iteration
  (matches single-pass density). Useful for the first 8h soak run
  when you want eyeballs on each case; turn off for the 7d run.

### Probe-session resilience (soak mode)

A week-long soak will hit transient probe-rs failures (USB hiccup,
timeout from a wedged stub, occasional `core.halt` returning an
error). Without explicit handling, the orchestrator dies on the first
one and Arthur loses days of silicon time.

The resilience contract:

1. **Per-case watchdog.** Every `run_against` call is wrapped in a
   `Duration::from_secs(60)` timeout. If a single case takes longer,
   the orchestrator forcibly `halt`s the core, marks the case as
   `Verdict::Fail` with `detail = "watchdog timeout"`, and continues.
   60s is generous — every catalogued case today completes in under
   2s — but allows for a one-off slow USB transfer.
2. **Probe-rs error handling per oracle.** A `run_against` returning
   `Err(probe_rs::Error)` is logged as `Verdict::Fail` with the error
   string, the orchestrator drops the current `Session`, sleeps 1
   second, and re-attaches via `Session::auto_attach`. If reattach
   itself fails, retry every 5 seconds for up to 60 seconds before
   giving up that iteration.
3. **Give-up threshold.** Three consecutive iteration-level reattach
   failures → orchestrator exits with a clear diagnostic. The probe is
   probably unplugged or the chip is dead; further retries are noise.
4. **Catastrophic-failure log.** Probe-rs errors and watchdog timeouts
   write a one-line entry to `fuzz-runs/test_silicon.<pid>.errors.log`
   in addition to stdout, so post-mortem after a tee'd log gets
   truncated still has the timestamps and seeds.

Termination paths:

- Without `--soak`: one pass, deterministic catalogue order, exit 1 on
  any FAIL.
- With `--soak`: runs until the deadline. **Ctrl-C also stops cleanly
  via** `ctrlc::set_handler` setting an `AtomicBool` polled at
  iteration boundary — the current case completes, then summary
  prints, then exit 0 (or 1 if any fail accumulated).
- Give-up threshold reached: exit 2 (distinct from "tests failed")
  with the last few error log lines printed for diagnosis.

The summary at end of a soak run reports total iterations, per-oracle
pass/fail counts, watchdog-timeout count, reattach count, and a
deduplicated list of failing cases with the smallest seed that
reproduced each. That seed lets a developer rerun
`test_silicon --soak 1m --seed <S>` to repro fast.

### Cross-oracle state-cleanup contract

The orchestrator runs oracles back-to-back inside one iteration. The
ISR oracle leaves VTOR pointing at SRAM; the cycle oracle expects the
default reset state. To avoid order-dependent flakes, **every
`run_against` MUST restore default state on exit, regardless of pass
or fail**:

| Oracle | Cleanup on exit |
|---|---|
| cycle | None needed (only writes SRAM scratch + DWT). |
| periph | Re-assert all RESETS bits the catalogue cleared (currently `RESET_PIO0`, `RESET_PIO1`, `RESET_PLL_SYS`, `RESET_IO_BANK0`, `RESET_PADS_BANK0` — any future scenario that deasserts a new RESETS bit MUST add it here too; the catalogue and cleanup must drift together or state leaks). |
| bank | None needed. |
| isr | Set VTOR=0; clear NVIC pending bits (`ICPR0..n` writes); clear FPCCR.LSPACT/LSPEN to defaults; CONTROL=0. |
| dualcore | Halt core 1; clear SIO spinlocks the catalogue touched (write 1 to SPINLOCK0..n to release). |

Each oracle's `run_against` documents its cleanup in a doc-comment
above the function. The orchestrator additionally calls
`core.reset_and_halt` between iterations (not between oracles within
one iteration — that would defeat the cross-oracle leakage detection
the soak loop intentionally exposes).

### CLI

```
Usage: test_silicon [--soak <duration>] [--seed <u64>] [--filter <substr>] [--verbose]

Options:
  --soak     Run continuously for the given duration (e.g. 30m, 4h, 7d).
             Default: single pass.
  --seed     Base RNG seed for soak-mode shuffling.
             Default: current Unix epoch seconds.
  --filter   Only run cases whose name contains <substr>. Applied to
             every oracle's catalogue. Default: all cases.
  --verbose  In soak mode, print full per-case output every iteration
             (default is quiet: failures + hourly heartbeat). No effect

```

Four flags, all optional. No env vars. No oracle-selection flag (the
filter substring is enough to scope down to one oracle's cases when
debugging — case names are unique across oracles by convention:
`pio0_*`, `pll_sys_*`, `cycle_*`, `bank_*`, `isr_*`, `dualcore_*`).

## Component 2 — `silicon_isr_diff_rp2350`

### Why a new oracle, not an extension of periph

Exception entry needs a *handler* — code in SRAM that runs when the
exception fires. The peripheral oracle's countdown sled is a fixed
`movw / subs / bne / bkpt` template; bolting handler dispatch onto it
makes the sled assembler the wrong shape. The ISR oracle owns its own
sled-equivalent: a vector table + a handler stub + a main routine, all
in SRAM, all per-scenario. Same probe-session/run-at-native-speed
pattern, different scaffolding.

### Shape

For each scenario:

1. Reset core 0; enable CYCCNT; halt core 1 (same as the other oracles).
2. Upload a per-scenario SRAM image: vector table at one fixed offset,
   handler bytecode after, main routine after that. VTOR is reprogrammed
   to point at the SRAM vector table.
3. Set CPU initial state per scenario (registers, CONTROL, CPACR for FP
   tests, FPCCR/FPCAR overrides where the scenario wants them).
4. Set PC to main routine entry. Resume.
5. Main routine sets up the trigger (e.g. `ICSR.PENDSVSET=1`), then
   busy-waits or BKPTs at a known label. Exception fires; handler runs.
6. Handler captures CYCCNT delta into a fixed mailbox slot and BKPTs.
7. Host halts on BKPT, reads observables (CYCCNT, stacked frame at
   pre-trigger SP, FPCCR, FPCAR, CONTROL, xPSR).
8. Emulator side: same image upload via `Emulator::poke`/`mmio_write32`,
   same CPU initial state via `core_mut(0).regs`, run forward enough
   cycles, gate at the same label, read the same observables.
9. Diff. First divergence wins.

### Scenario type

```rust
pub struct IsrScenario {
    pub name: &'static str,
    /// Bytes to write at SRAM_BASE (a per-scenario fixed location);
    /// includes vector table + handler + main + literal pool.
    pub image: &'static [u8],
    /// Offset (within `image`) of the main routine's first instruction.
    pub entry_offset: u32,
    /// Initial register snapshot (R0–R12, MSP, PSP, CONTROL, CPACR).
    /// Anything not listed is zero.
    pub init_regs: &'static [(IsrReg, u32)],
    /// Upper bound on sysclks before BKPT halts; if exceeded, scenario
    /// fails with timeout, no diff attempted.
    pub max_sysclks: u32,
    /// Observables: each a (label, reader_fn) pair. Labels appear in
    /// diff output for human-readable failure messages.
    pub observe: &'static [(&'static str, IsrObservable)],
}

pub enum IsrReg { R0, R1, ..., R12, MSP, PSP, CONTROL, CPACR, VTOR }

pub enum IsrObservable {
    Mmio(u32),                      // raw 32-bit MMIO read
    StackedReg(StackedReg),         // pulled from the stacked frame at MSP/PSP
    CycleDelta,                     // ISR_MAILBOX[0] (set by handler)
}
```

`init_regs` is `&'static`; `image` is `&'static`. Catalogue stays static
data, runner is the only code per scenario.

### SRAM layout (per scenario)

```
0x2000_2000  ISR_IMAGE_BASE         scenario `image` starts here
                                    (fixed layout; see below)
0x2000_3000  ISR_STACK_TOP          MSP/PSP top by default
0x2000_3FF8  ISR_MAILBOX_CYCCNT     u32, written by handler
0x2000_3FFC  ISR_MAILBOX_RESERVED   u32
```

Above the cycle oracle's slot (`0x2000_1000`) and the periph sled
(`SILICON_RUN_SLED = 0x2000_1100`); below the cycle mailbox
(`0x2004_0100`). Add `pub const ISR_IMAGE_BASE: u32 = 0x2000_2000;`,
`pub const ISR_STACK_TOP: u32 = 0x2000_3000;`,
`pub const ISR_MAILBOX_BASE: u32 = 0x2000_3FF8;` to `lib.rs`.

### Image layout (fixed convention)

Each scenario's `image: &'static [u8]` follows one fixed layout so the
runner doesn't need scenario-specific knowledge of where things live:

```
+ 0x000  vector table (16 entries × 4 bytes = 64 bytes; 32-word align
         is satisfied at ISR_IMAGE_BASE = 0x2000_2000):
           [0]  initial MSP                = ISR_STACK_TOP
           [1]  Reset_Handler              = ISR_IMAGE_BASE | 1 + main
                                             (i.e. main_offset|1)
           [2..13]  unused exceptions, all = ISR_DEFAULT_HANDLER | 1
                    (a 1-instr `bkpt` at a known offset)
           [14] PendSV_Handler             = ISR_IMAGE_BASE | 1 + handler_offset
           [15] SysTick_Handler            = ISR_IMAGE_BASE | 1 + systick_offset
                                             (entry shared with PendSV
                                             when the scenario uses both)
+ 0x040  default handler  (offset documented as ISR_DEFAULT_HANDLER_OFF):
           bkpt #1
+ 0x044  PendSV/SysTick handler  (handler_offset = 0x044):
           [scenario-specific]
           bkpt #0          ; final halt for host readback
+ 0x100  main routine  (main_offset = 0x100):
           [scenario-specific setup]
           [trigger: ICSR.PENDSVSET write or SYST_CSR enable]
           [busy-wait or BKPT — handler will preempt]
```

`IsrScenario` provides `main_offset`, `handler_offset`, and
`systick_offset` as fields (all relative to `ISR_IMAGE_BASE`). The
runner uses these to set VTOR's vector entries and to know where to
halt-detect at handler entry. Hand-assembled images include a small
inline-comment listing as in `cycle_cases::MEASUREMENT_STUB` so the
catalogue is auditable without re-disassembling.

Note: M33 with security extensions has both NS_VTOR (`0xE002_ED08`)
and S_VTOR (`0xE000_ED08`). RP2354 boots into secure state by default
per RP2350 datasheet §3.7; the catalogue writes both VTOR entries
identically so it works regardless of which state the test ends up
running in. CPACR similarly has S/NS aliases — the lazy-FP scenario
writes both. If a future scenario needs to test the S/NS boundary,
that becomes its own dimension; v1 just papers over it.

### Initial catalogue

Four scenarios — every one of these directly addresses `tech_debt.md:295`:

- `isr_pendsv_cold` — baseline. Main routine enables PendSV, BKPTs at a
  label after pend. Handler captures CYCCNT delta from "main BKPT" to
  "handler entry" and BKPTs. Validates: cycle count of cold ISR entry,
  stacked R0–R3/R12/LR/PC/xPSR, CONTROL.SPSEL update.
- `isr_lazy_fp_save` — CPACR enabled, FP register dirty (V0 = 0xC0DECAFE),
  CONTROL.FPCA=1, FPCCR.LSPEN=1 (default). Trigger PendSV. Handler
  immediately BKPTs without touching FP. Validates: FPCCR.LSPACT=1,
  FPCAR points at the reserved FP space inside the stacked frame, FP
  registers NOT pushed.
- `isr_eager_fp_save` — same setup but FPCCR.LSPEN=0. Validates: FPCCR.LSPACT=0,
  V0–V15 + FPSCR pushed onto the extended frame, frame size = 26 words
  (basic 8 + extended 18).
- `isr_tail_chain_pendsv_systick` — SysTick pre-armed with reload=4,
  PendSV pended. Both fire close together; entry should tail-chain.
  Validates: cycle-delta savings vs two cold entries (computed as
  `tail_chained_cycles - 2 * cold_entry_cycles < 0`).

### Critical simplifications

- Handler uses BKPT to halt. No RTE, no testing of return paths in v1.
  Exception *return* validation is its own catalogue item — adding it
  needs the handler to reach BKPT *after* RTE, which means main routine
  ends in a BKPT too. Defer to v2 unless cheap when the first scenarios
  land.
- No security state transitions (S/NS) in v1. RP2354 supports them but
  they're another combinatorial dimension; defer.
- No nested exception scenarios in v1. NVIC priority manipulation is
  available; first catalogue keeps priorities at default.

## Component 3 — `silicon_dualcore_diff_rp2350`

### Why a new oracle

`bank_conflict_test_rp2350` measures *single-core* bank contention via
halt-step. The emulator's `Bus::contention_check_active` flag
(`mdrp2350/src/bus/mod.rs`, the `core0_port` tracking pattern) implements
*cross-core* contention: when core 0's downstream port matches core 1's,
+1 cycle. That mechanism is unit-tested only — no silicon diff exists.

The dualcore oracle is structurally similar to the cycle oracle: a
measurement stub on core 0 reading CYCCNT around a sequence; the
difference is core 1 runs an antagonist loop concurrently.

### Shape

Per case:

1. Halt both cores. Enable CYCCNT on core 0.
2. Upload core-0 measurement stub (reuses `MEASUREMENT_STUB` from
   `cycle_cases::pack_stub`) at `STUB_START`.
3. Upload core-1 antagonist sequence at `DUALCORE_ANTAGONIST_SLOT`.
4. Set core 1 PC = antagonist, PSR.T = 1, SP = a per-core stack slot;
   resume core 1. It now spins in its antagonist loop forever.
5. Run core 0's cycle measurement (same K-delta protocol as cycle
   oracle: K_low=101, K_high=201, per_iter = (m_high - m_low) / 100).
6. Halt core 1.
7. Emulator side: same upload, both cores released, run forward via
   `Emulator::run` until the same K iterations complete (use the cycle
   oracle's emulator-side measurement helper, parameterised by which
   cores are active).
8. Diff per_iter HW vs EMU.

### Case type

```rust
pub struct DualCoreCase {
    pub name: &'static str,
    /// Sequence run by core 0 inside the K-iteration measurement loop.
    pub seq_core0: &'static [u16],
    /// Antagonist body run by core 1, looped forever via an infinite
    /// branch the runner appends.
    pub seq_core1: &'static [u16],
    /// Pre-loop register values for core 0 (R0..R7 only — stub
    /// preserves R4-R7).
    pub init_core0: &'static [(u8, u32)],
    /// Pre-loop register values for core 1 (R0..R12).
    pub init_core1: &'static [(u8, u32)],
    /// Emulator's per-iter cycle cost as of the last run, like
    /// `CycleCase::emu_baseline`.
    pub emu_baseline: u32,
}
```

### Initial catalogue

- `dualcore_load_same_bank` — core 0 `LDR r0, [r1]` (r1 = bank-0 data),
  core 1 `LDR r0, [r2]; STR r0, [r2]` thrashing bank 0. Expect HW per-iter
  > control case by N cycles (the cross-core contention penalty).
- `dualcore_load_diff_bank` — control. Same core 0 sequence; core 1
  thrashes bank 1 instead of bank 0. Expect HW per-iter == control.
- `dualcore_spinlock_churn` — both cores acquire/release SIO spinlock 0:
  `LDR r0, [r1]` (read claims), `STR r0, [r1]` (write releases). Tight
  contention. Validates spinlock fairness/throughput model.
- `dualcore_fifo_xfer` — core 0 pushes 4 words to SIO_FIFO_WR; core 1
  pops 4 words from SIO_FIFO_RD. Sequence terminates when FIFO drains.
  Validates FIFO end-state and core-1 wake from FIFO-not-empty.

### SRAM layout

```
0x2000_0100  STUB_START           core 0 measurement stub (reused)
0x2000_1000  CYCLE_SEQ_SLOT       core 0 sequence (reused)
0x2000_1100  DUALCORE_ANTAGONIST_SLOT  core 1 antagonist sequence
0x2000_1200  DUALCORE_CORE1_DATA  scratch words for core 1's load/store
0x2003_FE00  DUALCORE_CORE1_STACK core 1 stack (separate from core 0's)
```

`pub const DUALCORE_CORE1_DATA: u32 = 0x2000_1200;`,
`pub const DUALCORE_CORE1_STACK: u32 = 0x2003_FE00;` to `lib.rs`.

## Component 4 — Clock-reprogram scenarios in `silicon_periph_diff_rp2350`

### Why a scenario extension, not a new oracle

The peripheral oracle is already shaped around "MMIO writes + run for N
sysclks + read observables". Reprogramming PLL_SYS or a CLOCKS divider
mid-workload is two extra MMIO writes injected partway through the run.
The only thing missing is the ability to let a scenario specify its own
sled bytes (so MMIO writes can be interleaved with NOPs, instead of the
default `movw / subs / bne` countdown).

### Change to `PeriphScenario`

```rust
pub struct PeriphScenario {
    pub name: &'static str,
    pub setup: &'static [(u32, u32)],
    pub max_sysclks: u32,
    pub observe: &'static [(u32, u32)],
    pub observe_pins: u32,
    /// If `Some(bytes)`, the runner uploads these as the sled instead
    /// of auto-assembling a countdown. Bytes must end in `bkpt #0`
    /// (`0xBE00`). Existing scenarios leave this `None`.
    pub custom_sled: Option<&'static [u8]>,
}
```

### New scenarios

- `clock_pll_sys_reprogram_mid_run` — sled programs PLL_SYS to one
  FBDIV, runs ~500 sysclks of NOPs, reprograms FBDIV mid-run, runs
  another ~500 sysclks, BKPTs. Observes PLL_SYS.CS.LOCK timing,
  derived sys_clk frequency.
- `clock_div_change_pio_running` — PIO0 SM0 running a counter program;
  sled changes CLOCKS_CLK_SYS_DIV mid-run; observe SM0_ADDR progress
  ratio matches the divider change.

These exercise the dynamic ClockTree recompute path (Bus's cached
`ClockTree` is rebuilt on relevant register writes — see
`bus/clocks.rs`) under load, which is otherwise only unit-test covered.

**Cycle-vs-frequency semantics**: CYCCNT counts core ticks, not
wall-clock time. After a PLL reprogram both core ticks and CYCCNT
continue at the new rate, and the emulator's `Emulator::run(N)`
advances the same N core ticks regardless of the clock-tree state.
The actual_sysclks readback fed to the emulator therefore stays
consistent across mid-run frequency changes — but a scenario that
mixes wall-clock-sensitive observables (PIO clock divisions, etc.)
needs to keep that distinction in mind when picking what to assert.

## Assumptions (worth verifying early)

1. **DWT CYCCNT is per-core on RP2350.** The dualcore oracle measures
   core 0's CYCCNT while core 1 runs antagonist code. ARMv8-M DWT is
   per-core in spec; the existing single-core oracles confirm CYCCNT
   works on core 0 via `0xE000_1004`. Need to verify core 1's CYCCNT
   is at the same alias (per ARM CoreSight, each core sees its own
   private DWT at the standard address). Verifiable in <30 lines:
   release core 1 with a known cycle-cost loop, halt, read CYCCNT
   while attached to core 1 via `Session::core(1)`.
2. **VTOR remap to SRAM works on RP2354.** ARMv8-M permits VTOR pointing
   at SRAM (alignment requirement: 32-word for the table). Standard
   M33 behavior; mentioned in RP2350 datasheet §3.7. Verify with a
   one-shot scenario before the full ISR catalogue lands.
3. **Releasing core 1 with a custom PC/SP works via probe-rs.**
   `Session::core(1).write_core_reg + run` should be sufficient; the
   existing oracles only ever halt core 1, never release it. Verifiable
   independent of the dualcore oracle: write a "store known value to
   SRAM, then loop forever" stub, release, halt, read SRAM.
4. **Soak-mode RNG seeding from epoch seconds is reproducible enough.**
   For "find an intermittent then re-run with the failing seed",
   per-iteration `seed = base + iter` works because `base` is logged at
   start. Soak runs that find a regression report the iter index, and
   `--seed <base>` rerun-from-iter-0 will reach the same case in the
   same order. Adequate.

If (1) fails (e.g. CYCCNT on core 1 is unimplemented or maps elsewhere),
dualcore measurements fall back to wall-clock timing on core 0 only,
which loses the per-cycle precision but still catches end-state bugs
(`bank thrash visible in measurement` vs `not visible`). Acceptable
fallback for v1.

If (2) fails, the ISR oracle moves the vector table into ROM (the boot
ROM has its own table; we can't write that, but we *can* write a
trampoline at SRAM that the boot table points at via a post-reset
patch). More plumbing; flag in the smoke-binary results before
committing to the full catalogue.

## What this does NOT do

- No RP2040 silicon variants (no board).
- No `probe_diff_rp2350` integration in v1 (its `--fuzz` mode is its own
  beast; orchestrator integration is v2).
- No DMA oracle (no emulator-side implementation to diff against).
- No external-stimulus harness (USB/UART/SPI/I2C).
- No JSON/CSV reporting; plain text only.
- No CI integration; hardware-gated by definition.
- No cycle-by-cycle ISR trace (end-state only — same constraint as the
  peripheral oracle).
- No randomisation *within* cases in v1; soak mode randomises case
  order, not parameters. Case-parameter perturbation is a v2 lever
  worth adding once we know which oracles benefit (cycle-delta cases
  probably don't; ISR/dualcore probably do).

## Acceptance

1. `test_silicon` runs a single pass of all five oracles (cycle, periph,
   bank, isr, dualcore) under one probe session, prints a unified
   per-case PASS/FAIL table and an overall summary line, exits 0 if all
   pass and 1 otherwise.
2. `test_silicon --soak 5m` runs continuously for 5 minutes, randomising
   case order each iteration, prints a summary including total
   iterations, per-oracle pass/fail counts, and any failing-case seeds
   for repro. Ctrl-C during the run finishes the current case and
   prints the same summary.
3. `silicon_isr_diff_rp2350` standalone binary runs the four-scenario
   ISR catalogue and reports per-scenario diffs. The lazy-FP scenario
   detects FPCCR.LSPACT and FPCAR correctly on silicon.
4. `silicon_dualcore_diff_rp2350` standalone binary runs the four-case
   dualcore catalogue and reports HW vs EMU per-iter cycle cost.
5. The two new clock-reprogram scenarios in `silicon_periph_diff_rp2350`
   pass on silicon (or fail in a way that closes a tech-debt entry).
6. Each new oracle's first run either retires a `tech_debt.md` entry
   (with measured numbers) or opens a new one with reproducer info.
   Specifically: ISR oracle should retire or rescope `tech_debt.md:295`.

## Order of operations

1. **Verify Assumption 1** (per-core CYCCNT on RP2350) with a 30-line
   smoke binary. Delete after.
2. **Library-API extraction** of the three existing oracles into
   `run_against(&mut Core, &Args) -> Vec<CaseOutcome>` form. Existing
   binaries keep their CLI shape; this is purely refactoring.
3. **Ship `test_silicon`** orchestrator wrapping just the three existing
   oracles (single-pass and soak modes both). No new oracle cases yet —
   prove the orchestrator pattern on known-passing oracles first.
4. **Ship clock-reprogram scenarios** (smallest scope: extends an
   existing oracle, no new binary). Validates the `custom_sled` field
   and the soak-mode catalogue-shuffle path with new content.
5. **Ship `silicon_dualcore_diff_rp2350`** (next-smallest: reuses cycle
   oracle's stub + measurement protocol; only adds core-1 release path
   and a new catalogue).
6. **Ship `silicon_isr_diff_rp2350`** (largest: needs vector-table
   upload and CPU-state setup primitives that don't exist anywhere
   else). Verify Assumption 2 as part of the first scenario's bring-up.
7. **First soak run**: `test_silicon --soak 8h` overnight. Triage any
   failures. Either close them as emulator bugs, or open tech-debt
   entries with seeds for repro.
8. **Multi-day soak**: `test_silicon --soak 7d` once the 8h run is
   clean. Whatever this finds is the real prize.
9. **Update `CLAUDE.md`** under "Testing Topology" with the new
   binaries (`test_silicon`, `silicon_isr_diff_rp2350`,
   `silicon_dualcore_diff_rp2350`) and their hardware-gated
   prerequisites. Add the same entries to the harness binary list.
