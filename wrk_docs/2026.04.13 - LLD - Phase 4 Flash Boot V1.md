# Phase 4: Flash + Full Boot — Low-Level Design

Version: 0.1.0
Date: 2026-04-13
Parent: HLD Section 15, Phase 4
Depends: Phase 3 complete + TrustZone NS support (in progress separately)

## 1. Purpose

Load a Pico SDK application binary (e.g., blinky) into flash. The bootrom
discovers the image via XIP reads, validates it, and jumps to the application's
entry point. The application reaches `main()`.

### Milestone

`cargo test` integration test: load bootrom + blinky.uf2 → bootrom finds valid
image → application reaches `main()` and toggles a GPIO pin.

### What exists today

| Component | Status | Gap |
|-----------|--------|-----|
| Flash storage | `load_flash()` → `Vec<u8>` at 0x10000000 | Works |
| XIP reads | Direct vec read when `flash_loaded=true` | No cache (OK for Phase 4) |
| XIP SRAM | 16KB at 0x1C000000, read/write | Works |
| QMI stub | Returns TXEMPTY+RXEMPTY at 0x400D0000 | Needs expansion |
| Bootrom | Runs full secure path → `bxns` at 0x7EA4 | Needs TrustZone NS to continue |
| Flash image format | Not implemented | Need to understand picobin format |

### What the bootrom does with flash (from disassembly)

1. `connect_internal_flash` (0xE3C): Initialize QMI, probe for flash device
2. `flash_exit_xip` (0xF64): Switch flash from XIP to command mode, configure read
3. `flash_enter_cmd_xip` (0x658): Set up XIP read mode via QMI registers
4. `perform_flash_scan_and_maybe_run_image` (0x2DEC): Read flash at 0x10000000,
   search for valid picobin image header, validate, load, and execute
5. If valid image: `checked_ram_or_flash_window_launch` (0x36B4) → jump to app
6. If no valid image: `core0_boot_path_cant_boot` (0x3CDE) → nsboot (USB boot)

### What is NOT needed for Phase 4

| Feature | Why not | When |
|---------|---------|------|
| Real XIP cache | Direct flash reads are correct, just faster than real HW | Phase 8 |
| Write-back cache | Flash is read-only from XIP perspective | Phase 8 |
| QMI command mode | Bootrom uses it for setup but we can stub the handshake | N/A |
| Flash write/erase | Read-only flash is sufficient for boot | Phase 6+ |
| GDB RSP server | Nice to have but not on critical path | Phase 4b or later |

## 2. Key Design Decisions

### 2.1. No XIP cache — direct reads are sufficient

The HLD calls for a "16 kB, 2-way, 2-bank write-back cache." This is a Phase 8
performance optimization. For Phase 4 correctness, direct flash reads via the
existing `memory.xip_read32(offset)` path are functionally identical to cache
hits. Every XIP read returns the correct data in 1 cycle.

The existing code already does this when `flash_loaded == true`. No change needed.

### 2.2. QMI expansion — enough to not block the bootrom

The bootrom's flash initialization writes ~20 QMI registers to configure timing,
pin mapping, and XIP read mode. Our QMI stub currently accepts writes and returns
TXEMPTY. We need to expand it enough that:

1. The bootrom's QMI configuration writes succeed (accept and store)
2. QMI status reads return "ready" / "done" values
3. The bootrom's flash device ID read returns a plausible flash ID

The bootrom reads flash device info from QMI at 0x400D0000 + various offsets.
If it gets 0 for the device ID, it may conclude "no flash" and skip the flash
boot path. We need to return a valid flash device ID.

### 2.3. Picobin image format — what the bootrom looks for

The RP2350 bootrom scans flash (starting at 0x10000000) for a "picobin" image
block. The format is defined in the Pico SDK:

A valid picobin IMAGE_DEF block starts with:
- Magic: `0xffffded3` at the start of a 256-byte aligned block
- Followed by block header with image type, entry point, etc.

The Pico SDK's `pico_flash_binary_start` places this at flash offset 0x000
(address 0x10000000). The bootrom reads the first few words of flash to find it.

For Phase 4, we can either:
a) Load a real compiled Pico SDK binary (blinky.uf2 converted to raw binary)
b) Construct a minimal picobin header in test code

Option (a) is the real test. Option (b) is useful for unit testing.

### 2.4. The boot flow with flash

When flash contains a valid image:

```
Bootrom secure init (Phase 3, done)
  → bxns to NS code
  → NS bootrom: flash_scan at 0x10000000
  → Finds picobin header
  → Validates image (CRC/hash check)
  → Sets up XIP for app code
  → Jumps to application entry point (from picobin header)
  → Application runs from XIP (0x10000000+)
  → Reaches main()
```

### 2.5. Dependencies on TrustZone NS support

The flash scan happens AFTER `bxns` — in Non-Secure state. Without NS
execution support, the bootrom can't reach the flash scan. Phase 4
implementation is blocked on the TrustZone agent completing NS support.

Once NS works, the bootrom's flash path should "just work" because:
- XIP reads at 0x10000000 already serve flash data
- QMI stubs already return "ready"
- The only gap is QMI register expansion for the flash init handshake

## 3. QMI Register Expansion

The bootrom writes to many QMI registers during `connect_internal_flash` and
`flash_exit_xip`. Currently our stub ignores all writes and returns 0 for
unknown registers.

### 3.1. Registers to implement

From bootrom disassembly, these QMI registers are accessed:

| Offset | Name | Read behavior |
|--------|------|--------------|
| 0x000 | DIRECT_CSR | TXEMPTY=1, RXEMPTY=1, BUSY=0 (existing) |
| 0x004 | DIRECT_TX | Write: accept, ignore |
| 0x008 | DIRECT_RX | Read: return flash device ID or 0 |
| 0x00C | M0_TIMING | Write: accept (timing config) |
| 0x010 | M0_RCMD | Write: accept (read command config) |
| 0x014 | M0_WCMD | Write: accept (write command config) |
| 0x018 | M0_RFMT | Write: accept (read format) |
| 0x01C | M0_WFMT | Write: accept (write format) |
| 0x034 | ATRANS0 | Write: accept (address translation) |

Backing state: `qmi_regs: [u32; 16]` array on Bus, indexed by `offset >> 2`.
Read returns stored value. Write stores value.

Special cases:
- DIRECT_CSR (0x000): Always OR in TXEMPTY (bit 16) and RXEMPTY (bit 17)
- DIRECT_RX (0x008): Return the stored direct-RX value (written by DIRECT_TX
  response cycle — for Phase 4, return a fixed flash JEDEC ID like 0xEF4016
  for Winbond W25Q32, which the Pico SDK commonly uses)

### 3.2. Flash device ID

The bootrom issues a JEDEC-ID read command (0x9F) via QMI DIRECT_TX and reads
the response from DIRECT_RX. For our stub:

When DIRECT_TX is written with a command byte, set DIRECT_RX to:
- Command 0x9F (Read JEDEC ID): Store `0x001640EF` (Winbond W25Q32, 4MB)
- Other commands: Store 0x00

This makes the bootrom believe a valid flash chip is present.

## 4. Pico SDK Binary Loading

### 4.1. UF2 and raw binary formats

Pico SDK outputs `.uf2` files (UF2 format — chunked with headers) or `.bin`
files (raw flash image). For the emulator:

- **Raw binary**: Load directly via `emu.load_flash(&bin_data)`. The data
  appears at 0x10000000.
- **UF2**: Parse UF2 blocks, extract payload, reassemble into a flat binary,
  then load. UF2 parsing is a small utility function.

For Phase 4, support raw binary loading (which already works via `load_flash`).
UF2 support is a convenience that can be added later.

## 5. Integration Test

### 5.1. Full boot test

```rust
#[test]
fn test_bootrom_boots_flash_to_main() {
    let rom = std::fs::read("roms/bootrom-combined.bin").unwrap();
    let flash = std::fs::read("roms/blinky.bin").unwrap();
    
    let mut emu = Emulator::new(Config::default());
    emu.load_bootrom(&rom);
    emu.load_flash(&flash);
    emu.reset();
    
    // Run for up to 10M cycles
    let mut stuck_count = 0u32;
    let mut last_pc = 0u32;
    for _ in 0..10_000_000 {
        emu.step();
        let pc = emu.cores[0].regs.pc();
        if pc == last_pc {
            stuck_count += 1;
            if stuck_count > 100 { break; }
        } else {
            stuck_count = 0;
        }
        last_pc = pc;
    }
    
    // Application should have set GPIO 25 high
    // Check SIO GPIO output register
    let gpio_out = emu.bus.read32(0xD000_0010); // SIO GPIO_OUT
    assert!(gpio_out & (1 << 25) != 0, "GPIO 25 should be high (LED on)");
}
```

### 5.2. Flash scan unit test

Test the flash scan path independently:

```rust
#[test]
fn test_qmi_returns_flash_jedec_id() {
    let mut bus = Bus::new();
    // Write JEDEC-ID read command to DIRECT_TX
    bus.write32(0x400D_0004, 0x9F);
    // Read response from DIRECT_RX
    let id = bus.read32(0x400D_0008);
    assert_eq!(id, 0x001640EF, "Should return Winbond W25Q32 JEDEC ID");
}
```

## 6. Staging

### Stage A: QMI expansion + flash device ID

- Expand QMI stub with register backing store
- DIRECT_TX command → DIRECT_RX response (JEDEC ID)
- Status registers return "ready"
- Tests: QMI register round-trip, JEDEC ID read

### Stage B: Flash boot investigation

- Study picobin format from Pico SDK headers
- Build or obtain a minimal flash binary
- Trace bootrom flash scan path in emulator (diagnostic)
- Identify any missing stubs/registers that block the scan

This stage is primarily investigation, done in parallel with TrustZone work.

### Stage C: Integration (requires NS support)

- Load bootrom + flash binary
- Run full boot: secure init → NS → flash scan → app launch
- Assert application reached main() (GPIO state check)
- Debug any remaining stubs needed for the app init path

## 8. Known Limitations

- **No XIP cache**: All reads are 1-cycle cache "hits." Phase 8.
- **No flash write/erase**: Read-only sufficient for boot. Phase 6+.
- **No GDB RSP**: Deferred from Phase 4 scope. Separate task.
- **QMI is a response stub**: Doesn't simulate real QSPI transactions.
- **Picobin validation may be simplified**: If the bootrom's CRC/hash check
  fails, we may need to stub the DCP (which does SHA-256 for image validation).

## 9. Open Investigation Items

1. **Picobin image format**: Study `pico-sdk/src/rp2_common/boot_picobin_headers/`
   to understand the block header, IMAGE_DEF, and minimum valid image structure.
2. **DCP for image validation**: The bootrom may use DCP (CP4/5) for SHA-256
   hash verification of the flash image. Our DCP stub does no computation.
   If validation fails, the bootrom skips the image. May need to either:
   (a) implement DCP SHA-256, or (b) find a way to bypass validation.
3. **Second-stage bootloader (boot2)**: Pico SDK flash images include a 256-byte
   "boot2" at flash offset 0 that configures XIP for the specific flash chip.
   The bootrom may execute boot2 before the main application. This code runs
   from SRAM (copied there by the bootrom) and configures QMI/XIP.
4. **Application init path**: The Pico SDK runtime (`crt0.S`) initializes
   `.data`, `.bss`, clocks, and calls `main()`. This touches RESETS, CLOCKS,
   and potentially other peripherals we haven't stubbed. May need additional
   peripheral stubs.
5. **NS execution environment**: Blocked on TrustZone support.

## 10. Risk Assessment

The biggest risk is the picobin validation path. The bootrom uses DCP for
SHA-256 and RCP for integrity checks during image validation. Our stubs
return dummy values. If the bootrom's validation logic actually checks
these results (rather than just accepting any value), the flash boot path
will fail at validation and fall through to nsboot.

Mitigation: trace the bootrom's validation code path. If it hard-fails on
DCP results, implement minimal SHA-256 in the DCP stub. This is bounded
work (~100 lines of SHA-256 in Rust).
