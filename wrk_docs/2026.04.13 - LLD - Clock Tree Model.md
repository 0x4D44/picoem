# LLD: Clock Tree Model

**Version:** 0.1.0 (DRAFT)
**Date:** 2026-04-13
**Scope:** Model the RP2350 clock tree well enough that the emulated CPU runs
at the correct speed — ROSC at boot, 150 MHz after PLL configuration.

## 1. Problem

The emulator hardcodes `sys_clk_hz = 150_000_000` at construction. The
actual RP2350 boots on ROSC (~6.5 MHz), and the CPU stays there unless
firmware configures the PLL and switches the CLOCKS mux. Our blinky
firmware does neither — it just toggles GPIO in a loop. On real hardware
the delay loop takes ~167ms (visible blink); on our emulator it takes
~6.7ms (invisible). The emulator is lying about clock speed.

## 2. Goal

Make `sys_clk_hz` dynamic. After this change:

1. Emulator boots at ROSC speed (~6.5 MHz)
2. Bootrom may switch clk_ref to XOSC (12 MHz) during its init sequence
3. Firmware that configures PLL_SYS + switches CLK_SYS to PLL output sees
   the emulator speed up to 150 MHz
4. Firmware that does NOT configure clocks (our blinky) runs at whatever
   the bootrom left — producing a visible blink rate
5. The showcase app's pacer adjusts in real-time when clock speed changes

## 3. What We're NOT Modelling

- **Analog startup delays.** XOSC takes ~1ms to stabilise on real hardware;
  PLL takes ~100μs to lock. We report stable/locked immediately (existing
  behaviour). Modelling startup delays is Phase 8+ territory.
- **ROSC frequency variation.** Real ROSC drifts with temperature/voltage.
  We use a fixed 6.5 MHz constant.
- **Fractional CLK_SYS divider.** The integer part is sufficient for all
  standard SDK configurations. Fractional part is stored but ignored.
- **CLK_PERI, CLK_USB, CLK_ADC, CLK_RTC.** Only CLK_REF and CLK_SYS
  matter for CPU execution speed. Other clock domains are orthogonal.
- **Glitchless mux sequencing.** On real hardware, CLOCKS has a specific
  mux-switching protocol to avoid glitches. We switch instantly.

## 4. Design

### 4.1. New State: ClockTree

A new struct on `Bus`, computed from register values. Not a new file — it
lives inline in `bus/peripherals.rs` or a small `bus/clocks.rs` if
peripherals.rs gets crowded.

```rust
/// Derived clock tree state. Recomputed whenever CLOCKS, PLL, or XOSC
/// registers change.
struct ClockTree {
    /// Effective system clock frequency in Hz. Drives the pacer.
    sys_clk_hz: u32,
    /// Effective reference clock frequency in Hz.
    ref_clk_hz: u32,
}
```

This is a **cache** — it can always be recomputed from the raw register
state. We recompute it eagerly on every write to a clock-relevant register
rather than lazily on read, because the pacer needs the value every quantum.

### 4.2. Source Frequencies (Constants)

```rust
const ROSC_FREQ_HZ: u32 = 6_500_000;   // ~6.5 MHz nominal
const XOSC_FREQ_HZ: u32 = 12_000_000;  // 12 MHz Pico 2 crystal
```

ROSC is fixed. XOSC could technically vary per board, but every Pico 2
ships with a 12 MHz crystal; making it configurable via `Config` is a
possible future addition but not needed now.

### 4.3. PLL Model

Two PLLs: PLL_SYS (0x40050000) and PLL_USB (0x40058000). Each needs
three registers:

| Offset | Register   | Fields |
|--------|-----------|--------|
| 0x000  | CS        | [31] LOCK (read-only, always 1), [5:0] REFDIV |
| 0x008  | FBDIV_INT | [11:0] feedback divider |
| 0x00C  | PRIM      | [18:16] POSTDIV1, [14:12] POSTDIV2 |

Output frequency:

```
pll_out = (XOSC_FREQ_HZ / refdiv) * fbdiv / (postdiv1 * postdiv2)
```

Default register values at reset: REFDIV=1, FBDIV=0, POSTDIV1=7,
POSTDIV2=7 — PLL output is 0 Hz (no feedback) until configured.

Implementation: add `pll_sys_regs: [u32; 4]` and `pll_usb_regs: [u32; 4]`
backing arrays to Bus (offsets 0x000, 0x004, 0x008, 0x00C; 0x004 is PWR
which we accept writes to but ignore). Read CS always returns stored value
| LOCK bit. On write to any PLL register, call `recompute_clock_tree()`.

```rust
fn pll_output_hz(&self, regs: &[u32; 4]) -> u32 {
    let refdiv  = (regs[0] & 0x3F).max(1);
    let fbdiv   = (regs[2] & 0xFFF).max(1);
    let postdiv1 = ((regs[3] >> 16) & 0x7).max(1);
    let postdiv2 = ((regs[3] >> 12) & 0x7).max(1);
    (XOSC_FREQ_HZ / refdiv) * fbdiv / (postdiv1 * postdiv2)
}
```

### 4.4. CLOCKS Mux Model

Already partially implemented (CLK_REF_CTRL, CLK_SYS_CTRL stored). Extend
with one more register:

| Offset | Register       | Fields |
|--------|---------------|--------|
| 0x030  | CLK_REF_CTRL  | [1:0] SRC (0=ROSC, 2=XOSC), [7:5] AUXSRC |
| 0x038  | CLK_REF_SELECTED | read-only, 1 << src |
| 0x060  | CLK_SYS_CTRL  | [0] SRC (0=clk_ref, 1=aux), [7:5] AUXSRC (0=PLL_SYS, …) |
| 0x064  | CLK_SYS_DIV   | [31:8] INT, [7:0] FRAC (frac ignored) |
| 0x068  | CLK_SYS_SELECTED | read-only, 1 << src |

Add `clk_sys_div: u32` to Bus (default 1 << 8 = integer divider of 1).

Reference clock resolution:

```rust
fn ref_clk_hz(&self) -> u32 {
    match self.clk_ref_ctrl & 0x3 {
        0 => ROSC_FREQ_HZ,
        2 => XOSC_FREQ_HZ,
        1 => {  // aux — CLK_REF_CTRL[7:5]
            match (self.clk_ref_ctrl >> 5) & 0x7 {
                0 => self.pll_output_hz(&self.pll_usb_regs),
                _ => 0,
            }
        }
        _ => ROSC_FREQ_HZ,  // reserved → ROSC
    }
}
```

System clock resolution:

```rust
fn sys_clk_hz(&self) -> u32 {
    let src_hz = match self.clk_sys_ctrl & 0x1 {
        0 => self.ref_clk_hz(),   // clk_ref
        _ => {                    // aux — CLK_SYS_CTRL[7:5]
            match (self.clk_sys_ctrl >> 5) & 0x7 {
                0 => self.pll_output_hz(&self.pll_sys_regs),
                1 => self.pll_output_hz(&self.pll_usb_regs),
                2 => ROSC_FREQ_HZ,
                3 => XOSC_FREQ_HZ,
                _ => 0,
            }
        }
    };
    let int_div = ((self.clk_sys_div >> 8) & 0xFF_FFFF).max(1);
    src_hz / int_div
}
```

### 4.5. Recompute Trigger

`recompute_clock_tree()` is called on every write to:
- CLK_REF_CTRL (0x40010030)
- CLK_SYS_CTRL (0x40010060)
- CLK_SYS_DIV  (0x40010064)
- Any PLL_SYS register (0x40050000-0x4005000C)
- Any PLL_USB register (0x40058000-0x4005800C)

It updates `self.clock_tree.sys_clk_hz` and `self.clock_tree.ref_clk_hz`.

### 4.6. ROSC Stub

Currently not implemented (reads return 0). Add a minimal stub:

| Offset | Register | Value |
|--------|----------|-------|
| 0x018  | STATUS   | (1 << 31) \| (1 << 12) = stable + enabled |

Accept writes to all offsets (CTRL, FREQA, FREQB, etc.) but ignore them.
The bootrom reads ROSC_STATUS to check if it's running. Returning
stable+enabled is sufficient.

### 4.7. Exposing sys_clk_hz to the Emulator

Two options:

**Option A (simple):** `Bus` exposes `pub fn sys_clk_hz(&self) -> u32`
which returns `self.clock_tree.sys_clk_hz`. The sim thread reads this
every quantum.

**Option B (push-based):** Bus sets a `clock_changed: bool` flag on
recompute; sim thread checks the flag and reads the new value only when it
changes. Saves a field read per quantum but adds a flag.

Go with Option A. Reading a u32 field once per quantum (every ~1μs of sim
time) is trivial.

### 4.8. Pacer Adjustment

Add to `Pacer`:

```rust
pub fn update_sys_clk_hz(&mut self, new_hz: u32) {
    if new_hz == self.sys_clk_hz as u32 { return; }
    self.sys_clk_hz = new_hz as u64;
    let nominal = (self.tsc_freq as u128 * self.quantum_cycles as u128
                   / new_hz as u128) as u64;
    self.quantum_tsc_ticks = nominal.saturating_sub(self.overhead);
}
```

The sim thread calls this after each quantum:

```rust
let current_hz = emu.bus.sys_clk_hz();
pacer.update_sys_clk_hz(current_hz);
```

This is ~zero cost when the clock doesn't change (one comparison + early
return).

### 4.9. Config Change

`Config::sys_clk_hz` is **removed** (or ignored). The emulator always
boots at ROSC speed. The clock tree determines the actual speed. This is a
breaking API change for callers that relied on hardcoding 150 MHz — those
callers need to either:

- Configure PLL registers after boot (the SDK way), or
- Accept that the emulator now starts slow

Affected callers:
- `mdrp2354-app` sim thread: already uses `Config::default()` → now starts
  at 6.5 MHz. The Pacer is initialised with `sys_clk_hz` from the bus
  after `emu.reset()`.
- `paced_bench`: writes a tight SRAM loop, doesn't configure clocks. It
  needs to either (a) set up registers for 150 MHz or (b) accept running
  at ROSC speed (the benchmark measures throughput, not absolute speed).
- Unit tests using `Config { sys_clk_hz: 150_000_000 }`: continue to work
  if `Config` retains the field as an initial override. But the clock tree
  will overwrite it on first register access.

**Pragmatic compromise:** keep `Config::sys_clk_hz` as an optional initial
override — if set (non-zero), it determines the boot frequency until the
first CLOCKS register write. If 0 or default, use ROSC. This avoids
breaking existing tests.

Actually, simpler: **default to ROSC_FREQ_HZ** but keep the field so
callers can override. The clock tree recomputes from registers on any
write, so the override only matters before the first CLOCKS access.

```rust
impl Default for Config {
    fn default() -> Self {
        Self { sys_clk_hz: ROSC_FREQ_HZ }  // 6_500_000
    }
}
```

Existing tests that explicitly pass `sys_clk_hz: 150_000_000` still work.
The only change is that `Config::default()` no longer means 150 MHz.

## 5. Reset State

After `Emulator::reset()`:

| Register | Value | Meaning |
|----------|-------|---------|
| CLK_REF_CTRL | 0 | Source = ROSC (bits [1:0] = 0) |
| CLK_SYS_CTRL | 0 | Source = clk_ref (bit 0 = 0) |
| CLK_SYS_DIV  | 0x100 | Integer div = 1, frac = 0 |
| PLL_SYS CS   | 0x01 | REFDIV=1, LOCK forced on read |
| PLL_SYS FBDIV | 0 | No feedback → output = 0 Hz |
| PLL_SYS PRIM | 0x77000 | POSTDIV1=7, POSTDIV2=7 |
| PLL_USB (same) | same | Same defaults |

Effective boot frequency: CLK_SYS → CLK_REF → ROSC = **6.5 MHz**.

## 6. What Happens for Each Firmware

### Blinky (no clock setup)

Bootrom runs → may switch CLK_REF to XOSC (12 MHz) → jumps to user code.
Blinky's delay loop: 500K × 2 cycles / 12 MHz ≈ 83ms per toggle ≈ 6 Hz.
If bootrom stays on ROSC: 500K × 2 / 6.5M ≈ 154ms → 3 Hz. Both are
visibly blinking. We'll discover which one empirically.

### LCD demo / Benchmark (no clock setup)

Same boot path. LCD demo runs slower but still refreshes the display many
times per second. Benchmark runs at boot speed — cycle counts are the same
(cycle counting doesn't depend on wall-clock rate), but wall time is longer.
The showcase app's integration tests measure cycles, not wall time, so they
pass regardless of clock speed.

### SDK firmware (configures PLL)

SDK `runtime_init` writes: XOSC enable → wait stable → PLL_SYS config
(FBDIV=125, REFDIV=1, POSTDIV1=5, POSTDIV2=2) → wait lock → switch
CLK_SYS to PLL_SYS. Our recompute fires on each CLOCKS write; sys_clk_hz
jumps to 150 MHz. The pacer adjusts the same quantum. Emulator runs at
150 MHz from that point.

## 8. Tests

1. **Unit test: PLL output calculation.** Write PLL_SYS registers for
   (FBDIV=125, REFDIV=1, POSTDIV1=5, POSTDIV2=2), assert
   `bus.sys_clk_hz() == 150_000_000` after switching CLK_SYS to PLL_SYS.

2. **Unit test: boot defaults.** Fresh `Bus::new()`, assert
   `bus.sys_clk_hz() == ROSC_FREQ_HZ`.

3. **Unit test: CLK_SYS divider.** Configure PLL for 150 MHz, set
   CLK_SYS_DIV to 2 (integer), assert `bus.sys_clk_hz() == 75_000_000`.

4. **Unit test: CLK_REF source switching.** Write CLK_REF_CTRL=2 (XOSC),
   CLK_SYS on clk_ref, assert `bus.sys_clk_hz() == XOSC_FREQ_HZ`.

5. **Integration test: blinky blink rate.** Run blinky for N cycles, count
   GPIO 25 toggles. At ROSC speed (~6.5 MHz), 500K iterations per toggle
   = 1M cycles per toggle. Running 10M cycles should produce ~10 toggles.
   At 150 MHz (old behaviour) it would produce ~10 toggles too — the
   *cycle count* per toggle is the same. The difference is wall time, not
   cycle count. So the test verifies cycle-accurate GPIO toggling, and the
   pacer handles wall-time fidelity.

6. **Existing tests:** `test_clocks_source_tracking` continues to pass.
   Tests that use `Config { sys_clk_hz: 150_000_000 }` explicitly are
   unaffected. Tests using `Config::default()` now get 6.5 MHz — verify
   none break.

## 9. Risks

1. **Bootrom clock init sequence is unknown.** We don't know exactly which
   registers the bootrom writes. If it writes CLOCKS registers we don't
   handle, sys_clk_hz may compute incorrectly. Mitigation: run blinky
   after the change, trace `sys_clk_hz()` at each CLOCKS write, compare
   against expected boot sequence.

2. **`Config::default()` change breaks callers.** Any code expecting
   default = 150 MHz will now get 6.5 MHz. Mitigation: grep for
   `Config::default()` usage and verify each caller. The showcase app
   and paced_bench are the only two.

3. **PLL divider arithmetic overflow.** `(XOSC / refdiv) * fbdiv` could
   overflow u32 for large fbdiv values. Mitigation: use u64 intermediate,
   cast back. The max realistic value is (12M / 1) * 200 = 2.4B which
   fits in u32, but defensive u64 is cheap.

## 10. Non-Goals

- Accurate ROSC frequency modelling (temperature, voltage, trim)
- PLL startup timing (lock time simulation)
- XOSC startup timing (crystal oscillation ramp)
- Clock domains other than CLK_REF and CLK_SYS
- Power management (sleep modes, clock gating)
- ROSC frequency tuning via FREQA/FREQB registers
