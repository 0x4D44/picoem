# HLD: Emulator Showcase App

**Version:** 0.1.0 (DRAFT)
**Date:** 2026-04-13
**Scope:** A terminal dashboard that runs firmware on the emulator and shows off fidelity against real RP2350 hardware.

## 1. Problem

Today the emulator has no face. Every proof it works lives in test output:
`cargo test`, `qemu_diff`, `probe_diff`, `full_test`. That's fine for CI, but
it's invisible to anyone who wants to *see* the emulator do something.

We want a single command that loads a firmware binary, runs it on the
emulator, and displays a live terminal dashboard showing:

- The emulator actually running (cycles, MHz, PC, core state)
- Simulated external hardware reacting to GPIO / SPI writes (LED, character LCD)
- A benchmark firmware's results, side-by-side with hardcoded numbers from a
  real Pico 2, to demonstrate cycle-accurate fidelity

The point is to turn the emulator from an invisible library into something a
human can watch work.

## 2. Goal

One binary, `mdrp2354-app`, that:

1. Loads a firmware binary (blinky, benchmark, or custom path)
2. Runs the emulator paced at real-time
3. Renders a ratatui dashboard with live stats and simulated devices
4. Exits cleanly on `q` or Ctrl-C

The dashboard is the user-facing surface. Everything else is plumbing.

## 3. What We're NOT Building

- **A GUI.** Terminal only, via ratatui. No winit, no egui, no pixel rendering.
- **A debugger.** Stepping, breakpoints, and register inspection belong in the
  GDB RSP server (`mdrp2354-debug`). This is a *showcase*, not a dev tool.
- **A bitmap display.** The SPI display is a 20x2 character LCD. No pixels.
- **A test harness.** `qemu_diff`, `probe_diff`, `full_test` already exist.
- **Configurable peripherals via flags/env vars.** What is wired up is wired up
  in code. No knobs.
- **Subcommand soup.** One entry point, one positional argument.

## 4. Architecture

### 4.1. New Crate

A new workspace member: `crates/mdrp2354-app`. Binary-only. Depends on:

- `mdrp2354` (core emulator)
- `mdrp2354-periph` (SPI peripheral for LCD snoop)
- `ratatui` + `crossterm` (TUI)
- `anyhow` (error handling, matching other binaries)

No other new dependencies. No audio crates yet (see §9).

### 4.2. Threads

Two threads. That's it.

```
┌────────────────┐     Snapshot     ┌────────────────┐
│  Sim thread    │ ───(RwLock)────> │  UI thread     │
│                │                  │                │
│ - Owns Emulator│                  │ - ratatui loop │
│ - Paced run    │                  │ - Reads snap   │
│ - Observes     │                  │ - Draws panels │
│   peripherals  │                  │ - Reads kbd    │
└────────────────┘                  └────────────────┘
```

**Sim thread** owns the `Emulator`. In a loop:

1. Step the emulator forward by ~1ms worth of cycles (using the existing
   Pacer, the same pattern `paced_bench` uses).
2. Read peripheral state (GPIO out, SPI TX FIFO, benchmark result region).
3. Update a shared `Snapshot` struct via `Arc<RwLock<Snapshot>>`.
4. Check a shutdown flag; if set, exit.

**UI thread** is the main thread. In a loop:

1. Read the latest `Snapshot`.
2. Draw the dashboard.
3. Poll crossterm events; `q` or Ctrl-C sets the shutdown flag and breaks.

The emulator is never touched from the UI thread. The sim thread writes the
snapshot under the lock; the UI thread reads it. That's the whole
synchronisation story.

Arthur's "peripherals run in a separate thread" intent is honoured: the sim
thread drives the emulator, the UI thread renders observed peripheral state.
Neither the LED nor the LCD feeds anything back into emulation — they are
pure observers, so they cannot perturb timing.

### 4.3. Snapshot

The snapshot is a plain struct, written by the sim thread under the lock:

```rust
struct Snapshot {
    // Emulator state
    cycles:        u64,
    wall_ms:       u64,
    effective_mhz: f64,
    pc:            u32,
    halted:        bool,

    // GPIO / LED
    gpio_out: u32,
    gpio_oe:  u32,

    // SPI character LCD (20 cols x 2 rows)
    lcd: LcdState,

    // Benchmark results (None until firmware signals done)
    benchmark: Option<BenchmarkReport>,
}
```

Writes are short (copy a handful of fields) so RwLock contention is
negligible. No channels, no lock-free ring buffers. Simple.

## 5. Simulated External Devices

### 5.1. LED

Reading `gpio_out` bit 25 (or whichever pin the current firmware uses) is
enough. The UI renders it as a filled/empty block in the GPIO panel.

No state of its own. No thread of its own. A rendering of a bit.

### 5.2. Character LCD (20x2, SPI)

The sim thread snoops the SPI peripheral's TX FIFO each tick. Bytes it finds
there are fed through an `LcdState` state machine owned by the sim thread,
which holds the 20x2 character grid plus cursor position.

**Wire protocol** (simplest thing that works, firmware and model both ours):

| First byte | Meaning | Following bytes |
|---|---|---|
| `0x01` | Clear + home | — |
| `0x02` | Set cursor | col, row |
| All others | Character | — (cursor auto-advances, wraps, scrolls) |

That's the whole protocol. If it proves awkward we can extend it; we're not
emulating a real HD44780 here.

**How the snoop works:** the SPI peripheral already has a TX FIFO backed by
a bus-visible register. The sim thread drains whatever the firmware pushed
into it since the last tick. The SPI peripheral itself doesn't change — this
is a read-only observer. Exact hook point is LLD territory; the peripheral
module may already expose a `take_tx_bytes()` helper or we may need to add
one. Either way, no emulator-core changes.

## 6. Benchmark Firmware

A new firmware binary: `roms/benchmark.bin`. It's a Cortex-M33 program
(thumbv8m.main-none-eabihf, compiled from a small Rust or C source, TBD in
LLD) that:

1. Runs a suite of microbenchmark sections, each timing itself via DWT CYCCNT.
2. Writes results into a `BenchmarkReport` struct at a known SRAM address
   (e.g. `0x2003_FF00`).
3. Executes BKPT (or sets a sentinel field to indicate "done").

The sim thread polls that SRAM address; when the sentinel is set, it copies
the results into the snapshot.

### 6.1. Benchmark Sections (initial set)

| Section | What it measures | Why it's interesting |
|---|---|---|
| Arithmetic | ADD, SUB, MUL, SDIV/UDIV cycles | Shows multi-cycle divide modelled correctly |
| Memory | Sequential + strided loads/stores | Exercises the SRAM bank conflict model |
| Branches | Tight loop forward / backward, cond | Validates fetch + branch penalty |
| Bit manipulation | CLZ, RBIT, REV, BFI/BFX | M33-specific single-cycle ops |
| Multi-cycle | LDM/STM with 4/8/12 regs | Easy to get cycle count wrong |

Exact iteration counts and code fragments are LLD-level detail. The list
itself is cheap to extend later.

### 6.2. Reference Numbers

Hardcoded in `mdrp2354-app` as a static table:

```rust
const RP2350_REFERENCE: &[BenchmarkReference] = &[
    BenchmarkReference { name: "arith_add",   cycles: 100_000, ... },
    // ...
];
```

These come from running the same firmware on a real Pico 2 via `probe-rs`
before we ship. Captured once, checked into the repo.

The dashboard shows `real | emu | Δ` for each row, ideally all zero.

### 6.3. Instruction Cycle Stats Panel

Independent of the benchmark firmware: a static panel listing interesting
instruction classes and their cycle counts, drawn from the emulator's own
cycle table. No runtime behaviour — just proof-of-work that we have a table
to show.

## 7. CLI

```
mdrp2354-app [FIRMWARE]
```

`FIRMWARE` is one of:

- `blinky` (default) — loads `roms/blinky.bin`
- `benchmark` — loads `roms/benchmark.bin`
- `lcd` — loads `roms/lcd-demo.bin` (writes text to the SPI LCD)
- Any other value is treated as a path to a `.bin` file

No other flags. Not `--help`, not `--version`, not `--log-level`. If we need
those later we can add them. Not today.

## 8. Phased Build Order

This is a plan, not a hard gate list. Each phase ends with something running.

### Phase 1 — Skeleton

1. New crate `mdrp2354-app` with ratatui + crossterm + anyhow.
2. Sim thread owning an `Emulator`, running blinky paced.
3. UI thread with a single panel: cycles, MHz, PC, GPIO out bit 25 as LED.
4. `q` exits.

Ship criterion: `cargo run -p mdrp2354-app` runs blinky, the LED blinks in
the terminal.

### Phase 2 — LCD

1. Add `LcdState` and the SPI snoop hook in the sim thread.
2. New LCD panel in the dashboard.
3. New `roms/lcd-demo.bin` firmware that scrolls a message across 2 rows.
4. `mdrp2354-app lcd` loads it.

Ship criterion: dashboard shows scrolling text under blinky's LED.

### Phase 3 — Benchmark

1. Write benchmark firmware, get it booting on real hardware, capture
   reference numbers.
2. Add benchmark panel + reference table.
3. Add instruction cycle stats panel (static data).
4. `mdrp2354-app benchmark` loads it, dashboard shows side-by-side results.

Ship criterion: benchmark panel's Δ column is all zero.

Phases 1-3 are the HLD scope. Later phases are §9.

## 9. Out of Scope (for now)

- **DAC audio output.** Plumbing for a third thread feeding `cpal` from the
  emulator's DAC FIFO. Interesting, not urgent. The current architecture has
  room: add a `dac_samples: Ringbuf<f32>` field to the snapshot, spawn an
  audio thread when firmware uses the DAC. Deferred.
- **Bitmap SPI displays** (ST7789, ILI9341). Character LCD is enough to
  demonstrate SPI observation. Defer until there's a real reason.
- **Multiple firmwares running in sequence** (e.g. "boot test → benchmark →
  LCD demo"). One firmware per invocation is simpler.
- **Config files.** No.
- **Dumping snapshots to disk for replay.** No.

## 10. Risks

1. **SPI peripheral may not expose a clean observer hook yet.** Mitigation:
   check during LLD; if it doesn't, adding `take_tx_bytes()` to the SPI
   peripheral is a small, local change. Worst case the snoop reads the TX
   data register directly at a known MMIO offset.
2. **Real RP2350 reference numbers are fiddly to capture reproducibly.**
   Mitigation: write the capture procedure down next to the reference table
   (comment in source) so it can be re-run if the firmware changes. Reference
   numbers are static data, not generated at build time.
3. **Pacer drift under TUI load.** The UI thread shouldn't be heavy, but if
   ratatui's redraw rate eats a core the sim thread can lag. Mitigation:
   cap UI to ~30 fps. Easy.
4. **"It looks boring."** The bar for "looks cool in a terminal" is lower
   than "looks cool in a GUI", but it's not zero. Mitigation: focus polish
   on the one panel that carries the message — the benchmark comparison
   table with all-zero deltas. That's the screenshot.

## 11. Success Criteria

- `cargo run -p mdrp2354-app` blinks a simulated LED in under 2 seconds of
  wall time from launch.
- `cargo run -p mdrp2354-app benchmark` shows a side-by-side comparison
  where every Δ is zero.
- `cargo run -p mdrp2354-app lcd` shows live scrolling text driven by SPI
  writes from emulated firmware.
- No changes to the core `mdrp2354` crate. Peripheral crate changes (if any)
  are additive and justified by the snoop hook.
- Total new code in the app crate is under ~1000 lines including the
  benchmark firmware source.
