## Track A.2 HLD — Downstream `WrongApType`

### D1 — Phase 0 trace is being positioned as BLOCKING when a 15-minute inspection can reject one hypothesis outright

**Weakness.** §3.1 says "Phase 0 is BLOCKING, do this first" and §6.1 budgets ~1h
for the trace. But H3 ("cache path inconsistent") can be rejected by inspection
right now. Looking at the patched arm at
`communication_interface.rs:485-496` + the outer `previous_select !=
dp_state.current_select` flush at line 502: the patched arm mutates `cache`
via `*cache = SelectCache::DPv3(...)` **before** `previous_select` is
compared. `previous_select` was captured at line 461 as `DPv1`, and
`current_select` is now `DPv3`, so the guard at line 502 always fires and both
`SelectV3` + `Select1` get written. There is no ordering bug. The A.2 HLD's own
§2 "H3 is unlikely but cheap to rule out" concedes this but then keeps it in
the trace decision table. Drop H3 before asking the lead to sign off.

**Why it matters.** The HLD inflates its hypothesis space, making Phase 0 look
larger than it is. Leaving unproductive hypotheses on the board invites the
implementation agent to chase ghosts.

**Ask.** Delete H3 from the taxonomy and from the §3.1 decision table.
Explicitly call out that H3 was rejected by code inspection and cite lines
485–502.

### D2 — H4 (classifier gap) is inconsistent with the journal's own description of the symptom

**Weakness.** §1.1 correctly derives that `WrongApType` requires `IDR.TYPE`
low-nibble = `0x0` (i.e. `JtagComAp`). H4 says "perhaps the AP genuinely reports
an unknown TYPE". But `ApType::from_u8` returns `None` for unknown TYPE values,
which produces `RegisterParseError`, **not** `WrongApType` — the HLD itself
states this at §1.1 line 59 ("Any value outside that set returns `None`,
producing a `RegisterParseError`"). So H4 cannot produce `WrongApType` unless
the unknown TYPE happens to be exactly `0x0`, which collapses H4 into "the AP
IDR read returned a value with TYPE=0" — which is H1 or H2's payload.

**Why it matters.** H4 is a mis-framed fourth option that pads the taxonomy
without narrowing the search. Removing it sharpens the decision to a
binary (hybrid-DP vs transient-first-read).

**Ask.** Either reformulate H4 as "the IDR read is legitimate and returns
TYPE=0 genuinely because Raspberry Pi wired a non-standard AP class" — which
is a concrete testable thesis distinct from H1/H2 — OR drop H4. The current
wording conflates two distinct failure modes.

### D3 — "Keep the Track A `(V2, DPv1)` arm as defence-in-depth" is feel-good reasoning

**Weakness.** §5 and §8 both recommend keeping the Track A patched arm no
matter which hypothesis wins. But consider the possible worlds:

- If H1 (hybrid DP, RP2354 really is DPv2): the Track A arm is **actively
  harmful** — it forces DPv3 SELECT encoding on a target whose DP only
  understands DPv2 SELECT semantics. We get `SelectV3(0x209)` written which
  a DPv2 DP will parse as `APSEL=0x00, APBANKSEL=0x9`, which is then the
  actual cause of the downstream `WrongApType`. The defence-in-depth arm IS
  the bug.
- If H2 (transient): once the retry-DPIDR fix lands in `select_dp`, the cache
  will already be promoted to DPv3 by the time `select_ap_and_ap_bank` runs,
  so the Track A arm is dead code. Dead code is not defence-in-depth; it's
  dead code.
- If H4 (classifier): same as H2 — the Track A arm never fires after the fix.

So the Track A arm is either harmful or unused. "Defence-in-depth" is not a
virtue when the thing you're defending against either doesn't exist or is
something you caused.

**Why it matters.** This is exactly the "don't predict the future" warning
from CLAUDE.md — carrying two workarounds when one correct fix obviates the
first. The Track A arm was pragmatic when the panic was unexplained; now
that we understand more, keeping it is premature abstraction.

**Ask.** Add a §5a explicitly: if H1 or H2 is confirmed, the Track A arm
becomes a candidate for *removal* in the same commit, not preservation.
Quantify the test coverage needed to confirm removal is safe (should just be
§6.3's 8-item suite).

### D4 — "Revert Track A" (Option C) is rejected too breezily

**Weakness.** §4 Option C is rejected in three sentences with "reverting would
re-introduce the panic". But the real choice is **"replace the Track A arm
with an H1-shaped or H2-shaped fix in the same edit"**, not a naked revert.
The patched arm's only measurable win today is keeping `probe_diff_rp2350`'s
4000/4000 — but that path, per the 2026.04.21 HLD §3.5, succeeds because
"the initial DPIDR read happens to succeed on most fresh-from-power-up
attach attempts", i.e. the sentinel WARN never actually fires on that binary.
An H2-shaped fix (retry DPIDR) would *also* keep that path working because
the first read already works most of the time.

**Why it matters.** The HLD presents the choice as "add an A.2 patch" versus
"roll back and do nothing". The real choice is "add A.2 and *rewrite* the
Track A arm into a cleaner, more correct fix". That option is not even in
the option list.

**Ask.** Add Option A-prime: "Replace the Track A `(V2, DPv1)` arm with the
H1 or H2 fix in one edit, keeping a single well-designed workaround rather
than two bolted together." Evaluate it against Option A.

### D5 — Plan agent's "can't pick H1 vs H2 from inspection alone" is underselling available evidence

**Weakness.** The journal note on 2026-04-22 plan returns says the A.2 HLD
is "honest that it cannot pick H1 vs H2 from inspection alone". But:

1. The 2026.04.21 Track A hardware validation note already observes that
   `probe_diff_rp2350 --fuzz 4000` passes 400/400, and the previous HLD's
   §3.5 explains that path reaches steady-state DPv3 after one attach. If
   DPIDR returned DPv2 *permanently* (H1), `probe_diff_rp2350`'s `read_word`
   / `write_core_reg` calls would ALSO be addressing V2 APs against a
   DPv1-encoded SELECT and would fail the same way. They don't. That's
   evidence *against* H1.
2. The sentinel fires exactly once per session per the journal. If the DP
   were genuinely DPv2, no recovery would change the SELECT semantics, and
   we would expect repeat failures across the `reset_and_halt` churn on
   `silicon_periph_diff_rp2350`. The once-per-session firing is more
   consistent with H2's "first-read transient" story.

This doesn't prove H2, but it meaningfully lowers H1's prior. The HLD should
say so.

**Why it matters.** An HLD that says "we can't pick H1 vs H2" when one piece
of already-observed evidence discriminates between them is either unaware of
that evidence or downplaying it to justify more investigation. Either way,
the lead should press on it.

**Ask.** Add to §2.5 (ranking): cite the `probe_diff_rp2350` 4000/4000 observation
and explain why it down-weights H1. Revise the prior ranking.

### D6 — §6.3 test plan item 6 is a no-op

**Weakness.** "Regression check: `probe_diff_rp2040 --fuzz 1000` must remain
unchanged". But the A.1 HLD says RP2040 attach is broken — the binary can't
even start. So this regression check currently is "binary fails before the
patch; binary fails after the patch". That's not a meaningful regression
signal for A.2.

**Why it matters.** Either the A.2 implementation agent wastes time running
this, or they skip it and we lose a genuine regression-check slot. The HLD
should either remove the item or note explicitly "skip until Track A.1
lands".

**Ask.** Change item 6 to: "After Track A.1 lands, re-run `probe_diff_rp2040
--fuzz 1000`; until then, skipped".

### D7 — "Sentinel WARN firing ≤1 per re-attach cycle" during 30-min soak is not well-defined

**Weakness.** §6.3 item 8 says the 30-min soak must show sentinel firing "≤1
per re-attach cycle". But `test_silicon --soak` does per-case drop-and-reattach
on transient errors. Each reattach creates a fresh `Session`, which means fresh
`DpState`, which means fresh DPIDR read — so yes, the sentinel fires once per
reattach cycle, potentially many times per soak. Is that PASS or FAIL? The
acceptance criterion isn't crisp.

**Why it matters.** A 30-min soak is expensive hardware time. If the acceptance
criterion is ambiguous, the implementation agent may land a patch that either
looks like a regression (many firings on a long run where there are many
reattaches) or looks like a pass (fewer firings because the orchestrator
masks transient errors). Without a testable definition, the soak is
theater.

**Ask.** Rewrite the acceptance criterion in terms of what the sentinel fires
*per Session::auto_attach call*, not per "session" or "cycle". Count
`auto_attach` calls and match against sentinel count. Or remove the soak
criterion altogether and replace with "no panic, no regression in
9-oracle-per-pass PASS rate".

### D8 — Option A has four divergent sub-variants; recommendation is not actually a recommendation

**Weakness.** §5 says "Option A, gated on Phase 0 trace results" and then
lists four *different* fixes keyed to H1/H2/H3/H4. That's not a
recommendation; it's a decision tree dressed up as one. The HLD asks the
lead to sign off on an option whose concrete shape will only be known after
another agent runs a trace. This is the opposite of plan-then-dispatch.

**Why it matters.** Sign-off means "this is what we're going to build". If
the build depends on a Phase 0 result not yet collected, sign-off is
premature. Either collect the trace first (a 1-hour wetware step) and bring
a properly-specified HLD back to the lead, or sign off on Phase 0 *only* and
hand back the follow-on HLD once data is in.

**Ask.** Split the HLD into A.2a (Phase 0 trace + analysis — lead signs off
on the scoped investigation) and A.2b (the actual patch — written after
Phase 0 data, signed off separately). This matches the 2026.04.21 Track A
flow (HLD → signed → patch) and preserves the discipline.

### D18 — ADIv6 §B2 citation is unverified and load-bearing

**Weakness.** §"Why this is the right shape" claims "ADIv6 (§B2) defines
the V2 AP address format, and it is only accessible via a DPv3 debug
port." This is a load-bearing justification — it's the argument for why
`(V2, DPv1)` is impossible and thus why the cache upgrade is correct. If
§B2 doesn't actually say this, an upstream maintainer will push back.
Neither the Plan agent nor I have read the ARM ADIv6 spec to verify.
We know from reading probe-rs code (`communication_interface.rs:285`) that
DPv0/DPv1/DPv2 all route through V1-AP enumeration and DPv3 uses V2 AP
enumeration; that's a probe-rs-side decision, not necessarily an
architecture-spec one.

**Why it matters.** A maintainer who has the spec open will either confirm
our claim (great, PR lands) or demolish it (embarrassing, PR bounces).
Citing a spec section you haven't read is worse than citing a working
implementation.

**Ask.** Replace the "ADIv6 (§B2)" citation with a *probe-rs internal*
justification: "In probe-rs's own
`ArmCommunicationInterface::enumerate_access_ports` dispatch at
`communication_interface.rs:285–289`, V2 AP enumeration is only reachable
via `DebugPortVersion::DPv3`; all of DPv0/DPv1/DPv2 route through V1-AP
enumeration. Therefore any caller that *has* constructed a V2 AP address
expects a DPv3 DP." That's checkable in-tree, self-consistent, and
doesn't depend on the spec.

### D19 — Changelog fragment should be a separate *file*, not an embedded blockquote

**Why it matters.** This is a mechanical submission-format issue. It's
trivial to fix and trivial to get wrong. Maintainers will bounce it in
CI or review if the fragment file is missing from the diff.

**Ask.** Change the "Changelog" section to: "A `changelog/fixed-v2-ap-dpv1-recovery.md`
fragment is included in this PR's diff per `CONTRIBUTING.md`; see the
Files Changed tab." Remove the inline blockquote text (or keep it but
make clear it's a *copy* of the fragment's content, not a substitute for
the file).
