# RP2350 Coverage Gap Fill — HLD V1

**Date:** 2026-04-17
**Companion audit:** `wrk_docs/2026.04.16 - HLD - RP2350 Feature Coverage Audit.md`
**Scope:** the "clear work" bucket from the follow-up discussion on the audit —
finite, estimable gaps with well-understood shapes. Does **not** cover the
structural items (security enforcement, cycle-model deltas, bootrom execution,
RISC-V Hazard3). Those get their own HLDs.

## 1. Problem

The audit surfaced four classes of finite gap:

1. **Silent inert-register reads/writes** — any unmodelled MMIO address quietly
   hits the `HashMap<u32, u32>` fallthrough (`bus/mod.rs:231`). The emulator
   acts as if the peripheral were a passive memory, which hides bugs.
2. **One known wrong-address bug** — TICKS at offset `0x81C` (aliased form)
   silently drops writes. One failing silicon scenario.
3. **Interpolator dead storage** — `sio/mod.rs:45` is `[[u32; 32]; 2]` with no
   CTRL semantics.
4. **Missing peripherals** — roughly a dozen register blocks with no model.

## 2. Non-goals

- No migration path for existing code. The emulator is a dev-stage sandbox and
  there is no external consumer that requires source-compat.
- No environment-variable toggles. No feature flags.
- No security enforcement (SAU/MPU/ACCESSCTRL gating memory accesses). Separate
  HLD.
- No bootrom execution.
- No RISC-V Hazard3.
- No cycle-model fixes.
- No "framework" for peripheral modelling — the existing `peripherals/mod.rs`
  inherent-methods convention is already adequate; new peripherals follow it.
- No trait-ification of peripheral dispatch. The workspace explicitly decided
  against this (see `peripherals/mod.rs` §"Inherent-methods convention").

## 3. Approach at a glance

One design principle across all parts: **match the existing idiom, add nothing
new**. Every new peripheral is a plain struct with inherent `read32`/`write32`
methods, instantiated on `Bus`, dispatched from a new match arm in
`Bus::read32` / `Bus::write32`. Register storage uses `apply_alias_rmw` for
APB aliases. No traits. No generic abstractions.

## 4. Part A — Inert-register observability (half a day)

### A.1 Warn-once on HashMap fallthrough

**Change:** in `Bus::read32` and `Bus::write32`, when the access falls through
to `peripheral_regs`, emit a single `tracing::warn!` per unique word-aligned
address for the lifetime of the `Bus`.

**Implementation:**

```rust
// Bus struct
warned_addrs: std::collections::HashSet<u32>,

// In the fallthrough arms in read32 / write32:
if self.warned_addrs.insert(word_addr) {
    tracing::warn!(
        addr = format_args!("{:#010X}", word_addr),
        pc = format_args!("{:#010X}", self.last_fetch_pc),
        "unmodelled MMIO access"
    );
}
```

**Why a HashSet rather than rate-limit counter:** first-touch is the
actionable signal. Subsequent touches of the same address are noise. Test
runs never produce enough unique unmodelled addresses for the set to matter
for memory.

**Why not `error!`:** firmware hitting an unmodelled address is not emulator
failure — it is a coverage gap. `warn!` is the correct level per the tracing
guide.

**Tracking `pc`:** the bus does not today carry the fetching core's PC into
the access path. Add a single `pub last_fetch_pc: u32` field on `Bus` that
each core updates in its fetch path, and consume it in the warn payload.
(Alternative: don't include PC; simpler, less useful for debugging.
Recommendation: include it.)

**Testing:** one unit test writes to `0x4010_0000` (unmodelled sample) and
asserts the tracing subscriber sees exactly one warn for that address, and
zero on the second write.

### A.2 TICKS `0x81C` alias bug

`peripherals/ticks.rs` rejects writes to any offset outside its canonical
domain stride. RP2350 silicon masks the low 14 bits for APB alias decode;
offset `0x81C` is alias-2 (BITSET) of `0x01C`.

**Change:** at the top of `TicksRegs::read32` / `write32`, mask `offset`
against the 14-bit APB alias form before the stride match. This mirrors how
the other peripherals handle aliases via `Bus::write32`'s alias extraction —
the bug is that TICKS re-inspected the raw offset instead of the normalised
one.

**Testing:** enable the existing `ticks_timer0_retarget_halves_rate` silicon
scenario; confirm it passes. No new scenario required.

## 5. Part B — Interpolator CTRL semantics (2–3 days)

### B.1 What is there now

`crates/mdrp2350/src/sio/mod.rs:45` holds `interp: [[u32; 32]; 2]`. Writes
store the word; reads return it. Three unit tests exercise round-trip only.

### B.2 What the datasheet says

Datasheet §2.7 (ARM SDK `hardware/interp.h` confirms) — two interpolators
per core, each with:

- Two lanes (LANE0, LANE1). Each lane has ACCUM, BASE, CTRL_LANE.
- A shared BASE2, plus POP_LANE0 / POP_LANE1 / POP_FULL / PEEK_LANE0 /
  PEEK_LANE1 / PEEK_FULL results.
- Per-lane CTRL bits: SHIFT (5b), MASK_LSB (5b), MASK_MSB (5b), SIGNED,
  CROSS_INPUT, CROSS_RESULT, ADD_RAW, FORCE_MSB (2b), BLEND (interp0 only),
  CLAMP (interp1 only), OVERF0/OVERF1/OVERF (RO on CTRL_LANE0 of both).
- Writing ACCUMn sets ACCUMn. Writing BASEn sets BASEn. Reading PEEKn
  returns the computed result; reading POPn returns the result and also
  updates ACCUMn with (raw | ADD_RAW-gated).

### B.3 Design

Single module: `crates/mdrp2350/src/sio/interp.rs`. Struct `Interp` with
explicit `accum[2]`, `base[3]`, `ctrl_lane[2]`. Two instances per core, held
in the `Sio` struct (replacing `[[u32; 32]; 2]`).

Dispatch is inherent-methods, matching the existing peripheral convention.
The SIO module already dispatches interp offsets (`sio/mod.rs:107`/`:148`);
swap those arms for calls to `self.interp[idx].read(offset)` /
`.write(offset, val)`.

**Correctness oracle:** add scenarios to `silicon_scenarios.rs` that cover:
- linear-interpolation mode (BASE0/BASE1 + ACCUM0 shift/mask, POP_FULL)
- BLEND mode on interp0
- CLAMP mode on interp1
- CROSS_INPUT / CROSS_RESULT

Six scenarios total, one per CTRL feature combination the SDK uses. If the
scenario set is ever reduced, these are load-bearing.

### B.4 Non-goal

Cycle accuracy for interp ops — silicon interp operations take a single
cycle; our emulator bills them as a regular MMIO access, which is close
enough. If the cycle oracle surfaces a delta, fix then.

## 6. Part C — Duplicate peripheral instances (1–2 days total)

RP2350 has UART0/UART1, SPI0/SPI1, I2C0/I2C1 on distinct APB bases.
`peripherals/uart.rs`, `spi.rs`, `i2c.rs` each model a single instance
today with the base address baked into the module.

**Change:** hoist the base address out. Each peripheral module exposes:
- `UART0_BASE`, `UART1_BASE` constants
- `Uart` struct that no longer encodes its own base
- `Bus` holds `uart: [Uart; 2]`
- dispatch: match on `(addr & !0xFFF)` against the two bases, index into the
  array

No trait. No generic. Just an array of two. Same pattern for SPI and I2C.

**DREQs / IRQs:** each peripheral already emits a DREQ index and raises an
IRQ line. The second instance uses the RP2350-documented second set
(`UART1_IRQ`, `DREQ_UART1_TX`, etc. — these exist as constants in `dreq.rs`
and `irq.rs`).

**Testing:** duplicate each existing scenario (`uart0_tx_single_byte`, etc.)
for the `_1` instance. No new test logic, just the second address.

## 7. Part D — Simple peripherals (each ~1–3 days)

For each peripheral below, the design is: one file under
`crates/mdrp2350/src/peripherals/`, base-address const, struct with
storage-backed registers + the one or two side effects the datasheet
specifies, inherent `read32`/`write32`, `Bus` field + match arm, at least
one silicon scenario if the feature is silicon-observable.

### D.1 SYSCFG

Storage-only. One register that matters: `PROC_CONFIG` reports core running
states. Back it with a `Bus`-observable "core alive" bitmap if we do
anything; else plain storage.

### D.2 TBMAN

Storage-only. RP2350 test-bus manager is inert in normal operation. Model
as HashMap replacement: dedicated struct, no side effects.

### D.3 PSM

Power State Machine — on-state bitmap per subsystem. Model `FRCE_ON`,
`FRCE_OFF`, `WDSEL`, `DONE` as plain storage, with `DONE` mirroring
`FRCE_ON` (matches "instant" RESETS handshake in `bus/peripherals.rs`).
Firmware that polls `DONE` progresses.

### D.4 WATCHDOG

Countdown driven by TICKS WATCHDOG domain (already exists,
`DOMAIN_WATCHDOG = 4`). Registers: `CTRL` (ENABLE, PAUSE_*, TRIGGER), `LOAD`,
`REASON`, `SCRATCH0..7`, `TICK` (legacy alias to TICKS for RP2040 compat —
probably unused on RP2350 firmware but model as RO mirror).

**Side effect that matters:** when countdown reaches 0 and ENABLE=1, force a
system reset. Reset path for the emulator is "reseed state and jump PC to
vector table entry 0". Wire through `Bus::request_watchdog_reset()` that the
CPU step polls.

Scenario: program a short countdown, advance the cycle budget, verify
SCRATCH survives and PC is back at the reset vector.

### D.5 GLITCH_DETECTOR

Storage plus one field: `STATUS.ARM` is RO, forced to 0 because emulator
cannot glitch. `TRIG_STATUS` clears on W1C. No other observable behaviour.
Firmware that checks it sees "nominal". Matches what silicon looks like in
a glitch-free lab.

### D.6 OTP (storage-only)

Full OTP modelling is a separate HLD (signed-boot, fuse integrity, lockout
semantics). For this wave: OTP_DATA aperture as a plain 16 KB backing store
with the "already programmed" semantic (write-once-per-bit: OR-only). Read
path returns stored value. Load initial fuse state from an optional bytes
slice passed to the emulator builder. No lockout enforcement, no
unlock-dance registers — firmware that reads OTP sees a consistent fuse
bank; firmware that writes sees OR semantics.

Intentional limitation: `SBPI` serial-bus-programming-interface sequencing
not modelled. The `OTP_DATA_RAW_*` SBPI command registers are storage-only.

### D.7 TRNG

Backed by a seeded `rand_chacha::ChaCha20Rng`. The seed is fixed at
`Bus::new` so runs are deterministic. `RNG_OUT` reads advance the RNG.
Status bits (`READY` etc.) are always "ready" — we never block.

Intentional limitation: real TRNG is non-deterministic. Tests that want
randomness should test the interface, not statistical properties. If a
deterministic seed becomes load-bearing for a differential oracle, we
revisit then.

### D.8 SHA-256

Use the `sha2` crate. Registers: `CSR` (WDATA count, err, sum_valid), 16
`WDATA` slots, 8 `SUM0..7` output slots. On the 16th `WDATA` write,
finalise a block; on `CSR.START` (if it exists per datasheet) clear the
accumulator. Read `SUMn` for the digest.

Intentional limitation: DMA path to SHA-256 via DREQ is declared but
peripheral-driver code today does not emit it — the DMA work is separate.

## 8. Part E — Medium peripherals (each ~3–5 days)

### E.1 POWMAN

RP2350 power-management block. Three sub-areas:

1. **AON timer** — 64-bit count, MATCH, trigger IRQ when COUNT == MATCH.
   Advanced by a separate clock domain (LPOSC) — model as "one tick per
   sys_clk / POWMAN_LPOSC_DIV" since we don't separately clock LPOSC.
2. **VREG** — regulator voltage / startup flags. Plain storage, DONE bit
   mirrors FRCE semantics like PSM.
3. **ARCHSEL** — the boot architecture select. This is the register that a
   future RISC-V HLD will care about. For now: plain storage. **Write a
   one-line `warn!` on any write** that changes ARCHSEL away from its
   Arm-default value, because that write means the firmware wants RISC-V
   and we can't honour it. Document in the HLD body.

### E.2 CORESIGHT_TRACE

Storage-only for the `0xE004_1000` register bank. Trace sinks are not
modelled (ETM is missing entirely). Firmware that programs trace will write
configuration and read "no trace available" semantics.

## 9. Explicitly deferred (each warrants its own HLD)

- **USB 1.1 FS controller + PHY.** OTG host/device, endpoint FIFOs, SIE
  state machine. Not "clear work" — weeks of engineering.
- **HSTX (High-Speed Transmit Serialiser).** DMA-integrated DPI/DSI/HDMI
  datapath. Non-trivial datapath modelling + DREQ integration.
- **TMDS encoder in SIO.** Specialised; only meaningful in combination with
  HSTX.

The audit will re-classify these when their HLDs land.

## 10. Landing order

Recommend bottom-up, small diffs:

1. Part A (warn-once + TICKS alias) — observability first so subsequent
   work surfaces its own gaps.
2. Part C (UART1/SPI1/I2C1 instances) — simplest, uses existing modelled
   peripherals.
3. Part D.1–D.3 (SYSCFG, TBMAN, PSM) — storage-only, small.
4. Part D.4 (WATCHDOG) — needs reset-request plumbing; test before crypto.
5. Part D.5–D.8 (GLITCH_DETECTOR, OTP, TRNG, SHA-256).
6. Part B (Interpolators) — larger diff, wants its own review pass.
7. Part E.1 (POWMAN) — biggest of the medium peripherals.
8. Part E.2 (CORESIGHT_TRACE) — storage wrap-up.

Each lands as its own commit with its own tests. No "big-bang" PR.

## 11. Testing strategy

- **Unit tests per peripheral:** register round-trip, reset state, any
  side-effect specific to that peripheral (WATCHDOG reset, interp blend,
  SHA block boundary).
- **Silicon scenarios** in `silicon_scenarios.rs`: add one minimal scenario
  per peripheral where silicon-observable. Target: coverage scales with the
  module count.
- **Part A warn-trace test** uses `tracing_subscriber::fmt::test` or the
  `tracing-test` crate (pick whichever matches existing test idiom; grep
  `tracing` in `mdrp2350/tests.rs` first).
- **Interpolator scenarios** (six) are load-bearing for the claim that
  interp is modelled. These are the gate.

## 12. Risks

- **Interp scenarios need a real-hardware reference** to calibrate
  expected bits — the datasheet's textual description is subtle. Plan a
  short silicon-capture session (program interp, read POP results) before
  committing to expected values in the oracle.
- **WATCHDOG reset semantics** for the emulator reset path need to be
  defined precisely — which registers survive, which revert. Consult
  datasheet §4.5 before coding.
- **OTP storage ordering** — real silicon fuses are 24-bit ECC-protected
  rows. We model as u32 for simplicity; firmware that reads raw ECC bits
  (unusual) will diverge. Acceptable per non-goals.

## 13. What this HLD deliberately does not do

- Does not add a trait for peripherals. The workspace rejected that already.
- Does not introduce env-var / feature-flag configuration of any peripheral.
- Does not preserve backward-compatibility for any code path (dev sandbox).
- Does not attempt to "predict the future" by designing extensibility
  hooks. Each peripheral is concrete; refactor if and when a second
  requirement arrives.
- Does not ship USB, HSTX, or TMDS. Calling those "clear work" in the
  follow-up conversation was too generous; they need their own designs.
