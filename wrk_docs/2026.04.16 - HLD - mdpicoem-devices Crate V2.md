# HLD: mdpicoem-devices Crate (V2)

Date: 2026-04-16
Supersedes: V1

## Changes from V1

- **Dropped `GpioDevice` trait.** Three independent reviewers agreed
  it's premature (one implementor, contradicts `peripherals/mod.rs`
  lines 15-22 which explicitly removed the `Peripheral` trait for the
  same reason). PSRAM stays as a concrete `Option<Psram>` on Bus.
- **Dropped `I2sCapture → I2sDac` rename.** It's a decoder/capture,
  not a DAC. Name stays `I2sCapture`.
- **`picogus_pins.rs` stays in the harness.** Board wiring, not a
  device concern. Devices take pin numbers as constructor params.
- **Added missing callsites:** `Emulator::reset()`, `panels/lcd.rs`,
  `ui.rs`, harness `Cargo.toml` dependency.
- **Fixed false claim** "no new dependencies between existing crates"
  — `mdrp2040` and `mdpicoem-harness` both gain `mdpicoem-devices`.
- **Added `default_out_path()` disposition** — stays in harness.

## Problem

External (off-chip) device models are scattered across three crates:

| Device | Current location | Problem |
|--------|-----------------|---------|
| PSRAM (8 MB SPI) | `mdrp2040::peripherals::psram` | Chip crate contains board-specific hardware |
| LCD decoder | `mdrp2040app::devices::lcd` | Harness can't reuse it |
| I2S capture | `mdpicoem-harness::i2s_capture` | App can't reuse it |

This prevents sharing between app and harness, and mixes board-level
hardware with chip internals.

## Solution

New crate `mdpicoem-devices` for all off-chip device models. No trait
— each device is a concrete struct with its own API. The chip crate
depends on `mdpicoem-devices` for the types it needs to host (PSRAM).

### Why no trait?

PSRAM is the only device that drives GPIO pins back into the emulator.
LCD and I2S are pure observers called from outside the step loop.
A trait with one implementor is abstraction for abstraction's sake —
`peripherals/mod.rs` lines 15-22 already document why this workspace
prefers concrete types over traits for closed device sets. When a
second pin-driving device arrives, extract a trait then with the
benefit of knowing its actual shape.

## Dependency graph

```
mdpicoem-common
    ↑
mdpicoem-devices        ← PSRAM, LCD, I2sCapture
    ↑
mdrp2040                ← Bus holds Option<Psram>
    ↑
mdrp2040app             ← creates Psram, LCD; attaches via builder
mdpicoem-harness        ← creates Psram, I2sCapture; attaches via builder
```

New dependencies: `mdrp2040 → mdpicoem-devices` and
`mdpicoem-harness → mdpicoem-devices`. No circular deps.
`mdpicoem-devices` depends only on `mdpicoem-common` and `std`.

## Bus integration

### PSRAM field (concrete, no trait)

```rust
// mdrp2040::Bus
pub psram: Option<Psram>,   // was: pub psram: Psram
```

When `None`, `update_gpio()` skips the PSRAM tick entirely — zero cost
for emulator configs that don't need PSRAM (QEMU diff, unit tests).

### update_gpio() change

Current (lib.rs:488):
```rust
if let Some(miso) = self.bus.psram.tick(out) {
    let mask = 1u32 << psram::PIN_MISO;
    out = (out & !mask) | ((miso as u32) << psram::PIN_MISO);
}
```

Becomes:
```rust
if let Some(ref mut psram) = self.bus.psram {
    if let Some(miso) = psram.tick(out) {
        let mask = 1u32 << psram.pin_miso();
        out = (out & !mask) | ((miso as u32) << psram.pin_miso());
    }
}
```

### reset() (lib.rs:128)

Current: `self.bus.psram.reset_state();`

Becomes: `if let Some(ref mut psram) = self.bus.psram { psram.reset_state(); }`

### Builder API

```rust
// mdrp2040::EmulatorBuilder
pub fn psram(mut self, psram: Psram) -> Self {
    self.psram = Some(psram);
    self
}
```

## What moves where

### PSRAM (`psram.rs`)

Move from `mdrp2040::peripherals::psram`.

Changes:
- Hardcoded `PIN_*` constants become constructor parameters with
  a `Psram::new(pin_miso, pin_cs, pin_sck, pin_mosi)` constructor.
  Add `Psram::picogus()` convenience constructor with the PicoGUS
  v4.0.0 defaults (GPIO 0/1/2/3).
- Add `pub fn pin_miso(&self) -> u8` accessor for `update_gpio()`.
- Unit tests (lines 402-666) move with the code unchanged.
- Bus integration tests (lines 670-805) stay in `mdrp2040`, updated:
  `emu.bus.psram` → `emu.bus.psram.as_ref().unwrap()` /
  `.as_mut().unwrap()`. Builder: `.psram(Psram::picogus())`.
- PIO integration tests (lines 825-1022) stay in `mdrp2040`, same
  updates as bus integration tests.

### LCD decoder (`lcd.rs`)

Move from `mdrp2040app::devices::lcd`.

Changes:
- `LcdState` moves into this file (currently defined in
  `mdrp2040app::snapshot`; it's `rows: [[u8; 20]; 2],
  cursor: (u8, u8)` with no app dependencies).
- Pin constants (`SCLK_BIT`, `DATA_BIT`, `CS_BIT`) become constructor
  parameters: `LcdDecoder::new(sclk_pin: u8, data_pin: u8, cs_pin: u8)`.
- Unit tests move with the code.

### I2S capture (`i2s_capture.rs`)

Move from `mdpicoem-harness::i2s_capture`. Name stays `I2sCapture`.

Changes:
- Pin numbers become constructor parameters:
  `I2sCapture::new(sys_clk_hz, bclk_pin, lrclk_pin, dout_pin)`.
- Remove `use crate::picogus_pins::{I2S_BCLK, I2S_DOUT, I2S_LRCLK}`.
- `write_wav()` stays as a method on `I2sCapture`.
- `default_out_path()` stays in the harness as a free function (it
  hardcodes harness-specific paths — not a device concern).
- Unit tests move with the code. `tmp_dir()` helper's
  `CARGO_MANIFEST_DIR` path will change (harmless — still under
  `target/`).

### What does NOT move

- `picogus_pins.rs` — stays in `mdpicoem-harness`. Board wiring,
  not a device model. Devices take pin numbers as constructor params.
- `mdrp2040app::devices::bench` — SRAM sentinel poller, not a GPIO
  device. Stays in the app.
- `mdrp2040::peripherals::{adc, timer, uart, spi, i2c, pwm,
  watchdog_tick}` — on-chip RP2040 peripherals.
- `mdrp2040::Bus::external_gpio_in_mask/override` — unchanged.
