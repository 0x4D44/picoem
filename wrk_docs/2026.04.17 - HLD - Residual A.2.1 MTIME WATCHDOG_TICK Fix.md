# Residual A.2.1 — MTIME WATCHDOG_TICK timebase fix

**Date:** 2026-04-17
**Parent HLD:** `wrk_docs/2026.04.17 - HLD - Stage A.2 Silicon Oracle Residuals Handoff.md` (Residual 1)
**Parent journal:** `wrk_journals/2026.04.16 - JRN - Silicon Oracle Fidelity Gaps Fix Wave.md` (Stage A)
**Silicon symptom:** `HW=0x00 EMU=0x67` at `0xD000_01B0` (MTIME low), mask `0xFFFF_FFFF`, scenario `sio_mtime_count_and_match`.

---

## 1. Root-cause verdict

**Bug is emulator-side only. The scenario is correct.** The sled intentionally exercises the post-reset MTIME timebase without touching TICKS or `MTIME_CTRL.FULLSPEED` — both sides should count at whatever the post-bootrom TICKS state produces. Silicon reports 0 edges (correct for post-bootrom: `TICKS.RISCV.ENABLE=0`, `CYCLES=0`). The emulator reports 103 sysclks of counting because `Sio::tick_mtime_n` advances MTIME by the raw sys_clk count regardless of `FULLSPEED` or the RISCV tick domain.

### Datasheet evidence

- **§3.1.8 "RISC-V platform timer" (p. 43–44):** "The RISC-V timer can count either ticks from the system-level tick generator (Section 8.5), or system clock cycles, selected by the `MTIME_CTRL` register."
- **§3.1 Table 80 (MTIME_CTRL register at 0x1A4):**
  - bit 0 `EN` — reset `0x1` (timer enabled).
  - bit 1 `FULLSPEED` — reset `0x0`. "If 1, increment the timer every cycle (i.e. run directly from the system clock), rather than incrementing on the system-level timer tick input."
  - bits 2–3 `DBGPAUSE_CORE0/1` — reset `0x1` each.
- **§8.5 "Tick generators":** `TICKS_BASE = 0x4010_8000`. Six domains: `PROC0`, `PROC1`, `TIMER0`, `TIMER1`, `WATCHDOG`, `RISCV`. Each has `CTRL`, `CYCLES`, `COUNT`. The **RISCV** domain drives MTIME (not WATCHDOG — the parent HLD's "WATCHDOG_TICK" naming is a legacy-RP2040 artefact; on RP2350 the tick generator is split out and the MTIME source is the dedicated RISCV domain). Reset: `CYCLES=0`, `ENABLE=0` for every domain (datasheet Tables 618–635).

### Emulator current behaviour (confirming the bug)

At `crates/mdrp2350/src/sio/mod.rs:456`, `tick_mtime_n(cycles)` runs the body whenever `mtime_ctrl & 1 != 0` (EN bit only), adding `cycles as u64` straight into `self.mtime`. There is no check for `FULLSPEED`, no dependency on `TICKS.RISCV` edges. The reset value of `0x0F` has `FULLSPEED=0`, so every scenario silently sees emulator FULLSPEED-like behaviour.

The 103 sys_clks observed (EMU=0x67) corresponds to the sled's 50-iteration countdown loop plus MOVW/MOVT/STR framing — consistent with the trace "MTIME_CTRL=1 is held high for ~103 sys_clks".

The scenario (`S_SIO_MTIME_COUNT_AND_MATCH` at `crates/mdpicoem-harness/src/silicon_scenarios.rs:655`) writes only `MTIME_CTRL=0` pre-setup and never touches TICKS. That is the right shape for a "does MTIME count post-reset without user TICKS config?" scenario; silicon correctly says "no, because `TICKS.RISCV.CYCLES=0` halts the divider", and the emulator should match.

## 3. Current state of the TICKS model and MTIME wiring

**File:** `crates/mdrp2350/src/peripherals/ticks.rs` (already complete and well-tested — 614 lines, 19 unit tests).

- `TICKS_BASE = 0x4010_8000`, `DOMAIN_COUNT = 6` (PROC0, PROC1, TIMER0, TIMER1, WATCHDOG, RISCV).
- L60–L70: domain index constants including `DOMAIN_RISCV: usize = 5`.
- L116–L126 `Domain::advance(sys_clks)` — if `enable && cycles > 0`, accumulate into `sys_clks` and emit `sys_clks / cycles` edges per divisor, decrementing accumulator and latching into `pending_edges`.
- L165–L170 `post_bootrom()` — programs `TIMER0/TIMER1.CYCLES = 12` (SDK-programmed value) but leaves **all other domains at hardware-reset zero**, including `RISCV.CYCLES = 0, ENABLE = false`. That's the right post-bootrom state because the SDK only programs TIMER domains before handing off; RISCV (which feeds MTIME) remains silicon-realistic until firmware configures it.
- L188–L195: consumer drains for TIMER0/TIMER1 (`take_timer0_edges`, `take_timer1_edges`). **There is no `take_riscv_edges` yet — this is the missing wiring.** The RISCV domain ticks along with the other five (because `advance_all` iterates all six at L181–L185) but its `pending_edges` field is never drained. Today it saturates silently.

**Bus-level tick orchestration:** `crates/mdrp2350/src/bus/mod.rs:1037–1106` (`Bus::tick_peripherals`). Line 1041 advances all six TICKS domains; lines 1046/1056 drain the TIMER edges. No MTIME drain exists here.

**Delta to wire up MTIME:** small. Add `take_riscv_edges` to `TicksRegs`, call it from the bus/sio integration after `ticks.advance_all`, and change `Sio::tick_mtime_n` to interpret its argument as tick edges (plus a FULLSPEED fast-path that bypasses TICKS). The `route tick edges through TICKS` path is already the pattern used by TIMER0/1.

## 4. Proposed fix

**Design goal:** MTIME increments once per tick edge from `TICKS.RISCV` when `FULLSPEED=0`; once per sys_clk when `FULLSPEED=1`. EN gates both. `DBGPAUSE_CORE0/1` remain unmodelled (as today) — the silicon_periph oracle never halts cores during a scenario.

### Wiring sketch

```
Emulator::step                                  (lib.rs)
   └─ tick_peripherals(step_quantum)
        └─ Bus::tick_peripherals(sys_clks)      (bus/mod.rs)
             ├─ ticks.advance_all(sys_clks)         ; existing, L1041
             ├─ <timer0 drain>                      ; existing, L1046
             ├─ <timer1 drain>                      ; existing, L1056
             └─ sio.tick_mtime_from_ticks(
                    riscv_edges = ticks.take_riscv_edges(),
                    sys_clks    = sys_clks,
                )                                   ; NEW
```

The MTIME tick moves from `lib.rs::tick_peripherals` into `Bus::tick_peripherals` so it can drain the `TICKS` block directly. This matches the TIMER0/1 pattern exactly.

### `Sio::tick_mtime_from_ticks` semantics

```rust
pub fn tick_mtime_from_ticks(&mut self, riscv_edges: u32, sys_clks: u32) {
    if self.mtime_ctrl & MTIME_CTRL_EN == 0 {
        return;
    }
    let n = if self.mtime_ctrl & MTIME_CTRL_FULLSPEED != 0 {
        sys_clks
    } else {
        riscv_edges
    };
    // Existing increment + match-edge body from tick_mtime_n(n).
    ...
}
```

`MTIME_CTRL_EN = 1 << 0`, `MTIME_CTRL_FULLSPEED = 1 << 1`. Name them as module-level `const u32` in `sio/mod.rs`.

### Exact file edits

1. **`crates/mdrp2350/src/peripherals/ticks.rs`**
   - After L195 (`take_timer1_edges`): add `pub fn take_riscv_edges(&mut self) -> u32` that drains `domains[DOMAIN_RISCV].pending_edges`. One-liner symmetric with the TIMER drains.

2. **`crates/mdrp2350/src/sio/mod.rs`**
   - Add two `const u32` near the top of `impl Sio`: `MTIME_CTRL_EN = 1`, `MTIME_CTRL_FULLSPEED = 1 << 1`. (Or `pub(crate) const` at module scope — caller prefers module scope if future tests reference them.)
   - Replace `tick_mtime_n(n)` at L456–L471 with `tick_mtime_from_ticks(riscv_edges, sys_clks)` whose body branches on `FULLSPEED` to pick the source count, then runs the existing increment + match-edge code against that count. Keep the `n == 0` early-return.
   - Optionally keep `tick_mtime()` (the per-edge variant at L435) unchanged — useful for the unit-test harness path; rename its doc comment to "increment MTIME by one tick edge (test helper)".
   - Fix the doc comment at L635 — "FRACT=0" → "FULLSPEED=0".

3. **`crates/mdrp2350/src/bus/mod.rs`**
   - Inside `Bus::tick_peripherals` (L1037–L1106), after the existing `self.ticks.advance_all(sys_clks)` at L1041 and before the TIMER blocks, drain RISCV edges: `let riscv_edges = self.ticks.take_riscv_edges();` and call `self.sio.tick_mtime_from_ticks(riscv_edges, sys_clks);`. Placement after `advance_all` is mandatory (edges must be populated before the drain); placement before the TIMER drains is incidental but keeps the RISC-V-flavoured timekeeping grouped.

4. **`crates/mdrp2350/src/lib.rs`**
   - Remove L382 `self.bus.sio.tick_mtime_n(cycles);` — MTIME ticking now lives inside `Bus::tick_peripherals` at the correct point in the ordering.

### No scenario-side changes

The scenario stays as-is. Its purpose is "prove that post-reset-default MTIME matches silicon", and silicon correctness requires zero MTIME counting in that window. After the fix both sides read MTIME=0.

A follow-up scenario that explicitly configures `TICKS.RISCV` (CYCLES=12, ENABLE=1, MTIME_CTRL.EN=1, FULLSPEED=0) and counts real 1 µs edges is a worthwhile addition — that would catch a bug where the RISCV-to-MTIME wiring works in reset-config but not in live-config. Scope: out-of-wave follow-up, NOT required for A.2.1 closure.

## 5. Test plan (TDD)

### 5a. Unit tests in `crates/mdrp2350/src/sio/mod.rs::tests`

Three new tests exercising the new API, all of which must FAIL today and PASS post-fix:

**Test 1: `mtime_post_reset_does_not_count_from_sys_clks_alone`**

```rust
#[test]
fn mtime_post_reset_does_not_count_from_sys_clks_alone() {
    let mut sio = Sio::new();
    // Post-reset: MTIME_CTRL = 0x0F (EN=1, FULLSPEED=0).
    assert_eq!(sio.mtime_ctrl, 0x0F);
    // Pump sys_clks through the new API with ZERO RISCV edges.
    // Expected: MTIME does not move. Silicon parity.
    sio.tick_mtime_from_ticks(0, 1000);
    assert_eq!(sio.mtime, 0,
        "FULLSPEED=0 + zero RISCV edges must not advance MTIME");
}
```

Expected failure today: compilation fails because `tick_mtime_from_ticks` doesn't exist. (That's acceptable for TDD — we hand-verify against the current `tick_mtime_n` call: 1000 sys_clks with EN=1 would yield MTIME=1000, which is not zero.)

**Test 2: `mtime_advances_one_per_riscv_edge_in_ticks_mode`**

```rust
#[test]
fn mtime_advances_one_per_riscv_edge_in_ticks_mode() {
    let mut sio = Sio::new();
    sio.mtime_ctrl = 0x01; // EN=1, FULLSPEED=0.
    sio.tick_mtime_from_ticks(5, 0);
    assert_eq!(sio.mtime, 5, "5 RISCV edges → MTIME += 5 in TICKS mode");
    sio.tick_mtime_from_ticks(0, 1000);
    assert_eq!(sio.mtime, 5, "sys_clks alone never advance in TICKS mode");
}
```

**Test 3: `mtime_fullspeed_counts_sys_clks_directly`**

```rust
#[test]
fn mtime_fullspeed_counts_sys_clks_directly() {
    let mut sio = Sio::new();
    sio.mtime_ctrl = 0x03; // EN=1 + FULLSPEED=1.
    sio.tick_mtime_from_ticks(0, 100);
    assert_eq!(sio.mtime, 100, "FULLSPEED=1 → MTIME counts sys_clks");
    // RISCV edges ignored in FULLSPEED mode — no double-count.
    sio.tick_mtime_from_ticks(9, 50);
    assert_eq!(sio.mtime, 150, "edges ignored when FULLSPEED=1");
}
```

### 5c. End-to-end test in `crates/mdrp2350/src/tests.rs`

**Test 5: `mtime_stays_zero_at_post_reset_matches_silicon`**

```rust
#[test]
fn mtime_stays_zero_at_post_reset_matches_silicon() {
    // Mirrors the silicon scenario: no TICKS config, just enable MTIME and
    // burn ~100 sys_clks. Silicon reads MTIME=0 because
    // TICKS.RISCV.CYCLES=0 halts the divider. Emulator must agree.
    let mut emu = EmulatorBuilder::new(Config::default()).step_quantum(1).build();
    emu.core_mut(1).halt();
    emu.core_mut(0).halt();
    // Post-reset MTIME_CTRL is 0x0F; write it again explicitly so the
    // test survives a future reset-default change.
    emu.mmio_write32(0xD000_01A4, 0x01);
    emu.run(200);
    let mtime_lo = emu.mmio_read32(0xD000_01B0);
    assert_eq!(mtime_lo, 0,
        "MTIME must not advance without TICKS.RISCV configuration \
         (silicon reads 0 at this scenario gate)");
}
```

Today: emulator returns ~200 (one MTIME per sys_clk, both cores halted so step quantum still fires peripheral ticks). Test FAILS.
After fix: emulator returns 0. Test PASSES.

### MTIME-touching code surveyed

- `crates/mdrp2350/src/bus/mod.rs:918` — comment only.
- `crates/mdrp2350/src/core_riscv/csr.rs:66` — comment documenting MTIP source, no code change needed.

- `crates/mdrp2350/src/tests.rs:8911–8918` (MTIMEL byte-lane RMW test) — uses direct register writes, no counting. Unaffected.

### Regression risk per scenario

- `sio_divider_unsigned` / `sio_divider_signed` — no MTIME interaction. Safe.
- `timer0_alarm0_fire_and_clear` / `timer1_alarm0_fire_and_clear` — drive TIMER0/1 through the same TICKS mechanism. MTIME drain sits between `advance_all` and the TIMER drains; since TIMER drains consume their own domain indices, there is no cross-contamination. Run both scenarios post-fix to confirm TIMER edges still total the expected µs count. Unchanged expectation.
- `ticks_timer0_retarget_halves_rate` — explicitly reconfigures `TICKS.TIMER0.CYCLES`; touches only the TIMER0 domain. RISCV domain stays at reset. Unchanged expectation.
- `pwm_fractional_div` (separate residual A.2.2) — no MTIME path. Safe.
- `uart0_*` (separate residual A.2.3) — no MTIME path. Safe.
- Everything else in `SCENARIOS` — no MTIME observable.

### P4 RISC-V fan-out paths

RISC-V tests that depend on MTIP assertion use the `freeze_mtime` helper (`tests_p4.rs:270`) which sets `mtime_ctrl = 0` and explicitly asserts `mtime_match_asserted`. The new API still short-circuits on `EN=0`, so those tests retain their pre-existing behaviour.

If a future test enables MTIME with `mtime_ctrl = 1` and expects counting without configuring TICKS, it will now observe zero advancement (silicon-correct). Grep across `tests_p4.rs` and `core_riscv/` confirms no such test exists today.

### Performance

One extra `u32` drain per quantum (free; the domain was already advancing). One extra conditional in `Sio::tick_mtime_from_ticks`. Net cost: below noise floor of the step loop. No new hot-path allocations.
