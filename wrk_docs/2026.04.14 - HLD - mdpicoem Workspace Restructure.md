# mdpicoem Workspace Restructure

Version: 1.1.0
Date: 2026-04-14

## Problem

The workspace emulates one chip (RP2354) and is hardcoded to it throughout:
`Emulator.cores: [CortexM33; 2]`, `Bus.pio: [PioBlock; 3]`, M33-specific
execute paths, TrustZone banking, FPU, coprocessor dispatch. We want to
add RP2040 support and ship two emulator libraries that can be consumed
independently.

Forking the crate wholesale duplicates ~2600 lines of PIO, plus SIO/clock
primitives, peripheral register-file helpers, and the `Peripheral` trait
— much of which is chip-agnostic at the *primitive* level. Duplication
will bit-rot: fixes land in one crate, the other drifts. A single crate
with runtime or compile-time chip selection turns into a feature-flag
maze that obscures the differences that matter (CPU ISA, exception
model, memory map).

## Target layout

```
crates/
  mdpicoem-common/      # chip-agnostic primitives (library)
  mdrp2040/             # RP2040 emulator (library)
  mdrp2350/             # RP2350 emulator (library, renamed from mdrp2354)
  mdrp2040app/          # TUI demo consuming mdrp2040
  mdrp2350app/          # TUI demo consuming mdrp2350 (renamed from mdrp2354-app)
  mdpicoem-harness/     # differential test tools (renamed from mdrp2354-test-harness)
  mdpicoem-debug/       # GDB RSP scaffolding (renamed from mdrp2354-debug)
```

Repository name: **mdpicoem**.

The two stub crates `mdrp2354-periph` and `mdrp2354-pio` (each currently
a one-line `lib.rs` whose code lives elsewhere) are deleted. `Peripheral`
trait moves into `mdpicoem-common`; PIO source already lives in
`crates/mdrp2354/src/pio/` and moves to common.

## Naming

- **`mdrp2350`, not `mdrp2354`.** RP2354 = RP2350A with 2 MB stacked flash.
  The family is RP2350 (A/B steppings × flash variants). Flash size and pin
  count are construction-time config on a single `mdrp2350::Emulator`, not
  separate crates.
- **`mdpicoem`** as the repo and common-crate stem. Short for "MD Pico
  Emulator".

## Crate boundaries and performance policy

**The concern:** moving primitives into `mdpicoem-common` means every
bus access in the chip crate calls into a different crate. Without care
this defeats the inlining the Fast Path Bus Read HLD relies on (today:
`Bus::read16 → Memory::sram_read16`, annotated `#[inline(always)]`,
folded into one basic block by LLVM).

**The policy:**

1. **`lto = "fat"` stays on for release.** Already configured. Handles
   cross-crate inlining at link time — `#[inline(always)]` on
   `Memory::sram_read16` in common is honoured when called from `Bus` in
   the chip crate.
2. **`codegen-units = 1`** on the release profile of each chip crate
   (currently set on `mdrp2354`; mirror to `mdrp2040` and `mdrp2350`).
3. **Keep existing `#[inline(always)]` annotations** when methods move
   to common. No semantic change; just don't drop the attributes during
   the move.
4. **Common offers concrete types, not traits, on the hot path.**
   `Fifo`, `Divider`, `PioBlock`, `Memory`, `ClockTree` — chip crates
   embed these by value. No `dyn Bus`, `dyn Chip`, `dyn Core`.
5. **No cross-chip trait abstraction.** `mdrp2040::Emulator` and
   `mdrp2350::Emulator` are two unrelated concrete types. A user who
   wants polymorphism can write their own trait; neither library
   provides one.

The only place dynamic dispatch is acceptable is the existing
`Peripheral` trait (called once per system clock per peripheral, not
once per instruction). That trait moves to common unchanged.

**Validation gate:** *before* phase 1, capture pre-restructure
`paced_bench` steady-state throughput on the default `basic` workload
(paced_bench has a hardcoded workload, not a firmware-input tool).
Record emulated MHz in the phase 1 commit message. After phase 2,
re-run and confirm within 2% of that captured baseline. If it
regresses further, the hot-path inlining is not surviving the crate
split — fix before proceeding.

**Phase 0 baseline (captured 2026-04-14):** 32.9 MHz emulated, 0.6%
variance across 3 × 15s `--unpaced` runs. Phase 2 gate: ≥ 32.24 MHz.

## What moves where

| Subsystem | Target | Notes |
|---|---|---|
| `Fifo` (8-entry circular, today nested in `sio/mod.rs`) | `mdpicoem-common` | Pure primitive; lift out as its own type. |
| `Divider` (per-core integer divider state machine, today private in SIO) | `mdpicoem-common` | Same algorithm in both chips. Lift out. |
| Spinlock-bank helpers (32-bit claim bitmap) | `mdpicoem-common` | Identical on both chips. |
| `pio/*` (~2660 lines) | `mdpicoem-common` | ISA identical; block count (2 vs 3) is held by each chip's `Bus`. |
| `pacer.rs` | `mdpicoem-common` | Wall-clock pacer; `#[cfg(target_arch = "x86_64")]` gate stays. |
| `clock/mod.rs` | `mdpicoem-common` | Trivial cycle counter. |
| `bus/clocks.rs` PLL math (`pll_output_hz`, divider model, `ClockTree`) | `mdpicoem-common` | Pure arithmetic; identical between chips. Register *storage* stays chip-side. |
| `Peripheral` trait | `mdpicoem-common` | Verbatim from `crates/mdrp2354/src/lib.rs`. |
| `Memory` byte storage + scalar accessors (`sram_read/write_*`, `rom_read_*`, `xip_read_*`, `peek*`, `poke*`) | `mdpicoem-common` | Sized via `new(rom_size, sram_size)` constructor — **not** const-generic on size. |
| `Memory::bank_for_address` | **chip crate** | Bank topology is chip-specific (RP2350: 8-stripe + 2-scratch; RP2040: 4-stripe + 2-scratch). Co-locate with each chip's contention model. |
| `Sio` struct itself | **chip crate** | Composes `Fifo` / `Divider` / spinlock helpers from common, plus chip-specific extras (RP2350: doorbells, mtime, mtimecmp, CP0-bridge event hook; RP2040: smaller set, no doorbells, no mtime). |
| `bus/peripherals.rs` (today's `peripheral_regs` HashMap stub) | **stays in chip crate** | Stub; premature to share. Real peripherals will be chip-specific. |
| `bus/ppb.rs` | **chip crate** | RP2350 keeps current M33 Ppb (SAU, MPU, FPCCR/FPCAR/FPDSCR, CPACR, full SHPR, MMFAR/BFAR). RP2040 writes its own M0+ Ppb (no MPU/SAU/FP/CPACR; MMFAR/BFAR absent; HardFault-only; smaller NVIC). No shared trait. |
| `bus/mod.rs` | `mdrp2350` | Chip-specific: address decode, RESETS layout, contention model, QMI regs, `boot_ram` (4 KB at `0xEFFF_F000`), `xip_sram` (16 KB at `0x1C00_0000`), `rcp_count`/`rcp_salt`, PLL/ROSC/XOSC register storage. |
| `core/*` (CPU + decode + execute + exceptions + coprocessor + FPU) | `mdrp2350` | M33-specific; stays put under the rename. |
| `lib.rs` (Emulator) | `mdrp2350` | Concrete to the chip. `Bus::default()` retained — used by `core::execute_one` test paths. |
| `tests.rs` (6693 lines) | `mdrp2350` | M33-specific. |

New in `mdrp2040` (written fresh, using common's primitives): M0+ CPU,
RP2040 bus (different XIP at `0x1500_0000`, XIP_CTRL+SSI instead of
QMI, no `boot_ram`, no RCP), RP2040 PPB, RP2040 SIO composition, RP2040
`Memory::bank_for_address`, RP2040 `Emulator`, RP2040 tests.

**Rule of thumb for the split:** common owns *primitives* (types and
pure functions); chip crates own *composed structures* (anything that
mixes chip-specific fields with primitives). When in doubt, leave it
in the chip crate — cheaper to lift up later than push down.

## Anti-goals

- **No `Chip` / `Core` / `Bus` trait** spanning both chip crates. If the
  two emulator APIs diverge we pay for it by dropping polymorphism, not
  by papering over with traits.
- **No feature flags** selecting chip variants. Two library crates, two
  concrete APIs, pick one at the `Cargo.toml` dependency level.
- **No environment variables** for chip selection at runtime. The demo
  apps are two binaries, not one with `--chip=rp2040`.
- **No `mdpicoem` umbrella crate** re-exporting both. Dependents pick
  `mdrp2040` or `mdrp2350` directly.
- **No backwards-compatibility shims, deprecation aliases, or
  `pub use mdrp2350 as mdrp2354`.** The rename is atomic; old paths are
  gone.
- **No shared UI crate yet.** `mdrp2040app` is a copy of `mdrp2350app`
  that diverges as RP2040 features land. Premature UI abstraction is
  worse than duplication.
- **No `Memory<const N: usize>` const generics.** Bank topology is more
  than a size — sizes go on the constructor, topology lives chip-side.

## Sequencing

Each phase leaves the workspace compilable, all tests passing, and the
TUI app runnable. No big-bang restructure.

### Phase 0 — capture perf baseline

Run `paced_bench --unpaced --seconds 15` three times and record the
median emulated MHz. paced_bench uses a hardcoded default `basic`
workload (2-insn tight loop); no firmware input. Note the number in
the phase 1 commit message. Without this number, the phase 2 perf gate
has nothing to compare against.

**Captured 2026-04-14: 32.9 MHz median (0.6% variance).**

### Phase 1 — rename in place

- `git mv crates/mdrp2354 crates/mdrp2350`
- `git mv crates/mdrp2354-app crates/mdrp2350app`
- `git mv crates/mdrp2354-test-harness crates/mdpicoem-harness`
- `git mv crates/mdrp2354-debug crates/mdpicoem-debug`
- Delete `crates/mdrp2354-periph` and `crates/mdrp2354-pio`.
- Update `Cargo.toml` `[package]` names, workspace members, inter-crate
  `[dependencies]`, bin names. Lift `rust-version` to
  `[workspace.package]`.
- Rename `[profile.release.package.mdrp2354]` to `mdrp2350`.
- Reorganise `roms/` into `roms/rp2350/` (RP2040 subdir created empty).
- Doc sweep per "Documentation sweep" above.
- One commit. `cargo test --workspace` green, `mdrp2350app` runs.

### Phase 2 — extract `mdpicoem-common`

- Create `crates/mdpicoem-common` with empty lib.
- Move primitives one at a time per the table:
  1. `Peripheral` trait
  2. `clock/`, `pacer.rs`
  3. `Memory` (storage + accessors only; leave `bank_for_address` behind)
  4. PLL math + `ClockTree`
  5. `Fifo`, `Divider`, spinlock-bank helpers (lifted out of `sio/mod.rs`)
  6. `pio/`
- After each: `cargo test --workspace` green.
- After full extraction: re-run `paced_bench`, gate at within 2% of the
  phase 0 baseline.
- Bump `mdrp2350` to 0.3.0.

### Phase 3 — stub `mdrp2040`

- Create `crates/mdrp2040` with an empty `Emulator` struct that
  implements the same public surface as `mdrp2350::Emulator`
  (`new`, `reset`, `load_bootrom`, `load_flash`, `step`, `run`, `peek`,
  `poke`, `core`, `core_mut`, `cycles`, `gpio_*`).
- Every method is `todo!()` for now, except `new`/`reset` which set
  RP2040 memory sizes (264 KB SRAM, 16 KB ROM, no onboard flash).
- Smoke test: construct, reset, step once (which panics with `todo!`).
  Confirms wiring.

### Phase 4 — M0+ core

- Implement decoder, executor, exceptions for ARMv6-M.
- Most Thumb-16 ported from `mdrp2350::core::execute.rs`; delete
  M33-only behaviour (IT blocks, CBZ/CBNZ, wide-path in Thumb-16).
- Thumb-32 subset: BL, MRS, MSR, DSB, DMB, ISB only.
- Simpler exception model: 8-word stack frame, fixed priorities for NMI
  (-2) and HardFault (-1), no priority grouping, no FP context, no
  security state.
- Unaligned word access faults (M0+ does not support unaligned).

### Phase 5 — RP2040 bus, memory map, peripherals

- Address decode per RP2040 datasheet.
- SRAM: 4×64 KB striped (SRAM0–3) + 2×4 KB scratch (SRAM4–5).
  RP2040-specific `bank_for_address` and contention model.
- CLOCKS, RESETS, SIO, PADS_BANK0, IO_BANK0, XOSC, PLL_SYS, PLL_USB —
  register layouts differ from RP2350; implement against the RP2040 SVD,
  not by diffing from RP2350 code.
- 2 PIO blocks (vs 3).
- No coprocessor bridge on SIO. No DCP/RCP/HSTX. No `boot_ram`.
- XIP at `0x1500_0000` via XIP_CTRL+SSI, not QMI.

### Phase 6 — test harness split

**Note on oracle scope.** The QEMU diff harness validates **CPU
semantics** (instructions, flags, exception entry/return), not RP2350
bus or peripheral fidelity. It runs against a generic M33 board
(`-machine mps2-an505 -cpu cortex-m33`) — chip-agnostic CPU oracle.
Bus/peripheral fidelity is validated separately by `probe_diff` against
real silicon. The M0+ runner inherits the same scope: M0+ CPU oracle
plus probe-based bus oracle on a real Pico.

`mdpicoem-harness` layout:

- `src/lib.rs` — shared GDB client, shared register-diff logic.
- `src/thumb16_gen.rs` — Thumb-16 fuzz generator (mostly shared between
  ISAs; M33-only Thumb-16 encodings gated off for the M0+ runner).
- `src/thumb32_gen.rs` — M33-only.
- `src/bin/qemu_diff_m33.rs` — current `qemu_diff` retargeted to
  `mdrp2350`.
- `src/bin/qemu_diff_m0plus.rs` — new; targets `mdrp2040`.
  **TBD during this phase**: which `qemu-system-arm -machine ... -cpu
  cortex-m0plus` invocation produces a working GDB stub. Phase opens
  with a 1-day spike to identify the right combination. If no
  off-the-shelf machine works, fall back to a CPU-only differential
  against an alternative M0+ implementation (unicorn-engine via FFI is
  the fallback; not the primary path).
- `src/bin/probe_diff_rp2350.rs` — current `probe_diff` retargeted.
- `src/bin/probe_diff_rp2040.rs` — new; requires a Pico board (will not
  run in CI, since CI doesn't exist).
- `paced_bench`, `full_test`, `bank_conflict_test`, `probe_verify` —
  each gains a chip suffix or selects the chip via `use`.
- `softfloat_diff` — RP2350-only (RP2040 has no FPU). No M0+ counterpart.

### Phase 7 — `mdrp2040app`

- Copy `crates/mdrp2350app` to `crates/mdrp2040app`.
- Swap the `mdrp2350` dependency for `mdrp2040`.
- Trim panels that don't apply (FPU register views, coprocessor state).
- Leave the rest duplicated.

## Build and profile configuration

Workspace `Cargo.toml` release profile stays as-is (`opt-level = 3`,
`lto = "fat"`, `panic = "abort"`). The per-package override is mirrored
to both chip crates:

```toml
[profile.release.package.mdrp2040]
codegen-units = 1

[profile.release.package.mdrp2350]
codegen-units = 1
```

The `profiling` profile is unchanged. No new profiles.

## Risks

- **Perf regression at the common-crate seam.** Mitigation: phase 0
  captures baseline; phase 2 gate is `paced_bench` within 2% of it.
  First suspect on regression is a dropped `#[inline(always)]` during
  the move.
- **M0+ QEMU machine compatibility.** No verified off-the-shelf machine
  is known to accept a `cortex-m0plus` override and expose a working
  GDB stub. Mitigation: phase 6 starts with a 1-day spike; fallback is
  unicorn-engine FFI for ISA-only differential.
- **SVD drift between RP2040 and RP2350 peripheral register layouts.**
  Implement RP2040 peripherals against the SVD directly, not by diffing
  RP2350 code. Register offsets that look similar aren't.
- **M0+ exception model bugs.** Different stack frame, different
  EXC_RETURN encoding, no FP context. Mitigation: differential testing
  against the chosen QEMU oracle from phase 4 onwards; don't write
  RP2040 firmware smoke tests until the exception path is QEMU-verified.
- **RP2040 probe-differential goes dark without a Pico.** Accepted risk;
  documented in `CLAUDE.md` after phase 6.
- **Bootrom licensing and distribution.** RP2040 bootrom is BSD-3 from
  Raspberry Pi; include it as a binary asset under `roms/rp2040/` with
  its license text, same pattern as RP2350.
- **Versioning errors during the rename.** Easy to forget the
  `mdrp2350 → 0.3.0` bump after phase 2. Mitigation: include the bump
  in the same commit that completes the common extraction.
