# mdpicoem Workspace Restructure

Version: 1.0.0
Date: 2026-04-14

## Problem

The workspace emulates one chip (RP2354) and is hardcoded to it throughout:
`Emulator.cores: [CortexM33; 2]`, `Bus.pio: [PioBlock; 3]`, M33-specific
execute paths, TrustZone banking, FPU, coprocessor dispatch. We want to
add RP2040 support and ship two emulator libraries that can be consumed
independently.

Forking the crate wholesale duplicates ~2600 lines of PIO, ~800 lines of
SIO, clock-tree math, peripheral register-file helpers, and the
`Peripheral` trait — all of which are chip-agnostic or trivially
parameterised. Duplication will bit-rot: fixes land in one crate, the
other drifts. A single crate with runtime or compile-time chip selection
turns into a feature-flag maze that obscures the differences that matter
(CPU ISA, exception model, memory map).

## Target layout

```
crates/
  mdpicoem-common/      # chip-agnostic building blocks (library)
  mdrp2040/             # RP2040 emulator (library)
  mdrp2350/             # RP2350 emulator (library, renamed from mdrp2354)
  mdrp2040app/          # TUI demo consuming mdrp2040
  mdrp2350app/          # TUI demo consuming mdrp2350 (renamed from mdrp2354-app)
  mdpicoem-harness/     # differential test tools (renamed from mdrp2354-test-harness)
  mdpicoem-debug/       # GDB RSP scaffolding (renamed from mdrp2354-debug)
```

Repository name: **mdpicoem**.

The three stub-today crates (`mdrp2354-periph`, `mdrp2354-pio`, `mdrp2354-debug`)
are collapsed: PIO moves into `mdpicoem-common` (its consumer is the bus in
each chip crate, not an external peripheral); `mdrp2354-periph`'s
`Peripheral` trait moves into `mdpicoem-common`; `mdrp2354-debug` is renamed
to `mdpicoem-debug` in place. The separate PIO and periph crates disappear.

## Naming

- **`mdrp2350`, not `mdrp2354`.** RP2354 = RP2350A with 2 MB stacked flash.
  The family is RP2350 (A/B steppings × flash variants). Flash size and pin
  count are construction-time config on a single `mdrp2350::Emulator`, not
  separate crates.
- **`mdpicoem`** as the repo and common-crate stem. Short for "MD Pico
  Emulator".

## Crate boundaries and performance policy

**The concern:** moving `Memory`, `Sio`, `PioBlock`, `ClockTree` into
`mdpicoem-common` means every bus access in the chip crate calls into a
different crate. Without care this defeats the inlining the Fast Path Bus
Read HLD relies on (today: `Bus::read16 → Memory::sram_read16`,
annotated `#[inline(always)]`, folded into one basic block by LLVM).

**The policy:**

1. **`lto = "fat"` stays on for release.** Already configured. Handles
   cross-crate inlining at link time — `#[inline(always)]` on
   `Memory::sram_read16` in common is honoured when called from `Bus` in
   the chip crate.
2. **`codegen-units = 1`** on the release profile of each chip crate
   (currently set on `mdrp2354`; mirror to `mdrp2040` and `mdrp2350`).
3. **Keep existing `#[inline(always)]` annotations** on all hot accessors
   when they move to common. No semantic change; just don't drop the
   attributes during the move.
4. **Common offers concrete types, not traits, for the hot path.**
   `mdpicoem-common::Memory<const SRAM_SIZE: usize>`, `PioBlock`,
   `ClockTree`, `Sio` — chip crates embed these by value. No
   `dyn Bus`, `dyn Chip`, `dyn Core`.
5. **No cross-chip trait abstraction.** `mdrp2040::Emulator` and
   `mdrp2350::Emulator` are two unrelated concrete types. A user who
   wants polymorphism can write their own trait; neither library
   provides one.

The only place dynamic dispatch is acceptable is the existing
`Peripheral` trait (called once per system clock per peripheral, not
once per instruction). That trait moves to common unchanged.

Validation: after phase 2 (see Sequencing) run `paced_bench` against a
representative firmware and confirm steady-state cycles/sec is within 2%
of the current `mdrp2354` baseline. If it regresses further, the hot-path
inlining is not surviving the crate split — fix before proceeding.

## What moves where

| Subsystem | Target | Notes |
|---|---|---|
| `memory/mod.rs` | `mdpicoem-common` | Generic over SRAM/ROM/XIP sizes via const generics or config struct. Both chips use it. |
| `pio/*` | `mdpicoem-common` | ISA identical; block count (2 vs 3) is a chip-crate concern (how many `PioBlock`s the `Bus` holds). |
| `sio/mod.rs` | **split** | Divider, spinlocks, FIFO, interp → common. CP0 GPIO coprocessor bridge stays in `mdrp2350` (RP2040 has no such bridge). |
| `bus/clocks.rs` | `mdpicoem-common` | PLL math, divider model. Register offsets live in chip-specific bus code. |
| `bus/peripherals.rs` | `mdpicoem-common` | Register-file scaffolding, address-decode helpers. |
| `Peripheral` trait | `mdpicoem-common` | From today's `crates/mdrp2354/src/lib.rs`. |
| `pacer.rs` | `mdpicoem-common` | x86_64-gated wall-clock pacer; chip-agnostic. |
| `clock/mod.rs` | `mdpicoem-common` | Trivial cycle counter. |
| `bus/mod.rs` | `mdrp2350` | Chip-specific address decode, RESETS layout, contention model, QMI regs. |
| `bus/ppb.rs` | `mdrp2350` | M33-specific PPB registers (SHCSR, CFSR, CPACR, NVIC layout). RP2040 needs its own simpler PPB in `mdrp2040`. |
| `core/*` | `mdrp2350` | M33 CPU; stays put under the rename. |
| `lib.rs` (Emulator) | `mdrp2350` | Concrete to the chip. |
| `tests.rs` (6693 lines) | `mdrp2350` | M33-specific. RP2040 gets its own tests in `mdrp2040`. |

New in `mdrp2040` (written from scratch, using common's building blocks):
M0+ CPU (`core/`), RP2040 bus (`bus/mod.rs`), RP2040 PPB, RP2040
`Emulator`, RP2040 tests.

## Anti-goals

- **No `Chip` / `Core` / `Bus` trait** spanning both chip crates. If the
  two emulator APIs diverge we pay for it by dropping polymorphism, not
  by papering over with traits.
- **No feature flags** selecting chip variants. Two library crates, two
  concrete APIs, pick one at the `Cargo.toml` dependency level.
- **No environment variables** for chip selection at runtime. The demo
  apps are two binaries, not one with `--chip=rp2040`.
- **No `mdpicoem` umbrella crate** re-exporting both. Dependents pick
  `mdrp2040` or `mdrp2350` directly.
- **No backwards-compatibility shims, deprecation aliases, or
  `pub use mdrp2350 as mdrp2354`.** The rename is atomic; old paths are
  gone. (Per sandbox policy.)
- **No shared UI crate yet.** `mdrp2040app` is a copy of `mdrp2350app`
  that diverges as RP2040 features land. If they stay in lockstep for a
  while, we extract a UI crate later; premature abstraction here is
  worse than duplication.

## Sequencing

Each phase leaves the workspace compilable, all tests passing, and the
TUI app runnable. No big-bang restructure.

### Phase 1 — rename in place

- `git mv crates/mdrp2354 crates/mdrp2350`
- `git mv crates/mdrp2354-app crates/mdrp2350app`
- `git mv crates/mdrp2354-test-harness crates/mdpicoem-harness`
- `git mv crates/mdrp2354-debug crates/mdpicoem-debug`
- Delete `crates/mdrp2354-periph` and `crates/mdrp2354-pio` (stubs; their
  real code is already in `mdrp2354`).
- Update `Cargo.toml` `[package]` names, workspace members, inter-crate
  `[dependencies]`, bin names.
- Rename the `[profile.release.package.mdrp2354]` override to
  `mdrp2350`.
- Sweep `wrk_docs/`, `CLAUDE.md`, journal entries for the string
  `mdrp2354` and update to `mdrp2350` where the reference is to the
  crate (not to the physical chip part number, which stays RP2354 where
  it genuinely refers to the A4 variant).
- One commit. `cargo test --workspace` green, `mdrp2350app` runs.

### Phase 2 — extract `mdpicoem-common`

- Create `crates/mdpicoem-common` with an empty lib.
- Move modules listed in "What moves where" one at a time:
  `memory/`, `pio/`, `clock/`, `pacer.rs`, `Peripheral` trait, then SIO
  primitives, then clock-tree math.
- `mdrp2350` keeps its public re-exports (`pub use mdpicoem_common::Memory;`
  etc.) so downstream callers in `mdrp2350app` and `mdpicoem-harness`
  compile unchanged.
- After each module move: `cargo test --workspace` green. After the
  full extraction: `paced_bench` within 2% of pre-phase-2 throughput.

### Phase 3 — stub `mdrp2040`

- Create `crates/mdrp2040` with an empty `Emulator` struct that
  implements the same public surface as `mdrp2350::Emulator`
  (`new`, `reset`, `load_bootrom`, `load_flash`, `step`, `run`, `peek`,
  `poke`, `core`, `core_mut`, `cycles`, `gpio_*`).
- Every method is a `todo!()` for now, except `new`/`reset` which set
  up memory sizes per RP2040 (264 KB SRAM, 16 KB ROM, no onboard
  flash).
- Add a smoke test that constructs and resets — confirms wiring.

### Phase 4 — M0+ core

- Implement decoder, executor, exceptions for ARMv6-M.
- Most Thumb-16 ported from `mdrp2350::core::execute.rs`; delete M33-only
  behaviour (IT blocks, CBZ/CBNZ, wide-path in Thumb-16).
- Thumb-32 subset: BL, MRS, MSR, DSB, DMB, ISB only.
- Simpler exception model: 8-word stack frame, fixed priorities for NMI
  (-2) and HardFault (-1), no priority grouping, no FP context, no
  security state.
- Unaligned word access faults (M0+ does not support unaligned).

### Phase 5 — RP2040 bus, memory map, peripherals

- Address decode per RP2040 datasheet.
- SRAM striping: 4×64 KB striped banks (SRAM0–3) + 2×4 KB scratch
  (SRAM4–5). Contention model follows the same pattern as RP2350, with
  RP2040's bank count.
- CLOCKS, RESETS, SIO, PADS_BANK0, IO_BANK0, XOSC, PLL_SYS, PLL_USB —
  register layouts differ from RP2350; implement fresh against the SVD.
- 2 PIO blocks (vs 3).
- No coprocessor bridge on SIO. No DCP/RCP/HSTX.

### Phase 6 — test harness split

`mdpicoem-harness`:
- `src/lib.rs` — shared GDB client, shared register-diff logic.
- `src/thumb16_gen.rs` — Thumb-16 fuzz generator (shared between both
  ISA backends; both chips share most Thumb-16 encodings).
- `src/thumb32_gen.rs` — M33-only; used by the M33 binary.
- `src/bin/qemu_diff_m33.rs` — retarget current `qemu_diff` to
  `mdrp2350`.
- `src/bin/qemu_diff_m0plus.rs` — new; targets `mdrp2040` against
  `qemu-system-arm -M raspi-pico -cpu cortex-m0plus`.
- `src/bin/probe_diff_rp2350.rs` — current `probe_diff` retargeted.
- `src/bin/probe_diff_rp2040.rs` — new; requires a Pico board (will not
  run in CI).
- `paced_bench`, `full_test`, `bank_conflict_test`, `softfloat_diff`,
  `probe_verify` — each gains a chip suffix or picks the chip at the
  `use` statement. `softfloat_diff` is RP2350-only (RP2040 has no FPU).

### Phase 7 — `mdrp2040app`

- Copy `crates/mdrp2350app` to `crates/mdrp2040app`.
- Swap the `mdrp2350` dependency for `mdrp2040`.
- Trim panels that don't apply (FPU register views, coprocessor state).
- Leave the rest duplicated for now.

## Build and profile configuration

The workspace `Cargo.toml` release profile stays as-is (`opt-level = 3`,
`lto = "fat"`, `panic = "abort"`). The per-package override is mirrored
to both chip crates:

```toml
[profile.release.package.mdrp2040]
codegen-units = 1

[profile.release.package.mdrp2350]
codegen-units = 1
```

The `profiling` profile stays unchanged. No new profiles.

## Risks

- **Perf regression at the common-crate seam.** Mitigation: phase 2
  gate is `paced_bench` within 2% of baseline. If it fails, the first
  suspect is a dropped `#[inline(always)]` during the move. Do not
  ship phase 2 until this is green.
- **SVD drift between RP2040 and RP2350 peripheral register layouts.**
  Mitigation: implement RP2040 peripherals against the SVD directly,
  not by diffing from RP2350 code. Register offsets that look similar
  aren't.
- **M0+ exception model bugs.** Different stack frame, different
  EXC_RETURN encoding, no FP context. Mitigation: differential testing
  against QEMU from phase 4 onwards; don't write RP2040 firmware smoke
  tests until the exception path is QEMU-verified.
- **RP2040 probe-differential goes dark without a Pico.** Accepted risk;
  documented in `CLAUDE.md` after phase 6.
- **Bootrom licensing and distribution.** RP2040 bootrom is BSD-3 from
  Raspberry Pi; include it as a binary asset with its license text, same
  pattern as RP2350.
