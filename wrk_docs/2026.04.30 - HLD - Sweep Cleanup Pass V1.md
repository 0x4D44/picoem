## 4. Risks and mitigations

### 4.1 D7 — deleting `Ppb::set_irq_pending` / `clear_irq_pending` / `irq_enabled`

**Risk:** the action plan claims production paths use `merge_irq_pending`, direct `nvic_ispr` writes, and `any_pending_enabled`. If any production path actually does call the doomed helpers, deletion is a regression.

**Verification I did myself:**

```
grep -rn "\.set_irq_pending(\|\.clear_irq_pending(\|\.irq_enabled(" crates/ --include="*.rs"
```

Findings:

- `set_irq_pending` — 30+ callers, but **all on `CoreAtomics::set_irq_pending` in `threaded/atomics.rs`**, not the `Ppb` method. The two are name-collision twins; the dead-code report flagged this as one of the reasons to delete the `Ppb` version. Production calls (`crates/mdrp2350/src/core/mod.rs:980`, `lib.rs:1360`) are atomics-side. Tests in `core_riscv/tests_p4.rs` call `bus.atomics.set_irq_pending(...)`, not the PPB method.
- `clear_irq_pending` — only `Ppb` method definition + the one self-test in `tests.rs:21086`.
- `irq_enabled` — only `Ppb` method definition + the one self-test in `tests.rs:21092`.

So zero production callers of the three doomed `Ppb` methods. The four in-file PPB self-tests at `bus/ppb.rs:1180, 1208, 1219, 1230` use `set_irq_pending` for *setup* before testing other functions (`highest_priority_pending_irq`). Those four can be rewritten to use `merge_irq_pending` (existing public method, identical semantics for the in-range bit case) instead of being deleted. The action plan's "four self-tests" reference covers those — but they're salvageable, not redundant. Plan: keep their assertions; switch setup to `merge_irq_pending`.

**Mitigation:** the rewritten tests run under V4. If any of the four assertion targets changes behaviour (it shouldn't — `merge_irq_pending` is the production version of the same write), the test will catch it at run time.

### 4.2 H3 — RP2040 `pub dma` → `pub(crate) dma`

**Risk surfaced before writing this HLD:** the action plan says "external readers (likely 1-2 sites)". Reality from grep:

```
grep -rn "bus\.dma" crates/ --include="*.rs" | grep -v "/mdrp2040/src/" | grep -v "/mdrp2350/src/"
```

returns three sites, all in `crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs:2663, 2758, 2775`. Each fetches `&DmaChannel` via `emu.bus.dma.channel(ch)` and reads internal-state fields (`trig_ctrl`, `ever_wrote_pio1_txf_mask`, `transfers_issued`, `dreq_observed_mask`, `ctrl`) for diagnostic verdicts. None of these are reachable through MMIO without going through the (write-side-effecting) bus reads. Also: the existing `pub dma` carries an explicit doc-comment justification:

```
/// `pub` so diagnostic harnesses (e.g. `picogus_diff_rp2040`) can
/// read per-channel observation counters on `DmaChannel` without
/// going through MMIO.
```

So the original author *deliberately* kept it `pub`. The action plan's framing of "fix the asymmetry" runs against this deliberate decision.

**Mitigation:** add a `pub fn dma_channel(&self, i: usize) -> &DmaChannel` accessor on `Bus` (row 11 above) that routes through `Dma::channel`, which is already `pub` at `crates/mdrp2040/src/dma.rs:320`. This matches the PR-friendlier "method-not-field" rule of thumb without losing the harness diagnostic observability. The `picogus_diff_rp2040` migration is mechanical (3 sites, single rename).

**Open question lifted to §7:** is the action-plan framing here actually correct — i.e. should we disregard the explicit pub justification — or should we leave `pub dma` alone and update the doc comment to call out the asymmetry as deliberate? See §7 Q1.

## 5. Sequencing

**Proposal:** four atomic commits, in this order, separated by category. Argument for category-batching over one-big-commit and over per-file commits:

1. **Single commit** would mix bug fixes (B1 panic; B2 infinite loop) with cosmetic deletions (D2, D3, D4 annotations) with structural moves (Doc1 11-file archive). If a regression surfaces, `git bisect` lands on a 1000-line commit with no clue which sub-change broke things.
2. **Per-file commits** dilutes review. The hygiene one-liners (H1, H8) and the annotation deletions (D2, D3, D4) have nothing to verify individually beyond "still compiles" — they're not bug fixes; they don't deserve their own review.
3. **Per-category commits** strikes the balance: bug fixes get isolated history (so a future regression `git log`-grep finds the actual fix); dead-code stays together (one block of grep evidence in the message); hygiene + archive stays together (cheapest-to-revert).

Proposed commits:

| Commit | Contents | Action-plan items |
|---|---|---|
| C1 — `cleanup: fix Memory::load_rom and step_quantum panic/loop footguns` | rows 1–6 (B1 + B1 test, B2 + B2 tests on both chips) | Phase 1.1, 1.2 |
| C2 — `cleanup: hygiene one-liners (CLAUDE.md drift, qemu_diff_m33 hardcoded port, RP2040 Bus::dma asymmetry, pacer __cpuid wrapper)` | rows 7–15 | Phase 1.3 (H1, H2, H3, H8) |
| C3 — `cleanup: archive superseded RP2350 Coverage Gap Fill HLDs (V1..V11)` | row 16 | Phase 1.3 (Doc1) — kept separate so the file-rename diff is reviewable in isolation |
| C4 — `cleanup: drop stale dead-code annotations and fully-dead helpers` | rows 17–28 | Phase 1.4, Phase 2.1 (D2, D3, D4, D6, D7, D8) |

Each commit ends in a green workspace build + green test pass. C1 is the only commit with new tests; C2-C4 are pure compile-check.

**Rationale for putting Doc1 in its own commit:** `git mv` of 11 files makes a noisy diff that drowns C2's one-line hygiene changes. Splitting them lets the reviewer skim C2 in 30 seconds and review C3 as a pure rename block.

**Rejected ordering:** running C4 before C1 would trip `cargo test` in the middle of bug-fix landing if a deletion breaks an unrelated test by name collision. Order C1 → C2 → C3 → C4 ensures every step has a green test gate.
