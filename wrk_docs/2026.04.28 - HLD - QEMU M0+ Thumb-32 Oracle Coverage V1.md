# HLD — QEMU M0+ Thumb-32 Oracle Coverage V1

**Date:** 2026-04-28
**Author:** Arthur + Claude (opus 4.7)
**Supersedes:** `tech_debt.md` § "Thumb-32 subset not QEMU-differentially validated" (lines 597–613).

## 1. Problem statement

`qemu_diff_m0plus` is the cheap, CI-friendly oracle for the RP2040 ISA. Its `is_m0plus_safe` filter (`crates/mdpicoem-harness/src/bin/qemu_diff_m0plus.rs:292`) blanket-rejects every `TestCase` with `hw1.is_some()` — i.e. **every** Thumb-32 encoding. Phase 4.B shipped ~700 lines of Thumb-32 executor code in `crates/mdrp2040/src/core/execute_wide.rs` for the M0+ Thumb-32 subset (`BL`, `MRS`, `MSR`, `DSB`, `DMB`, `ISB`) backed only by hand-written unit tests. The QEMU oracle never exercises these paths.

The silicon oracle `probe_diff_rp2040` already admits this subset via `is_m0plus_silicon_safe` (`crates/mdpicoem-harness/src/bin/probe_diff_rp2040.rs:178`), but it requires a Pico debug probe attached to a Pico V1 / RP2040 board — useless for routine fuzz sessions or CI.

**Concrete symptom we want to catch.** A decode/flag/SYSm corner case in `execute_wide.rs` that happens to slip past hand-written unit tests but would fail a randomized differential. Examples of the kind of bug differential fuzzing catches and unit tests miss: SYSm read of unimplemented M0+ field returning the wrong "should be zero" pattern, BL with imm21 sign-extension off-by-one near ±2^20 boundaries, MSR write masking that mishandles a reserved bit.

**Key fact.** The QEMU oracle pins to QEMU's `cortex-m0` model (per `tech_debt.md:552–560`), not `cortex-m0plus` (which 10.2 doesn't ship). All six encodings in the M0+ subset (`BL`, `MRS`, `MSR`, `DSB`, `DMB`, `ISB`) are **plain ARMv6-M** — they exist on M0 too. QEMU `cortex-m0` will execute them. We do not need to switch CPU models.

## 3. Proposed design

The relaxed filter alone is not enough — both `run_qemu_side` and `run_emu_side` have no Thumb-32 plumbing today. Three pieces of work, all in `qemu_diff_m0plus.rs`:

### 3.1 Filter rewrite

Replace the body of `is_m0plus_safe` (`qemu_diff_m0plus.rs:292`) with a copy of `is_m0plus_silicon_safe`'s logic (`probe_diff_rp2040.rs:178–260`). The two filters happen to be identical for the M0+ ISA subset; intentional duplication is cheaper than premature abstraction (the soft constraints might drift — e.g. a future QEMU regression on a specific SYSm could force the QEMU-side filter to narrow further). ~50 lines duplicated, with shared *unit tests* as the consistency oracle, is the cheaper bet. If the filters track each other for ≥ 6 months, refactor then.

### 3.2 `run_qemu_side` — write hw1 + position BKPT

Today (`qemu_diff_m0plus.rs:340–341`):

```rust
gdb.write_mem(QEMU_M0PLUS_TEST_SLOT, &tc.opcode.to_le_bytes())?;
gdb.write_mem(QEMU_M0PLUS_TEST_SLOT + 2, &BKPT_BYTES)?;
```

For Thumb-32 cases `tc.hw1` is never written and `BKPT_BYTES` overwrites the slot where `hw1` should live. QEMU would execute `hw0` as a 16-bit instruction (or fault), then BKPT — `hw1` is invisible.

Replace with the shape used by `probe_diff_rp2040.rs:270–274` — build a small byte vector (`hw0`, optional `hw1`, BKPT) and write it as one call. Single-step semantics are unchanged: QEMU's GDB stub steps one instruction regardless of width.

### 3.3 `run_emu_side` — Thumb-32 dispatch

Today (`qemu_diff_m0plus.rs:428–432`):

```rust
let _cycles = if tc.needs_bus {
    core.execute_one_with_bus(tc.opcode, bus)
} else {
    core.execute_one(tc.opcode)
};
```

These take a single `u16`. `CortexM0Plus::execute_one_wide(_with_bus)(hw0, hw1)` exists at `crates/mdrp2040/src/core/mod.rs:240,247` but is never called.

Replace with the four-arm `match tc.hw1` dispatch from `probe_diff_rp2040.rs:388–403`.

### 3.4 Filter unit tests

Add a `mod tests` to `qemu_diff_m0plus.rs` mirroring the 9 tests in `probe_diff_rp2040.rs:744–945`. Same assertions, retargeted at `is_m0plus_safe`.

### 3.5 Tech-debt deletion

Delete `tech_debt.md:597–613` (the "Thumb-32 subset not QEMU-differentially validated" entry).

### 3.6 What we are NOT changing

- `crates/mdrp2040/src/core/execute_wide.rs` — the executor under test.
- `crates/mdpicoem-harness/src/thumb32_gen.rs` — encoders + curated cases already exist.
- `generate_all` / `generate_fuzz` — corpus is already wired.
- `BKPT_BYTES` constant — still 2 bytes; we just place it after `hw1` when present.

**Why no UndefOnSilicon-equivalent path on the QEMU side.** `probe_diff_rp2040` checks `classify_post_step_pc` after the step (`probe_diff_rp2040.rs:322`) because filter-gap escapes on real silicon can land in bootrom and silently dispatch a fault handler. On QEMU, a filter-gap escape produces a state diff against mdrp2040 anyway — the comparator already catches it. Adding a UndefOnSilicon-style early-return would just be a diagnostic shortcut; for ~50 expected diffs across a 100k fuzz session, plain comparator output is fine.

**Out of scope.**
- M33 Thumb-32 generators stubbed at `tech_debt.md:562–574` (mdrp2350 work).
- Any new MSR mask encodings (the mask=0b10 / NZCVQ hardcode in `enc_t32_msr` is documented and orthogonal to this work; if we want fuller mask coverage, that is a follow-up).
- Sharing filter code between the two oracles.
- Adding an MSP/PSP (sysm=8/9) test path — not in the existing generator, can be added later if the differential surfaces a need.

**Configuration.** No new env vars, no feature flags, no CLI surface change. The relaxed filter is unconditional.

## 4. Risk

**R1 — QEMU `cortex-m0` rejects an admitted encoding.**
If QEMU faults on, say, `MSR CONTROL,Rn` on M0 (it shouldn't, but ARMv6-M conformance varies), the harness reports a state diff (PC at fault handler vs. PC after instruction). Detection is automatic. Mitigation: smoke each of the six encoding shapes in step 5.1 below before running fuzz; if QEMU rejects a specific shape, narrow the QEMU filter only for that shape and document it in a comment.

**R2 — Real bugs in `execute_wide.rs`.**
The whole point. `--fuzz 10000` will surface them. Reproduce with `--seed`, fix in the executor, re-run.

**R3 — `gen_t32_misc_control` emits cases the new filter accidentally still rejects.**
Possible if the encoder pattern doesn't match the admit-list pattern bit-for-bit (e.g. `enc_t32_msr` produces hw1 = `0x8800 | sysm` whereas the admit pattern is `(hw1 & 0xFF00) == 0x8800` — these match but a future refactor could break this). Mitigation: step 5.2 logs admit/reject counts so a "0 admitted" outcome is loud.

**R4 — QEMU `cortex-m0` executes BL/barriers but with cycle behavior different from M0+.**
N/A. The QEMU oracle does not compare cycle counts (`tech_debt.md:556–558`). Architectural state only.

## 5. Test plan

**5.1 Smoke (one-shot, before fuzz).** Run the existing edge-cases path (`cargo run --release -p mdpicoem-harness --bin qemu_diff_m0plus`, no `--fuzz`). With the relaxed filter, the curated `gen_t32_misc_control` and BL cases from `gen_t32_branch` will flow through. Expect one of:
- All pass → proceed to 5.2.
- A specific pattern fails on every run → real emulator bug or QEMU divergence; investigate before fuzzing.

**5.2 Filter-counting sanity check.** A short ad-hoc dump (one print line in the harness, deleted before commit) verifying that "Thumb-32 admitted" is a positive number — e.g. ≥ 6 cases (BL × 2 + MSR/MRS PRIMASK + MSR/MRS CONTROL + barriers). Guards against R3.

**5.3 Filter unit tests.** `cargo test -p mdpicoem-harness --bin qemu_diff_m0plus`. The 9 mirrored tests must pass.

**5.4 Fuzz.** `qemu_diff_m0plus --fuzz 10000 --seed 1`, then scale to 100k. The fuzz path consumes `generate_fuzz_classes` (`qemu_diff_m0plus.rs` ~line 200), not `generate_all`. Its Thumb-32 buckets (`generate_fuzz_t32_alu`, `generate_fuzz_t32_mem` in `thumb32_gen.rs`) are M33-flavoured DP/multiply/load/store and are **all** rejected by the relaxed filter — so `--fuzz` mode admits **zero** Thumb-32 cases. It is therefore a **Thumb-16 regression gate**, confirming we haven't broken the pre-existing path. The actual differential signal for the M0+ Thumb-32 subset comes from `run_targeted` (the no-`--fuzz` mode), which exercises the ~12 curated cases that `gen_t32_branch` and `gen_t32_misc_control` admit through the filter. Randomising the M0+ T32 subset (BL imm21, MSR/MRS Rn/Rd within the admitted SYSm set) is listed in §7 as follow-up.

**5.5 Acceptance.**
- Every test from `mod tests` passes.
- `run_targeted` (no `--fuzz`) reports `OK` on every admitted case — this is where the new T32 coverage is validated.
- `--fuzz 100000` runs to completion with no diffs (regression gate; or any diffs are reproduced by `--seed` and either fixed or root-caused as a QEMU divergence and added to the filter as a narrow exception).
- Startup admit-count line shows a non-zero Thumb-32 admit count (sanity gate from §3 / Change 2 — guards against R3).

## 6. Estimate

- Filter rewrite (§3.1) + doc comment: 10 min.
- `run_qemu_side` Thumb-32 write (§3.2): 5 min.
- `run_emu_side` Thumb-32 dispatch (§3.3): 5 min.
- Unit tests mirrored (§3.4): 20 min.
- Smoke + 10k fuzz: ≤ 5 min wall.
- 100k fuzz: ≤ 30 min wall.
- Tech-debt deletion (§3.5): 1 min.

Single sitting. No commit-train, no phased rollout — three small co-located edits in one binary.

## 7. Follow-ups (not part of this HLD)

- **Randomised M0+ T32 generation.** Add an M0+-flavoured Thumb-32 generator (BL with random imm21 covering ±2^20 boundaries; MSR/MRS with random Rn/Rd over the admitted SYSm set {16, 20}; barriers across all option fields) so `--fuzz` mode becomes a deeper differential signal rather than a Thumb-16-only regression gate. Today the existing `generate_fuzz_t32_alu` / `_t32_mem` buckets are M33-only and are filtered out wholesale.
- Decide whether to add T32-class cases to `generate_fuzz_t32_alu`-style randomized generators for the M0+ subset. The corpus is small enough that randomized gen probably has low marginal value, but if 100k turns up nothing, that's a useful signal that hand-written cases plus existing classes cover the subset adequately.
- Backport the same filter change to any future M0+ oracle (e.g. a coverage-guided fuzzer if one is built).
- **MSR sysm=20 (CONTROL write) is admitted but unexercised.** `gen_t32_misc_control` emits MSR for sysm ∈ {16, 17, 19} only — sysm=20 is in the M0+ admit list but never generated. `execute_wide.rs`'s CONTROL-write semantics are not differentially validated by this work. Cheap fix: add a single MSR sysm=20 case to `gen_t32_misc_control` with `xpsr_mask: MASK_NO_FLAGS` (CONTROL is not in xPSR) and a defined R0 precondition.
- **MSR/MRS sysm=8/9 (MSP/PSP) unexercised.** The filter admits these (HLD §3.6 noted they're out of scope only because the existing generator doesn't emit them). Adding 4 cases (MSR/MRS × MSP/PSP) closes the M0+ banked-SP differential gap.
- **Per-case PASS print in `run_targeted`.** Today the smoke run prints `392/392 passed` with no per-case granularity. A `[T32 PASS] {case_name}` print whenever `tc.hw1.is_some()` would make future log captures auditable for "did the M0+ T32 cases actually run?" without inspection. ~3 lines.
