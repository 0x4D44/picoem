# HLD: Cycle and DualCore Timing Accuracy

**Date:** 2026-04-16
**Scope:** mdrp2350 cycle-timing fixes for 7 cycle oracle failures and 3 dualcore oracle failures
**Status:** Ready for implementation

---

## 1. Problem Statement

The `silicon_cycle_oracle_rp2350` and `silicon_dualcore_diff_rp2350` compare
per-iteration cycle costs (K-delta protocol, K_low=101, K_high=201) between
real RP2354 silicon and the mdrp2350 emulator. Ten cases fail at tolerance=0:

| Oracle | Case | HW | EMU | Delta | Direction |
|--------|------|---:|----:|------:|-----------|
| cycle | push_2_min_cost | 10 | 13 | -3 | EMU over |
| cycle | backward_branch_small | 13 | 11 | +2 | EMU under |
| cycle | backward_branch_large | 13 | 14 | -1 | EMU over |
| cycle | bank_contention_fetch_data_same | 9 | 11 | -2 | EMU over |
| cycle | bank_contention_fetch_data_diff | 9 | 11 | -2 | EMU over |
| cycle | ldm_8_reg | 17 | 18 | -1 | EMU over |
| cycle | back_to_back_alu | 14 | 16 | -2 | EMU over |
| dualcore | dualcore_load_same_bank | 7 | 8 | -1 | EMU over |
| dualcore | dualcore_load_diff_bank | 7 | 8 | -1 | EMU over |
| dualcore | dualcore_fifo_xfer | 10 | 15 | -5 | EMU over |

`nop_chain_8` (HW=11, EMU=16, delta=-5) is a known expected failure -- NOT addressed.

## 2. Measurement Framework and Calibration

### Per-iteration structure

Every case runs inside `MEASUREMENT_STUB`. The K-delta protocol cancels
per-invocation framing, leaving pure per-iteration cost:

```
per_iter = BLX_r6 + <seq_body> + BX_LR + SUBS_r7 + BNE_taken
```

Stub hot-loop instructions (halfword indices 12..14):

| Slot | Instruction | Address | Offset | Bank |
|------|-------------|---------|--------|------|
| [12] | BLX r6 | 0x2000_0118 | 0x118 | 6 |
| [13] | SUBS r7, #1 | 0x2000_011A | 0x11A | 6 |
| [14] | BNE -8 | 0x2000_011C | 0x11C | 7 |

Sequence body lives at CYCLE_SEQ_SLOT = 0x2000_1000 (bank 0).

### Calibration: `single_adds` (PASS at HW=EMU=7)

```
BLX r6        0x0118  bank6  [ns:BNE->BLX]     instr=1  bank6_wait=1  total=2
ADDS r0,r0,r1 0x1000  bank0  [ns:BLX->seq]     instr=1  bank_wait=0   total=1
BX LR         0x1002  bank0  [seq]              instr=1  bank_wait=0   total=1
SUBS r7,#1    0x011A  bank6  [ns:BXLR->stub]   instr=1  bank6_wait=1  total=2
BNE taken     0x011C  bank7  [seq]              instr=1  bank_wait=0   total=1
                                                                 Total = 7 ✓
```

Key observations:
- BLX fetch is non-sequential (target of BNE). Bank 6 penalty REAL.
- SUBS fetch is non-sequential (target of BX LR). Bank 6 penalty REAL.
- BX LR fetch at 0x1002 is sequential after ADDS. No penalty.
- BNE fetch at 0x011C is sequential after SUBS. No penalty.

Framing cost decomposition:
- `framing_excl_body` = BLX(2) + SUBS(2) + BNE(1) = 5
- `framing_incl_bxlr` = BLX(2) + BX_LR(depends) + SUBS(2) + BNE(1) = 5 + BX_LR

For single_adds: 5 + 1(BXLR) + 1(ADDS) = 7. ✓

### Current `sram_bank_wait` function

`crates/mdrp2350/src/bus/mod.rs:2321-2337`:

```rust
fn sram_bank_wait(addr: u32, burst: bool) -> u32 {
    if burst { return 0; }
    let offset = addr & 0x000F_FFFF;
    if offset < 0x8_0000 {

```

This adds +1 on every non-burst access to bank 2/6, including sequential
instruction fetches that the M33 prefetch buffer has already loaded.

## 3. Root Cause Analysis

Four distinct root causes.

### RC-A: Sequential fetch bank penalty (overcounts)

The M33 prefetch buffer services sequential instruction fetches without
re-arbitrating the SRAM bus. The emulator charges `sram_bank_wait` on
EVERY instruction fetch, including sequential ones.

**Rule:** bank 2/6 penalty applies to instruction fetches ONLY when the
fetch is at a non-sequential PC (branch target, exception entry). For
sequential PC advances (PC += 2 or PC += 4), the prefetch buffer absorbs
the penalty.

Note: this applies to INSTRUCTION fetches only. DATA accesses (via
LDR/STR) still incur the bank penalty because the D-bus has no prefetch
buffer.

**However**: looking at the calibration trace above, the bank-6 penalties
on BLX and SUBS ARE justified because they are non-sequential fetches.
The penalty on the 8 ADDS in `back_to_back_alu` includes 2 at bank 2
(0x1008, 0x100A) that ARE sequential and should NOT be penalized. This
accounts for the delta=-2 in back_to_back_alu.

### RC-B: Data-read bank penalty on PC-relative LDR (overcounts)

When `LDR Rt, [PC, #imm]` reads a literal from the same SRAM region as the
instruction stream, the D-bus data read hits `sram_bank_wait`. If the literal
lives in bank 2, the +1 penalty fires. But on the M33, the I-bus and D-bus
can access DIFFERENT banks simultaneously. When they access the SAME bank,
one stalls. When different, no stall.

For the bank_contention cases, the I-bus is fetching from bank 0 (the LDR
instruction itself is at 0x1000) while the D-bus reads from bank 2 (the
literal at 0x1008). Different banks -- no contention. The +1 penalty is wrong.

The root cause is that `sram_bank_wait` adds +1 for bank 2/6 as an absolute
penalty, rather than modeling it as a contention penalty between I-bus and
D-bus on the same bank. Since all the oracle sequences live in bank 0 for
instruction fetch, D-bus reads to bank 2 or 6 never contend with the I-bus.

**Rule:** Remove the `sram_bank_wait` +1 penalty on data reads entirely.
The penalty was originally intended to model I-bus/D-bus contention, but
the measurement data shows no observable contention in the sequence-in-loop
context. Both `bank_contention_fetch_data_same` and `_diff` produce
identical HW numbers (9), confirming zero contention signal.

### RC-C: PUSH formula for N<=2 (overcounts by 1)

`crates/mdrp2350/src/core/execute.rs:653-654`:
```rust
if count <= 2 { 2 * count } else { 1 + count }
```

For N=2, returns 4 instead of 3. The `2*N` special case was derived from
halt-step data that includes pipeline disruption from the debug halt/step
mechanism. In steady-state, PUSH follows `1+N` for all N.

### RC-D: Backward branch cost model (under- and overcounts)

`crates/mdrp2350/src/core/execute.rs:856-858`:
```rust
if (offset as i32) < -256 { 6 } else { 1 }
```

Binary threshold: 1 for small backward/forward, 6 for large backward.

1. Small backward branches are undercosted. Any backward branch flushes
   the prefetch buffer and requires a pipeline refill. Cost > 1.
2. Large backward branches are overcosted. The 6-cycle cost includes
   halt-step debug overhead.

### RC-E: STR to SIO costs 2, should cost 1

`crates/mdrp2350/src/core/execute.rs:506`: All STR variants return 2
regardless of target region. SIO (region 0xD) is single-cycle for stores
via the write buffer.

## 4. Proposed Fixes

### Fix 1: Remove `sram_bank_wait` entirely

**Files:** `crates/mdrp2350/src/bus/mod.rs`

**Change:** Make `sram_bank_wait` always return 0.

```rust
fn sram_bank_wait(_addr: u32, _burst: bool) -> u32 {
    0
}
```

**Rationale:** The bank 2/6 penalty model was derived from halt-step
measurements that include debug overhead. In the K-delta steady-state
measurement, neither the instruction-fetch penalty nor the data-access
penalty manifests:

1. Sequential instruction fetches are absorbed by the prefetch buffer.
2. Non-sequential instruction fetches at bank 2/6 branch targets DO
   exist, but the branch-target penalty is accounted for by the branch
   instruction's cycle cost (Fix 3), not by the fetch mechanism.
3. Data reads from bank 2/6 do not contend with I-bus fetches from
   different banks (confirmed by both contention test cases reading
   identically: HW=9=9).

The penalty was well-intentioned but measured the wrong thing. Removing
it outright is cleaner than adding a complex sequential-fetch tracker
that would be fragile and hard to test.

**Impact:** Removes unjustified +1 cycles on all bank 2/6 accesses.
Per-case savings:

| Case | Bank 2/6 penalties removed | Cycles saved |
|------|---------------------------|-------------|
| back_to_back_alu | 2x fetch at bank 2 (0x1008, 0x100A) | 2 |
| bank_contention_fetch_data_same | 1x data read at bank 2 (literal) | 1 |
| bank_contention_fetch_data_diff | 1x data read at bank 2 (literal) | 1 |
| ldm_8_reg | 1x data read at bank 2 (literal) | 1 |
| dualcore_fifo_xfer | 1x fetch at bank 2 (BX LR at 0x1008) | 1 |

But this also removes JUSTIFIED bank penalties:
- BLX at 0x0118 (bank 6): -1 per iteration on every case.
- SUBS at 0x011A (bank 6): -1 per iteration on every case.

These are non-sequential fetches where the penalty IS real. Removing
them would make `single_adds` go from EMU=7 to EMU=5, breaking the
calibration case.

**Conclusion: Full removal is wrong.** We need to keep the bank penalty
for non-sequential fetches and remove it for sequential fetches and
data reads. See Fix 1 (revised) below.

```rust
    bus.last_fetch_addr = if is_wide { pc.wrapping_add(2) } else { pc };
```

**Step 5:** When `populate_decode_cache` is called (cache miss), it now
computes `fetch_wait` from the bank of the PC address (Step 3). The
`is_sequential` check in `decode_execute` determines at dispatch time
whether to apply it. The cached `fetch_wait` is the RAW bank penalty
(0 or 1) -- it is always computed from the address, not from
sequentiality. The sequentiality check happens at dispatch time.

This means `populate_decode_cache` does NOT need to know about
`last_fetch_addr` -- it just stores the raw bank penalty. The dispatch
path applies it conditionally.

Update to Step 3: `populate_decode_cache` computes `fetch_wait` from
the address alone (no sequential check):

```rust
fn populate_decode_cache(&mut self, bus: &mut Bus, pc: u32) -> DecodedOp {
    bus.reset_extra_wait_states();
    let hw0 = bus.read16(pc);
    // ... fault checks ...
    let wide = is_wide(hw0);
    let hw1 = if wide { bus.read16(pc.wrapping_add(2)) } else { 0 };
    // ... fault checks ...

    // Compute raw bank penalty from the PC address.
    // bus.read16(pc) no longer accumulates sram_bank_wait (removed
    // in Step 2). We compute the fetch penalty directly.
    let fetch_wait: u8 = {
        let offset = pc & 0x000F_FFFF;
        if offset < 0x8_0000 {
            let bank = (offset >> 2) & 7;
            if bank == 2 || bank == 6 { 1 } else { 0 }
        } else { 0 }
    };

    // bus.extra_wait_states() may still have residual APB/XIP penalty
    // from the read16 call if fetching from non-SRAM regions.
    // Capture that separately.
    let extra_from_read = bus.extra_wait_states();
    bus.reset_extra_wait_states();

    // Build the cache entry with the raw bank penalty + any non-SRAM
    // fetch penalty.
    let total_fetch_wait = fetch_wait + extra_from_read as u8;

    // ... build DecodedOp with fetch_wait = total_fetch_wait ...
}
```

The M33 TRM says LDR to a zero-wait-state memory (SRAM) costs 2 cycles

can be hidden if the next instruction does not use the loaded register.

not consumed by the next instruction, 2 cycles if it is.

In the bank_contention sequences:
- `LDR r1, [PC, #4]` loads r1. Next instruction `LDR r0, [r1]` USES r1.
  Load-use penalty: 2 cycles.
- `LDR r0, [r1]` loads r0. Next instruction `BX LR` does NOT use r0.
  No load-use penalty: 1 cycle.

With this model: LDR_lit=2 + LDR_imm=1 + BX_LR=1 = 4. Still 1 too many.

### 5.9 (revised) dualcore_load_same_bank (HW=7, current EMU=8)

Core 0 seq: `LDR r0, [r1]` (r1=0x2000_1200, bank 0).

The current EMU=8 breaks down as:
```
BLX r6         0x0118  bank6  [ns:BNE]   1 + 1(bank6) = 2
LDR r0,[r1]    0x1000  bank0  [ns:BLX]   2 + 0        = 2
BX LR          0x1002  bank0  [seq]       1 + 0        = 1
SUBS r7,#1     0x011A  bank6  [ns:BXLR]  1 + 1(bank6) = 2
BNE taken      0x011C  bank7  [seq]       1 + 0        = 1
                                              Total    = 8
```

After Fix 1: No data-read bank penalty to remove (data at bank 0, no
penalty). No sequential fetch bank penalty to remove. EMU stays at 8.
Delta = -1.

The remaining -1 is the same as `single_adds`'s framing except with
LDR instead of ADDS. The LDR costs 2, ADDS costs 1. framing = 6.
HW body = 7 - 6 = 1. EMU body = LDR(2) + BXLR(1) = 3. No, wait:
BXLR is part of framing.

Actually: framing_excl_body = BLX(2) + SUBS(2) + BNE(1) = 5.
Body_incl_bxlr = LDR(2) + BXLR(1) = 3. Total = 5 + 3 = 8.
HW: 5 + body = 7. body = 2. So LDR + BXLR = 2.

On silicon, LDR costs 1 (not 2) when the loaded value is not used by
the next instruction. LDR r0, [r1] loads r0. BX LR does not use r0.
So LDR = 1 (no load-use penalty), BX LR = 1. Body = 2.

To fix this properly: LDR should return 1 when the next instruction
does not depend on the loaded register. But this requires look-ahead,
which is expensive.

Simpler: LDR to SRAM returns 1 + load_use_penalty. Without modeling
load-use, we can approximate by returning 1 for all LDR (matching the
common case where the load is not immediately consumed). This would
break other cases where load-use IS the bottleneck.

This is a deeper issue than the scope of this HLD. Accept delta=-1 for
these cases.

### Residual deltas

The 5 remaining cases have residual deltas of -1 or -2, caused by pipeline
overlaps that cannot be modeled with simple per-instruction cycle formulas:

1. **LDR load-use pipeline overlap** (bank_contention cases, dualcore cases):
   The M33 pipeline can overlap a load's writeback with the next instruction's
   fetch when there is no register dependency. Our LDR returns 2 uniformly;
   silicon returns 1 when no load-use conflict exists. Modeling this requires
   register-dependency tracking between consecutive instructions.

2. **PUSH/POP store-buffer overlap** (push_2_min_cost): The M33 write buffer
   drains PUSH stores in the background while POP loads execute, saving 2
   cycles for back-to-back PUSH+POP with N=2. Modeling this requires
   write-buffer state tracking.

These are Phase 2+ improvements documented in the recommendations below.

## 8. Risk Assessment

### Fix 1 risks

- **Regression on unit tests that check `bus.extra_wait_states()`:** Several
  tests in `crates/mdrp2350/src/tests.rs` (around line 5156) verify
  `bus.last_access_cycles()` and `bus.extra_wait_states()` after data reads
  to SRAM. Removing `sram_bank_wait` from data paths changes these. Update
  test expectations.

- **Decode cache invalidation:** The `fetch_wait` in the decode cache now
  stores the RAW bank penalty. The sequential check is at dispatch time.
  If an instruction at bank 2 is first reached via a branch (non-seq, +1)
  and later reached sequentially (+0), the cache entry's `fetch_wait=1` is
  correct for both cases because the dispatch path selectively applies it.
  No cache invalidation needed.

- **Performance:** Adding an `is_sequential` check in the hot decode_execute
  path. This is a simple integer comparison (`pc == last + 2 || pc == last + 4`),
  ~1-2 ns. Negligible compared to the instruction execution cost.

- **Bus default():** The `Bus::default()` used by `execute_one()` and
  `execute_one_with_bus()` must initialize `last_fetch_addr` to `u32::MAX`.
  These paths are used by unit tests that bypass `decode_execute`.

### Fix 2 risks

- **PUSH {R0,R1} halt-step regression:** The halt-step cycle oracle
  (`probe_diff_rp2350 --cycles`) measured PUSH{R0,R1} = HW 4, EMU 3.
  Changing EMU to 3 (=`1+2`) makes EMU match the old value. No regression.
  Actually: the old EMU was 3 (before the `2*N` fix was applied). Wait,
  current code has `2*count=4` for count=2. The old EMU was 3 (from `1+N`).
  The `2*N` was applied to MATCH the halt-step HW=4. Reverting to `1+N`
  would reopen the halt-step delta.

  **Mitigation:** The halt-step and K-delta oracles test different things.
  The K-delta oracle is the higher-fidelity measurement. Document the
  halt-step delta in tech_debt.md as a known artifact of the measurement
  mode, not an emulator bug.

### Fix 3 risks

- **QEMU differential tests:** `qemu_diff_m33` does not compare cycle
  counts, only register/memory state. No impact.

- **Forward branch cost unchanged at 1:** The `nop_chain_8` case already
  expects forward branches to cost 1. No change.

- **Backward conditional branches:** The fix only changes `thumb16_branch`
  (unconditional B). Conditional branches (`thumb16_cond_branch_svc`)
  currently return 1 for taken and 1 for not-taken. The BNE in the stub
  loop is a small backward conditional branch. Its cost should also be > 1
  per Fix 3's logic.

  **However:** `single_adds` calibrates at HW=EMU=7 with BNE costing 1.
  If we change BNE (conditional backward branch) to cost 3, single_adds
  breaks. Therefore: **do NOT change conditional branch costs.** The
  conditional branch's target prediction is better than unconditional
  branches because the M33 has a simple branch predictor that handles
  tight loops.

  The Fix 3 change applies ONLY to the unconditional `B` (T2 encoding)
  handler `thumb16_branch`. The conditional `B.cond` handler
  `thumb16_cond_branch_svc` remains at 1 cycle for taken branches.

### Fix 4 risks

- **STR to non-SIO regions unchanged:** The `if addr >> 28 == 0xD { 1 } else { 2 }`
  check only affects SIO. All other regions keep 2 cycles.

- **Thumb-32 STR.W paths:** Must also apply the region check. Grep for
  all Thumb-32 store instructions in `execute_thumb32.rs` that return a
  hardcoded 2.

## 9. Future Work (Phase 2)

The 5 residual-delta cases require deeper pipeline modeling:

1. **LDR load-use latency:** Track the destination register of loads and
   add +1 only when the next instruction reads that register. Requires
   light register-dependency analysis between consecutive instructions.

2. **Write-buffer drain overlap:** Track write-buffer occupancy and allow
   stores to be absorbed in 0 additional cycles when followed by loads.
   Affects PUSH+POP sequences.

3. **Branch target buffer (BTB) warmup:** In the first few iterations of
   a K-delta loop, branch targets are cold and incur the full fetch penalty.
   After warmup, the BTB absorbs the penalty. The K-delta protocol cancels
   this (warm iterations dominate), so this is not needed for oracle accuracy.

4. **Instruction prefetch buffer size:** Model the 4-word prefetch buffer
   explicitly instead of the binary sequential/non-sequential approximation.
   This would handle edge cases where a long instruction straddles the
   prefetch window boundary.

These are all significantly more complex than the fixes in this HLD and
should only be pursued if firmware-level timing fidelity demands it.
