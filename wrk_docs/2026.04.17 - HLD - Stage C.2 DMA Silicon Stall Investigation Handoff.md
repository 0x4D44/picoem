# Stage C.2 — DMA Silicon Stall Investigation (Hand-off HLD)

**Date:** 2026-04-17
**Origin:** Stage C of the silicon oracle infrastructure wave landed three
DMA scenarios with Thumb custom sleds + a major DMA CTRL bit-position
correction (RP2350 differs from RP2040 by 2 bits across all `[5:23]` fields).
Silicon re-verification revealed a **deeper bug** that the bit-position fix
exposed: silicon DMA stalls indefinitely despite correct CTRL field values.
Hand-off to a separate agent team.

**Parent journal:** `wrk_journals/2026.04.16 - JRN - Silicon Oracle Infra and DMA Sleds.md`

## State of the symptom

All three DMA scenarios (`dma_mem_to_mem_32bit`, `dma_chain_trigger`,
`dma_timer_paced`) hang silicon's core in BUSY-poll. Symptom evolved across the
investigation:

1. **Pre-Stage-C:** scenarios FAILed because DAP-write setup (debug port)
   didn't drive silicon's DMA bus-master port at all.
2. **Post-Stage-C sleds:** scenarios FAILed because emulator used RP2040
   CTRL bit positions; sleds wrote `0x001F_8039` which on silicon decoded as
   `TREQ_SEL=15` (PIO0_RX3, never asserted) instead of `TREQ_SEL=63` (FORCE).
3. **Post-bit-position-fix (commit `a7266bf`):** sleds now write `0x007E_0059`
   which decodes correctly on silicon. CPU runs the sled, `CTRL_TRIG` write
   is accepted, `BUSY=1` latches. **But BUSY never clears.** DMA accepted the
   trigger but transfers fail silently.

Failure point: PC=`0x2000_114A`, halfword [37] of the
`dma_mem_to_mem_32bit` sled — `ldr r2, [r1, #0x0C]` inside the BUSY-poll
loop. 5-second BKPT timeout fires.

## Hypothesis from the silicon-runner agent

> Silicon's RP2350 DMA engine requires bootrom-phase initialisation before
> AHB bus-master transfers complete (clock tree, bus fabric priority,
> ACCESSCTRL, or power-domain setup). `reset_and_halt` catches the CPU before
> the bootrom runs, leaving DMA's bus-master path in a partially-initialised
> state. The DMA controller accepts the trigger and asserts BUSY, but its AHB
> master transactions stall indefinitely.

Evidence:
- PIO custom sleds work — PIO uses APB writes from CPU + its own data path,
  no AHB bus-master.
- DMA needs the AHB bus-master port operational — this is the unique failing
  element.
- BUSY=1 (transfer accepted) + BUSY never clears = DMA accepted trigger but
  bus transactions fail.

This is a hypothesis — not verified.

## Investigation paths

### Path 1: Verify the bootrom-init hypothesis

Compare sled execution against an SDK-blinky-style firmware that does run DMA
successfully on silicon (after bootrom completes). What does the bootrom + SDK
init touch that the sled doesn't?

Candidate culprits (from RP2350 datasheet):
- **PSM (POWMAN)** — `0x4000_8000`. Power-on state machine; gates power to
  DMA, SRAM banks, peripherals. Bootrom releases these.
- **ACCESSCTRL** — `0x4006_0000`. Per-master, per-peripheral access masks.
  RP2350 default may be conservative; bootrom relaxes for DMA + bus masters.
- **Clock tree** — `0x4001_0000`. `clk_sys`, `clk_peri`, `clk_ref`. DMA may
  need clk_sys to be running on a non-ROSC source; or AHB needs `clk_sys`
  enabled.
- **Bus fabric priority** — `BUSCTRL` (`0x4006_8000`). Default arbitration
  may starve DMA's master port if CPU is in a tight poll.

### Path 2: Empirically isolate the gating register

Write a minimal sled that:
1. Reads `BUSY` (proves DAP/CPU access works).
2. Writes one byte through DMA channel 0 with TRANS_COUNT=1, TREQ=63,
   READ_ADDR=SRAM, WRITE_ADDR=SRAM+4.
3. Polls BUSY for 1000 cycles.
4. Reads back destination + a status register dump.

Iterate by progressively enabling candidate registers (PSM bits,
ACCESSCTRL bits, BUSCTRL priority) before the DMA trigger. The one that
moves the needle from "BUSY stuck" to "destination has 1 byte" is the
gating register.

### Path 3: Sled replays bootrom init prologue

Vendor a snippet of the RP2354 bootrom's pre-main initialisation (from the
official RP2350 bootrom source — already vendored elsewhere in the repo per
similar work for PicoGUS). Run it via the sled before the DMA trigger.
Heavy but unambiguous.

### Path 4: Don't `reset_and_halt`; let bootrom run, then halt

Modify the silicon oracle's reset strategy: instead of `reset_and_halt`
(which catches at reset vector), let the bootrom complete then halt at a
custom sentinel BKPT planted in SRAM. The sled then runs in an
already-initialised environment. Architectural change — affects ALL silicon
oracles, not just DMA.

## Suggested approach

Path 2 first (empirical isolation) → identify the gating register(s) →
either Path 3 (sled replay) or document the gap and Path 4 (orchestrator
change) for a future architectural revision.
