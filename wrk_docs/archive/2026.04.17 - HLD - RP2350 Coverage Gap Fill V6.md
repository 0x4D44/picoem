# 2026.04.17 — HLD — RP2350 Coverage Gap Fill V6

## §1 Goal

Close the Bucket A tranche of the 2026.04.17 coverage audit — the
peripherals that are (a) cheap to model, (b) directly verifiable against
real RP2354 silicon via `silicon_periph_diff_rp2350`, and (c) currently
STUB or PARTIAL-STORAGE. Ship each item with a new silicon-diff
scenario so the audit's "written but unverified" failure mode doesn't
reappear. Secondary goal: frame Buckets B/C/D as follow-on phases so a
reader can see the full plan without committing to it.

Target effort for Phase 1 (Bucket A): **~2 weeks** in the V5 cadence
(implement → review → apply → devil's advocate → commit per item).

## §2 Scope

### In scope — Phase 1 (Bucket A)

Six peripherals, register-level behaviour + one silicon-diff scenario
each:

| # | Peripheral | Base | Current | Target |
|---|---|---|---|---|
| 1 | SYSINFO | 0x4000_0000 | STUB | Fill remaining read-only fields to match silicon |
| 2 | XOSC startup | 0x4004_8000 | STUB (V5 §5.7 pins STABLE=1 at reset) | Post-enable STARTUP_DELAY modelled on cycle count; V5 §5.7 "stable at reset" preserved |
| 3 | ROSC COUNT | 0x400E_8000 | STUB | Deterministic COUNT countdown per enable |
| 4 | POWMAN COUNT/MATCH | 0x4010_0000 | STUB | AON counter advances; MATCH fires `POWMAN_IRQ_TIMER` (NVIC line 45) |
| 5 | GLITCH_DETECTOR | 0x4015_8000 | PARTIAL-STORAGE | ARM path readback; TRIG_STATUS stays zero |
| 6 | TBMAN | 0x4016_0000 | PARTIAL-STORAGE | PLATFORM mode selector correct |

Each item lands as: small behavioural model, unit tests, new
`silicon_periph_diff_rp2350` scenario in the `SCENARIOS` const at
`crates/mdpicoem-harness/src/silicon_scenarios.rs:1033`. Cargo
**minor** bump per item (1.8.3 → 1.9.x, matching V5 cadence).

**Previously-listed BUSCTRL perf counters removed from Phase 1** — on
closer inspection the "one event source" scoping requires a
datasheet-exact PERFSEL value and a Thumb-bytecode `custom_sled` for
the silicon scenario. Not the 2-day item I initially claimed. Moved
to Bucket B (§4).

### Out of scope (this HLD)

- **Bucket B** (IO_BANK0 funcsel routing, PADS_BANK0 effect, NVIC
  priority levels, IO_QSPI/PADS_QSPI, SHA-256 DMA hookup, OTP_CTRL) —
  Phase 2, each item gets its own small design note.
- **Bucket C** (QMI + XIP_CTRL/AUX, ACCESSCTRL/SAU/MPU) — Phase 3,
  each gets a dedicated HLD. Not ready to design here.
- **Bucket D** (USB, HSTX, ADC sample values) — Phase 4 or later,
  deferred until there's concrete firmware demand and a testable
  observable. Explicitly NOT in this plan.
- Cosmetic stubs (TRNG entropy, SHA-256 endianness validation,
  CORESIGHT_TRACE trace output, ROSC RANDOMBIT statistical quality) —
  no behavioural work planned.

### Non-goals

- No feature flags. No env-var gates. Each peripheral behaves the same
  way on every build.
- No backwards-compat layer for the pre-Phase-1 stub behaviour.
  Firmware that worked before keeps working; firmware that relied on
  the stub's specific wrongness (e.g. reading STATUS=0xFF from XOSC)
  needs to be fixed, not accommodated.
- No performance optimisation. Use plain u32 counters, simple tick
  callbacks. If something ends up hot, optimise in a later pass.

## §3 Phase 1 — per-item design

Each sub-section follows the same shape: current state, target
behaviour, silicon observable, datasheet reference, implementation
sketch.

### §3.1 SYSINFO — fill read-only fields

**Current** (`bus/peripherals.rs:48`): returns hardcoded CHIP_ID
(0x0000_0002), PACKAGE_SEL (0), PLATFORM (1). No storage; three
constants.

**Target**: populate remaining documented read-only fields
(GITREF_RP2350, PLATFORM bits, CHIP_ID revision field) with values that
match real RP2354 silicon. All fields stay read-only.

**Silicon observable**: one probe-rs read of each register at reset;
diff the 32-bit value against silicon.

**Datasheet**: RP2350 §5.1 SYSINFO register map.

**Implementation**: extend the existing match arm in
`sysinfo_read(offset)` with the new offsets. Values are constants,
captured once from silicon and hardcoded. Zero state; zero storage.

### §3.2 XOSC startup latency

**Current** (`bus/peripherals.rs:259`): STATUS reads fixed
`STABLE | ENABLED`; STARTUP_DELAY register accepted but ignored. V5
§5.7 pinned `STATUS.STABLE = 1 at reset` as a load-bearing invariant
for bootrom paths — there is a regression test protecting this
(`"XOSC.STATUS.STABLE must read 1 at reset (V5 §5.7)"` in
`peripherals/phase1_tests.rs:183`).

**Target**: STATUS.STABLE defaults to 1 at reset (preserving the V5
invariant; firmware that reads it without touching CTRL still sees
stable). On firmware-driven CTRL.ENABLE transition 1→0→1, arm a
cycle-count target at `master_cycle + startup_delay * 256`. STATUS.
STABLE reads 0 until the target, then 1. Firmware that only reads
STABLE never sees it change.

**Silicon observable**: write CTRL.ENABLE=0, write CTRL.ENABLE=1,
poll STATUS until STABLE; diff the cycle at which STABLE first
reads 1. Scenario must explicitly cycle ENABLE — otherwise the
V5-stable reset state dominates.

**Datasheet**: RP2350 §8.2 XOSC STARTUP register. Open question §9:
is STARTUP_DELAY counter sys-clk-paced or xosc-paced?

**Implementation**: add `xosc_stable_at_cycle: Option<u64>` to
`PeripheralState`. Mirrors the `pll_sys_lock_at_cycle` pattern from
Phase 4. `None` at reset = "stable by default" (V5 semantics);
`Some(target)` after firmware disables/re-enables. No new struct.

### §3.3 ROSC COUNT

**Current** (`bus/peripherals.rs:220`): COUNT reads 0 always;
RANDOM/RANDOMBIT read 0.

**Target**: COUNT is an 8-bit countdown. Writing COUNT loads it; each
sys_clk-paced ROSC tick decrements it. Reads return current value.
When COUNT reaches 0 it stays at 0 until next write.

**Silicon observable**: write COUNT=0xFF, run N cycles, read COUNT.
Expected: 0xFF - N (clamped). Diff.

**Datasheet**: RP2350 §8.3 ROSC COUNT.

**Implementation**: plain u8 field plus a write-arm hook. Tick path
already iterates peripherals per cycle; hook into the existing ROSC
branch. Do NOT model ROSC frequency — COUNT advances per sys_clk,
which is a documented approximation per §9 below.

Skip RANDOM / RANDOMBIT (Bucket D — statistical output not
silicon-diffable).

### §3.4 POWMAN COUNT / MATCH

**Current** (`peripherals/powman.rs:59`): COUNT and MATCH are storage
only; they never advance. warn-once on read.

**Target**:
- COUNT advances at 1 tick per the POWMAN clock source (default: XOSC
  DIV4, so 3 MHz on a 12 MHz XOSC — datasheet confirms in §9).
- ARCHSEL / AON_DRIVE / RTC pins remain storage-only (Bucket D).
- MATCH fires **`POWMAN_IRQ_TIMER` (NVIC line 45)** when COUNT ==
  MATCH and MATCH_EN is set. One-shot — IRQ asserts, firmware clears.
  `POWMAN_IRQ_POW` (line 44) stays unwired — no power events modelled.

**Silicon observable**: write MATCH=K, enable, wait N cycles; expect
NVIC ISPR bit 45 set after K cycles and COUNT advancing linearly.
Observable set is `(POWMAN_COUNT, 0xFFFF_FFFF)` and
`(NVIC_ISPR + (45/32)*4, 1 << (45%32))`.

**Datasheet**: RP2350 §12.8 POWMAN; IRQ table in
`2026.04.15 - HLD - RP2350 Peripheral Coverage V1.md` lines 346-347;
constants at `crates/mdrp2350/src/irq.rs:121-123`.

**Implementation**: add `count: u64`, `match_val: u64`,
`match_enable: bool` to `Powman`. Drive from
`tick_peripherals(cycles)` like TIMER0/1. Drop the warn-once on
COUNT/MATCH — they're real now. Keep warn-once on ARCHSEL /
AON_DRIVE. Route IRQ via `raise_irqs_u64(1u64 << 45 % 64)`
(POWMAN_IRQ_TIMER).

### §3.5 GLITCH_DETECTOR ARM readback

**Current** (`peripherals/inert.rs:47`): HashMap-storage;
STATUS.ARM forced 0 on read; TRIG_STATUS W1C.

**Target**: STATUS.ARM reads back what was written to CTRL.ARM.
TRIG_STATUS stays at 0 forever (no glitch on emulator). No IRQ.

**Silicon observable**: write CTRL.ARM=1, read STATUS.ARM, expect 1.
Read TRIG_STATUS, expect 0.

**Datasheet**: RP2350 §13.4 GLITCH_DETECTOR.

**Implementation**: replace the forced-0 in the HashMap read path
with a masked readback of the written value. 10-line change.

### §3.6 TBMAN PLATFORM

**Current** (`peripherals/inert.rs:45`): HashMap storage only.

**Target**: PLATFORM field reads 0b01 (real silicon), matching
RP2354 observable. Remaining bits zero; read-only.

**Silicon observable**: one-shot read at reset.

**Datasheet**: RP2350 §13.5 TBMAN.

**Implementation**: hardcode the PLATFORM bits in the read path.
Small enough to stay inside `peripherals/inert.rs` without a new
module.

### §3.7 BUSCTRL — moved to Bucket B

Original plan scoped BUSCTRL to "one event source" + counter
register surface. Removed from Phase 1 on self-review because:

- The "PERFSEL = everything" selector I specified may not exist on
  silicon. RP2350 §4.8 lists specific event sources (DMAC contended,
  SRAM N access, etc.); I don't have a datasheet-exact shortcut.
- The silicon scenario needs a `custom_sled` with a Thumb-bytecode
  loop producing a known MMIO-access count. Not the 2-day item I
  initially claimed.

Re-land in Phase 2 (§4) with a proper datasheet-grounded PERFSEL
mapping and a hand-authored measurement sled.

## §4 Phase 2 — Bucket B outline

Not designed in detail here. Each item will get its own short design
note when it lands. Sketch:

- **IO_BANK0 funcsel routing + PADS_BANK0 drive effect** — the
  "invisible gap": peripheral outputs (UART0 TX, I2C SDA, SPI SCK)
  must route through GPIO_CTRL.FUNCSEL to reach observable pins.
  Today they don't — only SIO GPIO reaches pins. Design work: every
  peripheral's output needs a "to-pin" callback gated by FUNCSEL.
  Silicon-oracle-testable via GPIO pin readback. Probably 1-2 weeks.

- **NVIC priority levels + BASEPRI** — extend `bus/ppb.rs` NVIC with
  full ARMv8-M priority model: 8-bit priority per interrupt, priority
  grouping via AIRCR.PRIGROUP, BASEPRI masking, priority comparison
  on pending. Integrates with existing `silicon_isr_diff_rp2350`.
  ~1 week.

- **SYSCFG.PROC_CONFIG.PROC1_RESET** — currently PARTIAL-STORAGE
  (dedicated `SysCfg` struct at `peripherals/inert.rs:58`). Firmware
  uses PROC_CONFIG to hold/release core 1. Oracle-testable: write
  PROC1_RESET=1, observe core 1 stops advancing; write 0, it resumes.
  ~2 days.

- **BUSCTRL perf counters** — register surface + one datasheet-exact
  event source with a Thumb-bytecode measurement sled. Moved here
  from V6 Phase 1 after self-review (§3.7). ~1 week.

- **IO_QSPI + PADS_QSPI** — same shape as IO_BANK0 but smaller.
  Only valuable after QMI (Bucket C).

- **SHA-256 DMA hookup** — connect existing SHA compress path to
  DMA treq/done. Days.

- **OTP_CTRL release-from-reset** — the OTP data plane works; the
  control plane is held in reset. Release fixture + register model.

Phase 2 starts once Phase 1 ships. No HLD commitment yet.

## §5 Phase 3 — Bucket C scope

Needs dedicated HLDs. Not designed here.

- **QMI + XIP_CTRL/AUX** — flash interface stack. QSPI command issue
  + XIP cache lines + stream DMA. Write-via-XIP + read-via-direct
  silicon diff. 2-3 weeks after HLD.
- **ACCESSCTRL + SAU + MPU** — ARMv8-M security stack. Register state
  easy; enforcement (Secure→NS fault) needs careful fixtures.

## §6 Phase 4 — deferred

- **USB** — defer. Per the coverage audit §5.2, silicon observable is
  not on SWD; in-process mock host tests our impl against itself, not
  silicon. Revisit when a concrete USB firmware target appears.
- **HSTX** — defer. Pixel stream requires HDMI capture hardware.
- **ADC sample values** — defer. Analog input non-deterministic
  without on-board signal generator.

## §7 Silicon oracle extensions

Phase 1 adds seven scenarios to `silicon_periph_diff_rp2350`. Each
follows the existing pattern (MMIO setup → cycle window → observable
read → diff). No new oracle infrastructure needed.

The `custom_sled` extension mechanism (per CLAUDE.md §Testing Topology)
handles items that need more than a plain register read — e.g.
BUSCTRL's "run N MMIO accesses" needs a measurement stub on silicon.
Reuse the existing cycle-oracle measurement stub pattern.

No new oracle binaries. No new infrastructure.

## §8 Landing plan

Per-item cadence matches the V5 gap fill (which closed 2026-04-17):
implement → code-review → apply-feedback → devil's-advocate → commit.
One item per cycle, ~1 day each for items 1–5, ~2 days for item 6
(POWMAN COUNT/MATCH has the most moving parts — per-cycle tick +
IRQ routing).

Order (by increasing surface area, so early wins build momentum):

1. **SYSINFO** — smallest change, no new state.
2. **TBMAN** — one read path.
3. **GLITCH_DETECTOR** — register readback fix.
4. **ROSC COUNT** — simple countdown.
5. **XOSC startup** — mirrors existing PLL lock pattern; preserves
   V5 §5.7 "stable at reset" invariant (§3.2).
6. **POWMAN COUNT/MATCH** — counter + `POWMAN_IRQ_TIMER` routing.

Each commit is self-contained: behaviour + unit tests + silicon-diff
scenario. Cargo **minor** bump per item (1.8.3 → 1.9.0 → 1.10.0 →
1.11.0 → 1.12.0 → 1.13.0 → 1.14.0; matches V5 cadence 1.0 → 1.7
over 7 steps).

Final step: plan-vs-implementation audit, same as V5 §10 item 7.

**Silicon-validation gate.** Each item's scenario is added to
`SCENARIOS` in `crates/mdpicoem-harness/src/silicon_scenarios.rs`
and compiles in CI, but actual silicon validation requires Arthur to
run `silicon_periph_diff_rp2350 --filter <name>` on hardware
(Pico probe + RP2354 board). CLAUDE.md confirms these binaries are
"not for CI". Work-in-progress items are shippable without a green
silicon run *for the relevant scenario only*; a V6-closure pass
should re-run all six scenarios before declaring the phase complete.

## §9 Open questions for datasheet confirmation

Flag at implementation time, resolve at amendment-gate time (same
pattern as V5 §9):

- XOSC STARTUP_DELAY register: is the counter sys-clk-paced or
  xosc-paced? Assumption: sys-clk-paced (matches how the existing
  PLL lock delay works).
- ROSC COUNT: what is the decrement rate in the emulator? Silicon
  uses ROSC itself, which we don't frequency-model. Assumption:
  sys_clk-paced is close enough for firmware timing measurements.
- POWMAN clock source: confirmed XOSC DIV4? Datasheet §12.8.3 likely
  answers.
- BUSCTRL PERFSEL "everything" — is there a single select value
  that counts all bus accesses, or is this actually three separate
  selects (AHB read, AHB write, APB)?
- TBMAN PLATFORM: is 0b01 the right value for RP2354, or is the
  encoding different?

## §10 Non-obvious design decisions

- **No tracing on the new hot paths.** SYSINFO / TBMAN / GLITCH
  reads are cold; no instrumentation. XOSC stable transition,
  POWMAN MATCH, and BUSCTRL counter saturation get `debug!` at
  lifecycle events only (per CLAUDE.md tracing guide).
- **No new Cargo features.** Everything is always-on.
- **Drop the warn-once on POWMAN COUNT/MATCH reads** — they're real
  now. Keep the warn-once on ARCHSEL / AON_DRIVE (still storage-only).
- **Reuse existing peripheral modules where possible.** SYSINFO,
  XOSC, ROSC stay in `bus/peripherals.rs` (they're inline register
  maps, not worth a module each). POWMAN stays in
  `peripherals/powman.rs`. BUSCTRL gets a new module only because
  it carries state.

## §11 Acceptance criteria

Phase 1 ships when:

1. All 6 items landed (BUSCTRL de-scoped to Bucket B per §3.7).
2. Unit tests cover each behavioural claim.
3. Each item has at least one `silicon_periph_diff_rp2350` scenario
   added to the `SCENARIOS` const. Compilation is required; actual
   silicon pass is a manual gate (see §8 silicon-validation gate).
4. No regression in the current **1162-test** lib baseline (was 966
   at V5 closure; +196 tests landed since on other workstreams).
5. `cargo build --release` clean across workspace.
6. The audit matrix (`wrk_docs/2026.04.17 - RP2350 Peripheral Coverage
   Audit.md`) gets updated: STUB rows for the 6 items move to PARTIAL-
   BEHAVIOUR or FULL; each gains an "oracle-coverage = YES" note.

## §12 Dependencies

- `hello_dma_firmware_completes_transfer` investigation: **resolved**
  before V6 started. The failure was a stale `hello_dma.bin` built
  against the RP2040 DMA CTRL bit layout; a concurrent agent
  regenerated it (commit `b67df6b`). DMA implementation was never
  wrong. No priority shift for V6.
- Concurrent: RISC-V Hazard3 track (other agent). No expected
  collision — Phase 1 touches only peripheral decoders and the POWMAN
  NVIC line, none of which the RISC-V track uses.

## §13 What this HLD is NOT

- Not a V7 teaser. Phase 2 design happens when Phase 1 ships.
- Not a refactor of the existing peripheral modules. Smallest change
  to satisfy each §3 item.
- Not a full BUSCTRL implementation — §3.7 is deliberately scoped
  to the counter surface + one event source.
- Not a rollback plan. Dev sandbox, no migration.
