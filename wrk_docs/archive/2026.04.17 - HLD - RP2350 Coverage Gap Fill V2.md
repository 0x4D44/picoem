# RP2350 Coverage Gap Fill — HLD V2

**Date:** 2026-04-17
**Supersedes:** V1 (2026-04-17). Round-1 review team: silicon-fidelity, Rust-idiom, testing, simplicity, devil's-advocate. V2 resolves their findings and records tie-break decisions. See §14.
**Companion audit:** `wrk_docs/2026.04.16 - HLD - RP2350 Feature Coverage Audit.md`.
**Related:** `wrk_docs/2026.04.15 - HLD - RP2350 Peripheral Coverage V5.md` (existing roadmap; this HLD extends it with the audit follow-up bucket).

## 1. Problem

The audit surfaced four classes of finite gap. V1 addressed three of them. V2 adds the fourth, which the devil's advocate flagged as the single biggest miss in V1:

1. **Silent inert-register reads/writes at unmodelled addresses** — any MMIO access not matched by a peripheral module hits `HashMap<u32, u32>` at `bus/mod.rs:231`.
2. **One known wrong-address bug** — the failing `ticks_timer0_retarget_halves_rate` silicon scenario.
3. **Interpolator dead storage** — `sio/mod.rs:45`.
4. **Missing peripherals** — roughly a dozen register blocks.
5. **(NEW)** **Inert-but-known registers inside modelled peripherals** — DMA BSWAP, CRC sniffer (`SNIFF_CTRL`/`SNIFF_DATA`), DMA HIGH_PRIORITY, PWM DREQs. V1's warn mechanism does not cover these because their containing peripheral is modelled; the warn only fires on the HashMap fallthrough. (Audit §5, §7 recommendation 2.)

## 2. What is out of scope

- **Security enforcement** (SAU / MPU / ACCESSCTRL actually gating bus accesses) — needs its own HLD; cross-cutting.
- **Cycle-model fixes** — each `tech_debt.md` entry is its own investigation.
- **Bootrom execution** — needs an RP2350 ROM binary and signed-boot policy decisions.
- **RISC-V Hazard3** — a second emulator; separate work programme.
- **USB, HSTX, TMDS** — engineering-week-scale; each gets its own HLD.
- **No migration / back-compat / feature flags / env vars / trait abstractions.** Dev sandbox.
- **No silicon-session for interpolator calibration as a blocking gate** — §6 explains why.

## 3. Approach at a glance

Match the existing `peripherals/mod.rs` inherent-methods convention exactly. New peripherals are plain structs, dispatched from match arms on `Bus::read32` / `Bus::write32`. APB aliases route through `apply_alias_rmw`. No trait, no generic abstraction, no new cross-cutting infrastructure beyond two `Bus` fields (warn set and watchdog-reset flag).

## 4. Part A — Inert-register observability

### A.1 Warn-once on HashMap fallthrough

**Change.** Add one field to `Bus`:

```rust
pub struct Bus {
    // … existing fields …
    warned_addrs: std::collections::HashSet<u32>,
}
```

At every HashMap fallthrough site in `Bus::read32` / `Bus::write32` (`bus/mod.rs:1280`, `:1549`, `:1559`, `:1692`, `:1952`, `:2047`), emit a single `tracing::warn!` per unique word-aligned address:

```rust
if self.warned_addrs.insert(word_addr) {
    tracing::warn!(
        addr = format_args!("{:#010X}", word_addr),
        "unmodelled MMIO access"
    );
}
```

**Design decisions (V2 tie-breaks):**

- *No PC field.* V1 proposed `last_fetch_pc: u32` as a new `Bus` field populated by each core's fetch path. The simplicity and Rust reviewers both objected: the field does not exist today, wiring it touches both cores' fetch loops, and the debugging benefit over "address alone" is marginal. **Cut.** If a specific future failure needs PC, add then.
- *HashSet, not counter-capped.* The simplicity reviewer suggested a fixed-capacity counter (e.g. "first 10 unique"). But there is no test or firmware run where a set of unique unmodelled addresses grows large enough to matter. HashSet is simpler to reason about.
- *One shared set across all fallthrough sites.* `HashSet::insert` returns `false` on duplicate regardless of which caller inserted — the set is therefore address-unique globally, which is the correct semantic.

**Dependency.** Requires `tracing` (already used workspace-wide). No new Cargo dependency.

**Testing.** One unit test writes to an actually-unmodelled address — **`0x400F_8000` (SHA-256 base, pre-Part D.8)** per `silicon_scenarios.rs` red-path cases — captures emitted events with `tracing::subscriber::with_default` + `tracing-subscriber`'s test utilities, and asserts exactly one `WARN` for that address across two writes. (V1 used `0x4010_0000`, which is TICKS — modelled. Testing reviewer caught it.) Add `tracing-subscriber = "0.3"` as a `[dev-dependencies]` entry in `crates/mdrp2350/Cargo.toml`; do not add to main deps.

### A.2 Warn-on-inert-bit convention for modelled peripherals (new in V2)

V1 only warned on unmodelled addresses. The devil's advocate pointed out the systemic miss: when a peripheral is modelled but a *specific register bit* inside it has no side effect, the warn never fires. This is the audit's single biggest concrete vulnerability (§5 "Plumbed ≠ enforced").

**Scope for V2:** only the bits explicitly called out by the audit §4.3, not every stub in the codebase:

| Peripheral | Inert register / bit | Action on write |
|---|---|---|
| DMA `CHn_CTRL` | `BSWAP` (bit 22) set | warn-once per channel |
| DMA `SNIFF_CTRL` | `EN` (bit 0) set | warn-once |
| DMA `SNIFF_DATA` | any write | warn-once |
| DMA `CHn_CTRL` | `HIGH_PRIORITY` (bit 1) set | warn-once |
| PWM `CHn_CSR` / `DMA` | any DREQ-enabling bit set | warn-once per slice |
| POWMAN `ARCHSEL` (E.1) | write changing value to non-Arm | warn-once |

**Implementation pattern.** Each peripheral module adds a small `HashSet<u32>` (or equivalent single-bit flag where "per channel" isn't needed) to track first-write-per-site. No shared infrastructure — each peripheral's convention stays self-contained.

**Why a convention, not infrastructure.** A per-register warn framework is scope creep. A documented convention plus six targeted sites is surgical.

### A.3 TICKS `0x81C` alias bug

The failing silicon scenario `ticks_timer0_retarget_halves_rate` writes to the alias-2 (BITSET) form of TIMER0's CTRL at `TICKS_BASE + 0x81C`. `TicksRegs::write32` receives `offset` already 12-bit-masked by the bus layer (`bus/mod.rs:2114`); the bug is in `ticks.rs`'s internal strict-offset check, which refuses anything outside `0x00..=0x47`.

**Fix.** Change the internal range gate in `ticks.rs` to mod the offset against the domain stride block (`offset & 0x7F` is what the existing `decode_offset` already does — verify path) before the domain-index decode. One-line change, already partly present; the Rust-idiom reviewer confirmed the code is "90% there".

**Testing.** Enable the existing `ticks_timer0_retarget_halves_rate` silicon scenario; confirm it passes. No new scenario.

## 5. Part B — Interpolator CTRL semantics

### B.1 Rewrite

Replace `interp: [[u32; 32]; 2]` in `sio/mod.rs:45` with a dedicated struct per interpolator instance. Two instances per core, held in the existing `Sio` struct as `interp0: [Interp; 2]` (one per core), `interp1: [Interp; 2]`.

```rust
// sio/interp.rs
pub struct Interp {
    pub accum:      [u32; 2],          // ACCUM0, ACCUM1
    pub base:       [u32; 3],          // BASE0, BASE1, BASE2
    pub ctrl_lane:  [u32; 2],          // CTRL_LANE0, CTRL_LANE1
    // OVERF flags live in CTRL_LANE0 bits [23:25] per datasheet.
}
```

Register map within a single interpolator (datasheet §2.7, all offsets relative to interp base `0x80` or `0xC0` inside the SIO window):

| Offset | Register          | Notes |
|--------|-------------------|-------|
| 0x00   | ACCUM0            | RW |
| 0x04   | ACCUM1            | RW |
| 0x08   | BASE0             | RW |
| 0x0C   | BASE1             | RW |
| 0x10   | BASE2             | RW |
| 0x14   | POP_LANE0         | RO, reads compute result and update ACCUMn |
| 0x18   | POP_LANE1         | RO, as above |
| 0x1C   | POP_FULL          | RO, as above |
| 0x20   | PEEK_LANE0        | RO, computes result, no side effects |
| 0x24   | PEEK_LANE1        | RO |
| 0x28   | PEEK_FULL         | RO |
| 0x2C   | CTRL_LANE0        | RW (write lane CTRL; read CTRL + OVERF bits) |
| 0x30   | CTRL_LANE1        | RW |
| 0x34   | ACCUM0_ADD        | W, writes ACCUM0 += value & 0xFFFFFF |
| 0x38   | ACCUM1_ADD        | W |
| 0x3C   | BASE_1AND0        | W, writes BASE0 and BASE1 as low/high 16 bits |

Dispatch in `sio/mod.rs` was at `sio/mod.rs:107` (read) and `:148` (write): swap the raw-storage arms for `self.interp[core][idx].read(offset_rel)` where `idx = (offset - 0x80) >> 6` and `offset_rel = (offset - 0x80) & 0x3F`.

### B.2 CTRL semantics

Per datasheet §2.7 bit fields on each CTRL_LANEn:
- SHIFT (bits [4:0]): shift raw input right by N.
- MASK_LSB (bits [9:5]): lane-result low bit to keep.
- MASK_MSB (bits [14:10]): lane-result high bit to keep.
- SIGNED (bit 15): sign-extend result from MASK_MSB.
- CROSS_INPUT (bit 16): use the *other* lane's ACCUM as this lane's raw input.
- CROSS_RESULT (bit 17): this lane's result comes from the other lane's arithmetic.
- ADD_RAW (bit 18): on POP, ACCUM update uses pre-shift raw input (else: shifted+masked).
- FORCE_MSB (bits [20:19]): force bits [31:30] of result.
- BLEND (bit 21, INTERP0 only): lane1 is an α-blend fraction over lane0 base.
- CLAMP (bit 22, INTERP1 only): lane0 result clamped to [BASE0, BASE1].
- OVERF0/OVERF1/OVERF (bits [23:25]): sticky overflow from signed arithmetic; W1C via CTRL_LANE0 write.

### B.3 Testing (revised from V1)

**V1 proposed six silicon scenarios calibrated against RP2354 silicon.** Three reviewers objected:
- *Testing:* end-state oracle cannot sample POP reads mid-sled; destructive reads defeat post-hoc sampling without a custom sled harness.
- *Simplicity:* silicon calibration is work-deferred-by-default; implement against the datasheet spec, use hand-computed unit tests, reach for silicon only if/when real firmware demands it.
- *Devil's advocate:* calibration session gates landing, which gates Part A's value.

**V2 decision:** unit tests only. Use hand-computed input/output pairs derived directly from the datasheet bit-field algebra (BLEND, CLAMP, SHIFT, MASK, signed/unsigned, CROSS_*). Cover one feature per test, plus two composite tests (BLEND+SHIFT, CLAMP+CROSS). If a real firmware scenario requires interp semantics and a unit test turns out to be wrong, land a silicon scenario then — the HLD does not need to pre-empt that.

**What we give up.** Unit tests cannot catch silicon-specific quirks not documented in §2.7. Accepted risk — interp arithmetic is well-specified and simple.

## 6. Part C — Duplicate peripheral instances (UART1 / SPI1 / I2C1)

### C.1 Layout

`Bus` holds `uart: [Uart; 2]`, `spi: [Spi; 2]`, `i2c: [I2c; 2]`. Each peripheral module hoists the base address out of the struct: base is passed in at construction.

```rust
// bus/mod.rs construction
uart: [
    Uart::new(IRQ_UART0_IRQ, DREQ_UART0_TX, DREQ_UART0_RX),
    Uart::new(IRQ_UART1_IRQ, DREQ_UART1_TX, DREQ_UART1_RX),
],
```

The IRQ / DREQ constants already exist in `irq.rs` / `dreq.rs`. The Rust reviewer caught that V1 did not specify the constructor call site — fixed here.

### C.2 Dispatch

```rust
match addr & 0xFFFF_F000 {
    UART0_BASE => self.uart[0].read32(addr & 0xFFF),
    UART1_BASE => self.uart[1].read32(addr & 0xFFF),
    // …
}
```

Direct `match`-on-base is as fast as field dispatch in practice (compiler folds both paths) and keeps the bus arm flat. No computed index, no array-of-bases indirection.

### C.3 Testing

**V1 proposed duplicating every existing scenario for the `_1` instance.** The testing reviewer cut this as overkill: the behavioural logic is shared, only address decode differs. **V2:** one scenario per peripheral that proves instance routing, naming the `_1` base and asserting the same quiescent state as `_0`. No full duplication. If instance-specific behaviour ever appears (it won't on these peripherals), add then.

## 7. Part D — Simple peripherals

### D.1 Storage-only cluster: SYSCFG + TBMAN + GLITCH_DETECTOR

V1 gave each its own module. The simplicity reviewer consolidated. **V2:** a single `peripherals/inert.rs` file containing one `struct SysCfg`, `struct Tbman`, `struct GlitchDetector`, each wrapping a `HashMap<u32, u32>` or a small fixed-register storage bank with the datasheet's RO defaults. Dispatched from three bus match arms.

- **SYSCFG** — storage.
- **TBMAN** — storage.
- **GLITCH_DETECTOR** — storage; `STATUS.ARM` forced to 0 on read (emulator cannot glitch); `TRIG_STATUS` W1C using `apply_alias_rmw`.

### D.2 PSM

Storage for `FRCE_ON`, `FRCE_OFF`, `WDSEL`. `DONE` mirrors `FRCE_ON` with a single note in the module doc: *"Real silicon has per-subsystem power-ramp latency. Emulator uses instant handshake. Firmware that measures ramp time will diverge — accepted limitation."* The silicon reviewer flagged this; we accept the gap and document.

### D.3 WATCHDOG

**V1 scoped a full watchdog-reset scenario.** The testing reviewer showed the end-state oracle cannot observe a reset event because reset clears core state. **V2 split:**

- **Countdown + pause behaviour:** unit-tested. Program `LOAD`, advance ticks, verify `CTRL.RUNNING` and `LOAD` countdown. Test `PAUSE_DBG0` / `PAUSE_JTAG` bits gate advancement.
- **Silicon scenario:** *non-firing* — program a large `LOAD`, enable, spin 1000 cycles, verify countdown advanced but did not fire, SCRATCH survives. End-state observable.
- **Reset-firing behaviour:** unit-tested only. When countdown hits 0 and `CTRL.ENABLE=1`, the CPU's step loop polls `Bus::watchdog_reset_requested()`, which returns `true` and clears. The unit test constructs the scenario, steps until the flag fires, and asserts post-reset state: cores at vector-table reset entry, SCRATCH0..7 preserved, all non-pause registers in reset state. Matches the `bus_fault` idiom already present on `Bus`.

**Silicon fidelity note (from reviewer).** RP2350 *has* removed the `WATCHDOG_TICK` register — tick generation lives in the TICKS block. V1's guess ("probably unused on RP2350") was not backed by a citation. V2: omit `WATCHDOG_TICK` from the register map. If firmware writes to that offset it will hit the HashMap fallthrough (warn-once) — the correct emulator response.

### D.4 OTP (storage-only)

16 KB backing store, word-addressable via the `OTP_DATA` aperture. Writes OR into storage (fuse semantics). Reads return stored word.

Intentional simplifications (silicon reviewer flagged, accepted):
- No SBPI sequencing. SBPI command registers land in the HashMap fallthrough → warn-once.
- No row-level lock bits. Firmware that sets lock + retries expecting failure will diverge.
- No `OTP_DATA.READY` status (always implicitly ready).
- **No fuse-load builder.** V1 proposed "load from an optional bytes slice at Bus construction". Simplicity reviewer cut this as speculative. V2 agrees — the initial fuse state is all-zeros. If pre-programmed fuses are needed for a future test, add the builder then.

### D.5 TRNG

**V1 used `rand_chacha` for a seeded PRNG.** Simplicity reviewer cut the dependency. **V2:** a 32-bit counter. `RNG_OUT` reads return and increment. `STATUS` always "ready". Deterministic by construction, zero new dependency.

If a future test needs actual pseudorandom bytes, add the crate then. No current test does.

### D.6 SHA-256

Use the `sha2` crate (already idiomatic Rust choice). Registers per datasheet:

- `CSR` — `START` (W, self-clearing), `WDATA_READY` (RO), `SUM_VALID` (RO), `ERR_WDATA_NOT_RDY` (RO, W1C).
- `WDATA` — single write port; 16 words per block.
- `SUM0..7` — RO digest output.

Flow: firmware writes `CSR.START` to reset accumulator; writes 16 × `WDATA`; `SUM_VALID` goes high; reads `SUM0..7`. The silicon reviewer's worry ("firmware may signal last-block differently") resolves to: SHA-256 as implemented in RP2350 is a block-at-a-time compressor — firmware handles padding and length, hardware just consumes 16-word blocks. The emulator mirrors this: no auto-finalisation, no padding logic in hardware. If firmware expects hardware-side padding, no RP2350 firmware does — they use the `sha2` software API paired with hardware acceleration for large messages.

**Testing.** Unit tests using FIPS-180 Appendix A test vectors (empty string, "abc", one-million-'a'). No silicon scenario until DMA-to-SHA is wired, which is out of scope.

## 8. Part E — Medium peripherals

### E.1 POWMAN

Three sub-areas:

1. **AON timer.** **V2 downgrade from V1:** storage-only. `COUNT` (64-bit write), `MATCH` (64-bit write), `STATUS.READY` always 1. No tick advancement, no match-fires-IRQ. Documented limitation: *"AON timer is storage-only in V2. No firmware in the current corpus uses it. When firmware does, revisit to add LPOSC-clocked advancement."* This avoids the silicon reviewer's question about the correct LPOSC divider (which is programmable via a register we'd also need to model).
2. **VREG.** Plain storage.
3. **ARCHSEL.** Plain storage. **`tracing::warn!` once on any write changing the value away from the Arm default**, with the message `"POWMAN.ARCHSEL write to {:#X} — RP2350 RISC-V (Hazard3) mode not supported; emulator will continue as Arm Cortex-M33"`. (V2 fills in what V1 described abstractly.)

### E.2 CORESIGHT_TRACE

Storage-only at `0xE004_1000`. ETM/TPIU stay out of scope. Firmware that programs trace configuration will write + read back; actual trace data is not produced.

## 9. Datasheet verification checklist (new in V2)

Before coding each item, confirm against the RP2350 datasheet — the silicon-fidelity reviewer correctly called out items the V1 design answered by guessing. Estimated 30 min of datasheet reading per row.

| Item | Datasheet section to verify |
|---|---|
| WATCHDOG_TICK register existence on RP2350 | §4.7, §8.5 — confirm `TICK` has moved to TICKS block |
| POWMAN ARCHSEL location and access semantics | §12 POWMAN — confirm write-enable window, OTP backing |
| PSM DONE latency semantics | §13 PSM — document which subsystems ramp instantly vs staged |
| OTP SBPI vs OTP_DATA access split | §11 OTP — confirm which registers firmware uses for reads |
| TRNG status / ready bits | §6 TRNG — confirm pico-sdk accessor blocking path |
| SHA-256 block boundary semantics | §9 SHA256 — confirm no hardware-side padding |
| GLITCH_DETECTOR ARM bit on read | §4.4 — confirm RO-zero semantics under no-glitch |
| Interpolator CTRL bit layout | §2.7 — all bit assignments match |

Each row is one datasheet lookup, not a research project. The checklist is a review gate, not a deliverable.

## 10. Landing order (simplified from 8 steps to 5)

1. **Part A.1** (warn-once) + **A.3** (TICKS alias fix) — observability up first.
2. **Part C** (UART1/SPI1/I2C1 array-of-two reshape).
3. **Parts D.1–D.6** as one cluster (SYSCFG/TBMAN/GLITCH_DETECTOR consolidated, PSM, WATCHDOG, OTP, TRNG, SHA-256).
4. **Part A.2** (inert-register warns in DMA + PWM) + **Part E** (POWMAN + CORESIGHT_TRACE).
5. **Part B** (interpolator) last — largest single diff, wants its own review pass.

Each step is its own commit with its own tests. The devil's advocate's concern that multiple steps touch `Bus` is real — step 1 adds `warned_addrs` and `watchdog_reset_requested` together (since step 3 needs the latter), so the shared `Bus` definition change lands once.

## 11. Testing strategy

- **Unit tests per peripheral.** Register round-trip; reset state; any side effect particular to that peripheral (watchdog reset-request flag rising, SHA FIPS test vectors, interp CTRL arithmetic per §5.2 semantics).
- **Silicon scenarios:** one new scenario per peripheral that has silicon-observable state at quiescent end-state. **Not for interp** (B.3) and **not for watchdog firing** (D.3). *Not* duplicated for every `_1` instance — one routing-proof scenario per peripheral type (C.3).
- **Warn-trace test.** Dev-dependency on `tracing-subscriber` 0.3 (§4.A1). Test address: `0x400F_8000` (SHA-256 base, before Part D.6 lands; then pick another unmodelled red-path address).
- **Noise tolerance during landing.** Between step 1 and step 3, scenario runs will emit warns for unmodelled addresses they touch. We tolerate the noise — it is signal, not bug. No allowlist infrastructure.

## 12. Risks

- **Datasheet verification** is front-loaded (§9). If any row comes back with surprising semantics (e.g. PSM DONE actually has a hardware latch firmware depends on), that peripheral's model needs revisiting. Budget: ~4 hours of datasheet reading for the full checklist.
- **Interpolator without silicon calibration** (B.3) means unit tests rest on our reading of §2.7. If §2.7 is subtle in an undocumented way, first firmware using interp blend/clamp will expose it. Accepted.
- **Warn noise during landing** (§11). Annoying but transient.

## 13. What V2 deliberately does not do

- Does not add per-register warn infrastructure for partially-modelled peripherals — covered by the targeted convention in §4.A2, not a framework.
- Does not track PC on `Bus` (cut from V1).
- Does not pre-load OTP fuses (cut from V1).
- Does not use an RNG crate for TRNG (cut from V1).
- Does not model AON-timer advancement (downgraded from V1).
- Does not land six pre-calibrated silicon interp scenarios (cut from V1; unit tests from datasheet spec replace them).
- Does not duplicate scenarios for every `_1` peripheral instance (cut from V1; one routing scenario per peripheral type).
- Does not address audit §7 items 3–6 (security enforcement, cycle-oracle deltas, bootrom execution, RISC-V). Those have their own HLDs or are explicitly deferred.

## 14. Review history — V1 → V2 (tie-breaks recorded)

V1 was reviewed by a five-agent team: silicon fidelity, Rust/codebase idiom, testing, simplicity, devil's advocate. Full findings in `wrk_journals/2026.04.17 - JRN - RP2350 Coverage Gap Fill Review.md` (written alongside this HLD).

**Cuts applied** (simplicity + Rust reviewers agreed):
- `last_fetch_pc` field on `Bus` — removed. Address alone in the warn.
- `rand_chacha` dependency for TRNG — removed. Counter instead.
- AON timer with clocked advancement — downgraded to storage-only.
- Per-module files for SYSCFG / TBMAN / GLITCH_DETECTOR — consolidated into `inert.rs`.
- OTP fuse-load builder — removed.
- Six pre-calibrated silicon interp scenarios — replaced with datasheet-derived unit tests.
- Full `_1` scenario duplication — one routing scenario per type.
- 8-step landing order — collapsed to 5.

**Adds applied** (devil's advocate + testing reviewers):
- §1 item 5 and §4.A2 — targeted warn-once convention for the audit §5 inert-register list inside modelled peripherals.
- §9 — datasheet verification checklist for the items V1 answered by assumption.
- §7 D.3 — split watchdog testing into unit-tested reset + non-firing silicon scenario, because end-state oracle cannot observe reset.
- Corrected warn-test address to `0x400F_8000` (testing reviewer caught V1's `0x4010_0000` is TICKS base).
- Explicit `tracing-subscriber` dev-dependency note.
- Explicit constructor call site for `[Uart; 2]` init (Rust reviewer gap).
- Interpolator register-map table + dispatch calculation (Rust reviewer gap).

**Tie-breaks where reviewers disagreed:**
- *HashSet vs counter-capped limit for warned addrs:* HashSet wins (simpler semantics; capacity is not a real concern).
- *`[Uart; 2]` vs `uart0, uart1` fields:* array wins (explicit construction list is fine; match arm stays flat).
- *Full interp silicon scenarios now vs unit-test-now-silicon-later:* unit-test wins (blocks-on-silicon is a real landing risk; §2.7 is well-specified).
- *Per-register warn framework vs six targeted convention sites:* convention wins (framework is scope creep; six surgical sites cover the audit's specific findings).

**Explicitly rejected finding:** the devil's advocate argued the HLD "solves the wrong problem at the wrong scale" because peripheral count doesn't move the audit's structural findings (security enforcement, cycle model, RISC-V). That framing is correct — but this HLD is deliberately the finite bucket from the follow-up conversation, not a total response to the audit. The structural items have their own HLDs (or will). V2 documents the scope explicitly in §2.
