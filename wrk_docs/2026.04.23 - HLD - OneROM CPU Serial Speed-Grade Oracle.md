# HLD — OneROM CPU Serial Speed-Grade Oracle

**Date**: 2026-04-23
**Status**: Proposed
**Author**: Arthur + Claude Opus 4.7 (1M)

## 1. Motivation

The threaded speed-grade oracle (`onerom_cpu_speed_grade_rp2350`, commit
`61f5204`) measures wall-clock stim-to-sample round-trip across a
ladder of target latencies. At `--step-quantum 1024` it produces a clean
inflection at ~500 ns wall-clock — well above the ~90 ns real-silicon
OneROM CPU access time.

Investigation (2026-04-23 journal) showed the ~5–6× gap is host-side
overhead, not emulator-correctness:

- Barrier true-sharing on the 5-party arrival counter (~300–450 ns per
  quantum, even amortized).
- Cross-core atomic coherency on GPIO (~100 ns).
- Windows scheduler jitter surviving TIME_CRITICAL + affinity.

The emulator's actual serve path is already ~13 cycles per byte —
`onerom_stress_cpu_rp2350` reports p50 60 ns, mean 80 ns at 150 MHz
emulated. That matches silicon. We just can't *measure* it via
wall-clock on a multi-threaded host.

**Gap**: a speed-grade oracle that measures **simulated cycles**, not
wall-clock. No barrier, no cross-core atomics, no driver-thread jitter —
just the walk-plan + sweep methodology of the threaded oracle applied
via the serial `Emulator`. This is the honest answer to "does our
emulator serve in cycle-count parity with silicon?".

## 2. Goal

One new binary: **`onerom_cpu_speed_grade_serial_rp2350`**.

- Same walk-plan (2048 cases, 1541 ROM set 0), same shuffle, same
  `verify_observed`, same fixture.
- Measures per-case **simulated cycles** from stim-write to
  observed-byte-matches-expected.
- Ladder becomes cycle-count thresholds (not ns).
- Reports per-rung verdict + cycle-latency distribution (min, p50,
  mean, p95, max).

## 3. Non-goals

- **No CLI mode-switch on the threaded binary.** Serial oracle is a
  separate binary. Different measurement semantics; mixing them behind
  one binary obscures what each answers.
- **No app `--mode serial|threaded` flag.** That's a larger piece of
  work (TUI state plumbing for threaded, lifecycle changes). If we
  want it, it gets its own HLD after we've validated the serial path
  here.
- **No configurable thread topology.** Discussed and rejected —
  premature optimization with low ceiling and high test-surface cost.
- **No refactor of existing oracles.** Threaded oracle stays exactly
  as it is.
- **No universal `trait DynEmulator` abstraction.** The two modes have
  different APIs and cycle-accounting models; abstracting now is
  speculative.
- **No auto-skip-idle-worker optimizations in the threaded runtime.**
  Tracked separately in `tech_debt.md` if/when it matters.

## 4. Design

### 4.1 Binary layout

```
crates/mdpicoem-harness/src/bin/onerom_cpu_speed_grade_serial_rp2350.rs
```

Windows/Unix-agnostic — no host-priority shims, no affinity
(single-threaded, no multi-thread jitter to fight). Same fixture and
ROM-set-forcing as the threaded oracle (reuse of
`force_rom_set_index_via_sel_pins`).

### 4.2 Measurement loop

```rust
// Setup
emu.bus.gpio_external_mask = plan[0].gpio_mask;

for step in &shuffled_plan {
    emu.bus.gpio_external_in.store(apply_stim(step), Ordering::Relaxed);

    let cy_start = emu.cycles();
    let mut observed: u8 = 0xFF;  // distinct from any legitimate byte
    for _ in 0..CYCLE_CAP {
        emu.step();
        let out = emu.bus.gpio_out();
        observed = ((out >> GPIO_DATA_BASE) & 0xFF) as u8;
        if observed == step.expected {
            break;
        }
    }
    let cy_delta = (emu.cycles() - cy_start) as u32;
    sample_cycles.push(cy_delta);
    if observed != step.expected {
        errors += 1;
    }
}
```

Two kinds of failure:
- `observed != expected` after `CYCLE_CAP` iterations: hard error
  (oracle wedged, emulator mis-decoded, or fixture wrong).
- `observed == expected` in `>N` cycles (where `N` is the ladder
  rung): rung-specific failure — emulator served the right byte but
  too slowly for that rung's budget.

Both contribute to the rung's error count; the cycle distribution
reports the detail.

### 4.3 `CYCLE_CAP`

Hard cap per sample: **64 cycles**. Real serve is ~13 cycles; 64 is
~5× headroom. Anything taking longer is considered wedged and the
sample is flagged. Serves as both loop-termination and sanity guard.

### 4.4 Ladder

Ladder entries are now cycle counts, not nanoseconds.

```rust
const DEFAULT_CYCLE_LADDER: &[u32] = &[20, 15, 13, 10, 8];
```

Probes the 13-cycle silicon floor. Above 13, we expect comfortable
pass; at 13, pass-rate tests emulator parity; below 13, increasing
failure tells us where the emulator's minimum cycle count sits.

### 4.5 Per-rung verdict

For each rung `N`:
- Count `served_in_N = samples with cy_delta ≤ N && observed == expected`
- `errors = total_samples - served_in_N`
- Verdict = PASS if `errors == 0`, else FAIL
- Report: verdict, error count, cycle percentiles across *all* samples
  (not just the passing ones) so we see the full distribution.

Cycle percentiles shared across all rungs of a sweep (distribution
doesn't change per rung — only the threshold does). Computed once per
sweep, reported per rung for clarity.

### 4.6 CLI

```
onerom_cpu_speed_grade_serial_rp2350
  --seed <u64>                   Shuffle seed (default 0x1541CAFE00000001)
  --ladder <csv>                 Cycle thresholds, decreasing
                                 (default 20,15,13,10,8)
  --sweeps-per-threshold <n>     Sweeps per rung (default 3)
  --all-rungs                    Continue past first failing rung
  --help
```

No `--mode`, no `--step-quantum`, no `--host-core` — all meaningless
for serial execution.

## 6. Correctness validation

Three checks before declaring the binary working:

1. **Cross-oracle cycle-count parity.** Run `onerom_stress_cpu_rp2350`
   and our new binary on the same fixture. `stress` reports mean
   latency 80 ns at 150 MHz = 12 cycles. Our serial oracle's mean
   cycle count across all sweeps should land at 12 ± 1.

2. **Walk-plan PASS at generous ladder.** With ladder `[64]`
   (= CYCLE_CAP), every sample must serve correctly. Anything else is
   a walk-plan or fixture bug.

3. **Throughput sanity.** 2048 samples × 3 sweeps × ~13 cycles ≈
   80 K emulated cycles. At serial throughput ~232 MHz, that's ~350 µs
   of emulated work plus ~10 ms of Rust overhead. Total ≤ 20 ms
   elapsed. If it takes multiple seconds, something's wrong.

## 8. What this unlocks

- A clear, silicon-directly-comparable answer to "does our emulator
  serve in ~13 cycles per byte?" — decouples emulator correctness
  measurement from host-threading overhead.
- A simple pattern for future serial-mode oracles (PIO-path cycle
  oracle next, if we want one).
- Precedent for "two binaries, one question each" when measurement
  semantics differ — cleaner than dual-mode binaries with overloaded
  flags.
