# HLD — Windows Process-Kill Runbook

**Status:** **Signed off** by team lead, 2026-04-15. Agent B authored the draft; §9 captures the lead's review and decisions that close out the open questions in §8. Implementation may proceed against this HLD as-is.

## 1. Goal & non-goals

**Goal.** Capture the one Windows process-kill technique that actually
worked during the 2026-04-14 overnight campaign (`kill -9 <POSIX_PID>`
from Git Bash after walking the PPID tree via `ps -W`), in a location a
future operator — human or AI — will *find* when their oracle zombies
on port 3333/3334 and `taskkill` hangs.

**Non-goals.**
- Not a Windows process-management treatise. Scope is "how to kill a
  hung fuzz-oracle process tree from Git Bash when the usual tools
  fail", nothing broader.
- Not a troubleshooter for Linux / macOS oracles. Unix `kill` works
  normally there.
- Not a replacement for the real fix (oracles should reap their QEMU
  children — Agent A's HLD). The runbook exists for the case where
  something still slips through, or legacy builds are in use.
- Not a general rant about Windows Defender. Mention it as a
  contributing cause; don't try to fix AV policy.

## 2. Background

Over the 2026-04-14 overnight campaign, zombie QEMUs accumulated on
port 3334 after transient M0+ oracle deaths (see journal entry
**"00:01 — M0+ runner entered hot failure loop"**
[`wrk_journals/2026.04.14 - JRN - Overnight QEMU Fuzz Campaign.md`]).
Cleanup was attempted in the **"00:05–00:15 — Cleanup attempts failed
on Windows"** entry: `TaskStop` (success-returned but children
survived), `kill -9 <WINPID>` ("No such process" — Git Bash's `kill`
expects POSIX PIDs), `taskkill //f //pid ...` (hung > 30 s),
`taskkill /F /IM` (hung), `powershell Stop-Process` (hung). None
worked under system load.

Later that night, in the **"06:09 — probe runner stopped early"**
entry, the working recipe was found: `ps -W` reports both the POSIX
PID and the WINPID, so you can walk the PPID tree (outer bash 103698 →
inner bash 103703 → oracle 114565) and then pass the POSIX PIDs to
`kill -9`. It terminated the full tree cleanly on the first try. This
is the method worth codifying.

## 3. Location options considered

1. **`tech_debt.md`.** Established debug-destination file, but its
   content is strictly "this is wrong, fix it" — cycle-timing
   mismatches, banked-SP bugs, WFE stubs. A runbook recipe ("when X
   happens, run Y") is a different genre and would dilute the debt
   tracker. Rejecting.

2. **New `RUNBOOK.md` at repo root.** Clean, canonical, extensible —
   we already have a pipeline of follow-on ops items (Defender exe
   locks, PID-qualified `.exe` copies, the zombie-reap fix's
   fallbacks). Adds one well-known filename to the repo root alongside
   `README.md` / `CLAUDE.md` / `tech_debt.md`, which is already the
   "top-level signpost" bucket. No existing precedent, but a repo-root
   `RUNBOOK.md` is a widespread convention and zero-cost to establish.

3. **`fuzz-runs/README.md` (does not currently exist;
   `ls fuzz-runs` → no README).** Maximum findability when the fuzzer
   hangs (same directory as the scripts that caused the problem).
   Downside: the process-kill technique is not fuzz-specific — it
   applies to any hung Windows child-process tree from Git Bash
   (probe runners, any future silicon oracle). Scoping it to
   `fuzz-runs` hides it from the other callers.

4. **`CLAUDE.md`.** Automatically loaded for every future Claude
   session, so findability for AI agents is maximal. But the file is
   already dense with conventions and architecture notes; adding a
   half-page recipe dilutes it, and a recipe is best consumed when
   you're *already stuck*, not preloaded. A short pointer is fine;
   the full recipe should live elsewhere.

5. **`wrk_docs/ops-windows-process-kill.md`.** `wrk_docs/` is
   HLD/LLD-only today; a naked ops doc sitting between PIO HLDs and
   Phase-5 LLDs is an outlier and future readers won't scan for it.
   Rejecting.

## 4. Recommended location

**Create `RUNBOOK.md` at repo root as the canonical home.** Add a
short pointer from `CLAUDE.md`'s conventions section and a one-line
pointer from a new `fuzz-runs/README.md`.

Rationale:
- The recipe is reusable across all Windows-hung-child scenarios, not
  just the fuzz loops — repo-root placement matches its scope.
- `RUNBOOK.md` is an expected filename; operators (and Claude agents
  reading the repo top-level) will find it by convention alone.
- We have a pipeline of other operational items queuing up (exe-lock
  transient-failure signature, zombie-port pre-cleanup, probe-USB
  reset dance) — a single file with sections is cheaper than
  scattering them across `tech_debt.md` and the journals where they
  currently live.
- The `CLAUDE.md` pointer gives AI-agent findability (the reminder
  lands in every session preamble); the `fuzz-runs/README.md` pointer
  gives context-proximal findability for the most common trigger.
  Canonical content lives once in `RUNBOOK.md`.

## 5. Content outline

Single section in `RUNBOOK.md`:

### **Killing a hung oracle process tree on Windows (Git Bash)**

- **Symptom** — one-line bullets: zombie QEMU on port 3333/3334;
  `taskkill` hangs for > 30 s; `kill -9 <WINPID>` returns "No such
  process"; new oracles connect to dead QEMU → os error 10060 →
  hot failure loop.
- **Root cause** — two-bullet explainer: Git Bash `kill` is a POSIX
  tool expecting POSIX PIDs, not WINPIDs; `taskkill` /
  `powershell Stop-Process` can hang under AV / WMI contention.
- **Recipe** — exact command sequence:
  1. `ps -W | grep <exe>` (or `grep <port>` via `netstat -ano`) to
     find the target's POSIX PID **and** WINPID.
  2. `ps -W | awk '...'` pipeline to walk `PPID` upward from the
     target to the owning bash loop (2-3 hops typical: outer bash →
     inner bash → oracle).
  3. `kill -9 <POSIX_PID1> <POSIX_PID2> ...` with all POSIX PIDs on
     one line (not WINPIDs).
  4. Verify with `ps -W | grep <exe>` — expect empty.
- **Worked example** — the 06:09 incident verbatim:
  `kill -9 114565 103703 103698` terminated the probe oracle and its
  two bash parents. Quote the journal entry directly.
- **When to reach for it** — explicit decision tree: first try to stop
  the bash loop via its task handle / Ctrl-C if interactive; try
  `taskkill` once with a short timeout; if either hangs or leaves
  children, jump to this recipe. Do **not** start with it — it is a
  fallback.
- **Scope and limits** — acknowledged caveats:
  - Depends on `ps -W` flag (Git-Bash / MSYS2 / MinGW `procps-ng`);
    may not work in other bash-on-Windows flavours (WSL's `ps` is
    Linux-native and does not expose WINPIDs at all — use
    `taskkill` from a Windows shell instead).
  - If Defender is *actively* scanning the target `.exe`, both
    `taskkill` and `kill -9` may stall until the scan completes —
    wait, don't hammer.
  - Does not address *why* the zombies appeared; see the companion
    HLD on QEMU child-process cleanup (Agent A) for the real fix.

**Estimated length:** 0.5 to 1 page of markdown (roughly 40-60 lines
in the rendered file). The worked-example block is the longest piece;
everything else is terse bullets.

## 8. Risks

- **`ps -W` flag drift.** The recipe depends on Git Bash's
  `procps-ng`-flavoured `ps` exposing the `-W` flag (adds a WINPID
  column). If a future Git Bash install swaps to a different `ps`
  (BusyBox, WSL shim), `-W` may silently drop or reformat, breaking
  the PPID walk. **Canary:** the **Scope and limits** bullet should
  include a one-line sanity check (`ps -W | head -1` — confirm the
  header shows `WINPID` and `PPID` columns). An operator running the
  recipe against an unfamiliar shell will see the sanity-check fail
  before trying the kill step.

- **Recipe becomes the first-reach tool.** The decision-tree wording
  in **When to reach for it** is deliberately gatekeeping. If
  operators skip the normal cleanup and go straight to `kill -9`,
  they'll lose the chance to observe cleaner bash-level behaviour
  (`trap` handlers, graceful QEMU shutdown). Keep the "try the
  gentler thing first" ordering explicit.

- **Pointer drift.** If `RUNBOOK.md` moves or is renamed, the two
  signposts (`CLAUDE.md`, `fuzz-runs/README.md`) go stale.
  Acceptable risk given how rarely files move in this repo; if it
  ever happens, both signposts are one-line edits.

- **Overlap with Agent A's HLD.** Agent A is landing the real fix
  (oracles reap their QEMU children on exit). Once that lands, the
  *need* for this runbook drops — but the recipe still applies to any
  future Windows-hung-child scenario, so the runbook shouldn't be
  retired. Accepted; no action.
