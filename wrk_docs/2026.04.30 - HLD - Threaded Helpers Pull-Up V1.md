## 1. Goal

Move three byte-identical worker-thread helpers — `panic_message`, `spawn_worker`, `pin_to_host_core` — out of the per-chip `threaded/emulator.rs` files and into a new submodule of `mdpicoem-common::threaded` so both chip crates share one copy. This is a pure deduplication: zero behaviour change, zero call-site shape change, ~100 LOC physical reduction. The pattern follows the precedent set by Stage 3a of the dual-execution HLD V1, which promoted `SpinBarrier` and `SpscQueue` from the RP2350 threaded tree to common; this finishes that move for the helpers that were too tightly intertwined with `ThreadedEmulator` to migrate at the time.

`boost_and_pin` (the third related helper, in `threaded_probe.rs`) is **out of scope** — see §5 for the rationale; it is sequenced under Du1 / Phase 5.2 (`paced_bench` unification) and merging it here would conflate two independent commits.

## 3. Target module

**Path:** `crates/mdpicoem-common/src/threaded/worker.rs`
**Name choice:** `worker` over `host` because the helpers are specifically the worker-thread spawn / pin / panic-payload trio, not generic host primitives. Keeps the option open to grow a separate `host.rs` later for non-worker host concerns (e.g. process priority — see §5 on `boost_and_pin`).

**Public API (final shape):**

```rust
// crates/mdpicoem-common/src/threaded/worker.rs

use std::any::Any;
use std::panic::AssertUnwindSafe;
use std::sync::Arc;
use std::thread::{self, JoinHandle};

use super::SpinBarrier;

pub fn panic_message(err: Option<&Box<dyn Any + Send>>) -> String { ... }

pub fn spawn_worker<F, R>(host_core: usize, barrier: Arc<SpinBarrier>, body: F) -> JoinHandle<R>
where
    F: FnOnce(Arc<SpinBarrier>) -> R + Send + 'static,
    R: Send + 'static,
{ ... }

pub fn pin_to_host_core(host_core: usize) { ... }
```

**Re-exports** added to `crates/mdpicoem-common/src/threaded/mod.rs`:

```rust
pub mod worker;
pub use worker::{panic_message, pin_to_host_core, spawn_worker};
```

This matches the existing `pub use barrier::{BarrierResult, SpinBarrier}; pub use spsc::SpscQueue;` style. Both chip emulator files already do `use super::{... SpinBarrier ...};` via their per-chip `threaded/mod.rs` re-export of `mdpicoem_common::threaded::*`. Adding `panic_message`/`spawn_worker`/`pin_to_host_core` to those re-export lists keeps every existing call site source-compatible (`spawn_worker(...)` / `panic_message(...)` / `pin_to_host_core(...)` continue to resolve through the chip's own `threaded` module path).

## 4. Cfg gate

The two chip crates currently gate their `threaded::emulator` module differently:

- **RP2350** (`crates/mdrp2350/src/threaded/mod.rs:29-33`): per-item gate.
  ```
  #[cfg(all(feature = "threading", target_arch = "x86_64",
            any(target_os = "windows", target_os = "linux")))]
  pub mod emulator;
  ```
- **RP2040** (`crates/mdrp2040/src/threaded/mod.rs:1-5`): inner attribute on the whole `threaded` subtree.
  ```
  #![cfg(all(target_arch = "x86_64",
             any(target_os = "windows", target_os = "linux"),
             feature = "threading"))]
  ```

`mdpicoem-common::threaded` itself gates only on `#![cfg(target_arch = "x86_64")]` (`threaded/mod.rs:1`) — the chip crates layer the OS + feature requirement on top.

**Decision:** Keep `mdpicoem-common::threaded`'s outer x86_64 gate as-is, but put a per-item OS gate on `worker.rs` so the affinity FFI compiles only where its dependencies resolve:

```rust
// In threaded/mod.rs:
#[cfg(any(target_os = "windows", target_os = "linux"))]
pub mod worker;

#[cfg(any(target_os = "windows", target_os = "linux"))]
pub use worker::{panic_message, pin_to_host_core, spawn_worker};
```

Rationale:
- `panic_message` is OS-agnostic but lives in the same module to keep all three helpers together. Splitting `panic_message` into its own OS-unrestricted file would scatter the trio across two files for no caller benefit (no caller uses `panic_message` outside the OS-gated chip emulators today).
- The chip crates already require `feature = "threading"` AND OS=Windows/Linux for their `threaded::emulator` module to compile; their importer paths only reach the new `worker` module on those configurations, so an additional `feature = "threading"` gate inside `mdpicoem-common` would be redundant defence-in-depth. `mdpicoem-common` has no `threading` feature and **does not need one** — the chip crates' feature flag is the gating boundary.
- This matches the current `pacer.rs` precedent in `mdpicoem-common`: `pub mod pacer;` is unconditional but `pub use self::pacer::Pacer;` carries `#[cfg(target_arch = "x86_64")]`.

**Alternative considered:** A blanket `#![cfg(...)]` on `worker.rs` with the full `target_arch + target_os` predicate. Rejected because the parent module is already x86_64-gated; nesting the same gate is noise.

## 5. Diff sketches per function

### 5.1 `panic_message` — moves verbatim, adopts richer doc comment, becomes `pub`

- Body: byte-identical move from RP2350 (or RP2040 — they're the same).
- Visibility: `fn` → `pub fn` to match the precedent of `SpinBarrier` (`pub` in `mdpicoem-common::threaded`).
- Doc comment: take the RP2350 version (3 extra lines of context). The RP2040 1-liner is a strict subset; no information is lost.
- Signature unchanged: `(err: Option<&Box<dyn std::any::Any + Send>>) -> String`.

### 5.2 `spawn_worker` — moves verbatim, adopts richer doc comment, becomes `pub`

- Body: byte-identical between chips.
- Visibility: `fn` → `pub fn`.
- Doc comment: take the RP2350 version (4 extra lines about the generic R rationale). Subset-compatible with the RP2040 docs.
- Signature unchanged: generic over `F: FnOnce(Arc<SpinBarrier>) -> R + Send + 'static, R: Send + 'static`.
- The fact that R is generic is important — the three body signatures (`CortexM33` / `PioBlock` / `()`) all share this single function in RP2350; RP2040 uses it with a different but equally polymorphic set of body return types. No specialisation is needed in common.

### 5.3 `pin_to_host_core` — moves verbatim, becomes `pub`

- Body: fully byte-identical, doc comment included. Trivial move.
- Visibility: `fn` → `pub fn`.
- The `assert!(host_core < usize::BITS as usize, ...)` precondition stays exactly as-is — same behaviour both chips rely on.

### 5.4 `panic_message_extracts_all_payload_kinds` test — follows the function

The RP2040 unit test at `crates/mdrp2040/src/threaded/emulator.rs:1356-1368` exercises all four arms of `panic_message`. This test was always strictly about the helper, never about RP2040 specifics. Two options:

- **Option A (recommended):** Move the test into `mdpicoem-common/src/threaded/worker.rs` as a `#[cfg(test)] mod tests { ... }` block. The function moves; its test moves with it. Single home, RP2350 implicitly inherits coverage by depending on `mdpicoem-common`.
- **Option B:** Leave the test where it is and rewrite its `panic_message(...)` call sites to import from `mdpicoem_common::threaded::panic_message`. Coverage stays in the RP2040 test surface, RP2350 still has none.

Option A is cleaner and matches the ownership move. **Decision: Option A.**

### 5.5 `boost_and_pin` (third copy) — DEFER

`crates/mdpicoem-harness/src/bin/threaded_probe.rs:24-50` and the two `paced_bench_*.rs` copies (referenced in §2.6 / Du1) are a different helper:

- Different shape: `boost_and_pin` does process priority (`SetPriorityClass`) + thread priority (`SetThreadPriority`) + affinity (`SetThreadAffinityMask`). `pin_to_host_core` only does affinity.
- Different platform support: `boost_and_pin` is Windows-only (no Linux/macOS arms). `pin_to_host_core` supports Windows + Linux.
- Different FFI style: `threaded_probe.rs` declares its own `extern "system"` prototypes; the chip helpers use `winapi`. Promoting it would also be a small dependency clean-up.
- Different return type: `boost_and_pin` returns `Result<(), &'static str>`; `pin_to_host_core` panics on failure.

The Action Plan §5.2 explicitly assigns `boost_and_pin` to the `paced_bench` unification work (Du1) — three copies live in harness binaries that Du1 will collapse into one shared `mdpicoem-harness::bench` module. Pulling `boost_and_pin` *up to* `mdpicoem-common` instead would mean that Du1 has nothing left to migrate — but Du1's commits will still need to touch its current call sites. Two independent migrations colliding on the same helper risks merge conflicts and review confusion.

**Decision: leave `boost_and_pin` for Du1 / Phase 5.2.** This HLD strictly targets the three byte-identical helpers in the chip threaded trees. If Du1 later finds a reason to promote `boost_and_pin` into common rather than `mdpicoem-harness::bench`, that is a Du1 concern, not Du2.

## 6. Imports and dependencies

`crates/mdpicoem-common/Cargo.toml` currently has:

```toml
[dependencies]
tracing = { workspace = true }
```

…and **no** `winapi` / `libc`. Both are needed by `pin_to_host_core`.

**Action required:** add the same per-target dependency stanzas already present in both chip crates' `Cargo.toml`:

```toml
[target.'cfg(all(target_arch = "x86_64", target_os = "windows"))'.dependencies]
winapi = { version = "0.3", features = ["processthreadsapi", "winbase"] }

[target.'cfg(all(target_arch = "x86_64", target_os = "linux"))'.dependencies]
libc = "0.2"
```

These are the exact same lines from `crates/mdrp2350/Cargo.toml:82-86` and `crates/mdrp2040/Cargo.toml:53-57`. Same versions, same features. Workspace already resolves both crates at a single version (cargo unifies); no new transitive cost.

After adding to common, the chip crates' `winapi`/`libc` declarations could in principle be removed — **but they should NOT be**, because each chip crate's `threaded/emulator.rs` still uses these crates directly for non-helper paths (the chip-specific worker bodies, error handling, etc.). Verifying which is true is mechanical work, but unnecessary for Du2 — the chip crates already declare these deps; leaving them in place is a no-op cost-wise and keeps the migration purely additive on the common side.

`tracing` is already in `mdpicoem-common`. None of the three helpers being moved use `tracing` directly; adding it isn't required by this move.

`std::panic::AssertUnwindSafe`, `std::sync::Arc`, `std::thread::{self, JoinHandle}`, `std::any::Any` — all in std, already trivially available.

## 7. Validation plan

After the move, run all of:

1. `cargo build --release --all-targets` — proves the workspace as-is still compiles.
2. `cargo build --release --all-targets --features threading,testing` (per chip crate) — proves the threading + testing combo still compiles. Specifically:
   - `cargo build -p mdrp2350 --features threading,testing`
   - `cargo build -p mdrp2040 --features threading,testing`
3. `cargo test -p mdpicoem-common` — picks up the moved `panic_message_extracts_all_payload_kinds` test in its new home.
4. `cargo test -p mdrp2350 --features threading` — chip unit tests, including any threaded-runtime in-crate tests.
5. `cargo test -p mdrp2040 --features threading` — same for RP2040.
6. `cargo test -p mdrp2350 --test dual_model --features threading` — the cross-execution-model parity oracle. End-state Serial vs Threaded must remain bit-identical.
7. `cargo test -p mdrp2040 --test dual_model --features threading` — same.
8. `cargo test -p mdrp2350 --test execution_model --features threading,testing` and `cargo test -p mdrp2040 --test execution_model --features threading,testing` — panic-containment integration tests. These exercise the `spawn_worker` → barrier-poison path end-to-end, so any byte-level breakage there shows up here.
9. `cargo build -p mdpicoem-harness --release --bin paced_bench_rp2350` and `--bin paced_bench_rp2040` — smoke that the harness binaries still link. **No need to actually run a benchmark** — the dual_model + execution_model tests already cover the runtime semantics; we just need link health on the harness side.
10. `cargo build -p mdpicoem-harness --release --bin threaded_probe` — same. Note: `threaded_probe` does NOT consume the moved helpers; it has its own `boost_and_pin`. This step exists only to confirm we didn't accidentally break harness compilation while editing chip crates.

**Pass criteria:** every command above exits 0. No new clippy warnings on the moved code (the helpers were warning-clean before; the move is character-preserving so they should remain so).

**Out of scope for validation:**
- Long-running fuzz sessions (`qemu_diff_*`, `silicon_*`). These don't exercise the threaded runtime helpers and would dilate the validation envelope unnecessarily.
- Real hardware oracles (`probe_diff_*`). Same reason.

## 8. Risks and open questions

**R1. Doc-comment loss.** The two chip copies have non-identical doc comments (RP2350 richer for `panic_message` and `spawn_worker`). If the reviewer disagrees that adopting the RP2350 docs is correct, the alternative is to compose the union (combine sentences from both). RP2040's docs are strict subsets, so I judged this a non-issue, but flagging it explicitly because it's the only place where "byte-identical" is technically false.

**R2. Test ownership move.** Moving `panic_message_extracts_all_payload_kinds` from `mdrp2040::threaded::emulator::tests` to `mdpicoem_common::threaded::worker::tests` is a low-risk relocation, but the test is currently inside a `mod tests { ... }` block alongside ~700 LOC of RP2040-specific threaded tests. Extracting it cleanly (without dragging `use` lines that reference RP2040 types) requires care. Implementer should verify the test compiles in its new location before deleting from the old one.

**R3. `winapi` / `libc` feature unification.** Both chip crates request `winapi` features `["processthreadsapi", "winbase"]`. The new common dep should request the same. If a future helper in common needs additional winapi features, it will surface as a build error in common — easier to debug than a feature-flag mismatch silently downgrading what's available to the helper.

**R4. The `assert!` precondition on `pin_to_host_core` panics on out-of-range `host_core`.** This is current behaviour, not a new risk, but worth noting: the helper is a hard panic on misuse. The move preserves that exactly. If a future caller wants `Result`-shaped failure, that's a separate redesign.

**R5. `mdpicoem-common`'s public API grows.** Today it exposes `SpinBarrier`, `SpscQueue`, `BarrierResult`. After this move it also exposes `spawn_worker`, `pin_to_host_core`, `panic_message`. That is a deliberate broadening — these are reusable thread-coordination primitives, not chip-implementation details — but it does mean third parties depending on `mdpicoem-common` (none today, beyond the workspace) gain visibility into the thread-affinity surface. Acceptable per the precedent set by `SpinBarrier`'s migration.

**R6. Open question — should the new module be `pub` or `pub(crate)`?** Precedent says `pub` (matches `barrier`, `spsc`). The chip crates need `pub` access through the re-export chain (`mdrp2350::threaded::spawn_worker(...)` does work today via `pub use`). Going `pub(crate)` would require the chip re-exports to be `pub use mdpicoem_common::threaded::worker::*;` which awkwardly re-exposes private items from a different crate — Rust allows it but it's gnarly. **Recommendation: `pub`, matching `SpinBarrier`.**

**R7. No subtle divergences missed.** I diffed the function bodies char-by-char. The only differences are doc comments. There are no per-chip variable names, no per-chip log strings (these helpers don't use `tracing` at all), no per-chip constants. The byte-identical claim from the sweep report is correct.

## 9. Sequencing

**One commit.** Justification:

- The change is small (~120 LOC moved across 4 files, 1 Cargo.toml edit).
- Splitting into "add to common" + "remove from chip A" + "remove from chip B" creates intermediate states where the workspace has duplicate symbols (the chip helpers shadow the common ones via `use super::{...};`). Either the duplicates resolve through the chip crate's own re-export (which would silently still call the chip-local fn rather than the common one, defeating the deduplication) or they collide at compile time. Both cases are noisy.
- The validation plan in §7 runs as a single batch; there is no incremental test value to staging.

**Suggested commit shape:**

```
mdpicoem-common: pull threaded::worker helpers up from chip crates

Moves panic_message, spawn_worker, pin_to_host_core into a new
mdpicoem-common::threaded::worker module so both chip crates share one
copy. Function bodies are byte-identical; the move adopts the richer
RP2350 doc comments. Adds per-target winapi/libc deps to
mdpicoem-common matching the existing chip-crate stanzas.

Closes Du2 in 2026.04.29 sweep report. Validation: dual_model +
execution_model integration tests (both chips), unit tests,
release build of all harness binaries.

Co-Authored-By: ...
```

Single commit, atomic, reviewable in one diff.
