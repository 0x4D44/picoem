# 2026.04.26 - HLD - Probe Driver Hardening V1

**Author:** Workstream 3 HLD agent (sonnet)
**Date:** 2026-04-26
**Status:** V1, supervisor-signed-off — see journal `2026.04.26 - JRN - Triple Workstream WFE-DMAirq-ProbeHardening.md`.
**Scope:** Tech-debt hardening of the probe fuzz pipeline so that a transient USB blip cannot silently degrade a batch (binary returning rc=0 with 76% skipped) or wedge into a multi-batch / multi-driver cascade. Two complementary fixes: (1) binary emits a new rc=3 when transport-error skips dominate a batch, (2) drivers grow rc=3 handling on top of the rc=2 30s back-off that landed at 23:18 on 2026-04-25.

## 1. Problem statement

Two recent incidents on the live probe fuzz campaign demonstrated that the binaries lie about success when the probe transport collapses mid-batch:

- **2026-04-25 08:51 — single-batch USB blip on RP2354.** A WinUSB `submit failed (os error 22)` mid-`T32_LDM` left the binary skipping every case from #189 onward (`Passed: 1885, Failed: 0, Skipped: 6115` ≈ 76% of the batch). The binary still exited rc=0 because `Failed > 0` is its only non-success criterion; the driver immediately launched batches 6–9, all of which exited rc=2 within <1s with the wedged probe. Recovery was passive — by batch 10 the probe self-healed. (Journal §"08:51 — USB blip on RP2354 probe (NOT a fuzz failure)".)
- **2026-04-25 16:55–17:15 — cascade USB lockup → RP2040 chip wedged.** Same root cause hit RP2354 phase-2 batch 3, but this time the broken-WinUSB state cascaded into both drivers. RP2354 batches 4–10 and RP2040 batches 11–22 all returned rc=2 in <1s each, burning ~30 dead seeds before manual recovery. Eventually the RP2040 target chip itself wedged at the SWD layer, requiring physical reset by Arthur. (Journal §"16:55–17:15 — Major incident: cascade USB lockup → RP2040 chip wedged".)
- A repeat at 23:15–23:18 confirmed the cascade pattern. The 23:18 patch added a 30s `sleep` on rc=2 to both drivers — already live — but the underlying signal "this batch was useless because the probe died mid-run" is still invisible to the driver.

The HLD addresses two connected gaps:

1. The binary has no exit-code distinction between "0 failures because every case passed" and "0 failures because the probe died after case 189." Both are rc=0.
2. The driver only knows about rc=2 (probe attach failure at startup). It cannot tell that a long-running rc=0 batch was actually 76% skipped.

## 3. Proposed design — binary side

### 3.1 What gets counted: transport-skip vs filter-skip

Confirmed in §2.1/§2.2: today the in-loop `skip` counter is **only** incremented from `Err(DiffError::ProbeError(_))`. Filter rejections in `probe_diff_rp2040` are dropped before the loop and never reach a `[SKIP]` line. `probe_diff_rp2350` has no compatibility filter at all — every case in `generate_all` / `generate_fuzz` is attempted.

→ **The existing `skip` counter already represents probe-transport skips exactly.** No new counter, no new substring on the `[SKIP]` line, no protocol change. This is the simplest possible binding.

(If a future change introduces an in-loop filter-driven skip — e.g. a runtime "this case is unsafe on revision X" check — it must be funnelled through a new error variant, not `DiffError::ProbeError`. Captured as risk in §8.)

### 3.2 Threshold and rc=3 decision

**Choice: percent of attempted cases, threshold = 25%.**

Single-axis rule:

- Let `attempted = pass + fail + skip` (the cases the loop actually iterated through; `undef` on the rp2040 path is also added to `attempted` since it represents a real probe step that just landed in bootrom).
- If `attempted >= 20` (sanity floor — protects against single-test invocations) **and** `100 * skip / attempted >= 25`, the binary exits **rc=3** instead of rc=0/1.
- The rc=1 path (any failures) takes precedence — a true ISA mismatch must still surface as rc=1 even if accompanied by lots of skips. Order: rc=1 > rc=3 > rc=0.

**Justification for 25% percent over absolute / trailing alternatives:**

- **Why percent, not absolute?** The two binaries run wildly different batch sizes — RP2354 fuzz `--fuzz 200` produces ~8 000 cases per batch, RP2040 ~2 550 cases (post-filter). A single `>100 skips` absolute threshold under-fires on the RP2354 oracle (1.25%, well below the 76% disaster ratio) or over-fires on a smaller invocation. A percent normalises across `--fuzz N` settings, future class additions, and the per-target filter difference.
- **Why 25%?** The 08:51 incident was 76% skipped — clearly catastrophic. Day-to-day baseline before the blip was 0% skipped over 4 800k cases (Phase-1 summary in journal). The cascade-2 trigger batch was 11% skipped (`Passed: 7169, Failed: 0, Skipped: 831` from §"16:55"). 25% comfortably above benign noise and well below the catastrophic case. The 5-consecutive-cap (§4.2) is the actual cascade defence; the percent threshold is a per-batch quality signal. False-positive cost is one minute back-off; false-negative is bounded by the cap.
- **Why not "trailing run of >50 in a row"?** The 08:51 scenario was a contiguous tail-skip — that variant would have caught it. But a Probe-rs GDB connection refused vs USB error mode produces interleaved skips earlier. Trailing-only logic is fragile against any pattern that recovers briefly. Percent-of-attempted is invariant to the temporal pattern.
- **Why not configurable?** Per brief, this is a tech-debt fix. One number, justified by data, baked in.

### 3.3 Where rc=3 lives in the binary

The decision goes at end-of-run, immediately after `print_summary` and before the existing `if fail > 0 { exit(1) }` block. Pseudocode for **`probe_diff_rp2350.rs::run_targeted`** (mirrors into `run_fuzz`, and into the rp2040 sibling — four insertion points total):

```rust
let elapsed = t0.elapsed();
print_summary("targeted", pass, fail, skip, cycle_mismatches, args.cycles, elapsed);

// New: degraded-mode detection. Order matters — fail > 0 still wins.
if fail > 0 {
    std::process::exit(1);
}
let attempted = pass + fail + skip; // rp2040: + undef
if attempted >= 20 && (skip * 100) / attempted >= 25 {
    eprintln!(
        "=== DEGRADED: {skip}/{attempted} cases skipped ({pct}%); \
         probe transport unstable, exiting rc=3 ===",
        pct = (skip * 100) / attempted
    );
    std::process::exit(3);
}
Ok(())
```

For `probe_diff_rp2040.rs`, `attempted` is `pass + fail + skip + undef`. The new banner line is the **only** new stdout/stderr output the binary produces, by design — keeps the failure-monitor's existing greps stable.

The threshold-decision logic is a single pure function `fn rc_for(pass: usize, fail: usize, skip: usize, [undef: usize]) -> i32` so it is unit-testable without a probe attached. See §6.1.

### 3.4 Banner / summary line

`print_summary` itself stays unchanged so existing log-archiving heuristics still work. The new `=== DEGRADED ... ===` line is a one-shot, written to stderr (matching `[SKIP]` / `[FAIL]` discipline), only when rc=3 fires. The driver-side back-off log line (§4.3) provides the second timestamp — between them, post-mortem of an rc=3 event has both binary-side and driver-side anchors.

## 4. Proposed design — driver side

### 4.1 rc-handling switch (diff sketch — bash)

Replace the current rc=2-only `if`/`fi` with a `case` statement. Same shape for both `run-probe.sh` and `run-m0plus-probe.sh`. The diff to current state is small:

```sh
"$BIN" \
  --fuzz 200 --seed "$SEED" "${PROBE_ARGS[@]}" >> "$LOG" 2>&1
rc=$?
echo "=== PROBE batch=$BATCH seed=$SEED end=$(date -Iseconds) rc=$rc ===" >> "$LOG"

# Track consecutive transport-related rcs (2 or 3). Reset on rc=0.
case "$rc" in
  0)
    CONSEC=0
    ;;
  1)
    # Real failure — leave loop policy unchanged (binary already exited
    # with the [FAIL] context; failure-monitor will catch it).
    CONSEC=0
    ;;
  2)
    CONSEC=$((CONSEC + 1))
    echo "=== PROBE rc=2 (probe attach failed) backoff=30s consec=$CONSEC at $(date -Iseconds) ===" >> "$LOG"
    sleep 30
    ;;
  3)
    CONSEC=$((CONSEC + 1))
    echo "=== PROBE rc=3 (degraded batch) backoff=60s consec=$CONSEC at $(date -Iseconds) ===" >> "$LOG"
    sleep 60
    ;;
  *)
    # Anything else is unexpected; log and continue, do not back off.
    echo "=== PROBE rc=$rc (unexpected) consec=$CONSEC at $(date -Iseconds) ===" >> "$LOG"
    ;;
esac

if [ "$CONSEC" -ge 5 ]; then
  echo "=== PROBE FATAL: consec=$CONSEC transport-faults; aborting driver at $(date -Iseconds) ===" >> "$LOG"
  exit 1
fi
```

`CONSEC` is initialised to `0` once before the `while` loop (alongside `BATCH=0`). The `*)` arm is intentionally permissive: rc=127 / signal-killed / etc. should not be amplified into a hard cap, only logged.

### 4.2 Back-off durations + cap

| rc | Action | Sleep | Advance seed? | Counts toward cap? |
|----|--------|-------|---------------|-------------------|
| 0  | Continue | 0 | n/a | resets cap |
| 1  | Continue | 0 | yes | resets cap |
| 2  | Back off, retry | 30 s | yes (next iter generates new) | yes |
| 3  | Back off, advance | 60 s | yes | yes |
| other | Continue | 0 | yes | no |
| 5 in a row of rc=2/3 | Driver exits rc=1, FATAL line | n/a | n/a | n/a |

**Rationale:**

- 30s for rc=2 matches the existing live patch — proven sufficient empirically (the cascade-2 reseat showed the WinUSB endpoint drains in ~30s when not actively poked).
- 60s for rc=3 is intentionally longer because rc=3 means the probe was working at attach-time but degraded mid-batch — the underlying USB stack is in a more disturbed state than a plain attach failure.
- Cap at 5 consecutive: matches the journal's experience that genuinely transient blips self-heal in 1–4 batches, while a real wedge needs human reseat. The driver also writes a `FATAL:` line which is matched by the existing failure-monitor regex.

### 4.3 Logging format

Every back-off and cap event writes a single timestamped line so the supervisor can reconstruct the sequence:

```
=== PROBE rc=2 (probe attach failed) backoff=30s consec=1 at 2026-04-26T18:42:11+01:00 ===
=== PROBE rc=3 (degraded batch) backoff=60s consec=2 at 2026-04-26T18:43:24+01:00 ===
=== PROBE FATAL: consec=5 transport-faults; aborting driver at 2026-04-26T18:50:00+01:00 ===
```

Format chosen so that:

- `rc=2 ===` / `rc=3 ===` per-batch lines preserve the existing `rc=[1-9]\d* ===` failure-monitor regex.
- `consec=N` lets a future heartbeat agent grep the latest value cheaply.
- ISO-8601 timestamps match the existing batch start/end markers.

## 5. Rollout plan

The binary build is decoupled from the live drivers (verified §2.6: drivers run from pid-suffixed copies). The bash scripts cannot be edited in place. Sequence:

### 5.1 Build cadence (safe immediately, pre-deadline)

1. Land the binary changes; merge.
2. `cargo build --release -p mdpicoem-harness --bin probe_diff_rp2350 --bin probe_diff_rp2040` to refresh `target/release/probe_diff_*.exe`. Live drivers are untouched (they hold pid-suffixed copies). Smoke-test the rebuilt binaries off-line per §6.

### 5.2 Stage the new driver scripts (pre-deadline)

Stage as **new files** in `fuzz-runs/`:

- `fuzz-runs/run-probe.sh.next`
- `fuzz-runs/run-m0plus-probe.sh.next`

Rationale for sibling-suffix in the same dir vs `wrk_scratch/`: keeps the script next to its log file and existing pid-binary copy, so the swap is a one-`mv` atomic rename. The `.next` suffix is non-executable to bash by convention.

### 5.3 Swap-in commands (after fuzz drainage)

After the live phase-3 drivers exit at deadline (~2026-04-26T16:13 local), confirm via `Get-Process` that no `probe_diff_*.exe` and no `bash` driver is alive (per RUNBOOK zombie-tree recipe). Then:

```bash
# From repo root, after both probe.log and m0plus-probe.log show "deadline reached":
cd fuzz-runs
mv run-probe.sh run-probe.sh.prev
mv run-probe.sh.next run-probe.sh
mv run-m0plus-probe.sh run-m0plus-probe.sh.prev
mv run-m0plus-probe.sh.next run-m0plus-probe.sh
chmod +x run-probe.sh run-m0plus-probe.sh

```

The `.sh.prev` snapshot stays as a one-revert undo. Do **not** delete pid-suffixed `.exe`s in `fuzz-runs/` per the memory file flag.

### 5.4 Smoke test for rc=3

The binary's threshold logic is unit-testable (§6.1) without hardware. For the **integrated** rc=3 path, two options:

- **One-shot manual.** Plug the dev probe, start `probe_diff_rp2350 --fuzz 200`, then physically yank the USB cable mid-run. Expected: `[SKIP]` lines flood, run completes, summary prints with `Skipped: ~200`, `=== DEGRADED ... rc=3 ===` line emits, exit code `3`.
- **Stub-binary smoke for the driver.** A tiny `probe_diff_stub.sh` that takes seed/probe args and exits with rc-from-environment lets the bash driver be exercised against a scripted sequence. Captured in §6.2.

## 6. Test plan

### 6.1 Binary side — unit test on `rc_for`

Extract the threshold logic into a private free function so it can be unit-tested without setting up a probe-rs `Session`:

```rust
fn rc_for(pass: usize, fail: usize, skip: usize) -> i32 {
    if fail > 0 { return 1; }
    let attempted = pass + fail + skip;
    if attempted >= 20 && (skip * 100) / attempted >= 25 {
        return 3;
    }
    0
}
```

(rp2040 sibling adds `undef` to both arguments and to `attempted`.)

Tests added under `#[cfg(test)] mod tests`:

- `rc_for_clean_run_returns_zero` — `(8000, 0, 0) -> 0`.
- `rc_for_any_failures_returns_one` — `(7999, 1, 0) -> 1`, including `(0, 1, 6000) -> 1` (failure beats degraded).
- `rc_for_high_skip_returns_three` — `(1885, 0, 6115) -> 3` (the 08:51 numbers).
- `rc_for_borderline_skip_below_threshold` — `(7169, 0, 831) -> 0` (cascade-2 trigger at 11%; intentionally below 25% — captures the design choice as a regression).
- `rc_for_small_attempted_does_not_trip` — `(0, 0, 5) -> 0` (sanity floor).
- `rc_for_exactly_at_threshold` — `(75, 0, 25) -> 3` (boundary inclusive).

Mirror tests in `probe_diff_rp2040.rs` adding `undef` arg.

### 6.2 Driver side — disposable smoke script

## 8. Open questions / risks

1. **Threshold value (25%).** Both 2026-04-25 incidents addressed by the percent + cap combination. Cascade-2 trigger batch at 11% does not trip rc=3 at 25%; supervisor accepts this — the 5-consecutive cap is the cascade defence. **Resolution: keep 25%.**
2. **Filter-driven skip false-positive risk.** §3.1 verifies that today no `[SKIP]` line in either binary comes from a filter rejection. This invariant is fragile against future contributors. Risk-mitigation: a comment on the `skip += 1` site noting "this counter directly drives rc=3; do not increment from filter rejections — funnel those through a new variant or pre-loop drop."
3. **rc=3 plus rc=1 simultaneity.** A degraded batch that *also* surfaces a real divergence on the few cases that ran cleanly should report rc=1 (failure dominates). §3.3 codifies this. Documented case: post-mortem of an unexplained rc=1 should consider transport instability as a fourth hypothesis after silicon, emulator, fuzz-generator.
4. **Stub-driver fidelity.** §6.2's smoke test exercises the bash logic but not the actual binary's rc=3 emission. The yank-cable manual test (§5.4) covers that gap but is unautomated.
5. **CONSEC reset on driver restart.** A respawned driver loses CONSEC state. Acceptable: human reseat is the actual recovery for cap-exceeding cases, and respawn implies a human in the loop.
6. **Bash partial-stream risk for the new file.** Even after swap, in-place editing the live `run-probe.sh` while running is unsafe. Inherits existing hygiene rule.
7. **Failure-monitor regex `rc=[1-9]\d* ===` — confirmed catches rc=3 (§2.5).** No monitor change needed.
