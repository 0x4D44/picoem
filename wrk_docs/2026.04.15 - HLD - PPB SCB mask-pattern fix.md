# HLD — mdrp2040 PPB SCB mask/pattern fix

**Status:** Draft, awaiting supervisor sign-off.
**Scope:** `crates/mdrp2040/src/bus/ppb.rs` + `crates/mdrp2040/tests/smoke.rs` + a previously-uncommitted `crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs` one-liner.
**Blocks:** Phase 4 of the PicoGUS v4.0.0 firmware bring-up — currently stalling at cycle 42569 because every SCB read returns 0 and every SCB write is silently dropped.

---

## 1. Problem statement

`crates/mdrp2040/src/bus/ppb.rs` masks incoming addresses with `addr & 0x0FFF_FFFF` but then pattern-matches against constants of the form `0x000E_DXXX`. For the canonical SCB addresses used by pico-sdk and any real M0+ firmware, the two never compare equal:

```text
addr              = 0xE000_ED08    (VTOR)
addr & 0x0FFF_FFFF = 0x0000_ED08
pattern constant  = 0x000E_D008    ← 0xED shifted one nibble left
match result      = _ (fall-through → read-as-zero / write-ignored)
```

Every SCB register in `Ppb::read32` / `Ppb::write32` is affected: CPUID, ICSR, VTOR, AIRCR, SHPR2, SHPR3. The field store *does* exist (and Phase 1's `direct_boot_from_flash` correctly assigns `bus.ppb[i].vtor`), but pico-sdk's `get_vtable()` path reads VTOR via `*(volatile u32*)0xE000_ED08`, which lands in the bus and returns 0. That 0 propagates into `irq_set_exclusive_handler`'s vtable-slot check, triggers `hard_assertion_failure`, and halts progress at cycle 42569 (= step 21501) — exactly where the live PicoGUS v4.0.0 firmware is currently stuck.

The bug was masked by:
- Unit tests in `crates/mdrp2040/src/tests.rs` that set `bus.ppb[0].vtor = ...` directly (lines 1394, 1843, 1874, 1929) rather than round-tripping through `write32`/`read32`.
- `crates/mdrp2040/tests/smoke.rs::direct_boot_from_flash_applies_vector_table` asserting against the field (`emu.bus.ppb[0].vtor`) rather than the memory-mapped path.
- The absence of any `#[cfg(test)] mod tests { ... }` block inside `bus/ppb.rs` itself. mdrp2350's `bus/ppb.rs:555` has one; mdrp2040 has none.

mdrp2350 has the correct idiom already (`crates/mdrp2350/src/bus/ppb.rs:173, 208`):

```rust
pub fn read32(&mut self, addr: u32) -> u32 {
    match addr & 0xFFFF {
        0xED00 => 0x411F_D210,     // CPUID
        0xED04 => self.icsr,
        0xED08 => self.vtor,
        ...
```

This HLD applies the same idiom to mdrp2040.

## 2. Fix

### 2.1 Mask + pattern rewrite

Rewrite `Ppb::read32` and `Ppb::write32` in `crates/mdrp2040/src/bus/ppb.rs` to mask `addr & 0xFFFF` and match on the low 16 bits, mirroring mdrp2350's idiom. Patterns fall in the `0xED00..=0xED20` SCB region.

```rust
// Before
pub fn read32(&self, addr: u32) -> u32 {
    match addr & 0x0FFF_FFFF {
        0x000E_D000 => 0x410C_C601,   // never matches
        0x000E_D004 => self.icsr,     // never matches
        0x000E_D008 => self.vtor,     // never matches
        0x000E_D00C => 0xFA05_0000,   // never matches
        0x000E_D01C => (self.shpr[7] as u32) << 24,
        0x000E_D020 => ((self.shpr[10] as u32) << 16) | ((self.shpr[11] as u32) << 24),
        _ => 0,
    }
}

// After
pub fn read32(&self, addr: u32) -> u32 {
    match addr & 0xFFFF {
        0xED00 => 0x410C_C601, // CPUID: Cortex-M0+ r0p1
        0xED04 => self.icsr,
        0xED08 => self.vtor,
        0xED0C => 0xFA05_0000, // AIRCR stub (VECTKEY echo)
        0xED1C => (self.shpr[7] as u32) << 24,
        0xED20 => ((self.shpr[10] as u32) << 16) | ((self.shpr[11] as u32) << 24),
        _ => 0,
    }
}
```

`write32` gets the same treatment:

```rust
pub fn write32(&mut self, addr: u32, val: u32) {
    match addr & 0xFFFF {
        0xED04 => {
            // ICSR: W1S/W1C PENDSVSET/CLR + PENDSTSET/CLR (logic unchanged)
            if val & (1 << 27) != 0 { self.icsr &= !(1 << 28); }
            if val & (1 << 28) != 0 { self.icsr |=  (1 << 28); }
            if val & (1 << 25) != 0 { self.icsr &= !(1 << 26); }
            if val & (1 << 26) != 0 { self.icsr |=  (1 << 26); }
        }
        0xED08 => self.vtor = val,
        0xED1C => { self.shpr[7]  = ((val >> 24) & 0xFF) as u8; }
        0xED20 => {
            self.shpr[10] = ((val >> 16) & 0xFF) as u8;
            self.shpr[11] = ((val >> 24) & 0xFF) as u8;
        }
        _ => {}
    }
}
```

No other behaviour changes. The ICSR bit manipulation, the SHPR byte encoding, the ignored-writes fallthrough, and the VTOR field layout all stay byte-identical. Only the mask and the pattern constants move.

### 2.2 Secondary fix (already in working tree — include in commit)

`crates/mdpicoem-harness/src/bin/picogus_diff_rp2040.rs:844` currently reads:

```rust
let sp_in_sram = (0x2000_0000..=0x2004_2000).contains(&sp_at_vtor);
```

The inclusive `..=` upper bound is already applied in the working tree. pico-sdk's canonical top-of-SRAM initial SP is `0x2004_2000` (one past the last valid SRAM byte — Thumb pushes pre-decrement, so the first push lands at `0x2003_FFFC`). The earlier exclusive `(0x2000_0000..0x2004_2000)` rejected that canonical value and caused the direct-boot heuristic to skip installation. Do **not** re-edit this line; just stage it as part of the same commit as the `ppb.rs` fix.

## 3. Test plan

### 3.1 New unit tests in `crates/mdrp2040/src/bus/ppb.rs`

`ppb.rs` currently has **no** `#[cfg(test)] mod tests` block (`grep "mod tests" crates/mdrp2040/src/bus/ppb.rs` returns nothing, while mdrp2350's equivalent is at line 555). Add a new module at the end of the file, mirroring the mdrp2350 style:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn cpuid_read_returns_m0plus_r0p1() {
        let ppb = Ppb::default();
        // Cortex-M0+ r0p1 CPUID constant per ARM DDI 0484C §B3.2.3.
        assert_eq!(ppb.read32(0xE000_ED00), 0x410C_C601);
    }

    #[test]
    fn vtor_roundtrip_through_memory_mapped_path() {
        // Regression for the Phase-2 mask/pattern bug: Phase 1's
        // direct_boot_from_flash set the field, but pico-sdk's
        // get_vtable() reads VTOR via 0xE000_ED08 and saw 0.
        let mut ppb = Ppb::default();
        ppb.write32(0xE000_ED08, 0x1000_0100);
        assert_eq!(ppb.read32(0xE000_ED08), 0x1000_0100);
    }

    #[test]
    fn icsr_pendsvset_is_sticky_through_read32() {
        let mut ppb = Ppb::default();
        ppb.write32(0xE000_ED04, 1 << 28); // PENDSVSET
        assert_eq!(ppb.read32(0xE000_ED04) & (1 << 28), 1 << 28);
    }

    #[test]
    fn aircr_stub_returns_vectkey_echo() {
        // SDK reset code reads AIRCR to preserve VECTKEYSTAT; stub returns
        // 0xFA05_0000 so a subsequent RMW writes a valid VECTKEY of 0x05FA.
        let ppb = Ppb::default();
        assert_eq!(ppb.read32(0xE000_ED0C), 0xFA05_0000);
    }

    #[test]
    fn shpr3_roundtrip_pendsv_and_systick() {
        let mut ppb = Ppb::default();
        // byte 2 = PendSV (exc 14 → idx 10), byte 3 = SysTick (exc 15 → idx 11)
        let val = (0xC0u32 << 16) | (0x80u32 << 24);
        ppb.write32(0xE000_ED20, val);
        assert_eq!(ppb.read32(0xE000_ED20), val);
        assert_eq!(ppb.shpr[10], 0xC0);
        assert_eq!(ppb.shpr[11], 0x80);
    }
}
```

The `vtor_roundtrip_through_memory_mapped_path` case is the exact regression oracle — it would have caught this bug before Phase 1 ever started.

## 4. Risk analysis

### 4.1 Is `addr & 0xFFFF` safe at every call site?

`Ppb::read32` / `Ppb::write32` are called from exactly eight places (all in `crates/mdrp2040/src/bus/mod.rs`):

| Line | Call                                                                                     | Address source            |
|------|------------------------------------------------------------------------------------------|---------------------------|
| 602  | `self.ppb[self.active_core].read32(addr & !3)` — `read8` region 0xE                      | CPU load, high nibble 0xE |
| 643  | `self.ppb[self.active_core].read32(addr & !3)` — `read16` region 0xE                     | CPU load, high nibble 0xE |
| 676  | `self.ppb[self.active_core].read32(addr)` — `read32` region 0xE                          | CPU load, high nibble 0xE |
| 743  | `let old = self.ppb[self.active_core].read32(word_addr)` — `write8` RMW region 0xE       | CPU store, high nibble 0xE |
| 746  | `self.ppb[self.active_core].write32(word_addr, ...)` — `write8` RMW region 0xE           | CPU store, high nibble 0xE |
| 810  | `let old = self.ppb[self.active_core].read32(word_addr)` — `write16` RMW region 0xE     | CPU store, high nibble 0xE |
| 814  | `self.ppb[self.active_core].write32(word_addr, new_word)` — `write16` RMW region 0xE     | CPU store, high nibble 0xE |
| 858  | `self.ppb[self.active_core].write32(addr, val)` — `write32` region 0xE                   | CPU store, high nibble 0xE |

Each call is guarded by `match region { ... 0xE => ... }` where `region = addr >> 28`. By construction, every address reaching PPB has the top nibble equal to 0xE. On ARMv6-M the PPB mapping is `0xE000_0000..=0xE00F_FFFF`, so bits [27:20] are effectively always 0 from real firmware. Taking `addr & 0xFFFF` keeps bits [15:0] — which are the only ones that distinguish SCB registers inside the 64 KB PPB window. Bits [19:16] being non-zero would land at `0xE00x_XXXX` (outside any register we model and outside the M0+-architectural PPB), and the old code also ignored those bits via fall-through, so behaviour is preserved.

**Verdict:** tightening to 16 bits is safe. Any address with non-zero bits [27:16] is either firmware reaching into an M33-specific / reserved PPB region (fault-worthy behaviour on M0+) or a bus aliasing scenario that isn't modelled today; either way, `addr & 0xFFFF` gives the same read-as-zero / write-ignored fall-through the old code did.

### 4.2 Does tightening the mask break any test?

Grep for all callers of `Ppb::read32` / `Ppb::write32` and for pattern-style address literals:

- `grep "ppb.*read32\|ppb.*write32" crates/mdrp2040/` → only the eight bus call sites above. All pass canonical `0xE000_XXXX` addresses coming out of the `addr >> 28` decoder. Every one of those satisfies `(addr & 0xFFFF) == (addr & 0x0FFF_FFFF)` when the high-order bits are zero.
- `grep "0x000E_D" crates/mdrp2040/` → only the six lines *inside* the buggy match arms being replaced. Nothing else in the crate uses the pattern-style constants.
- `crates/mdrp2040/src/tests.rs` lines 1394, 1843, 1874, 1929 — all use field-direct assignment `bus.ppb[0].vtor = ...`, which bypasses the match block entirely. Unaffected by this change.
- `crates/mdrp2040/src/core/exceptions.rs` lines 110, 140, 181, 224 — all use field-direct access (`bus.ppb[...].vtor`, `.mark_active`, `.any_active`, `.clear_active`). Unaffected.
- `crates/mdrp2040/tests/smoke.rs` lines 81, 82 — field-direct. Unaffected (but will be augmented with a `bus.read32` assertion in §3.2).

**Verdict:** no existing test depends on the old mask semantics. The fix is a strict bug correction with no downstream ripple.

### 4.3 Does the fix interact with Phase 1's `direct_boot_from_flash`?

Phase 1 assigns `self.bus.ppb[i].vtor = vtor_addr` in `lib.rs:204-205` — field-direct, no match involvement. After the Phase 2 fix, `Bus::read32(0xE000_ED08)` will return the same value the field already holds. The two fixes compose correctly: Phase 1 puts the value in place; Phase 2 lets pico-sdk observe it through the memory-mapped path. Neither supersedes the other.

### 4.4 Does the fix affect mdrp2350?

No. The change is strictly confined to `crates/mdrp2040/`. mdrp2350's `bus/ppb.rs` already uses the `addr & 0xFFFF` idiom and has a working test module — we're applying the same pattern to mdrp2040 to bring them into alignment.

## 7. Post-fix empirical plan

After `cargo test -p mdrp2040` goes green:

```bash
cargo build -p mdpicoem-harness --release --bin picogus_diff_rp2040
cp target/release/picogus_diff_rp2040.exe /tmp/picogus_diff_rp2040_ppb.exe
mdtimeout 600 /tmp/picogus_diff_rp2040_ppb.exe -- \
    --flash third_party/picogus/picogus-v4.0.0.bin \
    --bootrom roms/rp2040/bootrom-rp2040-b2.bin \
    --trace crates/mdpicoem-harness/fixtures/sample_gus.trace \
    --out /tmp/picogus_after_ppb.wav \
    --post-roll 0.5 \
    --duration 5.0
```

### Acceptance criteria

- **Primary:** firmware progresses **well past cycle 42569** (where the `hard_assertion_failure` call from `irq_set_exclusive_handler`'s vtable-slot check currently halts it). Ideally into real I2S output generation or a genuinely new panic site at a much later PC.
- **Secondary:** no stall warning at cycle 42569 in the harness output. The specific trace line "stalled at cycle 42569" / the `irq_set_exclusive_handler` assertion trace should disappear.
- **Reported outputs:**
  - Final cycle count at exit.
  - If a new panic surfaces: PC, disassembly context, any visible faulting-instruction bytes, and best-guess call-site (panic message or symbol if resolvable).
  - Audio-output status: does `/tmp/picogus_after_ppb.wav` contain non-silence? A yes here is a strong signal we've cleared the SDK init path into the GUS emulation main loop.

### Non-acceptance / follow-up

If the firmware halts at a new site (not 42569) and the new site is **also** an SDK pre-init path (vs. PicoGUS's own main loop), that's still progress — report and stop for supervisor triage. Do not attempt to chase further bugs in the same session.

If the firmware halts back at 42569 or earlier, something in the fix is wrong — re-verify that `cargo test -p mdrp2040` passed, that the rebuild picked up the patch (check mtime on `/tmp/picogus_diff_rp2040_ppb.exe` vs. the rebuild), and stop for supervisor triage.
