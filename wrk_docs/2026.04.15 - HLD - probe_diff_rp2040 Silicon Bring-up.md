**Date:** 2026-04-15
**Scope:** narrow — bring the already-landed `probe_diff_rp2040` runner up on real RP2040 silicon now that a Pico V1 is on the rig. Add one small CLI affordance so the runner can coexist with the RP2354 runner on one host.

## 2. Probe disambiguation

### 2.1 The problem

`probe-rs` 0.31 `Session::auto_attach(target, ...)` calls `Lister::list_all()` and opens the **first** probe returned — no fallback, no target-aware selection. Code path in `probe-rs/src/session.rs:446–458`:

```rust
let probes = lister.list_all();
let mut probe = probes.first().ok_or(...)?.open()?;
```

So with two CMSIS-DAP probes attached (one to RP2354, one to RP2040), `auto_attach("rp2040", ...)` hits the first-enumerated probe unconditionally. If USB enumeration orders the RP2354 probe first, the attach fails on target mismatch.

Every silicon binary today uses `auto_attach` with a hardcoded target string — this bug is latent in all of them, not specific to the RP2040 runner.

### 2.2 The fix — add `--probe <selector>` to `probe_diff_*`

Add an optional `--probe <selector>` CLI flag to `probe_diff_rp2040` and (for parity) `probe_diff_rp2350`. When supplied, route attach through `DebugProbeSelector::from_str(selector)` + `Session::attach` instead of `auto_attach`. When omitted, keep current `auto_attach` behaviour.

```rust
let mut session = match args.probe.as_ref() {
    None => Session::auto_attach("rp2040", SessionConfig::default())?,
    Some(sel) => {
        let selector = DebugProbeSelector::from_str(sel)?;
        let probe = probe_rs::probe::list::Lister::new().open(&selector)?;
        probe.attach("rp2040", probe_rs::Permissions::default())?
    }
};
```

Selector format is probe-rs-native: `VID:PID:SERIAL` (e.g. `2e8a:000c:E46410955F3C5C27`). Relevant API surfaces in probe-rs 0.31:

- `DebugProbeSelector` — `probe-rs-0.31/src/probe.rs:911`
- `impl TryFrom<&str> for DebugProbeSelector` — line 990
- `impl FromStr for DebugProbeSelector` (delegates to `TryFrom`) — line 1031
- `Lister::open(&impl Into<DebugProbeSelector>)` — `probe-rs-0.31/src/probe/list.rs:31`
- `Probe::attach(target, permissions)` — `probe-rs-0.31/src/probe.rs:328`

### 2.3 Why CLI flag (not env var, not auto-detect-by-TARGETID)

- **No env var** — per project policy; CLI flag is explicit, scoped to the invocation, doesn't leak into shell history as a persistent setting.
- **No auto-detect-by-TARGETID** — would require a custom `Lister::list_all()` → `attach_each_until_success` loop. Cheap if it works, but a slow/hung probe turns "zero config" into a 10 s+ stall, and the retry-each-probe path is exactly the kind of premature abstraction CLAUDE.md warns against. If we have two probes, we know which is which from `probe-rs list` once; pasting the serial is trivial.
- **Scope** — only `probe_diff_*` needs this right now. The other silicon binaries (`silicon_*_rp2350`) will keep using `auto_attach` until their bring-up waves land; extend the same flag to them then, not speculatively now.

### 2.4 CLAUDE.md probe-serial note (once both probes present)

Record the observed serials in `CLAUDE.md` under "Non-Obvious Conventions" so any operator knows which is which:

```
Probe serials on the lab rig:
- RP2354 target:  2e8a:000c:<RP2354 probe serial> — pass to probe_diff_rp2350 via --probe
- RP2040 target:  2e8a:000c:E46410955F3C5C27       — pass to probe_diff_rp2040 via --probe
```

Only populate the RP2354 row once that probe is plugged back in and we've read its serial.

## 3. Bring-up sequence

Bring-up is iterative — we don't know yet what silicon will expose. Plan:

1. **Run targeted suite.** `cargo run -p mdpicoem-harness --release --bin probe_diff_rp2040` with no fuzz. Expect: M0+-safe targeted cases pass end-to-end; some may fail and reveal bugs in either (a) `is_m0plus_silicon_safe` (admits something M0+ actually faults on), (b) our emulator (a gap between emu and hardware), or (c) the runner plumbing (e.g. reset/halt timing too aggressive on this probe firmware).
2. **Triage failures.** For each failure, classify as one of the three above. Fix. Re-run the exact case (targeted cases are deterministic).
3. **Short fuzz.** `--fuzz 1000` sanity run once targeted is clean.
4. **Standard fuzz.** `--fuzz 100000` — this is the real smoke test.
5. **Overnight soak.** Drop a `fuzz-runs/run-m0plus-probe.sh` driver (see §4) and let it run under the shared-deadline protocol.

This is classic bring-up — I'm not going to pre-design fixes for bugs that aren't on the table yet. The HLD's job here is to scope the work and name the exit criteria, not invent failure modes.

### 3.1 Exit criteria

- Targeted catalogue: 100 % pass, 0 skip on probe errors (skips during triage are fine; zero at exit).
- 100 K fuzz session: 0 semantic failures.
- Any bugs found and fixed are journaled in `wrk_journals/` with the seed + instruction class that caught them.

### 3.2 What I expect to find (informed guesses, not plans)

- **Reset-and-halt timing.** The runner already uses a 500 ms window; this may need adjustment on the new probe firmware. If so, bump it in one line and note why.
- **Bootrom interaction.** M0+ boots into ROM then jumps to flash. `reset_and_halt` sets `DEMCR.VC_CORERESET` (vector catch on reset), so probe-rs halts the core at `PC=0` before the bootrom executes. The runner then writes PC/SP/xPSR explicitly, so bootrom state doesn't contaminate the test. If this assumption is ever wrong, we'd see drift in post-state (MSP pointing somewhere surprising, R0 non-zero, etc.).
- **Filter gaps surfacing as silent drift.** `is_m0plus_silicon_safe`'s admit list is derived from the ARMv6-M spec, not silicon. If something slips through and UNDEFs on M0+, silicon takes a HardFault — `VTOR=0` at reset, so dispatch reads the handler pointer from the bootrom vector table and the CPU lands somewhere deep in ROM. Our `core.step()` completes but post-PC is in the bootrom, not at the BKPT sentinel. The current runner doesn't detect this — it compares registers and gets a mysterious divergence. **Fix: add a post-step PC sanity check**. After `core.step()`, assert PC is at `EMU_M0PLUS_TEST_SLOT + expected_insn_len` (the BKPT). If not, classify as `UNDEF_ON_SILICON` and report distinctly. ~5 lines, strictly diagnostic — doesn't change pass/fail semantics, just makes filter-gap bugs self-announce. Do this as part of §2 before the first real run.

### 3.3 Pre-flight sanity — the checks I've already done

Spent a pass looking at the obvious footguns:

- **Test-slot addresses.** `EMU_M0PLUS_TEST_SLOT=0x20000100`, `EMU_M0PLUS_TEST_SCRATCH=0x20000200`, `EMU_M0PLUS_TEST_STACK=0x20001000`. All in striped SRAM bank 0 on RP2040 (`0x20000000`–`0x2003FFFF`), nowhere near the bootrom scratchpad area near the top of SRAM. Safe to use without touching bootrom working memory.
- **Core 1 quiescence.** `reset_and_halt` issues `SYSRESETREQ` (system reset), which resets both cores, and the vector-catch bit halts both at their reset vectors. The runner only talks to `session.core(0)`, leaves core 1 halted and untouched. No cross-core contamination path.
- **Pico V1 flash contents are irrelevant.** Whatever MicroPython / blinky / garbage sits in the board's QSPI flash never executes, because we halt before bootrom runs and we run tests out of SRAM.
- **probe-rs API confirmed.** `DebugProbeSelector` at `probe-rs-0.31/src/probe.rs:911`, `FromStr`/`TryFrom<&str>` both present; `Lister::new().open(&selector)` and `Probe::attach(target, permissions)` are stable public API in 0.31.
- **SWD clock.** probe-rs default (1 MHz) is conservative and matches what we use for RP2354. If bring-up shows probe-rs errors that aren't semantic diffs, lower to 500 kHz before chasing other causes.

### 3.4 Filter duplication (debt, not blocker)

The two M0+ runners carry two overlapping filters:

- `is_m0plus_safe` in `mdpicoem-harness::lib` — rejects *all* Thumb-32 (QEMU's `cortex-m0` can't execute Thumb-32 so this keeps the QEMU oracle sane).
- `is_m0plus_silicon_safe` in `probe_diff_rp2040.rs` — admits the M0+ Thumb-32 subset.

Not a bring-up blocker; once silicon is green, consider collapsing them into one filter with a `ThumbSubset::{M0Only, M0PlusFull}` mode. Explicitly deferred — current duplication is tolerable (the silicon filter is only 80 lines) and collapsing requires touching both oracles. Don't do it as part of this HLD's work.

## 4. Fuzz driver

Drop a new overnight script `fuzz-runs/run-m0plus-probe.sh`, modelled exactly on `fuzz-runs/run-probe.sh`:

- Same deadline-file protocol (`fuzz-runs/deadline`).
- PID-qualified copy of `target/release/probe_diff_rp2040.exe` so concurrent rebuilds don't hit the Windows exclusive-lock issue.
- Log to `fuzz-runs/m0plus-probe.log`.
- Per-batch `--fuzz 200 --seed $RANDOM$RANDOM$RANDOM`.
- No `--cycles` flag (M0+ has no CYCCNT; this is already baked into the runner).
- Pass `--probe <RP2040 serial>` when the RP2354 probe is also plugged in; otherwise omit.

Exact mirror of `run-probe.sh` — copy, rename, change the binary and log paths. ~5 line delta.
