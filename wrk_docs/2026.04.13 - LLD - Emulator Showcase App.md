## 1. Purpose

Low-level design for `mdrp2354-app`: a ratatui dashboard that runs firmware
on the emulator paced at real-time and shows off fidelity via a simulated
LED, a simulated 20x2 character LCD, and a benchmark comparison against
hardcoded real-hardware reference numbers.

## 2. Revisions from the HLD

Two assumptions in the HLD turned out to be wrong. The revisions are small
but they simplify things rather than complicate them.

### 2.1. No SPI peripheral exists

`mdrp2354-periph` is currently a one-line placeholder. There is no SPI
model to snoop.

**Revision:** the LCD uses **GPIO bit-bang** for its wire protocol. The
firmware toggles three GPIO pins (SCLK, DATA, CS — see §7.2) to serialize
bytes. The external observer samples GPIO on clock edges and decodes.

This is *better* than adding SPI:

- Zero changes to `mdrp2354` or `mdrp2354-periph`.
- The "observer" is just a read of `bus.gpio_out` — the LCD becomes
  structurally identical to the LED.
- The firmware's SPI driver is ~40 lines of hand-assembled Thumb, no SPI
  peripheral setup boilerplate needed.

### 2.2. No DWT CYCCNT in the emulator

The core does not implement DWT; the cycle register is not memory-mapped.
The firmware cannot read its own cycle count.

**Revision:** host-driven cycle measurement. The firmware writes a **phase
sentinel** to a known SRAM address before and after each benchmark section.
The host (sim thread) polls that address; when the sentinel changes, it
records the emulator's current `emu.cycles()`. Section cycle count =
`cycles_at_end - cycles_at_start`.

Jitter: bounded by the sim thread's quantum (default 150 cycles = 1 µs on a
150 MHz config). Benchmark sections are sized ≥ 1M cycles, so jitter is
well under 0.02%.

This also means the firmware is pure portable Thumb — no co-processor
accesses, no ARM-specific timer setup. Clean.

## 4. Sim Thread

One file: `src/sim.rs`. One `run()` function. No sim-thread struct.

Firmware is loaded from disk in `main()` (§9) *before* the TUI enters raw
mode, so file-not-found errors hit stderr cleanly. The sim thread receives
already-read byte vectors — it cannot fail on I/O.

```rust
pub struct FirmwareBytes {
    pub bootrom: Vec<u8>,  // roms/bootrom-combined.bin
    pub flash:   Vec<u8>,  // the selected firmware
}

pub fn run(
    fw: FirmwareBytes,
    snapshot: Arc<RwLock<Snapshot>>,
    shutdown: Arc<AtomicBool>,
) -> anyhow::Result<()> {
    let config = Config::default();       // 150 MHz, dual-core
    let sys_clk_hz = config.sys_clk_hz;
    let mut emu = Emulator::new(config);

    emu.load_bootrom(&fw.bootrom);
    emu.load_flash(&fw.flash);
    emu.reset();
    emu.core_mut(1).halt();               // firmwares are single-core

    let mut pacer = Pacer::with_quantum(sys_clk_hz, 150);
    let qc = pacer.quantum_cycles();
    let start = Instant::now();

    let mut lcd = LcdDecoder::new();
    let mut bench = BenchmarkPoller::new();

    while !shutdown.load(Ordering::Relaxed) {
        pacer.begin_quantum();
        emu.run(qc);
        pacer.end_quantum();

        // Observe peripheral state
        let gpio_out = emu.bus.gpio_out;
        let gpio_oe  = emu.bus.gpio_oe;
        lcd.sample(gpio_out);
        bench.poll(&emu, start.elapsed());

        // Publish snapshot
        let elapsed = start.elapsed();
        let mut s = snapshot.write().unwrap();
        s.cycles        = emu.cycles();
        s.wall_ms       = elapsed.as_millis() as u64;
        s.effective_mhz = (emu.cycles() as f64) / elapsed.as_secs_f64() / 1e6;
        s.pc            = emu.core(0).regs.pc();
        s.gpio_out      = gpio_out;
        s.gpio_oe       = gpio_oe;
        s.lcd           = lcd.state();
        s.benchmark     = bench.report();
    }

    Ok(())
}
```

**Pacing modes:** there is one, always paced. Benchmark firmware completes
in well under one wall-clock second even paced at 150 MHz.

**Emulator config:** `Config::default()` — 150 MHz, dual-core. We halt
core 1 explicitly; none of our firmwares use it and an un-halted core would
fetch garbage from an unconfigured PC.

**Quantum:** 150 cycles, matching `paced_bench`. ~1 µs of simulation per
quantum. This is the sampling rate the LCD decoder sees for GPIO observation
(see §4.1 for the resulting timing contract) and the jitter bound on
benchmark sentinels (<0.02% on 1M-cycle sections).

**Error handling:** the function is `Result`-returning for ergonomics but
the steady-state loop is infallible — panics are the only failure mode, and
§6.1 covers propagating them to the UI.

### 4.1. GPIO sampling timing contract

Because the sim thread observes GPIO only once per quantum, any GPIO edge
that happens *inside* a quantum is invisible — we see only the state at the
end. A firmware bit-bang loop toggling SCLK every ~10 cycles would lose
bits silently.

**The contract:** any GPIO transition the observer must catch (i.e. SCLK
and CS edges on the LCD pins) must be separated from the next transition
on the same signal by **at least 2 × quantum_cycles = 300 cycles** at the
default quantum. This guarantees both edges fall in distinct quantum
samples.

The LCD decoder cares about SCLK edges. The LCD firmware therefore:

- Holds each SCLK level for ≥ 300 cycles before toggling (~500 kbit/s at
  150 MHz — still hundreds of refreshes per second for a 20×2 LCD)
- Holds CS low for ≥ 300 cycles after the last SCLK rising edge before
  raising CS
- Holds CS high for ≥ 300 cycles between frames

`gen_lcd_demo.py` emits an inline delay loop (`subs/bne` on a fixed counter)
at every edge transition to honour this. No magic numbers in the protocol —
the delay is large enough to be safely above any plausible quantum.

If we later reduce the quantum (e.g. to 50 cycles for lower observation
latency), the contract relaxes automatically. We do not reduce it now.

### 4.2. Thread spawning

`main()` spawns the sim thread via `std::thread::Builder::new().name("sim")
.spawn(move || sim::run(...))`, keeps the returned `JoinHandle`, and checks
`handle.is_finished()` each frame of the UI loop. A finished handle during
normal operation means the sim thread panicked (or returned Err); the UI
breaks its loop, joins the handle, and reports the error on stderr after
tearing down the terminal (§6.1).

## 6. UI Thread

Main thread. Event loop in `src/ui.rs`:

```rust
pub fn run(
    snapshot: Arc<RwLock<Snapshot>>,
    shutdown: Arc<AtomicBool>,
    sim_handle: &thread::JoinHandle<anyhow::Result<()>>,
) -> anyhow::Result<()> {
    let frame_period = Duration::from_millis(33);  // ~30 fps
    let mut next_frame = Instant::now();

    let mut terminal = Terminal::new(CrosstermBackend::new(stdout()))?;

    loop {
        // If the sim thread died, stop drawing so main() can surface the error.
        if sim_handle.is_finished() {
            shutdown.store(true, Ordering::Relaxed);
            break;
        }

        // Draw
        let snap = snapshot.read().unwrap().clone();
        terminal.draw(|f| draw_dashboard(f, &snap))?;

        // Poll input for remainder of frame budget
        let budget = next_frame.saturating_duration_since(Instant::now());
        if event::poll(budget)? {
            if let Event::Key(k) = event::read()? {
                let ctrl_c = k.code == KeyCode::Char('c')
                    && k.modifiers.contains(KeyModifiers::CONTROL);
                if k.code == KeyCode::Char('q') || ctrl_c {
                    shutdown.store(true, Ordering::Relaxed);
                    break;
                }
            }
        }
        next_frame += frame_period;
    }

    Ok(())
}
```

Note: `enable_raw_mode` / `disable_raw_mode` and `EnterAlternateScreen` /
`LeaveAlternateScreen` are not called here. They are the responsibility of
the terminal lifecycle guard in `main()` — see §6.1.

### 6.1. Terminal lifecycle (panic-safe)

A naive `enable_raw_mode()` + `disable_raw_mode()` pair is brittle: any
panic between them leaves the user's terminal in raw mode with no echo, no
cursor, and stuck in the alternate screen. `main()` installs two defences:

**1. RAII guard.** A `struct TerminalGuard;` whose `new()` calls
`enable_raw_mode()` + `execute!(stdout(), EnterAlternateScreen, Hide)` and
whose `Drop` reverses both — unconditionally, even on unwind.

```rust
struct TerminalGuard;

impl TerminalGuard {
    fn new() -> anyhow::Result<Self> {
        enable_raw_mode()?;
        execute!(stdout(), EnterAlternateScreen, cursor::Hide)?;
        Ok(Self)
    }
}

impl Drop for TerminalGuard {
    fn drop(&mut self) {
        let _ = execute!(stdout(), cursor::Show, LeaveAlternateScreen);
        let _ = disable_raw_mode();
    }
}
```

**2. Panic hook.** `main()` installs a panic hook *before* creating the
guard that calls the same teardown sequence, then delegates to the default
hook. This covers the case where `panic = "abort"` is in effect (workspace
release profile sets this) — aborting skips `Drop`, so the hook is our
only chance to restore the terminal before the process dies.

```rust
let default_hook = panic::take_hook();
panic::set_hook(Box::new(move |info| {
    let _ = execute!(stdout(), cursor::Show, LeaveAlternateScreen);
    let _ = disable_raw_mode();
    default_hook(info);
}));
```

**3. Sim thread failure.** After `ui::run()` returns, `main()` joins the
sim thread's `JoinHandle`. Three cases:

| Outcome | Action |
|---|---|
| `Ok(Ok(()))` | Normal shutdown, exit 0 |
| `Ok(Err(e))` | Sim returned an error, print `e` to stderr, exit 1 |
| `Err(panic_payload)` | Sim panicked, print panic payload to stderr, exit 1 |

The guard's `Drop` has already restored the terminal by the time we print,
so stderr lands cleanly.

## 7. Device Models

### 7.1. LED

Not a model. A single bit in `Snapshot.gpio_out` read by `panels/gpio.rs`.
Zero state. Zero code beyond the panel.

### 7.2. LCD — GPIO bit-bang decoder

The firmware uses 3 GPIO pins:

| Pin | Role |
|-----|------|
| 14  | SCLK (rising edge = sample DATA) |
| 15  | DATA (MOSI) |
| 16  | CS (active low — frames a transaction) |

These pins are chosen to be obviously distinct from GPIO 25 (the LED).
They are hardcoded — no configuration.

**Decoder state machine** (`devices/lcd.rs`):

```rust
pub struct LcdDecoder {
    prev_gpio:  u32,
    shift:      u8,
    bit_count:  u8,
    in_frame:   bool,
    rx_buf:     Vec<u8>,
    state:      LcdState,
}

impl LcdDecoder {
    pub fn sample(&mut self, gpio_out: u32) {
        let cs_now   = gpio_out & (1 << 16) == 0;      // active low
        let cs_prev  = self.prev_gpio & (1 << 16) == 0;
        let sclk_now = gpio_out & (1 << 14) != 0;
        let sclk_prev = self.prev_gpio & (1 << 14) != 0;
        let data     = gpio_out & (1 << 15) != 0;

        // CS falling edge: start frame
        if cs_now && !cs_prev {
            self.in_frame  = true;
            self.bit_count = 0;
            self.rx_buf.clear();
        }

        // SCLK rising edge inside frame: sample data
        if self.in_frame && sclk_now && !sclk_prev {
            self.shift = (self.shift << 1) | (data as u8);
            self.bit_count += 1;
            if self.bit_count == 8 {
                self.rx_buf.push(self.shift);
                self.shift = 0;
                self.bit_count = 0;
            }
        }

        // CS rising edge: end frame, apply bytes
        if !cs_now && cs_prev {
            self.in_frame = false;
            self.apply_bytes();
        }

        self.prev_gpio = gpio_out;
    }

    fn apply_bytes(&mut self) {
        // Command interpretation (see §7.3)
        // ...
    }

    pub fn state(&self) -> LcdState { self.state.clone() }
}
```

**Edge detection is per-quantum**, not per-instruction. The LCD firmware
must honour the timing contract from §4.1 — each SCLK level held for
≥ 2 × quantum_cycles = 300 cycles at the default quantum — or bits will
be silently dropped. `gen_lcd_demo.py` emits the required delay loops
around every edge transition.

Increasing fidelity by sampling GPIO after every `emu.step()` would work
but imposes ~150× more observation work per emulated second. Not
worthwhile: the contract solution is free, and the firmware cooperates
because we wrote it.

### 7.3. LCD wire protocol

Frame = bytes between CS-low and CS-high. First byte is the command.

| Cmd  | Name       | Args         | Effect |
|------|------------|--------------|--------|
| 0x01 | CLEAR      | —            | Fill with spaces, cursor = (0,0) |
| 0x02 | SET_CURSOR | col, row     | Move cursor; clamp col∈[0,19], row∈[0,1] |
| 0x03 | WRITE      | char+...     | Write chars; auto-advance; wrap at col 20; scroll at row 2 |

No DRAM, no font ROM, no control lines beyond the three GPIO pins. The
firmware uses CLEAR at start, SET_CURSOR before each line, WRITE for the
payload.

## 8. Benchmark

### 8.1. Sentinel protocol

One SRAM address is the "phase register": **`0x2003_FF00`** (near the top
of SRAM, safely above any stack or heap).

```
0x2003_FF00: u32  phase (written by firmware)
0x2003_FF04: u32  section_count (written by firmware)
0x2003_FF08: u32  magic = 0xBE0C_C0DE (set when report layout is valid)
```

Phase values:

| Phase | Meaning |
|-------|---------|
| 0x00  | Not yet started (initial SRAM content) |
| 0x1N  | Section N started (N = 1..=section_count) |
| 0x2N  | Section N done |
| 0xFF  | All sections complete, firmware halts |

The firmware writes the phase before and after each section, then busy-loops
on phase=0xFF forever. (No BKPT: avoids pulling in exception handling.)

**Iteration counts** for each section are baked into the firmware as
constants; the host knows them from `firmware.rs`'s reference table.

### 8.2. Poller

```rust
pub struct BenchmarkPoller {
    last_phase:    u32,
    section_start: u64,
    sections:      Vec<BenchmarkSection>,
    complete:      bool,
    stall:         Option<u32>,   // phase at which we gave up waiting
}

const STALL_TIMEOUT: Duration = Duration::from_secs(10);

impl BenchmarkPoller {
    pub fn poll(&mut self, emu: &Emulator, wall: Duration) {
        let phase = emu.peek(0x2003_FF00);

        if phase != self.last_phase {
            let now = emu.cycles();
            match phase & 0xF0 {
                0x10 => self.section_start = now,
                0x20 => {
                    let idx = (phase & 0x0F) as usize - 1;
                    if let Some(ref_section) = REFERENCE_TABLE.get(idx) {
                        self.sections.push(BenchmarkSection {
                            name:       ref_section.name,
                            emu_cycles: now - self.section_start,
                            ref_cycles: ref_section.cycles,
                            iterations: ref_section.iterations,
                        });
                    }
                }
                0xF0 => self.complete = true,
                _ => {}
            }
            self.last_phase = phase;
        }

        // Stall detection: any phase the firmware holds for more than the
        // timeout before reaching 0xFF is reported in the panel.
        if !self.complete && self.stall.is_none() && wall > STALL_TIMEOUT {
            self.stall = Some(phase);
        }
    }

    pub fn report(&self) -> Option<BenchmarkReport> {
        if self.sections.is_empty() && self.stall.is_none() {
            return None;
        }
        Some(BenchmarkReport {
            sections: self.sections.clone(),
            complete: self.complete,
            stall:    self.stall,
        })
    }
}
```

The stall field gets rendered by the bench panel as e.g. `stalled at phase
0x14 after 10s` when set. Since we wrote the firmware this is effectively a
"benchmark has a bug" indicator, not a normal operating condition.

### 8.4. Firmware builder

New file: `roms/gen_benchmark.py`. Same pattern as `roms/gen_blinky.py` —
hand-assembled Thumb, built as a picobin flash image. Outputs
`roms/benchmark.bin`.

Section bodies are tight loops with the instruction under test in the
critical path:

```
  ; Section 1: arith_add
  movw r0, #LO(0x2003FF00); movt r0, #HI(0x2003FF00)
  movs r1, #0x11
  str  r1, [r0]            ; phase = 0x11 (section 1 start)

  movw r2, #0xFFFF
  movt r2, #0x0000         ; r2 = iteration counter (load hi/lo appropriately)
  movs r3, #1
.L1:
  adds r3, r3, #1          ; the instruction under test
  subs r2, r2, #1
  bne  .L1

  movs r1, #0x21
  str  r1, [r0]            ; phase = 0x21 (section 1 done)
```

The loop's timing is dominated by the `adds` + `subs` + `bne` triplet per
iteration, not by the instruction under test — this would corrupt the
measurement. Solution: unroll 8x, measure the *marginal cost* by running
the same loop twice (once with 8 copies of `adds`, once with 0 copies) and
subtracting. But that's complex.

**Simpler:** don't pretend we're measuring ADDS in isolation. Report
"triplet cycles per iteration" and compare against the same triplet on real
hardware. The Δ column still shows fidelity — it just doesn't show
"ADDS = 1 cycle" directly. That's fine; the isa cycle table panel (§6.2)
shows the per-instruction numbers separately.

The builder Python script encodes iterations as constants and emits the
unrolled loops. ~300 LoC.

### 8.5. Reference number capture

Procedure, documented in `firmware.rs`:

```rust
// Reference cycle counts captured from a real Raspberry Pi Pico 2.
//
// How to regenerate:
//   1. Flash roms/benchmark.bin to a Pico 2 via probe-rs:
//        probe-rs download --chip RP235x_Arm roms/benchmark.bin
//   2. Attach via SWD and read back 0x2003_FF00..0x2003_FFFF.
//      (See tools/capture_bench_ref.rs — TODO before Phase 3 ships.)
//   3. Paste the values into REFERENCE_TABLE below.
//
// These numbers are static. They are re-captured if benchmark.bin changes.
```

Reference numbers live as `const REFERENCE_TABLE: &[BenchmarkReference] = &[...]`
in `firmware.rs`. No file I/O at runtime.

Note the chicken-and-egg: the firmware measures itself on the emulator, but
to get reference values we need to measure the firmware on real hardware.
The firmware itself does **not** need DWT access — it just writes phase
markers. Real-hardware cycle counts come from the SWD-side measurement
(single-stepping cycles, or enabling DWT via probe-rs at capture time).
This is a one-shot manual step, not automation.

## 9. CLI

Positional. Single argument. No flags.

Firmware bytes are read in `main()` *before* the terminal guard is
installed, so a missing file prints a clean stderr error and exits without
touching the terminal.

```rust
fn resolve_firmware_path(arg: &str) -> PathBuf {
    match arg {
        "blinky"    => PathBuf::from("roms/blinky.bin"),
        "benchmark" => PathBuf::from("roms/benchmark.bin"),
        "lcd"       => PathBuf::from("roms/lcd_demo.bin"),
        path        => PathBuf::from(path),
    }
}

fn main() -> anyhow::Result<()> {
    let arg = std::env::args().nth(1).unwrap_or_else(|| "blinky".into());
    let fw_path = resolve_firmware_path(&arg);

    let fw = FirmwareBytes {
        bootrom: std::fs::read("roms/bootrom-combined.bin")
            .context("reading roms/bootrom-combined.bin")?,
        flash:   std::fs::read(&fw_path)
            .with_context(|| format!("reading {}", fw_path.display()))?,
    };

    install_panic_hook();
    let guard = TerminalGuard::new()?;

    let snapshot = Arc::new(RwLock::new(Snapshot::default()));
    let shutdown = Arc::new(AtomicBool::new(false));

    let sim_handle = {
        let snapshot = Arc::clone(&snapshot);
        let shutdown = Arc::clone(&shutdown);
        std::thread::Builder::new()
            .name("sim".into())
            .spawn(move || sim::run(fw, snapshot, shutdown))?
    };

    let ui_result = ui::run(snapshot, shutdown.clone(), &sim_handle);

    // Restore the terminal *before* we print any diagnostics on stderr.
    drop(guard);

    // Propagate sim thread outcome (see §6.1 table).
    match sim_handle.join() {
        Ok(Ok(()))  => ui_result,
        Ok(Err(e))  => { eprintln!("sim thread error: {e:#}"); std::process::exit(1); }
        Err(payload) => {
            let msg = payload.downcast_ref::<&str>().copied()
                .or_else(|| payload.downcast_ref::<String>().map(String::as_str))
                .unwrap_or("unknown panic");
            eprintln!("sim thread panicked: {msg}");
            std::process::exit(1);
        }
    }
}
```

The bootrom path is `roms/bootrom-combined.bin`, same as the blinky
integration test (`crates/mdrp2354/src/tests.rs:5289`).

## 10. Firmware Binaries

Three `.bin` files in `roms/`, all built by Python scripts:

| File | Builder | LoC (est.) | Purpose |
|------|---------|------------|---------|
| `blinky.bin` | existing | — | Phase 1 |
| `lcd_demo.bin` | new — `gen_lcd_demo.py` | ~300 | Bit-bang "Hello\\nfrom mdrp2354" forever |
| `benchmark.bin` | new — `gen_benchmark.py` | ~400 | §8 benchmark sections + sentinels |

### 10.1. LCD demo firmware (`gen_lcd_demo.py`)

Structure:

1. **Vector table + picobin image block** — copy from `gen_blinky.py`
2. **GPIO init** — replicate blinky's pad + ctrl + OE sequence for *each*
   of the three LCD pins (GPIO 14, 15, 16). Per pin, ~8 instructions:
   - Write `0x34` to `PADS_BANK0_GPIO{N}` (IE=1, drive=4mA, …)
   - Write `5` (SIO function) to `IO_BANK0_GPIO{N}_CTRL`
   - Set bit `N` in `SIO_GPIO_OE_SET`
3. **Bit-bang helpers** — Python functions that emit Thumb:
   - `emit_delay(cycles)` — `movs rN,#imm; subs rN,#1; bne .-2` loop
     sized to burn at least `cycles` cycles (minimum 300, see §4.1)
   - `emit_gpio_set(mask)` / `emit_gpio_clr(mask)` — STR to SIO_GPIO_OUT_SET
     / SIO_GPIO_OUT_CLR
   - `emit_spi_byte(b)` — emit 8 × {data bit, SCLK↑, delay, SCLK↓, delay}
     framed by {CS↓, delay, …, delay, CS↑, delay}
4. **LCD frame helpers:** `emit_cmd_clear()`, `emit_cmd_set_cursor(col, row)`,
   `emit_cmd_write(text)`. Each wraps `emit_spi_byte` and applies the wire
   protocol from §7.3.
5. **Main loop** — clear, write row 0, write row 1, delay, repeat with a
   scrolled message.

GPIO pin setup is the bulk of the non-bit-bang boilerplate (~24 Thumb
instructions across 3 pins) and is why the LoC estimate is ~300, not ~150.

### 10.2. Benchmark firmware (`gen_benchmark.py`)

Same picobin + vector table pattern. No GPIO setup (benchmark does not
touch GPIO). Sections are unrolled inner loops as described in §8.4, each
bracketed by phase-sentinel stores. Terminates in `b .` after writing
phase=0xFF.

Both new builders include a `main()` that writes the output to the first
positional CLI argument, matching `gen_blinky.py`.

## 11. Phased Build

## 12. Test Strategy Summary

Per phase above. One rule: **no mocking the emulator**. Tests instantiate
real `Emulator` objects and run real firmware. The sim thread is not tested
in isolation; it's exercised through the end-to-end smoke tests.

Integration tests live in `crates/mdrp2354-app/tests/`. They use a
`run_for(duration_ms)` helper that spawns the sim thread, sleeps, sets
shutdown, joins, and returns the final snapshot.
