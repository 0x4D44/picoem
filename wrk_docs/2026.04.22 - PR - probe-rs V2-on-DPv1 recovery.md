# Recover from V2 AP access with DPv1 SELECT cache instead of panicking (fixes #3872)

## Summary

`ArmCommunicationInterface::select_ap_and_ap_bank` currently panics via
`unreachable!()` when an ADIv6 V2 access port is addressed while the DP
state cache is still `SelectCache::DPv1`. This PR replaces the panic for
the `(ApAddress::V2, SelectCache::DPv1)` cross-product with an in-place
cache upgrade to `DPv3` plus a single `tracing::warn!`, then proceeds
down the existing V2 path.

Closes #3872. Related: #3257.

Note: this replaces PR #3578's message-only improvement at the same call
site; if maintainers prefer, this PR can be rebased atop #3578 or #3578
can be closed.

## Why the panic fires in practice

`DpState::new()` always initialises `current_select` as
`SelectCache::DPv1(..)`. The cache is only promoted to `DPv3` in
`select_dp` when the initial DPIDR read returns
`idr.version == DebugPortVersion::DPv3`.

If that first DPIDR read returns any other version — observed on RP235x
silicon and on nRF9151 (see #3257) — the cache stays `DPv1`. Targets
whose YAML declares V2 APs (e.g. `targets/RP235x.yaml`, core0 at
`!v2 0x2000`) then resolve `memory_ap` via a V2 fully-qualified address
during `Session::attach_arm_debug_interface` →
`CombinedCoreState::enable_arm_debug` → `ArmDebugSequence::debug_core_start`
→ `ArmDebugInterface::memory_interface`. The first AP read hits
`select_ap_and_ap_bank`, falls through to the `_ =>` arm, and aborts.

Reported panic (from #3872, unchanged on master):

```
thread 'tokio-runtime-worker' panicked at
  probe-rs/src/architecture/arm/communication_interface.rs:...
internal error: entered unreachable code: Did not expect to be called with
FullyQualifiedApAddress { dp: Default, ap: V2(ApV2Address(Some(2000))) }.
This is a bug, please report it.
```

## The fix

```rust
// Recover from the initial DPIDR read reporting a pre-DPv3 version on
// an ADIv6 target. V2 APs are only reachable in probe-rs via the DPv3
// branch of access-port enumeration, so if we have been asked to
// address one, the DP really is ADIv6 and the cache just never got
// promoted. Upgrade it in place and proceed down the V2 path; the
// outer `previous_select != current_select` check below will flush the
// new SELECT / SELECT1 registers on this same call.
(ApAddress::V2(base), cache @ SelectCache::DPv1(_)) => {
    tracing::warn!(
        "ApV2 access on DPv1 SELECT cache; upgrading cache to DPv3"
    );
    *cache = SelectCache::DPv3(SelectV3(0), Select1(0));
    let SelectCache::DPv3(s, s1) = cache else {
        unreachable!("cache was just set to DPv3 above")
    };
    let address = base.0.unwrap_or(0) + ap_register_address;
    s.set_addr(((address >> 4) & 0xFFFF_FFFF) as u32);
    s1.set_addr((address >> 32) as u32);
}
```

The two existing arms (`(V1, DPv1)` and `(V2, DPv3)`) are untouched.
The remaining `_ => unreachable!()` still catches the two genuinely
impossible combinations `(V1, DPv3)` and whatever else future
`ApAddress` / `SelectCache` variants might add.

### Why this is the right shape

- **V2 APs are only reachable in probe-rs via DPv3.** In
  `ArmDebugInterface::access_ports` at
  `probe-rs/src/architecture/arm/communication_interface.rs:284-289`,
  the dispatch is:

  ```rust
  DebugPortVersion::DPv0 | DebugPortVersion::DPv1 | DebugPortVersion::DPv2 => {
      Ok(ap::v1::valid_access_ports(self, dp).into_iter().collect())
  }
  DebugPortVersion::DPv3 => ap::v2::enumerate_access_ports(self, dp),
  ```

  That is, V2 AP enumeration is reachable *only* through the DPv3 arm;
  all of DPv0/DPv1/DPv2 route through V1-AP enumeration. Therefore any
  caller that has constructed a V2 AP address has already been down the
  DPv3 branch and expects a DPv3 DP; promoting the cache to DPv3 in the
  panicking arm matches the invariant probe-rs already enforces at
  enumeration time.
- **Minimum-surface defensive fix.** No public API change; no new
  plumbing; no change to `select_dp`; only the previously-panicking arm
  is now handled.
- **Observable.** The `warn!` lets downstream users confirm whether
  they're hitting the recovery path. If it fires repeatedly in a single
  session, that's a separate DP-state bug this patch intentionally
  surfaces rather than hides.

## Known limitation

On RP2354 / Pi Pico 2 via CMSIS-DAP, the `unreachable!()` no longer
fires; some downstream workloads (e.g. core-0 reset-halt churn through
`Rp235x::reset_system` → `debug_core_start`) continue to surface a
separate `Arm(WrongApType)` error that I am investigating locally as an
orthogonal DP-state bug. I will file a follow-up issue once I have a
minimal reproducer that does not depend on my downstream test harness.
This PR's contribution — removing the `unreachable!()` panic at this
call site — is complete and independently valuable on its own.

## Reproducing the panic (pre-patch)

From #3872:

1. Use a Pico Probe (or any CMSIS-DAP probe) against a Raspberry Pi
   Pico 2 (RP235x) or equivalent ADIv6 V2-AP target.
2. `probe-rs attach --chip RP235x <firmware.elf>` (or `--chip rp2350`).
3. The session panics at the `unreachable!` with the `ApV2Address(..)`
   payload.

From #3257: same panic via `probe-rs reset` without `--chip` against an
nRF9151.

## After the patch

- No panic.
- `probe-rs attach --chip RP235x <firmware.elf>` proceeds past
  `debug_core_start`.
- On `RUST_LOG=warn`, exactly one
  `ApV2 access on DPv1 SELECT cache; upgrading cache to DPv3` line per
  session when the path is taken; zero lines when the initial DPIDR
  read succeeds as DPv3 (the normal path).
