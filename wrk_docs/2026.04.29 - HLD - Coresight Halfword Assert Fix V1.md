# HLD — Coresight Halfword Assert Fix V1

**Date:** 2026-04-29
**Author:** HLD agent (opus 4.7)
**Status:** Draft for supervisor review.
**Source of work:** `tech_debt.md` § "Residue-test failures discovered by V2 mutation sweep (2026-04-29)" entry #2.

## 1. Goal

Re-enable the unit test
`tests::stage3_bus_residue::coresight_trace_halfword_read_dispatches_through_byte_path`
(`crates/mdrp2350/src/tests.rs:25754`), which is currently skipped by the V2
mutation sweep because it trips a `debug_assert!` in `Bus::read16`. The fix is
either to broaden the assert exemption so it stops trapping legitimate
coresight-trace halfword traffic, or to delete the now-dead `0xE if
Self::is_coresight_trace(addr)` arms that motivated the test in the first
place. Symmetric across `read16` / `write16` (and, on inspection, `read32` /
`write32` — the same asymmetry exists at all three widths). No other
behavioural changes; no refactor of the bus or the wrapper.

**Key invariant the survey establishes:** the coresight_trace 0xE arms in
`Bus::read16` / `write16` / `read32` / `write32` are **dead from the
production CPU path**. Both `CortexM33::bus_read16/write16/read32/write32` and
`Emulator::mmio_read32/mmio_write32` short-circuit every region-0xE-non-boot-ram
address into `Ppb` before the bus is consulted. The bus arms are only
reachable from a direct `bus.read16(…)` call in tests. Byte-width is the
exception: `bus.read8/write8` have no PPB assert (and the wrappers route 0xE-
non-boot-ram bytes to a hard zero / drop without calling the bus), so the
coresight byte-arm is also strictly speaking unreachable from CPU code today.

## 3. Root cause

Commit `50fdf5e` (2026-04-16, "threading 0b.1 B") moved the PPB out of `Bus`
into per-core `CortexM33` ownership. To stop residual code paths from
reaching `Bus::read16/write16/read32/write32` for PPB addresses (which would
silently land on storage that no longer existed), the commit added the
`debug_assert!(addr >> 28 != 0xE || Self::is_boot_ram(addr), …)` guards. The
boot-RAM exemption preserved the legitimate `0xEFFF_F000..0xF000_0000`
arm. The coresight_trace exemption was missed — the `0xE if
Self::is_coresight_trace(addr)` arms (added in earlier work for an
`0xE004_1000..0xE004_2000` storage-only block) were left in place and the
assert sits structurally **before** them in the same function.

The later residue-coverage push (commit `00e82a8`, 2026-04-28, "tests: stage 3
— bus + peripherals + DMA coverage") added a halfword test that calls
`bus.read16` directly to drive the coresight half-word arm. That test panics
on the assert before reaching its target arm. The assert and the arm are
mutually inconsistent.

**The deeper observation:** because the wrappers and `Emulator::mmio_read32/
write32` route every region-0xE-non-boot-ram access to `Ppb` regardless of
whether it falls inside the coresight aperture, the coresight 0xE arms in
`Bus::read16/write16/read32/write32` are unreachable from any production
caller. They can only be reached by a direct `bus.read16(…)` in a unit test.
This means the test is exercising arms that never run in production. That is
a meaningful design observation independent of the assert fix.

## 4. Design — three options

### Option 1: extend the assert exemption to `is_coresight_trace`

```rust
debug_assert!(
    addr >> 28 != 0xE
        || Self::is_boot_ram(addr)
        || Self::is_coresight_trace(addr),
    "PPB address 0x{:08X} reached Bus::read16 — use CortexM33::bus_read16 wrapper",
    addr
);
```

Symmetric edit to `read16` (`:2123`), `write16` (`:2320`), `read32` (`:2770`),
and `write32` (`:2909`). Keeps the 0xE coresight match arms reachable; turns
the failing test green.

**Pros.** Minimal diff. Test as-written passes. Honours the apparent author
intent of the 0xE coresight arms (they were added deliberately).

**Cons.** Preserves dead-from-production code (the 0xE coresight arms in
`read16/write16/read32/write32`). Makes the assert message slightly
misleading: "PPB address" includes coresight_trace under that umbrella
already-debatable framing. The coresight 0xE arms still won't be reached by
any CPU-driven test, so the only callers that hit them are direct
`bus.read16(…)` test calls — same shape as a debug-only test path.

### Option 2: drop the assert entirely

The wrappers (`bus_read16/…`) have been the canonical entry path since 2026-
04-16. No production caller has tripped these asserts since they landed; the
sole tripper today is a unit test that *intentionally* drives the bus
directly. The safety net the asserts provide is now redundant — the same
invariant is enforced structurally at the wrapper level, not as a runtime
check on the bus.

**Pros.** Simpler. Aligns the four widths (`read8`/`write8` already lack the
assert). The 0xE coresight arms become legitimately reachable from any
caller, matching the natural reading of the match arm. Test passes.

**Cons.** Removes the early-warning that a future caller has bypassed the
wrapper and reached the bus for a PPB address. That caller would now silently
land on the unmapped-region default (`_ => self.atomics.set_bus_fault(…); 0`)
or the coresight aperture (if the address is inside it) — both of which are
behaviourally wrong from a PPB perspective but no longer panic in debug. The
wrapper is well-established, but "well-established" is a weaker guarantee
than a debug_assert.

### Option 3: change the test to call the wrapper

The test would create a `CortexM33`, call `core.bus_read16(addr, &mut bus)`,
and check the result. But the wrapper's region-0xE branch returns
`self.ppb.read32(addr & !3)` — it never reaches the bus's coresight arm at
all. So the test would not be testing the bus's coresight halfword arm; it
would be testing `Ppb::read32`, which is a different code path. This
doesn't preserve the test's stated intent.

**Verdict: rejected.** Option 3 changes what is being tested.

### Recommended: **Option 1**, with a concrete follow-up question

Extend the assert exemption. This is the smallest change, it preserves the
debug-only safety net for "future callers that bypass the wrapper for a real
PPB address", and it acknowledges the coresight arms as legitimate.

The dead-from-production observation (Option 2's hidden gain) is a separate
question — see §7. If the supervisor wants to lean on it, switch to Option 2
in this same change.

## 5. Concrete edit (Option 1)

Four sites, identical pattern:

```rust
// Bus::read16, line 2123–2127
debug_assert!(
    addr >> 28 != 0xE
        || Self::is_boot_ram(addr)
        || Self::is_coresight_trace(addr),
    "PPB address 0x{:08X} reached Bus::read16 — use CortexM33::bus_read16 wrapper",
    addr
);

// Bus::write16, line 2320–2324 — same pattern, message …Bus::write16…
// Bus::read32,  line 2770–2774 — same pattern, message …Bus::read32…
// Bus::write32, line 2909–2913 — same pattern, message …Bus::write32…
```

`read8` / `write8` are unaffected — they have no PPB assert (verified at
`:1426–1607` and `:1614–…`). The `0xD` DIV/INTERP guards immediately
following the read16/write16/read32/write32 PPB asserts are also unaffected.

No other 0xE arms exist in `Bus::read{8,16,32}` / `write{8,16,32}` (verified
via grep at survey).

**Add the symmetric write16 sibling.** Inside the same `mod
stage3_bus_residue` block, immediately after the existing read16 test, add:

```rust
#[test]
fn coresight_trace_halfword_write_dispatches_through_word_path() {
    let mut bus = Bus::new();
    // Pre-fill the word so we can confirm halfword RMW preserves the
    // unwritten half (matches the existing read16 test's address).
    bus.write32(0xE004_1100, 0xAAAA_5555, 0);
    // Halfword writes through the Bus::write16 0xE coresight arm.
    bus.write16(0xE004_1100, 0x1234, 0);
    bus.write16(0xE004_1102, 0x5678, 0);
    // Round-trip via byte reads (whose 0xE arm is and stays reachable).
    assert_eq!(bus.read8(0xE004_1100, 0), 0x34);
    assert_eq!(bus.read8(0xE004_1101, 0), 0x12);
    assert_eq!(bus.read8(0xE004_1102, 0), 0x78);
    assert_eq!(bus.read8(0xE004_1103, 0), 0x56);
}
```

This pins the write16 0xE coresight arm in the same way the existing test
pins read16. Naming follows the read-side test's `…dispatches_through_…`
convention. Same shape would apply for read32 / write32 if the supervisor
wants to extend coverage to all four widths in this commit; recommendation
is to add the read32/write32 pair only if the supervisor explicitly wants
the parallel coverage — they are not currently failing the V2 sweep.

**Existing PPB tests remain green.** The four PPB-address asserts still fire
for any region-0xE address that is *neither* boot_ram *nor* coresight_trace.
That is the entire `Ppb` aperture (`0xE000_xxxx`, `0xE000E…`, etc.). No
existing `bus.read16(0xE000_…)` or `bus.write16(0xE000_…)` call exists in
the test corpus (grep confirmed at survey: every `bus.{read,write}{16,32}`
on a 0xE address is either coresight or boot_ram). The PPB-direct tests use
`Ppb::read32` / `Ppb::write32` not `Bus::…`, e.g. `tests.rs:25774` ("`ppb.write32(0xE000_ED04, …)`").

## 7. Open questions / risks

**Q1. Should this commit also remove the dead 0xE coresight arms from
`Bus::read16` / `write16` / `read32` / `write32`?**
The wrappers and `Emulator::mmio_read32/write32` short-circuit every region-
0xE-non-boot-ram address into `Ppb` before the bus is consulted. The 0xE
coresight arms in those four bus methods are unreachable from any production
caller; they only fire for direct test calls. Possible cleanups:

- (a) Leave the arms in place (this HLD's recommendation). Tests can drive
  them; future refactors of the wrapper might want them.
- (b) Delete the arms and downgrade the tests to byte-only round-trip
  through `bus.{read,write}8` (which are reachable). This collapses to
  Option 2 of §4 plus arm removal.
- (c) Push the coresight aperture decision **into** the wrapper: route
  `is_coresight_trace` to `bus.read16/write16/read32/write32` rather than
  `ppb.read32`. This would make CPU coresight access actually land on the
  emulated coresight storage, which is the only behaviourally correct
  outcome if firmware ever touches the aperture.

**Recommendation:** out of scope for this fix (smallest-change principle).
File the decision as a separate tech-debt entry; this HLD's job is to unblock
the V2 mutation sweep.

**Q2. Is the assert exemption masking a real bug?**
No — the test that trips it is a unit test that intentionally drives `Bus`
directly to exercise a match arm. There is no production firmware path that
reaches `Bus::read16` for a coresight address. The assert was over-strict
relative to the match arms in the same function.

**Q3. What about read32 / write32 width parity?**
Both have the same assert and both have the same 0xE coresight arm. The
edit is symmetric across all four widths so the "tests can drive the
coresight arms" property holds at every width, not just the one currently
failing. No new tests for read32/write32 unless the supervisor wants them.

**Q4. Threaded runtime impact.**
None. The `Bus::read16/write16/read32/write32` body is shared between Serial
and Threaded paths; the wrappers are the only entry point in either. The fix
is a debug-build-only assertion change with no observable behaviour
difference at runtime.

**Q5. cargo-mutants impact.**
Section 305–337 of `tech_debt.md` records that V2 was passing `--skip
coresight_trace_halfword_read_dispatches_through_byte_path`. Once the test
is unskipped, V2 can re-run without that flag. Tech-debt entry update is in
the stage plan §9.

## 8. Out of scope

- Refactoring `Bus::read16/write16/read32/write32` (large, separate change).
- Changing the wrapper's behaviour (e.g. routing coresight through the bus —
  Q1 option (c)).
- Removing the 0xE coresight arms from the bus widths where they are dead
  (Q1 option (b)).
- Modifying `tech_debt.md` in the same commit. The tech-debt edit lands in
  Stage E so the fix-and-update arrive as separate, reviewable changes; this
  matches the project's practice of keeping tech-debt grooming out of
  source-change commits.
- The companion `bfc_full_width_clears_word` failure (entry #1 of the same
  tech-debt section). That is a real production bug (`1u32 << 32`); separate
  HLD.
- `read8` / `write8`: no assert, no change.

## 11. Suggested commit message

```
mdrp2350: exempt coresight_trace from PPB-routing assert in bus 16/32-bit access

Bus::{read,write}{16,32} guard a debug_assert! that PPB addresses
should never reach the bus directly — they must route through the
CortexM33::bus_* wrappers. The guard exempted boot_ram (0xEFFF_F000..)
but not the coresight_trace aperture at 0xE004_1000..0xE004_2000,
even though the same functions contain a legitimate `0xE if
Self::is_coresight_trace(addr)` match arm.

Extend the assert exemption to `Self::is_coresight_trace(addr)` at
all four sites (Bus::read16/write16/read32/write32). Re-enable
`coresight_trace_halfword_read_dispatches_through_byte_path` which
was skipped by the V2 mutation sweep, and add the matching
`coresight_trace_halfword_write_dispatches_through_word_path`
sibling.

Closes tech_debt.md "Residue-test failures discovered by V2
mutation sweep" item #2. Bumps mdrp2350 patch.
```
