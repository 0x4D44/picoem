# HLD — Open Source Release

**Date:** 2026-04-26
**Version:** V1
**Scope:** Pre-publication audit and prep across the whole workspace
**Status:** Draft — pending Arthur review

## 1. Motivation

We want to publish `mdpicoem` (this repo) as a public open-source project on
GitHub. The codebase is already dual-licensed MIT OR Apache-2.0 with a NOTICE
covering vendored bootroms, and the README is publishable as-is. The work that
remains is an audit-and-prune pass: confirming third-party licensing
obligations, sanitising 360-odd dev journals/HLDs, and adding the standard OSS
hygiene files.

Goal of this document: enumerate the work concretely so we can review
together, flag the two or three decisions that need Arthur's input, and avoid
discovering a problem after the repo is already public.

## 2. Goals

1. **Publish a self-contained, legally clean public repo** that a third party
   can clone, build, and reproduce the differential-fuzz / silicon-oracle
   results from.
2. **Preserve the project's history and HLDs** as part of what gets published —
   they document how the emulator was built and are part of the project's
   value, not a liability to strip out.
3. **No surprises post-publication** — every redistributed third-party binary
   has correct attribution, every doc has been read at least once for personal
   or sensitive content.

## 3. Non-goals

- **No CI on GitHub.** Decided. Tests run locally.
- Not adding marketing content (logo, website, demo videos). This is a code
  drop, not a launch.
- Not changing the workspace layout, build, or test topology.
- Not publishing app crates (`mdrp2350app` / `mdrp2040app`) or the harness
  crate to crates.io in V1. They get name-reservation placeholders only;
  real publication waits until we decide whether `cargo install` is part of
  the user story (§13).

## 5. PicoGUS firmware (item 1) — flip to vendored

**Today.** `third_party/picogus/.gitignore` excludes `*.bin`, `*.uf2`, `*.exe`,
`*.zip`, `UPSTREAM_README.md`, `upstream/`. The demo script (`scripts/picogus_demo.sh
--prepare`) fetches the upstream zip, verifies SHA256 against `VERSION`, and
extracts. Local tree currently contains the unpacked artefacts as untracked
files.

**Arthur's choice:** option (a) — vendor the binaries to make reproduction
trivial.

**Upstream license** (verified): PicoGUS `sw/` and `pgusinit/` collection is
GPL-2.0-or-later; some files dual-licensed BSD/MIT. Hardware (`hw/`) is CERN
OHL v2. We only redistribute software artefacts.

**Plan:**

1. Remove `third_party/picogus/*.{bin,uf2,exe,zip}` and `UPSTREAM_README.md`
   from `.gitignore`.
2. Commit:
   - `picogus.uf2`, `pg-ne2k.uf2`, `pgusinit.exe` (as published — stock
     upstream binaries).
   - `picogus-v4.0.0.bin` (UF2→bin conversion of `picogus.uf2`; functionally
     stock).
   - `picogus-v4.0.0.zip` (the upstream release archive).
   - `UPSTREAM_README.md` (extracted from zip).
   - **`picogus-v4.0.0-patched.bin`** — only 3 bytes differ from stock. We
     need to surface what those bytes are (presumably a hot-fix or test-mode
     hook) and either commit a `.patch` file alongside, or document the
     three-byte delta inline in the picogus README. This is a hard GPLv2
     requirement: the binary's "corresponding source" must be available.
3. Add a copy of the upstream `LICENSE` file as
   `third_party/picogus/LICENSE-PICOGUS-GPL-2.0.txt`.
4. Update `NOTICE` with a PicoGUS section listing the upstream URL, license,
   and pointer to the local LICENSE copy.
5. Update `third_party/picogus/README.md`: rewrite the "**not redistributed**"
   wording to "redistributed under GPL-2.0-or-later", explain the 3-byte
   patch and where to find the patch source, keep the demo-script staging
   path as the still-valid alternative for upgrades.
6. **Don't vendor `upstream/`** (the full source tree clone). It stays
   `.gitignored`. The pinned `VERSION` + upstream URL gives reproducibility;
   redistributing 4k+ source files has no practical benefit and makes the
   repo unwieldy. The upstream URL in NOTICE satisfies GPLv2's source-pointer
   requirement.

**The 3-byte patch — identified.** From `wrk_journals/2026.04.16 - JRN -
PicoGUS End-to-End Bring-up.md` (Phase E) and confirmed in
`wrk_journals/2026.04.24 - JRN - Single-voice dump and FM trace.md`
(Session 8):

- **Location:** flash offset `0x0b199` in `picogus-v4.0.0.bin` (RAM address
  `0x20012FA4` after the firmware's `.data` copy).
- **Original bytes:** `beq 0x1000b19c; b 0x1000b90c` — the conditional return
  path of `test_psram`.
- **Patched bytes:** `movs r0, #0; bx lr` — immediately returns 0 from
  `test_psram`.
- **Why:** the stock `test_psram` self-test is *correct* but performs a
  full-PSRAM read/write sweep that takes ~1 hour on our emulator (it runs in
  milliseconds on real silicon). The patch bypasses the test so the firmware
  proceeds past PSRAM init in seconds. Original implementation was a runtime
  SRAM poke applied by the harness after `.data` copy; later materialised as
  a permanent patched binary for convenience.
- **Affects:** `picogus_diff_rp2040` and `picogus_probe_pc` harnesses only.
- **Functional impact:** none — `test_psram` is a self-diagnostic, not part
  of the audio path. Firmware behaviour with the patch is identical to
  firmware running on hardware that passed the self-test.

**Plan to ship cleanly:** alongside `picogus-v4.0.0-patched.bin`, commit a
`picogus-v4.0.0-test_psram-bypass.patch` text file containing:

1. The 3-byte hex diff at offset 0x0b199.
2. A short rationale block (the four bullets above, condensed).
3. The original Thumb disassembly + the patched Thumb disassembly side-by-side.

This satisfies GPLv2's "corresponding source" obligation for the
modification — it's literally a 3-byte hand patch, fully documented.

## 7. Monkey Island ADLIB fixture (item 3)

   (FM-replay differential testing), and noting that no game data is included.
2. Mention in NOTICE under "Test fixtures" that the trace is functional
   capture, not redistributed game content.

## 13. crates.io — defer publication, claim placeholder names now

### 13.1 Why publish to crates.io eventually

- Discoverability. `cargo search rp2350` finds us; users can `cargo add mdrp2350`.
- Forces a tidy public API on the library crates.
- Implicit version pinning for downstream users.
- Signals "this is a real project" rather than just a code drop.

### 13.2 Why not yet

- API stability commitment. Once `0.1.0` is on crates.io, anyone depending
  on it expects semver — surprise breaks earn issues.
- Dependency-graph ordering. Publishing `mdrp2350` requires
  `mdpicoem-common` to be on crates.io first; publishing `mdrp2040` also
  requires `mdpicoem-devices`. We'd be committing the whole library tier
  to public versioning, not just the hero crates.
- Versioning discipline. We currently bump `Cargo.toml` casually within
  the workspace; crates.io publication requires real semver and
  breaking-change tagging.
- README per crate. Each published crate needs its own README that
  renders well on crates.io — not a 5-minute job across the namespace.

### 13.3 Crate inventory

The workspace has nine top-level crates. Tiered by squat-risk:

**Tier 1 — claim definitely.** Library crates that would be published if
crates.io ever happens. Dependency ordering means we can't publish a
hero crate without these.

| Crate | Role |
|---|---|
| `mdrp2350` | RP2350/RP2354 emulator library — the hero crate |
| `mdrp2040` | RP2040 emulator library — the hero crate |
| `mdpicoem-common` | Shared primitives — required prereq for both heroes |
| `mdpicoem-devices` | Off-chip device models — required prereq for `mdrp2040` |

**Tier 2 — claim if we want `cargo install` to work.** Niche enough that
the squat risk is low, but reserving them is cheap and keeps the install
story neat.

| Crate | Role |
|---|---|
| `mdrp2350app` | TUI app. `cargo install mdrp2350app` is a clean install path. |
| `mdrp2040app` | Same for RP2040. |

**Tier 3 — namespace consistency.** Holding the `mdpicoem-*` prefix
intact prevents anyone publishing a confusingly-similar crate.

| Crate | Notes |
|---|---|
| `mdpicoem-debug` | Currently a stub. If the GDB stub gets built out, we'd want this. |
| `mdpicoem-harness` | Internal test binaries. Minimal real squat risk; held for namespace coherence. |
| `mdpicoem` (no suffix) | Project identity name. Prevents anyone publishing `mdpicoem` and confusing search results. No façade crate yet. |

**Don't claim.** `epio-sys` — the underlying `epio` is a third-party
project (piersfinlayson/epio). The `-sys` convention belongs to upstream;
squatting it would be rude. Either coordinate with upstream or leave it
vendored.

### 13.4 Decision: publish for real in V1

After discussion: the codebase is mature enough that the public surface
(`Emulator`, `EmulatorBuilder`, `ExecutionModel`, `load_flash`/`run`/`step`)
has been stable for weeks; recent churn is internal. Deferring crates.io
behind a "let the public repo settle" wait was solving a problem (API
churn from outside usage) that doesn't start until we publish anyway.
There's no real benefit to making `cargo add mdrp2350` not work on day
one.

**Plan.** Publish the four library crates as real `0.1.0` releases.
Reserve the four namespace-coherence crates as `0.0.0` placeholders.
Don't claim Tier 2 (apps) — defer that decision.

| Crate | Action | Version |

| `mdpicoem-common` | Real publication | `0.1.0` |
| `mdpicoem-devices` | Real publication | `0.1.0` |
| `mdrp2350` | Real publication | `0.1.0` |

### 13.5 Prerequisites for real publication

The four `0.1.0` releases have non-trivial prep — these are tasks, not
blockers, but they need to land before `cargo publish` runs:

1. **Reset all four library-crate versions to `0.1.0`.** Today's versions
   are `mdrp2350 2.4.1`, `mdrp2040 0.19.0`, `mdpicoem-common 0.14.0`,
   `mdpicoem-devices 0.7.1` — internal bookkeeping bumps from the
   workspace's pre-public history. Publishing `mdrp2350 2.4.1` as the
   first public release would imply prior 2.x.0, 1.x.0, 0.x.0 history
   that doesn't exist. **Reset all four to `0.1.0`** for V1 publication;
   the pre-public version numbers remain in git history for anyone who
   cares to look.
2. **Per-crate READMEs.** crates.io renders each crate's README on its
   landing page. Today only the workspace has one. Each library crate
   needs a quickstart, a "this is part of the mdpicoem workspace" note,
   and a link back to the GitHub repo. Roughly 2 hours total.
3. **Per-crate Cargo.toml metadata — clean-slate for all four crates.**
   Verified during §16 critical review: `description`, `repository`,
   `homepage`, `documentation`, `readme`, `keywords`, `categories`,
   `exclude`, `[package.metadata.docs.rs]` are *all missing* across the
   four library crates today. The `license` and `rust-version` fields
   are correctly inherited from `[workspace.package]` (license =
   `"MIT OR Apache-2.0"`, MSRV = `1.88`). Remaining work is from-zero,
   not "tweak existing fields." Each library crate needs:
   `description` (required by crates.io), `repository =
   "https://github.com/0x4D44/mdpicoem"`, `homepage`, `documentation`
   (docs.rs URL), `readme = "README.md"`, `keywords` (≤ 5, e.g.
   `["emulator", "rp2350", "rp2040", "cortex-m", "embedded"]`),
   `categories` (e.g. `["emulators", "embedded"]`).
4. **API surface audit.** What's `pub` today that's actually internal?
   What's currently `pub(crate)` that consumers will need? Particular
   attention to `mdpicoem-common` — it grew organically as a "shared
   bits" crate (`Memory`, `ClockTree`, PIO primitives, threading
   primitives, `Pacer`) and isn't deliberately designed as a public
   API. May need a `prelude` module or some `pub(crate)` tightening.
5. **Switch workspace deps from `path = "..."` to
   `version = "0.1", path = "..."`.** Standard pattern: `cargo publish`
   resolves `version` against crates.io while local dev still uses
   `path`. Affects `mdrp2350/Cargo.toml`, `mdrp2040/Cargo.toml`,
   `mdpicoem-devices/Cargo.toml`, and the apps/harness if they depend
   on libraries we're publishing.
6. **Cross-platform build verification.** `mdrp2350` and `mdrp2040`
   gate `Threaded` / `Pacer` behind `cfg(target_arch = "x86_64",
   target_os = "windows")`. They *should* still build on Linux x86_64
   (which is what docs.rs uses) with those features unavailable.
   Confirm with `cargo check --target x86_64-unknown-linux-gnu` for
   each library crate before publishing — if a docs.rs build fails,
   the crate's first impression is "no documentation rendered."
7. **`exclude` directives in Cargo.toml.** Don't ship test fixtures,
   ROM binaries, or HLDs through `cargo publish`. Add `exclude = [
   "tests/", "fixtures/", ... ]` per crate so the published tarball
   stays small. crates.io has a 10 MB tarball limit.
8. **Decide on docs.rs build features.** docs.rs builds with
   `--all-features` by default; if `threading` or `testing` features
   break the build on Linux, we need a `[package.metadata.docs.rs]`
   section pinning a feature subset.

**Verified non-blocker:** the workspace-root `[patch.crates-io]
probe-rs = { path = "third_party/probe-rs-0.31.0-mdrp-patched" }` has
no effect on published crates, since neither `mdrp2350` nor `mdrp2040`
(the libraries) actually depend on probe-rs — only the unpublished
harness crate does. Confirmed by reading `[dependencies]` in each
library Cargo.toml during the §16 critical review.

### 13.6 Publish sequence

Once prereqs land, publish in dependency order:

```
mdpicoem-common 0.1.0    (no internal deps)
       ↓
mdpicoem-devices 0.1.0   (depends on mdpicoem-common)
       ↓
mdrp2350 0.1.0           (depends on mdpicoem-common)
```

## 18. Risks

- **Doc audit miss.** 360 Markdown files is a lot; targeted grep can miss
  free-form prose embarrassments. Mitigation: random-sample spot-read; once
  public, anything missed can be fixed in a follow-up commit.
- **Hardware-only oracles look "broken" to outside observers.** A casual
  visitor sees `silicon_*` binaries that "fail" or skip on their machine.
  Mitigation: README is already explicit about this; reinforce in
  CONTRIBUTING.md.
- **Surprise Cargo.lock churn after publication.** Public CI doesn't apply
  (no CI), but anyone running `cargo update` will see drift. Not really a
  risk, just expected.
- **Semver discipline burden post-publication.** Once `0.1.0` is on
  crates.io, every breaking API change forces a `0.2.0` and release-notes
  call-out. We've never had to think about this before — the workspace
  has been free to refactor `Bus` methods or shuffle the builder casually.
  Mitigation: `0.x` semver explicitly allows breakage; the obligation is
  to bump the minor version and document, not to *not* break. Still, this
  is a new ongoing cost that didn't exist before.
- **docs.rs build failure on first publish.** If our cross-platform check
  misses a Linux-only build issue, the crate's first impression on
  crates.io is "documentation: failed to build." Mitigation: §13.5
  prereq 6 (`cargo check --target x86_64-unknown-linux-gnu`) before
  every `cargo publish`. Recoverable post-hoc by publishing a patch
  release with a fix or a `[package.metadata.docs.rs]` feature pin.
- **First user file an issue we can't reproduce.** Without CI, we don't
  catch regressions outside our own dev hosts. First external bug report
  on Linux/macOS could be a real puzzle. Mitigation: explicit "Windows
  x86_64 is the developer platform; other targets best-effort" note in
  README + CONTRIBUTING.
