# Threaded Dual-Core Emulation

Version: 3.0.0
Date: 2026-04-14

## Problem

Dual-core paced throughput on a 3 GHz host: **73.8 MHz per core** (49% of
150 MHz target). Single-core is 143.8 MHz (96%). The 2x gap comes from
sequentially executing both cores in one host thread.

## Target (honest, modeled)

**Realistic ceiling: ~115–125 MHz per emulated core** (77–83% of 150 MHz).
Model:

- Single-core baseline: 143 MHz (21 host cycles/emu cycle)
- Each worker runs one emulated core on its own host core
- Per-quantum overheads: SpinBarrier crossing ×2 (~200ns total), coordinator
  work (~100ns), atomic-load overhead on memory fetches (~10% vs plain)
- Cache coherence traffic from cross-core writes: 5–15% depending on workload
- Net: ~15–25% hit on per-core throughput vs isolated single-core
- Expected: 107–121 MHz per core ≈ **2x improvement over 73.8 MHz**

Hitting 150 MHz per core requires additional interpreter work (decode cache
or targeted JIT). That is a **follow-up**, not this HLD.

This HLD is validated by Phase 0a workload study before substantial
engineering begins. If the workload profile doesn't support threading, we
shelve and do decode cache instead.

## Non-goals

- No per-cycle bus contention in threaded mode (documented trade-off).
- No hybrid mode — pure single-threaded OR pure threaded per invocation.
- No dynamic thread count.
- No env vars, no feature flags.
- No reverse conversion `ThreadedEmulator → Emulator` — one-way only.

## Phase 0: Validation + prerequisite refactors

### 0a. Workload study (~1 week)

Add instrumentation to single-threaded paced_bench to count per-core:
cycles in decode/execute, cycles in WFI, cycles stalled for contention,
peripheral access fraction. Run against:

- The bootrom (real workload, exists today)
- A dual-core synthetic: bootrom launches core 1 via SIO FIFO, both
  cores execute a hand-written Thumb loop with realistic memory access
  patterns (loads, stores, ADDS, conditional branches, SIO sync)

**No OneROM firmware exists yet.** The bootrom + synthetic is our
best available proxy. Acknowledge the chicken-and-egg: we can't measure
OneROM's behavior before we build OneROM, and OneROM can't be built at
real-time speed without this work. We proceed based on bootrom data.

**Decision gate:** if core 1 active ratio ≥ 20% on representative
workloads, proceed to Phase 0b. Otherwise shelve, do decode cache.

### 0b. Prerequisite refactors (~2 weeks)

These are correct and useful for single-threaded emulator independently.
Land them even if Phase 0a says "no" — they remove design debt.

**Split by threading-dependency:**

**Standalone value (ship regardless of threading decision):**

1. **Move PPB to `CortexM33`.** PPB (NVIC, SCB, MPU, SAU, SysTick) is
   per-core in hardware. Currently at `Bus::ppb: [Ppb; 2]` accessed via
   `Bus::active_core()` (a shared mutable flag). Move `Ppb` struct onto
   `CortexM33`. `Bus::active_core()` deleted. Every bus method that needed
   core identity now takes `CoreId` as a parameter.

2. **Implement LDREX/STREX properly.** Per-core `exclusive_address:
   Option<u32>` on `CortexM33`. LDREX sets it; STREX checks it and clears
   (regardless of success). Any write to that address from either core
   invalidates it. Without this, software spinlocks break. Useful for
   single-threaded correctness too — current stubs are a bug.

**Threading-only (gated on Phase 0a saying "yes"):**

3. **Atomize cross-core `CortexM33` fields.** `halted`, `wfe_waiting`,
   `event_flag` become `AtomicBool`. These are read/written across cores
   (SEV, WFE, core-1-launch). Only needed under threading; in lockstep
   mode, they stay as plain `bool`.

4. **CortexM33 field ownership table.** Audit every field and annotate:

   | Field | Per-core/Shared | Access | Threading action |
   |---|---|---|---|
   | `regs` | Per-core | Only owning core | Move with thread. |
   | `stall_cycles` | Per-core | Only owning core | Move with thread. |
   | `halted` | Per-core, cross-readable | Core reads+writes own; SEV/launch reads peer | `AtomicBool` |
   | `wfe_waiting` | Per-core, cross-readable | Core sets/clears own; SEV reads peer | `AtomicBool` |
   | `event_flag` | Per-core, cross-writable | Core clears own; SEV writes peer | `AtomicBool` |
   | `pending_fault` | Per-core | Only owning core | Move. |
   | `current_instr_addr` | Per-core | Only owning core | Move. |
   | `it_state` | Per-core | Only owning core | Move. |
   | `exclusive_address` | Per-core, cross-snoop-read | Core sets on LDREX; peer reads on write | `AtomicU64` (tag + valid bit) |
   | `ppb` | Per-core (after Phase 0b.1) | Only owning core | Move. |
   | `dcp_data` | Per-core (verified from datasheet) | Only owning core | Move. |
   | `rcp_salt` | Per-core (verified from datasheet) | Only owning core | Move. |
   | `secure` | Per-core | Only owning core | Move. |
   | `core_id` | Per-core | Only owning core | Move. |

Build this table during Phase 0b.1 PPB refactor; it tells the Phase 1
implementation exactly what to do.

## Phase 1: Threaded execution path

### API: two types, one-way conversion

```rust
/// Single-threaded cycle-accurate. Reference for validation.
pub struct Emulator { ... }

impl Emulator {
    pub fn run(&mut self, cycles: u64) -> u64 { ... }

    /// Consume self, produce a threaded emulator with the same state.
    /// Terminal: no way back. Rationale — the state representations
    /// differ fundamentally (atomic vs plain), and no real use case
    /// exists for mid-run conversion.
    pub fn into_threaded(self) -> ThreadedEmulator { ... }
}

pub struct ThreadedEmulator { ... }

impl ThreadedEmulator {
    /// Block until `stop` signals OR duration elapses OR
    /// both cores WFI indefinitely (no wake source).
    /// Returns ExitReason so caller can distinguish.
    pub fn run(
        &mut self,
        pacer: &mut Pacer,
        duration: Duration,
        stop: Arc<StopSignal>,
    ) -> ExitReason;
}

pub enum ExitReason {
    Duration,          // duration elapsed
    Stopped,           // caller signaled stop
    BothWfi,           // both cores WFI with no wake source
    Panic(String),     // a worker panicked (captured)
}
```

### StopSignal

```rust
pub struct StopSignal(AtomicBool);
impl StopSignal {
    pub fn new() -> Arc<Self> { ... }
    pub fn stop(&self) { self.0.store(true, Release); }
    pub fn is_stopped(&self) -> bool { self.0.load(Acquire) }
}
```

Workers check `stop.is_stopped()` at each barrier. Used for:
- User-initiated cancel (Ctrl-C handler)
- Breakpoint or fault escalation
- **Worker panic escalation** (see below)

### Worker panic handling

Naive: if worker panics, barrier deadlocks. Solution: `catch_unwind`
around the worker loop body, on panic set the `StopSignal` and poison
the barrier, propagate panic payload to the caller via `ExitReason::Panic`.

`SpinBarrier` gets a `poison()` method that sets a sentinel; `wait()`
returns `BarrierResult::Poisoned` immediately if set. `ThreadedEmulator::run`
detects poison and returns `ExitReason::Panic(payload)`.

### Thread topology: 2 workers, coordinator folded into worker 0

```
  ┌─────────────────────────────┐   ┌─────────────────────────────┐
  │ Worker 0 (pinned, also       │   │ Worker 1 (pinned)           │
  │ coordinator role)            │   │                             │
  │                              │   │                             │
  │ for 0..Q:                    │   │ for 0..Q:                   │
  │   core0.step(shared, ...)    │   │   core1.step(shared, ...)   │
  │ barrier.wait()                │   │ barrier.wait()              │
  │                              │   │                             │
  │ pacer.spin_wait()            │   │ (parked on 2nd barrier)     │
  │ dispatch cross-core events:  │   │                             │
  │   - SEV wakes                │   │                             │
  │   - timer ticks              │   │                             │
  │   - WFI wake check           │   │                             │
  │   - check stop_signal        │   │                             │
  │ barrier.wait()                │   │ barrier.wait()              │
  └─────────────────────────────┘   └─────────────────────────────┘
```

Two barriers per quantum. First releases when both workers finish Q
cycles (worker 0 then does pacer + events). Second releases when
worker 0 has done its coordinator work.

### SpinBarrier

```rust
pub struct SpinBarrier {
    generation: AtomicU32,
    count:      AtomicU32,
    poisoned:   AtomicBool,
}

pub enum BarrierResult { Released, Poisoned }

impl SpinBarrier {
    pub fn wait(&self) -> BarrierResult {
        if self.poisoned.load(Acquire) {
            return BarrierResult::Poisoned;
        }
        let my_gen = self.generation.load(Acquire);
        let n = self.count.fetch_add(1, AcqRel) + 1;
        if n == 2 {
            self.count.store(0, Relaxed);
            self.generation.store(my_gen.wrapping_add(1), Release);
        } else {
            loop {
                if self.poisoned.load(Acquire) { return BarrierResult::Poisoned; }
                if self.generation.load(Acquire) != my_gen { break; }
                std::hint::spin_loop();
            }
        }
        BarrierResult::Released
    }

    pub fn poison(&self) {
        self.poisoned.store(true, Release);
    }
}
```

Target crossing cost: <100 ns when both threads are ready. Two barriers
per quantum: ~200ns overhead at Q=150 = 20% (the main reason the target
is 115–125 MHz, not 140).

### Shared memory: AtomicU32 backing

```rust
pub struct SharedMemory {
    sram:      Box<[AtomicU32]>,       // 130K × 4B = 520 KB
    rom:       Box<[u8]>,              // read-only, no atomics
    xip:       Box<[AtomicU32]>,       // if writable via QMI
    exclusive: [AtomicU64; 2],         // per-core monitor: tag + valid
}
```

**Accesses:**
- `read32`: single atomic load (1 op)
- `read16`/`read8`: atomic load + bit extract (1 op + shift)
- `write32`: single atomic store (1 op) + snoop_exclusive
- `write16`/`write8`: CAS loop with masked RMW + snoop_exclusive

**Exclusive monitor snoop (cross-core aware):**

```rust
fn snoop_exclusive(&self, addr: u32, writer: CoreId) {
    // Invalidate the OTHER core's monitor if it was watching this range.
    // Release ordering publishes the data write before the monitor clear.
    // Peer re-reading via Acquire sees fresh data.
    let other = writer.other();
    let tag = addr & !3;
    loop {
        let cur = self.exclusive[other.0 as usize].load(Acquire);
        if cur == 0 { return; }
        if ((cur as u32) & 0xFFFF_FFFC) != tag { return; }
        match self.exclusive[other.0 as usize].compare_exchange(
            cur, 0, Release, Relaxed
        ) {
            Ok(_) => return,
            Err(_) => continue,
        }
    }
}
```

**The orderings:** memory accesses use Relaxed (matches Armv8-M weak
model). Exclusive monitor uses Acquire loads + Release stores (so the
write that invalidates the peer's monitor happens-after the data
write it corresponds to). DMB/DSB translate to SeqCst fences (below).

### Memory ordering: DMB/DSB → `fence(SeqCst)`

Critical fix from V2: AcqRel is insufficient. DMB on Armv8-M provides
store-load ordering (the strongest memory barrier — all memory accesses
before the DMB complete before any memory access after). AcqRel gives
only store-store and load-load ordering; on x86, `fence(AcqRel)` emits
nothing while `fence(SeqCst)` emits `mfence`. For Dekker-style mutual
exclusion idioms to work, SeqCst is required.

```rust
// In threaded execute path:
match instr {
    DMB | DSB => std::sync::atomic::fence(Ordering::SeqCst),
    ISB => {
        std::sync::atomic::fence(Ordering::SeqCst);
        // If we add a decode cache later, flush it here.
    }
}
```

Single-threaded mode: still no-ops (no other thread to synchronize with).

### WFI / halted semantics (explicit)

When a core executes WFI, it must stop executing until an interrupt
becomes pending. In threaded mode:

```
core.step() on WFI instruction:
  set core.halted = true (Release)
  return (this worker skips straight to barrier)

In worker loop:
  at start of each quantum's for-loop, check halted:
    if halted: skip inner loop (arrive at barrier immediately)

In worker 0's coordinator phase:
  for each core:
    if halted AND an IRQ is pending (check that core's NVIC):
      clear halted (Release)
      (next quantum resumes normally)
  if BOTH cores halted AND no external wake source in < duration:
    set ExitReason::BothWfi
    stop_signal.stop()
    poison barrier, exit
```

**Detecting "no external wake source":** safe over-approximation. If
both cores are halted AND no peripheral has an active timer that will
fire before `duration` elapses, we exit. If we're wrong, the caller
restarts. For real-time pacing, erring on the side of early exit is
correct.

### SIO: threaded-only redesign

Keep existing single-threaded `Sio` (VecDeque, plain u32 regs). Build
new `ThreadedSio` for threaded mode only:

```rust
pub struct ThreadedSio {
    fifo_to_core0: rtrb::Producer<u32>,  // producer: core 1, consumer: core 0
    fifo_to_core1: rtrb::Producer<u32>,  // producer: core 0, consumer: core 1
    // (consumers held by respective workers)
    spinlocks: [AtomicU32; 32],
    fifo_st_0: AtomicU32,                // sticky WOF/ROE per core
    fifo_st_1: AtomicU32,
    // ... rest of SIO state
}
```

**SPSC implementation: use `rtrb` crate.** ~500 LOC, zero transitive
deps, Loom-tested. Rationale: V2 proposed hand-roll to avoid supply
chain surface. Senior Rust review pushed back — correctness on
strict SPSC with bounded capacity + memory ordering is genuinely
subtle, `rtrb` has already solved it. Auditing `rtrb` once is
cheaper than auditing our hand-roll continuously. Accept the dep.

**Sticky WOF/ROE flags**: stay on the `ThreadedSio` struct as
`AtomicU32`s. `rtrb`'s push/pop return success/failure; we translate
full/empty into the sticky flags per hardware semantics.

### Peripherals: sharded mutexes, defined lock order

```rust
pub struct Peripherals {
    apb:     Mutex<ApbPeripherals>,
    ahb:     Mutex<AhbPeripherals>,
    clocks:  Mutex<ClocksPll>,
    qmi:     Mutex<QmiRegs>,
    resets:  Mutex<ResetsState>,
}
```

**Lock order (documented, enforced by `debug_assert`):**
`clocks` < `qmi` < `resets` < `apb` < `ahb`.

Matches boot sequence (clocks → flash → peripherals out of reset).
Any operation needing multiple locks acquires in this order. Prevents
deadlock by convention + debug assertion.

If profiling shows a single mutex is hot, split further (per
peripheral instance rather than per block). Defer until measured.

## Implementation phases + schedule

Revised from V2 based on review feedback. Each phase is a reviewable
commit that leaves the codebase in a working state.

- **Phase 0a** — Workload instrumentation + study (1 wk)
- **Phase 0b.1** — PPB move to CortexM33 + `active_core()` removal (1 wk)
- **Phase 0b.2** — LDREX/STREX exclusive monitor implementation (1 wk)
- **Phase 0b.3** — CortexM33 atomize cross-core fields (2 days)
- **Phase 1** — `SharedMemory` with AtomicU32 + exclusive snoop (1 wk)
- **Phase 2** — `ThreadedSio` with `rtrb` + `SpinBarrier` + Loom tests (1 wk)
- **Phase 3** — `ThreadedEmulator` mvp: spawn, barrier, fixed cycles,
  integration test (1 wk)
- **Phase 4** — Pacer + StopSignal + ExitReason + panic handling (1 wk)
- **Phase 5** — Benchmark, profile, tune, WFI deadlock handling (1 wk)

**Total: 7–9 weeks.** V2's 5-week estimate was optimistic.

Each phase bails cleanly if an insurmountable issue appears; each
adds independent value except Phase 3 which needs Phases 1+2 landed.

## Validation

1. **Existing single-threaded tests keep passing.** Additive change.

2. **Loom tests for synchronization primitives.** `SpinBarrier`,
   exclusive monitor snoop. `rtrb` comes with its own.

3. **Dual-run differential test (the primary oracle).** Run same
   firmware under `Emulator` and `ThreadedEmulator`. Assert observable
   state matches at every SIO sync point (FIFO state, spinlock state,
   memory locations firmware synchronized with DMB). Cycle counts
   will differ; that's by design.

4. **Thread Sanitizer in CI.** Run integration tests under TSan on
   Linux CI (via WSL2 locally, GitHub Actions remote). Catches race
   conditions the Rust type system missed.

5. **QEMU differential (extended to threaded mode).** The existing
   `qemu_diff` harness drives instruction-level correctness. Extend
   to dual-core test programs; verify results match in both modes.

6. **Manual benchmark.** `paced_bench --threaded --dual-core` must
   show ≥110 MHz per core (≥73% of target). ≥120 MHz per core is the
   aspiration. Below 110: investigate before declaring success.

## What this does NOT do

- No JIT or decode cache (follow-ups; bigger multiplicative wins).
- No cycle-accurate dual-core (single-threaded retains that).
- No support for the Hazard3 RISC-V cores. But the `CoreId`
  abstraction and per-core state isolation make future addition
  structurally possible.

## Risks

1. **Phase 0a says "no".** Bootrom + synthetic workload data might
   show core 1 mostly idle. If so, we shelve. Accept.

2. **115–125 MHz per core might not be achievable.** Could land at
   ~100 MHz per core. Still 35% improvement over 73.8, worth doing,
   but doesn't close the gap to real-time. Commit to decode cache
   as the follow-up.

3. **Cache coherence traffic worse than modeled.** If real workloads
   cross-write to shared structures heavily, MESI traffic could eat
   the gain. Phase 0a should detect cross-core write patterns.

4. **`rtrb` crate audit.** Single dependency, reviewed once during
   Phase 2; vendor it if we need to patch or understand deeply.

5. **Loom coverage gap.** Loom tests primitives, not the whole
   pipeline. Dual-run differential + TSan cover the gap.

## Open questions tracked, not blocking

- **Hazard3 RISC-V support**: out of scope for this HLD.
- **Exact Loom test list**: defined during Phase 2.
- **TSan CI integration**: add as part of Phase 3.
