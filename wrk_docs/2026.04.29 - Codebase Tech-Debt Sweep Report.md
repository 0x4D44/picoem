## 2. Findings by category

### 2.1 Real bugs (high confidence, fixable)

**B1. `Memory::load_rom` panics on >16 KB ROM into RP2040** *[verified, devil's-advocate confirmed]*

- **Where:** `crates/mdpicoem-common/src/memory.rs:59-62`
- **What:** `load_rom` clamps to a workspace-common `ROM_SIZE = 32 KB` constant (the RP2350 size) instead of `self.rom.len()`. RP2040 constructs `Memory` with `rom_size = 16 KB`. Any caller passing >16 KB into `Bus::load_bootrom` (`crates/mdrp2040/src/bus/mod.rs:736-739`) triggers a slice-bounds panic.
- **Why it survives review:** The sister method `load_flash` at `memory.rs:157-167` already does this correctly (`data.len().min(self.xip.len())`). This is an asymmetric oversight — whoever fixed `load_flash` didn't backport.
- **Caller exposure today:** Zero — the only in-tree consumer is the 16 KB `gen_blinky.py` bootrom. But the API takes `&[u8]` with no documented size limit; a future test or larger bootrom trips it.
- **Fix:** One line — replace `ROM_SIZE` with `self.rom.len()`. Symmetric with `load_flash`.

### 2.2 Latent footguns (high severity, no current trigger)

**B2. `step_quantum=0` produces silent infinite loop in release** *[verified]*

- **Where:** `crates/mdrp2350/src/lib.rs:1501-1505`, `crates/mdrp2040/src/lib.rs:1379-1381`
- **What:** Public builder method `step_quantum(n: u32)` uses `debug_assert!(n > 0, ...)` for input validation. `debug_assert!` is elided in `--release`. With `n = 0` the Serial path enters `while clock.cycles < target` where `target == clock.cycles`, then `clock.advance(0)` no-ops — true infinite loop. Threaded path is safe (has `step_q.max(1)` at `lib.rs:871`).
- **Caller exposure today:** Zero in-tree callers pass 0.
- **Fix:** One line — `n.max(1)` clamp at the builder, or return `Result<Self, ConfigError>`.
- **Cross-cutting:** This is the canonical example of `debug_assert!` used on a user-input path. Theme C in §3 below.

**B3. MPU registers stored but not enforced — silent divergence on MPU-protected firmware** *[verified, distinct from existing TrustZone debt]*

- **Where:** `crates/mdrp2350/src/bus/ppb.rs:99,340,552` (registers), `crates/mdrp2350/src/core/execute_fpu.rs:1216-1230` (lazy-flush comment: "MemManage — *not yet wired*"), `crates/mdrp2350/src/core/exceptions.rs:760-799` (only `TT` instruction consults regions).
- **What:** PPB stores `MPU_CTRL/RNR/RBAR/RLAR` and round-trips firmware writes cleanly. There is no MPU-region predicate on actual data reads/writes. Firmware writing `MPU_CTRL.ENABLE=1` sees all loads/stores succeed regardless of RBAR/RLAR.
- **Distinct from:** `tech_debt.md:1588` (TrustZone S-bit at exception entry) — that one bites NS exception entry; this one bites every MPU-protected workload.
- **Caller exposure today:** No corpus firmware enables MPU. Phase-8 work will surface this.
- **Fix:** Add `Bus::mpu_check(addr, kind, core) -> Option<Fault>` predicate, plumb through `read*/write*` and FPU lazy-flush. Gate on `MPU_CTRL.ENABLE=1` for zero-cost when disabled.
- **Interaction:** Connects to dead-code finding D1 (`Fault::MemManage` variant currently has only test constructors — keep it; it'll come back when this lands).

**B4. `step_pair_arm` exclusive-monitor invalidation is over-eager (Serial mode)** *[devil's-advocate reframing accepted]*

- **Where:** `crates/mdrp2350/src/lib.rs:1456-1460`
- **What:** `did_write_this_quantum` is set on **any** data write by either core. A peer LDREX is invalidated even if the write hit a different word. ARMv8-M §A3.4 specifies word-granular (or exclusivity-granule) invalidation. Liveness is preserved (LDREX/STREX retry loops are well-defined), but tight LDREX/STREX cycle counts diverge from silicon.
- **Reframing:** The wrongness report called this "leftover/redundant in favour of `ExclusiveMonitors::snoop`." The devil's advocate verified that `monitors.snoop` is **only** wired on the threaded path (`crates/mdrp2350/src/threaded/bus.rs`); serial `bus/mod.rs` never calls it. The mechanism here IS the only Serial-mode cross-core invalidator — just wrong granularity.
- **Caller exposure today:** No silicon oracle exercises cross-core LDREX/STREX competing-write — verified by grep over `cycle_cases.rs`, `dualcore_cases.rs`, `dual_model.rs`. So this is silicon-untested in either direction.
- **Fix:** Either wire `ExclusiveMonitors::snoop` into Serial mode, or replace `did_write_this_quantum` with per-core "wrote-to-word X" tracking. Larger lift than the discovery suggests.

### 2.4 Reframed findings (where the original framing was off)

**R1. `pub memory: Memory` on `Bus` — cache-invalidation hazard real, encapsulation framing wrong** *[devil's-advocate dissent recorded]*

- **Original tech-debt claim (H3):** Same shape as the existing Emulator pub-fields entry; recommend `pub(crate)` migration.
- **Dissent:** `Memory`'s own fields (`rom`, `sram`, `xip`) are **already private** at `crates/mdpicoem-common/src/memory.rs:9-11`. The hazard is not pub-field exposure; it's that `Memory`'s mutator surface (`load_rom`, `load_flash`, `sram_write*`, `xip_*`) does not notify `Bus::pending_invalidation_regions`. Making `bus.memory` `pub(crate)` does NOT fix it.
- **Reframed finding:** `Memory` mutator API needs an invalidation hook (callback or post-mutation invalidation routine on `Bus`). Severity medium, not high.

**R2. PPB writes through `Bus` directly — protection already exists** *[devil's-advocate falsified]*

- **Original tech-debt claim (H6):** No `debug_assert!` for PPB analogous to the SIO one. The `#[ignore]`d tests at `tests.rs:10520, 10570` are silently writing to placeholders.
- **Dissent:** A PPB-targeting `debug_assert!` already exists at `crates/mdrp2350/src/bus/mod.rs:2915-2921`:
  ```rust
  debug_assert!(addr >> 28 != 0xE || Self::is_boot_ram(addr) || Self::is_coresight_trace(addr),
                "PPB/coresight-aperture-bypass: address 0x{:08X} reached Bus::write32 — use CortexM33::bus_write32 wrapper", addr);
  ```
- **Reframed action:** The two ignored tests trip *that* assert. Update them to use `Emulator::mmio_write32` (which routes correctly per `lib.rs:1346-1364`). Severity drops from high to low — test cleanup, not missing protection.

**R3. Cycle costs scattered inline — feasibility worse than original report admits** *[devil's-advocate downgraded]*

- **Original tech-debt claim (H4):** Cycle costs hardcoded across ~6k LOC of executor; extract a `core::cycles::InstructionCost` table. Blocks all future cycle-fidelity work.
- **Dissent:** Sampled `crates/mdrp2350/src/core/execute_thumb32.rs:660-670`. Bus-state-dependent cycle costs are pervasive, not exceptional: LDR-immediate has `if rt == 15 { return 5 }` for PC loads; EXC_RETURN returns `self.exit_exception(val, bus)` (variable). The "80% case (single fixed-cost instructions)" framing under-sells how often "single fixed cost" is actually conditional. Track B Cycle Oracle Fidelity HLD declined the work for "too wide blast radius" — the centralized table doesn't change that radius; it relocates it.
- **Reframed:** Severity high → low. Don't extract until a use case drives it.

## 3. Cross-cutting themes

### Theme A — `pub`-field encapsulation footgun *[scope reduced after dissent]*

The existing `tech_debt.md:45-89` entry covers `Emulator.{cores,bus,clock}`. The tech-debt scout extended the pattern to `Bus.memory`, `Bus.dma` (RP2040), and `Registers`. The devil's advocate falsified the `Bus.memory` framing (Memory's fields are private — see R1 above). What remains:

- **Real:** `Emulator` direct-field access (already tracked).
- **Real:** `Memory` mutator API needs invalidation hook (reframed R1).
- **Real:** RP2040 `Bus::dma` pub asymmetry (H3).
- **Real:** `Registers.{r,xpsr,...}` direct mutation bypassing setters (latent, not currently bitten).

These should be addressed as **one migration**, not three. Per devil's advocate cross-finding interaction: ~2000+ call-site renaming pass; piecemeal stacks rewrites. Either commit to a single refactor that handles all four, or hold all four.

### Theme B — Half-modelled architectural state

B3 (MPU not enforced) interacts with the existing TrustZone S-bit FIXME at `exceptions.rs:191`, the FPSCR.AHP TODO at `execute_fpu.rs:1414`, and the RP2040 NVIC plumbing tracked in `tech_debt.md`. None surface as hard errors; firmware that hits any combination silently produces wrong results. Suggest adding a "Half-modelled architectural state" section in `tech_debt.md` with a checkbox-shape inventory:

| State machine | Stored | Enforced | Differential-validated |
|---|---|---|---|
| MPU regions | ✅ | ❌ | ❌ |
| TrustZone S-bit | partial | partial | ❌ |
| FPSCR.AHP | ✅ | ❌ | ❌ |
| RP2040 NVIC dispatch | partial | partial | ❌ (silicon_isr_diff_rp2040 exists but FAILs by design) |

### Theme C — `debug_assert!` on user-input paths

B2 is the worst case (zero quantum loops in release). Other `debug_assert!` sites sampled (`bus/mod.rs:1620` SIO, `lib.rs:693, 1502` placeholder guards) are reachable from internal paths only and correct.
