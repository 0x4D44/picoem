# HLD — OneROM CPU Speed Grade Oracle

**Date:** 2026-04-22 (revised, V3)
**Status:** Draft for review
**Target binary:** `onerom_cpu_speed_grade_rp2350`
**Applies to:** RP2350 CPU-mode OneROM serving; 1541 $E000 kernal fixture
**Host:** x86_64 Windows (gated — matches `Pacer`)

V3 changes vs V2:
- Phase 0 finding: 1541 fixture has CS on GPIO0, not GPIO13. No SDRR metadata parser exists; per-fixture pin maps are hardcoded library-wide (tech debt).
- Scope widened per Arthur: "do it properly". New Phase 0 is SDRR metadata reverse-engineering. New Phase 1 builds the parser + parameterises `CpuServingOracle`. Atomic pin I/O moved to Phase 2; speed-grade binary to Phase 3; calibration to Phase 4.
- Regression target widened: fixing the broken `onerom_stress_cpu_rp2350` (~140/2048 false-positive passes) is an explicit exit criterion of Phase 1 — it flips to full 2048/2048.

V2 changes vs V1:
- Phase 0 added: verify the 8 KB address-space claim. The two of thirteen address pins that alias with CS pins (A11↔GPIO15↔CS3, A12↔GPIO12↔CS2) mean "full 8 KB walk" isn't a given — requires investigation before the rest is viable.
- `ThreadedEmulator` used throughout (no serial→threaded promotion — that API isn't a thing).
- Ladder trimmed to 8 rungs (100 ns floor; `Instant::now()` overhead makes 80 ns noise-dominated).
- Pre-measurement microbench added so the ladder floor is grounded in the actual serve-loop rate, not extrapolation from `basic`.
- Host-config requirements (high-perf power plan, `HIGH_PRIORITY_CLASS`, `THREAD_PRIORITY_TIME_CRITICAL`) promoted from mitigations to hard requirements.
- Atomic conversion scope acknowledged as touching all `gpio_in` / `gpio_external_in` readers and writers, not a 30-line hit.
- Driver thread uses a stop-flag + short-chunk loop, not one huge `run_quanta`.

---

## 1. Goal

Measure the minimum wall-clock access time at which our emulator can still serve correct OneROM bytes — expressed as an equivalent EPROM speed grade (e.g. "reliable at 250 ns, fails at 200 ns").

The existing `onerom_serving_oracle_cpu_rp2350` reports **emulated** latency (ns-at-150 MHz derived from emulated cycles). `paced_bench_rp2350 --workload onerom` reports aggregate emulated-MHz throughput under a synthetic shape. Neither answers the real question: **"if a real CPU driving our emulated ROM at X ns access time read every byte, would it get the right data?"**

## 2. Non-goals

- Measuring PIO-mode serving speed. Separate oracle later if wanted.
- Varying the fixture at runtime. One fixture, hardcoded path.
- Profile-guided emulator optimisation. This oracle *measures*; follow-up work optimises.
- Comparing against real RP2354 silicon. Host-only; silicon oracle is a future pass.

## 3. Test subject

**Fixture:** `crates/mdpicoem-harness/fixtures/onerom-fire-24-a-rp2350-1541-cpu.bin`
**ROM being served:** 1541 $E000 kernal (901229-06AA), 8 KB (addresses $E000–$FFFF).
**Serve loop PC range:** `0x1000_09A4..=0x1000_09B0` (from `onerom_stress_cpu_rp2350.rs`).
**Serve loop shape:** 5-instruction tight loop: LDR (read gpio_in) → LDRB (shadow lookup) → STR (SIO_GPIO_OUT) → STR (SIO_GPIO_OE) → B (loop).

## 4. Phase 0 — SDRR metadata investigation

**Motivation.** Per-fixture pin profiles are baked into the OneROM firmware's flash metadata but are not parsed anywhere in our codebase. `CpuServingOracle`'s constants (CS1/CS2/CS3 on GPIO 13/12/15, `ADDR_PINS = [7,6,5,4,3,2,1,0,10,11,14,15,12]`) match `test-sdrr-0-cpu` but **not** `1541-cpu` (CS on GPIO0). Without a parser we can't address the 1541 correctly.

Additionally: two of the 13 address pins alias with CS pins under the test-sdrr-0 bake (GPIO12 doubles as A12/CS2; GPIO15 doubles as A11/CS3). Whether this aliasing also exists under the 1541 bake is an output of the investigation. If pin map differs, the 8 KB addressability question may resolve differently.

**Tasks.**

1. Locate the SDRR metadata bake in `crates/epio-sys/` (the `epio-sys` crate already links against the vendor's apio/epio code, and `onerom_full_system_rp2350.rs:37` says "parsed from the bundled fixture at file offset 0x80FC" — starting point). Identify the C struct(s) that define pin profile (CS pins, ADDR pins, DATA pins, OE pin, CS polarities, any bank-switching config).
2. Dump the relevant bytes of the `1541-cpu.bin` fixture at the metadata offset. Decode by hand against the struct definition. Record: CS assignments, ADDR pin list, DATA pin list, OE pin, CS polarities, anything else pin-related.
3. Repeat for `test-sdrr-0-cpu.bin` to confirm the decode matches the library's hardcoded constants (verification that our parser is correct).
4. Document findings + propose the Rust struct `SdrrPinProfile` and its parser signature.

**Exit criterion.** We can hand-decode both fixtures' pin profiles and confirm the decode is reproducible; we have a proposed `SdrrPinProfile` + parser spec ready for Phase 1 implementation.

**Artefacts.** `wrk_scratch/sdrr-metadata-notes.md` with the struct layout, the decoded profiles for both fixtures, and the Rust spec. No code yet.

**Decision gate.** If the metadata format is too opaque to reverse-engineer in a reasonable timebox (say 2 hours), escalate. Fallback: use `test-sdrr-0-cpu` for the speed-grade oracle (existing constants work), defer the 1541 variant. Not the preferred outcome, but a hard limit.

## 5. Architecture

Single `ThreadedEmulator` built up-front with `step_quantum = 256`. No serial phase; boot sync runs through the threaded runtime at the same quantum.

Two host threads on top of the 6 emulator workers:

- **Driver thread**: spawned from `main`. Loops `runtime.run_quanta(CHUNK)` with `CHUNK = 65_536` (≈ 65 ms of emulated time, well under any ladder-run wall-clock) until a `stop: AtomicBool` is set. Short chunks so shutdown is prompt; large enough that per-chunk overhead is noise.
- **Measurement thread**: pinned to a dedicated host core with `HIGH_PRIORITY_CLASS` + `THREAD_PRIORITY_TIME_CRITICAL`. Drives stimulus and samples data. Sets `stop` when the ladder is finished.

Workers pinned via the existing `thread_mask`. Measurement pinned separately. Driver inherits main's affinity (doesn't need its own core — mostly waits in `run_quanta`).

**Host config (mandatory, set by the binary at startup):**
- Windows high-performance power plan (set via `powercfg /setactive`, or document as a run prerequisite if setting it programmatically is clumsy).
- Process: `HIGH_PRIORITY_CLASS`.
- Measurement thread: `THREAD_PRIORITY_TIME_CRITICAL`, pinned.
- Worker threads: inherit from `thread_mask` / current worker config.

Document in the binary's `--help` that without these, timing is untrustworthy.

## 6. Atomic pin I/O (prerequisite)

`Bus::gpio_external_in: u32 → AtomicU32`
`Bus::gpio_in: u32 → AtomicU32`
`Bus::gpio_external_mask: u32` — stays plain; set once before the run.

**Ordering:** `Relaxed` on both. Single-writer per location (measurement thread writes `external_in`; worker's `update_gpio` writes `in`). No cross-location ordering needed — x86_64 + Relaxed is correct here.

**Callsite ripple.** Every reader/writer of these two fields updates to `.load(Relaxed)` / `.store(Relaxed)`:
- `Bus::update_gpio` (and any threaded-path merge equivalent — check if threaded architecture reroutes this)
- CPU's SIO MMIO path (SIO_GPIO_IN read)
- All existing harness binaries that read `emu.bus.gpio_in` / write `emu.bus.gpio_external_in` (at least `onerom_serving_oracle`, `onerom_serving_oracle_cpu`, `onerom_stress_cpu_rp2350`, plus anything the grep finds)

Expected surface area: ~40–60 callsites based on an initial grep. All mechanical, no semantic changes. `cargo test` covers correctness.

**Perf check.** Relaxed loads/stores on x86_64 compile to plain `mov`. Verify with `cargo asm` on the hot path if anything looks suspicious after the change; otherwise trust.

## 7. Stimulus and walk

Phase 0 produces a `Vec<WalkStep>` of length 8192 (assuming outcome (a)). Each step has a `gpio_stim: u32`, `gpio_mask: u32`, `expected: u8`.

**CS policy.** CS1 held low throughout the run. For multi-CS-mode walks (outcome (a) with multiple patterns), CS2/CS3 are part of the per-step `gpio_stim` — the mask is the union of all externally-driven pins.

**No gap phase per byte.** Real EPROM protocol is CS-held-asserted with address pins changing; we match that.

**Order:** per sweep, shuffle with a seeded PRNG (`rand::rngs::StdRng::seed_from_u64`, default seed `0x1541_CAFE_0000_0001`). `--seed <u64>` flag for reproducibility.

## 8. Measurement thread loop

Per sample:

```rust
let step = &plan[shuffle[i]];
let t0 = Instant::now();
bus.gpio_external_in.store(step.gpio_stim, Relaxed);
while t0.elapsed() < target { core::hint::spin_loop(); }
let merged = bus.gpio_in.load(Relaxed);
observed[i] = ((merged >> GPIO_DATA_BASE) & 0xFF) as u8;
```

**Timing source:** `Instant::now()` wraps `QueryPerformanceCounter` on Windows. Frequency-invariant, ~20 ns/call. No `rdtsc` path — not worth the complexity unless Phase 3 shows it's needed.

**Busy-wait:** tight loop on `Instant::elapsed()`. No `thread::sleep` — Windows scheduler granularity is ≥ 500 µs even with `timeBeginPeriod(1)`.

## 9. Ladder

```
[500, 400, 300, 250, 200, 150, 120, 100]  // ns, 8 rungs
```

80 ns dropped: `Instant::now()` overhead is ~20 ns per call, so 80 ns budget has ~25% measurement noise. 100 ns is the realistic floor given the timing source.

**Per threshold:**
- 3 full sweeps (24 576 samples for an 8 KB plan, 6 144 for a 2 KB plan).
- Each sweep uses an independently-shuffled order.
- Threshold **passes** iff every observed byte equals `plan[shuffle[i]].expected`.
- First mismatch per failed threshold logged (target_ns, sweep idx, sample idx, addr, expected, observed).

**Run strategy:** start at 500 ns, step down. Stop at first fail. Report highest-pass, first-fail, edge range.

## 10. Pre-measurement microbench (new in V2)

Before the ladder runs, the binary runs a **free-run throughput probe**:

1. Drive one fixed address stimulus.
2. Let the emulator run for 100 ms wall-clock.
3. Snapshot `core.cycles()` before/after.
4. Report: "serve loop emulated rate: XXX MHz (Y ns per emul cycle wall-clock)".

This anchors the ladder interpretation. If the probe shows the serve loop runs at 200 MHz, 100 ns is comfortable (5 cycles × 5 ns/cycle = 25 ns emul, leaving 75 ns slack). If it shows 100 MHz, 100 ns is borderline (50 ns emul per serve, 50 ns slack). If < 80 MHz, we warn "ladder floor may fail on emulator-throughput grounds, not real-timing grounds" and suggest raising the floor.

No gate — just a diagnostic printed before the ladder.

## 11. Verification (post-run)

After each sweep (clock already stopped):

```rust
for i in 0..observed.len() {
    if observed[i] != plan[shuffle[i]].expected {
        record_fail(target_ns, sweep_idx, i, ...);
    }
}
```

Not in the timed path.

## 12. Liveness and watchdog

- **Pre-sweep liveness:** snapshot `core(0).cycles()`. If after 100 µs of measurement the cycle count hasn't advanced, the emulator is wedged — abort.
- **Post-sweep PC check:** read `core(0).regs.pc`. Must be in the serve-loop PC range. Out-of-range → abort with diagnostic (firmware left the serve loop, probably due to bad stimulus or a drift bug).
- **Wall-clock watchdog:** main wraps the whole ladder in a 60 s `Duration` cap. Abort on expiry.

## 14. Risks and mitigations

| # | Risk | Mitigation |
|---|---|---|
| 1 | Phase 0 uncovers that 8 KB isn't reachable through the 1541-cpu firmware's CS protocol. | Fall back to the reachable subset; rename to "1541 N-KB window". Binary still works. |
| 2 | Scheduler jitter at ≤ 150 ns targets causes false fails. | Pin + TIME_CRITICAL + 3 sweeps per threshold. Accept ~100 ns as the realistic noise floor. |
| 3 | `Instant::now()` cost eats measurement budget. | Document in the report header ("timing source overhead ~20 ns"). `rdtsc` fast-path is a future optimisation if needed. |
| 4 | Bus atomic conversion introduces a subtle bug in an existing code path. | `cargo test -p mdrp2350 --lib` (1402 tests) + existing CPU oracle (15/15 pass) are the regression gate. Both must be green. |
| 5 | 1541-cpu fixture's PIO blocks aren't inert at serve-loop entry, producing pad contention on data pins. | Boot sync asserts `PIO1.CTRL = PIO2.CTRL = 0` (existing check). If 1541 fixture differs, adapt the assertion. |
| 6 | CPU frequency scaling changes perceived timing across a run. | High-perf power plan is a requirement, not a mitigation. Document in `--help`. |
| 7 | Driver thread's `run_quanta(CHUNK)` overhead gates the emulator. | `CHUNK = 65_536` at sq=256 ≈ 65 ms emul, well above per-chunk overhead. Chunks shorter than 1 ms would start to dominate. |

## 15. Phasing

**Phase 0 — SDRR metadata investigation** (~1-2 hours). §4 above. Notes + spec in `wrk_scratch/`. No code yet.

**Phase 1 — SDRR parser + library parameterisation** (~3-5 hours):
- `crates/mdpicoem-harness/src/sdrr_metadata.rs` — new module. Rust `SdrrPinProfile` struct + parser from raw flash bytes.
- Parameterise `CpuServingOracle` + related helpers to accept `&SdrrPinProfile` rather than baking constants.
- Update callers: `onerom_serving_oracle_cpu_rp2350` (threads through test-sdrr-0-cpu profile), `onerom_stress_cpu_rp2350` (threads through 1541-cpu profile). Any PIO-side callers that use the same constants.
- Regression gates: test-sdrr-0-cpu oracle stays 15/15; `onerom_stress_cpu_rp2350` flips to full 2048/2048 PASS on the 1541 fixture; `cargo test -p mdrp2350` (1402) + `cargo test -p mdpicoem-harness` unchanged.

Commit after Phase 1 green.

**Phase 2 — atomic pin I/O** (~1-2 hours). §6 above. All existing tests green post-change.

Commit after Phase 2 green.

**Phase 3 — speed-grade binary** (~3-4 hours):
- `crates/mdpicoem-harness/src/bin/onerom_cpu_speed_grade_rp2350.rs` — main, host-config setup, driver + measurement threads, ladder loop, report.
- `crates/mdpicoem-harness/src/onerom_cpu_speed_grade.rs` — stability-free, testable bits: walk plan, verification, ladder logic.
- Walk plan built from the 1541 $E000 shadow slice using the parameterised pin profile. Full 8 KB coverage if the profile and addressing math support it; document actual reach if less.
- Unit tests:
  - `walk_plan::full_walk_covers_target_span`
  - `ladder::stops_at_first_fail`
  - `verify::mismatch_recorded_with_context`
  - `measurement::busy_wait_respects_target` (host-timing-sensitive — tolerance allowed)

Commit after Phase 3 green.

**Phase 4 — calibration run** (~1 hour):
1. Throughput probe first. Confirms serve-loop rate + ladder-floor realism.
2. Run the ladder. Capture output.
3. Journal: entry in the existing implementation journal. Record what EPROM grade our emulator meets today.
4. If top rung fails → diagnose (too-aggressive ladder start? fixture issue? emulator bug?) before declaring done.

## 16. Success criteria

- Binary builds clean; no warnings in `mdrp2350` / `mdpicoem-common` / `mdpicoem-harness`.
- Unit tests green.
- Existing suite unaffected: `cargo test -p mdrp2350 --lib` 1402 pass; `onerom_serving_oracle_cpu_rp2350` 15/15 pass.
- A real run produces a meaningful ladder verdict (at least the 500 ns rung passes, ideally much lower).
- The throughput probe number is sensible (60–300 MHz range).
- `samply` profile of a calibration run shows the measurement thread's busy-wait + emulator workers dominate; no surprise host-side hot spots.

## 17. Explicitly out of scope

- Feature flags. Only command-line args: `--seed <u64>`, `--ladder <comma-list>`, `--sweeps-per-threshold <n>` (defaults baked in).
- Backwards-compat shims. Atomic conversion replaces old fields in place; no dual path.
- Multiple fixtures per run. One hardcoded fixture; if we want test-sdrr-0 later, clone the binary.
- `rdtsc` timing source. Phase 3 may request it if `Instant::now()` overhead dominates; out of scope for V2.
- Silicon comparison. Future oracle.
