# mdrp2040 Quantum Step

Version: 1.2.0
Date: 2026-04-14

## Problem

`mdrp2040::Emulator::step()` runs **one instruction per call** and ticks
peripherals (`tick_pio`, `update_gpio`, `wake_checks`) every time. The
sibling `mdrp2350::Emulator::step()` runs **many instructions per
quantum** and ticks peripherals once at the end. The unused
`step_quantum` field on `EmulatorBuilder` is the design hook for the
quantum model — it has been on the books since Phase 7 closeout
(`tech_debt.md:137-148`).

The new `paced_bench_rp2040` quantifies the cost. Bypassing the three
per-instruction peripheral calls in `step()` (basic ALU workload, no
GPIO/PIO traffic, single core, 2 s unpaced):

| Mode                          | Throughput | Host TSC ticks / emu cycle |
|-------------------------------|------------|----------------------------|
| Baseline (per-instruction)    | 78.8 MHz   | 39.0                       |
| Peripheral ticks bypassed     | 247.0 MHz  | 12.4                       |

So per-instruction peripheral overhead is roughly **106 host TSC ticks
per step**, two-thirds of the total. At the RP2040's stock 125 MHz the
baseline cannot sustain real-time on this host (58% of target, 100% of
quanta behind in paced mode).

## Proposed change

Make `step()` honour `step_quantum`. Drain both cores up to the cycle
target — one instruction per core per inner-loop iteration so bank
contention timing on core 1 is preserved — then tick peripherals once.

### Before (`crates/mdrp2040/src/lib.rs`)

```rust
pub fn step(&mut self) -> u64 {
    self.bus.set_active_core(0);
    let c0 = self.cores[0].step(&mut self.bus) as u64;
    self.maybe_wake_core1(0);

    if !self.cores[1].is_halted() {
        self.bus.set_active_core(1);
        self.bus.begin_core1_step();
        let _ = self.cores[1].step(&mut self.bus);
        self.bus.end_core1_step();
        self.maybe_wake_core1(1);
    } else {
        self.bus.end_core1_step();
    }

    self.clock.cycles = self.clock.cycles.wrapping_add(c0);
    self.tick_pio(c0 as u32);
    self.update_gpio();
    self.wake_checks();
    c0
}
```

### After

```rust
pub fn step(&mut self) -> u64 {
    debug_assert!(self.step_quantum > 0, "step_quantum must be >= 1");
    let start = self.clock.cycles;
    let target = start + self.step_quantum as u64;

    while self.clock.cycles < target && !self.cores[0].is_halted() {
        self.bus.set_active_core(0);
        let c0 = self.cores[0].step(&mut self.bus) as u64;
        self.maybe_wake_core1(0);

        if !self.cores[1].is_halted() {
            self.bus.set_active_core(1);
            self.bus.begin_core1_step();
            let _ = self.cores[1].step(&mut self.bus);
            self.bus.end_core1_step();
            self.maybe_wake_core1(1);
        } else {
            self.bus.end_core1_step();
        }

        self.clock.cycles = self.clock.cycles.wrapping_add(c0);
    }

    let consumed = self.clock.cycles.wrapping_sub(start);
    self.tick_pio(consumed as u32);
    self.update_gpio();
    self.wake_checks();
    consumed
}
```

What changes in semantics:

- **Peripheral ticks** fire once per quantum, with the summed cycle
  count, instead of every instruction with the per-instruction count.
  Total PIO advancement is identical; only the granularity changes.
- **`update_gpio` and `wake_checks`** are now quantum-end. `bus.gpio_in`
  is stale within a quantum. This matches `mdrp2350::Emulator` exactly
  (`crates/mdrp2350/src/lib.rs:188-195`).
- **`step()` return value** is now the quantum's consumed cycles, not
  the last instruction's cycles. `run()` only uses this to detect a
  stalled emulator (`consumed == 0` → break), so the contract change is
  invisible to it.

What does NOT change:

- Per-instruction interleaving of core 0 / core 1 — preserves bank
  contention timing on core 1's load/stores.
- `set_active_core`, `begin_core1_step` / `end_core1_step` — still
  per-instruction, exactly as today.
- `maybe_wake_core1` — still per-instruction, so a FIFO write from core
  0 wakes core 1 within the same quantum.
- `CortexM0Plus::step()` — unchanged. Cycles are still tracked
  per-instruction inside the CPU.
- Default `step_quantum = DEFAULT_STEP_QUANTUM = 64` — unchanged.
- Bus, SIO, PIO, memory model — unchanged.

## Test impact

About 22 unit-test sites call `emu.step()` expecting it to advance by
exactly one instruction. Two distinct breakage patterns:

- **PIO / pin-state assertions** — e.g. `pio_tests.rs:254`
  (`pio0_blinky_drives_gpio_in`) asserts pin state after each `step()`.
  Under the new default quantum of 64, the assertion fires mid-loop.
- **Exception-entry assertions** — e.g. `tests.rs:1831`
  (`step_handles_svc_and_return`) steps through SVC entry and asserts
  `pc() == handler` after step 1. Under quantum 64 the next instructions
  execute too, so PC has already advanced past the handler.
  `step_hardfault_on_undefined_then_unwinds:1865` and
  `step_primask_escalates_svc_to_hardfault:1914` are the same shape.

Fix: tests that need single-instruction granularity construct the
emulator via the builder with quantum 1 — same pattern mdrp2350 uses
(`crates/mdrp2350/src/pio_tests.rs:131`):

```rust
let mut emu = EmulatorBuilder::new(Config::default())
    .step_quantum(1)
    .build();
```

Most call sites go through helpers (`blinky_emulator`,
`park_core0_on_nops` and friends), so the change is concentrated:

| Test file                                  | Helpers / direct sites |
|--------------------------------------------|------------------------|
| `crates/mdrp2040/src/tests.rs`             | 6 direct (4 tests, incl. 3 exception-entry tests) |
| `crates/mdrp2040/src/pio_tests.rs`         | ~13 (mostly via `blinky_emulator` / `park_core0_on_nops`) |
| `crates/mdrp2040/tests/firmware.rs`        | 2 (likely pass without `step_quantum(1)`, but update for clarity) |
| `crates/mdrp2040/tests/smoke.rs`           | 0 (already builder-based) |

The self-documenting test
`pio_tests.rs:391` (`emu_step_advances_pio_by_core0_cycle_cost`)
asserts that PIO advances by `c0` ticks per `emu.step()`. It still
passes under `step_quantum(1)` (where `c0 == quantum`), but its
docstring ("If the cadence were fixed at 1 PIO tick per emu.step...")
becomes inaccurate post-change. Either update the docstring or retire
the test — the property it documents is still correct, just now opt-in
via `step_quantum(1)`.

`crates/mdrp2040app/` smoke test calls `Emulator::run`, not `step`, so
it is unaffected. `crates/mdpicoem-harness/src/bin/qemu_diff_m0plus.rs`
drives `CortexM0Plus` + a stripped bus directly (imports
`mdpicoem_harness::m0plus::{Bus, CortexM0Plus}`) and never constructs
an `Emulator`, so it is unaffected too.

## Risks

**GPIO_IN staleness within a quantum, and the PIO `IN PINS`
responsiveness change.** Real silicon updates pad-input-loopback
continuously; after the change, firmware that writes `GPIO_OUT` and
reads `GPIO_IN` in the same quantum sees the pre-write value. More
importantly, this is a genuine responsiveness change for PIO — *not*
just staleness inherited from mdrp2350. The OLD `step()` ticked PIO
with a freshly-merged `gpio_in` after every core instruction, so a PIO
program executing `IN PINS` back-to-back with core-side `GPIO_OUT`
writes saw those writes within ~1 instruction. The NEW `step()`
snapshots `gpio_in` once per quantum, so the same `IN PINS` sequence
only observes core-side writes at quantum boundaries — up to ~64 cycles
late at the default quantum (≈ 510 ns at 125 MHz). mdrp2350 has had
this exact quantum-end PIO behaviour since Phase 5 with no firmware
fallout, which suggests no realistic firmware loop straddles a quantum
without an intervening sync; but callers doing cycle-accurate PIO/GPIO
co-simulation should be aware the cadence changed here.

**WFE/SEV.** mdrp2040's `wake_checks` is currently a stub that just
clears `event_flag[0]`. M0+ WFE is not yet modelled. Quantum-end
clearing is functionally equivalent to per-instruction clearing for
this stub. When WFE lands, the model will need to break out of the
inner loop on `is_wfe_waiting()` — same shape as
`mdrp2350::Emulator::step()`.

**Core 1 halted at quantum start.** If core 0 wakes core 1 mid-quantum
via a FIFO write, `maybe_wake_core1(0)` sets `cores[1]` awake *within
the same inner-loop iteration*. The very next block (`if !self.cores[1]
.is_halted()`) then runs core 1's first instruction before the loop
advances. This was the same in the old `step()` (which also called
`maybe_wake_core1(0)` before checking `cores[1].is_halted()`), so there
is no timing change.

**`update_latest_cycles` parity with mdrp2350.** mdrp2350 publishes per-
core cycles into its PPB before each instruction so DWT_CYCCNT reads
land on a fresh value (`crates/mdrp2350/src/lib.rs:159`). mdrp2040 has
no DWT in its PPB model today, so no parallel call is needed.

**Pacer granularity in `mdrp2040app`.** `crates/mdrp2040app/src/sim.rs`
calls `emu.run(qc)` with `qc = pacer.quantum_cycles() = 150`. Today
`run(150)` makes ~50–150 `step()` calls of ~1–3 cycles each. Post-
change, `run(150)` makes ~3 `step()` calls of ~64 cycles each, with
overshoot up to `step_quantum - 1`. The pacer adapts (begin/end pair,
not strict quantum), and the extra overshoot is bounded, so real-time
pacing still converges — just at a slightly coarser effective
granularity (64 cycles, ~510 ns at 125 MHz). Not observable at the
human-facing 500 ms MHz-update cadence.

## Verification

1. `cargo test -p mdrp2040` and `cargo test -p mdrp2040app` pass.
2. `cargo test -p mdpicoem-harness` passes (binaries still build).
3. `cargo run -p mdpicoem-harness --release --bin paced_bench_rp2040
   -- --unpaced --seconds 2` → throughput moves from ~78 MHz toward
   the 247 MHz upper bound. Expect ~2.5× (~200 MHz), since some
   quantum-end work remains.
4. Paced run at default settings → `Verdict: REAL-TIME OK`.
5. `qemu_diff_m0plus --fuzz 100000` still passes — the harness drives
   `CortexM0Plus` + a stripped bus directly and never constructs an
   `Emulator`, so it is inherently unaffected by this change.

## Quantum-to-throughput scaling

Measured with `paced_bench_rp2040 --unpaced --seconds 2` at 125 MHz
target, single-core ALU loop:

| `--quantum` | Throughput |
|-------------|------------|
| 8           | 26 MHz     |
| 16          | 52 MHz     |
| 20          | 65.6 MHz   |
| 25          | 81.4 MHz   |
| 64 (default)| ~210 MHz (stable across 3 runs) |
| 125         | ~211 MHz   |

At small quanta, per-quantum peripheral-tick overhead dominates and
throughput scales roughly linearly with quantum size. Above ~64 cycles
the curve flattens — the peripheral tick is fully amortised and the CPU
inner loop dominates. The default `DEFAULT_STEP_QUANTUM = 64` is a
sweet spot: small enough for fine-grained real-time pacing (≈ 510 ns
granularity at 125 MHz), large enough to amortise peripheral-tick
overhead to ~14 host TSC ticks per emu cycle.
