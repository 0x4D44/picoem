# RP2040 Peripheral Coverage — HLD V1

## 1. Purpose

Add emulation for the RP2040 peripherals that real pico-sdk firmware touches, so `mdrp2040` can run representative SDK binaries to completion instead of falling into the `HashMap<u32, u32>` catch-all.

In scope: **TIMER, DMA, UART, SPI, I2C, ADC, PWM, WATCHDOG, RTC.**

### Non-goals

- Full datasheet coverage per peripheral. Model the observed register subset that real firmware touches; nothing more.
- USB, VREG, TBMAN, BUSCTRL, SYSCFG, PSM. Stay in the HashMap fallthrough until a concrete firmware demands them.
- Cycle-accurate timing to finer than SysTick resolution on the silicon oracle.
- Backward compatibility shims or migration paths. This is a dev-environment refactor; existing `peripheral_regs` consumers get their blocks promoted to real impls and the HashMap keeps shrinking.
- RP2350 mirror in this HLD. Impls will live in `mdpicoem-common` so RP2350 can consume them afterwards by adding match arms to its bus; tracked as follow-up.

## 2. Current state

- `crates/mdrp2040/src/bus/mod.rs:165` — `peripheral_regs: HashMap<u32, u32>` catches all unmodelled MMIO. Writes store, reads return stored value or 0. No side effects, no IRQs, no state machines.
- `crates/mdrp2040/src/bus/mod.rs:451-475` — `peripheral_read32` is a clean `match base { ... _ => peripheral_regs.get(...) }` ladder. Adding a peripheral means adding one arm.
- `crates/mdpicoem-common/src/lib.rs:28-33` — `Peripheral` trait is declared but has zero `impl` blocks anywhere in the workspace. Unused.
- **No path from bus back to NVIC.** No `nvic.set_pending` in the bus crate. Peripherals today have no way to fire IRQs. Hard blocker for TIMER, ADC, WATCHDOG, UART RX.
- **No generic per-cycle peripheral tick.** `crates/mdrp2040/src/lib.rs:303-314` has a per-cycle loop but it only ticks PIO (`tick_pio(1)`) and GPIO. Anything needing cycle-driven state advance (TIMER counter, DMA transfers) has no hook.
- No probe differential oracle exists for RP2040. `probe_diff_rp2040` is a stub (exits 2). `qemu_diff_m0plus` filters out all Thumb-32 encodings (see `is_m0plus_safe` at `qemu_diff_m0plus.rs:291-314`), so `BL`/`MRS`/`MSR`/`DSB`/`DMB`/`ISB` are unit-test-only.

## 3. Oracle strategy

Hardware: RP2040 on the lab rig back-to-back with a Pico debug probe, same topology as the RP2354 setup. Arthur ~30 min.

### 3.1 `probe_diff_rp2040`

Port `crates/mdpicoem-harness/src/bin/probe_diff_rp2350.rs` structure (probe-rs `Session::auto_attach` → `core(0)` → per-test write instruction + BKPT, set regs, single-step, diff). Drop the `is_m0plus_safe` Thumb-32 filter — on real silicon, the small Thumb-32 subset (`BL`/`MRS`/`MSR`/`DSB`/`DMB`/`ISB`) is now testable end-to-end. Keep the FPU/CBZ/IT rejections.

### 3.2 `silicon_periph_diff_rp2040`

Port `silicon_periph_diff_rp2350.rs`'s `PeriphScenario` struct verbatim:

```rust
pub struct PeriphScenario {
    pub name: &'static str,
    pub setup: &'static [(u32, u32)],
    pub max_sysclks: u32,
    pub observe: &'static [(u32, u32)],
    pub observe_pins: u32,
    pub custom_sled: Option<&'static [u8]>,
}
```

The one substitution: **M0+ has no DWT CYCCNT**. Swap the CYCCNT timing window for SysTick — 24-bit down-counter, present on every Cortex-M, no optional DWT required. At 125 MHz that's a ~134 ms window, plenty for any end-state scenario we care about. If a future scenario needs finer resolution, a PIO-driven counter is the escape hatch; not needed for V1.

### 3.3 Phase 0 exit criterion

Both binaries land with one trivial green scenario each (SIO GPIO toggle). Proves the oracle fires before we write any peripheral code.

## 4. Architecture

### 4.1 Peripheral pattern — static dispatch

Keep the existing match-ladder dispatch on the `Bus`. Each new peripheral is a **named field** on `Bus`, with `read32`/`write32`/`tick` methods. Adding a peripheral is three mechanical changes:

1. New module `crates/mdpicoem-common/src/peripherals/timer.rs` (etc.) exporting `TimerRegs`.
2. New field on `Bus`: `pub timer: TimerRegs`.
3. New arms in `peripheral_read32` / `peripheral_write32`: `TIMER_BASE => self.timer.read32(offset)`.

The `Peripheral` trait in `mdpicoem-common` stays as a documented interface convention — same shape every peripheral implements — but is **not** used for dynamic dispatch. No `Box<dyn Peripheral>`, no trait objects, no registration table. Nothing the compiler can't inline.

Rationale: the current match ladder works, the codebase already owns CLOCKS/RESETS/XOSC/PLL as named fields, and generalising to dynamic dispatch adds indirection we don't need. Existing modelled peripherals stay where they are; we do not refactor them.

The trait signature is updated once to carry IRQ plumbing:

```rust
pub trait Peripheral {
    fn read32(&mut self, offset: u32) -> u32;
    fn write32(&mut self, offset: u32, value: u32, irqs: &mut IrqLines);
    fn tick(&mut self, irqs: &mut IrqLines) {}  // default no-op
}
```

### 4.2 IRQ routing

One new struct on `Bus`:

```rust
#[derive(Default)]
pub struct IrqLines([bool; 32]);

impl IrqLines {
    pub fn assert(&mut self, irq: u8) { self.0[irq as usize] = true; }
    pub fn take(&mut self) -> [bool; 32] { std::mem::take(&mut self.0) }
}
```

Peripherals call `irqs.assert(IRQ_TIMER_IRQ_0)` directly. The `Emulator::step` loop, after each per-cycle tick, drains `IrqLines` and forwards asserted bits to **both cores' NVIC** (RP2040 has per-core NVIC; each core independently masks):

```rust
let raised = self.bus.irq_lines.take();
for irq in 0..32 {
    if raised[irq] {
        self.cores[0].nvic.set_pending(irq as u8);
        self.cores[1].nvic.set_pending(irq as u8);
    }
}
```

No feature flags, no routing tables. If a peripheral asserts an IRQ and no core has it enabled, the NVIC just doesn't take it — that's correct behaviour.

### 4.3 Per-cycle peripheral tick

Generalise the existing PIO tick loop at `crates/mdrp2040/src/lib.rs:303-314`. After the dual-core step loop, the slow path becomes:

```rust
for _ in 0..consumed {
    self.bus.tick_peripherals(); // timer, dma, pwm, adc, watchdog, rtc, pio
    self.bus.update_gpio();
}
```

`tick_peripherals` calls `.tick(&mut self.irq_lines)` on each stateful peripheral in a fixed deterministic order. PIO's existing per-cycle tick folds into this path. The fast path (PIO idle → bulk-advance) stays unchanged for PIO; we do not add a similar fast path for other peripherals in V1 — measure first.

TIMER, being a simple 64-bit microsecond counter, does **not** need a per-cycle callback — it can recompute `now()` lazily from `bus.master_cycle` on read and schedule alarm IRQs at write-time by computing "when does this alarm fire in cycles". We implement it that way. Its `tick()` is a no-op.

### 4.4 DMA — bus master, separate shape

DMA is architecturally different: it **issues** bus transactions, it doesn't just respond. It needs read/write access to other peripherals from inside its tick.

```rust
pub struct Dma { channels: [DmaChannel; 12], /* ctrl regs */ }

impl Dma {
    pub fn read32(&mut self, offset: u32) -> u32 { ... }
    pub fn write32(&mut self, offset: u32, value: u32, irqs: &mut IrqLines) { ... }
    pub fn tick(
        &mut self,
        mem: &mut dyn DmaMaster, // thin trait exposing just read/write on the bus
        dreqs: &[bool; DREQ_COUNT],
        irqs: &mut IrqLines,
    ) { /* per channel: if enabled && dreq high, issue one transfer */ }
}
```

`DmaMaster` is a small trait implemented on `Bus` that exposes only `read{8,16,32}` / `write{8,16,32}`. Needed because `Dma` lives on `Bus` and `&mut Dma` + `&mut Bus` together needs structural splitting — the trait gives us a narrowly-typed handle over the rest of Bus. Trivial to implement.

**DREQ** state: each peripheral exposes a getter (`self.uart0.tx_dreq() -> bool`, `self.pio[0].tx_dreq(sm) -> bool`, etc). `Bus::tick_peripherals` collects DREQs into a fixed `[bool; DREQ_COUNT]` array and passes it to `Dma::tick`. DREQ numbers follow the RP2040 datasheet Table 120.

V1 DMA scope:
- 12 channels, transfer sizes 1/2/4 bytes.
- Enable / busy / transfer count / read+write addr / ctrl.
- DREQ handshake: `DREQ_FORCE` (no gating), PIO TX/RX (both blocks, all 4 SMs each), UART0/1 TX+RX, SPI0/1 TX+RX, ADC, TIMER.
- IRQ0 / IRQ1 lines, per-channel enable mask.
- Not in V1: CRC/sniff, channel chaining, ring mode, byte swap, priority arbitration (we do fixed-priority lowest-channel-wins).

## 5. Phasing

| Phase | Content | Oracle |
|---|---|---|
| **0** | `probe_diff_rp2040` + `silicon_periph_diff_rp2040` scaffolding. Relax `is_m0plus_safe`. Swap CYCCNT→SysTick. One green smoke scenario each. | — (building the oracles themselves) |
| **1** | `IrqLines` + `tick_peripherals` on Bus. TIMER as first peripheral through the new pattern. | ≥3 TIMER scenarios in `silicon_periph_diff_rp2040`: alarm fires, TIMEH latching, busy_wait interop. |
| **2** | UART (0 and 1), SPI (0 and 1), I2C (0 and 1). Observed registers only — TX/RX FIFO, baud/speed config, status bits, IRQ lines. | Loopback scenarios per peripheral. |
| **3** | ADC (round-robin or one-shot, DREQ), PWM (8 slices, period/duty/wrap IRQ). | Small catalogue. |
| **4** | DMA — 12 channels, DREQ matrix covering all peripherals built so far, no chaining/CRC/sniff. | Channel-copy scenarios (mem→mem, periph→mem, mem→periph), DREQ-gated scenarios against PIO and UART. |
| **5** (opt) | WATCHDOG, RTC. As-needed. | As needed. |

Each phase ends with its oracle scenarios landing green on real RP2040 silicon before we move on.

## 6. Testing

- **Unit tests** — per-peripheral `#[cfg(test)]` modules in each `peripherals/<name>.rs`. Drive the peripheral directly via its `read32`/`write32`/`tick` API. No mocks. No bus stand-in.
- **Silicon oracle** — `silicon_periph_diff_rp2040` is the load-bearing oracle. Each new peripheral ships with ≥3 scenarios before it's called done. Scenarios are static `PeriphScenario` arrays, same as RP2350.
- **Integration smoke** — pick 1–2 representative pico-sdk examples per phase (e.g. `hello_timer` for Phase 1, `uart/hello_uart` for Phase 2) and run to a known checkpoint. Track in `wrk_journals/`.
- **Regression guard** — existing unit tests in `crates/mdrp2040/src/tests.rs` and `pio_tests.rs` stay green through every phase.

## 7. Risks & open questions

- **SysTick timing resolution** on `silicon_periph_diff_rp2040`: 24 bits at 125 MHz = ~134 ms window. Expected to be sufficient; if a scenario needs finer granularity, fall back to a PIO counter (uses a subsystem we already trust). Noted but not pre-built.
- **Per-cycle tick cost**: generalising to N stateful peripherals runs their `tick` every cycle. PIO's fast-path idle skip exists; other peripherals don't get one in V1. If benchmarking after Phase 3 shows material CPU-step regression, add per-peripheral `is_active()` gates. Not speculative work up front.
- **DMA is the hardest phase.** DREQ handshake with PIO — which has its own tick path and FIFO timing — is where the interaction is thorniest. If Phase 4 slips, UART/SPI/I2C are usable without DMA for firmware that polls; the firmware-blocker list just shrinks more slowly.
- **Interrupt ordering** between core 0 and core 1 when both have the same IRQ enabled: our forwarder asserts to both NVICs the same cycle. Real silicon is the same — they race. Single-threaded interleave in the emulator means core 0 always services first; unlikely to matter for SDK firmware which typically enables a given peripheral IRQ on one core only, but worth noting.
