# Threaded Dual-Core Emulation

Version: 1.0.0
Date: 2026-04-14

## Problem

Dual-core paced throughput on a 3 GHz host: **73.8 MHz (49% of target)**.
Single-core is 143.8 MHz (96%). The 2.5x gap comes from sequentially
executing both cores in a single host thread — doing 2x the work per
emulated cycle with one set of host cycles to spend.

Neither PGO nor inline annotations move the needle meaningfully; the
interpreter is already near its single-threaded ceiling. The structural
problem is that we have a multi-core host and we're only using one.

## Solution

Add a threaded execution mode. Each emulated core gets its own host
thread. A coordinator thread drives quantum barriers and the Pacer.
Single-threaded lockstep mode is retained as the cycle-accurate
reference used for validation against real silicon.

```
┌──────────────────────────────────────────────────────────────┐
│                    Coordinator thread                         │
│  - owns Pacer (rdtsc calibration, quantum target)             │
│  - holds barrier state                                        │
│  - spin-waits to meet real-time                               │
│  - handles WFI/WFE wake + timer tick                          │
└──────────────┬──────────────────────────────┬────────────────┘
               │                              │
               │ Arc<Barrier>                 │ Arc<Barrier>
               │ Arc<SharedState>             │ Arc<SharedState>
               │                              │
   ┌───────────▼───────────┐      ┌──────────▼───────────┐
   │  Core 0 thread        │      │  Core 1 thread       │
   │                       │      │                      │
   │  for Q cycles:        │      │  for Q cycles:       │
   │    decode + execute   │      │    decode + execute  │
   │    mem via atomics    │      │    mem via atomics   │
   │    peripherals via    │      │    peripherals via   │
   │      Mutex            │      │      Mutex           │
   │  wait on barrier      │      │  wait on barrier     │
   └───────────────────────┘      └──────────────────────┘
```

## Non-goals

- **No hybrid mode.** Pure single-threaded OR pure threaded — no
  dynamic switching mid-run, no "threaded for cores but single for bus".
- **No per-cycle bus contention modeling in threaded mode.** Accept the
  accuracy loss (documented below). Real firmware uses DMB/DSB/SIO
  spinlocks for cross-core ordering, which we honor.
- **No configurable thread count.** We have 2 emulated cores, period.
  3 host threads total (2 workers + coordinator).
- **No env vars, no feature flags.** Mode selected via which method the
  caller invokes.

## Design

### 1. Two entry points on `Emulator`

```rust
impl Emulator {
    /// Single-threaded lockstep. Cycle-accurate. Reference for validation.
    pub fn run(&mut self, cycles: u64) -> u64 { ... existing ... }

    /// Threaded: two worker threads, quantum-barrier synchronized.
    /// Blocks until duration elapses. Pacer drives real-time.
    pub fn run_threaded(&mut self, pacer: &mut Pacer, duration: Duration);
}
```

Caller picks. `paced_bench --threaded` chooses which.

### 2. Shared state layout

The current `Emulator` owns `[CortexM33; 2]`, `Bus`, `Sio`, `Clock`.
Threaded mode splits this into:

```rust
struct ThreadedState {
    /// Per-core state: owned by each worker thread.
    /// The thread moves its CortexM33 in at spawn, out at join.
    cores: [CortexM33; 2],  // split between threads at spawn

    /// Shared memory backing. Atomic bytes, Relaxed ordering.
    /// Both threads access concurrently without locks.
    memory: Arc<SharedMemory>,

    /// Peripheral registers + state. Mutex-wrapped — rare access.
    peripherals: Arc<Mutex<Peripherals>>,

    /// SIO (FIFOs, spinlocks, doorbells): lock-free inter-core channels.
    sio: Arc<ThreadedSio>,

    /// Quantum barrier: both worker threads + coordinator sync here.
    barrier: Arc<QuantumBarrier>,

    /// Master clock: single AtomicU64, advanced by coordinator.
    clock_cycles: Arc<AtomicU64>,
}
```

### 3. Memory model

Back SRAM (and ROM, XIP) with `[AtomicU8]` wrapped in `Arc`. Access
via `Relaxed` ordering. On x86, aligned atomic loads/stores are
single `mov` instructions — zero overhead versus plain memory.

```rust
pub struct SharedMemory {
    sram: Box<[AtomicU8]>,
    rom: Box<[u8]>,           // read-only, no atomics needed
    xip: Box<[AtomicU8]>,
}

impl SharedMemory {
    pub fn read16(&self, addr: u32) -> u16 {
        // Two AtomicU8 loads, combine
        let lo = self.sram[addr as usize].load(Relaxed);
        let hi = self.sram[(addr + 1) as usize].load(Relaxed);
        u16::from_le_bytes([lo, hi])
    }

    pub fn write16(&self, addr: u32, val: u16) {
        let [lo, hi] = val.to_le_bytes();
        self.sram[addr as usize].store(lo, Relaxed);
        self.sram[(addr + 1) as usize].store(hi, Relaxed);
    }
    // ... read32/write32 similar
}
```

**Accuracy note:** multi-byte reads are NOT atomic snapshots. Core 0
writing a u32 while core 1 reads it can produce torn values. This
matches a relaxed memory model; firmware that needs ordering uses
DMB/DSB, which we translate to host `fence(AcqRel)`. This is the same
model ARMv8-M specifies at the architectural level.

### 4. SIO redesign

Current SIO stores FIFOs as plain `VecDeque` accessed via `&mut`.
Threaded version uses lock-free data structures:

```rust
pub struct ThreadedSio {
    /// Core 0 → Core 1 FIFO (hardware has a separate FIFO each way)
    fifo_01: crossbeam_queue::ArrayQueue<u32>,
    /// Core 1 → Core 0 FIFO
    fifo_10: crossbeam_queue::ArrayQueue<u32>,
    /// Spinlock registers: 32 hardware spinlocks
    spinlocks: [AtomicU32; 32],
    /// Doorbells, interp, etc.
    ...
}
```

Pulls in `crossbeam` as a new dependency (single-header, no_std-compatible).

### 5. Peripheral access via Mutex

UART, SPI, I2C, PWM, ADC, etc. have side-effect logic on register
writes. Wrap the peripheral subsystem in a `Mutex`. Cores acquire
the lock briefly per peripheral access.

Peripheral writes are rare (maybe 1-5% of memory accesses in typical
firmware). Lock overhead is ~20-50ns uncontended on x86 — acceptable
for this access frequency.

If profiling later shows peripheral lock contention, we can shard
(e.g., one mutex per peripheral block) or move peripherals to the
coordinator thread with a message queue.

### 6. Quantum barrier protocol

```
Coordinator                  Worker 0             Worker 1
───────────                  ────────             ────────
pacer.begin_quantum()
signal "go" ────────────────►  run Q cycles ─────► run Q cycles
                                   │                    │
                                   ▼                    ▼
                             arrive at barrier    arrive at barrier
                                   │                    │
◄──────── signal "done" ───────────┴────────────────────┘
pacer.end_quantum()
  (spin-wait to meet real-time)
  advance clock_cycles by Q
  handle cross-core events
  (WFI wake, timer ticks)
loop
```

Implementation: `std::sync::Barrier::new(3)` — blocks until all 3
threads hit it. Simple and works.

Wait cost per quantum: two atomic fetches + a futex wait/wake. With
Q=150 cycles per quantum, barrier overhead per emulated cycle is
~50ns / 150 = 0.33ns. Acceptable.

### 7. Pacer integration

Coordinator thread owns the Pacer. `begin_quantum()` → signal workers
→ wait for barrier → `end_quantum()` (spin-wait). Workers know
nothing about wall time. Clean separation.

### 8. Thread lifecycle

`run_threaded()` takes `&mut self`, spawns the two worker threads,
runs, joins, restores state:

```rust
pub fn run_threaded(&mut self, pacer: &mut Pacer, duration: Duration) {
    let state = self.split_for_threaded();       // move fields into Arc<>
    let (core0, core1) = state.spawn_workers();  // std::thread::spawn
    state.coordinator_loop(pacer, duration);     // runs on caller's thread
    let (c0, c1) = state.join_workers(core0, core1);
    self.reassemble_from_threaded(state, c0, c1); // move back into self
}
```

After return, `Emulator` is back to single-threaded state and
subsequent `run()` calls work normally. No persistent thread pool.
Start cost: ~100 µs (2x `thread::spawn`). Amortized over seconds of
execution, negligible.

## Accuracy trade-off

**Single-threaded (reference, unchanged):**
- Per-cycle bus contention modeled exactly
- Cycle counts match real silicon bit-for-bit for differential testing
- Used by `qemu_diff`, `probe_diff`, `bank_conflict_test`

**Threaded:**
- No bus contention modeling (cores run independently within quantum)
- Cycle count may drift by up to 1 quantum per contended access
- Functional behavior (memory contents, GPIO output, register state
  at SIO sync points) identical to real hardware — DMB/DSB enforce
  visible ordering
- Used for real-time execution (downstream integration)

This is the same trade-off QEMU made with MTTCG. They abandoned cycle
accuracy for performance. We keep both modes, use each for what it's
best at.

## Validation strategy

1. **Existing single-threaded tests continue to pass.** No changes
   to `run()` or `step()`. The 2500+ existing tests are unaffected.

2. **New threaded-mode integration tests.** Run a small firmware
   that exercises both cores (dual-core SIO FIFO ping-pong, spinlock
   test, shared memory write/read-back). Assert final memory state
   and FIFO state match expected values.

3. **Dual-run differential test.** Run the same firmware in both
   single-threaded and threaded modes. At SIO sync points, assert
   both cores' observable state (registers, memory at defined
   addresses) matches. Cycle counts will differ — only compare
   state at sync points.

4. **Manual: `paced_bench --dual-core --threaded`.** Must show
   ≥100 MHz actual (up from current 73.8 MHz). 150 MHz would be
   the stretch goal.

## Implementation phases

Each phase is a reviewable commit. Build + test pass at each phase.

**Phase 1: Shared memory abstraction.** Introduce `SharedMemory`
with AtomicU8 backing. Single-threaded `Bus` wraps an
`Arc<SharedMemory>` (keeps current behavior). No threading yet. All
existing tests still pass.

**Phase 2: Threaded SIO.** Replace current Sio internals with
`ThreadedSio` (crossbeam queues, AtomicU32 spinlocks). Used in
both single-threaded and threaded modes.

**Phase 3: `run_threaded()` minimal viable.** Spawn threads, sync
barrier, no Pacer integration yet. Hard-coded duration. Proves
the core mechanism works.

**Phase 4: Pacer integration.** Coordinator thread drives Pacer.
Real-time execution in threaded mode.

**Phase 5: Benchmark and tune.** Run `paced_bench --threaded` with
both cores active. Measure. Adjust quantum size if barrier overhead
dominates.

## Risks

1. **Peripheral Mutex contention.** If hot — and some peripherals
   may be (PWM regs polled by both cores) — we shard or move to
   coordinator. Defer until profiled.

2. **crossbeam dependency.** Adds a dependency to the core crate.
   Trade-off for clean lock-free queues. Alternative: hand-roll
   SPSC ring buffer (~100 lines).

3. **Thread affinity.** Worker threads ideally pin to specific host
   cores (different from the coordinator's). On Windows, use the
   same raw FFI we added to `paced_bench`. Add to `run_threaded()`.

4. **Race-safety audit.** Every memory access in `execute.rs` /
   `execute_thumb32.rs` / `execute_fpu.rs` needs to go through
   `SharedMemory`. One missed path = data race = UB. The type
   system helps (Bus no longer has `&mut [u8]`) but we still need
   careful review.

## What this does NOT do

- No JIT — still an interpreter. Threading multiplies the interpreter's
  output by 2x; JIT would be 5-10x multiplicatively.
- No cross-thread cache simulation — we don't model L1 I-cache on real
  cores, and we don't model it between host threads either.
- No dynamic quantum sizing — one fixed value from the Pacer.
- No graceful thread crash recovery — panic in a worker panics the
  process. Matches existing single-threaded behavior.
