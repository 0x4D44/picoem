## 1. Purpose

The fixture-generalization work got fire-24-a clean and built a structurally
correct fire-32-a SeaBIOS byte-correctness binary. The remaining blocker is
not the fixture parser. It is the PIO serving oracle and PIO pin model still
assuming the old fire-24-a shape:

- `ServingOracle` matches a stimulus push with `hi16 == 0x2000` and
  `low16 == expected_pin_bits`.
- `expected_pin_bits` is a `u16`, so any stimulus bit above GPIO15 is lost.
- `picoem-common::pio::PioBlock` receives only a 32-bit `gpio_in` sample.
  It does not model the RP2350 PIO `GPIOBASE` register, so PIO cannot see
  a physical window such as GPIO16..47.

fire-32-a needs PIO1 to read an address window spanning GPIO16..34. Per the
RP2350 SDK and PAC docs, an RP2350 PIO instance still operates on a 32-pin
window; `GPIOBASE` chooses whether PIO-local pin 0 maps to physical GPIO0 or
physical GPIO16. The clean fix is therefore not a 64-bit PIO state machine.
It is:

1. Model `GPIOBASE` as a per-`PioBlock` base of 0 or 16.
2. Let RP2350 pass a 48-bit physical GPIO sample to each PIO block, and let
   the block project that sample into its 32-bit PIO-local window.
3. Replace the oracle's hardcoded `hi16/low16` predicate with an expected
   resolved-address predicate derived from the fixture's address-pin window.

No feature flags, no environment variables, no compatibility layer for the
old evaluator. We are in a development sandbox and should replace the wrong
shape outright.

## 2. Non-goals

- Do not write a general OneROM fixture framework.
- Do not sniff arbitrary PIO bytecode to infer every possible address
  assembly program. The two in-tree fixtures are enough to derive the needed
  PIO address window from `FixtureSpec`.
- Do not widen PIO shift registers, FIFOs, `X`, `Y`, `ISR`, or `OSR` to
  `u64`. Hardware PIO data paths are still 32-bit; only the physical GPIO
  namespace is wider.
- Do not add CLI switches, environment variables, or cargo features for old
  vs new behavior.
- Do not attempt live fire-32-a silicon validation in this change. This HLD
  is emulator/oracle correctness only.
- Do not support a future fixture that needs one PIO instance to touch both
  physical GPIO0..15 and GPIO32..47. RP2350 hardware cannot do that in one
  PIO instance either.

## 3. Current Failure Mode

The current smoke result for `seabios32_fixture_byte_correct` is about:

```
PASS=1024 / NoResolve=3072 out of 4096 servable smoke cases
```

The PASS cases are those where the old 16-bit assumptions happen to be enough.
Failures begin when a fire-32 address bit above the old low-16 matcher becomes
part of the resolved address.

The existing evaluator logic is:

```
expected_pin_bits = (stim_level & 0xFFFF) as u16
hi16 = resolved >> 16
low16 = resolved & 0xFFFF

if hi16 != 0x2000 || low16 != expected_pin_bits {
    continue; // not this case's push
}
```

That exactly matches fire-24-a's `IN X, 16; IN PINS, 16` program shape:

```
resolved = (0x2000 << 16) | low16(stim)
```

fire-32-a is different. Its address stimulus is in the PIO-local GPIOBASE=16
window, and the expected resolved address is:

```
resolved = SHADOW_BASE | pio_window_bits(stim, base=16, count=19)
```

So the evaluator needs to match the whole expected resolved address, not a
fixed `hi16` plus truncated low half.

## 4. Design Summary

### 4.1 PIO GPIOBASE

Add a `gpio_base: u8` field to `picoem_common::pio::PioBlock`.

Rules:

- Reset/default: `0`.
- Register offset `0x168` reads the current base.
- Register offset `0x168` writes only bit 4, so stored values are `0` or
  `16`.
- Alias writes should use the same read-modify-write helper as other stored
  PIO registers, then mask back to bit 4. This keeps the register consistent
  with the rest of `PioBlock::write32`.

Keep `StateMachine` internals 32-bit. `PioBlock` owns the physical-to-local
projection:

```rust
impl PioBlock {
    pub fn step(&mut self, gpio_in: u32) {
        self.step_with_pins(gpio_in as u64);
    }

    pub fn step_n(&mut self, n: u32, gpio_in: u32) {
        self.step_n_with_pins(n, gpio_in as u64);
    }

    pub fn step_with_pins(&mut self, gpio_pins: u64) {
        let local = self.local_gpio_window(gpio_pins);
        // existing per-SM execute path, still passing a u32
    }

    pub fn step_n_with_pins(&mut self, n: u32, gpio_pins: u64) {
        for _ in 0..n {
            self.step_with_pins(gpio_pins);
        }
    }

    fn local_gpio_window(&self, gpio_pins: u64) -> u32 {
        ((gpio_pins >> self.gpio_base) & 0xFFFF_FFFF) as u32
    }
}
```

This keeps RP2040 and existing direct `PioBlock::step(u32)` tests simple, while
letting RP2350 pass the full physical pin state when it has one.

### 4.2 Physical PIO Pad Mapping

`PioBlock::pad_out` and `pad_oe` stay 32-bit PIO-local words. RP2350 GPIO merge
must map them back to physical pins before combining SIO, PIO, and external
stimulus.

Add helpers on `PioBlock` or a private helper in `rp2350-emu`:

```rust
fn map_pio_local_to_physical(local: u32, gpio_base: u8) -> (u32, u32) {
    match gpio_base {
        0 => (local, 0),
        16 => (local << 16, local >> 16),
        _ => unreachable!("GPIOBASE stores only 0 or 16"),
    }
}
```

Use the same mapping for `pad_out` and `pad_oe`.

This matters beyond the current input bug. PIO2 still drives fire-32-a data
pins with base 0, but once `GPIOBASE` is modeled it would be wrong to leave
PIO outputs implicitly physical-low for every block.

### 4.3 RP2350 GPIO Input State

Add a high-bank companion to `Bus::gpio_in`:

```rust
pub gpio_in_hi: AtomicU32, // bit i = physical GPIO32+i, low 16 bits used
```

Serial `Emulator::update_gpio` becomes a two-bank merge:

1. Start with low SIO output (`sio.gpio_out & sio.gpio_oe`) and high output 0.
   The current SIO high output model is not needed for this change.
2. For each PIO block, map its local `pad_out/pad_oe` into physical low/high
   masks using `gpio_base`.
3. Overlay low external stimulus into `gpio_in`.
4. Overlay high external stimulus into `gpio_in_hi`.

`tick_peripherals` passes both halves to PIO:

```rust
let pins = (bus.gpio_in.load(Relaxed) as u64)
    | ((bus.gpio_in_hi.load(Relaxed) as u64) << 32);
pio.step_n_with_pins(cycles, pins);
```

`read_gpio_hi_in` continues to return the firmware-visible SIO high-input word:
GPIO32..47 in bits 0..15 plus the existing QSPI/USB noise behavior in the upper
bits. It should use `gpio_in_hi` for the low 16 bits and keep the existing
external-stimulus overlay behavior so direct harness reads remain unsurprising.

### 4.4 Threaded RP2350 Mirror

The threaded runtime needs the same model, not a serial-only fix:

- Add `in_hi: AtomicU32` to `threaded::gpio::AtomicGpio`.
- Seed it from `Bus::gpio_in_hi` during `ThreadedEmulator::from_emulator`.
- Add `read_in_hi`, `write_in_hi`, and `read_in64` helpers.
- The PIO worker calls `block.step_n_with_pins(step_q, shared.gpio.read_in64())`.
- The coordinator `update_gpio` computes and publishes both low and high banks.
- `WorkerBus::GPIO_HI_IN` reads low 16 bits from `in_hi`, plus existing
  high-register noise/external behavior.

The OneROM byte-correctness binary uses Serial, but this workspace treats
threaded parity as part of the RP2350 contract. Mirroring the high-bank path
now is cheaper than debugging a later dual-model divergence.

### 4.5 Fixture-Derived Address Shape

Do not parse PIO bytecode for Stage 4. It adds complexity and does not buy us
anything for the two fixtures we have.

Add a small harness-only value in `onerom_serving_oracle.rs`:

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct PioAddressShape {
    gpio_base: u8,  // 0 or 16
    pin_count: u8,  // fire-24-a: 16, fire-32-a: 19
}
```

Derive it from `FixtureSpec::addr_pins`:

```rust
impl PioAddressShape {
    fn from_fixture(spec: &FixtureSpec) -> Result<Self, ShapeError> {
        let max_gpio = spec
            .addr_pins
            .iter()
            .copied()
            .max()
            .ok_or(ShapeError::NoAddressPins)?;
        let gpio_base = if max_gpio >= 32 { 16 } else { 0 };

        // Hardware rule: one PIO instance can only see base..base+31.
        for &pin in &spec.addr_pins {
            if pin < gpio_base || pin >= gpio_base + 32 {
                return Err(ShapeError::PinsCrossPioWindow);
            }
        }

        let max_local = max_gpio - gpio_base;
        Ok(Self {
            gpio_base,
            pin_count: max_local + 1,
        })
    }

    fn expected_resolved_addr(&self, stim_level: u64) -> u32 {
        let mask = if self.pin_count == 32 {
            u32::MAX as u64
        } else {
            (1u64 << self.pin_count) - 1
        };
        let pio_bits = (stim_level >> self.gpio_base) & mask;
        SHADOW_BASE | pio_bits as u32
    }
}
```

This deliberately matches what the PIO address program consumes, not the
chip-internal address index. For fire-24-a, `pin_count=16`, so this reproduces
the old `SHADOW_BASE | low16(stim)` predicate. For fire-32-a, `gpio_base=16`
and `pin_count=19`, so it matches the 19-bit PIO-local address window.

If a future fixture has address pins outside a single RP2350 PIO window, reject
it loudly. The hardware cannot serve that fixture with one PIO instance either.

### 4.6 Evaluator Predicate

Replace `expected_pin_bits: u16` with `expected_resolved_addr: u32`.

Current:

```rust
fn evaluate_case_trace(..., expected_pin_bits: u16, trace: &[Observation])
```

Target:

```rust
fn evaluate_case_trace(
    case: Case,
    shadow: &[u8],
    shadow_size: usize,
    expected_resolved_addr: u32,
    trace: &[Observation],
) -> CaseResult
```

Then the push scanner is just:

```rust
if obs.resolved_addr != expected_resolved_addr {
    continue;
}
```

After a matching push, keep the existing shadow-range validation:

```rust
if !(SHADOW_BASE..SHADOW_BASE + shadow_size as u32).contains(&resolved) {
    return ResolvedAddrOutOfRange { addr: resolved };
}
```

This preserves the Stage G state machine: gap pushes are skipped, stability is
anchored after the matching push, and latency/envelope behavior is unchanged.
Only the definition of "this case's push" changes.

## 7. Acceptance Criteria

This change is complete only when all of these are true:

1. `seabios32_fixture_byte_correct --smoke` has no `NoResolve` cases among
   servable fire-32-a cases.
2. Full fire-32-a sweep reports all 262144 servable cases as PASS.
3. Existing fire-24-a SeaBIOS byte-correctness remains `pass=131072 / wrong=0`.
4. `cargo fmt`, `cargo clippy`, `cargo test -q`, and
   `cargo test -q --features threading` pass.
5. The old `hi16 == 0x2000` predicate is gone from
   `onerom_serving_oracle.rs`.
6. The partial-state warning in the fire-32-a binary is removed or replaced
   with a normal status header.

## 8. Risks

1. **GPIOBASE output mapping could expose old hidden assumptions.** Existing
   PIO output paths implicitly treat `pad_out/pad_oe` as physical low-bank
   masks. Mapping through `GPIOBASE` is correct, but tests around PIO output
   merge are required so the change is not input-only.

2. **Threaded parity has more moving pieces than the serial path.** The serial
   path is what the oracle uses, but leaving threaded low-only would create a
   future surprise. Keep the threaded change mechanical and test it directly.

3. **Fixture-derived shape assumes `IN_BASE=0` in the address PIO program.**
   That is true for the current fire-24-a and fire-32-a fixtures. If a later
   fixture uses a nonzero PIO `IN_BASE`, Stage 4 should fail with a clear
   mismatch rather than guessing. Do not solve that future fixture now.

4. **Full sweep runtime may be longer after the oracle starts resolving all
   cases.** The existing `--smoke` mode remains the development loop. Full
   sweep is the acceptance gate.

5. **Official RP2350 docs allow only GPIOBASE 0 or 16.** If the emulator sees
   any other value after alias writes, that is our bug. Mask to bit 4 and add
   a unit test.

## 9. Rejected Alternatives

### Bytecode Sniffer

Rejected for Stage 4. It would inspect PIO instruction memory, reconstruct
`IN X, N; IN PINS, M`, and build the matcher from that. That is more flexible
than we need and easier to get subtly wrong. The fixture pin map already tells
us which physical PIO window the address pins occupy.

### Widen PIO Internals to u64

Rejected. RP2350 has 48 physical GPIOs, but each PIO instance still operates
on a 32-pin window and the PIO registers/FIFOs/shift registers are 32-bit.
Widening everything would be both less accurate and more invasive.

### Fire-32-Specific Special Case in the Oracle

Rejected. Hardcoding "if chip_pins == 32 then base 16, count 19" would work
today but would preserve the same class of fixture-shaped bug we are fixing.
Deriving the shape from `FixtureSpec.addr_pins` is just as small and cleaner.

### Feature Flag or Environment Variable

Rejected. There is no reason to keep the wrong evaluator selectable.
