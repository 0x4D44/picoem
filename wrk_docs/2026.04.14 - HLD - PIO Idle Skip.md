# PIO Idle Skip

Version: 1.0.0
Date: 2026-04-14

## Problem

The basic `paced_bench_rp2350` workload (tight MOVS/ADDS/B loop, no PIO
activity whatsoever) runs at ~38 MHz paced on this 3 GHz host. A targeted
regression sweep across `7fa669a..512eae8` (see journal entry 2026-04-14 —
Performance Investigation) localised the bulk of the 112 MHz → 35 MHz
Phase 1-3 → Phase 6 regression to two commits:

| Commit | Subject | Δ paced MHz |
|---|---|---|
| `94c43ac` | Phase 6 Stage B: PIO clock divider + executor | **−48.6 (−50%)** |
| `b59859f` | Phase 6 Stage C: autopush/autopull + GPIO merge | **−16.3 (−34%)** |

The root cause sits in `crates/mdpicoem-common/src/pio/mod.rs`:

```rust
pub fn step(&mut self, gpio_in: u32) {
    for i in 0..4 {
        if self.sm[i].clock_tick() {
            self.sm[i].execute_cycle(&self.instr_mem, &mut self.irq_flags, gpio_in);
        }
    }
    self.merge_pin_outputs();
}

pub fn step_n(&mut self, n: u32, gpio_in: u32) {
    for _ in 0..n {
        self.step(gpio_in);
    }
}
```

Per emulated cycle, across three PIO blocks, the Emulator does:

- 3 × 4 `clock_tick()` calls — even when no SM is enabled
- 3 × `merge_pin_outputs()` walks — each iterating all 4 SMs

That is ~24 SM-level operations per emulated cycle of pure overhead on
workloads that never touch PIO at all. The code even admits this in the
`step_n` doc comment: *"A bulk-advance optimisation is future work if PIO
appears hot in a flamegraph."*

## Proposed change

Cache which SMs are enabled on the `PioBlock`, and early-return from
`step` / `step_n` when the cache says "none". No behaviour change — just
skipping work that provably cannot produce side effects.

The skip is a strict semantic no-op, not an approximation:
`StateMachine::clock_tick()` already short-circuits on `!self.enabled`
(`sm.rs:141`) without advancing the clock divider accumulator or any
other SM state, and `merge_pin_outputs` already `continue`s past
disabled SMs. When the mask is zero, the per-cycle loop body does
nothing observable. The fix is therefore not *changing* what happens
when all SMs are disabled — it is *not calling into the loop in the
first place*.

### Invariant

`PioBlock::sm_enabled_mask: u8` has bit `i` set iff `sm[i].enabled == true`.
The mask is maintained by routing every enable/disable through
`PioBlock::set_sm_enabled(i, bool)`. Direct writes to `sm[i].enabled` are
removed.

The mask is **deliberately redundant** with `sm[i].enabled`. The SM field
remains authoritative for all existing queries (the public getter
`StateMachine::enabled`, the `merge_pin_outputs` filter, chip-side
debug UI reads). The mask exists only for the single-load fast-path
check at the head of `step` / `step_n`. A reviewer should not
"deduplicate" by computing it on-the-fly — the whole point is to avoid
a four-SM iteration on every quantum.

### New field + helper on `PioBlock`

```rust
pub struct PioBlock {
    pub sm: [StateMachine; 4],
    // ... existing fields ...
    sm_enabled_mask: u8,
}

impl PioBlock {
    pub fn set_sm_enabled(&mut self, i: usize, enabled: bool) {
        let prev = self.sm[i].enabled;
        if prev == enabled {
            return;
        }
        self.sm[i].enabled = enabled;
        if enabled {
            self.sm_enabled_mask |= 1 << i;
        } else {
            self.sm_enabled_mask &= !(1 << i);
        }
        // Any enable-state transition can change which SMs contribute
        // pin bits — re-merge once now so that the fast-path skip in
        // `step` is safe (steady state: no SM enabled ⇒ no changes ⇒
        // skip is a no-op). In particular this clears a just-disabled
        // SM's stuck pin bits.
        self.merge_pin_outputs();
    }

    pub fn reset(&mut self) {
        for sm in &mut self.sm {
            sm.reset();     // sets sm.enabled = false via *self = Self::new()
        }
        self.instr_mem = [0; 32];
        self.irq_flags = 0;
        // ... existing field resets ...
        self.sm_enabled_mask = 0;  // NEW — keep the mask invariant across reset
    }
}
```

`PioBlock::reset` bypasses `set_sm_enabled` (it blanks each SM via
`StateMachine::reset`, which is a whole-struct re-init). The explicit
`self.sm_enabled_mask = 0;` at the end of `reset` keeps the invariant
intact. `pad_out` / `pad_oe` are already cleared by existing code in
`reset`, so a transition-time merge is unnecessary here.

### Guarded `step` / `step_n`

```rust
pub fn step(&mut self, gpio_in: u32) {
    if self.sm_enabled_mask == 0 {
        return;
    }
    for i in 0..4 {
        if self.sm[i].clock_tick() {
            self.sm[i].execute_cycle(&self.instr_mem, &mut self.irq_flags, gpio_in);
        }
    }
    self.merge_pin_outputs();
}

pub fn step_n(&mut self, n: u32, gpio_in: u32) {
    if self.sm_enabled_mask == 0 {
        return;
    }
    for _ in 0..n {
        self.step(gpio_in);
    }
}
```

The `step_n` guard avoids `n` redundant checks when the block is idle
(the common case on this bench). When at least one SM is enabled, the
per-`step` guard still fires but is trivially branch-predicted and
costs <1 host cycle amortised.

### Call-site migration

Four production sites in the PIO `CTRL` register-write handler (same
file, `write_ctrl` around lines 359 / 366 / 374 / 382 — one per
alias: normal / XOR / SET / CLR) currently write
`self.sm[i].enabled = ...` directly. These are replaced with
`self.set_sm_enabled(i, ...)`. A single CTRL write can therefore call
`set_sm_enabled` up to four times, each of which may run
`merge_pin_outputs` on a transition — acceptable overhead because
CTRL writes are rare (firmware configuration, not per-cycle) and
`merge_pin_outputs` is cheap; not worth a batched variant.

`SM_RESTART` and `CLKDIV_RESTART` handlers in the same function do
not touch `enabled`, so the mask invariant is preserved across
restart writes without further changes.

Nine test sites in the `pio/mod.rs` tests module write
`pio.sm[i].enabled = true` (or `= false`) directly (lines 503, 674,
704, 720, 735, 753, 830, 1063, 1069). These migrate to
`set_sm_enabled`. Without the migration these tests bypass the mask
and the fast-path skip would incorrectly fire during the test run.

`crates/mdrp2350/src/pio_tests.rs` and
`crates/mdrp2040/src/pio_tests.rs` contain no direct `.enabled = ...`
writes — only read-side `.enabled()` getter calls. Those are
unaffected by this change and require no migration.

## What does NOT change

- `StateMachine::enabled` visibility stays `pub(crate)`. No API
  visibility change on the SM side.
- `merge_pin_outputs` body is unchanged. It's called on every
  enable/disable transition and from the non-idle `step` — same as
  before.
- `Bus`, `Emulator::step`, `tick_peripherals`, and `update_gpio` are
  unchanged. No Bus-level "any PIO active" flag — the per-block
  early-return already makes the `for pio in &mut self.bus.pio` loop
  effectively free when all three blocks are idle.
- No chip-crate code changes outside of test-site migrations. Both
  `mdrp2350` and `mdrp2040` consume `mdpicoem-common::PioBlock`
  unchanged.
- No new public API beyond `set_sm_enabled`. No env vars, no feature
  flags, no conditional compilation.

## New tests

Added to `crates/mdpicoem-common/src/pio/mod.rs` tests module:

1. **`idle_block_step_is_noop`** — construct a fresh `PioBlock` (no
   SMs enabled), call `step_n(1000, 0)`, assert `pad_out == 0 &&
   pad_oe == 0` and that no SM's `pc` or `clock_acc` advanced. Proves
   the fast path is semantically a no-op.

2. **`disable_clears_pin_outputs`** — `set_sm_enabled(0, true)`, poke
   `pio.sm[0].pin_values = 0x1` and `pio.sm[0].pin_dirs = 0x1`
   (`pub(crate)` fields; test-only to avoid running a program),
   call `step(0)` once to propagate via `merge_pin_outputs` (assert
   `pad_out & pad_oe != 0`), then `set_sm_enabled(0, false)` and
   assert `pad_out == 0 && pad_oe == 0` on the same tick. Proves the
   pin-state-cleanup rule on the disable transition.

Existing PIO tests still pass after call-site migration.

## Success criteria

1. `cargo test -p mdrp2350 -p mdpicoem-common --release` green,
   including the two new tests.
2. `cargo build --release --workspace` warnings-clean.
3. `paced_bench_rp2350 --seconds 5` (release, no PGO) — `Avg MHz`
   moves from the current ~38 to ≥ 80. Paced mode matches the
   original Paced Benchmark journal methodology and the regression
   sweep comparator, so apples-to-apples. Projection from the sweep
   data is ~90 MHz: commits `94c43ac` (−48.6) and `b59859f` (−16.3)
   account for a combined 64.9 MHz tax at the Phase 6 measurement
   point, and the fix skips the per-cycle work they added when no SM
   is enabled (always true on the basic bench workload). ≥ 80 MHz is
   the commit-go gate; > 90 MHz is a happy surprise.
4. `qemu_diff_m33 --fuzz 1000` — no new diffs. qemu_diff exercises
   instruction-level semantics in SRAM, not peripheral state; this
   change is entirely inside `PioBlock` with no effect on
   fetch/decode/execute. The run is a sanity check that the shared
   `mdpicoem-common` crate still builds and behaves for the CPU path.

## Risks

**Stale pin state after disable.** Mitigated by `set_sm_enabled` calling
`merge_pin_outputs()` on every transition. Test T2 is the specific
regression probe.

**Forgotten call-site migration.** A direct `sm[i].enabled = true` that
slips through leaves `sm_enabled_mask` stale; the fast path then
incorrectly skips a block whose SM is nominally enabled. Symptom:
a PIO integration test that was passing stops firing SM instructions.
Caught by running the full test suite.

**Bulk-advance still naive inside `step_n`.** This HLD does not address
the case where *some* SM is enabled. If PIO ends up active on a future
workload, we still iterate `step()` n times with no per-SM fast path
inside `step`. That optimisation is deliberately out of scope —
bench-driven follow-up only if a flamegraph says so.
