# RP2350 — RISC-V Hazard3 Core Support

**Date:** 2026-04-17
**Crate:** `crates/mdrp2350/`
**Companion audit:** `wrk_docs/2026.04.16 - HLD - RP2350 Feature Coverage Audit.md` §4.1 ("**Missing — RISC-V Hazard3 cores. Zero code.**")

## 1. Goal

Run RP2350 firmware that selects the **Hazard3 RISC-V** alternative cores instead of Cortex-M33. A single `EmulatorBuilder` switch picks the architecture; everything from `Bus` outward is unchanged.

A successful first cut runs an `rv32imac` blinky against `mdrp2350app` and produces the same GPIO transitions as the existing M33 blinky.

## 2. Background

RP2350 ships **two** complete dual-core complexes on the same die:

- **Arm path** — 2× Cortex-M33 (ARMv8-M Mainline, FPU, TrustZone). Already implemented.
- **RISC-V path** — 2× Hazard3 (RV32IMACB_Zicsr_Zifencei, M+U mode, custom external IRQ controller). Not implemented.

Selection is by OTP fuse + POWMAN at chip power-up; only one complex runs at a time. The two paths share **Bus, SIO, peripherals, clocks, DMA, PIO, memory map** — they differ only in the CPU core and a small amount of CPU-adjacent state (PPB region for Arm, RVCSRs for Hazard3). The SIO side already exposes the RISC-V observables: `RISCV_SOFTIRQ`, `MTIME`/`MTIMECMP` (`crates/mdrp2350/src/sio/mod.rs:30-45`).

We do not run the bootrom (CLAUDE.md: `load_image` bypasses it). So **we do not need to model ARCHSEL or the POWMAN-gated handover** — the harness picks the architecture at construction time.

## 3. Non-goals (explicit)

To stay small and avoid overengineering, the following are **out of scope** for this HLD. Each can be added later as its own slice.

- **U-mode privilege enforcement.** Implement M-mode only; U-mode CSR writes / `ecall` from U-mode can be added later.
- **PMP (Physical Memory Protection).** Storage-only or absent. RP2350 PMP is the RISC-V analogue of the Arm MPU/SAU/IDAU work that the audit calls out as "plumbed but not enforced" — same scope decision, same reasoning.
- **Hazard3 debug module / SWD probe.** `probe_diff_riscv_rp2350` is **deferred** — there is no probe-rs RISC-V/Hazard3 attach in the harness today. First-cut validation is unit-test + a thin silicon smoke runner that uses `cargo objcopy`-built binaries staged in flash. (See §9 risks.)
- **Bootrom dispatch.** Not modelled; the chip-arch is a build-time choice on the emulator side.
- **POWMAN ARCHSEL register.** Not modelled.
- **Hazard3-specific power management** (`mintthresh` for WFI wakeup tuning beyond the trivial polling case).
- **Performance counters** beyond `mcycle` and `minstret` (we already have `Clock::cycles` to alias).
- **Fence semantics richer than nop.** Single-host-thread emulation; `fence`/`fence.i` are no-ops.
- **A-extension dual-core reservation precision.** lr/sc tracked on `Bus` as a single-entry reservation per core; the other core's stores invalidate. We never run cores concurrently in the same step (CLAUDE.md: per-quantum serial interleave), so a stronger model buys nothing today.

These exclusions follow the audit's discipline: get the **Verified** column populated for the RISC-V ISA core, then come back for the enforcement-gap items.

## 4. Design

### 4.1 Cores: enum, not trait

```rust
// crates/mdrp2350/src/lib.rs
pub enum Cores {
    Arm([CortexM33; 2]),
    RiscV([Hazard3; 2]),
}

pub struct Emulator {
    pub cores: Cores,         // was: [CortexM33; 2]
    pub bus: Bus,
    pub clock: Clock,
    pub step_quantum: u32,
}
```

Rationale:

- The two architectures are **mutually exclusive** at runtime. We never need a heterogeneous pair — RP2350 silicon doesn't support that.
- Enum dispatch happens **once per quantum** in `Emulator::step` — outside the hot per-instruction path. After the match the inner loop is monomorphic over a homogeneous `[CoreT; 2]`. No `dyn`, no vtable overhead.
- No cross-architecture trait surface to design and maintain. The audit (§5) flagged surface-area growth as a real problem; a `CoreCpu` trait would add a load-bearing abstraction for one new caller. Don't.

`Emulator::step` becomes:

```rust
pub fn step(&mut self) -> u64 {
    self.bus.master_cycle = self.clock.cycles;
    let target = self.clock.cycles + self.step_quantum as u64;
    match &mut self.cores {
        Cores::Arm(cores)   => step_pair(cores, &mut self.bus, target),
        Cores::RiscV(cores) => step_pair(cores, &mut self.bus, target),
    }
    self.clock.advance(self.step_quantum as u64);
    self.tick_peripherals(self.step_quantum);
    self.tick_systick_or_mtimer();
    self.wake_checks();
    self.clock.cycles
}
```

`step_pair` is generic over a private `CoreStep` trait whose only consumers are these two call sites — it's a code-deduplication helper, not a public abstraction. Methods: `is_halted`, `is_wfe_waiting`, `cycles`, `step(&mut Bus)`, plus a `publish_cycles(&mut Ppb)` no-op for RISC-V. The trait stays `pub(crate)`.

### 4.2 Builder

```rust
pub enum Arch { Arm, RiscV }

impl Default for Arch { fn default() -> Self { Arch::Arm } }   // backwards-compatible

EmulatorBuilder::new(Config::default())
    .arch(Arch::RiscV)
    .build()
```

That is the only knob. **No env var, no cargo feature.** Chip-arch is a per-emulator-instance fact, not a workspace-wide compilation choice — multiple test binaries in the same process should be free to mix.

### 4.3 Reset

Per-arch reset path. Arm path is unchanged (loads SP from word 0, PC from word 1). RISC-V path:

- Both cores: PC = `0x0000_0000` (start of bootrom region), all GPRs = 0, `mstatus = 0` (M-mode, MIE off), `mtvec = 0` (firmware sets it), all CSRs zero except hardware-fixed ones (`mvendorid`, `marchid`, `mhartid` per core).
- Per-hart `mhartid` = core index (0 or 1).
- The bus-side reset (RESETS, clocks, peripherals, SIO state) is already arch-agnostic and is reused verbatim.

`load_image` is unchanged. Firmware loaded into SRAM is responsible for setting `sp` and jumping into itself; this matches how the RISC-V SDK's `crt0.S` works.

### 4.4 New module layout

```
crates/mdrp2350/src/core_riscv/
    mod.rs            // Hazard3 struct, step(), reset(), CSR access
    decode.rs         // RV32I + M + A + C decode → Op enum
    execute.rs        // execute(Op, &mut Bus)
    csr.rs            // CSR read/write, including Hazard3 custom
    irq.rs            // External IRQ controller (meiea/meipa/meifa/meipra/meinext/meicontext)
    atomics.rs        // lr.w/sc.w + amo* against Bus
```

The existing `core/` module (M33) is **untouched**. No shared parent type, no shared traits exposed publicly. The two paths sit alongside each other in `lib.rs`:

```rust
pub mod core;          // existing M33
pub mod core_riscv;    // new
pub use self::core::CortexM33;
pub use self::core_riscv::Hazard3;
```

### 4.5 ISA scope (first cut)

| Extension | First cut? | Notes |
|---|---|---|
| RV32I base | **Yes** | All loads/stores, ALU, branches, jal/jalr, lui/auipc, system, fence (nop). |
| M (mul/div) | **Yes** | mul, mulh{,u,su}, div{,u}, rem{,u}. Div-by-zero per RISC-V spec. |
| A (atomic) | **Yes** | lr.w, sc.w, amoswap/add/and/or/xor/min/max{,u}.w. See §4.7. |
| C (compressed) | **Yes** | Required to run any standard rv32imac toolchain output. |
| Zicsr | **Yes** | csrr{w,s,c}{,i} — table-driven CSR dispatch. |
| Zifencei | **Yes** | `fence.i` invalidates the future RISC-V decoded-op cache (no-op for first cut). |
| Zba / Zbb / Zbs / Zbkb (B-ext subsets) | **Defer** | Hazard3 supports these but they are not load-bearing for blinky / pico-sdk-rp2350-rs's RISC-V port. Re-evaluate after first silicon firmware runs. |
| Zcb (extra compressed) | **Defer** | Same. |
| Custom Hazard3 instructions (`h3.bextm`, `h3.bextmi`) | **Defer** | Vendor-specific; nothing in the existing harness needs them. |

This matches the discipline the M33 path used in V1 — boot the chip first, fill in the long tail behind oracles.

### 4.6 Interrupts

Hazard3 has the standard RISC-V machine-mode interrupts (`msip`, `mtip`, `meip`) plus a vendor external IRQ controller exposed via custom CSRs. RP2350 NVIC equivalents:

| Source | RISC-V plumbing | RP2350 backing |
|---|---|---|
| `msip` (software) | `mip.MSIP` | `SIO.RISCV_SOFTIRQ` (already implemented, `sio/mod.rs:30,112,166`) |
| `mtip` (timer) | `mip.MTIP` | `SIO.MTIME` / `MTIMECMP` (already implemented, `sio/mod.rs:36-42`) |
| `meip` (external) | `mip.MEIP`, vectored via `meinext` | The 52 RP2350 NVIC lines (`crates/mdrp2350/src/irq.rs`) |

**The bus's per-core `irq_pending: [u64; 2]` mask is the transport** — peripherals already write into it via `assert_irq_core` / `assert_irq_shared`. This is intentionally arch-agnostic: a bit set means "core N has IRQ M latched," and the consumer decides how to deliver. On Arm, the consumer is the per-core PPB NVIC walk. On RISC-V, the consumer is `core_riscv::irq` reading the same `irq_pending[core]` and exposing it through the Hazard3 `meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` CSR window.

**The PPB region (`0xE000_E000+`) stays inert on RISC-V** — RISC-V firmware never reads it, and if it ever does, the existing storage just round-trips. No code deletion, no conditional plumbing. (This is the cheapest possible coexistence model and the right one for a dev sandbox.)

NMI: Hazard3's NMI source is `meinext`'s NMI bit plus `mintthresh`. First cut: deliver NMI on the same `pending_fault: Some(Fault::Nmi)` channel the M33 already uses for CP7 RCP failures, but route to the RISC-V NMI vector (`mtvec` with NMI cause) rather than the Arm exception #2.

### 4.7 Atomics

Single-host-thread emulation, serial per-quantum interleave (CLAUDE.md "Bank contention model"). The full LR/SC semantics collapse to:

- `Bus` gains `reservation: [Option<u32>; 2]` (per-core address, word-aligned).
- `lr.w` records the address into `reservation[active_core]` and returns the loaded word.
- Any `Bus::write*` to a word-aligned address `a` clears every core's reservation where `reservation[c] == Some(a)`.
- `sc.w` succeeds iff `reservation[active_core] == Some(addr)`; on success it clears the reservation, performs the store, returns 0; on failure it returns 1 and leaves memory untouched.
- `amo*.w` reads, modifies, writes within one bus call — atomic by construction because nothing else is running.

This is enough for `core::sync::atomic` and any pico-sdk-rp2350 spinlock alternative that uses A-extension instead of HW spinlocks.

### 4.8 Decoded-op cache

Skip it. The existing `bus.decode_cache` is M33-shaped (Thumb halfwords). RISC-V starts cache-less; if the perf benchmarks (`paced_bench_rp2350` analogue) show it matters, add `bus.decode_cache_riscv` later as a parallel structure. Don't generalize the existing cache; it's not the abstraction we want.

## 5. What stays unchanged (important for review)

- `Bus`, `Memory`, `Sio`, `Pio`, all peripherals, `ClockTree`, `Pacer`, `Dma`, `irq.rs` line numbers, RESETS layout, `mmio_read32` / `mmio_write32`, MMIO trace format, all existing oracles (`silicon_*`, `qemu_diff_m33`), all existing tests in `mdrp2350/src/tests.rs` and `pio_tests.rs`.
- M33 code (`crates/mdrp2350/src/core/`) — **no edits**. The audit's caution about touching `execute.rs` / `execute_thumb32.rs` while concurrent silicon-coverage work is in flight applies in full.
- Public API of `Emulator` for harness consumers, except:
  - `Emulator::cores` becomes `Cores` enum. Existing call sites (`paced_bench_rp2350`, `silicon_*`, the TUI app) use `cores[0]` indexing — they'll need to migrate to `cores.arm()[0]` (or panic-on-mismatch helpers). Per CLAUDE.md, we're in a dev sandbox: we just update those call sites, no compatibility shim.

## 6. Phasing

Each phase is independently shippable.

**P1 — Skeleton (1 PR).**
- `Cores` enum, `Arch` enum, `EmulatorBuilder::arch`.
- `Hazard3` struct with empty `step()` (returns 1, advances PC by 4). Reset path.
- All existing call sites migrated to the enum. All existing tests still pass.
- Smoke test: build a `Hazard3` emulator, step 100 times, observe `clock.cycles` advance.

**P2 — RV32I + Zicsr decode/execute (1 PR).**
- Full base ISA, CSR table (mstatus, mie, mip, mtvec, mepc, mcause, mtval, mscratch, mhartid, mvendorid, marchid, mimpid, mcycle, minstret, mcountinhibit).
- Trap entry/exit (`ecall`, `mret`, `ebreak`, illegal instruction → `mcause=2`).
- Unit tests per opcode, golden-value style.

**P3 — M, C, A extensions (1 PR).**
- Mul/div per spec.
- Compressed decoder (16-bit forms expand into the same Op enum).
- Atomics with the `Bus::reservation` table.

**P4 — IRQ controller + mtimer wiring (1 PR).**
- Hazard3 `meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` CSRs reading from `bus.irq_pending`.
- mtip from existing `SIO.mtime_match_asserted`.
- msip from existing `SIO.riscv_softirq`.
- Trap dispatch on the same `step()` boundary the M33 uses (`try_take_any_pending_exception` analogue).

**P5 — App integration + smoke firmware (1 PR).**
- `mdrp2350app` TUI: `--arch riscv` flag.
- Build `roms/rp2350/blinky-riscv.bin` from a tiny C source via `riscv32-unknown-elf-gcc -march=rv32imac -mabi=ilp32`. Commit the prebuilt binary alongside the existing `blinky.bin`.
- Smoke test in `crates/mdrp2350/tests/firmware.rs`: load it, run it, assert GPIO toggles within N quanta. Mirrors the mdrp2040app smoke test approach.

**P6 — Silicon harness (deferred, separate HLD).**
- `probe_diff_riscv_rp2350` once probe-rs Hazard3 attach is shown to work on the bench. Until then, P5's firmware smoke is the only end-to-end validation.

## 7. Testing strategy

**Per-instruction unit tests** (P2/P3): for each opcode, set up registers, execute, assert. Pattern matches the M33 `tests.rs` convention.

**Differential against an independent oracle** is the missing piece. Three options, with my recommendation:

1. **`spike`** — official RISC-V ISA simulator. Has rv32imac. Drives via a debug-style stepping API (or a custom spike-side stub). **Recommended** — closest analogue to the QEMU diff harness, and Hazard3 implements stock RV32IMAC for these instructions, so spike is a faithful oracle.
2. **`qemu-system-riscv32 -cpu rv32`** — works but Hazard3 isn't a QEMU CPU; we'd be diffing against generic rv32, which is fine for ISA but loses the vendor-CSR coverage.
3. **Silicon only** — what the M33 path now relies on for the long tail. Eventually correct, but slow to iterate against.

I'd start with (1) for the ISA core (P2/P3) and add silicon (P6) for the IRQ controller and CSR window where spike has no model.

## 8. Open questions / risks

- **Probe-rs Hazard3 support on the bench.** I haven't verified that probe-rs 0.31 attaches to RP2354's RISC-V core — it does support generic RISC-V over JTAG, but RP2350's debug module is its own thing. **Risk:** P6 may need a workaround harness (UART log capture, mailbox handshake) instead of register diff. Doesn't block P1–P5.
- **Spike availability on Windows.** The harness host is Windows. Spike doesn't ship a Windows binary; we'd need WSL or a custom build. Falling back to building it under MSYS2 should work but is a setup tax. If spike-on-Windows is too much friction, we ship P2/P3 unit-test-only and lean on P6 silicon for differential coverage — same shape as the M33 path's long tail today.
- **Hazard3 vendor CSRs.** The Hazard3 reference manual is the source of truth (`meiea`/`meipa`/`meifa`/`meipra`/`meinext`/`meicontext` in CSR addresses `0xBE0..0xBE5`). Need to read carefully — these look standard but the priority/preemption semantics are vendor-specific.
- **`tech_debt.md` knock-on.** The existing tech debt around cycle accuracy will get a sibling — RISC-V instruction cycle costs are mostly 1 cycle on Hazard3, but multiplies/divides and load-use latency need their own measurements. First cut: flat 1 cycle for everything except mul/div (3 cycles) and loads (2 cycles). Document the gap, don't pretend it's accurate.
- **Compressed-instruction PC offsets.** RV32IC mixes 16-bit and 32-bit instructions on 16-bit boundaries. The decode loop must handle a 32-bit instruction split across two cache lines / fetch buffers. M33 has the same issue (Thumb-32 across halfword boundaries) and solved it the same way — single-halfword fetches with a 2-step combine. Pattern is reusable but the code is not.

## 9. What this HLD deliberately does NOT include

Per CLAUDE.md / AGENTS.md quality philosophy:

- No migration plan from "Arm-only" to "Arm+RISC-V" — dev sandbox, no users to migrate.
- No backwards-compatibility shims for the `Emulator::cores` field type change.
- No feature flags. Chip-arch is a runtime-builder choice.
- No env vars. Same reason.
- No bootrom emulation, no ARCHSEL handshake, no POWMAN integration.
- No abstraction layer between the two CPUs. The enum is not the start of a `CoreCpu` trait — if a third architecture ever shows up, **then** we revisit. Two enum arms is not an abstraction problem.
- No cross-cutting cleanup of M33 code "while we're here."

If the design starts feeling more elaborate than this document, the elaboration is wrong.
