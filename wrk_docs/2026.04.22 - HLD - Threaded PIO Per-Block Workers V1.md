# HLD — Threaded PIO Per-Block Workers

**Date:** 2026-04-22
**Scope:** `mdrp2350` `ThreadedEmulator` only (Windows x86_64 threaded runtime).
**Goal:** Split the single PIO worker thread into three per-block workers
(PIO0, PIO1, PIO2) so the emulator stops serialising what the hardware runs
in parallel.

## 1. Motivation

`paced_bench_rp2350 --workload onerom --threaded --timing` (sq=256,
commit `990f1a7`, 2026-04-21) produced:

| Worker | work_mean | wait_mean | wait% |
|---|---|---|---|
| core0 | 1.1 μs | 4.5 μs | 80.6 % |
| core1 | ~0 | 5.6 μs | 99.4 % (halted) |
| **pio** | **4.9 μs** | 0.7 μs | 12.6 % |
| coord | 0.12 μs | 5.5 μs | 97.8 % |

Throughput: **37.5 MHz** (threaded) vs 42.1 MHz (serial). The PIO worker
is the critical path by ~4×. Everyone else spends 80–99 % of each
quantum waiting.

The PIO worker's cost is the sum of per-block `step_n` work, which the
`pio_microbench` measurements (`wrk_journals/2026.04.20 - JRN - PIO
step_n Profiling.md`) show is roughly linear in the number of active
SMs: ~4.9 ns/sysclk per active SM after the recent `sideset`/diag-counter
fixes. For the OneROM shape (PIO1 × 1 SM, PIO2 × 2 SMs) the single
worker runs 3 SMs × 256 cycles ≈ 3.8 μs of pure SM work per quantum.
Splitting across three threads reduces the critical path to the longest
single block, `max(PIO1, PIO2) ≈ 2.5 μs`.

Back-of-envelope: if PIO stops dominating, throughput climbs to whatever
the next bottleneck is — `max(core0 = 1.1, pio_max = 2.5, coord = 0.1)`
≈ 2.5 μs per quantum → ~100 MHz. Even if barrier/coherence overhead
eats 20 %, **~2× end-to-end is the realistic target** for OneROM.

The host already has 20 cores, so 6 worker threads don't create
scheduler pressure. The barrier scales fine — `count`/`generation` are
two atomics, and the Condvar path only engages when a worker parks
(which, at sq=256 with pipelined hardware, will be the norm).

## 2. Design delta

Turn the 4-worker topology into 6: **core0, core1, pio0, pio1, pio2, coord**.

Everything shared across threads in `super::ThreadedPio` is already
indexed by block (`sm_enabled: [AtomicU8; PIO_BLOCKS]`,
`pads: [AtomicU64; PIO_BLOCKS]`, `tx`/`rx` SPSCs `[[_; SMS]; BLOCKS]`).
The split is cleanly per-block with one exception: the command queue is
currently a single `Mutex<Vec<PioCommand>>` serving all blocks. Make
that per-block too.

### 2.1 Per-block PIO worker body

Replace `pio_worker_body(blocks: [PioBlock; 3], ...)` with
`pio_block_worker_body(block_idx: usize, block: PioBlock, ...)`. Each
worker owns exactly one block. The loop body is simpler than today's:

```rust
for _ in 0..n {
    for cmd in shared.pio.drain_commands(block_idx) {
        apply_pio_command(&mut block, &shared.pio, block_idx, cmd);
    }
    let gpio_in = shared.gpio.read_in();
    if shared.pio.read_sm_enabled(block_idx) != 0 {
        block.step_n(step_q, gpio_in);
        shared.pio.write_irq_flags(block_idx, block.pending_irqs() as u8);
    }
    shared.pio.write_pads(block_idx, block.pad_out, block.pad_oe);
    barrier.wait();
}
```

Observable state already per-block → no new cross-worker synchronisation
primitives. The `gpio_in` read is a shared `AtomicU64` load and is fine
at 3× the rate.

### 2.2 Per-block command queue

`ThreadedPio.commands` becomes `[Mutex<Vec<PioCommand>>; PIO_BLOCKS]`.
`send_command` routes by `cmd.block()`; `drain_commands(block_idx)`
drains one queue. Each `PioCommand` already carries a `block: u8`
field, so routing is a single field match. Add a `PioCommand::block()`
inherent method for clarity.

Ordering impact: CPU → PIO ordering for a single block is preserved
(same mutex still serialises concurrent pushes from two CPU workers
targeting the same block). Cross-block ordering was never guaranteed —
the single-threaded `Bus::write32` visits one block per MMIO write, and
two different blocks' writes were already independent.

Capacity: today's preallocation hint (`Vec::with_capacity(64)`) comes
from the worst-case single-block setup (INSTR_MEM 32 + per-SM config).
With per-block queues the preallocation stays at 64 per queue — slightly
over-reserved but bench-insignificant.

### 2.3 Barrier

`SpinBarrier::new(4)` → `SpinBarrier::new(6)` in
`emulator.rs:406`. The primitive already handles arbitrary party counts.

### 2.4 `thread_mask`

`[usize; 4]` → `[usize; 6]`. Default `[0, 1, 2, 3, 4, 5]`. Mapping:
`[core0, core1, pio0, pio1, pio2, coord]`. The minimum-host-cores
assertion in `from_emulator` bumps from `>= 4` to `>= 6`. (Test host
has 20, so this is academic; the 4-core advisory `eprintln!` goes away.)

### 2.5 Timing

`RunTimings` today has `core0 / core1 / pio / coord`. Replace `pio`
with `pio0 / pio1 / pio2`. `paced_bench_rp2350 --timing` printout grows
two rows. No behavioural change — just more rows in the table.

## 4. Test plan

1. **Unit tests in `mdrp2350`** — `cargo test -p mdrp2350` runs clean.
   The two `ThreadedPio` command tests need updating to the per-block
   API (`drain_commands(0)` etc.).
2. **Threaded dual-core integration tests** — the existing suite under
   `crates/mdrp2350/src/threaded` that exercises `ThreadedEmulator`
   end-to-end. Must stay green.
3. **Throughput regression, compute-heavy** — `paced_bench_rp2350
   --threaded --workload contention` (or similar PIO-light workload).
   Expected: no regression. This catches the "we made barrier/overhead
   worse for non-PIO paths" failure mode.
4. **Throughput win, onerom** — `paced_bench_rp2350 --threaded
   --workload onerom --timing` before and after. Target ≥ 1.8× mean
   throughput. If we land < 1.5×, we re-profile before declaring done.
5. **Silicon PIO diff oracles** — `silicon_periph_diff_rp2350` (if any
   PIO cases exercise threaded path today — currently none, so
   informational only) and the OneROM serving oracle smoke test
   (`onerom_serving_oracle_rp2350`, serial path — unaffected, included
   only to confirm no accidental fallout in shared PIO code).

## 5. Out of scope

- **RP2040 threaded path.** Separate chip, separate emulator, not
  threaded yet. Covered when that phase lands.
- **PIO→NVIC IRQ routing.** Today's PIO worker doesn't route IRQs to
  the NVIC (`pio_worker_body` docstring §). Same after the split.
- **DMA modelling.** Emulator DMA is stubbed; the harness `GlueDma`
  helper runs on the driver thread, not the worker pool. Real DMA
  threading is a later phase.
- **Per-SM split.** Splitting a single block across multiple workers
  would require per-SM pad merging inside the block, which the existing
  `PioBlock::step` doesn't support. The per-block split is enough for
  the OneROM shape (2 active blocks × ≤ 2 SMs each).
- **RISC-V (Hazard3) threading.** `ThreadedEmulator::from_emulator`
  already panics on RISC-V cores; no change.

## 6. Risks

- **Barrier arity cost.** Going from 4 → 6 parties adds cache-coherence
  traffic on `count`/`generation`. Expected to be small — both atomics
  fit in one line each and the hybrid spin-then-park design avoids
  continuous invalidation when workers park. If measured cost eats more
  than ~10 % of the split gain, consider a hierarchical barrier
  (2-level: per-group + global). Not expected to trigger.
- **False sharing on `ThreadedPio` arrays.** `pads: [AtomicU64; 3]` is
  24 bytes — three AtomicU64s in one cache line. Three workers each
  writing their own index is exactly the false-sharing pattern. If
  profiling shows this as a bottleneck, pad to one line per block with
  `#[repr(align(64))]` wrappers. Add if measured; don't pre-optimise.
- **Idle-block cost.** PIO0 is unused in OneROM — its worker still
  spawns, drains an empty command queue, skips `step_n` (enable mask 0),
  publishes zero pads, and parks at the barrier. This is cheap
  (nanoseconds of work, then Condvar park) but non-zero. If a future
  single-block workload shows this worth reclaiming, we can conditionally
  skip spawning — out of scope now.

## 7. Success criteria

- All existing `mdrp2350` and harness tests green.
- `paced_bench_rp2350 --threaded --workload onerom` throughput ≥ 1.8×
  pre-change mean.
- Non-PIO threaded workloads within ±5 % of pre-change throughput.
- `--timing` output shows the three PIO workers' `phase_work_ns` close
  to `(old_pio_work) / active_blocks` with `barrier_wait_ns` rising on
  the idle block(s), confirming the critical path has shifted off PIO.
