Date: 2026-05-04
Parents: `2026.04.15 - HLD - OneROM Serving Oracle (Stage G).md`,
         `2026.04.17 - HLD - OneROM CPU-Serve Oracle.md`
Depends: `wrk_journals/2026.05.04 - JRN - Fire-32-a SeaBIOS Firmware Build.md`

## 1. Purpose

Today the OneROM serving oracles and byte-correctness validator are wired to
exactly one hardware variant — `fire-24-a`, 13 address pins, 64 KiB shadow,
data on GPIO 16..23. Three pieces of fixture-specific shape are baked in as
constants, repeated across both oracles plus their drivers:

```
SHADOW_SIZE: usize = 0x1_0000;                       // 64 KiB shadow
ADDR_PINS: [u8; 13] = [7,6,5,4,3,2,1,0,10,11,14,15,12];
GPIO_DATA_BASE: u8 = 16;
GPIO_CS1/CS2/CS3 = 13/12/15;
```

The new `onerom-fire-32-a-rp2350-seabios.bin` fixture (256 KiB SeaBIOS, 27C020
on a 32-pin socket) needs an entirely different layout: 19 address pins
scattered across GPIO 16..34, data on GPIO 0..7, separate /CE and /OE, a
512 KiB SDRR-baked permutation table where each SeaBIOS byte appears twice
(A18 is don't-care for 27C020 content; see §5.3). The socket-generic `cs2`
field names GPIO16, the same physical pin used as A16 on 27C010/27C020, but
the live 27-series PIO runtime gates reads with `/CE` and `/OE`, not CS2
(§5.1).

The goal of this change is the smallest cleanup that lets the same harness
serve both fixtures (and future 27C0x0 variants) byte-correctly. We do this
by introducing one `FixtureSpec` value parsed from the firmware, threading
it through the two oracles, and deleting the constants it replaces. No
abstraction layer, no second oracle class, no env-var or feature-flag
selection.

We are in a dev sandbox (per workspace policy), so the old hardcoded API
goes away rather than living alongside the new one.

### 1.1 Non-goals

- **A new oracle.** The PIO `ServingOracle` and the CPU `CpuServingOracle`
  stay; we just unwire their fixture assumptions. No third "generic" oracle
  is introduced.
- **Live fire-32-a silicon validation.** We don't have fire-32-a hardware
  in the test rig today; this change is emulator-only. Probe-driven
  fire-32-a oracles are a later pass.
- **Bank switching, multi-fixture cohabitation, or runtime fixture switching.**
  One fixture per binary invocation, set at construction time.
- **Replacing or relocating `seabios-256k.bin`.** Source image stays
  exactly where it is.
- **Deciding the upstream linker-script patch or the official fixture
  filename convention.** Both are tracked in
  `wrk_journals/2026.05.04 - JRN - Fire-32-a SeaBIOS Firmware Build.md`
  follow-up list and resolved separately.

## 2. Scope

| Stage | Deliverable | Done when |
|-------|-------------|-----------|
| 1 | `FixtureSpec` parser | A single function takes a loaded OneROM `.bin` and returns the pin map, address width, data-pin base, CS/CE/OE assignments, and per-set shadow size. Two known fixtures (fire-24-a 27C256, fire-32-a 27C020) round-trip cleanly. |
| 2 | Oracle widening | `ServingOracle` and `CpuServingOracle` take a `FixtureSpec`, drop the three constants and the `ADDR_PINS` array, widen `Case` to a single u64 raw-GPIO mode, widen the shadow to `Box<[u8]>`. The existing fire-24-a binaries (`onerom_serving_oracle_rp2350`, `onerom_serving_oracle_cpu_rp2350`, `seabios_fixture_byte_correct` over the 24-pin SeaBIOS fixture) all pass unchanged on their respective fixtures. |
| 3 | fire-32-a byte-correctness | A new binary `seabios32_fixture_byte_correct` (PIO-serve, distinct from the existing fire-24-a CPU-serve binary; see §4.6 for why we fork) sweeps the full 19-bit fire-32-a pin-pattern space on the new fixture and proves every served byte matches `seabios-256k.bin`. This is 524,288 pin-pattern checks and 262,144 unique SeaBIOS source offsets for 27C020 content; A18 is the duplicate/don't-care line. |

Out of scope: changing what the oracles classify (verdicts, envelope,
stability rules), reworking the glue DMA pipeline, touching the trace
machinery.

## 3. Current shape (what we delete)

The fire-24-a fixture leaks into the harness in three places:

1. **`onerom_serving_oracle.rs`** — `SHADOW_SIZE: usize = 0x1_0000`,
   `ADDR_PINS: [u8; 13]`, `Case` carries both an `addr_bits: u16` (permuted
   through `ADDR_PINS` by `stimulus_level`) and an alternative
   `raw_pin_state: Option<u16>`. Two construction modes, both u16-bounded.
   The `ADDR_A11_A12_HIGH = 0x1800` invariant is fire-24-a-specific (CS2/CS3
   share GPIOs with A11/A12 in that pin map, so cases must keep those high).
2. **`onerom_serving_oracle_cpu.rs`** — same three constants re-declared,
   plus `GPIO_DATA_BASE`, `GPIO_CS1/2/3`, and the same `ADDR_PINS` array.
   It re-uses `Case` from `onerom_serving_oracle` so the construction-mode
   forking lives there.
3. **`seabios_fixture_byte_correct.rs`** — `CS1_BIT: u16 = 1 << 13` and a
   16-bit pin-state sweep over `0x0000..=0xFFFF`. The 128-KiB architectural
   ceiling lives here.

All three are deleted and replaced with calls into a `FixtureSpec` in §4.

The legacy `Case::new(addr_bits)` permutation API and `stimulus_level()`
helper go away. The 15 hand-authored fire-24-a default cases get re-expressed
in raw-pin form (mechanically: run them through the existing
`stimulus_level()` once at the source, paste the output as the new literal).
The `ADDR_A11_A12_HIGH` invariant becomes a per-fixture constraint
expressed inside `FixtureSpec`.

## 4. Target shape

### 4.1 `FixtureSpec`

One value, in `crates/picoem-harness/src/onerom_fixture.rs` (new module):

```rust
/// Hardware-variant pin map and capacity for one OneROM fixture.
#[derive(Clone, Debug)]
pub struct FixtureSpec {
    /// Variant tag, for diagnostics. e.g. "fire-24-a/27C256".
    pub label: &'static str,

    /// GPIO pin per address line, low-to-high (A0 first). The vector
    /// length is the address width in bits — 13 for fire-24-a/27C256,
    /// 19 for fire-32-a/27C020.
    pub addr_pins: Vec<u8>,

    /// GPIO pin per data line, D0..D7. Always 8 entries.
    /// fire-24-a: 16..=23. fire-32-a: 0..=7.
    pub data_pins: [u8; 8],

    /// Primary CS — the active-low gate that controls whether D0..D7
    /// are driven. Always present.
    pub cs1: u8,

    /// Pins that must be driven LOW during reads to enable serving.
    /// fire-32-a uses this for CE (P0:15) and OE (P0:14). fire-24-a
    /// has no such pins (CS1 is the read-active gate; CE/OE are not
    /// separate signals on 27C-family-with-no-CS-aliasing on the
    /// 24-pin board).
    pub asserted_low_during_read: Vec<u8>,

    /// Pins that must be driven HIGH during reads (deasserted, since
    /// the chip-select sense is active-low).
    ///
    /// fire-24-a: CS2 (P0:12) and CS3 (P0:15).
    ///
    /// fire-32-a in our 27C020 fixture: empty. fire-32-a has no CS3
    /// pin; its socket-generic CS2 field names P0:16, which is A16 for
    /// 27C020 and is driven by the address pattern. The live 27-series
    /// runtime gates reads via `/CE` + `/OE` (see §5.1).
    pub deasserted_high_during_read: Vec<u8>,

    /// Pin pattern bits that, when high, make the chip un-servable
    /// (data lines tristated by the firmware). The byte-correctness
    /// sweep skips any pin pattern P where `(P & unservable_when_high)
    /// != 0`. This is uniform across fixtures regardless of whether
    /// the unservable bit is a "real" CS GPIO outside `addr_pins` or
    /// an address-pin-aliased CS.
    ///
    /// fire-24-a: `1 << 13` — CS1 is at GPIO13. CS1=high tristates
    /// D0..D7 (the existing fire-24-a SeaBIOS path's `CS1_BIT` filter
    /// becomes this).
    ///
    /// fire-32-a/27C020: `0` — GPIO16 is A16 for this chip type, not a
    /// read gate. `/CE` and `/OE` are the active-low gates (§5.1), so no
    /// A16-high patterns are skipped.
    pub unservable_when_high: u64,

    /// Shadow size in bytes — comes from the per-set `sdrr_rom_set_t.size`
    /// field. fire-24-a/27C256: 65 536. fire-32-a/27C020: 524 288
    /// (the firmware-baked permutation table is 27C040-capacity-sized
    /// even for 27C020 content, with each SeaBIOS byte appearing twice
    /// — confirmed via byte-frequency histogram in
    /// `wrk_journals/2026.05.04 - JRN - Fire-32-a SeaBIOS Firmware Build.md`
    /// 2nd-pass analysis).
    pub shadow_size: usize,
}
```

`SHADOW_BASE = 0x2000_0000` stays a constant — it's the SRAM origin on
RP2350 and is shared by every OneROM fixture we target. No fixture in
flight changes it.

The struct is a plain value, not a trait. There is no `FixtureSpec` trait,
no per-spec impl block, no const-generic parameter. The two oracles
each take a `&FixtureSpec` and read what they need.

### 4.2 Loading the spec

`FixtureSpec::from_flash(flash: &[u8]) -> Result<FixtureSpec, FixtureError>`
parses the spec out of the loaded firmware:

- `sdrr_pins_t` at `flash + 0x80FC`: source for `addr_pins`, `data_pins`,
  `cs1`, `asserted_low_during_read`, `deasserted_high_during_read`,
  `unservable_when_high`. Field offsets within the struct are pinned
  in the implementation to match `sdrr/include/config_base.h` (the
  OneROM upstream header). Out-of-range pin numbers (≥ `MAX_USED_GPIOS`)
  abort the parse. The `unservable_when_high` mask is computed from the
  selected ROM type: 27C010/27C020/27C040 fixtures use `/CE` + `/OE` and
  keep GPIO16 addressable; older 23-series-style layouts can still model
  address-aliased deselect gates.
- The metadata-walked first ROM set (`sdrr_info_t` →
  `onerom_metadata_header_t` → `sdrr_rom_set_t[0]`): source for
  `shadow_size`. The existing `parse_rom_set_layout()` already returns
  this; we reuse it verbatim.
- `label` is constructed from a small fingerprint built from
  `(addr_pins.len(), data_pins[0], cs1)` — enough to disambiguate the
  two known fixtures for human-readable diagnostics. Not load-bearing.

Parse failures return a typed `FixtureError` (truncated image, bad pin,
unknown layout). Callers `unwrap` for the no-recovery path; they're all
test/diag binaries.

The parser lives next to `parse_rom_set_layout` in
`crates/picoem-harness/src/onerom_fixture.rs`. Existing helpers in
`onerom_serving_oracle.rs` that read the metadata struct chain
(`SDRR_INFO_OFFSET`, `SDRR_INFO_METADATA_PTR_OFFSET`,
`METADATA_HEADER_*`) move into the new module so the metadata parsing
sits in one place.

### 4.3 `Case` simplified

```rust
pub struct Case {
    pub label: &'static str,
    /// Raw GPIO pattern to drive. Bit `i` is the level for GPIO `i`.
    /// u64 because fire-32-a's A0 lands on GPIO 34, beyond u32.
    pub pin_pattern: u64,
}
```

Single mode, no more `addr_bits`/`raw_pin_state` fork, no
`ADDR_A11_A12_HIGH` invariant baked into construction. The
"deasserted-CS-during-read" and "asserted-CE/OE-during-read" rules
both move to the oracle, which composes the full stim level from
`spec.deasserted_high_during_read`, `spec.asserted_low_during_read`,
and `case.pin_pattern` (see §4.4). Callers no longer need to know
about those constraints.

A helper builds a case from an address index plus the spec:

```rust
impl Case {
    pub fn from_addr(label: &'static str, addr: u32, spec: &FixtureSpec) -> Self {
        let mut pat = 0u64;
        for (bit, &gpio) in spec.addr_pins.iter().enumerate() {
            if (addr >> bit) & 1 != 0 {
                pat |= 1u64 << gpio;
            }
        }
        Case { label, pin_pattern: pat }
    }
}
```

The 15 default fire-24-a cases become a `Vec<Case>` returned by
`default_cases(spec: &FixtureSpec)`, generated mechanically from the
existing labels + 13-bit address values via `Case::from_addr`. The
generator is identical for fire-32-a; the spec's `addr_pins.len()` decides
the address-bit width.

### 4.4 Oracles

`ServingOracle` and `CpuServingOracle` each gain a `spec: FixtureSpec`
field. Their constructors take `(spec, flash, ...)`. The shadow is
`Box<[u8]>` sized at `spec.shadow_size`; the boxed-fixed-array typing
goes away. Every place that referenced the constants now reads
`spec.shadow_size`, `spec.cs1`, `spec.data_pins[0]`, etc.

Per-case stimulus construction:

- **Inter-case gap level** — every pin in `spec.deasserted_high_during_read`
  driven HIGH; every pin in `spec.asserted_low_during_read` driven HIGH
  (gap-level = "chip deselected"); CS1 driven HIGH; addr/data pins low.
- **Stim level** — every pin in `spec.deasserted_high_during_read` driven
  HIGH; every pin in `spec.asserted_low_during_read` driven LOW (CE/OE
  asserted to enable read); CS1 driven LOW (read-active edge);
  `case.pin_pattern` OR'd in for addr+data bits.

Test-only `new_with_shadow` constructors take the spec too.

### 4.5 The byte-correctness binary

The fire-32-a SeaBIOS validator is a new binary
`seabios32_fixture_byte_correct.rs` driving the PIO `ServingOracle`
(see §4.6 for why this is a new binary rather than a generalisation of
the CPU-serve `seabios_fixture_byte_correct`). Sweep shape:

```rust
let spec = FixtureSpec::from_flash(&flash)?;
let n_addr = spec.addr_pins.len();
let sweep_size = 1u64 << n_addr;     // 8 KiB for 13-bit, 512 KiB for 19-bit
for addr in 0..sweep_size {
    let case = Case::from_addr("sweep", addr as u32, &spec);
    if (case.pin_pattern & spec.unservable_when_high) != 0 {
        continue;                    // fixture-specific unservable gate
    }
    let result = oracle.run_case(&mut emu, &mut glue, case);
    // Expected byte: SeaBIOS at the address decoded from the pattern.
    // For fire-32-a, A18 is treated as don't-care (mod by SeaBIOS
    // size handles the 2× table redundancy — see §5.2).
    let expected = seabios_image[(addr as usize) % seabios_image.len()];
    // compare result.observed_byte vs expected …
}
```

For fire-24-a the existing CPU-serve `seabios_fixture_byte_correct`
binary stays exactly as it is today — its loop already filters CS1=high
in 16-bit pin-state space (correctly, because fire-24-a's `cs1` GPIO
isn't in `addr_pins`). After stage 2 it just consumes `FixtureSpec`
to source the constants it currently re-declares; behaviour is
unchanged.

### 4.6 Why two byte-correctness binaries

The existing `seabios_fixture_byte_correct` is hardwired to
`CpuServingOracle` and the fire-24-a CPU-serve fixture
(`onerom-fire-24-a-rp2350-seabios-cpu.bin`). Our new fire-32-a fixture
is **PIO-served** — `sdrr-gen` was invoked without a CPU-serve flag in
the build session (see journal §Pipeline), so the only oracle that
applies is `ServingOracle`.

Two paths to "one binary that handles both":

1. Generalise `seabios_fixture_byte_correct` to dispatch between
   `ServingOracle` and `CpuServingOracle` based on a fixture-mode
   field in `FixtureSpec`. Cost: thread `GlueDma`, the PIO sync
   detector, and the inter-oracle API differences through one binary.
2. Build a fire-32-a-CPU-serve sibling fixture and use Method A
   (`build_seabios_fixture` style — overwrite the SDRR table with a
   flat SeaBIOS chunk laid out by pin state). Cost: write a
   fire-32-a-aware `build_seabios_fixture`; depends on the
   PIO-vs-CPU-serve serve-loop semantics being identical for that
   layout, which is not guaranteed.

Both are larger than the win. Forking — one CPU-serve binary for
fire-24-a, one PIO-serve binary for fire-32-a — keeps each binary
focused on the oracle it drives, sidesteps the dispatch question, and
costs only ~300 LOC of pin-pattern-sweep boilerplate (mostly the
boot-sync helper, which is already cookie-cutter across the existing
binaries). If a third SeaBIOS fixture appears later we'll revisit;
two is below the abstraction threshold.

## 5. Fire-32-a-specific layout details

### 5.1 CS2 metadata shares GPIO16 with A16, but 27C-series uses CE/OE

Fire-32-a/27C020 metadata has a socket-generic `cs2` field on P0:16,
which is also A16 in the 27C010/27C020 address bus. That name is not
the active read gate for the selected 27-series EPROM type. The live
OneROM PIO runtime reports `piorom_config.cs_base_pin = 14`,
`num_cs_pins = 2`, and PIO2 SM0 `PINCTRL.IN_BASE = 14`, so the CS
handler watches GPIO14/GPIO15 (`/OE` + `/CE`). GPIO16 remains an
address line.

Consequence: the fire-32-a 27C020 sweep runs all 2^19 = 524 288 pin
patterns, with `spec.unservable_when_high = 0`. For a 256 KiB source
image the sweep covers all 262 144 unique SeaBIOS source offsets; the
extra factor of two is A18 don't-care duplication (§5.3).

### 5.2 The rom-set image is a SDRR-baked permutation table, not flat SeaBIOS

Empirical inspection of the fire-32-a fixture (journal 2026-05-04 §Pin
map, plus a 2nd-pass byte-frequency analysis): the 524 288-byte
rom-set image contains each SeaBIOS byte with **exactly twice** the
frequency it appears in the 262 144-byte SeaBIOS source. The lower and
upper halves are NOT mirrors of each other (different byte sequences),
which means the 2× redundancy is interleaved across the table by
SDRR's address-permutation baking — not laid out as a contiguous
mirror.

Implication for byte-correctness: we cannot use the fire-24-a-CPU-mode
"shadow == seabios_chunk" pre-check (which works there because
`build_seabios_fixture` deliberately overwrites the SDRR table with a
flat-SeaBIOS layout, bypassing baking). For fire-32-a we use
**Method B** — compare the served byte against
`seabios[decoded_addr]`, where `decoded_addr` is reconstructed from
the pin pattern via `spec.addr_pins`.

### 5.3 A18 is don't-care for 27C020 content

The 32-pin socket wires A18 because the same socket also takes 27C040
(512 KiB). For 27C020 (256 KiB) content the chip die has no A18 pin.
SDRR's preprocessing fills the 524 288-byte buffer such that the
served byte is independent of A18 (the 2× byte-frequency confirms each
SeaBIOS byte appears under both A18=0 and A18=1 patterns).

The byte-correctness expected value is therefore
`seabios_image[(decoded_addr as usize) % seabios_image.len()]`. Both
A18=0 and A18=1 patterns yield duplicate checks for the same 256 KiB
source offset range.

If empirical sweep stage finds A18=0 and A18=1 patterns serving
*different* bytes for the same lower-18-bits address, that's a
fixture-build bug and the test fails loudly — exactly what we want.

## 6. Test plan

### 6.1 Regression — fire-24-a stays green

Run the existing fire-24-a binaries unchanged-from-the-user's-side
against the existing fire-24-a fixtures:

- `onerom_serving_oracle_rp2350` (15-case PIO sweep)
- `onerom_serving_oracle_cpu_rp2350` (CPU-serve sweep)
- `seabios_fixture_byte_correct` over `onerom-fire-24-a-rp2350-seabios-cpu.bin`
  (4 ROM sets × 32 KiB = 128 KiB byte-correct, same as today)

All three must exit 0 with the same per-case verdicts as the pre-change
runs. This is the floor.

### 6.2 New — fire-32-a byte-correctness

`seabios32_fixture_byte_correct --fixture
crates/picoem-harness/fixtures/onerom-fire-32-a-rp2350-seabios.bin` runs
the 19-bit sweep and verifies every served byte matches
`seabios-256k.bin[(addr) % 0x40000]` (§5.3).

Acceptance: 524 288 cases run; all PASS; zero unservable skips. This
proves byte correctness for 524 288 pin-pattern checks and all 262 144
unique SeaBIOS source offsets. `--smoke` mode runs the first 4096 cases
for a fast spot-check during development.

### 6.3 Unit tests

In `onerom_fixture.rs`:

- `FixtureSpec::from_flash` parses the bundled fire-24-a fixture and
  produces `addr_pins.len() == 13`, `data_pins[0] == 16`, `cs1 == 13`.
- Same for the bundled fire-32-a fixture: `addr_pins.len() == 19`,
  `data_pins[0] == 0`, `cs1 == 13`, `shadow_size == 524288`.
- A mangled flash (truncated, bad pin number) returns the appropriate
  `FixtureError` variant.

In `onerom_serving_oracle.rs`:

- `Case::from_addr` agrees with the legacy `stimulus_level` output for
  every fire-24-a default case (this is the migration sanity check —
  pin out the same numbers, just via the new code path).

## 7. Risks and open questions

1. **`sdrr_pins_t` field offsets.** The implementation needs to pin
   down the byte offsets of `data[8]`, `addr[N]`, `cs1`, `cs2`, `cs3`,
   `ce`, `oe` within the struct. Existing harness code reads `sel[]`
   at +52 and `sel_jumper_pull` at +59, which establishes the trailing
   layout but not the leading fields. The implementer cross-references
   `sdrr/include/config_base.h` from the upstream OneROM clone (the
   `/tmp/one-rom-work/one-rom` clone from the fixture-build session is
   the path of least resistance; if it's been deleted, re-clone with
   `git clone --depth 1 https://github.com/piersfinlayson/one-rom.git`
   per the journal's reproduction recipe). If the layout is awkward
   (variable-length per chip type), the parser inspects the chip-type
   field first and switches.

2. **Address-pin width for non-27C020 32-pin chips.** A future
   27C010 (128 KiB) fixture on the same fire-32-a hardware would have
   `addr_pins.len() == 17` even though the socket wires 19. Whether
   `sdrr_pins_t` reports the chip's native width or the socket's wired
   width determines whether we sweep 17 bits or 19. Resolution
   deferred to whichever fixture shows up next; the spec stores
   whatever the firmware reports.

3. **u64 pin pattern bandwidth.** RP2350 has 48 GPIOs (47 max index),
   so u64 has 16 bits of headroom. RP2040 caps at GPIO 29. Both fit.
   We do not anticipate pins above 47 in any OneROM HW variant, so
   u64 stays sufficient indefinitely.

4. **Sweep cost.** 262 144 servable cases × per-case timeout
   (~`PER_CASE_TIMEOUT` cycles) × emulator-to-wall-clock ratio: the
   fire-24-a 128-KiB sweep is already minutes-scale on warm CPUs;
   fire-32-a's 262 144 servable pin-pattern cases are ~2× that. Add a `--smoke`
   mode (first 4096 servable cases, fast spot-check) and a
   `--stride <N>` mode (sub-sample every Nth) for the dev loop.

5. **PIO oracle envelope tuning.** `ENVELOPE_CYCLES = 15..=45` was
   tuned empirically for fire-24-a's data pins on GPIO 16..23. fire-32-a
   moves data to GPIO 0..7 (different RP2350 pad timing characteristics
   are theoretically possible). If the fire-32-a sweep produces
   `LatencyOutOfEnvelope` verdicts on otherwise correct serves, the
   envelope widens — that's a tuning decision, not a byte-correctness
   regression. Byte-correct + LatencyOOE counts as PASS for the
   byte-correctness binary's success criterion (matches the fire-24-a
   binary's existing handling, line 350-358 of
   `seabios_fixture_byte_correct.rs`).

6. **CPU-serve constants are fire-24-a-specific.** `CPU_SERVE_LOOP_PC_LO`
   = 0x1000_0926 / `_HI` = 0x1000_0930 and `CPU_ENVELOPE_CYCLES = 7..=60`
   are baked from fire-24-a CPU-serve firmware traces. A future
   fire-32-a CPU-serve fixture would need new values — out of scope
   here (we have no fire-32-a CPU-serve fixture). The HLD does not
   move these constants into `FixtureSpec` because there's only one
   CPU-serve fixture in flight; if a second arrives we revisit. This
   is the deliberate "two-is-below-the-abstraction-threshold" call.

7. **fire-32-a SeaBIOS-source reachability.** The byte-correctness
   check requires `seabios-256k.bin` co-located with the fixture
   under `crates/picoem-harness/fixtures/sources/`. This file already
   ships (used by the fire-24-a SeaBIOS path); no new artefact
   needed.

8. **`build_seabios_fixture` is fire-24-a-only.** That binary
   overwrites the SDRR-baked table in a fire-24-a fixture with a
   flat-SeaBIOS-by-pin-state layout — works because fire-24-a
   CPU-serve does `byte = shadow[pin_state]` with no permutation. It
   has no equivalent for fire-32-a (PIO-served, with PIO1 doing
   address decode). We don't introduce one — we use Method B (§5.2)
   instead, which works directly off the OneROM-pipeline-built
   fixture.
