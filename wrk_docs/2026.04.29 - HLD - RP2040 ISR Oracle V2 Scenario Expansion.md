## 1. Problem

V1 ships **two** scenarios — `isr_m0_timer_cold` and `isr_m0_tail_chain_pendsv_systick`. The plumbing they exercise has landed and silicon validation has run (out-of-band — to be journalled separately). What V1 does not exercise, but the production code now claims to support:

- The NVIC priority array — V1 leaves all priorities at the default 0, so tie-break by exception number is the only path tested.
- The PRIMASK gate inside `try_take_any_pending_exception` (`mdrp2040/src/core/mod.rs:331`).
- The WFI wake path on a slow-path NVIC arrival (`tech_debt.md:1202-1213`, V5 §9.1 known limitation).
- ISER/ICER/ISPR/ICPR bits 26..31 silently latch instead of RAZ/WI (`tech_debt.md:1565-1584`, V5 §9.6).

Until each is exercised by a passing silicon-vs-emu scenario, those four code paths are unverified.

This HLD adds four scenarios + one one-line production fix + a doc-cleanup pass. Nothing else.

## 2. Out of scope

- **Per-core routing** (TIMER on core 0's NVIC only, core 1 stays clean — `tech_debt.md:1440-1462`). Real but blocked: today's runner drives core 0 only; covering this means a runner upgrade. Treat as V3.
- **Cycle observability.** M0+ has no DWT CYCCNT; emulating one with `Emulator.cycles` + a soft-window assertion is its own design choice. V3.
- **SysTick CLKSOURCE=0 external 1µs cadence** (`tech_debt.md:1495-1511`). Low-yield and adds external-tick MMIO setup complexity.
- **Step-quantum mid-quantum NVIC race** (`tech_debt.md:1541-1564`). Requires production change to the slow-path scheduler; not a scenario-shape fix.
- A new oracle binary, a new runner, or a new scenario format. The V1 `IsrScenario` struct is sufficient.

## 3. Scenario catalogue (V2 = V1 + 4)

Each new scenario follows the V1 shape exactly: a `&'static [u8]` image built by `build_image_m0plus`, an `INIT_*` reg array, an `OBS_*` observable array, and a `SCENARIOS` entry. No new abstractions.

### 3.1 `isr_m0_priority_preempt`

**What.** Pend two peripheral IRQs simultaneously, with the *lower-numbered* one assigned a *higher* numeric priority value (= lower priority); assert the higher-priority one runs first.

**Setup.**
- Use TIMER_IRQ_0 (NVIC #0) and TIMER_IRQ_1 (NVIC #1) via TIMER ALARM0 + ALARM1 armed at the same TIMERAWL deadline so both INTR bits set in the same tick.
- Write `NVIC_IPR0 = (0xC0 << 0) | (0x40 << 8)` — IRQ #0 gets priority 0xC0, IRQ #1 gets 0x40. M0+ implements bits [7:6] only; effective priorities 3 and 1.
- Enable both: `NVIC_ISER0 = 0x3`.
- Spin in main.

**Handlers.** Two distinct handler bodies — `HANDLER_IRQ0` increments `ctr_irq_0` and W1Cs ALARM0; `HANDLER_IRQ1` increments `ctr_irq_1` and W1Cs ALARM1. Each also writes its own IRQ number to `order_first_irq` if that cell is currently zero (no concurrency on M0+ V1 — `can_dispatch_now` blocks preemption, so the second handler runs as a tail-chain after the first returns; the test for zero is race-free). Vector entry [16] (TIMER_IRQ_0) → HANDLER_IRQ0; vector entry [17] (TIMER_IRQ_1) → HANDLER_IRQ1.

**Observables.**
- `ctr_irq_1 == 1` and `ctr_irq_0 == 1` (both fire eventually via tail-chain).
- `order_first_irq == 1` (the handler for IRQ #1 ran first, because of its lower priority value).

**Closes:** the priority-array path through `Nvic::highest_priority_pending` and `try_take_any_pending_exception`. Two handler bodies is simpler than one IPSR-reading handler — no MRS in handler hot path, no shared counter array.

### 3.2 `isr_m0_masked_pending_unmask`

**What.** Pend an IRQ while PRIMASK=1; the dispatch path must not fire. Clear PRIMASK with `cpsie i`; the next instruction must be the handler.

**Setup.**
- Set PRIMASK=1 (`cpsid i`).
- Pend TIMER_IRQ_0 via ISPR; enable via ISER.
- Write `gate = 1` to a SRAM cell (this is the "before unmask" probe).
- `cpsie i`.
- Write `gate = 2` (this should run *only* if dispatch did NOT happen between the two writes — but on M0+ the architecturally-required dispatch happens at the `cpsie i` boundary, so gate stays 1).
- Spin.

**Handler.** Standard increment-and-W1C, plus one extra instruction: load `gate` into r5 and copy it into a separate SRAM observable `gate_at_entry`. This is the load-bearing assertion: `gate_at_entry == 1` proves the handler ran *between* the two `gate` writes.

**Observables.**
- `ctr_timer == 1`.
- `gate_at_entry == 1` — the dispatch happened on the `cpsie i` boundary, before the `gate=2` store retired.
- `gate == 2` — main body resumed after handler returned.

**Closes:** the PRIMASK-gate at `core/mod.rs:331` and the post-CPS dispatch poll. The `gate_at_entry` observable is the difference between "handler ran at all" (existing scenarios) and "handler ran *at the right instant*".

### 3.3 `isr_m0_wfi_wake`

**What.** Core executes WFI; an alarm fires later; the core wakes, dispatches the handler, and main body resumes after WFI.

**Setup.**
- Enable TIMER_IRQ_0 (ISER + IPR + ALARM0).
- ARM ALARM0 with a deadline ~50 µs into the future (small enough that the oracle's wall-clock budget covers it; large enough that the WFI is reached first).
- Write `phase = 1` to a SRAM cell.
- `wfi`.
- Write `phase = 2`.
- Spin.

**Handler.** Standard increment-and-W1C; extra instruction loads `phase` into `phase_at_entry`.

**Observables.**
- `ctr_timer == 1`.
- `phase_at_entry == 1` — handler fired during the WFI window.
- `phase == 2` — main resumed after wake.

**Coverage limit.** This scenario verifies the wake *happened* and `phase_at_entry == 1` proves the handler ran during WFI rather than after. With a 1.5 s wall-clock budget it does **not** stress the per-event re-check latency that `tech_debt.md:1202-1213` actually calls out — only that the wake is reached eventually within the budget. A tighter wake-latency oracle requires cycle observability (V3). Concretely: V2 closes the "WFI never wakes" sub-case of V5 §9.1; the broader "re-check on every event" sub-case stays open.

### 3.4 `isr_m0_nvic_high_bits_razwi`

**What.** Write all-ones to ISER0 / ICER0 / ISPR0 / ICPR0; read back; assert bits 26..31 are zero (RP2040 has 26 IRQ lines per RP2040 datasheet §2.3.2; bits 26..31 are RAZ/WI on real silicon).

**Setup.** Tiny main: a sequence of 4 stores + 4 loads + 4 writes-to-SRAM observables. No handler dispatch — this scenario is pure register-shape.

**Observables.**
- `iser_readback == iser_expected` where `iser_expected = 0x03FF_FFFF`.
- Same shape for ICER0 (after writing then reading).
- `ispr_readback == 0x03FF_FFFF`.
- `icpr_readback == 0` (after using ICPR0 to clear).

**Production fix required.** `crates/mdrp2040/src/bus/mod.rs:1613-1632` — the four arms of `nvic_mmio_write32` for ISER0 / ICER0 / ISPR0 / ICPR0 currently write the full 32-bit value into `n.enabled` / `n.pending`. Each gets `& 0x03FF_FFFF` masking the input. One line each, four total.

**Closes:** `tech_debt.md:1565-1584`.

## 4. Production changes

Two parallel four-arm patches:

```rust
// bus/mod.rs:1614 (NVIC_ISER0)
0xE100 => { n.enabled |= val & crate::irq::IRQ_LINE_MASK; true }
// :1619 (NVIC_ICER0)
0xE180 => { n.enabled &= !(val & crate::irq::IRQ_LINE_MASK); true }
// :1624 (NVIC_ISPR0)
0xE200 => { n.pending |= val & crate::irq::IRQ_LINE_MASK; true }
// :1629 (NVIC_ICPR0)
0xE280 => { n.pending &= !(val & crate::irq::IRQ_LINE_MASK); true }
```

Apply the **same four-arm mask** in `crates/mdrp2040/src/threaded/bus.rs` (around `:896-911`). The threaded runtime carries a 1:1 port of the serial `nvic_mmio_write32`; if we only mask the serial path, `dual_model.rs` would diverge on RAZ/WI. (This twin was missed in the original HLD draft and surfaced by the Stage 1 code review.)

Add `pub const IRQ_LINE_MASK: u32 = (1 << IRQ_COUNT) - 1;` to `mdrp2040/src/irq.rs` next to the existing `pub const IRQ_COUNT`. No other call-sites to update — the mask is checked at the MMIO boundary, the rest of the NVIC code already operates on values that came through this path.

That's the entire production diff for V2. Everything else is harness-side.

## 6. Implementation order

Single small commit per item; each compiles and passes its tests independently. Order:

1. **Production fix** for §3.4 (bus mask) + new `IRQ_LINE_MASK` constant in `mdrp2040/src/irq.rs` (`pub const IRQ_LINE_MASK: u32 = (1 << IRQ_COUNT) - 1`). Add unit test in `bus/mod.rs` extending the existing NVIC MMIO test block at `:2480+` to cover bit 26..31 RAZ/WI.
2. **§3.4 scenario** (`nvic_high_bits_razwi`). Smallest, no handler dispatch — vector table entries [2..15] all point at `bkpt #1` default handler.
3. **§3.2 scenario** (`masked_pending_unmask`). Reuses TIMER, adds CPSID/CPSIE encodings to main.
4. **§3.3 scenario** (`wfi_wake`). Adds the `wfi` encoding; reuses TIMER alarm path.
5. **§3.1 scenario** (`priority_preempt`). Adds TIMER_IRQ_1 dispatch path with a second handler body (`HANDLER_IRQ1`); HANDLER_TIMER stays bit-identical for V1 scenarios.
6. **Doc cleanup** (§5).
7. **Silicon validation pass** of the four new scenarios on real RP2040 hardware. Journal the run alongside V2 landing.

Each step is one PR-shaped commit. No staging branches, no migration steps.

**Per-scenario implementation gotchas the implementer will hit:**
- **`primary_observable_addr` panics on unknown** (`isr_scenarios_rp2040.rs:862`). Every new scenario must add a match arm — pick the load-bearing observable per §3.x.
- **Const-assert pins for literal pools.** Every existing handler/main pins the literal-pool offsets (e.g. `HANDLER_TIMER[16] == 0x4034 && HANDLER_TIMER[17] == 0x4005`). New `HANDLER_*` and `MAIN_*` arrays need analogous pins so encoding drift fails at compile time.
- **EMU integration test fns.** `tests/isr_scenarios_rp2040_emu.rs` has one `#[test]` per scenario — add four new fns following the existing two-test pattern.
- **SRAM observable cells.** Eleven new u32 cells: `CTR_IRQ_0`, `CTR_IRQ_1`, `ORDER_FIRST_IRQ`, `GATE`, `GATE_AT_ENTRY`, `PHASE`, `PHASE_AT_ENTRY`, `ISER_READBACK`, `ICER_READBACK`, `ISPR_READBACK`, `ICPR_READBACK`. Allocate contiguously above the existing CTR_TIMER/CTR_PENDSV/CTR_SYSTICK block in the SRAM region the runner zeroes via `reset_scenario_state_*`.
- **`reset_scenario_state_hw` + `reset_scenario_state_emu`** must zero the new cells too — otherwise scenario N+1 sees scenario N's residue.
- **Threaded model parity.** Like the V1 scenarios, V2 scenarios run only via the Serial path. `dual_model.rs` end-state parity is not a V2 acceptance gate.

## 8. Risks and known unknowns

- **Priority scenario depends on TIMER_IRQ_1 being routable on RP2040.** TIMER on RP2040 has 4 alarms → 4 IRQ lines (IRQ #0-3). Both IRQ #0 and #1 exist. Setup needs ALARM0 *and* ALARM1 armed, or ALARM0 + a second source — pick one timer ALARM each so the two IRQs don't share state. Confirmed orthogonal in `peripherals/timer.rs`.
- **WFI scenario timing.** The alarm deadline must land between the WFI and the wall-clock budget. On real silicon at default clocks, 50 µs is comfortable. On EMU at host speed it's still fine (the EMU runs faster than wall-clock for most workloads). If the EMU somehow finishes the WFI before the alarm fires, the scenario times out — that *is* a real bug surfaced by the test, not a flake.
- **`gate_at_entry` / `phase_at_entry` are coarse oracles.** They prove "handler ran in the right window", not "handler ran at the right instruction boundary". M0+ has no architectural way to prove the latter without cycle counting; we do not pursue cycle observability in V2.
- **Doc cleanup ordering.** If §5 lands before §3, the comments will be wrong for the duration. Land §5 last (item 6 in §6).
