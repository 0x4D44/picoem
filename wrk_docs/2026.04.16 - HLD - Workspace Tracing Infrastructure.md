# HLD — Workspace Tracing Infrastructure

**Date**: 2026-04-16 (revised 2026-05-05)
**Status**: Implemented
**Scope**: All crates in the mdpicoem workspace

## 2026-05-05 revision

The original draft put `release_max_level_info` on `[workspace.dependencies]`,
which transitively enabled the cap on every library crate in the workspace.
That is a Cargo footgun: features are unified across the dep graph, so any
external consumer of `rp2040-emu` / `rp2350-emu` / `picoem-common` would
inherit the cap and have their own `debug!`/`trace!` calls compiled out in
release without their consent. The `tracing` maintainers explicitly call this
out — `release_max_level_*` is a binary-only feature.

Fixed by moving the feature to the three binary-producing crates
(`picoem-harness`, `rp2350-emu-tui`, `rp2040-emu-tui`). Feature unification
still propagates the cap *down* to the libraries when they're built into
those binaries, so the in-workspace zero-overhead guarantee is preserved.
Sections below were authored under the original (broken) layout; the
"Dependency additions" and "Overhead guarantee" sections have been
rewritten to match the corrected layout. The level-guide and instrumented
sites are unchanged.

## Problem

The workspace has no structured logging or tracing framework. All diagnostic
output is raw `println!`/`eprintln!` — roughly 730 call sites, concentrated
in the harness binaries.

This causes two problems:

1. **Repeated throwaway instrumentation.** When debugging emulator issues,
   agents add ad-hoc `eprintln!` breadcrumbs at strategic points (bus decode,
   exception entry, DMA transfers, clock reprogramming), debug the issue,
   then remove them. The next bug in the same subsystem requires re-adding
   the same instrumentation. This is wasted effort.

2. **No structured framework.** When stray `eprintln!` calls do appear in
   production code (historically in mdrp2040's DMA, PIO, and RESETS paths —
   since cleaned up), there is no framework to migrate them into. They get
   deleted rather than promoted to a proper level-gated log.

Both emulator crates already have a bespoke `trace_enabled` / `emit_trace`
system on `Bus` for MMIO wire-format tracing — well-engineered (`#[cold]`,
`#[inline(never)]`, optional sink, zero overhead when off) but not
extensible beyond per-bus-access events.

## Design Decision: `tracing` crate

Use the `tracing` ecosystem (`tracing` + `tracing-subscriber`) rather than
`log` + `env_logger`. Rationale:

- **Compile-time elimination.** `tracing` supports `release_max_level_*`
  features that make disabled levels expand to nothing — not even a branch.
  This is critical for a cycle-accurate emulator where the decode-execute
  loop runs millions of iterations/sec.
- **Structured fields.** `trace!(addr = %addr, val = %val, core = core)`
  produces machine-parseable output without manual `format!` strings.
- **Spans.** Useful for future profiling — wrapping `step()` in a span
  gives hierarchical timing for free.
- **Ecosystem compatibility.** `tracing` is the de facto standard in the
  Rust ecosystem; `log` is legacy.

### Overhead guarantee

The cap is set on binary-producing crates only. Library crates take
`tracing = { workspace = true }` with no features; binary crates
(`picoem-harness`, `rp2350-emu-tui`, `rp2040-emu-tui`) take
`tracing = { workspace = true, features = ["release_max_level_info"] }`.
Cargo unifies features down the dep graph, so when `picoem-harness` is
built, `rp2350-emu` and `picoem-common` are compiled with the cap on too —
the in-workspace zero-overhead guarantee still holds. External consumers
of our libraries get a plain `tracing` and choose their own cap (or none).

This means:
- `trace!()` and `debug!()` compile to **zero code** in `--release` builds
  of our binaries. Not a disabled branch — literally nothing. The macro
  expands to `{}`.
- `info!()`, `warn!()`, `error!()` remain active in release, but these are
  only placed on cold paths (startup, config changes, errors).
- In debug builds, all levels are active and can be filtered at runtime via
  `RUST_LOG`.

The harness and app crates will use `tracing-subscriber` with `env_filter`
for runtime level control.

## Crate-by-crate plan

### Tier 1 — Library crates (zero release overhead)

#### `mdpicoem-common`

Currently clean (no diagnostics). Add `tracing` dependency but only
instrument if/when we add code that benefits from it. No work needed now.

```toml
tracing = { workspace = true }
```

#### `mdrp2350`

**Bus MMIO trace migration.** The existing `trace_enabled` / `emit_trace`
system in `bus/mod.rs` is well-optimised but bespoke. Two options:

- **Option A — Keep bespoke, layer tracing alongside.** The MMIO trace has
  a specific wire format (`TRACE R/W size addr val=... core=N pc=...`) that
  downstream tools parse. Converting it to `tracing` would change the output
  format and break `mmio_trace_rp2350` consumers. Keep `emit_trace` for the
  MMIO wire format; add `tracing` for new instrumentation points.

- **Option B — Replace with a custom `tracing` subscriber layer.** Write a
  `tracing_subscriber::Layer` that formats MMIO events in the existing wire
  format when a specific target is matched. More unified, but more work for
  no immediate payoff.

**Recommendation: Option A.** The MMIO trace is a specialised protocol, not
general logging. Keep it. Add `tracing` instrumentation at these points:

| Location | Level | Fields | Purpose |
|----------|-------|--------|---------|
| `core/exceptions.rs` — exception entry | `debug!` | `exception_num, priority, pc, lr` | Debug exception dispatch issues |
| `core/exceptions.rs` — exception return | `debug!` | `exc_return, restored_pc` | Debug exception unwinding |
| `core/mod.rs` — HardFault escalation | `warn!` | `fault_type, pc, addr` | Always visible — indicates emulation problem |
| `bus/mod.rs` — unmapped address access | `debug!` | `addr, rw, size` | Debug bus decode misses |
| `bus/clocks.rs` — clock tree recompute | `debug!` | `sys_clk, ref_clk, peri_clk` | Debug clock reprogramming |
| `sio/` — spinlock acquire/release | `trace!` | `lock_id, core` | Debug multicore contention |
| `pio.rs` — SM enable/disable | `debug!` | `sm_id, enabled, pc` | Debug PIO bring-up |
| `lib.rs` — emulator construction | `info!` | `rom_size, sram_size, flash_size` | Startup config |
| `peripherals/` — DMA channel start | `debug!` | `ch, src, dst, count, size` | Debug DMA transfers |
| `peripherals/` — peripheral init | `debug!` | `peripheral_name, base_addr` | Debug peripheral setup |

#### `mdrp2040`

Same approach as mdrp2350. The historical stray `eprintln!` calls in DMA,
PIO TXF, and RESETS paths have already been cleaned up — no immediate
fixups needed. Instrument the same categories as mdrp2350 (exceptions, bus
faults, clock tree, SIO, PIO). mdrp2040 also has its own bespoke
`trace_enabled` / `emit_trace` system on `Bus` (same pattern as mdrp2350);
keep that for MMIO wire-format tracing.

### Tier 2 — App crates (subscriber init)

#### `mdrp2350app` / `mdrp2040app`

Add `tracing-subscriber` with `EnvFilter`:

```rust
tracing_subscriber::fmt()
    .with_env_filter(
        tracing_subscriber::EnvFilter::from_default_env()
    )
    .with_writer(std::io::stderr)  // TUI owns stdout
    .init();
```

This gives runtime control via `RUST_LOG`:
```bash
RUST_LOG=mdrp2350::bus=debug ./mdrp2350app
RUST_LOG=mdrp2040::core::exceptions=debug ./mdrp2040app
```

The existing 2 `eprintln!` calls (sim thread panic reporting) stay as-is —
these fire after the subscriber may have been torn down.

#### `mdpicoem-harness` binaries

Add `tracing-subscriber` init to each binary's `main()`. The structured
PASS/FAIL/DIFF output that harnesses produce is **not** logging — it's
program output. Keep that as `println!`. Add `tracing` for:

- Harness infrastructure diagnostics (probe connection, QEMU spawn, GDB
  handshake)
- Per-test-case progress at `info!` level (replaces ad-hoc progress
  `println!`)
- Error context at `warn!`/`error!` level

### Tier 3 — Not instrumented

#### `mdpicoem-debug`

Stub crate. Add `tracing` dependency when GDB RSP is implemented.

## Dependency additions

```toml
# Workspace Cargo.toml [workspace.dependencies]
# Plain tracing here — the release_max_level_info cap is binary-only.
tracing = { version = "0.1" }
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
```

```toml
# Library crates (rp2350-emu, rp2040-emu, picoem-common, picoem-devices)
[dependencies]
tracing = { workspace = true }

# Binary-producing crates (picoem-harness, rp2350-emu-tui, rp2040-emu-tui)
# Feature unification propagates the cap down to our libs at link time.
[dependencies]
tracing = { workspace = true, features = ["release_max_level_info"] }
tracing-subscriber = { workspace = true }
```

## What NOT to instrument

- **Instruction decode/execute hot path.** Do not add `trace!` inside
  `execute.rs`, `execute_thumb32.rs`, `execute_fpu.rs`, `decode.rs`, or
  `execute_wide.rs`. Even with compile-time elimination in release, debug
  builds would become unusably slow. These paths are already covered by the
  QEMU/silicon differential oracles — if an instruction is wrong, the oracle
  catches it.

- **Per-cycle bus dispatch.** The existing `trace_enabled` gate on
  `emit_trace` is purpose-built for MMIO tracing with a specific wire
  format. Don't duplicate it with `tracing`.

- **Test assertions.** `eprintln!` inside `#[test]` functions is fine — test
  output is already captured by the test harness and only shown on failure.
  No need to convert these.

- **Harness structured output.** The PASS/FAIL tables, DIFF lines, progress
  counters, and markdown reports in harness binaries are **program output**,
  not logging. They stay as `println!`/`eprintln!`.

## Level guide

| Level | Use for | Release build |
|-------|---------|---------------|
| `error!` | Emulation-breaking conditions (unrecoverable faults, internal invariant violations) | Active |
| `warn!` | Suspicious but non-fatal (HardFault escalation, unmapped access that firmware might intend, clock config that looks wrong) | Active |
| `info!` | One-time lifecycle events (emulator init, firmware loaded, clock tree configured) | Active |
| `debug!` | Subsystem-level events (exception entry/return, DMA transfer, PIO enable, peripheral reset, clock reprogram) | **Stripped** |
| `trace!` | High-frequency events (spinlock acquire/release, SIO FIFO push/pop, PIO instruction step) | **Stripped** |

## Implementation order

1. **Add workspace dependencies** to `Cargo.toml`. Add
   `[workspace.dependencies]` section (doesn't exist yet).
2. **Rename bespoke MMIO trace** from `trace_enabled` / `emit_trace` /
   `trace_sink` to `mmio_trace_enabled` / `emit_mmio_trace` /
   `mmio_trace_sink` in both `mdrp2350::bus` and `mdrp2040::bus`. Update
   all call sites, tests, and harness binaries that reference these.
3. **Instrument mdrp2350 and mdrp2040 cold paths.** Exception entry/return,
   clock tree recompute, bus faults. These are the places agents most
   frequently re-instrument during debugging.
4. **Add subscriber init.** Create a shared `harness_tracing_init()`
   function in `mdpicoem-harness` (avoids duplicating the one-liner across
   20+ binaries). Add stderr-based init to TUI apps.
5. **Update CLAUDE.md** with the Logging & Tracing section.
6. **Instrument remaining subsystems** (SIO, PIO, DMA, peripherals) as
   those areas are worked on — don't bulk-instrument everything at once.

Add a section to the project CLAUDE.md instructing agents to use `tracing`
instead of ad-hoc `eprintln!`:

```markdown
## Logging & Tracing

Use the `tracing` crate for all diagnostic output in library crates. Never
add raw `eprintln!` or `println!` for debugging — use the appropriate
tracing level instead.

### Level guide
- `error!` — emulation-breaking conditions
- `warn!` — suspicious but non-fatal (HardFault escalation, unmapped access)
- `info!` — one-time lifecycle events (init, firmware load, clock config)
- `debug!` — subsystem events (exception entry/return, DMA, PIO, clock reprogram)
- `trace!` — high-frequency events (spinlock ops, FIFO ops, PIO instruction step)

### What NOT to trace
- Instruction decode/execute hot path (`execute.rs`, `decode.rs`) — use

- The MMIO bus trace (`emit_trace`) — this is a purpose-built wire-format
  trace, not general logging
- Harness structured output (PASS/FAIL, DIFF lines) — this is program
  output, not logging
- Test-only `eprintln!` inside `#[test]` — test runner captures this

### Zero overhead guarantee

`release_max_level_info`. Cargo's feature unification propagates the cap
down to our libraries when they're built into those binaries, so `trace!`
and `debug!` compile to nothing in `--release`. The cap is *not* set on

Set `RUST_LOG` to control output at runtime:

    RUST_LOG=mdrp2040::core::exceptions=debug cargo run -p mdrp2040app
```

## Naming collision: `trace_enabled` vs `tracing`

Both emulator crates have a `Bus::trace_enabled` bool and `emit_trace()`
method for MMIO wire-format tracing. Introducing the `tracing` crate adds
a `trace!` macro at the same conceptual name.

This is a documentation problem, not a code problem — Rust's module system
keeps them unambiguous (`self.trace_enabled` vs `tracing::trace!()`). But
for humans reading the code, the overloaded "trace" is confusing.

**Decision**: Rename the bespoke system to `mmio_trace_enabled` /
`emit_mmio_trace` / `mmio_trace_sink` / `set_mmio_trace_sink` as part of
step 1. This is a crate-internal rename (the field is `pub` but
`pub(crate)` for the sink setter) so the blast radius is small. Update
MMIO trace harness binaries (`mmio_trace_rp2350`, `mmio_trace_rp2040`) and
tests that reference the old names.

## TUI subscriber: stderr is mandatory

The TUI apps (`mdrp2350app`, `mdrp2040app`) use `crossterm` with
`EnterAlternateScreen` on stdout. Any `tracing` output to stdout will
corrupt the terminal. The subscriber **must** route to stderr:

```rust
.with_writer(std::io::stderr)
```

Additionally: when the TUI's raw mode is active, stderr lines won't be
visible in the terminal anyway. Practical options for TUI debugging:

- **File sink**: `RUST_LOG_FILE=emu.log` environment variable + a custom
  subscriber layer that writes to a file. This is the most useful for TUI
  debugging — tail the log file in another terminal.
- **Post-exit dump**: Collect events during execution, dump to stderr after
  `LeaveAlternateScreen`. Only useful for short sessions.

**Decision**: Start with stderr. Add a file-sink option later if TUI
debugging proves painful.

## Debug build performance

With `release_max_level_info`, debug builds have all five levels active.
The `trace!` and `debug!` sites we're adding are on cold paths (exception
entry, clock reprogram, bus fault) so they won't tank debug-build perf.
But the "What NOT to instrument" section is load-bearing — if someone adds
`trace!` inside the decode loop in a debug build, performance will crater.
The CLAUDE.md section must be clear about this.

## `panic = "abort"` interaction

The workspace uses `panic = "abort"` in release. This is fine — `tracing`
doesn't rely on unwinding. No issue.

## No subscriber = silent

If a library crate emits `tracing` events but no binary initialises a
subscriber, the events are silently dropped (no-op global dispatcher).
This is correct behaviour — library crates should never initialise a
subscriber. But it means: if someone runs a harness binary and forgets to
add subscriber init, they'll see nothing. The implementation step for
harness binaries should add a one-liner `tracing_subscriber` init to a
shared `harness_init()` function rather than duplicating it in 20+ `main()`
functions.

## Risk assessment

- **Performance**: Zero risk in release builds (compile-time elimination).
  Debug builds will be slightly slower when tracing is enabled, but only
  on cold paths — controllable via `RUST_LOG` (default is off when no
  subscriber is installed, or `RUST_LOG=off`).
- **Dependency weight**: `tracing` is ~40 KB compiled; `tracing-subscriber`
  is larger but only in app/harness crates (not the emulator library).
- **Migration risk**: Low — this is additive. Existing `emit_mmio_trace`
  stays (renamed), existing harness output stays.
- **Format stability**: The MMIO trace wire format is preserved (Option A).
  Downstream tools are unaffected.
- **Naming confusion**: Mitigated by the `mmio_trace_*` rename.
