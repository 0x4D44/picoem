# Mutation Testing V1

Version: 1.1.0
Date: 2026-04-26

## Problem

We have strong differential oracles (QEMU diff, probe-rs silicon diff, OneROM,
PicoGUS) and a recent unit-test coverage push to ~98% line coverage. Coverage
tells us *what code ran*, not *whether the tests would notice if the code were
wrong*. We don't know:

- Are there decode/execute arms that the unit tests reach but no oracle would
  flag if their semantics silently changed?
- Are the QEMU and silicon oracles' instruction-class generators dense enough
  to catch off-by-one flag, shift, or carry mutations on every encoding?

A mutation tester answers these by literally breaking the code and watching
which broken versions slip past the suite. Surviving mutants point at gaps
the existing oracles can't see.

## Goal

Run `cargo-mutants` against the M33 and M0+ instruction decode/execute paths,
produce a list of surviving mutants, and triage them. Use the result to decide
whether further oracle/test investment is worthwhile.

That's it. This is a measurement exercise, not a process change.

## Non-goals

- Workspace-wide mutation testing. The harness, peripherals, bus, DMA, SIO,
  PIO, and apps are out of scope for V1. Decide on those later if the V1
  result is informative.
- CI integration. Mutation runs are slow (overnight class) and this is a dev
  sandbox.
- Custom mutation operators. Stock `cargo-mutants` is enough.
- Wiring the QEMU/silicon oracles in as the test command for cargo-mutants.
  Unit tests are the first-pass filter; oracle integration is a conditional
  follow-up gated on V1 results (see "Follow-up" below).
- Any new feature flag, env var, or build mode.

## Tool

[`cargo-mutants`](https://mutants.rs/). Stock invocation, no plugins. Install
with `cargo install cargo-mutants` (host-local; not added to any manifest).

How it works: parses the target file with `syn`, generates one mutant per
mutable construct (replace `+` with `-`, return `Default::default()`, flip
boolean operators, etc.), copies the workspace to a scratch directory, applies
the patch, and runs the configured test command. A mutant is "caught" if a
test fails, "missed" if all tests still pass, "timeout" if it hangs.

## Scope (V1)

Two crates, seven files, 6170 LOC total:

| File | LOC |
|---|---|
| `crates/mdrp2350/src/core/decode.rs` | 569 |
| `crates/mdrp2350/src/core/execute.rs` | 892 |
| `crates/mdrp2350/src/core/execute_thumb32.rs` | 1872 |
| `crates/mdrp2350/src/core/execute_fpu.rs` | 1517 |
| `crates/mdrp2040/src/core/decode.rs` | 110 |
| `crates/mdrp2040/src/core/execute.rs` | 979 |
| `crates/mdrp2040/src/core/execute_wide.rs` | 231 |

These are the hot paths the differential oracles are designed to validate.
If mutants survive *here*, that's the most actionable signal we can get.

`exceptions.rs` and `coprocessor.rs` are deliberately excluded from V1. They
are validated by `silicon_isr_diff_*` and the coprocessor unit tests, both
of which are slower or harder to run as `cargo test`. Add them if V1 looks
worthwhile.

## Configuration

One file at the repo root: `.cargo/mutants.toml`.

```toml
# Files cargo-mutants is allowed to mutate.
examine_globs = [
    "crates/mdrp2350/src/core/decode.rs",
    "crates/mdrp2350/src/core/execute.rs",
    "crates/mdrp2350/src/core/execute_thumb32.rs",
    "crates/mdrp2350/src/core/execute_fpu.rs",
    "crates/mdrp2040/src/core/decode.rs",
    "crates/mdrp2040/src/core/execute.rs",
    "crates/mdrp2040/src/core/execute_wide.rs",
]

# Some emulator unit tests are deliberately tight loops; give them headroom.
timeout_multiplier = 5.0

# Restrict cargo invocations to the two chip crates. Critically, this keeps
# probe-rs (only used by the harness) out of the per-mutant build graph.
# NOTE: confirm the field name against the installed cargo-mutants version
# before kicking off the full run — it has historically been one of
# `additional_cargo_args`, `test_package`, or `test_packages`. Verify with
# `cargo mutants --help` and a single-file calibration run (see below).
test_package = ["mdrp2350", "mdrp2040"]
```

Plus one line in `.gitignore`:

```
mutants.out/
```

And one dev-dep in each chip crate's `Cargo.toml`, only needed if any
`#[mutants::skip]` annotations are added during triage:

```toml
[dev-dependencies]
mutants = "0.0.3"   # empty marker crate; defines the skip attribute
```

Don't add this dev-dep up front. Add it only when triage produces the first
real candidate for `#[mutants::skip]`.

That is the entire footprint in the source tree. No driver scripts, no env
vars, no Makefile target. Run it with the standard CLI:

```bash
# Full V1 sweep (overnight class).
cargo mutants

# Single-file dry-run while iterating on the config.
cargo mutants --file crates/mdrp2350/src/core/decode.rs --no-shuffle

# Re-run only previously-missed mutants after fixing tests.
cargo mutants --in-place --iterate
```

## Test runner

`cargo test -p mdrp2350 -p mdrp2040`, restricted via the `test_package` config
above. Rationale:

- These crates already contain ~98%-coverage unit tests covering instruction
  semantics, decode edge cases, and exception mechanics.
- They have no external dependencies (no QEMU, no probe, no GDB ports).
- Neither crate depends on `probe-rs`, so the patched workspace probe-rs fork
  stays out of the per-mutant build graph entirely. This is the dominant
  win on per-mutant cost — a workspace-wide build pulls probe-rs and its
  `object`/`gimli` transitive tree, easily 5-10× heavier than chip-crates
  alone.

Note that `cargo test -p mdrp2350` runs **both** the in-crate unit tests
**and** the integration tests under `crates/mdrp2350/tests/` (`hello_dma`,
`hello_pwm`, `hello_riscv_blinky`, `hello_timer`, `hello_uart`, `lazy_fp`,
`dual_model`). The integration tests load real firmware and execute cycles;
they are slow but they are also exactly the kind of test that catches a
broken `execute.rs`. Same shape for mdrp2040 (`firmware`, `multicore`,
`smoke`, `dual_model`).

V1 keeps the integration tests in. If calibration shows per-mutant time is
unacceptable, fall back to `cargo mutants -- --lib` (or equivalent
`additional_cargo_args = ["--lib"]`) to scope to library tests only. That
choice should be deliberate, not silent.

The QEMU and silicon oracles are deliberately *not* the test runner. They are
the next line of defence: any mutant that survives the unit + integration
tests is a candidate for "is this actually caught by the differential oracle,
or is this a real gap?". That triage is manual in V1 (see below).

## Triage process

After a run, `mutants.out/missed.txt` lists the surviving mutants by file,
line, and patch text. For each survivor, classify into one of four buckets:

1. **Real test gap** — the unit tests should catch this; they don't.
   Action: write the missing unit test.
2. **Real oracle gap** — the unit tests can't reasonably catch this, but the
   QEMU or silicon oracle should and doesn't (e.g. an obscure flag bit that
   the instruction-class generator never sets). Action: extend the oracle's
   class table or generator.
3. **Caught by oracle, missed by unit tests** — manually patch the mutant,
   run the relevant fuzz oracle for ~5k iterations, confirm catch.
   Action: note this in the triage doc but don't necessarily add a unit test.
   The oracle is doing its job; the mutant survives only because oracles
   aren't the test runner.
4. **Equivalent or unreachable** — the mutation is semantically equivalent
   (e.g. a redundant bounds check) or sits in a code path no oracle can
   exercise. Action: annotate the source with `#[mutants::skip]` and a
   one-line comment explaining why.

Triage output: a single follow-up document
`wrk_docs/YYYY.MM.DD - HLD - Mutation Testing V1 Triage.md` listing the
survivor count by bucket and any concrete test/oracle changes proposed. We
stop at "list and propose"; actually implementing the changes is separate
work to be sized once the list exists.

## Preconditions

Before kicking off any cargo-mutants run:

1. **Baseline must be green.** cargo-mutants runs the unmodified test command
   first; if it fails, the entire run aborts. Confirm with
   `cargo test -p mdrp2350 -p mdrp2040` immediately before launch.
2. **Workspace `target/` should be warm.** A cold per-mutant build adds
   ~1-3 minutes of dep compilation. Warm `target/` brings per-mutant cost
   down by an order of magnitude. Run `cargo test -p mdrp2350 -p mdrp2040`
   once before launching cargo-mutants — this also serves as (1).
3. **Confirm the cargo-mutants config field name** by running
   `cargo mutants --help` and checking the project README pinned to the
   installed version. The config schema has churned across releases. The
   calibration step below catches this.
4. **Free disk space.** With `--jobs N`, cargo-mutants creates N parallel
   scratch trees, each containing a per-mutant `target/`. On Windows NTFS
   there is no reflink, so each is a full file copy. Plan for ~5-10 GB
   per worker once compilation populates each scratch — `--jobs 8` can
   peak in the 40-80 GB range.

## Calibration step (single file, before the full sweep)

Don't go straight to a 7-file overnight run. Run cargo-mutants on
`crates/mdrp2040/src/core/decode.rs` first — it's only 110 LOC, will
generate a tractable handful of mutants, and validates the entire pipeline:

```bash
cargo mutants --file crates/mdrp2040/src/core/decode.rs --no-shuffle
```

This run answers four questions with concrete data, in under an hour:

- Is the `.cargo/mutants.toml` config syntactically valid and applied?
- Is the baseline `cargo test -p mdrp2350 -p mdrp2040` green?
- What is the real per-mutant wall-clock on this host?
- Are there obvious systemic issues (timeouts, infinite loops, flaky tests)?

Multiply the measured per-mutant time by ~2000 and divide by your chosen
`--jobs` to project the full-sweep wall-clock. Only after that number is
within an acceptable window do we commit to the full run.

## Expected cost and runtime

Realistic estimate (to be replaced with calibration numbers before the
full run):

- **Mutant count.** cargo-mutants typically produces 0.3-0.5 mutants per
  LOC of mutable code. For 6170 LOC of mostly-mutable decode/execute
  logic, expect 1500-3000 mutants.
- **Per-mutant cost.** With probe-rs out of the dep graph (constrained by
  `test_package`) and a warm baseline `target/`, an incremental
  `cargo test -p mdrp2350 -p mdrp2040` on this workspace runs in roughly
  30-90 s — depending heavily on whether the `hello_*` integration tests
  fire (they load real firmware and run thousands of cycles). Plan
  60-180 s per mutant including the per-mutant `cargo check` baseline.
- **Wall-clock.** 1500-3000 mutants × 60-180 s ÷ `--jobs 8` ≈ 3-19 hours
  on a multi-core host. Single overnight is the right framing, but the
  spread is wide. Calibration tightens this.

`--shard` is available for splitting across multiple hosts:

```bash
cargo mutants --shard 0/4   # run on 4 hosts in parallel, this is shard 0
```

V1 does not require sharding.

## Risks

- **Compute time underestimate.** If the run blows past a single overnight
  window, scope down to one file at a time (`--file`) and decide which to
  prioritise from partial results. This is a measurement, not a deadline.
- **Disk pressure on Windows NTFS.** No reflinks, so each parallel scratch
  is a full file copy plus its own `target/`. Watch free space during the
  first parallel run; lower `--jobs` if it tightens. Scratch dir defaults
  under `target/mutants.out.tmp/`, gitignored via `target/`.
- **Flaky tests caught as mutants.** Any test that is timing-sensitive or
  has hidden ordering will show up as a "caught" mutant for the wrong
  reason. We have no known flakies in the chip-crate unit tests today; if
  one surfaces during the run, mark it and move on.
- **Integration tests in `tests/` slow per-mutant time more than expected.**
  If calibration shows per-mutant cost is dominated by `hello_*`/`firmware`
  tests rather than the unit tests, fall back to `--lib` and accept the
  weaker signal — see "Test runner" above.
- **Equivalent-mutant noise.** Real mutation testing always produces some
  fraction of equivalent mutants. The triage process handles them via
  `#[mutants::skip]`. Don't try to eliminate them ahead of time.
- **Config schema drift in cargo-mutants.** Field names have churned across
  releases. The calibration step exists specifically to catch this on a
  small file before committing to an overnight run.

## Acceptance criteria

V1 is done when:

1. `.cargo/mutants.toml` and the `.gitignore` entry are committed.
2. A full sweep has run to completion (or has been deliberately scoped down
   if compute was the binding constraint).
3. `mutants.out/missed.txt` exists and has been triaged into the four
   buckets above.
4. The triage HLD is written, listing concrete proposed test/oracle changes
   (or stating that the survivor list is empty / dominated by equivalents).

## Follow-up (conditional on V1 results)

Decide *after* V1, not now. The branches:

- **Survivor list is dominated by bucket 3 (oracle catches, tests don't).**
  Build a small "second-pass" runner: take `missed.txt`, apply each patch
  in turn, run `qemu_diff_m33 --fuzz 5000` (or `_m0plus`), and report
  whether the oracle caught it. This gives us a second mutation-survival
  number against the strongest oracle without paying QEMU costs on every
  mutant. Sized as a half-day script.
- **Survivor list is dominated by buckets 1 and 2.** Just write the missing
  tests / extend the generators. No new infra.
- **Survivor list is small or empty.** Expand scope to `exceptions.rs`,
  `coprocessor.rs`, and the bus/peripheral code in a V2 HLD.

We will pick exactly one of those after the triage doc lands.
