# HLD — OneROM CPU Serial Speed-Grade Oracle (V2)

**Date**: 2026-04-23
**Status**: Proposed
**Author**: Arthur + Claude Opus 4.7 (1M)
**Supersedes**: V1 (same date) — V1 reinvented machinery that
`CpuServingOracle::run_case()` already provides, proposed a wrong
ladder band, and proposed unnecessary multi-sweep + shuffle.

## 1. Motivation

The threaded speed-grade oracle (`onerom_cpu_speed_grade_rp2350`, commit
`61f5204`) measures wall-clock stim-to-sample round-trip across a
ladder of target latencies. At `--step-quantum 1024` its clean
inflection sits at ~500 ns wall-clock — well above the ~90 ns
real-silicon OneROM CPU access time.

Investigation (2026-04-23 journal) showed the ~5–6× gap is host-side
overhead, not emulator-correctness:

- Barrier true-sharing on the 5-party arrival counter (~300–450 ns per
  quantum, even amortized).
- Cross-core atomic coherency on GPIO (~100 ns).
- Windows scheduler jitter surviving TIME_CRITICAL + affinity.

The emulator's actual serve path is already ~13 cycles per byte —
`onerom_stress_cpu_rp2350` reports p50 60 ns, mean 80 ns at 150 MHz
emulated. That matches silicon. We just can't *measure* it via
wall-clock on a multi-threaded host.

**Gap**: a speed-grade oracle that reports **per-rung verdicts** in
**simulated cycles**, not wall-clock. No barrier, no cross-core
atomics, no driver-thread jitter. This is the honest answer to "does
our emulator serve in cycle-count parity with silicon?".

## 2. Goal

One new binary: **`onerom_cpu_speed_grade_serial_rp2350`**.

- Same walk set as `onerom_stress_cpu_rp2350` (2048 cases, 1541 ROM
  set 0, generated by `onerom_stress::generate_sweep_cases()`).
- Per-case measurement via `CpuServingOracle::run_case()` — reuses all
  the stability / gap-drive / zero-byte-trust machinery that's already
  there.
- Reports per-rung verdict (PASS = all cases served within `N` cycles,
  FAIL = any case over `N` or wedged) for a ladder of thresholds.
- Reports the cycle-latency distribution (min / p50 / mean / p95 /
  max) once via `onerom_stress::compute_histogram()`.

Expected output on the 1541 fixture (based on current envelope
7..=60):

```
   threshold     errors    verdict
      (cy)
         50          0     PASS
         30         14     FAIL
         20         71     FAIL
         13       1142     FAIL
         10       1847     FAIL

cycles across all cases: min=7 p50=12 mean=15 p95=40 max=60
```

## 3. Non-goals

- **No CLI mode-switch on the threaded binary.** Serial oracle is a
  separate binary; measurement semantics differ (cycles vs wall-clock),
  mixing them behind one binary obscures what each answers.
- **No app `--mode serial|threaded` flag.** Larger piece of work (TUI
  state plumbing, lifecycle changes). Separate HLD if/when we want it.
- **No configurable thread topology.** Premature optimization.
- **No refactor of existing oracles.** Threaded oracle and stress
  oracle stay exactly as they are.
- **No universal `trait DynEmulator` abstraction.** Speculative.
- **No multi-sweep, no shuffling.** Serial is deterministic — repeated
  sweeps add no statistical signal. One pass, one report.
- **No extension of `SweepReport`.** That type belongs to the threaded
  oracle's library; serial oracle has its own (smaller) reporting
  struct.

## 4. Design

### 4.1 Binary layout

```
crates/mdpicoem-harness/src/bin/onerom_cpu_speed_grade_serial_rp2350.rs
```

Windows/Unix-agnostic. No host-priority shims, no affinity, no driver
thread, no watchdog. Just `main` → boot-sync → walk → report.

Reuses:
- `onerom_serving_oracle_cpu::{CpuServingOracle, CpuVerdict}` — the
  per-case measurement (`run_case`) and verdict enum.
- `onerom_serving_oracle::CaseResult` — histogram-compatible result
  shape.
- `onerom_stress::{generate_sweep_cases, compute_histogram, Histogram}`
  — walk plan + distribution stats.
- `onerom_cpu_speed_grade_rp2350`'s `boot_sync` helper pattern (not
  the library type) — read fixture, create `Emulator`, sync to
  serve-loop PC, force ROM set 0 via `force_rom_set_index_via_sel_pins`.

### 4.2 Measurement loop

```rust
let mut emu = boot_sync(&bootrom, &flash)?;
let mut oracle = CpuServingOracle::new_at_sync(&mut emu.bus, &flash);
let cases = onerom_stress::generate_sweep_cases();

let mut latencies: Vec<u32> = Vec::with_capacity(cases.len());
let mut wedged: Vec<&Case> = Vec::new();

for case in &cases {
    let result = oracle.run_case(&mut emu, *case);
    match result.latency_cycles {
        Some(cy) => latencies.push(cy),
        None => wedged.push(case),
    }
}
```

All stability, gap-drive, OEN tracking, and zero-byte-trust handling
happens inside `run_case`. The binary is thin.

### 4.3 Wedged-case handling

`CpuServingOracle::run_case` returns `latency_cycles: None` when the
per-case `PER_CASE_TIMEOUT = 400` cycle budget elapsed without a
`Stable` decision — i.e. verdict is `DataPinsNotDriven`,
`NoStableByte`, or `WrongByte` (wrong byte has `latency_cycles: Some`
actually — only the "no measurement possible" outcomes produce None).

For the ladder oracle, wedged cases count as FAIL at **every** rung
(including the top one). Makes sense: no measurement = can't prove it
met any threshold.

```rust
for &rung_cy in &ladder {
    let served_in_rung = latencies.iter().filter(|&&cy| cy <= rung_cy).count();
    let errors = cases.len() - served_in_rung;  // includes wedged
    print_rung(rung_cy, errors);
}
```

### 4.4 Ladder

Entries are cycle-count thresholds. Default:

```rust
const DEFAULT_CYCLE_LADDER: &[u32] = &[50, 30, 20, 13, 10];
```

Band chosen to cover the observed envelope `CPU_ENVELOPE_CYCLES =
7..=60`:
- **50** — top of envelope minus slack; should PASS, validates oracle
  is calibrated.
- **30** — above p95 (~40 cycles); some tail misses.
- **20** — around p90.
- **13** — the silicon-claim floor (90 ns @ 150 MHz = 13 cycles).
  This is the interesting rung.
- **10** — below silicon; tests how much of the distribution sits at
  or below best-case.

If the distribution shifts (different fixture, emulator regression),
the default still gives a readable shape.

### 4.5 CLI

```
onerom_cpu_speed_grade_serial_rp2350
  --ladder <csv>     Cycle thresholds, strictly decreasing
                     (default 50,30,20,13,10)
  --all-rungs        Report every rung (default: stop at first FAIL)
  --help
```

No `--seed` (serial is deterministic, no shuffle, no sampling).
No `--sweeps-per-threshold` (one sweep = full data).
No `--mode`, no `--step-quantum`, no `--host-core`.

### 4.6 Report format

```
OneROM CPU Serial Speed-Grade Oracle — 1541 $E000 kernal (ROM set 0)
fixture:  crates/mdpicoem-harness/fixtures/onerom-fire-24-a-rp2350-1541-cpu.bin
cases:    2048 (full address sweep, A11=A12=1)

   threshold     errors    verdict
      (cy)

         50          0     PASS
         30         14     FAIL
         20         71     FAIL
         13       1142     FAIL
         10       1847     FAIL

cycles across all cases: min=7 p50=12 mean=15 p95=40 max=60
wedged:                   0 (cases with no latency_cycles measurable)

elapsed: 0.4 s wall-clock
```

Exit code: `SUCCESS` if the top rung passed, `FAILURE` otherwise. (The
default "stop at first FAIL" with top rung = 50 cycles should always
PASS unless the emulator regresses.)

## 5. Library changes

**None required.** All plumbing reused from existing modules:

| Need | Source | Kind |
|---|---|---|
| Per-case measurement | `CpuServingOracle::run_case` | Existing |
| Walk plan | `onerom_stress::generate_sweep_cases` | Existing |
| Distribution stats | `onerom_stress::compute_histogram` | Existing |
| CpuCaseResult → CaseResult adapter | `cpu_to_pio_result` in stress binary | Copy |
| Boot sync + ROM-set forcing | Inline helpers in speed-grade binary | Copy |

The "ladder reporting" is 20 lines of local helper:

```rust
fn print_ladder(latencies: &[u32], wedged: u32, cases: usize, ladder: &[u32]) {
    for &rung in ladder {
        let served = latencies.iter().filter(|&&cy| cy <= rung).count();
        let errors = cases - served;
        let verdict = if errors == 0 { "PASS" } else { "FAIL" };
        println!("{:>10}  {:>8}    {}", rung, errors, verdict);
    }
}
```

Lives in the binary, not a library module. One-off, not worth extracting.

## 6. Correctness validation

Three checks before declaring the binary working:

1. **Cross-oracle cycle-count parity.** Our serial oracle's
   `compute_histogram` output should match `onerom_stress_cpu_rp2350`'s
   exactly — same cases, same measurement, same `CpuServingOracle`.
   If they disagree, something is off (fixture drift, different
   `Case` ordering, etc.).

2. **Top rung passes on golden fixture.** With default ladder
   `[50, 30, 20, 13, 10]`, the 50-cycle rung must PASS (0 errors) on
   the 1541 ROM set 0 fixture. Anything else is either a fixture
   mismatch (wrong ROM baked) or a `CpuServingOracle` regression.

3. **Throughput sanity.** 2048 cases × ~100 cycles each (gap + serve
   + stability checks) ≈ 200 K emulated cycles. At serial ~232 MHz,
   ~0.9 ms of emulation + Rust overhead. Total expected elapsed
   ≤ 500 ms. If it takes multiple seconds, something's wrong.

## 8. What this unlocks

- Clear silicon-comparable answer to "does our emulator serve in ~13
  cycles per byte?" — decoupled from host-threading overhead.
- A pattern for future serial-mode oracles (PIO serve-path cycle
  oracle next if we want one).
- Precedent for "two binaries, one question each" when measurement
  semantics differ — cleaner than dual-mode binaries with overloaded
  flags.

## 9. Known edge cases

Documented behaviors the binary inherits from `CpuServingOracle`, not
bugs to fix:

- **Wedged cases (≤ handful on golden fixture)** — cases where the CPU
  doesn't produce a stable OEN-driven byte within 400 cycles. Mapped
  to FAIL at every rung. Tracked separately in the report.
- **Zero-byte fallback** — `ZERO_BYTE_TRUST_TIMEOUT_CPU = 40`. When
  the expected byte is 0x00 and the CPU was already driving 0x00
  before the stim (no visible transition), the oracle accepts the
  steady 0x00 after 40 ticks. Inflates the apparent `latency_cycles`
  for those cases; they tend to sit in the 40–50 cycle bucket.
- **`MIN_FRESH_ARRIVAL_CYCLE_CPU = 6`** — rejects matches before 6
  cycles. Our 10-cycle bottom rung will always show errors from cases
  served at exactly 7–9 cycles being accepted (good — they're real).

## 10. Open questions

- **Dropped** invented measurement loop (§4.2 in V1) — use
  `CpuServingOracle::run_case()`.

  uses `onerom_stress::Histogram` directly.
- **Dropped** multi-sweep + shuffle (`--seed`,
  `--sweeps-per-threshold`) — serial is deterministic, one sweep is
  the data.
- **Fixed** ladder defaults — V1's `[20, 15, 13, 10, 8]` missed the

- **Added** known edge cases (§9) — zero-byte fallback,
